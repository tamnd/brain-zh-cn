 # LeetCode 275，H 指数 II

 ## 问题理解

 这个问题要求我们从排序的引用计数列表中计算研究人员的 h 指数。 输入数组`citations`按非递减顺序排序，这意味着引用计数从最小到最大出现。 

h 指数定义为最大整数`h`使得研究人员至少有`h`论文至少有`h`各引文。 

例如，如果研究人员有引用计数`[0,1,3,5,6]`，那么：

 - 有 3 篇论文至少被引用 3 次，特别是`3,5,6`- 没有 4 篇论文被至少 4 次引用

 因此，h 指数为`3`。 

这个问题的重要细节是数组已经排序。 与可能需要排序的原始 H-Index 问题不同，这里我们可以利用排序来设计对数时间解决方案。 

输入大小可以大到`10^5`，因此低效的二次方法不起作用。 该问题明确需要对数时间算法，这强烈建议采用二分搜索。 

数组保证按升序排序，引用计数为非负整数。 这种保证非常重要，因为二分搜索仅适用于有序数据。 

考虑几个边缘情况很重要：

 - 所有引用计数的数组`0`- 每篇论文都有很高引用的数组
 - 只有一张纸的数组
 - h 索引等于论文总数的数组
 - h 索引所在的数组`0`幼稚的实现很容易犯差一的错误，因为必须仔细处理数组索引和剩余纸张数量之间的关系。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是测试每个可能的值`h`从`0`到`n`。 

对于每位候选人`h`，我们计算有多少篇论文的引用量大于或等于`h`。 如果至少`h`论文满足这个条件，那么`h`是有效的。 

由于数组已排序，因此我们可以扫描它以查找每个候选值。 

这种方法是正确的，因为它直接检查 h-index 的定义。 然而，它的效率很低，因为对于每一个可能的`h`，我们可以扫描整个数组。 

和`n`的可能值`h`直至`n`对每一项工作，总复杂度就变成`O(n^2)`。 

即使稍微优化，仍然不能满足对数时间要求。 

### 最佳二分搜索方法

 关键的观察结果是数组已排序。 

假设我们在索引处`i`在数组中。 由于数组是按升序排序的：

 - 所有元素来自`i`到`n - 1`至少是`citations[i]`- 剩余论文数量为`n - i`如果`citations[i] >= n - i`，那么至少有`n - i`论文至少有`n - i`引文。 

这意味着`n - i`是有效的 h 指数候选者。 

由于条件在排序数组中单调转换，二分搜索可以找到第一个索引，其中：```
citations[i] >= n - i
```一旦我们找到这个位置，答案很简单：```
n - i
```这将时间复杂度降低到`O(log n)`。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(1) | O(1) | 通过扫描论文测试每一个可能的 h 指数 |
 | 最佳| O(log n) | O(1) | O(1) | 对排序数组使用二分搜索 |

 ## 算法演练

 1. 让`n`是论文的数量。 

数组长度很重要，因为如果我们位于索引处`i`，那么正好有`n - i`右侧的论文，包括当前论文。 
2. 初始化二分查找边界。 

放：```
left = 0
right = n - 1
```我们将搜索 h 索引条件成立的第一个索引。 
3. 计算中间索引。 

在每次迭代期间：```
mid = (left + right) // 2
```4. 确定剩余多少张纸。 

由于数组是升序排序的，因此来自的论文`mid`到最后所有人都至少有`citations[mid]`引文。 

此类论文的数量为：```
papers = n - mid
```5. 检查当前位置是否满足h-index条件。 

如果：```
citations[mid] >= papers
```然后我们找到了一个有效的 h 指数候选者。 

然而，可能有一个更早的索引也可以工作并产生更大的 h 索引，因此继续在左侧搜索：```
right = mid - 1
```6. 否则，向右移动。 

如果：```
citations[mid] < papers
```那么当前位置无法产生有效的 h 指数。 

我们需要更大的引用值，因此搜索右半部分：```
left = mid + 1
```7. 二分查找完成后，`left`指向第一个有效索引。 

答案变成：```
n - left
```### 为什么它有效

 二分查找之所以有效，是因为条件是单调的。 

随着指数的增加：

 -`citations[i]`趋于增加
 -`n - i`decreases

 最终，条件：```
citations[i] >= n - i
```从 false 变为 true，之后保持 true。 

二分搜索非常适合有效地定位这个转变点。 

## Python 解决方案```python
from typing import List

class Solution:
    def hIndex(self, citations: List[int]) -> int:
        n = len(citations)

        left = 0
        right = n - 1

        while left <= right:
            mid = (left + right) // 2

            papers_with_at_least_mid_citations = n - mid

            if citations[mid] >= papers_with_at_least_mid_citations:
                right = mid - 1
            else:
                left = mid + 1

        return n - left
```实现首先将数组长度存储在`n`。 该值被重复用于计算从给定索引开始剩余多少篇论文。 

二分搜索边界初始化为`left`和`right`。 在每次迭代期间，计算中间索引。 

表达式：```python
papers_with_at_least_mid_citations = n - mid
```表示索引中存在多少篇论文`mid`到数组的末尾。 

条件：```python
citations[mid] >= papers_with_at_least_mid_citations
```检查这些论文是否满足 h 指数定义。 

如果条件为真，我们继续向左搜索，因为较早的索引可能会产生更大的有效 h 索引。 

如果条件为假，我们向右移动，因为需要更大的引用计数。 

循环终止后，`left`存储第一个有效索引，最终的 h 索引为`n - left`。 

## 解决方案```go
func hIndex(citations []int) int {
	n := len(citations)

	left := 0
	right := n - 1

	for left <= right {
		mid := left + (right-left)/2

		papers := n - mid

		if citations[mid] >= papers {
			right = mid - 1
		} else {
			left = mid + 1
		}
	}

	return n - left
}
```Go 实现遵循与 Python 版本相同的二分搜索逻辑。 

一个小的区别是计算`mid`:```go
mid := left + (right-left)/2
```这种风格避免了整数大小固定的语言中潜在的整数溢出。 虽然溢出不是这个问题的约束问题，但这是 Go 中标准的二分搜索实践。 

Go 切片自然地通过提供数组长度`len(citations)`，并且不需要额外的内存分配。

 ## 边缘情况

 当所有引用计数为零时，就会出现一种重要的边缘情况。 在这种情况下，没有一篇论文能够满足甚至 h 指数为`1`。 有错误的实现可能会错误地返回`1`由于二分查找中的差一错误。 此实现正确返回`0`因为条件`citations[mid] >= n - mid`永远不会成为事实，导致`left`一路移动到`n`。 

另一个重要的情况是每篇论文的引用次数都非常多。 例如，`[10,10,10,10]`应产生 h 指数`4`。 一些不正确的实现在找到有效候选者后过早停止。 该解决方案继续向左搜索以找到第一个有效索引，确保返回最大的 h 索引。 

第三个关键边缘情况是长度为一的数组。 仅凭一篇论文，答案只能是`0`或者`1`。 由于不正确的循环条件或指针更新，二分搜索实现在非常小的数组上经常失败。 此实现自然地处理单元素数组，因为标准二分搜索逻辑仍然正确应用。 

当引用计数恰好等于剩余论文数量时，就会出现另一个微妙的边缘情况。 例如：```
[0,1,3,5,6]
```在索引处`2`，我们有：```
citations[2] = 3
n - 2 = 3
```相等的情况必须算作有效。 使用`>`而不是`>=`会产生错误的答案。 这个实现正确地使用了`>=`，这符合 h 指数的数学定义。
