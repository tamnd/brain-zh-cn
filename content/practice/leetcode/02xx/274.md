 # LeetCode 274，H 索引

 ## 问题理解

 问题给出了一个名为`citations`，其中每个元素代表研究论文获得的引用次数。 每个索引对应一篇论文，该索引的值是该论文被引用的次数。 

我们必须计算研究人员的 **h 指数**。 h 指数定义为最大整数`h`使得研究人员至少有`h`论文至少有`h`各引文。 

这个定义非常重要，因为它结合了生产力和影响力。 论文多但被引用少的研究人员的 h 指数较低。 同样，一位拥有一篇极其著名的论文但其他论文很少的研究人员也可能具有有限的 h 指数。 

例如，考虑：```
[3,0,6,1,5]
```如果我们按降序排列这个数组：```
[6,5,3,1,0]
```我们可以检查有多少篇论文满足 h 指数条件：

 - 至少 1 篇论文至少被引用 1 次
 - 至少 2 篇论文至少被引用 2 次
 - 至少 3 篇论文至少被引用 3 次
 - 不少于 4 篇论文被引用至少 4 次

 所以最大有效值为`3`。 

限制相对较小：

 -`1 <= n <= 5000`-`0 <= citations[i] <= 1000`一个`O(n log n)`对于这些限制，解决方案是完全可以接受的。 然而，该问题还暗示将排序作为一个主题，这表明也可能存在线性时间解决方案。 

一些边缘情况很重要：

 - All citation counts may be zero
 - 引用计数可能远大于论文数量
 - 数组可能已经排序或完全未排序
 - 多篇论文可能具有相同的引用计数
 - There may only be one paper

 在检查候选人是否`h`是有效的。 

## 方法

 ### 蛮力方法

 蛮力方法会尝试所有可能的 h 指数`0`到`n`。 

对于每个候选值`h`，我们计算至少有多少篇论文`h`引文。 如果至少`h`论文满足该条件，那么`h`是有效的。 

例如：```
citations = [3,0,6,1,5]
```测试`h = 3`:

 - 至少被引用 3 次的论文：

 - 3
 - 6
 - 5

 这样的论文一共有 3 篇，所以`h = 3`是有效的。 

测试`h = 4`:

 - 至少被引用 4 次的论文：

 - 6
 - 5

 只有2篇论文满足条件，所以`h = 4`无效。 

这种方法是正确的，因为它直接检查 h-index 的定义。 然而，它的效率很低，因为对于每一个可能的`h`，我们再次扫描整个数组。 

时间复杂度变为`O(n^2)`。 

### 最佳方法

 关键的观察结果是，论文的确切顺序并不重要，重要的是有多少论文的引用计数高于阈值。 

如果我们按降序对数组进行排序，我们就可以一次性确定 h 索引。 

假设排序后的数组为：```
[6,5,3,1,0]
```在索引处`i`，正好有`i + 1`左侧的论文，包括当前论文。 

如果：```
citations[i] >= i + 1
```那么至少有`i + 1`论文至少有`i + 1`引文。 

我们继续下去，直到这个条件不成立。 

这样就将问题转化为排序后的简单扫描。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(1) | O(1) | 尝试每一个可能的 h 索引并每次重新扫描数组 |
 | 最佳| O(n log n) | O(n log n) | O(1) 或 O(n) | 对数组进行排序并扫描一次以查找最大有效 h 索引 |

 ## 算法演练

 ### 最优排序算法

 1. 排序`citations`数组按降序排列。 

我们首先想要被引用最多的论文，因为 h 指数取决于有多少论文超过阈值。 排序可以轻松地直接比较论文计数与引用计数。 
2. 使用索引迭代排序后的数组`i`。 

在位置`i`，正好有`i + 1`到目前为止考虑的论文。 
3. 对于每个位置，检查是否：```
citations[i] >= i + 1
```这意味着当前论文有足够的引用来支持 h 指数`i + 1`。 
4. 如果条件成立，则更新答案。 

我们继续扫描，因为更大的 h 指数仍然是可能的。 
5. 如果条件变为假，则停止检查较大的值。 

由于数组按降序排序，因此所有未来的引用计数将小于或等于。 因此，不可能存在更大的 h 指数。 
6. 返回找到的最大有效 h 指数。 

### 为什么它有效

 按降序排序后，索引处的论文`i`是`(i + 1)`被引用次数最多的论文。 该论文至少有`i + 1`引用，然后是第一个`i + 1`论文均满足h-index条件。 

因为数组是排序的，所以一旦条件失败，后面的每篇论文也会因为 h 值较大而失败。 这保证了扫描期间遇到的最大有效值是正确的 h 索引。 

## Python 解决方案```python
from typing import List

class Solution:
    def hIndex(self, citations: List[int]) -> int:
        citations.sort(reverse=True)

        h_index = 0

        for index, citation_count in enumerate(citations):
            paper_count = index + 1

            if citation_count >= paper_count:
                h_index = paper_count
            else:
                break

        return h_index
```实现首先按降序对引文进行排序。 这确保了被引用最多的论文首先出现。 

变量`h_index`存储迄今为止找到的最佳有效值。 

该循环使用以下方式迭代排序后的论文`enumerate`，它提供索引和引用计数。 每一步：```python
paper_count = index + 1
```这代表已审查了多少篇论文。 

条件：```python
citation_count >= paper_count
```检查是否至少有`paper_count`论文至少有`paper_count`各引文。 

如果满足条件，则可以安全地更新 h 指数。 否则，循环就会中断，因为更多的论文只会有更少的引用计数。 

最后，该方法返回扫描期间发现的最大有效 h 索引。 

## 解决方案```go
package main

import "sort"

func hIndex(citations []int) int {
	sort.Sort(sort.Reverse(sort.IntSlice(citations)))

	hIndex := 0

	for index, citationCount := range citations {
		paperCount := index + 1

		if citationCount >= paperCount {
			hIndex = paperCount
		} else {
			break
		}
	}

	return hIndex
}
```Go 解决方案遵循与 Python 版本相同的算法结构。 

Go 不提供整数切片的直接降序排序，因此实现使用：```go
sort.Sort(sort.Reverse(sort.IntSlice(citations)))
```其余逻辑是相同的。 该循环检查当前引用计数是否支持更大的 h 指数。 

不存在整数溢出问题，因为约束非常小。 Go 切片自然地安全地处理 nil 和空行为，尽管该问题保证至少有一篇论文。

扫描本身是`O(n)`，但排序需要`O(n log n)`时间，它在总体复杂性中占主导地位。 

辅助空间复杂度取决于排序的语言实现。 Python 的排序可能会在内部使用额外的内存，而 Go 的排序实现更接近就地行为。

 ## 边缘情况

 当每篇论文的引用次数为零时，就会出现一个重要的边缘情况，例如：```
[0,0,0]
```有错误的实现可能会错误地返回`1`只是因为至少有一篇论文。 然而，h 指数要求至少一篇论文至少被引用一次。 由于不存在，所以正确答案是`0`。 实现处理这个问题是因为条件：```
citation_count >= paper_count
```第一次迭代时立即失败。 

当引用计数远大于论文数量时，会出现另一个重要情况：```
[100,100,100]
```h指数永远不能超过论文总数。 尽管每篇论文都有 100 次引用，但总共只有 3 篇论文，所以答案一定是`3`。 该实现自然会强制执行此操作，因为最大可能的`paper_count`是`n`。 

第三种边缘情况涉及精确相等：```
[3,3,3]
```h 指数应为`3`， 不是`2`。 一些不正确的实现使用严格的大于比较而不是大于或等于。 正确的条件是：```
citation_count >= paper_count
```它正确处理了平等边界。 

另一个微妙的边缘情况是在扫描中间发生故障时：```
[10,8,2,1]
```一旦条件失败，算法就会正确停止。 由于数组按降序排序，因此后来的论文无法恢复较大 h 索引的有效性。 这保证了正确性并避免了不必要的工作。
