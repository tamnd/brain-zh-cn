 **难度：** 🟡 中等
 **主题：** 数组、设计、迭代器

 ## 解决方案

 ## 问题理解

 该问题要求我们使用额外的功能来扩展标准迭代器的功能`peek`手术。 标准迭代器提供两种操作：`next()`，它返回序列中的下一个元素并前进指针，并且`hasNext()`，它告诉是否还剩下更多元素。 这`PeekingIterator`增强了这个界面`peek()`，它返回下一个元素**而不推进迭代器**。 

输入是整数列表上的迭代器，输出是调用产生的结果序列`next`,`peek`， 和`hasNext`。 我们保证所有调用都是有效的，所以`next`当没有剩余元素时永远不会被调用。 列表大小很小，最多 1000 个元素，并且操作数量同样限制在 1000。这确保了即使是具有 O(n) 空间的简单解决方案也是可以接受的。 

重要的边缘情况包括具有单个元素的迭代器、多个元素的序列`peek`呼叫发生在`next`，以及迭代器耗尽的情况。 正确处理这些需要仔细跟踪“下一个”元素，而不是过早地消耗它。 

## 方法

 强力方法是简单地依赖底层迭代器来执行每个操作。 为了`peek()`，我们可以反复调用`next()`然后以某种方式存储消耗的元素以允许它再次返回。 这将是低效且容易出错的，因为`peek`可能需要对迭代器状态进行多次操作，这可能会引入错误和不必要的开销。 

最佳方法是**维护下一个元素的缓冲区**。 我们在初始化期间将下一个元素存储在私有变量中，并每次更新它`next()`被称为。 这允许`peek()`简单地返回缓冲值而不前进，`next()`返回缓冲值然后重新填充它，并且`hasNext()`检查缓冲区是否`None`。 这种方法保持操作干净，每次操作时间为 O(1)，并且仅需要 O(1) 额外缓冲区空间。

 | --- | --- | --- | --- |
 | 蛮力 | 每次查看 O(n) | O(n) | 反复推进迭代器以进行查看，可能存储元素 |
 | 最佳| 每次操作 O(1) | O(1) | O(1) | 为下一个元素维护一个缓冲区以有效支持查看 |

 ## 算法演练

 1. 初始化`PeekingIterator`与迭代器对象。 在初始化期间，检查迭代器是否有下一个元素，如果有，则将其存储在名为的缓冲区中`next_element`。 
2. 实施`peek()`简单地返回存储在的值`next_element`。 这保证了迭代器状态不会提前。 
3. 实施`next()`首先返回值`next_element`。 然后，检查底层迭代器是否有另一个元素。 如果有，请更新`next_element`具有新的值； 否则，将其设置为`None`。 
4. 实施`hasNext()`返回`True`如果`next_element`不是`None`，这表明还有更多元素需要迭代。 

为什么它有效：保持不变的是`next_element`始终保存下一个要返回的值。 这确保了`peek()`总是正确的，`next()`正确更新缓冲区，并且`hasNext()`准确反映迭代是否可以继续。 

## Python 解决方案```python
class PeekingIterator:
    def __init__(self, iterator: 'Iterator'):
        """
        Initialize your data structure here.
        :type iterator: Iterator
        """
        self.iterator = iterator
        self.next_element = iterator.next() if iterator.hasNext() else None

    def peek(self) -> int:
        """
        Returns the next element in the iteration without advancing the iterator.
        :rtype: int
        """
        return self.next_element

    def next(self) -> int:
        """
        :rtype: int
        """
        current = self.next_element
        self.next_element = self.iterator.next() if self.iterator.hasNext() else None
        return current

    def hasNext(self) -> bool:
        """
        :rtype: bool
        """
        return self.next_element is not None
```在Python实现中，我们维护`self.next_element`存储下一个值。`peek()`返回它而不前进，`next()`返回缓冲的值并通过调用底层迭代器（如果可用）来更新它，并且`hasNext()`只需检查缓冲区是否`None`。 这种设计确保每个操作的时间为 O(1)，并避免不必要地修改底层迭代器。 

## 解决方案```go
type PeekingIterator struct {
    iter        *Iterator
    nextElement int
    hasNextVal  bool
}

func Constructor(iter *Iterator) *PeekingIterator {
    pi := &PeekingIterator{iter: iter}
    if iter.hasNext() {
        pi.nextElement = iter.next()
        pi.hasNextVal = true
    } else {
        pi.hasNextVal = false
    }
    return pi
}

func (this *PeekingIterator) peek() int {
    return this.nextElement
}

func (this *PeekingIterator) next() int {
    current := this.nextElement
    if this.iter.hasNext() {
        this.nextElement = this.iter.next()
    } else {
        this.hasNextVal = false
    }
    return current
}

func (this *PeekingIterator) hasNext() bool {
    return this.hasNextVal
}
```在 Go 中，我们处理下一个元素和`hasNextVal`单独标记，因为 Go 没有`None`整数值。 这确保了`peek()`和`next()`行为与 Python 相同。 缓冲区允许所有操作在时间上保持 O(1)。

 ## 边缘情况

 一种边缘情况是具有单个元素的迭代器。 在这种情况下，`peek()`和`next()`最初应该返回相同的值，并且`hasNext()`应该正确返回`False`消耗元素后。 如果没有适当的缓冲，简单的实现可能会失败。 

另一个边缘情况是当多个`peek()`呼叫连续发生。 在查看期间消耗元素的简单解决方案将返回不同的值或过早地推进迭代器。 我们的缓冲区确保重复`peek()`调用总是返回相同的下一个元素。 

第三种边缘情况是迭代器在初始化时完全为空。`hasNext()`应立即返回`False`， 和`peek()`或者`next()`永远不应该根据约束调用。 有条件地处理缓冲区初始化可以防止任何空引用或无效访问错误。
