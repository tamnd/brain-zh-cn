 **难度：** 🔴难
 **主题：** 数组、动态规划

 ## 解决方案

 ## 问题理解

 该问题给了我们一个矩阵，称为`costs`， 在哪里`costs[i][j]`代表粉刷房屋的费用`i`有颜色`j`。 我们必须对每栋房屋进行油漆，使得没有两栋相邻的房屋使用相同的颜色，并且我们希望总油漆成本最小。 

如果有`n`房屋和`k`颜色，那么矩阵就有维度`n x k`。 每一行对应一栋房子，每一列对应该房子的颜色选择。 

关键的限制是相邻的房屋不能使用相同的颜色。 这意味着当我们为房子选择颜色时`i`，我们不能重复使用为房屋选择的颜色`i - 1`。 

输出是一个整数，即满足邻接约束的情况下可能的最小总成本。 

约束条件很重要：

 -`n <= 100`-`k <= 20`尝试每种可能的颜色的强力解决方案需要检查`k^n`组合，这很快就变得不可行。 即使只有 20 种颜色和 100 栋房屋，详尽的搜索也是不可能的。 

的值相对较小`k`表明动态规划是合适的，因为我们可以有效地跟踪每个房子的每种颜色选择的最佳成本。 

一些边缘情况很重要：

 - 单一的房子，我们只选择最便宜的颜色。 
- 颜色很多，但房子很少。 
- 由于相邻房屋必须不同而无法重复使用全球最便宜的颜色的情况。 
- 多种颜色可以实现最低成本的情况。 
- 非常小`k`， 尤其`k = 2`，其中交替约束变得严格。 

该问题保证了`k >= 2`，因此下一栋房子总是至少有一种有效的颜色选择。 

## 方法

 ### 蛮力

 暴力方法将递归地尝试每个房子的所有可能的颜色分配。 

对于每栋房子，我们都会尝试除前一栋房子使用的颜色之外的所有颜色。 一旦我们到达最终的房子，我们就会计算总成本并跟踪所有有效组合的最小值。 

这种方法是正确的，因为它明确地探索了每一种有效的绘画安排。 由于最佳解决方案必须是这些安排之一，因此暴力最终会找到它。 

然而，运行时间是指数级的。 对于每栋房子，我们最多可以有`k`选择，大致导致`O(k^n)`的可能性。 对于最大约束，这在计算上是不可能的。 

### 动态规划洞察

 重要的观察是，当前房屋的选择仅取决于之前的房屋。 

定义：

-`dp[i][j]`= 粉刷房屋的最低成本`0...i`哪里的房子`i`使用颜色`j`过渡是：```
dp[i][j] = costs[i][j] + min(dp[i-1][c]) for all c != j
```一个简单的实现将计算每个状态的所有先前颜色的最小值，从而产生`O(n * k^2)`时间。 

后续要求`O(nk)`运行时。 优化来自于注意到对于每一行我们只需要：

 - 上一行的最小值
 - 上一行的第二个最小值
 - 颜色指数的最小值

 然后：

 - 如果当前颜色`j`不是之前的最小颜色，则使用之前的最小值。 
- 否则，使用之前的第二个最小值。 

这避免了重复扫描所有颜色。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |

 ## 算法演练

 1. 处理空输入框。 

如果`costs`是空的，没有房子可以粉刷，所以答案是`0`。 
2. 初始化第一行。 

对于第一栋房子，每种颜色的最低成本只是油漆成本本身，因为没有以前的房子。 
3. 跟踪最小和第二小的成本。 

对于每个已处理的行，维护：

 -`min1`, 最小累计成本
 -`min2`，第二小的累积成本
 -`min1_color`，与相关的颜色索引`min1`这些值总结了前一行所需的所有内容。 
4. 逐一处理每个房屋。 

对于当前房屋中的每种颜色：

 - 如果颜色与`min1_color`，我们可以安全地扩展全局最便宜的先前配置。 
- 否则，我们必须使用`min2`因为相邻的房子不能有相同的颜色。 
5. 计算新的累积成本。 

过渡变为：```
current_cost = costs[i][j] + best_previous
```在哪里`best_previous`是`min1`或者`min2`。 
6. 更新当前行的最小值。 

当我们计算当前房屋的价值时，我们不断更新：

 - 新的最小累积成本
 - 新的第二小的累计成本
 - 相关的颜色索引
 7. 搬到下一个房子。 

处理完当前房屋的所有颜色后，新的最小值将成为下一次迭代的先前最小值。 
8. 返回最终的最小值。 

处理完所有房屋后，`min1`包含最低的总喷漆成本。 

### 为什么它有效

 动态规划不变量是：```
min1 = minimum cumulative cost for all processed houses
min2 = second minimum cumulative cost
```对于每种颜色，唯一禁止的过渡是使用与前一个房子相同的颜色。 因此：

 - 如果最便宜的先前配置使用不同的颜色，则最好对其进行扩展。 
- 否则，必须使用第二便宜的有效配置。 

由于每次状态转换都保留邻接约束，并且总是选择最优的有效前驱，因此最终结果是全局最优的。 

## Python 解决方案```python
from typing import List

class Solution:
    def minCostII(self, costs: List[List[int]]) -> int:
        if not costs:
            return 0

        n = len(costs)
        k = len(costs[0])

        prev_min1 = 0
        prev_min2 = 0
        prev_min1_color = -1

        for house in range(n):
            curr_min1 = float('inf')
            curr_min2 = float('inf')
            curr_min1_color = -1

            for color in range(k):
                if color == prev_min1_color:
                    current_cost = costs[house][color] + prev_min2
                else:
                    current_cost = costs[house][color] + prev_min1

                if current_cost < curr_min1:
                    curr_min2 = curr_min1
                    curr_min1 = current_cost
                    curr_min1_color = color
                elif current_cost < curr_min2:
                    curr_min2 = current_cost

            prev_min1 = curr_min1
            prev_min2 = curr_min2
            prev_min1_color = curr_min1_color

        return prev_min1
```实现首先处理空输入情况。 尽管这些限制保证了至少一所房子，但防御性编程使解决方案保持稳健。 

变量`prev_min1`,`prev_min2`， 和`prev_min1_color`总结前面的 DP 行。 而不是存储整个`dp`矩阵，我们只保留转换所需的信息。 

对于每个房子，算法计算每种颜色的最佳累积成本。 如果当前颜色与之前的最小颜色匹配，则算法使用`prev_min2`以避免违反邻接规则。 否则，它会安全地扩展全局最便宜的配置。 

在计算当前行时，算法不断更新最小和第二小的累积成本。 这允许下一次迭代以每种颜色的恒定时间运行。 

在最后，`prev_min1`包含可实现的最小总成本。 

## 解决方案```go
package main

import "math"

func minCostII(costs [][]int) int {
    if len(costs) == 0 {
        return 0
    }

    n := len(costs)
    k := len(costs[0])

    prevMin1 := 0
    prevMin2 := 0
    prevMin1Color := -1

    for house := 0; house < n; house++ {
        currMin1 := math.MaxInt32
        currMin2 := math.MaxInt32
        currMin1Color := -1

        for color := 0; color < k; color++ {
            currentCost := 0

            if color == prevMin1Color {
                currentCost = costs[house][color] + prevMin2
            } else {
                currentCost = costs[house][color] + prevMin1
            }

            if currentCost < currMin1 {
                currMin2 = currMin1
                currMin1 = currentCost
                currMin1Color = color
            } else if currentCost < currMin2 {
                currMin2 = currentCost
            }
        }

        prevMin1 = currMin1
        prevMin2 = currMin2
        prevMin1Color = currMin1Color
    }

    return prevMin1
}
```Go 实现遵循与 Python 版本相同的逻辑。 由于 Go 没有提供`float('inf')`，该解决方案使用`math.MaxInt32`作为一个大的哨兵值。 

切片自然地用于输入矩阵，并且整数溢出不是问题，因为最大可能的总成本很小：```go
100 houses * max cost 20 = 2000
```该实现还安全地处理空输入情况。

 ## 边缘情况

 一个重要的边缘案例是独栋房屋。 在这种情况下，不存在邻接约束，因为不存在相邻的房屋。 有缺陷的实现可能仍会尝试引用前一行或错误地强制执行颜色限制。 此实现可以自然地处理这种情况，因为第一次迭代只是在所有颜色中选择最小成本。 

另一个重要的边缘情况是多种颜色共享相同的最小累积成本。 当出现平局时，不正确的实现有时无法正确跟踪第二个最小值。 该解决方案显式地维护最小和第二小的累积值，即使多种颜色具有相同的成本，也能确保有效的转换。 

当最便宜的先前颜色与当前颜色匹配时，就会出现第三种关键边缘情况。 幼稚的优化可能总是重用前一行的全局最小值，这会违反邻接约束。 此实现通过检查来避免该错误`color == prev_min1_color`并切换到`prev_min2`每当有需要的时候。 

最后的边缘情况是颜色数量非​​常少，尤其是`k = 2`。 由于只有两种颜色可用，算法必须在它们之间小心地交替。 由于该实现在必要时明确排除了先前的最小颜色，因此它可以正确处理这种限制性配置，而无需特殊情况逻辑。
