[LeetCode 第 278 题](https://leetcode.com/problems/first-bad-version/)

 **难度：** 🟢简单
 **主题：** 二分查找、交互

 ## 解决方案

 ## 问题理解

 该问题为我们提供了一系列产品版本，编号为`1`到`n`。 在某些时候，一个版本会变得很糟糕，之后的每个版本也都会很糟糕。 这创建了一个单调模式：

 - 好的版本先出现
 - 随后出现不良版本

 例如：```
Version: 1 2 3 4 5
Status : G G G B B
```任务是找到第一个错误版本。 

我们不允许直接检查版本。 相反，我们得到了一个 API：```
isBadVersion(version)
```该函数返回：

 -`True`如果版本不好
 -`False`如果版本好的话

 面临的挑战是最大限度地减少 API 调用的数量。 

输入是：

 -`n`, 版本总数

 预期输出是：

 - 最小版本号`isBadVersion(version)`回报`True`约束条件很重要：

 -`1 <= bad <= n <= 2^31 - 1`这意味着`n`可以非常大，超过二十亿。 线性扫描可能需要数十亿次 API 调用，这太慢了。 这些约束强烈表明我们需要一个对数时间解。 

有几个重要的边缘情况：

 - 第一个版本可能已经很糟糕了
 - 最后一个版本可能是第一个糟糕的版本
 - 总共可能只有一个版本
 - 非常大的值`n`如果中点计算不正确，可能会导致某些语言中的整数溢出

 该问题保证至少存在一个错误版本。 

## 方法

 ### 蛮力方法

 最简单的解决方案是从版本开始`1`并使用一一检查每个版本`isBadVersion`。 

一旦我们遇到第一个坏版本，我们就会将其退回。 

这是有效的，因为版本是有序的。 一旦出现坏版本，所有后续版本也都是坏版本，因此第一个坏版本正是 API 返回的第一个版本`True`。 

然而，这种方法对于大输入来说太慢了。 

如果`n`非常大，第一个糟糕的版本即将结束，我们可能需要制作几乎`n`API 调用。 自从`n`可超过二十亿，这是不能接受的。 

### 最优方法，二分搜索

 关键的观察结果是版本形成单调结构：```
False False False False True True True
```这正是二分搜索效果很好的模式类型。 

我们不是检查每个版本，而是重复检查中间版本。 

- 如果中间的版本不好，那么第一个坏的版本一定在中间或左边的某个地方
 - 如果中间版本是好的，那么第一个坏版本一定在右边的某个地方

 通过每次将搜索空间减少一半，我们大大减少了 API 调用的数量。 

这给了我们对数时间复杂度。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |

 ## 算法演练

 1.初始化两个指针，`left`和`right`。 

-`left = 1`-`right = n`这些指针表示第一个错误版本可能存在的当前搜索范围。 
2.继续搜索`left < right`。 

这个条件确保我们在搜索空间缩小到单个候选者时停止。 
3. 安全地计算中间版本。```
mid = left + (right - left) // 2
```这可以避免 Go、Java 或 C++ 等语言中的整数溢出。 
4. 打电话`isBadVersion(mid)`。 

有两种可能：

 - 如果`mid`很糟糕：

 第一个糟糕的版本可能是`mid`本身或某些早期版本。 

所以我们保留左半部分：```
right = mid
```- 如果`mid`很好：

 第一个坏版本必须出现在`mid`。 

所以我们丢弃左半部分：```
left = mid + 1
```5. 重复直到`left == right`。 

此时，搜索范围内只剩下一个版本，并且它一定是第一个坏版本。 
6. 返回`left`。 

自从`left`和`right`相等，则可以返回其中之一。 

### 为什么它有效

 该算法保持了一个重要的不变量：

 - 第一个坏版本总是在当前搜索范围内`[left, right]`每个 API 调用都会删除一半的剩余搜索空间，同时保留此不变式。 最终，范围缩小到恰好一个版本，这一定是第一个坏版本。 

## Python 解决方案```python
# The isBadVersion API is already defined for you.
# def isBadVersion(version: int) -> bool:

class Solution:
    def firstBadVersion(self, n: int) -> int:
        left = 1
        right = n

        while left < right:
            mid = left + (right - left) // 2

            if isBadVersion(mid):
                right = mid
            else:
                left = mid + 1

        return left
```实现首先定义搜索边界`1`到`n`。 

这`while left < right`循环继续缩小范围，直到只剩下一个候选者。 

中点的计算方法为：```python
mid = left + (right - left) // 2
```这种形式是首选，因为它避免了具有固定大小整数的语言中的溢出。 

在循环内部，API 确定中点是否不良。 

如果中点不好，我们知道第一个坏版本位于`mid`或者更早，所以我们搬家`right`到`mid`。 

如果中点是好的，我们知道第一个坏版本一定会稍后出现，所以我们移动`left`到`mid + 1`。 

最终，两个指针都收敛到第一个错误版本，该版本被返回。 

## 解决方案```go
/** 
 * Forward declaration of isBadVersion API.
 * @param   version   your guess about first bad version
 * @return            true if current version is bad 
 *                    false if current version is good
 * func isBadVersion(version int) bool;
 */

func firstBadVersion(n int) int {
    left := 1
    right := n

    for left < right {
        mid := left + (right-left)/2

        if isBadVersion(mid) {
            right = mid
        } else {
            left = mid + 1
        }
    }

    return left
}
```Go 实现遵循与 Python 版本完全相同的二分搜索逻辑。 

一个重要的细节是中点计算：```go
mid := left + (right-left)/2
```这避免了潜在的整数溢出。 

Go 使用固定大小的整数，因此这个更安全的中点公式在以下情况下非常重要：`n`接近于`2^31 - 1`。 

不需要额外的内存结构，因此解决方案保持恒定的空间。

 ## 边缘情况

 ### 仅存在一个版本

 当`n = 1`，搜索范围开始为：```
left = 1
right = 1
```自从`left < right`立即为 false，循环永远不会执行。 算法正确返回`1`。 

这种情况很重要，因为某些实现意外地假设至少存在两个元素。 

### 第一个版本很糟糕

 如果版本`1`已经很糟糕了，任何中点上的每个 API 调用都会返回`True`。 

该算法不断缩小右边界，直到两个指针收敛于`1`。 

这种边缘情况很重要，因为不正确的二分搜索实现有时会跳过最左边的候选者。 

### 最后一个版本是第一个糟糕的版本

 如果只有最终版本不好，大多数中点检查都会返回`False`。 

该算法不断向左边界推进，直到最终达到最终版本。 

此案例验证了实现正确处理搜索空间最右边缘的转换。 

### 非常大的值`n`该约束允许值达到`2^31 - 1`。 

中点计算如下：```
mid = (left + right) // 2
```在某些具有固定大小整数的语言中可能会溢出。 

更安全的配方：```
mid = left + (right - left) // 2
```防止溢出，同时在数学上产生相同的结果。 Go 解决方案也使用这种更安全的计算。
