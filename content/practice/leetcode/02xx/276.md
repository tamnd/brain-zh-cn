[LeetCode 第 276 题](https://leetcode.com/problems/paint-fence/)

 **难度：** 🟡 中等
 **主题：** 动态规划

 ## 解决方案

 ## 问题理解

 这个问题给了我们一个栅栏`n`帖子和`k`可用颜色。 每根栅栏柱都必须使用其中一种颜色进行涂漆。 重要的限制是我们不允许三个或更多连续的帖子涂上相同的颜色。 

我们被要求计算有效绘画组合的总数。 

例如，如果`n = 3`和`k = 2`，我们可以使用两种颜色，例如红色和蓝色。 一些安排是有效的：

 - 红、红、蓝
 - 红、蓝、红
 - 蓝色，蓝色，红色

 然而，这样的安排：

 - 红，红，红
 - 蓝色，蓝色，蓝色

 无效，因为它们包含三个具有相同颜色的连续帖子。 

输入包括：

 -`n`, 栅栏柱的数量
 -`k`, 可用颜色的数量

 输出是一个整数，表示有效绘画配置的数量。 

限制相对较小：

 -`1 <= n <= 50`-`1 <= k <= 10^5`虽然`n`is small, the number of possible combinations grows exponentially if we try every arrangement directly. 这强烈表明强力递归解决方案将变得低效，而动态编程是一种更合适的方法。 

一些边缘情况很重要：

 - 当`n = 1`，每种颜色都是有效的，所以答案很简单`k`。 
- 什么时候`k = 1`，只有一种可用颜色。 这意味着：

-`n = 1`给出 1 个有效的排列。 
-`n = 2`给出 1 个有效的排列。 
-`n >= 3`给出 0 个有效排列，因为会出现三个相同的连续帖子。 
- 非常大的值`k`可以产生大量的中间计数，因此必须仔细实施递归关系。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是生成栅栏的每种可能的颜色并检查它是否满足约束。 

对于每个`n`帖子，我们有`k`选择。 这创造了`k^n`总组合。 我们可以递归地构建每个排列，并拒绝三个连续帖子共享相同颜色的任何配置。 

这种方法是正确的，因为它明确地检查了每种可能的绘画排列并仅计算有效的排列。 

然而，时间复杂度呈指数级增长。 即使具有中等值`n`和`k`，组合的数量变得非常多。 例如：

-`n = 50`-`k = 2`需要探索`2^50`可能性，这是不可行的。 

关键问题是许多子问题重复出现。 例如，绘制剩余帖子的有效方法的数量仅取决于最近的着色模式，而不是完整的历史记录。 

### 最优动态规划方法

 重要的观察是下一篇文章的有效性仅取决于前两篇文章。 

我们可以将有效安排分为两类：

 -`same`，最后两篇文章的颜色相同
 -`different`，最后两篇文章有不同的颜色

 这种分类足以建立递归关系。 

假设我们正在绘制当前的帖子：

 - 结束于`same`状态，当前帖子必须与前一篇匹配。 仅当之前的安排结束时才允许这样做`different`。 
- 结束于`different`状态，当前帖子必须使用与前一篇帖子不同的颜色。 We can choose any of the`k - 1`剩余颜色。 

这导致了有效的线性时间动态规划解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(k^n) | O(k^n) | O(n) | 递归生成所有可能的颜色 |
 | 最佳| O(n) | O(1) | O(1) | 使用两种运行状态的动态规划|

 ## 算法演练

 1. 处理只有一根栅栏柱的基础情况。 

如果`n == 1`，每种颜色都是有效的，所以答案很简单`k`。 
2. 初始化两个栅栏柱的状态。 

对于两个帖子：

 -`same = k`两个帖子都使用相同的颜色。 有`k`选择该颜色的方法。 
-`different = k * (k - 1)`第二篇文章必须与第一篇文章不同。 The first post has`k`选择，第二个有`k - 1`选择。 
3. 从第三篇文章开始迭代。 

For every new post:

- The new`same`价值变旧`different`。 

这是因为如果前一对不同，我们只能创建两个相等的连续帖子。 
- 新的`different`值变为：`(same + different) * (k - 1)`无论之前的状态如何，我们都可以将当前帖子绘制为与之前帖子不同的颜色。 
4. 每次迭代后更新运行状态。 

我们只需要之前的迭代值，因此我们重用变量而不是存储整个 DP 数组。 
5. 返回有效排列的总数。 

最终的答案是：`same + different`### 为什么它有效

 该算法保持精确的不变量：

 -`same`始终存储最后两个帖子共享相同颜色的有效排列的数量。 
-`different`始终存储最后两个帖子具有不同颜色的有效排列的数量。 

每个有效的排列都必须恰好属于这些类别之一。 过渡保留了三个连续帖子不能共享相同颜色的规则。 因为每个有效排列都只计算一次，所以递归会产生正确的总数。 

## Python 解决方案```python
class Solution:
    def numWays(self, n: int, k: int) -> int:
        if n == 1:
            return k

        same = k
        different = k * (k - 1)

        for _ in range(3, n + 1):
            new_same = different
            new_different = (same + different) * (k - 1)

            same = new_same
            different = new_different

        return same + different
```The implementation starts by handling the simplest case where only one fence post exists. 在这种情况下，每种颜色选择都是有效的。 

变量`same`和`different`代表两种动态规划状态。 对于两个栅栏柱：

 -`same`计算两个帖子匹配的排列。 
-`different`计数职位不同的安排。 

循环从第三个帖子开始，因为前两个帖子已经由初始状态值表示。 

循环内部：

 -`new_same`变成以前的`different`值，因为只有以不同颜色结尾的排列才能安全地添加一种匹配颜色。 
-`new_different`计算使用与上一篇文章不同的颜色的所有方法。 

最后，该解决方案返回两个状态的总和，因为每个有效的排列都以以下任一形式结束：`same`或者`different`类别。 

## 解决方案```go
func numWays(n int, k int) int {
    if n == 1 {
        return k
    }

    same := k
    different := k * (k - 1)

    for i := 3; i <= n; i++ {
        newSame := different
        newDifferent := (same + different) * (k - 1)

        same = newSame
        different = newDifferent
    }

    return same + different
}
```Go 实现遵循与 Python 版本完全相同的递归关系。 由于 Go 使用显式变量声明，因此临时变量`newSame`和`newDifferent`在循环内声明。 

该问题保证最终答案符合 32 位有符号整数，因此 Go 的标准`int`type 足以解决 LeetCode 上的这个问题。

 ## 边缘情况

 一种重要的边缘情况发生在以下情况：`n = 1`。 在这种情况下，不存在邻接约束，因为只存在一个帖子。 一个常见的错误是立即应用递归关系而不单独处理它。 该实现通过返回来避免此问题`k`就在任何动态编程逻辑开始之前。 

另一个关键的边缘情况出现时`k = 1`。 只有一种可用的颜色，只有在柱子少于三个的情况下才能有效地绘制栅栏。 幼稚的实现可能会意外地允许三个相同的连续帖子。 递归自然可以防止这种情况，因为一旦算法到达第三个帖子，`different`状态变为零，导致所有未来的有效配置消失。 

第三个重要的边缘情况涉及非常大的值`k`。 自从`k`可能大到`100000`，中间乘法结果会很快变大。 递归旨在有效地使用整数运算，而不需要不必要的存储结构。 该问题保证最终答案符合 32 位有符号整数，因此实现在预期约束内保持安全。
