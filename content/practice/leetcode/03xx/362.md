 ## 解决方案

 ## 问题理解

 该问题要求我们设计一个数据结构来跟踪过去 5 分钟内发生的事件数量（称为“点击”）。 每次点击都带有以秒为单位的时间戳，并且时间戳保证按时间顺序到达。 

该类必须支持三种操作：

 -`hit(timestamp)`在给定的秒记录新的点击。 
-`getHits(timestamp)`返回包含时间窗口内发生的点击次数`[timestamp - 299, timestamp]`。 
- 构造函数初始化计数器。 

重要的细节是系统只关心最后 300 秒。 任何超过 300 秒的命中不应再对答案有贡献。 

例如，如果在时间戳发生命中`1`，在时间戳查询时仍然应该计数`300`， 因为`300 - 1 = 299`，仍在 5 分钟窗口内。 然而，在时间戳`301`，同一命中变得太旧，必须排除。 

这些约束提供了一些有用的观察结果：

 - 时间戳单调递增，这意味着时间永远不会倒退。 
- 同一时间戳可能会发生多次点击。 
- 最大通话次数仅为`300`，这意味着效率较低的解决方案也可以通过。 
- 然而，后续明确询问了当点击量变得非常大时的可扩展性，因此我们应该考虑在重负载下仍然保持高效的设计。 

幼稚的实现很容易在边界条件周围犯错误。 最大的边缘情况是决定 300 秒前的点击是否仍然有效。 正确的解释是时间戳在范围内`[timestamp - 299, timestamp]`都包括在内。 另一个重要的情况是有效地处理同一时间戳的许多点击。 如果同一秒内有数百万个点击到达，则单独存储每个点击的设计可能会变得不必要的大。 

## 方法

 ### 蛮力方法

 最简单的解决方案是将每个命中时间戳存储在列表或队列中。 每当`hit(timestamp)`被调用时，我们将时间戳附加到结构中。 

什么时候`getHits(timestamp)`被调用后，我们会迭代所有存储的时间戳并计算有多少落在过去 300 秒内。 

这种方法是正确的，因为每个记录的点击都会直接根据有效时间窗口进行检查。 如果时间戳足够新，它就会有助于答案。 

然而，随着点击次数的增加，该解决方案变得效率低下。 每个查询都需要扫描整个命中集合，包括不再相关的非常旧的条目。 如果有数百万次点击到达，查询时间就会变得异常昂贵。 

### 最佳方法

 关键的观察是时间戳按时间顺序到达。 由于这种顺序保证，旧的命中自然会累积在数据结构的前面。 

我们可以使用队列并在超出 300 秒窗口时立即删除过期的命中，而不是重复扫描所有内容。 

该算法的工作原理如下：

 - 将每个点击时间戳存储在队列中。 
- 查询时：

 - 删除前面超过 300 秒的时间戳。 
- 剩余队列大小就是答案。 

这是有效的，因为每个命中都插入一次并删除一次。 没有重复处理时间戳。 

对于后续命中率极高的场景，我们可以通过存储来压缩同一秒内发生的多次命中`(timestamp, count)`成对而不是单独的时间戳。 这极大地减少了内存使用量。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 每个查询 O(n) | O(n) | 每次扫描所有点击|
 | 最佳| O(1) 摊销 | O(n) | 队列逐步删除过期的命中 |

 ## 算法演练

 ### 基于队列的最优算法

 1. 初始化一个空队列来存储命中时间戳。 

队列自动保留时间顺序，因为时间戳保证按递增顺序到达。 
2. 什么时候`hit(timestamp)`被调用，将时间戳附加到队列中。 

每次出现的命中都是独立存储的。 如果同一秒发生 3 次点击，则该时间戳会添加 3 次。 
3. 什么时候`getHits(timestamp)`被调用时，从队列前面删除过期的时间戳。 

如果出现以下情况，则时间戳已过期：$timestamp - old\_timestamp \geq 300$这意味着命中发生在 299 秒以上，并且不再属于有效窗口。 
4. 继续删除时间戳，直到队列前端再次有效。 

由于时间戳是按时间顺序排序的，一旦前面的时间戳有效，所有后面的时间戳也有效。 
5. 返回队列的大小。 

每个剩余时间戳对应于过去 300 秒内的点击。 

### 为什么它有效

 队列始终保持一个重要的不变量：其中的每个时间戳都属于有效的 300 秒窗口。 

每当`getHits`被调用时，过期的时间戳将从前面删除，直到恢复不变式。 由于时间戳是按排序顺序插入的并且从不重新排序，因此从前面删除就足够了。 因此，队列大小始终等于有效命中数。 

## Python 解决方案```python
from collections import deque
from typing import Deque

class HitCounter:

    def __init__(self):
        self.queue: Deque[int] = deque()

    def hit(self, timestamp: int) -> None:
        self.queue.append(timestamp)

    def getHits(self, timestamp: int) -> int:
        while self.queue and timestamp - self.queue[0] >= 300:
            self.queue.popleft()

        return len(self.queue)

# Your HitCounter object will be instantiated and called as such:
# obj = HitCounter()
# obj.hit(timestamp)
# param_2 = obj.getHits(timestamp)
```该实现使用Python的`deque`因为它支持从后面高效插入和从前面取出。 

构造函数初始化一个空队列。 

这`hit`方法只是附加时间戳。 由于时间戳已经按时间顺序排序，因此不需要排序或二分搜索。 

这`getHits`方法反复从前面删除过时的时间戳。 条件：```python
timestamp - self.queue[0] >= 300
```识别早于有效 300 秒窗口的点击。 

清理后，每个剩余的时间戳都是有效的，因此队列长度直接代表最近命中的数量。 

## 解决方案```go
type HitCounter struct {
    queue []int
}

func Constructor() HitCounter {
    return HitCounter{
        queue: []int{},
    }
}

func (this *HitCounter) Hit(timestamp int) {
    this.queue = append(this.queue, timestamp)
}

func (this *HitCounter) GetHits(timestamp int) int {
    for len(this.queue) > 0 && timestamp-this.queue[0] >= 300 {
        this.queue = this.queue[1:]
    }

    return len(this.queue)
}

/**
 * Your HitCounter object will be instantiated and called as such:
 * obj := Constructor();
 * obj.Hit(timestamp);
 * param_2 := obj.GetHits(timestamp);
 */
```Go 实现使用切片作为队列。 

附加新时间戳使用`append`，而删除过期条目是通过切片处理的：```go
this.queue = this.queue[1:]
```与Python不同`deque`，Go 切片不提供真正的 O(1) 前端移除，因为底层数组引用发生了变化。 然而，考虑到问题的限制，这种实现是完全可以接受的。 

Go 整数安全地处理时间戳范围，因为最大时间戳值仅`2 * 10^9`，它很适合 64 位整数，也适合 Go 的标准`int`在现代系统上。

 ### 示例 1

 输入：```

 ### 详细解释`getHits(301)`清理前：```
[1, 2, 3, 300]
```检查最旧的时间戳：```
301 - 1 = 300
```因为这大于或等于`300`, 时间戳`1`已过期并被删除。 

队列变为：```
[2, 3, 300]
```现在：```
301 - 2 = 299
```该时间戳仍然有效，因此清理工作停止。 

队列包含 3 个有效命中。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(1) 摊销 | 每个时间戳插入一次并删除一次 |
 | 空间| O(n) | 存储当前 300 秒窗口内的所有点击 |

 虽然`getHits`可以在一次调用中删除多个元素，每个时间戳在程序的整个生命周期内只能删除一次。 这给出了摊余常数时间复杂度。 

空间复杂度取决于最后 300 秒内发生的命中次数。 在最坏的情况下，所有点击都保留在活动窗口内。

 ## 边缘情况

 ### 正好 300 秒前

 最容易犯的错误之一是错误地处理 300 秒窗口边界处的时间戳。 

例如，时间戳命中`1`在时间戳查询时仍应计数`300`，但不应计入时间戳`301`。 

The implementation handles this correctly using:```
timestamp - old_timestamp >= 300
```仅删除至少 300 秒之前的点击。 

### 同一时间戳多次点击

 该问题明确允许同一秒内发生多次点击。 

有缺陷的实现可能会覆盖计数或意外删除重复的时间戳。 

该解决方案独立存储每个命中，因此如果时间戳发生三个命中`50`，队列包含：```
[50, 50, 50]
```因此，最终计数仍然准确。 

### 空数据结构

 呼唤`getHits`在记录任何点击之前是另一个重要的边缘情况。 

如果不仔细处理，从空队列中删除过期的时间戳可能会导致索引错误。 

实施安全地检查：```
while self.queue and ...
```这保证了只有当队列非空时才会发生前端访问。 

### 查询之间存在较大差距

 假设许多命中是很早记录的，然后查询发生得更晚。 

例子：```
hit(1)
hit(2)
hit(3)
getHits(1000)
```所有命中都应该过期。 

清理循环在返回队列大小之前删除每个过时的时间戳，确保过时的条目永远不会永久保留在内存中。
