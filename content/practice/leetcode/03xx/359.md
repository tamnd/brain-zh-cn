[LeetCode 问题 359](https://leetcode.com/problems/logger-rate-limiter/)

 **难度：** 🟢简单
 **主题：** 哈希表、设计、数据流

 ## 解决方案

 ## 问题理解

 该问题要求我们设计一个日志系统来控制打印相同消息的频率。 每条消息都关联一个时间戳，同一条消息只允许每10秒打印一次。 

更具体地说，当消息在时间戳处打印时`t`，下一次可以打印完全相同的消息的时间是时间戳`t + 10`。 在此之前任何打印相同消息的尝试都必须返回`false`。 

方法`shouldPrintMessage(timestamp, message)`确定是否应在当前时间戳打印消息。 如果消息被允许，该方法返回`true`并更新内部状态，以便将来的调用知道消息何时再次符合条件。 否则，它返回`false`。 

输入流保证按时间顺序到达，这意味着时间戳永远不会减少。 多条消息可能会在同一时间戳处到达。 这种保证很重要，因为它简化了逻辑并消除了处理无序事件的需要。 

限制相对较小：

 - 至多`10^4`将会拨打电话
 - 消息长度最多30个字符
 - 时间戳可以大到`10^9`虽然`10^4`操作并不是非常大，我们仍然需要一个高效的设计，因为问题本质上是关于实现实时速率限制器。 

一些边缘情况很重要：

 - 10秒内重复出现相同的信息
 - 消息精确到达边界，例如时间戳`11`在时间戳打印后`1`- 不同的消息到达相同的时间戳
 - 大时间戳可能会暴露不正确的算术逻辑
 - 以前从未见过的首次消息

 该问题保证了时间顺序，因此我们永远不需要重新考虑较早的时间戳或重新排序数据。 

## 方法

 ### 蛮力方法

 暴力解决方案将存储每条消息的每个成功打印时间戳。 每当新请求到达时，我们都会扫描该消息的历史记录，以确定自最近一次成功打印以来是否已经过去了至少 10 秒。 

例如，如果`"foo"`之前已按时间戳打印`[1, 15, 30]`，并且新请求出现在时间戳`35`，我们将检查最新的成功时间戳并确定是否`35 - 30 >= 10`。 

幼稚的实现甚至可能会在每次新请求到达时扫描消息的所有先前时间戳。 这是正确的，因为它在决定是否允许打印之前显式检查每条消息的历史记录。 

然而，这种方法效率低下，因为重复扫描会带来不必要的开销。 随着调用次数的增加，重复遍历的成本变得越来越高。 

### 最佳方法

 关键的观察是我们只关心每条消息最近的成功打印时间。 

如果消息最后打印的时间为时间戳`t`，那么下一个有效时间戳是`t + 10`。 较早的时间戳无关紧要，因为只有最新的成功打印才能确定资格。 

这意味着我们可以维护一个哈希图：

 - 键 = 消息字符串
 - 值 = 最近成功打印时间戳

 对于每个传入请求：

 - 如果以前从未见过该消息，请将其打印出来
 - 否则，检查是否`timestamp - lastPrinted >= 10`- 如果为 true，则更新时间戳并允许打印
 - 否则，拒绝请求

 哈希图提供平均值`O(1)`查找和更新时间，使解决方案非常高效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 每次调用 O(n) | O(n) | 存储完整的消息历史记录并可以扫描以前的时间戳 |
 | 最佳| 每次调用 O(1) | O(n) | 仅存储每条消息的最新成功时间戳 |

 ## 算法演练

 1. 初始化一个名为的哈希图`last_printed`。 

键将是消息字符串，值将是成功打印该消息的最新时间戳。 
2. 什么时候`shouldPrintMessage(timestamp, message)`调用时，首先检查该消息是否存在于哈希图中。 

如果该消息不存在，则意味着这是我们第一次看到它，因此应该始终打印它。 
3. 如果该消息存在，则检索其最近的成功打印时间戳。 

我们将当前时间戳与存储的值进行比较。 
4. 计算时间差。 

如果`timestamp - last_printed[message] >= 10`，已经过去了足够的时间，因此允许再次打印该消息。 
5. 如果该消息被允许，则更新哈希图。 

将当前时间戳存储为新的最近成功打印时间。 
6. 返回结果。 

返回`true`当消息被允许并且`false`否则。 

### 为什么它有效

 该算法之所以有效，是因为确定消息是否可以打印所需的唯一信息是其最近成功打印的时间戳。 

如果消息最后打印的时间为时间戳`t`，然后之前的每个时间戳`t + 10`必须被拒绝，并且每个时间戳或之后`t + 10`必须被接受。 早期历史不会影响未来的决策。 

通过始终维护每条消息的最新成功时间戳，该算法准确地保留了正确性所需的信息。 

## Python 解决方案```python
class Logger:

    def __init__(self):
        self.last_printed: dict[str, int] = {}

    def shouldPrintMessage(self, timestamp: int, message: str) -> bool:
        if message not in self.last_printed:
            self.last_printed[message] = timestamp
            return True

        if timestamp - self.last_printed[message] >= 10:
            self.last_printed[message] = timestamp
            return True

        return False

# Your Logger object will be instantiated and called as such:
# obj = Logger()
# param_1 = obj.shouldPrintMessage(timestamp, message)
```该实现使用名为的字典`last_printed`跟踪每条消息的最近成功打印时间戳。 

里面`__init__`，字典开始为空，因为尚未处理任何消息。 

在`shouldPrintMessage`，第一个条件检查该消息以前是否出现过。 如果不是，则立即允许该消息，并记录其时间戳。 

如果消息已存在，代码将计算当前时间戳与上次成功打印时间戳之间的差值。 当差异至少 10 秒时，消息再次符合条件，因此更新时间戳并`True`被返回。 

如果过去的时间少于 10 秒，则该方法返回`False`而不修改存储的时间戳。 

该实现直接遵循前面描述的算法，并使用哈希映射操作实现恒定时间平均性能。 

## 解决方案```go
type Logger struct {
    lastPrinted map[string]int
}

func Constructor() Logger {
    return Logger{
        lastPrinted: make(map[string]int),
    }
}

func (this *Logger) ShouldPrintMessage(timestamp int, message string) bool {
    lastTime, exists := this.lastPrinted[message]

    if !exists {
        this.lastPrinted[message] = timestamp
        return true
    }

    if timestamp-lastTime >= 10 {
        this.lastPrinted[message] = timestamp
        return true
    }

    return false
}

/**
 * Your Logger object will be instantiated and called as such:
 * obj := Constructor();
 * param_1 := obj.ShouldPrintMessage(timestamp,message);
 */
```Go 的实现与 Python 解决方案非常相似。 

Go 使用的不是 Python 字典`map[string]int`。 这`Constructor`函数使用以下命令初始化地图`make`。 

Go 映射在查找期间返回两个值：```go
lastTime, exists := this.lastPrinted[message]
```布尔值`exists`指示密钥是否存在。 这可以清楚地区分首次发送的消息和之前存储的消息。 

Go 整数就足够了，因为时间戳的范围是`10^9`，它很适合 Go 的整数范围。

 ## 边缘情况

 ### 消息恰好 10 秒后打印

 一个非常常见的错误是错误使用`>`而不是`>=`检查资格时。 

例如，如果`"foo"`在时间戳处打印`1`，然后是时间戳`11`必须被允许，因为`11 - 1 = 10`。 

该实现使用以下方式正确处理此问题：```
timestamp - self.last_printed[message] >= 10
```这可确保边界值的行为完全符合要求。 

### 同一时间戳有多个不同的消息

 多条消息可能会以相同的时间戳到达，并且不同的消息不应相互干扰。 

例如：```
(5, "foo")
(5, "bar")
```两者都应该被允许，因为它们是不同的消息。 

哈希映射为每个消息键独立存储时间戳，因此对一条消息的操作不会影响另一条消息。 

### 重复阻止的请求

 当被阻止的请求意外更新存储的时间戳时，会出现另一个微妙的问题。 

例如：```
(1, "foo")  -> allowed
(5, "foo")  -> blocked
(11, "foo") -> should still be allowed
```如果在时间戳处阻止请求`5`错误地更新了存储的时间戳，然后是时间戳`11`会错误地失败。 

该实现通过仅在成功打印消息时更新时间戳来避免这种情况。 被阻止的请求使存储的值保持不变。
