[LeetCode 问题 1531](https://leetcode.com/problems/string-compression-ii/)

 **难度：** 🔴难
 **主题：** 字符串、动态规划

 ## 解决方案

 ## 问题理解

 该问题要求我们在最多删除之后最小化游程编码字符串的长度`k`原始字符串中的字符。 

游程编码通过写入字符后跟其计数来压缩连续的重复字符，但仅当计数大于`1`。 

例如：

-`"a"`变成`"a"`与长度`1`-`"aa"`变成`"a2"`与长度`2`-`"aaa"`变成`"a3"`与长度`2`-`"aaaaaaaaaa"`变成`"a10"`与长度`3`重要的细节是压缩长度仅在特定计数阈值下发生变化：

 | 计数| 编码形式| 长度 |
 | --- | --- | --- |
 | 1 |`"a"`| 1 |
 | 2-9 | 2-9`"a2"`到`"a9"`| 2 |
 | 10-99 | 10-99`"a10"`到`"a99"`| 3 |
 | 100 | 100`"a100"`| 4 |

 我们最多可以删除`k`字符串中任意位置的字符。 删除后，剩余字符保持原来的顺序。 目标是产生尽可能短的压缩表示。 

输入包括：

 - 一根绳子`s`小写英文字母
 - 一个整数`k`代表允许的最大删除量

 输出是一个表示最小可能压缩长度的整数。 

限制相对较小：

 -`s.length <= 100`-`k <= 100`这些限制强烈表明动态规划是合适的。 尝试删除每个子集的强力解决方案将是指数级的且不可行。 

一些边缘情况很重要：

 - 如果`k >= len(s)`，我们可以删除整个字符串，产生长度`0`- 单字符运行不包含数字后缀
 - 压缩长度仅在计数交叉时增加`1`,`9`， 或者`99`- 删除匹配运行之间的字符可以将它们合并为更大的运行
 - 具有许多交替字符的字符串与具有长重复块的字符串的行为不同

 了解编码长度何时发生变化是最佳解决方案背后的关键见解。 

## 方法

 ### 蛮力方法

 蛮力方法会尝试最多的所有可能组合`k`删除。 

对于已删除位置的每个子集：

 1.构造剩余的字符串
 2.对其进行游程编码
 3. 计算压缩长度
 4. 跟踪最小值

 这种方法是正确的，因为它探索了每个有效的删除配置。 

然而，它太慢了。 长度为一串`100`有`2^100`可能的子集。 甚至限制删除最多`k`角色仍然会产生组合爆炸。 

因此，暴力解决方案是不切实际的。 

### 最优动态规划方法

 关键的观察结果是压缩长度仅取决于：

 - 当前角色运行
 - 该次运行的计数
 - 剩余的删除

 我们可以从左到右处理字符串并决定：

 - 保留角色以延长运行时间
 - 删除字符以避免增加压缩长度
 - 删除插入的字符以合并运行

 重要的见解是，当从位置开始构建运行时`i`，我们只关心：

 - 我们保留了多少个匹配的字符
 - 我们删除了多少个不匹配的字符

 这自然会导致动态规划。 

定义：

-`dp(i, k)`= 子串的最小压缩长度`s[i:]`最多使用`k`删除

 在每个位置：

 - 我们可以删除`s[i]`- 或者建立一个运行从`s[i]`在扩展运行时：

 - 匹配字符增加运行次数
 - 不匹配的字符消耗删除

 我们计算当前运行的压缩贡献并递归地求解剩余的后缀。 

因为字符串长度只有`100`，这个解决方案足够有效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(2^n * n) | O(2^n * n) | O(n) | 尝试每个删除子集 |
 | 最优动态规划| O(n² * k) | O(n * k) | 子串位置和删除的记忆 DP |

 ## 算法演练

 ### 第 1 步：定义 DP 状态

 我们定义：```
dp(index, remaining_deletions)
```这表示可从以下方式获得的最小压缩长度`s[index:]`最多使用`remaining_deletions`删除。 

这种状态就足够了，因为：

 - 剩余的子串决定未来的选择
 - 剩余的删除预算限制了运营

 ### 第 2 步：处理基本案例

 如果剩余子串长度小于或等于剩余删除次数，我们就可以删除所有内容。 

所以：```
if len(s) - index <= remaining_deletions:
    return 0
```这是一个重要的优化。 

### 步骤 3：选项 1，删除当前字符

 我们可以删除`s[index]`。 

这给出：```
dp(index + 1, remaining_deletions - 1)
```仅当我们仍有可用的删除时，此选项才有效。 

### 步骤 4：选项 2，构建运行

 我们尝试创建一个压缩组，开头为`s[index]`。 

我们迭代自`index`转发：

 - 如果字符匹配`s[index]`, 增加运行次数
 - 否则算删除

 我们维持：

 -`same_count`-`deleted_count`### 步骤 5：计算压缩成本

 压缩贡献取决于游程长度。 

| 运行次数 | 增加长度 |
 | --- | --- |
 | 1 | 1 |
 | 2-9 | 2-9 2 |
 | 10-99 | 10-99 3 |
 | 100 | 100 4 |

 我们定义一个辅助函数：```
encoded_length(count)
```### 步骤 6：递归求解剩余后缀

 形成结束于位置的游程后`j`，递归求解：```
encoded_length(same_count) + dp(j + 1, remaining_deletions - deleted_count)
```我们对所有可能的端点取最小值。 

### 第 7 步：记住结果

 许多州重复。 

我们将计算结果存储在一个记忆表中，该表的键值如下：```
(index, remaining_deletions)
```这将指数递归减少为多项式时间。 

### 为什么它有效

 该算法之所以有效，是因为每个最佳压缩字符串都必须以以下两个选择之一开始：

 - 删除当前字符
 - 将其作为跑步的一部分

 构建运行时，会探索每个可能的有效端点。 由于递归调用最优求解剩余后缀，因此通过动态规划最优子结构，整个解是最优的。 

记忆化保证每个状态只解决一次。 

## Python 解决方案```python
from functools import lru_cache

class Solution:
    def getLengthOfOptimalCompression(self, s: str, k: int) -> int:
        n = len(s)

        def encoded_length(count: int) -> int:
            if count == 1:
                return 1
            if count < 10:
                return 2
            if count < 100:
                return 3
            return 4

        @lru_cache(None)
        def dp(index: int, remaining_k: int) -> int:
            if remaining_k < 0:
                return float("inf")

            if index >= n or n - index <= remaining_k:
                return 0

            result = float("inf")

            # Option 1: delete current character
            result = dp(index + 1, remaining_k - 1)

            # Option 2: keep current character and build a run
            same_count = 0
            deleted_count = 0

            for j in range(index, n):
                if s[j] == s[index]:
                    same_count += 1
                else:
                    deleted_count += 1

                if deleted_count > remaining_k:
                    break

                current_length = encoded_length(same_count)

                result = min(
                    result,
                    current_length + dp(j + 1, remaining_k - deleted_count)
                )

            return result

        return dp(0, k)
```该实现紧密遵循前面描述的算法。 

这`encoded_length()`helper 计算一次运行对压缩字符串贡献了多少个字符。 这很重要，因为仅当计数跨越数字边界时编码大小才会改变。 

递归`dp()`函数解决字符串后缀的最小压缩问题。 

第一个优化检查是否可以完全删除剩余的子字符串。 如果是这样，压缩长度立即变为零。 

在递归内部，我们首先考虑删除当前字符。 这会消耗一个删除预算并移动到下一个位置。 

接下来，我们尝试从当前索引开始形成一个运行。 当我们扩展运行时：

 - 匹配字符增加`same_count`- 不匹配的字符被视为已删除

 如果删除超出可用预算，我们将停止扩展。 

对于每个有效的运行端点，我们计算：```python
compressed_length_of_current_run + optimal_solution_for_remaining_suffix
```记忆化确保重复的子问题只解决一次。 

## 解决方案```go
package main

import "math"

func getLengthOfOptimalCompression(s string, k int) int {
	n := len(s)

	encodedLength := func(count int) int {
		if count == 1 {
			return 1
		}
		if count < 10 {
			return 2
		}
		if count < 100 {
			return 3
		}
		return 4
	}

	memo := make(map[[2]int]int)

	var dp func(int, int) int

	dp = func(index int, remainingK int) int {
		if remainingK < 0 {
			return math.MaxInt32
		}

		if index >= n || n-index <= remainingK {
			return 0
		}

		key := [2]int{index, remainingK}

		if value, exists := memo[key]; exists {
			return value
		}

		result := dp(index+1, remainingK-1)

		sameCount := 0
		deletedCount := 0

		for j := index; j < n; j++ {
			if s[j] == s[index] {
				sameCount++
			} else {
				deletedCount++
			}

			if deletedCount > remainingK {
				break
			}

			currentLength := encodedLength(sameCount)

			candidate := currentLength + dp(j+1, remainingK-deletedCount)

			if candidate < result {
				result = candidate
			}
		}

		memo[key] = result

		return result
	}

	return dp(0, k)
}
```Go 的实现与 Python 解决方案非常相似。 

而不是Python的`lru_cache`，Go 使用带有二元素数组键的映射：```go
map[[2]int]int
```它存储记忆的 DP 状态。 

Go 没有内置的整数无穷大值，所以`math.MaxInt32`被用作一个大的哨兵值。 

Go 中的字符串以字节为索引，这在这里是安全的，因为输入仅包含小写英文字母。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n² * k) | 每个 DP 状态向前扫描字符串 |
 | 空间| O(n * k) | 记忆表存储状态 |

 最多有`n * k`民主党指出。 

对于每个州，我们最多可以扫描`n`角色在奔跑时向前推进。 

因此，总复杂度变为：```
O(n² * k)
```自从`n <= 100`，这已经足够有效了。 

记忆表每存储一个结果`(index, remaining_k)`配对，要求：```
O(n * k)
```空间。

 ## 边缘情况

 当删除预算足够大以删除整个剩余子串时，就会出现一种重要的边缘情况。 幼稚的实现可能会继续不必要的递归，甚至产生负长度。 此实现明确检查：```
if n - index <= remaining_k:
    return 0
```这保证了正确的处理并显着提高了效率。 

另一个棘手的边缘情况涉及计数阈值，例如`1`,`9`， 和`99`。 仅当位数发生变化时，压缩长度才会增加。 例如：

-`"a9"`有长度`2`-`"a10"`有长度`3`不正确的实现可能会假设每个附加字符都会增加编码长度。 辅助函数可以正确处理这些转换。 

第三个重要的边缘情况涉及通过删除中间字符来合并分离的运行。 例如：```
"aabbaa"
```删除两个`'b'`字符合并两个单独的字符`'aa'`合而为一`'aaaa'`团体。 只考虑本地压缩的贪婪方法会错过这种优化。 动态规划解决方案探索所有可能的运行扩展，从而正确识别此类合并。
