[LeetCode 问题 1505](https://leetcode.com/problems/minimum-possible-integer-after-at-most-k-adjacent-swaps-on-digits/)

 **难度：** 🔴难
 **主题：** 字符串、贪婪、二叉索引树、线段树

 ## 解决方案

 ## 问题理解

 问题给了我们一个数字字符串`num`和一个整数`k`。 每次操作都允许我们交换两个相邻的数字。 我们最多可以表演`k`此类交换，目标是构造尽可能小的整数，并以字符串形式返回。 

重要的细节是交换只允许在相邻位置之间进行。 这意味着从索引中移动一个数字`i`索引`j`成本正好`i - j`交换如果`i > j`。 我们不能像正常的排序问题一样自由地重新排列数字。 

例如，如果数字是`"4321"`和`k = 4`，我们可以移动数字`'1'`使用相邻的交换从末端到前面。 每一步都会向左移动一个位置。 左移动的总数决定了交换成本。 

限制条件非常大：

 -`num.length`可以达到`3 * 10^4`-`k`可以大到`10^9`这些限制立即排除了任何对互换的强力模拟。 甚至一个`O(n^2)`在这种规模下，这种方法就变得有风险。 我们需要一个接近的解决方案`O(n log n)`。 

另一个重要的观察结果是输出可能包含前导零。 例如，`"100"`一次交换就变成`"010"`。 因此，我们不应该将结果视为整数类型。 我们必须将其保存为字符串。 

一些边缘情况很重要：

 - 非常大`k`，我们可以在邻接约束下有效地产生按字典顺序排列的最小排列。 
- 具有许多重复数字的字符串。 
- 字符串已经处于最佳顺序。 
- 包含可能移到前面的零的输入。 
- 字符串后面存在较小数字的情况，但移动它会花费比我们剩余的更多的交换。 

## 方法

 ### 蛮力方法

 一种简单的方法是反复向前查看并模拟所有可能的相邻交换。 在每个位置，我们尝试将每个可到达的数字移到前面并选择最小的结果配置。 

一种可能的暴力方法是：

 1. 对于答案中的每个位置：

 - 搜索下一个`k`职位。 
- 找到可到达的最小数字。 
- 显式执行相邻交换。 
2. 重复此操作直至字符串完成。 

这种方法在逻辑上是正确的，因为贪婪地选择最小的可达数字会产生字典顺序最小的结果。 

然而，显式执行相邻交换的成本极其昂贵。 重复移动数组或字符串中的数字会产生成本`O(n)`每次。 由于我们可能对许多位置执行此操作，因此整体复杂性可能会降级为`O(n^2)`或者更糟。 

和`n = 30000`，这太慢了。 

### 关键见解

 核心观察是我们实际上不需要模拟每次交换。 

相反，我们只需要知道：

 - 每个数字当前存在的位置
 - 在此之前已经删除了多少个职位

 假设一个数字最初位于索引处`i`。 在提取一些较早的数字并将其放入答案后，其有效的当前位置会发生变化。 

这正是二元索引树（也称为 Fenwick 树）可以有效处理的问题类型。 

该策略变为：

 - 存储每个数字的索引`0-9`- 从左到右贪婪地构建答案
 - 在每一步中，尝试输入以下数字`'0'`到`'9'`- 计算需要多少次交换才能将该数字向前推进
 - 选择交换成本在剩余数之内的最小数字`k`二叉索引树有效地跟踪在给定索引之前已经删除了多少位置。 

这将复杂性降低到`O(n log n)`。

 ## 算法演练

 1. 为每个数字创建一个队列`0`到`9`。 

对于每一个角色`num`，将其索引存储在与该数字对应的队列中。 这使我们能够快速找到任何数字最左边未使用的出现位置。 
2. 初始化二叉索引树。 

芬威克树跟踪有多少数字已从早期位置删除。 这让我们可以在之前的操作之后计算数字的有效当前位置。 
3. 一次一个位置地构建答案。 

对于最终结果中的每个位置，我们尝试放置尽可能小的数字。 
4. 尝试以下数字`0`通过`9`。 

对于每个候选数字：

 - 检查是否存在未使用的事件。 
- 让`original_index`是第一个未使用的事件。 
5. 计算有效互换成本。 

一些较早的位置可能已被删除并放入答案中。 

如果：

-`removed_before`= 之前删除的索引数`original_index`那么该数字的有效当前位置变为：$\text{effective position} = \text{original index} - \text{removed before}$所需的交换次数等于相对于当前前沿的有效头寸。 
6. 检查成本是否在范围内`k`。 

如果所需的掉期小于或等于`k`，我们立即选择这个数字，因为按升序尝试数字可以保证词典编排的最小性。 
7. 更新数据结构。 

选择数字后：

 - 将其附加到结果中
 - 从中减去其成本`k`- 将其原始索引标记为在芬威克树中已删除
 - 从该数字的队列中删除索引
 8. 重复此操作，直至所有位置均已填满。 

### 为什么它有效

 在每一步中，我们都会选择在剩余交换预算内可以合法移动到当前位置的最小数字。 

字典顺序是从左到右确定的。 因此，一旦我们可以提前放置一个较小的数字，无论未来的决定如何，任何替代选择都会产生更大的最终结果。 

二叉索引树保证即使在从字符串中间提取并删除较早的数字之后，也能正确计算交换成本。 

## Python 解决方案```python
from collections import deque
from typing import List

class FenwickTree:
    def __init__(self, size: int):
        self.size = size
        self.tree = [0] * (size + 1)

    def update(self, index: int, delta: int) -> None:
        index += 1

        while index <= self.size:
            self.tree[index] += delta
            index += index & -index

    def query(self, index: int) -> int:
        index += 1
        result = 0

        while index > 0:
            result += self.tree[index]
            index -= index & -index

        return result

class Solution:
    def minInteger(self, num: str, k: int) -> str:
        n = len(num)

        positions = [deque() for _ in range(10)]

        for index, digit in enumerate(num):
            positions[int(digit)].append(index)

        fenwick = FenwickTree(n)

        result = []

        for _ in range(n):

            for digit in range(10):

                if not positions[digit]:
                    continue

                original_index = positions[digit][0]

                removed_before = fenwick.query(original_index)

                swaps_needed = original_index - removed_before

                if swaps_needed <= k:
                    k -= swaps_needed

                    result.append(str(digit))

                    fenwick.update(original_index, 1)

                    positions[digit].popleft()

                    break

        return "".join(result)
```该实现首先将每个数字的位置存储在单独的队列中。 由于数字是从左到右处理的，因此队列可以有效检索下一个未使用的事件。 

这`FenwickTree`类支持两种操作：

 -`update(index, delta)`将位置标记为已删除
 -`query(index)`返回到该索引为止存在多少个已删除的位置

 在构建结果期间，我们迭代数字`0`到`9`并测试最左边的事件是否可以在剩余的交换预算内移动到当前位置。 

表达式：$\text{swaps needed} = \text{original index} - \text{removed before}$计算已提取的数字后所需的相邻交换的有效数量。 

选择数字后：

 - 它永久固定在答案中
 - 它的位置在芬威克树中被标记为已删除
 - 交换预算减少

 重复贪婪过程，直到构建出整个答案。 

## 解决方案```go
package main

import (
	"strings"
)

type FenwickTree struct {
	tree []int
	size int
}

func NewFenwickTree(size int) *FenwickTree {
	return &FenwickTree{
		tree: make([]int, size+1),
		size: size,
	}
}

func (f *FenwickTree) Update(index int, delta int) {
	index++

	for index <= f.size {
		f.tree[index] += delta
		index += index & -index
	}
}

func (f *FenwickTree) Query(index int) int {
	index++

	result := 0

	for index > 0 {
		result += f.tree[index]
		index -= index & -index
	}

	return result
}

func minInteger(num string, k int) string {
	n := len(num)

	positions := make([][]int, 10)

	for i, ch := range num {
		digit := int(ch - '0')
		positions[digit] = append(positions[digit], i)
	}

	usedIndex := make([]int, 10)

	fenwick := NewFenwickTree(n)

	var result strings.Builder

	for i := 0; i < n; i++ {

		for digit := 0; digit < 10; digit++ {

			if usedIndex[digit] >= len(positions[digit]) {
				continue
			}

			originalIndex := positions[digit][usedIndex[digit]]

			removedBefore := fenwick.Query(originalIndex)

			swapsNeeded := originalIndex - removedBefore

			if swapsNeeded <= k {

				k -= swapsNeeded

				result.WriteByte(byte(digit + '0'))

				fenwick.Update(originalIndex, 1)

				usedIndex[digit]++

				break
			}
		}
	}

	return result.String()
}
```Go 实现遵循与 Python 版本相同的算法结构。 

一个区别是 Go 在标准库中没有内置的双端队列类型。 相反，我们将所有索引存储在切片中并维护一个名为的指针数组`usedIndex`跟踪每个数字的下一个未使用的出现位置。 

结果字符串是使用构造的`strings.Builder`，这比重复的字符串连接更有效。 

由于所有值都保持在 LeetCode 上 Go 的标准整数限制内，因此常规`int`类型就足够了。

 ## 边缘情况

 当输入已经代表最小的可能排列时，就会出现一种重要的边缘情况。 例如，`"12345"`无论交换预算如何，都无法得到改善。 有缺陷的实现可能仍会尝试不必要的操作或错误地对相等的数字进行重新排序。 该解决方案可以自然地处理这种情况，因为贪婪扫描总是发现当前的前面的数字是最佳的。 

另一个重要的情况涉及前导零。 在许多整数问题中，前导零无效或自动删除。 在这里，它们是明确允许的。 例如，`"100"`一次交换就变成`"010"`。 由于实现始终将数字视为字符串，并且从不将其转换为整数类型，因此可以正确保留前导零。 

重复的数字是错误的另一个常见来源。 考虑`"1111"`或者`"9090"`。 我们必须始终使用每个数字最左边未使用的出现位置，因为选择较晚出现的位置可能会浪费交换并破坏最优性。 队列确保事件按正确的顺序进行处理。 

最后的临界边缘情况涉及非常大的值`k`。 自从`k`可以达到`10^9`，一一模拟交换的实现变得不可行。 该解决方案仅使用 Fenwick 树以数学方式计算交换计数，因此即使对于巨大的交换预算，性能也保持高效。
