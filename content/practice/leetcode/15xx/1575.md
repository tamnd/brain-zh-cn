 # LeetCode 1575 - 计算所有可能的路线

 ## 问题理解

 这个问题给了我们一组位于数轴上的城市。 数组`locations`存储每个城市的坐标，其中`locations[i]`代表城市的地位`i`。 

我们还得到：

 -`start`，我们开始的城市的索引
 -`finish`, 目的地城市索引
 -`fuel`，可用燃料总量

 从城市搬家`i`到城市`j`费用：$|locations[i]-locations[j]|$燃料单位。 

任务不是找到最短路线或单个有效路线。 相反，我们必须计算从以下位置开始的每条可能的路线：`start`并结束于`finish`，只要燃料永远不会变成负值。 

一条路线可能会多次重访城市，包括起点城市和终点城市。 这个细节非常重要，因为它意味着允许循环。 例如，这样的路线：```
0 -> 1 -> 0 -> 1 -> 2
```如果存在足够的燃料，则完全有效。 

答案可能会变得非常大，因此我们将其取模返回：$10^9+7$这些约束揭示了有关预期解决方案的重要信息：

 | 约束| 意义|
 | --- | --- |
 |`locations.length <= 100`| 我们可以研究每对城市之间的转变|
 |`fuel <= 200`| 燃料足够小，可以对燃料状态进行动态编程|
 | 坐标可达`10^9`| 我们永远不应该构建基于坐标的网格 |
 | 城市各具特色 | 不同城市之间的距离始终为正 |

 最重要的边缘情况是：

 - 起始城市可能已经等于终点城市。 在这种情况下，留在城市算作一条有效路线。 
- 即使一次也可能无法到达目的地。 
- 因为允许重新访问，所以简单的递归可能会呈指数级增长。 
- 许多不同的路径可以到达相同的路径`(city, remainingFuel)`状态，强烈建议记忆或动态编程。 

## 方法

 ### 蛮力方法

 暴力解决方案将递归地尝试当前城市中所有可能的下一个城市。 

从城市出发`i`，我们尝试搬到其他所有城市`j`燃料成本可以承受的地方。 移动后，我们递归地继续探索从`j`。 

每当我们到达`finish`，我们计算一条有效路线。 

这种方法是正确的，因为它明确枚举了每个有效的移动序列。 

然而，它太慢了。 由于城市可能会被反复访问，因此可能的路径数量会随着燃料量呈指数增长。 递归重复地重新计算相同的状态。 

例如，假设我们达到：```
(city = 2, fuel = 7)
```通过多个不同的路径。 暴力解决方案每次都会从这个状态重新计算所有未来的可能性。 

这种重叠的子问题结构使得暴力破解效率低下。 

### 最优方法，记忆化动态规划

 关键的观察是，未来的可能性仅取决于：

 - 当前城市
 - 剩余燃料

 其他都不重要。 

这意味着我们可以定义一个 DP 状态：```
dp(city, remainingFuel)
```表示从当前城市到目的地最多使用的有效路线条数`remainingFuel`。 

一旦我们计算了这个值一次，我们就可以在其他地方重用它。 

其递归式为：

 - 如果当前城市等于`finish`，立即统计一条路线。 
- 然后尝试移动到剩余燃料可以到达的所有其他城市。 
- 将所有递归结果加在一起。 

记忆可以防止重复工作，从而大大降低复杂性。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 指数| O(fuel) 递归深度 | 多次重新计算相同的状态 |
 | 最佳 | O(n² × 燃料) | O(n × 燃料) | 使用记忆法解决重叠子问题 |

 ## 算法演练

 1.定义递归函数`dfs(city, remainingFuel)`。 

该函数返回从以下位置开始的有效路线的数量`city`和`remainingFuel`剩余燃油。 
2. 使用记忆来缓存计算状态。 

由于许多路径可以导致相同的状态，因此记忆可以防止重复计算。 
3. 初始化当前状态的答案。 

如果`city == finish`，那么停留在目的地就已经形成了一条有效的路线。 
4. 尝试去其他所有城市旅行。 

对于每个城市`nextCity`：

 - 跳过如果`nextCity == city`- 计算燃料成本：$cost=|locations[city]-locations[nextCity]|$- 如果剩余足够的燃料，则递归探索：```
dfs(nextCity, remainingFuel - cost)
```5. 将所有有效的递归结果加在一起。 

由于结果可能会变得很大，因此取模`10^9 + 7`添加后。 
6. 返回存储的结果。 

### 为什么它有效

 该算法之所以有效，是因为每条有效路线都可以分解为：

 - 当前城市
 - 下一步
 - 来自下一个状态的所有有效路线

 递归对每个 DP 状态的每个合法转换精确地探索一次。 记忆化保证相同的状态不会被重新计算，同时仍然计算每条不同的路线。 

## Python 解决方案```python
from typing import List
from functools import lru_cache

class Solution:
    def countRoutes(
        self,
        locations: List[int],
        start: int,
        finish: int,
        fuel: int
    ) -> int:
        MOD = 10**9 + 7
        n = len(locations)

        @lru_cache(None)
        def dfs(city: int, remaining_fuel: int) -> int:
            routes = 1 if city == finish else 0

            for next_city in range(n):
                if next_city == city:
                    continue

                fuel_cost = abs(
                    locations[city] - locations[next_city]
                )

                if fuel_cost <= remaining_fuel:
                    routes += dfs(
                        next_city,
                        remaining_fuel - fuel_cost
                    )

            return routes % MOD

        return dfs(start, fuel)
```实现首先定义常量并检索城市数量。 

递归`dfs`函数代表DP状态。 记忆装饰器`@lru_cache(None)`存储每个的结果`(city, remaining_fuel)`一对。 

在函数内部，如果当前城市等于目的地，我们首先将当前状态计为一条有效路线。 这很重要，因为即使需要额外的燃料来进行更多的旅行，任何时候到达目的地都会立即生效。 

然后循环尝试过渡到所有其他城市。 燃料成本是使用坐标之间的绝对距离计算的。 

如果存在足够的燃料，则以减少的燃料继续递归。 

最后返回结果取模`10^9 + 7`。 

## 解决方案```go
package main

func countRoutes(locations []int, start int, finish int, fuel int) int {
	const MOD int = 1_000_000_007

	n := len(locations)

	memo := make([][]int, n)
	for i := 0; i < n; i++ {
		memo[i] = make([]int, fuel+1)
		for j := 0; j <= fuel; j++ {
			memo[i][j] = -1
		}
	}

	var dfs func(city int, remainingFuel int) int

	dfs = func(city int, remainingFuel int) int {
		if memo[city][remainingFuel] != -1 {
			return memo[city][remainingFuel]
		}

		routes := 0

		if city == finish {
			routes = 1
		}

		for nextCity := 0; nextCity < n; nextCity++ {
			if nextCity == city {
				continue
			}

			cost := locations[city] - locations[nextCity]
			if cost < 0 {
				cost = -cost
			}

			if cost <= remainingFuel {
				routes += dfs(nextCity, remainingFuel-cost)
				routes %= MOD
			}
		}

		memo[city][remainingFuel] = routes
		return routes
	}

	return dfs(start, fuel)
}
```Go 解决方案使用 2D 切片`memo`而不是Python的`lru_cache`。 

每个条目存储计算出的答案：```go
(city, remainingFuel)
```未计算的状态被初始化为`-1`。 

Go 没有提供内置的整数绝对值函数，因此距离计算是手动处理的。 

在累加期间应用模运算以避免整数溢出。

 ## 边缘情况

 ### 起始城市等于结束城市

 一个微妙的细节是，如果满足以下条件，起始城市本身就被视为有效路线：`start == finish`。 

例如：```
locations = [1, 2, 3]
start = 0
finish = 0
fuel = 0
```即使不动，答案也应该是`1`。 

一个常见的错误是当当前城市等于目的地时忘记立即计算当前状态。 该实现通过初始化正确处理这个问题：```
routes = 1 if city == finish else 0
```在每个 DP 状态内。 

### 循环和重访城市

 该问题明确允许重新访问城市。 这会在状态图中创建循环。 

例如：```
0 -> 1 -> 0 -> 1 -> 2
```没有记忆的原始 DFS 会变得指数级缓慢，因为相同的状态会被重复重新计算。 

记忆缓存确保每个`(city, remainingFuel)`状态只解决一次。 

### 大坐标值

 坐标可能大到：```
10^9
```简单的解决方案可能会错误地尝试坐标压缩或网格遍历。 

该实现完全避免了这种情况。 它只直接计算成对的绝对距离：```
abs(locations[i] - locations[j])
```无论坐标大小如何，这都使算法保持高效。
