[LeetCode 1500 题](https://leetcode.com/problems/design-a-file-sharing-system/)

 **难度：** 🟡 中等
 **主题：** 哈希表、设计、排序、堆（优先级队列）、数据流

 ## 解决方案

 ## 问题理解

 这个问题要求我们设计一个微型的点对点文件共享系统。 该文件分为`m`块，其中每个块都有一个 ID`1`到`m`。 用户可以在已经拥有一些块的情况下加入系统，完全离开系统，并向其他用户请求块。 

主要挑战不是块传输本身，而是有效维护所有权信息，同时正确管理可重用的用户 ID。 

当用户加入时，系统必须分配最小的可用正整数作为其用户 ID。 ID 是可重复使用的，这意味着如果用户离开，他们的 ID 可以再次供未来的用户使用。 这立即表明我们需要一个能够有效检索最小可用 ID 的数据结构。 

这`request(userID, chunkID)`操作稍显微妙。 该方法必须返回当前拥有所请求块的所有用户，并按升序排序。 此外，如果至少一个用户拥有该块，则发出请求的用户会成功下载该块，并且现在也拥有该块。 

约束条件很重要：

 -`m`可以大到`10^5`- 最多有`10^4`运营
 - 每个用户初始最多拥有`100`块

 这些限制告诉我们，我们不能针对每个操作重复扫描每个用户或每个块。 我们需要近乎恒定的时间更新和有效检索排序的所有者。 

一些边缘情况很重要：

 - 用户可以在没有任何块的情况下加入
 - 一个块当前可能没有所有者
 - 请求用户可能已经拥有所请求的块
 - ID 必须始终重用最小的可用值
 - 多个用户可以拥有同一个块
 - 离开的用户必须完全从所有所有权结构中删除

 幼稚的实现很容易失败，因为忘记在休假时删除块所有权，或者错误地处理可重用 ID。 

## 方法

 ### 蛮力方法

 一个简单的实现将存储每个用户拥有的块，并且对于每个请求，扫描所有活动用户以确定谁拥有所请求的块。 

例如：

 - 维护从用户 ID 到拥有的块的映射
 - 对于`request(userID, chunkID)`，遍历每个活跃用户并检查他们是否拥有`chunkID`- 为了`leave(userID)`，只需删除该用户

 这种方法是正确的，因为所有权始终直接源自权威的用户数据。 

然而，它的效率很低。 在最坏的情况下，每个请求操作都会扫描所有用户。 由于最多可能有`10^4`操作，重复的全扫描变得昂贵。 

如果简单地实现，可重复使用的 ID 要求也会变得尴尬。 每次连接连续搜索最小的未使用 ID 可能会花费线性时间。 

### 最佳方法

 关键的观察是所有权查询频繁发生，因此我们应该按块索引所有权，而不是重复搜索所有用户。 

我们维持两个主要关系：

 - 对于每个用户，他们拥有哪些块
 - 对于每个块，哪些用户当前拥有它

 这允许：

 - 在连接和离开期间快速插入/移除
 - 在请求期间快速检索所有所有者

 为了有效地重用最小的可用用户 ID，我们使用最小堆。 每当用户离开时，他们的 ID 就会被推回到堆中。 当新用户加入时，如果可能的话，我们首先重用最小的可用 ID。 否则，我们分配一个新的递增 ID。 

我们还需要按排序顺序返回所有权列表。 使用有序集合结构是可行的，但 Python 本身并不提供这种结构。 相反，我们使用常规集合并仅在返回结果时进行排序。 由于最多有`10^4`操作，这仍然有效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | 每个请求 O(U) | O(U × C) | 扫描所有用户的所有权 |
 | 最佳 | 每个请求 O(log U + K log K) | O(U × C) | 使用块到用户索引和可重用 ID 堆 |

 这里：

-`U`是用户数量
 -`C`是每个用户的平均块数
 -`K`是块的所有者数量

 ## 算法演练

 1.初始化三个核心数据结构。 

我们维持：

 -`user_chunks`，从用户 ID 到他们拥有的块集的映射
 -`chunk_owners`，从块 ID 到拥有它的用户集的映射
 -`available_ids`，存储可重用用户 ID 的最小堆

 我们还保留`next_id`，如果不存在可重用 ID，则表示要分配的下一个全新 ID。 
2. 处理`join`手术。 

当新用户加入时：

 - 如果堆包含可重用的ID，则弹出最小的一个
 - 否则，分配`next_id`并增加它

 然后：

 - 存储用户的块`user_chunks`- 对于每个拥有的块，将用户插入`chunk_owners[chunk]`这确保两个映射保持同步。 
3. 处理`leave`手术。 

当用户离开时：

 - 检索该用户拥有的所有块
 - 从每个相应的块所有权集中删除用户
 - 删除用户`user_chunks`- 将用户的ID推送到可重用的ID堆中

 这会将用户从系统中完全删除，同时使 ID 再次可用。 
4. 处理`request`手术。 

对于请求的块：

 - 检索所有所有者`chunk_owners[chunkID]`- 返回前对它们进行排序

 如果所有者列表非空：

 - 将块添加到请求用户拥有的块中
 - 将请求用户添加到块的所有者集中

 至此模型下载成功。 
5. 返回排序后的所有者列表。 

该问题明确要求升序，因此排序发生在请求操作期间。 

### 为什么它有效

 该算法维护两个同步不变量：

 - 每个用户拥有的块都准确存储在`user_chunks`- 每个块的所有者都准确存储在`chunk_owners`每当所有权发生变化时，两个结构都会一起更新。 因为 ID 在期间被删除`leave`被插入到最小堆中，在期间总是首先检索最小的可重用 ID`join`。 因此，所有权跟踪和 ID 分配在所有操作中都保持正确。 

## Python 解决方案```python
from typing import List
from collections import defaultdict
import heapq

class FileSharing:

    def __init__(self, m: int):
        self.user_chunks = {}
        self.chunk_owners = defaultdict(set)

        self.available_ids = []
        self.next_id = 1

    def join(self, ownedChunks: List[int]) -> int:
        if self.available_ids:
            user_id = heapq.heappop(self.available_ids)
        else:
            user_id = self.next_id
            self.next_id += 1

        self.user_chunks[user_id] = set(ownedChunks)

        for chunk in ownedChunks:
            self.chunk_owners[chunk].add(user_id)

        return user_id

    def leave(self, userID: int) -> None:
        owned_chunks = self.user_chunks[userID]

        for chunk in owned_chunks:
            self.chunk_owners[chunk].discard(userID)

        del self.user_chunks[userID]

        heapq.heappush(self.available_ids, userID)

    def request(self, userID: int, chunkID: int) -> List[int]:
        owners = sorted(self.chunk_owners[chunkID])

        if owners:
            if chunkID not in self.user_chunks[userID]:
                self.user_chunks[userID].add(chunkID)
                self.chunk_owners[chunkID].add(userID)

        return owners

# obj.leave(userID)
# param_3 = obj.request(userID, chunkID)
```该实现紧密遵循前面描述的算法。 

构造函数初始化所有状态跟踪结构。`user_chunks`从用户的角度存储所有权，同时`chunk_owners`从块的角度存储所有权。 最小堆`available_ids`有效管理可重复使用的 ID。 

这`join`方法首先确定要分配哪个ID。 如果存在先前释放的 ID，则通过以下方式重用最小的 ID：`heapq.heappop`。 否则，将生成一个新的 ID`next_id`。 

这`leave`方法迭代离开用户拥有的每个块，并将该用户从每个所有权集中删除。 清理后，用户 ID 将返回到可重用池中。 

这`request`方法检索所请求块的所有所有者并在返回之前对它们进行排序。 如果所有权存在，则请求者成功下载该块，因此所有权被添加到两个跟踪结构中。 

使用集合可以自动防止重复的所有权条目。 

## 解决方案```go
package main

import (
	"container/heap"
	"sort"
)

type MinHeap []int

func (h MinHeap) Len() int {
	return len(h)
}

func (h MinHeap) Less(i, j int) bool {
	return h[i] < h[j]
}

func (h MinHeap) Swap(i, j int) {
	h[i], h[j] = h[j], h[i]
}

func (h *MinHeap) Push(x interface{}) {
	*h = append(*h, x.(int))
}

func (h *MinHeap) Pop() interface{} {
	old := *h
	n := len(old)
	val := old[n-1]
	*h = old[:n-1]
	return val
}

type FileSharing struct {
	userChunks   map[int]map[int]bool
	chunkOwners  map[int]map[int]bool
	availableIDs MinHeap
	nextID       int
}

func Constructor(m int) FileSharing {
	h := MinHeap{}
	heap.Init(&h)

	return FileSharing{
		userChunks:   make(map[int]map[int]bool),
		chunkOwners:  make(map[int]map[int]bool),
		availableIDs: h,
		nextID:       1,
	}
}

func (this *FileSharing) Join(ownedChunks []int) int {
	var userID int

	if this.availableIDs.Len() > 0 {
		userID = heap.Pop(&this.availableIDs).(int)
	} else {
		userID = this.nextID
		this.nextID++
	}

	this.userChunks[userID] = make(map[int]bool)

	for _, chunk := range ownedChunks {
		this.userChunks[userID][chunk] = true

		if _, exists := this.chunkOwners[chunk]; !exists {
			this.chunkOwners[chunk] = make(map[int]bool)
		}

		this.chunkOwners[chunk][userID] = true
	}

	return userID
}

func (this *FileSharing) Leave(userID int) {
	for chunk := range this.userChunks[userID] {
		delete(this.chunkOwners[chunk], userID)
	}

	delete(this.userChunks, userID)

	heap.Push(&this.availableIDs, userID)
}

func (this *FileSharing) Request(userID int, chunkID int) []int {
	ownersMap, exists := this.chunkOwners[chunkID]

	if !exists || len(ownersMap) == 0 {
		return []int{}
	}

	owners := []int{}

	for owner := range ownersMap {
		owners = append(owners, owner)
	}

	sort.Ints(owners)

	if !this.userChunks[userID][chunkID] {
		this.userChunks[userID][chunkID] = true
		this.chunkOwners[chunkID][userID] = true
	}

	return owners
}

/**
 * Your FileSharing object will be instantiated and called as such:
 * obj := Constructor(m);
 * param_1 := obj.Join(ownedChunks);
 * obj.Leave(userID);
 * param_3 := obj.Request(userID,chunkID);
 */
```Go 版本密切反映了 Python 实现，但 Go 需要更明确的数据结构管理。 

由于 Go 没有为整数提供内置堆，因此我们实现`heap.Interface`手动使用`container/heap`。 

Python 集合使用以下方式表示`map[int]bool`在围棋中。 这是在 Go 中对哈希集进行建模的惯用方法。 

与 Python 不同，Go 区分 nil 映射和初始化映射，因此我们必须在插入之前显式分配映射。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | 每个请求 O(log U + K log K) | 堆操作加上排序所有者|
 | 空间| O(U × C) | 商店所有权关系|

 这`join`和`leave`操作以堆操作和更新所有权集为主。 

这`request`操作必须按排序顺序返回所有者，这需要排序`K`业主。 这种排序成本是不可避免的，除非我们维护永久排序的结构，这会使更新成本更高。 

总空间复杂度来自存储两个方向的所有权关系：

 - 用户分块
 - 给用户的块

 ## 边缘情况

 当用户在没有块的情况下加入时，就会出现一种重要的边缘情况。 粗心的实现可能会假设每个用户至少拥有一个块，并且无法正确初始化所有权结构。 在此解决方案中，无论大小如何，都会初始化用户的块集，因此自然会处理空所有权。 

另一个关键的边缘情况涉及可重复使用的 ID。 假设用户`1`和`2`按该顺序离开。 下一个加入的用户必须收到 ID`1`， 不是`3`。 单纯的增量系统会违反问题要求。 最小堆保证最小的可用 ID 始终首先被重用。 

第三种微妙的边缘情况发生在对同一块的重复请求期间。 如果请求用户已经拥有该块，我们必须避免重复的所有权条目。 对用户所有权和块所有权使用集会自动防止重复并保持数据一致。 

最后，离开的用户必须从每个块所有权映射中完全删除。 忘记此清理将导致过时的用户出现在未来的请求结果中。 这`leave`实现显式地迭代所有拥有的块，并将用户从每个相应的所有权集中删除。
