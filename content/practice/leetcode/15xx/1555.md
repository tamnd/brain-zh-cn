[LeetCode 问题 1555](https://leetcode.com/problems/bank-account-summary/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题给了我们两个数据库表，`Users`和`Transactions`，并要求我们在应用所有记录的交易后计算每个用户的最终帐户余额。 

这`Users`表包含每个用户的起始信用余额。 每一行代表一个银行账户，由`user_id`。 这`credit`列是处理交易之前用户的当前余额。 

这`Transactions`表记录用户之间的资金转移。 每笔交易都有：

 -`paid_by`, 发件人
 -`paid_to`，接收器
 -`amount`, 转账金额

 当交易发生时：

 - 发送者亏钱，因此他们的余额减少了`amount`- 接收者获得金钱，因此他们的余额增加`amount`所有交易应用后，我们必须返回：

 -`user_id`-`user_name`- 更新`credit`-`credit_limit_breached`这`credit_limit_breached`列是`"Yes"`如果最终余额为负数，否则`"No"`。 

结果可以按任何顺序返回，因此除非明确请求，否则不需要排序。 

这从根本上来说是一个聚合问题。 对于每个用户，我们需要计算：```
final_credit =
initial_credit
- total_money_sent
+ total_money_received
```重要的观察是每笔交易恰好影响两个用户：

 - 一次借记操作`paid_by`- 一项信用操作`paid_to`约束没有明确列出，但由于这是来自 LeetCode 的 SQL 数据库问题，我们应该假设表可能包含许多行。 这意味着我们应该避免重复扫描`Transactions`每个用户的表。 

一些边缘情况很重要：

 - 用户可能永远不会出现在`Transactions`根本没有桌子
 - 用户只能汇款
 - 用户只能收到钱
 - 多个交易可能涉及同一用户
 - 用户可能会以完全结束`0`信用，不被视为违反
 - 交易可能导致余额为负数

 正确的解决方案必须考虑所有这些情况。 

## 方法

 ### 蛮力方法

 暴力方法独立处理每个用户。 

对于中的每一行`Users`表，我们扫描整个`Transactions`表并计算：

 - 用户支付的总金额
 - 用户收到的总金额

 然后我们使用以下方法计算最终余额：```
final_credit = initial_credit - paid_amount + received_amount
```这种方法是正确的，因为它明确检查每个用户的每笔交易并累积所有相关的汇款。 

然而，它的效率很低。 如果有`U`用户和`T`交易，然后我们对每个用户的所有交易执行全面扫描。 这导致时间复杂度为`O(U × T)`。 

对于大型数据集，重复扫描事务表会变得不必要的昂贵。 

### 最佳方法

 关键的见解是每笔交易都会独立地影响用户的净余额变化。 

我们可以将交易表预处理为每个用户的单个聚合余额调整，而不是每个用户一次扫描所有交易。 

我们可以将每笔交易视为生成两条记录：

 - 发件人得到`-amount`- 接收者得到`+amount`综合用户的所有这些调整后，我们得到每个用户的净交易效果。 

然后我们只需将这个聚合结果与`Users`表并将其添加到原始信用中。 

这将工作量减少为一次传递交易数据，然后与用户连接。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(U × T) | O(1) | O(1) | 重复扫描每个用户的所有交易 |
 | 最佳 | O(U + T) | O(U) | 聚合一次交易效果，然后加入 |

 ## 算法演练

 1. 从`Transactions`表并将每笔交易转换为余额变化。 

对于用户 A 向用户 B 支付金额 X 的交易：

 - 用户 A 收到余额变化`-X`- 用户 B 收到余额变化`+X`这会将交易历史记录转换为一组每个用户的余额调整。 
2. 按用户汇总所有余额更改。 

对于每个用户，计算总净交易效应：```
net_change = total_received - total_sent
```SQL 聚合函数，例如`SUM()`是这一步的理想选择。 
3. 将汇总的交易结果与`Users`桌子。 

有些用户可能根本没有交易，所以我们使用`LEFT JOIN`以确保每个用户仍然出现在结果中。 
4. 计算最终余额。 

将合计净变化添加到原始贷项中：```
final_credit = original_credit + net_change
```如果用户没有交易历史，则将其净变化视为`0`。 
5. 判断是否违反信用额度。 

如果最终余额为负数：```
"Yes"
```否则：```
"No"
```6. 返回所需的列。 

### 为什么它有效

 每笔交易都会在两个账户之间节省资金：

 - 发件人损失的正是转移的金额
 - 接收者获得完全相同的数量

 通过汇总每个用户的所有借方和贷方，我们可以获得所有交易引起的准确的净余额变化。 将此净变化添加到初始信用中将为每个用户产生正确的最终余额。 

使用`LEFT JOIN`保证没有交易的用户仍然包含在余额不变的情况下。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    u.user_id,
    u.user_name,
    u.credit + COALESCE(t.balance_change, 0) AS credit,
    CASE
        WHEN u.credit + COALESCE(t.balance_change, 0) < 0
        THEN 'Yes'
        ELSE 'No'
    END AS credit_limit_breached
FROM Users u
LEFT JOIN (
    SELECT
        user_id,
        SUM(balance_change) AS balance_change
    FROM (
        SELECT
            paid_by AS user_id,
            -amount AS balance_change
        FROM Transactions

        UNION ALL

        SELECT
            paid_to AS user_id,
            amount AS balance_change
        FROM Transactions
    ) balances
    GROUP BY user_id
) t
ON u.user_id = t.user_id;
```该解决方案首先将每笔交易转换为余额调整。 发送者贡献负数，而接收者贡献正数。 

这`UNION ALL`将这两组行合并到一个包含所有余额更改的虚拟表中。 我们使用`UNION ALL`而不是`UNION`因为重复的值不能被删除。 每笔交易都很独立。 

接下来，外部聚合分组为`user_id`并计算每个用户的总余额变化。 

然后将结果与`Users`表使用一个`LEFT JOIN`。 这确保没有任何交易的用户仍然出现在输出中。`COALESCE()`通过替换处理没有匹配交易记录的用户`NULL`和`0`。 

最后，`CASE`表达式检查结果余额是否为负并生成所需的`"Yes"`或者`"No"`价值。

 ## 边缘情况

 ### 没有交易的用户

 一个常见的错误是意外地排除了从未出现在列表中的用户`Transactions`桌子。 

如果一个`INNER JOIN`被用来代替`LEFT JOIN`，此类用户完全从结果中消失。 该实现通过使用来避免这种情况`LEFT JOIN`并将缺失的交易总额替换为`0`通过`COALESCE()`。 

### 用户以完全零信用结束

 仅当信用值小于`0`。 

条件很容易被错误地写为`<= 0`，这会错误地将零余额标记为已违反。 该解决方案仅显式检查`< 0`。 

### 重复交易金额

 如果`UNION`被用来代替`UNION ALL`，重复的行可能会被意外删除。 

例如，同一用户之间相同金额的两笔独立交易将合并为一行，从而产生不正确的余额。 实现正确使用`UNION ALL`所以每笔交易都是独立贡献的。
