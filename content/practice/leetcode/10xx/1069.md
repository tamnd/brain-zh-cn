[LeetCode 问题 1069](https://leetcode.com/problems/product-sales-analysis-ii/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题要求我们根据记录中的记录计算**每种产品的总销售量**`Sales`桌子。 

这`Sales`表包含事务级别信息。 每行代表特定年份特定产品的销售情况，以及销售数量和单价。 由于产品可以出现在多行中，并且可能跨越不同的年份，因此我们需要合并所有这些行并计算每个产品的销售总量`product_id`。 

这`Product`表包含映射到的产品名称`product_id`，但问题只要求我们报告：

 -`product_id`-`total_quantity`由于输出不需要`product_name`，我们实际上不需要使用`Product`我们的解决方案中的表。 

换句话说，任务是将所有行分组`Sales`表格依据`product_id`并求和`quantity`每个组的列。 

例如，如果产品`100`出现在多个带有数量的销售记录中`10`和`12`，则其销售总量变为：$$10 + 12 = 22$$该问题保证了`(sale_id, year)`是独一无二的，这意味着每条销售记录都是不同的。 还，`product_id`在`Sales`是一个有效的外键`Product`，因此每个引用的产品都存在。 

一个重要的细节是**只有具有销售的产品才应出现在结果中**。 即使产品存在于`Product`表，例如`300`在示例中，如果没有匹配的销售记录，则不应将其包含在输出中。 

幼稚的实施可能会错误地包括来自`Product`表或无法正确聚合多个销售条目。 另一个常见的错误是按两者分组`product_id`和`year`，这会错误地为每个产品生成多行而不是单个总计。 

由于这是一个数据库聚合问题，因此使用 SQL 聚合的预期解决方案是简单且高效的。 

## 方法

 ### 蛮力方法

 解决此问题的一种强力方法是手动处理每个销售记录并重复扫描表以累积每个产品的总计。 

例如，对于每个独特的`product_id`，我们可以迭代整个`Sales`表格并对所有匹配数量求和。 虽然这会产生正确的答案，但效率很低，因为我们反复重新访问相同的行。 

如果有`n`销售记录和`m`独特的产品，这可能需要`O(n × m)`最坏情况下的时间。 

这种方法之所以有效，是因为每条销售记录都只为其相应的产品总数贡献一次，但重复扫描会导致不必要的昂贵。 

### 最佳方法

 关键的观察是，这是一个经典的**分组和聚合**问题。 

我们可以处理`Sales`通过将具有相同行的行分组到单次传递中的表`product_id`并总结`quantity`价值观。 SQL 直接通过`GROUP BY`结合`SUM()`聚合函数。 

这是可行的，因为同一产品的所有行都属于同一逻辑组，并且对每个组内的数量求和即可得出所需的销售总量。 

自从`Product`请求的输出不需要表，我们避免不必要的连接并保持查询简单高效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n × m) | O(米) | 反复扫描每个产品的销售记录 |
 | 最佳| O(n) | O(米) | 单一聚合使用`GROUP BY`|

 在哪里：

-`n`= 中的行数`Sales`-`m`= 不同的数量`product_id`价值观

 ## 算法演练

 ### 最优算法

 1. 读取所有行`Sales`桌子。 

每行包含一个`product_id`和一个`quantity`。 由于多行可能对应同一个产品，因此我们必须将它们组合起来。 
2. 行分组依据`product_id`。 

分组的目的是将属于同一产品的所有销售记录收集到一个逻辑桶中。 
3. 计算总和`quantity`对于每个组。 

对行进行分组后，我们通过将该组中的所有数量加在一起来计算每种产品的总销售数量。 
4. 返回结果。 

输出应包含一行`product_id`与计算出的`total_quantity`。 

SQL 实现变得非常简洁，因为关系数据库针对聚合操作进行了优化。 

### 为什么它有效

 该算法之所以有效，是因为每条销售记录都贡献了一个`quantity`值恰好为 1`product_id`。 通过对属于同一产品的所有行进行分组并对它们的数量进行求和，我们确保每笔销售都被计算一次且仅计算一次。 由于没有产品以外`Sales`表提供任何数量，输出自然只包含实际销售的产品。 

## Python 解决方案

 LeetCode 数据库问题使用 SQL 而不是 Python，但如果我们以编程方式对逻辑进行建模，等效的实现将如下所示：```python
from collections import defaultdict
from typing import List

class Solution:
    def totalQuantity(self, sales: List[List[int]]) -> List[List[int]]:
        quantity_by_product = defaultdict(int)

        for _, product_id, _, quantity, _ in sales:
            quantity_by_product[product_id] += quantity

        return [
            [product_id, total_quantity]
            for product_id, total_quantity in quantity_by_product.items()
        ]
```该实现使用哈希映射，特别是`defaultdict(int)`，累计每种产品的总数量。 当我们迭代销售记录时，我们提取`product_id`和`quantity`，然后将该数量添加到该产品的运行总计中。 

由于字典查找和插入的平均时间是恒定的，因此聚合可以在单次传递中高效运行。 

对于实际的 LeetCode 提交，预期的答案是 SQL：```python
SELECT
    product_id,
    SUM(quantity) AS total_quantity
FROM Sales
GROUP BY product_id;
```查询对共享相同内容的行进行分组`product_id`并使用以下方法计算销售总量`SUM(quantity)`。 别名`total_quantity`匹配所需的输出格式。 

## 解决方案

 由于这是一个数据库问题，所以在实际的LeetCode提交中并没有使用Go。 然而，Go 中的等效聚合逻辑如下所示：```go
package main

func totalQuantity(sales [][]int) [][]int {
	productTotals := make(map[int]int)

	for _, sale := range sales {
		productID := sale[1]
		quantity := sale[3]

		productTotals[productID] += quantity
	}

	result := [][]int{}

	for productID, totalQuantity := range productTotals {
		result = append(result, []int{
			productID,
			totalQuantity,
		})
	}

	return result
}
```Go 版本使用`map[int]int`存储每个的运行总计`product_id`。 Go 中的地图提供平均值`O(1)`插入和查找，使它们非常适合聚合问题。 

与Python不同`defaultdict`，Go 映射会自动返回缺失键的零值，因此增加不存在的键自然会起作用。 由于该问题允许以任意顺序返回结果，因此无需对输出进行排序。 

对于实际的 LeetCode 问题，SQL 解决方案仍然是：```go
SELECT
    product_id,
    SUM(quantity) AS total_quantity
FROM Sales
GROUP BY product_id;

 ## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(n) | 每个销售行均处理一次 |
 | 空间| O(米) | 不同产品的商店总数 |

 该算法扫描一次销售数据并更新每种产品的运行总计。 由于每行对哈希映射条目仅贡献一次，因此时间复杂度与销售记录的数量呈线性关系。 

空间复杂度取决于销售表中出现的不同产品的数量。 在最坏的情况下，每次销售都可能涉及不同的产品，需要`O(m)`额外的存储空间。 

对于 SQL 解决方案，数据库引擎通常实现`GROUP BY`在内部使用散列或排序，为聚合工作负载带来接近线性的性能。

 ## 边缘情况

 ### 没有销售的产品

 产品可能存在于`Product`表但从未出现在`Sales`。 如果有人错误地执行完整连接或迭代每个产品，这很容易导致错误。 问题只需要实际销售的产品。 由于实现直接从`Sales`表中，没有销售的产品将被自动排除。 

### 不同年份的多次销售

 同样的产品可能会在几年后出现。 一个常见的错误是按两者分组`product_id`和`year`，这将为同一产品创建多行。 我们的实施小组仅通过`product_id`，确保所有年份的数量正确组合。 

### 同年多次销售

 一种产品在同一年内可能有多个单独的销售记录。 简单的解决方案可能会意外地覆盖较早的数量而不是对它们求和。 由于我们不断地添加到运行总计中，使用`SUM(quantity)`在 SQL 或代码中的哈希映射中，每笔销售都会正确地贡献到最终总额。
