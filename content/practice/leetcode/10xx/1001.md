[LeetCode 1001 题](https://leetcode.com/problems/grid-Illumination/)

 **难度：** 🔴难
 **主题：** 数组、哈希表

 ## 解决方案

 ## 问题理解

 该问题模拟了一个非常大的棋盘状网格，其中某些单元包含有源灯。 一盏灯同时照亮四个方向：

 - 整行
 - 整个专栏
 - 它的主对角线，由`row - col`- 它的反对角线，由下式确定`row + col`对于每个查询，我们必须确定所查询的单元格是否被至少一盏当前活动的灯照亮。 回答查询后，我们必须关闭位于查询单元或其八个相邻单元之一的所有灯。 

重要的细节是照明沿着行、列和对角线是全局的。 一盏灯在`(r, c)`照亮所有细胞：

 -`(r, any)`-`(any, c)`-`(r + k, c + k)`-`(r + k, c - k)`对于所有有效职位。 

输入包括：

 -`n`，网格大小
 -`lamps`，初始活动灯位置列表
 -`queries`，要检查的单元序列

 输出是一个数组，其中：

 -`1`表示查询的单元格被照亮
 -`0`意味着它没有被照亮

 约束是这个问题最重要的部分：

 -`n`可以大到`10^9`- 最多`20,000`灯
 - 最多`20,000`查询

 的巨大价值`n`立即告诉我们明确构建网格是不可能的。 一个`10^9 x 10^9`网格无法存储或迭代。 这意味着解决方案必须仅取决于有源灯的位置，而不取决于网格尺寸本身。 

一些边缘情况很重要：

 - 输入中可能会出现重复的灯位置
 - 关闭灯不得多次减少重复的计数器
 - 查询可能会重复针对同一区域
 - 先前查询移除的灯必须保持移除状态
 - 被查询的单元本身可能包含一盏灯
 - 周围的 3x3 移除区域可能部分超出网格范围

 正确的解决方案必须有效支持：

 1. 快速照明检查
 2. 快速拆卸灯管
 3. 重复安全簿记

 ## 方法

 ### 蛮力方法

 一个简单的解决方案将明确地模拟照明过程。 

对于每个查询：

 1. 检查每个活跃的灯
 2、判断是否有灯共享：

 - 同一行
 - 同一列
 - 相同的对角线
 3. 如果任何灯匹配，则该单元被照亮
 4. 然后再次扫描所有活动灯并移除 3x3 邻域中的灯

 这种方法是正确的，因为它直接遵循问题定义。 每个查询都会与每个活动灯进行比较，因此不会错过任何亮起的灯。 

然而，这太慢了。 

如果有`L`灯和`Q`查询：

 - 每次照明检查费用`O(L)`- 每个移除阶段也需要花费`O(L)`整体复杂度变为`O(Q * L)`。 

两者都可能等于`20,000`，这样可以达到`400 million`操作量太大。 

### 最佳方法

 关键的观察是我们不需要确切地知道哪些细胞被照亮。 我们只需要知道至少一个活动灯是否影响所查询的单元即可。 

我们不是模拟整个网格的照明，而是维护计数：

 - 每行有多少个活动灯
 - 每列中有多少个活动灯
 - 每个主对角线上有多少个活动灯
 - 每个反对角线上有多少个活动灯

 然后是一个细胞`(r, c)`如果其中任何计数为正，则该灯会亮起：

 -`row_count[r] > 0`-`col_count[c] > 0`-`diag_count[r - c] > 0`-`anti_diag_count[r + c] > 0`这将照明检查转换为恒定时间哈希图查找。 

我们还维护活动灯位置的哈希集，以便可以有效地执行删除操作并安全地处理重复项。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(Q * L) | O(L) | 检查每个灯的每个查询 |
 | 最佳| O(L + Q) | O(L) | 使用哈希映射和哈希集进行恒定时间检查 |

 ## 算法演练

 1. 创建四个哈希映射来对活动灯进行计数：

 - 行
 - 专栏
 - 主对角线（`row - col`）
 - 反对角线（`row + col`）

 这些结构让我们能够在恒定时间内确定光照。 
2. 创建包含所有唯一活动灯位置的哈希集。 

这很重要，因为输入可能包含重复的灯。 我们只想对每个活动灯计数一次。 
3. 使用独特的灯位置初始化计数图。 

对于每盏灯`(r, c)`:

 - 增量`rows[r]`- 增量`cols[c]`- 增量`diag[r - c]`- 增量`anti[r + c]`4. 处理每个查询`(r, c)`。 

如果满足以下任一条件，则单元格将被照亮：

 -`rows[r] > 0`-`cols[c] > 0`-`diag[r - c] > 0`-`anti[r + c] > 0`如果有的话，请附加`1`到答案数组。 否则追加`0`。 
5. 回答查询后，检查以`(r, c)`。 

这包括：

 - 被查询的单元格本身
 - 所有八个相邻单元格
 6. 对于每个候选单元格`(nr, nc)`在该地区：

 - 验证它位于网格内
 - 检查活动灯组中是否存在

 如果灯存在：

 - 将其从集合中删除
 - 减少与其关联的所有四个计数器
 7. 继续，直到处理完所有查询。 

### 为什么它有效

 该算法保持一个不变量：

 - 散列图始终反映影响每行、列和对角线的当前活动灯的确切数量。 

当且仅当至少一个活动灯对这四种结构之一做出贡献时，被查询的单元才会被照亮。 由于每次灯插入和移除都会一致更新所有相关计数器，因此照明检查始终正确。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class Solution:
    def gridIllumination(
        self,
        n: int,
        lamps: List[List[int]],
        queries: List[List[int]]
    ) -> List[int]:

        rows = defaultdict(int)
        cols = defaultdict(int)
        diag = defaultdict(int)
        anti_diag = defaultdict(int)

        active_lamps = set()

        # Add unique lamps only
        for r, c in lamps:
            if (r, c) in active_lamps:
                continue

            active_lamps.add((r, c))

            rows[r] += 1
            cols[c] += 1
            diag[r - c] += 1
            anti_diag[r + c] += 1

        result = []

        directions = [
            (-1, -1), (-1, 0), (-1, 1),
            (0, -1),  (0, 0),  (0, 1),
            (1, -1),  (1, 0),  (1, 1)
        ]

        for r, c in queries:

            illuminated = (
                rows[r] > 0 or
                cols[c] > 0 or
                diag[r - c] > 0 or
                anti_diag[r + c] > 0
            )

            result.append(1 if illuminated else 0)

            # Turn off lamps in surrounding 3x3 area
            for dr, dc in directions:
                nr = r + dr
                nc = c + dc

                if not (0 <= nr < n and 0 <= nc < n):
                    continue

                if (nr, nc) not in active_lamps:
                    continue

                active_lamps.remove((nr, nc))

                rows[nr] -= 1
                cols[nc] -= 1
                diag[nr - nc] -= 1
                anti_diag[nr + nc] -= 1

        return result
```该实现首先构建四个频率图，跟踪照亮每行、每列和对角线的活动灯数量。 

这`active_lamps`set 可防止重复的灯被多次计数。 由于输入可能包含重复的灯坐标，因此此步骤对于正确性至关重要。 

在每次查询期间，仅使用四个哈希查找来检查照明。 这避免了扫描所有灯。 

这`directions`数组代表 3x3 邻域中的九个单元格。 对于每个附近的单元格，我们首先验证边界，然后检查是否存在灯。 如果是，我们将其删除并减少所有关联的计数器。 

哈希映射和集合上的每个操作都是预期的`O(1)`，这使得整个算法保持高效。 

## 解决方案```go
package main

func gridIllumination(n int, lamps [][]int, queries [][]int) []int {
	rows := make(map[int]int)
	cols := make(map[int]int)
	diag := make(map[int]int)
	antiDiag := make(map[int]int)

	active := make(map[[2]int]bool)

	// Add unique lamps only
	for _, lamp := range lamps {
		r, c := lamp[0], lamp[1]

		key := [2]int{r, c}

		if active[key] {
			continue
		}

		active[key] = true

		rows[r]++
		cols[c]++
		diag[r-c]++
		antiDiag[r+c]++
	}

	directions := [][2]int{
		{-1, -1}, {-1, 0}, {-1, 1},
		{0, -1}, {0, 0}, {0, 1},
		{1, -1}, {1, 0}, {1, 1},
	}

	result := make([]int, 0, len(queries))

	for _, query := range queries {
		r, c := query[0], query[1]

		illuminated := rows[r] > 0 ||
			cols[c] > 0 ||
			diag[r-c] > 0 ||
			antiDiag[r+c] > 0

		if illuminated {
			result = append(result, 1)
		} else {
			result = append(result, 0)
		}

		// Turn off lamps in surrounding 3x3 area
		for _, d := range directions {
			nr := r + d[0]
			nc := c + d[1]

			if nr < 0 || nr >= n || nc < 0 || nc >= n {
				continue
			}

			key := [2]int{nr, nc}

			if !active[key] {
				continue
			}

			delete(active, key)

			rows[nr]--
			cols[nc]--
			diag[nr-nc]--
			antiDiag[nr+nc]--
		}
	}

	return result
}
```Go 版本遵循与 Python 实现相同的算法结构。 

Go没有内置的元组类型，因此灯坐标使用固定大小的数组表示`[2]int`，可以用作地图键。 

Go 中的映射会自动返回缺失键的零值，这简化了照明检查，因为不存在的计数表现为`0`。 

实现使用`delete`从哈希集表示中删除活动灯。

 - 四次恒定时间照明检查

        cols = defaultdict(int)
        diag = defaultdict(int)
        anti_diag = defaultdict(int)

 ## 边缘情况

 一种重要的边缘情况是输入中存在重复的灯条目。 该问题明确允许重复坐标`lamps`。 简单的实现可能会对同一盏灯进行多次计数，从而导致行和对角线计数变得不正确。 此实现通过首先将灯存储在哈希集中并在初始化期间忽略重复项来避免该错误。 

当查询删除先前查询已删除的灯时，会出现另一个关键的边缘情况。 如果不检查灯是否仍处于活动状态，计数器可能会减少到零以下。 该解决方案安全地检查成员资格`active_lamps`在执行任何删除操作之前。 

边界处理也很重要，因为网格边缘或角落附近的查询具有有效范围之外的相邻单元格。 例如，查询`(0,0)`具有负坐标的邻居。 该实现明确验证：```
0 <= nr < n and 0 <= nc < n
```在尝试删除之前，防止无效访问。 

最后一个微妙的边缘情况涉及极大的网格尺寸。 自从`n`或许`10^9`，由于内存限制，任何尝试显式构建网格的解决方案都会立即失败。 此实现仅存储活动灯位置和聚合计数，因此内存使用量仅取决于灯的数量，而不取决于网格尺寸。
