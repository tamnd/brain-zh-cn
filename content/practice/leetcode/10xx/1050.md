[LeetCode 问题 1050](https://leetcode.com/problems/actors-and-directors-who-cooperated-at-least-third-times/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 这个问题要求我们识别每一个`(actor_id, director_id)`演员和导演至少合作过三次的组合。 

输入是一个名为的数据库表`ActorDirector`。 每一行代表演员和导演之间的一次合作事件。 该表包含三列：

 -`actor_id`，唯一标识一个演员
 -`director_id`，唯一标识一个董事
 -`timestamp`，唯一标识每个协作记录

 重要的细节是`timestamp`是主键，意味着每一行都是唯一的。 即使同一演员和导演多次合作，每次合作也会存储为具有不同时间戳的单独行。 

目标是返回在表中至少一起出现 3 次的所有演员和导演对。 换句话说，我们需要计算每个存在多少条记录`(actor_id, director_id)`组合并仅保留那些计数大于或等于的`3`。 

例如，如果演员`1`与导演合作`1`三次，该对应该出现在输出中。 如果演员`1`与导演合作`2`只有两次，该对不应该出现。 

由于这是一个数据库问题，因此预期的解决方案是基于 SQL 的。 问题所隐含的规模很简单，因为对分组记录进行计数是数据库优化的操作。 关键的观察是，除了每一行代表一次合作这一事实之外，我们并不关心单独的时间戳。 我们只关心每个演员和导演组合的频率。 

一些边缘情况值得预先考虑。 有些演员和导演组合可能会出现恰好三次，这些必须包括在内。 有些可能出现少于三次，必须将其排除。 可能存在多个限定对，并且可以按任何顺序返回结果。 该问题还保证了时间戳的唯一性，因此不可能出现主键重复导致的重复记录。 

## 方法

 ### 蛮力方法

 强力解决方案将手动计算每个可能的演员和导演对的合作。 

思考这个问题的一种方法是首先收集所有不同的`(actor_id, director_id)`组合。 然后，对于每一对，再次扫描整个表并计算有多少行与该演员和导演匹配。 如果计数至少达到 3，则将该对添加到结果中。 

这种方法之所以有效，是因为每一对都会根据每个协作记录进行明确检查，从而保证准确的计数。 但效率较低，因为可能会重复扫描表。 如果有`n`行和许多唯一的对，这种重复扫描变得不必要的昂贵。 

在数据库系统中，与数据库专门设计用于优化的聚合操作相比，重复迭代同一个表的效率较低。 

### 最佳方法

 关键的见解是这个问题本质上是一个分组和计数问题。 

我们想知道每次有多少次`(actor_id, director_id)`出现对。 SQL为此提供了一种直接机制`GROUP BY`。 一旦按演员和导演对行进行分组，我们就可以使用以下方法计算属于每个组的行数`COUNT(*)`。 

计算完这些计数后，我们只保留计数至少为`3`。 SQL 提供了`HAVING`专门用于过滤分组结果的子句。 

这种方法非常有效，因为数据库一次性对相关分组数据执行聚合，避免了重复扫描。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(1) | O(1) | 重复扫描表中的每一对 |
 | 最佳 | O(n) | O(n) | 用途`GROUP BY`和`HAVING`高效统计合作 |

 ## 算法演练

 1. 对表行进行分组`(actor_id, director_id)`。 

我们将每个演员和导演的组合视为一个独特的组，因为我们希望独立计算每个特定组合的合作。 
2. 计算每组中的行数。 

由于每一行代表一次合作，`COUNT(*)`给出演员和导演合作的总次数。 
3. 过滤数量至少为`3`。 

这`HAVING`使用子句代替`WHERE`因为过滤发生在聚合之后。 我们只需要协作数量大于或等于三的组。 
4. 返回`actor_id`和`director_id`列。 

该问题仅要求限定对，因此协作计数本身不需要包含在输出中。 

### 为什么它有效

 正确性来自以下事实：分组依据`(actor_id, director_id)`确保特定对的所有协作都收集在一起。 由于每一行恰好对应一个合作事件，因此对每组内的行进行计数即可得出该对的准确合作数量。 过滤用`HAVING COUNT(*) >= 3`保证结果中仅保留有效的对。 

## Python 解决方案

 虽然这是一个数据库问题，并且在 LeetCode 上没有使用 Python，但下面以编程方式演示了等效逻辑。```python
from collections import defaultdict
from typing import List

class Solution:
    def actorsAndDirectors(self, actorDirector: List[List[int]]) -> List[List[int]]:
        collaboration_count = defaultdict(int)

        for actor_id, director_id, _ in actorDirector:
            collaboration_count[(actor_id, director_id)] += 1

        result = []

        for (actor_id, director_id), count in collaboration_count.items():
            if count >= 3:
                result.append([actor_id, director_id])

        return result
```该实现使用哈希图，通过以下方式实现`defaultdict(int)`，有效地统计协作。 每个键都是一个元组`(actor_id, director_id)`相应的值存储该对出现的次数。 

我们对每个协作记录进行一次迭代，并增加相关对的计数。 时间戳值被忽略，因为计数不需要它。 

处理完所有记录后，我们迭代字典并收集计数至少为的每对记录`3`。 最终结果准确包含合格的演员和导演组合。 

### SQL 解决方案

 这是实际的 LeetCode 提交解决方案：```sql
SELECT actor_id, director_id
FROM ActorDirector
GROUP BY actor_id, director_id
HAVING COUNT(*) >= 3;
```该查询按演员和导演对行进行分组，对每对的合作进行计数，并进行筛选以仅保留至少有 3 次合作的合作。 

## 解决方案

 尽管 LeetCode 期望使用 SQL 来解决此问题，但以下 Go 实现反映了相同的计数逻辑。```go
package main

type pair struct {
	actorID    int
	directorID int
}

func actorsAndDirectors(actorDirector [][]int) [][]int {
	collaborationCount := make(map[pair]int)

	for _, record := range actorDirector {
		actorID := record[0]
		directorID := record[1]

		key := pair{
			actorID:    actorID,
			directorID: directorID,
		}

		collaborationCount[key]++
	}

	result := [][]int{}

	for key, count := range collaborationCount {
		if count >= 3 {
			result = append(result, []int{key.actorID, key.directorID})
		}
	}

	return result
}
```Go 实现使用自定义`pair`struct 作为映射键，因为 Go 映射不能直接使用切片作为键。 该地图追踪了每对演员和导演的合作次数。 

与 Python 不同，Go 需要显式的结构定义和类型化映射声明。 由于问题只涉及整数计数，因此在正常约束下不存在整数溢出的问题。

对于 SQL 解决方案，确切的复杂性取决于数据库实现和索引策略，但从概念上讲，它的行为就像对所有行进行分组操作。

 ## 边缘情况

 一个重要的边缘情况是一对合作恰好三次。 一个常见的错误是使用严格的比较，例如`COUNT(*) > 3`，这会错误地排除有效结果。 这个实现正确地使用了`>= 3`，确保包含准确的阈值情况。 

当多个演员和导演同时获得资格时，就会出现另一种边缘情况。 幼稚的实现可能会意外覆盖计数或仅返回一个结果。 由于该算法独立存储每个`(actor_id, director_id)`key，所有有效对都被保留并返回。 

第三种边缘情况是没有演员和导演达到所需的阈值。 某些实现可能会错误地返回部分结果或由于空集合而失败。 在这里，如果没有计数达到`3`，结果列表保持为空并正确返回。 

最后，由于计数机制独立地隔离了每一对，因此可以安全地处理具有许多独特协作的案例。 即使每一行包含不同的演员和导演组合，算法仍然可以正确处理数据，不会发生冲突或逻辑错误。
