[LeetCode 问题 1013](https://leetcode.com/problems/partition-array-into- Three-parts-with-equal-sum/)

 **难度：** 🟢简单
 **主题：** 数组、贪心

 ## 解决方案

 ## 问题理解

 问题给了我们一个整数数组`arr`并询问是否可以将其精确地分为三个非空连续部分，使得所有三个部分具有相同的总和。 

分区必须保留数组的原始顺序。 我们不允许重新排列元素。 相反，我们选择两个剪切位置将数组分割为：

 - 第 1 部分：`arr[0...i]`- 第 2 部分：`arr[i+1...j-1]`- 第 3 部分：`arr[j...n-1]`问题需要：

 - 每个部分必须至少包含一个元素
 - 三部分的总和必须相等

 如果存在这样的分区，我们返回`true`。 否则，我们返回`false`。 

关键的观察是，如果数组的总和不能被整除`3`，那么不可能存在三个等和划分。 每个分区必须贡献总和的三分之一。 

限制条件是：

 -`3 <= arr.length <= 5 * 10^4`-`-10^4 <= arr[i] <= 10^4`该数组可以包含负数、零和正数。 由于输入大小可以达到五万个元素，因此检查每对可能的分区边界等低效方法会太慢。 

一些边缘情况很重要：

 - 总和不能被整除的数组`3`- 包含许多零的数组
 - 带有负数的数组可能会导致总和波动
 - 等额部分和较早出现，但剩余部分为空的情况
 - 存在多个有效分区的数组

 该问题保证数组长度至少为`3`，因此形成三个非空部分至少在结构上是可能的。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是尝试每对可能的分区索引。 

我们选择：

 - 索引后第一次切割`i`- 索引前的第二次切割`j`然后我们计算：

 - 总和`arr[0...i]`- 总和`arr[i+1...j-1]`- 总和`arr[j...n-1]`如果任何对的所有三个总和都相等`(i, j)`，我们返回`true`。 

这种方法是正确的，因为它显式检查每个有效的分区配置。 然而，它的效率很低。 

有`O(n^2)`可能的分区对。 如果我们天真地计算每个分区的总和，复杂度就变成了`O(n^3)`。 即使有前缀和，它仍然需要`O(n^2)`检查，这对于`n = 5 * 10^4`。 

### 最优贪心法

 重要的见解是我们实际上不需要测试每个分区边界。 

假设总和是`S`。 

如果数组可以分为三个相等的部分，则每个部分的总和必须为：$$\frac{S}{3}$$那么问题就变成了：

 - 我们能找到一个带总和的前缀吗`target`- 然后再用 sum 加上另一个前缀`target`- 为最终分区保留至少一个元素

 我们扫描一次数组，同时保持运行总和。 

每当运行总和等于`target`，我们计算一个分区并将运行总和重置为零。 如果我们可以形成至少三个这样的分区，那么答案是`true`。 

贪心策略之所以有效，是因为在从左到右的遍历过程中自然形成了连续的分区。

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(1) 或 O(n) | 尝试每个可能的分区对 |
 | 最佳 | O(n) | O(1) | O(1) | 单遍贪婪积累 |

 ## 算法演练

 1. 计算数组的总和。 

我们首先计算所有元素的总和。 如果总和不能被整除`3`，那么三个相等的划分是不可能的，所以我们立即返回`false`。 
2. 计算目标分区总和。 

每个分区必须有总和：$$target = \frac{total}{3}$$3. 初始化变量。 

我们维持：

 -`current_sum`, 当前分区的运行总和
 -`partitions_found`，总和等于的分区数`target`4. 从左到右遍历数组。 

对于每个数字：

 - 添加到`current_sum`- 如果`current_sum == target`:

 - 增量`partitions_found`- 重置`current_sum`到`0`5. 检查是否至少找到三个分区。 

如果我们可以用 sum 形成至少三个连续的段`target`，则数组可以正确分区。 

否则，返回`false`。 

### 为什么它有效

 该算法依赖于这样一个事实：数组总和等于`3 * target`。 因此，每当我们用 sum 来识别两个较早的连续分区时`target`，其余元素的总和也必须为`target`。 

贪婪扫描永远不会错过有效的解决方案，因为分区是按顺序形成的，并且在遍历过程中自然保留了连续的边界。 

## Python 解决方案```python
from typing import List

class Solution:
    def canThreePartsEqualSum(self, arr: List[int]) -> bool:
        total_sum = sum(arr)

        if total_sum % 3 != 0:
            return False

        target = total_sum // 3

        current_sum = 0
        partitions_found = 0

        for num in arr:
            current_sum += num

            if current_sum == target:
                partitions_found += 1
                current_sum = 0

        return partitions_found >= 3
```实现首先计算数组的总和。 如果总和不能被整除`3`，函数立即返回`False`因为相等的划分在数学上是不可能的。 

接下来，我们使用整数除法计算每个分区所需的总和。 

然后该算法对数组执行一次遍历。 变量`current_sum`累加当前段的值。 每当运行总和达到目标值时，我们就将该段视为一个已完成的分区。 

找到这样的分区后，我们重置运行总和，以便下一个分区的累积重新开始。 

最后，如果发现至少三个有效分区，我们返回`True`。 

该实现不会显式跟踪分区索引，因为贪婪累积已经保证了连续的段。 

## 解决方案```go
func canThreePartsEqualSum(arr []int) bool {
    totalSum := 0

    for _, num := range arr {
        totalSum += num
    }

    if totalSum%3 != 0 {
        return false
    }

    target := totalSum / 3

    currentSum := 0
    partitionsFound := 0

    for _, num := range arr {
        currentSum += num

        if currentSum == target {
            partitionsFound++
            currentSum = 0
        }
    }

    return partitionsFound >= 3
}
```Go 实现遵循与 Python 版本相同的逻辑。 

Go切片直接用于遍历。 整数运算在这里是安全的，因为约束足够小，Go 的标准不关心溢出问题`int`类型。 

与 Python 不同，Go 不提供内置的`sum()`函数，因此总和是通过循环手动计算的。

 ## 边缘情况

 一种重要的边缘情况是总和不能被整除`3`。 在这种情况下，相等的划分在数学上是不可能的。 有错误的实现可能仍会尝试分区扫描并错误地返回`true`。 该实现通过执行早期的可分性检查来避免这种情况。 

另一个重要的情况是包含全零的数组，例如`[0,0,0]`。 目标分区总和变为零，这意味着每个前缀都可能看起来有效。 某些实现在找到两个分区后会错误地停止。 我们的实现正确地贪婪地计算分区并验证至少存在三个有效段。 

负数也会产生微妙的行为，因为运行总和可能会不可预测地增加和减少。 例如，前缀可能会超出目标并稍后返回目标。 简单的两指针方法在这里会失败。 贪婪运行和累加自然地处理负值，因为它只检查当前连续段是否等于目标和。 

最后一个微妙的边缘情况涉及确保分区非空。 假设我们太早找到两个有效分区，并且没有为第三个分区留下任何元素。 由于该算法在遍历期间仅计算已完成的连续段，因此最终分区必须包含剩余后缀中的实际元素。 这自然会强制执行非空要求。
