[LeetCode 问题 1090](https://leetcode.com/problems/largest-values-from-labels/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、贪心、排序、计数

 ## 解决方案

 ## 问题理解

 问题给了我们两个数组，`values`和`labels`，其中每个索引代表一个项目。 索引处的项目`i`有一个价值`values[i]`以及类别或组标识符`labels[i]`。 

我们想要选择这些项目的子集，以满足两个约束：

 - 我们最多可以选择`numWanted`总项目。 
- 对于任何特定标签，我们最多可以选择`useLimit`带有该标签的物品。 

在所有有效子集中，我们必须最大化所选值的总和。 

重要的细节是优化目标纯粹是值的总和。 标签仅起到限制作用，限制可以选择同一类别的项目数量。 

例如，如果几个项目的值非常大，但都共享相同的标签，我们可能不会被允许拿走所有这些项目，因为`useLimit`限制。 这迫使我们在选择高价值商品和尊重每个标签的限制之间取得平衡。 

约束很重要，因为它们告诉我们什么样的算法是可行的：

 -`n`可以大到`2 * 10^4`- 值和标签是整数`2 * 10^4`对所有子集进行强力搜索是不可能的，因为子集的数量呈指数增长。 和`n = 20000`，即使检查所有子集也是完全不可行的。 

这些约束强烈表明我们需要一个贪婪或基于排序的解决方案，其粗略的`O(n log n)`复杂。 

有几种边缘情况值得立即考虑：

 - 多个大值可能共享同一个标签，导致标签限制成为瓶颈。 
-`numWanted`可能大于我们实际允许携带的物品数量。 
- 某些值可能为零，这意味着选择它们可能不会改善答案。 
- 所有物品可能共用相同的标签。 
-`useLimit`或许`1`，这意味着每个标签只能获取一件商品。 
- 最佳解决方案可能使用少于`numWanted`项目，因为标签限制阻止了额外的选择。 

该问题保证两个数组具有相同的长度并且所有约束都有效，因此我们不需要处理格式错误的输入。 

## 方法

 ### 蛮力方法

 蛮力的想法是检查每个可能的项目子集。 对于每个子集，我们将：

 1. 计算有多少个项目被选中。 
2. 计算每个标签出现的次数。 
3. 验证子集满足两个约束。 
4. 计算总值。 
5. 跟踪最大有效金额。 

这种方法是正确的，因为它确实检查了每一种可能的解决方案并选择最好的解决方案。 

然而，它太慢了。 一套`n`项目有`2^n`可能的子集。 即使是为了`n = 30`，这已经太大了。 由于实际限制是`20000`，暴力破解是完全不可能的。 

### 最佳解决方案的关键见解

 关键的观察是，只要有可能，我们总是更喜欢较大的值而不是较小的值。 

假设我们有两个具有相同标签的项目，其中一个具有更大的值。 如果只允许我们取其中之一，我们应该总是取较大的一个。 

这自然会导致贪婪策略：

 1. 按价值降序对所有项目进行排序。 
2. 从最大到最小迭代项目。 
3. 如果出现以下情况，请选择一个项目：

 - 我们还有空间`numWanted`- 其标签未超标`useLimit`因为我们从最高值到最低值处理项目，所以每个选择都是局部最优的。 如果一件物品可以合法地包含在内，那么立即拿走它总是有益的，因为任何后来的物品都将具有相同或更小的价值。 

我们使用哈希图来跟踪每个标签已被使用的次数。 

这给出了一个有效的`O(n log n)`解决方案以排序为主。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(2^n * n) | O(2^n * n) | O(n) | 枚举所有子集并验证每个子集 |
 | 最佳| O(n log n) | O(n log n) | O(n) | 按值排序后的贪心选择 |

 ## 算法演练

 1. 将每个项目的值和标签组合成一对。 

我们需要一起处理两条信息，因此将它们存储为元组，例如`(value, label)`使得算法更容易实现。 
2. 按值降序对所有项目进行排序。 

这是核心的贪婪步骤。 通过首先检查最大值，我们可以尽早最大化总和。 
3. 创建哈希图来跟踪标签使用情况。 

地图存储每个标签已被选择的次数。 这允许恒定时间检查`useLimit`。 
4. 初始化变量：

 - 运行总和
 - 所选项目的数量
 5. 迭代已排序的项目。 

对于每个`(value, label)`对：

 - 检查标签是否已经到达`useLimit`。 
- 如果有，请跳过该项目。 
- 否则：

 - 为答案添加价值
 - 增加标签数量
 - 增加所选项目的数量
 6.停一次`numWanted`项目已被选择。 

由于项目是按降序处理的，一旦我们选择了足够的项目，剩余的项目就无法改善答案。 
7. 返回累计金额。 

### 为什么它有效

 该算法之所以有效，是因为贪婪排序。 

每一步，我们都会考虑最大的剩余价值。 如果选择它不违反约束，那么选择它总是最优的，因为每个未来候选者的价值都小于或等于当前候选者。 

不变量是：

 - 处理第一个之后`k`按排序顺序排列的项目，所选子集在所有有效子集中仅使用这些子集具有最大可能的总和`k`项目。 

由于该算法永远不会跳过有效的高价值项目而选择低价值项目，因此最终结果是全局最优的。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class Solution:
    def largestValsFromLabels(
        self,
        values: List[int],
        labels: List[int],
        numWanted: int,
        useLimit: int
    ) -> int:

        items = list(zip(values, labels))

        # Sort by value descending
        items.sort(reverse=True)

        label_count = defaultdict(int)

        total_sum = 0
        selected = 0

        for value, label in items:

            if label_count[label] >= useLimit:
                continue

            total_sum += value
            label_count[label] += 1
            selected += 1

            if selected == numWanted:
                break

        return total_sum
```实现首先使用将每个值与其相应的标签配对`zip`。 这为分类和处理创建了一个方便的结构。 

接下来，项目按降序排序。 Python 元组排序自动优先考虑第一个元素，即值。 

一个`defaultdict(int)`用于跟踪每个标签被选择的次数。 这避免了手动初始化检查。 

循环从最高值到最低值处理项目。 如果标签已经达到`useLimit`, the item is skipped. 否则，该值将添加到答案中并更新标签计数。 

算法提前停止一次`numWanted`项目已被选择。 这种优化避免了不必要的处理。 

最后返回累计的最大和。 

## 解决方案```go
package main

import "sort"

func largestValsFromLabels(values []int, labels []int, numWanted int, useLimit int) int {

	type Item struct {
		value int
		label int
	}

	n := len(values)

	items := make([]Item, n)

	for i := 0; i < n; i++ {
		items[i] = Item{
			value: values[i],
			label: labels[i],
		}
	}

	sort.Slice(items, func(i, j int) bool {
		return items[i].value > items[j].value
	})

	labelCount := make(map[int]int)

	totalSum := 0
	selected := 0

	for _, item := range items {

		if labelCount[item.label] >= useLimit {
			continue
		}

		totalSum += item.value
		labelCount[item.label]++
		selected++

		if selected == numWanted {
			break
		}
	}

	return totalSum
}
```Go 实现遵循与 Python 版本相同的逻辑，但使用自定义`Item`存储值标签对的结构。 

排序是用`sort.Slice`，使用自定义比较器按降序值对项目进行排序。 

一个`map[int]int`跟踪标签使用计数。 对于缺少的键，Go 映射会自动返回零值，因此不需要显式初始化。 

由于在问题约束下所有值都完全符合标准整数限制，因此整数溢出在 Go 中不是问题。

 ## 边缘情况

 当所有项目共享相同标签时，就会出现一种重要的边缘情况。 在这种情况下，`useLimit`成为可以选择的项目数量的真正上限，无论`numWanted`。 有错误的实现可能会继续选择太多项目，因为它只跟踪总数。 该解决方案通过在哈希图中维护精确的每个标签计数来避免这种情况。 

另一个重要的情况是当`numWanted`大于可以合法选择的项目数。 例如，如果所有项目共享一个标签并且`useLimit = 1`，我们可能只能选择一个项目，即使`numWanted = 10`。 该实现自然地处理了这个问题，因为它只选择有效的项目，并在没有更多有效选择时简单地完成迭代。 

第三种边缘情况涉及同一标签的重复高值。 考虑几个最高价值的商品都属于一个标签，而限制很小。 不仔细执行标签计数的天真贪婪实现可能会错误地从同一组中选择太多标签。 该解决方案在每次选择之前都会检查标签计数，确保始终遵守约束。 

另一个微妙的情况是值包含零。 由于目标是最大化总和，因此选择零值项目仅当它们有助于填充可用槽并在标签约束下保持有效时才有用。 贪婪排序仍然可以正常工作，因为首先处理较大的正值，并且仅在没有更好的剩余项时才选择零值项。
