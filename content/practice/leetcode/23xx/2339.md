[LeetCode 问题 2339](https://leetcode.com/problems/all-the-matches-of-the-league/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 的`Teams`表包含参加联赛的所有球队的名称。 每一行代表一个团队，并且`team_name`保证列包含唯一值。 

该问题要求我们根据以下规则生成联赛中每场可能的比赛：

 - 每对球队比赛两次。 
- 在一场比赛中，A队为主队，B队为客队。 
- 在另一场比赛中，B 队为主队，A 队为客队。 

这意味着我们必须生成不同团队的所有有序对。 

例如，如果我们有：

 -`Leetcode FC`-`Ahly SC`那么输出必须包含两者：

 -`(Leetcode FC, Ahly SC)`-`(Ahly SC, Leetcode FC)`重要的细节是团队不能与自己对抗。 因此，组合如下：

 -`(Leetcode FC, Leetcode FC)`绝不能出现在结果中。 

输入是单个表：

 | 专栏 | 意义|
 | --- | --- |
 |`team_name`| 团队名称 |

 预期输出包含：

 | 专栏 | 意义|
 | --- | --- |
 |`home_team`| 球队主场作战 |
 |`away_team`| 球队客场作战 |

 问题陈述允许以任何顺序返回结果，因此除非明确要求，否则我们不需要应用任何排序。 

由于这是一个数据库问题，因此主要挑战是使用 SQL 操作表达每个团队与其他团队之间的关系。 此类问题的自然运算是笛卡尔积，也称为交叉连接。 

一个重要的观察是，输入保证了唯一的团队名称。 这简化了逻辑，因为我们不需要担心重复的球队会产生重复的比赛。 

主要的边缘情况是表格仅包含一支球队时。 在这种情况下，不存在有效的比赛，因为球队无法自行比赛，因此结果应该为空。 

## 方法

 ### 蛮力方法

 蛮力的想法是手动将每个团队与其他团队进行比较。 

从概念上讲，我们可以将其视为两个嵌套循环：

 1. 选择一支球队作为主队。 
2. 再次遍历所有球队作为潜在客队。 
3. 跳过两队相同的情况。 
4. 输出剩余的对。 

这种方法保证产生所有有效的匹配，因为每个可能的有序对的不同球队都会被检查一次。 

在伪代码中，逻辑如下所示：```
for each team A:
    for each team B:
        if A != B:
            output (A, B)
```尽管这种方法很简单，但手动实现嵌套迭代并不是 SQL 的典型优化方式。 在 SQL 中，笛卡尔积运算已经以声明方式高效地执行此操作。 

### 最佳方法

 关键的观察是我们需要不同团队的所有有序对。 这正是`CROSS JOIN`产生。 

一个`CROSS JOIN`将第一个表中的每一行与第二个表中的每一行合并。 既然我们加入了`Teams`表格本身，我们生成每对可能的团队。 

然而，这也包括团队与自身配对的情况。 我们使用删除那些无效的匹配`WHERE`条款：```
WHERE t1.team_name != t2.team_name
```这为我们提供了每一个有效的主客场配对。 

该方案简洁高效，直接对问题需求进行建模。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(1) 不包括输出 | 手动比较每对球队 |
 | 最佳 | O(n²) | O(1) 不包括输出 | 使用 SQL CROSS JOIN 生成所有有序对 |

 ## 算法演练

 1. 从`Teams`表并使用别名创建它的两个逻辑副本，例如`t1`和`t2`。 

我们需要两份参考资料，因为一份代表主队，另一份代表客队。 
2. 执行`CROSS JOIN`之间`t1`和`t2`。 

交叉联接在两个表中的行之间创建所有可能的配对。 如果有`n`团队，这会产生`n × n`组合。 
3. 删除球队与自己比赛的无效比赛。 

我们应用条件：```
t1.team_name != t2.team_name
```这会过滤掉自我匹配，例如`(Real Madrid, Real Madrid)`。 
4. 选择具有适当名称的列。 

第一个表别名变为`home_team`，第二个就变成了`away_team`。 
5. 返回结果。 

由于该问题允许任何顺序，因此不需要排序。 

### 为什么它有效

 该算法之所以有效，是因为`CROSS JOIN`生成每对有序的团队。 过滤条件准确地删除无效的自我配对并保留所有不同的团队组合。 由于每个有效对在每个方向上出现一次，因此输出正确地代表了所有联赛。 

## Python 解决方案

 尽管这本质上是一个 SQL 问题，但 LeetCode 数据库解决方案通常直接用 SQL 编写。 下面是嵌入 Python 字符串中的完整 SQL 解决方案，用于演示目的。```python
class Solution:
    def allMatches(self):
        return """
        SELECT
            t1.team_name AS home_team,
            t2.team_name AS away_team
        FROM Teams t1
        CROSS JOIN Teams t2
        WHERE t1.team_name != t2.team_name
        """
```该解决方案使用同一个表的两个别名：

 -`t1`代表主队。 
-`t2`代表客队。 

这`CROSS JOIN`生成每个可能的对。 这`WHERE`条款删除了自我比赛，确保只保留有效的联赛比赛。 

由于有序对被保留，因此：

 -`(A, B)`-`(B, A)`出现在输出中。 

## 解决方案

 LeetCode数据库问题不需要Go实现，因为执行环境需要SQL查询。 然而，为了在算法上反映逻辑，等效的 Go 实现将如下所示。```go
package main

import "fmt"

type Match struct {
	HomeTeam string
	AwayTeam string
}

func allMatches(teams []string) []Match {
	var matches []Match

	for i := 0; i < len(teams); i++ {
		for j := 0; j < len(teams); j++ {
			if i != j {
				matches = append(matches, Match{
					HomeTeam: teams[i],
					AwayTeam: teams[j],
				})
			}
		}
	}

	return matches
}

func main() {
	teams := []string{
		"Leetcode FC",
		"Ahly SC",
		"Real Madrid",
	}

	result := allMatches(teams)

	for _, match := range result {
		fmt.Println(match.HomeTeam, "vs", match.AwayTeam)
	}
}
```Go 版本明确使用嵌套循环来模拟 SQL 自动执行的笛卡尔积`CROSS JOIN`。 

与 Python 或 SQL 不同，Go 需要一个自定义结构来表示每个匹配。 逻辑仍然相同：

 - 迭代每对团队。 
- 跳过相同的索引。 
- 将有效匹配存储在切片中。

 ## 边缘情况

 ### 单队

 如果表仅包含一支球队，则交叉联接仍会生成一行：```
(A, A)
```然而，过滤条件将其删除，因为球队不能与自己比赛。 最终结果为空。 如果忘记过滤步骤，幼稚的实现可能会意外地包含自匹配。 

### 两队

 如果恰好有两支球队，则应该恰好有两场比赛：```
(A, B)
(B, A)
```一些不正确的实现通过将关系视为无序而错误地仅生成一种组合。 该问题明确需要两个回家方向。 

### 自我匹配

 最常见的错误是忘记排除主客队相同的比赛。 由于交叉连接自然会创建这些组合，因此条件：```
WHERE t1.team_name != t2.team_name
```对于正确性至关重要。 

### 重复的团队名称

 该问题保证了`team_name`价值观是独一无二的。 这简化了逻辑，因为否则重复的行可能会生成重复的匹配项。 由于保证了唯一性，因此每个生成的对都对应于一个有效的匹配。
