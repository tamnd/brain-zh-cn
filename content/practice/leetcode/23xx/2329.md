 **难度：** 🟢简单

 ## 解决方案

 ## 问题理解

 这个问题要求我们计算每个用户在所有购买中花费了多少钱。 

我们有两个数据库表：

 的`Sales`表存储购买记录。 每行代表涉及用户购买的特定产品的交易以及购买的数量。 

这`Product`表存储每种产品的价格。 

要计算用户的总支出，我们必须合并两个表中的信息。 对于每一行`Sales`，我们通过乘以以下方式确定购买成本：```
quantity × product price
```然后我们将属于同一用户的所有购买成本相加。 

输出应包含：

 -`user_id`-`spending`，这是用户花费的总金额

 结果必须排序：

 1. 通过`spending`按降序排列
 2. 如果两个用户花费相同的金额，则`user_id`按升序排列

 重要的观察结果是`Sales`表不直接包含价格，因此我们必须将其与`Product`表使用`product_id`。 

该问题保证了每个`product_id`在`Sales`存在于`Product`， 因为`product_id`是外键。 这意味着我们永远不需要处理缺失的价格。 

尽管这被标记为简单数据库问题，但它仍然测试了几个重要的 SQL 概念：

 - 表连接
 - 聚合`SUM`- 分组为`GROUP BY`- 多级排序`ORDER BY`一些重要的边缘情况包括用户多次购买同一产品、用户具有相同的总支出以及产品出现在许多销售行中。 未正确聚合的简单实现可能会产生重复的行或不正确的总计。 

## 方法

 ### 蛮力方法

 从概念上讲，暴力方法将独立处理每个用户。 

对于每个用户，我们可以扫描整个`Sales`表查找他们的所有购买记录。 对于每次购买，我们都会扫描`Product`表格查找相应的产品价格。 在计算出每次购买的成本后，我们会将它们加在一起。 

这种方法是正确的，因为它显式地计算每个交易成本并累积每个用户的总计。 然而，它的效率很低，因为`Product`反复搜索表以寻找匹配的价格。 

如果有：

 -`S`销售行
 -`P`产品行
 -`U`用户

 那么重复扫描表格会导致不必要的重复工作。 

### 最佳方法

 最佳解决方案使用 SQL`JOIN`在一次操作中将销售信息与产品价格结合起来。 

加入后：

 - 每个销售行已包含其产品价格
 - 我们可以计算`quantity * price`- 然后使用汇总每个用户的总数`SUM`- 最后按照需要的顺序对结果进行排序

 关键的见解是关系数据库针对连接和聚合进行了优化。 数据库引擎无需重复手动搜索匹配产品，而是使用索引关系有效地匹配行。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(S × P) | O(U) | 每次销售时都会反复扫描产品表 |
 | 最佳| O(S + P) | O(U) | 高效使用连接和聚合 |

 ## 算法演练

 ### 最优 SQL 算法

 1. 从`Sales`表，因为它包含所有购买交易。 
2. 加入`Sales`表与`Product`表使用`product_id`。 

这一步是必要的，因为销售数据只告诉我们购买了多少单位，而产品表告诉我们每个单位的价格。 
3. 对于每个连接的行，计算交易成本：```sql
quantity × price
```这给出了单次购买的花费金额。 
4. 对所有行进行分组`user_id`。 

分组可确保将属于同一用户的所有购买收集在一起。 
5. 使用`SUM(quantity * price)`计算每个用户的总支出。 
6. Sort the results:

 - 首先由`spending`按降序排列
 - 然后通过`user_id`按升序排列打破平局
 7. 返回包含以下内容的最终表：

 -`user_id`-`spending`### 为什么它有效

 该算法之所以有效，是因为每个销售行都为一个用户贡献了一笔购买成本。 加盟保证每次购买都会收到正确的产品价格。 分组依据`user_id`确保同一用户的所有购买都累积在一起，并将交易成本相加得出正确的总支出。 

## Python 解决方案

 尽管这是一个数据库问题并且通常使用 SQL 解决，但为了清楚起见，可以使用 Python 演示等效逻辑。```python
from collections import defaultdict
from typing import List, Dict

class Solution:
    def productSalesAnalysis(
        self,
        sales: List[List[int]],
        products: List[List[int]]
    ) -> List[List[int]]:
        
        price_map: Dict[int, int] = {}

        for product_id, price in products:
            price_map[product_id] = price

        spending_map = defaultdict(int)

        for sale_id, product_id, user_id, quantity in sales:
            spending_map[user_id] += quantity * price_map[product_id]

        result = []

        for user_id, spending in spending_map.items():
            result.append([user_id, spending])

        result.sort(key=lambda x: (-x[1], x[0]))

        return result
```该实现首先构建一个哈希映射`product_id`到`price`。 这允许恒定时间的价格查找。 

接下来，代码迭代每个销售行。 对于每笔交易，它将购买数量乘以产品价格，并将结果添加到该用户的累计支出中。 

处理完所有事务后，结果列表按照问题要求排序：

 - 支出下降
 - 关系的升序用户 ID

 这反映了 SQL 解决方案中使用的确切逻辑。 

### SQL 解决方案```sql
SELECT
    s.user_id,
    SUM(s.quantity * p.price) AS spending
FROM Sales s
JOIN Product p
    ON s.product_id = p.product_id
GROUP BY s.user_id
ORDER BY spending DESC, s.user_id ASC;
```该查询直接在数据库引擎内执行整个计算。 

## 解决方案```go
package main

import (
	"sort"
)

type Result struct {
	UserID  int
	Spending int
}

func productSalesAnalysis(sales [][]int, products [][]int) [][]int {
	priceMap := make(map[int]int)

	for _, product := range products {
		productID := product[0]
		price := product[1]
		priceMap[productID] = price
	}

	spendingMap := make(map[int]int)

	for _, sale := range sales {
		productID := sale[1]
		userID := sale[2]
		quantity := sale[3]

		spendingMap[userID] += quantity * priceMap[productID]
	}

	result := [][]int{}

	for userID, spending := range spendingMap {
		result = append(result, []int{userID, spending})
	}

	sort.Slice(result, func(i, j int) bool {
		if result[i][1] == result[j][1] {
			return result[i][0] < result[j][0]
		}
		return result[i][1] > result[j][1]
	})

	return result
}
```Go 实现遵循与 Python 版本相同的逻辑。 

Go 地图用于恒定时间产品价格查找和累积支出聚合。 由于 Go 不像 Python 那样提供内置的元组排序，`sort.Slice`与自定义比较器功能一起使用。 

Go 整数算术在这里就足够了，因为约束足够小，标准整数类型可以安全地处理乘法和求和运算。

实际上，主要工作来自处理销售行和对用户总计进行排序。

 ## 边缘情况

 ### 具有相同支出的多个用户

 当两个或多个用户花费完全相同的金额时，就会出现一种微妙的情况。 仅按支出排序的解决方案可能会产生不一致的排序。 该实现通过添加辅助排序条件来处理此问题`user_id`按升序排列。 

### 多次购买同一产品

 用户可能会在多次不同的交易中购买相同的产品。 不正确的实现可能会覆盖以前的总数而不是累积它们。 该解决方案正确地将每笔交易成本添加到用户的运行总额中。 

### 单个产品表条目多次使用

 相同的产品可能会出现在许多销售行中。 在暴力解决方案中，反复搜索其价格是低效的。 优化的实现通过将价格存储在哈希图中以进行恒定时间查找来避免这种情况。 

### 整个数据集中的单个用户

 如果仅存在一个用户，则分组逻辑必须仍然正常工作并恰好返回一行。 由于该算法使用映射动态聚合，因此它自然可以处理这种情况，而不需要任何特殊情况逻辑。
