[LeetCode 问题 2365](https://leetcode.com/problems/task-scheduler-ii/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、模拟

 ## 解决方案

 ## 问题理解

 问题给了我们一个数组`tasks`，其中每个值代表一个任务类型。 任务必须严格按照给定的顺序完成，这意味着我们不能重新安排它们以优化进度。 

我们还得到一个整数`space`。 完成某种类型的任务后，我们至少必须等待`space`再次执行相同任务类型的天数。 在等待的日子里，我们要么执行其他任务，要么休息一下。 

目标是计算完成所有任务所需的最少总天数，同时遵守冷却时间规则。 

例如，假设我们执行任务类型`1`当天`2`和`space = 3`。 下次我们被允许执行任务类型`1`是一天`6`，因为两次执行之间必须至少间隔 3 天。 

约束条件很重要：

 -`tasks.length`可以大到`10^5`- 任务值可能非常大，最多可达`10^9`-`space`也可以很大

 这些限制立即告诉我们，日复一日地重复扫描进行模拟会太慢。 我们需要一种高效的解决方案，能够在近乎恒定的时间内处理每项任务。 

一个重要的观察是任务必须保持有序。 这消除了对堆或优先级队列等高级调度结构的需要。 每一步，我们只关心下一个任务是否可以立即执行，或者是否必须及时向前跳跃。 

一些重要的边缘情况包括：

 - 多个连续的相同任务，导致许多空闲时间
 - 非常大`space`价值观
 - 所有任务都是唯一的数组，这意味着不需要等待
 - 一项任务频繁重复的数组
 - 任务值较大，这意味着我们应该使用哈希映射而不是按任务 ID 索引的数组

 ## 方法

 ### 蛮力方法

 简单的模拟将日复一日地处理时间表。 

我们维护当前日期并反复检查下一个任务是否可以执行。 如果满足冷却条件，我们就执行任务。 否则，我们会增加该天并将其算作休息日。 

为了确定任务是否可以运行，我们将存储每种任务类型执行的最后一天。 

这种方法是正确的，因为它忠实地模拟了所描述的规则。 然而，当冷却时间造成较大间隙时，它就会变得低效。 例如，如果`space`非常大，我们可能会花费很多次迭代来简单地一次递增日期计数器。 

在最坏的情况下，模拟总天数可能会比任务数量大得多。 

### 最佳方法

 关键的见解是我们永远不需要单独模拟闲置的日子。 

假设我们现在是一天`current_day`，并且下一个任务类型最后执行日期是`last_day`。 

如果：```
current_day - last_day <= space
```然后我们就被迫等待。 我们可以直接跳转到第一个有效执行日，而不是逐日递增。 

最早有效日期为：```
last_day + space + 1
```这将问题转化为简单的线性扫描，并使用存储每个任务类型的最后执行日的哈希图。 

因为每个任务都被处理一次，所以解决方案变得非常高效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(总天数) | O(n) | 单独模拟每一天 |
 | 最佳| O(n) | O(n) | 直接跳转到下一个有效日|

 ## 算法演练

 1. 创建一个名为的哈希图`last_execution_day`。 

该地图存储执行每种任务类型的最近一天。 键为任务类型，值为最后执行日期。 
2. 初始化`current_day = 0`。 

该变量跟踪当前模拟的天数。 
3. 按顺序一项一项地处理任务。 

由于顺序是固定的，我们只需迭代`tasks`大批。 
4. 在尝试执行该任务之前，将当前日期加一。 

每个任务执行都会消耗一天的时间，因此我们首先转到第二天。 
5. 检查该任务以前是否见过。 

如果哈希映射中已存在该任务类型，则检索其上一个执行日期。 
6. 验证是否满足冷却时间要求。 

如果：```
current_day - previous_day <= space
```那么冷却时间还没有结束。 
7. 直接跳转至最早有效执行日。 

不要单独模拟中断，而是更新：```
current_day = previous_day + space + 1
```这会跳过所有不必要的中间日子。 
8. 记录任务的当前执行日期。 

更新哈希图，以便将来发生的事件可以正确执行冷却时间。 
9. 继续，直到处理完所有任务。 
10. 返回`current_day`。 

处理完所有任务后，该值表示所需的最小总天数。 

### 为什么它有效

 该算法始终将每个任务安排在最早的有效日期。 

如果冷却时间已经满足，我们立即执行。 否则，我们会跳转到满足冷却时间限制的第一个合法日期。 

由于任务必须保持有序，因此将任务延迟到最早的有效日期之后永远不会有任何好处。 因此，贪婪地选择最早的有效执行日会产生最小的总计划长度。 

## Python 解决方案```python
from typing import List

class Solution:
    def taskSchedulerII(self, tasks: List[int], space: int) -> int:
        last_execution_day = {}
        current_day = 0

        for task in tasks:
            current_day += 1

            if task in last_execution_day:
                previous_day = last_execution_day[task]

                if current_day - previous_day <= space:
                    current_day = previous_day + space + 1

            last_execution_day[task] = current_day

        return current_day
```实现直接遵循算法。 

字典`last_execution_day`存储每种任务类型的最近执行日。 由于任务值可以大到`10^9`，使用字典比分配一个巨大的数组实用得多。 

变量`current_day`跟踪当前的时间线。 对于每个任务，我们首先假设我们将通过递增在第二天执行它`current_day`。 

如果该任务之前出现过，我们检索它之前的执行日期并检查是否违反冷却时间规则。 如果是这样，我们使用以下命令直接跳转到最早的法定日期：```python
current_day = previous_day + space + 1
```最后，我们更新任务的最后执行日期并继续处理。 

由于每个任务都只处理一次，因此即使对于最大输入大小，该解决方案也能高效运行。 

## 解决方案```go
func taskSchedulerII(tasks []int, space int) int64 {
	lastExecutionDay := make(map[int]int64)
	var currentDay int64 = 0
	space64 := int64(space)

	for _, task := range tasks {
		currentDay++

		if previousDay, exists := lastExecutionDay[task]; exists {
			if currentDay-previousDay <= space64 {
				currentDay = previousDay + space64 + 1
			}
		}

		lastExecutionDay[task] = currentDay
	}

	return currentDay
}
```Go 实现密切反映了 Python 逻辑。 

一个重要的区别是整数处理。 函数签名需要返回`int64`，因此全天计算使用`int64`以避免总天数变大时出现溢出问题。 

Go 映射的使用方式与 Python 字典类似。 表达式：```go
previousDay, exists := lastExecutionDay[task]
```在单个操作中检查任务是否存在并检索其上一个执行日期。

 ## 边缘情况

 当所有任务都是唯一的时，就会出现一种重要的边缘情况。 在这种情况下，冷却时间规则并不重要，因为没有任务类型重复。 有缺陷的实现可能仍会尝试插入不必要的空闲时间。 该解决方案可以自然地处理这种情况，因为哈希图中不存在的任务会立即执行。 

另一个重要的情况是连续重复的任务，例如`[1,1,1]`。 这些输入强制执行之间的最大空闲天数。 不正确的实现通常会在计算下一个有效日时出现一个错误。 该解决方案正确地将下一次发生的时间安排在：```
previous_day + space + 1
```这完全保证了`space`相同任务之间的天数。 

第三种边缘情况涉及非常大的任务值，例如`10^9`。 由于内存使用问题，使用按任务 ID 索引的数组是不可能的。 此实现使用哈希映射，该映射仅存储实际出现的任务类型。 

最后一个微妙的情况是，由于干预任务，冷却时间已经自然满足。 例如：```
tasks = [1,2,3,1]
space = 2
```到了第二次的时候`1`已处理完毕，已经过去了足够的天数。 该算法能够正确检测到这一点，因为：```
current_day - previous_day > space
```所以不需要跳转。
