[LeetCode 问题 2323](https://leetcode.com/problems/find-minimum-time-to-finish-all-jobs-ii/)

 **难度：** 🟡 中等
 **主题：** 数组、贪婪、排序

 ## 解决方案

 ## 问题理解

 这个问题要求我们以最小化完成所有工作所需的总天数的方式向工人分配工作。 

我们有两个长度相等的整数数组：

 -`jobs[i]`代表所需的工作量`i-th`工作。 
-`workers[j]`代表了多少工作量`j-th`工人一天即可完成。 

每个工人必须准确地分配一项工作，并且每项工作必须准确地分配给一名工人。 一旦为工人分配了工作，该工人完成工作所需的天数为：$$\lceil \frac{\text{job}}{\text{worker}} \rceil$$这意味着如果工人能够完成`5`每天的单位和工作要求`12`单位，需要：$$\lceil 12/5 \rceil = 3$$天。 

目标是最大限度地减少**所有任务所需的最大天数**，因为所有工人都独立操作，并且在最慢的任务完成时完成工作。 

约束条件很重要：

 -`n`可以大到`10^5`- 工作规模和工人能力也可以达到`10^5`自从`n`很大时，任何阶乘或二次分配策略都太慢。 我们需要一个算法`O(n log n)`轻松处理输入大小。 

问题中还有几个保证：

 - 数组的长度始终相等。 
- 每个工人和工作都有积极的价值，因此不存在被零除的问题。 
- 每个工人必须得到一份工作。 

一个重要的观察结果是，糟糕的分配会大大增加最大完成时间。 例如，将最强的工人分配给最简单的工作，将最弱的工人分配给最难的工作可能会造成不必要的过长的完成时间。 

一些边缘情况立即脱颖而出。 如果只有一名工人和一份工作，答案就是该工人对该工作的最高分配。 如果所有工人都同样强大，那么只有工作顺序才重要。 如果所有工作都相同，配对选择仍然很重要，因为较弱的工人可能会成为瓶颈。 工人力量和工作规模之间的巨大不匹配可能会暴露贪婪推理的缺陷。 

## 方法

 ### 蛮力方法

 强力解决方案将尝试将工人分配给工作的**所有可能的分配**。 

由于必须为每个工人分配一份唯一的工作，因此这成为一个排列问题。 对于每种可能的工人-工作配对配置：

 1. 计算分配的每对所需的天数。 
2. 找出这些作业中的最长天数。 
3. 保留所有排列中的最小最大值。 

这保证了正确性，因为每个有效的分配都会被检查。 

然而，作业的数量是：$$n!$$为了`n = 10^5`，这是一个天文数字，完全不可行。 

即使是为了`n = 15`，暴力破解已经不切实际了。 

### 最佳解决方案的关键见解

 关键的见解来自贪婪匹配原则。 

假设我们想要最小化最差完成时间。 如果我们将一项非常大的工作分配给一个弱工人，而一个强工人正在处理一项简单的工作，那么弱工人就会成为瓶颈。 

为了减少最大完成时间，我们应该配对：

 - 工作规模较小，工人能力较弱
 - 更大的工作岗位和更强的工人

 这是贪婪匹配策略的一个例子，类似于最小化最大配对成本。 

我们对两个数组进行排序：

 - 排序`jobs`按升序排列。 
- 种类`workers`按升序排列。 

然后将相同索引处的元素配对。 

对于每一对，计算：$$\left\lceil \frac{\text{job}}{\text{worker}} \right\rceil$$答案是这些值中的最大值。 

为什么排序有效？ 

如果两个工人相对于工作难度来说是无序的，交换他们不会使最差完成时间变长，并且通常会改善它。 这是一个经典的交换论证。 将最强大的工人与最艰苦的工作配对可以最大限度地减少不平衡。

 | ---| ---| ---| ---|
 | 蛮力 | O(n! × n) | O(n! × n) | O(n) | 尝试每个分配排列 |

 ## 算法演练

 1. 排序`jobs`数组按升序排列。 

我们希望较小的工作首先出现，然后较大的工作出现。 这创造了难度的自然进展。 
2. 排序`workers`数组按升序排列。 

这会将较弱的工人放在第一位，然后将较强的工人放在后面。 
3. 将相同索引的作业和工人配对。 

最弱的工人接受最小的工作，第二弱的工人接受第二小的工作，依此类推。 
4. 对于每一对，计算所需的天数。 

由于工人可能无法完美地划分工作规模，因此我们使用上限划分：$$\left\lceil \frac{job}{worker} \right\rceil$$在整数运算中：```
(job + worker - 1) // worker
```这避免了浮点精度问题。 
5. 跟踪最大天数。 

由于所有作业都是独立运行的，因此总完成时间由最慢的分配决定。 
6. 返回找到的最大值。 

### 为什么它有效

 正确性来自贪婪交换论证。 如果将较大的作业分配给较弱的工作线程，而将较小的作业分配给较强的工作线程，则交换这些分配不会增加最大完成时间。 反复应用这个推理会导致工作和工人都按顺序排序和配对。 这可以最大限度地缩短所有作业的最坏情况完成时间。 

## Python 解决方案```python
from typing import List

class Solution:
    def minimumTime(self, jobs: List[int], workers: List[int]) -> int:
        jobs.sort()
        workers.sort()

        minimum_days = 0

        for job, worker in zip(jobs, workers):
            days_needed = (job + worker - 1) // worker
            minimum_days = max(minimum_days, days_needed)

        return minimum_days
```实现首先对两个数组进行排序。 这建立了最佳配对顺序，其中较弱的工人获得较小的工作，而较强的工人获得较大的工作。 

排序后，我们使用以下方法同时迭代两个数组`zip`。 对于每一个`(job, worker)`对，我们使用上限除法计算所需的天数：```python
(job + worker - 1) // worker
```该公式无需浮点运算即可正确计算上限。 

我们持续跟踪最大天数，因为总体完成时间是由最慢的工人作业分配决定的。 最后，我们返回该最大值。 

## 解决方案```go
package main

import "sort"

func minimumTime(jobs []int, workers []int) int {
	sort.Ints(jobs)
	sort.Ints(workers)

	maxDays := 0

	for i := 0; i < len(jobs); i++ {
		daysNeeded := (jobs[i] + workers[i] - 1) / workers[i]

		if daysNeeded > maxDays {
			maxDays = daysNeeded
		}
	}

	return maxDays
}
```Go 实现遵循与 Python 版本完全相同的逻辑。 我们使用以下方法对两个切片进行排序`sort.Ints`，迭代匹配索引，使用整数算术计算上限除法，并维护最大值。 

Go 在这里不需要对整数溢出进行特殊处理，因为约束足够小。 最大中间值最多为：$$10^5 + 10^5 - 1$$很容易适合 Go 的内部`int`类型。 

由于切片是就地修改的，所以原来的顺序被覆盖了，就像Python的就地一样`.sort()`。

 ## 边缘情况

 一个重要的边缘情况是只有一个工作和一个工人。 幼稚的实现可能会使逻辑过于复杂或索引处理不当。 由于数组总是具有相等的长度，我们的实现自然会处理这种情况，因为对单元素数组进行排序不会改变任何内容，并且循环只执行一次。 

当工人明显强于分配的工作时，就会出现另一个重要的边缘情况。 例如，`jobs = [1, 2, 3]`和`workers = [100, 100, 100]`。 整数除法可能是这里错误的来源，因为标准除法会错误地产生`0`如果直接使用楼层划分。 我们的上限除法公式确保每项非零工作至少需要一天。 

第三个重要的边缘情况是工人力量高度不平衡。 考虑`jobs = [10, 10, 10]`和`workers = [1, 2, 100]`。 糟糕的分配策略可能会将最强大的工人与一份轻松的工作配对，而让最弱的工人超负荷工作，从而增加最大完成时间。 排序保证平衡匹配，最大限度地减少瓶颈。 

最后，未排序的输入是一个重要的实际案例。 该问题不保证任一数组的任何顺序。 由于我们的实现在配对之前显式对两个数组进行排序，因此无论输入顺序如何，它总是计算最佳分配。
