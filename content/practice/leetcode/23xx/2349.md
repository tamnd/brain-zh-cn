 # LeetCode 2349 - 设计数字容器系统

 ## 问题理解

 该问题要求我们设计一个有效支持两种操作的数据结构：

 1. 为给定索引分配一个数字。 
2. 查找当前分配给给定数字的最小索引。 

重要的细节是`change(index, number)`操作既可以插入值也可以替换值。 如果索引已包含数字，则旧数字将被覆盖。 

这`find(number)`操作必须返回当前映射到该数字的最小索引。 如果没有索引包含该数字，我们返回`-1`。 

从概念上讲，我们正在维护这样的动态映射：```
index -> number
```但查询操作是相反的：```
number -> smallest index
```这意味着仅单向映射是不够的。 我们需要一种有效地回答反向查找的方法。 

约束条件很重要：

 - 最多`10^5`业务总计
 - 索引和数值可以大到`10^9`大的值范围告诉我们不能使用直接按值索引的数组。 我们需要基于哈希的结构，例如字典或地图。 

操作计数还告诉我们`O(n)`扫描每个`find()`在最坏的情况下会变得太慢。 我们需要接近对数或常数时间的运算。 

一些边缘情况很重要：

 - 通话`find()`对于一个不存在的数字
 - 用不同的数字替换现有的索引
 - 将相同的数字重新分配给相同的索引
 - 多个索引共享相同的编号
 - 由于替换而删除数字的最小索引

 简单的实现很容易留下过时的数据，尤其是在替换之后。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是仅维护从索引到数字的哈希映射。```
indexToNumber[index] = number
```当我们打电话时`change(index, number)`，我们只需更新映射即可。 

当我们打电话时`find(number)`，我们迭代每个存储的索引并检查哪些索引当前包含请求的数字。 在这些匹配中，我们返回最小的索引。 

这是正确的，因为我们每次都会检查整个状态，因此永远不会错过有效的索引。 

然而，性能较差。 如果有`n`存储的索引，然后每个`find()`运营成本`O(n)`时间。 高达`10^5`操作，在最坏的情况下这可能会变成二次方。 

### 最佳方法

 关键的观察是`find(number)`总是要求与数字关联的最小索引。 

这自然建议对每个数字使用一个最小堆。 

我们维持：

 1. 从索引到当前数字的哈希映射
 2. 从数字到索引最小堆的哈希映射

 当我们为一个数字分配一个索引时，我们将该索引推入该数字的堆中。 

挑战在于处理替代品。 

假设索引`1`先前包含的`10`，现在我们将其更改为`20`。 堆为`10`仍然包含索引`1`。 有效地从堆中删除任意元素是很困难的。 

我们不使用立即删除，而是使用延迟删除。 

期间`find(number)`，我们反复检查堆的顶部索引。 如果该索引不再映射到请求的数字，则它已过时，因此我们将其弹出。 最终，堆顶变得有效，或者堆变空。 

这提供了高效的操作，同时避免了昂贵的堆删除。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 |`O(n)`每`find`|`O(n)`| 扫描所有索引以找到最小匹配 |
 | 最佳|`O(log n)`摊销|`O(n)`| 使用带有延迟删除功能的哈希映射和堆 |

 ## 算法演练

 1. 创建一个名为的哈希图`index_to_number`。 

这存储分配给每个索引的当前编号。```
index_to_number[index] = number
```2. 创建另一个哈希映射，名为`number_to_heap`。 

每个数字映射到一个最小堆，其中包含曾经分配给该数字的所有索引。```
number_to_heap[number] = min-heap of indices
```3.为了`change(index, number)`：

- 更新`index_to_number[index] = number`- 将索引推入该数字的堆中

 我们不会尝试从任何旧堆中删除索引，因为堆删除的成本很高。 
4. 对于`find(number)`：

 - 查看堆中是否有请求的数字
 - 当堆不为空时：

 - 检查顶部的最小索引
 - 如果`index_to_number[top] == number`，这个索引是有效的，所以返回它
 - 否则，索引已过时，因为它后来被重新分配，因此将其弹出
 5. 如果堆变空，则返回`-1`。 

### 为什么它有效

 每个数字的堆始终包含分配给该数字的每个索引，包括过时的条目。 这`index_to_number`map 存储真实的当前状态。 

期间`find(number)`，我们丢弃陈旧的堆条目，直到堆顶代表有效的当前分配。 由于堆始终首先公开最小元素，因此遇到的第一个有效索引必须是该数字的最小有效索引。 

这个不变量保证了正确性。 

## Python 解决方案```python
from collections import defaultdict
from heapq import heappush, heappop
from typing import Dict, List

class NumberContainers:

    def __init__(self):
        self.index_to_number: Dict[int, int] = {}
        self.number_to_heap: Dict[int, List[int]] = defaultdict(list)

    def change(self, index: int, number: int) -> None:
        self.index_to_number[index] = number
        heappush(self.number_to_heap[number], index)

    def find(self, number: int) -> int:
        heap = self.number_to_heap[number]

        while heap:
            smallest_index = heap[0]

            if self.index_to_number.get(smallest_index) == number:
                return smallest_index

            heappop(heap)

        return -1

# Your NumberContainers object will be instantiated and called as such:
# obj = NumberContainers()
# obj.change(index, number)
# param_2 = obj.find(number)
```该实现完全按照算法中的描述使用两个字典。 

这`index_to_number`字典存储分配给每个索引的最新值。 这代表了系统的权威状态。 

这`number_to_heap`字典将每个数字映射到候选索引的最小堆。 我们使用`defaultdict(list)`因此堆会在需要时自动创建。 

在`change()`，我们覆盖当前映射​​并将索引推送到与该数字关联的堆中。 

在`find()`，我们反复检查堆顶。 如果顶部索引仍然映射到请求的数字，则它是有效的并立即返回。 否则，它就会过时并被删除。 

惰性删除策略是保持操作高效的关键优化。 

## 解决方案```go
package main

import (
	"container/heap"
)

type IntHeap []int

func (h IntHeap) Len() int {
	return len(h)
}

func (h IntHeap) Less(i, j int) bool {
	return h[i] < h[j]
}

func (h IntHeap) Swap(i, j int) {
	h[i], h[j] = h[j], h[i]
}

func (h *IntHeap) Push(x interface{}) {
	*h = append(*h, x.(int))
}

func (h *IntHeap) Pop() interface{} {
	old := *h
	n := len(old)
	value := old[n-1]
	*h = old[:n-1]
	return value
}

type NumberContainers struct {
	indexToNumber map[int]int
	numberToHeap  map[int]*IntHeap
}

func Constructor() NumberContainers {
	return NumberContainers{
		indexToNumber: make(map[int]int),
		numberToHeap:  make(map[int]*IntHeap),
	}
}

func (this *NumberContainers) Change(index int, number int) {
	this.indexToNumber[index] = number

	if _, exists := this.numberToHeap[number]; !exists {
		h := &IntHeap{}
		heap.Init(h)
		this.numberToHeap[number] = h
	}

	heap.Push(this.numberToHeap[number], index)
}

func (this *NumberContainers) Find(number int) int {
	h, exists := this.numberToHeap[number]

	if !exists {
		return -1
	}

	for h.Len() > 0 {
		smallestIndex := (*h)[0]

		if this.indexToNumber[smallestIndex] == number {
			return smallestIndex
		}

		heap.Pop(h)
	}

	return -1
}

/**
 * Your NumberContainers object will be instantiated and called as such:
 * obj := Constructor();
 * obj.Change(index, number);
 * param_2 := obj.Find(number);
 */
```Go 版本遵循相同的整体设计，但需要使用显式堆实现`container/heap`包裹。 

与Python内置的不同`heapq`，Go 需要定义方法，例如`Len`,`Less`,`Swap`,`Push`， 和`Pop`。 

Go 实现将堆指针存储在映射内，因此堆操作直接修改原始堆。 

Go 映射对于缺少的键返回零值，因此我们在访问堆之前显式检查堆是否存在。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 |`O(log n)`摊销| 堆插入和删除需要对数时间 |
 | 空间|`O(n)`| 映射和堆最多存储所有操作 |

 每个`change()`操作执行堆插入，其成本`O(log n)`。 

每个陈旧的堆条目在所有未来中最多被删除一次`find()`运营。 由于这种摊销行为，总成本在所有操作中仍然有效。 

空间复杂度是线性的，因为我们存储与操作数量成比例的映射和堆条目。

 ## 边缘情况

 当索引被重新分配给不同的编号时，就会出现一种重要的边缘情况。 这会在旧号码的堆内创建过时的条目。 幼稚的堆实现可能会错误地返回过时的索引。 惰性删除策略通过根据权威验证堆顶来防止这种情况发生`index_to_number`归还之前的地图。 

另一个重要的边缘情况是多次将相同的数字分配给相同的索引。 这会在堆中创建重复的条目。 该实现仍然可以正常工作，因为所有重复项都指向相同的有效映射。 即使存在冗余堆条目，也可以保留正确性。 

第三个重要的边缘情况是调用`find()`位于从未插入过的号码上。 如果不仔细处理，这可能会产生关键错误或无效的堆访问。 该实现通过返回来安全地处理丢失的条目`-1`。 

当最小的有效索引在重新分配后变得陈旧时，就会出现一种微妙的情况。 例如，如果索引`[1, 2, 3]`属于号码`10`和索引`1`更改为`20`，堆为`10`仍含有`1`。 期间`find(10)`，该算法会删除陈旧的条目，直到到达下一个有效的最小索引，即`2`。
