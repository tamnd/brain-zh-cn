[LeetCode 问题 2372](https://leetcode.com/problems/calculate-the-influence-of-each-salesperson/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题要求我们计算分配给每个销售人员的客户所产生的总销售价值。 

我们得到三个数据库表：

 的`Salesperson`表包含销售人员列表。 每个销售人员都有独特的`salesperson_id`和一个`name`。 

这`Customer`表将客户映射到销售人员。 每个客户都属于一位销售人员`salesperson_id`foreign key.

 这`Sales`table records purchases made by customers. 每笔销售包含一个`customer_id`以及相应的`price`。 

目标是生成一个结果表，其中包含：

 -`salesperson_id`-`name`-`total`，分配给该销售人员的客户的所有销售额的总和

 一个非常重要的细节是，没有客户或从未购买过客户的销售人员仍然必须出现在输出中，总计`0`。 

从概念上讲，关系链是：`Salesperson -> Customer -> Sales`我们需要汇总整个关系链的销售价值。 

该问题从根本上来说是一个涉及连接和分组的数据库聚合问题。 

The input guarantees:

 - 每个销售员 ID 都是唯一的。 
- 每个客户 ID 都是唯一的。 
- 外键关系有效。 
- 销售参考现有客户。 

最重要的边缘情况是：

 - 没有顾客的销售员。 
- 没有销售的客户。 
- 多个客户分配给同一销售人员。 
- 同一客户进行多次销售。 
- 空的中间关系，其中联接可能会意外删除行。 

仅使用内部联接的简单实现将会失败，因为没有客户或销售的销售人员将从结果中消失。 这就是为什么正确处理缺失的关系至关重要。 

## 方法

 ### 蛮力方法

 蛮力方法将独立处理每个销售人员。 

For every salesperson:

1. Scan the`Customer`表查找属于该销售人员的所有客户。 
2. 对于每个匹配的客户，扫描`Sales`表查找所有购买。 
3. 将所有相应价格相加。 
4. 存储最终结果。 

这是有效的，因为每个销售人员都会明确检查所有可能的客户以及与他们相关的销售记录。 

然而，这种方法效率低下，因为它会重复扫描大表。 如果有`S`销售人员，`C`客户，以及`N`销售行，重复扫描会产生不必要的工作。 

随着数据集的增长，暴力方法变得昂贵，因为相同的销售行可能会被扫描多次。 

### 最佳方法

 关键在于 SQL 数据库是为关系聚合而设计的。 

我们可以：

 1. 将表连接一次。 
2. 使用以下方法汇总所有销售额`SUM`。 
3. 按销售人员分组。 

主要挑战是保留没有匹配客户或销售的销售人员。 这是使用解决的`LEFT JOIN`。 

最优解执行：

 -`Salesperson LEFT JOIN Customer`-`Customer LEFT JOIN Sales`然后它按销售人员分组并计算：```
COALESCE(SUM(price), 0)
```

`COALESCE`皈依者`NULL`总计为`0`。 

这种方法避免了重复扫描并利用 SQL 的优化连接和聚合操作。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(S * C * N) | O(1) | O(1) | 反复扫描每个销售人员的客户和销售情况 |
 | 最佳| O(C + N) | O(1) 额外 | 有效地使用连接和聚合 |

 ## 算法演练

 1. 从`Salesperson`表，因为每个销售人员都必须出现在输出中，即使他们没有客户或销售。 
2. 执行`LEFT JOIN`从`Salesperson`到`Customer`使用`salesperson_id`。 这确保了所有销售人员都保留在中间结果中，包括那些没有客户的销售人员。 
3. 执行另一个`LEFT JOIN`从`Customer`到`Sales`使用`customer_id`。 这会附加每个客户的所有购买行为。 
4. 按以下方式对结果行进行分组：

 -`salesperson_id`-`name`分组使我们能够独立计算每个销售人员的总数。 
5. 使用`SUM(price)`计算所有关联客户产生的总收入。 
6. 某些销售人员可能没有任何匹配的销售行。 在这种情况下，`SUM(price)`变成`NULL`。 使用`COALESCE(SUM(price), 0)`取代`NULL`和`0`。 
7. 返回最终分组结果。 

### 为什么它有效

 该算法之所以有效，是因为连接正确地模拟了销售人员、客户和销售人员之间的关系链。`LEFT JOIN`保证丢失的客户或销售不会将销售人员从结果中删除。 按销售人员对行进行分组，并对每个组内的价格求和产生所需的总影响力值。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    sp.salesperson_id,
    sp.name,
    COALESCE(SUM(sa.price), 0) AS total
FROM Salesperson sp
LEFT JOIN Customer c
    ON sp.salesperson_id = c.salesperson_id
LEFT JOIN Sales sa
    ON c.customer_id = sa.customer_id
GROUP BY sp.salesperson_id, sp.name;
```查询开始于`Salesperson`表，因为每个销售人员都必须出现在输出中。 

第一个`LEFT JOIN`connects each salesperson with their customers. 如果销售人员没有客户，该行仍会保留`NULL`客户列的值。 

第二个`LEFT JOIN`将客户与其销售记录联系起来。 未购买的客户仍保留在结果中。 

这`GROUP BY`子句为每个销售人员创建一个组。 在每个组内，`SUM(sa.price)`计算合并销售额。 

当销售人员没有匹配的销售行时，总和变为`NULL`。`COALESCE`转换为`NULL`进入`0`，符合问题要求。

 ## 边缘情况

 ### 没有顾客的销售员

 销售人员可能存在于`Salesperson`表中没有任何关联客户`Customer`桌子。 解决方案使用`INNER JOIN`会意外地从结果中完全删除该销售人员。 

此实现通过使用避免了该问题`LEFT JOIN`。 即使不存在匹配的客户，销售人员行仍然存在。 由此产生的`NULL`销售总额转换为`0`使用`COALESCE`。 

### 没有销售的客户

 有些顾客可能永远不会出现在`Sales`桌子。 如果不小心处理，聚合可能会跳过这些行或产生不正确的总计。 

因为查询使用`LEFT JOIN`从`Customer`到`Sales`，没有购买的客户仍然是分组结果的一部分。 它们缺失的销售值对总和没有贡献，最终的总和变为`0`如果根本不存在销售。 

### 每个客户的多次销售

 一个顾客可能有很多条购买记录。 幼稚的实现可能会意外地只计算一笔销售或覆盖以前的总计。 

该解决方案自然可以处理多行，因为 SQL 聚合独立处理每个连接的销售记录。`SUM(price)`自动累积所有匹配的行。 

### 每个销售员有多个客户

 一名销售人员可能管理许多客户，每个客户都有很多销售额。 不正确的分组可能会混淆销售人员的总数。 

查询显式分组为`salesperson_id`和`name`，确保每个销售人员收到一个独立的聚合范围。
