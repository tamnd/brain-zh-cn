[LeetCode 第 668 题](https://leetcode.com/problems/kth-smallest-number-in-multiplication-table/)

 **难度：** 🔴难
 **主题：** 数学、二分查找

 ## 解决方案

 ## 问题理解

 这个问题给了我们一个`m x n`乘法表，其中每个单元格包含其行索引和列索引的乘积，使用基于 1 的索引。 这意味着位置的值`(i, j)`简直就是`i * j`。 

例如，当`m = 3`和`n = 3`，乘法表如下所示：

 | | 1 | 2 | 3 |
 | --- | --- | --- | --- |
 | 1 | 1 | 2 | 3 |
 | 2 | 2 | 4 | 6 |
 | 3 | 3 | 6 | 9 |

 如果我们对所有值进行扁平化和排序，我们会得到：`[1, 2, 2, 3, 3, 4, 6, 6, 9]`任务是返回`k`此排序顺序中的第最小值。 

一个重要的细节是重复值单独计算。 例如，值`2`上表中出现两次，在确定`k`最小的元素。 

约束条件极其重要：

 -`1 <= m, n <= 3 * 10^4`-`1 <= k <= m * n`因此，乘法表最多可以包含：```
30000 * 30000 = 900,000,000
```元素。 

这立即告诉我们显式生成所有值是不可能的。 即使存储表也需要太多的内存，并且对数亿个值进行排序将非常昂贵。 

这些限制强烈表明我们需要一种基于数学或二分搜索的解决方案，而不是直接模拟。 

一些边缘情况值得尽早认识：

 - 非常小的桌子，例如`1 x 1`- 非常长方形的桌子，例如`1 x 30000`- 存在许多重复值的情况
 - 情况`k = 1`，这意味着我们需要最小值
 - 情况`k = m * n`，这意味着我们需要最大值
 - 大量输入，暴力破解会立即超时

 该问题保证了有效的输入，因此我们永远不需要处理无效的尺寸或超出范围`k`。 

## 方法

 ### 蛮力方法

 最直接的解决方案是生成乘法表中的每个值，将它们存储在数组中，对数组进行排序，然后返回`k`第一个元素。 

对于每一行`i`从`1`到`m`，以及每一列`j`从`1`到`n`，我们计算：```
i * j
```收集所有值后，我们按升序对数组进行排序并返回索引处的元素`k - 1`。 

这是有效的，因为排序会产生乘法表值的精确顺序，包括重复项。 

然而，这种方法对于给定的约束是完全不切实际的。 该表最多可包含 9 亿个值。 生成、存储和排序这么多整数将超出内存和时间限制。 

### 关键见解

 关键的观察是我们实际上不需要生成表。 

相反，我们可以对答案本身进行二分搜索。 

假设我们猜一个数字`x`。 我们可以有效地确定乘法表中有多少个值小于或等于`x`。 

对于固定行`i`，行值为：```
i, 2i, 3i, 4i, ...
```该行中数字的个数`<= x`是：```
min(n, x // i)
```因为：

-`x // i`告诉我们有多少个倍数`i`适合`x`- 我们不能超过行长度`n`对所有行求和得出表值的总数小于或等于`x`。 

这种计数操作允许我们在值范围内执行二分搜索`[1, m * n]`。 

如果至少`k`数字是`<= x`，那么答案可能是`x`或更小。 

否则，答案一定更大。 

这将问题从不可能的显式生成转化为高效计数加二分搜索。

 ## 算法演练

 1. 初始化二分查找范围。 

乘法表中的最小可能值是`1`。 

最大可能值为`m * n`。 

因此，我们在以下范围内进行搜索：```
left = 1
right = m * n
```2. 对取值范围进行二分查找。 

在每次迭代时，计算：```
mid = (left + right) // 2
```目标是确定是否`k`最小的数小于或等于`mid`。 
3. 统计有多少个表值小于或等于`mid`。 

对于每一行`i`从`1`到`m`:```
count += min(n, mid // i)
```这是有效的，因为行`i`包含：```
i, 2i, 3i, ..., ni
```和`mid // i`告诉我们有多少个倍数`i`至多是`mid`。 
4. 使用计数来缩小搜索空间。 

如果：```
count >= k
```那么至少已经有`k`值小于或等于`mid`。 

这意味着答案不大于`mid`，所以我们向左移动：```
right = mid
```否则：```
left = mid + 1
```因为答案一定更大。 
5. 继续直到搜索收敛。 

二分查找在以下情况下停止：```
left == right
```在那一刻，我们找到了最小的数字，使得至少`k`值小于或等于它。 

### 为什么它有效

 关键的不变量是真实答案始终保留在二分搜索范围内。 

对于任何候选值`x`，计数函数正确计算乘法表条目的数量`<= x`。 

如果少于`k`值是`<= x`， 然后`x`肯定是太小了。 

如果至少`k`值是`<= x`，那么答案可能是`x`或更小。 

因为count函数是单调的，意味着更大`x`值永远不会减少计数，二分查找保证收敛到最小的有效值，这正是`k`最小的数字。 
## Python 解决方案```python
class Solution:
    def findKthNumber(self, m: int, n: int, k: int) -> int:
        def count_less_equal(value: int) -> int:
            count = 0

            for row in range(1, m + 1):
                count += min(n, value // row)

            return count

        left = 1
        right = m * n

        while left < right:
            mid = (left + right) // 2

            if count_less_equal(mid) >= k:
                right = mid
            else:
                left = mid + 1

        return left
```实现直接遵循二分搜索策略。 

辅助函数`count_less_equal`计算乘法表中有多少个数字小于或等于给定值。 

对于每一行，表达式：```python
value // row
```确定有多少个倍数`row`适合`value`。 

由于每一行只有`n`列，我们使用以下方法限制计数：```python
min(n, value // row)
```二分查找保留了一系列可能的答案。 当计数足够大时，我们就知道答案最多是`mid`，所以我们缩小右边界。 否则，我们增加左边界。 

最终，两个指针都收敛到最小的有效数，这就是答案。 

## 解决方案```go
func findKthNumber(m int, n int, k int) int {
	countLessEqual := func(value int) int {
		count := 0

		for row := 1; row <= m; row++ {
			count += min(n, value/row)
		}

		return count
	}

	left := 1
	right := m * n

	for left < right {
		mid := (left + right) / 2

		if countLessEqual(mid) >= k {
			right = mid
		} else {
			left = mid + 1
		}
	}

	return left
}

func min(a int, b int) int {
	if a < b {
		return a
	}
	return b
}
```Go 实现密切反映了 Python 逻辑。 

一个显着的区别是 Go 不提供内置的`min`整数函数，所以我们定义自己的助手。 

Go 中的整数除法会自动截断为零，这与计算倍数所需的行为相匹配。 

不需要额外的内存结构，因此实现保持恒定空间。

 ## 边缘情况

 一种重要的边缘情况是只有一行或一列的表格。 在这些情况下，乘法表实际上已经变成了排序序列。 有缺陷的实现可能会错误地假设一个方桌或错误地处理行计数。 计数公式仍然可以完美运行，因为每一行贡献零个或一个有效段。 

另一个重要的边缘情况涉及重复值。 乘法表自然包含重复的数字，例如`2`两者都出现`1 * 2`和`2 * 1`。 一个常见的错误是将价值观视为独特的。 该问题显式地单独计算重复项，基于计数的二分搜索自然可以处理此问题，因为它计算的是位置，而不是不同的值。 

第三个重要的边缘情况发生在以下情况：`k = m * n`，这意味着我们需要表中最大的元素。 那么答案一定是`m * n`。 一些二分搜索实现会由于上限附近的差一错误而失败。 使用标准下界二分搜索模式`while left < right`即使在搜索范围的极端情况下也能保证正确的收敛。 

最终的边缘情况涉及接近约束极限的极大尺寸。 任何显式生成表的方法都将因运行时间过多或内存使用量过多而失败。 最佳解决方案完全避免了这种情况，因为它从不存储表值，只执行算术计数操作。
