[LeetCode 第 690 题](https://leetcode.com/problems/employee-importance/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、树、深度优先搜索、广度优先搜索

 ## 解决方案

 ## 问题理解

 该问题提供了一个员工集合，其中每个员工包含三条信息：

 - 唯一的员工 ID
 - 整数重要性值
 - 代表其直接下属的 ID 列表

 我们还获得了一名员工的 ID，并且必须计算该员工及其在组织层次结构中每个人（包括直接和间接下属）的总重要性。 

换句话说，这是一个管理树的遍历问题。 从某个特定的员工开始，我们需要访问通过下属关系可以到达的每一位员工，并汇总他们所有的重要性值。 

输入不是以节点之间带有指针的显式树结构形式给出的。 相反，员工存储在平面数组中。 每个员工仅通过 ID 引用下属。 这意味着在有效地遍历层次结构之前，我们需要一种方法来快速将 ID 映射到其对应的员工对象。 

这些约束告诉我们一些重要的事情：

 - 员工数量最多可达 2000 名，这足以导致重复的线性扫描变得低效。 
- 员工 ID 是唯一的，这使得它们成为哈希映射的理想键。 
- 每个员工最多可以有一个经理，因此该结构形成一棵有效的树或森林，没有循环。 
- 保证下属身份证有效，因此我们不需要对失踪员工进行防御性检查。 

关键的挑战是有效地从一个员工 ID 导航到其员工对象，同时递归或迭代地探索所有后代。 

一些边缘情况很重要：

 - 所请求的员工可能没有下属。 
- 重要性值可能为负。 
- 层次结构可能非常深。 
- 层次结构可能有广泛的分支，有许多下属。 
- 起始员工可以是组织中的任何位置，不一定是根员工。 

由于输入保证了具有唯一 ID 且无循环的有效层次结构，因此我们可以安全地执行 DFS 或 BFS 遍历，而不必担心无限循环。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是每次遇到下级 ID 时扫描整个员工列表来递归搜索员工。 

这个想法是这样的：

 1. 从给定的员工 ID 开始。 
2. 扫描整个员工数组以查找匹配的员工。 
3. 添加该员工的重要性。 
4. 对每个下属递归地重复该过程。 

这种方法是正确的，因为它最终只访问每个下属一次并累积所有重要性值。 

然而，它的效率很低，因为每次员工查找都需要对员工列表进行全面扫描。 如果有`n`员工，并且我们可能对每个员工执行查找，总时间复杂度变为二次。 

对于多达 2000 名员工，这在实践中仍然可能通过，但速度不必要地缓慢，并且扩展性不佳。 

### 最佳方法

 关键的见解是员工 ID 是唯一的，因此我们可以将员工列表预处理为哈希映射。 

哈希映射允许我们使用其 ID 在恒定时间内检索员工对象。 

建立这个查找表后，问题就变成了标准的图或树遍历问题。 我们可以使用：

 - 深度优先搜索（DFS）
 - 广度优先搜索（BFS）

 DFS 在这里特别自然，因为层次结构根据定义是递归的。 对于每位员工：

 - 添加它们的重要性
 - 递归处理所有下级

 每个员工都被访问一次，并且每次查找都是`O(1)`。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(h) | 每次查找时都会重复扫描员工列表 |
 | 最佳| O(n) | O(n) | 使用哈希映射进行恒定时间员工查找 |

 这里，`h`表示层次结构的递归深度。 

## 算法演练

 1. 创建一个名为的哈希图`employee_map`其中键是员工 ID，值是员工对象本身。 

此预处理步骤至关重要，因为输入是作为平面列表而不是连接结构给出的。 如果没有地图，我们就需要重复的线性搜索。 
2. 定义接受员工 ID 的 DFS 辅助函数。 

辅助函数将：

 - 从哈希映射中检索员工
 - 从该员工的重要性值开始
 - 递归访问每个下属
 - 将次要重要性总计添加到运行总和中
 3. 在 DFS 函数内部，初始化一个名为`total_importance`与当前员工的重要性。 

这确保了在处理下属之前包括员工自己的贡献。 
4. 迭代当前员工的`subordinates`列表。 

对于每个从属 ID：

 - 递归调用DFS
 - 将返回值添加到`total_importance`5. 从 DFS 函数返回累计总数。 

当递归完成时，总数包含当前员工和层次结构中每个后代的重要性。 
6. 通过对给定的调用 DFS 开始遍历`id`。 
7. 返回最终结果。 

### 为什么它有效

 该算法之所以有效，是因为组织层次结构形成了一个没有循环的树状结构。 DFS 保证每个可到达的下级都被访问一次。 

在每次递归调用时，该函数都会正确计算：

 - 员工自身的重要性
 - 加上所有从属子树的总重要性

 由于递归结果是相加组合的，因此最终答案是以给定员工为根的整个层次结构的完整重要性总计。 

## Python 解决方案```python
from typing import List

"""
# Definition for Employee.
class Employee:
    def __init__(self, id: int, importance: int, subordinates: List[int]):
        self.id = id
        self.importance = importance
        self.subordinates = subordinates
"""

class Solution:
    def getImportance(self, employees: List['Employee'], id: int) -> int:
        employee_map = {employee.id: employee for employee in employees}

        def dfs(employee_id: int) -> int:
            employee = employee_map[employee_id]

            total_importance = employee.importance

            for subordinate_id in employee.subordinates:
                total_importance += dfs(subordinate_id)

            return total_importance

        return dfs(id)
```实现首先构建一个名为的字典`employee_map`。 这将扁平的员工列表转换为高效的查找结构，可以使用其 ID 在恒定时间内访问任何员工。 

嵌套的`dfs`函数执行递归遍历。 它首先检索与提供的 ID 关联的员工对象。 员工自身的重要性会立即增加，因为每个员工都对整体做出贡献。 

然后，该函数迭代所有下级 ID 并递归计算每个下级的总重要性。 这些结果被累积到`total_importance`。 

最后，外部方法只是从请求的员工 ID 开始 DFS 遍历并返回计算出的总数。 

这种实现很简洁，因为递归结构自然地反映了层次结构本身。 

## 解决方案```go
/**
 * Definition for Employee.
 * type Employee struct {
 *     Id int
 *     Importance int
 *     Subordinates []int
 * }
 */

func getImportance(employees []*Employee, id int) int {
    employeeMap := make(map[int]*Employee)

    for _, employee := range employees {
        employeeMap[employee.Id] = employee
    }

    var dfs func(int) int

    dfs = func(employeeID int) int {
        employee := employeeMap[employeeID]

        totalImportance := employee.Importance

        for _, subordinateID := range employee.Subordinates {
            totalImportance += dfs(subordinateID)
        }

        return totalImportance
    }

    return dfs(id)
}
```Go 实现遵循与 Python 版本相同的整体结构。 地图用于恒定时间员工查找，递归 DFS 函数计算总重要性。 

Go 特有的一个细节是员工存储为指针（`*Employee`）在映射中，这避免了不必要的结构复制。 

递归 DFS 函数是使用变量赋值来声明的，因为 Go 中的递归匿名函数要求变量在赋值之前就存在。 

Go 切片自然会处理空的从属列表，因此不需要特殊的 nil 检查。

 ## 边缘情况

 当新任员工没有下属时，就会出现一种重要的边缘情况。 在这种情况下，算法应该简单地返回员工自己的重要性值，而不执行额外的递归。 有缺陷的实现可能会错误地假设每个员工都有下属或错误地处理空列表。 此实现可以自然地处理这种情况，因为迭代空的从属列表会执行零递归调用。 

另一个重要的例子是负重要性值。 由于该问题允许重要性值介于`-100`和`100`，随着下属的处理，总重要性可能会降低。 一些实现错误地假设所有重要性值为正，并且可能不正确地初始化总数。 此解决方案始终严格按照给定值添加值，因此可以正确处理负贡献。 

第三个关键边缘情况是非常深的层次结构，其中每个员工只有一名下属。 这将创建一个类似链表的结构。 递归解决方案必须通过所有递归调用正确地将累积总数传播回去。 由于 DFS 函数返回每个子树的完整小计，因此无论层次结构深度如何，累加都保持正确。 

第四个微妙的边缘情况是从非 root 员工开始的。 该问题并不能保证所请求的员工是高层管理人员。 该算法仅正确计算以请求的员工为根的子树，因为遍历专门从提供的 ID 开始，而不是假设遍历应从组织根开始。
