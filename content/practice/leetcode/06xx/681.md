[LeetCode 第 681 题](https://leetcode.com/problems/next-closest-time/)

 **难度：** 🟡 中等
 **主题：** 哈希表、字符串、回溯、枚举

 ## 解决方案

 ## 问题理解

 该问题为我们提供了格式为的有效时间字符串`"HH:MM"`并要求我们仅使用原始时间中已经存在的数字来构造下一个按时间顺序排列的时间。 

重要的细节是数字可以重复使用任意次。 如果输入是`"19:34"`，允许的数字是`{1, 9, 3, 4}`。 我们可以重复使用这些数字中的任何一个来形成另一个有效时间。 目标是找到按时间顺序接下来发生的有效时间。 

短语“下一个最近时间”是指每分钟向前移动的最小正时间差。 如果当天不存在更大的有效时间，则答案将延续到第二天。 例如，从`"23:59"`下一个有效时间是`"22:22"`第二天。 

输入约束非常小。 输入长度始终为5，保证时间有效。 由于一天只有 24 × 60 = 1440 分钟，所以即使是暴力解决方案也是可行的。 这个小的搜索空间是关键的观察，使我们能够使用非常直接和可靠的方法。 

一些边缘情况很重要：

 - 下一个有效时间可能发生在第二天。 
- 当前时间本身无法立即返回，因为我们需要下一次出现。 
- 某些输入仅允许单个有效时间。 例如，`"11:11"`只能生产`"11:11"`，所以答案在一整天后就结束了。 
- 接近午夜的时间，例如`"23:59"`需要适当的模运算。 
- 考生时间仍必须满足有效的时钟限制，即少于 24 小时和少于 60 分钟。 

## 方法

 ### 蛮力方法

 暴力解决方案使用可用数字生成所有可能的 4 位数字组合，并检查它是否形成有效时间。 

如果最多有 4 个唯一数字，则最多有：$$4^4 = 256$$可能的组合。 对于每种组合，我们验证小时和分钟值，将有效时间转换为总分钟数，并计算与原始时间的向前时间差。 

然后，我们选择具有最小正差异的有效候选者。 

这种方法是完全正确的，因为它详尽地检查了可从允许的数字构造的每个可能的有效时间。 由于搜索空间很小，因此性能是可以接受的。 

然而，它仍然对许多不可能的组合执行不必要的生成和验证。 

### 最佳方法

 更好的观察是，一天可能只有 1440 分钟。 我们可以简单地从当前时间一分钟一分钟地向前移动，并检查结果时间是否仅使用允许的数字，而不是生成所有组合。 

这很有效，因为遇到的第一个有效时间自动成为正确答案。 我们永远不需要手动比较候选者或计算最小差异​​。 

算法变得非常干净：

 1. 将输入时间转换为分钟。 
2. 将允许的数字存储在一组中。 
3. 使用模 1440 反复将时间前进一分钟。 
4. 将候选人转换回`"HH:MM"`格式。 
5. 检查每个数字是否属于允许的集合。 
6. 返回第一个有效候选者。 

由于我们最多检查 1440 次，因此运行时间实际上是恒定的。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(4^4) = O(1) | O(4^4) = O(1) | O(1) | O(1) | 生成所有可能的数字组合 |
 | 最佳 | O(1440) = O(1) | O(1) | O(1) | 模拟每分钟向前搜索 |

 ## 算法演练

 1. 从输入时间中提取所有可用的数字。 

我们忽略冒号并将剩余的数字放入哈希集中。 集合是理想的，因为成员资格检查是恒定时间的。 如果输入是`"19:34"`，允许的数字集变为`{'1', '9', '3', '4'}`。 
2. 将当前时间转换为总分钟数。 

将时间转换为单个整数可以简化时间算术。 例如：$$19 \times 60 + 34 = 1174$$这种表示方式使时钟的递增变得简单。 
3. 启动无限循环，将时间提前一分钟。 

每次迭代计算：$$(current + 1) \bmod 1440$$模运算会在午夜自动处理环绕。 
4. 将候选分钟计数转换回小时和分钟格式。 

我们计算：

 -`hour = current // 60`-`minute = current % 60`然后将候选格式设置为零填充字符串，例如`"19:39"`。 
5. 验证候选时间中的每个数字都属于允许的集合。 

我们跳过冒号并仅检查数字字符。 如果所有数字都出现在允许的集合中，则该候选数字有效。 
6. 返回遇到的第一个有效候选者。 

因为我们按照时间顺序一分钟一分钟地搜索，所以第一个有效时间一定是下一个最接近的时间。 

### 为什么它有效

 该算法从输入时间之后立即开始按严格递增的时间顺序检查时间。 由于每个可能的未来分钟在重复之前都会被检查一次，因此遇到的第一个有效的可构造时间必须是最小的前向时间差。 因此，返回的结果保证是正确的下一个最接近的时间。 

## Python 解决方案```python
class Solution:
    def nextClosestTime(self, time: str) -> str:
        allowed_digits = set(time.replace(":", ""))

        current_minutes = int(time[:2]) * 60 + int(time[3:])

        while True:
            current_minutes = (current_minutes + 1) % 1440

            hours = current_minutes // 60
            minutes = current_minutes % 60

            candidate = f"{hours:02d}:{minutes:02d}"

            if all(char in allowed_digits for char in candidate if char != ":"):
                return candidate
```实现首先将可用数字提取到一组中。 使用集合可以在验证候选时间时进行有效的成员资格测试。 

接下来，输入时间将转换为从午夜开始的总分钟数。 这避免了手动处理小时和分钟进位逻辑。 

该循环不断地使时钟前进一分钟。 使用模数`1440`确保之后`"23:59"`时间正确回绕到`"00:00"`。 

对于每个候选分钟值，代码使用零填充格式重建格式正确的时间字符串。 这很重要，因为诸如此类的时间`"01:05"`必须保留前导零。 

最后，`all()`检查验证候选中的每个数字是否属于允许的集合。 第一个有效候选者将立即返回。 

## 解决方案```go
package main

import (
	"fmt"
)

func nextClosestTime(time string) string {
	allowedDigits := make(map[rune]bool)

	for _, ch := range time {
		if ch != ':' {
			allowedDigits[ch] = true
		}
	}

	hours := int(time[0]-'0')*10 + int(time[1]-'0')
	minutes := int(time[3]-'0')*10 + int(time[4]-'0')

	currentMinutes := hours*60 + minutes

	for {
		currentMinutes = (currentMinutes + 1) % 1440

		h := currentMinutes / 60
		m := currentMinutes % 60

		candidate := fmt.Sprintf("%02d:%02d", h, m)

		valid := true

		for _, ch := range candidate {
			if ch != ':' && !allowedDigits[ch] {
				valid = false
				break
			}
		}

		if valid {
			return candidate
		}
	}
}
```Go 实现遵循与 Python 版本相同的逻辑。 一个`map[rune]bool`用于代替 Python 集进行恒定时间数字查找。 

Go 需要手动将时间字符解析为整数，因为没有像 Python 那样直接切片到 int 的转换。 格式化的候选字符串是使用创建的`fmt.Sprintf("%02d:%02d", h, m)`保留前导零。 

不存在溢出问题，因为所有计算都保持在 0 到 1439 的范围内。

 ## 边缘情况

 当下一个有效时间是在第二天时，就会出现一个重要的边缘情况。 输入如`"23:59"`需要环绕处理。 仅在当天进行搜索的简单实现将会失败。 模数`1440`操作确保时钟正确地循环回到午夜。 

当只能形成一个有效时间时，就会出现另一种棘手的情况。 例如，`"11:11"`仅包含数字`1`。 唯一可能的有效时间就是它本身。 该算法正确地处理了这个问题，因为它会继续一分钟一分钟地搜索，直到全天周期返回到`"11:11"`再次。 

前导零是错误的另一个常见来源。 时间如`"01:05"`必须保留小时和分钟的精确两位数格式。 如果没有零填充，候选者就像`"1:5"`会错误地省略数字并破坏验证逻辑。 使用格式化字符串，例如`f"{hours:02d}:{minutes:02d}"`确保正确性。 

最后一个微妙的边缘情况涉及无效的中间组合。 即使允许所有数字，像这样的组合`"29:99"`不是有效的时钟时间。 每分钟模拟方法自然避免了构造无效时间，因为每个生成的候选值都来自 0 到 1439 之间的有效分钟计数。
