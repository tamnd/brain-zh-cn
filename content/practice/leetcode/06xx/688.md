[LeetCode 第 688 题](https://leetcode.com/problems/knight-probability-in-chessboard/)

 **难度：** 🟡 中等
 **主题：** 动态规划

 ## 解决方案

 ## 问题理解

 该问题要求我们计算国际象棋马留在棋子上的概率`n x n`准确制作后的板`k`移动。 

骑士从位置开始`(row, column)`。 在每次移动时，它都会以相同的概率随机选择八个可能的骑士移动之一，即`1/8`每一步。 重要的是，骑士不会避免无效的动作。 即使一步棋会将其从棋盘上移走，该棋步仍被视为随机选择集的一部分。 

该过程在以下两种情况之一停止：

 - 骑士已经完全完成`k`动作
 - 马离开棋盘

 我们的任务是返回马在恰好之后仍然在棋盘上某个位置的概率`k`移动。 

骑士以L形移动。 从一个位置`(r, c)`，八种可能的移动是：

 -`(r + 2, c + 1)`-`(r + 2, c - 1)`-`(r - 2, c + 1)`-`(r - 2, c - 1)`-`(r + 1, c + 2)`-`(r + 1, c - 2)`-`(r - 1, c + 2)`-`(r - 1, c - 2)`限制相对较小：

 -`n <= 25`-`k <= 100`这些限制立即表明指数暴力遍历将变得不可行。 由于每个动作都会分支为 8 种可能性，因此简单的递归解决方案将探索最多`8^k`路径。 为了`k = 100`，这是一个天文数字。 

重要的边缘情况包括以下情况：

 -`k = 0`，因为没有采取任何行动，马会自动保留在棋盘上
 -`n = 1`，因为棋盘只有一个格子，任何移动都会立即离开棋盘
 - 骑士从边缘或角落附近开始，那里的许多动作都是无效的
 - 大号`k`值，如果不进行优化，重复计算就会变得昂贵

 该问题保证了有效的输入坐标，因此我们永远不需要处理无效的起始位置。 

## 方法

 ### 蛮力方法

 蛮力策略是递归地模拟每一个可能的骑士动作序列。 

在每一步，骑士都有八种可能的动作。 我们递归地探索所有这些，每次将剩余的移动数减少一。 如果马移动到棋盘之外，该路径会贡献概率`0`。 如果骑士成功完成所有任务`k`在板内移动时，该路径贡献概率`1`。 

因为每一个动作都有概率`1/8`，最终的概率是所有递归分支的平均值。 

这种方法是正确的，因为它明确地模拟了完整的概率树。 每个可能的移动序列都会被考虑一次。 

然而，相同的棋盘位置会被重复重新计算。 例如，从位置幸存的概率`(2,3)`和`5`剩余的移动可能会被计算数百或数千次。 

时间复杂度呈指数增长`O(8^k)`，这对于`k = 100`。 

### 最优动态规划方法

 关键的观察结果是该问题具有重叠的子问题。 

如果我们定义：

 -`dp[move][r][c]`作为骑士在单元格的概率`(r, c)`后`move`移动同时仍然留在棋盘上，那么每个状态仅取决于前一个移动的状态。 

我们不是递归地重新计算概率，而是迭代地构建它们。 

我们从概率开始`1.0`在起始位置。 然后，对于每次移动，我们将当前概率平均分配给所有有效的骑士目的地。 

这将指数递归树转变为可管理的动态编程解决方案。 

因为最多有：

 -`k <= 100`-`n <= 25`州总数仅为：

 -`100 * 25 * 25 = 62,500`这是非常有效的。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(8^k) | O(8^k) | O(k) | 递归探索每个可能的移动序列 |
 | 最优动态规划| O(k * n²) | O(k * n²) | O(n²) | 重用之前计算的概率 |

 ## 算法演练

 1. 定义八种可能的马走法。 

我们将所有合法的骑士运动偏移存储在一个列表中。 这使我们能够统一迭代给定单元格的所有可能的转换。 
2. 为当前移动状态创建概率网格。 

我们使用一个名为的二维数组`current`。 每个单元格存储骑士经过一定次数的移动后当前处于该位置的概率。 
3. 初始化起始位置。 

在采取任何行动之前，骑士肯定处于`(row, column)`， 所以：```
current[row][column] = 1.0
```4. 一次处理一个动作。 

对于每一个举动`1`到`k`，我们创造了一个新鲜的`next_state`网格用零初始化。 
5. 将概率分配给可到达的单元格。 

对于每个细胞`(r, c)`在当前网格中：

 - 如果其概率为零，则跳过它
 - 否则，尝试所有八个骑士动作
 - 如果目标单元格位于板内，请添加：```
current[r][c] / 8
```到那个目的地

 这对每个马的移动概率均等进行了建模。 
6.更换当前网格。 

处理完一次移动的所有转换后，分配：```
current = next_state
```所以算法进入下一个移动层。 
7. 对所有剩余概率求和。 

恰好之后`k`移动时，网格中留下的每个值都代表骑士仍在棋盘上的有效方式。 

答案是最终网格中所有概率的总和。 

### 为什么它有效

 动态规划状态保持一个重要的不变量：

 >`current[r][c]`总是表示马处于位置的概率`(r, c)`在当前移动次数之后，同时仍留在棋盘上。 

每个转变根据骑士的均匀随机选择来分配概率质量。 无效的移动会被自动丢弃，因为它们离开了棋盘，因此不会对未来的状态做出贡献。 

由于每条有效路径的贡献完全取决于其概率，因此所有棋盘概率的最终总和等于骑士在所有棋局中幸存的概率`k`移动。 

## Python 解决方案```python
class Solution:
    def knightProbability(self, n: int, k: int, row: int, column: int) -> float:
        moves = [
            (2, 1),
            (2, -1),
            (-2, 1),
            (-2, -1),
            (1, 2),
            (1, -2),
            (-1, 2),
            (-1, -2),
        ]

        current = [[0.0 for _ in range(n)] for _ in range(n)]
        current[row][column] = 1.0

        for _ in range(k):
            next_state = [[0.0 for _ in range(n)] for _ in range(n)]

            for r in range(n):
                for c in range(n):
                    if current[r][c] == 0:
                        continue

                    probability = current[r][c] / 8.0

                    for dr, dc in moves:
                        nr = r + dr
                        nc = c + dc

                        if 0 <= nr < n and 0 <= nc < n:
                            next_state[nr][nc] += probability

            current = next_state

        total_probability = 0.0

        for r in range(n):
            for c in range(n):
                total_probability += current[r][c]

        return total_probability
```实现首先定义八个骑士的移动方向。 这些被存储为坐标偏移，因此我们可以有效地迭代它们。 

这`current`矩阵存储当前移动次数后的概率分布。 最初，骑士保证位于起始方格，因此该位置接收概率`1.0`。 

对于每次移动迭代，我们创建一个名为的新矩阵`next_state`。 这表示额外一步移动后的概率分布。 

然后我们扫描板上的每个单元格。 如果一个单元当前的概率为零，我们会跳过它，因为那里不存在概率质量。 

否则，我们将单元格的概率平均分配给八个可能的骑士动作。 对于每个有效的目标单元格，我们将贡献添加到`next_state`。 

处理完所有单元格后，我们替换`current`和`next_state`。 

Finally, we sum every probability remaining on the board. This total represents the probability that the knight never left the board during the`k`移动。 

## 解决方案```go
func knightProbability(n int, k int, row int, column int) float64 {
    moves := [][2]int{
        {2, 1},
        {2, -1},
        {-2, 1},
        {-2, -1},
        {1, 2},
        {1, -2},
        {-1, 2},
        {-1, -2},
    }

    current := make([][]float64, n)
    for i := range current {
        current[i] = make([]float64, n)
    }

    current[row][column] = 1.0

    for move := 0; move < k; move++ {
        nextState := make([][]float64, n)

        for i := range nextState {
            nextState[i] = make([]float64, n)
        }

        for r := 0; r < n; r++ {
            for c := 0; c < n; c++ {
                if current[r][c] == 0 {
                    continue
                }

                probability := current[r][c] / 8.0

                for _, dir := range moves {
                    nr := r + dir[0]
                    nc := c + dir[1]

                    if nr >= 0 && nr < n && nc >= 0 && nc < n {
                        nextState[nr][nc] += probability
                    }
                }
            }
        }

        current = nextState
    }

    totalProbability := 0.0

    for r := 0; r < n; r++ {
        for c := 0; c < n; c++ {
            totalProbability += current[r][c]
        }
    }

    return totalProbability
}
```The Go implementation follows the same dynamic programming structure as the Python version.

 主要区别在于内存分配。 In Go, we explicitly allocate each row of the 2D slice using`make`。 

Go 还使用固定数字类型，因此概率存储为`float64`。 由于所有概率运算都是小数，因此整数类型将是不正确的。 

与 Python 列表不同，Go 切片在使用前需要手动初始化。 除了语法差异之外，算法行为是相同的。

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(k * n²) | O(k * n²) | 对于每次移动，我们都会处理每个棋盘单元和最多 8 个转换 |
 | 空间| O(n²) | 一次仅存储两个概率网格 |

 该算法迭代整个棋盘`k`次。 在每次迭代期间，每个单元格都会检查一次，并且每个单元格最多考虑 8 个骑士动作。 由于 8 是常数，复杂度简化为`O(k * n²)`。

 ## 边缘情况

 一种重要的边缘情况发生在以下情况：`k = 0`。 在这种情况下，马永远不会移动，因此留在棋盘上的概率必须始终为`1.0`。 有错误的实现可能仍会尝试转换或意外返回`0`。 该解决方案可以自然地处理这种情况，因为移动循环永远不会执行，从而使起始单元格概率保持不变。 

另一个关键的边缘情况是非常小的电路板，例如`n = 1`或者`n = 2`。 在这些棋盘上，许多或所有的骑士动作都是无效的。 幼稚的实现可能会错误地假设至少存在一个合法的举动。 在此解决方案中，在将概率添加到下一个状态之前，会检查每个移动目的地的边界条件。 无效的动作将被简单地忽略。 

第三个重要的边缘情况是从拐角或边缘附近开始的。 靠近边界的骑士的有效动作比靠近中心的骑士少得多。 不正确的实现有时仅对有效动作的概率进行归一化，这是错误的，因为问题表明骑士总是在所有八个动作中统一选择。 该实现正确地将概率除以`8`无论棋盘上还有多少步棋。 

另一个微妙的边缘情况涉及较大的值`k`。 没有记忆的递归解决方案很容易超时或超出递归深度限制。 迭代动态规划方法完全避免了递归，并有效地处理了最大约束`k = 100`。
