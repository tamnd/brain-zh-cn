[LeetCode 602 题](https://leetcode.com/problems/friend-requests-ii-who-has-the-most-friends/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题给了我们一个名为`RequestAccepted`，其中每一行代表两个用户之间成功接受的好友请求。 每条记录都包含一个`requester_id`， 一个`accepter_id`，以及请求被接受的日期。 

重要的细节是友谊是相互的。 如果用户`1`向用户发送好友请求`2`并且被接受，那么两个用户就成为彼此的朋友。 因此，每一行都向请求者和接受者贡献一个朋友。 

目标是确定哪个人的朋友总数最多，并返回用户的 ID 和他们拥有的朋友数量。 

例如，考虑以下关系：```
1 <-> 2
1 <-> 3
2 <-> 3
3 <-> 4
```用户`3`已连接到用户`1`,`2`， 和`4`，所以他们有`3`朋友总数。 没有其他用户有那么多朋友，所以结果是：```
id = 3
num = 3
```该表保证`(requester_id, accepter_id)`是唯一的，这意味着同一接受的请求不能在同一方向出现两次。 然而，该问题并没有明确保证反向对不能单独出现，因此鲁棒的解决方案仍然应该仔细考虑计数逻辑。 

问题陈述还保证只有一个用户拥有最大好友数量。 后续问题删除了这一保证，并询问如何返回与最大值相关的所有用户。 

一个重要的观察是，我们没有被要求计算直接图遍历或连接组件。 我们只需要友谊图中每个节点的度数。 每个接受的友谊都会为两个相关用户贡献一个朋友计数。 

有几种边缘情况值得考虑：

 - 用户只能以请求者的身份出现，而不能以接受者的身份出现。 
- 用户只能以接受者的身份出现，而不能以请求者的身份出现。 
- 拥有最多朋友的用户可能不会频繁出现在单独的一栏中，因此仅计数`requester_id`或仅`accepter_id`是不正确的。 
- 整个表中可能只有一个已接受的请求。 
- 后续场景中，多个用户可以共享相同的最大好友数。 

## 方法

 ### 暴力方法

 暴力解决方案将单独检查每个用户并计算该用户涉及的好友数量。 

一种方法是：

 1. 从两者中提取所有不同的用户 ID`requester_id`和`accepter_id`。 
2. 对于每个用户，再次扫描整个表并计算任一列中包含该用户的行数。 
3. 跟踪迄今为止看到的最大计数。 

这种方法是正确的，因为涉及用户的每条友谊都为其好友计数贡献了 1。 通过检查每个用户的所有行，我们最终准确地计算每个用户的程度。 

然而，这种方法效率低下，因为表被重复扫描。 如果有`N`友谊记录和`U`唯一用户，总工作量变为`O(U * N)`。 在大型数据集中，这种重复扫描变得不必要的昂贵。 

### 最佳方法

 关键的见解是，每一个被接受的友谊都为双方都贡献了一个朋友。 

我们可以处理每个好友一次，并立即增加涉及的两个用户的好友计数，而不是单独处理每个用户。 

从概念上讲，我们可以将表格转换为统一的用户外观流：```
(requester_id)
(accepter_id)
```然后我们按用户 ID 进行分组并统计每个用户出现的次数。 

在 SQL 中，这很自然地表达为`UNION ALL`:

 - 一个查询提取所有请求者。 
- 另一个查询提取所有接受者。 
- 将它们组合起来会为每次友谊参与创建一行。 
- 分组和计数给出每个用户的好友总数。 

最后，我们按好友数量降序排序并返回排名靠前的用户。 

该解决方案仅处理每个友谊一次，从而显着提高效率。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(U * N) | O(U) | 重复扫描表中的每个用户 |
 | 最佳| O(N) | O(U) | 在单个聚合过程中计算所有友谊 |

 ## 算法演练

 1. 创建所有友谊参与的统一列表。 

每个被接受的友谊都涉及两个用户。 因此，我们创建一个组合数据集，其中包含：

 - 每个`requester_id`- 每一个`accepter_id`我们使用`UNION ALL`而不是`UNION`因为我们想保留所有发生的事情。 每一次出现都代表着一份友谊的贡献。 
2. 按用户 ID 对组合数据集进行分组。 

合并两列后，每一行代表用户的一次友谊参与。 按用户 ID 分组可以让我们统计每个用户有多少好友。 
3. 计算每个用户的行数。 

给定用户的计数等于该用户拥有的朋友总数。 
4. 按好友数量降序对用户进行排序。 

计数最高的用户应该首先出现。 
5. 返回最上面的结果。 

由于该问题保证只有一个用户拥有最大好友数，所以我们可以放心使用`LIMIT 1`。 

### 为什么它有效

 每个接受的友谊都为双方参与者贡献了一位朋友。 通过将每条友谊转换为两个单独的用户外观（一个用于请求者，一个用于接受者），用户的总外观次数将完全等于其朋友的数量。 因此，分组和计数可以计算每个用户的正确好友总数。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    id,
    COUNT(*) AS num
FROM (
    SELECT requester_id AS id
    FROM RequestAccepted
    
    UNION ALL
    
    SELECT accepter_id AS id
    FROM RequestAccepted
) AS friendships
GROUP BY id
ORDER BY num DESC
LIMIT 1;
```该解决方案首先构建一个名为的派生表`friendships`。 

第一个查询选择全部`requester_id`值并将该列重命名为`id`。 第二个查询选择全部`accepter_id`值并将该列重命名为`id`。 

使用`UNION ALL`合并两个结果集，同时保留重复项。 保留重复项很重要，因为每次出现都代表着独特的友谊参与。 

构建此组合数据集后，查询按`id`。 这`COUNT(*)`然后操作计算每个用户出现的次数，这直接对应于该用户拥有的朋友数量。 

最后将结果按照好友数降序排序，`LIMIT 1`返回好友数量最多的用户。 

## 解决方案```go
// Write your MySQL query statement below

SELECT
    id,
    COUNT(*) AS num
FROM (
    SELECT requester_id AS id
    FROM RequestAccepted
    
    UNION ALL
    
    SELECT accepter_id AS id
    FROM RequestAccepted
) AS friendships
GROUP BY id
ORDER BY num DESC
LIMIT 1;
```由于这是 LeetCode 上的数据库问题，因此解决方案完全用 SQL 而不是 Go 应用程序代码编写。 无论界面中选择哪种语言，都会提交相同的 SQL 查询。 

逻辑仍然相同：

 - 将两个友谊列扁平化为一个用户 ID 流。 
- 计算每个用户的出现次数。 
- 返回计数最高的用户。

 ## 边缘情况

 当用户仅出现在`requester_id`列，并且从未在`accepter_id`柱子。 只计算接受者的有缺陷的实现会错误地忽略该用户的好友关系。 该解决方案通过使用组合两列来避免此问题`UNION ALL`。 

当用户仅作为接受者出现时，会出现另一个重要的边缘情况。 这与前面的情况对称，并且类似地说明了为什么必须同等地处理两列。 由于查询独立地从两列中提取 ID，因此实现可以正确处理此问题。 

第三个重要的边缘案例涉及关系。 尽管最初的问题保证了唯一的最大值，但现实世界的数据通常包含具有相同数量朋友的多个用户。 一个天真的`LIMIT 1`解决方案将任意丢弃绑定用户。 后续版本可以通过单独计算最大好友数并返回所有等于该最大好友数的用户来解决。 

最后一个微妙的边缘情况涉及重复处理。 使用`UNION`而不是`UNION ALL`会删除重复的行并产生不正确的朋友计数，因为重复出现是有意义的。 每一次友谊参与都必须独立计算，这就是为什么`UNION ALL`是必须的。
