[LeetCode 1321 题](https://leetcode.com/problems/restaurant-growth/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 此问题要求我们计算餐厅收入的滚动 7 天摘要。 输入表存储各个客户交易。 每行代表单个客户在特定日期花费的金额。 

重要的细节是，多个客户可能在同一天访问，这意味着我们不能直接对原始行应用移动平均值。 相反，我们首先需要汇总每天的所有客户支出。 

对于从第七个可用日开始的每一天，我们必须计算：

 - 当日及前六天的消费总额
 - 这 7 天的平均每日收入
 - 平均值四舍五入至小数点后两位

 结果应包含：

 -`visited_on`, 7 天窗口的结束日期
 -`amount`, the total revenue across the entire seven day window
 -`average_amount`, 7 天平均收入

 输出必须按时间顺序排序`visited_on`。 

该问题保证每天至少有一个客户。 这一保证极其重要，因为这意味着时间表中不会遗漏任何日期。 如果没有这种保证，我们将需要额外的逻辑来在计算滚动窗口之前生成缺失的日历日期。 

仔细考虑这个例子。 在`2019-01-10`，有两个客户交易：

 - 130 来自客户 1
 - 150 来自客户 3

 每日收入为`2019-01-10`因此是：```
130 + 150 = 280
```7 天窗口期`2019-01-04`通过`2019-01-10`变成：```
130 + 110 + 140 + 150 + 80 + 110 + 280 = 1000
```那么平均值是：```
1000 / 7 = 142.857...
```四舍五入到小数点后两位：```
142.86
```幼稚的实现很容易在几个地方犯错误：

 - 忘记汇总同一天发生的多笔交易
 - 使用七行而不是七个不同的日期
 - 在完整的 7 天窗口存在之前开始输出
 - 忘记正确舍入平均值
 - 日期排序处理不当

 输入保证了连续的日期，这显着简化了滑动窗口的计算。 

## 方法

 ### 蛮力方法

 强力解决方案首先汇总每个日期的每日收入。 此后，对于每个符合条件的日子，我们都会从头开始重新计算前 7 天的总收入。 

假设我们有`n`不同的日子。 对于从索引 6 开始的每一天，我们向后迭代前 7 天并手动汇总其收入。 

这种方法是正确的，因为每 7 天的窗口都是使用问题陈述中的确切定义独立计算的。 然而，它执行了多余的工作。 连续的窗口严重重叠。 从一个窗口移动到下一个窗口时，七天内有六天保持不变，但强力解决方案会再次重新计算所有内容。 

尽管七在技术上是恒定的，但一般模式效率低下，并且不能很好地适应较大的窗口尺寸。 

### 最佳方法

 关键的观察结果是相邻的 7 天窗口仅相差两个值：

 - 有一天离开窗户
 - 新的一天即将来临

 我们维护一个运行窗口总计，而不是每次都重新计算整个总和。 

这是经典的滑动窗口技术。 

我们首先按日期汇总每日收入。 然后我们按时间顺序迭代日期，同时维护：

 - 当前 7 天总和
 - 当前窗口边界

 当窗口增长超过 7 天时，我们减去最早一天的收入。 这使得每个新结果都可以在恒定时间内计算出来。 

这避免了重复的求和工作并产生有效的线性解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n × 7) | O(n) | 独立重新计算每个 7 天窗口 |
 | 最佳| O(n) | O(n) | 使用带有运行总计的滑动窗口 |

 ## 算法演练

 ### 第 1 步：按日期汇总收入

 原始表包含客户级别的交易，但问题需要日级别的收入。 

我们首先对行进行分组`visited_on`并计算：```
daily_total[date] = sum(amounts for that date)
```例如：

 | 日期 | 每日收入|
 | --- | --- |
 | 2019-01-01 | 100 | 100
 | 2019-01-02 | 110 | 110
 | 2019-01-03 | 120 | 120
 | ... | ... |

 这种转变是必要的，因为滚动窗口是按天运行的，而不是针对个人客户。 

### 第 2 步：按时间顺序对日期进行排序

 仅当按升序处理日期时，滑动窗口才能正常工作。 

我们对所有不同的日期进行排序。 

### 第三步：初始化滑动窗口

 我们维持：

 -`window_sum`，当前 7 天窗口内的总收入
 - 左指针代表窗口中最早的一天

 最初，两个指针都从头开始。 

### 第 4 步：一天一天地展开窗口

 当我们迭代日期时：

 - 将当天的收入添加到`window_sum`- 在活动窗口中包含当前日期

 ### 步骤 5：如果超过 7 天，则缩小窗口

 如果窗口变得超过 7 天：

 - 删除最早一天的收入
 - 向前移动左指针

 这保证了窗口始终最多包含 7 天。 

### 步骤 6：窗口大小达到 7 时记录结果

 每当窗口恰好包含 7 天时：

 -`amount = window_sum`-`average_amount = round(window_sum / 7, 2)`店铺：```
(current_date, amount, average_amount)
```### 步骤 7：返回按日期排序的结果

 由于我们按时间顺序处理日期，因此结果已正确排序。 

### 为什么它有效

 滑动窗口始终保持当前 7 天间隔的准确收入总额。 

每一步：

 - 新的日子只添加一次
 - 旧时光被删除一次
 - 产生输出时窗口绝不会少于或超过 7 天

 因此，每个计算出的总和和平均值都精确对应于所需的 7 天时间段。 

## Python 解决方案```python
from collections import defaultdict
from typing import List

class Solution:
    def restaurantGrowth(self, customer: List[List]) -> List[List]:
        daily_revenue = defaultdict(int)

        # Aggregate revenue by date
        for _, _, visited_on, amount in customer:
            daily_revenue[visited_on] += amount

        # Sort dates
        sorted_dates = sorted(daily_revenue.keys())

        result = []

        left = 0
        window_sum = 0

        for right in range(len(sorted_dates)):
            current_date = sorted_dates[right]
            window_sum += daily_revenue[current_date]

            # Maintain exactly 7 days in the window
            if right - left + 1 > 7:
                oldest_date = sorted_dates[left]
                window_sum -= daily_revenue[oldest_date]
                left += 1

            # Record result when window size becomes 7
            if right - left + 1 == 7:
                average_amount = round(window_sum / 7, 2)

                result.append([
                    current_date,
                    window_sum,
                    average_amount
                ])

        return result
```实施开始于`defaultdict(int)`汇总每日收入。 这是必要的，因为多个客户可能会在同一天出现。 

聚合后，对日期进行排序，以便滑动窗口按时间顺序处理日期。 

变量`left`和`right`定义有效的 7 天窗口。 作为`right`指针前进，将当天的收入添加到`window_sum`。 

每当窗口增长超过 7 天时，最旧一天的收入将被删除，并且`left`指针前进。 这可确保窗口始终代表正确的滚动间隔。 

一旦窗口恰好达到 7 天，算法就会计算平均值并附加结果。 

该解决方案每天只执行持续的工作，因此效率很高。 

## 解决方案```go
package main

import (
	"math"
	"sort"
)

func restaurantGrowth(customer [][]interface{}) [][]interface{} {
	dailyRevenue := make(map[string]int)

	// Aggregate revenue by date
	for _, row := range customer {
		visitedOn := row[2].(string)
		amount := row[3].(int)

		dailyRevenue[visitedOn] += amount
	}

	// Sort dates
	var dates []string
	for date := range dailyRevenue {
		dates = append(dates, date)
	}

	sort.Strings(dates)

	var result [][]interface{}

	left := 0
	windowSum := 0

	for right := 0; right < len(dates); right++ {
		currentDate := dates[right]
		windowSum += dailyRevenue[currentDate]

		// Keep window size at most 7
		if right-left+1 > 7 {
			oldestDate := dates[left]
			windowSum -= dailyRevenue[oldestDate]
			left++
		}

		// Record result for valid 7-day windows
		if right-left+1 == 7 {
			average := math.Round((float64(windowSum)/7.0)*100) / 100

			result = append(result, []interface{}{
				currentDate,
				windowSum,
				average,
			})
		}
	}

	return result
}
```Go 实现遵循与 Python 版本相同的逻辑，但有一些特定于语言的细节。 

Go 没有具有自动默认值的 Python 风格动态字典，因此使用标准映射进行聚合。 

日期存储为字符串，因为 ISO 格式的日期按字典顺序正确排序。 

浮点舍入需要使用显式处理`math.Round`。 

结果类型使用`[][]interface{}`因为行包含混合类型、字符串和数值。

 ## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 每个日期进入和离开滑动窗口一次 |
 | 空间| O(n) | 商店每日总收入|

 聚合阶段对每行处理一次。 滑动窗口还对每个不同的日期处理一次。 由于每个日期最多只能在窗口中添加和删除一次，因此整体运行时间是线性的。 

辅助空间主要来自于存储每日汇总收入。

 ## 边缘情况

 ### 同一日期的多笔交易

 最容易犯的错误之一是将每一行视为单独的一天。 输入表存储客户交易，而不是每日摘要。 

如果多个客户在同一日期访问，则必须在滑动窗口计算开始之前合并他们的金额。 

该实现使用以下方式正确处理此问题：```
daily_revenue[visited_on] += amount
```这保证了每个日期都为滚动窗口贡献了一个聚合值。 

### 正好七个不同的日子

 如果输入恰好包含 7 天，则只有一个有效的输出行。 

某些实施错误地需要 7 天以上才能生成结果。 其他人意外地没有产生任何输出。 

滑动窗口逻辑显式检查：```
if right - left + 1 == 7
```这可确保一旦 7 天可用，就会立即生成第一个有效窗口。 

### 日收入值较大

 当许多客户在 7 天内花费大量资金时，收入总额可能会变得非常大。 

使用小整数类型的实现在某些语言中可能会溢出。 

Python 整数自动扩展为任意精度，因此 Python 解决方案自然是安全的。 在 Go 中，标准`int`值足以满足典型的 LeetCode 约束，但仔细使用整数运算仍然很重要。 

该算法增量存储运行总和，避免不必要的重新计算并最大限度地降低算术风险。
