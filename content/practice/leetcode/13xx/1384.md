[LeetCode 问题 1384](https://leetcode.com/problems/total-sales-amount-by-year/)

 **难度：** 🔴难
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 这是一个 SQL 数据库问题，我们需要计算**每年每种产品的总销售额**，即使销售期跨越多个日历年也是如此。 

我们有两张表：

 的`Product`表包含有关产品的元数据。 每行代表一个独特的产品及其`product_id`和`product_name`。 

这`Sales`表包含产品的销售期间。 每行指定：

 -`product_id`，识别销售记录属于哪个产品
 -`period_start`, 销售期的第一天
 -`period_end`, 销售期的最后一天
 -`average_daily_sales`，该期间每天的平均销售量

 一个关键细节是**开始日期和结束日期都包含在内**。 这意味着在计算一段时间内的天数时，我们必须计算两个端点。 

挑战的出现是因为单个销售期可能跨越多年。 我们不是报告整个期间的总金额，而是必须将期间分成每年的部分，并分别计算每年的销售额。 

例如，如果产品销售自`2018-12-01`到`2020-01-01`，我们不能将其视为一个连续范围。 我们必须将其分解为：

 - 属于2018年的部分
 - 属于2019年的部分
 - 属于2020年的部分

 对于每一年，我们计算：

 \text{total_amount} = \text{days_in_that_year_segment} \times \text{average_daily_sales}

 预期输出必须包括：

 -`product_id`-`product_name`-`report_year`-`total_amount`结果必须按以下顺序排序`product_id`和`report_year`。 

一个重要的约束大大简化了问题：**销售年份仅在 2018 年至 2020 年之间**。 这意味着任何销售期最多需要考虑三年。 如果没有这个限制，我们将需要一个更通用的日期扩展策略。 

一些边缘情况很容易在简单的实现中导致错误。 销售期可能完全存在于一年内，这意味着不需要分割。 另一种情况是一个时期恰好在年份边界上开始或结束，例如`2020-01-01`。 包含日期处理在这里尤其重要，因为忘记额外的一天会产生错误的总计。 我们还要正确对待两三年的时期。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是将每个销售期扩展为单独的日子。 

对于每条销售记录，我们可以迭代`period_start`到`period_end`，一天一天。 对于每一天，我们确定它的年份并累积`average_daily_sales`总计为`(product_id, year)`。 

这种方法之所以有效，是因为它直接对问题定义进行建模。 每一天都准确地贡献了相应年份的日均销售额。 

然而，该解决方案效率低下。 如果销售期跨越数百天，那么每天的迭代就会成为不必要的开销。 由于问题只持续了几年`2018`到`2020`，处理单个日期会浪费计算。 

### 最佳方法

 关键的见解是我们**不需要单独处理每一天**。 

相反，我们将销售期分成每年的部分。 仅仅几年以来`2018`,`2019`， 和`2020`存在，我们可以检查这些年份中的每一年并计算销售期间与该年份之间的重叠。 

对于给定年份：

 - 该年的开始日期是`YYYY-01-01`- 年终日期是`YYYY-12-31`We compute:

 -`overlap_start = max(period_start, year_start)`-`overlap_end = min(period_end, year_end)`如果`overlap_start <= overlap_end`，存在重叠。 

天数为：```
DATEDIFF(overlap_end, overlap_start) + 1
```我们添加`+1`因为日期是包含在内的。 

该年的总金额变为：```
days * average_daily_sales
```因为只有三年的时间来检查，所以这个解决方案非常有效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(D) | O(D) | 迭代所有销售期间的每一天 |
 | 最佳 | O(N) | O(1) | O(1) | 每项销售记录的支票仅重叠三年 |

 这里，`D`是所有销售期间的总天数，并且`N`是行数`Sales`。 

## 算法演练

 1. 加入`Sales`表与`Product`表使用`product_id`这样每条销售记录都可以访问到相应的产品名称。 
2. 对于每条销售记录，迭代候选年份`2018`,`2019`， 和`2020`。 我们只检查这些年份，因为该问题保证所有销售日期都在此范围内。 
3. 对于每年，定义年份边界：

 - 开始日期：`YYYY-01-01`- 结束日期：`YYYY-12-31`4. 计算销售期与当年的重叠部分：

 -`overlap_start = GREATEST(period_start, year_start)`-`overlap_end = LEAST(period_end, year_end)`5. 检查是否存在有效重叠。 如果`overlap_start <= overlap_end`，那么部分销售期属于今年。 
6. 使用以下方法计算重叠天数：```
DATEDIFF(overlap_end, overlap_start) + 1
```额外的`+1`确保包含计数。 
7. 将天数乘以`average_daily_sales`计算年销售额。 
8. 输出：

 -`product_id`-`product_name`-`report_year`-`total_amount`9. 对最终结果进行排序`product_id`和`report_year`。 

### 为什么它有效

 该算法之所以有效，是因为每个销售期都被划分为不重叠的年度部分。 对于每年，我们计算与销售间隔重叠的确切日期，并仅计算属于该年的天数。 由于年度重叠的并集准确地重建了原始销售间隔，并且没有一天被计算两次，因此计算出的年度总计保证是正确的。 

## Python 解决方案

 由于这是一个数据库问题，Python 解决方案只是将 SQL 查询作为字符串返回。```python
class Solution:
    def totalSales(self) -> str:
        return """
        SELECT
            s.product_id,
            p.product_name,
            YEAR(y.year_start) AS report_year,
            (
                DATEDIFF(
                    LEAST(s.period_end, y.year_end),
                    GREATEST(s.period_start, y.year_start)
                ) + 1
            ) * s.average_daily_sales AS total_amount
        FROM Sales s
        JOIN Product p
            ON s.product_id = p.product_id
        JOIN (
            SELECT
                '2018-01-01' AS year_start,
                '2018-12-31' AS year_end
            UNION ALL
            SELECT
                '2019-01-01',
                '2019-12-31'
            UNION ALL
            SELECT
                '2020-01-01',
                '2020-12-31'
        ) y
        ON s.period_start <= y.year_end
        AND s.period_end >= y.year_start
        ORDER BY s.product_id, report_year
        """
```该实现创建了一个包含三个候选年份的小型虚拟表。 该表与`Sales`评估重叠。 

加入条件：```python
s.period_start <= y.year_end
AND s.period_end >= y.year_start
```确保我们只保留与销售期相交的年份。 

一旦我们确定了重叠年份，我们就可以使用以下方法计算确切的重叠范围`LEAST`和`GREATEST`。 这可以防止计算当前年份之外的日期。 

最后，`DATEDIFF(...)+1`计算包含天数，并乘以`average_daily_sales`给出所需的年度总数。

 ## 边缘情况

 一个重要的边缘情况是销售期完全包含在一年内。 有缺陷的实现可能仍会尝试不必要地分割间隔或错误地创建重复行。 这个实现很自然地处理这种情况，因为只有一年满足重叠条件。 

当销售期恰好触及年份边界时，会出现另一个重要的边缘情况，例如`2020-01-01`到`2020-01-01`。 如果没有包含在内的计数，`DATEDIFF`会错误地返回`0`。 该实现明确添加了`+1`，确保正确计算一日期间。 

第三个棘手的案例是跨越多年的销售期。 幼稚的实现可能会错误地将整个持续时间归因于起始年份或结束年份。 通过独立计算销售期与每个日历年之间的交集，该实施保证了跨年天数的准确分配。 

最后一个微妙的边缘情况是闰年处理`2020`。 自从`DATEDIFF`适用于实际日历日期，适用时自动包含 2 月 29 日。 不需要特殊的闰年逻辑，这避免了与日期相关的错误的常见来源。
