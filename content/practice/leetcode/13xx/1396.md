[LeetCode 第 1396 题](https://leetcode.com/problems/design-underground-system/)

 **难度：** 🟡 中等
 **主题：** 哈希表、字符串、设计

 ## 解决方案

 ## 问题理解

 这个问题要求我们为地下铁路网络设计一个小型跟踪系统。 系统必须支持三种操作：

 1. 顾客进站时进行录音。 
2. 顾客从车站结账时进行录音。 
3. 计算两站之间的平均行程时间。 

每个客户都由一个唯一的整数标识`id`。 当顾客签到时，我们会得到车站名称和签到时间。 稍后，当同一位顾客结账时，我们会得到目的地车站和结账时间。 

一次旅行被定义为从一个车站到另一个车站的直接旅程。 例如，如果有人在`"Leyton"`并退房于`"Waterloo"`, 算作 1`"Leyton" -> "Waterloo"`旅行。 

关键的要求是`getAverageTime(startStation, endStation)`必须返回该确切路线的所有已完成行程的平均持续时间。 

该问题保证所有操作都是有效的并且按时间顺序发生。 这意味着：

 - 用户永远不会在签入之前签出。 
- 用户永远不会同时签入多个站点。 
- 每一个`getAverageTime`查询指的是至少一次已完成的行程。 

这些保证简化了实现，因为我们不需要防御性验证逻辑。 

约束条件相对较小，最多`2 * 10^4`总操作。 尽管限制不是很大，但问题本质上是使用适当的数据结构设计有效的状态管理。 

最重要的观察是我们不需要单独存储每个历史旅行。 要计算平均值，我们只需要：

 - 一条路线的总累计行程时间。 
- 该路线已完成的行程数。 

重要的边缘情况包括：

 - 多个用户同时旅行。 
- 同一对车站之间的多次行程。 
- 存在于两个方向的路线，因为`"A" -> "B"`和`"B" -> "A"`是不同的路线。 
- 通话`getAverageTime`在新的旅行发生之前反复进行。 
- 用户与其他用户交替签入和签出。 

如果每次请求平均值时重复扫描所有行程，简单的实现很容易变得低效。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是单独存储每个已完成的行程。 

我们可以维护：

 - 从客户 ID 到有效签到信息的映射。 
- 另一张地图来自`(startStation, endStation)`到行程持续时间列表。 

当顾客结帐时：

 1. 检索他们的签到数据。 
2. 计算行程时间。 
3. 将持续时间添加到路线列表中。 

什么时候`getAverageTime`称为：

 1. 检索路线的持续时间列表。 
2. 将所有持续时间相加。 
3. 除以行程次数。 

这种方法是正确的，因为每次行程持续时间都被显式存储，因此始终可以准确计算平均值。 

然而，它的效率很低，因为每个平均查询都需要迭代该路线的所有行程。 如果存在许多行程，重复的平均计算就会变得昂贵。 

### 最佳方法

 关键的见解是平均值不需要存储每个单独的行程。 

要计算平均值，我们只需要：

 - 所有行程时间的总和。 
- 行程总数。 

利用这一观察，我们可以维持：

 - 活跃签到的哈希图：

 -`id -> (stationName, checkInTime)`- 路由统计的哈希图：

 -`(startStation, endStation) -> (totalTime, tripCount)`当顾客结帐时：

 1. 检索他们的签到信息。 
2. 计算行程持续时间。 
3. 更新该路线的累计总时间。 
4. 增加路线的行程计数。 

现在`getAverageTime`变得非常有效，因为答案很简单：```
average = totalTime / tripCount
```无需对历史旅行进行迭代。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | 每个平均查询 O(n) | O(n) | 单独存储每个行程持续时间 |
 | 最佳 | 每次操作 O(1) | O(n) | 仅存储汇总统计数据 |

 ## 算法演练

 1. 创建一个名为的哈希图`check_ins`。 

该地图存储当前活跃的乘客。 键为乘客ID，值包含：

 - 他们办理登机手续的车站
 - 入住时间

 示例：```
45 -> ("Leyton", 3)
```2. 创建另一个哈希映射，名为`route_stats`。 

该地图存储每条路线的汇总统计数据。 

关键是一对：```
(startStation, endStation)
```该值包含：

 - 累计旅行时间
 - 已完成行程总数

 示例：```
("Leyton", "Waterloo") -> (22, 2)
```3. 什么时候`checkIn(id, stationName, t)`称为：

 将乘客当前的行程信息存储在`check_ins`。 

这允许我们稍后将结账事件与相应的签入事件进行匹配。 
4. 什么时候`checkOut(id, stationName, t)`称为：

 从以下位置检索乘客的登机数据`check_ins`。 

计算行程持续时间：```
duration = checkoutTime - checkinTime
```构造路由键：```
(startStation, endStation)
```更新累积路由统计信息：

 - 将持续时间添加到总旅行时间中
 - 增加行程计数

 将乘客从`check_ins`因为他们的旅程已经完成。 
5. 什么时候`getAverageTime(startStation, endStation)`称为：

 检索存储的路线统计信息。 

计算：```
totalTime / tripCount
```以浮点值形式返回结果。 

### 为什么它有效

 该算法之所以有效，是因为每次完成的行程都会对相应的路线统计数据贡献一次。 

对于每条路线，我们维护两个不变值：

 - 所有已完成行程持续时间的总和
 - 已完成行程的计数

 自：```
average = totalSum / totalCount
```返回的值始终是正确的平均行程时间。 

这`check_ins`map保证每次签出操作都能正确恢复匹配的签入信息。 

## Python 解决方案```python
class UndergroundSystem:

    def __init__(self):
        # id -> (station_name, check_in_time)
        self.check_ins = {}

        # (start_station, end_station) -> [total_time, trip_count]
        self.route_stats = {}

    def checkIn(self, id: int, stationName: str, t: int) -> None:
        self.check_ins[id] = (stationName, t)

    def checkOut(self, id: int, stationName: str, t: int) -> None:
        start_station, check_in_time = self.check_ins[id]

        duration = t - check_in_time
        route = (start_station, stationName)

        if route not in self.route_stats:
            self.route_stats[route] = [0, 0]

        self.route_stats[route][0] += duration
        self.route_stats[route][1] += 1

        del self.check_ins[id]

    def getAverageTime(self, startStation: str, endStation: str) -> float:
        total_time, trip_count = self.route_stats[(startStation, endStation)]

        return total_time / trip_count

# Your UndergroundSystem object will be instantiated and called as such:
# obj = UndergroundSystem()
# obj.checkIn(id, stationName, t)
# obj.checkOut(id, stationName, t)
# param_3 = obj.getAverageTime(startStation, endStation)
```该实现使用两个字典。 

这`check_ins`字典跟踪当前在系统中旅行的所有活跃乘客。 每个乘客 ID 都映射到行程开始的车站和时间戳。 

这`route_stats`字典存储每条路线的聚合信息。 我们不会单独存储每次行程，而是只保留累计行程时间和行程次数。 

在结帐期间，代码检索原始签入信息，计算持续时间，并更新相应的路线统计信息。 

平均查询变得非常高效，因为结果是直接从存储的聚合计算出来的，无需扫描历史行程。 

将乘客从`check_ins`检验后可确保活动跳闸状态保持准确。 

## 解决方案```go
package main

type CheckInData struct {
	station string
	time    int
}

type RouteStats struct {
	totalTime int
	tripCount int
}

type UndergroundSystem struct {
	checkIns  map[int]CheckInData
	routeData map[string]RouteStats
}

func Constructor() UndergroundSystem {
	return UndergroundSystem{
		checkIns:  make(map[int]CheckInData),
		routeData: make(map[string]RouteStats),
	}
}

func (this *UndergroundSystem) CheckIn(id int, stationName string, t int) {
	this.checkIns[id] = CheckInData{
		station: stationName,
		time:    t,
	}
}

func (this *UndergroundSystem) CheckOut(id int, stationName string, t int) {
	checkIn := this.checkIns[id]

	duration := t - checkIn.time
	routeKey := checkIn.station + "->" + stationName

	stats := this.routeData[routeKey]
	stats.totalTime += duration
	stats.tripCount++

	this.routeData[routeKey] = stats

	delete(this.checkIns, id)
}

func (this *UndergroundSystem) GetAverageTime(startStation string, endStation string) float64 {
	routeKey := startStation + "->" + endStation

	stats := this.routeData[routeKey]

	return float64(stats.totalTime) / float64(stats.tripCount)
}

/**
 * Your UndergroundSystem object will be instantiated and called as such:
 * obj := Constructor()
 * obj.CheckIn(id, stationName, t)
 * obj.CheckOut(id, stationName, t)
 * param_3 := obj.GetAverageTime(startStation, endStation)
 */
```Go 实现遵循与 Python 版本相同的逻辑，但使用结构体和类型化映射。 

由于 Go 不像 Python 那样方便地支持元组键，因此路由键表示为连接字符串：```go
startStation + "->" + endStation
```Go 地图会针对缺失的键自动返回零值结构，这简化了更新路由统计信息。 

平均计算将整数显式转换为`float64`以避免整数除法。

 | 测量| 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(1) | O(1) | 每个操作仅执行恒定时间哈希映射操作 |

 所有三个操作的时间复杂度都是恒定的，因为哈希图插入、查找和更新操作的平均情况为 O(1)。 

空间复杂度随着以下因素的增加而增加：

 - 当前办理登机手续的活跃乘客数量。 
- 不同车站到车站路线的数量。 

在最坏的情况下，两者都会随着操作数量成比例增长。

 ## 边缘情况

 一种重要的边缘情况是多个用户同时旅行。 有缺陷的实施可能会覆盖或混淆乘客之间的登机记录。 该解决方案避免了这个问题，因为每次活动行程都由唯一的客户 ID 来键入`check_ins`字典。 

另一个关键的边缘情况是定向路由。 平均出行时间从`"A"`到`"B"`不一定等于`"B"`到`"A"`。 有缺陷的实现可能会意外地将两个方向合并到同一个统计数据桶中。 这个实现正确地对待`(startStation, endStation)`作为有序对，因此两条路线保持独立。 

第三个重要的边缘情况涉及在新行程发生之前重复的平均查询。 在添加其他已完成的行程之前，结果应保持不变。 由于该实现存储累积总计而不是每次从原始数据重新计算，因此重复调用可以有效地返回稳定且正确的结果。 

另一个微妙的情况是在多次旅行中重复使用同一个乘客 ID。 退房后，旧的入住记录必须删除。 否则，未来的旅行可能会意外地使用过时的信息。 该实施明确删除了乘客`check_ins`处理结帐后，确保每次行程都是独立处理的。
