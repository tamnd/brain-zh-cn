[LeetCode 1303 题](https://leetcode.com/problems/find-the-team-size/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题提供了一个数据库表，名为`Employee`，其中每一行代表一名员工及其所属的团队。 该表包含两列：

 | 专栏 | 意义|
 | ---| ---|
 |`employee_id`| 员工的唯一标识符 |
 |`team_id`| 员工所属团队的标识符 |

 任务是计算每个员工团队的规模。 换句话说，对于每个员工，我们需要确定有多少员工共享相同的`team_id`。 

输出应包含：

 | 专栏 | 意义|
 | ---| ---|
 |`employee_id`| 员工身份证|
 |`team_size`| 该员工团队中的员工人数 |

 结果可以按任何顺序返回，这意味着除非明确要求，否则我们不需要对输出进行排序。 

重要的观察是，同样`team_id`可以出现多次，该团队中的每个员工一次。 因此，这个问题本质上是要求我们统计每一个的出现频率。`team_id`然后将该计数与每个员工关联起来。 

因为`employee_id`保证是唯一的，我们永远不需要担心重复的员工行。 该问题还保证每个员工都属于一个团队。 

一个重要的边缘情况是只有一名员工的团队。 在这种情况下，团队规模应该是`1`。 另一个重要的情况是当所有员工都属于同一个团队时，这意味着每个员工都会收到相同的大计数。 对于大型数据集来说，重复扫描表中每个员工的简单实现可能会变得低效。 

由于这是一个数据库问题，因此预期的解决方案通常是使用聚合和连接用 SQL 编写的。 

## 方法

 ### 蛮力方法

 暴力解决方案单独检查每个员工并计算有多少员工共享相同的信息`team_id`。 

对于表中的每一行：

 1. 阅读员工的`team_id`2.再次扫描全表
 3. 统计有多少行有相同的`team_id`4. 算作员工团队规模的产出

 这种方法是正确的，因为它直接计算出每个员工属于同一团队的确切员工数量。 

然而，它的效率很低，因为对于每个员工，我们都会对表执行另一次完整扫描。 如果有`n`员工，那么每个`n`行需要一个`O(n)`扫描，结果是`O(n²)`时间复杂度。 

### 最佳方法

 关键的见解是许多员工都有相同的看法`team_id`，因此重复计算同一团队是浪费的。 

相反，我们可以使用以下方法计算每个团队的规模`GROUP BY`。 获得映射后`team_id`根据团队规模，我们将该结果连接回原始表，以便每个员工都会收到相应的计数。 

这很有效，因为：

 1.`GROUP BY team_id`计算一次团队规模
 2. 连接将每个员工与其团队人数相关联
 3、无需重复扫描

 这将工作量减少到基本上是表的线性处理。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(1) | O(1) | 重复扫描表中的每个员工 |
 | 最佳| O(n) | O(n) | 使用聚合`GROUP BY`和一个加入 |

 ## 算法演练

 ### 最优 SQL 算法

 1. 首先，将所有员工分组`team_id`。 

此步骤计算每个团队有多少员工。 我们使用 SQL`COUNT(*)`聚合函数，因为我们想要每个团队的行数。 
2. 将分组结果存储为临时派生表。 

派生表包含：

 | 团队 ID | 团队规模 |
 | ---| ---|
 | 8 | 3 |
 | 7 | 1 |
 | 9 | 2 |

 这可以防止多次重新计算相同的计数。 
3. 将派生表连接回原始表`Employee`桌子。 

加入条件为：```sql
Employee.team_id = grouped.team_id
```这允许每个员工行检索相应的团队规模。 
4. 选择所需的列。 

最终输出只需要：

 -`employee_id`-`team_size`### 为什么它有效

 该算法之所以有效，是因为每个员工都属于一个`team_id`，并且分组表仅包含每个团队的一行以及正确的员工人数。 加入于`team_id`确保每位员工都获得与其团队相关的正确团队规模。 

## Python 解决方案

 尽管这是一个数据库问题并且 LeetCode 需要 SQL，但以下 Python 实现以编程方式演示了相同的逻辑。```python
from typing import List, Dict
from collections import Counter

class Solution:
    def findTeamSize(self, employees: List[List[int]]) -> List[List[int]]:
        team_counts: Dict[int, int] = Counter()

        # Count employees in each team
        for employee_id, team_id in employees:
            team_counts[team_id] += 1

        # Build result
        result = []

        for employee_id, team_id in employees:
            result.append([employee_id, team_counts[team_id]])

        return result
```该实现遵循与最佳 SQL 方法相同的逻辑。 

第一个循环计算每个循环有多少员工`team_id`。 一个`Counter`使用它是因为它提供了方便的频率图结构，其中键是团队 ID，值是团队规模。 

构建频率图后，第二个循环再次迭代员工，并为每个员工附加相应的团队规模。 

最终结果包含以下几对：```python
[employee_id, team_size]
```这反映了预期的 SQL 输出结构。 

## 解决方案```go
package main

func findTeamSize(employees [][]int) [][]int {
	teamCounts := make(map[int]int)

	// Count employees in each team
	for _, employee := range employees {
		teamID := employee[1]
		teamCounts[teamID]++
	}

	// Build result
	result := [][]int{}

	for _, employee := range employees {
		employeeID := employee[0]
		teamID := employee[1]

		result = append(result, []int{
			employeeID,
			teamCounts[teamID],
		})
	}

	return result
}
```Go 的实现与 Python 版本非常相似。 一个`map[int]int`用于存储团队频率。 Go 切片用于动态构造结果。 

与Python不同`Counter`，Go 需要显式的映射初始化和手动递增。 除了语法差异之外，算法保持相同。 

由于所有值都是小整数计数，因此在正常问题约束中不需要考虑整数溢出。 

## SQL 解决方案```sql
SELECT
    e.employee_id,
    t.team_size
FROM Employee e
JOIN (
    SELECT
        team_id,
        COUNT(*) AS team_size
    FROM Employee
    GROUP BY team_id
) t
ON e.team_id = t.team_id;
```该解决方案首先使用以下方法计算每个团队的规模`GROUP BY`。 然后将派生表连接回原始表`Employee`表将每个员工与其相应的团队规模相关联。

 ## 边缘情况

 ### 只有一名员工的团队

 一个常见的错误是错误地假设每个团队都包含多名员工。 如果一个团队在表中仅出现一次，则其计数仍必须正确计算为`1`。 

该实现自然地处理了这个问题，因为计数阶段每次发生时都会增加频率一次。 出现一次的队伍就可以被计数`1`。 

### 所有员工都属于同一个团队

 当每个员工共享相同的信息时，就会出现另一种边缘情况`team_id`。 幼稚的实现可能会重复地为每个员工重新计算相同的计数，从而导致不必要的工作。 

优化的方法避免了这个问题，因为团队计数仅计算一次并为所有员工重复使用。 

### 每个员工都有一个独特的团队

 在这种情况下，每个团队的规模都等于`1`。 这可能会暴露开发人员错误聚合或假设重复团队始终存在的错误。 

频率图正确地为每个独特的团队创建一个条目，并分配一个计数`1`给每个员工。 

### 大量员工

 对于大型数据集，暴力方法变得低效，因为它会重复扫描整个表。 

优化的解决方案可有效扩展，因为它仅对数据执行线性传递并使用恒定时间哈希映射查找。
