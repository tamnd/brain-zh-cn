[LeetCode 第 1383 题](https://leetcode.com/problems/maximum-performance-of-a-team/)

 **难度：** 🔴难
 **主题：** 数组、贪婪、排序、堆（优先级队列）

 ## 解决方案

 ## 问题理解

 这个问题要求我们组建一个最多`k`工程师，使团队的绩效最大化。 

每个工程师都有两个属性：

 -`speed[i]`，代表工程师的速度有多快
 -`efficiency[i]`，代表工程师的效率有多高

 团队绩效定义为：$$\text{performance} = (\text{sum of team speeds}) \times (\text{minimum efficiency in the team})$$这个定义很重要，因为所有选定工程师的最低效率成为整个团队的瓶颈。 

我们可以从以下人员中选择任意数量的工程师`1`最多`k`。 我们不必精确地使用`k`工程师。 

输入包括：

 -`n`, 工程师总数
 -`speed`，长度数组`n`-`efficiency`，另一个长度数组`n`-`k`, 允许的最大团队规模

 输出应该是最大可能的性能模数：$$10^9 + 7$$限制条件非常大：

 -`n`可以达到`100000`- 速度可达`100000`- 效率可达`100000000`这些限制立即排除了指数或二次方法。 任何解决方案明显比`O(n log n)`可能会超时。 

一些边缘情况很重要：

 -`k = 1`，我们只需要单个工程师拥有最大的`speed * efficiency`-`k = n`，其中所有工程师都有可能被选择
 - 效率极高但速度低下的工程师
 - 速度极高但效率低下的工程师
 - 最佳团队使用少于的情况`k`工程师
 - 大值可能会溢出 32 位整数，尤其是在 Go 中

 该问题保证：

 -`speed`和`efficiency`长度相等
 - 所有数值均为正值
 - 至少存在一名工程师

 因为所有值都是正数，所以增加速度通常会有所帮助，但增加效率低下的工程师可能会大大降低团队的最低效率。 平衡这两个相互竞争的因素是关键的挑战。 

## 方法

 ### 蛮力方法

 暴力解决方案将尝试每一个可能的工程师子集，其规模最多为`k`。 

对于每个子集：

 1. 计算速度总和
 2. 计算最低效率
 3. 计算性能
 4. 追踪最大结果

 这是有效的，因为它直接评估每个有效的团队配置，保证最佳答案。 

然而，子集的数量是巨大的。 有：$$2^n$$总共可能的子集。 甚至将子集大小限制为最多`k`没有足够的帮助时`n = 100000`。 

即使对于中等值，这种方法在计算上也是不可能的`n`。 

### 最优贪婪+堆方法

 关键的见解来自于对公式的分析：$$(\text{sum of speeds}) \times (\text{minimum efficiency})$$假设我们确定某个工程师是团队中效率最低的工程师。 

如果该工程师确定了最低效率，则所有其他选定的工程师的效率都必须大于或等于该工程师的效率。 

这一观察结果建议按效率降序对工程师进行排序。 

当加工工程师从最高效率到最低效率时：

 - 当前工程师成为效率最低的候选人
 - 所有之前处理过的工程师的效率至少一样大
 - 因此，任何由被处理的工程师组成的团队，其最低效率等于当前工程师的效率

 现在问题变成：

 > 对于当前最低效率，选择最多`k`总速度最大的工程师。 

为了有效地最大化速度总和，我们使用最小堆：

 - 跟踪选定的速度
 - 如果团队规模超过`k`, 去掉最小速度
 - 保持速度的运行总和

 这给出了一个有效的`O(n log k)`排序后的解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(2^n * n) | O(2^n * n) | O(n) | 枚举每个可能的子集 |
 | 最佳 | O(n log n) | O(n log n) | O(k) | Sort by efficiency and maintain best speeds using a heap |

 ## 算法演练

 1. Combine each engineer's efficiency and speed into a pair.

 我们创建如下元组：```
(efficiency, speed)
```这使我们能够一起处理这两个值。 
2. 按效率降序对工程师进行排序。 

这是关键的贪心步骤。 

当处理工程师从最高效率到最低效率时，当前工程师总是成为当前候选团队中效率最低的。 
3. 初始化一个最小堆来存储选定的速度。 

堆帮助我们有效地维护`k`迄今为止遇到的最大速度。 
4. 保持运行的速度总和。 

每次我们将工程师的速度添加到堆中时，我们也会将其添加到运行总计中。 
5. 迭代排序后的工程师。 

对于每位工程师：

 - 将工程师的速度添加到堆中
 - 将速度添加到运行总和中
 6. 如果堆大小超过`k`，去掉最小的速度。 

因为我们最多只想要`k`工程师，我们抛弃了团队中目前最慢的工程师。 

最小堆使此操作变得高效。 
7. 计算当前性能。 

由于当前工程师在迄今为止处理的所有工程师中效率最低：$$\text{performance} = (\text{current speed sum}) \times (\text{current efficiency})$$8.更新目前看到的最大性能。 
9. 返回模数答案`10^9 + 7`。 

### 为什么它有效

 该算法之所以有效，是因为排序顺序。 

在每次迭代中，当前工程师都会定义团队的最低效率。 所有先前考虑​​的工程师都具有相同或更高的效率，因此添加他们不会进一步降低最低效率。 

因此，一旦确定了最低效率，唯一剩下的目标就是最大化速度总和。 保持`k`使用堆的最大速度保证了该效率阈值的最佳可能速度总和。 

通过对每个可能的最低效率进行一次评估，该算法探索所有有效的最佳团队配置。 

## Python 解决方案```python
from typing import List
import heapq

class Solution:
    def maxPerformance(
        self,
        n: int,
        speed: List[int],
        efficiency: List[int],
        k: int
    ) -> int:
        MOD = 10**9 + 7

        engineers = sorted(
            zip(efficiency, speed),
            reverse=True
        )

        speed_heap = []
        speed_sum = 0
        max_performance = 0

        for current_efficiency, current_speed in engineers:
            heapq.heappush(speed_heap, current_speed)
            speed_sum += current_speed

            if len(speed_heap) > k:
                removed_speed = heapq.heappop(speed_heap)
                speed_sum -= removed_speed

            performance = speed_sum * current_efficiency
            max_performance = max(max_performance, performance)

        return max_performance % MOD
```实施首先使用将效率和速度配对在一起`zip`。 然后我们按照效率降序对工程师进行排序。 

这`speed_heap`存储选定的工程师速度。 自从Python的`heapq`是一个最小堆，最小的速度总是在根部。 

当我们迭代工程师时，我们将每个工程师的速度添加到堆和运行速度总计中。 

如果堆大小超过`k`，我们去掉最小的速度。 这保证了堆始终包含当前效率阈值的最佳可能速度集。 

在每次迭代中，我们使用以下方法计算性能：```python
speed_sum * current_efficiency
```由于工程师是按照效率降序处理的，所以保证当前效率是当前团队中效率最低的。 

最后，我们返回模数结果`10^9 + 7`。 

## 解决方案```go
package main

import (
	"container/heap"
	"sort"
)

const MOD int = 1e9 + 7

type MinHeap []int

func (h MinHeap) Len() int {
	return len(h)
}

func (h MinHeap) Less(i, j int) bool {
	return h[i] < h[j]
}

func (h MinHeap) Swap(i, j int) {
	h[i], h[j] = h[j], h[i]
}

func (h *MinHeap) Push(x interface{}) {
	*h = append(*h, x.(int))
}

func (h *MinHeap) Pop() interface{} {
	old := *h
	n := len(old)
	value := old[n-1]
	*h = old[:n-1]
	return value
}

func maxPerformance(n int, speed []int, efficiency []int, k int) int {
	type Engineer struct {
		efficiency int
		speed      int
	}

	engineers := make([]Engineer, n)

	for i := 0; i < n; i++ {
		engineers[i] = Engineer{
			efficiency: efficiency[i],
			speed:      speed[i],
		}
	}

	sort.Slice(engineers, func(i, j int) bool {
		return engineers[i].efficiency > engineers[j].efficiency
	})

	speedHeap := &MinHeap{}
	heap.Init(speedHeap)

	var speedSum int64 = 0
	var maxPerformance int64 = 0

	for _, engineer := range engineers {
		heap.Push(speedHeap, engineer.speed)
		speedSum += int64(engineer.speed)

		if speedHeap.Len() > k {
			removedSpeed := heap.Pop(speedHeap).(int)
			speedSum -= int64(removedSpeed)
		}

		performance := speedSum * int64(engineer.efficiency)

		if performance > maxPerformance {
			maxPerformance = performance
		}
	}

	return int(maxPerformance % int64(MOD))
}
```Go 解决方案遵循与 Python 版本相同的算法结构，但 Go 需要使用显式堆实现`container/heap`包裹。 

定制`MinHeap`type 实现所需的堆接口方法。 

Go 特有的一个重要细节是整数溢出。 性能计算可以超出32位整数的范围，因此实现时使用`int64`为了：

-`speedSum`-`maxPerformance`- 中间乘法

 如果没有这种转换，大输入上就会出现溢出错误。

    def maxPerformance(self, n: int, speed: List[int], efficiency: List[int], k: int) -> int:
        import heapq

        MOD = 10**9 + 7

        engineers = sorted(zip(efficiency, speed), reverse=True)

        speed_heap = []
        speed_sum = 0
        answer = 0

        for e, s in engineers:
            heapq.heappush(speed_heap, s)
            speed_sum += s

            if len(speed_heap) > k:
                speed_sum -= heapq.heappop(speed_heap)

            answer = max(answer, speed_sum * e)

        return answer % MOD

 ## 边缘情况

 一种重要的边缘情况发生在以下情况：`k = 1`。 在这种情况下，每个团队只包含一名工程师，因此性能变为：$$\text{speed} \times \text{efficiency}$$有错误的实现可能仍然会尝试不必要的堆逻辑或意外地合并工程师。 当前的实现自然会处理这一问题，因为堆大小仅限于一个元素。 

当最优解使用少于`k`工程师。 由于问题说“至多`k`“，我们不需要完全填满团队。天真的实施可能会错误地强制准确`k`工程师融入团队，不必要地降低了最低效率。 基于堆的解决方案会评估每一步的性能，因此会自动考虑较小的团队。 

大整数溢出是另一个主要问题。 速度总和可以为：$$100000 \times 100000 = 10^{10}$$再次乘以效率可以产生以下值：$$10^{18}$$这超出了 32 位整数限制。 Go 实现明确使用`int64`对于所有关键算术以避免溢出错误。 

另一个微妙的边缘情况涉及从堆中删除工程师。 当堆超过大小时`k`，我们必须去掉最小的速度，而不是最大的。 删除错误的值会不必要地降低速度总和并产生错误的结果。 使用最小堆可以保证首先丢弃最不有价值的速度贡献。
