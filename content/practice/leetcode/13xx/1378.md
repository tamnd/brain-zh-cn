[LeetCode 问题 1378](https://leetcode.com/problems/replace-employee-id-with-the-unique-identifier/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题要求我们组合两个数据库表中的信息并以特定格式返回结果。 

我们被赋予了一个`Employees`包含基本员工信息的表，特别是员工`id`和`name`。 我们还被赋予了`EmployeeUNI`映射员工的表`id`到一个`unique_id`。 目标是产生这样的结果：每个员工及其相应的信息都只出现一次`unique_id`如果存在的话。 

换句话说，对于公司中的每一位员工`Employees`表中，我们想要查找该员工是否有条目`EmployeeUNI`。 如果存在匹配记录，我们将显示关联的记录`unique_id`。 如果不存在匹配记录，我们显示`null`反而。 

关键细节是**每个员工都必须出现在输出中**，即使他们在`EmployeeUNI`。 这立即表明我们应该保留来自`Employees`并可选择附加来自的匹配数据`EmployeeUNI`。 

输入由两个关系表组成：

 -`Employees(id, name)`包含所有员工。 
-`EmployeeUNI(id, unique_id)`包含从员工 ID 到唯一标识符的映射。 

预期输出是一个表格，其中包含：

 -`unique_id`-`name`行的顺序并不重要，这意味着我们不需要对结果进行排序。 

约束告诉我们有关数据的几个重要信息：

 -`Employees.id`是主键，意味着员工 ID 是唯一的。 
-`(id, unique_id)`是主键`EmployeeUNI`，意味着不存在重复的映射。 
- 部分员工可能不会出现在`EmployeeUNI`。 
- 每一个`EmployeeUNI.id`对应员工ID。 

最重要的边缘情况是没有相应唯一标识符的员工。 使用错误类型的连接的幼稚实现可能会意外地将它们从结果中排除。 我们必须确保这些员工仍然带着`null`作为他们的`unique_id`。 

## 方法

 ### 蛮力方法

 暴力解决方案将手动搜索匹配的`unique_id`对于每个员工。 

对于每一行`Employees`，我们可以迭代整个`EmployeeUNI`寻找匹配的表`id`。 如果找到匹配项，我们返回`unique_id`。 否则，我们返回`null`。 

这种方法是正确的，因为它明确检查每个员工的每个可能的匹配项。 由于我们检查了所有行`EmployeeUNI`，我们保证找到正确的映射（如果存在）。 

然而，这种方法效率低下，因为它会重复扫描第二个表。 如果有`n`员工和`m`唯一的ID记录，总工作量成正比`n × m`。 

### 最佳方法

 关键的观察结果是，这是一个经典的**连接操作**问题。 

我们需要保留所有员工，同时附上匹配的唯一 ID（如果有）。 在 SQL 中，这正是 **LEFT JOIN** 的作用。 

一个`LEFT JOIN`保留左表中的所有行（`Employees`）并填充右表中不匹配的值（`EmployeeUNI`） 和`NULL`。 

由于关系数据库针对连接进行了优化，因此该解决方案既简洁又高效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n × m) | O(1) | O(1) | 扫描`EmployeeUNI`对于每一位员工|
 | 最佳 | O(n + m) | O(1)* | O(1)* 使用 SQL`LEFT JOIN`高效匹配 ID |

 *数据库引擎可能在内部使用索引或散列连接，但从查询编写的角度来看，不使用额外的显式空间。 

## 算法演练

 ### 使用 LEFT JOIN 的最优算法

 1. 从`Employees`表，因为每个员工都必须出现在输出中。 
2. 执行`LEFT JOIN`之间`Employees`和`EmployeeUNI`使用雇员`id`。 

我们匹配以下行：```
Employees.id = EmployeeUNI.id
```这确保了如果有相应的`unique_id`存在，它将附加到员工行。 
3. 选择所需的列：

 -`EmployeeUNI.unique_id`-`Employees.name`4. 如果员工没有匹配的行`EmployeeUNI`,SQL自动放置`NULL`在`unique_id`列，因为我们使用了`LEFT JOIN`。 
5. 由于不需要排序，因此以任意顺序返回结果。 

### 为什么它有效

 该解决方案的正确性取决于`LEFT JOIN`。 一个`LEFT JOIN`保证左表中的每一行都保留在输出中。 如果可用，则包含右表中的匹配行，并且不匹配的值将替换为`NULL`。 

由于该问题要求每个员工只出现一次，因此`null`对于缺失的标识符，a`LEFT JOIN`精确匹配所需的行为。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT eu.unique_id, e.name
FROM Employees e
LEFT JOIN EmployeeUNI eu
ON e.id = eu.id;
```该实现直接将算法翻译成SQL。 

We begin with the`Employees`表，因为每个员工都必须包含在结果中。 然后我们使用一个`LEFT JOIN`和`EmployeeUNI`在共享的`id`柱子。 

别名`e`代表`Employees`， 和`eu`代表`EmployeeUNI`。 使用别名可以使查询简洁且更易于阅读。 

这`SELECT`语句仅检索所需的列：

 -`eu.unique_id`-`e.name`如果雇员不存在于`EmployeeUNI`，连接产生一个`NULL`自动值，与问题要求完全匹配。

 ## 边缘情况

 当员工在数据库中没有匹配的行时，就会出现一种重要的边缘情况。`EmployeeUNI`。 一个常见的错误是使用`INNER JOIN`，这将从结果中完全删除不匹配的员工。 通过使用`LEFT JOIN`，不匹配的员工被保留并接收`NULL`自动值。 

另一个边缘情况是**所有员工都缺乏唯一的 ID**。 在这种情况下，每个员工仍必须出现在结果表中。 该实现正确地处理了这个问题，因为`LEFT JOIN`永远不会从左表中删除行。 

第三个重要的情况是**每个员工都有一个匹配的唯一 ID**。 在这种情况下，结果的行为类似于`INNER JOIN`，但是`LEFT JOIN`仍然可以正常工作并返回所有匹配项而无需修改。 

最后，还有一种情况，`EmployeeUNI`表仅包含员工的子集。 查询自然地处理这个问题，因为匹配的行接收有效的`unique_id`不匹配行收到的值`NULL`。
