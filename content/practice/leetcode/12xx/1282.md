[LeetCode 问题 1282](https://leetcode.com/problems/group-the-people-given-the-group-size-they-belong-to/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、贪婪

 ## 解决方案

 ## 问题理解

 问题给了我们一个名为`groupSizes`，其中每个索引代表一个人，每个值代表该人必须所属的组的大小。 

每个人都有一个唯一的 ID，范围从`0`到`n - 1`， 在哪里`n`是数组的长度。 对于任何人`i`，值`groupSizes[i]`准确地告诉我们该人的组中必须存在多少人。 

例如，如果`groupSizes[2] = 3`，那么人`2`必须属于恰好包含三个人的组。 重要的是，该组内的每个人还必须具有所需的组大小`3`。 

任务是构造并返回满足所有这些约束的组列表：

 - 每个人只出现一次。 
- 每个人都属于一个规模相匹配的群体`groupSizes[i]`。 
- 每个小组均包含所需人数。 
- 可能存在多个有效答案，并且返回任何有效分组都是可以接受的。 

输入是一个整数数组：```
groupSizes[i] = required size of person i's group
```输出是一个二维列表，其中每个内部列表代表一组有效的人。 

例如：```
groupSizes = [3,3,3,3,3,1,3]
```有效的结果可能是：```
[[5], [0,1,2], [3,4,6]]
```人`5`需要团体规模为`1`，所以他们单独组成一个群体。 剩下需要尺寸的人`3`被分成恰好由三个成员组成的有效组。 

约束条件告诉我们有关问题规模的有用信息：

 -`1 <= n <= 500`-`1 <= groupSizes[i] <= n`自从`n`至多是`500`，甚至一个`O(n²)`解决方案可能会通过，但问题结构强烈建议采用更有效的线性时间解决方案。 

该问题还保证至少有一个有效的解决方案始终存在。 这种保证很重要，因为这意味着我们永远不必担心不可能的配置或无效输入的错误处理。 

有几种边缘情况值得预先考虑。 当许多人需要相同的组大小时，幼稚的实现可能会很困难，因为我们必须小心地将他们分成不同的组而不重叠。 另一个棘手的情况是当组大小等于`1`，因为这些人必须立即组成独立的团体。 我们还需要确保一旦组达到所需的大小，它就会被最终确定，并且以后不会被意外修改。 

## 方法

 ### 蛮力方法

 暴力方法会尝试反复搜索兼容的人并手动构建群体。 

对于每个未分配的人，我们可以搜索剩余的人，以找到足够多的具有相同所需团体规模的人。 一旦找到足够的人，我们就会组成一个小组并将这些人标记为已分配。 

这种方法之所以有效，是因为人们只能属于与其所需规模相匹配的群体。 通过反复扫描列表并对兼容的个体进行分组，我们最终分配每个人。 

然而，这种方法变得低效，因为每个人都可能触发对剩余阵列的另一次扫描。 在最坏的情况下，这会导致重复遍历输入，从而导致二次时间复杂度。 

例如，如果许多人属于相同的组大小，我们会重复搜索数组以查找可以更有效地跟踪的候选者。 

### 最优方法，哈希图分组

 关键的观察结果是，具有相同所需群体规模的人自然会归属在一起。 

我们可以处理一次输入，并使用哈希映射按所需的大小对人员进行分组，而不是重复搜索兼容的人员。 

哈希映射存储部分形成的组：```
group size -> current people collected
```当我们遍历数组时：

 - 将当前人员添加到相应的临时组中。 
- 如果临时组达到所需大小，则完成它。 
- 将已完成的组添加到答案中。 
- 重置该大小的临时组。 

这是有效的，因为有效组的所有成员必须共享相同的所需大小。 由于输入保证了有效的解决方案，一旦我们收集到所需数量的人员，我们就知道该小组已经完成。 

这避免了重复搜索，并且对每个人只处理一次。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(n) | 反复扫描匹配的人|
 | 最佳 | O(n) | O(n) | 使用哈希映射增量构建组 |

 ## 算法演练

 ### 最优算法

 1. 创建一个空结果列表来存储已完成的组。 
2. 创建一个哈希映射，其中：```
key = group size
value = temporary list of people
```该地图帮助我们跟踪每个所需大小的部分构建的组。 
3. 迭代`groupSizes`使用人员的索引和所需的团体规模。 
4. 对于每个人：

 - 将他们的 ID 添加到临时列表中，以满足其所需的团体规模。 
- 这意味着我们正在收集属于同一类型群体的人。 
5. 添加人员后，检查临时群组是否达到要求的规模。 

例如：```
group size = 3
temporary group = [0,1,2]
```由于现在列表长度是`3`，该组已完成。 
6. 将完成的组添加到结果中。 
7. 重置该小组规模的临时列表，以便将来的人员可以组成相同规模的其他小组。 
8. 继续，直到处理完所有人员。 
9. 返回完成的结果列表。 

### 为什么它有效

 该算法保持了一个重要的不变量：

 > 每个临时小组仅包含需要相同小组规模的人员。 

由于只有当组恰好达到其所需的大小时才最终确定，因此每个完成的组都是有效的。 

此外，每个人都只被处理一次，并立即被分到一个临时组中。 一旦最终确定，该组就不会再被修改。 因为输入保证了有效的解决方案，所以每个人最终都会属于一个完整的有效群体。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class Solution:
    def groupThePeople(self, groupSizes: List[int]) -> List[List[int]]:
        result = []
        groups = defaultdict(list)

        for person_id, group_size in enumerate(groupSizes):
            groups[group_size].append(person_id)

            if len(groups[group_size]) == group_size:
                result.append(groups[group_size])
                groups[group_size] = []

        return result
```实施首先创建一个`result`存储已完成组的列表。 

然后我们使用`defaultdict(list)`简化哈希图管理。 这允许我们将人员追加到组大小的存储桶中，而无需检查密钥是否已存在。 

在迭代过程中，`enumerate(groupSizes)`给出此人的 ID 和所需的团体人数。 

对于每个人，我们将他们的 ID 添加到相应的临时组中：```python
groups[group_size].append(person_id)
```插入后，我们立即检查该组是否已达到所需的大小。```python
if len(groups[group_size]) == group_size:
```如果有，则该组已完成，因此我们将其附加到结果中并为未来的成员重置存储桶。 

此重置步骤很重要，因为可能有多个具有相同所需大小的组。 

例如：```python
[3,3,3,3,3,3]
```需要两个不同尺寸的组`3`。 

最后，我们返回完成的结果列表。 

## 解决方案```go
func groupThePeople(groupSizes []int) [][]int {
	result := [][]int{}
	groups := make(map[int][]int)

	for personID, groupSize := range groupSizes {
		groups[groupSize] = append(groups[groupSize], personID)

		if len(groups[groupSize]) == groupSize {
			result = append(result, groups[groupSize])
			groups[groupSize] = []int{}
		}
	}

	return result
}
```Go 实现遵循与 Python 版本完全相同的逻辑。 

而不是`defaultdict`, Go 使用`map[int][]int`其中键是所需的组大小，值是收集的人员的一部分。 

即使切片尚不存在，追加也会自然地进行：```go
groups[groupSize] = append(groups[groupSize], personID)
```Go 自动将缺失的映射条目视为零值，对于切片来说是`nil`。 附加到一个`nil`slice 工作正常，因此不需要显式初始化。 

当一个组变满时，我们将其附加到结果中并用新的空切片替换它。 

自从`n <= 500`，不用担心整数溢出。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 每个人只被处理一次 |
 | 空间| O(n) | 哈希图和输出存储可能包含所有人|

 时间复杂度为`O(n)`因为我们遍历数组一次，并且每次哈希映射插入和查找平均需要恒定的时间。

 ## 边缘情况

 ### 每个人都需要一个规模为一的团体

 考虑：```
[1,1,1,1]
```每个人都必须被安排在一个独立的小组中。 有缺陷的实现可能会意外地将人们组合在一起，因为他们共享相同的所需大小。 

我们的实现自然地处理了这个问题。 每次将一个人添加到临时组中时`1`，该组立即完成并添加到结果中。 

### 具有相同所需大小的多个组

 考虑：```
[3,3,3,3,3,3]
```此输入需要**两个独立的组**大小`3`。 

一个常见的错误是忘记在完成后重置临时组，这会错误地创建过大的组。 

我们的实现通过重置来避免这个问题：```
groups[group_size] = []
```每完成一组后。 

### 大组消耗全部输入

 考虑：```
[5,5,5,5,5]
```所有人都属于一个群体。 

一些实现错误地过早地完成了组或错误地处理了累积。 

我们的算法会等到临时列表长度与所需的组大小完全匹配才最终确定，以确保正确构建整个组。 

### 混合组大小交错

 考虑：```
[2,3,2,3,3,2]
```需要相同团体规模的人不相邻。 

依赖连续元素的简单实现在这里会失败。 

哈希映射方法可以正常工作，因为分组仅取决于所需的大小，而不取决于顺序。 无论人员出现在输入数组中的哪个位置，都会将其累积到适当的存储桶中。
