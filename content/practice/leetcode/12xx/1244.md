 # LeetCode 1244 - 设计排行榜

 ## 问题理解

 这个问题要求我们设计一个高效支持三种操作的排行榜系统。 每个玩家都有独特的`playerId`以及相关的分数。 排行榜一开始是空的，可以在执行操作时动态添加玩家。 

这`addScore(playerId, score)`操作要么创建一个具有给定分数的新玩家，要么增加现有玩家的分数。 这`top(K)`运算返回最高的总和`K`当前分数出现在排行榜上。 这`reset(playerId)`该操作通过将玩家的分数重置为零来删除玩家的分数，从而有效地将其从活动排行榜中删除。 

输入由一系列方法调用和参数组成。 预期输出是每个产生值的操作返回的结果，特别是`top()`手术。 修改排行榜而不返回任何结果的方法`null`在示例输出中。 

约束对于选择实施策略很重要：

 - 最多有`1000`函数调用。 
-`playerId`和`K`至多是`10000`。 
- 个人分数增量最多很小`100`。 

总操作数量较少意味着我们不一定需要高度复杂的平衡树结构或具有延迟删除的堆。 在问题限制内，使用哈希图和排序的简单而干净的解决方案是完全可以接受的。 

尽早识别一些边缘情况很重要：

 - 随着时间的推移，玩家可能会收到多个分数更新。 
- 多个玩家可能有相同的分数。 
- 重置将玩家完全排除在考虑范围之外。 
-`top(K)`保证至少有`K`活跃玩家。 
- 排行榜一开始是空的，因此实现必须正确初始化内部数据结构。 

## 方法

 ### 蛮力方法

 最简单的实现将每个玩家的当前分数存储在哈希图中。 每当`top(K)`被调用时，我们将所有分数收集到一个列表中，按降序对它们进行排序，并对第一个分数求和`K`价值观。 

这种方法是正确的，因为排序保证最大的分数首先出现，所以取第一个`K`元素产生所需的确切答案。 

缺点是每`top(K)`查询对所有活跃玩家执行完整排序。 如果玩家数量变多，重复排序就会变得低效。 

尽管如此，因为约束将总操作限制为仅`1000`，这个解决方案对于 LeetCode 来说实际上已经足够快了。 

### 优化方法

 更好的方法维护两种数据结构：

 1. 哈希映射来自`playerId`到当前分数。 
2. 存储所有当前分数的排序多重集结构。 

当玩家的分数发生变化时，我们从排序结构中删除旧分数并插入更新的分数。 然后`top(K)`可以直接迭代最大分数，而无需每次都重新排序。 

在内置平衡树或排序容器的语言中，这种方法提高了重复查询的效率。 然而，在这里手动实现真正的平衡树是不必要的。 

对于 LeetCode，实际的最优解决方案通常被认为是哈希图加排序方法，因为约束条件故意很小。

 | 最佳 | O(N log N) 最坏情况总体操作 | O(N) | 分数的哈希图，仅在需要时排序 |

 ## 算法演练

 ### 使用哈希图和排序的最优策略

 1. 初始化一个名为的哈希图`player_scores`。 

key是玩家ID，value是玩家当前的总分。 这为更新和重置提供了恒定的时间访问。 
2. 对于`addScore(playerId, score)`:

 - 如果该玩家已经存在，则将新分数添加到现有总分中。 
- 否则，使用给定分数创建一个新条目。 

哈希映射在这里是理想的选择，因为玩家查找和更新是平均的`O(1)`运营。 
3.为了`top(K)`:

 - 从哈希图中提取所有得分值。 
- 按降序排列它们。 
- 对第一个求和`K`价值观。 

排序保证最高分数首先出现。 
4. 对于`reset(playerId)`:

 - 从哈希图中完全删除玩家。 

由于该问题将重置定义为从排行榜中删除玩家，因此删除比将分数设置为零更合适。 

### 为什么它有效

 核心不变量是哈希图始终存储每个活跃玩家的准确当前分数。 因为`top(K)`在选择最大的之前对当前分数的完整集合进行排序`K`，它总是计算正确的排行榜总和。 更新和重置会立即修改哈希图，确保所有未来的查询都在最新状态上运行。 

## Python 解决方案```python
class Leaderboard:

    def __init__(self):
        self.player_scores = {}

    def addScore(self, playerId: int, score: int) -> None:
        if playerId in self.player_scores:
            self.player_scores[playerId] += score
        else:
            self.player_scores[playerId] = score

    def top(self, K: int) -> int:
        sorted_scores = sorted(
            self.player_scores.values(),
            reverse=True
        )

        return sum(sorted_scores[:K])

    def reset(self, playerId: int) -> None:
        del self.player_scores[playerId]

# Your Leaderboard object will be instantiated and called as such:
# obj = Leaderboard()
# obj.addScore(playerId, score)
# param_2 = obj.top(K)
# obj.reset(playerId)
```该实现首先初始化一个名为的空字典`player_scores`。 这本字典是所有活跃玩家及其分数的核心事实来源。 

这`addScore`方法检查播放器是否已经存在。 如果是这样，则分数增加。 否则，将创建一个新的玩家条目。 

这`top`方法使用提取所有当前分数`values()`，按降序对它们进行排序，并对第一个求和`K`条目。 Python 的内置排序高效且简洁，使得实现简单明了。 

这`reset`方法完全删除玩家使用`del`。 这确保玩家不再为未来的排行榜计算做出贡献。 

## 解决方案```go
package main

import "sort"

type Leaderboard struct {
	playerScores map[int]int
}

func Constructor() Leaderboard {
	return Leaderboard{
		playerScores: make(map[int]int),
	}
}

func (this *Leaderboard) AddScore(playerId int, score int) {
	this.playerScores[playerId] += score
}

func (this *Leaderboard) Top(K int) int {
	scores := make([]int, 0, len(this.playerScores))

	for _, score := range this.playerScores {
		scores = append(scores, score)
	}

	sort.Sort(sort.Reverse(sort.IntSlice(scores)))

	total := 0

	for i := 0; i < K; i++ {
		total += scores[i]
	}

	return total
}

func (this *Leaderboard) Reset(playerId int) {
	delete(this.playerScores, playerId)
}

/**
 * Your Leaderboard object will be instantiated and called as such:
 * obj := Constructor()
 * obj.AddScore(playerId, score)
 * param_2 := obj.Top(K)
 * obj.Reset(playerId)
 */
```Go 的实现与 Python 解决方案非常相似。 从整数玩家 ID 到分数的映射提供了高效的更新和查找。 

Go 特有的一个重要细节是，映射访问会针对丢失的键自动返回零。 这允许`AddScore`使用：```go
this.playerScores[playerId] += score
```而不检查播放器是否已经存在。 

为了排序，Go 需要显式构造一个分数切片，然后应用`sort.Sort(sort.Reverse(sort.IntSlice(scores)))`以获得降序排列。 

这`delete`内置在重置操作期间干净地删除玩家。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(N log N) 为`top()`| 对所有活动分数进行排序主导运行时间 |
 | 空间| O(N) | 哈希图存储所有活跃玩家|

 这`addScore`和`reset`操作都以平均恒定时间运行，因为哈希映射操作非常高效。 昂贵的操作是`top(K)`，对所有当前玩家得分进行排序。 如果有`N`活跃玩家，排序需要`O(N log N)`时间。 

空间复杂度是线性的，因为我们为每个活跃玩家存储一个哈希映射条目。

 ## 边缘情况

 ### 同一玩家重复得分

 错误的一个常见来源是错误地覆盖玩家的分数而不是累积它。 问题明确指出`addScore`添加到现有分数。 该实现通过增加当前值而不是替换它来处理这个问题。 

### 重置玩家并再次添加他们

 重置后，如果稍后再次添加，玩家的行为应该像全新的玩家一样。 一些实现错误地留下了过时的数据。 该解决方案将玩家完全从哈希映射中删除，因此将来的添加自然从零开始。 

### 多个得分相同的玩家

 排行榜通常包含平局。 有缺陷的实现可能会在排序或存储期间意外地删除相同值的重复项。 由于该解决方案独立存储每个玩家的分数并对原始分数值进行排序，因此在`top(K)`计算。
