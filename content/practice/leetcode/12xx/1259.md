[LeetCode 第 1259 题](https://leetcode.com/problems/handshakes-that-dont-cross/)

 **难度：** 🔴难
 **主题：** 数学、动态规划

 ## 解决方案

 ## 问题理解

 在这个问题中，我们有偶数个人围成一圈。 每个人都必须参加一次握手，这意味着人们被分成两对。 挑战在于计算有多少种不同的方式可以形成这些配对，使得在圆圈内画直线时不会有两次握手交叉。 

例如，如果有 4 个人按顺时针方向标记为`1, 2, 3, 4`，正好有两个有效的非交叉配置：

 -`(1,2)`和`(3,4)`-`(1,4)`和`(2,3)`然而，配对`(1,3)`和`(2,4)`无效，因为线相交。 

输入是单个整数`numPeople`，它总是偶数。 输出是有效的非交叉握手安排的数量模`10^9 + 7`。 

约束条件很重要：

 -`2 <= numPeople <= 1000`-`numPeople`总是均匀的

 由于配置的数量增长得非常快，暴力枚举变得不可行。 模数要求还表明答案可能变得非常大。 

一个重要的观察结果是，该问题在结构上与计算有效括号组合或计算圆圈中非交叉和弦配对相同。 这直接导致了加泰罗尼亚数的重现。 

一些边缘情况很重要：

 - 最小的输入，`numPeople = 2`，只有一次握手安排。 
- 大量输入，例如`1000`需要一个高效的动态规划解决方案。 
- 没有记忆的简单递归解决方案将呈指数级爆炸。 
- 由于结果变得巨大，因此在计算过程中必须仔细应用模运算。 

## 方法

 ### 蛮力方法

 暴力解决方案将尝试生成所有可能的配对，然后检查是否有任何两次握手交叉。 

该过程如下所示：

 1. 选择一名未配对的人。 
2. 尝试将他们与其他所有有空的人配对。 
3. 递归地继续，直到每个人都配对为止。 
4. 对于每个完成的配对配置，测试是否有任何握手相交。 

这种方法是正确的，因为它探索了每一种可能的完美匹配并过滤掉无效的交叉匹配。 

然而，配对的数量增长得非常快。 之间的完美匹配数`n`人们是：$$(n-1)(n-3)(n-5)\dots 1$$为了`numPeople = 1000`，这是一个天文数字。 即使在检查交叉之前，生成所有配对也是完全不可行的。 

### 最优动态规划方法

 关键的见解是，选择一次握手会将循环分成两个完全独立的子问题。 

假设人`0`与人握手`k`。 

因为握手不能交叉：

 - 之间的所有人`0`和`k`必须在内部配对。 
- 该时间间隔之外的所有人员也必须在内部配对。 

这会产生两个较小的非交叉握手问题。 

如果：

 - 左侧包含`left`人
 - 右侧包含`right`人

 那么本次分割的配置总数为：$$dp[left] \times dp[right]$$总结每个有效的合作伙伴`0`给出递归式：$$dp[n] = \sum dp[left] \times dp[right]$$这正是加泰罗尼亚数的递推式。 

动态规划解决方案可以自下而上有效地计算所有偶数的答案，直到`numPeople`。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 指数| 指数| 生成所有配对并检查交叉 |
 | 最佳 | O(n²) | O(n) | 使用加泰罗尼亚递归的动态规划 |

 ## 算法演练

 1.创建动态规划数组`dp`尺寸的`numPeople + 1`。 

价值`dp[i]`代表有效的非交叉握手安排的数量`i`人们。 
2. 初始化基本情况。 

只有一种方法可以安排零人之间的握手：$$dp[0] = 1$$这个空配置很重要，因为它允许循环乘法。 
3. 迭代所有偶数人`2`到`numPeople`。 

奇数将被忽略，因为如果计数为奇数，则不可能将每个人配对。 
4. 对于每个`people`，尝试将第一个人与每个可能的有效伙伴配对。 

如果第一个人与人配对`partner`，那么：

 - 区间内的人构成一个子问题。 
- 区间外的人形成另一个子问题。 
5. 计算两个子问题的大小。 

如果第一人称与位置配对`partner`:

 - 左侧尺寸：$$left = partner - 1$$- 右侧尺寸：$$right = people - partner - 1$$6. 将左右子问题的路数相乘。 

由于这两个区域是独立的：$$dp[left] \times dp[right]$$将此贡献添加到`dp[people]`。 
7. 每次加法后应用模。 

这可以防止整数溢出并满足问题要求。 
8.填表后返回`dp[numPeople]`。 

### 为什么它有效

 每当一个握手被固定时，非交叉条件就会迫使剩余的握手进入两个独立的区域。 每个有效排列都是通过组合这两个较小区域的有效排列而唯一形成的。 因此，递归对每个有效配置精确计数一次，并且从不计数无效交叉排列。 

## Python 解决方案```python
class Solution:
    def numberOfWays(self, numPeople: int) -> int:
        MOD = 10**9 + 7

        dp = [0] * (numPeople + 1)
        dp[0] = 1

        for people in range(2, numPeople + 1, 2):
            for partner in range(1, people, 2):
                left = partner - 1
                right = people - partner - 1

                dp[people] += dp[left] * dp[right]
                dp[people] %= MOD

        return dp[numPeople]
```实施直接遵循加泰罗尼亚语重现。 

这`dp`数组存储每偶数人的有效配置数。 基本情况`dp[0] = 1`代表空配置。 

外循环处理增加的偶数值`people`。 对于每个值，内循环都会为第一个人选择一个伙伴。 

合作伙伴指数增加`2`因为左边必须包含偶数人才能完成配对。 

对于每个分割：

 -`left`计算所选握手中的人数
 -`right`计算其之外的人数

 此分割的有效排列数是两个独立子问题的乘积。 

每次更新后都会应用模算术，以保持数字易于管理。 

## 解决方案```go
func numberOfWays(numPeople int) int {
    const MOD int = 1e9 + 7

    dp := make([]int, numPeople+1)
    dp[0] = 1

    for people := 2; people <= numPeople; people += 2 {
        for partner := 1; partner < people; partner += 2 {
            left := partner - 1
            right := people - partner - 1

            dp[people] = (dp[people] + dp[left]*dp[right]) % MOD
        }
    }

    return dp[numPeople]
}
```Go 的实现与 Python 解决方案非常相似。 

使用切片而不是 Python 列表。 由于 Go 整数可能在某些平台上溢出，因此在每次更新期间都会应用小心的模运算。 

递归和迭代结构保持相同。

 ## 边缘情况

 一个重要的边缘情况是尽可能最小的输入，`numPeople = 2`。 握手的可能性只有一次，所以答案一定是`1`。 忘记初始化的实现`dp[0] = 1`这种情况经常会失败，因为递归依赖于空子问题的乘法贡献。 

另一个重要的情况是非常大的输入值，例如`numPeople = 1000`。 配置的数量变得巨大，远远超过正常的整数范围。 如果在每次更新期间不应用模运算，许多语言都会出现溢出问题。 实施安全适用`% MOD`每次添加后。 

一个微妙的边缘情况涉及确保仅考虑均匀大小的子问题。 如果伙伴选择不正确，算法可能会生成无法完全配对的奇怪大小的区域。 通过迭代合作伙伴的步骤`2`，两个产生的子问题始终包含偶数个人数，保证有效的递归结构。 

最后一个边缘情况涉及空子问题。 当第一个人与最近的邻居或最后一个人配对时，分割的一侧包含零人。 该算法自然地处理这个问题，因为`dp[0] = 1`，正确表示一种有效的空排列。
