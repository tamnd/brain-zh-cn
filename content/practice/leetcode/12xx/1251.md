[LeetCode 第 1251 题](https://leetcode.com/problems/average- sell-price/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 这个问题要求我们根据两个表计算每种产品的**平均售价**：`Prices`和`UnitsSold`。 

这`Prices`该表告诉我们在特定日期范围内产品的成本是多少。 每行包含一个`product_id`, 一个`start_date`， 一个`end_date`，以及`price`在那段时期。 一个产品可能有多个定价周期，但问题是保证同一产品的这些周期**不重叠**。 这一保证很重要，因为它意味着任何购买日期最多只能匹配产品的一个价格区间。 

这`UnitsSold`表记录销售交易。 每一行都告诉我们具体的数量`units`的产品在特定的`purchase_date`。 同一产品和日期允许有多行。 

任务是计算每种产品的**平均售价**。 公式为：$$\text{average price} = \frac{\text{total revenue}}{\text{total units sold}}$$为了计算总收入，我们必须通过匹配每笔销售来确定哪个价格适用`purchase_date`对照正确的定价区间`Prices`。 一旦我们知道正确的价格，我们就乘以：$$\text{units} \times \text{price}$$并对产品所有销售的这些值进行求和。 

该问题还引入了一个重要的边缘情况：**没有销售的产品**。 如果产品存在于`Prices`但没有相应的销售单位，其平均售价应为`0`。 

最后，答案必须四舍五入到小数点后两位，并且结果可以按任何顺序返回。 

约束相对较小，因为这是一个简单的数据库问题，但效率仍然很重要。 由于每一笔销售都属于一个价格范围，因此我们可以通过连接操作有效地将表组合起来，而不是重复搜索所有价格范围。 

重要的边缘情况包括：

 - 产品存在于`Prices`但没有匹配的行`UnitsSold`。 结果应该是`0.00`。 
- 一种产品有多个定价期，并且销售发生在不同的范围内。 我们必须将每个购买日期与其有效价格区间正确匹配。 
- 同一天发生多次销售或存在重复行`UnitsSold`。 这些都应该独立地贡献于总数。 
- 边界日期很重要，因为`purchase_date`可以等于`start_date`或者`end_date`。 比较必须具有包容性。 

## 方法

 ### 蛮力方法

 一个简单的解决方案将迭代每个产品销售，并针对每个销售扫描该产品的每个定价区间，直到找到正确的日期范围。 

对于中的每一行`UnitsSold`，我们会：

 1. 查找该产品的所有价格记录。 
2. 检查每个区间以确定是否`purchase_date`落在之间`start_date`和`end_date`。 
3. 乘法`units × price`。 
4. 累计每种产品的总收入和总单位数。 

处理完所有销售后，我们将总收入除以总单位数，并四舍五入到小数点后两位。 

这种方法是正确的，因为每次销售最终都会找到匹配的定价区间，并且问题保证区间不会重叠。 然而，它变得效率低下，因为每次销售可能需要扫描许多定价周期。 

### 最佳方法

 关键的见解是，这从根本上来说是一个**连接问题**。 

每笔销售已包含`product_id`和`purchase_date`，而每个定价记录定义产品的有效日期间隔。 由于定价周期不重叠，我们可以直接连接两个表：

 - 匹配`product_id`-`purchase_date BETWEEN start_date AND end_date`加入后，每次销售都会自动收到正确的价格。 

加入后：

 - 使用计算总收入`units * price`- 使用计算总销售单位`SUM(units)`- 按单位划分收入
 - 使用`ROUND(..., 2)`用于格式化

 为了确保没有销售的产品仍然出现，我们使用 **LEFT JOIN**`Prices`到`UnitsSold`。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(P × U) | O(P)| 对于每次销售，扫描价格区间 |
 | 最佳 | O(P + U)（逻辑 SQL 执行）| O(P)| 连接匹配日期并高效聚合 |

 这里：

-`P`= 中的行数`Prices`-`U`= 中的行数`UnitsSold`在实践中，数据库索引和查询优化使连接解决方​​案变得高效。 

## 算法演练

 1. 从`Prices`表，因为每个产品都必须出现在输出中，即使它没有销售额。 这可确保未购买的产品不会被意外排除。 
2. 执行`LEFT JOIN`和`UnitsSold`使用两个条件：

 -`product_id`必须匹配。 
-`purchase_date`必须落在价格区间内：`purchase_date BETWEEN start_date AND end_date`。 

这保证了每次销售都与正确的价格配对。 
3. 行分组依据`product_id`。 由于产品可能有多个定价区间和多个销售，分组让我们可以将所有匹配的记录聚合在一起。 
4. 使用以下方法计算总收入：```
SUM(price * units)
```这给出了该产品赚取的总金额。 
5. 使用以下方法计算销售总量：```
SUM(units)
```6、处理没有销售的产品。 自从`LEFT JOIN`可能会产生`NULL`值，除法将失败或返回`NULL`。 我们使用：```
IFNULL(...)
```或返回的等效逻辑`0`。 
7. 将总收入除以总单位数，并将结果四舍五入到小数点后两位。 

### 为什么它有效

 该算法之所以有效，是因为每一笔销售都恰好属于其产品的一个定价区间。 该问题保证不存在重叠的日期范围，因此连接会为每次销售准确地生成一个有效价格。 求和`units × price`给出总收入，求和`units`给出销售总量，将它们相除得出加权平均销售价格。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    p.product_id,
    ROUND(
        IFNULL(SUM(p.price * u.units) / SUM(u.units), 0),
        2
    ) AS average_price
FROM Prices p
LEFT JOIN UnitsSold u
    ON p.product_id = u.product_id
    AND u.purchase_date BETWEEN p.start_date AND p.end_date
GROUP BY p.product_id;
```此实施开始于`Prices`表，以便每个产品都出现在最终结果中。 这`LEFT JOIN`使用两者将销售与其有效定价区间连接​​起来`product_id`和日期范围条件。 

聚合步骤计算每种产品的两个数量：

 -`SUM(p.price * u.units)`计算总收入。 
-`SUM(u.units)`计算总销售单位。 

由于没有销售的产品会产生`NULL`聚合期间的值，`IFNULL(..., 0)`将结果转换为零。 最后，`ROUND(..., 2)`确保答案符合所需的精度。

 ## 边缘情况

 ### 没有销售的产品

 一个常见的错误是无意中排除了从未出现过的产品`UnitsSold`。 如果我们使用一个`INNER JOIN`，这些产品完全从结果中消失。 使用`LEFT JOIN`确保每个产品都保留在输出中，并且`IFNULL(..., 0)`将缺失的平均值正确转换为`0.00`。 

### 边界日期销售

 购买可能正好发生在`start_date`或者`end_date`。 使用严格的不等式（`>`或者`<`）会错误地错过这些销售。 实现使用`BETWEEN`，它具有包容性并正确处理边界日期。 

### 同一产品的多个价格区间

 一种产品在不同时期可能有不同的价格。 如果忽略日期，幼稚的实现可能会应用错误的价格。 连接条件明确检查购买日期是否在有效范围内，确保每次销售都获得正确的价格。 

### 中的重复行`UnitsSold`该问题明确指出可能存在重复行。 有缺陷的解决方案可能会意外地删除它们的重复项。 由于聚合使用`SUM(units)`和`SUM(price * units)`直接在连接的行上，重复项自然会贡献多次，这是正确的行为。
