 # LeetCode 1205 - 每月交易 II

 ## 问题理解

 此问题要求我们使用两个数据库表中的信息生成每个国家的每月财务摘要：`Transactions`和`Chargebacks`。 

这`Transactions`表存储传入的事务。 每笔交易都有一个唯一的ID、一个国家、一个州（`approved`或者`declined`)、金额和交易日期。 

这`Chargebacks`表存储退款事件。 每个退款都引用来自`Transactions`表通过`trans_id`外键。 退款还有其自己的日期，表示退款发生的时间。 

目标是为每个人生产`(month, country)`组合，以下聚合值：

 - 批准的交易数量
 - 批准的交易总额
 - 退款次数
 - 退款总额

 月份的格式必须为`YYYY-MM`。 

一个重要的细节是退款是按退款日期而不是原始交易日期分组的。 但是，国家和金额信息仍必须来自原始交易`Transactions`桌子。 

关于忽略全零行的注释意味着我们应该只返回包含至少一项已批准交易或至少一项退款的月份-国家组合。 

该问题保证每次退款都引用有效的交易。 这意味着我们可以安全地加入`Chargebacks`和`Transactions`使用交易 ID。 

尽管没有显示显式约束，LeetCode 上的数据库问题通常是为高效的基于集合的 SQL 解决方案而设计的。 重复扫描表的简单程序方法无法很好地扩展。 相反，聚合和分组操作应该被推入 SQL 本身。 

一些边缘情况很重要：

 - 一个月可能包含已批准的交易，但没有退款。 
- 一个月可能包含退款但没有批准的交易。 
- 与国家的交易`declined`不计入批准的总额，但仍可能出现在退款中。 
- 不同月份可能存在多次退款。 
- 某些月份可能包含多个国家/地区的数据。 

该解决方案必须正确地将这些案例组合成一个聚合结果。 

## 方法

 ### 蛮力方法

 蛮力策略会迭代所有可能的方法`(month, country)`配对并重复扫描表以计算所需的聚合。 

对于批准的交易，我们将搜索`Transactions`用于将行与状态进行匹配的表`approved`。 对于退款，我们会将每个退款加入其原始交易并手动聚合匹配值。 

这种方法在逻辑上是正确的，因为它显式地计算了每个所需的指标。 然而，它的效率很低，因为它会重复扫描大表并执行冗余计算。 

从程序上来说，如果月份数、国家/地区、交易和退款数量增加，这可能会变得极其昂贵。 

### 最佳方法

 关键的见解是 SQL 数据库针对分组和聚合操作进行了优化。 

我们可以：

 1. 汇总已批准的交易`(month, country)`2. 按以下方式汇总退款`(month, country)`3. 合并两个结果集
 4. 执行最终分组以合并重叠行

 实现这一目标的最干净的方法是使用`UNION ALL`。 

我们创建一个查询来生成已批准的交易统计信息，并创建另一个查询来生成退款统计信息。 每个查询都会用零填充它不使用的字段。 

将数据集与`UNION ALL`，我们再次分组`(month, country)`并对列求和。 

这种方法非常高效，因为每个表仅扫描一次，并且聚合工作被委托给数据库引擎。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(T × C) 或更差 | O(1) | O(1) | 重复扫描表 |
 | 最佳 | O(T + C) | O(T + C) | 高效使用 SQL 聚合和分组 |

 这里：

-`T`= 交易行数
 -`C`= 退款行数

 ## 算法演练

 1. 首先，处理经批准的交易`Transactions`桌子。 

对于每笔带有状态的交易`approved`，提取：

 - 使用日期格式的月份
 - 国家
 - 已批准交易的计数
 - 批准的交易金额

 由于此查询仅处理已批准的交易，因此将退款字段设置为零。 
2. 接下来，处理退款。 

加入`Chargebacks`表与`Transactions`表使用：```
Chargebacks.trans_id = Transactions.id
```这种加入是必要的，因为`Chargebacks`表不包含国家或金额信息。 
3. 对于每个退款行：

 - 从中提取退款月份`Chargebacks.trans_date`- 使用国家/地区`Transactions`- 计算退款
 - 原始交易金额的总和

 由于此查询仅处理退款，因此将批准的交易字段设置为零。 
4. 使用组合两个结果集`UNION ALL`。`UNION ALL`优先于`UNION`因为我们不希望重复消除。 我们希望保留所有聚合行。 
5. 执行最终分组`(month, country)`。 

对所有四个指标列求和：

 -`approved_count`-`approved_amount`-`chargeback_count`-`chargeback_amount`6. 返回最终聚合表。 

### 为什么它有效

 该算法之所以有效，是因为每笔已批准的交易都只为已批准的聚合贡献一次，并且每次退款只为退款聚合贡献一次。 

通过将两个数据集转换为相同的模式并将它们与`UNION ALL`，最后的分组步骤自然会合并属于同一行的行`(month, country)`一对。 

聚合在数学上是正确的，因为求和在类别之间是关联且独立的。 

## SQL 解决方案```sql
# MySQL solution

SELECT
    month,
    country,
    SUM(approved_count) AS approved_count,
    SUM(approved_amount) AS approved_amount,
    SUM(chargeback_count) AS chargeback_count,
    SUM(chargeback_amount) AS chargeback_amount
FROM
(
    SELECT
        DATE_FORMAT(trans_date, '%Y-%m') AS month,
        country,
        COUNT(*) AS approved_count,
        SUM(amount) AS approved_amount,
        0 AS chargeback_count,
        0 AS chargeback_amount
    FROM Transactions
    WHERE state = 'approved'
    GROUP BY DATE_FORMAT(trans_date, '%Y-%m'), country

    UNION ALL

    SELECT
        DATE_FORMAT(c.trans_date, '%Y-%m') AS month,
        t.country,
        0 AS approved_count,
        0 AS approved_amount,
        COUNT(*) AS chargeback_count,
        SUM(t.amount) AS chargeback_amount
    FROM Chargebacks c
    JOIN Transactions t
        ON c.trans_id = t.id
    GROUP BY DATE_FORMAT(c.trans_date, '%Y-%m'), t.country
) AS combined
GROUP BY month, country;
```该解决方案分为两个主要的聚合查询。 

第一个查询仅处理已批准的交易。 它使用以下方式过滤行：```sql
WHERE state = 'approved'
```然后，它按月份和国家/地区进行分组，并计算批准的数量和金额。 

第二个查询处理退款。 自从`Chargebacks`表不包含国家或金额信息，我们将其加入`Transactions`。 

退款分组基于退款日期，因为问题陈述要求按退款发生月份提供退款统计信息。 

两个结果集使用组合`UNION ALL`。 两个查询返回相同的列结构，这使得它们可以无缝合并。 

最后，外部查询再次分组`(month, country)`并对指标列求和以产生最终结果。

 ## 边缘情况

 ### 拒绝交易的退款

 一个常见的错误是假设退款仅适用于已批准的交易。 该问题明确指出退款也可能涉及拒绝的交易。 

该实现可以正确处理此问题，因为退款聚合直接与所有事务连接，而不对状态进行过滤。 

### 仅出现退款的月份

 有些月份可能会出现退款，但交易不会获得批准。 批准的交易和退款之间的天真的内部联接会意外地排除这些行。 

该解决方案通过先独立聚合已批准的交易和退款，然后再将其与`UNION ALL`。 

### 拒绝交易且不退款

 被拒绝的交易不应计入批准的统计数据，如果没有退款，则根本不应出现在结果中。 

实现自然会处理这个问题，因为：

 - 批准的查询将其过滤掉
 - 退款查询仅包含退款引用的交易

 因此，不相关的行永远不会进入组合数据集。
