 # LeetCode 1264 - 页面推荐

 ## 问题理解

 该问题模拟了一个具有两个数据库表的小型社交网络。 

这`Friendship`表存储用户之间的好友关系。 每行`(user1_id, user2_id)`意味着这两个用户是朋友。 友谊实际上是双向的，尽管每一对在表中只出现一次。 

这`Likes`表存储每个用户喜欢哪些页面。 每行`(user_id, page_id)`意味着用户喜欢该页面。 

任务是推荐页面`user_id = 1`。 如果出现以下情况，则应推荐页面：

 1. 用户至少一名好友`1`喜欢该页面。 
2. 用户`1`尚未喜欢该页面。 

结果必须包含唯一的页面 ID。 如果多个朋友喜欢同一页面，该页面仍应仅在输出中出现一次。 

输出表包含一列：

 | 专栏 | 意义|
 | --- | --- |
 | 推荐页面 | 用户 1 的朋友喜欢的页面，但用户 1 尚未喜欢的页面 |

 重要的细节是识别用户的所有朋友`1`。 由于友谊存储为`(user1_id, user2_id)`, 用户`1`可以出现在任一列中。 例如：

-`(1, 2)`表示用户`2`是用户的朋友`1`-`(6, 1)`表示用户`6`也是用户的好友`1`正确的解决方案必须处理这两种情况。 

另一个重要的要求是删除重复项。 如果两个不同的朋友喜欢同一页面，则该页面在最终答案中应该只出现一次。 

该问题保证：

 - 友谊对是独一无二的。 
- 用户页面的点赞是独一无二的。 
- 这些表是格式良好的关系数据。 

主要的边缘情况是：

 - 出现在友谊关系两边的朋友。 
- 多个朋友喜欢同一页面。 
- 用户`1`已经喜欢了朋友也喜欢的页面。 
- 用户`1`没有朋友。 
- 朋友不喜欢任何页面。 
- 所有朋友喜欢的页面都已被用户喜欢`1`。 

## 方法

 ### 蛮力方法

 强力解决方案将检查每个用户喜欢的每个页面，并反复检查是否：

 1. 该用户是该用户的好友`1`2. 用户`1`已经喜欢该页面
 3. 该页面已添加到结果中

 一种可能的暴力策略是：

 1. 反复扫描好友关系表，判断每个用户是否是该用户的好友`1`。 
2. 对于每一行`Likes`，检查用户是否为好友。 
3. 对于每个候选页面，扫描`Likes`再次表判断是否用户`1`已经喜欢了。 
4. 最后使用重复消除。 

这是有效的，因为每个可能的候选页面都会被检查。 然而，由于重复地重新扫描相同的数据，因此效率低下。 

### 最佳方法

 关键的见解是，这从根本上来说是一个集合过滤问题。 

我们只需要三件事：

 1. 用户设置`1`的朋友
 2. 用户已经喜欢的页面集合`1`3. 那些朋友喜欢但用户不喜欢的页面`1`在 SQL 中，这成为以下内容的干净组合：

 - 派生表，提取用户的所有好友`1`- 与`Likes`表
 - 过滤器删除用户已经喜欢的页面`1`-`DISTINCT`消除重复项

 最佳解决方案避免重复重新扫描，并让数据库引擎有效地执行连接和过滤。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(F × L) | O(L) | 重复扫描友谊和喜欢表|
 | 最佳 | O(F + L) | O(F + L) | 使用集合式过滤并高效连接 |

 这里：

-`F`= 友谊行数
 -`L`= 点赞行数

 ## 算法演练

 ### 最优 SQL 算法

 1、首先识别用户的所有好友`1`。 

由于友谊是双向的，用户`1`可能出现在任一列中。 我们创建一个派生表，将友谊标准化为单个`friend_id`柱子。 

如果`user1_id = 1`，那么这个朋友就是`user2_id`。 

如果`user2_id = 1`，那么这个朋友就是`user1_id`。 
2. 接下来，检索这些朋友喜欢的所有页面。 

我们通过以下方式加入好友列表`Likes`表使用：```sql
friend_id = Likes.user_id
```这为我们提供了至少一个朋友喜欢的每个页面。 
3.然后，删除用户已经喜欢的页面`1`。 

我们使用子查询或反连接来排除已存在于以下位置的页面：```sql
SELECT page_id
FROM Likes
WHERE user_id = 1
```4. 最后，删除重复项。 

多个朋友可能喜欢同一个页面，所以我们使用`DISTINCT`确保每个推荐页面仅出现一次。 

### 为什么它有效

 该算法之所以有效，是因为它精确地模拟了推荐定义。 

好友提取步骤保证用户的每一位好友`1`只包含一次。 加入与`Likes`保证这些朋友喜欢的每个页面都会被考虑。 排除过滤器保证页面已经被用户喜欢`1`被删除。 最后，`DISTINCT`保证结果的唯一性。 

这些步骤共同产生了一组有效的建议。 

## Python 解决方案

 尽管这是一个数据库问题并且通常在 SQL 中解决，但以下 Python 实现使用内存数据结构模拟相同的逻辑。```python
from typing import List, Tuple, Set

class Solution:
    def pageRecommendations(
        self,
        friendships: List[Tuple[int, int]],
        likes: List[Tuple[int, int]]
    ) -> List[int]:

        user_id = 1

        friends: Set[int] = set()

        for user1, user2 in friendships:
            if user1 == user_id:
                friends.add(user2)
            elif user2 == user_id:
                friends.add(user1)

        liked_by_user: Set[int] = set()

        for user, page in likes:
            if user == user_id:
                liked_by_user.add(page)

        recommendations: Set[int] = set()

        for user, page in likes:
            if user in friends and page not in liked_by_user:
                recommendations.add(page)

        return list(recommendations)
```实现直接遵循算法。 

第一个循环构建朋友集。 由于友谊是双向的，因此代码会检查每个友谊行的两列。 

第二个循环构建用户已经喜欢的页面集`1`。 哈希集是理想的，因为成员资格检查平均时间是恒定的。 

第三个循环再次扫描所有喜欢的内容。 如果喜欢的用户是朋友并且该页面尚未被用户喜欢`1`，该页面被添加到推荐集中。 

当多个朋友喜欢同一页面时，使用一组推荐会自动删除重复项。 

## 解决方案```go
package main

type Solution struct{}

func (s Solution) pageRecommendations(
	friendships [][2]int,
	likes [][2]int,
) []int {

	userID := 1

	friends := make(map[int]bool)

	for _, friendship := range friendships {
		user1 := friendship[0]
		user2 := friendship[1]

		if user1 == userID {
			friends[user2] = true
		} else if user2 == userID {
			friends[user1] = true
		}
	}

	likedByUser := make(map[int]bool)

	for _, like := range likes {
		user := like[0]
		page := like[1]

		if user == userID {
			likedByUser[page] = true
		}
	}

	recommendations := make(map[int]bool)

	for _, like := range likes {
		user := like[0]
		page := like[1]

		if friends[user] && !likedByUser[page] {
			recommendations[page] = true
		}
	}

	result := []int{}

	for page := range recommendations {
		result = append(result, page)
	}

	return result
}
```Go 版本密切反映了 Python 逻辑。 

Go 没有内置的集合类型，因此映射为`bool`值用于模拟集合。 这是成员资格测试和重复消除的常见 Go 实践。 

切片用于输入和输出集合。 由于该问题允许以任意顺序返回结果，因此不需要排序。 

不存在整数溢出问题，因为该算法仅存储和比较 ID。

 ## 边缘情况

 ### 以相反方向存储的友谊

 一个微妙的问题是友谊行不能保证存储用户`1`在第一列中。 一个简单的实现，只检查`user1_id = 1`会错过像这样的行`(6,1)`。 

该实现通过检查两列来处理此问题：```
if user1 == 1:
    friend = user2
elif user2 == 1:
    friend = user1
```这保证了无论订购如何，所有朋友都会被发现。 

### Multiple Friends Liking the Same Page

Different friends may like the same page. 如果没有重复处理，结果可能包含重复的建议。 

该实现将建议存储在一个集合中，该集合会自动删除重复项：```
recommendations.add(page)
```这保证了最终输出的唯一性。 

### 好友喜欢的页面已被用户 1 喜欢

 如果用户`1`已经喜欢了，甚至很多朋友也喜欢。 

如果推荐生成发生在排除过滤之前，这很容易导致错误。 

该实现通过维护一个来防止这种情况发生`liked_by_user`在添加推荐之前设置并检查成员资格：```
if page not in liked_by_user:
```这保证了已经喜欢的页面被排除在结果之外。
