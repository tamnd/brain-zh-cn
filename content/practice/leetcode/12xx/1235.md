[LeetCode 第 1235 题](https://leetcode.com/problems/maximum-profit-in-job-scheduling/)

 **难度：** 🔴难
 **主题：** 数组、二分查找、动态规划、排序

 ## 解决方案

 ## 问题理解

 该问题给了我们三个相等长度的数组：

 -`startTime[i]`代表当`i-th`工作开始
 -`endTime[i]`代表当`i-th`工作完成
 -`profit[i]`代表我们完成那项工作后赚到的钱

 我们的目标是选择时间上不重叠的工作子集，同时最大化总利润。 

如果第二个作业在第一个作业结束时或之后开始，则两个作业被认为是兼容的。 这个细节非常重要，因为该问题明确允许：

 - 一项工作在某个时间结束`X`- 另一项工作恰好在该时间开始`X`例如：

 - 工作A：`[1, 3]`- 工作B：`[3, 6]`这些工作是兼容的并且都可以选择。 

输出是一个整数，表示可实现的最大利润。 

限制条件很大：

 - 最多`5 * 10^4`职位
 - 时间值高达`10^9`这些限制立即排除了许多简单的递归解决方案。 对所有子集进行指数搜索将极其缓慢。 甚至一个`O(n^2)`动态规划解决方案存在风险`50,000`工作机会。 

该问题结合了几个经典思想：

 - 排序间隔
 - 二分查找
 - 动态规划

 这是经典加权区间调度问题的变体。 

一些边缘情况很重要：

 - 多个作业可以同时开始
 - 多个作业可能会同时结束
 - 一项工作可能会在另一项工作结束时恰好开始
 - 最佳答案可能会跳过许多小工作而选择一项大工作
 - 最佳答案可能需要结合许多兼容的小型作业
 - 作业最初并未排序

 输入保证：

 - 每项工作都有正的持续时间，因为`startTime[i] < endTime[i]`- 每笔利润都是正值
 - 所有数组都具有相同的长度

 这些保证简化了实施，因为我们从不处理无效间隔或负利润。 

## 方法

 ### 蛮力方法

 强力解决方案将尝试所有可能的作业子集。 

对于每个子集：

 1. 检查所选作业是否重叠
 2. 如果有效，计算总利润
 3. 跟踪找到的最大利润

 这保证了正确性，因为每个可能的组合都会被检查。 

然而，这种方法效率极低。 和`n`职位，有`2^n`可能的子集。 即使对于相对较小的值`n`，这在计算上变得不可能。 

另一种稍微改进的蛮力方法使用递归：

 - 在每项工作中，选择：

 - 接受这份工作
 - 跳过工作
 - 如果接受该工作，则递归搜索下一个兼容的工作

 尽管这避免了显式生成无效子集，但相同的子问题会被重复重新计算，从而导致指数复杂度。 

### 关键见解

 关键的观察是，一旦作业按开始时间或结束时间排序，问题就会形成最佳子结构。 

假设我们目前正在考虑工作`i`。 

我们只有两个有意义的选择：

 1. 跳过工作`i`2. 接受工作`i`，然后继续下一个不重叠的作业

 如果我们能够快速找到下一个兼容的工作，那么剩下的问题在结构上就与原来的问题相同。 

这自然会导致动态规划。 

剩下的挑战是有效地找到下一个兼容的工作。 由于作业是排序的，我们可以使用二分查找来查找开始时间大于或等于当前作业结束时间的第一个作业。 

这将解决方案转换为：

 - 排序
 - 二分查找
 - 记忆动态规划

 最终复杂度变为`O(n log n)`，这足够有效`50,000`工作机会。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(2^n) | O(2^n) | O(n) | 递归尝试作业的每个子集 |
 | 最佳| O(n log n) | O(n log n) | O(n) | 排序+二分查找+动态规划 |

 ## 算法演练

 1. 将所有工作信息合并到一个结构中。 

每个工作包含：

 - 开始时间
 - 结束时间
 - 利润

 这使得分类和处理变得更加容易。 
2. 按开始时间对作业进行排序。 

排序是必要的，因为二分查找仅适用于有序数据。 作业排序后，所有未来兼容的作业都会出现在当前作业之后。 
3. 将所有开始时间提取到一个单独的数组中。 

该数组允许对下一个兼容作业进行高效的二进制搜索。 
4.定义动态规划函数`dfs(index)`。 

该函数返回从工作开始可获得的最大利润`index`。 
5. 在每项工作中，计算两个选择。 

第一选择：

 - 跳过当前作业
 - 直接移动到`index + 1`第二选择：

 - 接受目前的工作
 - 二分查找下一个兼容的作业
 - 添加当前利润加上最佳未来利润
 6. 使用二分查找查找下一个兼容的作业。 

我们搜索开始时间大于或等于当前作业结束时间的第一个作业。 

这是有效的，因为作业是按开始时间排序的。 
7. 使用记忆存储计算结果。 

如果没有记忆，递归将多次重新计算相同的状态。 缓存确保每个状态都被解决一次。 
8. 返回最佳选择。 

每个州的答案是：`max(skip_current, take_current)`9.从索引开始递归`0`。 

这会计算所有工作的最佳可能利润。 

### 为什么它有效

 对于每项工作，算法都会通过两个详尽的选择来考虑所有有效的可能性：

 - 要么包括当前的工作
 - 或排除它

 如果包含当前作业，二分查找可保证我们直接跳转到下一个兼容作业，确保不会发生重叠。 

动态规划保证了最优性，因为每个子问题都存储从给定索引开始的最大可实现利润。 由于未来的每个决策仅取决于剩余的工作，因此该问题具有最优子结构。 

记忆化确保每个子问题只解决一次。 

## Python 解决方案```python
from typing import List
from bisect import bisect_left
from functools import lru_cache

class Solution:
    def jobScheduling(
        self,
        startTime: List[int],
        endTime: List[int],
        profit: List[int]
    ) -> int:

        jobs = sorted(zip(startTime, endTime, profit))

        starts = [job[0] for job in jobs]

        @lru_cache(None)
        def dfs(index: int) -> int:
            if index >= len(jobs):
                return 0

            # Option 1: skip current job
            skip_profit = dfs(index + 1)

            current_start, current_end, current_profit = jobs[index]

            # Find next compatible job
            next_index = bisect_left(starts, current_end)

            # Option 2: take current job
            take_profit = current_profit + dfs(next_index)

            return max(skip_profit, take_profit)

        return dfs(0)
```该实现首先将三个输入数组组合成一个元组列表。 每个元组代表一项作业，其中包含：

 - 开始时间
 - 结束时间
 - 利润

 作业按开始时间排序，因为二分搜索需要有序数据。 

这`starts`数组仅存储开始时间。 这很重要，因为 Python 的`bisect_left`直接对排序数组进行操作。 

递归`dfs(index)`函数从特定的工作指数开始计算最佳可能的利润。 

当索引超出最终工作时，就会出现基本情况。 在这种情况下，无法赚取更多利润，因此函数返回`0`。 

在递归内部，算法评估两种可能性：

 - 跳过当前作业
 - 接受目前的工作

 当获取当前作业时，二分搜索会识别第一个兼容的未来作业。 然后将当前利润添加到递归返回的最优未来利润中。 

这`lru_cache`装饰器会记住结果，因此每个状态都会计算一次。 

最后，`dfs(0)`从第一个作业开始返回最佳答案。 

## 解决方案```go
package main

import (
	"sort"
)

func jobScheduling(startTime []int, endTime []int, profit []int) int {
	type Job struct {
		start  int
		end    int
		profit int
	}

	n := len(startTime)

	jobs := make([]Job, n)

	for i := 0; i < n; i++ {
		jobs[i] = Job{
			start:  startTime[i],
			end:    endTime[i],
			profit: profit[i],
		}
	}

	sort.Slice(jobs, func(i, j int) bool {
		return jobs[i].start < jobs[j].start
	})

	starts := make([]int, n)

	for i := 0; i < n; i++ {
		starts[i] = jobs[i].start
	}

	dp := make([]int, n)

	var dfs func(int) int

	dfs = func(index int) int {
		if index >= n {
			return 0
		}

		if dp[index] != 0 {
			return dp[index]
		}

		// Option 1: skip current job
		skipProfit := dfs(index + 1)

		currentJob := jobs[index]

		// Find next compatible job
		nextIndex := sort.Search(
			n,
			func(i int) bool {
				return starts[i] >= currentJob.end
			},
		)

		// Option 2: take current job
		takeProfit := currentJob.profit + dfs(nextIndex)

		if skipProfit > takeProfit {
			dp[index] = skipProfit
		} else {
			dp[index] = takeProfit
		}

		return dp[index]
	}

	return dfs(0)
}
```Go 实现遵循与 Python 版本相同的算法结构。 

定制`Job`struct 干净地存储作业信息。 

Go 不像 Python 那样提供内置的记忆化装饰器`lru_cache`，所以我们使用`dp`手动切片。 由于利润始终为正，因此值为`0`安全地指示未计算的状态。 

二分查找是使用以下方法实现的`sort.Search`，它可以有效地找到第一个兼容的作业索引。 

使用 Go 切片而不是数组，因为它们的大小是动态的并且更方便解决算法问题。 

整数溢出在这里不是一个问题，因为最大总利润完全适合 Go 的范围`int`现代系统的范围。

from typing import List

class Solution:
    def jobScheduling(self, startTime: List[int], endTime: List[int], profit: List[int]) -> int:
        from bisect import bisect_left
        from functools import lru_cache

        jobs = sorted(zip(startTime, endTime, profit))
        starts = [job[0] for job in jobs]

        @lru_cache(None)
        def dfs(i):
            if i >= len(jobs):
                return 0

            skip = dfs(i + 1)

            next_i = bisect_left(starts, jobs[i][1])

            take = jobs[i][2] + dfs(next_i)

            return max(skip, take)

        return dfs(0)

 ## 边缘情况

 当作业恰好接触端点时，就会出现一种重要的边缘情况。 许多间隔调度实现错误地将它们视为重叠。 在这个问题中，作业在时间结束`X`与另一个开始时间兼容`X`。 该实现通过使用正确处理这个问题`bisect_left(starts, current_end)`，它搜索第一个大于或等于当前结束时间的开始时间。 

另一个重要的边缘情况是所有工作重叠。 在这种情况下，算法必须准确选择一项工作，特别是利润最大的一项。 递归动态编程方法自然可以处理这个问题，因为每个状态都会比较接受当前作业与跳过它。 

第三个重要的边缘情况是未排序的输入。 该问题不保证作业的任何排序。 假设排序数据的简单解决方案将无法通过二进制搜索和兼容性检查。 该实现在处理之前显式地对所有作业进行排序，确保无论输入顺序如何都正确。 

第四个微妙的边缘情况涉及多个作业共享相同的开始时间。 二分查找和动态编程仍然可以正常工作，因为排序后作业仍然保持正确的顺序。 递归探索所有可能性，并且记忆可以防止冗余计算。 

最后，非常大的时间值高达`10^9`可能会导致尝试时间轴模拟或按时间索引的密集数组的算法出现问题。 该解决方案完全避免了该问题，因为它仅在排序作业索引和二分搜索上运行，而不是在实际时间范围上运行。
