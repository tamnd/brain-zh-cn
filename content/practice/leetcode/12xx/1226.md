[LeetCode 第 1226 题](https://leetcode.com/problems/the-dining-philosophers/)

 **难度：** 🟡 中等
 **主题：** 并发

 ## 解决方案

 ## 问题理解

 这个问题要求我们为经典的**哲学家就餐**问题实现并发同步机制。 我们有五个哲学家围坐在一张圆桌旁，每对相邻的哲学家之间都放着一把叉子。 为了吃饭，哲学家必须同时拥有左右叉子。 由于叉子是共享资源，两个相邻的哲学家不能同时使用同一个叉子。 

挑战不仅仅是让哲学家吃饭，而是设计一个正确的同步规则，避免常见的并发失败，例如**死锁**和**饥饿**。 

当每个哲学家拿起一把叉子并永远等待第二把叉子时，就会出现僵局。 例如，如果所有哲学家同时拿起他们左边的叉子，则没有哲学家可以获得他们右边的叉子，从而导致系统永久冻结。 

当一位哲学家因邻近的哲学家反复首先获得叉子而被无限期地禁止进食时，就会发生饥饿。 

我们必须实现的方法是：```
wantsToEat(
    philosopher,
    pickLeftFork,
    pickRightFork,
    eat,
    putLeftFork,
    putRightFork
)
```这`philosopher`参数标识哪个哲学家想吃东西，编号从`0`到`4`按顺时针顺序。 

回调函数代表操作：

 -`pickLeftFork()`拿起哲学家左边的叉子。 
-`pickRightFork()`拿起哲学家的右手叉子。 
-`eat()`允许哲学家吃饭。 
-`putLeftFork()`释放左叉。 
-`putRightFork()`释放右叉。 

预期输出是隐式的。 我们不返回值。 相反，解决方案的正确性取决于并发执行下操作是否以有效顺序发生。 

限制相对较小：

 -`1 <= n <= 60`然而，困难并不来自输入大小。 这是一个**并发问题**，意味着正确性取决于同步而不是算法缩放。 即使只有五位哲学家，幼稚的实现也很容易陷入僵局。 

一个重要的细节是同一位哲学家的`wantsToEat()`方法可能会在前一个调用完成之前再次调用。 这意味着我们不能假设每个哲学家都是顺序执行的，并且我们的同步必须是线程安全的。 

一些边缘情况很重要：

 如果所有五个哲学家同时行动，每个哲学家首先拿起左边的叉子的天真的解决方案可能会立即陷入僵局。 

来自同一位哲学家的多个请求可能会重叠，这意味着即使重复调用，分叉访问也必须保持安全。 

当所有哲学家反复尝试同时吃饭时，可能会发生严重的争用。 正确的解决方案仍然必须保证进展。 

该问题保证恰好有五个哲学家和有效的哲学家 ID`0`到`4`。 

## 方法

 ### 蛮力方法

 一个幼稚的实现只是让每个哲学家先拿起他们的左叉子，然后再拿起他们的右叉子。 

在此设计中，每个分叉都由一个互斥体表示。 当哲学家想要吃饭时，他们锁定左叉互斥体，然后锁定右叉互斥体，吃东西，最后释放两个叉子。 

这看起来是正确的，因为相互排斥是强制执行的，这意味着没有两个哲学家可以同时拿着同一个叉子。 

然而，这种方法会遇到僵局。 

想象一下所有五位哲学家同时执行：

 - 哲学家 0 选择左叉。 
- 哲学家 1 选择左叉。 
- 哲学家 2 选择左叉。 
- 哲学家 3 选择左叉。 
- 哲学家 4 选择左叉。 

现在，每个哲学家都会永远等待正确的叉子，而该叉子已经被邻居拿着了。 由于没有人可以进步，系统永久陷入僵局。 

虽然实现简单，但是对于并发执行来说从根本上来说是不安全的。 

### 最佳方法

 关键的观察结果是，死锁的发生是因为所有哲学家可能会尝试同时以相同的顺序获取分叉，从而产生循环依赖。 

为了防止死锁，我们必须打破循环。 

一个标准而优雅的解决方案是使用**全局信号量（或互斥量限制）**，最多允许**四个哲学家同时竞争分叉**。 

由于只有四位哲学家可以尝试同时吃饭，因此至少一位哲学家将始终保持思考。 这保证了至少一对叉保持可用，防止循环等待并确保进度。 

我们仍然为每个分叉使用互斥锁以保留独占访问权限。 信号量仅限制争用。 

该过程变为：

 1. 获得信号量的许可。 
2. 锁定左货叉。 
3. 锁定右叉。 
4. 吃。 
5. 松开两个叉子。 
6.释放信号量权限。 

这可以避免死锁，同时保持正确性。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(1) | O(1) | O(1) | O(1) | 简单的叉锁，但可能会死锁 |
 | 最佳| O(1) | O(1) | O(1) | O(1) | 使用叉锁加准入控制来防止死锁 |

 ## 算法演练

 ### 最优算法

 1. 创建 5 个互斥体，每个 fork 一个。 

由于叉子是共享资源，因此一次只有一位哲学家可以拿着叉子。 互斥体是独占所有权的自然同步原语。 
2. 创建具有容量的信号量`4`。 

信号量充当看门人的角色。 最多允许四位哲学家同时尝试吃饭。 这可以防止导致死锁的循环等待条件。 
3. 当哲学家想吃饭时，首先获取信号量。 

如果四位哲学家已经在争夺叉子，那么哲学家就会等待。 这确保了一位哲学家始终处于竞争之外。 
4. 确定分叉索引。 

对于哲学家来说`p`:

 - 左叉 =`p`- 右叉=`(p + 1) % 5`由于哲学家围成一圈，模算术自然会环绕。 
5. 锁定左叉互斥体。 

获取后，调用`pickLeftFork()`。 
6. 锁定右叉互斥锁。 

获取后，调用`pickRightFork()`。 
7. 执行`eat()`。 

由于保证两把叉子都是独占的，所以哲学家可以安全地吃饭。 
8. 按相反顺序释放货叉。 

调用`putRightFork()`，解锁右侧叉子，然后调用`putLeftFork()`，解锁左叉。 
9. 释放信号量访问。 

另一位哲学家现在可能会尝试吃饭。 

### 为什么它有效

 关键的不变量是**最多四个哲学家可以同时竞争叉子**。 

死锁需要一个涉及所有五个哲学家的循环等待链。 通过阻止所有五个同时进入分叉获取阶段，我们消除了完全循环依赖的可能性。 

分叉互斥体保证独占访问，而信号量保证进度。 因此，哲学家可以无限期地在吃和思考之间交替，而不会陷入僵局。 

## Python 解决方案```python
from threading import Lock, Semaphore
from typing import Callable

class DiningPhilosophers:

    def __init__(self):
        self.forks = [Lock() for _ in range(5)]
        self.semaphore = Semaphore(4)

    def wantsToEat(
        self,
        philosopher: int,
        pickLeftFork: 'Callable[[], None]',
        pickRightFork: 'Callable[[], None]',
        eat: 'Callable[[], None]',
        putLeftFork: 'Callable[[], None]',
        putRightFork: 'Callable[[], None]'
    ) -> None:

        left_fork = philosopher
        right_fork = (philosopher + 1) % 5

        self.semaphore.acquire()

        self.forks[left_fork].acquire()
        pickLeftFork()

        self.forks[right_fork].acquire()
        pickRightFork()

        eat()

        putRightFork()
        self.forks[right_fork].release()

        putLeftFork()
        self.forks[left_fork].release()

        self.semaphore.release()
```该实现首先初始化五个锁，每个分叉一个。 由于分叉是共享资源，因此必须相互排斥，以避免多个哲学家同时使用同一个分叉。 

还创建了大小为 4 的信号量。 这是至关重要的死锁预防机制。 

里面`wantsToEat()`，我们使用哲学家 ID 计算分叉索引。 哲学家在尝试锁定分叉之前首先获得信号量的许可。 

一旦授予访问权限，哲学家就会锁定左叉，执行`pickLeftFork()`，然后锁定右分叉并执行`pickRightFork()`。 

只有当两个货叉都固定好后才可以`eat()`称为。 

最后，哲学家放下右叉子和左叉子，释放它们的锁。 信号量槽也被释放，允许另一位哲学家进入。 

该顺序确保了独占分叉访问并防止死锁。 

## 解决方案```go
package main

import "sync"

type DiningPhilosophers struct {
	forks [5]sync.Mutex
	limit chan struct{}
}

func Constructor() DiningPhilosophers {
	return DiningPhilosophers{
		limit: make(chan struct{}, 4),
	}
}

func (this *DiningPhilosophers) wantsToEat(
	philosopher int,
	pickLeftFork func(),
	pickRightFork func(),
	eat func(),
	putLeftFork func(),
	putRightFork func(),
) {
	leftFork := philosopher
	rightFork := (philosopher + 1) % 5

	this.limit <- struct{}{}

	this.forks[leftFork].Lock()
	pickLeftFork()

	this.forks[rightFork].Lock()
	pickRightFork()

	eat()

	putRightFork()
	this.forks[rightFork].Unlock()

	putLeftFork()
	this.forks[leftFork].Unlock()

	<-this.limit
}
```Go 实现遵循与 Python 版本相同的设计，但使用 Go 并发原语。 

Go 使用具有容量的缓冲通道来代替信号量对象`4`。 发送到通道需要获得许可，而接收则释放许可。 

分叉是使用以下方式实现的`sync.Mutex`。 

与 Python 不同，Go 需要显式的结构初始化。 这`Constructor()`方法初始化通道。 

不用担心整数溢出，因为哲学家 ID 仅限于`0`通过`4`。

 **输入：**```
n = 1

 #### 步骤 1：哲学家 0

 - 获取信号量。

 | 1 | 哲学家 0 |

 | 4 | 免费|

 #### 步骤 2：哲学家 1

 哲学家 1 需要叉子`1`和`2`。 

如果哲学家 0 已经发布了 fork`1`，哲学家 1 立即继续。 

| 叉| 业主|
 | ---| ---|
 | 0 | 免费|
 | 1 | 哲学家 1 |

 #### 第三步：剩下的哲学家

 哲学家`2`,`3`， 和`4`类似地进行。 

在任何时候，所有五位哲学家都不会同时被阻止，因为信号量将并发限制为四个活跃的竞争者。 

因此，永远不会发生死锁。 

输出中的确切执行顺序可能有所不同，因为线程调度是不确定的。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(1) | O(1) | 每个哲学家执行恒定数量的锁定和解锁操作 |

## 测试用例```python
from threading import Thread

def test_dining_philosophers():
    dp = DiningPhilosophers()

    results = []

    def create_callbacks(philosopher):
        return (
            lambda: results.append((philosopher, "pick_left")),
            lambda: results.append((philosopher, "pick_right")),
            lambda: results.append((philosopher, "eat")),
            lambda: results.append((philosopher, "put_left")),
            lambda: results.append((philosopher, "put_right")),
        )

    # Test 1: Single philosopher request
    callbacks = create_callbacks(0)
    dp.wantsToEat(0, *callbacks)

    assert ("eat" in [x[1] for x in results])  # basic execution

    results.clear()

    # Test 2: All philosophers eat once concurrently
    threads = []

    for i in range(5):
        callbacks = create_callbacks(i)

        thread = Thread(
            target=dp.wantsToEat,
            args=(i, *callbacks)
        )

        threads.append(thread)
        thread.start()

    for thread in threads:
        thread.join(timeout=2)

    assert len(results) > 0  # ensures no deadlock

    results.clear()

    # Test 3: Repeated requests from same philosopher
    threads = []

    for _ in range(10):
        callbacks = create_callbacks(0)

        thread = Thread(
            target=dp.wantsToEat,
            args=(0, *callbacks)
        )

        threads.append(thread)
        thread.start()

    for thread in threads:
        thread.join(timeout=2)

    assert results.count((0, "eat")) == 10  # repeated calls

    results.clear()

    # Test 4: Stress concurrency
    threads = []

    for _ in range(20):
        for philosopher in range(5):
            callbacks = create_callbacks(philosopher)

            thread = Thread(
                target=dp.wantsToEat,
                args=(philosopher, *callbacks)
            )

            threads.append(thread)
            thread.start()

    for thread in threads:
        thread.join(timeout=5)

    eat_count = sum(
        1 for action in results if action[1] == "eat"
    )

    assert eat_count == 100  # high contention stress

 ## 边缘情况

 一个重要的边缘情况是**所有五位哲学家尝试同时吃饭**。 这是简单解决方案的典型死锁场景。 如果没有协调，每个哲学家都可以拿起一把叉子并永远等待。 信号量可以防止这种情况发生，因为一次只能有四位哲学家竞争，确保至少有一位哲学家总能完成进食并释放资源。 

另一个重要的情况是**来自同一位哲学家的多个重叠请求**。 该问题明确允许`wantsToEat()`在前一次调用完成之前再次为同一位哲学家调用。 有缺陷的实现可能会假设哲学家按顺序执行。 由于使用互斥体保护分叉访问，因此重叠调用保持安全并正确同步。 

第三个边缘情况是**与重复的进食请求的最大争用**。 自从`n`可以高达`60`，线程可能会重复竞争fork。 该实现可以正确处理此问题，因为每个操作都通过锁定和准入控制进行保护，从而防止死锁，同时保持安全的资源共享。 

最后一个微妙的案例涉及**哲学家 4**，他的右叉子环绕着叉子`0`。 不正确的索引计算可能会导致超出范围的访问或不正确的分叉所有权。 使用：```
(philosopher + 1) % 5
```正确模拟圆桌结构并确保哲学家`4`与哲学家共用一把叉子`0`。
