 ## 解决方案

 ## 问题理解

 该问题给了我们一个名为`Queries`。 每行代表对数据库运行特定查询的结果。 这些列是：

 | 专栏 | 意义|
 | ---| ---|
 |`query_name`| 查询组名称|
 |`result`| 返回结果字符串 |
 |`position`| 结果的排名或位置 |
 |`rating`| 评估结果质量的分数从 1 到 5 |

 目标是为每个不同的计算两个指标`query_name`。 

第一个指标称为`quality`。 对于给定的查询组，我们计算比率：$$\frac{\text{rating}}{\text{position}}$$对于属于该查询的每一行，然后取所有这些比率的平均值。 

第二个指标称为`poor_query_percentage`。 如果一个查询被认为是糟糕的`rating`小于`3`。 我们必须计算：$$\frac{\text{number of poor queries}}{\text{total queries}} \times 100$$对于每个`query_name`。 

最后，这两个值都必须四舍五入到小数点后两位。 

输出应包含每个唯一的一行`query_name`，连同其计算出的`quality`和`poor_query_percentage`。 

约束相对较小且简单。 这`position`范围从`1`到`500`， 和`rating`范围从`1`到`5`。 该问题没有指定巨大的数据集，并且由于这是一个数据库聚合问题，因此预期的解决方案是有效地使用 SQL 聚合函数。 

一个重要的细节是可能存在重复的行。 我们不应该删除重复项，因为每一行都代表有效的查询发生，并且独立地影响平均值和百分比。 

另一个重要的边缘情况是当查询的所有行都是不良查询时，这意味着百分比变为`100.00`。 同样，如果没有一个是差的，则百分比变为`0.00`。 我们还必须确保使用浮点除法而不是整数除法，否则计算出的质量值将不正确。 

## 方法

 ### 蛮力方法

 暴力解决方案将处理每个不同的`query_name`分别地。 

对于每个唯一的查询名称：

 1. 扫描整个表。 
2. 收集属于该查询的所有行。 
3. 计算总和`rating / position`。 
4. 计算总行数。 
5. 计算有多少行`rating < 3`。 
6. 计算最终平均值和百分比。 

这种方法是正确的，因为每个查询组都是使用问题陈述中的精确公式独立评估的。 但是，它会重复扫描整个表以查找每个不同的查询名称。 

如果有`n`行和`k`不同的查询名称，此方法可能需要最多`O(n * k)`工作。 在最坏的情况下，每行都有不同的查询名称，这会变成`O(n^2)`。 

### 最佳方法

 关键的观察结果是，所有必需的值都是按以下分组的聚合统计数据`query_name`。 

我们可以按以下方式对行进行分组，而不是重复扫描表`query_name`一次并计算：

 - 平均数`rating / position`- 行的百分比`rating < 3`SQL 聚合函数非常适合此目的：

 -`AVG(rating / position)`计算质量。 
-`AVG(CASE WHEN rating < 3 THEN 1 ELSE 0 END) * 100`计算不良查询百分比。 

由于 SQL 数据库针对分组和聚合进行了优化，因此该解决方案可以在一次分组过程中高效地处理表。

 ## 算法演练

 1. 对所有行进行分组`query_name`。 

每个查询名称需要一个最终输出行，因此分组自然会将所有相关行组织在一起。 
2. 对于组中的每一行，计算`rating / position`。 

该值有助于查询质量指标。 由于质量被定义为这些比率的平均值，因此每一行的贡献相等。 
3. 计算该组中所有比率的平均值。 

这给出了`quality`该查询名称的值。 
4. 使用条件识别不良查询`rating < 3`。 

每个糟糕的查询都有贡献`1`，而非不良查询则贡献`0`。 
5. 计算这些指标值的平均值并乘以`100`。 

由于 0 和 1 的平均值等于 1 的分数，因此乘以`100`将其转换为百分比。 
6. 将两个计算值四舍五入到小数点后两位。 

该问题明确要求具有两位小数精度的格式化数字输出。 
7. 每个查询组返回一行。 

### 为什么它有效

 该算法之所以有效，是因为两个必需的指标都是属于同一行的所有行的平均值`query_name`。 

对于质量：$$\text{quality} = \frac{ \sum (\text{rating} / \text{position}) }{ \text{number of rows} }$$对于较差的查询百分比：$$\text{poor percentage} = \frac{ \text{poor rows} }{ \text{total rows} } \times 100$$分组可确保每行只为正确的查询组贡献一次，并且聚合函数直接计算这些公式。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    query_name,
    ROUND(AVG(rating / position), 2) AS quality,
    ROUND(
        AVG(CASE WHEN rating < 3 THEN 1 ELSE 0 END) * 100,
        2
    ) AS poor_query_percentage
FROM Queries
GROUP BY query_name;
```该解决方案使用 SQL 聚合来计算单个分组查询中的两个所需指标。 

这`GROUP BY query_name`子句确保同一查询的所有行都一起处理。 

表达式：```python
AVG(rating / position)
```计算所需的平均比率`quality`公制。 

这`CASE`表达式将不良查询转换为`1`和非不良查询`0`:```python
CASE WHEN rating < 3 THEN 1 ELSE 0 END
```取这些值的平均值即可得出不良查询的比例。 乘以`100`将分数转换为百分比。 

最后，`ROUND(..., 2)`根据需要将结果格式化为小数点后两位。

 ## 边缘情况

 ### 所有查询都很差

 如果查询的每一行都有`rating < 3`，那么较差的查询百分比应该变成`100.00`。 

有缺陷的实现可能会意外地错误地划分整数或错误处理百分比转换。 使用：```
AVG(CASE WHEN rating < 3 THEN 1 ELSE 0 END) * 100
```正确产生`100.00`当所有行的计算结果为`1`。 

### 没有糟糕的查询

 如果每个评级至少`3`，那么百分比应该变成`0.00`。 

一些实现错误地忽略了`ELSE 0`分支在`CASE`语句，可以产生`NULL`价值观。 明确返回`0`保证平均值正确工作。 

### 非常大的头寸价值

 仓位可以大到`500`，产生非常小的比率，例如：$$\frac{1}{500} = 0.002$$使用整数除法的粗心实现会错误地产生`0`。 SQL 浮点除法保留小数精度，最后的舍入步骤确保输出格式完全符合要求。
