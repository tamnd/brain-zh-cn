 # LeetCode 881，救人的船

 ## 问题理解

 这个问题要求我们在给定两个约束的情况下确定救援所有人所需的最少船只数量。 每艘船最多可载两人，船上人员的总重量不得超过规定的重量限制。 

输入包括：

 -`people`，一个数组，其中每个值代表一个人的体重
 -`limit`, 单船可承载的最大总重量

 目标是将每个人都安置在一艘船上，同时最大限度地减少使用的船只总数。 

例如，如果`people = [1,2]`和`limit = 3`，两个人可以共用一条船，因为`1 + 2 = 3`，不超过限制。 因此，只需要一艘船。 

该问题保证每个人的体重小于或等于船的限制，因此如果有必要，每个人总是可以单独登上船。 这很重要，因为这意味着总是至少有一个有效的解决方案。 

约束足够大，效率很重要：

 - 最多`5 * 10^4`人
 - 重量和限制可达`3 * 10^4`为每个人重复搜索合作伙伴的二次解决方案可能会太慢。 我们需要更接近的东西`O(n log n)`或更好。 

预先考虑几个边缘情况很重要：

 - 每个人可能都需要自己的船，因为没有一对符合限制。 
- 每双都可以完美贴合，从而实现最大程度的共享。 
- 数组可能包含许多重复的权重。 
- 可能只有一个人。 
- 最重的人可能只能单独适应，这会影响我们如何与其余的人配对。 

核心挑战是找到一种有效的策略，尽可能将人们配对在一起，同时又不浪费船只的容量。 

## 方法

 ### 蛮力方法

 一个简单的暴力解决方案会反复尝试将每个人与另一个剩余的人配对，而该人的总重量保持在限制范围内。 

一种可能的实现是：

 1. 选择一个未分配的人员。 
2. 在所有剩余的未分配人员中搜索最重的有效伙伴。 
3. 将他们分配到一艘船上。 
4. 重复此操作，直至分配完每个人。 

这种方法是正确的，因为它最终让每个人都上船，同时尊重约束。 然而，重复的搜索使得效率低下。 

如果我们在剩余的人中搜索每个人，时间复杂度就变成了`O(n^2)`。 高达`50,000`人们，这可能变得太慢了。 

### 最优贪婪两指针方法

 关键的见解是排序使我们能够有效地做出最佳配对决策。 

权重排序后：

 - 最轻的人在开始。 
- 最重的人在最后。 

最重的人是最难安置的，因为他们的伙伴最少。 因此，我们应该始终首先处理剩下的最重的人。 

对于每个最重的人：

 - 如果他们可以与剩下的最轻的人共用一条船，我们应该将他们配对。 
- 如果他们不能与最轻的人分享，那么他们也不能与其他任何人分享，因为其他人都更重。 

这一观察使得贪婪策略成为最优策略。 

我们使用两个指针：

 -`left`对于剩下最轻的人
 -`right`对于剩下最重的人

 每一步：

 - 尝试配对`people[left] + people[right]`- 如果配对合适，则移动两个指针
 - 否则，最重的人会单独走，所以只能移动`right`- 在这两种情况下，都使用一艘船

 这给出了一个有效的`O(n log n)`解决方案，因为排序在运行时占主导地位。

 ## 算法演练

 1. 排序`people`数组按非降序排列。 

排序使我们能够有效地比较剩余的最轻和最重的人。 这种结构使得贪婪策略成为可能。 
2. 初始化两个指针。 

放：

-`left = 0`对于最轻的人
 -`right = len(people) - 1`对于最重的人

 同时初始化`boats = 0`。 
3. 处理人员的同时`left <= right`。 

只要还有未分配的人员，我们就继续分配船只。 
4. 检查最轻和最重的人是否可以共用一条船。 

如果：$people[left] + people[right] \le limit$然后他们就可以一起骑车了。 

在这种情况下：

 - 增量`left`- 递减`right`我们成功地将两个人安置在一艘船上。 
5. 否则，最重的人必须单独前往。 

如果剩下的最轻的人无法与最重的人配对，那么没有人可以与最重的人配对，因为其他人都更重。 

所以：

 - 递减`right`只有最重的人才会被分配到这艘船上。 
6. 增加船只数量。 

每次迭代都只使用一艘船。 
7. 继续，直到分配完所有人员。 

什么时候`left > right`，大家都已经处理完毕了。 
8. 返回船只总数。 

### 为什么它有效

 正确性来自于始终为剩余最重的人提供尽可能最佳的位置。 

如果最重的人可以与最轻的人配对，那么将他们配对是最佳选择，因为它可以有效地使用一艘船，同时保留较重的人以供将来配对。 

如果最重的人无法与最轻的人配对，他们就无法与其他任何人配对。 因此，单独发送它们是不可避免的，也无法改进。 

这种贪婪的选择总是安全的，保证了最优解。 

## Python 解决方案```python
from typing import List

class Solution:
    def numRescueBoats(self, people: List[int], limit: int) -> int:
        people.sort()

        left = 0
        right = len(people) - 1
        boats = 0

        while left <= right:
            if people[left] + people[right] <= limit:
                left += 1

            right -= 1
            boats += 1

        return boats
```该实现首先对数组进行排序，以便可以使用指针有效地访问最轻和最重的人。 

这`left`指针从数组的开头开始，而`right`指针从末尾开始。 变量`boats`跟踪已使用了多少艘船。 

在循环内，算法检查剩余的最轻和最重的人是否可以共享一艘船。 如果可以的话，最轻的人会与最重的人配对，所以`left`向前移动。 

无论配对是否成功，在当前迭代期间，最重的人总是被分配到一条船上，因此`right`总是向后移动并且`boats`总是加一。 

一旦所有人员都被分配到船上，循环就会停止。 

## 解决方案```go
package main

import "sort"

func numRescueBoats(people []int, limit int) int {
	sort.Ints(people)

	left := 0
	right := len(people) - 1
	boats := 0

	for left <= right {
		if people[left]+people[right] <= limit {
			left++
		}

		right--
		boats++
	}

	return boats
}
```Go 实现遵循与 Python 版本相同的逻辑。 主要区别在于使用`sort.Ints`从 Go 的标准库中对切片进行就地排序。 

Go 切片是类似引用的结构，因此排序会直接修改原始切片。 整数溢出在这里不是一个问题，因为最大可能的总和是`60000`，它很容易适合 Go 的`int`类型。 

该实现自然可以正确处理空切片和单元素切片，尽管约束保证至少有一个人。

 两个指针的遍历本身是线性的，因为每个指针只向一个方向移动，并且每个人都被处理一次。 

排序步骤需要`O(n log n)`时间，它在整体复杂性中占主导地位。 

该算法仅使用输入数组之外的一些额外变量。 然而，排序实现可能会在内部使用额外的堆栈空间，这就是为什么一些分析报告`O(log n)`辅助空间。

 ## 边缘情况

 ### 每个人都必须独自骑行

 当没有两个人可以共用一条船时，就会出现一种常见的边缘情况。 例如：```
people = [4,4,4]
limit = 4
```每个人都已经达到了单独的体重限制，因此不可能配对。 有缺陷的实现可能仍会尝试无效的配对或错误处理指针移动。 

两指针解决方案自然地处理了这个问题，因为每次配对检查都会失败，导致每次迭代都单独分配最重的人。 

### 完美配对场景

 另一个重要的情况是每艘船只能有效地容纳两个人，例如：```
people = [1,1,2,2]
limit = 3
```糟糕的贪婪策略可能会过早地将较小的人配对在一起，从而浪费空间。 

排序的两指针方法避免了这个问题，因为它总是尝试首先将最重的剩余人配对，以确保最佳的船只使用。 

### 剩下一个人

 最终，算法可能会达到只剩下一个人的状态：```
left == right
```如果循环条件不正确，这可能是差一错误的根源。 

实现使用：```
while left <= right:
```这保证了最后一个未配对的人在循环退出之前仍然收到一艘船。
