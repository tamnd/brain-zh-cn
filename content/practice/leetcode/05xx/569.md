 # LeetCode 569，员工薪资中位数

 ## 问题理解

 这个问题给了我们一个`Employee`包含三列的表：

 | 专栏 | 意义|
 | --- | --- |
 |`id`| 唯一的员工标识符 |
 |`company`| 公司名称 |
 |`salary`| 员工薪资|

 我们需要返回与每家公司的中位数工资相对应的行。 

重要的细节是工资必须首先按升序排序。 如果两个员工的工资相同，则排序由下式确定：`id`。 这个打破平局的规则很重要，因为中位数取决于确切的顺序。 

根据公司员工人数是奇数还是偶数，问题的表现略有不同。 

如果一家公司的员工人数为奇数，则中间行恰好有一个。 

如果公司的员工人数为偶数，则中间有两行，两者都必须返回。 

例如，如果一家公司排序后有 6 名员工，则位置 3 和 4 就是中位数。 如果一家公司有 5 名员工，则位置 3 是中位数。 

输出应包含来自的原始行`Employee`与这些中位位置相对应的表。 

约束没有明确列出，但这是一个旨在测试 SQL 排名和分组逻辑的数据库问题。 主要挑战是正确识别每个公司分区内的中位职位，同时使用工资和 ID 保持确定性排序。 

一些边缘情况很重要：

 公司可能包含重复的工资。 在这种情况下，仅按工资排序是不够的，因为顺序变得不明确。 该问题明确告诉我们使用以下方法打破关系`id`。 

一家公司可能只包含一名员工。 在这种情况下，该员工就是中位数。 

公司可能包含偶数个员工，需要两排而不是一排。 

幼稚的实现可能会仅使用工资值而不是员工职位来错误地计算中位数。 该问题要求对员工进行排序后的中位数行，而不是数学中位数工资值。 

## 方法

 ### 蛮力方法

 暴力解决方案独立处理每个公司。 

对于每家公司：

 1. 提取属于该公司的所有员工。 
2. 排序依据`(salary, id)`。 
3. 计算员工总数。 
4. 确定一个或多个中值指数。 
5. 返回相应的行。 

这种方法很简单并且保证了正确性，因为它直接模拟问题陈述中给出的定义。 

然而，如果在没有排名支持的情况下手动实现，它会变得效率低下，因为我们会重复对分区进行排序和扫描列表。 在 SQL 中，这通常会导致相关子查询或自连接，计算成本很高。 

### 最佳方法的关键见解

 重要的观察结果是，中位数完全取决于按顺序排序后每个员工在公司内的排名`(salary, id)`。 

如果我们可以分配每个员工：

 - 他们的位置按排序顺序
 - 公司员工总数

 那么确定中位数就变得很容易。 

For a company with`n`员工：

 - 如果`n`是奇数，中位位置是`(n + 1) / 2`- 如果`n`是偶数，中位数位置是`n / 2`和`n / 2 + 1`使用 SQL 窗口函数，我们可以计算：

 -`ROW_NUMBER()`对于排序位置
 -`COUNT()`适合公司规模

 然后我们简单地过滤排名与中值位置匹配的行。 

这将问题转化为排序问题，而不是重复排序和扫描。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n log n) | O(n log n) | O(n) | 独立对每家公司进行排序并手动定位中位数 |

 ## 算法演练

 1.按公司划分员工。 

我们独立对待每家公司，因为每家公司的工资中位数都是单独计算的。 
2. 对每个公司内部的员工进行排序。 

员工按以下顺序排序：

 -`salary ASC`-`id ASC`二次排序依据`id`确保薪资相同时的确定性排名。 
3. 分配行号。 

我们使用`ROW_NUMBER()`为每个员工分配公司内唯一的级别。 

示例：

 | 公司 | 薪资| 编号 | 行号 |
 | --- | --- | --- | --- |
 | 一个 | 15 | 15 3 | 1 |
 | 一个 | 341 | 341 2 | 2 |
 | 一个 | 451 | 451 5 | 3 |
 4. 计算公司规模。 

使用`COUNT(*) OVER (PARTITION BY company)`，我们确定每个公司有多少员工。 
5. 确定中间位置。 

对于公司规模`n`：

 - 左中间位置=`(n + 1) / 2`- 右中位 =`(n + 2) / 2`这些公式适用于奇数和偶数计数。 

示例：

 | n | 左| 对|
 | --- | --- | --- |
 | 5 | 3 | 3 |
 | 6 | 3 | 4 |
 6. 过滤排名与中位位置匹配的行。 

返回行号位于两个中值边界之间的员工。 

### 为什么它有效

 该算法之所以有效，是因为`ROW_NUMBER()`产生问题陈述所需的精确顺序。 一旦对员工进行排名，中位数就纯粹是一个职位属性。 左右中位数位置的公式可以正确处理奇数和偶数公司规模，确保返回所有必需的中位数行。 

## Python 解决方案```python
# This problem is a SQL problem, so the "Python solution"
# represents the SQL query as a multiline string.

class Solution:
    def medianEmployeeSalary(self):
        return """
        WITH RankedEmployees AS (
            SELECT
                id,
                company,
                salary,
                ROW_NUMBER() OVER (
                    PARTITION BY company
                    ORDER BY salary, id
                ) AS rn,
                COUNT(*) OVER (
                    PARTITION BY company
                ) AS total_count
            FROM Employee
        )
        SELECT
            id,
            company,
            salary
        FROM RankedEmployees
        WHERE rn BETWEEN (total_count + 1) / 2
                     AND (total_count + 2) / 2;
        """
```该解决方案首先创建一个名为的公用表表达式`RankedEmployees`。 

在 CTE 内，每个员工都会收到两个计算值：

 -`rn`, 员工在公司内的级别
 -`total_count`, 该公司的员工总数

 排名使用：```python
ORDER BY salary, id
```这完全符合打破平局的问题要求。 

排序后，外部查询会过滤排名位于两个中间位置之间的行。 

对于奇数计数，两个公式计算到相同的位置，生成一行。 

对于偶数计数，公式会生成两个连续位置，从而生成两行。 

这可以用一个条件优雅地处理这两种情况。

 ## 边缘情况

 当多名员工分享相同的薪水时，就会出现一个非常重要的边缘情况。 如果我们仅按薪水排序，排序就会变得不确定，这可能会在执行过程中产生不一致的中位数。 该实现通过显式排序来避免这种情况`(salary, id)`因此，每位员工都会获得独特且稳定的等级。 

另一个重要的边缘情况是公司员工数量为偶数时。 许多不正确的解决方案通过计算单个中值仅返回一个中间行。 这个问题需要中间两行。 该实现正确计算两个中值边界并返回排名位于它们之间的每一行。 

一家只有一名员工的公司是另一个微妙的例子。 某些实现可能会错误地计算无效边界或假设至少存在两名员工。 这里，两个边界公式的计算结果为`1`，因此单独的员工被正确返回为中位数。 

最后的边缘情况涉及未排序的输入数据。 不保证数据库行出现在工资顺序中。 该算法在分配行号之前对每个公司分区内的员工进行显式排序，从而确保无论输入顺序如何都正确。
