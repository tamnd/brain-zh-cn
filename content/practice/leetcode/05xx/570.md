[LeetCode 570 题](https://leetcode.com/problems/managers-with-at-least-5-direct-reports/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 的`Employee`表代表公司的层次结构。 每行对应一名员工，包含四条信息：

 | 专栏 | 意义|
 | --- | --- |
 |`id`| 唯一的员工标识符 |
 |`name`| 员工姓名|
 |`department`| 员工所属部门 |
 |`managerId`| 这`id`该员工的经理的 |

 如果`managerId`是`NULL`，该员工不向任何人汇报，因此处于组织的最高层。 

该问题要求我们找到所有至少有五名直接下属的经理。 直接下属是指其雇员`managerId`直接指向该经理的`id`。 

重要的细节是，只有直接报告才算数。 间接报告，例如层次结构中较低的员工，不应包括在内。 

例如：

 - 如果是雇员`101`管理员工`102`,`103`,`104`,`105`， 和`106`，然后是员工`101`有五名直接下属。 
- 如果是雇员`102`管理其下的其他人员，这些员工不计入员工`101`的总数。 

预期输出是一个仅包含满足条件的经理姓名的表。 

输入保证了几个重要的属性：

 -`id`是独一无二的。 
-`managerId`引用另一名员工的`id`，或者是`NULL`。 
- 没有员工能够自我管理。 

这些保证简化了问题，因为我们不需要处理涉及自我管理的无效引用或循环。 

一些边缘情况很重要：

 - 员工`NULL`作为`managerId`如果其他人向他们汇报，他们可能仍然是经理。 
- 应包括恰好有五份报告的员工。 
- 报告数量少于五份的员工不应出现。 
- 多个管理者可以满足该条件。 
- 经理可能属于任何部门，部门列与此问题无关。 
- 没有任何直接下属的员工不应出现在结果中。 

## 方法

 ### 蛮力方法

 暴力解决方案将检查每个员工并计算有多少员工向他们报告。 

对于每位员工：

 1. 扫描整个表。 
2. 计算行数，其中`managerId == current_employee.id`。 
3. 如果计数至少为五，请注明员工姓名。 

这是有效的，因为每个可能的报告关系都被明确检查。 

然而，这种方法效率低下，因为对于每个员工，我们都会对表执行另一次完整扫描。 如果有`n`员工，总工作变成`O(n^2)`。 

对于较大的数据集，重复扫描同一个表会变得不必要的昂贵。 

### 最佳方法

 关键的观察结果是，我们只需要按以下分组的员工人数`managerId`。 

我们可以使用以下方法一次性汇总所有报告计数，而不是重复地独立计算每个经理的报告数量`GROUP BY`。 

最佳 SQL 解决方案分两个阶段工作：

 1. 对员工进行分组`managerId`。 
2. 仅保留计数至少为 5 的组。 
3. 将这些经理 ID 添加回`Employee`用于检索经理姓名的表。 

这是有效的，因为计数工作只发生一次。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(1) | O(1) | 重复扫描整个表中的每个员工 |
 | 最佳 | O(n) | O(n) | 使用分组和聚合对报告进行一次计数 |

 ## 算法演练

 ### 最优 SQL 算法

 1. 从`Employee`表并重点关注`managerId`柱子。 

每个员工行都告诉我们他们向谁报告。 通过将相同的行分组`managerId`，我们可以确定每个经理有多少个直接下属。 
2. 对员工进行分组`managerId`。 

这会为每个管理员 ID 创建一个组。 组内的每一行对应一个直接报告。 
3. 统计每组的员工人数。 

使用`COUNT(*)`，我们计算每个经理有多少个直接下属。 
4. 使用过滤组`HAVING COUNT(*) >= 5`。 

这`HAVING`子句在计数后过滤聚合组。 只剩下至少有五名直接下属的经理。 
5. 将分组结果与`Employee`桌子。 

分组结果仅包含管理员 ID。 为了检索经理姓名，我们将分组的经理 ID 与`Employee`表使用：```sql
Employee.id = grouped.managerId
```6. 返回经理姓名。 

最终输出包含直接管理至少五个人的员工姓名。 

### 为什么它有效

 该算法之所以有效，是因为每位员工都为其直接经理的团队贡献了一次计数。 分组依据`managerId`因此，可以为每位经理生成准确数量的直接下属。 过滤用`HAVING COUNT(*) >= 5`保证只留下合格的经理。 连接回员工表可以正确地将经理 ID 映射到经理姓名。 

## Python 解决方案

 尽管这是一个数据库问题，但 LeetCode 数据库问题通常仅使用 SQL 来解决。 为了完整起见，下面是在 Python 字符串中表示的标准 SQL 解决方案。```python
class Solution:
    def managersWithFiveReports(self) -> str:
        return """
        SELECT e.name
        FROM Employee e
        JOIN (
            SELECT managerId
            FROM Employee
            WHERE managerId IS NOT NULL
            GROUP BY managerId
            HAVING COUNT(*) >= 5
        ) m
        ON e.id = m.managerId
        """
```该解决方案首先创建一个分组子查询，对每个查询的员工进行计数`managerId`。```python
SELECT managerId
FROM Employee
GROUP BY managerId
HAVING COUNT(*) >= 5
```这会生成至少有五个直接下属的所有经理 ID。 

外部查询将这些管理器 ID 连接回`Employee`桌子：```python
ON e.id = m.managerId
```这使我们能够检索相应的经理名称。 

这`WHERE managerId IS NOT NULL`条件不是严格要求的，因为`NULL`groups 永远不会与连接中的经理 ID 匹配，但包含它可以使意图更清晰并避免不必要的分组工作。 

## 解决方案```go

func managersWithFiveReports() string {
	return `
SELECT e.name
FROM Employee e
JOIN (
    SELECT managerId
    FROM Employee
    WHERE managerId IS NOT NULL
    GROUP BY managerId
    HAVING COUNT(*) >= 5
) m
ON e.id = m.managerId
`
}
```Go 版本完全反映了 SQL 逻辑。 由于 LeetCode 数据库问题是作为 SQL 查询而不是传统的 Go 函数执行的，因此 SQL 语句本身是重要的部分。 

一个小的区别是字符串处理：

 - Python 使用三引号多行字符串。 
- Go 使用反引号括起来的原始字符串文字。 

两者都为多行 SQL 查询保留了干净的格式。

 ## 边缘情况

 ### 拥有五份报告的经理

 该条件规定“至少有五名直接报告者”，这意味着必须包括向他们汇报的恰好有五名员工的经理。 一个常见的错误是使用`>`而不是`>=`在`HAVING`条款。 实现正确使用：```
HAVING COUNT(*) >= 5
```其中包括拥有五份报告的经理。 

### 没有经理的员工

 部分员工有`managerId = NULL`。 这些员工不向任何人汇报。 幼稚的分组实现可能会意外计数`NULL`作为一个经理组。 该解决方案使用以下方式安全过滤：```
WHERE managerId IS NOT NULL
```分组前。 

### 间接报告链

 员工可能管理的人本身就是经理。 只有立即报告才算数。 

例如：

 - A管理B
 - B 管理 C、D、E、F、G

 A 只有一名直接下属，B.

 递归或基于层次结构的实现可能会错误地计算间接后代。 该解决方案完全避免了该问题，因为它仅直接按`managerId`。
