 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 问题是要求我们跟踪每个玩家的累积游戏活动。 具体来说，我们被赋予`Activity`表，其中每行代表特定设备上玩家的单个登录会话和日期，以及该会话期间玩的游戏数量。 目标是生成一份报告，显示每个玩家及其玩的每个日期，该玩家截至（包括该日期）玩过的游戏总数。 

换句话说，对于给定的玩家，我们需要总计`games_played`订购者`event_date`。 输入保证`(player_id, event_date)`是唯一的，因此没有玩家在同一日期拥有多行。 输出应包括玩家登录的每个日期，以及截至该日期的累计总数。 

重要的边缘情况包括只有一项记录的玩家、其中的会话`games_played`为零，并且玩家在会话之间的日期有间隙。 解决方案必须正确处理这些问题，以确保累积总和仅反映玩家按时间顺序登录的日期。 

## 方法

 蛮力方法将迭代每个玩家，然后对于每个日期将所有玩家相加`games_played`截至该日期。 虽然这会产生正确的结果，但效率很低，因为它会重复对先前的条目求和，在最坏的情况下给出的时间复杂度为 O(n²)，其中 n 是表中的行数。 

最佳解决方案的关键在于 SQL 支持 **窗口函数**，特别是`SUM() OVER(PARTITION BY ... ORDER BY ...)`。 通过对数据进行分区`player_id`并订购`event_date`，我们可以在一次传递中计算运行总计。 这种方法避免了重复求和，直接得出每行的累积总数。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(n) | 将每个玩家和日期的所有先前行相加； 对于大桌子来说效率低下|
 | 最佳| O(n) | O(n) | 使用SQL窗口函数计算按玩家分区并按日期排序的累积和 |

 ## 算法演练

 1. 首先选择我们需要的列：`player_id`,`event_date`， 和`games_played`。 
2. 应用窗函数`SUM(games_played) OVER(PARTITION BY player_id ORDER BY event_date)`计算每个玩家的累积游戏总数。 
3. 将窗口函数的结果别名为`games_played_so_far`为了清楚起见。 
4.返回结果，包括`player_id`,`event_date`，以及计算出的累积和。 除非特别需要，结果中的行顺序并不重要。 
5. 确保所有玩家都经过独立处理`PARTITION BY player_id`条款，并且累积总和遵循时间顺序使用`ORDER BY event_date`。 

**为什么起作用**：窗口函数在每个分区（播放器）内维护一个运行总计。 SQL 保证分区中的行按照指定的顺序进行处理`ORDER BY`，因此累积总和始终包含该玩家之前的所有行，从而产生正确的`games_played_so_far`。 

## Python 解决方案```python
import sqlite3
from typing import List, Tuple

def games_played_so_far() -> str:
    """
    Returns the SQL query string to compute cumulative games played per player.
    """
    return """
    SELECT 
        player_id,
        event_date,
        SUM(games_played) OVER(PARTITION BY player_id ORDER BY event_date) AS games_played_so_far
    FROM Activity
    """
```此 Python 函数仅返回计算累积和的 SQL 查询字符串。 这`SUM() OVER(PARTITION BY ... ORDER BY ...)`是算法的核心部分，确保我们按时间顺序计算每个玩家的运行总数。

 ## 边缘情况

 一个重要的边缘情况是玩家仅登录一次。 在这种情况下，累计总和应等于`games_played`那天，窗口函数自然会处理这个问题，因为单行的总和就是该行的值。 

另一种边缘情况发生在`games_played`为零。 如果玩家登录但没有玩任何游戏，则累计金额应反映零加法。 SQL 窗口函数正确加零，不会影响之前的总计。 

第三种边缘情况是玩家的非连续日期。 该算法必须确保累积总和跳过缺失的日子而不是重置。 通过使用`ORDER BY event_date`，无论日期之间的差距如何，运行总计都会正确维护。 这一点至关重要，因为假设每日连续性的简单方法可能会错误计算总数。
