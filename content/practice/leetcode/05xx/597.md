[LeetCode 597 题](https://leetcode.com/problems/friend-requests-i-overall-acceptance-rate/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 这个问题要求我们计算社交网络系统中好友请求的总体接受率。 提供了两个数据库表。 第一个表，`FriendRequest`，存储用户相互发送的所有好友请求。 第二个表，`RequestAccepted`，存储已接受的请求。 

接受率定义为：$\text{Acceptance Rate} = \frac{\text{Number of Unique Accepted Requests}}{\text{Number of Unique Friend Requests}}$重要的细节是两个表都可能包含重复的行。 同一对用户之间的多个相同请求只应计数一次。 同样，多个相同的接受也应该只计算一次。 因此，唯一性是由所涉及的用户对决定的。 

例如，如果用户`3`向用户发送两个请求`4`，它们仍然只算作一个请求。 同样，如果用户`4`两次接受请求，仍算作一次接受。 

另一个关键点是接受的请求不需要存在于`FriendRequest`桌子。 即使在没有相应请求的情况下出现接受，它仍然必须计入分子中。 

预期输出是一个名为`accept_rate`，四舍五入至小数点后两位。 

该问题还指定了一个重要的边缘情况。 如果根本没有好友请求，接受率应该是`0.00`而不是导致除零错误。 

因为这是一个数据库问题，所以主要挑战不是传统意义上的算法复杂性，而是使用 SQL 聚合函数正确处理重复项和边缘条件。 

## 方法

 ### 蛮力方法

 暴力方法将手动处理每一行并使用应用程序端逻辑跟踪重复项。 我们可以迭代所有行`FriendRequest`, 存储唯一`(sender_id, send_to_id)`成对成组，然后迭代`RequestAccepted`并存储独特的`(requester_id, accepter_id)`另一组中的对。 

构建完这两个集合后，我们将计算：

 - 独特请求总数
 - 独特接受总数
 - 录取率

 这种方法会产生正确的结果，因为集合自然会消除重复项。 然而，它在关系数据库环境中效率低下且不必要，因为 SQL 已经提供了为此目的优化的聚合和非重复计数操作。 

将数据移出数据库层还会增加内存使用量和网络开销。 

### 最佳方法

 关键的见解是我们只需要每个表中唯一用户对的计数。 SQL提供`COUNT(DISTINCT ...)`，这使得数据库引擎能够有效地处理重复消除。 

最优解计算：

 - 不同的数量`(sender_id, send_to_id)`对来自`FriendRequest`- 不同的数量`(requester_id, accepter_id)`对来自`RequestAccepted`然后将这两个值相除并将结果四舍五入到小数点后两位。 

当没有请求时，我们还必须防止被零除。 SQL 函数如`IFNULL`和`NULLIF`帮助干净地处理这个问题。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(R + A) | O(R + A) | 使用外部集删除重复项 |
 | 最佳| O(R + A) | O(1) 额外 | 使用 SQL 聚合和非重复计数 |

 这里：

-`R`是行数`FriendRequest`-`A`是行数`RequestAccepted`## 算法演练

 1. 通过选择不同的来统计所有独特的好友请求`(sender_id, send_to_id)`对来自`FriendRequest`桌子。 这消除了相同用户之间的重复请求。 
2. 通过选择不同的来计算所有唯一接受的请求`(requester_id, accepter_id)`对来自`RequestAccepted`桌子。 这消除了重复接受。 
3. 将唯一接受计数除以唯一请求计数以计算接受率。 
4. 使用`NULLIF(request_count, 0)`以避免被零除。 如果分母变为零，SQL 返回`NULL`而不是抛出错误。 
5. 使用`IFNULL(..., 0)`这样一个`NULL`结果变成`0`。 
6. 使用`ROUND(..., 2)`以确保结果恰好包含两位小数。 

### 为什么它有效

 该解决方案之所以有效，是因为问题定义明确指出重复请求和重复接受只应计数一次。 使用`COUNT(DISTINCT ...)`保证每个唯一的用户对恰好贡献一个计数。 因此，最终的划分完全符合接受率的数学定义。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    ROUND(
        IFNULL(
            (
                SELECT COUNT(DISTINCT requester_id, accepter_id)
                FROM RequestAccepted
            ) /
            NULLIF(
                (
                    SELECT COUNT(DISTINCT sender_id, send_to_id)
                    FROM FriendRequest
                ),
                0
            ),
            0
        ),
        2
    ) AS accept_rate;
```该查询分为三个逻辑部分。 

第一个子查询计算不同接受的请求对的数量`RequestAccepted`桌子。 因为重复项只计算一次，所以我们使用`COUNT(DISTINCT requester_id, accepter_id)`。 

第二个子查询对来自`FriendRequest`表使用相同的想法。 

接下来，分母被包裹起来`NULLIF(..., 0)`。 如果没有请求，则分母变为`NULL`，防止被零除错误。 

外层`IFNULL(..., 0)`转换一个`NULL`结果变成`0`，满足问题要求。 

最后，`ROUND(..., 2)`将答案格式化为小数点后两位。

 ## 边缘情况

 一种重要的边缘情况发生时`FriendRequest`桌子完全是空的。 幼稚的实现可能会尝试除以零，从而导致运行时 SQL 错误。 该解决方案通过使用避免了该问题`NULLIF(request_count, 0)`，它将零分母转换为`NULL`，然后使用`IFNULL(..., 0)`返回`0.00`。 

另一个微妙的边缘情况涉及重复的行。 因为两个表都明确允许重复，所以使用普通`COUNT(*)`会产生不正确的结果。 该实现通过仅计算不同的用户对来正确处理此问题。 

当存在接受但没有相应请求时，就会出现第三种边缘情况。 问题陈述明确指出这些接受仍然应该算作。 某些实现错误地在表之间执行联接，这将错误地丢弃不匹配的接受。 该解决方案完全避免了联接，并独立地计算每个表中的唯一行，从而保证了正确性。
