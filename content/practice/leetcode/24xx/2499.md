[LeetCode 问题 2499](https://leetcode.com/problems/minimum-total-cost-to-make-arrays-unequal/)

 **难度：** 🔴难
 **主题：** 数组、哈希表、贪心、计数

 ## 解决方案

 ## 问题理解

 给你两个数组，`nums1`和`nums2`, 两者的长度`n`。 您只能在以下位置执行操作`nums1`。 在一次操作中，您可以交换任意两个索引`nums1`，该操作的成本是交换中涉及的两个指数的总和。 

目标是重新排列`nums1`这样对于每个索引`i`，条件：```
nums1[i] != nums2[i]
```确实如此。 

在所有可能的有效重新安排中，您必须计算最小总交换成本。 如果不存在有效的重排，则返回`-1`。 

重要的细节是交换仅发生在内部`nums1`。 数组`nums2`永远不会改变。 

限制条件很大：```
1 <= n <= 100000
```这立即排除了对所有交换状态的强力排列生成或图搜索。 任何可接受的解决方案都必须在近似线性时间内运行。 

最重要的观察结果是，只有满足以下条件的索引：```
nums1[i] == nums2[i]
```有问题。 这些位置已经违反了要求，必须予以修复。 

另一个微妙之处是，某些值可能会在有问题的位置中频繁出现。 如果一个值占据太多冲突位置，则可能无法重新排列数组而不在其他地方产生另一个冲突。 

一些边缘情况尤其重要：

 - 已经满足条件的数组应该返回`0`。 
- 所有值都相同的数组可能是不可能的。 
- 一个值主导冲突位置的情况需要额外的辅助索引。 
- 非常小的数组，尤其是大小`1`，很容易变得不可能。 

## 方法

 ### 蛮力方法

 暴力解决方案将尝试生成所有可能的重新排列`nums1`可通过交换获得并检查结果数组是否满足：```
nums1[i] != nums2[i]
```对于每个索引。 

对于每个有效的排列，我们可以计算将原始数组转换为该排列所需的最小交换成本。 

这种方法在理论上是正确的，因为它探索了每种可能的最终配置。 然而，排列的数量呈阶乘增长：```
O(n!)
```即使对于相对较小的`n`，这在计算上变得不可能。 由于约束允许最多`100000`要素，蛮力是完全行不通的。 

### 最佳解决方案背后的关键见解

 关键的观察是我们只关心以下索引：```
nums1[i] == nums2[i]
```这些指数已经失效，必须参与掉期。 

假设我们将所有此类指数收集到一组“坏头寸”中。 如果我们仔细地在这些不好的立场之间交换价值观，我们通常可以解决所有冲突。 

然而，当一个值在不良位置中出现过于频繁时，就会出现另一个问题。 让：

-`totalBad`= 不良位置的数量
 -`maxFreq`= 不良头寸中任何值的最高频率

 如果：```
maxFreq * 2 > totalBad
```那么主导价值就不能安全地只分配在不好的位置上。 我们必须从坏集合之外招募额外的索引。 

这些额外的索引必须满足：```
nums1[i] != nums2[i]
```已经，而且：```
nums1[i] != dominantValue
nums2[i] != dominantValue
```这样他们就可以安全地吸收多余的主导事件。 

贪心策略是始终使用尽可能小的索引，因为交换成本直接取决于索引总和。

 ## 算法演练

 ### 第 1 步：识别冲突索引

 遍历数组并收集每个索引`i`在哪里：```
nums1[i] == nums2[i]
```这些是目前违反要求的职位。 

对于每个这样的索引：

 - 将其索引添加到总成本中。 
- 计算其值的频率。 
- 跟踪哪个值出现最频繁。 

我们维持：

 -`total_swaps_needed`, 冲突索引的数量
 -`cost`，初始化为冲突索引的总和
 -`frequency[value]`-`dominant_value`-`dominant_count`### 步骤2：检查主导值是否有问题

 如果主导值在冲突位置中出现太多次，则仅在冲突集中进行交换仍可能会留下冲突。 

具体来说，如果：```
dominant_count * 2 > total_swaps_needed
```那么我们需要额外的辅助索引。 

所需的附加索引数量为：```
required = dominant_count * 2 - total_swaps_needed
```### 步骤 3：查找辅助索引

 再次遍历所有索引。 

我们希望索引满足：```
nums1[i] != nums2[i]
nums1[i] != dominant_value
nums2[i] != dominant_value
```这些指数已经有效，并且双方都不包含主导值。 他们可以安全地参与互换。 

对于每个辅助索引：

 - 将其索引添加到总成本中
 - 减少`required`我们贪婪地按升序排列索引，从而最小化总成本。 

### 步骤 4：验证可行性

 如果扫描完所有索引后：```
required > 0
```那么就不可能消除所有的冲突。 

返回`-1`。 

否则，返回累计成本。 

### 为什么它有效

 该算法之所以有效，是因为每个冲突索引都必须参与至少一次交换。 因此，它们的指数必须对最终成本有所贡献。 

当一个值在冲突集合中占主导地位时，由于鸽子约束，仅在该集合内部重新排列就变得不可能。 在数学上需要额外的辅助索引来分离重复的主导值。 

使用最小有效辅助索引的贪婪选择可以最大限度地减少额外成本，同时保持正确性。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class Solution:
    def minimumTotalCost(self, nums1: List[int], nums2: List[int]) -> int:
        frequency = defaultdict(int)

        total_conflicts = 0
        total_cost = 0

        dominant_value = -1
        dominant_count = 0

        n = len(nums1)

        for i in range(n):
            if nums1[i] == nums2[i]:
                value = nums1[i]

                total_conflicts += 1
                total_cost += i

                frequency[value] += 1

                if frequency[value] > dominant_count:
                    dominant_count = frequency[value]
                    dominant_value = value

        required = dominant_count * 2 - total_conflicts

        for i in range(n):
            if required <= 0:
                break

            if nums1[i] != nums2[i]:
                if nums1[i] != dominant_value and nums2[i] != dominant_value:
                    total_cost += i
                    required -= 1

        if required > 0:
            return -1

        return total_cost
```实现首先扫描所有索引并识别冲突`nums1[i] == nums2[i]`。 每个冲突索引最终都必须参与交换，因此其索引会立即添加到总成本中。 

同时，我们维护出现在冲突位置的值的频率图。 这使我们能够确定主导价值，即冲突中最常出现的价值。 

第一次通过后，我们计算需要多少个额外的辅助索引。 如果主导值不太频繁，则不需要额外的工作。 

如果辅助索引是必要的，则第二遍搜索已经满足不等式条件并且两边不包含主导值的索引。 这些指数安全地吸收了过量的主要事件。 

最后，如果找不到足够的辅助索引，则配置不可能，我们返回`-1`。 

## 解决方案```go
package main

func minimumTotalCost(nums1 []int, nums2 []int) int64 {
	frequency := make(map[int]int)

	totalConflicts := 0
	var totalCost int64 = 0

	dominantValue := -1
	dominantCount := 0

	n := len(nums1)

	for i := 0; i < n; i++ {
		if nums1[i] == nums2[i] {
			value := nums1[i]

			totalConflicts++
			totalCost += int64(i)

			frequency[value]++

			if frequency[value] > dominantCount {
				dominantCount = frequency[value]
				dominantValue = value
			}
		}
	}

	required := dominantCount*2 - totalConflicts

	for i := 0; i < n && required > 0; i++ {
		if nums1[i] != nums2[i] &&
			nums1[i] != dominantValue &&
			nums2[i] != dominantValue {

			totalCost += int64(i)
			required--
		}
	}

	if required > 0 {
		return -1
	}

	return totalCost
}
```Go 实现遵循与 Python 解决方案相同的逻辑。 一个`map[int]int`取代Python的`defaultdict`。 

一个重要的区别是返回类型是`int64`，因为索引之和可能超出 32 位整数的范围`n`很大。 

算法本身保持不变。

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 对阵列进行两次线性扫描 |
 | 空间| O(n) | 频率哈希图最多可以存储 n 个值 |

 ## 边缘情况

 当数组已经满足要求时，就会出现一种重要的边缘情况。 在这种情况下，不存在冲突的指数，因此不需要互换。 有缺陷的实现可能仍会尝试不必要的处理或产生非零答案。 此实现正确返回`0`因为初始冲突计数仍然为零。 

当一个值在冲突位置上占主导地位时，就会发生另一种关键的边缘情况。 例如：```
nums1 = [2,2,2]
nums2 = [2,2,2]
```即使在任意交换之后，每个位置仍然包含`2`，使问题变得不可能。 该算法通过优势公式来检测这一点：```
dominant_count * 2 > total_conflicts
```并正确返回`-1`当辅助索引不足时。 

第三种微妙的边缘情况涉及辅助索引选择。 辅助索引不得包含任一数组中的主导值。 否则，添加该索引实际上不会减少支配问题。 实施仔细检查：```
nums1[i] != dominant_value
nums2[i] != dominant_value
```在接受辅助索引之前，防止无效交换并确保正确性。
