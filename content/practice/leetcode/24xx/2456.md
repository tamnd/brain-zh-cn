[LeetCode 问题 2456](https://leetcode.com/problems/most-popular-video-creator/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、字符串、排序、堆（优先级队列）

 ## 解决方案

 ## 问题理解

 该问题给了我们三个并行数组：

 -`creators[i]`代表着创造者`i`th video
 -`ids[i]`代表视频ID`i`第一个视频
 -`views[i]`代表观看次数`i`第一个视频

 每个索引对应一个视频。 多个视频可以属于同一创作者，不同的视频甚至可以共享相同的 ID。 不保证 ID 是唯一的。 

创作者的受欢迎程度定义为其所有视频的观看次数总和。 我们必须确定哪一位或哪些创作者的总受欢迎程度最高。 

对于每个最受欢迎的创作者，我们还需要确定他们观看次数最多的视频：

 - 选择观看次数最多的视频
 - 如果多个视频具有相同的最高观看次数，请选择字典顺序最小的 ID

 最终答案是一个对的列表：```
[creator_name, most_popular_video_id]
```返回对的顺序并不重要。 

约束条件很重要：

 -`n`可以大到`10^5`- 二次解太慢
 - 我们需要接近线性时间的东西
 - 哈希映射是一个自然的选择，因为我们需要按创作者有效地对视频进行分组

 有几个重要的边缘情况需要记住：

 - 多个创作者可以并列以获得最大人气
 - 同一创作者的多个视频可以并列获得最大观看次数
 - 必须正确处理词典比较
 - 视频可能有重复的 ID
 - 观看次数可能为零
 - 一个创作者只能有一个视频

 幼稚的实现很容易在打破平局逻辑上失败，特别是当多个视频具有相同的观看次数时。 

## 方法

 ### 蛮力方法

 强力解决方案将独立处理每个创建者。 

对于每一位独特的创作者，我们可以：

 1. 扫描整个输入以计算其总受欢迎程度
 2. 再次扫描整个输入以查找观看次数最多的视频
 3.追踪全球最大人气
 4. 构建最终结果

 这种方法是正确的，因为它明确检查每个创作者的所有视频。 然而，它的效率很低，因为重复的全阵列扫描会导致过多的工作。 

如果有`k`独特的创作者和`n`视频，复杂度大约变为`O(k * n)`。 在最坏的情况下，每个视频都属于不同的创作者，所以`k = n`， 导致`O(n^2)`时间复杂度。 

和`n = 10^5`，这太慢了。 

### 最佳方法

 关键的见解是可以在一次遍历中收集所有必需的信息。 

对于每一个创作者，我们需要维护：

 - 总人气
 - 最高的个人视频观看次数
 - 对应最佳视频ID

 哈希映射允许我们在遍历数组时有效地更新所有这些信息。 

遍历过程中：

 - 将当前观看次数添加到创作者的总受欢迎度中
 - 将当前视频与创作者的最佳视频进行比较
 - 在以下情况下更新最佳视频：

 - 当前视频有更多观看次数，或者
 - 当前视频具有相同的观看次数，但按字典顺序排列的 ID 较小

 处理完所有视频后，我们对存储在哈希图中的创作者执行另一次遍历，以确定哪些创作者具有最大的受欢迎程度。 

这给了我们线性时间复杂度。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(n) | 重复扫描每个创建者的数组 |
 | 最佳 | O(n) | O(n) | 使用哈希映射的单遍聚合 |

 ## 算法演练

 1. 创建一个哈希图来存储每个创建者的信息。 

对于每一位创作者，我们需要：

 - 总人气
 - 最高视频观看次数
 - 最佳视频ID

 从概念上讲：```
creator -> [total_views, max_video_views, best_video_id]
```2. 遍历所有视频一次。 

对于每个索引`i`：

- 读：

-`creator = creators[i]`-`video_id = ids[i]`-`view_count = views[i]`3.更新创作者总人气。 

添加`view_count`到创建者的累计总数。 
4.更新创作者最佳视频。 

将当前视频与存储的最佳视频进行比较：

 - 如果当前观看次数较大，则替换最佳视频
 - 如果观看次数相等且当前 ID 按字典顺序较小，则替换最佳视频

 这保证了正确的平局打破。 
5.追踪全球最大人气。 

在更新创作者总数的同时，保持迄今为止最大的人气。 
6. 构建最终答案。 

遍历哈希图中的所有创建者：

 - 如果创作者的受欢迎度等于全球最高值：

 - 添加`[creator, best_video_id]`到结果
 7. 返回结果列表。 

### 为什么它有效

 该算法之所以有效，是因为每个创建者的统计数据在遍历过程中都会一致更新。 

任何时刻：

 - 存储的总受欢迎程度等于该创作者所有已处理视频的总和
 - 存储的最佳视频始终满足：

 - 处理后的视频的最大观看次数
 - 绑定视频中按词典顺序最小的 ID

 完整遍历后，对于每个创建者来说，存储的信息都是完整且正确的。 因此，选择最受欢迎的创作者会产生正确的最终答案。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class Solution:
    def mostPopularCreator(
        self,
        creators: List[str],
        ids: List[str],
        views: List[int]
    ) -> List[List[str]]:
        
        creator_data = {}
        max_popularity = 0

        for creator, video_id, view_count in zip(creators, ids, views):

            if creator not in creator_data:
                creator_data[creator] = [
                    0,              # total popularity
                    view_count,     # max video views
                    video_id        # best video id
                ]

            creator_data[creator][0] += view_count

            current_max_views = creator_data[creator][1]
            current_best_id = creator_data[creator][2]

            if (
                view_count > current_max_views or
                (
                    view_count == current_max_views and
                    video_id < current_best_id
                )
            ):
                creator_data[creator][1] = view_count
                creator_data[creator][2] = video_id

            max_popularity = max(
                max_popularity,
                creator_data[creator][0]
            )

        result = []

        for creator, data in creator_data.items():
            total_views, _, best_video_id = data

            if total_views == max_popularity:
                result.append([creator, best_video_id])

        return result
```该实现使用名为的字典`creator_data`汇总有关每个创建者的所有信息。 

每个创建者存储三个值：

 - 总人气
 - 最大视频观看次数
 - 最佳视频ID

 主循环只处理每个视频一次。 在这次遍历过程中：

 - 人气总数已更新
 - 使用平局决胜规则维持最佳视频选择
 - 全球最大人气逐步更新

 字典比较是使用 Python 字符串比较自然处理的。 由于Python默认按字典顺序比较字符串，因此条件：```python
video_id < current_best_id
```正确落实问题要求。 

最后，第二个循环过滤流行度等于全局最大值的创作者并构建结果列表。 

## 解决方案```go
func mostPopularCreator(creators []string, ids []string, views []int) [][]string {

	type CreatorInfo struct {
		totalViews int64
		maxViews   int
		bestID     string
	}

	creatorData := make(map[string]*CreatorInfo)
	var maxPopularity int64 = 0

	for i := 0; i < len(creators); i++ {

		creator := creators[i]
		videoID := ids[i]
		viewCount := views[i]

		if _, exists := creatorData[creator]; !exists {
			creatorData[creator] = &CreatorInfo{
				totalViews: 0,
				maxViews:   viewCount,
				bestID:     videoID,
			}
		}

		info := creatorData[creator]

		info.totalViews += int64(viewCount)

		if viewCount > info.maxViews ||
			(viewCount == info.maxViews && videoID < info.bestID) {

			info.maxViews = viewCount
			info.bestID = videoID
		}

		if info.totalViews > maxPopularity {
			maxPopularity = info.totalViews
		}
	}

	result := [][]string{}

	for creator, info := range creatorData {
		if info.totalViews == maxPopularity {
			result = append(result, []string{
				creator,
				info.bestID,
			})
		}
	}

	return result
}
```Go 实现遵循与 Python 解决方案相同的逻辑，但使用结构体来存储创建者信息。 

One important Go-specific detail is the use of`int64`以获得总人气。 虽然个人观点符合`int`，总和可能超出标准 32 位整数限制，因为：```go
10^5 videos * 10^5 views = 10^10
```使用`int64`防止溢出问题。 

结果切片被初始化为空切片而不是`nil`，这对于 LeetCode 提交来说是完全可以接受的。

 ## 边缘情况

 ### 多个创作者同等人气

 一个常见的错误是仅返回一位最受欢迎的创作者。 该问题明确要求返回所有与最高受欢迎度相关的创作者。 

例如：```
alice -> 10 views
bob -> 10 views
```两位创作者都必须出现在输出中。 该实现通过首先计算全球最大流行度，然后收集与其流行度匹配的每个创建者来处理此问题。 

### 具有相同最大观看次数的多个视频

 当创作者拥有多个与最高观看次数相关的视频时，就会出现另一种微妙的边缘情况。 

例如：```
IDs = ["zzz", "aaa"]
Views = [5, 5]
```正确答案是`"aaa"`因为它按字典顺序更小。 

仅更新严格较大视图的幼稚实现会错误地保留`"zzz"`。 该解决方案通过字典顺序比较显式地处理平等视图平局打破。 

### 重复的视频 ID

 问题表明 ID 不是唯一的。 两个不同的视频可能共享相同的 ID。 

例如：```
ids = ["same", "same"]
views = [3, 10]
```有缺陷的实现可能会假设 ID 唯一标识视频并意外覆盖信息。 

此解决方案从不使用 ID 作为哈希映射键。 ID 纯粹被视为与视频关联的字符串，因此重复的 ID 可以自然且正确地处理。
