[LeetCode 1986 问题](https://leetcode.com/problems/minimum-number-of-work-sessions-to-finish-the-tasks/)

 **难度：** 🟡 中等
 **主题：** 数组、动态规划、回溯、位操作、位掩码

 ## 解决方案

 ## 问题理解

 这个问题要求我们将一组任务安排到最少数量的工作会话中。 每个任务都有固定的持续时间，每个工作会话都有最大允许长度，`sessionTime`。 

一个任务不能拆分到多个会话中。 一旦任务在会话内开始，它就必须在同一会话内完全完成。 然而，任务可以按任何顺序执行，这意味着我们可以自由地重新排列它们以实现更好的打包策略。 

输入包括：

 -`tasks`，一个数组，其中`tasks[i]`是持续时间`i-th`任务
-`sessionTime`，单个会话中允许的最大小时数

 输出是一个整数，表示完成所有任务所需的最小会话数。 

约束在这里非常重要：

 -`n <= 14`-`sessionTime <= 15`的小值`n`强烈建议涉及子集或位掩码的指数算法是可以接受的。 实际上，`2^14 = 16384`，对于子集的动态规划来说足够小。 

一些边缘情况值得立即识别。 

如果所有任务都适合一个会话，那么答案很简单`1`。 如果每个任务完全等于`sessionTime`，那么每个任务都需要自己的会话。 另一个重要的情况是当许多小任务可以以不同的方式组合时，因为贪婪的打包策略可能无法找到真正的最优值。 

例如：```
tasks = [1,2,3,4]
sessionTime = 5
```天真的贪婪策略可能会导致`4`独自一人，那么`3+2`， 然后`1`，使用 3 个会话。 但最优的安排是`4+1`和`3+2`，只需要 2 个会话。 

这意味着我们需要全局最优策略而不是局部贪婪选择。 

## 方法

 ### 蛮力方法

 强力解决方案将尝试所有可能的任务顺序并模拟将任务放入会话中。 由于任务可以按任意顺序出现，因此有`n!`排列。 

对于每个订单，我们可以贪婪地将任务打包到会话中并计算需要多少个会话。 然后我们将在所有排列中取最小值。 

这种方法是正确的，因为它探索了任务的每一种可能的安排。 最终，它会发现最优的调度。 

然而，时间复杂度太大了。 即使是为了`n = 14`，排列数为：```
14! ≈ 87 billion
```这是完全不可行的。 

我们需要一种更有效的方法来表示状态并避免重新计算等效子问题。 

### 关键见解

 重要的观察结果是会话中任务的实际顺序并不重要。 重要的只是：

 1. 哪些任务已经完成
 2.当前会话还剩多少空间

 这自然会导致使用位掩码的动态编程。 

位掩码可以表示一组已完成的任务：

 - 位`i = 1`意味着任务`i`已经完成
 - 位`i = 0`意味着任务`i`尚未完成

 自从`n <= 14`，任务的每个子集都可以使用来自的整数表示`0`到`(1 << n) - 1`。 

我们不仅跟踪最小会话数，还跟踪当前会话的剩余时间。 这一点至关重要，因为会话次数相同的两个州未来的潜力可能不同。 

例如：```
2 sessions used, 4 hours remaining
```优于：```
2 sessions used, 1 hour remaining
```因为第一个状态可以适应更多未来的任务。 

因此，我们使用动态规划，其中每个子集存储：```
(sessions_used, remaining_time)
```我们总是更喜欢：

 - 更少的会话
 - 如果会话平局，则剩余时间更长

 这给出了对于约束足够有效的最佳指数时间解决方案。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n! × n) | O(n! × n) | O(n) | 尝试每个任务排序 |
 | 最佳位掩码 DP | O(n × 2^n) | O(n × 2^n) | O(2^n) | O(2^n) | 子集上的动态规划|

 ## 算法演练

 ### 步骤 1：使用位掩码表示任务子集

 我们使用整数掩码，其中每一位代表任务是否已完成。 

例如：```
tasks = [1,2,3]
mask = 101₂
```意味着任务`0`和`2`已完成。 

最终的目标状态是：```
(1 << n) - 1
```所有位均已设置的位置。 

### 步骤 2：定义 DP 状态

 对于每个子集`mask`，我们存储：```
dp[mask] = (sessions_used, remaining_time)
```这代表了准确完成任务的最佳方式`mask`。 

我们按字典顺序比较状态：

 1.会话数越少越好
 2. 如果场数平局，剩余时间越大越好

 第二个条件很重要，因为更多的剩余时间可以为未来的任务提供更大的灵活性。 

### 步骤 3：初始化基本情况

 最初，没有任务完成：```
mask = 0
```我们从一个可用的空会话开始：```
dp[0] = (1, sessionTime)
```这意味着：

 - 我们目前正在使用 1 个会话
 - 整个会话仍未使用

 ### 第 4 步：过渡到新状态

 对于每个当前子集`mask`，我们尝试添加每个未完成的任务。 

认为：```
task_time = tasks[i]
```有两种可能性。 

#### 情况 1：任务适合当前会话

 如果：```
remaining_time >= task_time
```然后我们将任务放入当前会话中：```
new_state = (
    sessions_used,
    remaining_time - task_time
)
```#### 情况 2：任务不适合

 否则，我们必须开始一个新会话：```
new_state = (
    sessions_used + 1,
    sessionTime - task_time
)
```我们更新目标子集：```
new_mask = mask | (1 << i)
```如果新状态比当前存储的状态更好，我们将替换它。 

### 步骤 5：继续，直到处理完所有子集

 我们迭代每个掩码：```
0 to (1 << n) - 1
```并处理所有转换。 

###第6步：返回最终答案

 答案是：```
dp[(1 << n) - 1][0]
```这是完成所有任务所需的最少会话数。 

### 为什么它有效

 DP 探索已完成任务的每个可能的子集以及扩展这些子集的每个有效方法。 由于每次转换要么将任务放入当前会话中，要么启动新会话，因此会表示每个合法的计划。 

DP 始终根据以下条件保持每个子集的最佳状态：

 1. 最少会议次数
 2. 最大剩余时间

 因此，不会丢失更好的未来时间表，并且保证完整掩模的最终状态是最佳的。 

## Python 解决方案```python
from typing import List

class Solution:
    def minSessions(self, tasks: List[int], sessionTime: int) -> int:
        n = len(tasks)
        total_masks = 1 << n

        # dp[mask] = (sessions_used, remaining_time)
        dp = [(float("inf"), -1)] * total_masks
        dp[0] = (1, sessionTime)

        for mask in range(total_masks):
            sessions_used, remaining_time = dp[mask]

            for i in range(n):
                if mask & (1 << i):
                    continue

                task_time = tasks[i]
                next_mask = mask | (1 << i)

                # Task fits in current session
                if remaining_time >= task_time:
                    candidate = (
                        sessions_used,
                        remaining_time - task_time
                    )
                else:
                    # Start new session
                    candidate = (
                        sessions_used + 1,
                        sessionTime - task_time
                    )

                current = dp[next_mask]

                # Better if fewer sessions,
                # or same sessions with more remaining time
                if (
                    candidate[0] < current[0]
                    or (
                        candidate[0] == current[0]
                        and candidate[1] > current[1]
                    )
                ):
                    dp[next_mask] = candidate

        full_mask = total_masks - 1
        return dp[full_mask][0]
```实现首先计算子集的总数：```python
1 << n
```每个子集都表示为位掩码。 

这`dp`数组存储元组：```python
(sessions_used, remaining_time)
```最初：```python
dp[0] = (1, sessionTime)
```因为还没有完成任何任务，并且第一节课是完全免费的。 

外循环迭代所有子集。 对于每个子集，内部循环尝试添加每个未完成的任务。 

条件：```python
if mask & (1 << i):
```检查是否有任务`i`已经完成了。 

添加任务时，算法会确定该任务是否适合当前会话。 如果是这样，剩余时间就会减少。 否则，将开始一个新会话。 

更新逻辑确保 DP 始终存储每个子集的最佳状态。 较少的会话始终是首选，如果会话计数平局，则保留剩余容量较多的状态。 

最后，从所有任务完成的子集中检索答案。 

## 解决方案```go
package main

import "math"

func minSessions(tasks []int, sessionTime int) int {
	n := len(tasks)
	totalMasks := 1 << n

	type State struct {
		sessions int
		remaining int
	}

	dp := make([]State, totalMasks)

	for i := 0; i < totalMasks; i++ {
		dp[i] = State{
			sessions: math.MaxInt32,
			remaining: -1,
		}
	}

	dp[0] = State{
		sessions: 1,
		remaining: sessionTime,
	}

	for mask := 0; mask < totalMasks; mask++ {
		current := dp[mask]

		for i := 0; i < n; i++ {
			if (mask & (1 << i)) != 0 {
				continue
			}

			taskTime := tasks[i]
			nextMask := mask | (1 << i)

			var candidate State

			if current.remaining >= taskTime {
				candidate = State{
					sessions: current.sessions,
					remaining: current.remaining - taskTime,
				}
			} else {
				candidate = State{
					sessions: current.sessions + 1,
					remaining: sessionTime - taskTime,
				}
			}

			best := dp[nextMask]

			if candidate.sessions < best.sessions ||
				(candidate.sessions == best.sessions &&
					candidate.remaining > best.remaining) {
				dp[nextMask] = candidate
			}
		}
	}

	fullMask := totalMasks - 1
	return dp[fullMask].sessions
}
```Go 实现遵循与 Python 版本完全相同的逻辑。 由于 Go 不直接支持元组比较，因此需要自定义`State`结构体用于存储：```go
sessions
remaining
```DP 数组使用非常大的会话计数进行初始化：```go
math.MaxInt32
```使用 Go 切片代替 Python 列表，但子集转换逻辑保持相同。 

不需要对整数溢出进行特殊处理，因为在问题约束下所有值都非常小。

 ## 边缘情况

 当所有任务都已适合单个会话时，就会出现一种重要的边缘情况。 在这种情况下，最佳答案应该是`1`。 一些不正确的实现可能会不必要地创建额外的会话，因为它们错误地初始化了 DP 或无法正确地重用剩余容量。 此实现可以自然地处理这种情况，因为只要存在足够的剩余时间，任务就会继续添加到当前会话中。 

另一个重要的边缘情况是每个任务完全相等`sessionTime`。 由于没有两个任务可以共享一个会话，因此答案必须等于任务数。 当实现意外地允许会话超出限制或错误地合并任务时，经常会出现错误。 这里的转换逻辑严格检查：```
remaining_time >= task_time
```在将任务放入当前会话之前。 

第三种微妙的边缘情况涉及会话数量相同但剩余容量不同的状态。 例如：```
(2 sessions, 4 remaining)
```严格优于：```
(2 sessions, 1 remaining)
```因为未来的任务更容易安排。 如果实现仅存储最小会话计数，则它可能会放弃未来更好的可能性并产生不正确的结果。 当会话计数平局时，该解决方案正确地保持具有较大剩余容量的状态。 

最后一个重要的边缘情况是最大约束大小：```
n = 14
```由于重复的子问题，没有记忆的简单递归搜索可能会变得非常慢。 位掩码 DP 通过精确地求解每个子集一次来避免这种情况，即使在上限下也能确保高效的性能。
