[LeetCode 1949 题](https://leetcode.com/problems/strong-friendship/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 问题给了我们一个名为`Friendship`，其中每一行代表两个用户之间的友谊关系。 每个友谊仅存储一次，因为该问题保证`user1_id < user2_id`。 

我们被要求识别所有友谊被认为“强”的用户对。 用户之间的友谊`x`和`y`如果他们有至少三个共同的朋友，那么他们就很强大。 

共同的朋友是指与双方都直接有联系的用户`x`和`y`。 

例如，如果：

 - 用户 1 与 3、4、5 和 6 是朋友
 - 用户 2 也是 3、4、5 和 6 的朋友

 那么用户1和2有四个共同的朋友，所以他们的友谊很牢固。 

输出必须包含：

 -`user1_id`-`user2_id`-`common_friend`，这是共同好友的数量

 结果应仅包含表中已存在的有效友谊。 这很重要，因为两个用户可能有许多共同的朋友，但他们自己却没有直接联系。 

输入保证：

 - 每对友谊都是独一无二的
 -`user1_id < user2_id`- 友谊是无方向的关系

 这意味着友谊`(1,2)`是一样的`(2,1)`，即使只存储一个方向。 

主要挑战是有效地计算现有友谊对之间的共同朋友。 

简单的实现可能会变得非常昂贵，因为检查每对可能的用户并重复比较朋友列表将涉及许多冗余计算。 

重要的边缘情况包括：

 - 与恰好三个共同朋友的友谊，这些必须包括在内
 - 没有共同好友的用户
 - 稀疏图表，大多数用户的友谊很少
 - 许多用户相互连接的密集图表
 - 由于友谊的无向性而导致的重复计数

 该问题保证不存在重复的友谊行，从而简化了对称关系的处理。 

## 方法

 ### 蛮力方法

 蛮力方法是单独检查每个友谊对并显式计算他们的朋友列表的交集。 

首先，我们构建一个邻接列表，其中每个用户映射到他们的所有朋友。 

那么，对于每一份友谊`(u, v)`：

 1. 检索所有好友`u`2. 检索所有好友`v`3. 统计两组中出现的用户数量
 4. 如果计数至少为 3，则将该对包含在结果中

 这是有效的，因为牢固友谊的定义完全取决于友谊图中共享邻居的数量。 

然而，当用户有很多朋友时，这种方法可能会变得昂贵。 如果两个用户各自拥有大量好友列表，则为每个好友对重复地交叉大集合会导致大量开销。 

### 最佳方法

 关键的见解是可以通过自加入直接生成共同的友谊。 

假设用户`f`是双方共同的朋友`u`和`v`。 

那么必然存在：

 - 友谊`(u, f)`- 友谊`(v, f)`如果我们枚举所有此类组合，我们可以直接生成共享共同好友的用户对。 

这将问题转化为计算每个用户对作为共享连接出现的次数。 

在 SQL 中，这个问题自然可以通过友谊表上的自连接来解决。 

该过程变为：

 1. 将友谊扩展为无向的表征
 2. 在普通好友上加入与自身的好友关系表
 3. 生成拥有相同好友的用户对
 4. 统计出现次数
 5. 仅保留数量至少为 3 的对
 6. 确保两人本身就是现有的友谊

 这避免了重复地相交大型集合并有效地利用 SQL 的分组和聚合。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(F × D) 到 O(F × D²) | O(F) | 反复交集好友列表 |
 | 最佳 | 最坏情况 | O(F²) O(F) | 有效地使用连接和聚合 |

 这里：

-`F`= 好友数量
 -`D`= 用户的平均程度

 ## 算法演练

 1. 首先，将友谊表转换为无向表示。 

由于该表只存储`(u, v)`在哪里`u < v`，我们创建两个方向：

 -`(u, v)`-`(v, u)`这使得统一查找用户的所有好友变得容易。 
2. 在无向友谊表上执行自连接。 

认为：

-`(a.user_id, a.friend_id)`-`(b.user_id, b.friend_id)`如果`a.friend_id = b.friend_id`，那么两个用户共享同一个共同的朋友。 
3. 确保用户对的顺序一致。 

我们强制执行：```
a.user_id < b.user_id
```这可以防止重复计数，例如两者`(1,2)`和`(2,1)`。 
4. 按用户对分组。 

自连接中的每个匹配行都对应一个共享好友。 

通过分组：```
GROUP BY a.user_id, b.user_id
```我们可以数一下共同的朋友有多少。 
5. 只与至少三个共同的朋友结对。 

这是使用以下方法完成的：```
HAVING COUNT(*) >= 3
```6. 验证两人本身是真正的友谊。 

这个问题需要牢固的友谊，而不仅仅是与许多共同的朋友结对。 

因此，我们连接回到原始的友谊表以确保该对存在。 

### 为什么它有效

 该算法之所以有效，是因为每个共同的朋友在自连接中都贡献了一个匹配的行。 

如果用户`u`和`v`两者都连接到用户`f`，然后连接会生成代表该共享朋友的一行。 

将所有这些行分组在一起给出了之间共同朋友的确切数量`u`和`v`。 

因为我们强制执行`u < v`，每对都只计算一次。 

最后，连接回原始友谊表可以保证我们只返回实际的友谊。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    f.user1_id,
    f.user2_id,
    COUNT(*) AS common_friend
FROM
(
    SELECT user1_id AS user_id, user2_id AS friend_id
    FROM Friendship

    UNION ALL

    SELECT user2_id AS user_id, user1_id AS friend_id
    FROM Friendship
) a
JOIN
(
    SELECT user1_id AS user_id, user2_id AS friend_id
    FROM Friendship

    UNION ALL

    SELECT user2_id AS user_id, user1_id AS friend_id
    FROM Friendship
) b
ON a.friend_id = b.friend_id
AND a.user_id < b.user_id
JOIN Friendship f
ON f.user1_id = a.user_id
AND f.user2_id = b.user_id
GROUP BY f.user1_id, f.user2_id
HAVING COUNT(*) >= 3;
```该解决方案首先构建友谊图的无向版本。 由于原始表仅存储每个友谊的一个方向，因此我们使用`UNION ALL`添加相反方向。 

之后，我们对共享好友标识符执行自加入。 这使我们能够生成拥有共同朋友的所有用户对。 

条件：```python
a.user_id < b.user_id
```确保每对仅出现一次。 

接下来，我们将生成的用户对连接回原始友谊表。 此步骤保证该对本身是直接连接的。 

最后，我们按友谊对进行分组，并计算存在多少个共享朋友。 这`HAVING`子句过滤掉共同朋友少于三个的配对。

 ## 边缘情况

 ### 正好三个共同的朋友

 一个非常常见的错误是使用`>`而不是`>=`。 

如果两个用户恰好有三个共同的朋友，那么友谊仍然必须被认为是牢固的。 

该实现使用以下方式正确处理此问题：```
HAVING COUNT(*) >= 3
```### 没有直接友谊的共享朋友

 两个用户可能有许多共同的朋友，但实际上并没有直接联系。 

例如：

-`(1,3)`-`(2,3)`-`(1,4)`-`(2,4)`-`(1,5)`-`(2,5)`用户 1 和 2 有 3 个共同的朋友，但他们自己并不是朋友。 

连接回到原来的状态`Friendship`表可防止此类无效对出现在结果中。 

### 重复对生成

 因为友谊是无向的，天真的自我加入可能会产生以下两种情况：

 -`(1,2)`-`(2,1)`这将导致重复计数和重复输出行。 

该实现通过强制执行来避免这种情况：```
a.user_id < b.user_id
```这保证了每对都被处理一次。
