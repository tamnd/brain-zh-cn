 ## 解决方案

 ## 问题理解

 这个问题要求我们根据银行账户的月收入将其分为三个薪资类别，然后统计每个类别有多少个账户。 

输入是一个名为的数据库表`Accounts`。 每行包含两列：

 -`account_id`，唯一标识一个银行帐户
 -`income`，代表与该账户相关的月收入

 任务是生成一个包含三行的结果表，每一行对应于每个薪资类别：

 -`"Low Salary"`对于收入严格低于`20000`-`"Average Salary"`对于收入之间`20000`和`50000`, 包括
 -`"High Salary"`对于收入严格大于`50000`输出必须包含所有三个类别，即使没有帐户属于其中之一。 在这种情况下，该类别的计数必须是`0`。 

一个关键细节是类别边界并不都是对称的。 这`"Low Salary"`类别不包括`20000`，而`"Average Salary"`类别包括两者`20000`和`50000`。 相似地，`"High Salary"`排除`50000`。 这些边界条件的不正确处理是此问题中最常见的错误来源之一。 

该问题被归类为数据库问题，因此预期的解决方案是 SQL 而不是传统的算法实现。 挑战不在于计算复杂性，而在于正确地对记录进行分组和计数，同时确保所有三个类别都出现在结果中。 

一个重要的边缘情况发生时`Accounts`表是空的。 即便如此，结果仍然必须包括所有三个薪资类别，其计数为`0`。 另一个重要的边缘情况是所有帐户都属于一个类别。 该实现仍必须返回其他两个类别的行。 

## 方法

 ### 蛮力方法

 一种简单的方法是针对`Accounts`桌子。 

第一个查询对所有行进行计数`income < 20000`。 第二个查询计算行数，其中`income BETWEEN 20000 AND 50000`。 第三个查询计算行数，其中`income > 50000`。 

独立计算三个计数后，我们将它们组合在一起使用`UNION`语句产生最终结果表。 

这种方法很容易理解并保证正确性，因为每个类别都是根据其定义显式计算的。 然而，它扫描`Accounts`表三分开。 虽然这对于小型数据集来说是可以接受的，但对于较大的表来说效率很低，因为相同的数据会被重复处理。 

### 最佳方法

 更好的方法是仅扫描表一次。 

关键的观察结果是，每个账户都属于一个薪资类别。 我们可以使用一个方法对每一行进行分类，而不是运行三个独立的查询`CASE`表达式，按生成的类别进行分组，并计算每组中的行数。 

然而，一个平淡的`GROUP BY`解决方案引入了另一个问题。 如果某个类别没有匹配的客户，则该类别将从结果集中完全消失。 由于该问题明确要求所有三个类别都出现，因此我们需要一种机制来保证它们的存在。 

标准解决方案是创建一个包含所有三个类别的派生表，然后执行`LEFT JOIN`对照汇总计数。 这可以确保每个类别只出现一次，即使其计数为零。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(3N) | O(1) | O(1) | 分别扫描表格三次 |
 | 最佳| O(N) | O(1) | O(1) | 具有类别映射的单通道聚合 |

 ## 算法演练

 1. 创建一个包含三个所需薪资类别的虚拟表。 这保证了最终结果始终包含所有类别，即使某些类别的匹配帐户为零。 
2. 遍历`Accounts`表一次并使用`CASE`表达式：

 - 如果`income < 20000`，标记它`"Low Salary"`- 如果`income <= 50000`，标记它`"Average Salary"`- 否则，贴上标签`"High Salary"`3. 按类别对分类行进行分组，并统计每个组有多少个帐户。 
4. 执行`LEFT JOIN`预定义类别表和聚合计数之间的关系。 这可确保没有匹配项的类别仍出现在结果中。 
5. 使用`IFNULL`或者`COALESCE`将缺失的计数替换为`0`。 

### 为什么它有效

 该算法之所以有效，是因为每个帐户都恰好满足三个互斥的薪资条件之一。 这`CASE`表达式将每个帐户映射到其正确的类别，并且聚合正确地计算每个类别的帐户数量。 预定义的类别表保证所有必需的类别都存在于最终输出中，即使没有行与类别匹配。 

## Python 解决方案

 由于这是一个数据库问题，Python 部分演示了在 LeetCode 上提交的 SQL 查询。```python
# Write your MySQL query statement below

WITH categories AS (
    SELECT 'Low Salary' AS category
    UNION ALL
    SELECT 'Average Salary'
    UNION ALL
    SELECT 'High Salary'
),
salary_counts AS (
    SELECT
        CASE
            WHEN income < 20000 THEN 'Low Salary'
            WHEN income <= 50000 THEN 'Average Salary'
            ELSE 'High Salary'
        END AS category,
        COUNT(*) AS accounts_count
    FROM Accounts
    GROUP BY category
)

SELECT
    c.category,
    COALESCE(s.accounts_count, 0) AS accounts_count
FROM categories c
LEFT JOIN salary_counts s
ON c.category = s.category;
```该查询首先定义一个名为的公用表表达式`categories`。 这充当包含三个所需工资标签的固定查找表。 使用此表可确保最终结果始终包含所有类别。 

第二个公共表表达式，`salary_counts`，处理`Accounts`桌子。 这`CASE`表达式将每项收入准确地分类为一个类别。 分类后，查询按类别对行进行分组并计算每个组的计数。 

最终查询将预定义类别与聚合计数连接起来。 一个`LEFT JOIN`至关重要，因为没有匹配帐户的类别将会消失。`COALESCE`皈依者`NULL`值转化为`0`，满足问题要求。 

## 解决方案

 LeetCode数据库问题不需要提交Go代码，因为预期的解决语言是SQL。 但是，以下 Go 实现以编程方式演示了相同的逻辑。```go
package main

import "fmt"

type Account struct {
	AccountID int
	Income    int
}

type Result struct {
	Category     string
	AccountsCount int
}

func countSalaryCategories(accounts []Account) []Result {
	counts := map[string]int{
		"Low Salary":     0,
		"Average Salary": 0,
		"High Salary":    0,
	}

	for _, account := range accounts {
		if account.Income < 20000 {
			counts["Low Salary"]++
		} else if account.Income <= 50000 {
			counts["Average Salary"]++
		} else {
			counts["High Salary"]++
		}
	}

	return []Result{
		{"Low Salary", counts["Low Salary"]},
		{"Average Salary", counts["Average Salary"]},
		{"High Salary", counts["High Salary"]},
	}
}

func main() {
	accounts := []Account{
		{3, 108939},
		{2, 12747},
		{8, 87709},
		{6, 91796},
	}

	results := countSalaryCategories(accounts)

	for _, result := range results {
		fmt.Println(result)
	}
}
```Go 实现密切反映了 SQL 逻辑。 映射存储每个薪资类别的计数，初始化为零，以便所有类别始终存在。 使用条件语句对每个帐户进行分类，然后递增相应的计数器。 

Go 特有的一个细节是地图中所有类别的显式初始化。 与 SQL 连接不同`COALESCE`，Go要求我们在计数之前确保key存在。 整数溢出在这里不是一个问题，因为相对于 Go 的整数范围来说，约束很小。

 ## 边缘情况

 一个重要的边缘情况是空的`Accounts`桌子。 一个天真的`GROUP BY`查询根本不会返回任何行，因为没有要聚合的数据。 然而，该问题明确要求所有三个类别的计数都为零。 该实现通过创建预定义的类别表并使用`LEFT JOIN`。 

另一个关键的边缘情况涉及边界值，例如`20000`和`50000`。 这些值属于`"Average Salary"`因为范围是包含在内的。 不正确使用比较运算符，例如`<`而不是`<=`很容易对这些记录进行错误分类。 该实现仔细地使用了：

 -`income < 20000`-`income <= 50000`-`ELSE`这保证了正确的边界处理。 

当所有账户都属于同一类别时，就会出现第三种边缘情况。 例如，如果每项收入都大于`50000`，一个普通的分组查询只会返回`"High Salary"`。 该实现通过加入固定类别列表来避免此问题，确保其他类别仍然显示计数`0`。 

另一个微妙的边缘情况是重复的收入值。 多个账户可以共享相同的收入，但每个账户仍必须独立计算。 由于查询使用`COUNT(*)`，每一行都单独贡献，这保证了正确的行为，无论重复的收入值如何。
