[LeetCode 问题 1815](https://leetcode.com/problems/maximum-number-of-groups-getting-fresh-donuts/)

 **难度：** 🔴难
 **主题：** 数组、动态规划、位操作、记忆、位掩码

 ## 解决方案

 ## 问题理解

 这个问题要求我们通过选择最佳的群体排序来最大化“满意”的客户群体的数量。 

甜甜圈店生产的甜甜圈批量准确`batchSize`。 仅当前一批完全消耗完后，新批次才会开始。 如果该组中的第一个顾客收到了一批完全新鲜的甜甜圈，则该组被认为是快乐的。 

每组包含`groups[i]`顾客，每个顾客只吃一个甜甜圈。 由于必须连续为各组提供服务，因此一个组可能会留下影响下一组的剩余甜甜圈。 

关键的观察是，只有组大小模的余数`batchSize`很重要。 认为`batchSize = 5`:

 - 一组大小`10`恰好消耗了两批完整的产品，并且没有留下任何剩余物。 
- 一组大小`12`树叶`2`甜甜圈消耗到下一批。 
- 一组大小`7`行为与一群大小完全相同`2`关于剩菜。 

因此，我们不关心确切的组大小，而是只关心：```
groups[i] % batchSize
```目标是对组重新排序，以便在当前剩余金额为零时开始尽可能多的组。 

约束条件很重要：

 -`batchSize <= 9`-`groups.length <= 30`这些限制足够小以允许状态压缩动态编程。 由于批量大小很小，因此剩余类别的数量也很小，这使得记忆变得可行。 

一些边缘情况很重要：

 - 可整除的组`batchSize`他们总是很高兴，因为他们总是从一批新鲜的开始。 
- 具有互补余数的多个组可以完美组合。 
- 顺序很重要，所以贪婪的选择可能会失败。 
- 由于最多可以有 30 个组，因此无法进行强力排列生成。 

## 方法

 ### 蛮力方法

 直接的暴力解决方案将尝试所有可能的组排序。 

对于每个排列：

 1.模拟按顺序服务分组。 
2. 跟踪当前剩余计数模数`batchSize`。 
3. 计算当余数为零时有多少组开始。 

这是有效的，因为它明确地检查了每种可能的排列，从而保证了最佳答案。 

然而，其复杂性是灾难性的。 最多 30 个组，排列数为：```
30!
```这是完全不可行的。 

即使我们尝试修剪，搜索空间仍然太大。 

### 关键见解

 关键的观察是只有余数模`batchSize`很重要。 

我们不跟踪确切的组大小，而是计算属于每个剩余类别的组数量：```
remainder = group % batchSize
```例如，如果`batchSize = 4`，那么每个组都属于以下之一：```
0, 1, 2, 3
```现在问题变成：```
How do we arrange remainder categories to maximize the number of times
the running sum modulo batchSize becomes zero?
```因为`batchSize <= 9`，我们可以使用动态规划来记忆剩余余数组的计数。 

国家由以下部分组成：

 - 每个余数还剩下多少组
 - 当前累计余数

 在每一步中，我们都会选择要服务的下一个剩余组。 

这将不可能的排列问题转化为压缩状态上可管理的 DP 问题。

 ## 算法演练

 ### 第 1 步：将组转换为余数计数

 对于每个组：```
remainder = group % batchSize
```存储有多少组属于每个剩余类别。 

例如：```
batchSize = 3
groups = [1,2,3,4,5,6]

remainders:
1 % 3 = 1
2 % 3 = 2
3 % 3 = 0
4 % 3 = 1
5 % 3 = 2
6 % 3 = 0
```所以：```
count[0] = 2
count[1] = 2
count[2] = 2
```### 步骤 2：立即处理余数零

 任何余数为零的组总是从新开始。 

为什么？ 

因为它消耗了精确数量的批次并且不留下任何剩余物。 

所以我们立即添加：```
happy = count[0]
```这些群体不需要参加 DP。 

### 步骤 3：定义 DP 状态

 递归函数跟踪：

 - 每个余数的剩余计数
 - 当前剩余余额

 假设：```
current_remainder = 2
```这意味着当前批次已经消耗了 2 个甜甜圈。`batchSize`。 

如果下一组开始时：```
current_remainder == 0
```那么那个群体就会很快乐。 

### 步骤 4：尝试所有可能的下一个剩余部分

 对于每个余数`r`仍然有未使用的组：

 1. 使用一组余数`r`2. 更新新的余数：```
new_remainder = (current_remainder + r) % batchSize
```1. 递归地解决较小的问题

 如果`current_remainder == 0`，则所选组贡献一个快乐组。 

### 步骤 5：记忆状态

 许多递归路径都会导致相同的状态。 

例如：```
remaining counts = [0,2,1,0]
current remainder = 1
```可能会重复出现。 

记忆化避免了重新计算这些状态。 

### 第 6 步：返回最佳结果

 在所有可能的余数选择中，选择使快乐群体数量最大化的一个。 

## 为什么它有效

 DP 探索剩余组的每个有效排序，但它将等效配置压缩为相同的状态。 由于只有当前余数和剩余计数影响未来的行为，因此 DP 状态完全捕获所有相关信息。 

在每个状态下，算法都会考虑每个可能的下一个选择并获取最大结果。 因此，通过最优子结构，最终答案是全局最优的。 

## Python 解决方案```python
from typing import List
from functools import lru_cache

class Solution:
    def maxHappyGroups(self, batchSize: int, groups: List[int]) -> int:
        remainder_count = [0] * batchSize
        
        for group in groups:
            remainder_count[group % batchSize] += 1
        
        happy_groups = remainder_count[0]
        
        counts = tuple(remainder_count[1:])
        
        @lru_cache(None)
        def dfs(state: tuple, current_remainder: int) -> int:
            best = 0
            
            for remainder in range(1, batchSize):
                index = remainder - 1
                
                if state[index] == 0:
                    continue
                
                next_state = list(state)
                next_state[index] -= 1
                
                gained = 1 if current_remainder == 0 else 0
                
                best = max(
                    best,
                    gained + dfs(
                        tuple(next_state),
                        (current_remainder + remainder) % batchSize
                    )
                )
            
            return best
        
        return happy_groups + dfs(counts, 0)
```该实现首先计算有多少组属于每个剩余类别。 由于余数为零的组会自动满意，因此它们会直接添加到答案中。 

剩余的余数计数被转换为元组，以便它们可以用作记忆键的一部分。 

递归`dfs`函数表示从当前状态可以实现的额外快乐群体的最佳数量。 该函数尝试每个可用的剩余类别并递归地探索结果状态。 

记忆化至关重要，因为许多递归分支达到相同的配置。 使用`@lru_cache`确保每个状态只解决一次。 

最终答案结合：

 - 自动快乐余数为零的组
 - 最优DP结果

 ## 解决方案```go
package main

func maxHappyGroups(batchSize int, groups []int) int {
	remainderCount := make([]int, batchSize)

	for _, group := range groups {
		remainderCount[group%batchSize]++
	}

	happyGroups := remainderCount[0]

	type State struct {
		counts []int
		remain int
	}

	memo := make(map[string]int)

	encode := func(counts []int, remain int) string {
		key := ""

		for _, value := range counts {
			key += string(rune(value + 'A'))
		}

		key += "#"
		key += string(rune(remain + 'A'))

		return key
	}

	var dfs func([]int, int) int

	dfs = func(counts []int, currentRemain int) int {
		key := encode(counts, currentRemain)

		if value, exists := memo[key]; exists {
			return value
		}

		best := 0

		for remainder := 1; remainder < batchSize; remainder++ {
			index := remainder - 1

			if counts[index] == 0 {
				continue
			}

			counts[index]--

			gained := 0
			if currentRemain == 0 {
				gained = 1
			}

			candidate := gained + dfs(
				counts,
				(currentRemain+remainder)%batchSize,
			)

			if candidate > best {
				best = candidate
			}

			counts[index]++
		}

		memo[key] = best
		return best
	}

	initialCounts := make([]int, batchSize-1)

	for i := 1; i < batchSize; i++ {
		initialCounts[i-1] = remainderCount[i]
	}

	return happyGroups + dfs(initialCounts, 0)
}
```Go 解决方案遵循与 Python 实现相同的逻辑，但记忆化是使用映射手动实现的。 

由于切片不能直接用作映射键，因此 counts 数组被序列化为字符串表示形式。 DFS 就地改变计数切片，然后在递归后恢复它，这避免了重复的切片分配。 

Go 整数就足够了，因为答案永远不会超过组的数量。

 ## 边缘情况

 当每个组大小都可以被整除时，就会出现一个重要的边缘情况`batchSize`。 在这种情况下，每个组都会自动以新鲜批次开始，因为在为任何组提供服务后都没有剩余的食物。 有缺陷的实现可能仍然会不必要地通过 DP 发送这些组，从而增加运行时间和复杂性。 此实现通过在递归开始之前立即将所有余数为零的组计数为快乐来正确处理这种情况。 

另一个棘手的边缘情况是`batchSize = 1`。 由于每个数字模 1 都等于 0，所以每个组都很高兴。 某些实现意外地创建了无效的 DP 状态，因为不存在非零余数类别。 该解决方案自然地处理了这种情况，因为递归状态变为空并且 DFS 立即返回 0。 

第三个重要的边缘情况涉及许多组共享相同的余数。 例如：```
batchSize = 4
groups = [1,1,1,1]
```天真的贪婪方法可能会错误地假设每个新群体都能变得快乐。 实际上，累积的余数会在非零状态之间循环，并且只有一组可以重新开始。 记忆的 DP 正确评估所有可能的序列并避免计数过多。 

另一种微妙的情况发生在团体规模极大的情况下，例如`10^9`。 跟踪实际甜甜圈计数的简单实现可能会溢出或变得低效。 该解决方案仅存储：```
group % batchSize
```无论输入大小如何，这都使所有计算保持小而高效。
