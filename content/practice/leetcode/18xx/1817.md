[LeetCode 问题 1817](https://leetcode.com/problems/finding-the-users-active-minutes/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表

 ## 解决方案

 ## 问题理解

 此问题要求我们分析用户活动日志的集合，并确定有多少用户拥有特定数量的唯一活跃分钟数。 

每个日志条目表示为：```
[IDi, timei]
```在哪里：

-`IDi`是用户的ID
 -`timei`是该用户执行操作的分钟

 用户可以在同一分钟内执行多个操作，但同一分钟内重复的操作仅计入该用户的活跃分钟数一次。 

关键定义是用户活跃分钟数 (UAM)：

 > 用户的 UAM 是用户执行至少一项操作的不同分钟数。 

计算完每个用户的 UAM 后，我们必须构建一个长度的结果数组`k`。 

结果在概念上是 1 索引的：

 -`answer[1]`代表有多少用户正好有 1 分钟的活跃时间
 -`answer[2]`表示有多少用户正好有 2 分钟的活跃时间
 - ...
 -`answer[k]`代表到底有多少用户`k`活跃分钟数

 由于编程语言使用 0 索引数组，因此我们通常存储 UAM 的计数`j`在索引处`j - 1`。 

考虑第一个例子：```
logs = [[0,5],[1,2],[0,2],[0,5],[1,3]]
```用户`0`分钟出现：```
5, 2, 5
```独特的分钟数是：```
{2, 5}
```所以 UAM 是`2`。 

用户`1`分钟出现：```
2, 3
```这也给出了 UAM`2`。 

因此，两个用户的 UAM 等于`2`，所以答案就变成：```
[0,2,0,0,0]
```约束条件很重要：

 -`logs.length <= 10^4`- 用户 ID 可以非常大，最多可达`10^9`- 时间值也可以很大

 这些限制强烈表明我们不应该使用按用户 ID 或时间索引的数组。 相反，基于哈希的结构（例如字典/映射和集合）是理想的。 

该问题还保证：```
k >= maximum UAM of any user
```因此每个用户的 UAM 始终适合答案数组。 

一些边缘情况很重要：

 - 一个用户可能在同一分钟内出现多次
 - 多个用户可以在同一分钟内进行操作
 - 只能存在一个用户
 - 每个日志条目可能属于不同的分钟
 -`k`可能大于实际最大UAM

 简单地计算每个用户的日志条目的简单实现将会失败，因为重复的分钟数只能计算一次。 

## 方法

 ### 蛮力方法

 强力解决方案将单独处理每个用户并重复扫描整个日志数组以收集该用户的独特分钟数。 

一种可能的实现是：

 1. 提取所有唯一的用户 ID。 
2. 对于每个用户：

 - 扫描每个日志条目。 
- 将该用户的分钟数收集到临时集中。 
- 计算设置的大小。 
3.更新最终的频率数组。 

这是有效的，因为集合会自动消除重复的分钟，为每个用户生成正确的 UAM。 

但是，这种方法效率低下，因为要为每个用户重复扫描日志数组。 

如果有：

 -`n`日志条目
 -`u`唯一用户

 那么复杂度大约变为：```
O(u * n)
```在最坏的情况下，每个日志都属于不同的用户，使得复杂性接近：```
O(n^2)
```这对于给定的约束是不必要的。 

### 最佳方法

 关键的观察是我们只需要处理每个日志条目一次。 

我们可以维护：```
user_id -> set of unique minutes
```当我们迭代日志时：

 - 如果以前没有见过某个用户，则创建一个新组。 
- 将当前分钟插入该用户的集合中。 

由于集合会自动忽略重复项，因此同一分钟内的重复操作不会影响最终计数。 

构建此结构后：

 - 每组的大小等于该用户的 UAM。 
- 我们计算每个 UAM 有多少用户。 
- 将这些频率存储在答案数组中。 

这将复杂性降低到相对于日志数量的线性时间。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(u * n) | O(n) | 重复扫描每个用户的所有日志 |
 | 最佳| O(n) | O(n) | 使用哈希图和集合来有效地跟踪独特的分钟数 |

 ## 算法演练

 1. 创建一个哈希映射，其中：

 - 密钥是用户 ID
 - 该值是该用户的一组唯一的活跃分钟数
 2. 迭代每个日志条目：

 - 提取物`user_id`和`minute`- 插入`minute`进入该用户的集合
 3、处理完所有日志后：

 - 每个用户的集合准确包含他们独特的活跃分钟数
 - 该集合的大小等于该用户的 UAM
 4. 创建一个大小为答案的数组`k`用零初始化。 
5. 迭代每个用户的集合：

 - 计算：```
uam = len(minutes_set)
```- 增量：```
answer[uam - 1]
```因为数组是从 0 索引的，而 UAM 值从 1 开始。 
6. 返回答案数组。 

### 为什么它有效

 该算法之所以有效，是因为每个用户的活动分钟数都存储在一个集合中，并且集合保证了唯一性。 因此，同一分钟内的重复动作仅计算一次。 处理完所有日志后，每组日志的大小与该用户的 UAM 完全匹配。 计算这些集合大小的频率直接产生所需的答案数组。 

## Python 解决方案```python
from collections import defaultdict
from typing import List

class Solution:
    def findingUsersActiveMinutes(self, logs: List[List[int]], k: int) -> List[int]:
        user_minutes = defaultdict(set)

        for user_id, minute in logs:
            user_minutes[user_id].add(minute)

        answer = [0] * k

        for minutes_set in user_minutes.values():
            uam = len(minutes_set)
            answer[uam - 1] += 1

        return answer
```实施首先创建一个`defaultdict(set)`。 这很有用，因为每个用户第一次出现时都会自动获得一个空集。 

在第一个循环期间，每个`(user_id, minute)`对已处理。 该分钟将插入到相应用户的集合中。 如果同一分钟对同一用户出现多次，则该集会自动忽略重复项。 

处理完所有日志后，字典将包含每个用户的完整的唯一分钟集。 

答案数组初始化为`k`零，因为我们必须准确返回`k`条目。 

第二个循环迭代每组分钟。 该集合的大小给出了用户的UAM。 由于结果数组是 0 索引的，因此 UAM 的计数`x`存储在索引处`x - 1`。 

最后返回完整的频率数组。 

## 解决方案```go
func findingUsersActiveMinutes(logs [][]int, k int) []int {
	userMinutes := make(map[int]map[int]bool)

	for _, log := range logs {
		userID := log[0]
		minute := log[1]

		if _, exists := userMinutes[userID]; !exists {
			userMinutes[userID] = make(map[int]bool)
		}

		userMinutes[userID][minute] = true
	}

	answer := make([]int, k)

	for _, minutesSet := range userMinutes {
		uam := len(minutesSet)
		answer[uam-1]++
	}

	return answer
}
```Go 实现使用嵌套映射结构，因为 Go 没有内置的集合类型。 

外部地图存储：```go
userID -> minute set
```内部映射作为一个集合：```go
minute -> true
```当多次插入一分钟时，它只是覆盖相同的键，从而保持唯一性。 

其余逻辑与 Python 解决方案紧密匹配。 

与 Python 不同，Go 需要在插入之前显式初始化嵌套映射。 该解决方案通过在添加分钟之前检查用户的地图是否已存在来处理此问题。

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 每个日志条目都会处理一次 |
 | 空间| O(n) | 哈希图和集合可以唯一地存储所有日志条目 |

 该算法在插入哈希集时只处理每个日志一次。 哈希集插入是平均情况下的常数时间，使得总运行时间与日志条目的数量成线性关系。 

空间复杂度也是线性的，因为在最坏的情况下，每个日志条目都可以代表一个唯一的`(user, minute)`必须存储的对。

 ## 边缘情况

 当用户在同一分钟内执行许多操作时，就会出现一个重要的边缘情况。 简单地计算操作的简单实现会过多计算 UAM。 例如：```
[[1,5],[1,5],[1,5]]
```应该产生一个 UAM`1`， 不是`3`。 该实现可以正确处理此问题，因为设置会自动删除重复的分钟值。 

当多个用户在同一分钟内进行操作时，会出现另一个重要的边缘情况。 由于 UAM 是根据每个用户独立计算的，因此不同用户之间的相同时间戳不得相互干扰。 哈希映射按用户 ID 分隔数据，确保独立跟踪每个用户的分钟数。 

当发生第三种边缘情况时`k`大于每个实际 UAM 值。 答案数组仍必须准确包含`k`条目。 该实现用大小初始化结果数组`k`，因此任何未使用的频率自然保持为零。 

最后一个微妙的边缘情况涉及非常大的用户 ID。 由于 ID 可能大到`10^9`，使用按 ID 索引的数组是不切实际的。 该实现使用散列映射，允许有效处理稀疏的、非常大的 ID，而不浪费内存。
