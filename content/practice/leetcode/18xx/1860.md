 **难度：** 🟡 中等

 ## 解决方案

 ## 问题理解

 该问题模拟了一个随着时间的推移不断消耗内存的错误程序。 有两个内存条，用整数表示`memory1`和`memory2`。 程序每秒分配的位数不断增加：

 - 第二次`1`，它分配`1`少量。 
- 第二次`2`，它分配`2`位。 
- 第二次`3`，它分配`3`位。 
- 等等。 

分配总是发生在具有更多可用内存的记忆棒上。 如果两个内存条具有相同数量的可用内存，则从第一个内存条进行分配。 

该过程将继续，直到两个棒都没有足够的内存来满足当前的分配请求。 就在这时，程序崩溃了。 

输出必须包含三个值：

 -`crashTime`，无法进行分配时的第一秒
 -`memory1crash`，崩溃时第一根棒中的剩余内存
 -`memory2crash`，崩溃时第二根棒中的剩余内存

 约束允许的值大到`2^31 - 1`，这意味着实施必须高效并避免不必要的开销。 然而，分配的数量随着时间的推移线性增加，因此模拟步骤的数量比原始内存值可能建议的要少得多。 

一个重要的观察是，之后分配的总内存`k`秒是：$1+2+3+\cdots+k=\frac{k(k+1)}{2}$它呈二次方增长，因此即使对于非常大的内存值，迭代次数仍然是可控的。 

一些边缘情况很重要：

 - 两个记忆棒最初可能包含`0`- 一根棍子可以从`0`而另一个包含内存
 - 两根棍子可能会反复变得相等
 - 成功分配后可能会立即发生崩溃
 - 当值相等时，分配必须始终优先选择第一根棍子

 忘记打破平局规则的幼稚实现将产生错误的答案。 

## 方法

 ### 蛮力方法

 蛮力解决方案直接逐秒模拟该过程。 

每一秒：

 1. 比较`memory1`和`memory2`2、从较大的记忆棒中减去当前的第二个值
 3. 增加时间计数器
 4. 继续，直到两根棍子都不能满足分配

 这种方法很简单，因为问题本身描述了一个模拟过程。 由于每一步都完全反映了规则，因此很容易推断出正确性。 

尽管限制允许内存值高达约 20 亿，但迭代次数仍然相对较少。 第一个的总和`k`整数呈二次方增长，因此该过程大致在以下时间后终止：$k\approx\sqrt{2(memory1+memory2)}$对于最大可能的输入大小，迭代次数仅为 65,000 次左右，这已经足够快了。 

### 优化观察

 不需要复杂的数据结构或数学捷径，因为模拟本身已经足够高效。 

关键的一点是，即使内存值很大，分配量也会每秒增加。 这会快速消耗总内存，从而使循环迭代次数保持相对较小。 

因此，最佳解决方案就是仔细处理平局规则的干净模拟。

## 算法演练

 1. 初始化变量`time`到`1`。 

该变量表示当前秒内必须分配的内存量。 
2. 开始无限循环。 

循环继续，直到两个记忆棒都不能满足当前的分配请求。 
3.比较`memory1`和`memory2`。 

如果`memory1 >= memory2`，分配必须来自第一根棍子。 该问题明确指出，平局的解决有利于第一根棍子。 
4. 检查所选内存条是否有足够的可用内存。 

如果所选的棒至少包含`time`位，减`time`从它。 
5. 如果所选的记忆棒没有足够的内存，请尝试使用其他记忆棒。 

这种情况只有当选择的棍子较大但仍然不够时才会出现。 在某些配置中，较小的内存条可能仍然有足够的内存。 
6. 如果两个棒都没有足够的内存，则停止模拟。 

返回：

 - 当前`time`- 其余的`memory1`- 其余的`memory2`7. 增量`time`并继续。 

下一秒需要更大的分配。 

### 为什么它有效

 每时每刻，算法都严格遵循问题陈述中描述的规则。 所选择的记忆棒始终是具有更大可用内存的记忆棒，并与第一根记忆棒相关。 仅当容量充足时才会扣除内存。 因此，模拟的状态始终与预期的系统行为相匹配，从而保证了正确性。 

## Python 解决方案```python
from typing import List

class Solution:
    def memLeak(self, memory1: int, memory2: int) -> List[int]:
        time = 1

        while True:
            if memory1 >= memory2:
                if memory1 >= time:
                    memory1 -= time
                elif memory2 >= time:
                    memory2 -= time
                else:
                    return [time, memory1, memory2]
            else:
                if memory2 >= time:
                    memory2 -= time
                elif memory1 >= time:
                    memory1 -= time
                else:
                    return [time, memory1, memory2]

            time += 1
```实现直接遵循模拟过程。 

变量`time`存储当前秒，还表示该秒内必须分配的内存量。 

在循环内部，算法首先确定哪个记忆棒当前具有更多可用内存。 条件`memory1 >= memory2`正确处理大于情况和平局打破规则。 

选择首选棒后，代码检查该棒是否可以满足分配。 如果可以，则扣除所需金额。 

如果首选棒无法满足请求，则实施会检查另一个棒。 如果两个内存条都没有足够的内存，程序就会崩溃，并立即返回所需的结果。 

最后，`time`递增，因此下一次迭代请求更大的分配量。 

## 解决方案```go
func memLeak(memory1 int, memory2 int) []int {
    time := 1

    for {
        if memory1 >= memory2 {
            if memory1 >= time {
                memory1 -= time
            } else if memory2 >= time {
                memory2 -= time
            } else {
                return []int{time, memory1, memory2}
            }
        } else {
            if memory2 >= time {
                memory2 -= time
            } else if memory1 >= time {
                memory1 -= time
            } else {
                return []int{time, memory1, memory2}
            }
        }

        time++
    }
}
```Go 的实现几乎与 Python 版本相同，因为算法简单且迭代。 

Go 解决方案不返回 Python 列表，而是使用以下命令返回整数切片`[]int{...}`。 

整数溢出在这里不是一个问题，因为这些约束很适合 Go 的范围`int`在 LeetCode 环境中输入。

 ## 边缘情况

 当两个记忆棒都以零内存启动时，会出现一种重要的边缘情况。 在这种情况下，程序立即崩溃`1`because neither stick can allocate even a single bit. An implementation that assumes at least one successful allocation would fail here. 该解决方案自然地处理了这个问题，因为第一次迭代立即检查分配的可行性。 

Another critical edge case involves equal memory values. 该问题明确要求当两个值相等时从第一根棍子进行分配。 Missing this rule changes the entire simulation sequence and produces incorrect outputs. The implementation handles this correctly using the condition`memory1 >= memory2`。 

当较大的内存条无法满足分配但较小的内存条可以时，就会出现第三种边缘情况。 粗心的实现可能只会检查较大的棒并错误地提前终止。 该解决方案在确定程序必须崩溃之前正确尝试从另一根棒进行分配。
