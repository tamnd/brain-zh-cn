[LeetCode 920 题](https://leetcode.com/problems/number-of-music-playlists/)

 **难度：** 🔴难
 **主题：** 数学、动态规划、组合学

 ## 解决方案

 ## 问题理解

 问题给了我们`n`独特的歌曲并要求我们建立长度的播放列表`goal`。 歌曲可以重复，但必须始终保持两个重要的限制。 

首先，每一个`n`歌曲必须在播放列表中至少出现一次。 其次，歌曲一旦播放完毕，就不能再次播放，至少要等到`k`其间还播放了其他歌曲。 

我们被要求计算这些规则下存在多少个有效的播放列表。 由于答案可能变得非常大，我们将其模数返回`10^9 + 7`。 

输入参数代表如下：

 -`n`是可用的不同歌曲的数量。 
-`goal`是播放列表的总长度。 
-`k`是重复限制距离。 

输出是精确长度的播放列表的数量`goal`至少使用所有歌曲一次并满足重播限制。 

约束条件很重要：

 -`0 <= k < n <= goal <= 100`自从`goal`最多为 100，指数暴力生成是不可能的，但多项式时间动态规划是非常可行的。 小上限强烈建议采用基于播放列表长度和歌曲使用计数的状态的 DP 解决方案。 

一些边缘情况尤其重要：

 - 当`k = 0`，歌曲可能会立即重复，所以唯一的要求是每首歌曲至少出现一次。 
- 什么时候`goal = n`，每首歌曲必须恰好出现一次，因为没有多余的重复空间。 
- 什么时候`k = n - 1`, a song can only repeat after every other song has been played, which creates very strict ordering constraints.
 - 小值，例如`n = 1`仍必须正常工作。 
- 重复计数很容易溢出标准整数，因此必须一致地应用模运算。 

## 方法

 ### 蛮力

 暴力解决方案将递归地生成每个可能的长度播放列表`goal`。 在每个位置，我们都会尝试所有`n`歌曲，检查是否满足重播约束，并在最后验证每首歌曲至少出现一次。 

这种方法在概念上很简单，因为它直接对问题定义进行建模。 然而，它的复杂性是巨大的。 在最坏的情况下，有`n^goal`可能要检查的播放列表。 

例如，如果`n = 100`和`goal = 100`，搜索空间变得天文数字般大。 即使是积极的修剪也无法使之变得可行。 

### 关键见解

 重要的观察是，之前播放的歌曲的确切顺序大多无关紧要。 真正重要的是：

 - 有多少职位已被填补。 
- 到目前为止已经使用了多少首独特的歌曲。 

这自然会导致动态规划。 

假设我们定义：

 -`dp[i][j]`作为长度的播放列表的数量`i`恰好包含`j`独特的歌曲。 

从这个状态开始，只有两种可能的转换：

 1.添加一首以前从未使用过的全新歌曲。 
2. 重播当前允许的旧歌曲`k`限制。 

这极大地将状态空间从指数减小到多项式。

 | 方法| 时间复杂度| 空间复杂度| 笔记|

 ## 算法演练

 ### 动态规划状态

 我们定义：$$dp[i][j]$$作为长度的播放列表的数量`i`恰好包含`j`独特的歌曲。 

最终答案将是：$$dp[goal][n]$$因为我们需要一个长度的播放列表`goal`使用所有`n`歌曲。 

### 转换逻辑

 在每个州，我们都有两种选择。 

#### 1. 添加新歌曲

 如果我们目前有`j - 1`独特的歌曲和想要达到的`j`独特的歌曲，我们可以添加一首新歌。 

可用的未使用歌曲数量为：$$n - (j - 1)$$所以过渡变成：$dp[i][j] += dp[i-1][j-1] \times (n-(j-1))$这意味着：

 - 建立一个长度的播放列表`i - 1`和`j - 1`独特的歌曲。 
- 选择一首未使用的歌曲进行附加。 

#### 2. 重播现有歌曲

 我们也可以重播以前使用过的歌曲，但前提是它不是最后一首歌曲`k`播放歌曲。 

如果我们已经有`j`独特的歌曲，然后：

 -`k`歌曲暂时被屏蔽。 
-`j - k`歌曲可以重播。 

这个转变是：$dp[i][j] += dp[i-1][j] \times (j-k)$此转换仅适用于以下情况`j > k`。 

### 基本情况

 使用零首歌曲的空播放列表只有一个有效配置：$$dp[0][0] = 1$$所有其他状态最初都从零开始。 

### 逐步算法

 1.创建尺寸为2D的DP表`(goal + 1) × (n + 1)`初始化为零。 
2. 设置`dp[0][0] = 1`因为只有一个空播放列表。 
3. 迭代播放列表长度`1`到`goal`。 
4. 对于每个长度，迭代可能的独特歌曲数量`1`到`n`。 
5. 计算添加新歌曲的贡献：

 - 开始于`dp[i - 1][j - 1]`- 乘以未使用的歌曲数量。 
6. 计算重播一首老歌的贡献：

 - 只有在以下情况下才可能`j > k`- 开始于`dp[i - 1][j]`- 乘以可重复使用的歌曲数量。 
7. 应用模数`10^9 + 7`每次更新后。 
8. 返回`dp[goal][n]`。 

### 为什么它有效

 DP 状态完全捕获继续构建有效播放列表所需的所有信息。 在任何时候，只有播放列表的长度和独特歌曲的数量很重要。 每个有效的播放列表扩展都属于以下两个类别之一：

 - 添加一首新歌
 - 重播现有允许的歌曲

 由于转换会计算所有有效的可能性，而不会重叠或遗漏，因此 DP 正确地枚举每个有效的播放列表一次。 

## Python 解决方案```python
class Solution:
    def numMusicPlaylists(self, n: int, goal: int, k: int) -> int:
        MOD = 10**9 + 7

        dp = [[0] * (n + 1) for _ in range(goal + 1)]
        dp[0][0] = 1

        for length in range(1, goal + 1):
            for unique in range(1, n + 1):

                # Add a new song
                dp[length][unique] += (
                    dp[length - 1][unique - 1]
                    * (n - (unique - 1))
                )

                # Replay an old song
                if unique > k:
                    dp[length][unique] += (
                        dp[length - 1][unique]
                        * (unique - k)
                    )

                dp[length][unique] %= MOD

        return dp[goal][n]
```实施直接遵循DP的制定。 

我们首先创建一个 DP 表，其中行代表播放列表长度，列代表已使用的独特歌曲数量。 

基本情况`dp[0][0] = 1`代表空播放列表。 

对于每个状态，我们计算两个转换。 

第一个过渡添加了一首新的未使用的歌曲。 如果我们之前有`unique - 1`不同的歌曲，那么有`n - (unique - 1)`剩余未使用的歌曲。 

第二个过渡重复使用了一首老歌。 然而，仅`unique - k`歌曲符合资格，因为最后`k`歌曲无法立即重播。 

每次更新后都会应用模运算，以防止整数溢出并满足问题要求。 

最后，我们返回`dp[goal][n]`，它表示每首歌曲至少使用一次的完整长度的播放列表。 

## 解决方案```go
func numMusicPlaylists(n int, goal int, k int) int {
	const MOD int = 1_000_000_007

	dp := make([][]int, goal+1)
	for i := range dp {
		dp[i] = make([]int, n+1)
	}

	dp[0][0] = 1

	for length := 1; length <= goal; length++ {
		for unique := 1; unique <= n; unique++ {

			// Add a new song
			dp[length][unique] +=
				dp[length-1][unique-1] *
					(n - (unique - 1))

			dp[length][unique] %= MOD

			// Replay an old song
			if unique > k {
				dp[length][unique] +=
					dp[length-1][unique] *
						(unique - k)

				dp[length][unique] %= MOD
			}
		}
	}

	return dp[goal][n]
}
```Go 实现密切反映了 Python 逻辑。 由于 Go 不会自动调整多维数组的大小，因此我们显式分配 2D 切片结构。 

每次更新后都会仔细执行模运算，以避免溢出增长。 在这些约束下，Go 整数对于中间乘法来说足够大，特别是因为随后立即发生模数减少。 

与 Python 不同，Go 不支持负索引或动态列表增长，因此循环和索引稍微更明确。

 ## 边缘情况

 ### 案例 1：`k = 0`什么时候`k`为零，歌曲可能会立即重复。 这显着改变了重播逻辑，因为之前使用的每首歌曲始终可以重复使用。 

有缺陷的实现可能会意外地禁止立即重复，即使`k = 0`。 我们的实现可以正确处理这个问题，因为重播转换使用`unique - k`，这变成`unique`。 

### 案例 2：`goal = n`当播放列表长度恰好等于不同歌曲的数量时，每首歌曲必须恰好出现一次。 不可能有重复。 

在这种情况下，答案应该简单地计算歌曲的排列。 DP 自然会处理这个问题，因为在使用所有歌曲之前，重播过渡永远不会产生有意义的影响。 

### 案例 3：`k = n - 1`这是最严格的重播限制。 在所有其他歌曲播放完毕之前，一首歌曲无法重复播放。 

这种边缘情况很容易处理不当，因为可重复使用的歌曲数量变得非常少。 我们的过渡条件`if unique > k`保证仅当存在足够多的不同歌曲以满足间隔规则时才会发生重播。 

### 情况 4：单首歌曲输入

 当`n = 1`，只有一首可能的歌曲。 如果`k = 0`，播放列表是唯一确定的，无论`goal`。 

假设存在多首歌曲的实现可能会错误地计算重播计数或访问无效的 DP 状态。 即使对于这种最小配置，我们的 DP 配方也能自然发挥作用。
