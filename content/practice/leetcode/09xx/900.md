 **难度：** 🟡 中等
 **主题：** 数组、设计、计数、迭代器

 ## 解决方案

 ## 问题理解

 这个问题要求我们在游程编码序列上设计一个迭代器，而不是显式地存储完整序列。 

在游程编码中，数组是成对组织的：

 -`encoding[i]`表示某个值出现的次数
 -`encoding[i + 1]`代表值本身

 例如：```
[3,8,2,5]
```方法：```
8 appears 3 times
5 appears 2 times
```所以解码后的序列变成：```
[8,8,8,5,5]
```迭代器必须支持重复调用：```
next(n)
```该操作消耗下一个`n`序列中的元素并返回最后用尽的值。 

例如，如果剩余序列是：```
[8,8,5,5]
```我们称之为：```
next(3)
```那么耗尽的元素是：```
8,8,5
```返回值为：```
5
```剩下的序列变成：```
[5]
```如果没有足够的元素可供耗尽`n`物品，我们返回`-1`。 

约束条件很重要：

 - 计数可以大到`10^9`-`n`也可以大到`10^9`- 最多可以有`1000`打电话给`next`这些限制立即告诉我们，显式扩展序列是不切实际的。 像这样的序列：```
[1000000000, 7]
```如果完全解压缩，将需要存储十亿个元素，这在正常内存限制内是不可能的。 

关键的观察是我们实际上从来不需要扩展序列。 我们只需要跟踪：

 - 我们当前正在消耗哪个运行
 - 该次运行中还剩下多少元素

 一些边缘情况很重要：

 - 运行计数`0`- 拨打电话`n`跨越多次运行
 - 准确完成一次运行的呼叫
 - 请求的元素多于剩余元素的调用
 - 数量非常多而且非常大`n`价值观

 该问题保证：

 - 编码长度为偶数
 - 值为非负数
 -`next`只会收到积极的`n`这使我们能够安全地处理计数值对中的数组。 

## 方法

 ### 蛮力方法

 最直接的想法是将游程编码数组完全解码为实际序列。 

例如：```
[3,8,2,5]
```会变成：```
[8,8,8,5,5]
```然后迭代器可以维护一个指向这个扩展数组的指针。 每个`next(n)`call 只是将指针前进`n`定位并返回最后消耗的元素。 

这种方法很容易理解和实施。 由于序列是显式存储的，因此回答查询就变成了简单的指针算术。 

然而，对于给定的约束，该解决方案是完全不切实际的。 计数可能大到`10^9`，这意味着扩展的序列可能包含数十亿个元素。 内存使用和构建时间都变得不可能。 

### 最佳方法

 关键的见解是我们永远不需要完全扩展的序列。 

相反，我们可以直接处理编码。 由于编码已经告诉我们每个值出现了多少次，因此我们可以通过数学方式消耗计数。 

我们维持：

 - 指向当前运行的指针
 - 该次运行中的剩余计数

 当`next(n)`称为：

 - 如果当前运行少于`n`剩余元素，我们消耗整个运行并移动到下一个。 
- 否则，我们消费`n`来自当前运行的元素并返回其值。 

这是有效的，因为编码结构已经包含了模拟穷举所需的所有信息，而无需具体化序列。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(总解码长度) | O(总解码长度) | 完全扩展序列，对于大计数来说是不可能的 |
 | 最佳 | 每次调用 O(处理的运行次数) | O(1) 额外空间 | Consume无需解压直接运行 |

 ## 算法演练

 1. 存储编码后的数组并初始化一个指针。 

指针始终指向编码数组中的当前计数位置。 由于编码使用对：```
[count, value, count, value, ...]
```指针以两步移动。 
2. 在每次`next(n)`调用，重复处理当前运行。 

每一步：

 -`encoding[index]`是剩余计数
 -`encoding[index + 1]`是值
 3. 如果当前运行包含的元素少于所需的元素：```
remaining_count < n
```然后消耗整个运行。 

减去计数`n`因为在这次运行耗尽之后我们仍然需要更多的元素。 

将指针移至下一对。 
4. 如果当前运行包含足够的元素：```
remaining_count >= n
```然后将剩余计数减少`n`。 

最后耗尽的元素必须是当前值，因此立即返回它。 
5. 如果所有运行都耗尽后再消费`n`元素，返回`-1`。 

### 为什么它有效

 该算法保持了当前指针完全耗尽之前的所有运行的不变性，而当前运行准确地存储了剩余的未使用计数。 

每个`next(n)`只要有可能，调用就会准确地消耗所请求的元素数量。 由于运行是按顺序处理的并且计数已正确更新，因此返回的值始终是最终耗尽的元素。 如果剩余元素不足，算法会正确检测到耗尽并返回`-1`。 

## Python 解决方案```python
from typing import List

class RLEIterator:

    def __init__(self, encoding: List[int]):
        self.encoding = encoding
        self.index = 0

    def next(self, n: int) -> int:
        while self.index < len(self.encoding):

            current_count = self.encoding[self.index]
            current_value = self.encoding[self.index + 1]

            if current_count < n:
                n -= current_count
                self.index += 2
            else:
                self.encoding[self.index] -= n
                return current_value

        return -1

# Your RLEIterator object will be instantiated and called as such:
# obj = RLEIterator(encoding)
# param_1 = obj.next(n)
```构造函数存储编码后的数组并初始化一个名为`index`。 

指针始终引用编码数组内的当前计数位置。 由于该结构使用计数值对，因此关联值始终位于`index + 1`。 

里面`next`，我们反复检查当前运行。 

如果当前运行不包含足够的元素，我们将消耗整个运行：```python
n -= current_count
self.index += 2
```这将我们带到下一个计数值对。 

如果当前运行包含足够的元素，我们通过减去来部分消耗它`n`从剩余计数中：```python
self.encoding[self.index] -= n
```当前值就是最终耗尽的元素，因此我们返回它。 

如果在消耗所有必需元素之前所有运行都已耗尽，则循环结束并返回`-1`。 

## 解决方案```go
type RLEIterator struct {
	encoding []int
	index    int
}

func Constructor(encoding []int) RLEIterator {
	return RLEIterator{
		encoding: encoding,
		index:    0,
	}
}

func (this *RLEIterator) Next(n int) int {

	for this.index < len(this.encoding) {

		currentCount := this.encoding[this.index]
		currentValue := this.encoding[this.index+1]

		if currentCount < n {
			n -= currentCount
			this.index += 2
		} else {
			this.encoding[this.index] -= n
			return currentValue
		}
	}

	return -1
}

/**
 * Your RLEIterator object will be instantiated and called as such:
 * obj := Constructor(encoding);
 * param_1 := obj.Next(n);
 */
```Go 实现遵循与 Python 解决方案完全相同的逻辑。 

一个显着的区别是 Go 显式使用结构体字段：```go
encoding []int
index int
```迭代器就地更新原始编码片以跟踪剩余计数。 

整数溢出不是一个问题，因为 Go 的`int`类型安全地处理至少可达的值`10^9`在标准 LeetCode 环境中。

 ## 边缘情况

 ### 零计数运行

 编码可能包含如下条目：```
[0, 9]
```这意味着值`9`出现零次，应该被有效地忽略。 

有错误的实现可能会意外返回`9`或无法正确推进。 此实现可以自然地处理这种情况，因为当计数小于`n`，立即跳过运行。 

### 在边界处精疲力竭

 考虑：```
[3, 8]
```和：```
next(3)
```实现必须正确返回`8`然后让迭代器完全耗尽。 

这可能是差一错误的根源。 该解决方案通过精确减去来避免这种情况`n`从返回之前的当前计数开始。 

### 请求大于剩余元素

 假设只剩下一个元素，但调用是：```
next(2)
```迭代器必须返回`-1`，即使一个有效元素被部分消耗。 

幼稚的实现可能会错误地返回最后一个可用值。 该解决方案正确跟踪剩余所需金额，并且仅在全部满足时才返回一个值`n`元素可以成功耗尽。 

### 非常大的计数

 计数可达`10^9`。 

任何将序列扩展为列表或数组的实现都将耗尽内存或时间。 该解决方案从不存储解码序列，仅以数学方式操作计数，从而使其能够有效处理极大的输入。
