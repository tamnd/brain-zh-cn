[LeetCode 901 题](https://leetcode.com/problems/online-stock-span/)

 **难度：** 🟡 中等
 **主题：** 堆栈、设计、单调堆栈、数据流

 ## 解决方案

 ## 问题理解

 该问题要求我们设计一个类，一次处理一天的股票价格，并且对于每个新价格，返回当天的股票跨度。 

股票跨度定义为截至今天股票价格低于或等于今天价格的连续天数。 我们从当天开始，向后移动前几天，直到遇到比今天价格更高的价格。 所有有效连续天数的计数就是跨度。 

例如，假设传入价格为：```
100, 80, 60, 70, 60, 75, 85
```当当前价格为`75`，我们向后看：```
75 >= 60  -> valid
75 >= 70  -> valid
75 >= 60  -> valid
75 < 80   -> stop
```所以跨度是`4`。 

输入不是一次性提供的。 相反，价格是通过反复致电`next(price)`方法。 这意味着该解决方案必须以在线方式工作，一次处理一个值，而无需从头开始重新计算所有内容。 

限制相对较小，最多`10^4`电话，但预期的解决方案仍然预计是有效的。 在最坏的情况下，向后扫描每个查询的简单方法可能会降低到二次时间，尤其是当价格严格上涨时。 

一个重要的观察是，一旦我们知道先前的价格小于或等于当前的价格，先前的价格就永远不会再次阻止未来的跨度。 这一观察自然地导致了单调堆栈解决方案。 

一些边缘情况很重要：

 - 严格降低价格，每个跨度都是`1`- 严格提高价格，跨度不断增长
 - 重复同等价格，因为条件是`<=`， 不是`<`- 单一价格输入
 - 大型连续递增序列会使简单的方法变慢

 该问题保证所有价格都是正整数并且操作次数是有界的。 

## 方法

 ### 蛮力方法

 最简单的方法是将所有以前的价格存储在一个数组中。 对于每个新价格，我们都会从最近一天开始向后扫描，直到找到比当前价格更高的价格。 

例如：```
Prices: [100, 80, 60, 70]
Current price: 70
```我们向后扫描：```
70 >= 60 -> count
70 < 80  -> stop
```跨度为`2`。 

这种做法是正确的，因为它直接实现了span的定义。 然而，它可能会变得低效。 在最坏的情况下，如果价格严格上涨，则每个查询都会扫描所有先前的元素。 

例子：```
1, 2, 3, 4, 5, 6
```工作变成：```
1 + 2 + 3 + 4 + 5 + 6
```这是`O(n^2)`全面的。 

### 最优方法，单调堆栈

 关键的见解是，一旦出现更高的价格，许多先前的价格就变得无关紧要。 

假设我们有：```
100, 80, 60, 70
```加工时`70`, 价格`60`被弹出是因为`70`大于或等于它。 发生这种情况后，`60`对于未来的跨度计算永远不会再重要，因为`70`已经占据主导地位并且是最近才出现的。 

这表明保持单调递减的堆栈。 每个堆栈条目存储：

 - 股票价格
 - 与该价格相关的跨度

 当新价格到达时：

 - 弹出所有带有价格的堆栈元素`<= current price`- 积累他们的跨度
 - 以合并跨度推动新价格

 这使我们能够一次跳过大量的日子，而不是单独扫描。 

每个元素被压入一次并弹出一次，给出摊销`O(1)`每次操作的时间。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 每次查询 O(n)，总共 O(n²) | O(n) | 向后扫描所有之前的价格 |
 | 最佳 | 每个查询分摊 O(1)，总共 O(n) | O(n) | 使用单调递减堆栈 |

 ## 算法演练

 1. 初始化一个空堆栈。 

堆栈将存储以下对：```
(price, span)
```堆栈按价格从下到上的降序排列。 
2. 当新价格到达时，将跨度初始化为`1`。 

每个价格总是独立计算，因此最小跨度始终是`1`。 
3. 当堆栈不为空且最高价格小于或等于当前价格时，弹出堆栈。 

这些弹出价格保证包含在今天的范围内，因为它们小于或等于今天的价格。 
4. 将弹出元素的span 添加到当前span 中。 

我们不再一一计算天数，而是重复使用之前计算的跨度。 这是使算法高效的优化。 
5. 推对`(current_price, current_span)`到堆栈上。 

这保留了递减堆栈属性。 
6. 返回计算出的跨度。 

### 为什么它有效

 堆栈始终按严格降序维护价格。 近期较大价格背后的任何较小或相等的价格都变得无关紧要，因为较大的价格已经涵盖了较小价格可能贡献的所有范围。 通过在弹出过程中合并跨度，我们可以有效地将连续的有效天数压缩到单个堆栈条目中。 由于每个元素最多被压入和弹出一次，因此该算法既正确又高效。 

## Python 解决方案```python
class StockSpanner:

    def __init__(self):
        self.stack = []

    def next(self, price: int) -> int:
        span = 1

        while self.stack and self.stack[-1][0] <= price:
            previous_price, previous_span = self.stack.pop()
            span += previous_span

        self.stack.append((price, span))

        return span

# Your StockSpanner object will be instantiated and called as such:
# obj = StockSpanner()
# param_1 = obj.next(price)
```该实现使用一个堆栈，其中每个元素都是一个包含价格及其跨度的元组。 

里面`__init__`，我们初始化一个空堆栈，该堆栈在方法调用之间持续存在。 这是必要的，因为该类会随着时间的推移逐步处理价格。 

里面`next`，我们开始于`span = 1`因为当天总是会计入其自身的跨度。 

这`while`循环删除所有小于或等于当前价格的先前价格。 由于这些价格属于当前范围，因此它们存储的范围将直接添加到当前范围。 这避免了重新扫描个别日子。 

删除所有较小或相同的价格后，我们推动当前的价格`(price, span)`配对入栈。 此时，堆栈保持单调递减。 

最后，我们返回计算出的跨度。 

## 解决方案```go
type Pair struct {
	price int
	span  int
}

type StockSpanner struct {
	stack []Pair
}

func Constructor() StockSpanner {
	return StockSpanner{
		stack: []Pair{},
	}
}

func (this *StockSpanner) Next(price int) int {
	span := 1

	for len(this.stack) > 0 &&
		this.stack[len(this.stack)-1].price <= price {

		top := this.stack[len(this.stack)-1]
		this.stack = this.stack[:len(this.stack)-1]

		span += top.span
	}

	this.stack = append(this.stack, Pair{
		price: price,
		span:  span,
	})

	return span
}

/**
 * Your StockSpanner object will be instantiated and called as such:
 * obj := Constructor();
 * param_1 := obj.Next(price);
 */
```Go 实现遵循与 Python 版本相同的逻辑，但使用名为`Pair`储存`(price, span)`价值观。 

Go 切片用于模拟堆栈。 弹出是通过切片执行的：```go
this.stack = this.stack[:len(this.stack)-1]
```与 Python 不同，Go 没有内置元组支持，因此自定义结构更清晰、更具可读性。 

整数溢出不是问题，因为最大调用次数仅为`10^4`。 

## 工作示例

 ### 示例 1

 输入价格：```
100, 80, 60, 70, 60, 75, 85
```| 日 | 价格| 堆栈之前 | 运营| 跨度| 堆栈之后 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 100 | 100 []| 推 (100,1) | 1 | [(100,1)] |
 | 2 | 80| [(100,1)] | 没有流行| 1 | [(100,1),(80,1)] |
 | 3 | 60| [(100,1),(80,1)] | 没有流行| 1 | [(100,1),(80,1),(60,1)] |
 | 4 | 70 | 70 [(100,1),(80,1),(60,1)] | 流行 (60,1) | 2 | [(100,1),(80,1),(70,2)] |
 | 5 | 60| [(100,1),(80,1),(70,2)] | 没有流行| 1 | [(100,1),(80,1),(70,2),(60,1)] |
 | 6 | 75 | 75 [(100,1),(80,1),(70,2),(60,1)] | 流行音乐 (60,1)、流行音乐 (70,2) | 4 | [(100,1),(80,1),(75,4)] |
 | 7 | 85 | 85 [(100,1),(80,1),(75,4)] | 流行音乐 (75,4)、流行音乐 (80,1) | 6 | [(100,1),(85,6)] |

 最终输出：```
[1,1,1,2,1,4,6]
```### 为什么 85 的跨度是 6

 加工时`85`:

 -`75`贡献跨度`4`-`80`贡献跨度`1`- 当日贡献`1`全部的：```
4 + 1 + 1 = 6
```该算法重用之前计算的跨度，而不是单独重新计算天数。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | 每次调用摊销 O(1) | 每个元素最多被压入和弹出一次 |
 | 空间| O(n) | 堆栈可以按降序存储所有价格 |

 虽然`while`循环可能会显得昂贵，每个股票价格只能从堆栈中移除一次。 在所有操作中，推入和弹出的总数是线性的。 因此，总运行时间`n`调用的是`O(n)`，这意味着每次操作成本`O(1)`摊销时间。

 ## 边缘情况

 ### 严格降价

 递减序列例如：```
100, 90, 80, 70
```是一种重要的边缘情况，因为之前的价格不小于或等于当前价格。 因此，每个跨度都应该精确地`1`。 

有缺陷的实现可能会意外地错误地合并跨度或无法在较大的值处停止。 单调递减堆栈可以自然地处理这个问题，因为不会发生弹出。 

### 重复同等价格

 条件使用`<=`， 不是`<`。 

例如：```
50, 50, 50
```跨度应该是：```
1, 2, 3
```如果实现使用严格的`<`比较，相等的价格将无法正确合并，并且跨度都会错误地变为`1`。 

该解决方案通过以下方式正确处理此问题：```
while stack_top_price <= current_price
```### 严格涨价

 递增序列例如：```
10, 20, 30, 40, 50
```是暴力方法的最坏情况，因为每个查询都会扫描所有先前的元素。 

然而，单调堆栈解决方案仍然高效，因为每个元素在整个执行过程中仅弹出一次。 这保证了每次操作的摊销恒定时间。 

### 单一价格输入

 当仅处理一个价格时，跨度必须始终为`1`。 

此案例验证了实现在进入循环之前正确初始化了跨度，并且不依赖于堆栈中存在的先前元素。
