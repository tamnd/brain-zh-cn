[LeetCode 第 10 题](https://leetcode.com/problems/regular-expression-matching/)

 **难度：** 🔴难
 **主题：** 字符串、动态规划、递归

 ## 解决方案

 ## 问题理解

 LeetCode 10，正则表达式匹配，要求我们确定整个输入字符串是否`s`匹配一个模式`p`。 该模式支持两个特殊的正则表达式字符：

 -`.`匹配任何单个字符
 -`*`匹配紧邻其前面的字符零次或多次出现

 重要的细节是匹配必须覆盖整个字符串，而不仅仅是子字符串。 这意味着当字符串的一部分匹配时我们不能提前停止。 中的每个角色`s`必须被模式消耗，并且模式的每个有意义的部分都必须参与匹配。 

例如：

-`"aa"`不匹配`"a"`因为模式只匹配一个字符
 -`"aa"`比赛`"a*"`因为`*`允许重复`'a'`-`"ab"`比赛`".*"`因为`.`匹配任何字符并且`*`允许无限次重复

 输入由两个字符串组成：

 -`s`，我们要匹配的文本
 -`p`，正则表达式样式模式

 限制很小：

 -`1 <= s.length <= 20`-`1 <= p.length <= 20`尽管输入大小很小，但引入的递归分支`*`如果简单地实现，仍然可以产生指数行为。 这使得动态编程或记忆成为首选方法。 

一些边缘情况尤其重要：

 - 图案如`"a*"`可以匹配空序列
 -`".*"`几乎可以匹配任何东西
 - 多个`*`运算符可以在逻辑术语中连续出现，例如`"a*b*c*"`- 算法必须区分消耗字符和跳过字符`*`完全分组
 - 仅贪婪匹配是不够的，因为有时需要较少的重复次数才能成功完成完整匹配

 该问题保证了每个`*`总是有一个有效的前置字符，因此无效的模式，如`"*a"`永远不会出现。 

## 方法

 ### 蛮力递归回溯

 最直接的解决办法就是递归回溯。 在每个位置，我们都会比较当前字符`s`和`p`。 

如果下一个模式字符不是`*`，那么当前字符必须直接匹配，要么因为它们相等，要么因为模式包含`.`。 然后我们递归地移动到两个字符串中的下一个位置。 

如果下一个模式字符是`*`，我们有两种可能的选择：

 1. 跳过整个`x*`模式并在模式中前进
 2. 使用 1 次出现`x*`如果当前字符匹配，则继续匹配相同的模式位置

 这种蛮力方法是正确的，因为它探索了每一个有效的解释`*`。 然而，许多州却重复了这一点。 相同`(i, j)`位置对可以多次重新计算，导致指数时间复杂度。 

### 带记忆的动态规划

 关键的见解是递归状态完全由两个索引确定：

 -`i`，当前位置在`s`-`j`，当前位置在`p`一旦我们知道是否`s[i:]`比赛`p[j:]`，我们永远不需要再次重新计算它。 

这一观察使得记忆成为可能。 我们存储每个之前计算的结果`(i, j)`一对。 由于最多有`len(s) * len(p)`不同的状态，复杂性变成多项式。 

这将指数递归搜索转变为高效的动态编程解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(2^(m+n)) | O(2^(m+n)) | O(m+n) | 反复探索所有递归可能性 |
 | 最佳 | O(m × n) | O(m × n) | 记忆递归避免重新计算 |

 这里，`m = len(s)`和`n = len(p)`。 

## 算法演练

 ### 最优动态规划算法

 1.定义递归函数`dp(i, j)`。 

该函数返回子串是否`s[i:]`匹配模式子串`p[j:]`。 

使用索引而不是切片字符串可以避免不必要的内存分配并保持解决方案的效率。 
2. 处理基本情况。 

如果`j`到达模式末尾，仅当匹配成功时`i`也到达字符串的末尾。 

这确保了整个字符串的匹配，而不仅仅是前缀。 
3、判断当前字符是否匹配。 

如果满足以下条件，则存在匹配：

 -`i < len(s)`, 和
 - 要么`s[i] == p[j]`或者`p[j] == '.'`该逻辑处理精确字符匹配和通配符匹配。 
4. 检查下一个模式字符是否为`*`。 

这是通过验证来完成的：```
j + 1 < len(p) and p[j + 1] == '*'
```如果一个`*`存在的话，有两种可能：

 - 跳过`x*`完全：```
dp(i, j + 2)
```- 使用 1 次出现`x*`如果当前字符匹配：```
first_match and dp(i + 1, j)
```请注意，第二个选项保留`j`不变，因为`*`可能会继续消耗字符。 
5.如果没有`*`，需要直接字符匹配。 

在这种情况下，两个指针都向前移动：```
first_match and dp(i + 1, j + 1)
```6. 将结果存储在记忆缓存中。 

在计算状态之前，检查它是否已经被解决。 

这可以防止重复的递归探索并保证多项式的复杂性。 

### 为什么它有效

 该算法之所以有效，是因为每个递归状态都精确地代表了问题：

 “是吗？`s[i:]`匹配`p[j:]`？”

 对于每个模式位置，该算法都会探索所有合法有效的解释`*`，要么消耗字符，要么完全跳过模式段。 由于每个状态都计算一次并缓存，因此递归最终会解决每个可能的匹配配置，而无需多余的工作。 这保证了正确性和效率。 

## Python 解决方案```python
class Solution:
    def isMatch(self, s: str, p: str) -> bool:
        memo = {}

        def dp(i: int, j: int) -> bool:
            if (i, j) in memo:
                return memo[(i, j)]

            if j == len(p):
                return i == len(s)

            first_match = (
                i < len(s) and
                (s[i] == p[j] or p[j] == '.')
            )

            if j + 1 < len(p) and p[j + 1] == '*':
                result = (
                    dp(i, j + 2) or
                    (first_match and dp(i + 1, j))
                )
            else:
                result = (
                    first_match and
                    dp(i + 1, j + 1)
                )

            memo[(i, j)] = result
            return result

        return dp(0, 0)
```实现首先创建一个名为的记忆字典`memo`。 每个键都是一个元组`(i, j)`表示字符串和模式中的位置。 

嵌套的`dp`函数执行递归匹配逻辑。 第一个操作检查状态是否已经被计算。 如果是，则立即返回缓存的结果。 

当模式指针到达模式末尾时，就会发生基本情况。 此时，字符串指针也必须位于末尾才能匹配成功。 

这`first_match`变量确定当前字符是否兼容。 这包括对通配符的支持`.`。 

实施中最重要的部分是处理`*`。 自从`*`适用于前面的字符，代码检查`p[j + 1]`。 

探索了两种递归可能性：

 - 跳过整个`x*`- 消耗一个字符并继续匹配相同的模式位置

 如果没有`*`存在时，该解决方案执行普通字符匹配并推进两个指针。 

最后，计算结果在返回之前存储在记忆字典中。 

## 解决方案```go
func isMatch(s string, p string) bool {
    type State struct {
        i int
        j int
    }

    memo := make(map[State]bool)
    visited := make(map[State]bool)

    var dp func(i int, j int) bool

    dp = func(i int, j int) bool {
        state := State{i, j}

        if visited[state] {
            return memo[state]
        }

        visited[state] = true

        if j == len(p) {
            memo[state] = (i == len(s))
            return memo[state]
        }

        firstMatch := (
            i < len(s) &&
                (s[i] == p[j] || p[j] == '.')
        )

        var result bool

        if j+1 < len(p) && p[j+1] == '*' {
            result =
                dp(i, j+2) ||
                    (firstMatch && dp(i+1, j))
        } else {
            result =
                firstMatch &&
                    dp(i+1, j+1)
        }

        memo[state] = result
        return result
    }

    return dp(0, 0)
}
```Go 实现遵循与 Python 解决方案相同的递归记忆结构。 由于 Go 不允许像 Python 那样直接将元组作为映射键，因此自定义`State`struct 用于表示`(i, j)`。 

Go 映射无法区分未设置的键和已存储的键`false`值，所以一个单独的`visited`map 用于跟踪状态是否已被计算。 

Go 中的字符串索引以字节为单位进行操作，这在这里是安全的，因为该问题仅保证小写英文字母和特殊 ASCII 字符。

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(m × n) | 每个`(i, j)`状态计算一次 |
 | 空间| O(m × n) | 记忆缓存存储所有状态 |

 递归函数仅取决于索引对`(i, j)`。 自从`i`范围从`0`到`m`和`j`范围从`0`到`n`, 最多有`m × n`独特的状态。 每个状态在递归调用之外执行恒定的工作，从而导致多项式复杂性。 

递归栈深度最多为`O(m + n)`，但记忆表在总空间使用中占主导地位。

 ## 边缘情况

 一种重要的边缘情况是模式可以匹配空字符串。 图案如`"a*"`,`"a*b*"`， 或者`".*"`可以合法地消耗零个字符。 幼稚的实现通常会忘记允许跳过这些部分。 该解决方案通过递归分支正确处理案例`dp(i, j + 2)`，它会跳过整个`x*`部分。 

另一个关键的边缘情况涉及贪婪匹配陷阱。 例如，在`"bbbba"`匹配对`".*a*a"`，最初消耗太多字符会阻止剩余模式正确匹配。 纯粹的贪婪算法在这里会失败。 递归探索确保考虑两种可能性：消耗字符或在需要时停止消耗。 

第三个重要的边缘情况是在字符串完全消耗之前到达模式的末尾。 例如，`"aa"`相对`"a"`必须返回`false`。 基本情况明确检查两个索引是否同时到达各自的末端，确保拒绝部分匹配。 

最后一个微妙的情况发生在重复的递归状态中。 图案有很多`*`运算符可能会导致朴素递归中的指数重新计算。 记忆缓存通过存储每个已解决的问题来防止这种情况发生`(i, j)`状态，即使对于高度分支的输入也能保证高效执行。
