[LeetCode 问题 2590](https://leetcode.com/problems/design-a-todo-list/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、字符串、设计、排序

 ## 解决方案

 ## 问题理解

 这个问题要求我们设计一个小型的任务管理系统，类似于一个轻量级的待办事项应用程序。 我们需要实施一个`TodoList`支持添加任务、将任务标记为已完成、检索用户的所有待处理任务以及按标签过滤待处理任务的类。 

每个任务都属于特定用户，并包含四个重要信息：

 - 独特的顺序`taskId`- 文字描述
 - A`dueDate`- 标签列表

 系统还必须跟踪任务是否已完成。 

关键操作涉及按排序顺序检索任务。 具体来说，当我们获取任务时，它们必须按以下顺序排序`dueDate`，并且只应显示未完成的任务。 此外，按标签过滤应仅返回包含该特定标签的未完成任务。 

让我们用更简单的术语重述一下操作：

 的`addTask`方法为用户创建一个新任务并为其分配一个自动增加的 ID。 第一个任务获取ID`1`,第二个得到ID`2`， 等等。 

这`getAllTasks`方法返回给定用户的所有不完整的任务描述，按截止日期排序。 

这`getTasksForTag`方法的行为类似，但它仅包含包含指定标签的不完整任务。 

这`completeTask`方法将任务标记为已完成，但前提是：

 1.任务确实存在。 
2. 任务属于指定用户。 
3. 任务尚未完成。 

如果其中任何一个条件失败，则该操作不会执行任何操作。 

LeetCode 中的输入由一系列方法调用组成`TodoList`目的。 预期输出对应于每个方法调用的返回值。 方法返回`void`生产`null`。 

这些约束对于选择解决方案策略非常重要。 

- 最多有`100`每个方法的调用次数。 
-`userId`,`taskId`， 和`dueDate`最多都是`100`。 
- 截止日期保证是唯一的。 
- 标签和描述很小。 

这些限制非常小。 由于总共最多有几百个任务，因此即使在检索期间涉及排序的方法也是完全可以接受的。 我们不需要高级的平衡树、堆或索引系统。 

一些边缘情况立即脱颖而出。 

用户可能尚不存在，因此检索方法应返回空列表。 任务完成请求可能引用错误的用户或不存在的任务，这应该安全地不执行任何操作。 任务可能没有标签，这意味着标签过滤自然会排除它们，除非相关。 由于截止日期是唯一的，因此排序永远不会面临决断的歧义。 

## 方法

 ### 蛮力方法

 最直接的解决方案是将每个任务存储在一个全局列表中。 每个任务将包含所有相关信息，包括用户所有权、完成状态、标签和截止日期。 

对于像这样的检索操作`getAllTasks`，我们将扫描整个任务列表并过滤以下任务：

 - 属于所请求的用户
 - 未完成

 然后我们将按截止日期对过滤后的任务进行排序并返回其描述。 

同样，对于`getTasksForTag`，我们会再次扫描每个任务，并额外检查任务的标签列表中是否存在请求的标签。 

这是有效的，因为每个查询都会显式检查所需的条件，并且排序可以保证正确的排序。 

然而，这种方法效率低下，因为每个查询都会扫描全局的所有任务，甚至是属于不相关用户的任务。 

### 最佳方法

 更好的设计是按用户组织任务。 

我们维持：

 1. 哈希映射来自`userId → list of taskIds`2. 哈希映射来自`taskId → task data`3. 顺序任务ID计数器

 每个任务存储：

 - 描述
 - 截止日期
 - 标签
 - 完成状态
 - 所有者（`userId`）

 检索任务时，我们仅检查该用户拥有的任务，而不是全局扫描所有任务。 

由于约束很小，我们可以简单地在检索期间对用户的活动任务进行排序。 截止日期是唯一的，因此订购很简单。 

主要见解是检索是按用户进行的，因此按用户对任务进行分组可以减少不必要的工作并使设计更加清晰。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 每个查询 O(n log n) | O(n) | 扫描全球所有任务 |
 | 最佳 | 每次查询 O(k log k) | O(n) | 仅扫描一位用户的任务 |

 这里：

-`n`= 任务总数
 -`k`= 特定用户的任务数

 自从`k ≤ n`，最优解在实践中严格来说更好。 

## 算法演练

 ### 第 1 步：创建任务存储

 我们维护一个字典映射`taskId`到任务信息。 

每个任务存储：

 -`userId`-`description`-`dueDate`-`tags`-`completed`这允许按任务 ID 进行 O(1) 查找。 

### 步骤 2：按用户对任务进行分组

 我们维护另一个字典：```
user_tasks[userId] → [taskIds]
```这可以防止我们扫描不相关用户的任务。 

每当添加任务时，我们都会将其 ID 添加到相应的用户列表中。 

### 步骤 3：维护顺序任务 ID

 我们的柜台起始于`1`。 

每次`addTask`称为：

 1. 分配当前计数器值。 
2. 增加计数器。 
3. 存储任务。 

这保证了 ID 的顺序。 

### 步骤 4：添加任务

 当`addTask`称为：

 1. 生成新的任务ID。 
2. 创建任务对象。 
3. 将其存储在任务图中。 
4. 将任务ID 添加到用户列表中。 
5. 返回任务ID。 

该操作是恒定时间的。 

### 步骤 5：检索所有任务

 当`getAllTasks(userId)`称为：

 1. 检索该用户的任务 ID。 
2. 迭代它们。 
3. 忽略已完成的任务。 
4. 收集`(dueDate, description)`对。 
5. 按截止日期排序。 
6. 仅返回描述。 

排序可确保正确的排序。 

### 步骤 6：检索标签的任务

 当`getTasksForTag(userId, tag)`称为：

 1. 检索用户的任务 ID。 
2. 跳过已完成的任务。 
3. 检查标签是否存在。 
4.收集匹配任务。 
5. 按截止日期排序。 
6. 退货说明。 

### 第 7 步：完成任务

 当`completeTask(userId, taskId)`称为：

 1. 检查任务是否存在。 
2. 验证所有权。 
3. 确认是否未完成。 
4. 将其标记为已完成。 

如果任何条件失败，则不执行任何操作。 

### 为什么它有效

 正确性来自于在保留任务元数据的同时维护用户和任务之间的一致映射。 

每个任务都只存储一次，并且每个用户仅维护对自己任务的引用。 检索方法显式过滤掉已完成的任务并按截止日期对剩余任务进行排序，保证所需的排序。 由于任务完成仅修改布尔标志，因此已完成的任务自然会从未来的查询中消失。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class TodoList:

    def __init__(self):
        self.next_task_id = 1
        self.tasks = {}
        self.user_tasks = defaultdict(list)

    def addTask(
        self,
        userId: int,
        taskDescription: str,
        dueDate: int,
        tags: List[str]
    ) -> int:

        task_id = self.next_task_id
        self.next_task_id += 1

        self.tasks[task_id] = {
            "userId": userId,
            "description": taskDescription,
            "dueDate": dueDate,
            "tags": set(tags),
            "completed": False
        }

        self.user_tasks[userId].append(task_id)

        return task_id

    def getAllTasks(self, userId: int) -> List[str]:
        pending_tasks = []

        for task_id in self.user_tasks.get(userId, []):
            task = self.tasks[task_id]

            if not task["completed"]:
                pending_tasks.append(
                    (task["dueDate"], task["description"])
                )

        pending_tasks.sort()

        return [description for _, description in pending_tasks]

    def getTasksForTag(
        self,
        userId: int,
        tag: str
    ) -> List[str]:

        filtered_tasks = []

        for task_id in self.user_tasks.get(userId, []):
            task = self.tasks[task_id]

            if (
                not task["completed"]
                and tag in task["tags"]
            ):
                filtered_tasks.append(
                    (task["dueDate"], task["description"])
                )

        filtered_tasks.sort()

        return [description for _, description in filtered_tasks]

    def completeTask(
        self,
        userId: int,
        taskId: int
    ) -> None:

        if taskId not in self.tasks:
            return

        task = self.tasks[taskId]

        if task["userId"] != userId:
            return

        if task["completed"]:
            return

        task["completed"] = True
```实现严格遵循算法。 

构造函数初始化顺序 ID 计数器和两个字典。 这`tasks`字典提供通过 ID 快速查找任务，同时`user_tasks`按所有者对任务 ID 进行分组。 

这`addTask`方法创建一个任务条目并将其插入到两个结构中。 标签被转换为集合，因此成员资格检查变为 O(1)。 

检索方法仅迭代所请求的用户的任务，过滤掉已完成的项目并可选择按标签进行过滤。 由于输出必须按截止日期排序，我们收集`(dueDate, description)`元组并对它们进行排序。 

完成方法在更新状态之前安全地验证任务的存在和所有权。 

## 解决方案```go
package main

import "sort"

type Task struct {
	userId     int
	description string
	dueDate    int
	tags        map[string]bool
	completed   bool
}

type TodoList struct {
	nextTaskID int
	tasks      map[int]*Task
	userTasks  map[int][]int
}

func Constructor() TodoList {
	return TodoList{
		nextTaskID: 1,
		tasks:      make(map[int]*Task),
		userTasks:  make(map[int][]int),
	}
}

func (this *TodoList) AddTask(
	userId int,
	taskDescription string,
	dueDate int,
	tags []string,
) int {

	taskID := this.nextTaskID
	this.nextTaskID++

	tagSet := make(map[string]bool)
	for _, tag := range tags {
		tagSet[tag] = true
	}

	this.tasks[taskID] = &Task{
		userId:     userId,
		description: taskDescription,
		dueDate:    dueDate,
		tags:       tagSet,
		completed:  false,
	}

	this.userTasks[userId] =
		append(this.userTasks[userId], taskID)

	return taskID
}

func (this *TodoList) GetAllTasks(
	userId int,
) []string {

	type Pair struct {
		dueDate    int
		description string
	}

	var pending []Pair

	for _, taskID := range this.userTasks[userId] {
		task := this.tasks[taskID]

		if !task.completed {
			pending = append(
				pending,
				Pair{
					dueDate: task.dueDate,
					description: task.description,
				},
			)
		}
	}

	sort.Slice(
		pending,
		func(i, j int) bool {
			return pending[i].dueDate <
				pending[j].dueDate
		},
	)

	result := make([]string, 0, len(pending))

	for _, task := range pending {
		result = append(
			result,
			task.description,
		)
	}

	return result
}

func (this *TodoList) GetTasksForTag(
	userId int,
	tag string,
) []string {

	type Pair struct {
		dueDate    int
		description string
	}

	var filtered []Pair

	for _, taskID := range this.userTasks[userId] {
		task := this.tasks[taskID]

		if !task.completed &&
			task.tags[tag] {

			filtered = append(
				filtered,
				Pair{
					dueDate: task.dueDate,
					description: task.description,
				},
			)
		}
	}

	sort.Slice(
		filtered,
		func(i, j int) bool {
			return filtered[i].dueDate <
				filtered[j].dueDate
		},
	)

	result := make([]string, 0, len(filtered))

	for _, task := range filtered {
		result = append(
			result,
			task.description,
		)
	}

	return result
}

func (this *TodoList) CompleteTask(
	userId int,
	taskId int,
) {

	task, exists := this.tasks[taskId]

	if !exists {
		return
	}

	if task.userId != userId {
		return
	}

	if task.completed {
		return
	}

	task.completed = true
}
```Go 解决方案密切反映了 Python 实现。 

由于 Go 没有内置集合，标签使用以下方式存储`map[string]bool`。 丢失的密钥自然会计算为`false`，使标签检查变得简单。 

映射对于缺少的键返回零值，因此`this.userTasks[userId]`安全返回`nil`，它在迭代期间的行为就像一个空切片。 

整数溢出不是问题，因为约束非常小。

 ## 边缘情况

 ### 用户不存在

 检索请求可能引用从未添加任务的用户。 幼稚的实现可能会意外地引发查找错误。 

我们的实现通过使用来避免这种情况`.get(userId, [])`在 Python 中并依赖 Go 的零值`nil`切片行为。 在这两种情况下，迭代都会安全地发生在空集合上，从而产生空结果。 

### 完成另一个用户拥有的任务

 任务可能存在，但属于不同的用户。 这是很微妙的，因为仅仅检查任务是否存在是不够的。 

我们的实现在修改状态之前明确验证所有权。 如果`task["userId"] != userId`，操作立即返回，防止意外修改其他用户的任务。 

### 没有标签的任务

 某些任务可能具有空标签列表。 幼稚的实现可能会在标签过滤期间错误地包含它们或产生错误。 

我们通过将标签存储为集合或哈希映射来自然地处理这个问题。 成员资格检查完全失败，这意味着未标记的任务被排除在特定于标记的查询之外。 

### 完成已经完成的任务

 同一任务可能会多次标记为完成。 脆弱的实现可能会出现不可预测的行为或重复的副作用。 

我们的解决方案首先检查完成标志。 如果任务已经完成，该方法立即返回，从而使操作安全且幂等。
