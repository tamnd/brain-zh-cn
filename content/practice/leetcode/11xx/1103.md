[LeetCode 第 1103 题](https://leetcode.com/problems/distribute-candies-to-people/)

 **难度：** 🟢简单
 **主题：** 数学、模拟

 ## 解决方案

 ## 问题理解

 该问题描述了在一排人中顺序分配糖果的过程。 我们有两个整数，`candies`和`num_people`。 目标是模拟按递增顺序分配糖果，直到所有糖果都用完。 

分配模式遵循严格的顺序。 第一个人收到 1 颗糖果，第二人收到 2 颗糖果，第三人收到 3 颗糖果，以此类推。 到达该行中的最后一个人后，该过程返回到开头，但糖果数量继续增加而不是重置。 

比如有4人，第一个周期分配：

 - 0 号人得到 1 号
 - 1 人得到 2 人
 - 2 人得到 3 人
 - 第 3 个人得到 4 个

 第二个周期继续：

 - 0 号人得到 5 号
 - 第 1 个人得到 6
 - 2 人得到 7
 - 第 3 个人得到 8

 这种情况一直持续到没有足够的糖果来完成下一个预定的礼物为止。 在这种情况下，当前的人只会收到所有剩余的糖果。 

输出必须是长度的数组`num_people`，其中每个元素代表在完整分发过程完成后该人收到的糖果总数。 

约束条件很重要：

 -`candies`可以大到`10^9`-`num_people`可以大到`1000`上界相对较小`num_people`意味着存储结果数组很简单。 然而，上界非常大`candies`建议我们应该尽可能避免不必要的昂贵操作。 

立即识别几个边缘情况非常重要。 如果糖果的数量小于下一个预期礼物的数量，则算法必须正确地仅给出剩余的糖果。 如果只有一个人，则无论分配顺序如何，该人都会收到所有糖果。 当糖果在完整分配步骤之后恰好用完时，会发生另一种微妙的情况，因为算法必须干净地终止，而无需尝试另一次迭代。 

## 方法

 ### 蛮力方法

 最直接的解决方案是完全按照问题陈述中的描述来模拟过程。 

我们维持：

 - 用零初始化的结果数组
 - 代表下一个礼物金额的变量
 - 指示下一个应该收到糖果的人的指针

 每一步：

 1. 确定实际可以给予多少糖果
 2.将该金额添加到当前人员上
 3.从剩余的糖果中减去它
 4.循环移动到下一个人
 5. 赠送金额增加1

 这种方法很容易理解，因为它准确地反映了问题陈述。 每次迭代对应一个分布事件。 

该方法是正确的，因为模拟保留了问题所需的准确顺序和数量。 每次糖果的分发都是按照规则进行的。 

虽然`candies`可能很大，分配操作的数量只会增加，直到累积和超过`candies`。 自从：$$1 + 2 + 3 + \dots + k = \frac{k(k+1)}{2}$$迭代次数大约为：$$O(\sqrt{\text{candies}})$$为了`candies = 10^9`，这仍然是可以管理的。 

### 最佳方法的关键见解

 重要的观察是，我们永远不需要模拟单个糖果，只需要模拟分发回合。 

每次迭代都会给出可预测的增量：$$1, 2, 3, 4, \dots$$我们可以直接有效地模拟礼物操作，而不是复杂的数学推导，因为即使对于大量输入，操作数量仍然相对较少。 

对于问题约束来说，模拟方法已经足够有效。 因此，最佳解决方案侧重于干净的循环分配，并仔细处理最终的部分礼物。

 ## 算法演练

 1.初始化一个长度的结果数组`num_people`所有值均设置为零。 

该数组存储每个人在整个过程中收到的糖果总数。 
2. 初始化变量`current_gift`至 1。 

该变量跟踪在下一个分发步骤中应该给出多少糖果。 
3. 初始化变量`person_index`至 0。 

这可以识别当前收到糖果的人。 
4. 在剩余糖果的情况下继续该过程。 

在每次迭代中，我们都会确定实际可以分发多少糖果。 
5. 计算捐赠金额。 

预定的礼物是`current_gift`，但如果剩余的糖果少于该数量，我们只给出剩余的糖果：$$\text{gift} = \min(\text{current\_gift}, \text{candies})$$6. 将礼物添加到当前人员的总数中。 

更新：$$\text{result[person\_index]} += \text{gift}$$7. 从剩余的总数中减去分发的糖果。 

更新：$$\text{candies} -= \text{gift}$$8. 循环移动到下一个人。 

由于行环绕，我们使用模算术：$$\text{person\_index} = (\text{person\_index} + 1) \bmod \text{num\_people}$$9. 增加下一个预期的礼物金额。 

更新：$$\text{current\_gift} += 1$$10. 当所有糖果都用完后，返回结果数组。 

### 为什么它有效

 该算法保持了每个分布步骤都与问题陈述中描述的规则完全匹配的不变性。 每次操作后，当前的礼物金额总是增加一，并且当前的人在数组中正确循环。 使用`min(current_gift, candies)`保证最终的部分分配得到正确处理，且不超过可用糖果。 

## Python 解决方案```python
from typing import List

class Solution:
    def distributeCandies(self, candies: int, num_people: int) -> List[int]:
        result = [0] * num_people
        
        current_gift = 1
        person_index = 0
        
        while candies > 0:
            gift = min(current_gift, candies)
            
            result[person_index] += gift
            candies -= gift
            
            current_gift += 1
            person_index = (person_index + 1) % num_people
        
        return result
```该实现首先创建结果数组，其中每个索引对应于该行中的一个人。 

变量`current_gift`跟踪下一个要分配的金额。 它从 1 开始，因为第一次分配给了一颗糖果。 

这`person_index`变量标识哪个人收到当前礼物。 每次分配后，必要时，模算术会将索引返回到行的开头。 

在循环内部，`gift = min(current_gift, candies)`是正确处理最终部分分布的关键细节。 如果剩余的糖果少于预定的礼物数量，则分发剩余的糖果。 

在更新结果数组并减去分发的糖果后，算法会增加预期的礼物金额并前进到下一个人。 

一旦所有糖果都分发完毕，循环自然终止。 

## 解决方案```go
func distributeCandies(candies int, num_people int) []int {
    result := make([]int, num_people)

    currentGift := 1
    personIndex := 0

    for candies > 0 {
        gift := currentGift
        if candies < currentGift {
            gift = candies
        }

        result[personIndex] += gift
        candies -= gift

        currentGift++
        personIndex = (personIndex + 1) % num_people
    }

    return result
}
```Go 的实现与 Python 解决方案非常相似。 主要区别在于 Go 不提供内置的`min`函数用于整数，因此代码使用显式条件语句来确定实际礼物金额​​。 

结果数组使用以下方法实现为切片`make([]int, num_people)`。 由于 Go 切片会自动使用零值进行初始化，因此不需要额外的设置。 

整数溢出不是问题，因为约束安全地符合 LeetCode 平台上 Go 的标准整数范围。

 ## 边缘情况

 当只有一个人时，就会出现一种重要的边缘情况。 在这种情况下，每个分发步骤都针对同一个人。 有缺陷的实现可能会错误地尝试旋转不存在的索引或错误处理模算术。 该实现自然地处理了这个问题，因为`(0 + 1) % 1`总是评估为`0`，因此单身者会不断收到糖果，直到没有剩余为止。 

当剩余糖果少于预期的下一份礼物数量时，就会发生另一个关键的边缘情况。 例如，如果下一个预期的礼物是 10 个，但只剩下 3 颗糖果，则算法必须恰好分发 3 颗糖果并立即停止。 使用`min(current_gift, candies)`保证这种行为并防止糖果计数为负。 

第三种重要情况发生在糖果在完全分发步骤之后恰好用完时。 某些实现会意外地继续进行另一次迭代或在耗尽后错误地增加变量。 此实现避免了该问题，因为循环条件检查`candies > 0`在每次迭代之前，因此一旦分发完所有糖果，算法就会干净地终止。
