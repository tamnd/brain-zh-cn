 ## 解决方案

 ## 问题理解

 这个问题要求我们分析在线购物平台上的购买活动。 我们得到三个数据库表：`Users`,`Orders`， 和`Items`。 我们的任务是生成一个结果，其中包含每个用户、他们的加入日期以及他们在 2019 年作为买家下的订单数量。 

关键细节是我们计算的是用户的购买量，而不是销售量。 中的相关栏目`Orders`因此表是`buyer_id`， 不是`seller_id`。 

这`Users`表中每个用户包含一行。 每行存储用户的唯一标识符、他们加入平台的日期以及他们最喜欢的品牌。 

这`Orders`表中每个订单包含一行。 每个订单都包含订单日期、买家、卖家和购买的商品。 

这`Items`表存在于模式中，但它实际上与这个特定问题无关，因为输出仅取决于用户和订单计数。 不需要有关物品品牌或物品元数据的信息。 

预期输出应包含：

 -`buyer_id`，对应于用户的`user_id`-`join_date`从`Users`桌子
-`orders_in_2019`，这是订单计数，其中：

 - 用户显示为`buyer_id`- 订单日期在2019年以内

 一个重要的细节是，每个用户都必须出现在结果中，即使他们在 2019 年进行了零购买。这意味着我们不能在`Users`和`Orders`，因为没有符合条件的订单的用户将从结果中消失。 

约束没有明确列出，但由于这是一个 SQL 数据库问题，我们应该假设表可能包含许多行。 因此，有效的聚合和连接非常重要。 我们想要一个能够干净地扫描表而无需不必要的重复工作的解决方案。 

一些边缘情况很重要：

 - 用户可能根本没有订单
 - 用户可能有订单，但 2019 年没有订单
 - 2019年同一买家可能存在多个订单
 - 2019 年以外年份的订单不得计算在内
 - 某些用户可能仅以卖家身份出现，而从不以买家身份出现

 如果排除合格订单为零的用户或意外计算错误年份的订单，幼稚的实现很容易失败。 

## 方法

 ### 蛮力方法

 暴力解决方案将单独处理每个用户并扫描整个用户`Orders`用于统计匹配订单数量的表。 

对于每个用户`Users`表，我们会：

 1. 将计数器初始化为零
 2. 迭代每个订单
 3. 检查是否：

 - 订单的`buyer_id`匹配当前用户
 - 订单日期属于2019年
 4. 如果两个条件都成立，则增加计数器
 5.输出用户信息和最终计数

 这种方法既简单又保证正确性，因为每个订单都会针对每个用户进行明确检查。 

然而，性能较差。 如果有`U`用户和`O`订单，总复杂度变为`O(U × O)`。 对于大型数据集，重复扫描整个订单表会变得低效。 

### 最佳方法

 更好的解决方案是聚合订单计数一次，然后将聚合结果与用户表连接起来。 

关键的观察是我们不需要重复扫描每个用户的订单。 相反，我们可以首先按以下方式对所有 2019 年订单进行分组：`buyer_id`并计算单次传递中的计数。 

计算完这些计数后，我们执行`LEFT JOIN`从`Users`到汇总结果。 左连接可确保所有用户保留在输出中，即使他们没有匹配的订单。 

如果用户2019年没有订单，则聚合结果为`NULL`，所以我们将其替换为`0`使用`IFNULL`或者`COALESCE`。 

这种方法效率更高，因为只需扫描一次订单表即可进行聚合。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(U × O) | O(1) | O(1) | 扫描每个用户的所有订单 |
 | 最佳| O(U + O) | O(U) | 聚合一次，然后连接结果 |

 ## 算法演练

 1. 从`Orders`表并仅过滤订单日期属于 2019 年的行。这可确保立即忽略其他年份的订单。 
2. 对过滤后的订单进行分组`buyer_id`。 分组使我们能够将属于同一买家的所有订单收集在一起。 
3. 统计每组中的订单数量。 结果成为从买家到订单计数的临时映射。 
4. 使用`Users`表作为查询中的主表。 这很重要，因为每个用户都必须出现在最终输出中，即使是零购买的用户。 
5. 执行`LEFT JOIN`之间`Users`并使用以下方式汇总订单计数：

 -`Users.user_id = aggregated.buyer_id`6. 更换任何`NULL`订单计数为`0`使用`IFNULL`或者`COALESCE`。 一个`NULL`当用户在 2019 年没有匹配的订单时出现。 
7. 选择所需的列：

 -`user_id`作为`buyer_id`-`join_date`- 订单计数为`orders_in_2019`### 为什么它有效

 聚合步骤可确保每个买家收到正确数量的 2019 年订单，因为每个合格订单只为其买家组贡献一次。 

左连接保证所有用户保留在最终输出中，包括零匹配订单的用户。 更换`NULL`和`0`正确代表 2019 年未进行购买的用户。 

这些属性共同确保查询准确地生成所需的结果。 

## Python 解决方案```
# Write your MySQL query statement below

SELECT
    u.user_id AS buyer_id,
    u.join_date,
    IFNULL(o.orders_in_2019, 0) AS orders_in_2019
FROM Users u
LEFT JOIN (
    SELECT
        buyer_id,
        COUNT(*) AS orders_in_2019
    FROM Orders
    WHERE YEAR(order_date) = 2019
    GROUP BY buyer_id
) o
ON u.user_id = o.buyer_id;
```该解决方案首先构建一个子查询，计算每个买家 2019 年的订单数量。 

在子查询中：

 -`YEAR(order_date) = 2019`过滤相关订单
 -`GROUP BY buyer_id`每个买家的订单分组
 -`COUNT(*)`计算每个买家的合格订单数量

 然后外部查询使用`Users`表作为主表并执行`LEFT JOIN`与汇总结果。 

使用左连接至关重要，因为 2019 年没有订单的用户仍然需要出现在最终输出中。 

最后，`IFNULL(o.orders_in_2019, 0)`将缺失计数转换为零。 

## 解决方案```

SELECT
    u.user_id AS buyer_id,
    u.join_date,
    IFNULL(o.orders_in_2019, 0) AS orders_in_2019
FROM Users u
LEFT JOIN (
    SELECT
        buyer_id,
        COUNT(*) AS orders_in_2019
    FROM Orders
    WHERE YEAR(order_date) = 2019
    GROUP BY buyer_id
) o
ON u.user_id = o.buyer_id;

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(U + O) | 扫用户一次，下单一次 |
 | 空间| O(U) | 每个买家的聚合商店数量|

 聚合步骤只对每个订单处理一次。 加入步骤只对每个用户处理一次。 因此，总运行时间与用户和订单数量呈线性关系。 

额外的空间来自分组聚合结果，每个用户最多可以包含一个条目。

 ## 边缘情况

 当用户根本没有订单时，就会出现一种重要的边缘情况。 简单的内部联接会将此类用户从结果集中完全删除。 该实现通过使用`LEFT JOIN`从`Users`到聚合订单表。 这保证了每个用户只出现一次。 

另一个重要的边缘情况是，用户有订单，但没有一个是在 2019 年下的。如果没有适当的过滤，这些订单可能会被意外计数。 该实现通过在聚合之前过滤订单来正确处理这个问题`YEAR(order_date) = 2019`。 

当 2019 年多个订单属于同一买家时，就会出现第三种边缘情况。不正确的分组逻辑可能会产生重复的行，而不是单个聚合计数。 该实现通过分组来避免这种情况`buyer_id`并申请`COUNT(*)`，确保每个买家只有一个结果行。 

最后一个边缘案例涉及仅以卖家身份出现的用户。 由于该问题专门要求以买方身份发出的订单，因此卖方活动不得影响计数。 该实现仅正确计算按以下分组的行`buyer_id`。
