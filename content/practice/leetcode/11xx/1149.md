[LeetCode 第 1149 题](https://leetcode.com/problems/article-views-ii/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题给了我们一个名为`Views`。 每行代表一个查看事件，其中用户在特定日期查看了一篇文章。 这些列是：

 | 专栏 | 意义|
 | ---| ---|
 |`article_id`| 正在查看的文章 |
 |`author_id`| 撰写该文章的作者 |
 |`viewer_id`| 查看该文章的用户 |
 |`view_date`| 查看日期 |

 任务是找到在同一日期查看过多篇文章的每个人。 

换句话说，我们必须识别所有`viewer_id`值，使得至少存在一个日期，其中该查看者观看了至少两篇不同的文章。 

输出应包含一个名为`id`，对应于资格赛`viewer_id`价值观。 结果必须按升序排序。 

一个非常重要的细节是表可能包含重复的行。 这意味着同一观看事件可以出现多次。 简单地计算行数的简单解决方案可能会错误地将重复行视为多个文章视图。 因此，我们必须计算在同一日期查看的不同文章。 

考虑这个问题的例子：

 | 查看者 ID | 查看日期 | 文章 ID |
 | ---| ---| ---|
 | 5 | 2019-08-01 | 1 |
 | 5 | 2019-08-01 | 3 |

 观众`5`在同一天查看了两篇不同的文章，因此它们符合资格。 

然而：

 | 查看者 ID | 查看日期 | 文章 ID |
 | ---| ---| ---|
 | 4 | 2019-07-21 | 3 |
 | 4 | 2019-07-21 | 3 |

 这些是同一篇文章的重复行。 观众`4`在该日期仅查看了一篇不同的文章，因此它们不符合资格。 

就 SQL 复杂性而言，约束相对较小，但正确性比原始性能更重要。 关键的挑战是正确地对行进行分组并处理重复项。 

重要的边缘情况包括：

 - 同一文章和日期的重复行
 - 观众在同一日期多次观看同一篇文章
 - 观众在不同日期查看多篇文章，但在同一日期查看的文章数不会超过一篇
 - 同一观众有多个资格日期
 - 多名观众同时参加资格赛

 该问题保证了有效的表行，因此我们不需要处理格式错误的数据或空值。 

## 方法

 ### 蛮力方法

 强力解决方案将单独检查每个查看者和每个日期，然后手动计算查看了多少篇不同的文章。 

一种方法是：

 1. 迭代所有行。 
2. 对于每一行，将其与其他所有行进行比较。 
3. 检查是否：

 - 的`viewer_id`比赛，
 - 的`view_date`比赛，
 - 以及`article_id`是不同的。 
4. 如果存在这样的查看器对，则将该查看器标记为有效。 

这种方法之所以有效，是因为它直接检查查看者是否在同一天查看了多篇不同的文章。 

然而，它的效率很低，因为每一行都可能需要与其他每一行进行比较。 如果有`n`行，这需要`O(n²)`比较。 

当 SQL 提供高效的分组和聚合操作时，这会变得不必要的昂贵。 

### 最佳方法

 关键的见解是该问题本质上是一个分组问题。 

我们需要按以下方式对行进行分组：

 -`viewer_id`-`view_date`然后，对于每个组，计算有多少个不同的`article_id`价值观是存在的。 

如果不同文章数大于`1`，该观看者符合资格。 

SQL 聚合非常适合此目的，因为：

 -`GROUP BY`自然地将行划分为查看者日期组。 
-`COUNT(DISTINCT article_id)`自动删除重复项。 
-`HAVING`聚合后过滤组。 

这产生了一个简洁而有效的解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(1) | O(1) | 比较每对行 |
 | 最佳 | O(n log n) 或 O(n)，具体取决于数据库引擎 | O(n) | 使用分组和聚合 |

 ## 算法演练

 1. 首先使用两者对表行进行分组`viewer_id`和`view_date`。 

这会为每个日期的每个观看者创建一个组。 我们这样做是因为该问题专门询问一个人是否在同一日期查看了多篇文章。 
2. 对于每个组，计算不同组的数量`article_id`价值观。 

使用`COUNT(DISTINCT article_id)`很重要，因为表可能包含重复的行。 没有`DISTINCT`，重复的条目可能会错误地夸大计数。 
3. 仅保留不同文章数大于的组`1`。 

这可确保查看者在该日期实际查看了多篇不同的文章。 
4. 提取`viewer_id`来自资格组的值。 

由于同一观看者可能在多个日期符合资格，因此分组后可能会出现重复的观看者 ID。 
5. 使用`DISTINCT`关于最终观众 ID。 

这保证了每个符合条件的观看者在结果中仅出现一次。 
6. 对结果进行排序`id`按升序排列。 

该问题明确需要排序输出。 

### 为什么它有效

 该算法之所以有效，是因为问题中的每个相关条件都直接编码到分组逻辑中。 

分组依据`(viewer_id, view_date)`隔离一个人一天内的所有观看活动。 计数不同`article_id`值确保重复项不会影响正确性。 过滤计数大于 1 的组可保证仅选择在同一日期看到多篇不同文章的查看者。 

由于每个有效观看者都必须满足这些条件，并且每个合格组都被检查一次，因此该算法是正确的。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT DISTINCT
    viewer_id AS id
FROM Views
GROUP BY viewer_id, view_date
HAVING COUNT(DISTINCT article_id) > 1
ORDER BY id;
```该解决方案使用 SQL 聚合来直接对问题需求进行建模。 

这`GROUP BY viewer_id, view_date`子句为每个日期的每个观看者创建一个组。 这是问题陈述所要求的确切范围。 

下一个，`COUNT(DISTINCT article_id)`计算每组中查看了多少篇独特的文章。 这`DISTINCT`关键字是必不可少的，因为表可能包含重复的行。 

这`HAVING`子句过滤聚合组。 仅保留不同文章数超过 1 的组。 

最后，`SELECT DISTINCT viewer_id AS id`确保每个符合资格的观看者在结果中仅出现一次，即使他们在多个日期符合资格。 

这`ORDER BY id`子句保证升序输出。

 ## 边缘情况

 一种重要的边缘情况是重复行。 该表明确允许重复，这意味着即使查看者重复查看同一篇文章，他们也可能会出现多个视图。 一个有缺陷的解决方案使用`COUNT(*)`而不是`COUNT(DISTINCT article_id)`会错误地将此类观看者归类为有效观看者。 该实现通过仅计算不同的文章 ID 来避免这种情况。 

另一个重要的边缘情况是观众在不同日期观看多篇文章。 例如，观众可能会观看文章`1`周一和文章`2`周二。 这不符合条件，因为该问题需要同一日期的多篇文章。 按两者分组`viewer_id`和`view_date`确保正确隔离日期。 

第三种边缘情况是同一观众在多个日期符合资格。 不使用`DISTINCT`在最终选择中，查看者 ID 可能会在结果集中出现多次。 该实现通过仅选择一次不同的查看者 ID 来正确处理此问题。 

最后一个微妙的边缘情况涉及在同一天重复观看同一篇文章的观众。 即使存在多行，不同文章的数量仍然为一。 使用`COUNT(DISTINCT article_id)`保证这些观众被正确排除。
