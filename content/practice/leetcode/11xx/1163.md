[LeetCode 第 1163 题](https://leetcode.com/problems/last-substring-in-lexicographyal-order/)

 **难度：** 🔴难
 **主题：** 两个指针，字符串

 ## 解决方案

 ## 问题理解

 该问题要求我们找到给定字符串的子字符串`s`这是所有可能的子串中按字典顺序最大的。 

子字符串是字符串的任何连续部分。 对于一个长度的字符串`n`， 有`O(n²)`可能的子字符串，因为每个起始位置都可以与许多结束位置配对。 

词典顺序与词典中使用的顺序相同。 比较两个字符串时：

 - 从左到右比较字符
 - 第一个不同的字符决定较大的字符串
 - 如果一个字符串是另一个字符串的前缀，则较长的字符串被认为较大

 例如：

 -`"bab" > "aba"`因为`'b' > 'a'`-`"tcode" > "leetcode"`因为`'t' > 'l'`-`"banana" > "ban"`因为较短的字符串是前缀

 输入是一个小写英文字符串，长度可达`4 * 10^5`。 这个约束极其重要。 二次或三次算法将会超时。 甚至一个`O(n log n)`解决方案是可以接受的，但该问题是专门为线性时间解决方案设计的。 

关键的观察是每个子字符串都可以由其起始索引表示。 如果我们知道最好的起始索引，那么答案就是从那里开始的后缀。 

一些边缘情况很重要：

 - 所有字符都相同的字符串，例如`"aaaaa"`- 最佳子串在末尾附近开始的字符串
 - 重复的模式，例如`"abababab"`- 非常大的字符串，低效的子字符串创建变得昂贵
 - 多个候选后缀共享长公共前缀

 该问题保证：

 - 字符串非空
 - 仅使用小写英文字母
 - 答案总是存在，因为每个非空字符串至少有一个子字符串

 ## 方法

 ### 蛮力方法

 暴力解决方案生成每个可能的子串并选择字典顺序最大的子串。 

对于每个起始索引`i`，我们生成子字符串：

 -`s[i:i+1]`-`s[i:i+2]`- ...
 -`s[i:n]`然后我们将每个子字符串与当前最大值进行比较。 

这是有效的，因为它明确地检查所有可能性，保证正确性。 然而，对于限制而言，它太慢了。 

有`O(n²)`子字符串，并且比较字符串可以采取`O(n)`最坏情况下的时间。 这导致整体复杂性`O(n³)`在最坏的情况下。 

即使仅考虑后缀进行稍微优化仍然会导致`O(n²)`比较，因为后缀可能共享长前缀。 

### 最佳解决方案的关键见解

 按字典顺序排列的最大子字符串必须是字符串的后缀。 

为什么？ 

如果两个子字符串从同一位置开始，则较长的子字符串在字典顺序上总是较大，因为较短的子字符串是其前缀。 因此，对于每个起始索引，最佳子字符串就是从那里开始的后缀。 

那么问题就变成了：

 > 查找字典顺序最大的后缀。 

我们可以使用类似于布斯算法或最大后缀计算中使用的算法的两指针策略，而不是独立比较每个后缀。 

主要的见解是：

 - 维持两个候选人的起始位置
 - 增量比较字符
 - 批量淘汰落选候选人
 - 永远不要重新访问已经被淘汰的地区

 这使得算法能够在线性时间内运行。

 ## 算法演练

 我们使用三个整数：

 -`best`,当前最佳后缀起始索引
 -`candidate`，另一个竞争的后缀`best`-`offset`，当前比较的字符偏移量

 该算法的工作原理是逐个字符地比较后缀。 

### 第 1 步：初始化两个竞争后缀

 从以下开始：

 1.`best = 0`2.`candidate = 1`3.`offset = 0`这意味着：

 - 从索引开始的后缀`0`目前被认为是最好的
 - 从索引开始的后缀`1`正在与之竞争

 ### 步骤 2：增量比较字符

 比较：

 -`s[best + offset]`-`s[candidate + offset]`有三种可能性。 

### 第 3 步：字符匹配

 如果字符相等：```
s[best + offset] == s[candidate + offset]
```那么这两个后缀都不是更好。 

增加`offset`经过`1`并继续比较更深层次的人物。 

这可以有效地跳过匹配的前缀。 

### 步骤 4：候选后缀更好

 如果：```
s[candidate + offset] > s[best + offset]
```那么候选后缀按字典顺序更大。 

这意味着：

 - 之间开始的所有后缀`best`和`best + offset`也更糟
 - 我们可以安全地丢弃它们

 更新：

 1.`best = candidate`2.`candidate = best + 1`3.`offset = 0`### 第 5 步：当前最佳状态仍然更好

 如果：```
s[candidate + offset] < s[best + offset]
```那么候选人就输了。 

之间开始的所有后缀`candidate`和`candidate + offset`也输了。 

将候选人向前推进：```
candidate = candidate + offset + 1
```重置：```
offset = 0
```### 步骤 6：避免将后缀与其自身进行比较

 如果`best == candidate`, 增量`candidate`。 

### 第 7 步：继续，直到候选人到达终点

 曾经`candidate >= n`，不再存在竞争后缀。 

返回：```
s[best:]
```### 为什么它有效

 该算法保持了不变式，即保证每个被消除的后缀按字典顺序小于当前最佳后缀。 

当两个后缀在某个偏移量上不同时：

 - 在该偏移量处具有较大字符的后缀获胜
 - 任何共享丢失前缀的后缀也可以被消除

 由于每个索引最多被跳过一次，因此该算法以线性时间处理字符串。 

## Python 解决方案```python
class Solution:
    def lastSubstring(self, s: str) -> str:
        n = len(s)

        best = 0
        candidate = 1
        offset = 0

        while candidate + offset < n:
            if s[best + offset] == s[candidate + offset]:
                offset += 1
            elif s[best + offset] < s[candidate + offset]:
                best = best + offset + 1
                if best <= candidate:
                    best = candidate

                candidate = best + 1
                offset = 0
            else:
                candidate = candidate + offset + 1
                offset = 0

            if best == candidate:
                candidate += 1

        return s[best:]
```该实现遵循前面描述的精确的两指针策略。 

变量`best`存储当前最佳后缀起始索引。 变量`candidate`存储与其进行比较的另一个后缀。 变量`offset`跟踪到目前为止有多少个字符匹配。 

当候选后缀仍有剩余字符时，循环将继续。 

当字符匹配时，我们通过增加将比较深入到后缀`offset`。 

当候选后缀变大时，我们将最佳指针向前移动并丢弃所有先前丢失的位置。 这是防止二次行为的关键优化。 

当当前最佳后缀仍然较大时，候选者和所有等效的失败前缀将被一次性跳过。 

最后，我们返回从以下位置开始的后缀：`best`。 

## 解决方案```go
func lastSubstring(s string) string {
	n := len(s)

	best := 0
	candidate := 1
	offset := 0

	for candidate+offset < n {
		if s[best+offset] == s[candidate+offset] {
			offset++
		} else if s[best+offset] < s[candidate+offset] {
			best = best + offset + 1

			if best <= candidate {
				best = candidate
			}

			candidate = best + 1
			offset = 0
		} else {
			candidate = candidate + offset + 1
			offset = 0
		}

		if best == candidate {
			candidate++
		}
	}

	return s[best:]
}
```Go 实现与 Python 版本几乎相同，因为该算法仅依赖于整数索引和直接字符串索引。 

一些特定于 Go 的细节值得注意：

 - Go字符串是字节切片，这里是安全的，因为输入只包含小写英文字母
 - 除了返回的子字符串之外，不需要额外的内存分配
 - 整数溢出不是问题，因为索引保持在字符串长度范围内

 ## 边缘情况

 ### 所有字符都相同

 考虑：```
"aaaaaa"
```每个后缀都以相同的字符开头，因此算法必须进行深入比较才能确定哪个后缀更大。 

这是错误的常见来源，因为幼稚的实现可能会重复比较相同的前缀，从而导致二次行为。 

实施的解决方案使用以下方法有效地处理了这个问题`offset`指针。 匹配的字符会逐渐跳过，而无需从头开始比较。 

### 最佳子串出现在末尾附近

 考虑：```
"azzz"
```字典顺序最大的子串是`"zzz"`。 

假设较长的字符串总是更好的幼稚实现可能会错误地返回`"azzz"`。 

该算法正确地优先考虑较早的字符差异而不是长度。 自从`'z' > 'a'`，从索引开始的后缀`1`立即成为最佳人选。 

### 长重复模式

 考虑：```
"abababababab"
```许多后缀共享长前缀，使得简单的后缀比较极其昂贵。 

这个案例强调了实现是否正确地跳过丢失区域而不是反复重新检查它们。 

两点淘汰策略保证一旦一块后缀输掉，就不再重新考虑。 即使对于高度重复的输入，这也保留了线性时间复杂度。
