[LeetCode 第 1115 题](https://leetcode.com/problems/print-foobar-alternately/)

 **难度：** 🟡 中等
 **主题：** 并发

 ## 解决方案

 ## 问题理解

 这个问题是一个经典的并发同步任务。 We are given a class`FooBar`有两种方法，`foo()`和`bar()`。 每个方法都由单独的线程执行：

 - 线程A重复调用`foo()`- 线程B重复调用`bar()`目标是确保输出序列变为：```
foobarfoobarfoobar...
```确切地`n`次。 

挑战在于线程异步执行。 如果没有同步，操作系统调度程序可能会比另一个线程运行得快得多。 例如，`foo()`线程可能会打印所有`"foo"`之前的值`bar()`线程完全运行，产生不正确的输出，例如：```
foofoofoobarbarbar
```而不是：```
foobarfoobarfoobar
```因此，问题不在于计算或数据处理，而在于协调线程之间的执行顺序。 

输入由单个整数组成`n`，指定组合序列的次数`"foobar"`必须出现。 预期输出是一种交替模式，其中每个`"foo"`紧接着是`"bar"`。 

限制很小：```
1 <= n <= 1000
```这告诉我们性能并不是困难的部分。 重要的挑战是并发执行下的正确性。 虽然`n`很小，如果实现设计不仔细，线程同步错误仍然可能发生。 

一些重要的观察立即浮现出来：

 - 的`foo()`方法必须始终在相应的方法之前执行`bar()`在每次迭代中调用。 
- 两个线程必须重复协调，而不仅仅是一次。 
- 解决方案必须避免竞争条件。 
- 解决方案不得死锁，这意味着两个线程永远等待。 
- 尽管线程调度具有不确定性，但输出顺序必须保持确定性。 

边缘情况主要涉及同步行为：

 -`n = 1`，最小的有效输入，仍然需要严格的排序。 
- 一个线程的快速执行不应破坏顺序。 
- 多次迭代中的重复交替必须保持正确。 

## 方法

 ### 蛮力方法

 一个蛮力的想法是让两个线程独立运行并尝试依靠计时或忙等待来保持顺序。 

例如，可以在循环中重复检查共享变量：```
while turn != "foo":
    pass
```类似地对于`"bar"`。 

如果仔细实现，这在技术上是可行的，因为每个线程都会等到轮到它时才进行打印。 然而，这种方法浪费了 CPU 周期，因为线程在等待时不断旋转。 这称为忙等待或自旋锁定。 

忙等待效率低下，因为处理器会重复检查条件而不是休眠直到收到通知。 在实际系统中，这会严重降低性能。 

另一个糟糕的蛮力策略是使用插入人为延迟`sleep()`。 这是不可靠的，因为线程调度计时是不确定的并且取决于操作系统。 

### 最佳方法

 正确的解决方案使用专门为线程协调设计的同步原语。 

信号量是这里的理想选择。 信号量维护一个内部计数器：

 - 如果计数器为正，则线程可以继续进行。 
- 如果计数器为零，则线程将阻塞，直到另一个线程释放信号量。 

我们使用两个信号量：

 - 一个人控制何时`foo()`可以执行。 
- 一个人控制何时`bar()`可以执行。 

最初：

-`fooSemaphore = 1`-`barSemaphore = 0`这意味着：

-`foo()`被允许先运行。 
-`bar()`最初被阻止。 

后`foo()`印刷`"foo"`，它发出信号`bar()`通过释放第二个信号量。 

后`bar()`印刷`"bar"`，它发出信号`foo()`通过释放第一个信号量。 

这创建了严格的交替执行模式。 

主要见解是同步原语允许线程在等待时有效地休眠，而不是持续消耗 CPU 时间。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n) | O(1) | O(1) | 使用繁忙等待或计时技巧，效率低下且不可靠 |
 | 最佳 | O(n) | O(1) | O(1) | 使用信号量进行精确的线程同步 |

 ## 算法演练

 1. 创建两个同步原语，一个用于`foo()`线程和一个用于`bar()`线。 
2. 初始化信号量控制`foo()`有价值`1`。 这允许`foo()`线程立即执行。 
3. 初始化信号量控制`bar()`有价值`0`。 这迫使`bar()`线程最初等待。 
4. 内部`foo()`:

 - 打印前，获取`foo`信号。 
- 如果信号量不可用，线程会自动阻塞。 
- 打印`"foo"`。 
- 释放`bar`信号量所以`bar()`线程可以继续进行。 
5. 内部`bar()`:

 - 获得`bar`信号。 
- 这保证了`"foo"`已经为当前迭代打印。 
- 打印`"bar"`。 
- 释放`foo`信号量所以下一个`"foo"`可以执行。 
6. 完全重复此过程`n`两个线程中的时间。 

信号量强制执行严格的交替执行顺序：```
foo -> bar -> foo -> bar
```无论线程调度顺序如何。 

### 为什么它有效

 关键的不变量是：```
Only one thread is allowed to proceed at a time.
```最初，仅`foo()`可能会运行，因为其信号量计数为正。 打印后，`foo()`将执行权限转移到`bar()`通过释放第二个信号量。 

相似地，`bar()`将权限转移回`foo()`打印后。 

由于执行权限在每次打印操作后交替，因此输出必须始终遵循确切的顺序：```
foobarfoobar...
```任何竞争条件都不能违反此顺序，因为信号量会串行执行。 

## Python 解决方案```python
from threading import Semaphore
from typing import Callable

class FooBar:
    def __init__(self, n: int):
        self.n = n
        self.foo_semaphore = Semaphore(1)
        self.bar_semaphore = Semaphore(0)

    def foo(self, printFoo: 'Callable[[], None]') -> None:

        for _ in range(self.n):
            self.foo_semaphore.acquire()

            # printFoo() outputs "foo". Do not change or remove this line.
            printFoo()

            self.bar_semaphore.release()

    def bar(self, printBar: 'Callable[[], None]') -> None:

        for _ in range(self.n):
            self.bar_semaphore.acquire()

            # printBar() outputs "bar". Do not change or remove this line.
            printBar()

            self.foo_semaphore.release()
```构造函数初始化两个信号量。```python
self.foo_semaphore = Semaphore(1)
```允许`foo()`线程立即启动。```python
self.bar_semaphore = Semaphore(0)
```迫使`bar()`线程等待`"foo"`已打印。 

里面`foo()`，线程首先获取其信号量。 一旦允许，它就会打印`"foo"`然后释放`bar`信号。 这唤醒了`bar()`线。 

里面`bar()`，则发生相反的过程。 线程等待直到`foo()`发出信号，打印`"bar"`，然后释放`foo`下一次迭代的信号量。 

该实现直接反映了算法演练中描述的同步策略。 

## 解决方案```go
package main

import "sync"

type FooBar struct {
	n       int
	fooChan chan struct{}
	barChan chan struct{}
}

func NewFooBar(n int) *FooBar {
	fb := &FooBar{
		n:       n,
		fooChan: make(chan struct{}, 1),
		barChan: make(chan struct{}, 1),
	}

	fb.fooChan <- struct{}{}

	return fb
}

func (fb *FooBar) Foo(printFoo func()) {
	for i := 0; i < fb.n; i++ {
		<-fb.fooChan

		// printFoo() outputs "foo". Do not change or remove this line.
		printFoo()

		fb.barChan <- struct{}{}
	}
}

func (fb *FooBar) Bar(printBar func()) {
	for i := 0; i < fb.n; i++ {
		<-fb.barChan

		// printBar() outputs "bar". Do not change or remove this line.
		printBar()

		fb.fooChan <- struct{}{}
	}
}
```Go 在标准库中没有内置信号量，因此缓冲通道通常用于同步。 

通道的行为与信号量类似：

 - 从通道接收数据会阻塞，直到有值可用为止。 
- 发送到已满缓冲的通道会阻塞，直到空间存在为止。 

这`fooChan`通道以一个令牌开始，允许`Foo()`首先执行。 这`barChan`开始为空，迫使`Bar()`等待。 

每次打印操作后，通过向另一个通道发送令牌来转移执行权限。 

与 Python 不同，Go 使用通道作为一流的并发原语，这使得实现简洁且惯用。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 每个线程都准确执行`n`同步和打印操作|
 | 空间| O(1) | O(1) | 仅存储恒定数量的同步原语 |

 时间复杂度是线性的，因为每次迭代执行固定量的工作。 信号量操作是恒定时间的。 

空间复杂度保持不变，因为该算法只存储两个同步对象，而不管`n`。

 ## 边缘情况

 一种重要的边缘情况是尽可能最小的输入：```
n = 1
```即使只有一次迭代，仍然需要同步。 如果没有适当的协调，`bar()`理论上，线程可以尝试首先打印。 信号量初始化保证`foo()`总是在之前执行`bar()`。 

当一个线程的运行速度明显快于另一个线程时，就会出现另一种重要的边缘情况。 例如，`foo()`线程可能会重复尝试执行之前`bar()`已完成。 如果没有同步，这可能会产生如下输出：```
foofoofoo...
```信号量会阻塞快速线程，直到较慢的线程完成其转动，从而确保正确的交替，无论调度速度如何。 

第三个重要的边缘情况涉及许多迭代，例如：```
n = 1000
```如果信号量释放被遗忘或放错地方，重复同步可能会暴露死锁错误。 该实现在每次成功的打印操作后都会小心地释放相反的信号量，从而保证所有迭代的进展。
