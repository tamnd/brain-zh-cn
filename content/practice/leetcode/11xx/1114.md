[LeetCode 第 1114 题](https://leetcode.com/problems/print-in-order/)

 **难度：** 🟢简单
 **主题：** 并发

 ## 解决方案

 ## 问题理解

 这个问题要求我们协调三个独立的线程，使它们按照严格的顺序执行，而不管操作系统如何调度它们。 我们有一个包含三种方法的类，`first()`,`second()`， 和`third()`。 每个方法都由不同的线程调用，并且线程可以按任何顺序启动。 

目标是保证以下执行顺序：

 1.`first()`必须在之前完成`second()`开始
 2.`second()`必须在之前完成`third()`开始

 重要的细节是线程调度是不确定的。 即使输入显示为`[1,2,3]`，操作系统实际上可能会在线程 1 之前运行线程 3。如果没有同步，输出可能会变成`"thirdfirstsecond"`或任何其他不正确的排序。 

示例中显示的输入数组实际上并未传递到求解方法中。 它仅描述了测试期间线程启动的顺序。 实现本身必须针对每个可能的调度顺序正确工作。 

限制非常小，因为总是只有三种方法。 这意味着挑战不在于算法的可扩展性，而在于正确的同步和线程协调。 关键的困难是确保后面的方法等到前面的方法完成。 

当线程执行无序时，简单地立即调用打印函数的简单实现将会失败。 另一个常见错误是使用忙等待，其中一个线程不断检查循环中的条件。 这种方法浪费了 CPU 资源，并且被认为是糟糕的并发设计。 

该问题保证：

 - 仅有一个线程调用每个方法
 - 这些方法每个被调用一次
 - 所需的顺序始终是`first -> second -> third`由于这些保证，我们只需要一个定向依赖链的同步原语。 

## 方法

 ### 蛮力方法

 强力方法将使用带有共享布尔标志的忙等待。 例如，`second()`可以连续检查是否`first()`已经完成，并且`third()`可以连续检查是否`second()`已完成。 

在 Python 中，这在概念上可能类似于：```
while not first_done:
    pass
```这是有效的，因为后面的方法拒绝继续，直到前面的方法设置完成标志。 

然而，这种方法效率低下，因为等待线程在轮询条件时不断消耗 CPU 周期。 这称为旋转或忙等待。 在真正的并发系统中，繁忙的等待是一种浪费，并且会严重损害性能。 

尽管问题规模很小，但适当的同步原语是正确的解决方案，因为它们允许线程有效地休眠，直到收到通知。 

### 最佳方法

 更好的解决方案使用同步原语，例如信号量、锁、事件或条件变量。 

关键的见解是我们不需要重复检查先前的任务是否完成。 相反，我们可以阻塞一个线程，直到另一个线程明确发出信号表明它可以继续。 

依赖链很简单：

 -`second()`取决于`first()`-`third()`取决于`second()`我们可以用两个同步对象来表示这些依赖关系：

 - 一个物体发出信号`first()`已完成
 - 另一个物体表明`second()`已完成

 在Python中，`threading.Event`对于这个问题非常自然。 事件以未设置状态开始。 线程调用`wait()`阻塞直到另一个线程调用`set()`。 

在 Go 中，通道是一种优雅的并发原语，用于在 goroutine 之间发出完成信号。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(最坏情况下无限轮询) | O(1) | O(1) | 使用忙等待，浪费 CPU 周期 |
 | 最佳 | O(1) | O(1) | O(1) | O(1) | 使用正确的同步原语 |

 ## 算法演练

 1. 初始化期间创建两个同步信号。 

第一个信号代表是否`first()`已完成。 第二个信号代表是否`second()`已完成。 

最初，两个信号都被阻止或取消设置，因为两个操作都尚未完成。 
2. 执行`first()`立即地。 

自从`first()`没有依赖关系，它总是可以立即运行。 

打印后`"first"`，表明第一阶段已完成。 这会唤醒任何在内部等待的线程`second()`。 
3.制作`second()`等待`first()`。 

打印前`"second"`， 这`second()`方法等待直到第一个完成信号可用。 

一次`first()`完成并发出完成信号，`second()`收益。 

打印后`"second"`，表明第二阶段已完成。 这会唤醒任何在内部等待的线程`third()`。 
4.制作`third()`等待`second()`。 

打印前`"third"`， 这`third()`方法等待直到第二个完成信号可用。 

一次`second()`完成并发出完成信号，`third()`安全进行。 

### 为什么它有效

 核心不变量是每个方法只能在其依赖关系完成后才能继续。 

-`second()`无法执行直到`first()`信号完成
 -`third()`无法执行直到`second()`信号完成

 由于同步原语强制执行这些依赖性，因此无论线程调度顺序如何，都可以保证顺序。 

## Python 解决方案```python
from threading import Event
from typing import Callable

class Foo:
    def __init__(self):
        self.first_done = Event()
        self.second_done = Event()

    def first(self, printFirst: 'Callable[[], None]') -> None:

        # printFirst() outputs "first". Do not change or remove this line.
        printFirst()

        self.first_done.set()

    def second(self, printSecond: 'Callable[[], None]') -> None:

        self.first_done.wait()

        # printSecond() outputs "second". Do not change or remove this line.
        printSecond()

        self.second_done.set()

    def third(self, printThird: 'Callable[[], None]') -> None:

        self.second_done.wait()

        # printThird() outputs "third". Do not change or remove this line.
        printThird()
```该实现使用Python的`threading.Event`类，它提供了线程之间简单的信号机制。 

里面`__init__`，我们创建两个事件对象：

 -`first_done`跟踪完成情况`first()`-`second_done`跟踪完成情况`second()`这`first()`方法立即执行，因为它没有依赖项。 打印后`"first"`，它调用`set()`在`first_done`。 这将事件永久标记为已完成，并唤醒等待该事件的所有线程。 

这`second()`方法首先调用`wait()`在`first_done`。 如果`first()`尚未完成，线程会高效阻塞，而不消耗 CPU 资源。 一旦事件被设置，执行就会继续并且`"second"`被打印。 

之后，`second()`通过设置信号完成`second_done`。 

这`third()`方法遵循相同的模式。 它等待着`second_done`打印前`"third"`。 

这个结构直接反映了问题所需的依赖链。 

## 解决方案```go
package main

type Foo struct {
	firstDone  chan struct{}
	secondDone chan struct{}
}

func NewFoo() *Foo {
	return &Foo{
		firstDone:  make(chan struct{}),
		secondDone: make(chan struct{}),
	}
}

func (f *Foo) First(printFirst func()) {
	// Do not change this line
	printFirst()

	close(f.firstDone)
}

func (f *Foo) Second(printSecond func()) {
	<-f.firstDone

	/// Do not change this line
	printSecond()

	close(f.secondDone)
}

func (f *Foo) Third(printThird func()) {
	<-f.secondDone

	// Do not change this line
	printThird()
}
```Go 解决方案使用通道进行同步。 

每个通道充当完成信号：

 -`firstDone`信号完成`First()`-`secondDone`信号完成`Second()`表达式：```go
<-f.firstDone
```阻塞直到通道关闭。 

后`First()`完成，关闭`firstDone`，这会解锁`Second()`。 同样，之后`Second()`完成，关闭`secondDone`，这会解锁`Third()`。 

这种方法是 Go 的惯用方法，因为通道是专门为 goroutine 协调和同步而设计的。 

与 Python 不同，Go 在这里不使用事件对象。 相反，封闭的频道自然地充当一次性广播信号。

 -`first()`-`third()`-`second()`初始状态：

 | 变量| 状态|
 | --- | --- |
 |`first_done`| 取消设置 |
 |`second_done`| 取消设置 |

 执行轨迹：

 | 步骤| 主题 | 行动| 之后的状态 |
 | --- | --- | --- | --- |

## 测试用例```python
from threading import Thread
from queue import Queue

def run_test(order):
    foo = Foo()
    output = Queue()

    def print_first():
        output.put("first")

    def print_second():
        output.put("second")

    def print_third():
        output.put("third")

    methods = {
        1: lambda: foo.first(print_first),
        2: lambda: foo.second(print_second),
        3: lambda: foo.third(print_third),
    }

    threads = [Thread(target=methods[x]) for x in order]

    for thread in threads:
        thread.start()

    for thread in threads:
        thread.join()

    result = "".join(list(output.queue))
    return result

# Provided example 1
assert run_test([1, 2, 3]) == "firstsecondthird"

# Provided example 2
assert run_test([1, 3, 2]) == "firstsecondthird"

# Completely reversed order
assert run_test([3, 2, 1]) == "firstsecondthird"

# Second starts first
assert run_test([2, 1, 3]) == "firstsecondthird"

# Third starts first
assert run_test([3, 1, 2]) == "firstsecondthird"

# Random valid permutation
assert run_test([2, 3, 1]) == "firstsecondthird"

print("All tests passed!")

 ## 边缘情况

 一种重要的边缘情况发生在以下情况：`third()`在两者之前开始`first()`和`second()`。 一个幼稚的实现可能允许`third()`立即打印，产生无效输出。 在我们的实施中，`third()`阻止`second_done.wait()`，所以它无法继续，直到`second()`明确表示完成。 

另一个重要的边缘情况发生在`second()`之前开始`first()`。 如果没有同步，输出可能会变成`"secondfirstthird"`。 我们的解决方案通过强制处理这个问题`second()`等待`first_done`继续之前的事件。 

一个微妙的边缘情况涉及线程调度延迟。 例如，`first()`可能会提前很久完成`second()`甚至开始。 在这种情况下，同步机制仍必须正常工作。 事件对象和关闭的通道永久保留其信号状态，因此即使等待线程稍后到达，它也会立即继续而不会发生死锁。 

最后一个边缘情况涉及 CPU 效率。 繁忙的等待解决方案在技术上可能会产生正确的结果，但它们在等待时会持续消耗处理器时间。 我们的实现完全避免了这个问题，因为阻塞线程可以有效地休眠，直到同步原语通知为止。
