 # LeetCode 1127，用户购买平台

 ## 问题理解

 的`Spending`表记录用户在电商平台上的购买行为。 每行代表一个用户在特定日期的支出，使用`mobile`平台或`desktop`平台。 

该表有四列：

 | 专栏 | 意义|
 | ---| ---|
 |`user_id`| 进行购买的用户 |
 |`spend_date`| 购买日期 |
 |`platform`| 任何一个`mobile`或者`desktop`|
 |`amount`| 花费金额|

 主键是`(user_id, spend_date, platform)`，这意味着用户每天每个平台最多可以拥有一行。 

任务是为每个日期生成摘要。 对于每个日期，我们必须将用户准确分类为以下三类之一：

 | 类别 | 意义|
 | ---| ---|
 |`mobile`| 用户当天仅使用手机 |
 |`desktop`| 用户当天仅使用桌面 |
 |`both`| 用户当天同时使用移动设备和桌面设备 |

 对于每个类别和每个日期，我们必须计算：

 1.`total_amount`, 支出总额
 2.`total_users`，该类别的用户数量

 一个重要的细节是，结果必须始终包含每个日期的所有三个平台类别，即使计数和金额为零。 

例如，如果某一天没有人使用这两个平台，我们仍然需要：```
| date | both | 0 | 0 |
```输入大小没有明确说明，但数据库问题通常期望解决方案能够最大限度地减少不必要的连接和重复扫描。 由于聚合是问题的核心，因此理想的解决方案应该在计算总数之前对用户进行有效分组。 

几种边缘情况可能会导致幼稚实现中的错误：

 - 一个用户一天只能出现一次，这意味着他们属于任一`mobile`或者`desktop`。 
- 一个用户一天可能出现两次，每个平台一次，这意味着他们属于`both`。 
- 某些日期可能没有一个或多个类别中的用户，但这些行仍必须显示为零值。 
- 同一天多个用户可以属于同一类别，因此分类后必须进行聚合。 

关键的挑战是在汇总总数之前对每个日期的每个用户进行正确分类。 

## 方法

 ### 蛮力方法

 强力策略将独立检查每个日期并重复扫描表以确定哪些用户使用哪些平台。 

对于每个`(user_id, spend_date)`配对，我们可以：

 1. 搜索该用户和日期的所有行。 
2.判断用户是否使用：

 - 仅限移动设备
 - 仅限桌面
 - 两者
 3. 将总计汇总到不同的组中。 

这是可行的，因为每个用户的平台使用情况最终可以通过检查所有匹配的行来确定。 

但是，这种方法效率低下，因为它会重复扫描表以获取相同的信息。 如果有`n`行，重复查找很容易导致二次行为。 

### 最佳方法

 关键的观察是分类应该每个发生一次`(user_id, spend_date)`一对。 

我们首先聚合每个用户在给定日期的活动，而不是重复扫描表：

 - 计算用户当天的总支出。 
- 计算他们使用了多少个不同的平台。 

由于平台只能`mobile`或者`desktop`:

 -`COUNT(DISTINCT platform) = 2`表示用户同时使用了两者。 
- 否则，单一平台值告诉我们用户是否仅使用移动设备或仅使用桌面设备。 

对用户进行分类后，我们执行第二个聚合步骤：

 - 分组依据`spend_date`和类别
 - 金额
 - 计算用户数量

 最后我们生成所有的`(date, platform)`组合，因此可以使用以下方法用零填充缺失的类别`LEFT JOIN`。 

这种方法避免了重复扫描并以结构化方式执行聚合。 

## 方法比较

 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(n) | 重复扫描行以对用户进行分类 |
 | 最佳| O(n) | O(n) | 使用分组聚合和分类 |

 ## 算法演练

 1. 首先，对表格进行分组`(user_id, spend_date)`。 

此步骤会合并用户在特定日期的所有活动。 我们计算：

 - 该用户当天的总支出
 - 使用了多少个不同的平台
 2.确定用户的类别。 

如果不同平台计数为`2`，类别为`both`。 

否则，用户只使用一个平台，因此我们可以使用`MAX(platform)`或者`MIN(platform)`检索平台名称。 
3. 存储分类结果。 

分类后，每个用户日对成为一行，其中包含：

 -`spend_date`- 类别 （`mobile`,`desktop`， 或者`both`）
 - 花费总额
 4. 聚合分类行。 

分组依据：

 -`spend_date`- 类别

 然后计算：

 - 总支出
 - 用户总数
 5. 生成每个日期的所有平台类别。 

创建一个小型派生表，其中包含：

 -`mobile`-`desktop`-`both`将其与所有不同的日期交叉连接。 
6. 左连接聚合结果。 

这可确保丢失的类别仍然出现。 

如果不存在匹配行，则使用`COALESCE`取代`NULL`价值观与`0`。 

### 为什么它有效

 该算法之所以有效，是因为给定日期的每个用户都属于一个互斥类别：

 - 仅限移动设备
 - 仅限桌面
 - 两者

 第一个聚合步骤通过检查该用户在该日期使用的所有平台来保证正确的分类。 第二个聚合步骤正确地将同一类别内的用户组合起来。 最后，交叉连接保证了每个日期每个平台类别的完整输出覆盖。 

## Python 解决方案```python
# Write your MySQL query statement below

WITH user_summary AS (
    SELECT
        user_id,
        spend_date,
        CASE
            WHEN COUNT(DISTINCT platform) = 2 THEN 'both'
            ELSE MAX(platform)
        END AS platform_type,
        SUM(amount) AS total_amount
    FROM Spending
    GROUP BY user_id, spend_date
),
aggregated AS (
    SELECT
        spend_date,
        platform_type,
        SUM(total_amount) AS total_amount,
        COUNT(*) AS total_users
    FROM user_summary
    GROUP BY spend_date, platform_type
),
platforms AS (
    SELECT 'mobile' AS platform
    UNION ALL
    SELECT 'desktop'
    UNION ALL
    SELECT 'both'
),
dates AS (
    SELECT DISTINCT spend_date
    FROM Spending
)

SELECT
    d.spend_date,
    p.platform,
    COALESCE(a.total_amount, 0) AS total_amount,
    COALESCE(a.total_users, 0) AS total_users
FROM dates d
CROSS JOIN platforms p
LEFT JOIN aggregated a
    ON d.spend_date = a.spend_date
   AND p.platform = a.platform_type;
```该解决方案使用通用表表达式将逻辑组织成清晰的阶段。 

这`user_summary`CTE 执行最重要的步骤，根据日期对每个用户进行分类。 这`COUNT(DISTINCT platform)`判断用户是否属于`both`类别。 否则，`MAX(platform)`检索使用的单一平台。 

这`aggregated`然后，CTE 将属于同一类别和日期的用户组合起来。 此时，计算出最终总数。 

这`platforms`CTE 明确创建所需的平台类别。 这很重要，因为某些类别可能并不自然存在于聚合数据中。 

这`dates`CTE 提取每个不同的支出日期。 

最后，查询交叉连接日期和平台以创建所有所需的组合，然后左连接聚合结果。`COALESCE`将缺失值转换为零。

 ## 边缘情况

 ### 用户出现在两个平台上

 一个用户可能同时拥有`mobile`行和一个`desktop`在同一日期行。 简单的实现可能会对用户进行两次计数，每个类别一次。 

该解决方案通过首先分组来避免这种情况`(user_id, spend_date)`分类前。 一旦分组，用户就成为当天的单个逻辑实体，确保他们被专门放入`both`类别。 

### 约会缺少类别

 有些日期可能并不自然地包含所有这三个类别。 例如，一天可能仅包含移动购买。 

简单的聚合会完全忽略结果中缺失的类别。 然而，该问题明确要求每个类别都出现。 

该解决方案通过将所有日期与所有三个平台标签交叉连接，然后左连接聚合结果来处理此问题。 使用以下方法将缺失值替换为零`COALESCE`。 

### 同一类别中的多个用户

 同一天，多个用户可能属于同一类别。 幼稚的实现可能会错误地覆盖总数而不是累加它们。 

第二个聚合步骤正确分组`(spend_date, platform_type)`并计算：

 -`SUM(total_amount)`-`COUNT(*)`这保证了所有用户对最终总计的正确贡献。
