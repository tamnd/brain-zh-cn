[LeetCode 第 1125 题](https://leetcode.com/problems/smallest-sufficient-team/)

 **难度：** 🔴难
 **主题：** 数组、动态规划、位操作、位掩码

 ## 解决方案

 ## 问题理解

 这个问题要求我们建立尽可能最小的团队，以共同涵盖所有所需的技能。 

我们有两个输入：

 -`req_skills`，独特所需技能的列表
 -`people`， 在哪里`people[i]`包含人所拥有的技能`i`如果一个团队的每一项技能都被认为是足够的`req_skills`出现在至少一名团队成员的技能列表中。 

我们的目标不是找到所有有效的团队，而是找到人数最少的团队。 

输出应该是代表所选人员的索引列表。 

约束在这里非常重要：

 - 最多可以有 16 项所需技能
 - 最多可容纳 60 人

 所需技能的数量较少是关键的观察结果。 由于最多只有 16 个技能，因此我们可以使用位掩码来表示所涵盖的技能集。 16 位的位掩码可以代表技能的每个可能的子集。 

例如：

 - 位`0`代表`"java"`- 少量`1`代表`"nodejs"`- 少量`2`代表`"reactjs"`然后像这样的面具`101₂`方法：

-`"java"`被覆盖
 -`"reactjs"`被覆盖
 -`"nodejs"`没有被覆盖

 这将问题转化为子集上的最短覆盖问题。 

一些边缘情况很重要：

 - 有些人可能没有贡献有用的技能
 - 多人可能拥有重叠的技能
 - 一个人可以同时掌握多种技能
 - 最优解可能不是唯一的
 - 贪婪的方法可能会失败，因为局部最优选择并不总是产生全局最小的团队

 该问题保证至少存在一支足够的团队，因此我们永远不需要处理不可能的情况。 

## 方法

 ### 蛮力方法

 最直接的解决方案是检查每个可能的人群子集。 

对于每个子集：

 1. 结合该子集中的人所拥有的所有技能
 2.检查是否涵盖了所有必需的技能
 3. 跟踪找到的最小有效子集

 由于有`n`人们，有`2^n`可能的子集。 

当人数达到 60 人时，这是完全不可行的：$$2^{60}$$这是一个天文数字。 

尽管暴力解决方案在概念上很简单并且保证能找到最佳答案，但它无法在合理的时间限制内运行。 

### 关键见解

 重要的观察是，所需技能的数量非常少，最多 16 种。 

我们可以跟踪技能的子集，而不是跟踪人员的子集。 

只有：$$2^{16} = 65536$$可能的技能组合。 

这是可以管理的。 

我们可以在以下情况下使用动态规划：

 - 状态是代表涵盖技能的位掩码
 - 该值是实现该面具的最小团队

 对于每个人：

 - 确定他们贡献哪些技能
 - 尝试扩展每个现有状态
 - 如果新团队规模较小，则更新 DP 表

 这将人员指数级问题转变为技能指数级问题，由于技能数量很少，所以很容易处理。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(2^n × n × s) | O(2^n × n × s) | O(1) | O(1) | 检查每个人的子集 |
 | 使用位掩码的最佳动态规划 | O(n × 2^m) | O(n × 2^m) | O(2^m) | O(2^m) | 跟踪每个技能子集的最小团队 |

 在哪里：

-`n = number of people`-`m = number of required skills`-`s = average skills per person`## 算法演练

 ### 第 1 步：为每个技能分配一个位位置

 我们创建从技能名称到位索引的映射。 

例子：```
"java"   -> 0
"nodejs" -> 1
"reactjs"-> 2
```这使我们能够有效地将技能集表示为整数。 

### 步骤 2：将每个人的技能转换为位掩码

 对于每个人，我们计算一个代表他们拥有的所有技能的位掩码。 

例子：```
["nodejs", "reactjs"]
```变成：```
110₂
```这意味着此人涵盖技能 1 和技能 2。 

### 步骤3：初始化DP表

 我们使用字典：```
dp[mask] = smallest team achieving this mask
```最初：```
dp[0] = []
```面具`0`意味着没有涵盖任何技能，而空团队就实现了这一点。 

### 步骤 4：处理每个人

 对于每个人：

 1.拿走他们的技能面具
 2. 迭代所有现有的DP状态
 3.将人的技能与现有的面具相结合

 这给出：```
new_mask = old_mask | person_mask
```如果新团队小于当前存储的团队`new_mask`，更新一下。 

### 步骤 5：继续建设更好的国家

 随着处理的人员越来越多，DP 表逐渐积累针对越来越大的技能子集的最佳团队。 

由于每次转换要么改进状态，要么保持不变，因此 DP 表始终存储每个掩码的最小已知团队。 

###第6步：返回全覆盖状态

 目标掩码是：```
(1 << number_of_skills) - 1
```这代表了涵盖的所有技能。 

我们归还为该面具存储的团队。 

### 为什么它有效

 DP 状态不变量为：

 >`dp[mask]`始终存储迄今为止发现的最小团队，该团队完全涵盖了以下技能`mask`。 

每一个可能的团队都可以通过一次添加一个人来逐步构建。 在处理过程中，算法通过状态转换考虑所有此类组合。 

每当发现具有某项技能的较小团队时，它就会取代之前的团队。 

由于所有人都经过处理并且每个可达到的技能子集都被探索，因此完整技能掩码的最终 DP 条目必须代表最小规模的足够团队。 

## Python 解决方案```python
from typing import List

class Solution:
    def smallestSufficientTeam(
        self,
        req_skills: List[str],
        people: List[List[str]]
    ) -> List[int]:

        skill_to_bit = {
            skill: i
            for i, skill in enumerate(req_skills)
        }

        people_masks = []

        for skills in people:
            mask = 0

            for skill in skills:
                mask |= 1 << skill_to_bit[skill]

            people_masks.append(mask)

        dp = {0: []}

        for person_index, person_mask in enumerate(people_masks):

            current_dp = list(dp.items())

            for existing_mask, team in current_dp:

                new_mask = existing_mask | person_mask

                if new_mask == existing_mask:
                    continue

                new_team = team + [person_index]

                if (
                    new_mask not in dp
                    or len(new_team) < len(dp[new_mask])
                ):
                    dp[new_mask] = new_team

        full_mask = (1 << len(req_skills)) - 1

        return dp[full_mask]
```实现首先将每个所需的技能转换为一个位位置。 这使得恒定时间位操作成为可能，而不是昂贵的集合比较。 

然后每个人的技能被压缩成一个整数掩码。 此预处理步骤简化了后续的 DP 转换。 

DP 字典存储每个可实现的技能组合的最小团队。 键是技能掩码，值是所选人员指数列表。 

对于每个人，我们迭代当前的 DP 状态。 我们使用按位或来计算新的涵盖技能集。 如果添加当前人员可以提高该州的团队规模，我们就会更新 DP 表。 

迭代使用`list(dp.items())`以避免在迭代字典时修改字典。 

最后，算法返回与涵盖所有必需技能的掩码相对应的团队。 

## 解决方案```go
func smallestSufficientTeam(req_skills []string, people [][]string) []int {

	skillToBit := make(map[string]int)

	for i, skill := range req_skills {
		skillToBit[skill] = i
	}

	peopleMasks := make([]int, len(people))

	for i, skills := range people {

		mask := 0

		for _, skill := range skills {
			mask |= 1 << skillToBit[skill]
		}

		peopleMasks[i] = mask
	}

	dp := make(map[int][]int)
	dp[0] = []int{}

	for personIndex, personMask := range peopleMasks {

		currentStates := make(map[int][]int)

		for k, v := range dp {

			copied := make([]int, len(v))
			copy(copied, v)

			currentStates[k] = copied
		}

		for existingMask, team := range currentStates {

			newMask := existingMask | personMask

			if newMask == existingMask {
				continue
			}

			newTeam := append([]int{}, team...)
			newTeam = append(newTeam, personIndex)

			oldTeam, exists := dp[newMask]

			if !exists || len(newTeam) < len(oldTeam) {
				dp[newMask] = newTeam
			}
		}
	}

	fullMask := (1 << len(req_skills)) - 1

	return dp[fullMask]
}
```Go 实现遵循与 Python 版本相同的逻辑，但有一些特定于语言的注意事项。 

Go 切片是可变引用，因此我们必须在修改切片之前显式复制切片。 否则，多个 DP 状态可能会意外共享相同的底层数组。 

DP表是使用一个`map[int][]int`，其中整数键是技能掩码。 

位运算对于 Go 整数的表现很自然，因为最大技能计数仅为 16，完全在标准整数限制之内。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(n × 2^m) | O(n × 2^m) | 每个人都可以更新每个技能子集 |

 在哪里：

-`n`是人数
 -`m`是所需技能的数量

 DP 状态的数量由`2^m`。 自从`m ≤ 16`，最大状态数只有65536。 

对于每个人，我们可能会遍历所有状态一次。 这产生：$$O(n \times 2^m)$$存储的团队贡献了额外的内存使用量，但状态数量仍然主导着复杂性分析。

 ## 边缘情况

 ### 没有技能的人

 有些人的技能列表可能是空的。 幼稚的实现可能仍将它们包含在转换中，从而创建不必要的状态或不正确的更新。 

这个实现可以安全地处理它们，因为它们的掩码是`0`。 与任何现有状态结合时：```
new_mask = existing_mask | 0
```状态不会改变。 该算法明确地跳过此类无改进的转换。 

### 多个具有相同技能的人

 几个人可能贡献完全相同的技能。 幼稚的实施可能会导致团队冗余并变得不必要的庞大。 

DP 更新规则仅在找到严格较小的团队时才替换状态。 因此，多余的人自然会被忽视，除非他们改进解决方案。 

### 一个人涵盖所有技能

 有时一个人就已经满足了所有要求。 贪婪或结构不当的解决方案可能仍然会在发现这一点之前建立更大的团队。 

位掩码 DP 立即处理这个问题。 一旦该人被处理，团队规模为 1 时就会达到全技能面具，这是理论上的最小值，永远无法提高。
