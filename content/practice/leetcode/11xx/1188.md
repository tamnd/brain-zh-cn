 ## 解决方案

 ## 问题理解

 这个问题要求我们实现一个线程安全的有界阻塞队列，它是一种以先进先出（FIFO）顺序存储元素的数据结构，但增加了多个线程可能同时访问它的约束。 队列有固定的容量，有两种类型的操作：`enqueue`，将元素添加到队列中，并且`dequeue`，从队列中删除元素。 如果队列已满，则`enqueue`操作必须阻塞，直到有可用空间。 同样，如果队列为空，则`dequeue`操作必须阻塞，直到有元素可用为止。 这`size`操作只是返回队列中当前元素的数量并且不会阻塞。 

输入由队列的容量和序列组成`enqueue`和`dequeue`由多个生产者和消费者线程执行的操作。 输出是结果`dequeue`操作和队列的最终大小。 

约束告诉我们，生产者和消费者的数量很少（各最多 8 个），并且最大队列大小适中（30）。 这意味着我们不需要担心极端的可扩展性，但我们必须正确处理线程同步。 边缘情况包括尝试`dequeue`从空队列中，`enqueue`到一个完整的队列，以及多个线程之间可能相互解除阻塞的交互。 

简化实施的关键保证：数量`enqueue`调用始终大于或等于`dequeue`调用次数，调用次数上限为40次。 

## 方法

 一种幼稚或暴力的方法是使用列表或数组实现队列，并简单地追加和弹出元素而不同步。 此方法在多线程上下文中会失败，因为并发访问可能会破坏队列状态，并且当队列已满或为空时，它不会处理阻塞。 

最佳方法利用线程同步原语，例如`threading.Lock`为了相互排斥和`threading.Condition`用于发信号。 一个`Condition`允许线程等待，直到满足特定条件（例如，队列不空或未满），然后安全地继续。 使用这些原语可确保一次只有一个线程修改队列，而其他线程则有效阻塞而不是忙等待。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | 每次操作 O(1) | O（容量）| 非线程安全，无法处理阻塞 |
 | 最佳| 每次操作 O(1) | O（容量）| 线程安全，使用条件变量有效处理阻塞 |

 ## 算法演练

 1. 将队列初始化为空列表并存储最大容量。 创建一个`Lock`互斥对象和两个`Condition`对象，一种用于生产者（当队列已满时等待），一种用于消费者（当队列为空时等待）。 
2. 对于`enqueue`操作时，获取锁进入临界区。 当队列已满时，请致电`producer_condition.wait()`阻塞直到有可用空间。 一旦有空间，将元素追加到队列中，并通知任何等待的消费者该元素可用`consumer_condition.notify()`。 
3. 对于`dequeue`操作，获取锁。 当队列为空时，调用`consumer_condition.wait()`阻塞直到有元素入队。 一旦元素可用，将其从队列前端删除，并通知任何等待的生产者空间现在可用：`producer_condition.notify()`。 
4. 的`size`操作只是获取锁并返回队列的长度。 这可确保返回的大小与正在进行的操作一致。 

为什么它有效：`Lock`确保一次只有一个线程修改队列，从而防止竞争情况。 这`Condition`对象确保线程在队列无法继续时有效地阻塞，并在满足必要条件时准确地唤醒。 队列保持 FIFO 顺序，因为元素添加在后面并从前面删除。 

## Python 解决方案```python
import threading

class BoundedBlockingQueue(object):

    def __init__(self, capacity: int):
        self.capacity = capacity
        self.queue = []
        self.lock = threading.Lock()
        self.not_full = threading.Condition(self.lock)
        self.not_empty = threading.Condition(self.lock)

    def enqueue(self, element: int) -> None:
        with self.not_full:
            while len(self.queue) >= self.capacity:
                self.not_full.wait()
            self.queue.append(element)
            self.not_empty.notify()

    def dequeue(self) -> int:
        with self.not_empty:
            while not self.queue:
                self.not_empty.wait()
            value = self.queue.pop(0)
            self.not_full.notify()
            return value

    def size(self) -> int:
        with self.lock:
            return len(self.queue)
```Python 解决方案使用`Lock`为了相互排斥。 二`Condition`对象管理生产者和消费者的阻塞和唤醒。`enqueue`当队列已满时等待，并且`dequeue`当队列为空时等待。 这可确保正确的 FIFO 行为和正确的线程同步。 

## 解决方案```go
package main

import "sync"

type BoundedBlockingQueue struct {
    capacity int
    queue    []int
    lock     sync.Mutex
    notFull  *sync.Cond
    notEmpty *sync.Cond
}

func Constructor(capacity int) BoundedBlockingQueue {
    b := BoundedBlockingQueue{
        capacity: capacity,
        queue:    make([]int, 0, capacity),
    }
    b.notFull = sync.NewCond(&b.lock)
    b.notEmpty = sync.NewCond(&b.lock)
    return b
}

func (b *BoundedBlockingQueue) Enqueue(element int) {
    b.lock.Lock()
    defer b.lock.Unlock()
    for len(b.queue) >= b.capacity {
        b.notFull.Wait()
    }
    b.queue = append(b.queue, element)
    b.notEmpty.Signal()
}

func (b *BoundedBlockingQueue) Dequeue() int {
    b.lock.Lock()
    defer b.lock.Unlock()
    for len(b.queue) == 0 {
        b.notEmpty.Wait()
    }
    val := b.queue[0]
    b.queue = b.queue[1:]
    b.notFull.Signal()
    return val
}

func (b *BoundedBlockingQueue) Size() int {
    b.lock.Lock()
    defer b.lock.Unlock()
    return len(b.queue)
}
```Go 实现镜像了 Python 版本。`sync.Mutex`确保相互排斥。`sync.Cond`处理满队列或空队列的阻塞。 切片用于队列，并仔细附加和切片用于 FIFO 行为。

 ## 边缘情况

 关键边缘情况是队列容量为 1 时。入队和出队都必须适当阻塞，并且代码不得死锁。 该实现使用条件变量来处理这一问题，并确保一次只有一个线程修改队列。 

当多个线程同时尝试排入完整队列时，会出现另一种边缘情况。 这里，`notFull.wait()`确保每个生产者阻塞直到有可用空间。
