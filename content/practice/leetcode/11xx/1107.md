[LeetCode 第 1107 题](https://leetcode.com/problems/new-users-daily-count/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 我们有一个名为的数据库表`Traffic`记录不同日期的不同用户活动。 每行包含一个`user_id`， 一个`activity`类型，以及一个`activity_date`。 用户可能在同一天出现多次，因为他们可以执行不同的活动，例如`login`,`logout`,`homepage`,`jobs`， 或者`groups`。 该表还可能包含重复的行。 

任务是确定最近的每个日期`90`天数从`2019-06-30`，有多少用户在该日期**首次**登录。 

关键细节是我们没有计算所有登录事件。 我们只关心用户的**最早登录日期**。 找到每个用户的首次登录日期后，我们仅包含那些在允许范围内的日期`90-day`窗口结束于`2019-06-30`。 最后，对于每个有效日期，我们计算当天首次登录的用户数量。 

为了更好地理解需求，考虑用户`5`从例子来看：

 - 用户`5`已登录`2019-03-01`- 用户`5`再次登录`2019-06-21`虽然`2019-06-21`在过去 90 天内，我们**不**在那一天计算该用户，因为他们的首次登录已经发生在`2019-03-01`。 

输入表示活动日志，其中：

 -`user_id`识别用户。 
-`activity`告诉我们发生了什么动作。 
-`activity_date`告诉我们事情发生的时间。 

预期输出包含：

 | 专栏 | 意义|
 | ---| ---|
 |`login_date`| 至少有一个用户首次登录的日期 |
 |`user_count`| 在该日期首次登录的用户数量 |

 仅应显示计数非零的日期。 

问题陈述保证`activity`是一组固定的枚举值之一，并且可能存在重复的行。 由于这是一个数据库问题，因此效率很重要，因为表可能很大。 我们希望避免重复扫描表中的每个用户或日期。 

预先识别一些边缘情况很重要。 用户可能在同一天有多个登录记录，可能存在重复的行，或者用户可能在不同日期登录多次。 我们必须始终为每个用户使用**最短登录日期**。 另一个微妙的情况是，首次登录发生在 90 天窗口之外的用户，即使后来的登录发生在窗口之内，也不能被计算在内。 

## 方法

 ### 蛮力方法

 一种简单的方法是首先识别每个不同的用户，然后为每个用户扫描所有行以查找其最早登录日期。 之后，我们将检查最早的登录是否在过去 90 天内，并增加该日期的计数器。 

这是有效的，因为对于每个用户，我们明确计算他们的首次登录日期，这保证了正确性。 然而，它的效率很低，因为对于每个用户，我们都会重复扫描整个表。 如果有`n`行和`u`用户，这可能需要`O(u × n)`工作。 

在数据库系统中，重复的全表扫描是昂贵且不必要的。 

### 关键见解

 重要的观察是我们只关心**每个用户的最早登录日期**。 SQL 已经提供了聚合函数来有效地解决这个问题。 

我们可以：

 1. 过滤行`activity = 'login'`。 
2. 分组依据`user_id`。 
3. 计算`MIN(activity_date)`为每个用户获取首次登录日期。 
4. 将首次登录日期过滤为仅 90 天内的日期`2019-06-30`。 
5. 按登录日期再次分组并对用户进行计数。 

这避免了重复扫描并让数据库引擎执行高效的分组操作。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(u × n) | O(u) | 重复扫描每个用户的表 |
 | 最佳 | O(n log n) | O(n log n) | O(u) | 使用分组和聚合来有效计算首次登录日期 |

 ## 算法演练

 1、首先过滤`Traffic`表仅包含其中的行`activity = 'login'`。 这是必要的，因为在确定用户的首次登录日期时只有登录事件才重要。 
2. 对筛选后的行进行分组`user_id`。 对于每个用户，计算最小值`activity_date`。 这为我们提供了每个用户登录的最早日期。 
3. 从这些首次登录日期起，仅保留那些在允许的 90 天范围内的日期`2019-06-30`。 由于今天是固定的，截止日期变为`2019-04-01`。 
4. 按首次登录日期对剩余结果进行分组。 
5. 计算每个日期有多少用户。 
6. 返回包含列的结果表：

 -`login_date`-`user_count`### 为什么它有效

 正确性来自于这样一个事实：对于每个用户，我们只计算一个值，即他们的最早登录日期`MIN(activity_date)`。 由于每个用户仅贡献一次，因此按首次登录日期分组可以保证准确的计数。 计算最小值后进行过滤可确保我们正确排除首次登录发生在 90 天窗口之前的用户，即使他们稍后再次登录也是如此。 

## Python 解决方案```python
# Write your MySQL query statement below

SELECT
    first_login AS login_date,
    COUNT(*) AS user_count
FROM (
    SELECT
        user_id,
        MIN(activity_date) AS first_login
    FROM Traffic
    WHERE activity = 'login'
    GROUP BY user_id
) AS first_logins
WHERE first_login >= DATE_SUB('2019-06-30', INTERVAL 90 DAY)
GROUP BY first_login;
```该查询首先将表过滤为仅登录活动。 然后我们分组`user_id`并计算`MIN(activity_date)`确定每个用户的首次登录日期。 

这个中间结果存储在一个名为的派生表中`first_logins`。 使用子查询使逻辑更容易理解，因为我们将查找首次登录日期的任务与计算它们分开。 

接下来，我们应用 90 天过滤器。 由于今天固定为`2019-06-30`，我们使用`DATE_SUB('2019-06-30', INTERVAL 90 DAY)`动态确定有效范围。 

最后，我们分组`first_login`并对每个日期的用户进行计数。 

## 解决方案```go

 ## 边缘情况

 ### 一个用户多次登录

 一个常见的错误是计算每个登录事件而不是第一个登录事件。 用户可能会在几个月内重复登录。 如果我们直接分组`activity_date`，以后的登录会错误地增加计数。 使用`MIN(activity_date)`保证每个用户只贡献一次。 

### 表中的重复行

 该问题明确指出可能存在重复行。 如果我们简单地计算登录记录，这可能会导致计数过多。 由于我们首先分组`user_id`并计算最早登录日期，重复项不会改变最小值，因此不会影响正确性。 

### 90 天期限之外首次登录

 当用户在截止时间之前首次登录，但在有效期内再次登录时，会出现一个微妙的错误。 幼稚的实现可能会错误地计算稍后的登录。 通过先计算最早登录并随后进行过滤，我们可以正确排除此类用户。 

### 首次登录无效

 每个用户的首次登录可能发生在 90 多天之前`2019-06-30`。 在这种情况下，过滤后的数据集将变为空，并且查询正确地不返回任何行，而不是产生无效计数。
