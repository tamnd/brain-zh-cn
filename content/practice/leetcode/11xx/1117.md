[LeetCode 第 1117 题](https://leetcode.com/problems/building-h2o/)

 **难度：** 🟡 中等
 **主题：** 并发

 ## 解决方案

 ## 问题理解

 这个问题要求我们协调多个并发线程，以便它们正确地形成水分子。 水分子恰好包含两个氢原子和一个氧原子，因此同步逻辑必须确保线程仅以三个一组进行，其中三个线程恰好由两个氢原子和一个氧线程组成。 

每个氢线程调用`hydrogen()`方法，每个氧气线程调用`oxygen()`方法。 在这些方法中，我们得到了回调函数：

 -`releaseHydrogen()`，打印`"H"`-`releaseOxygen()`，打印`"O"`单个分子内的字符顺序并不重要。 例如，`"HHO"`,`"HOH"`， 和`"OHH"`都是有效的，因为每个基团恰好包含两个氢和一个氧。 

重要的要求是分子不能重叠。 在下一个分子的任何线继续进行之前，当前分子的所有三个线必须完成结合在一起。 如果我们将最终输出分成三个字符的块，则每个块必须恰好包含两个字符`H`人物和一个`O`特点。 

示例中的输入字符串表示线程到达的顺序，而不是所需的输出顺序。 线程可以按任意顺序到达，但同步逻辑必须正确协调它们。 

限制很小：

 -`1 <= n <= 20`- 总长度为`3 * n`- 确切地`2 * n`存在氢
 - 正是如此`n`氧气存在

 因为这是一个并发问题，难点不在于计算复杂度，而在于同步正确性。 一个简单的实现可以很容易地允许：

 - 氢气太多，无法在氧气到达之前继续进行
 - 多个分子错误地交错
 - 线程永远等待的死锁
 - 不同步共享状态导致的竞争条件

 该问题保证了足够的氢和氧线最终到达形成有效的分子，因此我们不需要处理不可能的情况。 

## 方法

 ### 蛮力方法

 强力解决方案将维护用于等待氢和氧线程的共享计数器，并重复轮询，直到有足够的原子可用于形成分子。 

例如，线程可以：

 1. 获取互斥体
 2. 增加其对应的计数器
 3.不断检查是否`hydrogen >= 2`和`oxygen >= 1`4.等待时睡觉或旋转
 5. 分子形成后计数器递减

 这种方法在概念上可行，但效率低下且容易出错。 繁忙等待会浪费 CPU 周期，因为线程会重复唤醒并检查条件。 如果没有仔细实施障碍，也很难保证正确的分子分组并避免竞争条件。 

尽管约束很小，但并发问题应该使用适当的同步原语而不是主动轮询。 

### 最佳方法

 关键的见解是信号量自然地模拟资源可用性。 

我们需要执行两条规则：

 1. 一个分子中只能有两条氢线参与
 2. 一个分子中只能有一根氧丝参与

 我们可以使用：

 - 氢信号量初始化为`2`- 氧气信号量初始化为`1`- 屏障初始化为`3`信号量控制每种类型的线程数量可以进入当前分子。 屏障确保所有三个线程都等到完整的分子组装完毕后再继续。 

该过程的工作原理如下：

 - 氢螺纹获得一份氢许可证
 - 氧气线获得一份氧气许可证
 - 每个线程打印它的字符
 - 每个线程在屏障处等待
 - 一旦所有三个线程到达，屏障就会将它们一起释放
 - 离开屏障后，释放下一个分子的许可证

 这种设计清楚地分离了：

 - 使用信号量进行资源控制
 - 使用屏障的分子同步

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n) | O(1) | O(1) | 使用共享计数器和忙等待 |
 | 最佳 | O(n) | O(1) | O(1) | 使用信号量和屏障同步 |

 ## 算法演练

 ### 最优同步算法

 1. 初始化一个带有 value 的氢信号量`2`。 

这允许最多两个氢线参与当前分子。 
2. 用 value 初始化氧气信号量`1`。 

这使得恰好有一根氧线参与当前分子。 
3. 初始化一个具有大小的屏障`3`。 

该屏障确保形成分子的所有三个线程在它们中的任何一个继续之前到达。 
4. 当氢线程到达时：

 - 获得一份氢信号许可证
 - 打印`"H"`使用`releaseHydrogen()`- 在屏障处等待，直到两个氢气和一个氧气到达
 - 屏障完成后释放氢信号量许可证
 5. 当氧气线程到达时：

 - 获得氧气信号许可证
 - 打印`"O"`使用`releaseOxygen()`- 在屏障处等待，直到完整的分子形成
 - 屏障完成后释放氧气信号量许可
 6. 一旦三个线程到达屏障：

 - 屏障同时释放所有三个
 - 该分子被认为是完整的
 - 许可证可用于下一个分子

 ### 为什么它有效

 信号量保证每个分子中最多有两个氢线程和一个氧线程参与。 屏障保证这三个线程在任何下一个分子开始之前一起完成。 因此，每组三个释放的线程始终恰好包含两个氢和一个氧。 

## Python 解决方案```python
from threading import Semaphore, Barrier
from typing import Callable

class H2O:
    def __init__(self):
        self.hydrogen_semaphore = Semaphore(2)
        self.oxygen_semaphore = Semaphore(1)
        self.barrier = Barrier(3)

    def hydrogen(self, releaseHydrogen: 'Callable[[], None]') -> None:
        self.hydrogen_semaphore.acquire()

        # releaseHydrogen() outputs "H". Do not change or remove this line.
        releaseHydrogen()

        self.barrier.wait()

        self.hydrogen_semaphore.release()

    def oxygen(self, releaseOxygen: 'Callable[[], None]') -> None:
        self.oxygen_semaphore.acquire()

        # releaseOxygen() outputs "O". Do not change or remove this line.
        releaseOxygen()

        self.barrier.wait()

        self.oxygen_semaphore.release()
```实现首先在构造函数内创建两个信号量和一个屏障。 

氢信号量从值开始`2`，意味着只有两条氢线可以进入当前分子。 氧气信号量以值开始`1`，只允许一根氧气线。 

里面`hydrogen()`，线程首先获得氢气许可证。 如果两个氢线程已经参与当前分子，则额外的氢线程会阻塞，直到获得许可为止。 

获得权限后，线程打印`"H"`使用提供的回调函数。 

然后线程在屏障处等待。 屏障会暂停执行，直到恰好三个参与线程到达。 这确保分子完成以原子方式发生。 

一旦所有三个线程到达，屏障就会将它们一起释放。 然后氢线程释放其信号量许可证，以便未来的分子可以再次使用氢。 

氧气逻辑是相同的，只是它使用氧气信号量，该信号量只允许每个分子有一个氧气线程。 

## 解决方案```go
package main

import (
	"sync"
)

type H2O struct {
	hydrogenSemaphore chan struct{}
	oxygenSemaphore   chan struct{}
	barrier           cyclicBarrier
}

func NewH2O() *H2O {
	h := &H2O{
		hydrogenSemaphore: make(chan struct{}, 2),
		oxygenSemaphore:   make(chan struct{}, 1),
		barrier:           newCyclicBarrier(3),
	}

	h.hydrogenSemaphore <- struct{}{}
	h.hydrogenSemaphore <- struct{}{}

	h.oxygenSemaphore <- struct{}{}

	return h
}

func (h *H2O) Hydrogen(releaseHydrogen func()) {
	<-h.hydrogenSemaphore

	// releaseHydrogen() outputs "H". Do not change or remove this line.
	releaseHydrogen()

	h.barrier.wait()

	h.hydrogenSemaphore <- struct{}{}
}

func (h *H2O) Oxygen(releaseOxygen func()) {
	<-h.oxygenSemaphore

	// releaseOxygen() outputs "O". Do not change or remove this line.
	releaseOxygen()

	h.barrier.wait()

	h.oxygenSemaphore <- struct{}{}
}

type cyclicBarrier struct {
	total      int
	count      int
	generation int
	mutex      sync.Mutex
	cond       *sync.Cond
}

func newCyclicBarrier(total int) cyclicBarrier {
	b := cyclicBarrier{
		total: total,
	}

	b.cond = sync.NewCond(&b.mutex)

	return b
}

func (b *cyclicBarrier) wait() {
	b.mutex.Lock()

	gen := b.generation
	b.count++

	if b.count == b.total {
		b.count = 0
		b.generation++
		b.cond.Broadcast()
		b.mutex.Unlock()
		return
	}

	for gen == b.generation {
		b.cond.Wait()
	}

	b.mutex.Unlock()
}
```Go 版本没有像 Python 那样提供内置的可重用屏障`threading.Barrier`，所以我们使用我们自己的循环屏障`sync.Mutex`和`sync.Cond`。 

使用缓冲通道模拟信号量：

 - 氢通道容量为`2`- 氧气通道容量为`1`从通道接收数据会获得许可，发送回通道会释放许可。 

自定义循环障碍轨道：

 - 有多少线程已到达
 - 当前世代数
 - 等待线程的条件变量

 当所需数量的线程到达时，所有等待线程同时被唤醒。

 ## 边缘情况

 ### 氧气线程先于氢气线程到达

 一个常见的错误是即使没有足够的氢线程也允许氧线程立即继续。 例如，如果多个氧气线程首先到达，则实现必须阻塞除一个氧气线程之外的所有线程，直到两个氢气可用。 

氧信号量只允许一条氧线进入当前分子，从而干净地解决了这个问题。 额外的氧线程保持阻塞状态，直到当前分子完成。 

### 多余的氢线程提前到达

 当许多氢线程先于任何氧线程到达时，会发生另一种棘手的情况。 如果没有同步限制，所有氢线程可能会立即打印，产生无效输出，例如`"HHHH"`。 

氢信号量可以防止这个问题，因为在氧线程加入分子之前只有两个氢线程可以继续进行。 

### 分子交织

 最微妙的并发问题是允许不同分子的原子混合在一起。 例如，一个分子可能在另一个分子开始之前部分形成。 

该屏障通过在任何下一个分子开始形成之前强制三个线程同步在一起来防止这种情况发生。 这保证了每个连续的三个输出字符组恰好包含两个氢和一个氧。
