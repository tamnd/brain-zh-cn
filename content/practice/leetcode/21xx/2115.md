[LeetCode 问题 2115](https://leetcode.com/problems/find-all-possible-recipes-from-given-supplies/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、字符串、图论、拓扑排序

 ## 解决方案

 ## 问题理解

 这个问题要求我们确定当我们从一组可用供应开始并允许递归创建其他配方时可以创建哪些配方。 

每个食谱都有所需成分的列表。 有些成分是我们已经拥有的基本用品，而其他成分本身可能就是食谱。 一旦配方变得可创建，它就会有效地转变为新的可用供应，可以帮助创建其他配方。 

输入由三个数组组成：

 -`recipes[i]`是的名字`i-th`食谱。 
-`ingredients[i]`包含创建所需的所有成分`recipes[i]`。 
-`supplies`包含最初无限量供应的成分。 

目标是返回最终可以创建的每个配方。 

重要的细节是食谱可以依赖于其他食谱。 例如：

-`"sandwich"`可能需要`"bread"`-`"bread"`本身可能就是一个需要的食谱`"yeast"`和`"flour"`如果我们能够创造`"bread"`， 然后`"bread"`变得可用于创建`"sandwich"`。 

问题还提到菜谱可能会形成循环。 例如：

-`"A"`需要`"B"`-`"B"`需要`"A"`除非其中一个配方已可作为供应，否则无法创建此类配方。 

约束相对较小，最多有 100 个配方和 100 个补给，但依赖结构自然形成了一个图。 尽管暴力破解可能会低于这些限制，但预期的解决方案是基于图的并使用拓扑排序。 

一些边缘情况很重要：

 - 食谱的原料已经完全可以供应。 
- 食谱取决于多个深度的其他食谱。 
- 永远无法解决的循环依赖。 
- 既不是供应品也不是食谱的成分。 
- 不交互的独立配方链。 

该问题保证配方名称和供应名称是唯一的，并且每个成分列表不包含重复项。 

## 方法

 ### 蛮力方法

 一个简单的解决方案会重复扫描所有食谱并检查食谱的每种成分当前是否可用。 

我们从一套包含所有用品的套装开始。 然后：

 1. 迭代每个食谱。 
2. 如果配方的所有成分均可用，则将配方本身添加到可用组中。 
3. 重复此过程，直到无法添加新配方为止。 

这是有效的，因为随着配方的依赖关系得到解决，配方逐渐变得可用。 最终，当无法创建额外的配方时，系统会稳定下来。 

这种方法的主要问题是效率低下。 我们反复重新检查依赖项仍然不可用的食谱。 在最坏的情况下，在最终结果稳定之前会发生许多不必要的扫描。 

尽管约束足够小，这可以通过，但它不是最佳的，并且不能很好地扩展。 

### 最优方法，图+拓扑排序

 关键的见解是这个问题从根本上来说是一个依赖图问题。 

食谱取决于其成分。 当某种成分可用时，它有助于解锁需要它的食谱。 

这与拓扑排序非常相似：

 - 每种成分都指向依赖它的食谱。 
- 每个食谱都会追踪仍然缺少多少必需成分。 
- 当所有必需的成分都可用时，配方就可以创建了。 

我们可以使用以下方法对此进行建模：

 - 从成分→需要它的食谱的图表。 
- 入度计数代表每个配方仍需要多少成分。 
- 包含当前可用项目的队列。 

最初：

 - 所有补给都插入队列中。 
- 每当有物品可用时，我们就会减少需要它的食谱的依赖计数。 
- 如果配方的剩余依赖性计数变为零，则该配方现在可创建并添加到队列中。 

这可以有效地一次性处理依赖关系。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(R² × I) | O(R + S) | 反复重新扫描食谱直至稳定 |
 | 最佳| O(R × I) | O(R × I) | 使用图遍历和拓扑排序 |

 在哪里：

-`R`= 食谱数量
 -`I`= 平均成分数
 -`S`= 供应数量

 ## 算法演练

 ### 第 1 步，构建依赖关系图

 创建一个图表，其中每种成分映射到依赖于它的所有食谱。 

例如：```
"bread" -> ["sandwich", "burger"]
"meat" -> ["sandwich", "burger"]
```这使我们能够在某种成分可用时快速找到哪些食谱受到影响。 

我们还创建了一个`indegree`地图：```
indegree[recipe] = number of ingredients still needed
```最初，这等于每个食谱的成分总数。 

### 第2步，初始化队列

 将所有初始供应插入队列中。 

这些都是一开始就已经准备好的材料。 

我们使用队列是因为这自然匹配依赖项的广度优先处理。 

### 步骤 3，处理可用成分

 当队列不为空时：

 1. 删除一项可用的项目。 
2. 根据该项目查找所有食谱。 
3. 减少剩余的依赖数量。 
4. 如果菜谱计数变为零：

 - 将其添加到结果列表中。 
- 将其推入队列，因为它现在可以作为其他食谱的成分。 

### 步骤 4，继续直到精疲力竭

 最终队列变空。 

此时：

 - 每个可实现的食谱都已创建。 
- 循环或不可能的配方仍未解决​​，因为它们的依赖计数永远不会达到零。 

### 为什么它有效

 该算法保持了这样的不变性：放入队列中的任何项目都绝对可用。 

最初，供应品确实如此。 之后，只有当所有必需的成分都可用时才会添加食谱，这意味着它们可以有效创建。 

每个依赖项在其成分可用时都会被处理一次。 因此，当一个配方的入度达到零时，它的所有成分都得到满足，保证了正确性。 

循环自然会失败，因为除非外部电源中断循环，否则所涉及的配方都无法将其依赖性计数减少到零。 

## Python 解决方案```python
from collections import defaultdict, deque
from typing import List

class Solution:
    def findAllRecipes(
        self,
        recipes: List[str],
        ingredients: List[List[str]],
        supplies: List[str]
    ) -> List[str]:

        graph = defaultdict(list)
        indegree = {}

        for recipe, ingredient_list in zip(recipes, ingredients):
            indegree[recipe] = len(ingredient_list)

            for ingredient in ingredient_list:
                graph[ingredient].append(recipe)

        queue = deque(supplies)
        result = []

        while queue:
            current = queue.popleft()

            for recipe in graph[current]:
                indegree[recipe] -= 1

                if indegree[recipe] == 0:
                    result.append(recipe)
                    queue.append(recipe)

        return result
```实现从构建依赖图开始。 每种成分都存储了需要它的食谱列表。 这种反向依赖结构很重要，因为当一种成分可用时，我们立即知道哪些食谱现在可以完成。 

这`indegree`字典存储创建食谱之前仍需要多少成分。 最初，这等于食谱中成分的总数。 

队列使用所有供应品进行初始化，因为这些供应品已经可用。 然后我们重复处理可用的项目。 

对于每种可用的成分或配方：

 - 我们根据它检查所有食谱。 
- 我们减少他们的剩余需求数量。 
- 如果配方的剩余需求达到零，它就可以创建。 

那一刻，我们：

 - 将配方添加到结果中。 
- 将其推入队列，以便它可以帮助创建其他食谱。 

该算法自然地处理依赖链并避免冗余的重新扫描。 

## 解决方案```go
package main

import "container/list"

func findAllRecipes(recipes []string, ingredients [][]string, supplies []string) []string {
	graph := make(map[string][]string)
	indegree := make(map[string]int)

	for i, recipe := range recipes {
		ingredientList := ingredients[i]
		indegree[recipe] = len(ingredientList)

		for _, ingredient := range ingredientList {
			graph[ingredient] = append(graph[ingredient], recipe)
		}
	}

	queue := list.New()

	for _, supply := range supplies {
		queue.PushBack(supply)
	}

	result := []string{}

	for queue.Len() > 0 {
		front := queue.Front()
		queue.Remove(front)

		current := front.Value.(string)

		for _, recipe := range graph[current] {
			indegree[recipe]--

			if indegree[recipe] == 0 {
				result = append(result, recipe)
				queue.PushBack(recipe)
			}
		}
	}

	return result
}
```Go 实现遵循与 Python 版本完全相同的算法结构。 

一个`map[string][]string`用于依赖图，并且`map[string]int`跟踪入度。 

Go 不提供与 Python 等效的内置双端队列结构`collections.deque`， 所以`container/list`用作队列。 

当配方变得可创建时，切片会动态附加。 

与 Python 不同，从链表队列检索值时需要显式类型断言。

 ## 边缘情况

 ### 循环依赖

 错误的一个主要来源是循环配方依赖性。 

例如：```
A requires B
B requires A
```除非最初提供一种食谱，否则这两种食谱都无法获得。 

没有适当循环处理的简单 DFS 解决方案可能会无限递归或错误地将配方标记为可创建。 

该实现通过入度计数自然地处理循环。 由于两个配方的入度都未达到零，因此两者都不会添加到队列中。 

### 缺少非食谱成分

 有些成分可能不存在于供应品或食谱中。 

例子：```
cake requires milk
milk is nowhere available
```有缺陷的实现可能会错误地假设每种成分最终都可以被创建。 

这里，`"milk"`从不进入队列，所以`"cake"`永远不会达到入度零。 

### 深度依赖链

 食谱可以形成长链：```
A -> B -> C -> D
```递归解决方案可能会反复重新计算依赖关系，从而导致效率低下。 

基于队列的拓扑方法对每个依赖关系只处理一次。 一次`"A"`变得可用，它解锁`"B"`，这会解锁`"C"`，等等在线性时间内。
