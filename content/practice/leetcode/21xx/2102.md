 **难度：** 🔴难
 **主题：** 设计、堆（优先级队列）、数据流、有序集

 ## 解决方案

 ## 问题理解

 该问题要求我们设计一个数据结构，连续跟踪按两条规则排名的景点：

 1. 更高`score`意味着更好的位置。 
2. 如果两个位置的分数相同，则按字典顺序较小的一个`name`被认为更好。 

系统支持两种操作：

 -`add(name, score)`插入一个新位置。 
-`get()`返回`ith`最好的位置，在哪里`i`是次数`get()`到目前为止已被调用。 

第二个要求是问题的关键难点。 返回值`get()`随着时间的推移而变化，因为每次调用都会提高请求的排名。 

例如：

 - 第一个`get()`返回最佳位置。 
- 第二个`get()`返回第二最佳位置。 
- 第三个`get()`返回第三最佳位置。 

重要的是，位置永远不会被删除。 数据集只会增长。 

约束条件也很重要：

 - 至多`4 * 10^4`操作总计。 
- 每一个`name`是独一无二的。 
- 数量`get()`调用次数永远不会超过`add()`来电。 

对每个操作的所有位置重新排序的简单实现会变得太慢。 因此，我们需要一种能够动态、高效地维护排名信息的数据结构。 

一个特别棘手的部分是排序规则：

 - 分数越大越好。 
- 当分数相同时，名字越小越好。 

这意味着比较不是简单的数字比较。 

另一个微妙的边缘情况是新添加的位置可能属于排名中的任何位置。 它可能成为新的最佳位置，也可能位于中间的某个位置。 该结构必须有效地适应这些插入，同时仍然允许重复的顺序排名查询。 

## 方法

 ### 蛮力方法

 最直接的解决方案是将每个位置存储在列表中。 

每当`get()`称为：

 1. 根据排名规则对整个列表进行排序。 
2.返回index处的元素`getCount - 1`。 

排序规则将是：

 - 分数高者优先。 
- 按字典顺序排列较小的名字在前。 

这种方法是正确的，因为排序显式地构建了问题所需的确切排名顺序。 

然而，它的效率很低。 如果有`n`地点，每个`get()`运营成本`O(n log n)`因为我们必须重复对整个集合进行排序。 高达`4 * 10^4`操作，这变得太慢了。 

### 最佳解决方案的关键见解

 关键的观察是`get()`查询按顺序发生。 

我们不需要任意排名查询，例如：

 - “给我第 17 个最佳位置”
 - “再次给我第五个最佳位置”

 相反：

 - 第一个查询要求排名 1。 
- 第二个查询要求排名 2。 
- 第三个查询要求排名 3。 

这种单调行为使我们能够维护两个堆：

 - 一个堆存储当前顶部`k`地点。 
- 另一个堆存储剩余位置。 

在哪里`k`等于`get()`已拨打电话。 

更具体地说：

 - 左边的堆恰好包含最好的`k`地点。 
- 左堆的根是那些顶部中最差的`k`地点。 
- 该根正是下一个的答案`get()`。 

当添加新位置时，我们会重新平衡堆，因此这个不变量仍然成立。 

这将每个操作的时间减少到对数。

 ## 算法演练

 ### 数据结构设计

 我们维护两个堆：

 -`leftHeap`- 包含当前顶部`k`地点。 
- 根是那些顶级中最差的`k`。 
- 这个根是下一个根的答案`get()`称呼。 
-`rightHeap`- 包含所有剩余位置。 

困难的部分是仔细选择堆顺序。 

### 排名定义

 一个地点`A`比位置好`B`如果：

 1.`A.score > B.score`2. 或者分数相等且`A.name < B.name`### 逐步算法

 1. 定义位置的比较顺序。 

我们将每个位置表示为`(score, name)`。 

由于 Python 堆是最小堆，因此我们策略性地反转值以模拟所需的排序。 
2. 保持不变量：

 -`leftHeap`总是准确地包含`k`最好的元素，在哪里`k`等于完成的数量`get()`来电。 
- 的根源`leftHeap`是那些顶级中最差的`k`元素。 
3.期间`add(name, score)`：

 - 将新位置插入`leftHeap`。 
- 堆现在可能包含一个额外的元素。 
- 删除最差的元素`leftHeap`。 
- 将移除的元素推入`rightHeap`。 

这保留了不变的尺寸关系。 
4.期间`get()`：

 - 最佳候选人来自`rightHeap`现在应该进入排名最高的组。 
- 从中删除最好的元素`rightHeap`。 
- 将其推入`leftHeap`。 
- 的根源`leftHeap`成为当前答案。 
5. 返回根名称`leftHeap`。 

### 为什么它有效

 不变量是：

 -`leftHeap`始终准确存储顶部`k`排名位置之后`k`打电话给`get()`。 
- 的根源`leftHeap`是那些顶级中最差的`k`。 

当下一个`get()`发生时，我们将最好的剩余位置从`rightHeap`进入`leftHeap`。 这增加了从顶部开始跟踪的前缀`k`到顶部`k + 1`。 

由于堆总是正确分区，因此返回值始终是准确的`ith`问题所需的最佳位置。 

## Python 解决方案```python
import heapq
from typing import List, Tuple

class SORTracker:

    def __init__(self):
        self.left_heap: List[Tuple[int, str]] = []
        self.right_heap: List[Tuple[int, str]] = []

    def add(self, name: str, score: int) -> None:
        heapq.heappush(self.left_heap, (score, name))

        score, name = heapq.heappop(self.left_heap)

        heapq.heappush(self.right_heap, (-score, name))

    def get(self) -> str:
        score, name = heapq.heappop(self.right_heap)

        heapq.heappush(self.left_heap, (-score, name))

        return self.left_heap[0][1]
```### 实现说明

 该实现依赖于精心选择的堆顺序。 

这`left_heap`存储当前排名最高的位置。 由于 Python 使用最小堆，因此最小的元素出现在根部。 我们有意将条目存储为`(score, name)`所以根变成：

 - 最低分优先
 - 领带的字典顺序最小的名字在前

 这实际上使根成为跟踪的顶级位置中最差的。 

这`right_heap`存储剩余的候选者。 我们使用负分数来模拟最大堆行为。 因此，它的根成为最好的剩余位置。 

期间`add()`：

 1.我们首先插入`left_heap`。 
2. 这可能违反尺寸不变性。 
3.我们删除最差的元素`left_heap`。 
4.我们将其移入`right_heap`。 

期间`get()`：

 1. 我们将最好的剩余位置从`right_heap`进入`left_heap`。 
2. 根源`left_heap`然后成为当前查询排名的正确答案。 

这种结构保证了对数插入和检索。 

## 解决方案```go
package main

import (
	"container/heap"
)

type Location struct {
	score int
	name  string
}

type LeftHeap []Location

func (h LeftHeap) Len() int {
	return len(h)
}

func (h LeftHeap) Less(i, j int) bool {
	if h[i].score == h[j].score {
		return h[i].name < h[j].name
	}
	return h[i].score < h[j].score
}

func (h LeftHeap) Swap(i, j int) {
	h[i], h[j] = h[j], h[i]
}

func (h *LeftHeap) Push(x interface{}) {
	*h = append(*h, x.(Location))
}

func (h *LeftHeap) Pop() interface{} {
	old := *h
	n := len(old)
	item := old[n-1]
	*h = old[:n-1]
	return item
}

type RightHeap []Location

func (h RightHeap) Len() int {
	return len(h)
}

func (h RightHeap) Less(i, j int) bool {
	if h[i].score == h[j].score {
		return h[i].name > h[j].name
	}
	return h[i].score > h[j].score
}

func (h RightHeap) Swap(i, j int) {
	h[i], h[j] = h[j], h[i]
}

func (h *RightHeap) Push(x interface{}) {
	*h = append(*h, x.(Location))
}

func (h *RightHeap) Pop() interface{} {
	old := *h
	n := len(old)
	item := old[n-1]
	*h = old[:n-1]
	return item
}

type SORTracker struct {
	left  LeftHeap
	right RightHeap
}

func Constructor() SORTracker {
	left := LeftHeap{}
	right := RightHeap{}

	heap.Init(&left)
	heap.Init(&right)

	return SORTracker{
		left:  left,
		right: right,
	}
}

func (this *SORTracker) Add(name string, score int) {
	heap.Push(&this.left, Location{
		score: score,
		name:  name,
	})

	item := heap.Pop(&this.left).(Location)

	heap.Push(&this.right, item)
}

func (this *SORTracker) Get() string {
	item := heap.Pop(&this.right).(Location)

	heap.Push(&this.left, item)

	return this.left[0].name
}

/**
 * Your SORTracker object will be instantiated and called as such:
 * obj := Constructor();
 * obj.Add(name,score);
 * param_2 := obj.Get();
 */
```### Go 特定注释

 去的`container/heap`包需要手动实现堆接口。 

与 Python 不同，Go 不提供内置的最大堆。 因此，我们定义了两种不同的独立堆类型`Less()`方法：

-`LeftHeap`其行为类似于最小堆排序顺序。 
-`RightHeap`行为类似于最大堆超过排序顺序。 

该逻辑在其他方面与 Python 实现完全匹配。 

这里不存在整数溢出问题，因为分数最多是`10^5`。

 ## 边缘情况

 ### 不同名字得分相同

 错误的一个主要来源是错误地处理关系。 

如果两个位置具有相同的分数，则字典顺序较小的名称必须排名较高。 许多不正确的实现在使用堆时会意外颠倒此顺序。 

例如：```
("alpha", 5)
("beta", 5)
```正确的顺序是：```
alpha before beta
```该实现显式将此比较规则编码到堆排序中，确保正确处理关系。 

### 新增最佳位置

 新插入的位置可能会立即成为最佳的整体位置。 

例如：```
add("a", 1)
get() -> "a"

add("b", 100)
```虽然`"a"`之前已返回，以后的排名必须正确调整。 

堆重新平衡可确保新添加的位置立即插入到正确的分区中。 

### add() 和 get() 之间频繁交替

 当操作频繁交替时，会出现另一种微妙的情况：```
add
get
add
get
add
get
```不正确的实现可能会丢失对跟踪分区中应保留多少顶部元素的跟踪。 

此解决方案避免了该问题，因为：

 -`left_heap`始终包含与完成的元素一样多的元素`get()`来电。 
- 每一个`get()`将该大小增加一倍。 
- 每一个`add()`通过重新平衡保持不变性。 

因此，顺序排名跟踪始终保持正确。
