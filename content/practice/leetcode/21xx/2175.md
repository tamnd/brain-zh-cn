[LeetCode 问题 2175](https://leetcode.com/problems/the-change-in-global-rankings/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 这个问题要求我们确定国家队积分更新后全球排名如何变化。 

我们有两个数据库表：

 的`TeamPoints`表包含每个团队当前的排名信息。 每行包括：

 -`team_id`，团队的唯一标识符
 -`name`, 国家名称
 -`points`，当前排名积分

 的`PointsChange`表包含每支球队的积分调整。 每行包括：

 -`team_id`-`points_change`，可能是正数、负数或零

 排名系统的工作原理如下：

 1. 队伍按照积分降序排列。 
2. 如果两队积分相同，则按国家名称字典顺序排列。 

任务是：

 1. 计算原始排名。 
2. 应用点更改。 
3. 计算更新后的排名。 
4. 返回每支球队的旧排名和新排名之间的差异。 

输出列`rank_diff`代表：```
old_rank - new_rank
```这意味着：

 - 正值意味着球队的排名有所提高。 
- 负值表示球队排名下降。 
- 零意味着排名保持不变。 

该问题保证：

 - 每个`team_id`在两个表中都是唯一的。 
- 出现在的每支球队`TeamPoints`也出现在`PointsChange`。 

这个保证很重要，因为这意味着我们永远不需要处理丢失的更新或重复的团队。 

An important detail is the tie-breaking rule. 积分相同的两支球队按照其名字的字典顺序进行排名。 忽略这种二级排序的简单实现将产生不正确的排名。 

当多支球队获得或失去足够的分数以完全重新排列排名时，就会出现另一个重要的边缘情况。 该解决方案必须在更新后从头开始重新计算排名，而不是尝试增量调整。 

## 方法

 ### 蛮力方法

 暴力解决方案通过将每个团队与其他团队进行比较来手动计算排名。 

首先，我们计算每个团队的原始排名。 对于每支球队，我们都会将其与所有其他球队进行比较，并根据排名规则计算有多少支球队应该出现在它之前。 排名变为：```
1 + number of teams ahead of it
```之后，我们使用以下方法更新所有点`points_change`值并重复相同的成对比较过程来计算新的排名。 

最后，我们从每支球队的旧排名中减去新排名。 

这种方法是正确的，因为它直接实现了排名定义。 然而，它的效率很低，因为排名计算需要比较每对团队，导致二次复杂度。 

### 最佳方法

 关键的观察是排名完全由排序顺序决定。 

我们不必将每个团队与其他团队进行比较，而是可以：

 1. 按照球队原来的排名标准对球队进行排序。 
2. 根据排序顺序分配排名。 
3.更新点。 
4. 使用更新后的点再次排序。 
5. 分配新的等级。 
6. 计算差异。 

排序会自动处理按分数进行的主要排序和按团队名称进行的辅助排序。 

这显着提高了效率，因为排序需要`O(n log n)`时间而不是`O(n²)`。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(n) | 将每个团队与其他团队进行两次比较 |
 | 最佳| O(n log n) | O(n log n) | O(n) | 使用排序来高效计算排名 |

 ## 算法演练

 1.使用连接两个表`team_id`。 

我们首先将原始得分和得分变化结合起来，以便每支球队的记录包含：

 - 团队ID
 - 团队名称
 - 原始点
 - 更新点

 更新后的点计算如下：```
updated_points = points + points_change
```2. 计算原始排名。 

我们使用以下方法对所有团队进行排序：

 - 降序原始点
 - 字典顺序升序的名称

 排序后，第一组获得排名`1`，第二个获得排名`2`， 等等。 

我们将这些排名存储在映射中`team_id`到`old_rank`。 
3. 计算更新后的排名。 

我们再次对相同的团队进行排序，但这次使用：

 - 降序更新点
 - 字典顺序升序的名称

 我们再次分配排名并将其存储为`new_rank`。 
4. 计算排名差异。 

对于每个团队：```
rank_diff = old_rank - new_rank
```积极的结果意味着球队的排名上升。 
5. 返回最终结果。 

输出包含：

 -`team_id`-`name`-`rank_diff`### 为什么它有效

 该算法之所以有效，是因为排名完全由球队的排序顺序决定。 通过积分更新前后的准确排名规则进行排序，准确再现官方排名。 由于每个团队在每个排序列表中只收到一个位置，因此减去位置可以正确衡量排名变动。 

## Python 解决方案```python
import pandas as pd

def global_ratings_change(
    team_points: pd.DataFrame,
    points_change: pd.DataFrame
) -> pd.DataFrame:
    
    # Merge both tables
    teams = team_points.merge(points_change, on="team_id")
    
    # Compute updated points
    teams["new_points"] = teams["points"] + teams["points_change"]
    
    # Original rankings
    original = teams.sort_values(
        by=["points", "name"],
        ascending=[False, True]
    ).reset_index(drop=True)
    
    original["old_rank"] = range(1, len(original) + 1)
    
    # Updated rankings
    updated = teams.sort_values(
        by=["new_points", "name"],
        ascending=[False, True]
    ).reset_index(drop=True)
    
    updated["new_rank"] = range(1, len(updated) + 1)
    
    # Build rank mappings
    old_rank_map = original.set_index("team_id")["old_rank"]
    new_rank_map = updated.set_index("team_id")["new_rank"]
    
    # Compute final result
    result = teams[["team_id", "name"]].copy()
    
    result["rank_diff"] = (
        old_rank_map[result["team_id"]].values
        - new_rank_map[result["team_id"]].values
    )
    
    return result
```实现首先使用以下命令合并两个输入表`team_id`。 这样可以访问每个团队的原始分数和相应的分数变化。 

接下来，代码通过添加计算每个团队的更新分数`points_change`到原来的点。 

然后，该算法创建数据的两个排序版本。 第一次排序计算原始排名，第二次排序计算更新后的排名。 两种排序都使用问题所需的确切排名规则：

 - 下降点
 - 字典顺序升序的名称

 排序后，使用顺序分配排名`range(1, n + 1)`。 

该代码将这些排名存储在查找映射中，索引为`team_id`。 这样可以快速检索每个团队的新旧排名。 

最后，构建结果数据框并计算排名差异：```python
old_rank - new_rank
```这直接符合问题所需的定义。 

## 解决方案```go
package main

import (
	"sort"
)

type TeamPoints struct {
	TeamID int
	Name   string
	Points int
}

type PointsChange struct {
	TeamID      int
	PointsChange int
}

type Result struct {
	TeamID  int
	Name    string
	RankDiff int
}

type Team struct {
	TeamID    int
	Name      string
	Points    int
	NewPoints int
}

func globalRatingsChange(
	teamPoints []TeamPoints,
	pointsChange []PointsChange,
) []Result {

	changeMap := make(map[int]int)

	for _, p := range pointsChange {
		changeMap[p.TeamID] = p.PointsChange
	}

	teams := make([]Team, 0)

	for _, t := range teamPoints {
		teams = append(teams, Team{
			TeamID:    t.TeamID,
			Name:      t.Name,
			Points:    t.Points,
			NewPoints: t.Points + changeMap[t.TeamID],
		})
	}

	oldOrder := make([]Team, len(teams))
	copy(oldOrder, teams)

	sort.Slice(oldOrder, func(i, j int) bool {
		if oldOrder[i].Points == oldOrder[j].Points {
			return oldOrder[i].Name < oldOrder[j].Name
		}
		return oldOrder[i].Points > oldOrder[j].Points
	})

	oldRank := make(map[int]int)

	for i, team := range oldOrder {
		oldRank[team.TeamID] = i + 1
	}

	newOrder := make([]Team, len(teams))
	copy(newOrder, teams)

	sort.Slice(newOrder, func(i, j int) bool {
		if newOrder[i].NewPoints == newOrder[j].NewPoints {
			return newOrder[i].Name < newOrder[j].Name
		}
		return newOrder[i].NewPoints > newOrder[j].NewPoints
	})

	newRank := make(map[int]int)

	for i, team := range newOrder {
		newRank[team.TeamID] = i + 1
	}

	result := make([]Result, 0)

	for _, team := range teams {
		result = append(result, Result{
			TeamID:  team.TeamID,
			Name:    team.Name,
			RankDiff: oldRank[team.TeamID] - newRank[team.TeamID],
		})
	}

	return result
}
```Go 实现遵循与 Python 版本相同的算法结构。 

地图用于关联每个`team_id`及其点的变化。 这允许在构建更新的团队记录时进行恒定时间查找。 

Go 不提供内置的数据帧操作，因此使用切片和自定义结构体来代替。 排序逻辑是使用实现的`sort.Slice`具有自定义比较功能。 

创建团队切片的两个单独副本，以便可以独立对原始排名和更新排名进行排序。 

由于 Go 切片是对共享后备数组的引用，因此使用`copy()`避免无意中两次修改同一个切片很重要。 

Go 整数可以安全地处理这个问题的约束，因此不需要特殊的溢出处理。

 ## 边缘情况

 ### 更新后队伍打成平手

 当两支或更多球队在应用分数变化后最终得分相同时，就会出现一种重要的边缘情况。 有缺陷的实现可能会保留旧的排序或使用任意排序而不是字典排序。 

此实现显式排序：```
(points descending, name ascending)
```在更新之前和之后，确保每次都正确处理关系。 

### 负点变化

 有些球队可能会失去分数而不是获得分数。 一个幼稚的解决方案可能会假设排名只会在更新后提高。 

该算法在更新后从头开始重新计算整个排名，因此排名的下降是自然处理的。 消极的`rank_diff`值正确地代表团队向下移动。 

### 单队输入

 如果只有一支球队，则新旧排名都必须保留`1`。 

某些实现在分配排名时会意外地引入相差一的错误。 由于该解决方案始终使用以下方式分配排名：```
range(1, n + 1)
```单队情况正常运行并产生排名差异`0`。 

### 排名大幅调整

 一支球队可以获得足够的积分，从排名垫底跃升至榜首。 在这种情况下，增量更新策略通常容易出错。 

该解决方案通过在应用更新后再次对完整数据集进行排序来完全避免该问题。 无论排序变化有多大，重新计算的排名始终是全局正确的。
