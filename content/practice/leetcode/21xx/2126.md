[LeetCode 第 2126 题](https://leetcode.com/problems/destroying-asteroids/)

 **难度：** 🟡 中等
 **主题：** 数组、贪婪、排序

 ## 解决方案

 ## 问题理解

 在这个问题中，我们给出了行星的起始质量和小行星质量列表。 行星可以按照我们选择的任何顺序与小行星相撞。 每次行星与小行星相撞时，都会发生以下两种情况之一：

 - 如果行星当前的质量大于或等于小行星的质量，则小行星被摧毁，并且行星获得该小行星的质量。 
- 否则，行星会立即被摧毁，并且进程会失败。 

目标是确定小行星是否存在某种排序，以便行星能够成功摧毁所有小行星。 

重要的细节是我们可以任意重新排序小行星。 这将问题从固定的模拟问题转变为优化问题，我们必须选择最佳的碰撞序列。 

输入包括：

 -`mass`，行星的初始质量。 
-`asteroids`，一个数组，其中每个值代表一颗小行星的质量。 

输出是一个布尔值：

 -`true`如果所有的小行星都能被摧毁。 
-`false`否则。 

约束足够大，效率很重要：

 - 最多`10^5`小行星
 - 每个小行星的质量也可以达到`10^5`二次解太慢，所以我们需要一些东西`O(n log n)`或更好。 

一些边缘情况很重要：

 - 一颗比初始质量大的小行星。 
- 许多微小的小行星逐渐增加地球的质量。 
- 重复的小行星质量。 
- 已排序或反向排序的输入。 
- 摧毁几乎所有小行星后，地球对于最后一颗小行星来说仍然太小。 

由于行星的质量在成功碰撞后不断增加，因此处理顺序非常重要。 

## 方法

 ### 蛮力方法

 蛮力的想法是尝试所有可能的小行星排序并模拟碰撞。 

对于每个排列：

 1. 从初始行星质量开始。 
2. 按此顺序处理小行星。 
3.如果这个星球能摧毁所有小行星，就返回`true`。 
4. 否则，尝试另一种排列。 

这种方法是正确的，因为它明确地检查所有可能的有效订单。 如果存在任何成功的订单，暴力最终会找到它。 

然而，这种方法对于给定的约束是完全不切实际的。 如果有`n`小行星，有`n!`possible orderings. 即使对于相对较小的值`n`，阶乘增长变得巨大。 

例如：

-`10! = 3,628,800`-`15!`已经是天文数字了

 自从`n`可以是`100,000`，暴力是不可能的。 

### 最优贪心法

 关键的观察是，最好的策略始终是摧毁目前可用的最小的小行星。 

为什么这有效？ 

如果行星可以摧毁一颗小行星，它就会以最小的风险获得额外的质量。 首先摧毁较小的小行星可以最大限度地促进地球的发展，然后再尝试摧毁较大的小行星。 

假设我们有两颗小行星：

 - 小小行星：`a`- 大型小行星：`b`- 在哪里`a <= b`如果地球不能毁灭`a`，它绝对不能破坏`b`。 

如果地球可以毁灭`b`，它也可以破坏`a`，并摧毁`a`首先只会增加行星的质量，使得`b`之后就容易了。 

这意味着按升序对小行星进行排序始终是最佳的。 

算法变为：

 1. 对小行星进行排序。 
2.从小到大迭代。 
3. 如果当前小行星太大，则返回`false`。 
4.否则，吸收并继续。 

这种贪心策略保证了正确性。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n! × n) | O(n! × n) | O(n) | 尝试所有可能的排序 |
 | 最佳| O(n log n) | O(n log n) | O(1) 或 O(log n) 取决于排序 | 排序上升并贪婪地吸收小行星 |

 ## 算法演练

 ### 第 1 步：对小行星进行排序

 排序`asteroids`数组按升序排列。 

排序的原因是先摧毁较小的小行星总是更安全。 每一次成功的碰撞都会增加行星的质量，从而提高我们以后遇到更大的小行星的机会。 

例如：```
asteroids = [3, 9, 19, 5, 21]
```排序后：```
[3, 5, 9, 19, 21]
```### 第 2 步：跟踪当前行星质量

 初始化一个变量来存储当前的行星质量。 

最初：```
current_mass = mass
```每次成功碰撞后该值都会发生变化。 

### 步骤 3：从小到大处理小行星

 迭代排序后的数组。 

对于每个小行星：

 - 如果`current_mass < asteroid`，行星无法摧毁它，所以返回`false`。 
- 否则，将小行星质量添加到`current_mass`。 

这贪婪地最大化了未来的增长。 

### 第 4 步：成功完成

 如果循环顺利完成，则每颗小行星都被成功摧毁。 

返回`true`。 

### 为什么它有效

 贪婪策略之所以有效，是因为首先摧毁较小的小行星永远不会伤害我们。 

如果一颗小行星现在无法被摧毁，那么任何更大的小行星现在也无法被摧毁。 相反，如果一颗较小的小行星可以被摧毁，吸收它只会增加行星的质量并提高未来的可能性。 

因此，按升序处理小行星总是在每一步中提供最大可能的增长。 如果此策略失败，则任何其他排序都不会成功。 

## Python 解决方案```python
from typing import List

class Solution:
    def asteroidsDestroyed(self, mass: int, asteroids: List[int]) -> bool:
        asteroids.sort()

        current_mass = mass

        for asteroid in asteroids:
            if current_mass < asteroid:
                return False

            current_mass += asteroid

        return True
```实现首先按升序对小行星数组进行排序。 这直接应用了贪婪的见解，即较小的小行星应始终首先处理。 

变量`current_mass`存储地球不断变化的质量。 我们用给定的起始质量初始化它。 

该循环按排序顺序迭代每个小行星。 对于每颗小行星，我们首先检查该行星是否大到足以摧毁它。 如果没有，我们立即返回`False`因为一旦剩余的最小小行星已经太大，未来的排序就不可能成功。 

如果碰撞成功，小行星的质量将被添加到`current_mass`，模拟吸收过程。 

如果循环完全完成，则所有小行星均已成功销毁，因此该方法返回`True`。 

## 解决方案```go
package main

import "sort"

func asteroidsDestroyed(mass int, asteroids []int) bool {
	sort.Ints(asteroids)

	currentMass := int64(mass)

	for _, asteroid := range asteroids {
		if currentMass < int64(asteroid) {
			return false
		}

		currentMass += int64(asteroid)
	}

	return true
}
```Go 实现遵循与 Python 解决方案相同的逻辑。 

一个重要的区别是使用`int64`为了`currentMass`。 虽然约束条件单独符合标准整数，但重复添加可能会明显大于初始值。 使用`int64`避免积累过程中溢出的问题。 

内置的`sort.Ints()`函数有效地按升序对切片进行排序。 

Go 切片本质上是数组的动态视图，因此迭代不需要额外的复制。

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n log n) | O(n log n) | 排序在运行时占据主导地位

 主要成本来自对小行星阵列的排序。 排序后，算法对数组执行一次线性扫描。 

迭代本身是`O(n)`，但排序需要`O(n log n)`，它在总运行时间中占主导地位。 

额外的内存使用量很小，因为该算法仅存储除输入数组之外的几个变量。 确切的辅助空间取决于语言的排序实现。

 ## 边缘情况

 当行星的质量恰好等于小行星的质量时，就会出现一种重要的边缘情况。 问题陈述称，当行星的质量大于或等于小行星时，行星就成功了。 一个常见的错误是意外地使用了严格的大于比较。 这个实现正确地使用了`<`用于故障检测，因此相等成功成功。 

另一个重要的情况是最小的小行星已经太大了。 由于数组是排序的，如果第一颗小行星无法被摧毁，那么其他排序就不可能起作用。 执行立即返回`False`在这种情况下无需进行不必要的计算。 

第三个重要的边缘情况涉及非常大的累积质量增长。 尽管个别小行星的值最多可达`10^5`，重复添加它们会产生非常大的总数。 具体来说，在 Go 中，使用标准`int`不小心可能会在某些系统上带来溢出风险。 Go 实现通过使用避免了这种情况`int64`为运行总质量。 

另一个微妙的边缘情况是成功完全取决于选择正确的顺序。 例如：```
mass = 2
asteroids = [1,3,2]
```如果按给定顺序处理：```
2 -> destroy 1 -> mass 3
3 -> destroy 3 -> mass 6
6 -> destroy 2
```成功发生。 

但不利的订单，例如`[3,1,2]`会立即失败。 排序保证我们始终首先选择最安全的增长策略。
