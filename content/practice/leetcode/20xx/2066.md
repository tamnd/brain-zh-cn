[LeetCode 2066 题](https://leetcode.com/problems/account-balance/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题要求我们计算每笔交易后每个银行帐户的运行余额。 

我们有一个表名为`Transactions`其中每一行代表帐户在特定日期执行的单笔交易。 每笔交易都有：

 | 专栏 | 意义|
 | ---| ---|
 |`account_id`| 执行交易的账户 |
 |`day`| 交易日期 |
 |`type`| 任何一个`Deposit`或者`Withdraw`|
 |`amount`| 交易金额|

 主键是`(account_id, day)`，这意味着每个账户每天最多有一笔交易。 这很重要，因为它保证同一帐户在同一天不会发生多笔交易，因此按天排序足以正确处理交易。 

每个账户的余额起始于`0`。 一个`Deposit`增加平衡，同时`Withdraw`减少它。 

目标是对于每个交易行，在处理该交易后立即输出该帐户的余额。 

结果必须按以下顺序排序：

 1.`account_id`上升
 2.`day`上升

 这个问题还保证余额永远不会变成负值。 这意味着我们不需要验证提款或处理无效状态。 

例如，如果一个帐户执行：

 - 押金 2000
 - 提现1000
 - 押金 3000

 那么运行余额变为：

 - 2000
 - 1000
 - 4000

 这本质上是一个运行总计问题，有时称为累积和问题。 

重要的边缘情况包括仅存款的账户、提款后归零的账户以及仅进行单笔交易的账户。 另一个重要的考虑因素是不同账户的交易必须独立处理，因此余额不能跨账户泄漏。 

## 方法

 ### 蛮力方法

 一种简单的方法是独立计算每笔交易的余额。 

对于每个事务行：

 1. 查找同一账户的所有先前交易，其日期小于或等于当前行的日期。 
2、积极存款。 
3. 提款金额为负数。 
4. 返回结果总数。 

这是有效的，因为交易后的余额只是截至该点的所有已签名交易金额的总和。 

但是，这种方法效率低下，因为对于每一行，我们都会重复扫描同一帐户中较早的行。 如果有`n`事务总数，这可能需要检查每个事务的几乎所有行。 

这会产生二次行为。 

### 最佳方法

 关键的观察是余额是累积的。 

我们可以按时间顺序处理事务并保持运行余额，而不是从头开始重新计算每一行的余额。 

SQL 窗口函数正是针对此类问题而设计的。 

最佳解决方案的工作原理是：

 1. 将存款转为正值。 
2. 将提款转换为负值。 
3. 使用累积`SUM()`窗口函数按帐户分区并按日期排序。 

这使得数据库引擎能够有效地独立维护每个帐户的运行总计。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(1) | O(1) | 反复重新计算以前的余额 |
 | 最佳| O(n log n) | O(n log n) | O(n) | 使用窗函数求累计和 |

 SQL 窗口函数的确切复杂性取决于数据库引擎，但按帐户和日期排序通常在运行时占主导地位。 

## 算法演练

 1. 从`Transactions`桌子。 

每行包含一个增加或减少帐户余额的交易。 
2. 将每笔交易转换为带符号的值。 

如果交易类型是`Deposit`，保持金额为正。 

如果交易类型是`Withdraw`，将金额设为负数。 

这种转换使我们能够在求和过程中统一处理所有交易。 
3. 行分区依据`account_id`。 

每个账户都有自己独立的余额历史记录，因此必须单独计算每个账户的余额。 
4. 对每个账户内的交易进行排序`day`。 

由于余额会随着时间的推移而变化，因此必须按时间顺序处理交易。 
5. 应用累积`SUM()`窗函数。 

运行总和给出每笔交易后的余额。 
6. 返回所需的列：

 -`account_id`-`day`- 计算出的`balance`7. 对最终输出进行排序`account_id`和`day`。 

### 为什么它有效

 一笔交易后的余额等于该账户之前所有已签名交易（包括当前交易）的总和。 

通过将存款转换为正值并将提款转换为负值，累积金额自然会随着时间的推移跟踪账户余额。 

分区确保帐户是隔离的，排序确保交易按时间顺序应用。 

## Python 解决方案

 LeetCode 数据库问题使用 SQL 而不是可执行的 Python 代码。 然而，为了完整起见，下面使用 pandas 风格的处理演示了 Python 中的等效逻辑。```python
from typing import List
import pandas as pd

def account_balance(transactions: pd.DataFrame) -> pd.DataFrame:
    transactions = transactions.copy()

    transactions["signed_amount"] = transactions.apply(
        lambda row: row["amount"]
        if row["type"] == "Deposit"
        else -row["amount"],
        axis=1
    )

    transactions = transactions.sort_values(
        by=["account_id", "day"]
    )

    transactions["balance"] = transactions.groupby(
        "account_id"
    )["signed_amount"].cumsum()

    return transactions[
        ["account_id", "day", "balance"]
    ]
```该实现首先创建一个签名的交易值。 存款保持正值，而提款则变为负值。 

然后按帐户和日期对行进行排序，以便按时间顺序计算余额。 

这`groupby(...).cumsum()`操作是 SQL 窗口函数的 Python 等效项。 它为每个帐户维护一个独立的运行总计。 

最后，仅返回所需的列。 

## 解决方案

 由于这是一个数据库问题，Go 通常不适用于 LeetCode。 真正的提交应该是SQL。 尽管如此，下面的 Go 实现在程序上演示了相同的运行平衡逻辑。```go
package main

import (
	"fmt"
	"sort"
)

type Transaction struct {
	AccountID int
	Day       string
	Type      string
	Amount    int
}

type Result struct {
	AccountID int
	Day       string
	Balance   int
}

func accountBalance(transactions []Transaction) []Result {
	sort.Slice(transactions, func(i, j int) bool {
		if transactions[i].AccountID == transactions[j].AccountID {
			return transactions[i].Day < transactions[j].Day
		}
		return transactions[i].AccountID < transactions[j].AccountID
	})

	balances := make(map[int]int)
	results := []Result{}

	for _, t := range transactions {
		if t.Type == "Deposit" {
			balances[t.AccountID] += t.Amount
		} else {
			balances[t.AccountID] -= t.Amount
		}

		results = append(results, Result{
			AccountID: t.AccountID,
			Day:       t.Day,
			Balance:   balances[t.AccountID],
		})
	}

	return results
}

func main() {
	transactions := []Transaction{
		{1, "2021-11-07", "Deposit", 2000},
		{1, "2021-11-09", "Withdraw", 1000},
		{1, "2021-11-11", "Deposit", 3000},
		{2, "2021-12-07", "Deposit", 7000},
		{2, "2021-12-12", "Withdraw", 7000},
	}

	results := accountBalance(transactions)

	for _, r := range results {
		fmt.Println(r)
	}
}
```Go 解决方案显式地维护一个哈希映射`account_id`至当前余额。 

与 SQL 窗口函数不同，Go 需要手动状态管理。 对交易进行排序后，我们迭代一次数组并增量更新余额。 

地图自动隔离帐户余额。 

## SQL 解决方案

 这就是LeetCode提交的实际解决方案。```sql
SELECT
    account_id,
    day,
    SUM(
        CASE
            WHEN type = 'Deposit' THEN amount
            ELSE -amount
        END
    ) OVER (
        PARTITION BY account_id
        ORDER BY day
    ) AS balance
FROM Transactions
ORDER BY account_id, day;
```## 工作示例

 ## 边缘情况

 ### 仅进行一笔交易的账户

 一个账户可能只包含一次存款或取款。 有缺陷的实现可能会错误地假设每个帐户都存在多行。 

该实现自然地处理了这个问题，因为单行的累积和只是该行的有符号值。 

### 多个独立账户

 一个常见的错误是不小心混合了账户之间的余额。 

例如，如果帐户 1 以余额 5000 结尾，则帐户 2 仍必须从 0 开始。 

的`PARTITION BY account_id`SQL 中的子句保证帐户之间完全隔离。 

### 提款将余额减至零

 某些实现会错误地处理返回到零的转换，特别是在余额存储或更新不正确的情况下。 

该问题保证余额永远不会变成负数，因此减法总是安全的。 当提款等于之前的存款时，运行金额正确地达到零。 

### 按时间顺序处理

 余额必须反映交易顺序。 

如果处理交易时没有按天排序，则可能会错误地计算余额。 

该解决方案显式对行进行排序`day`窗口函数内部，确保按时间顺序累积。
