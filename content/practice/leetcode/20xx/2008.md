[LeetCode 2008 题](https://leetcode.com/problems/maximum-earnings-from-taxi/)

 **难度：** 🟡 中等
 **主题：** 数组、哈希表、二分查找、动态规划、排序

 ## 解决方案

 ## 问题理解

 该问题描述了一辆出租车从点沿单向道路行驶`1`指向`n`。 一路上，乘客纷纷叫车。 每次骑行都表示为`[start, end, tip]`，这意味着乘客想要从`start`到`end`并额外支付小费。 

如果我们接受乘车，则从该乘客身上赚取的总收入为：$$(end - start) + tip$$出租车一次只能搭载一名乘客，这意味着我们不能重叠乘坐。 但是，我们_可以_立即在上一次骑行结束的确切位置开始另一次骑行。 

目标是通过选择不重叠游乐设施的最佳子集来确定可能的最大总收入。 

约束条件很重要：

 -`n`可以大到`10^5`-`rides.length`可以大到`3 * 10^4`对游乐设施的所有子集进行强力搜索是不可能的，因为子集的数量呈指数增长。 

游乐设施也不能保证被排序，因此我们必须有效地处理它们。 

一个重要的观察是，这个问题本质上是一个加权区间调度问题：

 - 每次骑行都是一个间隔`[start, end]`- 每次骑行都有利润`end - start + tip`- 我们想要非重叠区间的最大利润子集

 重要的边缘情况包括：

 - 多个游乐设施在同一地点结束
 - 从同一地点出发的多个游乐设施
 - 完美链接在一起的游乐设施
 - 乘坐一次大型游乐设施比乘坐几次小型游乐设施更糟糕的情况
 - 完全没有游乐设施重叠的情况
 - 几乎每次骑行都重叠的情况

 该问题保证：

 -`start < end`- 所有点都位于之间`1`和`n`- 小费为正整数

 这些保证简化了实现，因为我们永远不需要处理无效的间隔。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是尝试所有可能的游乐设施子集。 

对于每个子集，我们将：

 1. 检查游乐设施是否重叠
 2. 如果不重叠，计算总收入
 3. 跟踪最大有效收入

 这是有效的，因为它会探索所有可能的组合，因此最终必须找到最佳解决方案。 

然而，这种方法太慢了。 如果有`m`游乐设施，有`2^m`子集。 自从`m`可以达到`3 * 10^4`，指数时间是完全不可行的。 

即使添加修剪或记忆仍然会很困难，除非我们更智能地利用区间结构。 

### 关键见解

 关键的观察结果是，骑行只会根据其间隔发生冲突。 

如果我们按结束位置对行程进行排序，那么对于每个行程，我们可以确定：

 - 乘坐此行程所赚取的利润
 - 本次骑行开始前可实现的最佳利润

 这自然会导致动态规划。 

对于每次骑行：$$dp[i] = \max( \text{skip current ride}, \text{take current ride} )$$为了有效地找到之前最好的兼容骑行，我们使用二分搜索。 

这将问题转化为经典的加权间隔调度问题：

 - 排序
 - 动态规划
 - 二分查找

 这提供了一种在限制范围内轻松适应的有效解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(2^m) | O(2^m) | O(米) | 尝试所有游乐设施 |
 | 最佳| O(m log m) | O(米) | 使用二分查找进行动态规划 |

 这里，`m = len(rides)`。 

## 算法演练

 ### 使用二分搜索的最优动态规划

 1. 按结束位置对所有游乐设施进行排序。 

按结束时间排序使我们能够按时间顺序处理行程。 在考虑行程时，所有先前处理的行程不晚于当前行程结束。 
2. 计算每次乘车的利润。 

搭车`[start, end, tip]`，收益为：$$profit = (end - start) + tip$$3. 创建已排序结束位置的列表。 

我们单独存储所有骑行终点，因为我们将使用二分搜索来快速找到当前骑行开始之前完成的最新骑行。 
4. 定义DP状态。 

让`dp[i]`代表使用第一个可实现的最大收入`i`按排序顺序乘坐。 

这意味着：

-`dp[0] = 0`-`dp[i]`考虑到指数的乘车，存储最大可能的利润`i - 1`5. 逐一处理行程。 

对于每次骑行：

 - 使用二分搜索查找终点小于或等于当前骑行起点的最右边骑行
 - 这提供了最新的兼容骑行
 6. 计算两个选择。 

对于当前行程：

 - 跳过它：$$dp[i] = dp[i-1]$$- 拿走：$$dp[compatible] + currentProfit$$7. 存储最大值。 

最佳答案为`dp[i]`是两个选择中较大的一个。 
8. 返回最终结果。 

答案存储在最后一个 DP 条目中。 

### 为什么它有效

 该算法之所以有效，是因为一旦我们知道最新的兼容的先前骑行，每个骑行决策都是独立的。 

在每一步中，最佳解决方案必须：

 - 排除当前行程
 - 包括当前的骑行并将其与之前的最佳兼容解决方案相结合

 由于 DP 表始终存储较小前缀的最佳答案，因此将它们组合起来可以保持最佳性。 二分搜索可确保我们有效地找到兼容的游乐设施。 

## Python 解决方案```python
from bisect import bisect_right
from typing import List

class Solution:
    def maxTaxiEarnings(self, n: int, rides: List[List[int]]) -> int:
        rides.sort(key=lambda ride: ride[1])

        ends = [ride[1] for ride in rides]

        m = len(rides)
        dp = [0] * (m + 1)

        for i in range(1, m + 1):
            start, end, tip = rides[i - 1]

            profit = end - start + tip

            compatible_index = bisect_right(ends, start, hi=i - 1)

            take = dp[compatible_index] + profit
            skip = dp[i - 1]

            dp[i] = max(skip, take)

        return dp[m]
```实施首先根据游乐设施的结束位置对其进行排序。 此顺序至关重要，因为 DP 重复取决于之前完成的游乐设施。 

这`ends`数组分别存储所有骑行结束位置。 这使得二进制搜索能够使用`bisect_right`。 

DP数组有大小`m + 1`， 在哪里`m`是乘车次数。 使用基于 DP 的索引可以简化转换，因为`dp[i]`自然地用第一个表示答案`i`游乐设施。 

对于每次骑行：

 - 我们计算它的利润
 - 我们二进制搜索最后一个兼容的骑行
 - 如果我们搭车，我们会计算利润
 - 我们将其与跳过乘车的利润进行比较

 这两个选择中的最大值成为当前位置的 DP 值。 

最后，`dp[m]`包含最优总收益。 

## 解决方案```go
package main

import (
	"sort"
)

func maxTaxiEarnings(n int, rides [][]int) int64 {
	sort.Slice(rides, func(i, j int) bool {
		return rides[i][1] < rides[j][1]
	})

	m := len(rides)

	ends := make([]int, m)
	for i := 0; i < m; i++ {
		ends[i] = rides[i][1]
	}

	dp := make([]int64, m+1)

	for i := 1; i <= m; i++ {
		start := rides[i-1][0]
		end := rides[i-1][1]
		tip := rides[i-1][2]

		profit := int64(end - start + tip)

		compatibleIndex := sort.Search(i-1, func(j int) bool {
			return ends[j] > start
		})

		take := dp[compatibleIndex] + profit
		skip := dp[i-1]

		if take > skip {
			dp[i] = take
		} else {
			dp[i] = skip
		}
	}

	return dp[m]
}
```Go 实现遵循与 Python 解决方案相同的逻辑。 

主要区别在于 Go 需要显式处理整数大小。 由于总收益可能会变大，因此 DP 阵列使用`int64`。 

Go 没有像 Python 那样内置的二等分实用程序，所以`sort.Search`用于实现二分查找。 

使用切片代替 Python 列表，但整体 DP 结构保持相同。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(m log m) | 对每个行程进行排序和二分搜索 |
 | 空间| O(米) | DP 数组和结束位置数组 |

 这里，`m`是乘车次数。 

对游乐设施进行排序占据了部分运行时间和成本`O(m log m)`。 然后，对于每次骑行，我们执行一次二分搜索，这也会花费`O(log m)`每个。 由于有`m`游乐设施，总运行时间保持不变`O(m log m)`。 

空间复杂度是线性的，因为我们存储：

 - DP阵列
 - 排序结束位置数组

 两者都需要`O(m)`记忆。

 ## 边缘情况

 当游乐设施共享端点时，就会出现一种重要的边缘情况。 例如，一次骑行可能恰好在另一次骑行开始的地方结束。 一个常见的错误是将这些游乐设施视为重叠。 该问题明确允许这种转换，因此二分搜索必须使用`<= start`兼容性逻辑。 使用`bisect_right`正确处理本案。 

另一个重要的边缘情况是，长途骑行看起来很有吸引力，但几次较短的骑行一起产生更多利润。 基于行程长度或即时利润的贪婪策略在这里会失败。 DP 方法避免了这个问题，因为它系统地比较所有兼容的组合。 

第三种边缘情况涉及许多共享同一终点的游乐设施。 如果实现不正确地处理排序或二分搜索边界，它可能会跳过有效的转换或重复计数。 即使多个游乐设施在相同位置结束，使用排序的结束位置并仔细限制二分搜索范围也能确保正确性。
