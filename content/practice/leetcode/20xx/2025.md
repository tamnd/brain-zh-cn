 **难度：** 🔴难
 **主题：** 数组、哈希表、计数、枚举、前缀和

 ## 解决方案

 ## 问题理解

 该问题要求我们在有选择地将最多一个元素更改为给定值后计算数组中存在多少个有效分区点`k`。 

分区由枢轴索引定义`pivot`这样：

 -`1 <= pivot < n`- 左侧元素之和等于右侧元素之和。 

如果我们定义：

 - 左总和 =`nums[0] + ... + nums[pivot - 1]`- 右和 =`nums[pivot] + ... + nums[n - 1]`那么在以下情况下枢轴有效：$$\text{leftSum} = \text{rightSum}$$我们可以：

 - 保持数组不变，或者
 - 选择一个索引并替换`nums[i]`和`k`。 

我们的目标是在进行此可选修改后最大化有效主元的数量。 

数组长度可以大到`10^5`，这立即排除了昂贵的二次或三次解。 我们需要一种接近线性时间的算法。 

一个关键的观察是每个分区都可以使用前缀和来表示。 让：$$prefix[i] = nums[0] + nums[1] + ... + nums[i]$$对于一个枢轴`p`，左边的和是`prefix[p - 1]`，右边的和是：$$totalSum - prefix[p - 1]$$因此，分区在以下情况下有效：$$prefix[p - 1] = totalSum - prefix[p - 1]$$简化为：$$2 \times prefix[p - 1] = totalSum$$这种关系成为最优解决方案的基础。 

一些边缘情况很重要：

 - 已经有许多有效分区且未经修改的阵列。 
- 更改一个元素会破坏一些分区但在其他地方创建更多分区的数组。 
- 负数，防止贪婪假设。 
- 大值和大数组大小，需要高效的计数结构。 
- 奇数总和，除非修改改变奇偶校验，否则不能存在分区。 

该问题保证：

 -`2 <= n <= 10^5`- Values fit safely within standard integer ranges, though using 64 bit arithmetic is safest in Go.

 ## 方法

 ### 蛮力方法

 The brute force solution tries every possible modification.

 对于每个索引`i`:

 1. 临时更换`nums[i]`和`k`。 
2. 重新计算所有分区总和。 
3. 计算有多少个主元是有效的。 
4. 恢复原值。 

我们还需要考虑不进行修改的情况。 

为了对一种配置的分区进行计数，我们扫描所有主元并比较左右总和。 

由于有`n`可能的修改，每个修改都需要一个`O(n)`扫描，总复杂度变为`O(n^2)`。 

和`n = 10^5`，这太慢了。 

### 关键见解

 我们不是在每次修改后重新计算所有分区，而是分析更改一个元素如何影响分区平衡。 

假设：

 - 原始总和 =`total`- 我们改变`nums[i]`到`k`- 引入的差异 =$$delta = k - nums[i]$$那么新的总数就变成：$$total + delta$$现在考虑枢轴处的分区`p`。 

有两种情况：

 - 如果`p <= i`，则修改后的元素位于右侧。 
- 如果`p > i`，则修改后的元素位于左侧。 

这意味着平衡条件会根据相对于轴的位置而发生不同的变化`i`。 

使用前缀和，我们可以得出：

 对于之前或之后的枢轴`i`:$$2 \times prefix[p-1] = total + delta$$对于之后的枢轴`i`:$$2 \times prefix[p-1] = total - delta$$这将问题转化为计算有多少前缀和满足特定目标值。 

我们可以使用哈希映射有效地维护这些计数。

 ## 算法演练

 ### 步骤 1，计算前缀和

 我们首先计算数组的前缀和。 

对于每个枢轴`p`，左分区总和就是`prefix[p - 1]`。 

这允许在恒定时间内进行分区检查。 

### 步骤 2，计算现有的有效分区

 在不修改任何内容的情况下，分区在以下情况下有效：$$2 \times prefix[p-1] = total$$我们将所有此类枢轴视为基线答案。 

### 步骤 3，准备哈希图

 我们使用两个哈希图：

 -`rightCounts`-`leftCounts`最初：

-`rightCounts`包含与枢轴对应的所有前缀和的计数。 
-`leftCounts`是空的。 

每个映射存储前缀和的频率。 

这个想法是：

 -`leftCounts`严格跟踪当前索引之前的枢轴。 
-`rightCounts`跟踪当前索引处或之后的枢轴。 

当我们迭代可能的修改索引时，枢轴从右向左迁移。 

### 步骤 4，尝试修改每个索引

 假设我们修改索引`i`。 

定义：$$delta = k - nums[i]$$新的总数变为：$$total + delta$$现在检查枢轴条件。 

对于之前或之后的枢轴`i`:$$2 \times prefix = total + delta$$重新排列：$$prefix = \frac{total + delta}{2}$$这些枢轴是从`leftCounts`。 

对于之后的枢轴`i`:$$2 \times prefix = total - delta$$这些枢轴是从`rightCounts`。 

所以修改索引后有效分区总数`i`是：$$leftCounts[targetLeft] + rightCounts[targetRight]$$在哪里：$$targetLeft = \frac{total + delta}{2}$$

$$targetRight = \frac{total - delta}{2}$$我们使用哈希图查找在恒定时间内有效地计算这一点。 

### 第 5 步，更新地图

 处理后指标`i`，我们移动对应位置的枢轴`i + 1`从`rightCounts`到`leftCounts`。 

这使地图与未来的迭代保持同步。 

### 为什么它有效

 该算法之所以有效，是因为每个分区条件仅取决于前缀和和总数组和。 

更改一个元素会使总和移动固定量`delta`。 根据修改后的索引位于主元的左侧还是右侧，所需的前缀和会发生可预测的变化。 

通过将枢轴分为修改索引之前和之后的枢轴，我们可以仅使用哈希图频率查找来计算所有有效分区。 

每个主元在正确的类别中都会被考虑一次，从而保证正确性。 

## Python 解决方案```python
from typing import List
from collections import defaultdict

class Solution:
    def waysToPartition(self, nums: List[int], k: int) -> int:
        n = len(nums)

        prefix = [0] * n
        prefix[0] = nums[0]

        for i in range(1, n):
            prefix[i] = prefix[i - 1] + nums[i]

        total = prefix[-1]

        # rightCounts stores prefix sums for pivots not yet passed
        rightCounts = defaultdict(int)

        for pivot in range(1, n):
            rightCounts[prefix[pivot - 1]] += 1

        # Count valid partitions without modification
        answer = 0

        if total % 2 == 0:
            answer = rightCounts[total // 2]

        leftCounts = defaultdict(int)

        for i in range(n):
            delta = k - nums[i]

            currentWays = 0

            # Pivots before index i
            leftTarget = total + delta

            if leftTarget % 2 == 0:
                currentWays += leftCounts[leftTarget // 2]

            # Pivots after index i
            rightTarget = total - delta

            if rightTarget % 2 == 0:
                currentWays += rightCounts[rightTarget // 2]

            answer = max(answer, currentWays)

            # Move pivot i+1 from right to left
            if i < n - 1:
                pivotPrefix = prefix[i]

                rightCounts[pivotPrefix] -= 1

                if rightCounts[pivotPrefix] == 0:
                    del rightCounts[pivotPrefix]

                leftCounts[pivotPrefix] += 1

        return answer
```该实现首先构建前缀和，以便可以立即计算每个分区和。 

接下来，我们填充`rightCounts`与所有可能的主元前缀和。 每个枢轴对应于`prefix[pivot - 1]`。 

基线答案是使用原始总和计算的。 如果总数是偶数，则任何具有前缀和的主元`total // 2`是有效的。 

主循环考虑将每个元素更改为`k`。 

对于每个索引：

 -`delta`表示总和的变化量。 
- 我们计算修改索引之前和之后的枢轴所需的前缀和目标。 
- 哈希图查找立即给出有效枢轴的数量。 

最后，我们将当前的枢轴前缀从`rightCounts`进入`leftCounts`，保持未来迭代的不变性。 

## 解决方案```go
package main

func waysToPartition(nums []int, k int) int {
	n := len(nums)

	prefix := make([]int64, n)
	prefix[0] = int64(nums[0])

	for i := 1; i < n; i++ {
		prefix[i] = prefix[i-1] + int64(nums[i])
	}

	total := prefix[n-1]

	rightCounts := make(map[int64]int)

	for pivot := 1; pivot < n; pivot++ {
		rightCounts[prefix[pivot-1]]++
	}

	answer := 0

	if total%2 == 0 {
		answer = rightCounts[total/2]
	}

	leftCounts := make(map[int64]int)

	for i := 0; i < n; i++ {
		delta := int64(k - nums[i])

		currentWays := 0

		leftTarget := total + delta

		if leftTarget%2 == 0 {
			currentWays += leftCounts[leftTarget/2]
		}

		rightTarget := total - delta

		if rightTarget%2 == 0 {
			currentWays += rightCounts[rightTarget/2]
		}

		if currentWays > answer {
			answer = currentWays
		}

		if i < n-1 {
			pivotPrefix := prefix[i]

			rightCounts[pivotPrefix]--

			if rightCounts[pivotPrefix] == 0 {
				delete(rightCounts, pivotPrefix)
			}

			leftCounts[pivotPrefix]++
		}
	}

	return answer
}
```Go 解决方案遵循与 Python 版本相同的逻辑，但使用`int64`为了安全起见，因为前缀和可能超过 32 位整数限制。 

Go 映射会针对缺失的键自动返回零值，这简化了频率查找。 

与Python不同`defaultdict`, Go 需要使用显式映射初始化`make`。

 ## 边缘情况

 当数组在没有任何修改的情况下已经拥有最大可能数量的有效分区时，就会出现一种重要的边缘情况。 粗心的实施可能总是会强制进行更改并意外地减少答案。 此实现在尝试修改之前显式计算基线答案，确保考虑未更改的数组。 

另一个棘手的情况涉及奇数总和。 分区要求总和能被均分为相等的两半。 如果总数是奇数，则最初不存在分区。 然而，改变一个元素可能会改变总数的奇偶性。 该实现在计算目标之前会仔细检查整除性，以防止错误的楼层划分行为。 

具有许多重复前缀和的数组也很重要。 多个主元可以共享相同的前缀值，尤其是在包含零或重复模式的数组中。 使用频率图而不是集合可确保正确计算每个有效的主元。 

最后一个微妙的情况涉及相对于修改后的索引的枢轴。 修改元素之前的枢轴和修改元素之后的枢轴的行为不同，因为更改的值对分区的不同侧有贡献。 该算法通过维护单独的左右频率图来处理这个问题，保证每个枢轴使用正确的平衡方程。
