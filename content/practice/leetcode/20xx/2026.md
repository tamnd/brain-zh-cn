[LeetCode 2026 题](https://leetcode.com/problems/low-quality-problems/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题给了我们一个名为`Problems`。 每行代表一个 LeetCode 问题并包含三列：

 | 专栏 | 意义|
 | --- | --- |
 |`problem_id`| 问题的唯一标识符 |
 |`likes`| 喜欢该问题的用户数量 |
 |`dislikes`| 不喜欢该问题的用户数量 |

 我们必须找出所有喜欢百分比严格小于的问题`60%`。 

相似百分比定义为：$$\frac{\text{likes}}{\text{likes} + \text{dislikes}} \times 100$$如果该百分比小于，则问题被视为低质量`60`。 

输出应仅包含`problem_id`此类问题的值，按升序排列。 

这本质上是一个过滤问题。 对于表中的每一行，我们计算喜欢与总票数的比率，并检查它是否低于阈值。 

与算法密集型问题相比，输入规模非常小，因为这是一个 SQL 数据库问题。 我们不是在代码中处理数百万个操作。 相反，重点是在 SQL 中正确表达过滤条件。 

一个重要的观察结果是条件严格小于`60%`。 如果问题恰好有`60%`喜欢，它不应该包含在结果中。 

另一个微妙之处是整数除法。 在 SQL 中，根据数据库系统，整数相除可能会截断小数。 使用整数除法的简单实现可能会产生不正确的结果。 我们必须确保使用十进制算术。 

该问题保证每一行都有一个有效的`problem_id`，总得票数是有意义的。 由于百分比公式除以`(likes + dislikes)`，我们假设分母非零。 

## 方法

 ### 蛮力方法

 暴力方式是逐一处理每一行，手动计算相似百分比，然后收集百分比低于的所有行`60`。 

从概念上讲，这意味着：

 1. 读取表中的每一行。 
2. 计算：$$\frac{\text{likes}}{\text{likes} + \text{dislikes}} \times 100$$3. 将结果与`60`。 
4. 保持匹配`problem_id`价值观。 
5. 对最终结果进行排序。 

这种方法是正确的，因为每个问题都是根据低质量问题的确切定义进行独立评估的。 

然而，在数据库系统中，在 SQL 之外手动逐行迭代是低效且不必要的。 数据库针对声明式过滤操作进行了优化，使用`WHERE`条款。 

### 最佳方法

 关键的见解是 SQL 数据库旨在直接在查询中使用算术表达式来有效地过滤行。 

我们可以直接表达条件，而不是外部迭代：```
likes / (likes + dislikes) < 0.6
```为了避免整数除法问题，我们将一个操作数转换为十进制值：```
likes * 1.0 / (likes + dislikes)
```这保证了浮点运算。 

数据库引擎在内部评估每行的条件并仅返回匹配的行。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n) | O(n) | 手动迭代所有行并存储结果 |
 | 最佳| O(n) | O(1) | O(1) | 直接在数据库引擎中使用SQL过滤|

 ## 算法演练

 1. 首先从`Problems`桌子。 
2. 对于每一行，使用以下公式计算相似比率：$$\frac{\text{likes}}{\text{likes} + \text{dislikes}}$$3. 通过乘法将除法转换为浮点运算`likes`经过`1.0`。 这可以防止整数截断。 
4. 将计算出的比率与`0.6`。 
5. 仅保留比率严格小于的行`0.6`。 
6. 仅返回`problem_id`柱子。 
7. 对输出进行排序`problem_id`按升序排列。 

### 为什么它有效

 该算法直接实现了低质量问题的数学定义。 使用精确的百分比条件独立检查每一行。 由于 SQL 评估所有行的过滤条件，因此每个符合条件的问题都只包含一次，并且排除每个不符合条件的问题。 

## Python 解决方案

 尽管这是一个数据库问题并且通常使用 SQL 解决，但等效的 Python 逻辑可以编写如下。```python
from typing import List

class Solution:
    def lowQualityProblems(
        self,
        problems: List[List[int]]
    ) -> List[int]:
        result: List[int] = []

        for problem_id, likes, dislikes in problems:
            total_votes = likes + dislikes
            like_ratio = likes / total_votes

            if like_ratio < 0.6:
                result.append(problem_id)

        result.sort()

        return result
```该实现迭代每个问题条目并使用浮点除法计算相似比率。 

变量`total_votes`存储分母，即喜欢和不喜欢的总数。 

变量`like_ratio`代表喜欢该问题的用户比例。 

如果该比率严格小于`0.6`， 这`problem_id`被附加到结果列表中。 

最后，在返回之前对结果进行排序，匹配所需的输出顺序。 

对于实际的LeetCode数据库提交，SQL查询是：```python
SELECT problem_id
FROM Problems
WHERE likes * 1.0 / (likes + dislikes) < 0.6
ORDER BY problem_id;
```## 解决方案```go
package main

import (
	"sort"
)

type Solution struct{}

func (s Solution) lowQualityProblems(problems [][]int) []int {
	result := []int{}

	for _, problem := range problems {
		problemID := problem[0]
		likes := problem[1]
		dislikes := problem[2]

		totalVotes := likes + dislikes
		likeRatio := float64(likes) / float64(totalVotes)

		if likeRatio < 0.6 {
			result = append(result, problemID)
		}
	}

	sort.Ints(result)

	return result
}
```Go 版本遵循与 Python 实现相同的逻辑。 

Go 特有的一项重要细节是显式类型转换。 Go 中的整数除法会截去小数，因此两个操作数都必须转换为`float64`划分之前。 

结果切片使用动态扩展`append`， 和`sort.Ints`用于确保升序。 

对于实际的 LeetCode 数据库解决方案，SQL 仍然是：```go

FROM Problems
WHERE likes * 1.0 / (likes + dislikes) < 0.6
ORDER BY problem_id;

 ## 边缘情况

 ### 点赞数刚好 60% 的问题

 一个常见的错误是使用`<= 0.6`而不是`< 0.6`。 该问题明确指出低质量问题的百分比必须严格低于`60%`。 

例如：```
likes = 60
dislikes = 40
```比例正好是`0.6`，所以这个问题一定不会出现在结果中。 

实现正确地使用了严格比较。 

### 整数除法错误

 在许多 SQL 引擎和编程语言中，整数除法会截断小数值。 

例如：```
1 / 2 = 0
```而不是：```
0.5
```如果不小心使用了整数除法，许多比率就会变得不正确，从而导致错误的过滤结果。 

SQL 解决方案通过使用以下方式避免了这种情况：```
likes * 1.0 / (likes + dislikes)
```这强制浮点运算。 

### 空结果集

 有可能没有问题满足低质量条件。 

例如：```
[1, 10, 1]
[2, 20, 2]
```这两个问题的相似百分比均大于`60%`。 

该实现正确返回空结果，没有错误或特殊情况处理。
