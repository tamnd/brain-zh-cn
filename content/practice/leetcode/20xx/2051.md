 # LeetCode 2051 - 商店中每个会员的类别

 ## 问题理解

 这个问题要求我们根据每个商店成员的购物行为将他们分类为一个类别。 分类取决于会员访问商店后购买的频率。 

我们得到三个数据库表：

 -`Members`包含所有成员的列表。 
-`Visits`记录会员的每次商店访问。 
-`Purchases`记录访问期间的购买情况。 

表之间的重要关系是：

 - 一个会员可以多次访问。 
- 一次购买与一次访问相关。 
- 并非每次访问都会产生购买。 

转化率定义为：$$\text{conversion rate} = \frac{100 \times \text{number of purchases}}{\text{number of visits}}$$类别规则为：

 | 转化率| 类别 |
 | --- | --- |
 | >= 80 | 钻石 |
 | >= 50 且 < 80 | 黄金|
 | < 50 | 银 |
 | 没有访问 | 铜奖|

 输出必须包括：

 -`member_id`-`name`-`category`对于每一位成员`Members`桌子。 

一个关键细节是访问量为零的成员仍必须在输出中显示为`"Bronze"`。 这意味着我们不能简单地汇总`Visits`单独表，因为这样做会排除从未访问过的成员。 

另一个重要的细节是，购买是通过匹配之间的访问 ID 来计算的。`Visits`和`Purchases`。 由于每个购买行对应一次访问，因此会员的购买次数实际上就是出现在购买行中的访问次数。`Purchases`桌子。 

该问题保证：

 -`member_id`是独一无二的`Members`-`visit_id`是独一无二的`Visits`-`visit_id`在`Purchases`引用现有访问

 这使得连接变得简单并消除了歧义。 

重要的边缘情况包括：

 - 没有来访的会员
 - 有访问但零购买的会员
 - 转化率正好达到 50% 的会员
 - 转化率恰好达到 80% 的会员
 - 转化率为小数的会员，例如`33.33`实现必须仔细正确地处理部门和类别边界。 

## 方法

 ### 蛮力方法

 强力解决方案将单独处理每个成员并重复扫描`Visits`和`Purchases`表。 

对于每个会员：

 1. 扫描整个`Visits`用于统计访问次数的表。 
2. 对于每次匹配的访问，扫描`Purchases`表来确定购买是否存在。 
3. 计算转化率。 
4. 指定类别。 

这种方法之所以有效，是因为它显式地计算每个成员所需的统计数据。 然而，它的效率很低，因为同一个表被扫描了很多次。 

如果有：

 -`M`会员
 -`V`访问
 -`P`购买

 那么重复扫描大致会导致：$$O(M \times (V + P))$$时间复杂度。 

对于大型数据集，这会变得不必要的昂贵。 

### 最佳方法

 关键的见解是聚合应该发生一次，而不是重复。 

我们可以：

 1. 每个会员的总访问量。 
2. 每个会员的购买总额。 
3. 将这些汇总结果与`Members`桌子。 
4. 使用 a 计算类别`CASE`表达。 

这很有效，因为 SQL 数据库是为分组聚合和连接而设计的。 通过仅对访问和购买进行一次分组，我们可以避免重复扫描。 

最佳方法使用：

 -`LEFT JOIN`保留没有访问的成员
 -`GROUP BY`汇总计数
 -`CASE`来确定类别

 ## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(M × (V + P)) | O(M × (V + P)) | O(1) | O(1) | 重复扫描每个成员的表 |
 | 最佳| O(V + P + M) | O(M)| 聚合一次并高效连接 |

 ## 算法演练

 1. 从`Members`表，因为每个成员都必须出现在最终结果中，即使是那些没有访问过的成员。 
2. 执行`LEFT JOIN`从`Members`到`Visits`。 这确保了未访问的成员仍包含在`NULL`访问值。 
3. 执行另一个`LEFT JOIN`从`Visits`到`Purchases`。 这使我们能够确定哪些访问导致了购买。 
4. 将行分组依据`member_id`和`name`。 分组后：

 -`COUNT(v.visit_id)`给出访问次数。 
-`COUNT(p.visit_id)`给出购买数量。 
5、处理会员零访问的特殊情况。 此类成员被归类为`"Bronze"`立即避免被零除。 
6. 否则，计算转化率：$$100 \times \frac{\text{purchase count}}{\text{visit count}}$$1. 使用`CASE`赋值语句：

 -`"Diamond"`如果转化率 >= 80
 -`"Gold"`如果转化率 >= 50
 -`"Silver"`否则
 2. 返回会员ID、姓名、类别。 

### 为什么它有效

 该算法之所以有效，是因为每次访问都恰好属于一个会员，并且每次购买都恰好属于一次访问。 加入后的分组可以正确聚合每个​​成员的所有访问和购买。 

使用`LEFT JOIN`保证保留未访问的成员。 聚合产生的计数准确地表示了转换公式所需的总数。 类别条件是互斥的，涵盖所有可能的情况，因此每个成员都只会收到一个类别。 

## Python 解决方案

 即使这是一个数据库问题，LeetCode 也需要 SQL 查询。 以下查询是完整接受的解决方案。```python
# Write your MySQL query statement below

SELECT
    m.member_id,
    m.name,
    CASE
        WHEN COUNT(v.visit_id) = 0 THEN 'Bronze'
        WHEN 100 * COUNT(p.visit_id) / COUNT(v.visit_id) >= 80 THEN 'Diamond'
        WHEN 100 * COUNT(p.visit_id) / COUNT(v.visit_id) >= 50 THEN 'Gold'
        ELSE 'Silver'
    END AS category
FROM Members m
LEFT JOIN Visits v
    ON m.member_id = v.member_id
LEFT JOIN Purchases p
    ON v.visit_id = p.visit_id
GROUP BY m.member_id, m.name;
```查询开始于`Members`表，因为每个成员都必须出现在输出中。 

第一个`LEFT JOIN`connects visits to members. 由于外部联接行为，没有访问的成员仍保留在结果中。 

第二个`LEFT JOIN`将购买与访问联系起来。 由于并非每次访问都会进行购买，因此此加入也必须是`LEFT JOIN`。 

连接后，行按成员分组。 这允许聚合函数计算总计：

 -`COUNT(v.visit_id)`统计访问次数。 
-`COUNT(p.visit_id)`计算购买量。 

这`CASE`然后表达式确定正确的类别。 首先检查青铜条件，因为它可以防止被零除，并且代表与转换百分比无关的特殊类别。 

其余条件从最高阈值到最低阈值进行评估。

 ## 边缘情况

 ### 没有访问过的会员

 这是问题中最重要的边缘情况。 使用内部连接的简单解决方案`Members`和`Visits`会将此类成员完全排除在结果之外。 

该实现通过使用`LEFT JOIN`开始于`Members`。 没有访问过的成员仍保留在分组结果中`COUNT(v.visit_id) = 0`，允许查询正确分配`"Bronze"`。 

### 有访问但没有购买的会员

 有些会员可能会多次光临商店但没有购买任何东西。 在这些情况下，购买次数变为零，而访问次数仍为正值。 

该实现自然地处理了这个问题，因为`COUNT(p.visit_id)`当不存在匹配的购买行时变为零。 因此转化率变为`0`，正确映射到`"Silver"`。 

### 边界转换率

 阈值，例如精确值`50%`确切地说`80%`是差一错误的常见来源。 

该实现明确使用`>= 80`为了`"Diamond"`和`>= 50`为了`"Gold"`。 这保证：

 -`50%`变成`"Gold"`-`80%`变成`"Diamond"`与问题规范完全匹配。
