 ## 解决方案

 ## 问题理解

 这个问题要求我们实现一个`read(buf, n)`使用受限制的 API 调用的函数`read4(buf4)`。 挑战在于我们不允许直接访问文件，相反，我们一次只能检索最多四个字符的数据块。 

乍一看，这可能看起来与 LeetCode 157 非常相似，但有一个关键的区别：`read()`函数可能被调用多次。 这极大地改变了问题，因为`read4()`可以过度读取不是立即需要的数据。 

要理解为什么这很重要，请考虑一个文件`"abcdef"`和一个电话`read(buf, 3)`:

 -`read4()`回报`"abcd"`- 我们只需要`"abc"`- 额外的角色`"d"`一定不能丢失

 如果`read()`稍后再次调用，例如`read(buf, 2)`，我们必须返回`"de"`, 意思是剩余的`"d"`上一次调用的内容必须仍然可用。 

换句话说，这个问题要求我们在多次调用中保持**持久的内部状态**`read()`。 

输入概念上包括：

 - 隐藏文件流
 - 一系列`read(n)`来电
 - 目标缓冲区`buf`写字符的地方

 每次调用的预期输出是实际读取的字符数。 这可能小于`n`如果到达文件末尾。 

限制相对较小，文件长度可达`500`并且至多`10`查询。 这意味着性能要求不是很高。 然而，挑战不在于规模，而在于正确处理调用之间的剩余字符。 

一些边缘情况很容易破坏简单的实现。 请求可能要求少于四个字符，从而导致`read4()`获取额外未使用的字符。 文件可能会在此之前结束`n`字符被读取。 文件用完后可能会发生多次连续调用。 另一个重要的细节是 LeetCode 在测试用例中保留类变量，因此实例状态必须正确初始化，而不是意外地全局共享。 

## 方法

 ### 蛮力方法

 一个幼稚的实现会重复调用`read4()`在每次调用期间`read()`并且只复制字符直到`n`字符被收集。 

这种方法的问题是它不会保留以前未使用的字符`read4()`来电。 自从`read4()`始终前进文件指针，任何获取的额外字符都将永久消耗。 

例如：```
file = "abcdef"

read(3):
read4() -> "abcd"
return "abc"

read(2):
read4() -> "ef"
```人物`"d"`完全消失。 

因为`read4()`无法倒回文件指针，任何过度读取的字符都必须缓冲在某处。 忽略这一事实的强力解决方案是不正确的。 

### 最佳方法

 关键的观察是`read4()`以固定的四个块读取，而请求的数量`n`可以是任何值。 因此，我们必须维护一个**内部缓冲区**来存储已读取但未消耗的剩余字符。 

我们保留：

 - 大小固定的内部缓冲区`4`- 指向该缓冲区中当前未读位置的指针
 - 当前存储的有效字符数

 每当`read()`称为：

 1. 首先消耗内部缓冲区中已有的所有剩余字符。 
2. 如果内部缓冲区变空，调用`read4()`再次。 
3. 继续直到：

 -`n`字符被复制，或者
 - 已到达文件末尾。 

这可确保调用之间不会丢失字符。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n) | O(1) | O(1) | 多次调用不正确，因为多余的字符被丢弃 |
 | 最佳| O(n) | O(1) | O(1) | 使用持久缓冲区保留未读字符 |

 ## 算法演练

 1. 在构造函数（或 Go 的闭包）中初始化持久状态。 我们维持：

 -`buffer4`，大小为 4 的可重用内部缓冲区
 -`buffer_pointer`, 下一个未读索引
 -`buffer_count`, 当前存储的有效字符数
 2. 什么时候`read(buf, n)`被调用，初始化一个变量`total_read = 0`。 这会跟踪已将多少字符复制到目标缓冲区中。 
3.同时`total_read < n`，检查内部缓冲区是否有剩余字符。 
4. 如果内部缓冲区耗尽（`buffer_pointer == buffer_count`）， 称呼`read4(buffer4)`重新填充它。 
5. 重置`buffer_pointer = 0`因为我们是从刷新缓冲区的开头开始的。 
6.如果`read4()`回报`0`，我们已经到达文件末尾，所以立即停止。 
7. 将字符从内部缓冲区一一复制到`buf`直到：

 - 我们到达`n`请求的字符，或
 - 内部缓冲区耗尽。 
8. 更新`buffer_pointer`当字符被消耗时，未来的调用将从正确的位置继续。 
9. 返回`total_read`。 

### 为什么它有效

 不变的是内部缓冲区始终存储由返回的每个未读字符`read4()`。 我们绝不会意外丢弃字符。 这`buffer_pointer`确保我们准确地从上次调用停止的地方继续读取。 自从`read4()`仅当内部缓冲区为空时才调用，每个文件字符仅处理一次并以正确的顺序返回。 

## Python 解决方案```python
from typing import List

# The read4 API is already defined for you.
# def read4(buf4: List[str]) -> int:

class Solution:
    def __init__(self):
        self.buffer4 = [""] * 4
        self.buffer_pointer = 0
        self.buffer_count = 0

    def read(self, buf: List[str], n: int) -> int:
        total_read = 0

        while total_read < n:
            # Refill internal buffer if exhausted
            if self.buffer_pointer == self.buffer_count:
                self.buffer_count = read4(self.buffer4)
                self.buffer_pointer = 0

                # End of file
                if self.buffer_count == 0:
                    break

            # Copy characters from internal buffer
            while (
                total_read < n
                and self.buffer_pointer < self.buffer_count
            ):
                buf[total_read] = self.buffer4[self.buffer_pointer]
                total_read += 1
                self.buffer_pointer += 1

        return total_read
```该实现使用三个实例变量来保存多个调用之间的状态。`buffer4`存储从以下位置获取的临时字符`read4()`。`buffer_pointer`跟踪下一个未读字符，同时`buffer_count`记录缓冲区中当前存在多少个有效字符。 

里面`read()`，我们反复尝试满足要求`n`人物。 在复制数据之前，我们检查内部缓冲区是否还有未读的字符。 如果没有，我们使用`read4()`。 

什么时候`read4()`回报`0`，我们知道文件已耗尽并立即停止。 

内部循环将字符从内部缓冲区复制到目的地`buf`同时更新两个指针。 至关重要的是，未使用的角色仍保留在里面`buffer4`以供将来调用。 

## 解决方案```go
/**
 * The read4 API is already defined for you.
 *
 *     read4 := func(buf4 []byte) int
 */

var solution = func(read4 func([]byte) int) func([]byte, int) int {
    buffer4 := make([]byte, 4)
    bufferPointer := 0
    bufferCount := 0

    return func(buf []byte, n int) int {
        totalRead := 0

        for totalRead < n {
            // Refill internal buffer if exhausted
            if bufferPointer == bufferCount {
                bufferCount = read4(buffer4)
                bufferPointer = 0

                // End of file
                if bufferCount == 0 {
                    break
                }
            }

            // Copy from internal buffer
            for totalRead < n && bufferPointer < bufferCount {
                buf[totalRead] = buffer4[bufferPointer]
                totalRead++
                bufferPointer++
            }
        }

        return totalRead
    }
}
```Go 解决方案遵循与 Python 完全相同的逻辑，但使用闭包变量而不是实例变量。 由于 Go 没有`Solution`在这个问题存根中的类中，我们声明`buffer4`,`bufferPointer`， 和`bufferCount`在返回的函数之外，因此它们在调用之间持续存在。 

使用切片代替 Python 列表，并将字节直接复制到`buf`。 整数溢出不是问题，因为输入大小非常小。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 每个字符最多被复制一次 |

 时间复杂度为`O(n)`因为我们最多复制`n`每次调用期间将字符写入目标缓冲区。 虽然`read4()`有时可能会读取额外的字符，每个文件字符总体上仅处理一次。 

空间复杂度为`O(1)`因为辅助缓冲区总是大小`4`，无论输入大小如何。

 ## 边缘情况

 ### 阅读少于四个字符

 错误的常见来源发生在以下情况：`read4()`检索的字符多于当前请求实际需要的字符。 例如，如果文件是`"abcdef"`我们打电话给`read(3)`,`read4()`可能会取到`"abcd"`。 幼稚的实现可能会意外丢弃`"d"`。 

此实现通过维护持久的内部缓冲区和指针来避免该问题。 未使用的字符将被存储以供将来调用。 

### 请求的字符数多于现有字符数

 如果`n`超过剩余文件长度，我们应该只返回可用的字符。 例如，阅读`4`字符来自`"abc"`应该返回`3`。 

该实现通过检查是否正确处理了这个问题`read4()`回报`0`，表示文件结束。 此时，阅读立即停止。 

### 文件结束后多次调用

 文件用完后，以后的调用应该一致返回`0`而不是尝试无效读取。 

实现自然地处理了这个问题。 一次`read4()`回报`0`，任何额外的字符都不能加载到内部缓冲区中，因此后续调用会立即终止。 

### 调用中剩余的字符

 这是问题的决定性挑战。 在一次调用中获取但未使用的字符必须在以后保持可用。 

例如：```
file = "abcdef"

read(1) -> "a"
read(2) -> "bc"
read(3) -> "def"
```如果没有持久状态，该序列将会失败，因为在第一次调用期间获取的额外字符将会丢失。 内部缓冲机制通过准确地按要求保存未读数据来保证正确性。
