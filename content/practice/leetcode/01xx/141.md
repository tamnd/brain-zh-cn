 # LeetCode 141，链表循环

 ## 问题理解

 本题要求我们判断一个单向链表是否包含环。 遵循以下规则时存在循环`next`指针最终会返回到已经访问过的节点，而不是到达`None`。 

输入是单链表的头节点。 每个节点包含一个值和一个指向下一个节点的指针。 问题陈述提到了一个名为`pos`，但该值仅由 LeetCode 在内部使用来构建测试用例。 它没有传递到函数中，我们不需要在我们的解决方案中直接使用它。 

预期输出是一个布尔值：

 - 返回`True`如果列表中某处存在循环。 
- 返回`False`如果列表正常终止于`None`指针。 

约束告诉我们列表最多可以包含`10^4`节点。 这个值足够大，以至于低效的重复遍历可能会出现问题，但又足够小，以至于线性时间解决方案完全可行。 

一些边缘情况很重要：

 - 列表可能为空，这意味着`head`是`None`。 
- 该列表可能只包含一个节点。 
- 单个节点可能指向其自身，从而创建长度为 1 的循环。 
- 循环可以从头节点开始。 
- 循环可能从列表中间的某个位置开始。 
- 该列表可能根本不包含循环。 

重复重新访问节点而不跟踪它们的简单实现可能会进入无限循环，因此循环检测是问题的核心挑战。 

## 方法

 ### 蛮力方法

 一个简单的解决方案是使用哈希集跟踪我们访问的每个节点。 

当我们遍历链表时，我们将每个节点引用存储在集合中。 在访问一个节点之前，我们检查它是否已经存在于集合中：

 - 如果是，我们就返回到之前访问过的节点，这意味着存在循环。 
- 如果我们到达`None`，链表正常结束，不存在循环。 

这种方法是正确的，因为非循环列表中的每个节点都被访问一次。 在循环列表中，最终遍历必须重新访问已经见过的节点。 

缺点是需要额外的内存使用。 在最坏的情况下，我们可能会存储哈希集中的所有节点，需要`O(n)`额外的空间。 

### 最佳方法

 最优解采用弗洛伊德周期检测算法，也称为龟兔赛跑算法。 

关键的观察是，如果存在循环，则以不同速度移动的两个指针最终必须在循环内相遇。 

我们使用：

 - 缓慢移动的指针，一次移动一步
 - 一次移动两步的快速指针

 如果没有循环，快指针最终到达`None`。 

如果存在循环，则快指针比慢指针更快地围绕循环循环，因此最终两个指针指向同一个节点。 

这种方法完全避免了额外的内存并实现了恒定的空间复杂度。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n) | O(n) | 使用哈希集来跟踪访问过的节点 |
 | 最佳| O(n) | O(1) | O(1) | 使用两个以不同速度移动的指针 |

 ## 算法演练

 ### 弗洛伊德的两指针算法

 1.初始化两个指针，`slow`和`fast`，都从头节点开始。 
2. 在列表中移动`fast`和`fast.next`不是`None`。 此条件确保快速指针可以安全地向前移动两步，而不会导致错误。 
3. 将慢速指针移动一步：```
slow = slow.next
```4. 将快指针移动两步：```
fast = fast.next.next
```5. 移动两个指针后，检查它们是否指向同一个节点。 
6. 如果`slow == fast`，存在循环。 返回`True`。 
7. 如果循环退出是因为`fast`或者`fast.next`变成`None`，列表正常终止并且不存在循环。 返回`False`。 

### 为什么它有效

 如果链表没有循环，则快指针最终会到达链表末尾，因为它比慢指针移动得更快。 因此，算法正确返回`False`。 

如果链表包含循环，则两个指针最终都会进入循环。 一旦进入，快速指针在每次迭代期间都会在慢速指针上获得一个节点，因为它移动两步，而慢速指针移动一步。 由于循环的长度有限，因此快指针最终必须赶上慢指针，使它们相遇。 因此，算法正确返回`True`。 

## Python 解决方案```python
# Definition for singly-linked list.
# class ListNode:
#     def __init__(self, x):
#         self.val = x
#         self.next = None

from typing import Optional

class Solution:
    def hasCycle(self, head: Optional[ListNode]) -> bool:
        slow = head
        fast = head

        while fast and fast.next:
            slow = slow.next
            fast = fast.next.next

            if slow == fast:
                return True

        return False
```实现首先分配两个`slow`和`fast`到头节点。 

这`while`仅当快速指针可以安全地向前移动两步时，循环才会继续。 这可以防止解除引用`None`。 

Inside the loop:

 -`slow`advances one node
 -`fast`前进两个节点

 After moving the pointers, the code checks whether they point to the same node. If they do, a cycle exists.

 If the loop terminates naturally, the fast pointer reached the end of the list, meaning no cycle exists.

 该解决方案紧密遵循前面描述的算法，并且仅使用恒定的附加内存。 

## 解决方案```go
/**
 * Definition for singly-linked list.
 * type ListNode struct {
 *     Val int
 *     Next *ListNode
 * }
 */
func hasCycle(head *ListNode) bool {
    slow := head
    fast := head

    for fast != nil && fast.Next != nil {
        slow = slow.Next
        fast = fast.Next.Next

        if slow == fast {
            return true
        }
    }

    return false
}
```Go 实现与 Python 版本几乎相同。 

主要区别在于 Go 使用`nil`而不是`None`。 指针比较也是显式的，因为链表节点是使用指针表示的。 

在这个问题中，Go 不需要对整数溢出或内存分配进行特殊处理，因为该算法只操作节点引用。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n) | 每个指针最多遍历线性数量的节点 |
 | 空间| O(1) | O(1) | 只使用了两个指针|

 时间复杂度是线性的，因为每个指针在列表中移动最多相对于节点数恒定的次数。 即使在循环情况下，指针最多也会在`O(n)`动作。 

空间复杂度是恒定的，因为无论输入大小如何，该算法仅存储两个节点引用。

 ## 边缘情况

 ### 空列表

 空列表意味着`head`是`None`。 如果算法假设至少存在一个节点，那么这种情况很容易处理错误。 该实现可以安全地处理这个问题，因为`while fast and fast.next`条件立即失败，当`fast`是`None`。 

### 单节点无循环

 包含一个节点的列表，该节点指向`None`可能会暴露不正确的指针移动逻辑。 如果算法尝试移动`fast.next.next`没有检查`fast.next`，它会引发错误。 该实现通过检查两者来防止这种情况发生`fast`和`fast.next`在前进之前。 

### 单节点自循环

 一个节点可以直接指向它自己。 某些实现错误地假设循环需要多个节点。 在这种情况下，慢指针和快指针在移动后最终都指向同一个节点，因此算法正确地识别了循环。 

### 从头部开始循环

 该循环可以立即从第一个节点开始。 这意味着指针永远不会遍历非循环前缀。 弗洛伊德的算法仍然有效，因为快指针最终会在循环内绕过慢指针。 

### 长非循环列表

 没有循环的长列表可确保算法最终终止而不是永远循环。 快指针到达`None`，证明列表是非循环的。
