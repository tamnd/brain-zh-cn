[LeetCode 1402 题](https://leetcode.com/problems/reducing-dishes/)

 **难度：** 🔴难
 **主题：** 数组、动态规划、贪心、排序

 ## 解决方案

 ## 问题理解

 在这个问题中，我们给出一个整数数组，称为`satisfaction`，其中每个元素代表厨师烹制的菜肴的满意度。 厨师可以按照任意顺序烹饪菜肴，并且每道菜只需要一个单位的时间来准备。 

重要的细节是如何计算分数。 如果一道菜煮得及时`t`，其对最终得分的贡献为：```
t * satisfaction[i]
```总分是所有选定菜肴的这些贡献的总和。 

厨师还可以完全丢弃菜肴。 这一点至关重要，因为如果在错误的时间加入负面满意度的菜肴，可能会降低总分，或者根本不会。 

任务是计算最大可能的总喜欢时间系数。 

输入尺寸相对较小：

 -`1 <= n <= 500`-`-1000 <= satisfaction[i] <= 1000`自从`n`只有500，一个`O(n^2)`动态规划的解法是可行的。 然而，排序后问题有一个更好的贪心解。 

一些重要的观察立即浮现出来：

 - 积极的菜肴通常是有益的，因为较长的烹饪时间会增加其积极价值。 
- 如果添加负菜品将大型正菜品移至稍后时间，则负菜品可能仍然有用。 
- 如果所有菜肴均为阴性，则最佳答案是`0`，意思是什么都不煮。 
- 顺序很重要，因为后面的位置会获得更大的乘数。 

例如，如果我们做饭`[2,3,4]`:```
1*2 + 2*3 + 3*4 = 20
```但不同的顺序会产生不同的结果：```
1*4 + 2*3 + 3*2 = 16
```So the problem is fundamentally about selecting an optimal subset and arranging it optimally.

 ## 方法

 ### 蛮力方法

 The brute force solution considers every possible subset of dishes and every possible ordering of those dishes.

 对于每个子集：

 1. 生成所有排列。 
2. 计算总点赞时间系数。 
3. 追踪看到的最高分数。 

This works because it exhaustively checks every valid cooking plan, guaranteeing the optimal answer.

 However, it is computationally impossible for the given constraints. 和`n`菜品：

 - 有`2^n`子集。 
- Each subset can have factorially many permutations.

 复杂度大致变为：```
O(2^n * n!)
```即使对于相对较小的投入，这也是远远不可行的。 

### 最佳解决方案的关键见解

 关键的观察是排序极大地改变了问题的结构。 

假设菜肴按升序排列：```
[-9, -8, -1, 0, 5]
```现在想象一下从右到左制定烹饪时间表。 

如果我们已经选择了一些菜肴，则在前面添加新菜肴会使每个现有菜肴的烹饪时间增加 1。因此，添加菜肴会改变总分：```
current_sum_of_selected_dishes + new_dish_value
```更具体地说：

 - 让`suffix_sum`是当前选择的菜肴的总和。 
- 如果添加新菜品仍然存在`suffix_sum > 0`，总分增加。 
- 如果运行总和变为非正数，添加更多菜肴只会损害结果。 

这导致了贪婪策略：

 1. 对数组进行排序。 
2.从最大满意度遍历到最小满意度。 
3. 维护一个连续的后缀和。 
4. 在后缀和保持正数的情况下继续添加菜肴。 

这是有效的，因为较大的菜肴从接收较大的乘数中获益最多，并且排序的顺序自然会最大化该效果。

 ## 算法演练

 ### 最优贪心算法

 1. 排序`satisfaction`数组按升序排列。 

排序很重要，因为我们希望更大的满意度值出现在烹饪顺序的后面，在那里他们获得更大的时间乘数。 
2.初始化三个变量：

 -`suffix_sum = 0`-`total_score = 0`-`best_score = 0`这`suffix_sum`代表当前选择的菜肴的总和。 
3. 从右向左遍历排序后的数组。 

这意味着我们首先从最大的满意度值开始。 
4. 将当前菜品添加到`suffix_sum`。 

从概念上讲，我们将这道菜插入时间表的开头。 
5. 检查是否`suffix_sum`是积极的。 

如果是正数，则添加此菜肴会改善最终结果，因为所有先前选择的菜肴都会稍后移动一个时间单位并获得额外的贡献。 
6. 如果`suffix_sum > 0`：

- 添加`suffix_sum`到`total_score`- 更新`best_score`7.如果`suffix_sum <= 0`:

 - 立即停止处理。 
- 左侧任何较小的值只会进一步降低分数。 
8. 返回`best_score`。 

### 为什么它有效

 贪婪不变量是：

 > 只有当某道菜的加入增加了日程表的总贡献时，才应添加该菜品。 

当在前面插入菜肴时，每个已选择的菜肴都会获得一个额外的乘数。 因此，净改进等于插入后所有选定菜肴的总和。 

如果该总和变为非正数，则总分不再提高。 由于数组已排序，所有剩余的菜品都更小，因此继续下去无济于事。 这保证了最优性。 

## Python 解决方案```python
from typing import List

class Solution:
    def maxSatisfaction(self, satisfaction: List[int]) -> int:
        satisfaction.sort()

        suffix_sum = 0
        total_score = 0
        best_score = 0

        for i in range(len(satisfaction) - 1, -1, -1):
            suffix_sum += satisfaction[i]

            if suffix_sum <= 0:
                break

            total_score += suffix_sum
            best_score = max(best_score, total_score)

        return best_score
```实现首先按升序对数组进行排序。 这确保了更大的满意度值自然会在烹饪顺序的后期结束，在那里他们会获得更大的乘数。 

循环从右到左迭代，因为我们要考虑首先添加更大的菜肴。 变量`suffix_sum`跟踪当前选择的所有菜肴的总和。 

当我们将一道菜肴添加到时间表中时，每道已选择的菜肴都会稍后移动一个位置。 这意味着分数的总增加等于当前分数`suffix_sum`。 

如果`suffix_sum`变为非正数时，算法立即停止，因为添加更小的盘子也无法改善结果。 

变量`total_score`累积所有所选菜肴的贡献，并且`best_score`存储看到的最大值。 

## 解决方案```go
package main

import "sort"

func maxSatisfaction(satisfaction []int) int {
	sort.Ints(satisfaction)

	suffixSum := 0
	totalScore := 0
	bestScore := 0

	for i := len(satisfaction) - 1; i >= 0; i-- {
		suffixSum += satisfaction[i]

		if suffixSum <= 0 {
			break
		}

		totalScore += suffixSum

		if totalScore > bestScore {
			bestScore = totalScore
		}
	}

	return bestScore
}
```Go 实现遵循与 Python 版本完全相同的逻辑。 

内置的`sort.Ints`函数按升序对切片进行排序。 Go 切片已经动态运行，因此不需要特殊的数组处理。 

这些约束保证整数溢出对于 Go 的标准来说不是问题`int`输入，因为最大可能分数仍然在范围内。 

与 Python 不同，Go 需要显式变量声明和手动最大比较。

 ## 边缘情况

 当所有菜肴的满意度值为负时，就会出现一种重要的边缘情况。 一个幼稚的实现可能仍然会尝试烹饪一些菜肴，从而产生负的总分。 然而，这个问题允许完全丢弃所有盘子。 贪心解决方案很自然地处理这个问题，因为第一个后缀和变为非正数，导致算法立即停止并返回`0`。 

当一些负面菜肴仍然有益时，就会出现另一种微妙的情况。 例如：```
[-2, 5]
```仅限烹饪`5`给出：```
5
```但做饭`[-2, 5]`给出：```
(-2*1) + (5*2) = 8
```这说明了为什么我们不能简单地丢弃所有负值。 只要运行后缀和保持正数，实现就会正确地包括负菜。 

第三个重要的情况涉及零。 零价值的菜肴既不会直接带来帮助，也不会造成直接伤害，但它们可以在以后改变积极的菜肴。 该算法自然地处理这个问题，因为零保留后缀和而不减少它。 如果运行后缀和保持正数，则仍包含零。 

另一个边缘情况是重复值。 由于该算法仅依赖于排序和累积和，因此重复的数字不会产生任何特殊的处理问题。 数组就像`[5,5,5]`正确处理并产生最佳加权总数。 

最后，最小可能的输入大小，其中`n = 1`，也必须正确工作。 该实现可以正确处理正单元素数组和负单元素数组，而不需要任何特殊情况逻辑。
