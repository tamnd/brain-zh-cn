[LeetCode 第 1406 题](https://leetcode.com/problems/stone-game-iii/)

 **难度：** 🔴难
 **主题：** 数组、数学、动态规划、博弈论

 ## 解决方案

 ## 问题理解

 在这个游戏中，两个玩家，爱丽丝和鲍勃，轮流从一排的开头移走石头。 每块石头都有一个整数值，可以是正数、零或负数。 在每一回合中，玩家可以从剩余行的前面恰好拿走 1、2 或 3 个石子。 

玩家的分数是其个人收集的宝石值的总和。 爱丽丝先行动，两个玩家总是做出最优的决定。 目标是确定游戏的最终结果：

 - 返回`"Alice"`如果爱丽丝以更高的总分完成比赛。 
- 返回`"Bob"`如果鲍勃以更高的总分完成比赛。 
- 返回`"Tie"`如果两个分数相等。 

输入是一个数组`stoneValue`， 在哪里`stoneValue[i]`代表的值`i-th`排中的石头。 

约束条件很重要：

 - 数组长度可以大到`5 * 10^4`- 宝石价值范围为`-1000`到`1000`这些约束立即排除了指数暴力递归。 由于每个位置最多可以分支为三个选择，因此朴素递归会组合爆炸。 

另一个重要的观察结果是宝石价值可能为负。 这显着改变了策略。 有时，拿更少的棋子可以更好地避免负值，而有时，拿更多的棋子是必要的，迫使对手陷入不利的境地。 

重要的边缘情况包括：

 - 仅包含负数的数组
 - 长度为 1、2 或 3 的非常短的数组
 - 双方玩家可以强制得分相等的情况
 - 最好的举动不是贪婪地获取最大的直接总和的情况
 - 大量输入，没有记忆的递归会超时

 该问题保证至少存在一颗石头，因此我们永远不需要处理空的输入数组。 

## 方法

 ### 蛮力方法

 最直接的方法是递归地模拟每个可能的移动序列。 

在任何位置`i`，当前玩家最多有三个选择：

 - 拿走 1 块石头
 - 拿2块石头
 - 拿3块石头

 对于每个选择，游戏都会从下一个位置递归地继续。 由于两名球员都发挥最佳水平，因此每个球员都试图最大化他们的最终分数差异。 

递归状态由数组中的当前索引定义。 从这个位置开始，我们递归地探索所有可能的未来动作。 

这种方法是正确的，因为它明确地评估每个有效的游戏路径并在每个阶段选择最佳的移动。 

然而，它太慢了。 每个状态最多可分为 3 个新状态，大致产生：$$O(3^n)$$最坏情况下的时间复杂度。 

和`n = 50000`，这是完全不可行的。 

### 最佳解决方案的关键见解

 关键的观察是游戏有重叠的子问题。 

假设我们定义：

 -`dp[i]`=当前玩家从索引开始可以获得的最大分数差`i`“分数差”这句话极其重要。 

我们不是单独跟踪 Alice 和 Bob，而是跟踪：$$\text{current player's score} - \text{opponent's score}$$从位置`i`, 如果当前玩家拿走总价值的石子`take`，那么对手将最优地实现`dp[nextIndex]`。 

因此，净优势变为：$$take - dp[nextIndex]$$这是有效的，因为在当前移动之后，角色会切换。 

我们只需要计算每个索引一次，这大大降低了复杂性。

 ## 算法演练

 1.定义一个DP数组，其中`dp[i]`表示当前玩家从index开始能达到的最大分差`i`。 
2. 初始化基本情况：

 -`dp[n] = 0`这意味着当没有剩余棋子时，双方都无法获得任何额外分数。 
3. 从右向左处理数组。 

我们向后计算结果，因为位置的答案`i`取决于职位`i+1`,`i+2`， 和`i+3`。 
4. 对于每个位置`i`，尝试取出 1、2 和 3 颗宝石（如果存在）。 

维持运行总和：

 -`currentSum += stoneValue[i + k]`5. 对于每一个可能的动作：

 - 当前玩家获得`currentSum`- 对手可以实现`dp[i + k + 1]`所以得到的分数差就变成了：$$currentSum - dp[i + k + 1]$$6. 选择使差异最大化的举措。 

这代表了当前玩家的最优策略。 
7. 将最佳结果存储在`dp[i]`。 
8. 填充DP数组后：

 - 如果`dp[0] > 0`, 爱丽丝获胜
 - 如果`dp[0] < 0`, 鲍勃获胜
 - 否则，平局

 ### 为什么它有效

 该算法之所以有效，是因为`dp[i]`始终代表从索引处开始回合的玩家可获得的最佳分数差`i`。 

当玩家选择一步棋时，对手就成为剩余棋子的“当前玩家”。 自从`dp[next]`已经代表了对手在该位置的最佳优势，减去它可以正确地模拟双方的最佳比赛。 

这创建了一个有效的最优子结构，使得动态规划变得适用。 

## Python 解决方案```python
from typing import List

class Solution:
    def stoneGameIII(self, stoneValue: List[int]) -> str:
        n = len(stoneValue)

        dp = [0] * (n + 1)

        for i in range(n - 1, -1, -1):
            best_diff = float("-inf")
            current_sum = 0

            for k in range(3):
                if i + k >= n:
                    break

                current_sum += stoneValue[i + k]

                best_diff = max(
                    best_diff,
                    current_sum - dp[i + k + 1]
                )

            dp[i] = best_diff

        if dp[0] > 0:
            return "Alice"
        elif dp[0] < 0:
            return "Bob"

        return "Tie"
```实现首先创建一个大小为 DP 的数组`n + 1`。 额外的位置代表所有棋子都已被拿走的状态。 

该数组被向后处理，因为每个状态都取决于未来的状态。 在每个索引处，我们都会尝试所有合法的走法：拿走 1、2 或 3 个棋子。 

变量`current_sum`记录当前移动中所取棋子的总价值。 这避免了重复地重新计算总和。 

对于每个可能的移动，我们计算：```python
current_sum - dp[next_index]
```这代表当前玩家的增益减去对手的最优未来优势。 

最后，`dp[0]`告诉我们 Alice 最终的最佳分数差。 正值表示 Alice 获胜，负值表示 Bob 获胜，零表示平局。 

## 解决方案```go
func stoneGameIII(stoneValue []int) string {
	n := len(stoneValue)

	dp := make([]int, n+1)

	for i := n - 1; i >= 0; i-- {
		bestDiff := -1 << 30
		currentSum := 0

		for k := 0; k < 3; k++ {
			if i+k >= n {
				break
			}

			currentSum += stoneValue[i+k]

			candidate := currentSum - dp[i+k+1]

			if candidate > bestDiff {
				bestDiff = candidate
			}
		}

		dp[i] = bestDiff
	}

	if dp[0] > 0 {
		return "Alice"
	} else if dp[0] < 0 {
		return "Bob"
	}

	return "Tie"
}
```Go 实现遵循与 Python 版本相同的逻辑。 

一个小的区别是负无穷大的初始化。 由于 Go 没有提供内置的整数负无穷大值，因此我们使用一个非常小的整数：```go
-1 << 30
```Go 切片是动态大小的数组，因此 DP 数组是使用创建的`make`。 

整数溢出不是问题，因为最大可能的绝对分数受以下限制：$$50000 \times 1000 = 5 \times 10^7$$很容易适合 Go 的内部`int`。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(n) | 每个索引最多评估 3 个转换 |
 | 空间| O(n) | DP 数组每个位置存储一个值 |

 该算法是线性的，因为每个索引只处理一次，并且每个状态最多考虑三个移动。 常数因子非常小。 

由于DP阵列，空间复杂度也是线性的。 由于只需要未来状态，因此该解决方案在技术上可以进一步优化到恒定空间，但当前的实现更简单且更容易理解。

 ## 边缘情况

 一种重要的边缘情况是所有宝石值均为负值。 在这些情况下，玩家被迫采取错误的行动，而最佳策略是最小化损失而不是最大化收益。 天真的贪婪方法会失败，因为拿更多的石头实际上可能会更糟。 DP 公式自然地处理了这个问题，因为它评估每一步的未来后果。 

另一个重要的边缘情况是长度小于 3 的非常小的数组。由于玩家最多可以拿三个棋子，因此实现必须避免访问越界索引。 内部循环显式检查：```
if i + k >= n:
    break
```它安全地限制移动到有效位置。 

领带的情况也很微妙。 许多实现错误地假设一名玩家必须始终获胜。 然而，最佳的比赛可以产生相同的分数。 该算法正确地处理了这个问题，因为`dp[0] == 0`明确表示玩家之间的分数差异为零。 

最后一个重要的边缘情况涉及接近最大约束大小的大输入。 没有记忆的递归解决方案将超出时间限制或递归深度限制。 自下而上的动态规划解决方案完全避免了递归，并且在线性时间内高效运行。
