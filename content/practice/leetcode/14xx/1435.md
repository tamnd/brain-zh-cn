[LeetCode 问题 1435](https://leetcode.com/problems/create-a-session-bar-chart/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 问题提供了一个名为`Sessions`有两列：

 | 专栏 | 意义|
 | ---| ---|
 |`session_id`| 会话的唯一标识符 |
 |`duration`| 会话时长（以秒为单位）|

 我们需要将会话分组到预定义的持续时间范围（称为垃圾箱）中，并计算每个垃圾箱中有多少会话。 

所需的垃圾箱是：

 | 垃圾箱标签| 持续时间范围 |
 | ---| ---|
 |`[0-5>`| 0 分钟至 5 分钟以内 |
 |`[5-10>`| 5 分钟（含）至 10 分钟以内 |
 |`[10-15>`| 10 分钟（含）至 15 分钟以内 |
 |`15 or more`| 15 分钟或更长 |

 由于持续时间以秒为单位存储，因此我们必须将分钟边界转换为秒：

 | 垃圾箱标签| 秒范围 |
 | ---| ---|
 |`[0-5>`|`0 <= duration < 300`|
 |`[5-10>`|`300 <= duration < 600`|
 |`[10-15>`|`600 <= duration < 900`|
 |`15 or more`|`duration >= 900`|

 输出应包含每个 bin，即使计数为零。 

该问题从根本上来说是一个分类和聚合任务。 对于每个会话，我们确定它属于哪个存储桶，然后增加该存储桶的计数。 

一个重要的细节是结果必须包括具有零会话的垃圾箱。 仅计算现有匹配项的简单分组查询可能会意外忽略空箱。 

输入大小足够小，性能不是问题，但仔细编写 SQL 很重要，因为我们必须保证所有四个类别都出现在最终结果中。 

一些重要的边缘情况包括：

 - 会话完全在 300、600 或 900 秒等边界上
 - 仍必须出现在结果中的空垃圾箱
 - 多个会话落入同一个垃圾箱
 - 非常长的持续时间，全部属于`"15 or more"`类别

 正确处理包含和排除边界是此问题中最常见的错误来源。 

## 方法

 ### 蛮力方法

 蛮力的想法是扫描`Sessions`每个 bin 单独列出一个表。 

例如：

 - 一个查询计算 0 到 299 之间的持续时间
 - 另一个计算 300 到 599 之间的持续时间
 - 另一个计算 600 到 899 之间的持续时间
 - 另一个计数持续时间大于或等于 900

 然后我们使用以下方法将四个计数结合起来`UNION`。 

这种方法是正确的，因为每个会话都属于一个 bin，并且每个 bin 都是独立计数的。 

但是，它会多次重复扫描该表。 尽管这个问题中的数据集很小，但重复遍历同一张表是低效且不必要的。 

### 最佳方法

 更好的方法是扫描一次表并使用条件聚合对每一行进行分类。 

关键的见解是 SQL 聚合函数可以使用以下表达式有条件地计算行数：```
SUM(condition)
```或者```
COUNT(CASE WHEN ... THEN 1 END)
```这使我们能够一次性处理所有会话，同时维护每个类别的计数。 

由于该问题还需要计数为零的 bin，因此我们显式构造输出行并附加聚合计数。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(4N) | O(1) | O(1) | 每个 bin 扫描一次表 |
 | 最佳| O(N) | O(1) | O(1) | 具有条件聚合的单遍 |

 ## 算法演练

 ### 最优 SQL 算法

 1. 遍历`Sessions`表一次。 

每行包含一个会话持续时间（以秒为单位）。 我们确定持续时间属于哪个预定义范围。 
2.内部维护4个计数器。 

我们需要为每个垃圾箱配备一个计数器：

 -`[0-5>`-`[5-10>`-`[10-15>`-`15 or more`3. 对于每个会话，评估持续时间范围。 

我们检查：

 - 持续时间是否小于 300？ 
- 是在300到599之间吗？ 
- 是在 600 到 899 之间吗？ 
- 至少900吗？ 
4. 增加匹配计数器。 

由于范围是互斥的，因此每个会话都只贡献于一个 bin。 
5. 显式返回所有四个 bin。 

即使计数为零，该行仍必须出现在结果中。 

### 为什么它有效

 该算法之所以有效，是因为四个范围将所有可能的持续时间划分为不重叠的类别。 

每个持续时间都满足一个条件：

 - 少于300
 - 300 至 599 之间
 - 600 至 899 之间
 - 至少 900

 由于每个会话只贡献一个存储桶，因此最终计数是正确的。 

## Python 解决方案

 LeetCode 数据库问题是使用 SQL 而不是可执行的 Python 代码来解决的。 以下是MySQL的正确解决方案。```python
# This problem is solved using SQL, not executable Python code.

"""
SELECT '[0-5>' AS bin,
       COUNT(CASE WHEN duration < 300 THEN 1 END) AS total
FROM Sessions

UNION ALL

SELECT '[5-10>' AS bin,
       COUNT(CASE WHEN duration >= 300 AND duration < 600 THEN 1 END) AS total
FROM Sessions

UNION ALL

SELECT '[10-15>' AS bin,
       COUNT(CASE WHEN duration >= 600 AND duration < 900 THEN 1 END) AS total
FROM Sessions

UNION ALL

SELECT '15 or more' AS bin,
       COUNT(CASE WHEN duration >= 900 THEN 1 END) AS total
FROM Sessions;
"""
```该解决方案执行四次聚合，每个容器一次。 每个查询仅对满足相应持续时间范围的行进行计数。`COUNT(CASE WHEN ... THEN 1 END)`有效是因为`COUNT`忽略`NULL`价值观。 匹配条件的行贡献`1`，而不匹配的行贡献`NULL`。`UNION ALL`被用来代替`UNION`因为我们不需要重复消除。 使用`UNION ALL`效率稍微高一些。 

每个 SELECT 语句都显式定义 bin 标签，确保所有 bin 出现在输出中，即使它们的计数为零。

 ## 边缘情况

 ### 边界持续时间

 精确等于 300、600 和 900 秒的值很容易引入相差一的错误。 

例如：

 - 300秒必须属于`[5-10>`- 600秒必须属于`[10-15>`- 900秒必须属于`15 or more`该实现通过仔细使用包含下限和排除上限来正确处理此问题。 

### 空垃圾箱

 一个常见的错误是仅返回包含行的容器。 然而，该问题明确要求所有四个 bin 都出现，即使计数为零。 

该实现通过显式构造四个 SELECT 语句并将它们与`UNION ALL`。 

### 空表

 如果`Sessions`表不包含任何行，查询仍必须返回：

 | 斌 | 总计 |
 | ---| ---|
 |`[0-5>`| 0 |
 |`[5-10>`| 0 |
 |`[10-15>`| 0 |
 |`15 or more`| 0 |

 由于聚合函数如`COUNT`在空输入时返回零，查询自然会正确处理这种情况。
