[LeetCode 问题 1409](https://leetcode.com/problems/queries-on-a-permutation-with-key/)

 **难度：** 🟡 中等
 **主题：** 数组、二叉索引树、模拟

 ## 解决方案

 ## 问题理解

 这个问题要求我们模拟整数的动态排列并在元素不断移动时回答位置查询。 

最初，我们得到一个排列：```
P = [1, 2, 3, ..., m]
```对于每一个值`queries`数组，我们必须执行两个操作：

 1. 查找当前位置`queries[i]`在排列中`P`，使用**基于 0 的索引**。 
2. 将该查询值移至排列的**前面**。 

移动元素之前找到的位置将成为结果数组的一部分。 

换句话说，每个查询都会更改排列的排列，并且未来的查询取决于更新的顺序。 这意味着排列会随着时间的推移而演变，因此我们无法独立处理每个查询。 

例如，如果：```
P = [1,2,3,4,5]
queries[i] = 3
```价值`3`目前处于索引`2`，所以我们记录`2`在答案中。 然后我们移动`3`到前面：```
P = [3,1,2,4,5]
```下一个查询将处理此修改后的排列。 

输入包括：

 -`queries`，表示请求值的整数数组
 -`m`，它定义了初始排列`[1,2,3,...,m]`输出是一个数组，其中每个元素代表相应查询值在移动到前面之前的位置。 

限制相对较小：

 -`m <= 1000`-`queries.length <= m <= 1000`这些限制告诉我们，即使是二次解也是可以接受的。 由于最大工作量约为`1000 × 1000 = 10^6`，暴力破解是可行的。 然而，该问题被标记为**二元索引树**，这表明存在一种更具可扩展性和优雅的方法。 

有几个边缘情况需要考虑。 重复查询可以多次将相同的数字移到前面，这意味着以后的访问可能会突然变成索引`0`。 查询还可能会重复地以接近排列末尾的值为目标，从而迫使幼稚的实现进行许多转变。 该问题保证所有查询值都是介于`1`和`m`，所以我们永远不需要处理丢失的元素或无效的输入。 

## 方法

 ### 暴力模拟

 最直接的解决方案是直接模拟排列。 

我们维护一个表示当前排列的列表。 对于每个查询：

 1. 使用线性扫描搜索查询值。 
2. 记录其索引。 
3. 将其从当前位置移除。 
4. 将其插入到开头。 

这是有效的，因为它完全遵循问题的规则。 每个查询都会正确更新排列，因此后面的查询会遵守正确的顺序。 

然而，定位一个元素需要`O(m)`时间，并且删除和插入列表也会花费时间`O(m)`因为元素会移动位置。 由于我们以这种方式处理每个查询，因此总复杂度变为`O(n × m)`在哪里`n = len(queries)`。 

虽然在当前的限制下可以接受，但这种方法对于较大的输入来说变得低效。 

### 最优方法，二叉索引树+位置跟踪

 关键的观察是我们需要反复回答这个问题：

 >“给定数字之前出现了多少个元素？”

 这是一个经典的前缀和问题。 

我们可以为每个数字分配一个**位置索引**，并维护一个跟踪哪些位置被占用的结构，而不是物理地移动数组中的元素。 

我们使用：

 - **哈希映射/数组**来存储每个数字的当前位置。 
- **二元索引树（芬威克树）**，用于有效计算某个位置之前存在的元素数量。 

诀窍是为未来的移动预留空间。 

假设有`n`查询。 

我们最初将数字放在以下位置：```
n+1, n+2, ..., n+m
```第一个`n`职位仍然空着。 

每当出现查询值时：

 1. 使用二叉索引树来计算其位置之前存在多少个活动元素。 
2. 将号码从原来的位置删除。 
3. 将其移动到下一个空闲的前端位置。 
4. 更新其存储位置。 

这完全避免了昂贵的移位操作。 

### 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n × m) | O(米) | 排列的直接模拟 |

 ## 算法演练

 1.让`n = len(queries)`并创建一个大小为的二叉索引树`n + m`。 

我们分配额外的空间，因为查询的元素将​​移动到前面。 我们没有改变值，而是为它们分配新的较小索引。 
2. 存储每个值的初始位置`1`到`m`。 

最初，值`x`放置在：```
position[x] = n + x
```我们故意离开岗位`[1...n]`为将来的前面插入留空。 
3. 将二元索引树中的所有初始位置标记为已占用。 

每个活跃号码都贡献`1`在目前的位置。 
4. 维护一个名为`front_position`。 

从以下开始：```
front_position = n
```这代表前面的下一个可用插槽。 
5. 一次处理一个查询。 

对于查询的值`x`:

 1. 获取当前位置`position[x]`。 
2. 查询二叉索引树以获取其之前的元素数量：```
rank = prefix_sum(current_position) - 1
```我们减去`1`因为前缀和包括元素本身，但我们只需要它之前的元素。 
3. 将此排名添加到结果数组中。 
4. 通过减去将元素从原来的位置删除`1`在二叉索引树中。 
5. 将其移至`front_position`通过添加`1`那里。 
6. 更新`position[x]`。 
7. 减量`front_position`。 
6. 处理完所有查询后返回结果数组。 

### 为什么它有效

 二叉索引树始终维护当前包含元素的位置的准确计数。 由于每个值都有唯一的位置，因此元素位置的前缀总和等于该位置之前或该位置处的活动元素的数量。 减一给出当前排列中该值的精确的从 0 开始的索引。 每次查询后更新位置可以保留正确的排序不变式，确保所有未来的查询都遵守更新后的排列。 

## Python 解决方案```python
from typing import List

class Solution:
    def processQueries(self, queries: List[int], m: int) -> List[int]:
        n = len(queries)
        size = n + m

        # Fenwick Tree
        fenwick = [0] * (size + 1)

        def update(index: int, delta: int) -> None:
            while index <= size:
                fenwick[index] += delta
                index += index & -index

        def query(index: int) -> int:
            total = 0
            while index > 0:
                total += fenwick[index]
                index -= index & -index
            return total

        # Store current positions of numbers
        positions = [0] * (m + 1)

        # Initialize permutation positions
        for value in range(1, m + 1):
            position = n + value
            positions[value] = position
            update(position, 1)

        result = []
        front_position = n

        for value in queries:
            current_position = positions[value]

            # Find 0-based index
            index = query(current_position) - 1
            result.append(index)

            # Remove old position
            update(current_position, -1)

            # Move to front
            positions[value] = front_position
            update(front_position, 1)

            front_position -= 1

        return result
```该实现首先创建一个芬威克树，它有效地支持前缀求和运算和对数时间内的点更新。 这`update()`helper 调整特定位置的计数，而`query()`计算给定位置之前存在多少个活动元素。 

这`positions`数组存储每个数字的当前位置。 每个值最初都从范围开始，而不是直接将元素放置在数组的前面`[n+1, n+m]`，为将来的前面插入留出空间。 

对于每个查询，代码都会检索查询值的当前位置，并使用 Fenwick 前缀和计算其排名。 由于查询的元素会影响其自身的前缀和，因此减一会将结果转换为所需的从 0 开始的索引。 

记录答案后，实现将元素从其旧位置删除，将其插入当前的前槽，更新其存储位置，并将前指针向左移动以进行下一个查询。 

## 解决方案```go
func processQueries(queries []int, m int) []int {
	n := len(queries)
	size := n + m

	// Fenwick Tree
	fenwick := make([]int, size+1)

	update := func(index int, delta int) {
		for index <= size {
			fenwick[index] += delta
			index += index & -index
		}
	}

	query := func(index int) int {
		sum := 0
		for index > 0 {
			sum += fenwick[index]
			index -= index & -index
		}
		return sum
	}

	// Current positions of each value
	positions := make([]int, m+1)

	// Initialize positions
	for value := 1; value <= m; value++ {
		position := n + value
		positions[value] = position
		update(position, 1)
	}

	result := make([]int, 0, n)
	frontPosition := n

	for _, value := range queries {
		currentPosition := positions[value]

		// Get 0-based index
		index := query(currentPosition) - 1
		result = append(result, index)

		// Remove from old position
		update(currentPosition, -1)

		// Move to front
		positions[value] = frontPosition
		update(frontPosition, 1)

		frontPosition--
	}

	return result
}
```Go 实现遵循与 Python 解决方案相同的逻辑。 由于 Go 不像 Python 那样自然地支持嵌套命名函数，因此 Fenwick Tree 助手被实现为闭包。 切片用于动态存储芬威克树和位置。 

无需特殊处理`nil`需要与空切片进行对比，因为该问题保证了有效的输入大小。 整数溢出也不是问题，因为约束非常小并且所有值都适合 Go 的范围`int`类型。

 ## 边缘情况

 ### 重复查询相同的值

 错误的常见来源是重复查询同一元素。 在第一次查询之后，该元素应该已经位于前面，这意味着所有后续访问都应该返回索引`0`。 

例如：```
queries = [3,3,3]
m = 3
```第一次查询后，`3`移动到前面。 该实现正确更新了它在`positions`数组，因此后续前缀和计算返回`0`。 

### 最小输入大小

 最小的有效情况是：```
queries = [1]
m = 1
```由于排列是`[1]`，索引处已经存在唯一的值`0`。 该实现可以正确处理此问题，因为芬威克树仍然支持单个位置并且前缀和逻辑仍然有效。 

### 接近排列末尾的值

 查询可能会重复定位当前排列后面附近的元素，这在简单的移位解决方案中可能会很昂贵。 

例如：```
queries = [5,4,3,2,1]
m = 5
```暴力方法会反复改变许多元素。 二叉索引树解决方案通过更新位置映射和占用计数来完全避免物理移动，从而保持每个查询的对数性能。
