[LeetCode 问题 2258](https://leetcode.com/problems/escape-the-spreading-fire/)

 **难度：** 🔴难
 **主题：** 数组、二分搜索、广度优先搜索、矩阵

 ## 解决方案

 ## 问题理解

 这个问题要求我们确定当火势随着时间的推移在网格中蔓延时，在开始从网格的左上角移动到右下角之前，我们可以安全等待多长时间。 

网格包含三种类型的单元格：

 -`0`代表玩家和火都可以穿过的空草。 
-`1`代表火源。 
-`2`代表一堵阻挡运动和火势蔓延的墙。 

玩家开始于`(0, 0)`想要到达安全屋`(m - 1, n - 1)`。 

每分钟的事件顺序非常重要：

 1. 玩家先移动。 
2. 搬家后，火势蔓延到相邻的牢房。 

火势向上、下、左、右四个方向蔓延，就像标准的广度优先搜索扩展一样。 

目标是计算玩家在开始移动之前可以在起始单元保持静止的最大分钟数，同时仍然能够安全到达安全屋。 

存在三种可能的结果：

 - 返回`-1`即使立即启动也无法逃脱。 
- 返回`10^9`无论等待时间如何，逃生总是可能的。 
- 否则，返回最大有效等待时间。 

一条微妙但极其重要的规则是，在火灾到达安全屋的同一时间到达安全屋仍然被认为是安全的。 此例外仅适用于目标单元格。 对于所有其他牢房，玩家必须严格在火灾发生前到达。 

限制条件很大：

 -`m * n <= 2 * 10^4`这立即告诉我们，对整个网格进行昂贵的重复模拟可能会出现问题。 我们需要每个主要操作接近线性或近线性的复杂性。 

一些边缘情况尤其重要：

 - 火灾可能已经立即堵塞所有路径。 
- 火可能完全被墙壁围住。 
- 玩家和火焰可能同时到达细胞。 
- 安全屋允许相同的到达时间，但中间牢房不允许。 
- 在运动开始之前，起始单元本身可能最终会着火。 

幼稚的实现通常会失败，因为它错误地处理了时序比较或忘记了目标单元的特殊规则。 

## 方法

 ### 蛮力方法

 最直接的解决办法就是把每一种可能的等待时间都一一尝试。 

对于选定的等待时间`t`：

 1. 模拟火势蔓延`t`分钟。 
2. 为播放器启动BFS。 
3. 每分钟：

 - 移动播放器。 
- 蔓延火势。 
4.检查玩家是否安全到达安全屋。 

这种方法在概念上很简单，因为它直接遵循问题陈述。 不幸的是，它太慢了。 

最大有用等待时间可能非常长，可能长达`10^9`。 即使我们根据网格大小将搜索限制在某个实际限制内，重复模拟火力和玩家移动也会变得极其昂贵。 

主要的低效率是在每次测试的等待时间内从头开始重新计算火势蔓延。 

### 关键见解

 关键的优化是预先计算火灾到达每个单元的最早时间。 

这将问题从动态仿真转变为时序比较问题。 

我们可以同时从每个火力单元开始执行多源 BFS。 这给了我们：

 -`fire_time[r][c] = earliest minute fire reaches cell`一旦我们知道火灾到达时间，我们就可以使用玩家的另一个 BFS 来测试特定的等待时间是否可行。 

在玩家的 BFS 期间：

 - 对于中间单元：

 - 玩家到达时间必须严格小于火灾到达时间
 - 对于目的地：

 - 玩家到达时间可能小于或等于火灾到达时间

 现在我们可以二分搜索答案，因为可行性是单调的：

 - 如果等待`x`分钟有效，那么所有较小的等待时间也有效。 
- 如果等待`x`分钟失败，那么所有更长的等待时间也会失败。 

这将问题转化为：

 - 一个用于火灾预处理的 BFS
 - 二分搜索期间的多次 BFS 检查

 这对于约束来说足够有效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O((m × n)^2) 或更糟 | O(m × n) | 反复模拟火灾和玩家移动 |
 | 最佳 | O(m × n × log(m × n)) | O(m × n × log(m × n)) | O(m × n) | 预先计算触发时间和二分搜索等待时间 |

 ## 算法演练

 1. 使用多源 BFS 预先计算火灾到达时间。 

我们创建一个矩阵`fire_time`初始化为无穷大。 每个初始火单元随时间插入 BFS 队列`0`。 

使用 BFS 可以保证我们第一次访问某个单元时就是火灾最早到达该单元的时间。 
2. 定义可行性检查功能。 

功能`can_escape(wait)`决定玩家等待后能否生存`wait`移动前几分钟。 
3. 小心处理起始单元。 

如果火势达到`(0, 0)`在玩家开始移动之前或恰好当玩家开始移动时，逃脱是不可能的。 

由于玩家首先等待，我们要求：```
wait < fire_time[0][0]
```除非火永远不会到达起点。 
4. 为播放器运行 BFS。 

玩家的初始时间为`wait`。 

对于每个动作：

 - 搬到邻居会增加时间`1`- 无法进入墙壁
 - 跳过访问过的单元格
 5. 比较玩家到达时间和火灾到达时间。 

对于正常细胞：```
player_time < fire_time[cell]
```对于安全屋：```
player_time <= fire_time[safehouse]
```这直接实现了声明中的特殊规则。 
6. 返回安全屋是否可达。 

如果BFS在有效的时序约束下到达目的地，则等待时间是可行的。 
7. 二分查找最大有效等待时间。 

由于可行性是单调的：

 - 有效的等待形成前缀
 - 无效等待形成后缀

 我们对等待时间进行二分搜索。 
8. 处理无限等待的情况。 

如果最大可行等待非常大，具体来说至少`m * n`，那么火焰永远无法有效地阻挡玩家。 

在这种情况下，返回：```
10^9
```### 为什么它有效

 火灾 BFS 正确计算每个可到达单元格的最早可能火灾到达时间，因为 BFS 探索未加权网格中的最短路径。 

然后，玩家 BFS 检查玩家是否可以沿着某条路径保持在火势前方。 由于每次移动只花费一分钟，BFS 再次保证最短的到达时间。 

二分查找是有效的，因为等待更长的时间永远无法提高生存能力。 一旦等待时间变得不可能，所有更长的等待时间也都是不可能的。 

这些属性共同保证了正确性。 

## Python 解决方案```python
from collections import deque
from typing import List

class Solution:
    def maximumMinutes(self, grid: List[List[int]]) -> int:
        rows = len(grid)
        cols = len(grid[0])

        INF = 10**18
        directions = [(1, 0), (-1, 0), (0, 1), (0, -1)]

        fire_time = [[INF] * cols for _ in range(rows)]
        queue = deque()

        # Multi-source BFS for fire
        for r in range(rows):
            for c in range(cols):
                if grid[r][c] == 1:
                    fire_time[r][c] = 0
                    queue.append((r, c))

        while queue:
            r, c = queue.popleft()

            for dr, dc in directions:
                nr = r + dr
                nc = c + dc

                if (
                    0 <= nr < rows
                    and 0 <= nc < cols
                    and grid[nr][nc] != 2
                    and fire_time[nr][nc] == INF
                ):
                    fire_time[nr][nc] = fire_time[r][c] + 1
                    queue.append((nr, nc))

        def can_escape(wait: int) -> bool:
            # Fire reaches start before or at departure
            if wait >= fire_time[0][0]:
                return False

            queue = deque([(0, 0, wait)])
            visited = [[False] * cols for _ in range(rows)]
            visited[0][0] = True

            while queue:
                r, c, time = queue.popleft()

                if r == rows - 1 and c == cols - 1:
                    return True

                for dr, dc in directions:
                    nr = r + dr
                    nc = c + dc
                    next_time = time + 1

                    if not (0 <= nr < rows and 0 <= nc < cols):
                        continue

                    if grid[nr][nc] == 2 or visited[nr][nc]:
                        continue

                    fire_arrival = fire_time[nr][nc]

                    # Destination allows equal arrival
                    if nr == rows - 1 and nc == cols - 1:
                        if next_time > fire_arrival:
                            continue
                    else:
                        if next_time >= fire_arrival:
                            continue

                    visited[nr][nc] = True
                    queue.append((nr, nc, next_time))

            return False

        left = 0
        right = rows * cols + 1
        answer = -1

        while left <= right:
            mid = (left + right) // 2

            if can_escape(mid):
                answer = mid
                left = mid + 1
            else:
                right = mid - 1

        if answer == rows * cols + 1:
            return 10**9

        return answer
```该实现首先计算每个单元的最早火灾到达时间。 这是使用多源 BFS 完成的，其中所有火力单元最初都插入到队列中。 

这`fire_time`矩阵存储火到达每个单元的最短分钟。 无法到达的单元格保持无穷远。 

辅助函数`can_escape(wait)`等待后检查是否可以逃脱`wait`分钟。 它会立即拒绝在运动开始之前起始单元燃烧的情况。 

玩家的 BFS 跟踪位置和当前时间。 每个动作都会增加一分钟的时间。 

时序比较是实现中最重要的部分：

 - 中间单元格需要严格的不平等。 
- 目的地允许平等。 

最后，二分查找有效地确定了最大可行等待时间。 

## 解决方案```go
package main

import "container/list"

func maximumMinutes(grid [][]int) int {
	rows := len(grid)
	cols := len(grid[0])

	const INF int = 1_000_000_000

	directions := [][]int{
		{1, 0},
		{-1, 0},
		{0, 1},
		{0, -1},
	}

	fireTime := make([][]int, rows)
	for i := range fireTime {
		fireTime[i] = make([]int, cols)
		for j := range fireTime[i] {
			fireTime[i][j] = INF
		}
	}

	type Node struct {
		r, c int
	}

	queue := list.New()

	// Multi-source BFS for fire
	for r := 0; r < rows; r++ {
		for c := 0; c < cols; c++ {
			if grid[r][c] == 1 {
				fireTime[r][c] = 0
				queue.PushBack(Node{r, c})
			}
		}
	}

	for queue.Len() > 0 {
		front := queue.Front()
		queue.Remove(front)

		cur := front.Value.(Node)

		for _, d := range directions {
			nr := cur.r + d[0]
			nc := cur.c + d[1]

			if nr < 0 || nr >= rows || nc < 0 || nc >= cols {
				continue
			}

			if grid[nr][nc] == 2 {
				continue
			}

			if fireTime[nr][nc] != INF {
				continue
			}

			fireTime[nr][nc] = fireTime[cur.r][cur.c] + 1
			queue.PushBack(Node{nr, nc})
		}
	}

	canEscape := func(wait int) bool {
		if wait >= fireTime[0][0] {
			return false
		}

		type State struct {
			r, c, t int
		}

		visited := make([][]bool, rows)
		for i := range visited {
			visited[i] = make([]bool, cols)
		}

		queue := list.New()
		queue.PushBack(State{0, 0, wait})
		visited[0][0] = true

		for queue.Len() > 0 {
			front := queue.Front()
			queue.Remove(front)

			cur := front.Value.(State)

			if cur.r == rows-1 && cur.c == cols-1 {
				return true
			}

			for _, d := range directions {
				nr := cur.r + d[0]
				nc := cur.c + d[1]
				nt := cur.t + 1

				if nr < 0 || nr >= rows || nc < 0 || nc >= cols {
					continue
				}

				if grid[nr][nc] == 2 || visited[nr][nc] {
					continue
				}

				fireArrival := fireTime[nr][nc]

				if nr == rows-1 && nc == cols-1 {
					if nt > fireArrival {
						continue
					}
				} else {
					if nt >= fireArrival {
						continue
					}
				}

				visited[nr][nc] = true
				queue.PushBack(State{nr, nc, nt})
			}
		}

		return false
	}

	left := 0
	right := rows*cols + 1
	answer := -1

	for left <= right {
		mid := (left + right) / 2

		if canEscape(mid) {
			answer = mid
			left = mid + 1
		} else {
			right = mid - 1
		}
	}

	if answer == rows*cols+1 {
		return 1_000_000_000
	}

	return answer
}
```Go 实现与 Python 版本非常相似，但存在一些特定于语言的差异。 

Go不提供内置的双端队列，所以`container/list`用于 BFS 队列。 

结构体用于清晰地表示 BFS 状态。 这避免了使用嵌套切片或数组来获取坐标和时间戳。 

这`INF`value 使用大整数常量而不是 Python 的任意精度整数来表示。 

切片是手动初始化的，因为 Go 不支持 Python 风格的列表推导式。

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(m × n × log(m × n)) | O(m × n × log(m × n)) | 一火 BFS 加上带有 BFS 检查的二分搜索 |
 | 空间| O(m × n) | 触发时间、访问的数组和 BFS 队列 |

 火灾预处理 BFS 最多访问每个单元一次，给出`O(m × n)`复杂。

二分查找执行`O(log(m × n))`检查，因此总复杂度变为：```
O(m × n × log(m × n))
```这对于包含多达`2 × 10^4`细胞。

 ## 边缘情况

 ### 火永远不会到达安全屋

 当墙壁将火焰与玩家的路径完全隔离时，就会出现一种棘手的情况。 在这种情况下，火灾 BFS 给许多单元留下了无限的到达时间。 

有缺陷的实现可能仍然会施加人为的时间限制并错误地拒绝较长的等待时间。 

此实现正确处理了这种情况，因为无法到达的开火时间保持无限，允许玩家 BFS 永远自由移动。 当二分搜索检测到任意大的可行等待时，算法返回`10^9`。 

### 玩家和火力同时到达目的地

 目标单元格有一个特殊的规则：```
player_time <= fire_time[destination]
```许多不正确的解决方案意外地要求各处都存在严格的不平等。 

此实现显式检查当前单元格是否为安全屋，并仅在此处应用宽松比较。 

### 火在运动开始前到达起始单元

 如果玩家等待太久，起始单元本身可能会在移动开始之前点燃。 

这很容易被忽视，因为许多 BFS 实现仅在运动开始后检查时序。 

该解决方案使用以下方法立即正确拒绝此类等待：```
if wait >= fire_time[0][0]:
    return False
```这保证了玩家永远不会从燃烧的细胞开始。
