[LeetCode 问题 2205](https://leetcode.com/problems/the-number-of-users-that-are-eligible-for-discount/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 问题给了我们一个名为`Purchases`，其中每行代表用户进行的购买。 每条记录包含三个字段：

 -`user_id`, 识别客户
 -`time_stamp`, indicating when the purchase happened
 -`amount`，代表花了多少钱

 这对`(user_id, time_stamp)`是唯一的，这意味着同一用户不能在完全相同的时间戳进行两次购买。 

我们还给出了三个参数：

 -`startDate`-`endDate`-`minAmount`如果用户至少进行了一次购买且满足以下两个条件，则视为有资格获得折扣：

 1、购买时间在包含区间内`[startDate, endDate]`2. 购买金额大于或等于`minAmount`一个重要的细节是如何解释日期。 两个都`startDate`和`endDate`被视为一天的开始，这意味着：```
2022-03-05  ->  2022-03-05 00:00:00
```这意味着该间隔仅包含精确的午夜时间戳。 期间稍后购买`endDate`除非恰好发生在午夜，否则不包括这一天。 

目标是返回满足条件的不同用户的总数。 

预期输出是包含一列的单行：

 | 用户_cnt |
 | --- |
 | 合格用户数量|

 SQL操作的问题规模相对较小，任务主要是正确过滤行和计算唯一用户。 

一些边缘情况很重要：

 - 一名用户可以进行多次购买，但只需一次符合资格的购买。 
- 同一用户的多次合格购买仍应算作一个用户。 
- 准确购买`startDate 00:00:00`或者`endDate 00:00:00`都包括在内。 
- 稍后购买`endDate`日被排除在外。 
- 某些用户可能满足日期条件但不满足金额条件，反之亦然。 

## 方法

 ### 蛮力方法

 暴力法从概念上讲是逐一检查每条购买记录。 对于每一行，我们验证：

 1. 时间戳是否在允许的区间内
 2、金额是否至少`minAmount`如果两个条件都成立，我们存储`user_id`在合格用户的集合中。 

最后，我们计算收集了多少不同的用户。 

这是有效的，因为每次购买都经过独立检查，因此不会错过任何合格记录。 然而，在传统的编程环境中，手动扫描所有行可能无法有效地扩展海量数据集。 

然而，在 SQL 数据库中，关系引擎针对过滤和聚合进行了优化。 我们可以让 SQL 直接执行过滤和非重复计数，而不是手动迭代记录。 

### 最佳方法

 关键的观察结果是，我们只关心至少有一次合格购买的不同用户。 

SQL 已经为此提供了有效的操作：

 -`WHERE`过滤行
 -`COUNT(DISTINCT user_id)`计算唯一匹配用户的数量

 所以最优解是：

 1. 过滤时间戳落在区间内的行
 2. 过滤金额至少为的行`minAmount`3. 计数不同的`user_id`其余行中的值

 这种方法简洁、高效、直接映射问题需求。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n) | O(u) | 扫描每笔购买并存储合格用户|
 | 最佳 | O(n) | 内部 O(1) 或 O(u) | 具有不同计数的 SQL 过滤 |

 这里：

-`n`是购买记录的数量
 -`u`是唯一合格用户的数量

 ## 算法演练

 1. 首先读取所有行`Purchases`桌子。 
2. 使用时间间隔应用时间戳过滤器`[startDate, endDate]`。 Since both dates are interpreted as midnight timestamps, we compare directly against the datetime values.
 3. Apply the amount filter by keeping only rows where`amount >= minAmount`。 
4. 过滤后，多行可能仍属于同一用户。 由于每个用户只应计数一次，因此使用`COUNT(DISTINCT user_id)`。 
5. 返回结果为`user_cnt`。 

### 为什么它有效

 该算法之所以有效，是因为每次符合条件的购买都必须满足这两个过滤条件。 一旦所有有效行被隔离，计算不同的行`user_id`Values 保证每个符合条件的用户都会为最终答案准确贡献 1，无论他们进行了多少次符合条件的购买。 

## Python 解决方案```python
SELECT
    COUNT(DISTINCT user_id) AS user_cnt
FROM Purchases
WHERE time_stamp BETWEEN startDate AND endDate
    AND amount >= minAmount;
```该查询有两个主要部分。 

这`WHERE`子句过滤购买，以便仅保留满足这两个条件的行：

 -`time_stamp BETWEEN startDate AND endDate`-`amount >= minAmount`过滤后，`COUNT(DISTINCT user_id)`确保每个符合条件的用户仅被计数一次，即使该用户进行了多次符合条件的购买。 

最终结果返回为`user_cnt`，它与所需的输出格式匹配。 

## 解决方案```go
SELECT
    COUNT(DISTINCT user_id) AS user_cnt
FROM Purchases
WHERE time_stamp BETWEEN startDate AND endDate
    AND amount >= minAmount;
```由于这是一个数据库问题，因此解决方案语言是 SQL，而不是像 Go 这样的命令式语言。 无论平台标签是Python还是Go，都会提交相同的SQL查询。 

重要的实现细节是使用`COUNT(DISTINCT user_id)`，这可以避免重复计算多次符合条件的购买的用户。

 ## 边缘情况

 ### 同一用户多次购买

 用户可以进行多次满足条件的购买。 简单的解决方案可能会意外地计算每个符合条件的行而不是每个符合条件的用户。 

该实现通过使用以下方式避免了这种情况：```
COUNT(DISTINCT user_id)
```这保证了每个用户只对最终计数贡献一次。 

### 在午夜之后的结束日期购买

 问题明确指出`endDate`被解释为一天的开始。 这意味着：```
2022-03-20
```被视为：```
2022-03-20 00:00:00
```购买地点：```
2022-03-20 15:00:00
```因此应排除在外。 这个细节很容易被忽视，如果错误地包括一整天，可能会产生不正确的结果。 

通过直接与提供的日期时间边界进行比较，SQL 比较正确地遵循问题定义。 

### 金额等于 minAmount

 该条件要求购买至少`minAmount`。 

这意味着平等是有效的。 购买：```
amount = minAmount
```必须符合资格。 

实现使用：```
amount >= minAmount
```其中正确地包括平等情况。
