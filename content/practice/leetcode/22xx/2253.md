[LeetCode 问题 2253](https://leetcode.com/problems/dynamic-unpivoting-of-a-table/)

 **难度：** 🔴难
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 这个问题要求我们将宽表转换为标准化的基于行的格式。 数据库表`Products`每个产品包含一行，每个商店都有自己的专用列。 商店列内的值表示该商店中产品的价格。 

例如，一行可能如下所示：

 | 产品 ID | LC_Store | Nozama | Shop |
 | --- | --- | --- | --- |
 | 1 | 100 | 100 空 | 110 | 110

 这意味着：

 - 产品`1`出售于`LC_Store`为了`100`- 产品`1`不出售于`Nozama`- 产品`1`出售于`Shop`为了`110`所需的输出是“未旋转”表示。 我们需要许多具有三列的行，而不是具有许多存储列的一行：

 -`product_id`-`store`-`price`所以前一行变成：

 | 产品 ID | 商店 | 价格|
 | --- | --- | --- |
 | 1 | LC_商店 | 100 | 100
 | 1 | 店铺 | 110 | 110

 重要的细节是`NULL`值必须被忽略。 如果某产品在商店中无货，则`(product_id, store)`组合不应出现在结果中。 

挑战来自于存储列名称是动态的这一事实。 测试用例之间的名称可能有所不同，并且可以有 1 到 30 个存储列。 由于架构会动态变化，因此我们无法在 SQL 查询中对商店名称进行硬编码。 

这意味着解决方案必须：

 1.动态检查表模式
 2.自动发现所有店铺栏目
 3. 构建动态SQL查询
 4. 执行生成的查询

 这就是为什么这个问题特别需要实现一个存储过程而不是一个简单的静态 SQL 查询。 

一些边缘情况很重要：

 - 一种产品可能只存在于一家商店
 - 一种产品可能存在于所有商店
 - 产品可能根本不存在于任何商店中，这意味着每个商店栏都是`NULL`- 商店名称事先未知
 - 该表最多可以包含 30 个动态存储列

 简单的硬编码查询会失败，因为它假设商店名称是固定的。 正确的解决方案必须自动适应任何模式。 

## 方法

 ### 蛮力方法

 蛮力方法会手动编写一个`UNION ALL`查询每个商店列。 

例如：```sql
SELECT product_id, 'LC_Store' AS store, LC_Store AS price
FROM Products
WHERE LC_Store IS NOT NULL

UNION ALL

SELECT product_id, 'Nozama' AS store, Nozama AS price
FROM Products
WHERE Nozama IS NOT NULL
```这是有效的，因为每个`SELECT`提取一个商店的行，并且`UNION ALL`将所有商店合并到一个结果集中。 

然而，这种方法有一个大问题。 商店列是动态的并且事先是未知的。 由于测试用例之间的模式会发生变化，因此不可能对列名称进行硬编码。 

因此，暴力方法对于这个问题来说并不实用。 

### 最佳方法

 关键的观察是数据库模式本身包含我们需要的信息。 

MySQL 将有关表和列的元数据存储在`INFORMATION_SCHEMA.COLUMNS`桌子。 我们可以查询此元数据来动态检索属于该元数据的所有列名`Products`桌子。 

一旦我们获得了store列名，我们就可以动态生成所需的`UNION ALL`询问。 

该过程的工作原理如下：

 1. 读取除`product_id`2. 建造一个`SELECT`每个商店列的报表
 3. 将所有语句与`UNION ALL`4.动态执行生成的SQL

 这种方法会自动适应任意数量的商店列和任意商店名称。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n × s) | O(1) | O(1) | 需要硬编码商店名称 |
 | 最佳 | O(n × s) | O(s) | 动态处理任何架构 |

 这里：

-`n`= 产品数量
 -`s`= 存储列数

 ## 算法演练

 1. 查询数据库元数据使用`INFORMATION_SCHEMA.COLUMNS`。 

我们从以下位置检索每个列名称`Products`表除了`product_id`。 其余的列代表商店名称。 
2.对于每个store列，构造一个单独的`SELECT`陈述。 

每个生成的查询都具有以下形式：```sql
SELECT product_id,
       'StoreName' AS store,
       StoreName AS price
FROM Products
WHERE StoreName IS NOT NULL
```字符串文字成为输出商店名称，而实际列值成为价格。 
3. 使用组合所有生成的查询`UNION ALL`。`UNION ALL`是首选，因为我们不需要重复消除。 每行代表一个不同的`(product_id, store)`一对。 
4. 将生成的 SQL 存储在变量中。 

由于查询是动态生成的，因此我们必须在执行之前将其组装为字符串。 
5. 准备动态语句。 

MySQL 需要使用`PREPARE`用于动态生成的 SQL。 
6. 执行准备好的语句。 

这将运行生成的查询并返回未透视的结果表。 
7. 释放准备好的语句。 

这会释放与准备好的查询相关的资源。 

### 为什么它有效

 该算法保证了正确性，因为每个存储列都贡献了一个`SELECT`堵塞。 Each block outputs all non-null prices for that store. Combining all blocks with`UNION ALL`确保每一个有效`(product_id, store, price)`元组在最终结果中只出现一次。 

由于存储列是从架构本身动态发现的，因此该解决方案适用于任何有效的测试用例配置。 

## Python 解决方案

 尽管这是一个数据库问题并且通常使用 SQL 解决，但以下 Python 字符串代表了正确的 LeetCode SQL 过程解决方案。```python
class Solution:
    def unpivotProducts(self) -> str:
        return """
CREATE PROCEDURE UnpivotProducts()
BEGIN
    SET SESSION group_concat_max_len = 1000000;

    SELECT GROUP_CONCAT(
        CONCAT(
            'SELECT product_id, ''',
            COLUMN_NAME,
            ''' AS store, ',
            COLUMN_NAME,
            ' AS price FROM Products WHERE ',
            COLUMN_NAME,
            ' IS NOT NULL'
        )
        SEPARATOR ' UNION ALL '
    )
    INTO @query
    FROM INFORMATION_SCHEMA.COLUMNS
    WHERE TABLE_NAME = 'Products'
      AND COLUMN_NAME != 'product_id';

    PREPARE stmt FROM @query;
    EXECUTE stmt;
    DEALLOCATE PREPARE stmt;
END
"""
```实施开始于增加`group_concat_max_len`。 这可以防止动态生成的 SQL 查询在存在许多存储列时被截断。 

然后查询从中读取元数据`INFORMATION_SCHEMA.COLUMNS`。 每列除了`product_id`被视为存储列。 

对于每个商店列，代码动态构建一个`SELECT`提取的语句：

 - 产品ID
 - 商店名称作为字符串文字
 - 相应列中的价格值`GROUP_CONCAT`将所有生成的语句合并为一个大型 SQL 查询`UNION ALL`。 

结果查询字符串存储在`@query`。 MySQL动态SQL需要使用`PREPARE`和`EXECUTE`运行存储在变量内的查询。 

最后，`DEALLOCATE PREPARE`清理准备好的语句。

 ## 边缘情况

 当每家商店都缺货时，就会出现一种重要的边缘情况。 在这种情况下，所有存储列都包含`NULL`。 简单的实现可能仍会生成包含空价格的行。 正确的解决方案通过添加来避免此问题`WHERE store_column IS NOT NULL`到每个生成的查询块。 

另一个重要的例子涉及动态商店名称。 模式可能在不同的测试用例中包含完全不同的存储列。 硬编码的 SQL 将立即失败，因为预期的列名不存在。 使用`INFORMATION_SCHEMA.COLUMNS`确保解决方案自动适应当前架构。 

当表包含最大数量的商店时，会出现第三种边缘情况。 动态生成的 SQL 字符串可能会变得很大。 不增加`group_concat_max_len`，MySQL 可能会截断生成的查询，导致语法错误或输出不完整。 该实现显式增加了此限制以安全地处理大型模式。
