[LeetCode 1603 题](https://leetcode.com/problems/design-parking-system/)

 **难度：** 🟢简单
 **主题：** 设计、模拟、计数

 ## 解决方案

 ## 问题理解

 这个问题要求我们设计一个非常小的停车场管理系统。 该停车场包含三种类型的停车位：

 - 宽敞的停车位
 - 中型停车位
 - 小型停车位

 构造函数接收每种类型的可用空间数。 初始化后，每次到达一辆汽车，对于每辆到达的汽车，我们必须确定是否仍然有所需大小的可用停车位。 

重要的限制是汽车只能停在完全相同类型的停车位中。 大型汽车不能使用中型或小型槽，其他类型的汽车也同样如此。 

这`addCar(carType)`函数代表一辆新车进入停车场：

 -`carType = 1`意味着一辆大汽车
 -`carType = 2`意思是中型车
 -`carType = 3`意思是小型汽车

 该函数应该：

 - 返回`true`如果该类型的插槽可用，并保留一个插槽
 - 返回`false`如果没有剩余该类型的插槽

 限制非常小：

 - 每个停车位最多`1000`- 至多`1000`打电话给`addCar`将会发生

 这些限制告诉我们，性能并不是主要问题。 即使是简单的实施也很容易在时间限制内完成。 然而，该问题从根本上来说是一个设计和状态管理问题，因此首选最干净的解决方案。 

一些边缘情况很重要：

 - 停车类型可能以`0`空间
 - 多辆同类型车辆可能会连续到达
 - 一旦停车类型已满，该类型的每个未来请求都必须返回`false`- 该问题保证`carType`始终有效，这意味着它只会是`1`,`2`， 或者`3`由于保证输入有效，因此我们不需要对无效汽车类型进行额外的错误处理。 

## 方法

 ### 蛮力方法

 暴力方法将明确地单独表示每个停车位。 

例如，我们可以维护三个数组：

 - 一个阵列用于大插槽
 - 一个阵列用于中型插槽
 - 一个阵列用于小插槽

 每个槽可以存储它是否被占用。 每当一辆新车到达时，我们都会扫描相应的数组，寻找第一个未使用的插槽。 

如果我们发现一个空槽：

 - 将其标记为已占用
 - 返回`true`否则：

 - 返回`false`这种方法是正确的，因为它直接模拟了插槽级别的停车场。 每辆停放的汽车恰好占用一个停车位。 

然而，该解决方案不必要地昂贵。 每个`addCar`呼叫可能需要扫描最多`1000`插槽。 该问题不需要跟踪各个停车位，只需要跟踪容量是否剩余。 

### 最佳方法

 关键的观察是我们不关心使用哪个确切的停车位。 我们只关心每种停车类型还有多少剩余停车位。 

我们可以简单地维护三个计数器，而不是单独存储每个槽：

 - 剩余大空间
 - 剩余中等空间
 - 剩余的小空间

 当汽车到达时：

 1.检查对应的计数器是否大于零
 2. 如果是，则递减计数器并返回`true`3.否则返回`false`这是有效的，因为停车只会改变剩余停车位的数量。 确切的插槽标识无关紧要。 

这将操作减少到恒定时间。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 每次操作 O(n) | O(n) | 明确存储和扫描停车位 |
 | 最佳| 每次操作 O(1) | O(1) | O(1) | 仅存储剩余计数 |

 ## 算法演练

 ### 最优算法

 1. 使用每种类型的可用停车位数量初始化停车系统。 

我们将计数存储在按汽车类型索引的数据结构中。 由于汽车类型有`1`,`2`， 和`3`，我们可以将它们直接映射到计数。 
2. 什么时候`addCar(carType)`被调用时，检查该类型的剩余计数。 

如果计数为零，则没有可用空间，因此我们返回`False`。 
3. 如果计数大于零，则将其减一。 

这模拟为到达的汽车预留停车位。 
4. 返回`True`成功停车后。 

其高效工作的原因是系统的状态完全由剩余计数决定。 不需要额外的跟踪。 

### 为什么它有效

 该算法保持不变，即每个计数器始终等于该车型的剩余可用车位数量。 

最初，计数器由构造函数正确设置。 每次成功的停车操作都会将相应的计数减少一，与停车位的消耗相匹配。 失败的操作不会修改计数器。 

由于计数器始终反映剩余停车位的准确数量，因此检查汽车是否可以停车始终是正确的。 

## Python 解决方案```python
class ParkingSystem:

    def __init__(self, big: int, medium: int, small: int):
        self.slots = {
            1: big,
            2: medium,
            3: small
        }

    def addCar(self, carType: int) -> bool:
        if self.slots[carType] == 0:
            return False

        self.slots[carType] -= 1
        return True

# Your ParkingSystem object will be instantiated and called as such:
# obj = ParkingSystem(big, medium, small)
# param_1 = obj.addCar(carType)
```构造函数初始化一个名为的字典`slots`。 钥匙直接对应于问题中定义的汽车类型：

 -`1`对于大
 -`2`对于介质
 -`3`对于小

 这些值存储剩余空间的数量。 

里面`addCar`，该实现首先检查请求的停车类型是否有任何剩余容量。 如果该值为零，则该类型的停车场已满，因此该函数立即返回`False`。 

否则，该方法减少剩余计数并返回`True`。 

该实现很紧凑，因为问题只需要计算剩余空间而不是跟踪各个停车位置。 

## 解决方案```go
type ParkingSystem struct {
    slots [4]int
}

func Constructor(big int, medium int, small int) ParkingSystem {
    ps := ParkingSystem{}

    ps.slots[1] = big
    ps.slots[2] = medium
    ps.slots[3] = small

    return ps
}

func (this *ParkingSystem) AddCar(carType int) bool {
    if this.slots[carType] == 0 {
        return false
    }

    this.slots[carType]--
    return true
}

/**
 * Your ParkingSystem object will be instantiated and called as such:
 * obj := Constructor(big, medium, small);
 * param_1 := obj.AddCar(carType);
 */
```Go 解决方案使用固定大小的数组而不是映射。 由于有效的汽车类型只有`1`,`2`， 和`3`，数组简单高效。 

数组有大小`4`使得指数`1`,`2`， 和`3`可以直接使用，无需进行偏移计算。 

与 Python 字典不同，Go 数组需要固定大小和显式索引，但其他逻辑是相同的。 

不存在溢出问题，因为计数非常小，并且仅从初始值开始减少。

 ## 边缘情况

 ### 零初始容量

 停车类型可以从零可用空间开始。 如果实现假设每种类型至少有一个槽，那么这是常见的错误来源。 

例如：```
ParkingSystem(0, 1, 2)
```在这种情况下，每`addCar(1)`调用必须立即返回`false`。 

该实现自然地处理这个问题，因为它在递减之前检查剩余计数是否为零。 

### 容量满后重复请求

 当停车类型已满并且其他请求不断到达时，就会出现另一个重要的边缘情况。 

例如：```
ParkingSystem(1, 0, 0)
```第一个`addCar(1)`成功了，但后来`addCar(1)`一定会失败。 

有缺陷的实现可能会意外地允许负计数或继续递减到零以下。 我们的解决方案通过在计数达到零时提前返回来防止这种情况发生。 

### 独立停车类别

 每种停车类型必须独立跟踪。 

例如：```
ParkingSystem(1, 1, 1)
```停放大型车辆不得影响中小型车辆的可用性。 

该实现可以正确处理这个问题，因为每种车型都有自己的专用计数器。 更新一个计数器不会修改其他计数器。
