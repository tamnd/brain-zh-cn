[LeetCode 问题 1655](https://leetcode.com/problems/distribute-repeating-integers/)

 **难度：** 🔴难
 **主题：** 数组、哈希表、动态规划、回溯、位操作、计数、位掩码

 ## 解决方案

 ## 问题理解

 该问题询问我们是否可以使用数组中的重复整数来满足一组客户请求`nums`。 

每个客户都想要一定数量的数字，由下式给出`quantity[i]`。 重要的限制是提供给单个客户的每个号码都必须相同。 一位顾客要求`3`物品无法接收`[1,2,1]`，他们必须收到类似的东西`[5,5,5]`。 

实际数值单独并不重要。 重要的是每个值出现的次数。 例如：

-`nums = [1,1,1,2,2,3]`- 频率为：

 -`1 -> 3`-`2 -> 2`-`3 -> 1`一位客户要求`2`可以使用价值来满足物品`1`或值`2`，但不值`3`。 

目标是确定是否可以同时满足所有客户。 

约束条件非常重要：

 -`nums.length`可以大到`100000`- 最多有`50`独特的价值观
 -`quantity.length <= 10`大尺寸`nums`表明重复迭代原始数组的成本太高。 然而，客户数量较少是关键的观察结果。 由于最多有`10`客户，我们可以对客户子集使用位掩码动态编程。 

问题的根本在于将客户组分配到频率桶。 

一些边缘情况很重要：

 - 客户可能会请求比任何频率都能提供的更多的物品。 
- 多个客户可能需要小心地共享相同的频率桶。 
- 一些值`nums`可能永远不会被使用。 
- 仅当分配的总金额不超过该值的频率时，客户才能收到相同的数值。 

例如：

-`nums = [1,1,1,1]`-`quantity = [2,2]`这是有效的，因为两个客户都可以获得价值`1`。 

但：

-`nums = [1,1,1]`-`quantity = [2,2]`此操作失败，因为总需求超出了可用数量。 

## 方法

 ### 蛮力方法

 强力解决方案将尝试将客户分配给整数值的所有可能的方法。 

首先，我们计算每个不同值的频率`nums`。 然后，对于每个客户，我们尝试将他们分配到能够满足他们需求的可用频率之一。 

递归看起来像：

 - 选择一个客户
 - 尝试每个仍有足够剩余计数的频率桶
 - 扣除数量
 - 继续递归

 这种方法是正确的，因为它探索了所有可能的有效分配。 

然而，由于作业数量呈指数级增长，它变得非常慢。 即使只有`10`客户和`50`不同的频率，分支因子是巨大的。 

强力解决方案会受到等效状态的重复重新计算的影响。 

### 最优方法，位掩码动态规划

 关键的洞察是客户数量非常少，最多`10`。 

这意味着我们可以使用位掩码表示客户的任何子集：

 -`0b00101`意味着顾客`0`和`2`包括在内
 - 总子集 =`2^m`- 自从`m <= 10`，这最多是`1024`我们不会天真地一一分配客户，而是预先计算：

 - 每个客户子集所需的总数量

 然后，对于每个频率桶，我们尝试分配适合该频率的当前未服务客户的任何子集。 

这将问题转化为子集 DP 问题。 

DP状态变为：

 - 哪些客户子集已经得到满足

 这大大减少了重复工作。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 指数，大约为 O(k^m) | O(米) | 递归尝试所有分配 |
 | 最佳 | O(n * 3^m) | O(n * 3^m) | O(2^m) | O(2^m) | 使用带有位掩码优化的子集 DP |

 这里：

-`k`= 唯一值的数量
 -`m`= 顾客数量

 自从`m <= 10`,`3^m`是可以管理的。 

## 算法演练

 ### 第 1 步：计算频率

 我们首先统计每个整数出现的次数`nums`。 

例如：```
nums = [1,1,1,2,2,3]

frequencies = [3,2,1]
```实际的整数值在计数后无关紧要。 

### 步骤 2：预先计算子集和

 我们使用位掩码表示客户子集。 

认为：```
quantity = [2,3,1]
```然后：

 | 面膜| 客户 | 总和 |
 | --- | --- | --- |
 | 001| {0} | 2 |
 | 010| {1} | 3 |
 | 011| {0,1} | 5 |
 | 111 | 111 {0,1,2} | 6 |

 我们将这些总和存储在一个数组中：```
subset_sum[mask]
```这允许恒定时间查找任何子集的总需求。 

### 步骤 3：定义 DP 状态

 我们定义：```
dp[mask]
```含义：

 - 是否是子集`mask`到目前为止，使用经过处理的频率可以满足客户的要求。 

最初：```
dp[0] = True
```因为满足零客户总是可能的。 

### 步骤 4：处理每个频率

 对于每个频率计数：```
count
```我们创建一个新的 DP 数组。 

对于每个当前满意的状态：```
mask
```我们尝试分配额外的不满意的客户子集。 

### 步骤 5：枚举子集

 假设：```
remaining = full_mask ^ mask
```这代表客户还不满意。 

我们枚举所有子掩码`remaining`。 

对于每个子掩码：

 - 计算所需数量
 - 检查它是否适合当前频率```
subset_sum[submask] <= count
```如果有效：```
new_mask = mask | submask
```将其标记为可达。 

###第6步：返回最终结果

 如果：```
dp[full_mask]
```是真的，那么所有客户都能满意。 

否则，返回 false。 

## 为什么它有效

 该算法之所以有效，是因为每个 DP 状态都代表了客户子集的完整且有效的分配。 

在处理频率桶时，我们会考虑该桶可以满足的剩余客户的每个可能子集。 由于系统地探索了所有子集，因此不会遗漏任何有效的排列。 

位掩码唯一地标识哪些客户已经得到满足，从而防止重复重新计算等效状态。 

由于每个客户子集都是通过 DP 转换精确考虑的，因此该算法保证了正确性。 

## Python 解决方案```python
from typing import List
from collections import Counter

class Solution:
    def canDistribute(self, nums: List[int], quantity: List[int]) -> bool:
        frequencies = list(Counter(nums).values())

        m = len(quantity)
        full_mask = (1 << m) - 1

        subset_sum = [0] * (1 << m)

        for mask in range(1 << m):
            total = 0

            for i in range(m):
                if mask & (1 << i):
                    total += quantity[i]

            subset_sum[mask] = total

        dp = [False] * (1 << m)
        dp[0] = True

        for count in frequencies:
            next_dp = dp[:]

            for mask in range(1 << m):
                if not dp[mask]:
                    continue

                remaining = full_mask ^ mask
                submask = remaining

                while submask:
                    if subset_sum[submask] <= count:
                        next_dp[mask | submask] = True

                    submask = (submask - 1) & remaining

            dp = next_dp

        return dp[full_mask]
```实现从转换开始`nums`使用频率计数`Counter`。 由于客户只关心收到相同的数量，因此实际值无关紧要。 

这`subset_sum`array 预先计算每个客户子集的总需求。 这避免了在 DP 转换期间重复重新计算总和。 

DP数组存储当前可以满足哪些客户子集。 

对于每个频率桶，我们迭代每个可到达的状态并尝试分配额外的不满意的客户子集。 

子集枚举技巧：```python
submask = (submask - 1) & remaining
```有效地迭代所有子集`remaining`。 

最后，如果可以达到完整的客户掩码，则所有客户都可以满意。 

## 解决方案```go
package main

func canDistribute(nums []int, quantity []int) bool {
	freqMap := make(map[int]int)

	for _, num := range nums {
		freqMap[num]++
	}

	frequencies := []int{}

	for _, count := range freqMap {
		frequencies = append(frequencies, count)
	}

	m := len(quantity)
	fullMask := (1 << m) - 1

	subsetSum := make([]int, 1<<m)

	for mask := 0; mask < (1 << m); mask++ {
		total := 0

		for i := 0; i < m; i++ {
			if mask&(1<<i) != 0 {
				total += quantity[i]
			}
		}

		subsetSum[mask] = total
	}

	dp := make([]bool, 1<<m)
	dp[0] = true

	for _, count := range frequencies {
		nextDP := make([]bool, 1<<m)
		copy(nextDP, dp)

		for mask := 0; mask < (1 << m); mask++ {
			if !dp[mask] {
				continue
			}

			remaining := fullMask ^ mask
			submask := remaining

			for submask > 0 {
				if subsetSum[submask] <= count {
					nextDP[mask|submask] = true
				}

				submask = (submask - 1) & remaining
			}
		}

		dp = nextDP
	}

	return dp[fullMask]
}
```Go 实现遵循与 Python 版本相同的逻辑。 

而不是`Counter`，使用标准图进行频率计数。 

切片用于 DP 数组和子集和。 Go 没有 Python 方便的列表复制语法，所以`copy()`用于复制 DP 状态。 

整数溢出不是一个问题，因为所有值都在 Go 的范围内`int`范围。

 ## 边缘情况

 当客户请求的商品数量超过任何频率桶包含的商品数量时，就会出现一种重要的边缘情况。 例如：```
nums = [1,1,2,2]
quantity = [3]
```没有任何值出现三次，所以答案一定是错误的。 简单的实现可能会错误地组合不同的值，但 DP 解决方案可以正确地防止这种情况，因为每个子集分配都会根据单个频率计数进行检查。 

另一个棘手的边缘情况是多个客户共享相同的价值。 例如：```
nums = [1,1,1,1]
quantity = [2,2]
```双方客户都能获得价值`1`。 一些不正确的解决方案假设一种价值只能满足一位客户。 基于子集的 DP 自然可以处理跨多个客户划分频率桶的情况。 

当存在许多小客户请求时，会出现第三种重要的边缘情况：```
nums = [1,1,1,1,1]
quantity = [1,1,1,1,1]
```所有客户都可以使用相同的价值感到满意。 这强调算法是否正确处理许多子集组合。 由于 DP 系统地探索了所有客户子集，因此它可以正确识别有效的安排。 

最后的边缘情况涉及未使用的数字：```
nums = [1,1,2,3,4]
quantity = [2]
```只有两个`1`这很重要。 其余数字无关紧要。 该实现自然地处理了这个问题，因为无用的频率根本不会促成成功的 DP 转换。
