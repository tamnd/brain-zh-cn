[LeetCode 1642 题](https://leetcode.com/problems/furthest-building-you-can-reach/)

 **难度：** 🟡 中等
 **主题：** 数组、贪婪、堆（优先级队列）

 ## 解决方案

 ## 问题理解

 问题给了我们一个数组`heights`，其中每个值代表建筑物的高度。 你从建造开始`0`并尝试按顺序向右移动，一次移动一栋建筑物。 

从建筑物搬出时`i`到建筑物`i+1`，有两种可能：

 - 如果下一栋建筑较短或高度相同，您可以免费移动。 
- 如果下一栋建筑物较高，您必须使用以下任一方法补偿高度差：

 - 砖块的高度差等于砖块的高度差，或者
 - 正好一个梯子。 

目标是确定在最佳利用资源的情况下可以达到的最远建筑指数。 

重要的细节是，梯子可以覆盖任何尺寸的攀爬，而砖块的消耗与攀爬高度成比例。 因此，梯子通常在大型攀爬中更有价值，而砖块则更适合用于较小的攀爬。 

限制条件很大：

 -`heights.length`可以达到`100000`- 高度可以大到`10^6`- 砖块可以大到`10^9`这些限制立即排除了指数或二次探索方法。 我们需要一种接近线性时间的算法。 

一些边缘情况很重要：

 - 所有建筑物可能已经下降，这意味着不需要任何资源。 
- 梯子的数量可能为零。 
- 可能有零块砖。 
- 单次攀登可能会超出可用的砖块。 
- 梯子可能需要动态重新分配以应对稍后遇到的较大攀爬。 
- 一步的最佳决策可能取决于未来的攀登。 

诸如“始终首先使用砖块”或“始终首先使用梯子”之类的幼稚贪婪策略并不总是有效。 

## 方法

 ### 蛮力方法

 每当我们遇到向上攀登时，蛮力解决方案都会探索所有可能的选择。 对于每个正高度差，我们可以：

 - 花费砖块，如果有足够的可用砖块，或者
 - 花费一把梯子，如果还有的话。 

这将创建一个分支决策树。 每次攀爬时，最多可以有两种选择，因此可能性的总数呈指数级增长。 

例如，如果有`k`向上爬，可能的资源分配组合数量可以接近`2^k`。 

这种方法是正确的，因为它探索了每一个有效的分配策略并选择其中最远的可达建筑物。 然而，对于`100000`建筑物。 

### 关键见解

 关键的观察是梯子应该保留用于最大的攀登。 

假设我们在一次非常大的攀爬中使用了砖块，后来在一次较小的攀爬中使用了梯子。 交换这些选择总是可以节省砖块或保持相同的总成本。 

这意味着最优策略是：

 - 使用砖块进行较小的攀爬，
 - 使用梯子进行较大的攀爬。 

挑战在于我们无法提前知道未来的攀登情况。 

为了解决这个问题，我们从左到右处理建筑物，同时将迄今为止遇到的所有向上爬升保留在最小堆中。 

这个想法是：

 - 暂时假设每次向上攀爬都使用梯子，
 - 如果攀爬次数超过可用梯子的数量，请从堆中移除最小的攀爬次数，并用砖块代替。 

这保证了梯子始终被分配给迄今为止最大的攀爬。

 ## 算法演练

 1. 初始化一个最小堆来存储迄今为止遇到的所有正爬升。 

该堆帮助我们有效地跟踪当前分配的梯子的最小爬升。 
2. 从左到右遍历建筑物。 

对于每对相邻建筑物，计算：```
climb = heights[i+1] - heights[i]
```3.如果`climb <= 0`，继续前往下一座大楼。 

不需要任何资源，因为下一栋建筑并不高。 
4. 如果`climb > 0`，将爬升值推入最小堆。 

从概念上讲，我们暂时为这次攀爬分配了一个梯子。 
5.插入爬梯后，检查堆大小是否超过梯子数量。 

如果是这样，我们分配的梯子攀爬次数将超过允许的次数。 
6. 从堆中删除最小的爬升。 

这个最小的攀爬是用砖块而不是梯子支付的最便宜的攀爬。 
7. 从可用的积木中减去最小的攀爬高度。 

此步骤将梯子重新分配给更大的攀爬。 
8.如果bricks变为负数，则返回当前的建筑索引。 

这意味着我们无法完成到下一栋大楼的跳跃。 
9. 如果我们成功完成循环，则返回最后一个建筑物索引。 

### 为什么它有效

 该算法保持堆始终包含当前分配的梯子的攀爬不变性，并且这些是迄今为止遇到的最大攀爬。 

每当攀爬次数超过梯子数量时，最小的攀爬次数就会从梯子使用量转换为砖块使用量。 由于梯子在大型攀爬中提供最大的好处，因此这种贪婪的重新分配始终是最佳的。 

由于每个决策都会在所有先前看到的攀爬中保留最佳可能的梯子分配，因此该算法可以正确计算最远的可到达建筑物。 

## Python 解决方案```python
from typing import List
import heapq

class Solution:
    def furthestBuilding(self, heights: List[int], bricks: int, ladders: int) -> int:
        min_heap = []

        for i in range(len(heights) - 1):
            climb = heights[i + 1] - heights[i]

            if climb <= 0:
                continue

            heapq.heappush(min_heap, climb)

            if len(min_heap) > ladders:
                bricks -= heapq.heappop(min_heap)

            if bricks < 0:
                return i

        return len(heights) - 1
```实现直接遵循贪婪堆策略。 

这`min_heap`存储迄今为止遇到的每一次积极的爬升。 每次插入都代表临时为该攀登分配一个梯子。 

当堆的大小超过可用的梯子数量时，我们会移除最小的爬梯并使用砖块支付费用。 这确保了梯子保留用于更大的攀登。 

条件`bricks < 0`表示我们没有足够的砖块来完成当前的转换，因此立即返回当前索引。 

如果循环结束，则每次转换都成功，这意味着我们可以到达最终的建筑物。 

## 解决方案```go
package main

import (
	"container/heap"
)

type MinHeap []int

func (h MinHeap) Len() int {
	return len(h)
}

func (h MinHeap) Less(i, j int) bool {
	return h[i] < h[j]
}

func (h MinHeap) Swap(i, j int) {
	h[i], h[j] = h[j], h[i]
}

func (h *MinHeap) Push(x interface{}) {
	*h = append(*h, x.(int))
}

func (h *MinHeap) Pop() interface{} {
	old := *h
	n := len(old)
	value := old[n-1]
	*h = old[:n-1]
	return value
}

func furthestBuilding(heights []int, bricks int, ladders int) int {
	minHeap := &MinHeap{}
	heap.Init(minHeap)

	for i := 0; i < len(heights)-1; i++ {
		climb := heights[i+1] - heights[i]

		if climb <= 0 {
			continue
		}

		heap.Push(minHeap, climb)

		if minHeap.Len() > ladders {
			bricks -= heap.Pop(minHeap).(int)
		}

		if bricks < 0 {
			return i
		}
	}

	return len(heights) - 1
}
```Go 版本使用`container/heap`包来实现最小堆。 

与Python不同，Go不提供内置的优先级队列抽象，因此我们定义了一个自定义的`MinHeap`类型实现所需的堆接口方法。 

该算法本身与 Python 版本相同。 整数溢出不是问题，因为约束在 Go 中安全地适合`int`LeetCode 环境的范围。

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |

堆的增长永远不会比梯子的数量大得多，因此实际空间使用量很小。

 ## 边缘情况

 当所有建筑物都下降或高度相等时，就会出现一种重要的边缘情况。 在这种情况下，不需要砖块或梯子。 有缺陷的实现可能会不必要地消耗资源或错误地处理零爬升。 此实现正确地跳过了具有该条件的所有非正爬升`climb <= 0`。 

另一个关键的边缘情况是梯子为零时。 那样的话，每次向上的攀爬都必须全部用砖块支付。 堆仍然可以正常工作，因为每次插入都会立即导致弹出，将所有爬升转换为砖块使用。 

一个微妙的边缘情况涉及动态重新分配梯子。 假设我们最初在中等难度的攀爬中使用砖块，后来遇到了更大的攀爬。 永久致力于早期选择的幼稚实现可能会失败。 该解决方案通过始终将攀登存储在堆中并在必要时追溯将最小的梯子分配攀登转换为砖块使用来避免该问题。 

当攀爬后砖块恰好为零时，就会出现最后的边缘情况。 由于资源充足，该算法仍应允许进展。 仅当以下情况时才会停止实施：`bricks < 0`，它正确区分了耗尽和不足。
