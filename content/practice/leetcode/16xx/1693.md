[LeetCode 第 1693 题](https://leetcode.com/problems/daily-leads-and-partners/)

 **难度：** 🟢简单
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 问题提供了一个名为`DailySales`，其中每行代表涉及产品制造商的销售事件（`make_name`), 一条线索 (`lead_id`）和合伙人（`partner_id`）在特定日期（`date_id`）。 

目标是计算每一个独特的组合`date_id`和`make_name`，两个值：

 1. 与该日期和制造商相关的 **不同线索 ID** 的数量。 
2. 与该日期和制造商相关的**不同合作伙伴 ID** 的数量。 

重要的细节是该表**没有主键**，这意味着可能存在重复的行。 这意味着我们不能简单地计算行数或假设唯一性。 相反，我们必须使用不同的语义来计算**唯一值**。 

换句话说，我们将数据分组为`(date_id, make_name)`然后计算：

 -`unique_leads`= 不同的数量`lead_id`该组中的值
 -`unique_partners`= 不同的数量`partner_id`该组中的值

 输出可以以**任何顺序**返回，因此除非明确请求，否则不需要排序。 

例如，假设我们有：

 | 日期_id | 名称 | 铅_id | 合作伙伴 ID |
 | ---| ---| ---| ---|
 | 2020年12月8日 | 丰田 | 0 | 1 |
 | 2020年12月8日 | 丰田 | 1 | 0 |
 | 2020年12月8日 | 丰田 | 1 | 2 |

 为了`(2020-12-8, toyota)`：

- 清楚的`lead_id`值是`{0, 1}`, 计数 =`2`- 清楚的`partner_id`值是`{0, 1, 2}`, 计数 =`3`所以结果行变成：

 | 日期_id | 名称 | 独特的线索 | 独特的合作伙伴 |
 | ---| ---| ---| ---|
 | 2020年12月8日 | 丰田 | 2 | 3 |

 由于该问题属于LeetCode上的**数据库**类别，因此预期的解决方案是用**SQL**编写的，而不是Python或Go。 

对于 SQL 聚合问题来说，约束相对较小，并且任务的结构强烈建议使用`GROUP BY`结合`COUNT(DISTINCT ...)`。 

一个重要的边缘情况是存在重复行。 如果一样的话`(lead_id, partner_id)`对于同一制造商和日期，对出现多次，我们仍然必须仅对每个 ID 计数一次。 另一种边缘情况是多行包含相同的潜在客户但不同的合作伙伴，反之亦然。 我们必须独立计算潜在客户和合作伙伴的独特性。 

## 方法

 ### 蛮力方法

 暴力解决方案将在概念上处理每一个独特的`(date_id, make_name)`分别配对。 对于每个组，我们可以扫描整个表并手动维护可见的集合`lead_id`和`partner_id`价值观。 

这是有效的，因为每一行都属于同一行`(date_id, make_name)`组合提供可能的潜在客户和合作伙伴 ID。 使用集合结构可以保证唯一性。 

然而，这种方法效率低下，因为对于每个唯一的组，我们都会重复扫描整个表。 如果有`g`团体和`n`行，最坏情况的复杂度变成`O(g × n)`，这是不必要的。 

### 最佳方法

 关键的观察结果是 SQL 数据库是为分组聚合而设计的。 由于该问题明确要求每个计数`(date_id, make_name)`一对，`GROUP BY`自然适合。 

在每个组中，SQL 提供`COUNT(DISTINCT column)`有效地计算唯一值。 这可以避免自动重复计数并消除手动跟踪的需要。 

通过一次分组并在同一查询中计算两个不同的计数，我们可以高效、干净地解决问题。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(g × n) | O(n) | 重复扫描每个组的表 |
 | 最佳 | O(n log n) | O(n log n) | O(n) | 用途`GROUP BY`和`COUNT(DISTINCT)`|

 ## 算法演练

 1. 对行进行分组`date_id`和`make_name`。 

此步骤可确保同一天属于同一制造商的所有销售都一起处理。 由于结果需要每行一行`(date_id, make_name)`对，这种分组是解决方案的基础。 
2. 计数不同的`lead_id`每个组内的值。 

我们使用`COUNT(DISTINCT lead_id)`因此，相同线索的重复出现仅计算一次。 这可以正确处理重复的行和重复的引线。 
3. 计数不同的`partner_id`每个组内的值。 

相似地，`COUNT(DISTINCT partner_id)`确保每个伙伴每组最多贡献一个计数。 
4. 返回分组结果。 

每组成为一个输出行，其中包含：

 -`date_id`-`make_name`-`unique_leads`-`unique_partners`### 为什么它有效

 正确性来自于分组隔离属于同一行的事实`(date_id, make_name)`一对。 在每个组内，`COUNT(DISTINCT ...)`保证重复的 ID 只计算一次。 由于问题定义明确要求不同的计数，因此这与所需的行为精确匹配。 

## SQL 解决方案```sql
SELECT
    date_id,
    make_name,
    COUNT(DISTINCT lead_id) AS unique_leads,
    COUNT(DISTINCT partner_id) AS unique_partners
FROM DailySales
GROUP BY date_id, make_name;
```查询首先按以下方式对行进行分组`date_id`和`make_name`。 分组后，`COUNT(DISTINCT lead_id)`计算唯一潜在客户的数量，同时`COUNT(DISTINCT partner_id)`计算唯一合作伙伴的数量。 因为重复项会被忽略`DISTINCT`，即使表包含重复的行，解仍然正确。

 ## 边缘情况

 一种重要的边缘情况是**重复行**。 由于表没有主键，因此相同的行可能会出现多次。 一个天真的`COUNT(*)`方法会高估结果。 使用`COUNT(DISTINCT ...)`确保重复项不会影响最终计数。 

另一个重要的边缘情况是当**同一线索出现在多个合作伙伴**时。 例如，一位潜在客户可能在同一天与多个合作伙伴进行互动。 我们应该只计算一次领先优势，同时仍然计算所有不同的合作伙伴。 该解决方案可以处理此问题，因为潜在客户和合作伙伴的唯一性是独立计算的。 

当**同一个合作伙伴出现多个潜在客户**时，就会出现第三种边缘情况。 在这种情况下，合作伙伴数量必须保持唯一，同时潜在客户数量适当增加。 再次分开`COUNT(DISTINCT ...)`操作确保这两个指标保持准确。 

最后，一组可能包含**仅一行**。 在这种情况下，两个唯一计数都应该是`1`，假设 ID 有效。 由于聚合仍然适用于单行组，因此该实现可以自然地处理这种情况。
