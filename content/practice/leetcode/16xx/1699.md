[LeetCode 问题 1699](https://leetcode.com/problems/number-of-calls- Between-two-persons/)

 **难度：** 🟡 中等
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 该问题提供了一个数据库表，名为`Calls`，其中每一行代表两个人之间的电话通话。 该表包含三列：

 | 专栏 | 意义|
 | ---| ---|
 |`from_id`| 来电者|
 |`to_id`| 接收器|
 |`duration`| 通话时长 |

 重要的细节是，原始数据中的呼叫是有方向的，但最终结果应将两个人之间的呼叫视为属于同一对，无论方向如何。 

例如，这两行：```
(1, 2, 59)
(2, 1, 11)
```两者都描述了人与人之间的交流`1`和`2`。 该问题要求我们将它们组合成一个聚合结果。 

所需的输出应包含：

 | 专栏 | 意义|
 | ---| ---|
 |`person1`| 较小的人 ID |
 |`person2`| 较大的人员 ID |
 |`call_count`| 他们之间的通话总数|
 |`total_duration`| 他们之间所有通话的持续时间总和 |

 条件`person1 < person2`保证每个无序对在结果中恰好出现一次。 

该表不包含主键，这意味着允许重复的行。 我们必须独立计算每一行，包括重复项。 这很重要，因为重复的记录代表多次调用，并且应计入计数和总持续时间。 

约束相对简单，因为这是一个 SQL 聚合问题而不是算法优化问题。 主要挑战是正确标准化每一对，以便：```
(1, 2)
(2, 1)
```被分组在一起。 

幼稚的实现可能会错误地将它们视为单独的组。 另一个常见错误是忘记强制执行订购条件`person1 < person2`。 

重要的边缘情况包括：

 - 同一用户之间双向出现呼叫
 - 重复的通话记录
 - 数据集中多个不同的对
 - 仅与一次通话配对
 - 持续时间长但仍必须正确求和

 该问题保证了`from_id != to_id`，所以自调用永远不会发生。 

## 方法

 ### 蛮力方法

 暴力方法会尝试将每一行与其他每一行进行比较，并手动确定它们是否属于同一无序对。 

对于每个调用，我们可以：

 1. 将这对标准化为`(min(from_id, to_id), max(from_id, to_id))`2. 搜索之前处理过的对
 3. 更新计数和持续时间（如果找到）
 4. 否则创建一个新组

 如果通过重复扫描组来实现得不好，这可能会变得低效，因为每次插入可能需要对现有组进行线性搜索。 

尽管这种方法最终会产生正确的答案，但随着记录数量的增加，它的扩展性很差。 

### 最佳方法

 关键的观察结果是，呼叫对于两个参与者来说是对称的。 这对：```
(from_id, to_id)
```应始终转换为：```
(LEAST(from_id, to_id), GREATEST(from_id, to_id))
```一旦每一行都被规范化为规范排序，标准 SQL 聚合就变得非常简单。 

我们可以：

 1. 标准化每对
 2. 按标准化对分组
 3. 计算行数
 4. 总持续时间

 这将问题转化为一个简单的问题`GROUP BY`询问。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(n) | 重复扫描现有组 |
 | 最佳 | O(n) | O(n) | 对规范化后使用 SQL 分组 |

 ## 算法演练

 1. 对于每一行`Calls`表，确定较小和较大的用户 ID。 

我们使用：```
LEAST(from_id, to_id)
GREATEST(from_id, to_id)
```这确保每个无序对始终具有相同的表示。 
2. 将较小的 ID 存储为`person1`较大的 ID 为`person2`。 

这满足了以下要求：```
person1 < person2
```3. 对所有行进行分组`(person1, person2)`。 

归一化后，两个方向的呼叫都属于同一组。 
4. 计算每组中的行数。 

每一行代表一次调用，包括重复的调用。 
5. 求和`duration`每个组的列。 

这给出了两个用户之间的总通信时间。 
6. 返回分组结果。 

### 为什么它有效

 该算法之所以有效，是因为每对无序的用户都被转换为唯一的规范表示。 两个都`(1,2)`和`(2,1)`变得`(1,2)`。 因此，同一两个人之间的所有呼叫都会正确分组在一起。 然后，聚合函数计算每个组所需的总数。 

## Python 解决方案

 虽然这是一个数据库问题，但 LeetCode 数据库解决方案是用 SQL 编写的。 以下是完整的SQL解决方案。```python
SELECT
    LEAST(from_id, to_id) AS person1,
    GREATEST(from_id, to_id) AS person2,
    COUNT(*) AS call_count,
    SUM(duration) AS total_duration
FROM Calls
GROUP BY
    LEAST(from_id, to_id),
    GREATEST(from_id, to_id);
```查询首先对每对用户进行规范化。 这`LEAST()`函数总是选择较小的 ID，而`GREATEST()`选择较大的一个。 这保证了相反方向的呼叫映射到同一对。 

接下来，查询使用标准化对对行进行分组。 一旦分组，`COUNT(*)`计算呼叫总数，同时`SUM(duration)`计算组合持续时间。 

由于 SQL 聚合中保留了重复行，因此可以正确计算重复行。 

## 解决方案

 LeetCode数据库问题不需要Go实现，因为预期的提交语言是SQL。 然而，Go 中的等效逻辑可以表示如下。```go
package main

import "fmt"

type Call struct {
	FromID  int
	ToID    int
	Duration int
}

type PairStats struct {
	Person1      int
	Person2      int
	CallCount    int
	TotalDuration int
}

func normalize(a, b int) (int, int) {
	if a < b {
		return a, b
	}
	return b, a
}

func aggregateCalls(calls []Call) []PairStats {
	statsMap := make(map[[2]int]*PairStats)

	for _, call := range calls {
		p1, p2 := normalize(call.FromID, call.ToID)

		key := [2]int{p1, p2}

		if _, exists := statsMap[key]; !exists {
			statsMap[key] = &PairStats{
				Person1: p1,
				Person2: p2,
			}
		}

		statsMap[key].CallCount++
		statsMap[key].TotalDuration += call.Duration
	}

	result := []PairStats{}

	for _, stats := range statsMap {
		result = append(result, *stats)
	}

	return result
}

func main() {
	calls := []Call{
		{1, 2, 59},
		{2, 1, 11},
		{1, 3, 20},
		{3, 4, 100},
		{3, 4, 200},
		{3, 4, 200},
		{4, 3, 499},
	}

	result := aggregateCalls(calls)

	for _, r := range result {
		fmt.Println(r)
	}
}
```Go 实现使用由一对标准化 ID 作为键控的哈希映射。 这反映了 SQL 分组行为。 数组被用作映射键，因为 Go 中的固定大小数组是可比较和可散列的。 

与 Python 字典不同，Go 映射在更新值之前需要明确的存在性检查。

    return (min(a, b), max(a, b))

    result = {}

    return result

 ## 边缘情况

 一种重要的边缘情况是双向调用。 一个幼稚的实现可能会对待`(1,2)`和`(2,1)`作为不同的群体。 这会错误地将聚合分成两行。 该实现通过始终使用标准化对来避免这种情况`LEAST()`和`GREATEST()`。 

另一个重要的边缘情况是重复记录。 由于表没有主键，因此相同的行可能会出现多次。 某些实现会在聚合之前错误地删除重复项。 这会低估呼叫次数和总持续时间。 正确的实现使用独立地计算每一行`COUNT(*)`。 

第三个重要的边缘情况是只有一次调用的配对。 即使一对中仅存在一条记录，聚合逻辑仍必须生成有效行。 分组操作自然会处理这个问题，因为具有一行的组仍然会产生正确的计数和持续时间值。 

最后的边缘情况涉及较大的持续时间值。 如果同一对之间存在许多呼叫，则总持续时间可能会变长。 SQL 聚合函数可以安全地处理这个问题，Go 实现直接使用整数累加，无需截断或浮点转换。
