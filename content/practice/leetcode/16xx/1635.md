[LeetCode 问题 1635](https://leetcode.com/problems/hopper-company-queries-i/)

 **难度：** 🔴难
 **主题：** 数据库

 ## 解决方案

 ## 问题理解

 此问题要求我们使用三个数据库表中的信息生成 2020 年的每月统计数据：`Drivers`,`Rides`， 和`AcceptedRides`。 

第一个必需的统计量是`active_drivers`。 对于 2020 年的每个月，我们必须统计截至该月底已有多少司机加入公司。 如果驾驶员的行为符合以下条件，则被视为活跃驾驶员：`join_date`小于或等于所评估月份的最后一天。 未来几个月加入的司机尚未计算在内。 

第二个所需的统计量是`accepted_rides`。 对于 2020 年的每个月，我们必须计算该月接受的乘车次数。 The accepted rides are stored in the`AcceptedRides`表，但实际请求日期来自`Rides`通过共享表`ride_id`。 这意味着我们需要将这两个表连接在一起，以确定每个月属于哪些已接受的行程。 

输出必须包含 2020 年 1 月到 12 月每个月的一行，即使一个月内接受的乘车次数为零。 这些行必须按月份编号升序排列。 

输入表表示如下：

 -`Drivers`存储驱动程序注册信息。 
-`Rides`存储乘车请求及其请求日期。 
-`AcceptedRides`存储司机实际接受的乘车服务。 

一个重要的细节是，并非所有乘车请求都会被接受。 因此，仅仅计算乘车请求是不够的。 我们必须只计算出现在`AcceptedRides`。 

另一个重要细节是驾驶员数量是累积的。 如果司机在 3 月份加入，他们应该出现在 3 月、4 月、5 月以及 2020 年以后的每个月份。 

该问题保证每个接受的乘车都存在于`Rides`表，所以之间的连接`AcceptedRides`和`Rides`始终有效。 

一些边缘情况很容易导致错误。 有些月份可能不包含已接受的乘车服务，因此解决方案仍必须输出计数为零的月份。 2020 年之前加入的司机在 2020 年的所有月份中仍然活跃，因此必须包括在内。 2020 年之后加入的司机不应参与统计。 不得包括 2020 年以外年份接受的游乐设施。 

## 方法

 ### 蛮力方法

 一个简单的解决方案将独立处理每个月。 

对于从 1 号到 12 号的每个月，我们可以扫描整个`Drivers`表格并计算有多少司机在该月最后一天或之前加入。 然后我们可以扫描所有接受的游乐设施，并通过`Rides`表，并计算该月接受的乘车次数。 

这是有效的，因为每个月都是单独评估的，并且所有相关记录都会直接检查。 

然而，这种方法每个月都会重复扫描相同的表。 如果表变得很大，重复执行全扫描就会变得低效。 

### 最佳方法

 关键的观察结果是，可以使用分组和累积计数有效地预先计算所需的统计数据。 

对于接受的游乐设施，我们只关心 2020 年的每月总数。我们可以加入`AcceptedRides`和`Rides`，过滤 2020 年，并按月分组。 

对于活跃驾驶员，计数是累积的。 我们可以先计算每个月加入的司机数量，然后计算跨月的运行总数，而不是每个月从头开始重新计算总数。 

另一个重要的观察结果是输出必须始终包含全部 12 个月。 因此，我们应该生成一个从 1 到 12 月份的固定表，并将聚合结果左连接到该表上。 

这种方法避免了重复扫描并生成干净、可扩展的 SQL。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(12 × (D + R)) | O(12 × (D + R)) | O(1) | O(1) | 每月重复扫描所有司机和行程 |
 | 最佳 | O(D + R + A) | O(12) | 使用分组和累积聚合 |

 这里：

-`D`是司机的数量
 -`R`是乘车次数
 -`A`是接受的乘车次数

 ## 算法演练

 1. 创建从 1 到 12 的所有月份的列表。这保证了最终结果包含每个月，即使该月不存在数据。 
2. 2020 年按月加入的司机总数。对于每个月，计算该月有多少司机加入。 
3. 单独统计2020年之前加入的所有司机。 这些驱动程序从 2020 年 1 月开始就已开始运行。 
4. 逐月计算累计活跃驾驶员。 每个月：

 - 从 2020 年之前加入的司机数量开始。 
- 添加在 2020 年当月和前几个月加入的所有司机。 
5. 加入`AcceptedRides`和`Rides`使用`ride_id`。 这样可以访问每个已接受行程的请求日期。 
6. 过滤加入的行程，仅包含 2020 年期间请求的行程。 
7. 按月对接受的乘车进行分组并进行计数。 
8. 将每月接受的乘车次数左加入月份列表中。 使用`COALESCE`因此，没有接受游乐设施的月份显示`0`。 
9. 返回按月份升序排列的最终结果。 

### 为什么它有效

 该解决方案之所以有效，是因为它将两个所需的指标分成独立的聚合。 

对于活跃司机来说，累积计数保证每个司机在加入月份后仍然保持活跃状态​​。 对于已接受的行程，筛选至 2020 年后进行分组可确保仅计算正确年份的已接受行程。 

使用固定月份表可保证从 1 月到 12 月的完整产出覆盖。 

## Python 解决方案

 LeetCode 数据库问题使用 SQL 而不是可执行的 Python，但以下 SQL 查询是完整的 LeetCode 可提交解决方案。```python
SELECT
    m.month,
    (
        SELECT COUNT(*)
        FROM Drivers d
        WHERE d.join_date <= LAST_DAY(CONCAT('2020-', m.month, '-01'))
    ) AS active_drivers,
    COALESCE(ar.accepted_rides, 0) AS accepted_rides
FROM
(
    SELECT 1 AS month
    UNION SELECT 2
    UNION SELECT 3
    UNION SELECT 4
    UNION SELECT 5
    UNION SELECT 6
    UNION SELECT 7
    UNION SELECT 8
    UNION SELECT 9
    UNION SELECT 10
    UNION SELECT 11
    UNION SELECT 12
) m
LEFT JOIN
(
    SELECT
        MONTH(r.requested_at) AS month,
        COUNT(*) AS accepted_rides
    FROM AcceptedRides ar
    JOIN Rides r
        ON ar.ride_id = r.ride_id
    WHERE YEAR(r.requested_at) = 2020
    GROUP BY MONTH(r.requested_at)
) ar
ON m.month = ar.month
ORDER BY m.month;
```该查询首先构建一个包含 1 到 12 个月的派生表。这保证了每个月都出现在最终结果中。 

这`active_drivers`值是使用相关子查询计算的。 对于每个月，该查询都会计算所有司机的数量`join_date`小于或等于该月的最后一天。 

接受的乘车次数是单独计算的。 查询连接`AcceptedRides`和`Rides`，筛选 2020 年的行，按月分组，并计算已接受的乘车次数。 

最后，一个`LEFT JOIN`将接受的行程计数与月份表合并。`COALESCE`将缺失值转换为零。

 ## 边缘情况

 当一个月没有接受乘车时，就会出现一个重要的边缘情况。 一个简单的内部连接可能会从结果中完全删除这些月份。 该解决方案通过显式生成所有 12 个月并使用`LEFT JOIN`结合`COALESCE`。 

另一个重要的边缘案例涉及 2020 年之前加入的司机。这些司机从 2020 年 1 月开始就已经活跃，必须包含在每个月的累计计数中。 相关子查询自然会处理这个问题，因为它会计算加入日期在当月月底之前的所有司机。 

第三个重要的边缘情况涉及 2020 年以外请求的乘车。2019 年或 2021 年接受的乘车不得影响 2020 年的统计数据。查询使用正确的过滤`WHERE YEAR(r.requested_at) = 2020`。 

当司机正好在一个月的最后一天加入时，就会出现第四种微妙的边缘情况。 该驱动程序应算作该月的活跃驱动程序。 该解决方案使用了一个`<=`与该月最后一天进行比较，确保包容性行为。
