[LeetCode 问题 1665](https://leetcode.com/problems/minimum-initial-energy-to-finish-tasks/)

 **难度：** 🔴难
 **主题：** 数组、贪婪、排序

 ## 解决方案

 ## 问题理解

 该问题为我们提供了一个任务列表，其中每个任务表示为`[actual, minimum]`。 

对于每项任务：

 -`minimum`是我们在开始任务之前必须拥有的能量。 
-`actual`是完成任务后消耗的能量。 

假设一个任务是`[4, 10]`。 我们至少需要`10`能量来开始它。 完成后，我们的能量会减少`4`。 

重要的细节是任务可以按任何顺序完成。 我们的目标是确定尽可能小的初始能量，以便存在一些任务顺序，使我们能够完成所有任务。 

这本质上是一个排序优化问题。 不同的任务顺序需要不同的起始能量水平。 我们想要最小化所需初始能量的顺序。 

限制条件很大：

 - 最多`10^5`任务
 - 每个值最多可达`10^4`因此，指数或阶乘解是不可能的。 我们周围需要一些东西`O(n log n)`。 

另一个重要的观察结果是每项任务都满足：```
actual <= minimum
```这保证了如果我们可以开始一项任务，完成它后我们永远不会立即变为负值。 

一些边缘情况很重要：

 - 任务所在`actual == minimum`- 这些都是严格的任务，因为它们没有留下安全余地。 
- 任务之间差距很大`minimum`和`actual`- 这些任务启动起来很困难，但执行起来相对便宜。 
- 单一任务输入

 - 答案就是任务的`minimum`。 
- 具有相同值的任务

 - 排序逻辑必须仍然正确运行。 

## 方法

 ### 蛮力方法

 暴力解决方案会尝试所有可能的任务顺序。 

对于每个排列：

 1. 模拟按顺序完成任务。 
2. 计算该排序所需的最小初始能量。 
3. 取所有排列中的最小值。 

为了计算一个订单所需的初始能量，我们按顺序处理任务并确保在每个任务之前我们的能量至少是其`minimum`。 

这种方法是正确的，因为它探索了每一种可能的排序，所以它不会错过最佳的排序。 

然而，它太慢了。 

如果有`n`任务，有：```
n!
```可能的排列。 

即使是为了`n = 15`，这变得不可行。 由于真正的约束是`10^5`，暴力破解是完全不可能的。 

### 最佳解决方案的关键见解

 核心挑战是确定最佳顺序。 

考虑两个任务：```
A = [a1, m1]
B = [a2, m2]
```假设我们执行`A`前`B`。 

开始`A`，我们至少需要`m1`。 

完成后`A`，我们的能量减少了`a1`，所以在开始之前`B`我们需要：```
initial_energy - a1 >= m2
```这意味着：```
initial_energy >= a1 + m2
```因此，如果`A`出现在之前`B`，所需能量为：```
max(m1, a1 + m2)
```同样，如果`B`出现在之前`A`，所需能量为：```
max(m2, a2 + m1)
```我们应该选择产生较小需求的订单。 

简化比较后，我们得到贪心规则：

 任务排序依据：```
(minimum - actual) descending
```为什么这有效？ 

数量：```
minimum - actual
```表示任务相对于其成本的要求程度。 

- 差异较大：

 - 很难开始
 - 完成成本低廉
 - 小差异：

 - 相对于能量消耗而言更容易启动

 差距较大的任务应该趁精力还旺盛的时候早点完成。 

一旦任务以这种方式排序，我们就可以贪婪地模拟执行并计算所需的最小初始能量。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n!·n) | O(n!·n) | O(n) | 尝试所有可能的排序 |
 | 最佳 | O(n log n) | O(n log n) | O(1) 或 O(log n) | 贪心排序依据`(minimum - actual)`|

 ## 算法演练

 ### 第 1 步：对任务进行排序

 按降序对所有任务进行排序：```
minimum - actual
```这会优先考虑需要大启动缓冲区的任务。 

例如：```
[1,7] -> 6
[5,11] -> 6
[2,4] -> 2
```具有较大值的任务优先。 

### 步骤 2：初始化跟踪变量

 我们维持：

 -`current_energy`- 模拟剩余能量
 -`required_energy`- 到目前为止所需的最小初始能量

 最初两者都是`0`。 

### 步骤 3：按排序顺序处理任务

 对于每一项任务`[actual, minimum]`：

 如果当前能量小于`minimum`，我们必须增加我们的初始能量。 

所需额外金额为：```
minimum - current_energy
```我们将此金额添加到两者中：

 -`required_energy`-`current_energy`现在我们可以安全地执行任务了。 

### 步骤 4：消耗任务能量

 完成任务后：```
current_energy -= actual
```继续，直到处理完所有任务。 

###第五步：返回结果

 最后：```
required_energy
```是使整个计划可行的最小初始能量。 

### 为什么它有效

 贪婪排序确保在先前任务耗尽能量之前，首先处理启动开销最大的任务。 

证明交换论证的正确性。 如果两个相邻任务不是按降序排列`(minimum - actual)`，交换它们不能增加所需的初始能量。 重复应用此交换规则可将任何最优排序转换为贪婪排序，从而证明贪婪排列是最优的。 

## Python 解决方案```python
from typing import List

class Solution:
    def minimumEffort(self, tasks: List[List[int]]) -> int:
        tasks.sort(key=lambda task: task[1] - task[0], reverse=True)

        required_energy = 0
        current_energy = 0

        for actual, minimum in tasks:
            if current_energy < minimum:
                extra = minimum - current_energy
                required_energy += extra
                current_energy += extra

            current_energy -= actual

        return required_energy
```实现首先根据贪婪规则对任务进行排序。 lambda 函数计算：```python
task[1] - task[0]
```对应于：```python
minimum - actual
```按降序排列。 

变量`required_energy`存储到目前为止我们必须添加的总初始能量。 变量`current_energy`模拟执行期间剩余的能量。 

对于每一项任务，我们首先检查我们是否有足够的精力来开始它。 如果不是，我们将两个变量都增加恰好缺失的量。 

之后，我们减去任务的实际能量成本。 

因为我们只添加必要的最少额外能量，所以最终结果是最佳的。 

## 解决方案```go
package main

import "sort"

func minimumEffort(tasks [][]int) int {
	sort.Slice(tasks, func(i, j int) bool {
		return (tasks[i][1] - tasks[i][0]) > (tasks[j][1] - tasks[j][0])
	})

	requiredEnergy := 0
	currentEnergy := 0

	for _, task := range tasks {
		actual := task[0]
		minimum := task[1]

		if currentEnergy < minimum {
			extra := minimum - currentEnergy
			requiredEnergy += extra
			currentEnergy += extra
		}

		currentEnergy -= actual
	}

	return requiredEnergy
}
```Go 实现遵循与 Python 版本相同的逻辑。 

主要区别在于排序语法。 Go 使用`sort.Slice`带有自定义比较器。 

Go 整数就足够了，因为最大可能的答案完全在 32 位整数范围内：```go
10^5 * 10^4 = 10^9
```直接使用切片，因为每个任务都表示为`[]int`。

 ## 边缘情况

 一个重要的边缘情况是只有一项任务时。 在这种情况下，答案就是任务所需的最低能量。 有缺陷的实现可能会错误地再次添加实际的能源成本或错误地处理初始化。 所提供的实现正确地检查当前能量是否低于最小值并仅添加所需的量。 

当多个任务具有相同的值时，会出现另一个重要情况：```
minimum - actual
```贪心证明保证这些任务之间的任何相对顺序都是有效的。 某些实现错误地依赖了不必要的辅助排序规则，并且可能使推理复杂化。 该解决方案仅根据所需的贪婪标准进行排序，这已经足够了。 

第三个关键边缘情况涉及以下任务：```
actual == minimum
```这些任务很严格，因为完成它们后，能量会大幅下降，而且没有额外的缓冲。 有缺陷的实现可能会由于不正确的比较运算符而导致任务在能量不足的情况下启动。 该实现使用：```
if current_energy < minimum:
```它正确地强制执行确切的最小阈值。 

另一个微妙的情况是当任务具有极大的启动要求但执行成本很小时，例如：```
[1, 10000]
```如果此任务推迟到稍后，先前消耗的能量可能会迫使初始需求更大。 按降序排序`(minimum - actual)`尽早正确地确定这些任务的优先顺序，防止日程安排后期不必要的能源膨胀。
