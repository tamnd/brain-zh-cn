 # LeetCode 1710 - 卡车上的最大单位

 ## 问题理解

 该问题为我们提供了几种类型的框，其中每种框类型包含两个值：

 - 该类型可用的盒子数量
 - 该类型每个盒子内的单位数量

 我们还有一辆卡车，最多可以运载`truckSize`总箱数，无论类型如何。 

我们的目标是最大限度地增加卡车上装载的单位总数。 

换句话说，每个箱子恰好占据卡车上的一个槽位，但不同的箱子类型贡献的单位数量不同。 由于卡车的容量有限，我们希望优先考虑每箱能提供最多单位的箱子。 

例如，如果一种箱子类型每个箱子包含 10 个单位，而另一种箱子类型每个箱子仅包含 1 个单位，则通常最好先装载 10 个单位的箱子，因为它们为相同的卡车空间提供更多价值。 

输入`boxTypes`是一个二维数组，其中：

 -`boxTypes[i][0]`是类型的盒子数量`i`-`boxTypes[i][1]`是类型的每箱单位`i`预期输出是一个整数，表示卡车上可容纳的最大总单位数。 

约束条件很重要：

 - 最多可以有1000种盒子类型
 - 每种类型最多可容纳 1000 个盒子
 -`truckSize`可以大到`10^6`这些限制表明指数或组合解决方案速度太慢。 我们需要一个有效的策略。 

有几种边缘情况值得考虑：

 - 在处理所有类型的箱子之前，卡车可能已满。 
- 卡车可能足够大，可以装下所有可用的箱子。 
- 多种盒子类型每个盒子可能具有相同的单位。 
- 箱子类型可能包含比剩余卡车容量更多的箱子。 
- 总是至少有一种箱子类型，并且卡车尺寸始终为正，因此我们不需要处理空输入数组。 

## 方法

 ### 蛮力方法

 暴力解决方案将尝试从不同类型中选择盒子的所有可能方法，并确定哪种组合给出最大的总单元数。 

从概念上讲，这类似于背包式搜索。 对于每种箱子类型，我们可以决定要取多少个箱子，从零到可用数量，同时跟踪剩余的卡车容量。 

这种方法保证能找到最佳答案，因为它探索了每一个有效的组合。 

然而，可能的组合数量增长得非常快。 即使输入相对较小，搜索空间也会变得巨大。 自从`truckSize`能达到一百万，穷举探索是完全不切实际的。 

因此，我们需要更有效的观察。 

### 最优贪心法

 关键的见解是每个箱子恰好占据一个单位的卡车空间。 

这意味着唯一重要的是我们每个盒子槽位获得多少单位。 

如果我们始终首先选择每箱数量最多的可用箱类型，我们将最大化每个卡车位置获得的价值。 

这是一个经典的贪婪策略。 

该算法的工作原理如下：

 1. 按每个盒子的数量降序对盒子类型进行排序。 
2. 从最有价值的类型中取出尽可能多的盒子。 
3. 转向下一个最有价值的类型。 
4. 继续直至卡车装满。 

这是有效的，因为在选择高价值的盒子之前选择低价值的盒子永远不会提高总单位数。

 ## 算法演练

 1. 排序`boxTypes`数组按降序排列基于`numberOfUnitsPerBox`。 

这确保了最有价值的盒子首先被处理。 由于每个箱子消耗相同的卡车容量，因此最大化每个箱子的单位始终是最佳的直接选择。 
2. 初始化变量`total_units`到`0`。 

该变量将累计装载到卡车上的单位总数。 
3. 按排序顺序迭代每个框类型。 

对于每种类型，确定剩余卡车容量实际上可以容纳多少个箱子。 
4. 计算要拿走的盒子数量。 

我们拿走的箱子数量是：```
min(available_boxes, remaining_truck_capacity)
```我们不能超过可用数量或剩余卡车空间。 
5. 添加这些框贡献的单位。 

乘：```
boxes_taken * units_per_box
```将此结果添加到`total_units`。 
6.减少剩余卡车容量。 

减去从中取出的盒子数量`truckSize`。 
7. 如果卡车满了，请尽早停车。 

一次`truckSize`达到零时，无法添加更多盒子。 
8. 返回`total_units`。 

### 为什么它有效

 贪婪策略是正确的，因为每个箱子正好消耗一个单位的卡车容量。 因此，每当我们选择单位较少的盒子而不是单位较多的盒子时，我们就会失去潜在价值，而不会获得任何优势。 

按每箱单位分类可确保每个卡车槽位得到尽可能高效的利用。 由于每个决策局部最大化每个盒子获得的单位，因此整体解决方案是全局最优的。 

## Python 解决方案```python
from typing import List

class Solution:
    def maximumUnits(self, boxTypes: List[List[int]], truckSize: int) -> int:
        # Sort by units per box in descending order
        boxTypes.sort(key=lambda box: box[1], reverse=True)

        total_units = 0

        for number_of_boxes, units_per_box in boxTypes:
            if truckSize == 0:
                break

            boxes_to_take = min(number_of_boxes, truckSize)

            total_units += boxes_to_take * units_per_box
            truckSize -= boxes_to_take

        return total_units
```该实现首先根据每个盒子的单位以降序对盒子类型进行排序。 这直接实现了总是优先考虑最有价值的盒子的贪婪思想。 

变量`total_units`存储装载到卡车上的累计单位数。 

该循环一次处理每个框类型。 对于每种类型，代码确定剩余卡车容量可以容纳多少个箱子，使用`min(number_of_boxes, truckSize)`。 

所选框的贡献被添加到`total_units`，卡车运力相应减少。 

提前停止条件会在卡车满载后终止，从而稍微提高效率。 

## 解决方案```go
package main

import "sort"

func maximumUnits(boxTypes [][]int, truckSize int) int {
	sort.Slice(boxTypes, func(i, j int) bool {
		return boxTypes[i][1] > boxTypes[j][1]
	})

	totalUnits := 0

	for _, boxType := range boxTypes {
		if truckSize == 0 {
			break
		}

		numberOfBoxes := boxType[0]
		unitsPerBox := boxType[1]

		boxesToTake := numberOfBoxes
		if truckSize < numberOfBoxes {
			boxesToTake = truckSize
		}

		totalUnits += boxesToTake * unitsPerBox
		truckSize -= boxesToTake
	}

	return totalUnits
}
```Go 实现遵循与 Python 版本相同的贪婪策略。 

主要区别在于使用`sort.Slice`按每个框的单位降序对 2D 切片进行排序。 

Go 没有内置的`min`函数用于整数，因此代码手动比较`truckSize`和`numberOfBoxes`以确定要拿多少个盒子。 

这里整数溢出不是问题，因为在给定的约束下，最大可能的答案完全符合 Go 的标准整数范围。

 ## 边缘情况

 ### 卡车容量小于单箱式

 当卡车无法取出当前类型的所有箱子时，就会出现常见的错误来源。 

例如：```
boxTypes = [[10,5]]
truckSize = 3
```幼稚的实现可能会意外添加所有 10 个框，而不是仅 3 个。该解决方案使用以下方法正确处理此问题：```
min(number_of_boxes, truckSize)
```这保证了我们永远不会超出容量。 

### 卡车大于可用箱子总数

 当卡车的容量大于可用箱子的总数时，就会发生另一种边缘情况。 

例如：```
boxTypes = [[2,3],[1,5]]
truckSize = 10
```正确的行为是获取每个可用的框，并在输入耗尽时自然停止。 该实现会自动处理这个问题，因为循环在处理完所有框类型后就完成了。 

### 多种盒子类型，每盒数量相等

 如果多种盒子类型的每个盒子提供相同的单位，则它们之间的排序顺序并不重要。 

例如：```
boxTypes = [[2,4],[3,4]]
```任何订单都会产生相同的总单位数，因为每个卡车槽位的贡献均等。 贪心算法仍然可以正确工作，因为所有等效选择都会产生相同的值。 

### 卡车提前满员

 在处理所有类型的箱子之前，卡车可能已满。 

例如：```
boxTypes = [[5,10],[5,1]]
truckSize = 2
```一旦卡车装满两个高价值箱子后，就没有必要继续循环了。 该实施包括提前终止检查：```
if truckSize == 0:
    break
```这可以避免不必要的计算，同时保持正确性。
