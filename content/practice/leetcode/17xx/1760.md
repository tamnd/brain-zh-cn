[LeetCode 1760 题](https://leetcode.com/problems/minimum-limit-of-balls-in-a-bag/)

 **难度：** 🟡 中等
 **主题：** 数组、二分查找

 ## 解决方案

 ## 问题理解

 给你几袋球，其中`nums[i]`代表里面有多少个球`i-th`包。 您最多可以表演`maxOperations`拆分操作。 在一次操作中，您将一个袋子分成两个较小的袋子，两个新袋子都至少装有一个球。 

目标是最小化惩罚，其中惩罚被定义为所有操作完成后最大包的大小。 

思考这个问题的另一种方式是：执行一些分割后，最小的可能值是多少`x`使得每个袋子最多包含`x`球？ 

例如，如果一个包包含`9`球，我们希望每个袋子最多包含`3`球，我们可以分裂：

 -`9 -> 6 + 3`-`6 -> 3 + 3`现在所有包都最多有尺寸`3`，并且我们准确地使用了`2`运营。 

约束条件非常重要：

 -`nums.length`可以达到`10^5`- 每个`nums[i]`可以大到`10^9`-`maxOperations`也可以大到`10^9`这些限制立即排除了任何尝试所有可能的分裂袋子方式的模拟。 搜索空间是巨大的。 

该问题保证每个袋子最初包含至少一个球，并且允许至少一次操作。 

一些边缘情况很重要：

 - 一个非常大的袋子，需要进行多次操作。 
- 情况`maxOperations`足够大，可以缩小每个包的尺寸`1`。 
- 由于运营过于有限而无法实现有意义的削减的情况。 
- 附近的大值`10^9`，低效的算法或容易溢出的算术可能会失败。 

关键的挑战是确定候选最大袋子尺寸是否可以在允许的操作次数内实现。 

## 方法

 ### 蛮力方法

 蛮力策略将尝试所有可能的方法来分割袋子并跟踪可实现的最小最大袋子尺寸。 

对于每一次操作，我们都可以选择任何一个包，并以各种可能的方式将其拆分。 不幸的是，这会产生指数数量的状态。 即使是单包大小`100`有多种可能的分割组合，并且随着多次操作，可能性的数量呈爆炸式增长。 

另一种暴力变体将尝试所有可能的惩罚值`1`最多`max(nums)`并模拟是否可以实现。 虽然这比探索所有拆分配置更好，但它仍然太慢，因为`max(nums)`或许`10^9`。 

蛮力方法是正确的，因为它明确地探索了可能的结果，但对于给定的约束，它在计算上是不可行的。 

### 最优方法，对答案进行二分搜索

 关键的见解是该问题具有单调性。 

假设我们问：

 “我们能否让每个包最多有`x`最多使用的球`maxOperations`行动？”

 如果对于某些值来说答案是肯定的`x`，那么对于任何更大的值也将是 yes。 

例如：

 - 如果我们能够实现最大袋子尺寸`3`,
 - 那么我们一定可以实现`4`,`5`,`6`， 等等。 

这种单调行为使得该问题非常适合二分搜索。 

我们对答案空间进行二分搜索：

 - 可能的最低处罚=`1`- 最大可能处罚 =`max(nums)`对于候选人处罚`mid`，我们计算需要多少次操作。 

如果包有尺寸`num`，我们希望每个最终的袋子最多有尺寸`mid`，则所需的分割数为：$\left\lfloor\frac{num-1}{mid}\right\rfloor$这是有效的，因为：

 - 袋子已经小于或等于`mid`需要`0`运营。 
- 否则，我们会反复分裂，直到所有部分最多为止`mid`。 

如果所需操作总数在`maxOperations`， 然后`mid`是可行的，我们尝试较小的值。 

否则，我们需要更大的惩罚。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 指数| 指数| 尝试多种分体配置 |
 | 最佳 | O(n log M) | O(n log M) | O(1) | O(1) | 答案空间上的二分搜索 |

 这里：

-`n = len(nums)`-`M = max(nums)`## 算法演练

 1. 初始化二分查找边界。 

最小可能的惩罚是`1`，因为每个袋子必须至少包含一个球。 

最大可能的处罚是`max(nums)`，因为我们总是可以选择不分割任何东西。 
2. 重复计算中间值。 

让`mid = (left + right) // 2`。 

这代表我们正在测试的候选最大袋子尺寸。 
3. 计算需要多少次操作。 

适用于各种包袋尺寸`num`， 计算：$\left\lfloor\frac{num-1}{mid}\right\rfloor$这给出了所需的最小分割数，因此每个最终的袋子最多具有尺寸`mid`。 

将所有行李中的这些值相加。 
4. 检查可行性。 

如果所需的总操作量小于或等于`maxOperations`， 然后`mid`是可以实现的。 

由于我们想要尽可能最小的惩罚，因此继续搜索左半部分。 
5. 否则，搜索右半部分。 

如果需要的操作数超过允许的操作数，那么`mid`太小了，无法工作。 

增加下限。 
6. 继续，直到搜索空间崩溃。 

什么时候`left == right`，我们找到了最小的可行惩罚。 

### 为什么它有效

 该算法之所以有效，是因为可行性是单调的。 

如果惩罚值`x`是可以实现的，那么每个更大的值也是可以实现的。 这将创建一个排序的真/假搜索空间：

 - 小额处罚可能是不可能的。 
- 更大的处罚成为可能。 

二分查找可以有效地找到不可能值和可能值之间的过渡点。 

该操作公式也是最优的，因为每次分割都会使袋子的数量恰好增加 1，因此该公式计算将袋子减少为足够小的碎片所需的最小分割数。 

## Python 解决方案```python
from typing import List

class Solution:
    def minimumSize(self, nums: List[int], maxOperations: int) -> int:
        left = 1
        right = max(nums)

        while left < right:
            mid = (left + right) // 2

            operations_needed = 0

            for num in nums:
                operations_needed += (num - 1) // mid

            if operations_needed <= maxOperations:
                right = mid
            else:
                left = mid + 1

        return left
```实现首先定义二分搜索范围`1`到`max(nums)`。 

在循环内部，`mid`代表候选者允许的最大行李尺寸。 

然后，代码会迭代每个包并计算减少该包所需的操作次数，以便所有结果块最多`mid`。 

公式：$\left\lfloor\frac{num-1}{mid}\right\rfloor$有效地计算所需的分割，而无需显式模拟它们。 

如果所需操作总数在`maxOperations`，候选惩罚是可行的，因此算法通过移动来搜索更小的答案`right`。 

不然的话，惩罚就太小了，所以`left`增加了。 

最终，两个指针都收敛到最小可行惩罚。 

## 解决方案```go
package main

func minimumSize(nums []int, maxOperations int) int {
	left := 1
	right := 0

	for _, num := range nums {
		if num > right {
			right = num
		}
	}

	for left < right {
		mid := (left + right) / 2

		operationsNeeded := 0

		for _, num := range nums {
			operationsNeeded += (num - 1) / mid
		}

		if operationsNeeded <= maxOperations {
			right = mid
		} else {
			left = mid + 1
		}
	}

	return left
}
```Go 实现遵循与 Python 版本完全相同的算法结构。 

一个小小的区别是 Go 没有提供内置的`max()`函数用于切片，因此我们在初始化时手动计算最大值`right`。 

Go 中的整数除法自然会对整数进行整除，这符合所需的公式。 

在 LeetCode 约束下，所有值都安全地符合 Go 的标准整数范围。

 ## 边缘情况

 一种重要的边缘情况是所有行李都已经满足最优惩罚。 例如，`nums = [1,1,1]`。 有错误的实现可能会尝试不必要的操作或错误地减少下面的答案`1`。 该实现可以自然地处理这种情况，因为二分搜索下界是`1`，并且操作计数保持为零。 

另一个重要的情况是单个超大包，例如`nums = [1000000000]`。 简单的模拟方法会太慢或占用大量内存。 二分搜索解决方案仍然高效，因为它从不显式执行拆分。 它仅在数学上计算需要多少次分割。 

当操作不足以显着减少最大的袋子时，就会出现第三种关键的边缘情况。 例如，`nums = [100]`和`maxOperations = 1`。 一些实现错误地假设重复减半总是可能的。 这里，只能执行一次分割，因此可实现的最佳结果是`50`。 基于公式的可行性检查正确地捕捉到了这一限制。 

另一个微妙的情况是精确的可行性边界，其中所需的操作等于`maxOperations`。 例如，`nums = [8]`和`maxOperations = 3`。 我们可以分成四个大小的袋子`2`，正好使用三个操作。 实现正确使用`<= maxOperations`，确保精确配合被认为是可行的。
