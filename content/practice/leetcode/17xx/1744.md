[LeetCode 1744 题](https://leetcode.com/problems/can-you-eat-your-favorite-candy-on-your-favorite-day/)

 **难度：** 🟡 中等
 **主题：** 数组、前缀和

 ## 解决方案

 ## 问题理解

 问题给了我们一个数组`candiesCount`在哪里`candiesCount[i]`代表糖果类型存在多少种糖果`i`。 糖果类型必须按顺序吃，这意味着你不能吃任何类型的糖果`i`直到所有先前类型的糖果`0`通过`i - 1`已经被吃掉了。 

您还会收到多个查询。 每个查询包含：

 -`favoriteType`-`favoriteDay`-`dailyCap`对于每个查询，我们必须确定是否可以吃至少一种类型的糖果`favoriteType`当天`favoriteDay`，同时遵守所有规则：

 1. 您在当天开始进食`0`。 
2.每天必须至少吃一颗糖果。 
3. 饮食不能超过`dailyCap`任何一天都有糖果。 
4. 糖果种类必须按顺序食用。 

输出是一个布尔数组，其中每个位置对应一个查询。 

限制条件很大：

 - 最多`10^5`糖果种类
 - 最多`10^5`查询
 - 日值和上限可以大到`10^9`这些限制立即告诉我们，日复一日地进行模拟是不可能的。 我们需要一个基于数学或前缀和的解决方案。 

一个重要的观察结果是，对于某一天：

 - 到那时你必须吃掉最少数量的糖果
 - 到那时你可以吃的糖果数量有上限

 我们可以将每个查询视为范围重叠问题。 

一些边缘情况很重要：

 - 查询可能会询问日期`0`-`dailyCap`可能非常大
 - 最喜欢的糖果类型可能是第一种或最后一种
 - 前缀和可能变得非常大，因此需要 64 位整数
 - 糖果类型可能会变得无法访问，因为较早的糖果类型消耗了太多天数

 ## 方法

 ### 蛮力方法

 暴力解决方案将尝试模拟每个查询的糖果消耗。 

对于每个查询：

 1.模拟一天一天吃糖果
 2. 遵守每日最高上限
 3. 追踪当前可用的糖果类型
 4. 检查目标糖果类型是否可以在目标日期食用

 这种方法在概念上是正确的，因为它直接遵循问题的规则。 然而，它很快就变得不可行。 

的价值`favoriteDay`可以达到`10^9`，这使得日常模拟变得不可能。 即使贪婪地模拟对于`10^5`查询。 

### 最佳解决方案的关键见解

 我们可以推断范围，而不是模拟消费。 

假设我们正在回答一个查询：

 -`favoriteType = t`-`favoriteDay = d`-`dailyCap = c`白天`d`：

 - 最少吃掉的糖果数量是`d + 1`，因为你每天必须至少吃一颗糖果。 
- 最多吃掉多少糖果`(d + 1) * c`。 

现在考虑糖果类型`t`。 

让：

-`prefix[t]`= 不同类型的糖果总数`0`通过`t`-`prefix[t - 1]`= 输入前糖果总数`t`然后：

 - 第一种类型的糖果`t`是糖果号`prefix[t - 1] + 1`- 最后一种糖果类型`t`是糖果号`prefix[t]`吃一颗类型的糖果`t`当天`d`，每天吃的糖果范围`d`必须与类型占用的范围重叠`t`。 

这就变成了区间重叠问题。 

如果满足以下条件，则可以进行查询：```
maximum candies eaten by day d >= first candy of type t
AND
minimum candies eaten by day d <= last candy of type t
```或者等价地：```
(d + 1) * c > prefix[t - 1]
AND
(d + 1) <= prefix[t]
```这将问题转化为高效的前缀和查找。 

## 方法比较

 | 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(Q × D) | O(1) | O(1) | 模拟日常糖果消耗 |
 | 最佳 | O(N + Q) | O(N) | 使用前缀和和间隔重叠逻辑 |

 在哪里：

-`N = len(candiesCount)`-`Q = len(queries)`-`D`可以大到`10^9`## 算法演练

 1. 构建前缀和数组。 

前缀和数组存储每种类型糖果的累计数量。```
prefix[i] = candiesCount[0] + candiesCount[1] + ... + candiesCount[i]
```这使我们能够快速确定：

 - 一种类型之前存在多少糖果
 - 最多一种类型的糖果总数
 2. 独立处理每个查询。 

对于查询`[favoriteType, favoriteDay, dailyCap]`：

- 让：```
t = favoriteType
d = favoriteDay
c = dailyCap
```3. 计算每天最少吃掉的糖果`d`。 

由于每天至少必须吃一颗糖果：```
minEaten = d + 1
```4. 计算一天最多吃掉多少糖果`d`。 

因为至多`c`每天可以吃的糖果有：```
maxEaten = (d + 1) * c
```5. 计算类型的糖果范围`t`。 

糖果属于类型`t`占据：```
firstCandy = prefix[t - 1] + 1
lastCandy = prefix[t]
```如果`t == 0`， 然后：```
firstCandy = 1
```6. 检查范围是否重叠。 

我们可以吃类型`t`当天`d`如果：```
maxEaten >= firstCandy
AND
minEaten <= lastCandy
```7. 存储布尔结果。 

对所有查询重复此过程。 

### 为什么它有效

 该算法之所以有效，是因为每个有效的饮食计划都会产生每天吃掉的糖果总数`d`位于：```
[d + 1, (d + 1) * dailyCap]
```糖果型`t`在全局糖果排序中占据固定区间：```
[firstCandy, lastCandy]
```如果这些间隔重叠，则存在一天吃掉的糖果的有效数量`d`落在类型范围内`t`。 因此，饮食型`t`当天`d`是可能的。 

如果间隔不重叠，则没有有效的饮食计划可以达到类型`t`在那一天。 

## Python 解决方案```python
from typing import List

class Solution:
    def canEat(self, candiesCount: List[int], queries: List[List[int]]) -> List[bool]:
        n = len(candiesCount)

        # Build prefix sums
        prefix = [0] * n
        prefix[0] = candiesCount[0]

        for i in range(1, n):
            prefix[i] = prefix[i - 1] + candiesCount[i]

        answer = []

        for favoriteType, favoriteDay, dailyCap in queries:
            min_eaten = favoriteDay + 1
            max_eaten = (favoriteDay + 1) * dailyCap

            candies_before = prefix[favoriteType - 1] if favoriteType > 0 else 0
            candies_up_to = prefix[favoriteType]

            can_eat = (
                max_eaten > candies_before and
                min_eaten <= candies_up_to
            )

            answer.append(can_eat)

        return answer
```实现首先构建一个前缀和数组。 该数组允许恒定时间查找特定类型之前存在多少糖果以及该类型之前存在多少糖果。 

对于每个查询，代码计算：

 - 目标日内尽可能少吃的糖果
 - 目标日内最多可能吃掉的糖果

 然后，它确定最喜欢的糖果类型占据的间隔。 

条件：```python
max_eaten > candies_before
```确保我们能够在那天之前达到目标类型。 

条件：```python
min_eaten <= candies_up_to
```确保我们在那一天之前尚未用尽目标类型。 

如果两个条件都成立，则区间重叠，答案为`True`。 

## 解决方案```go
func canEat(candiesCount []int, queries [][]int) []bool {
	n := len(candiesCount)

	// Build prefix sums using int64 to avoid overflow
	prefix := make([]int64, n)
	prefix[0] = int64(candiesCount[0])

	for i := 1; i < n; i++ {
		prefix[i] = prefix[i-1] + int64(candiesCount[i])
	}

	answer := make([]bool, len(queries))

	for i, query := range queries {
		favoriteType := query[0]
		favoriteDay := int64(query[1])
		dailyCap := int64(query[2])

		minEaten := favoriteDay + 1
		maxEaten := (favoriteDay + 1) * dailyCap

		var candiesBefore int64 = 0
		if favoriteType > 0 {
			candiesBefore = prefix[favoriteType-1]
		}

		candiesUpTo := prefix[favoriteType]

		canEatCandy := (
			maxEaten > candiesBefore &&
				minEaten <= candiesUpTo
		)

		answer[i] = canEatCandy
	}

	return answer
}
```Go 实现遵循与 Python 解决方案相同的逻辑。 主要区别在于 Go 需要显式处理整数溢出。 

由于值可能超过 32 位整数限制：```go
(10^9 + 1) * 10^9
```所有涉及天数或上限的前缀和和算术使用`int64`。 

切片自然地用于前缀和和结果。 不需要对 nil 切片进行特殊处理，因为约束保证了有效的输入大小。

 ## 边缘情况

 ### 零日查询

 查询`favoriteDay = 0`很容易处理不当，因为只发生了一天的进食。 实现正确计算：```
minEaten = 1
maxEaten = dailyCap
```这确保了逻辑在第一天仍然有效。 

### 超大每日上限

 的价值`dailyCap`可以达到`10^9`，并将其乘以`(favoriteDay + 1)`可以超过 32 位整数限制。 在某些语言中使用常规整数的简单实现会溢出。 

Go 解决方案使用`int64`，Python 天然支持任意精度整数。 

### 喜欢的类型已经用完了

 当一天吃的最少糖果时，就会出现一个微妙的情况`d`已经超过了目标类型的最后一个糖果指数。 

例如：```
candiesCount = [2]
query = [0,5,1]
```白天`5`，至少`6`糖果一定是被吃掉了，但只是`2`糖果类型`0`存在。 

条件：```
minEaten <= candiesUpTo
```正确检测到这一点并返回`False`。 

### 大量查询

 既然两者`candiesCount`和`queries`可以包含`10^5`元素，任何每个查询的线性扫描都会超时。 

前缀和方法保证了预处理后的恒定时间查询评估，使解决方案对于约束具有足够的可扩展性。
