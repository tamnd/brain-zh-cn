[LeetCode 第 458 题](https://leetcode.com/problems/poor-pigs/)

 **难度：** 🔴难
 **主题：** 数学、动态规划、组合学

 ## 解决方案

 ## 问题理解

 该问题给了我们一组`buckets`其中正好有一桶装有毒药。 我们需要在严格的时限内使用尽可能少的猪来确定哪个桶有毒。 

每头猪可以参加多轮测试。 猪确实死了`minutesToDie`喝毒药后几分钟。 总的测试窗口是`minutesToTest`，这意味着我们可以进行多轮实验。 

关键细节是猪可以在同一轮中从多个桶中喝水，并且可以将桶提供给多只猪。 这从根本上提出了如何有效编码信息的问题。 

输入参数代表如下：

 -`buckets`是可能有毒桶的数量。 
-`minutesToDie`是指中毒的猪需要多长时间才能死亡。 
-`minutesToTest`是可用的测试时间总量。 

输出是在规定的时间内唯一识别毒桶所需的最小猪数量。 

限制相对较小，最多 1000 个桶，但挑战是概念性的，而不是计算性的。 对所有可能的喂养计划进行强力模拟很快就会变得极其复杂。 预期的解决方案依赖于组合学和信息论。 

一些边缘情况很重要：

 - 如果只有一个桶，则不需要猪，因为毒桶是已知的。 
- 如果`minutesToTest == minutesToDie`，我们只进行一轮测试。 
- 如果我们有多个回合，每头猪可以编码的不仅仅是生或死的信息。 
- 天真的二分搜索式解释是不正确的，因为猪可以参与多轮，因此代表多个状态，而不仅仅是两个。 

## 方法

 ### 蛮力方法

 暴力方法将尝试显式模拟所有可能的测试计划。 我们可以尝试每轮中哪些猪从哪些桶中喝水的每种组合，然后验证由此产生的死亡模式是否唯一地标识每个桶。 

这是有效的，因为每个测试策略都会创建存储桶和可观察的猪结果之间的映射。 如果每个桶都映射到唯一的结果，则该策略是有效的。 

然而，这很快就变得不可行。 可能的饲养配置的数量随着猪的数量和轮数呈指数增长。 即使只有少数的猪，国家空间也变得巨大。 

因此，暴力方法是不切实际且不必要的。 

### 最佳洞察力

 关键的观察是，每头猪可以代表多种不同的状态，而不仅仅是活着或死了。 

假设我们可以执行：$$\text{rounds} = \frac{\text{minutesToTest}}{\text{minutesToDie}}$$测试轮次。 

一头猪可以准确地结束`rounds + 1`可能的状态：

 - 在第 1 轮死亡
 - 在第 2 轮死亡
 - ...
 - 圆形死亡`rounds`- 在所有回合中幸存

 这意味着一头猪可以编码`rounds + 1`不同的结果。 

如果我们使用`p`猪，可区分结果的总数变为：$$(\text{rounds} + 1)^p$$我们需要足够的独特结果组合来识别每个桶：$$(\text{rounds} + 1)^p \ge \text{buckets}$$因此，任务简化为寻找最小整数`p`满足这个不等式。 

这将问题从模拟转化为紧凑的数学计算。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | 指数| 指数| 模拟所有喂养时间表和结果 |
 | 最佳| O(日志桶) | O(1) | O(1) | 使用组合状态计数 |

 ## 算法演练

 1. 计算可用的测试轮数。 

完整测试轮数为：$$\text{rounds} = \frac{\text{minutesToTest}}{\text{minutesToDie}}$$例如，如果猪在 15 分钟内死亡，而我们总共有 60 分钟的时间，那么我们可以运行 4 轮。 
2. 确定一头猪可以代表多少个状态。 

猪可以：

 - 在第一轮死亡
 - 在第 2 轮死亡
 - ...
 - 在最后一轮死亡
 - 完全生存

 因此，一头猪有：$$\text{statesPerPig} = \text{rounds} + 1$$可能的结果。 
3. 计算可以表示多少个桶`p`猪。 

如果每头猪都有`statesPerPig`可能的状态，那么`p`猪在一起可以编码：$$(\text{statesPerPig})^p$$独特的组合。 
4. 求最少的猪数量。 

开始于`pigs = 0`并反复增加直到：$$(\text{statesPerPig})^{pigs} \ge \text{buckets}$$第一个有效值是答案。 

### 为什么它有效

 每个桶都可以分配一个独特的猪结果组合。 从概念上讲，我们在位置数字系统中对桶号进行编码，其中基数是`statesPerPig`。 

每头猪的行为就像该编号系统中的一位数字。 自从`p`猪可以准确地生产`(statesPerPig)^p`独特的结果模式，至少具有与存储桶一样多的模式，保证每个存储桶都可以被唯一识别。 

## Python 解决方案```python
class Solution:
    def poorPigs(self, buckets: int, minutesToDie: int, minutesToTest: int) -> int:
        rounds = minutesToTest // minutesToDie
        states_per_pig = rounds + 1
        
        pigs = 0
        
        while states_per_pig ** pigs < buckets:
            pigs += 1
        
        return pigs
```该实现首先计算可用的测试轮数。 由此得出每头猪可以代表的状态数。 

变量`pigs`从零开始，因为当只有一个桶时，可能不需要猪。 

循环反复检查当前的猪数量是否可以区分足够的桶。 表达式：```python
states_per_pig ** pigs
```表示独特结果组合的总数。 

一旦这个值至少达到桶的数量，我们就知道当前的猪数量足够了，所以我们返回它。 

实现非常紧凑，因为问题的困难部分是数学洞察力，而不是编码本身。 

## 解决方案```go
func poorPigs(buckets int, minutesToDie int, minutesToTest int) int {
    rounds := minutesToTest / minutesToDie
    statesPerPig := rounds + 1

    pigs := 0

    for power(statesPerPig, pigs) < buckets {
        pigs++
    }

    return pigs
}

func power(base int, exp int) int {
    result := 1

    for exp > 0 {
        result *= base
        exp--
    }

    return result
}
```Go 实现遵循与 Python 版本相同的逻辑。 由于 Go 没有像 Python 那样的内置整数求幂运算符`**`，我们实现一个名为的小辅助函数`power`。 

整数溢出在这里不是一个问题，因为约束很小。 即使在最大的情况下，计算的幂仍然在 Go 的整数范围内。

 ## 边缘情况

 当只有一个存储桶时，会出现一种重要的边缘情况。 在这种情况下，不需要进行任何实验，因为毒桶是已知的。 有缺陷的实现可能会错误地返回一只猪，因为它假设始终需要测试。 当前的实现自然地处理了这个问题，因为当循环条件立即失败时`buckets == 1`。 

当只有一轮测试可用时会发生另一个重要情况，这意味着`minutesToTest == minutesToDie`。 在这种情况下，每头猪只有两种状态，生或死。 问题实际上变成了二进制编码。 错误地假设多轮总是可用的实现可能会高估每只猪的信息容量。 

当桶的数量恰好是`(rounds + 1)`。 例如，如果每头猪有 5 个状态，并且正好有 625 个桶，那么 4 头猪就足够了，因为：$$5^4 = 625$$使用循环条件，例如`<=`而不是`<`会错误地添加不必要的猪。 该实现通过使用正确的严格比较条件来避免此错误。
