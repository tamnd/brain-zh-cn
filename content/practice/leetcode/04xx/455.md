 # LeetCode 455，分配 Cookie

 ## 问题理解

 这个问题要求我们最大化能够满足可用 cookie 的儿童数量。 每个孩子都有一个贪婪因素，每个饼干都有一个大小。 只有当孩子收到一块大小大于或等于其贪婪因子的饼干时，他们才会感到满足。 

输入由两个整数数组组成：

 -`g`， 在哪里`g[i]`表示子进程所需的最小 cookie 大小`i`-`s`， 在哪里`s[j]`代表cookie的大小`j`每个孩子最多可以接收一个 cookie，并且每个 cookie 只能分配一次。 目标是确定可以满足的最大儿童数量。 

问题的重要部分是我们并没有试图最大化 cookie 的总使用量或最小化浪费。 我们只关心最大化满意儿童的数量。 

约束条件很重要：

 - 两个数组最多可以包含`3 * 10^4`元素
 - Cookie 大小和贪婪因子可以是非常大的整数
 - 输入大小足够大，低效的嵌套匹配方法可能会变得太慢

 因为每个数组可以包含数万个元素，所以我们应该期望`O(n log n)`解决方案是适当的，而天真`O(n * m)`在最坏的情况下，解决方案可能会变得低效。 

有几个重要的边缘情况：

 - 可能根本没有cookie
 - 饼干可能比孩子还少
 - 饼干的数量可能比孩子的数量还多
 - 有些饼干对于每个孩子来说可能太小
 - 多个子项或 cookie 可能具有相同的值
 - 不保证数组已排序

 正确的实现必须一致地处理所有这些情况。 

## 方法

 ### 蛮力方法

 一种简单的方法是尝试使用嵌套循环将 cookie 一个一个地分配给子级。 

对于每个孩子，我们可以扫描所有可用的 cookie，并选择满足孩子贪婪因素的最小的未使用 cookie。 分配 cookie 后，我们将其标记为已使用，因此无法重复使用。 

这种方法会产生正确的答案，因为它显式检查所有可能的分配并确保每个 cookie 最多使用一次。 

然而，性能较差。 如果有`n`儿童和`m`cookies，那么对于每个孩子，我们可以扫描整个cookie数组。 这导致`O(n * m)`时间复杂度。 

两个数组都可能具有大小`3 * 10^4`，最坏的情况可能涉及`9 * 10^8`操作，速度太慢。 

### 最优贪心法

 关键的观察是我们应该使用能够满足孩子需求的尽可能小的饼干。 

如果我们把一块大饼干浪费在一个贪心很小的孩子身上，我们以后可能无法满足一个真正需要更大饼干的贪婪孩子。 

这自然暗示了一种贪婪策略：

 1. 对两个数组进行排序
 2.总是尝试使用剩余的最小的足够的cookie来满足剩余的最不贪婪的孩子

 通过对两个数组进行排序，我们可以使用两个指针有效地移动它们。 

如果当前 cookie 对于当前子项来说足够大，我们会分配它并将两个指针向前移动。 

如果 cookie 太小，则该 cookie 无法满足当前的孩子或任何未来的孩子，因为未来的孩子将具有相同或更大的贪婪。 因此，我们安全地丢弃该 cookie 并转到下一个。 

这种贪婪的决定是最优的，因为它为贪婪的孩子保留了更大的饼干。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(n * m) | O(米) | 为每个孩子尝试每一款饼干 |
 | 最佳| O(n log n + m log m) | O(n log n + m log m) | O(1) 或 O(log n) 取决于排序 | 对两个数组进行排序并使用两个指针 |

 ## 算法演练

 1. 排序`g`数组按升序排列。 

这使我们能够将孩子从最不贪婪到最贪婪进行处理。 较小的贪婪要求更容易满足，因此我们首先处理它们。 
2. 排序`s`数组按升序排列。 

这使我们能够按照从最小到最大的顺序处理 cookie。 当较小的饼干可以使用时，我们希望避免浪费大饼干。 
3. 初始化两个指针。 

一个指针跟踪当前子项，另一个指针跟踪当前 cookie。```
child_index = 0
cookie_index = 0
```4. 当两个指针都保持在边界内时进行迭代。 

在每一步中，将当前 cookie 大小与当前子进程的贪婪因子进行比较。 
5、如果cookie能让孩子满意：```
s[cookie_index] >= g[child_index]
```然后将cookie分配给孩子。 

增加两个指针，因为：

 - 那个孩子现在很满意
 - 该 cookie 已被使用
 6.如果cookie太小：```
s[cookie_index] < g[child_index]
```然后丢弃cookie。 

仅增加 cookie 指针，因为：

 - 饼干不能满足这个孩子
 - 它也不能满足任何未来的孩子，因为未来的贪婪值更大
 7. 继续直到：

 - 所有孩子都满意，或者
 - 所有 cookie 均已耗尽
 8. 满足的子项数量等于子项指针值。 

### 为什么它有效

 该算法保持了不变式，即我们总是分配能够满足当前最不贪心的孩子的尽可能小的 cookie。 

这种贪婪的选择是最佳的，因为不必要地使用更大的饼干可能会降低我们以后满足贪婪的孩子的能力。 通过始终匹配最小的足够 cookie，我们最大限度地提高了未来的灵活性。 

排序可以确保一旦 cookie 对于某个孩子来说太小，那么对于后面的每个孩子来说它也会太小，从而使我们能够安全地丢弃它。 

## Python 解决方案```python
from typing import List

class Solution:
    def findContentChildren(self, g: List[int], s: List[int]) -> int:
        g.sort()
        s.sort()

        child_index = 0
        cookie_index = 0

        while child_index < len(g) and cookie_index < len(s):
            if s[cookie_index] >= g[child_index]:
                child_index += 1

            cookie_index += 1

        return child_index
```实现首先对两个数组进行排序。 这是贪婪策略的基础，因为它允许我们以递增的顺序处理子项和 cookie。 

变量`child_index`追踪到目前为止有多少孩子感到满意。 变量`cookie_index`跟踪我们当前正在考虑的 cookie。 

在循环内，我们将当前 cookie 与当前子进程的贪婪因子进行比较。 

如果 cookie 足够大，我们就满足该孩子并转移到下一个孩子。 无论 cookie 成功还是失败，我们总是会移动到下一个 cookie，因为每个 cookie 只能使用一次。 

在最后，`child_index`代表满意儿童的总数。 

实现很简洁，因为贪婪逻辑消除了对额外数据结构或簿记的需要。 

## 解决方案```go
package main

import "sort"

func findContentChildren(g []int, s []int) int {
	sort.Ints(g)
	sort.Ints(s)

	childIndex := 0
	cookieIndex := 0

	for childIndex < len(g) && cookieIndex < len(s) {
		if s[cookieIndex] >= g[childIndex] {
			childIndex++
		}

		cookieIndex++
	}

	return childIndex
}
```Go 实现遵循与 Python 解决方案相同的逻辑。 

主要区别在于 Go 使用`sort.Ints()`从标准库中对切片进行就地排序。 

Go 切片自然会处理空输入，因此不需要对空 cookie 数组进行特殊处理。 

也不存在整数溢出问题，因为我们只比较值和增量索引。

 ## 边缘情况

 当没有可用的 cookie 时，就会出现一种重要的边缘情况。 在这种情况下，无论贪婪因素如何，任何孩子都不可能得到满足。 有缺陷的实现可能会尝试访问空 cookie 数组中的元素并崩溃。 两个指针循环自然地处理这个问题，因为循环条件立即失败`len(s) == 0`。 

另一个重要的边缘情况涉及饼干太小。 例如：```
g = [5, 6, 7]
s = [1, 2, 3]
```幼稚的实现可能会低效地反复重试不可能的匹配。 排序贪婪方法可以正确处理这个问题，因为一旦 cookie 对于当前子进程来说太小，它就会被立即丢弃。 

第三个重要的边缘情况涉及重复值。 多个孩子可能具有相同的贪婪因子，并且多个饼干可能具有相同的大小。 一些不正确的实现会意外地重用 cookie 或错误处理重复值。 此实现避免了这些问题，因为每个 cookie 指针只前进一次，保证每个 cookie 最多使用一次。 

当输入数组未排序时，会发生另一种微妙的情况。 贪心策略只有在排序后才能正确工作。 如果不进行排序，以任意顺序分配 cookie 可能会将较大的 cookie 浪费在不太贪心的孩子身上，并减少满意的孩子的总数。 排序确保我们始终做出局部最优决策，从而获得全局最优结果。
