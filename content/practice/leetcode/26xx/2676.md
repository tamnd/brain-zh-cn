 **难度：** 🟡 中等
 **主题：** —

 ## 解决方案

 ## 问题理解

 这个问题要求我们为一个函数实现一个限流机制。 我们被赋予一个函数`fn`和延迟间隔`t`以毫秒为单位。 我们必须返回一个新函数，称为节流函数，它控制频率`fn`被允许执行。 

节流函数的行为遵循两个重要规则：

 1. 第一个调用立即执行。 
2.接下来的时间里`t`毫秒，其他调用将被阻止立即执行。 但是，受限制的函数必须记住在此阻塞期间提供的最新参数。 

一旦延迟到期，如果保存了任何参数，该函数将仅使用最近保存的参数再次执行。 该执行启动了一个新的长度限制窗口`t`，并且重复该过程。 

关键细节是只有最新阻止的呼叫才重要。 如果在延迟结束之前有新的呼叫到达，则先前阻塞的呼叫将被丢弃。 

输入示例代表函数调用的时间线。 每个调用都有：

 - 时间戳`t`- 输入参数数组

 预期输出是实际执行计划`fn`，包括：

 - 当函数真正运行时
 - 使用哪些参数

 限制非常小：

 -`calls.length <= 10`-`t <= 1000`这意味着性能不是主要问题，但异步计时行为的正确性至关重要。 挑战在于理解油门机制并精确实施它们。 

一些边缘情况很重要：

 - 在同一节流窗口期间进行多次调用，其中只有最新的参数应该保留。 
- 呼叫恰好在节流窗口结束时到达。 
- 油门持续时间`0`，其中每个调用都应立即执行。 
- 递归调度行为，执行延迟调用会创建一个全新的冷却时间。 

简单的实现常常会失败，因为它：

 - 稍后执行每个被阻止的调用，而不是仅执行最新的调用
 - 延迟执行后忘记重新开始冷却
 - 错误处理计时器重置和保存的参数

 ## 方法

 ### 蛮力方法

 暴力方法将手动模拟整个时间线。 我们可以一一处理每个传入呼叫，同时维护一个延迟执行队列。 每次新调用到达时，我们都会检查所有待处理的计划事件，确定它们是否应该在当前时间戳之前执行，并相应地更新节流状态。 

这是有效的，因为我们按时间顺序明确地对每个事件进行建模。 我们始终知道：

 - 油门窗口是否处于活动状态
 - 当前存储了哪些参数
 - 下一次延迟执行何时发生

 然而，这种方法变得不必要地复杂。 管理完整的事件队列和重复扫描计划的操作会引入不必要的额外簿记。 

尽管约束很小，但蛮力方法更难推理并且更容易出错。 

### 最佳方法

 关键的观察是节流阀只需要少量的状态：

 - 当前执行是否被阻止
 - 最新保存的参数
 - 结束冷却时间的计时器

 我们不需要记住每个被阻止的呼叫。 该问题明确指出，只有最近被阻止的参数才重要。 

这允许我们使用以下方法来实现节流：

 - 表示活动冷却时间的布尔值或计时器状态
 - 存储最新待处理参数的变量
 - 继续执行链的递归超时回调

 每当冷却时间结束时：

 - 如果存在未决参数，则立即执行它们
 - 重新启动冷却窗口
 - 否则，完全解锁油门

 这创建了一个干净的状态机风格的解决方案。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(n) | 手动模拟所有预定事件 |
 | 最佳| O(n) | O(1) | O(1) | 仅维护最新的挂起呼叫和冷却状态 |

 ## 算法演练

 1. 创建变量来跟踪油门状态。 

我们需要：

 - 存储活动计时器的变量
 - 存储最新待处理参数和上下文的变量

 这些变量在对节流函数的调用之间持续存在。 
2. 定义一个在冷却结束时运行的辅助函数。 

该助手确定每个限制窗口到期后会发生什么。 

如果有未决的参数：

 - 提取最近保存的通话
 - 清除待处理存储
 - 执行`fn`与这些论点
 - 为下一个冷却时间启动另一个计时器

 否则：

 - 不存在待处理的呼叫
 - 完全清除定时器状态
 - 油门解锁
 3. 返回节流包装函数。 

每次用户调用节流函数时：

 - 如果没有激活冷却时间，则立即执行
 - 启动计时器`t`毫秒
 - 否则，将最新参数保存为待处理
 4. 在冷却期间覆盖待处理的呼叫。 

该问题需要仅保留最新的被阻止的呼叫。 

因此：

 - 每个被阻止的调用都会替换之前保存的参数
 - 先前阻止的呼叫将被丢弃
 5. 继续递归。 

每次延迟执行都会启动另一个冷却期。 

这个递归定时器链是问题中最重要的行为。 

### 为什么它有效

 该算法保持了一个不变量，即任何时间最多有一个延迟执行待处理。 在冷却窗口期间，每个传入呼叫都会用新的参数替换已保存的参数。 当冷却时间到期时，最新保存的调用将只执行一次，满足限制定义。 由于每次延迟执行都会启动新的冷却时间，因此执行计划与所需的行为精确匹配。 

## Python 解决方案```python
from typing import Any, Callable, Optional
from threading import Timer

class Solution:
    def throttle(self, fn: Callable, t: int) -> Callable:
        timer: Optional[Timer] = None
        pending_call = None

        def timer_callback():
            nonlocal timer, pending_call

            if pending_call is None:
                timer = None
                return

            args, kwargs = pending_call
            pending_call = None

            fn(*args, **kwargs)

            timer = Timer(t / 1000, timer_callback)
            timer.start()

        def throttled(*args: Any, **kwargs: Any) -> None:
            nonlocal timer, pending_call

            if timer is None:
                fn(*args, **kwargs)

                timer = Timer(t / 1000, timer_callback)
                timer.start()
            else:
                pending_call = (args, kwargs)

        return throttled
```实现首先在闭包内创建两个共享变量。 

这`timer`变量跟踪冷却窗口当前是否处于活动状态。 如果`timer`是`None`，油门解锁，函数可以立即执行。 

这`pending_call`变量存储最新的被阻止的调用。 它包含位置参数和关键字参数，因此包装器的行为与原始函数完全相同。 

这`timer_callback`每当冷却时间结束时函数就会运行。 它检查在之前的时间间隔内是否保存了任何被阻止的呼叫。 

如果不存在待处理的呼叫：

 - 油门解锁
 - 定时器参考被清除

 如果存在待处理的呼叫：

 - 执行保存的参数
 - 待处理的存储被清除
 - 另一个冷却计时器立即开始

 节流包装器本身很简单。 

如果没有激活冷却时间：

 - 立即执行
 - 启动冷却计时器

 否则：

 - 保存最新的参数
 - 覆盖任何之前的待处理呼叫

 这与确切的问题规范相符。 

## 解决方案```go
package main

import (
	"time"
)

func throttle(fn func(...interface{}), t int) func(...interface{}) {
	var timer *time.Timer
	var pendingArgs []interface{}

	var callback func()

	callback = func() {
		if pendingArgs == nil {
			timer = nil
			return
		}

		args := pendingArgs
		pendingArgs = nil

		fn(args...)

		timer = time.AfterFunc(
			time.Duration(t)*time.Millisecond,
			callback,
		)
	}

	return func(args ...interface{}) {
		if timer == nil {
			fn(args...)

			timer = time.AfterFunc(
				time.Duration(t)*time.Millisecond,
				callback,
			)
		} else {
			pendingArgs = args
		}
	}
}
```Go 实现遵循与 Python 版本相同的逻辑结构。 

一个重要的区别是计时器处理。 在 Go 中，我们使用`time.AfterFunc`安排延迟回调。 返回的`*time.Timer`作为我们的冷却指示器。 

另一个区别是参数处理。 Go 使用可变参数`...interface{}`模拟 JavaScript 风格的灵活函数参数。 

覆盖待处理调用的逻辑保持相同。 在主动冷却期间，仅存储最新被阻止的参数。

 ## 边缘情况

 当多个呼叫在同一冷却时间内到达时，会出现一种重要的边缘情况。 有缺陷的实现可能会将所有被阻止的调用排队并稍后执行它们。 然而，该问题明确要求仅存储最近被阻止的调用。 此实现通过覆盖正确处理该问题`pending_call`每次新的阻塞调用到达时。 

另一个棘手的情况是当`t = 0`。 在这种情况下，实际上没有冷却期。 糟糕的实现可能会意外地造成不必要的延迟或递归循环。 在这里，计时器立即到期，允许每个调用正确执行，而不会违反节流行为。 

当调用正好到达冷却边界时，会发生第三种微妙的情况。 例如，如果冷却时间结束于`100ms`一个新的电话到达`100ms`，它应该立即执行，而不是再次延迟。 该实现会处理此问题，因为一旦冷却完全结束，计时器回调就会清除油门状态。 

第四个重要案例涉及递归冷却链。 当发生延迟执行时，它会创建另一个冷却窗口。 一些不正确的实现在执行挂起的调用后忘记重新启动冷却。 该解决方案在每次延迟执行后显式启动一个新计时器，从而正确保留节流语义。
