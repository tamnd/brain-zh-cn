[LeetCode 问题 2622](https://leetcode.com/problems/cache-with-time-limit/)

 **难度：** 🟡 中等
 **主题：** —

 ## 解决方案

 ## 问题理解

 这个问题要求我们实现一个存储键值对的缓存，但与普通的哈希图不同的是，每个条目都有一个过期时间。 存储的值仅在以毫秒为单位的有限持续时间内保持可访问。 一旦持续时间到期，密钥应该表现得好像它不再存在一样。 

我们需要实现一个名为`TimeLimitedCache`具有三个操作：

 -`set(key, value, duration)`使用值和过期时间插入或更新键。 
-`get(key)`如果密钥仍然存在且尚未过期，则检索该值。 
-`count()`返回缓存中剩余的当前有效、未过期的键数。 

最重要的细节是密钥在其有效期结束后自动过期。 过期的密钥不应再由`get()`，并且他们不应该为`count()`。 

这`set()`方法有特殊要求。 它应该返回`true`如果密钥已经存在并且尚未过期，否则应该返回`false`。 即使键已经存在，该方法也会覆盖值和过期时间。 

示例中的输入模拟一段时间内的一系列操作。 这`actions`数组告诉我们调用了哪个方法，`values`提供方法参数，以及`timeDelays`描述每个操作相对于开始发生的时间。 这些延迟很重要，因为到期时间取决于经过的时间。 

这些约束告诉我们有关问题规模的几个重要信息：

 - 最多有100个操作，这是非常小的。 
- 键和值可以大到`10^9`，这意味着我们不应该依赖由键索引的数组。 
- 持续时间最多1000毫秒，延迟很小。 

尽管限制对于更简单的方法来说足够小，但我们仍然应该以高效和干净的实施为目标。 

一些边缘情况值得关注：

 - 当另一个操作发生时，密钥可能会过期。 我们必须仔细检查过期时间是包含的还是排除的。 一旦达到过期时间，密钥就会失效。 
- 密钥可能会在过期前被覆盖。 在这种情况下，旧的过期计时器应该不再重要。 
-`duration = 0`意味着密钥立即过期，所以`get()`应该返回`-1`除非在同一执行时间内立即检查。 
-`count()`应该只包含有效的密钥，这意味着必须忽略或删除过期的条目。 

## 方法

 ### 蛮力方法

 暴力解决方案会将每个插入的密钥及其过期时间戳存储在一起。 每当`get()`或者`count()`被调用时，我们将扫描所有存储的条目并手动删除过期的条目。 

为了`set()`，我们可以检查密钥是否存在以及其过期时间戳是否仍然有效。 然后我们覆盖值和过期时间。 

为了`get()`，我们将搜索密钥并验证当前时间是否仍然小于其过期时间。 

为了`count()`，我们将迭代每个键并仅计算那些尚未超过过期时间的键。 

这种方法是正确的，因为过期仅取决于将当前时间戳与每个密钥存储的过期时间进行比较。 然而，`count()`因为它会重复扫描所有键，所以效率很低。 

### 关键见解

 关键的观察结果是 JavaScript 环境提供了计时器（`setTimeout`）可以在正确的时刻自动删除过期的密钥。 

我们可以在插入密钥时主动安排删除，而不是重复扫描过期条目。 

我们使用哈希映射，其中：

 - 键映射到其存储的值。 
- 我们还保留计时器引用，以便在覆盖密钥时可以取消现有的到期时间。 

当插入新值时：

 1. 检查是否已存在未过期的密钥。 
2. 如有必要，取消任何旧计时器。 
3. 创建一个新的计时器，在之后删除密钥`duration`毫秒。 
4. 存储更新后的值和计时器。 

然后：

-`get()`变成简单的哈希查找。 
-`count()`成为哈希图的大小。 

这使得每项操作都高效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | ---| ---| ---| ---|
 | 蛮力 | 每个查询 O(n) | O(n) | 重复扫描密钥过滤过期条目 |
 | 最佳| O(1) 平均 | O(n) | 使用哈希映射和预定的过期时间 |

 ## 算法演练

 1. 创建哈希映射来存储缓存条目。 

每个条目存储两条信息：值和计时器参考。 需要计时器，以便如果在过期之前相同的密钥被覆盖，我们可以取消旧的过期事件。 
2. 什么时候`set(key, value, duration)`调用时，首先检查key是否已经存在。 

如果该键存在于哈希映射中，则意味着它当前未过期，因为过期的条目会被自动删除。 这决定了该方法是否返回`true`或者`false`。 
3. 如果该key已存在，则取消其旧定时器。 

这是必要的，因为覆盖该值后，先前的到期时间不应再适用。 
4. 使用创建一个新计时器`setTimeout`。 

计时器将在之后自动删除该密钥`duration`毫秒。 这可确保过期条目消失而无需手动清理。 
5. 将更新后的值和计时器存储在哈希图中。 

这将取代任何以前版本的密钥。 
6. 什么时候`get(key)`调用时，检查该键是否存在于哈希映射中。 

如果存在，则返回其存储值。 否则，返回`-1`。 
7. 什么时候`count()`被调用时，只需返回哈希图大小。 

由于过期的密钥会自动删除，因此映射仅包含有效的条目。 

### 为什么它有效

 正确性依赖于散列映射始终仅包含未过期键的不变性。 每个插入的密钥都会在到期时间准确地安排自己的删除，并且覆盖密钥会取消先前的计时器以防止过时的删除。 所以，`get()`和`count()`始终对仅包含有效缓存条目的结构进行操作。 

## Python 解决方案```python
from typing import Dict, Tuple
from threading import Timer

class TimeLimitedCache:

    def __init__(self):
        self.cache: Dict[int, Tuple[int, Timer]] = {}

    def set(self, key: int, value: int, duration: int) -> bool:
        key_exists = key in self.cache

        if key_exists:
            _, old_timer = self.cache[key]
            old_timer.cancel()

        def expire() -> None:
            self.cache.pop(key, None)

        timer = Timer(duration / 1000, expire)
        timer.start()

        self.cache[key] = (value, timer)

        return key_exists

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1

        return self.cache[key][0]

    def count(self) -> int:
        return len(self.cache)
```该实现使用一个字典，其中每个键映射到一个包含存储值和活动计时器的元组。 

里面`set()`，我们首先判断key是否已经存在。 由于过期的键会自动删除，因此字典中存在的任何键都保证仍然有效。 

如果密钥存在，我们在覆盖之前取消旧计时器。 如果没有此步骤，先前的计时器仍可能触发并意外删除新更新的值。 

一个嵌套的`expire()`当计时器结束时，函数删除钥匙。 然后我们使用创建一个新的计时器`Timer(duration / 1000, expire)`因为Python计时器使用秒而不是毫秒。 

这`get()`方法故意简单。 由于过期条目会自动删除，因此我们只需要检查密钥是否存在即可。 

相似地，`count()`返回字典长度，因为存储中仅保留有效条目。 

**重要提示：** LeetCode 本题的原始环境是 JavaScript，其中`setTimeout`可用。 Python 提交可能会因执行支持而异。 算法思想保持不变。 

## 解决方案```go
package main

import (
	"sync"
	"time"
)

type CacheEntry struct {
	value int
	timer *time.Timer
}

type TimeLimitedCache struct {
	cache map[int]CacheEntry
	mutex sync.Mutex
}

func Constructor() TimeLimitedCache {
	return TimeLimitedCache{
		cache: make(map[int]CacheEntry),
	}
}

func (this *TimeLimitedCache) Set(key int, value int, duration int) bool {
	this.mutex.Lock()
	defer this.mutex.Unlock()

	_, exists := this.cache[key]

	if exists {
		this.cache[key].timer.Stop()
	}

	timer := time.AfterFunc(
		time.Duration(duration)*time.Millisecond,
		func() {
			this.mutex.Lock()
			defer this.mutex.Unlock()
			delete(this.cache, key)
		},
	)

	this.cache[key] = CacheEntry{
		value: value,
		timer: timer,
	}

	return exists
}

func (this *TimeLimitedCache) Get(key int) int {
	this.mutex.Lock()
	defer this.mutex.Unlock()

	entry, exists := this.cache[key]
	if !exists {
		return -1
	}

	return entry.value
}

func (this *TimeLimitedCache) Count() int {
	this.mutex.Lock()
	defer this.mutex.Unlock()

	return len(this.cache)
}
```Go 版本遵循相同的设计，但使用`time.AfterFunc()`而不是Python的`Timer`。 由于计时器在 goroutine 中异步执行，因此需要互斥体来保护对共享映射的并发访问。 

与 Python 不同，Go 没有映射的自动线程安全性。 如果没有同步，并发计时器执行可能会导致竞争条件。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(1) 平均 | 哈希图操作和定时器设置都是恒定时间 |
 | 空间| O(n) | 最多`n`存储在缓存中的活动密钥 |

 每个操作都会执行恒定数量的哈希映射查找、插入或删除。 由于过期是由定时器异步处理的，因此不需要额外的扫描工作。 

空间复杂度是线性的，因为我们为每个活动键存储一个映射条目和一个计时器。

 ## 边缘情况

 ### 在过期之前覆盖密钥

 密钥可以在其先前的到期计时器触发之前被更新。 这是错误的常见来源，因为旧计时器仍可能删除新更新的值。 

例如，如果键`1`到期于`50ms`，但我们将其覆盖`40ms`与一个新的`100ms`持续时间，原始到期不得删除更新的条目。 该实现通过在创建新计时器之前取消前一个计时器来处理此问题。 

### 持续时间等于零

 持续时间为`0`表示密钥立即过期。 幼稚的实现可能会意外地使密钥的可访问时间比预期的长。 

基于计时器的解决方案可以自然地处理这个问题，因为到期回调会立即运行。 密钥几乎立即变得不可用并且`get()`正确返回`-1`。 

### 刚好在查询时过期

 当操作正好在过期时间戳发生时，就会出现微妙的边界条件。 密钥应该已经被视为已过期。 

由于过期时间是通过计时器精确安排的，因此一旦持续时间过去，密钥就会从映射中删除。 任何后续的`get()`或者`count()`调用的行为正确，就好像密钥从未存在过一样。
