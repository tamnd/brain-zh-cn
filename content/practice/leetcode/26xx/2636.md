 **难度：** 🟡 中等
 **主题：** —

 ## 解决方案

 ## 问题理解

 这个问题要求我们为异步操作实现一个并发限制器。 

我们有一个数组叫做`functions`，其中每个元素本身就是一个函数。 当调用这些函数之一时，它会返回一个 Promise。 每个 Promise 代表一些异步工作，例如等待超时或发出网络请求。 

我们还得到一个整数`n`，表示允许同时运行的 Promise 的最大数量。 这称为池限制。 

目标是创建一个名为`promisePool`在遵守并发限制的同时执行异步函数。 

重要的细节是我们应该始终尽力保持池尽可能满。 如果少于`n`Promise 当前正在运行，并且仍有函数需要执行，我们应该立即启动另一个函数。 

执行顺序很重要。 我们必须从`functions[0]`， 然后`functions[1]`， 然后`functions[2]`， 等等。 然而，完成顺序不一定与执行顺序匹配，因为不同的 Promise 可能需要不同的时间来解决。 

返回的 Promise 应该仅在每个输入函数完成后解析。 

例如：

 - 如果`n = 1`，一次只能运行一个 Promise，因此函数是按顺序执行的。 
- 如果`n = 2`，两个 Promise 可以同时运行。 
- 如果`n`大于函数个数，那么所有函数都可以立即启动。 

限制非常小：

 -`0 <= functions.length <= 10`-`1 <= n <= 10`这意味着性能并不是实际输入大小的主要问题，但该问题旨在测试对异步控制流和并发管理的理解。 

一些边缘情况很重要：

 - 输入数组可能为空。 
-`n`可能大于函数的数量。 
-`n`可能等于`1`，强制严格顺序执行。 
- 多个 Promise 可能几乎同时解决。 
- 该问题保证 Promises 永远不会拒绝，因此我们不需要错误处理逻辑。 

## 方法

 ### 蛮力方法

 最直接的解决方案是按顺序执行函数。 

我们可以遍历数组并`await`在开始下一个 Promise 之前。 这保证了正确性，因为一次只有一个 Promise 处于活动状态，因此永远不会超出池限制。 

然而，这种方法完全忽略了并发限制`n > 1`。 即使允许多个 Promise 同时运行，我们仍然一一执行它们。 

例如，如果三个任务各花费 1 秒并且`n = 3`，顺序求解仍需要 3 秒而不是 1 秒。 

该解决方案是正确的，但效率低下，因为它没有利用可用的并发性。 

### 最佳方法

 关键的见解是我们应该始终保持`n`尽可能主动做出承诺。 

我们可以在一个任务完成时立即启动一项新任务，而不是等待所有当前正在运行的任务完成。 

实现此目的的常见方法是：

 1. 跟踪下一个要执行的函数索引。 
2. 启动至`n`工人协程。 
3、每个工人反复：

 - 获取下一个可用的函数索引。 
- 执行该功能。 
- 等待它完成。 
- 重复直到没有任何功能剩余。 

这创建了一个动态调度系统，完成的工作人员可以自动接手新的工作。 

重要的观察是最多`n`工人同时存在，所以最多`n`Promise 立即生效。 

| 方法| 时间复杂度| 空间复杂度| 笔记|
 | --- | --- | --- | --- |
 | 蛮力 | O(米) | O(1) | O(1) | 按顺序执行每个 Promise |
 | 最佳| O(米) | O(n) | 维持至`n`并发承诺 |

 这里，`m`代表函数的数量。 

## 算法演练

 1. 首先，创建一个共享变量，名为`next_index`跟踪下一个尚未启动的功能。 
2. 定义异步工作函数。 该工作人员负责重复从共享队列中提取任务。 
3.工人内部：

 - 检查是否`next_index`仍在范围内。 
- 如果没有，则没有剩余工作，因此返回。 
- 否则，存储当前索引和增量`next_index`。 
4. 通过调用执行该索引处的函数`await functions[current_index]()`。 
5. Promise 解决后，循环返回并尝试获取另一个任务。 
6. 创建最多`n`工人。 如果函数少于`n`，只创建必要数量的工人。 
7. 使用`await asyncio.gather(...)`在Python中，或者`sync.WaitGroup`在 Go 中，等待所有工人完成。 
8. 一旦所有工作人员完成，所有 Promise 都已解决，因此池函数也可以解决。 

### 为什么它有效

 该算法保持了每个函数索引仅分配一次的不变性。 

因为所有工人共享相同的`next_index`，每个任务在执行前都是唯一声明的。 由于最多有`n`并发运行的工作线程，活动 Promise 的数量永远不会超过池限制。 

每当工作线程完成一个 Promise 时，它​​就会立即尝试启动另一个任务，从而尽可能高效地利用池。 

## Python 解决方案```python
from typing import List, Callable, Awaitable
import asyncio

class Solution:
    async def promisePool(
        self,
        functions: List[Callable[[], Awaitable[None]]],
        n: int
    ) -> None:
        next_index = 0

        async def worker() -> None:
            nonlocal next_index

            while True:
                if next_index >= len(functions):
                    return

                current_index = next_index
                next_index += 1

                await functions[current_index]()

        worker_count = min(n, len(functions))

        await asyncio.gather(
            *(worker() for _ in range(worker_count))
        )
```实现首先定义`next_index`，它充当指向下一个未处理函数的共享指针。 

嵌套的`worker`协程反复从共享索引中提取工作。 每个工作人员通过存储当前索引并递增来声明一项任务`next_index`。 

声明任务后，工作人员使用以下命令执行异步函数`await`。 

这`while True`循环允许每个工作人员继续处理任务，直到没有剩余任务为止。 

我们最多创造`n`因为池限制定义了最大并发数。 如果功能少于工人，我们只会为可用任务创建足够的工人。 

最后，`asyncio.gather`在解析池之前等待所有工作人员完成。 

## 解决方案```go
package main

import "sync"

type AsyncFunc func() chan struct{}

func promisePool(functions []AsyncFunc, n int) chan struct{} {
	done := make(chan struct{})

	go func() {
		defer close(done)

		var mutex sync.Mutex
		nextIndex := 0

		var wg sync.WaitGroup

		worker := func() {
			defer wg.Done()

			for {
				mutex.Lock()

				if nextIndex >= len(functions) {
					mutex.Unlock()
					return
				}

				currentIndex := nextIndex
				nextIndex++

				mutex.Unlock()

				<-functions[currentIndex]()
			}
		}

		workerCount := n
		if len(functions) < workerCount {
			workerCount = len(functions)
		}

		wg.Add(workerCount)

		for i := 0; i < workerCount; i++ {
			go worker()
		}

		wg.Wait()
	}()

	return done
}
```Go 版本使用 goroutine 而不是 Python 协程。 

一个`sync.Mutex`保护访问`nextIndex`因为多个工人可能会尝试同时领取任务。 

一个`sync.WaitGroup`跟踪活跃的工作线程并允许主 goroutine 等待所有工作线程完成。 

异步函数表示为返回通道的函数。 等待中`<-functions[currentIndex]()`模拟等待 Promise。 

与 Python 不同，Go 需要显式同步原语，因为 goroutine 在系统级别并发执行。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(米) | 每个函数只执行一次 |
 | 空间| O(n) | 最多`n`工人同时存在|

 该算法只对每个函数处理一次，因此总工作量与任务数量呈线性关系。 

额外的内存主要来自活跃的工作协程或 goroutine。 因为至多`n`Workers同时存在，辅助空间使用量与池大小成正比。 

## 测试用例```python
import asyncio

class Solution:
    async def promisePool(self, functions, n):
        next_index = 0

        async def worker():
            nonlocal next_index

            while True:
                if next_index >= len(functions):
                    return

                current = next_index
                next_index += 1

                await functions[current]()

        await asyncio.gather(
            *(worker() for _ in range(min(n, len(functions))))
        )

async def run_tests():
    sol = Solution()

    # Empty input
    await sol.promisePool([], 3)

    # Single task
    result = []

    async def task1():
        result.append(1)

    await sol.promisePool([task1], 1)
    assert result == [1]  # Single function execution

    # Sequential execution with n = 1
    order = []

    async def a():
        order.append("a")

    async def b():
        order.append("b")

    async def c():
        order.append("c")

    await sol.promisePool([a, b, c], 1)
    assert order == ["a", "b", "c"]  # Sequential ordering

    # More workers than tasks
    result = []

    async def x():
        result.append("x")

    async def y():
        result.append("y")

    await sol.promisePool([x, y], 10)
    assert sorted(result) == ["x", "y"]  # All tasks still execute

    # Multiple concurrent tasks
    counter = 0

    async def increment():
        nonlocal counter
        counter += 1

    await sol.promisePool([increment for _ in range(5)], 2)
    assert counter == 5  # Every task executed exactly once

asyncio.run(run_tests())

 | --- | --- |
 | 空输入 | 确保不会创建不必要的工人 |
 | 单任务 | 验证最小非空情况 |
 |`n = 1`| 确认顺序执行 |
 |`n > len(functions)`| 确保所有任务立即开始 |
 | 多个并发任务 | 验证每个任务恰好执行一次 |

 ## 边缘情况

 ### 空函数数组

 如果`functions`为空，没有什么可执行的。 幼稚的实现可能仍会尝试创建工作线程或访问无效索引。 

此实现正确处理了这种情况，因为`worker_count`变成`0`， 所以`asyncio.gather`不接收任何工人并立即解决。 

### 池大小大于任务数

 如果`n`超过功能数量时，我们不应该创建不必要的工人。 

例如：```
functions.length = 2
n = 10
```由于只有两项任务可用，因此只需要两名工作人员。 实现正确使用：```
min(n, len(functions))
```以避免多余的工人。 

### 顺序执行`n = 1`这种情况有效地将池变成了队列。 

一个常见的错误是在等待完成之前意外启动多个任务。 在此实现中，只有一个工作人员存在，当`n = 1`，因此任务严格地一个接一个地执行。 

### 同时 Promise 解析

 多个 Promise 可能几乎同时完成。 如果不仔细分配任务，两个工作人员可能会意外执行相同的函数索引。 

该实现通过增加来防止这种情况发生`next_index`当工人领取任务时立即。 因此，每个任务索引只分配一次。
