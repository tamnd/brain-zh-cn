 ## 解决方案
 ## 问题理解

 我们获得了按时间顺序排列的事件流，描述了来自不同站点的工作请求，以及一台在站点之间移动并在其访问的每个站点上工作固定天数的挖掘机。 

每个请求都与站点索引及其出现的日期相关联。 挖掘机还以离散时间运行，按顺序向前穿过站点，当它到达某个站点时，它会在那里停留一段固定的时间，然后可能进一步移动，具体取决于当时已经出现的请求。 

关键的交互是请求随着时间的推移而累积，但挖掘机的移动取决于当前工作间隔结束时出现的最新请求。 这在时间进程和空间进程之间产生了耦合：在每个阶段，我们在当前时间窗口下已经变得“可见”的所有请求中尽可能地扩展挖掘机的位置。 

输出需要跟踪挖掘机随着时间的推移有效地跨站点“跳跃”多远，并积累这些跳跃的统计数据，特别是跳跃的最大距离以及实现该最大值的跳跃的总持续时间。 

从复杂度的角度来看，输入是有序的，因此不需要排序。 这些限制意味着，如果时间线很大，我们就无法逐日进行模拟，因为每天可能需要向前扫描许多事件。 在最坏的情况下，简单的模拟会降级为二次行为，其中每个站点都会导致事件列表的重复重新扫描。 

一个关键的微妙之处是，在一个挖掘机间隔期间，多个请求可能同时变得相关，并且在做出下一个移动决策之前，必须全部吸收这些请求。 另一个边缘情况是当请求恰好在挖掘机完成站点的边界日到达时，这会影响该请求是属于当前段还是下一个段。 

天真的处理的最小失败场景是：

 输入：```
2 2
1 1
2 2
```如果错误地将第二个请求严格地视为属于站点 1 完成后的下一阶段，则计算出的跳跃计时会偏离一天，从而导致不正确的持续时间累积。 

当在任何移动完成之前发生多个请求时，会出现另一种微妙的情况：```
3 5
1 1
2 2
3 3
```简单的每日模拟可能进展太慢，反复重新处理已经消耗的事件。 

## 方法

 蛮力的想法是明确地模拟时间。 每天，我们都会检查是否出现新请求，根据迄今为止看到的所有请求更新可到达的最远站点，然后逐步跨站点移动挖掘机。 每次移动都会触发对截至该时刻出现的所有请求的扫描，以找出我们可以将当前段扩展多远。 

这是正确的，因为它直接模仿了问题中描述的过程。 然而，每个站点转换可能需要重新扫描不断增长的事件前缀。 如果有 n 个事件并且挖掘机移动 O(n) 次，则总复杂度变为 O(n²)，这对于大输入来说太慢了。 

关键的一点是，请求已经按照时间排序了，一旦挖掘机的工作间隔固定，我们就可以在一次向前扫描中消耗掉时间在该间隔内的所有请求。 当我们在列表中推进指针时，每个请求最多被处理一次。 这自然会导致两指针或线性扫描策略：一个指针跟踪当前请求索引，另一个指针跟踪挖掘机的当前时间窗口端点。 

我们不会重复扫描过去的请求，而是单调地推进它们，确保每个事件只处理一次。 然后根据下一次转变之前时间窗口延伸的距离导出空间移动。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(n) | 太慢了|
 | 最优两指针 | O(n) | O(n) | 已接受 |

 ## 算法演练

 我们维护一个请求指针并模拟挖掘机可以将其当前连续工作间隔延长多远。 

1. 首先将所有请求读入一个数组，按天保留它们的顺序，因为它们已经按时间顺序给出。 我们还跟踪每个请求的站点索引和到达日期。 
2. 初始化一个指针`i`在第一次请求时。 这表示可能扩展当前挖掘机段的最早的未处理请求。 
3. 对于每个路段，根据最早尚未处理的请求设置挖掘机的当前站点和开始时间。 
4. 定义当前工作间隔的结束时间为`current_day + k - 1`，因为挖掘机在每个地点正好停留 k 天。 此边界确定哪些请求在此段期间变得可见。 
5. 当下一个请求的到达时间小于或等于当前间隔结束时，前进指针并更新迄今为止到达的最远站点索引。 这一步至关重要，因为所有此类请求都会影响我们一批而不是单独地延长挖掘机移动的距离。 
6. 一旦没有更多请求落入当前间隔，则将空间跳跃计算为最后处理的站点与当前站点之间的差异，并根据对齐情况将时间贡献计算为下一个请求时间与当前段开始或结束之间的差异。 
7. 由于移动继续向前，因此将当前站点更新为最远可到达的站点加一级。 
8. 更新当前时间以反映挖掘机转换到下一个站点的时刻，即当前间隔的末尾加一。 
9. 重复此过程，直到消耗完所有请求。 

### 为什么它有效

 正确性取决于以下不变量：在每个段的开始处，所有时间小于当前段结束的请求都已被恰好考虑一次，并且指针永远不会向后移动。 这确保了每个请求都对一个最大可达间隔做出贡献。 由于挖掘机仅在耗尽当前时间窗口内的所有相关请求后才改变位置，因此可达段的贪婪扩展始终是最大的并且与所描述的过程一致。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    req = []
    for _ in range(n):
        t, x = map(int, input().split())
        req.append((t, x))

    i = 0
    cur_time = req[0][0]
    cur_site = req[0][1]

    ans_max_jump = 0
    ans_days = 0

    while i < n:
        start_time = cur_time
        end_time = cur_time + k - 1

        furthest_site = cur_site

        while i < n and req[i][0] <= end_time:
            # absorb all requests in current window
            furthest_site = max(furthest_site, req[i][1])
            i += 1

        jump = furthest_site - cur_site

        if jump > ans_max_jump:
            ans_max_jump = jump
            ans_days = 0

        if jump == ans_max_jump:
            ans_days += (end_time - start_time + 1)

        cur_site = furthest_site + 1
        cur_time = end_time + 1

    print(ans_max_jump, ans_days)

if __name__ == "__main__":
    solve()
```实现直接遵循两指针结构。 变量`i`确保每个请求都被处理一次。 段边界是用包含端点来处理的，所以`end_time = cur_time + k - 1`避免计算天数时出现相差一的错误。 

更新内容`cur_site = furthest_site + 1`反映在耗尽所有可到达的影响后，挖掘机向最远的受影响地点移动一步。 每当发现新的最大跳跃时，累积逻辑都会仔细地重置总日计数器，这符合仅跟踪最大跳跃间隔的贡献的要求。

 ## 边缘情况

 当多个请求正好到达段结束时间的边界时，就会出现一种边缘情况。 在这种情况下，它们必须被纳入当前的吸收阶段。 例如，如果`cur_time = 1`和`k = 2`， 然后`end_time = 2`，并且在移动之前仍必须处理时间 2 的请求。 

另一个边缘情况是当段内没有新请求到达时，这会迫使算法产生零跳转。 指针仍然随时间前进，确保模拟不会停止。 

最后一个微妙的情况是所有请求都位于一个早期窗口中。 该算法正确地将它们折叠成一个最大范围计算，因为内部 while 循环吸收了所有索引`i`满意的`req[i][0] <= end_time`，在该窗口中不留下任何剩余的未处理事件。
