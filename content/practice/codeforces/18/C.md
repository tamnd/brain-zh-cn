 ## 解决方案
 ## 问题理解

 我们有一条单元格，每个单元格包含一个整数。 我们可以仅在相邻单元之间切割条带，这将阵列分成左部分和右部分。 任务是计算有多少个切割位置产生了两个总和相等的非空部分。 

例如，如果数组是：```
[1, 2, 3, 3]
```在第二个元素之后切割给出：```
[1, 2] | [3, 3]
```左边的总和是`3`，正确的总和是`6`，所以这个剪切是无效的。 

输入大小达到`10^5`，这立即排除了每次切割重复重新计算总和的算法。 二次解的执行大致如下`10^10`最坏情况下的操作，远远超出了 2 秒的限制。 目标复杂度是线性时间，或者非常接近它的时间。 

这些数字也可能是负数，因此我们不能依赖单调行为。 前缀总和可以任意增加或减少。 任何基于两个指针或贪婪扩展的解决方案都会失败，因为总数不会朝着可预测的方向移动。 

有几种容易被忽略的边缘情况。 

考虑单个元素：```
1
5
```没有有效的切割，因为两块都必须包含至少一个元素。 正确答案是：```
0
```一个粗心的实现，检查所有索引`0`到`n`可能会意外地计算空分区。 

当总和为奇数时，会出现另一个棘手的情况：```
4
1 2 3 5
```总计为`11`。 两个相等的整数一半是不可能的，所以答案一定是：```
0
```即使不存在解决方案，某些实现仍然会扫描所有切割。 

负值是错误的另一个来源：```
5
2 -2 2 -2 0
```总和是`0`，并且有几个有效的削减。 任何假设前缀和只增长的方法都会在这里失败。 

最后，剪切位置本身很重要。 我们不能在最后一个元素之后进行剪切，因为右侧将是空的。 例如：```
2
1 -1
```总和是`0`，但在第一个元素之后只有一个可能的剪切：```
[1] | [-1]
```总和不相等，所以答案是`0`。 

## 方法

 最直接的解决方案是尝试每一种可能的切割并独立计算左右部分的总和。 

假设我们在索引之后进行切割`i`。 我们可以计算：```
left_sum  = sum(a[0..i])
right_sum = sum(a[i+1..n-1])
```如果总和匹配，我们就增加答案。 

这种方法是正确的，因为它明确地检查每个合法分区。 问题是效率。 计算一个范围内的总和需要`O(n)`如果天真地做的话，时间，并且有`n - 1`可能的削减。 总复杂度变为`O(n^2)`。 

和`n = 100000`，这大致意味着：```
100000 * 100000 = 10^10
```在最坏的情况下，操作速度太慢了。 

关键的观察结果是相邻的切割严重重叠。 当我们将剪切向右移动一步时，几乎所有元素都保留在同一分区中。 从头开始重新计算总和会浪费工作量。 

这自然暗示了前缀和。 

如果我们知道整个数组的总和，那么对于索引后的切割`i`:```
left_sum  = prefix[i]
right_sum = total_sum - prefix[i]
```条件变为：```
prefix[i] == total_sum - prefix[i]
```简化为：```
2 * prefix[i] == total_sum
```现在可以在恒定的时间内检查每次切割。 我们扫描一次数组，维护一个运行的前缀和，并计算有多少位置满足相等性。 

这将复杂性从二次降低到线性。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(1) | O(1) | 太慢了 |
 | 最佳 | O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 读取数组并计算其总和。 

我们需要总计，因为每个右侧总和都可以写为：```
total_sum - left_sum
```2. 将运行前缀和初始化为`0`答案为`0`。 

前缀总和表示当前剪切的左分区的总和。 
3. 从索引处迭代数组`0`到`n - 2`。 

我们停在`n - 2`因为剪切必须在右侧至少留下一个元素。 
4. 将当前元素添加到前缀和中。 

添加后`a[i]`，如果我们在索引之后进行切割，则前缀总和等于左分区的总和`i`。 
5. 检查是否：```
prefix_sum * 2 == total_sum
```如果这个条件成立，则左分区和右分区的总和相等。 
6. 如果条件为真，则增加答案。 
7. 处理完所有有效剪切位置后，打印答案。 

### 为什么它有效

 在每一步中，运行前缀总和等于当前索引之后切割创建的左分区的总和。 正确的分区必须有总和：```
total_sum - prefix_sum
```削减在以下情况下有效：```
prefix_sum == total_sum - prefix_sum
```该算法对每个合法切割位置的此条件仅检查一次。 由于每个可能的切割都会被检查，并且相等性测试在数学上等同于原始要求，因此算法不会错过有效的切割或计算无效的切割。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n = int(input())
a = list(map(int, input().split()))

total_sum = sum(a)

prefix_sum = 0
answer = 0

for i in range(n - 1):
    prefix_sum += a[i]

    if prefix_sum * 2 == total_sum:
        answer += 1

print(answer)
```第一部分读取输入并计算数组的总和。 这使我们能够立即获得每次切割的右侧总和。 

变量`prefix_sum`存储左侧分区的运行总和。 当我们迭代数组时，每个新元素都成为左侧的一部分。 

循环仅运行到`n - 2`。 这个细节很重要。 如果我们允许`i = n - 1`，右侧分区将为空，这违反了问题陈述。 

条件：```
prefix_sum * 2 == total_sum
```完全避免了分裂。 这更干净，也避免了总数奇数的问题。 如果总和是奇数，则任何整数前缀和都不能满足相等，所以条件自然不成立。 

Python 整数自动安全地处理大值，因此溢出不是这里的问题。 在具有固定宽度整数的语言中，仍然建议使用 64 位类型。

 ## 边缘情况

 考虑尽可能最小的输入：```
1
5
```循环运行结束：```
range(n - 1) = range(0)
```所以不会发生迭代。 答案依然存在`0`，这是正确的，因为我们不能将一个元素拆分为两个非空部分。 

现在考虑一个奇数总和：```
4
1 2 3 5
```总和是`11`。 

扫描期间：

 | 我| 前缀总和 | 前缀总和 * 2 |
 | --- | --- | --- |
 | 0 | 1 | 2 |
 | 1 | 3 | 6 |
 | 2 | 6 | 12 | 12

 没有一个等于`11`，所以答案仍然是`0`。 该算法自然会拒绝不可能的情况，无需特殊处理。 

接下来，考虑负值：```
5
2 -2 2 -2 0
```总和是`0`。 

运行前缀和变为：```
2, 0, 2, 0
```每当前缀和为`0`，其余后缀的总和也为`0`，所以这些削减被正确计算。 该算法从不假设总和单调增加，因此负数不会引起问题。 

最后，考虑边界条件：```
2
1 -1
```唯一合法的削减是在指数之后`0`。 

前缀和变为`1`，而右侧是`-1`，所以条件不成立，答案是`0`。 

该算法从不检查最后一个元素之后的剪切，因为循环停止于`n - 2`。 这可以避免意外计数空的右侧分区。
