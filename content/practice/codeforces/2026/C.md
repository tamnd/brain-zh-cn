 ## 解决方案
 ## 问题理解

 我们得到了一系列编号为 1 到 n 的动作人物。 图 i 花费 i 个币，但无法在第一天立即购买； 它仅从第一天开始可用。 第 n 天之后，一切都可用。 

在 n 天中，每天要么是 Monocarp 可以访问商店的工作日，要么是他不能访问商店的封锁日。 在访问日，他可以购买当前可用人物的任何子集。 如果他在同一次访问中至少购买了两个玩偶，则该批次中最昂贵的一个是免费的。 

我们的目标是只购买每个玩偶一次，同时最大限度地减少总花费。 

关键的困难在于购买决策受到时间的限制：较早的数据总是可用的，但较晚的数据需要等待特定的日期，并且由于折扣规则，分组购买很重要。 

约束很大，测试用例的总 n 高达 4·10^5，因此任何针对天数或数字的二次策略都是不可能的。 如果重复使用大量数据结构实现，即使每个测试用例的 O(n log n) 在最坏的情况下也会太慢，因此我们应该瞄准线性或近线性行为。 

当访问日早稀疏但晚访问日密集时，就会出现微妙的边缘情况。 例如，如果只有最后一天可用，则每个模型必须一起购买，并且只有最大数量是免费的。 这导致成本 1 + 2 + ... + (n−1)。 天真的贪婪者试图在不考虑可用性的情况下推迟购买，很容易通过过度使用后期分组来低估成本。 

另一个棘手的情况是访问日是连续的。 例如，s =“11111”。 然后我们可以将每个相邻日期的购买配对以最大化折扣。 每次访问总是购买一件商品的幼稚策略会失去组合购买和降低成本的机会。 

真正的紧张在于决定何时推迟购买玩偶以便稍后配对，而不是立即购买以避免失去配对机会。 

## 方法

 强力解释将模拟决策：对于每个人物，选择购买它的日期，并为每一天选择将哪些可用人物分组在一起。 这成为指数分支的分配问题，因为一天购买的每个商品子集都会影响未来的可用性和折扣。 即使我们将自己限制在子集上的 DP 或几天内的 DP 和“未购买的掩码”，状态空间也是 2^n，这对于 n 达到 4·10^5 来说是立即不可能的。 

关键的观察结果是，折扣结构极其严格：在任何一天，只有当天购买的最昂贵的商品才会免费。 这意味着每件“免费物品”必须与当天购买的更昂贵的物品配对，并且每天最多只能贡献一件免费物品。 

因此，整个问题简化为将每个项目 i 与某些 j > i 配对（其中 j 是两者都可用的日期）或不配对。 每个配对 (i, j) 都会消除成本 i。 成本 j 总是要支付的，除非它本身与更大的东西配对。 

现在观点发生了转变：我们不再考虑天数，而是只关心哪些索引可以分组，并且分组仅受两个项目必须在所选日期可用的条件的限制。 由于项目 j 在 j 天变得可用，因此涉及 j 的任何对都必须在 j 天或之后发生，这意味着 i < j 两个项目在 j 天都可用。 

因此，每个配对只是选择一个“后来的锚点”j，它可以吸收一个较早的项目 i < j。 

我们希望最大化总节省，其中每个 j 最多可以节省 1 个 i < j，并且每个 i 最多可以使用一次。 问题变成了如何贪婪地将较小的索引分配给较大的索引。

我们从左到右处理索引，并维护一个“可访问的可用天数”池，我们仍然可以将较小的项目与未来较大的项目配对。 每次我们遇到 s[i] = 1 的一天，它都可以作为潜在的配对端点，但前提是我们确保可用性约束的可行性。 

正确的贪心变成：当我们到达位置 i 时，我们决定是否将 i 作为免费项目与稍后访问的一天配对或付费。 我们维护由访问天数创建的多组活动“时段”，并将小索引分配给最早可能的时段，以最大限度地提高使用率。 

出现了更具体的简化：我们从左到右进行模拟，维护可用访问容量的计数器。 每个“1”增加容量； 每次我们遇到一个项目时，如果可能的话，我们都会尝试将其分配为免费，否则我们会付费。 这种贪婪之所以有效，是因为将较小的项目分配给较早的可能访问可以保留较大项目的灵活性，而较大项目由于可用性限制而具有较少的选择。 

这简化为线性扫描，具有简单的结构，跟踪有多少项目仍然可以“免费配对”。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 将项目暴力分配给天/子集 | O(2^n) | O(2^n) | O(n) | 太慢了|
 | 贪婪容量模拟| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1.从1到n遍历索引，维护一个计数器`free_slots`表示仍有多少较早的商品可以分配给未来的访问以进行折扣配对。 每次我们看到访问日时，我们都会增加此容量，因为它可能会举办配对。 
2. 当我们到达位置 i 时，我们首先确保我们考虑了可用性：如果第 i 天是访问日，则它增加了形成未来折扣组的能力，因此我们增加`free_slots`。 
3. 如果我们有空位（`free_slots > 0`），我们将项目 i 分配为“在未来的配对中自由”，这意味着我们递减`free_slots`并且不支付我的费用。 
4. 如果没有空位，我们必须立即支付 i，并将 i 添加到答案中。 
5. 继续直到 n，确保每个项目都已付款或分配给有效的未来配对机会。 

关键的微妙之处在于，在配对时并不直接使用访问天数；而是在配对时直接使用访问天数。 相反，它们创建的容量被早期未分配的项目消耗。 这种反转就是贪婪算法发挥作用的原因。 

### 为什么它有效

 在任何时刻，`free_slots`代表我们仍然可以推迟并与稍后访问的一天匹配的项目数量。 每个访问日都会贡献一个潜在的“免费商品机会”，因为每次访问只能对一批中最昂贵的商品进行折扣。 首先分配较小的索引可确保每次使用访问时都能产生最大的节省，因为它释放了尽可能小的剩余成本。 可用访问容量和最小未解决项目之间的这种贪婪匹配保留了最优性，因为任何推迟小项目而有利于较大项目的偏差只会增加总成本。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = input().strip()

        free_slots = 0
        ans = 0

        for i in range(n):
            if s[i] == '1':
                free_slots += 1

            # try to use a slot for item i+1
            if free_slots > 0:
                free_slots -= 1
            else:
                ans += (i + 1)

        print(ans)

if __name__ == "__main__":
    solve()
```实现直接遵循贪心解释。 循环索引i对应于图i+1。 每次我们看到“1”，我们就会增加未来可用配对机会的数量。 当处理一个图形时，我们要么将其分配给这些机会之一（消耗一个槽），要么支付其成本。 

一个微妙的点是，槽在使用时会立即被消耗。 这反映出每次访问只能“保存”一项，因此我们不能多次重复使用同一个槽。 正确性依赖于总是贪婪地消耗最早可能的项目的插槽。

 ## 边缘情况

 当除第 n 天之外没有到最后一刻的访问天数时，算法不会累计`free_slots`直到最后，所以除了那些可以在最后一天配对的商品之外，所有较早的商品都会被支付。 这符合以下事实：所有商品最后只能分组一次，从而提供最大的折扣使用，但每个访问批次仍受一件免费商品的限制。 

当所有日子都是访问日时，`free_slots`永远不会用完，因此每件商品一出现就会被匹配。 该算法立即消耗插槽，这反映出每个数字都可以被吸收到未来的某个批次中，从而最大限度地降低成本。 

当访问日稀疏且较早集中时，时段会累积，但可能会在大指数出现之前被消耗掉。 贪婪消费确保小索引总是首先被分配，保留大索引用于以后的强制支付，这与最优结构相匹配，因为一旦配对容量可用，延迟小项目永远不会有帮助。
