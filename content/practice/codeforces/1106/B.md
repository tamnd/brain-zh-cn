 ## 解决方案

 ## 问题理解

 我们有一家餐厅，有多种菜肴。 每种类型都有当前库存和每道菜的固定价格。 顾客一个接一个地到来，每个顾客都会多次点特定类型的菜肴。 

对于每道请求的菜肴，如果仍有库存，餐厅会尝试提供请求的类型。 如果该类型为空，餐厅不会立即失败。 相反，它转而提供全球最便宜且仍有剩余库存的菜肴类型，从而打破了较小指数的束缚。 如果根本没有任何菜品，顾客会立即离开，即使某些菜肴已经上桌，该顾客的全部成本也为零。 

输出是每个客户在处理整个请求序列或在库存完全耗尽时提前停止后支付的总成本。 

关键的难点在于，每个请求可能很大，可达千万份，我们无法一一模拟每一道菜。 对于多达十万名顾客和十万种菜肴类型，重复搜索最便宜的可用菜肴的简单模拟会太慢。 

一种幼稚的方法还会在每次请求的类型用完时重复扫描成本最低的可用菜肴。 在最坏的情况下，每个回退查询都可以扫描所有类型，从而导致二次行为。 

当客户排序过程中库存完全耗尽时，就会出现微妙的边缘情况。 即使在筋疲力尽之前有些菜品已经上桌，总成本也必须被丢弃。 例如，如果客户请求大量商品，并且最后几个步骤耗尽了所有剩余库存，则最终答案为零，而不是部分总和。 

另一个棘手的情况是，当请求的类型变空并且最便宜的后备类型在每次服务后也会动态变化时。 幼稚的方法可能会错误地或过于频繁地重新计算最小值。 

## 方法

 暴力模拟一次处理每个顾客点的一道菜。 对于每个单位，我们检查所请求的类型是否有库存； 如果没有，我们会扫描所有类型以找到最便宜的可用类型。 这是正确的，但速度非常慢。 每个顾客最多可以点千万个菜品，每次扫描所有类型大约会得到$O(m \cdot d_j \cdot n)$，这是完全不可行的。 

关键的观察结果是，我们实际上并不需要单独处理每道菜。 重要的是在发生变化之前客户可以从固定来源连续获取多长时间：要么请求的类型用完，要么所有剩余库存耗尽。 

这建议将相同类型的连续服务分组，并使用始终提供当前最便宜的可用类型的数据结构。 按成本（以及打破平局的索引）排序的最小堆允许我们始终在对数时间内检索下一个后备类型。 我们还维护数组中的剩余计数并忽略过时的堆条目。 

对于每个客户，我们重复地从请求的类型或全球最便宜的可用类型中消费，但我们不是单步消费，而是批量消费：我们在一个块中获取尽可能多的数量，直到其中一个限制条件发生变化。 

关键的改进是，每次类型变空时，就不再使用它，因此每个类型都会有效地删除一次。 这确保堆操作受以下限制$O(n \log n)$全面的。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 |$O(m \cdot n \cdot \max d_j)$|$O(n)$| 太慢了 |
 | 最佳|$O((n + m)\log n)$|$O(n)$| 已接受 |

 ## 算法演练

 我们维持剩余库存`r[i]`, 成本`c[i]`，以及一个包含所有当前可用类型的最小堆，其键控为`(cost, index)`。 

对于每个客户，我们模拟他们的请求，同时跟踪他们是否已经因完全耗尽而“失败”。 

1.将当前客户的答案初始化为0和一个标志`dead = False`。 该标志记录客户是否遇到完全耗尽事件。 
2. 对于每一个`d_j`要求菜品：

 1.如果请求的类型`t_j`还有库存，直接上菜，减去一个单位`r[t_j]`。 费用正常添加。 
2. 如果是空的，我们必须找到最便宜的可用类型。 我们反复从堆中弹出，直到找到仍有库存的类型。 这种惰性删除避免了维护严格的堆结构。 
3. 如果不存在有效类型，则设置`dead = True`并完全停止处理该客户，因为进一步的服务没有任何贡献。 
4. 否则，提供所选后备类型的一个单位并减少其库存。 
5. 如果该类型变为零，则不会立即删除它； 相反，它会在未来的堆弹出中被忽略。 
3. 结束或提早休息后，如果`dead`为真，最终答案为0； 否则输出累计成本。 

堆清理工作缓慢的原因是每种类型仅从正库存转换到零一次，因此每种类型最多一次被从考虑中删除。 

### 为什么它有效

 在每一步中，该算法都会保留以下不变性：所有可用类型要么在堆中正确表示，要么安全地作为过时条目忽略。 在剩余库存为正的类型中，堆总是产生最便宜的当前有效类型。 由于每次服务都会减少一个单位的库存，并且类型一旦空就不会重新引入，因此无效堆弹出的数量受到类型总数的限制。 这保证了正确性，同时保持总操作对数。 

## Python 解决方案```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    c = list(map(int, input().split()))
    
    r = a[:]
    
    heap = []
    for i in range(n):
        heapq.heappush(heap, (c[i], i))
    
    for _ in range(m):
        t, d = map(int, input().split())
        t -= 1
        
        cost = 0
        dead = False
        
        for _ in range(d):
            if r[t] > 0:
                r[t] -= 1
                cost += c[t]
            else:
                while heap and r[heap[0][1]] == 0:
                    heapq.heappop(heap)
                
                if not heap:
                    dead = True
                    break
                
                price, idx = heap[0]
                r[idx] -= 1
                cost += price
        
        if dead:
            print(0)
        else:
            print(cost)

if __name__ == "__main__":
    solve()
```该代码保留了按成本排序的全局最小菜肴类型堆。 当请求的类型不可用时，它会通过重复从堆中删除空类型直到找到有效类型来解决回退问题。 

微妙的一点是懒惰删除条件`r[heap[0][1]] == 0`。 当项目达到零时，我们从不明确删除项目； 相反，我们仅在它们出现在顶部时才清理它们，这避免了昂贵的堆更新。 

每个客户的循环很简单：除非系统完全耗尽，否则它会累积成本，在这种情况下，它会立即输出零。

 ## 边缘情况

 一个关键的情况是，所请求的类型始终可用，直到最终单元，之后系统完全变空。 该算法正确地处理了这个问题，因为它在尝试回退后立即检查耗尽； 一旦堆为空，它就会停止并丢弃累积的成本。 

另一种情况是最便宜的类型动态变化，因为之前最便宜的类型用完了。 惰性堆清理确保仅在访问时删除过时的条目，因此该算法始终检索当前有效的最小值，而无需在每次递减期间进行显式更新。
