[CF 165B - 午夜燃烧的石油](https://codeforces.com/problemset/problem/165/B)

 **求解时间：** 1m 42s
 **已验证：** 是的

 ## 解决方案
 ## 问题理解

 瓦西亚至少要写`n`一晚上的代码行数。 他从生产力开始`v`，这意味着他写`v`第一次茶歇前排队。 每次休息后，他的工作效率都会下降`k`，使用整数除法。 

他写的总行数是：$$v + \left\lfloor \frac{v}{k} \right\rfloor + \left\lfloor \frac{v}{k^2} \right\rfloor + \cdots$$一旦下一项变为零，该过程就会停止。 我们必须找到最小的起始生产率`v`使得总的书写行数至少为`n`。 

约束足够大，以至于尝试一切可能的方法`v`天真地会太慢。`n`可以达到`10^9`，所以线性扫描`1`向上可能需要十亿次迭代。 即使每次迭代都很小，也远远超出了 2 秒的时间限制。 

总和的结构很重要。 作为`v`增加，写入的总行数永远不会减少。 较高的起始生产率总是至少能生产与以前一样多的生产线。 这种单调行为正是二分搜索适用的原因。 

有一些边缘情况可能会悄悄地破坏粗心的实现。 

考虑：```
1 2
```正确答案是：```
1
```有缺陷的实现可能会从以下位置开始二分搜索`0`当答案本身是最小可能值时，会错误地处理条件。 

另一个微妙的情况是当总和超过`n`早期的：```
59 10
```为了`v = 54`:$$54 + 5 = 59$$答案正是`54`。 如果实现计算像这样的幂`k^i`直接地，其他语言中可能会出现溢出或不必要的工作。 迭代除法更安全、更干净。 

一个更重要的场景是当`k`很小，特别是`2`:```
1000000000 2
```该序列包含许多非零项，因为除以`2`缓慢减少。 低效地反复重新计算大幂的解决方案可能会变得太慢。 预期的方法只需要对数多次除法。 

## 方法

 最直接的方法就是暴力破解。 我们可以尝试每个值`v`开始于`1`。 对于每个候选人，我们计算：$$v + \left\lfloor \frac{v}{k} \right\rfloor + \left\lfloor \frac{v}{k^2} \right\rfloor + \cdots$$直到项变为零。 第一个`v`其总和至少达到`n`就是答案。 

这是有效的，因为定义与问题陈述中的过程完全匹配。 问题在于规模。 在最坏的情况下，答案本身可能接近于`10^9`，因此一一检查候选人变得异常缓慢。 

关键的观察结果是，总的书写行数形成了一个单调函数：`v`。 

如果有一些值`v`足以完成程序，那么每个较大的值也足够了。 同样，如果一些`v`不足，每一个较小的值也不足。 

这将问题转换为答案空间上的经典二分搜索。 

我们不是测试每个值，而是搜索范围`[1, n]`。 对于每个中点`mid`，我们计算 Vasya 可以从以下位置开始写入多少行`mid`。 如果总数至少为`n`，那么答案就在左半部分，包括`mid`。 否则，我们向右移动。 

辅助计算本身是高效的。 每一项除以`k`，因此迭代次数只是对数`v`。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n log n) | O(n log n) | O(1) | O(1) | 太慢了 |
 | 最佳| O(log n × log n) | O(log n × log n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 定义辅助函数`enough(v)`计算 Vasya 从生产力开始可以写多少行`v`。 
2. 在辅助函数中，重复将当前生产率添加到运行总计中，然后将生产率除以`k`。 
3. 一旦生产率变为零就停止，因为所有后续项也将为零。 
4. 如果最终总数至少为`n`， 返回`True`。 否则返回`False`。 
5. 对范围运行二分查找`[1, n]`。 
6. 计算`mid = (left + right) // 2`。 
7. 检查是否`mid`使用辅助函数就足够了。 
8. 如果`mid`有效，将其记录为可能的答案并继续搜索左半部分。 我们这样做是因为我们想要最小有效值。 
9.如果`mid`不起作用，搜索右半部分。 
10. 继续，直到搜索间隔变空。 
11. 输出找到的最小有效值。 

### 为什么它有效

 正确性取决于单调性。 

让`f(v)`是从生产力开始写入的总行数`v`。 

总和中的每一项：$$\left\lfloor \frac{v}{k^i} \right\rfloor$$不减为`v`增加。 这意味着`f(v)`本身是不减的。 

因此存在一个边界点，其中小于答案的值是不够的，而大于或等于答案的值是足够的。 二分搜索总是正确地维护这个边界，并最终隔离出最小有效的`v`。 

辅助函数也是正确的，因为它直接模拟了问题中描述的生产力下降。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def enough(v, n, k):
    total = 0
    current = v

    while current > 0:
        total += current
        current //= k

    return total >= n

def solve():
    n, k = map(int, input().split())

    left, right = 1, n
    answer = n

    while left <= right:
        mid = (left + right) // 2

        if enough(mid, n, k):
            answer = mid
            right = mid - 1
        else:
            left = mid + 1

    print(answer)

solve()
```辅助函数遵循问题的准确生产过程。 开始于`v`，它不断添加当前的贡献并除以`k`每一步之后。 

使用迭代除法比计算能力更安全`k^i`。 一旦贡献变为零，循环自然停止。 

二分查找保持每个值都严格小于的不变量`left`已知是无效的，而每个大于的值`right`已经被处理或丢弃。 

搜索范围是`[1, n]`因为`n`本身总是足够的。 即使 Vasya 只写了最初的一批，之后什么也不写，从`n`线条明显有效。 

一个常见的差一错误是在找到有效的中点后更新错误的边界。 由于我们想要最小有效值，因此我们必须继续搜索左半部分：```
right = mid - 1
```另一个微妙的细节是在向左移动之前存储候选答案。 否则最终的有效中点可能会丢失。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(log n × log n) | O(log n × log n) | 二分搜索执行 O(log n) 次迭代，每个辅助调用需要 O(log n) 次除法 |
 | 空间| O(1) | O(1) | 仅使用了少数整数变量 |

 即使在最大约束下`n = 10^9`，二分查找只需要大约 30 次迭代。 每个辅助计算也最多执行大约 30 个除法`k = 2`。 总工作量很容易在时间限制内完成。

 ## 边缘情况

 考虑尽可能最小的输入：```
1 2
```二分查找开始于`left = right = 1`。 

为了`mid = 1`:$$1 + 0 = 1$$条件立即成功，因此答案变为`1`。 

这种情况证实了搜索边界已正确初始化，并且算法可以处理最小的有效答案而不会下溢。 

现在考虑：```
10 2
```正确答案是`6`。 

跟踪辅助计算：

 | 当前| 总计 |
 | ---| ---|
 | 6 | 6 |
 | 3 | 9 |
 | 1 | 10 | 10
 | 0 | 停止|

 总数正好达到`10`， 所以`6`是有效的。 一个常见的错误是使用`>`而不是`>=`检查充分性时。 该错误会错误地拒绝完全匹配。 

最后，考虑生产力几乎立即下降的情况：```
100 10
```为了`v = 91`:$$91 + 9 = 100$$下一项为零。 

此案例证实，一旦除法达到零，辅助函数就会正确停止，而不是永远继续或执行不必要的工作。
