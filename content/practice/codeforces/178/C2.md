 ## 解决方案
 ## 问题理解

 我们正在模拟一个支持插入和删除项的哈希表，但插入不是直接的。 每个项目都有一个由其哈希值给出的首选起始位置，如果该位置被占用，则表会以固定大小的跳跃向前探测`m`模数`h`直到找到一个空闲单元。 

我们需要的关键数量不是最终的放置，而是插入过程中的低效率。 每次算法在尝试放置新项目时检查已占用的单元格时，该检查都会被视为一次“虚拟调用”。 删除只是释放一个细胞，不会增加成本。 

因此，任务是处理一系列插入和删除操作，维护表的当前状态，并对插入期间进行的所有失败探测求和。 

该结构本质上是一个具有步长的圆形数组`m`，这意味着每次插入都会沿着模算术中的确定性循环进行，直到找到一个空槽。 

约束条件达到`2 * 10^5`操作和表大小`2 * 10^5`。 如果跨操作执行许多探测，则线性扫描直到每次插入找到空闲槽的简单模拟可能会降级为二次行为。 这将超出时间限制，因为每次插入都可能遍历表的很大一部分。 

一个微妙的一点是，删除很重要，因为它们可能会打开改变未来探测路径的漏洞。 另一个重要的细节是 id 对于插入来说是唯一的，因此我们可以在删除时将每个 id 直接映射到其当前位置。 

一个幼稚的错误是从头开始重新计算插入而不跟踪位置。 例如，如果我们不存储每个 id 的放置位置，则删除将变得不可能或需要搜索，这太慢了。 

当多个插入聚集在同一探测周期中时，会出现另一种失败情况。 例如，如果`h = 5`,`m = 2`，插入到哈希中`0, 0, 0, 0`会重复扫描同一个周期`0 → 2 → 4 → 1 → 3 → 0`，产生许多碰撞。 简单的方法可能会重复遍历相同的占用路径，从而导致二次成本。 

## 方法

 蛮力的想法很简单。 维护一个表示哈希表的数组。 每次插入，从hash值开始，一步步重复移动`m`模数`h`直到找到一个空槽，将遇到的每个被占用槽计数为虚拟调用。 找到空闲单元后，将项目放置在那里并将其位置存储在由 id 键控的字典中。 

这是正确的，因为它遵循精确的探测规则。 然而，其每次插入的最坏情况成本与成功之前遇到的占用单元的数量成正比。 如果表变得密集或者探测周期很长，单次插入可能会遍历`O(h)`职位。 超过`n`操作，这导致`O(nh)`行为，这对于`2 * 10^5`。 

关键的观察是我们不需要一步一步地对每个探针进行物理模拟。 重要的是：给定一个起始哈希，我们需要沿着固定的算术级数模找到第一个空位置`h`。 这成为“沿循环序列的下一个可用时隙”问题。 

我们可以维护每个单元格是否被占用。 关键的优化是，每个位置仅在它被占用以及我们在某些插入期间扫描它时才被访问。 我们通过向前移动直到找到空闲槽来确保每个占用的单元在 O(1) 摊余时间内被跳过，但我们必须避免重复地重新扫描长链。 

有效实现这一目标的标准方法是在更新状态时直接模拟探测，但确保每个单元格设置一次并清除一次。 由于每次插入仅填充一个单元格，而每次删除则释放一个单元格，因此每个单元格状态更改 O(1) 次。 每个成功的放置可能仍然需要遍历一条链，但在整个过程中，每个占用的单元格总共会被跳过有限次，因为一旦被填充，它就会保持阻塞状态直到被删除。 

这产生摊销线性解。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(nh) | O(h + n) | 太慢了|
 | 优化模拟| O(n + h) 摊销 | O(h + n) | 已接受 |

 ## 算法演练

 我们维护一个数组`table`尺寸的`h`，其中每个单元格存储`-1`(空) 或占用它的 id。 我们还维护一本字典`pos[id]`存储每个插入的 id 的当前位置。 

我们按顺序模拟操作。 

1.如果操作是删除`id`，我们查找它的位置`pos`，将该单元格标记为空`table`，并从地图中删除 id。 不进行探测，因此不会增加成本。 
2.如果操作是插入`(id, hash)`，我们从`cur = hash`。 
3.同时`table[cur]`被占用，我们将答案加 1 并移动`cur = (cur + m) % h`。 

每个这样的步骤都与虚拟探针完全对应，因为我们检查了占用的插槽。 
4. 当我们找到一个空单元格时，我们将 id 放在那里，存储`pos[id] = cur`，并标记`table[cur] = id`。 

重要的想法是我们永远不会从头开始探测，也永远不会进行全局搜索。 我们严格遵循问题定义的循环进程。 

### 为什么它有效

 在任何时刻，每个单元要么是空的，要么被一个 id 占据。 探测规则为每个插入定义了候选位置的确定性序列，除了通过占用之外，与过去的插入无关。 

我们的模拟准确地反映了该顺序。 每次我们在探测过程中遇到一个被占用的单元格时，我们都会正确地计算一次失败的尝试。 由于我们仅按照与规则相同的顺序停在第一个空单元格处，因此最终的位置与定义匹配。 

由于每个单元格在被释放之前仅被占用一次，因此指针经过单元格的每次转换都对应于真正的冲突事件，因此不会发生过度计数或计数不足的情况。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    h, m, n = map(int, input().split())
    
    table = [-1] * h
    pos = {}
    ans = 0

    for _ in range(n):
        parts = input().split()
        if parts[0] == '-':
            id_ = int(parts[1])
            idx = pos.pop(id_)
            table[idx] = -1
        else:
            id_ = int(parts[1])
            start = int(parts[2])

            cur = start
            while table[cur] != -1:
                ans += 1
                cur = (cur + m) % h

            table[cur] = id_
            pos[id_] = cur

    print(ans)

if __name__ == "__main__":
    solve()
```该实现保留一个直接数组用于占用，因此每个探测的时间复杂度为 O(1)。 字典`pos`确保删除是恒定的时间，避免任何搜索表的需要。 插入循环完全按照散列规则的要求进行，并且计数器每次碰撞都会增加一次。 

一个微妙的点是我们总是更新`cur`模数`h`，保留循环结构。 另一个细节是，删除不会直接影响探测成本，但对于正确性至关重要，因为它们会打开未来的插槽。

 ## 边缘情况

 步长为 1 的最小表强调最坏情况下的线性探测行为。 例如，在大小为 4 的表中，在同一散列处插入三个项目会导致每次插入时进行完全扫描。 该算法可以正确处理此问题，因为每个占用的单元格每次遇到时都会递增计数器一次，并且指针以表大小为模确定性地前进。 

第二个边缘情况是频繁删除，从而重新打开早期插槽。 即使槽被释放，未来的插入仍然可能会通过它，具体取决于起始哈希。 该算法在每个探测步骤中正确区分占用的细胞和空的细胞，因此一旦细胞被释放，后续的探针就会停止将其计数为碰撞。 

第三种边缘情况是当`m`和`h`不是互质的，产生的循环不覆盖整个表。 该算法仍然有效，因为探测严格在由`(t + i*m) % h`，并且由问题陈述保证终止，确保插入始终是可能的。
