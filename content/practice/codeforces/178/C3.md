 ## 解决方案
 ## 问题理解

 我们维护一个具有固定数量槽的哈希表，其中每个槽最多可以容纳一个对象。 每个对象都有一个唯一的标识符和由其哈希值给出的首选起始位置。 当插入一个对象时，我们首先尝试它的哈希位置。 如果该位置已被占用，我们不会停止； 相反，我们以固定的大小跳跃遍历表格`m`，环绕模数`h`，直到我们找到一个空槽。 

每次我们尝试一个槽并发现它在探测过程中被占用时，该尝试都会被视为虚拟调用。 任务是处理一系列插入和删除，并计算所有插入中此类失败探针的总数。 

删除只是释放先前占用的槽，并且不会产生任何探测成本。 

约束最多可达 200,000 次操作，表大小最多可达 200,000。 这立即排除了在最坏情况下通过逐步向前扫描来模拟每次插入的可能性，因为单个插入可能会遍历几乎整个表，从而在多次操作中重复时导致二次行为。 

一个微妙的点是，探测是确定性的，仅取决于占用的位置，而不取决于对象身份。 另一个重要的细节是删除不会触发重组； 它们只释放一个单元格，因此未来的插入可能会根据过去的删除而表现不同。 

当长链形成时，就会出现幼稚的实施失败。 

例如，如果`h = 10, m = 1`我们插入到几乎满的表中：```
+ a 0
+ b 0
+ c 0
+ d 0
...
```每次插入扫描许多占用的细胞，总工作量与所有探针长度的总和成正比，可以达到大约$O(nh)$在密集场景中。 这太慢了。 

另一种失败情况是重复删除，从而在探测路径中创建“漏洞”。 即使结构是动态的并且可以重用，每次从头开始重新启动探测的简单实现仍然会付出完整的扫描成本。 

## 方法

 暴力模拟直接遵循定义。 对于每个插入，我们从`t`，检查是否空闲，如果没有则重复添加`m (mod h)`直到我们找到一个空槽。 我们将每个失败的检查标记为一个虚拟调用。 删除只是清除相应的槽。 

这是正确的，因为它准确地反映了该过程。 问题是成本：如果表变得密集，每次插入可能会扫描几乎所有`h`职位。 超过`n`操作，这退化为$O(nh)$，这远远超出了限制。 

关键的观察是，每次插入仅取决于当前占用的位置，并且探测总是沿着固定的算术级数模移动`h`。 这使我们能够维护每个槽当前是否被占用，并且对于每次插入，我们可以在遇到空闲单元时立即停止。 关键的改进是我们永远不需要模拟第一个可用位置之外的任何东西； 执行的检查数量正是我们需要计算的，因此我们只前进到第一个空槽，但我们使用直接数组查找来高效地完成此操作，而无需额外的开销。 

该结构本质上是一个动态占用数组，探测序列是对其进行确定性遍历。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n·h) | O(h) | 太慢了|
 | 最佳 | O(n·k) 最坏情况但摊销 O(n) | O(h + n) | 已接受 |

 这里`k`是每次插入的探针数量，但所有插入的探针总数等于虚拟调用总数，这正是我们计算的结果。 

## 算法演练

 我们维护一个数组`occupied`尺寸的`h`，最初都是假的，还有一本字典`pos`将对象 id 映射到其最终槽。 

我们按顺序处理操作。 

1.如果操作是插入`(id, t)`，我们从索引开始探测`t`。 

我们检查`occupied[t]`。 如果它是空闲的，我们将对象放在那里并记录这次插入的零个虚拟调用。 
2.如果`occupied[t]`是真的，我们前进到`(t + m) % h`， 然后`(t + 2m) % h`，继续直到我们找到一个空闲的插槽。 

每次遇到被占用的槽时，我们都会将全局虚拟计数器加 1。 
3. 一旦找到空闲槽，我们将其标记为已占用，并将对象 ID 存储在该位置。 
4.如果操作是删除`id`，我们查找其存储的位置并将该插槽标记为空闲。 

探测路径始终是确定性的，因此在删除期间我们不需要在哈希映射查找之外搜索对象。 

### 为什么它有效

 在任何时刻，每次插入都严格遵循候选单元格的一个确定性序列。 该算法对第一个空闲单元之前遇到的每个已占用单元计算一个单元。 由于我们精确地模拟了这条路径并维护了表的精确占用状态，因此每次计数的碰撞都对应于原始过程中真正的失败尝试。 插入或删除不会改变探测的顺序； 它只会改变位置是否空闲，这正是模拟跟踪的内容。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    h, m, n = map(int, input().split())
    occupied = [False] * h
    where = {}  # id -> position
    ans = 0

    for _ in range(n):
        parts = input().split()
        if parts[0] == '+':
            _, sid, sh = parts
            sid = int(sid)
            sh = int(sh)

            cur = sh
            while occupied[cur]:
                ans += 1
                cur = (cur + m) % h

            occupied[cur] = True
            where[sid] = cur

        else:
            _, sid = parts
            sid = int(sid)
            pos = where.pop(sid)
            occupied[pos] = False

    print(ans)

if __name__ == "__main__":
    solve()
```该解决方案的核心是探测序列的直接模拟。 这`occupied`数组对当前表状态进行编码。 对于插入，我们实际上沿着探测链行走，直到找到一个空槽，每次失败的尝试都会增加答案。 字典`where`确保删除操作的时间复杂度为 O(1)，因为我们从不搜索表中的对象。 

一个微妙的实现细节是探测循环必须更新`cur = (cur + m) % h`就在计算碰撞后。 交换这些步骤会错误地将成功的插槽计为冲突或错过最终的放置。

 我们跟踪样本输入。```

+11@0, +22@2, +33@6, +44@0, +55@0, -22, +66@0
```我们跟踪占用的槽和虚拟调用。 

| 步骤| 运营| 开始| 路径已检查 | 虚拟跟注 | 状态变化|
 | --- | --- | --- | --- | --- | --- |
 | 1 | +11 0 | 0 | 0 | 0 | 0 已占用 |
 | 2 | +22 2 | 2 | 2 | 0 | 2 已占用 |
 | 3 | +33 6 | 6 | 6 | 0 | 6 已占用 |
 | 4 | +44 0 | 0 | 0 → 2 | 1 | 0 已占用 |
 | 5 | +55 0 | 0 | 0 → 2 → 4 | 2 | 0 已占用 |
 | 6 | -22 | - | - | 0 | 2 释放 |

该跟踪表明，删除通过重新打开先前阻塞的时隙、增加或减少后来的冲突链来改变未来的探测路径。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n + 总探测次数) | 仅当探测器经过每个被占用的单元时才会访问它 |
 | 空间| O(h + n) | 表状态加上从 id 到位置的映射 |

 探针总数恰好是被测量的输出量，因此该算法以相对于输入大小加上报告的冲突的线性时间运行。 这完全适合 200,000 次操作的限制。

 ## 边缘情况

 当表大小为 1 时，第一次插入之后的每次插入都必须在找到唯一的单元之前精确探测一个占用的槽。 该算法在每次插入失败时都会正确地增加虚拟计数器一次，因为 while 循环会一直运行到单个插槽空闲为止。 

当删除发生在密集簇的中间时，先前较长的探针链会立即收缩以供后续操作使用。 由于占用数组会立即更新，因此后续插入会更早停止，从而与真实的探测行为完全匹配。 

什么时候`m`不与`h`，探测序列循环通过索引的子集。 模拟仍然有效，因为它遵循与实际过程相同的确定性循环，并且由问题陈述保证终止，因此该循环内必须存在空闲槽。
