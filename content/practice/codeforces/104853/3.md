 ## 解决方案
 ## 问题理解

 我们有一个由多个地下城组成的游戏世界，每个地下城都包含一个具有固定强度值的怪物。 玩家从初始力量开始，可以以任何顺序进入任何地下城。 只有当玩家当前的力量严格大于怪物的力量时才能清除地下城。 击败怪物后，玩家的力量会增加该怪物的力量，并且地下城会变空。 

目标不仅仅是击败地下城中的最终boss`n`，但这样做的同时尽量减少总战斗次数。 每场战斗在发生时都必须是可获胜的，因此排序本身必须遵守当前强度始终严格大于所选怪物的约束。 

如果根本无法击败 Boss，则输出为零，或者描述所有选定战斗执行顺序的一系列地下城索引，最后一个元素强制为`n`。 

约束条件`n ≤ 100000`立即排除任何基于排列的搜索。 任何试图探索所有可能订单中哪怕一小部分的解决方案都会发生组合爆炸。 这将我们推向贪婪或基于排序的构造，可能使用维护当前可达选择的数据结构。 

一个关键的微妙之处是，我们没有被要求最大化力量或最小化总时间，而是特别要求最小化战斗次数。 这改变了通常贪婪的直觉：我们可以跳过可选的地下城，并且我们只想选择到达老板所必需的地下城。 

典型的失败案例来自于总是选择最小的可用怪物或总是选择最大的怪物。 比如，如果忽视早期的小怪，我们可能永远也达不到boss所要求的门槛。 相反，如果我们尽早贪婪地挑选大型怪物，我们可能会阻碍自己达到中间所需的阈值。 

另一个重要的边缘情况是 Boss 本身最初就已经太强了。 如果`x ≤ a[n]`，那么不存在序列，因为如果不赢得战斗，力量永远不会增加，并且每次战斗都需要严格更大的力量。 

## 方法

 暴力解释将尝试地下城的所有可能子集以及其中的所有有效顺序。 对于每个排列，我们模拟战斗并检查 Boss 是否可达以及战斗次数是否最少。 即使将我们限制在可行的序列中，排列的数量也是`n`，甚至修剪无效状态也不能防止指数爆炸。 

问题的结构暗示了一个可达性过程：根据当前的强度，我们可以“解锁”所有比它弱的怪物，击败一个怪物会增加强度，可能会解锁更多怪物。 这类似于经典的贪婪增长过程，其中可用操作随着状态的增加而扩展。 

关键的见解是，一旦地下城变得可访问，按照怪物强度递增的顺序来考虑它总是有益的。 如果我们总是击败当前最弱的怪物，我们就能尽快最大化未来的可访问性。 然而，由于我们还希望确保最终能够通过最少的战斗到达 Boss，因此我们必须小心地仅包含那些实际上有助于提高可达性的战斗`a[n]`。 

这将问题变成了重复获取最小的可用怪物的过程，但仅限于当前严格小于我们的力量的怪物，同时随着力量的增加动态添加新的可到达的地下城。 所有候选人的最小堆在这里自然起作用。

 | --- | --- | --- | --- |
 | 蛮力 | O(n!) | O(n) | 太慢了 |
 | 贪婪堆 | O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 我们将除 Boss 之外的所有地下城视为候选地牢，并维护当前可以击败的地下城。 

1. 对所有地下城进行排序，除了`n`以怪物的力量。 这使我们能够随着我们实力的增强逐步揭示可用的内容。 
2. 初始化电流强度为`x`，并在排序列表上维护一个指针，将所有怪物强度严格小于当前强度的地下城添加到以强度为键的最小堆中。 
3.反复检查boss副本是否存在`n`已经是可以打败的了。 如果当前强度大于`a[n]`，我们可以在确保所有选择的中间步骤有效后完成。 
4. 虽然 Boss 尚未被击败，但我们反复从堆中取出最小的可用地下城。 如果堆是空的，则不可能取得进一步的进展，因此无法到达 Boss。 
5. 对于每个选定的地下城，我们将其索引添加到答案中，并通过其怪物强度来增加当前强度。 
6. 每次增加后，我们将新解锁的地下城（其强度现在小于当前强度）推入堆中。 
7.继续，直到可以到达boss，然后追加地牢`n`作为最后一步。 

我们总是选择最小的可用怪物的原因是，尽早增加力量可以更快地进入更多未来的地下城，从而最大限度地减少到达 Boss 之前所需的中间步骤的数量。 

### 为什么它有效

 每时每刻，算法都保持不变，即堆中恰好包含在当前强度下当前可击败的地下城。 任何不在堆中的地下城要么已经被使用过，要么仍然太强大而无法击败。 选择最小的可用怪物可确保力量的增长尽可能渐进，同时仍然严格增加可达性。 任何替代选择要么不会提高可达性，要么会提前消耗掉更大的怪物，这永远不会减少解锁 Boss 条件之前所需的步骤数。 这确定了该进程以最少数量的可达状态扩展到达了boss。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

import heapq

n, x = map(int, input().split())
a = list(map(int, input().split()))

boss = a[n - 1]

# If we already cannot beat boss, impossible
if x <= boss:
    print(0)
    sys.exit()

# prepare other dungeons
arr = []
for i in range(n - 1):
    arr.append((a[i], i + 1))

arr.sort()

heap = []
res = []
i = 0
cur = x

while True:
    # push all newly reachable dungeons
    while i < n - 1 and arr[i][0] < cur:
        heapq.heappush(heap, arr[i])
        i += 1

    # if boss is now reachable, finish
    if cur > boss:
        break

    if not heap:
        print(0)
        sys.exit()

    val, idx = heapq.heappop(heap)
    res.append(idx)
    cur += val

# append boss
res.append(n)

print(len(res))
print(*res)
```该实现准确地反映了贪婪过程。 排序数组与指针相结合，确保我们只在每个地下城变得可达时插入一次。 堆保证我们总是选择最小的可用怪物，这对于控制力量的增长速度至关重要。 

一个微妙的点是严格的不平等`cur > boss`。 平等是不够的，因为老板严格要求更大的力量。 这种情况在早期不可能检查和终止期间都会出现。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n log n) | O(n log n) | 排序一次，每个地牢进入和离开堆一次 |
 | 空间| O(n) | 堆、数组和结果序列的存储 |

 最多 100000 个元素的约束使这种复杂性变得非常高效。 每个操作都是活动地牢数量的对数，并且每个地牢被处理恒定的次数。

 ## 边缘情况

 当boss一开始就已经太强时，算法会立即退出，因为再多的战斗也无法降低boss强度要求。 支票`x <= boss`在任何处理开始之前捕获此信息。 

当所有怪物与初始强度相比非常弱时，堆立即变大，并且算法可能会处理许多可选的战斗。 贪婪的命令仍然有效，因为每次战斗都是有效的，力量只会增加，永远不会使未来的选择无效。 

当除一个之外的所有怪物都比初始强度更强时，算法会正确停止，直到第一个可到达的怪物按排序顺序出现。 一旦被击败，级联解锁就会通过堆插入自然发生，确保只有在逻辑上可能的情况下才能继续进行。 

当不存在序列时，堆变空，而 Boss 仍然无法访问。 该状态直接对应于可达空间中的死胡同，并且算法正确终止而不会尝试无效的移动。
