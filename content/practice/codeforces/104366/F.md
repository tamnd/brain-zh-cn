 ## 解决方案
 ## 问题理解

 我们正在模拟一个随时间变化的聊天组。 人们要么加入群组，要么发送消息，并且群组有严格的规则，可以强行删除成员。 

第一条规则是容量限制。 该群组最多可容纳 N 人。 如果在群组已满的情况下有新人尝试加入，则当前群组中的成员将被移除以腾出空间。 该问题指定被删除的用户是所有当前成员中最近活动时间最长的用户，这意味着最近最不活跃的用户被驱逐。 

除此之外，还有第二条更为激进的规则。 如果任何成员在长度为 T 的滑动时间窗口内发送 K 条消息（从上次加入时间算起并包括两个端点），他们将立即被踢出。 重要的是，加入会重置该人的计数窗口，因为仅考虑其最近加入之后的消息。 

每次加入都会自动生成一条名为“hello”的消息，因此新加入的成员总是会立即收到至少一条消息。 

输入是按时间顺序排列的事件流。 对于每个活动，我们要么看到一个人加入，要么一个人发送消息。 如果该人在事件时间之前当前在群组中，则该事件是一条消息； 否则它是一个连接。 任务是处理所有事件，按时间顺序输出每个踢出的成员，最后输出剩余的成员。 

约束范围最多可达 100 万个事件和 100 万个用户，时间值最多可达 10 亿。 这立即排除了任何扫描每个事件的所有成员或使用朴素数据结构维护每个成员滑动窗口的方法。 任何重复迭代活跃成员的解决方案在最坏的情况下都会退化为二次行为并失败。 

一个微妙的困难在于两个驱逐规则之间的相互作用。 用户可能因为与其他人相比不活动（容量规则）或因为时间窗口规则中的垃圾邮件而被删除。 另一个棘手的方面是加入会重置消息窗口，这会使旧消息历史记录无效并使朴素前缀计数不正确。 

经常破坏简单实现的一个小边缘情况是重复的加入-踢-重新加入行为。 假设用户在时间 1 加入，快速发送 K 条消息，被踢出，稍后重新加入。 只有第二次加入之后的消息才重要，并且之前的历史记录不得泄漏。 

## 方法

 暴力模拟将维护组成员的完整列表，并且对于每个事件，如果需要删除，则重新计算最近最不活跃的成员。 对于每个消息事件，我们还将通过扫描每个用户的完整历史记录或所有事件来重新计算每个用户在最后 T 时间窗口内拥有的消息数量。 在最坏的情况下，M个事件中的每一个都可以触发扫描所有N个用户，并且每个用户最多可以维护M条消息。 这导致了 O(MN) 量级的复杂性，这对于一百万个事件来说远远超出了可行的范围。 

关键的观察结果是，这两个规则仅取决于最近的活动：容量驱逐的最新消息时间和垃圾邮件驱逐的滑动窗口计数。 这表明维护紧凑的每个用户状态而不是完整的历史记录。 

对于每个用户，我们只需要他们的最后一次加入时间、该加入后的消息时间戳双端队列以及他们的最新活动时间。 那么容量规则就变成了始终提取活跃用户中最小“最后活动时间”的问题。 这是一个经典的优先级队列用例，但由于活动时间发生变化而导致更新延迟。 

对于滑动窗口约束，我们不是存储所有消息，而是为每个用户维护一个队列，并丢弃早于当前时间减去 T 的时间戳。这确保每条消息最多插入和删除一次，从而实现摊销 O(1) 维护。

总之，这导致系统中每个事件由于堆更新而以对数时间处理，而每个用户队列总体上保持线性。

 | 最佳 | O(M log N) | O(M log N) | O(M)| 已接受 |

 ## 算法演练

 我们维持三个核心结构。 活动成员的字典，每个用户的消息时间戳双端队列，以及按上次活动时间排序的用于驱逐决策的堆。 

每个事件的处理如下。 

1. 如果用户当前不在组中，我们将该事件视为加入。 我们为它们分配一个加入时间戳，并使用代表自动“hello”消息的单个条目初始化它们的消息队列。 我们还将它们的最后活动时间设置为连接时间，并将它们推送到以此值作为键的堆中。 这确保了他们立即被视为积极做出驱逐决定。 
2. 如果在处理连接之前组已满，我们会重复从堆中删除最后活动时间最小的用户，直到找到活动集中仍然有效的用户。 该用户已被踢出。 我们记录驱逐时间并将其标记为非活动状态。 堆可能包含过时的条目，因此我们在使用弹出的元素之前验证成员身份。 
3. 如果用户已在组中，则该事件是一条消息。 我们将时间戳附加到它们的消息双端队列中，并将它们的上次活动时间更新为当前时间，将新条目推送到堆中。 
4. 每次插入消息后，我们都会强制执行滑动窗口规则。 我们从双端队列的左侧删除落在区间 [t - T, t] 之外的时间戳。 如果剩余消息数达到K以上，则立即将用户踢出。 我们记录该事件并将其从活动集中删除。 
5. 当用户因任何原因被踢出时，我们会将其标记为非活动状态。 在提取过程中，它们的任何未来堆条目都将被忽略。 

关键思想是堆条目永远不会被显式删除。 相反，我们依靠延迟删除来检查弹出条目时用户是否仍然处于活动状态。 

### 为什么它有效

 该算法保持了这样一个不变式：每个活动用户在堆中都至少有一个条目反映他们最近的活动，并且他们的消息双端队列恰好包含自上次加入以来的消息。 由于两种驱逐规则仅依赖于这两条信息，因此不需要历史数据。 即使存在多个过时的活动记录，惰性堆清理也能保证正确性，因为在选择逐出候选者时仅考虑每个用户的最新有效状态。 

## Python 解决方案```python
import sys
import heapq
from collections import deque

input = sys.stdin.readline

def solve():
    N, M, T, K = map(int, input().split())

    active = set()
    last_join = {}
    last_activity = {}
    msgs = {}

    # (last_activity_time, user)
    heap = []
    events = []
    kicks = []

    def kick(user, t):
        if user in active:
            active.remove(user)
            kicks.append((t, user))

    for _ in range(M):
        t, p = map(int, input().split())

        if p not in active:
            # join
            if len(active) >= N:
                while heap:
                    time, u = heapq.heappop(heap)
                    if u in active and last_activity[u] == time:
                        kick(u, t)
                        break

            active.add(p)
            last_join[p] = t
            msgs[p] = deque([t])  # hello message
            last_activity[p] = t
            heapq.heappush(heap, (t, p))

        else:
            # message
            msgs[p].append(t)
            last_activity[p] = t
            heapq.heappush(heap, (t, p))

            # sliding window
            dq = msgs[p]
            while dq and dq[0] < t - T:
                dq.popleft()

            if len(dq) >= K:
                kick(p, t)

    print(len(kicks), len(active))
    for t, u in kicks:
        print(t, u)
    print(*sorted(active))

if __name__ == "__main__":
    solve()
```实现的重点是将会员跟踪与排序逻辑分开。 这`active`set 提供 O(1) 成员资格检查。 堆按最后一个活动存储候选逐出顺序，但由于同一用户存在多个更新，因此我们根据当前活动验证每个堆条目`last_activity`。 

每个用户的双端队列对于滑动窗口约束至关重要。 它确保我们只存储相关的时间戳，并且每个时间戳都被推送和弹出一次。 

kick 功能集中了删除逻辑，因此容量和垃圾邮件规则都使用相同的状态转换。 

一个微妙的点是，我们总是更新每条消息的堆，即使旧条目仍然存在。 这就是实现延迟删除并避免昂贵的堆更新的原因。

 ## 边缘情况

 一种重要的边缘情况是重复的连接重置行为。 用户加入，建立消息历史记录，被踢出，然后重新进入。 该算法通过在每次连接时重置双端队列来处理此问题，确保永远不会考虑旧消息。 

另一个边缘情况是陈旧的堆条目。 用户在堆中可能有多个过时的活动时间戳。 惰性验证步骤仅确保条目匹配`last_activity`有效，因此过时的条目将被忽略，而不影响正确性。 

最后一个微妙的情况是在一条消息之后同时满足两个驱逐规则。 该算法始终在更新消息后立即检查滑动窗口规则，并在任何进一步的容量决策之前应用删除，以确保一致的状态转换。
