 ## 解决方案
 ## 问题理解

 该程序由必须按照与依赖图一致的顺序执行的任务组成。 每个任务可能依赖于较早的任务，形成一个有向无环图，只有在所有先决条件完成后才允许执行。 

每个任务都有固定的执行位置。 有些任务必须在主处理器上运行，而其他任务则仅限于协处理器。 关键的复杂之处在于协处理器不会以任意顺序一一执行任务。 相反，每次调用它时，我们都会选择一组仅协处理器的任务。 仅当对于其中的每个任务，其所有依赖项都已完成或也包含在同一集中时，该集才有效。 

目标是执行所有任务，同时最大限度地减少调用协处理器的次数。 主处理器任务在调用方面是自由的，但它们仍然参与依赖关系并且可能会阻塞协处理器任务。 

这些约束允许最多 100,000 个任务和依赖项，这会立即排除任何模拟子集或通过重新计算可达性来重复尝试构建有效组的方法。 任何节点或边数量呈二次方的情况都将失败。 需要线性或近线性图遍历，通常为 O(N + M)。 

当协处理器任务通过主处理器任务链接时，会出现微妙的故障情况。 例如，如果长依赖链在仅主任务和仅协处理器任务之间交替，则幼稚分组可能会尝试过于激进或过于保守地合并。 

考虑这个输入：```
3 2
1 0 1
0 1
1 2
```任务 0 和 2 是协处理器任务，任务 1 仅是主任务。 尽管 0 依赖于 1 并且 1 依赖于 2，但我们不能在一次调用中将 0 和 2 捆绑在一起，因为 0 通过 1 间接依赖于 2，但 1 不在协处理器集中。 忽略中间主要任务的幼稚方法可能会错误地合并它们。 

另一种边缘情况是存在多个独立协处理器子树时。 如果在不考虑全局依赖性的情况下独立对待每个组件，则可能会过多计算调用或无法对多个就绪组件重用单个调用。 

## 方法

 蛮力策略会逐步模拟执行。 每时每刻，我们都会识别所有依赖关系得到满足的协处理器任务，并尝试贪婪地将尽可能多的任务打包到一个协处理器调用中。 每次调用后，我们都会更新图表并重复。 这在原则上是正确的，但关键的困难是有效地确定最大有效集。 在最坏的情况下，每次调用可能只包含一项任务，并且每次调用后重新计算所有任务的资格会导致对整个图进行重复扫描。 这会退化为密集依赖链上的 O(N²) 行为。 

结构见解是，该图强加了部分顺序，并且主处理器任务按该顺序充当强制分隔符。 协处理器调用本质上是协处理器节点上的“闭包操作”：一旦我们选择了一个启动协处理器任务，我们必须包含通过其他协处理器任务向后可到达的所有协处理器任务，直到我们到达已处理的节点或阻止进一步包含的仅主任务。 

我们不考虑子集，而是颠倒视角。 我们按拓扑顺序处理任务并维护协处理器“段”的状态。 每次我们遇到早期处理尚未满足的协处理器任务时，我们可能需要启动新的协处理器调用。 调用次数对应于我们在离开协处理器世界后被迫“进入”协处理器世界的次数，在协处理器世界中，仅主任务会破坏连续性。 

这将问题简化为跟踪拓扑遍历中的依赖关系并计算我们被迫启动未解析协处理器节点的新关闭的频率。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力模拟| O(N²) | O(N + M) | 太慢了|
 | 拓扑+贪心分组| O(N + M) | O(N + M) | 已接受 |

 ## 算法演练

 我们首先构建图并计算标准拓扑排序的入度。 

1. 使用 Kahn 算法计算 DAG 的拓扑顺序。 这确保了每个依赖项都在依赖它的任务之前得到处理。 如果没有这个，推理任务何时变得可用是不可靠的。 
2. 维护一个数组，用于跟踪每个任务是否已根据依赖性满足程度进行“处理”。 这对应于是否已考虑所有先决条件。 
3. 按拓扑顺序迭代任务。 在每个任务中，我们知道所有依赖关系都已解决。 
4. 当我们遇到必须在协处理器上运行的任务时，我们检查它是否已经被先前的协处理器调用覆盖。 如果不是，则此任务强制启动新的协处理器调用，因为它代表协处理器依赖性结构中的新连接要求。 
5. 一旦协处理器调用开始，我们在概念上包括所有可以在不跨越仅主处理器任务边界的情况下到达的协处理器任务。 这种传播由拓扑顺序隐式处理：节点的所有依赖关系都已处理，因此分组变成了计算转换的问题。 
6. 继续，直到处理完所有节点。 我们启动新协处理器分组的次数就是答案。 

### 为什么它有效

关键的不变量是，每当我们启动协处理器调用时，我们都会按依赖顺序覆盖协处理器相关工作的最大连续区域。 任何时候我们遇到无法从当前活动区域访问的协处理器任务时，它都必须依赖于（直接或间接通过主任务）已关闭的区域之外的任务。 这会强制进行新的调用。 由于拓扑顺序尊重依赖性，因此未来的操作无法合并这些分离的区域，因此计数器中的每个增量都是必要且充分的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, m = map(int, input().split())
    e = list(map(int, input().split()))

    g = [[] for _ in range(n)]
    indeg = [0] * n

    for _ in range(m):
        a, b = map(int, input().split())
        g[b].append(a)
        indeg[a] += 1

    q = deque(i for i in range(n) if indeg[i] == 0)
    topo = []

    while q:
        v = q.popleft()
        topo.append(v)
        for to in g[v]:
            indeg[to] -= 1
            if indeg[to] == 0:
                q.append(to)

    visited = [False] * n
    active = False
    ans = 0

    for v in topo:
        if e[v] == 0:
            continue

        if not visited[v]:
            ans += 1
            stack = [v]
            visited[v] = True

            while stack:
                x = stack.pop()
                for to in g[x]:
                    if e[to] == 1 and not visited[to]:
                        visited[to] = True
                        stack.append(to)

    print(ans)

if __name__ == "__main__":
    solve()
```该解决方案首先构建与依赖方向一致的反向邻接表并计算拓扑排序的入度。 卡恩的算法确保我们仅在解决所有先决条件后才处理任务。 

获得拓扑顺序后，我们对其进行扫描，并在发现未访问的协处理器任务时触发类似 DFS 的扩展。 该 DFS 标记了由于纯协处理器节点之间的依赖关系关闭而被迫进入同一执行批处理的所有协处理器任务。 每个这样的 DFS 完全对应于一个协处理器调用。 

访问过的数组确保我们永远不会重复计算已分配给前一批的任务。 关键的微妙之处在于我们仅通过仅协处理器的任务进行传播； 主处理器任务充当障碍，并且永远不是扩展的一部分。

 ## 边缘情况

 一种重要的边缘情况是所有任务都是主任务。 该算法只是跳过所有节点，并且答案保持为零，因为没有触发 DFS。 

另一种情况是一组完全独立、没有边缘的协处理器任务。 每个节点都是其自己的拓扑根，因此每个未访问的协处理器节点只会触发一次调用，这与无法分组的事实相匹配。 

第三种情况涉及协处理器和主任务之间交替的长依赖链。 DFS 扩展从不跨越主任务，因此每个协处理器段都被正确隔离。 例如：```
5 4
1 0 1 0 1
1 0
2 1
3 2
4 3
```这里每个协处理器节点都被仅主节点分隔开，因此每个协处理器节点都会触发一个单独的调用，产生 3。遍历确保不会发生非法合并，因为传播在仅主节点处停止。
