 ## 解决方案
 ## 问题理解

 我们有一排篮子，每个篮子都有固定的最大容量。 在连续几天的时间里，苹果每天都会被收获并分配到一个篮子里。 当苹果放入篮子时，篮子永远不能超过其容量。 任何溢出都会被丢弃，并且不会进入任何其他影响状态的篮子或未来结构。 

处理完前 D 天后，每个篮子都有一些当前的存储量，这只是到目前为止分配给它的苹果总数，以其容量为上限。 主要任务是回答以下形式的查询：D 天之后，当前存储在索引 L 到 R 的篮子中的苹果总数是多少。 

因此，问题从根本上讲是关于维护一个随时间演化的数组，其中每次更新都会影响单个位置，但该位置的值不是线性累积，而是一个饱和函数：它随着累积添加而增长，直到达到固定上限。 

这些限制迫使我们仔细思考更新和查询如何交互。 对于多达 100,000 个篮子、100,000 天和 100,000 个查询，任何针对每个查询从头开始重新计算篮子状态的方法都会太慢。 每个查询的简单重新计算将花费 O(N) 每个查询，在最坏的情况下导致 10^10 次操作，这在 1 秒限制下是不可行的。 

一个更微妙的问题是，每天只影响一个篮子，但影响取决于历史。 一旦篮子达到其容量，对其进行进一步更新不会改变其价值。 这种非线性是关键的复杂性。 

一些边缘案例暴露了常见的错误。 如果篮子已经满了并且收到了更多的苹果，则不会有任何变化。 例如，如果容量为 5，当前为 5，则添加 10 使其保持为 5，而不是 15。另一个微妙的情况是，多个更新部分填充了篮子，但后来又使其饱和； 中间查询取决于 D 天是否已经饱和。 

最后，查询取决于时间前缀，而不是固定的最终状态，因此我们无法预先计算单个数组并直接回答所有查询。 

## 方法

 蛮力方法很简单。 对于每个查询，模拟直到 D 天的所有 M 天，维护一个篮子内容数组，完成后，在 L 到 R 范围内求和。每天都会更新一个带有上限添加的篮子，因此每个查询的模拟成本为 O(D + N)。 经过 Q 个查询后，这变成了 O(QM + QN)，在最坏的情况下大约是 10^10 次操作，太慢了。 

关键的观察是更新是单调的和本地化的。 每天仅更改一个篮子，并且该更改的影响可以表示为篮子当前值的增量。 如果我们在支持范围求和查询的数据结构中维护每个篮子的当前值，我们就可以按顺序处理天并离线回答查询。 

我们不是重新计算每个查询的答案，而是扫描从 1 到 M 的天数。我们维护所有篮子的当前状态。 每天之后，我们只更新一个篮子，但我们将这一更新转化为支持篮子前缀和的全局结构中的增量变化。 然后，所有具有当天索引的查询都可以立即得到答复。 

这将问题转化为使用 Fenwick 树或线段树对篮子索引进行离线扫描。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(Q·(M + N)) | O(Q·(M + N)) | O(N) | 太慢了 |
 | 使用 Fenwick 树进行离线扫描 | O((M + Q) log N) | O((M + Q) log N) | O(N) | 已接受 |

 ## 算法演练

 我们为每个篮子维护两个关键的状态：到目前为止分配给它的累计苹果总数，以及受其容量限制的实际存储值。 我们还在存储当前存储值的篮子索引上维护一个芬威克树。

我们按升序处理日期，并维护按日期 D 分组的查询答案。 

### 步骤

 1.初始化一个数组`sum[i] = 0`对于分配到篮子 i 的累积苹果，以及`cur[i] = 0`对于当前存储的苹果。 

我们还初始化索引 1 到 N 的 Fenwick 树，最初全为零。 
2. 按 D 值对所有查询进行分组。 对于每一天 D，我们都会知道当时哪些查询可以回答。 
3. 迭代从 1 到 M 的天数。对于第 t 天，我们得到一个更新 (b_t, a_t)。 
4. 在应用更新之前，计算篮子b_t的当前存储值，即`cur[b_t] = min(cap[b_t], sum[b_t])`。 
5.增加新收获：更新`sum[b_t] += a_t`。 
6. 计算新的存储值`new_cur = min(cap[b_t], sum[b_t])`。 
7. 计算增量`delta = new_cur - cur[b_t]`。 如果 delta 非零，则将其应用于 Fenwick 树的位置 b_t 并设置`cur[b_t] = new_cur`。 

这样做的原因是，只有实际存储的数量对查询很重要，并且芬威克树维护这些存储值的总和。 
8. 处理完第 t 天后，通过查询 Fenwick 树以获得 [L, R] 上的范围总和来回答所有 D = t 的查询。 

### 为什么它有效

 关键的不变量是，在处理第 t 天之后，芬威克树准确地存储了 t 更新后当前购物篮内容的向量。 树中的每个篮子值等于`min(cap[i], total apples assigned to i up to t)`。 

每次更新仅影响一个篮子，并且我们仅应用其先前上限值和新上限值之间的差值。 由于所有其他篮子保持不变，芬威克树始终与真实状态保持同步。 因此，对树的任何范围总和查询都与 D 天之后该区间内的苹果总和完全匹配。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, m, q = map(int, input().split())
    cap = [0] + list(map(int, input().split()))

    events = [None] * (m + 1)
    for i in range(1, m + 1):
        b, a = map(int, input().split())
        events[i] = (b, a)

    queries_by_day = [[] for _ in range(m + 1)]
    for idx in range(q):
        d, l, r = map(int, input().split())
        queries_by_day[d].append((l, r, idx))

    fenw = Fenwick(n)
    total = [0] * (n + 1)
    cur = [0] * (n + 1)

    ans = [0] * q

    for day in range(1, m + 1):
        b, a = events[day]

        old = min(cap[b], total[b])
        total[b] += a
        new = min(cap[b], total[b])

        if new != old:
            fenw.add(b, new - old)
            cur[b] = new

        for l, r, qi in queries_by_day[day]:
            ans[qi] = fenw.range_sum(l, r)

    sys.stdout.write("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```芬威克树是这里的中心结构。 每个位置在封盖后将当前实际的苹果存储在该篮子中。 更新步骤仅仔细计算新一天的添加引起的变化，确保我们永远不会重建结构。 

一个常见的实现错误是忘记在更新累积和之前重新计算先前的上限值。 在不减去旧值的情况下，芬威克树将累积原始总和而不是上限值，一旦篮子达到容量，这就会破坏正确性。

 ## 边缘情况

 一种重要的边缘情况是，篮子通过多个步骤精确达到容量，然后又收到更多添加。 该算法确保一旦`total[b] >= cap[b]`，进一步的更新产生零增量，因此芬威克树保持稳定。 例如，如果容量为 10，更新为 +6、+4、+100，则只有前两次更新会产生有意义的更改。 

另一个微妙的情况是当篮子开始满并立即接收更新时。 在那种情况下，`old = new = cap[i]`，因此不会将任何更新推送到 Fenwick 树，从而防止人为通货膨胀。 

最后，自然地处理要求第 1 天或第 M 天边界的查询，因为查询是按精确的日期索引分组的，并在处理当天的更新后立即得到答复，从而确保更新应用程序和查询解析之间不会出现相差一位的转变。
