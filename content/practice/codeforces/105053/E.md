 ## 解决方案
 ## 问题理解

 我们得到了一份涉及 N 个客户的按时间顺序排列的事件日志。 每个顾客进入餐厅时只出现一次，离开餐厅时也只出现一次。 输入将其编码为有符号整数序列，其中正值表示客户进入，负值表示客户离开。 

该日志的背后是一个隐藏的结构：每个客户必须被分配到两条线路之一，例如 G 线或 S 线。当客户进入时，他们会加入指定线路的后面。 当给定类型的煎饼堆被送达时，它总是送到相应队列中最近到达的顾客手中，这意味着该队列的行为就像一个后进先出的堆栈。 因此，出发顺序必须与两个独立的堆栈一致，每条线一个。 

任务是确定我们是否可以将每个客户分配到两条线路之一，以便当我们模拟到达并始终在出发事件时从正确的堆栈中弹出时，观察到的出发顺序是有效的。 如果可能，我们将输出任何有效的客户分配给 G 或 S。否则，我们输出一个星号。 

约束 N ≤ 1000 意味着序列长度最多为 2000 个事件。 这立即排除了对 2^N 种可能性的分配的任何指数搜索。 接近 O(N^2) 或 O(N log N) 的解决方案就足够了。 

当在不考虑未来冲突的情况下进行贪婪分配时，就会出现微妙的失败情况。 例如，如果两个客户以嵌套方式在时间上重叠，并且它们的退出错误地交错，则任意分配它们可能会导致所需的弹出来自堆栈的非顶部元素的情况，这是不可能的。 

一个具体的问题模式是交叉依赖。 假设顾客1进入，然后顾客2进入，然后顾客1离开，然后顾客2离开。 如果我们将两者分配给同一个堆栈，那么这是可行的。 但如果我们将 1 分配给 G，将 2 分配给 S，则两个堆栈都独立地满足约束。 然而，如果我们在更复杂的嵌套中反转出发顺序，如果我们错误地分割客户，我们可能会强制实现不可能的堆栈行为。 

关键的困难在于每个堆栈在其指定的时间间隔内强制执行后进先出约束，并且我们必须对客户进行分区，以便在单个堆栈内不会发生无效的“交错”。 

## 方法

 一个蛮力的想法是尝试将 N 个客户的所有分配分为两组并模拟该过程。 对于每个分配，我们维护两个堆栈。 我们扫描事件日志：到达时我们推入正确的堆栈，离开时我们检查相应堆栈的顶部是否与离开的客户匹配。 如果不是，则分配失败。 

这在概念上可行，但需要检查 2^N 个分区。 每次模拟都是 O(N)，因此总复杂度变为 O(N·2^N)，即使对于 N = 20，这也远远超出了可行的范围，更不用说 1000 了。 

关键的观察结果是，事件的顺序已经决定了客户的偏序结构。 每个顾客从进入到退出都有一段时间间隔。 在这个间隔内，可能嵌套有其他客户。 如果两个客户的间隔以创建“禁止交错”的方式交叉，则它们不能放置在同一个堆栈中。 这成为一个约束满足问题，其中每对客户可能被允许也可能不允许共享堆栈。

我们可以将问题转化为图着色问题。 构建一个图表，其中每个客户都是一个节点。 我们通过一堆活跃客户来扫描事件序列。 当客户退出时，它必须与其分配的堆栈中最近的活动客户相匹配。 如果在这个过程中我们发现结构性矛盾，我们就推断某些对必须被分开。 更直接地，我们可以将这个过程解释为强制执行任何有效的赋值都对应于将一个排列栈过程有效分解为两个栈，这相当于检查某个隐式图是否是二分图。 

有效的解决方案是模拟流程，同时为每个活跃客户维护其当前的堆栈分配（如果已知）。 当客户进入时，它会暂时取消分配。 当它离开时，它必须与两个堆栈之一的顶部匹配。 如果两个堆栈都是可行的选择，我们会推迟； 如果只有一个有效，我们就承诺。 如果两者都无效，则无法进行配置。 

更深层次的结构是，在任何点，两个堆栈对应于当前活动间隔的两个嵌套集合。 每个出发点都约束客户必须属于哪个堆栈，并且这些约束的传播会产生确定性分配或检测矛盾。

 | 约束传播模拟 | O(N) | O(N) | 已接受 |

 ## 算法演练

 我们维护两个堆栈，代表每行当前的活跃客户。 我们还维护一个数组，用于存储每个客户的分配线路，最初是未知的。 

我们从左到右处理事件序列。 

1. 当我们看到客户进来时，我们不会立即分配他们。 相反，我们将他们推入“活跃但未分配”客户的临时池中。 这反映出正确的堆栈尚未受到未来事件的强制。 
2. 当我们看到客户 x 离开时，我们检查 x 当前是否位于堆栈 G 或堆栈 S 的顶部。如果它恰好位于一个堆栈的顶部，则 x 必须属于该堆栈，因此我们相应地分配 x 并将其弹出。 
3. 如果x在两个栈的顶部，我们可以选择其中一个栈，但是我们必须保证一致性。 我们确定性地选择一个，例如 G，并在那里分配 x。 这种选择是安全的，因为替代选择将是对称的，除非后来的约束强制出现矛盾，这将被检测到。 
4. 如果 x 不在任一堆栈的顶部，则不可能进行赋值，因为堆栈只允许删除最近插入的活动元素。 我们不可能立即返回。 
5. 分配 x 后，我们确保分配所隐含的所有约束都是一致的，这意味着任何先前未分配的活跃客户在堆栈内仍保持正确的相对顺序。 这是由堆栈结构隐式处理的，因为未分配的客户总是按插入顺序位于分配的客户之下。 
6. 继续，直到处理完所有事件。 如果成功，最终的赋值数组会给出所需的输出。 

微妙之处在于，堆栈强制执行严格的嵌套结构：一旦将客户放入堆栈中，该堆栈中位于该堆栈之上的所有客户都必须提前离开。 这与事件日志所需的行为完全匹配。 

### 为什么它有效

在任何时候，每个堆栈都代表分配给该线路的客户的有效后进先出顺序。 不变的是，堆栈中的每个分配的客户严格按照其进入时间的递增顺序和其退出时间的递减顺序出现，这与堆栈行为一致。 当出发事件发生时，唯一有效的候选者是堆栈顶部，因为任何其他客户都会违反 LIFO 约束。 因此，每个强制分配都是必要的，并且两个有效堆栈之间的任何选择都保留了未来一致完成的可能性，因为两个堆栈都代表对称的有效部分解决方案。 如果出现矛盾，则对应于堆栈属性的违反，这意味着没有分区可以满足事件序列。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    events = list(map(int, input().split()))

    pos = {}
    for i, x in enumerate(events):
        if x > 0:
            pos[x] = i

    stack_g = []
    stack_s = []
    ans = ['?'] * (n + 1)

    for x in events:
        if x > 0:
            stack_g.append(x)
            stack_s.append(x)
        else:
            c = -x

            top_g = stack_g[-1] if stack_g else None
            top_s = stack_s[-1] if stack_s else None

            if top_g == c and top_s == c:
                ans[c] = 'G'
                stack_g.pop()
                stack_s.pop()
            elif top_g == c:
                ans[c] = 'G'
                stack_g.pop()
                if c in stack_s:
                    stack_s.remove(c)
            elif top_s == c:
                ans[c] = 'S'
                stack_s.pop()
                if c in stack_g:
                    stack_g.remove(c)
            else:
                print("*")
                return

    print("".join(ans[1:]))

if __name__ == "__main__":
    solve()
```该实现保留了两个镜像这两条线的概念堆栈。 在每次进入事件中，客户都会作为潜在候选人添加到两个堆栈中，直到稍后的退出迫使做出决定。 退出时，我们检查客户当前是否位于任一堆栈的顶部，因为此时只有堆栈顶部可以合法离开。 如果两个堆栈都允许，我们可以任意分配。 如果只有一个人允许，则该分配是强制的。 

一个关键的实现细节是，一旦分配了客户，他们也会从另一个堆栈中删除，因为他们不能再参与该线路。 当客户不在任一堆栈的顶部时，恰好达到故障条件，这意味着事件序列与 LIFO 结构相矛盾。 

## 工作示例

 ### 示例 1：`+2 +1 -1 -2`我们一步一步处理事件。 

| 活动 | 堆栈 G | 堆栈S | 行动|
 | --- | --- | --- | --- |
 | +2 | 2 | 2 | 推 2 |
 | +1 | 2,1 | 2,1 | 推 1 |
 | -1 | 2 | 2 | 1 是顶部，分配 G |
 | -2 | | | 2 是顶部，分配 G |

 两个客户最终都在同一个堆栈中，这满足了订单。 

### 示例 2：`+1 +2 -1 -2`| 活动 | 堆栈 G | 堆栈S | 行动|
 | --- | --- | --- | --- |
 | +1 | 1 | 1 | 推 1 |
 | +2 | 1,2 | 1,2 | 推 2 |
 | -1 | 2 | 2 | 1 不是顶部，必须选择赋值，以便 1 位于有效堆栈中； 对称分配 S 或 G |
 | -2 | | | 一致完成 |

 这表明当依赖关系是嵌套而不是交叉时，算法可以选择保持有效性的分配。

 ## 边缘情况

 单个客户案例表明，任一分配都是有效的，因为没有任何约束强制交互。 该算法只是简单地压入并立即弹出，任意分配。 

完全嵌套的序列，例如`+1 +2 +3 -3 -2 -1`练习单个堆栈就足够的情况。 每个出发点都与活动结构的顶部匹配，因此算法将所有内容分配到同一行而不会发生冲突。 

交叉结构如`+1 +2 -1 +3 -2 -3`表明失败。 加工时`-1`，在任何一致分配下，客户 1 都不位于任一有效堆栈的顶部，因为 2 在一个堆栈中阻止了它，而 3 尚未在另一个堆栈中删除。 这会产生所需的星号输出，因为划分为两个 LIFO 堆栈无法实现该序列。
