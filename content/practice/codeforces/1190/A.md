 ## 解决方案
 ## 问题理解

 我们得到一长串索引从 1 到$n$。 他们之中，$m$职位被标记为特殊。 这些特殊物品会通过轮次重复的过程被移除。 

在每一轮中，我们将当前行分组为固定大小的长度块$k$，就像书中的页面一样。 然后，我们查找至少包含一个特殊项目的第一页（从左到右）。 在该页面上，所有特殊项目都会立即删除。 移除后，剩余的项目会向左移动以填补空白，因此位置会动态变化。 我们重复这个过程，直到没有特殊物品剩余。 

输出是这些移除轮数。 

虽然$n$可以大到$10^{18}$，特殊项目的数量最多为$10^5$。 这立即告诉我们，我们无法模拟阵列或移位过程。 任何解决方案都必须仅针对特殊位置进行操作，并推理它们的相对结构如何变化。 

关键的难点在于，删除后，剩余元素的位置会左移，因此固定的索引并不稳定。 简单的模拟会重复重建阵列，从而增加成本$O(nm)$或者更糟，这是不可能的。 

当多个特殊项目位于同一页面中或删除导致项目跨页面边界移动时，会出现微妙的边缘情况。 

例如，如果$k = 3$,$n = 10$，特殊位置是$[3, 4, 5, 6]$，那么在删除第 1 页中的项目后，剩余的项目会发生移动，并且有些可能会跨入更早的页面。 天真的“按索引删除”方法会失败，因为索引在每次操作后不再有效。 

真正的挑战是跟踪随着时间的推移，随着删除操作压缩数组，有多少页面被“激活”。 

## 方法

 暴力模拟会重复维护完整的数组：

 1.重建页面结构，
 2. 找到包含特殊项目的第一页，
 3.删除该页面中的所有特殊项目，
 4.转移要素。 

每次移除都会花费$O(n)$，并且最多可以有$m$搬迁、给予$O(nm)$，这是不可能的，当$n$很大。 

关键的观察是我们实际上不需要模拟移位数组。 我们只需要知道每页删除了多少特殊项目，以及删除元素时页面边界如何有效移动。 

我们不是动态跟踪位置，而是跟踪每个特殊位置之前发生了多少次删除。 每次删除都会将所有后面的位置左移1，因此特殊项的有效位置$p_i$后$t$在它变成之前删除$p_i - t$。 

现在每个特殊项目都可以映射到页码：$$\text{page}(i) = \left\lfloor \frac{p_i - \text{shift}(i) - 1}{k} \right\rfloor$$当我们按升序处理特殊项目时，我们会维护已删除的项目数量，以及适用的转变量。 我们统计页面索引改变了多少次； 每个变化对应一个新的操作。 

直觉是，删除仅在聚合时才重要，并且随着早期删除的发生，每个特殊项目实际上都被“向左拖动”。

 | ---| ---| ---| ---|
 | 暴力模拟|$O(nm)$|$O(n)$| 太慢了 |
 | 轮班跟踪（贪婪）|$O(m)$|$O(1)$| 已接受 |

 ## 算法演练

 我们按升序处理特殊职位。 

1.初始化一个计数器`removed = 0`跟踪有多少特殊项目已被删除。 这表示数组向左移动了多远。 
2. 对于每个特殊职位$p_i$，计算其当前有效位置为$p_i - removed$。 这反映了早期删除如何压缩数组。 
3. 计算该调整位置的页面索引为$(p_i - removed - 1) // k$。 
4. 维护一个变量`current_page`代表当前操作发生的页面。 如果这是第一项，则对其进行初始化。 
5. 每当一个新项目属于与之前完全不同的页面时`current_page`，我们需要一个新的操作。 增加答案并更新`current_page`。 
6. 每个处理过的特殊项目都被视为已删除，因此增量`removed`1.

 关键思想是，按排序顺序处理可确保当我们到达每个元素时已考虑所有移位效果。 

### 为什么它有效

 在任何时候，唯一重要的是在给定位置之前有多少特殊物品被移除。 这完全确定了其在压缩数组中的当前索引。 由于页面是大小连续的块$k$，一旦我们知道调整后的索引，页面标识就固定了。 

每当我们遇到一个特殊项目，其调整后的页面与前一个页面不同时，这意味着算法必须在实际过程中移动到新页面，从而触发新的操作。 任何隐藏的重新排列都无法更改此顺序，因为移位保留了相对顺序。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    p = list(map(int, input().split()))

    removed = 0
    current_page = -1
    ops = 0

    for x in p:
        pos = x - removed
        page = (pos - 1) // k

        if page != current_page:
            ops += 1
            current_page = page

        removed += 1

    print(ops)

if __name__ == "__main__":
    solve()
```该实现依赖于我们从不显式修改数组的事实。 变量`removed`对当前位置之前由删除引起的所有移位进行编码。 

计算`(pos - 1) // k`对于正确的页面索引至关重要，因为页面在位置上是 1 索引，但在计算中是 0 索引。

 ## 边缘情况

 一个重要的边缘情况是，所有特殊项目都位于同一页面中，但删除会导致它们“转移”到同一页面内较早的位置。 例如，与$k = 5$和$p = [1,2,3,4]$，每次删除都会向左移动剩余的项目，但它们永远不会跨越页面边界。 算法保持`current_page`固定并计算单个操作，与真实过程相匹配。 

另一种情况是当项目完全分布在页面边界时，例如$p = [5, 6, 7]$和$k = 5$。 第一项位于第 0 页，但删除后，后面的项也可能会移至第 0 页。 公式$(p_i - removed - 1) // k$正确捕获此压缩，确保不会错误地计算额外的操作。 

最后一个微妙的情况是$k = 1$。 每个项目都有自己的页面，因此每次删除都必须触发新的操作。 该算法反映了这一点，因为每个调整后的位置总是形成一个新的页面索引，从而准确地产生$m$运营。
