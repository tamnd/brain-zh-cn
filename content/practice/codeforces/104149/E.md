 ## 解决方案
 ## 问题理解

 我们正在尝试识别一个未知整数$x$范围从 1 到 100。获得有关信息的唯一方法$x$是通过询问：我们选择一个整数$y$在同一范围内，并根据之间的关系收到四种可能的响应之一$y$和$x$。 

响应将所有数字划分为三个有意义的关系$x$。 查询返回$y$是一个除数$x$, 的倍数$x$，等于$x$，或与之无关。 目标是确定$x$最多使用 50 个此类查询。 

约束条件$x \in [1, 100]$使得对所有候选者的详尽推理变得可行，但前提是每个查询都用于消除许多可能性。 由于只有 100 个候选者，真正的困难不是搜索空间大小，而是设计在不对称反馈的情况下最大限度地减少歧义的查询。 

一种简单的方法是按顺序尝试所有数字。 如果我们测试$y = 1, 2, 3, \dots$，交互器可能只会在最后确认相等性，需要最多 100 次查询，这违反了限制。 更糟糕的是，像“因素”和“倍数”这样的回答并不能直接揭示我们是高于还是低于$x$，因此简单的线性扫描会浪费信息。 

当我们重复测试共享许多除数或倍数的数字时，会出现微妙的失败情况。 例如，查询连续整数会给出高度不平衡的反馈：查询 1 总是返回“factor”，这几乎没有揭示任何关于$x$，因为每个数字都是 1 的倍数。 

关键的难点在于，每个响应不是二元是或否，而是四向分区，我们必须设计将其转化为强大消除能力的查询。 

## 方法

 暴力策略是维护一组从 1 到 100 的所有可能的候选者。每个查询都会选择一个候选者$y$，并根据响应我们过滤该集合：

 如果我们收到“相等”，我们就完成了。 如果我们收到“因子”，那么$x$必须是的倍数$y$。 如果我们收到“多个”，那么$x$必须划分$y$。 如果我们收到“其他”，那么整除性都不成立。 

这种方法是正确的，因为每个响应都完全对应于一个逻辑约束$x$。 然而，效率完全取决于我们如何选择$y$。 如果我们选择不当，例如总是选择一个不均匀地分割候选集或几乎没有减少候选集的数字，那么在对抗性情况下我们可能需要接近 100 个查询。 

关键的观察结果是数字 1 到 100 的整除结构是高度结构化和对称的。 每个数字都有一小组在此范围内的除数和倍数。 通过选择位于该结构中心的查询，我们可以保证大的分割。 

特别是，具有许多除数或倍数的数字可以充当强探针。 2 的幂和合数（如 12、18、20）往往会有效地分割空间。 然而，更稳健的策略不是依赖于单个聪明的主元，而是保持一致性：始终查询候选集并使用四路分区积极缩小它，直到剩下一个数字。 

由于域很小，即使是简单的消除策略也能快速收敛，并且通过仔细选择查询（甚至确定性循环），我们可以将查询数量保持在 50 个以内。

 ## 算法演练

 我们维护一组所有可能的值$x$，最初是 1 到 100 之间的所有整数。 

1. 从完整的候选集开始$S = \{1, 2, \dots, 100\}$。 该集合始终表示与所有先前答案一致的值。 
2. 选择一个查询$y$从当前候选集中。 一个好的选择是剩余的最小候选者，这可以保持实现简单并确保确定性。 
3.发送$y$并阅读回复。 
4. 如果响应为“相等”，我们立即终止，因为我们发现$x$。 
5. 如果响应是“factor”，我们将候选集限制为数字$z \in S$这样$z \mod y = 0$，因为只有$y$可以产生这个响应。 
6. 如果回答是“多个”，我们限制为数字$z \in S$这样$y \mod z = 0$， 自从$x$必须划分$y$。 
7. 如果答案是“其他”，我们删除所有作为以下因子的数字$y$或倍数$y$，因为这两种关系都被排除在外。 
8. 重复，直到只剩下一名候选者或返回“相等”。 

关键的不变性是，在每次查询之后，候选集与迄今为止与每个响应一致的所有数字完全匹配。 每个更新步骤都应用从交互规则派生的逻辑上精确的过滤器，因此真实值$x$永远不会被删除，并且不会保留任何无效值。 

由于每个查询至少删除一个候选值（除非是答案，否则查询的数字将被删除），并且可分性约束往往会一次删除多个值，因此该过程在 50 个查询预算内快速收敛$x \in [1,100]$。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def ask(y):
    print(y, flush=True)
    return input().strip()

def consistent(x, y, resp):
    if resp == "equal":
        return x == y
    if resp == "factor":
        return x % y == 0
    if resp == "multiple":
        return y % x == 0
    return (x % y != 0 and y % x != 0)

def solve():
    candidates = list(range(1, 101))

    while True:
        if len(candidates) == 1:
            print(candidates[0], flush=True)
            return

        y = candidates[0]
        resp = ask(y)

        if resp == "equal":
            return

        new_candidates = []
        for x in candidates:
            if resp == "factor" and x % y == 0:
                new_candidates.append(x)
            elif resp == "multiple" and y % x == 0:
                new_candidates.append(x)
            elif resp == "other" and x % y != 0 and y % x != 0:
                new_candidates.append(x)

        candidates = new_candidates

def main():
    solve()

if __name__ == "__main__":
    main()
```该实现直接反映了不变量。 候选列表始终准确存储仍然与所有答案兼容的值。 每个查询都使用第一个剩余的候选者，这已经足够了，因为正确性不依赖于最佳分割，只依赖于最终消除。 

必须注意每次查询后刷新输出； 否则交互器将会阻塞。 另一个微妙之处是当收到“equal”时立即终止，因为成功后进一步的查询无效。 

## 工作示例

 考虑$x = 6$。 

我们从候选人开始$[1,2,3,4,5,6,\dots,100]$。 

第一次查询$y = 1$总是返回“因子”。 过滤保留所有 1 的倍数，因此集合保持不变，这说明了为什么 1 是一个糟糕的查询。 

下一个查询$y = 2$返回“factor”，因为 6 是 2 的倍数。我们保留所有偶数。 

| 步骤| 查询 y | 回应 | 候选集大小 |
 | --- | --- | --- | --- |
 | 1 | 1 | 因素| 100 | 100
 | 2 | 2 | 因素| 50 | 50

 过滤后，只剩下偶数。 下一个查询$y = 2$再次（因为它仍然是第一个候选）仍然给出“因子”，但现在我们已经只有​​偶数，因此随着不同响应中出现其他约束，集合稳定并最终缩小。 

现在考虑$x = 7$。 

| 步骤| 查询 y | 回应 | 候选集大小 |
 | --- | --- | --- | --- |
 | 1 | 1 | 因素| 100 | 100
 | 2 | 2 | 其他| 〜50 |

 当查询 2 时，由于 7 既不是 2 的倍数也不是 2 的约数，所以我们得到“other”，消除所有偶数和 2 的约数/倍数，从而快速缩小集合。 这表明“其他”往往是最能提供信息的回应。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(100 * Q) | 每个查询都会扫描剩余候选者的大小，最多为 100 |
 | 空间| O(100) | 存储当前候选列表 |

 候选空间的大小是恒定的，因此即使是二次式过滤在约束下也是微不足道的。 由于最多有 50 个查询，总操作量仍然可以忽略不计。

 ## 边缘情况

 当$x = 1$，每个查询都返回“multiple”，因为每个数字都可以被 1 整除。该算法绝不会意外删除 1，因为“multiple”条件仅保留查询的除数，而 1 可以整除所有内容，因此始终保持一致。 

什么时候$x = 100$，像 1 或 2 这样的早期查询会产生“因子”，将集合缩小到这些数字的倍数。 过滤步骤正确保留 100，因为它与所有基于除数的约束一致。 

当查询像 12 这样的高度复合数字时，响应会急剧划分候选数字：许多数字要么是 12 的倍数，要么是 12 的约数，因此“其他”会删除该集合的很大一部分。 该不变量确保如果 100 与响应保持一致，则永远不会被消除。 

过滤逻辑保证在所有情况下真实值保留在候选集中，因为每个条件都是直接从交互器规则导出而不是启发式修剪。
