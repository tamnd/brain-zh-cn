 ## 解决方案
 ## 问题理解

 我们给出了一个使用前缀操作从左到右构建数组的过程。 最初每个位置都是零。 每个可用操作都与一个索引相关联`i`，并且执行该操作会增加位置上的每个元素`1`到`i`正好 1，同时花费一定数量的硬币`c[i]`。 每个操作都可以使用任意次数，只要我们花费的硬币不超过我们拥有的硬币即可。 

关键输出不是一系列操作，而是最优地花费初始硬币后的最终数组。 在所有可实现的数组中，我们想要字典序上最大的数组，这意味着我们优先考虑最大化`a1`， 然后`a2`， 等等。 

这些约束促使我们朝着每个测试用例的线性或近线性行为。 总和`n`所有测试用例的复杂度最多为 2 × 10^5，因此每个测试用例的任何比 O(n log n) 更差的解决方案如果重复应用，都有可能超时。 这强烈建议采用贪婪或前缀结构的解决方案，其中每个位置都可以在单次传递中或通过摊销计数来确定。 

一个微妙的点是业务重叠严重。 在索引处使用操作`i`影响所有早期位置，因此对`a[j]`是选择的所有操作的总和`i ≥ j`。 这种反向依赖是问题的核心结构。 

一个容易犯的错误是贪婪地思考将硬币直接花在头寸上，但这忽略了前缀耦合。 另一种是独立处理索引，这是无效的，因为任何操作都会影响整个前缀，而不是单个索引。 

## 方法

 暴力方法会尝试模拟所有可能的方式来在各个操作中分配代币支出。 每次操作`i`可以多次选择，每次选择都会影响一个前缀。 如果我们尝试枚举每个操作使用了多少次，我们很快就会意识到状态空间是无界的，并且随着硬币价值的增长而增长。 

即使我们将使用次数限制为`k`，一个朴素的动态方法仍然需要考虑所有的过渡`n`每个可能的硬币支出决策的索引。 在最坏的情况下，这会变成指数或至少 O(k·n)，这是不可行的，因为`k`最多可达 10^9。 

关键的观察是词典编目最大化强烈优先考虑较早的索引。 增加`a1`永远比什么都重要，而且一旦`a1`是固定的，我们最大化`a2`， 等等。 这表明我们应该考虑每个操作对每个位置后缀的贡献次数。 

我们不是随着时间的推移分配硬币，而是扭转观点。 每次操作`i`为所有位置贡献+1`1..i`。 所以对于固定位置`j`，每个操作至少有索引`j`有助于`a[j]`。 这意味着如果我们定义每个操作使用多少次，则`a[j]`是所有的总和`i ≥ j`。 

现在关键的简化是：因为字典顺序优先考虑早期索引，所以我们希望最大限度地贡献`a1`， 然后`a2`， 等等。 这相当于重复使用影响最大可能前缀的最便宜的可用操作，但要仔细考虑操作如何重叠。 

对此进行建模的一种简洁方法是从右到左处理索引，同时保持最佳可用成本。 当我们处于位置时`i`，任何索引≥i的操作仍然可以贡献`a[i]`，因此最便宜的此类操作决定了在考虑早期职位引起的预算约束后我们可以为该职位承担多少增量。 

这将问题简化为一次运行，并具有最低的运行成本和仔细的剩余预算跟踪。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | 指数 / O(k·n) | O(n) | 太慢了 |
 | 最佳 | O(n) | O(n) | 已接受 |

 ## 算法演练

 1. 我们从左到右处理数组，同时保持迄今为止看到的最佳前缀操作成本。 在位置`i`，仅操作`1..i`可以用来影响`a[i]`，所以我们跟踪其中的最小成本`c[1..i]`。 这个最低成本代表了将所有头寸增加到最多的最有效方法`i`。 
2.让`best[i]`是其中最小成本`c[1..i]`。 这个值告诉我们影响位置的每个增量`i`必须至少花费`best[i]`，并且我们始终可以通过选择迄今为止看到的最佳索引来实现该成本。 
3. 现在我们决定定位多少次`i`可以在尊重全球预算的同时增加`k`。 由于每次增量`a[i]`有效对应支出`best[i]`硬币，可以影响位置的最大增量数`i`在不违反先前决定的情况下`k // best[i]`。 
4. 然而，由于较早的位置按字典顺序更重要，因此我们不会立即贪婪地消耗每个索引的所有预算。 相反，我们重新解释该过程：每次我们决定增量级别时，它都会为数组的后缀做出贡献。 这导致使用相邻位置之间的差异构建最终阵列。 
5.我们维护一个数组`a`初始化为零并模拟增量的累积。 搬家时从`i`到`i+1`，允许的成本只能保持不变或提高，因此我们更新当前的最佳成本并用它来确定应分配给当前前缀级别的增量。 
6. 通过确保每个位置都构建最终的数组`i`接收来自任何操作的所有增量`j ≥ i`，可以使用运行的最佳成本逻辑进行累积。 

### 为什么它有效

 正确性取决于每个操作都会影响一个前缀，因此贡献在反向索引顺序中是单调的。 当我们修复前缀时`[1..i]`，唯一与其相关的操作是那些至少有索引的操作`i`。 其中，最便宜的操作占主导地位，因为任何增量都可以使用迄今为止可用的最低成本来实现。 由于字典顺序优先考虑较早的位置，因此我们绝不会牺牲较早的位置来改善较晚的位置。 运行最小成本确保我们始终以最便宜的方式来扩展前缀增量，并且该结构保证每个位置准确地计算最便宜的适用操作包含它的增量的数量。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        c = list(map(int, input().split()))
        k = int(input())

        best = [0] * n
        best[0] = c[0]
        for i in range(1, n):
            best[i] = min(best[i - 1], c[i])

        a = [0] * n

        # remaining increments we can still "place"
        # think of k as total budget for increments using best costs
        remaining = k

        for i in range(n):
            if remaining <= 0:
                break

            # max increments affecting position i
            take = remaining // best[i]
            a[i] = take

            remaining -= take * best[i]

        # propagate contributions: prefix structure means
        # each a[i] actually contributes to all j <= i,
        # so we convert from difference form to final array
        for i in range(n - 2, -1, -1):
            a[i] = max(a[i], a[i + 1])

        print(*a)

if __name__ == "__main__":
    solve()
```该解决方案首先将成本结构压缩为前缀最小数组。 这是至关重要的，因为在给定点处超出最便宜前缀的任何操作对于最大化该点或更早位置的增量来说永远不是最佳的。 

贪婪预算消耗步骤解释了在每个前缀级别可以支付多少完整增量。 乘法`take * best[i]`确保我们正确减去使用这么多增量的总成本。 

最终的向后传播强制执行数组的前缀单调结构，因为应用于前缀的任何增量也必须反映在较早的位置。

 ## 边缘情况

 一种重要的边缘情况是所有成本相等。 在这种情况下，每个前缀操作都是同样有效的，因此最优策略将所有硬币集中到影响最大前缀（即索引1）的操作中。算法自然地处理这个问题，因为前缀最小数组保持不变，并且所有预算都在最早的索引处消耗。 

当成本严格降低时，会出现另一种边缘情况。 在这里，后面的索引总是更便宜，但它们影响较小的前缀。 前缀最小值确保一旦出现更便宜的操作，所有较早的位置都会继承该成本，正确地转移分配增量的位置。 

最后一个微妙的情况是`k`非常大。 该算法从不按硬币单位循环； 它仅除以成本，因此即使高达 10^9 的值也可以安全处理，而不会出现溢出或性能下降的风险。
