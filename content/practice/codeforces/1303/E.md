 ## 解决方案

 ## 问题理解

 我们得到一个初始字符串`s`和一个目标字符串`t`。 我们可以构造一个新的字符串`p`通过执行最多两轮相同的操作来从空开始。 在每一轮中，我们选择当前的任何子序列`s`，从中删除那些选定的字符`s`，并将选定的子序列附加到末尾`p`。 关键的限制是我们最多可以执行两次此操作，并且一旦从`s`不能重复使用。 

所以在操作上，我们正在对字符进行分区`s`最多分为三组：一组在第一个子序列中使用，一组在第二个子序列中使用，一组完全丢弃（因为在两次删除之后，剩余的字符不再相关）。 两个选定子序列的串联形成最终字符串`p`，我们想知道是否`p`可以完全等于`t`。 

约束以非常具体的方式很小：测试用例中所有字符串的总长度最多为 400。 这会立即排除每个测试用例的任何重二次或三次 DP，除非它被仔细限制。 它还表明我们应该考虑贪婪或线性扫描与小 DP 状态的结合。 

这个问题的一个微妙问题是子序列可以任意选择，因此`s`不需要保持连续。 这通常会误导子集或匹配 DP。 然而，最多两个子序列的存在施加了很强的结构约束：中使用的每个字符`t`必须来自第一个子序列或第二个子序列，并且每个子序列中的顺序必须与`s`。 

一个常见的失败案例是假设我们只需要检查是否`t`是一个子序列`s`，这是不正确的，因为我们可以通过分成两个子序列来重新排序。 例如，`s = "ba"`和`t = "ab"`作为单个子序列失败，但通过采取成功`"b"`在第一次操作中和`"a"`在第二个。 

另一种失败模式是假设我们可以贪婪地分配`t`到最早可能的位置`s`不考虑我们只有两个递增的子序列层。 当贪婪分配强制超过两个单调段时，这种情况就会中断。 

## 方法

 暴力解释是分配每个字符`s`为三种状态之一：未使用、在子序列 1 中使用或在子序列 2 中使用，然后检查连接子序列 1 和子序列 2 是否等于`t`。 这是指数级的`n`，因为每个角色都有三个选择，大致给出`3^n`可能性，甚至远远超出任何限制`n = 400`。 

关键的见解是扭转观点。 而不是构造子序列`s`，我们尝试模拟匹配`t`通过贪婪地匹配它`s`同时允许在子序列之间最多进行一次“切换”。 一旦我们决定一个角色`t`取自较晚的位置`s`与前一个相比，我们实际上仍然处于相同的子序列中； 当我们需要“重置”到较早的位置时`s`相对于上一场比赛，这会强制开始第二个子序列。 

那么问题就变成了：我们能否嵌入`t`进入`s`按顺序选择字符，同时最多使用两次递增的传递`s`？ 这可以建模为对位置的动态规划`t`和状态表示我们是在第一个还是第二个子序列中，加上最后使用的索引`s`。 

自从`|s|, |t| ≤ 400`，我们可以定义一个 DP 来跟踪是否可以匹配前缀`t`最多使用两个子序列，确保每个子序列中的索引严格递增。 标准技巧是通过预先计算下一个事件来压缩转换。 

最有效和最干净的解决方案是贪婪模拟`s`两次，但有一个转折：我们尝试匹配`t`作为一个子序列`s`按顺序，每当我们失败时，我们都会重新启动另一次扫描`s`。 如果我们最多可以在两次扫描内完成，那么答案是肯定的。 这是可行的，因为每次扫描对应一个子序列，并且在一次扫描中我们保留递增的索引顺序。 

因此我们正在检查是否`t`可以表示为最多两个子序列的串联`s`。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 将每个字符暴力分配给 3 个状态 | O(3^n) | O(3^n) | O(n) | 太慢了|
 | 贪心两遍子序列匹配 | 最坏情况 O(n²) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们模拟匹配`t`反对`s`最多使用两次通过。 

1. 初始化一个指针`i = 0`超过`t`，和一个通行证计数器`used = 1`。 我们开始第一次子序列扫描`s`。 
2. 虽然`i < len(t)`和`used ≤ 2`，我们扫描`s`从左到右尝试匹配`t[i]`。 每当我们发现`s[j] == t[i]`，我们通过递增来消耗它`i`并继续向前扫描。 
3. 如果我们到达终点`s`并且仍然有不匹配的字符`t`，我们增加`used`并重新开始扫描`s`从一开始。 这代表开始第二个子序列。 
4. 如果两次全扫描后仍然有不匹配的字符`t`，我们返回NO。 
5. 如果我们成功匹配了中的所有字符`t`，我们返回 YES。 

我们可以安全地从头开始扫描的原因是每次扫描都会强制增加子序列内的索引，并且重新启动会强制子序列之间的分离。 

### 为什么它有效

 每次我们穿越`s`，我们正在按递增索引顺序构造一个子序列。 由于我们最多允许两次遍历，因此我们将自己限制为最多两个递增子序列，其串联形式`t`。 任何有效的构造都必须对应于这样的分区，因为每个选择的子序列`s`根据定义，索引是严格递增的。 贪婪匹配确保我们总是消耗`t`在每次传递中尽可能早地进行匹配，因此，如果存在解决方案，则延迟匹配无法提高可行性，并且在两次传递内未能匹配意味着不存在有效的分割。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def can_build(s, t):
    n, m = len(s), len(t)
    i = 0
    used = 1

    while used <= 2 and i < m:
        progress = False

        for ch in s:
            if i < m and ch == t[i]:
                i += 1
                progress = True

        if i == m:
            return True

        if not progress:
            return False

        used += 1

    return i == m

T = int(input())
for _ in range(T):
    s = input().strip()
    t = input().strip()
    print("YES" if can_build(s, t) else "NO")
```该函数迭代`s`最多两次。 指针`i`跟踪有多少`t`已匹配。 每一遍都会贪婪地消耗尽可能多的字符。 这`progress`标志确保当没有字符时我们不会无用地循环`t`可以在完整扫描中匹配，这意味着不可能。 

关键的实现细节是`i`在传递之间永远不会重置，因此我们有效地进行了分割`t`最多分成两个子序列，同时保持顺序。

 ## 边缘情况

 一个关键的边缘情况是当`t`需要重用早期的字符`s`在不同的片段中多次。 例如，`s = "abacaba", t = "aaaa"`成功是因为第一遍选择了两个`a`s，第二遍选择剩下的两个。 该算法自然地处理这个问题，因为每次扫描都会从头开始重新开始扫描`s`。 

另一个边缘情况是完整通道中没有字符匹配。 为了`s = "abc", t = "d"`，第一次扫描进度为零，立即触发失败。 这可以防止不必要的第二遍计算并尽早正确地检测到不可能性。
