 ## 解决方案
 ## 问题理解

 我们给出了几个独立的场景。 每个cookie中都有很多cookie，每个cookie属于一种类型，并且有一个消失的截止时间。 Jan 想要随着时间的推移吃饼干，每次他吃一块饼干时，下一块饼干之前的等待时间都会随着他已经吃掉的饼干数量而增加。 第一个饼干可以立即吃掉，第二个需要在吃完第一个后等待 1 个单位，第三个需要在吃完第二个后等待 2 个单位，以此类推。 如果Jan已经吃过饭了$k-1$饼干并吃$k$-th 时间$t$，那么下一个不能在时间之前吃掉$t + (k-1)$。 

每块饼干都会在指定的时间消失，但​​简也可以在那个时间吃掉它。 存在多个相同类型的饼干，Jan 可以吃任意数量的饼干。 目标是最大限度地增加 Jan 至少吃一次的不同饼干类型的数量。 

关键的困难在于，吃更多的饼干会增加未来的等待时间，这使得后面的截止日期更难满足。 决定的不仅仅是某种类型是否可用，而是是否可以在成本不断增加的时间表中尽早安排。 

这些限制意味着我们需要接近的东西$O(n \log n)$或者$O(n \log m)$每个测试用例。 高达$2 \cdot 10^5$cookie 总数，任何尝试所有子集或独立模拟每种类型的计划的方法都太慢。 即使是不排序的贪婪的每种类型模拟也会面临二次行为的风险。 

当一种类型具有多个具有不同截止日期的 cookie 时，就会出现微妙的边缘情况。 选择错误的发生很重要：

 例如，假设类型 1 在时间 1 和 100 处有 cookie，类型 2 在时间 2 处有 cookie。如果我们贪婪地选择每种类型中最早的可能 cookie，而不考虑未来成本，我们可能会在时间 1 处获取类型 1，在时间 2 处获取类型 2，这是有效的。 但是，如果类型 2 的截止日期为 1 而不是 2，则首先选择类型 1 会阻止类型 2，即使不同的排序也会成功。 这表明我们必须考虑所选类型的订购，而不仅仅是可用性。 

另一个边缘情况是类型仅具有较晚的 cookie。 即使某个类型“存在”，由于延迟成本增加，它也可能只有在序列的早期安排时才可用。 

## 方法

 蛮力的想法是独立处理每种类型，并尝试确定 Jan 可以按某种顺序成功选择哪些类型子集。 对于固定的类型子集，我们会尝试为每个选定的类型分配一个代表性 cookie，然后模拟是否可以按照截止日期和递增延迟规则按某种顺序安排它们。 

这立即变得昂贵，因为类型子集的数量是指数级的。 即使我们修复了一个子集，检查可行性本身也很重要，因为对于每个排序，我们必须重新计算取决于序列中位置的到达时间。 和$m$最多$5 \cdot 10^4$，这是不可行的。 

关键的观察是，每种类型我们永远不需要多个 cookie，并且对于每种类型，最好只考虑其最新的可用截止日期候选者，因为早期的 cookie 只会降低灵活性。 一旦我们决定采用一种类型，我们只关心能够支持它的最佳 cookie。 

现在的问题变成了：我们想要选择尽可能多的类型，并且每个选择的类型都会贡献一个截止日期约束。 如果我们选择$k$类型，我们必须为它们分配位置$1$通过$k$，以及$i$- 选择的类型必须最多在某个时间可以实现$i(i-1)/2$加上调度的一些基本转变，但更简单的是，我们增量模拟：$i$-第一个选择的cookie在等于延迟总和的时间被吃掉$0 + 1 + 2 + \dots + (i-1)$，即$(i-1)i/2$，如果我们假设我们从时间 0 开始。 

然而，由于 cookie 具有任意的截止日期，我们需要直接进行可行性检查：如果我们通过增加截止日期对所选类型进行排序，我们希望确保当我们按该顺序分配它们时，每个类型都可以在累积延迟增长下不晚于其截止日期放置。 

这导致了贪婪策略：考虑按最佳截止日期排序的类型。 维护我们已经选择的类型。 对于每种类型，我们检查是否可以包含它。 如果我们的规模$k$，下一个类型将在延迟后被吃掉$k$，所以我们测试它选择的截止日期是否至少是在给定当前序列长度的情况下它会被吃掉的时间。 如果是，我们将其包括在内。 

我们将每种类型简化为单个值：可实现的最佳截止日期就是其 cookie 中的最大截止日期，因为 Jan 可以选择吃哪个副本。 然后，我们按照这些值的升序贪婪地选择类型，保持运行的可行性约束。

 ## 算法演练

 我们首先压缩输入，使每种类型都由一个数字表示：该类型的所有 cookie 中的最大消失时间。 这捕获了使用该类型的最佳机会，因为任何早期的 cookie 只会使约束更加严格。 

1. 读取所有 cookie 并计算每种类型出现的最大期限。 这将问题转化为选择$m$项目，每个项目都有一个截止日期。 
2. 按计算出的截止日期以非降序对所有类型进行排序。 原因是，我们希望首先承诺最严格的类型，因为一旦累积的进食延迟增加，延迟它们只会增加我们超过最后期限的风险。 
3. 初始化计数器$k = 0$，代表到目前为止我们已经成功选择了多少种类型。 
4. 迭代排序的截止日期列表。 对于每种类型都有截止日期$d$，计算 Jan 吃下一块 cookie 的时间（如果我们将其包含在内）。 该时间就是当前累计的等待成本，等于$k(k+1)/2$如果准确跟踪，但我们可以通过增量维护下一个可用时间来避免完整的公式。 如果下次所需时间不超过$d$，我们接受这种类型并增量$k$。 否则我们就跳过它。 

关键的想法是，接受类型只会增加未来的延迟，因此一旦类型未通过可行性测试，它就永远不会变得可行。 

### 为什么它有效

 在任何时候，该算法都会维护一组已选择的类型，这些类型可以按截止日期的升序进行安排，而不会违反约束。 按截止日期排序可确保当我们考虑一种新类型时，我们会针对其在所有可行选择中的位置的最小可能增长状态进行测试。 如果某个类型无法在该排序中尽可能早的位置放入，则稍后将其插入任何位置只会增加其所需的等待时间，使其更加不可行。 这表明贪婪的接受永远不会使未来的可行性决策无效，并且跳过某种类型是安全的，因为任何包含它的有效解决方案都需要用更严格的截止日期替换一些早期接受的类型，这与排序顺序最优性相矛盾。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        m, n = map(int, input().split())
        
        # best deadline per type
        best = [0] * (m + 1)
        
        for _ in range(n):
            a, ti = map(int, input().split())
            if ti > best[a]:
                best[a] = ti
        
        deadlines = [best[i] for i in range(1, m + 1)]
        deadlines.sort()
        
        k = 0
        current_time = 0
        
        for d in deadlines:
            # if we take this as (k+1)-th cookie, it is eaten at current_time + k
            if current_time + k <= d:
                current_time += k
                k += 1
        
        out.append(str(k))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```压缩步骤确保我们只跟踪每种类型最许可的 cookie。 排序后的截止日期数组创建了贪婪选择所需的结构。 变量`k`和`current_time`编码累积延迟效应：当选择下一个类型时，等待成本恰好增加已选择类型的数量。 

条件`current_time + k <= d`检查是否可以在下一个 cookie 消失之前放置它，因为下一个吃食时间是当前累积延迟加上将其放置在位置引起的额外延迟`k+1`。

 ## 边缘情况

 当许多类型共享相同的截止日期，并且在累积延迟超过该截止日期之前只能选择少数类型时，就会出现一种微妙的情况。 对于输入：```
1
4 4
1 1
2 1
3 1
4 10
```压缩的最后期限是$[1, 1, 1, 10]$。 该算法首先以成本 0 采取第一种类型，然后立即尝试第二种类型，但失败，因为下一个所需时间为 1，而 current_time + k 变为 1，这等于截止时间并且仍然允许。 选择两种类型后，下一次尝试将需要时间 2，该时间超过 1，因此紧密组中只能有两种类型。 截止日期为 10 的最终类型根据订单的不同会提前或推迟接受，但由于它很大，所以在紧的类型用完后它总是适合的。 

这证实了算法在从宽松的约束中受益之前正确地饱和了早期约束。
