 ## 解决方案
 ## 问题理解

 我们有一个系统$n$所有接收相同控制参数的发动机$x$，我们可以将其视为全局电压。 每个引擎都会以分段线性方式对该电压做出反应。 每台发动机$i$有一个门槛$z_i$。 如果电压至多为该阈值，则发动机处于第一模式并贡献与$a_i x$。 如果电压超过阈值，发动机就会切换行为：其功率变为$a_i z_i + b_i (x - z_i)$，这意味着它随斜率线性增长$b_i$断点之后，同时保持连续性$z_i$。 

目标是选择最小的整数电压$x$使得所有发动机功率的总和至少为$p$。 

发动机数量少的限制，$n \le 100$，但目标功率$p$可以大到$10^{12}$，所以最终电压也可以很大。 这立即表明答案不是通过构建或模拟所有状态找到的，而是通过搜索来找到的$x$并能够快速计算任何固定的总功率$x$。 

一个天真的方法是尝试增加$x$从1向上计算每次的总功率。 这是正确的，但可能不可行，因为$x$可能需要长大到大约$10^{12}$，以及每次评估成本$O(n)$，导致$10^{14}$最坏情况下的操作。 

当引擎在不同阈值切换状态时，会出现一个更微妙的问题。 粗心的实现可能会错误地仅应用一个公式，或者忘记不同的引擎会在不同点改变行为。 例如，如果所有引擎都有不同的$z_i$，函数的结构变成了许多“扭结”线的总和，而不是单个线性函数。 

关键的观察结果是总功率是$x$是单调非递减且分段线性，仅在值处有断点$z_i$。 这使得二分搜索$x$有效，只要我们能够有效地评估该函数。 

## 方法

 蛮力策略很简单：从$x = 1$，计算总功率，达到时停止$p$。 每次评估都会扫描所有引擎并根据是否$x \le z_i$或不。 这是可行的，因为该函数是单调的，所以一旦我们超过了所需的幂，我们就找到了答案。 然而，在最坏的情况下，答案本身可能非常大，我们可能需要最多$10^{12}$迭代，每次成本计算$O(n)$，这太慢了。 

问题的结构表明单调性：增加$x$永远不会减少任何发动机的贡献，因为两个斜率$a_i$和$b_i$是积极的。 这使我们能够用二分搜索代替线性搜索$x$。 剩下的要求是一种快速评估固定电源总功率的方法$x$。 

对于固定的$x$，每个发动机在恒定时间内独立评估，因此计算总功率为$O(n)$。 与足够大范围内的二分搜索相结合，这产生了有效的解决方案。 

我们还需要确定二分搜索的安全上限。 一个简单的界限是$10^{18}$，因为即使最大斜率总和也受以下限制$10^6$，乘以这样的范围就可以轻松超过$10^{12}$。

 | ---| ---| ---| ---|
 | 暴力增量|$O(x \cdot n)$|$O(1)$| 太慢了 |
 | 二分查找+求值|$O(n \log X)$|$O(1)$| 已接受 |

 ## 算法演练

 我们将问题视为寻找最小的$x$使得单调函数$F(x)$至少达到$p$。 

1. 定义一个函数$F(x)$计算总功率。 对于每个引擎$i$， 如果$x \le z_i$，我们使用$a_i x$。 否则我们使用$a_i z_i + b_i (x - z_i)$。 这直接对分段定义进行编码，没有简化错误。 
2.设置二分查找范围$[0, R]$， 在哪里$R$足够大以安全地包含答案，例如$10^{18}$。 这避免了对确切的最大所需电压的推理。 
3. 反复选取中点$m$, 计算$F(m)$，并将其与$p$。 
4.如果$F(m) \ge p$，我们知道答案最多是$m$，所以我们将右边界移动到$m$。 否则我们将左边界移动到$m + 1$。 
5. 继续直到搜索收敛，然后输出左边界。 

它之所以有效，与单调性有关。 每个引擎的贡献不减少$x$，所以它们的总和也是不减的。 一旦值为$x$就足够了，所有较大的值仍然足够。 这保证了二分查找永远不会丢弃真实答案，并且始终收敛到最小的有效答案$x$。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n, p = map(int, input().split())
engines = [tuple(map(int, input().split())) for _ in range(n)]

def power(x):
    total = 0
    for z, a, b in engines:
        if x <= z:
            total += a * x
        else:
            total += a * z + b * (x - z)
    return total

lo, hi = 0, 10**18

while lo < hi:
    mid = (lo + hi) // 2
    if power(mid) >= p:
        hi = mid
    else:
        lo = mid + 1

print(lo)
```功能`power(x)`是分段定义的直接翻译。 二分查找保持以下所有值的不变性`lo`不足且所有值等于或高于`hi`就足够了。 所选的上限可以避免 Python 中的溢出问题并保证终止。 

一个常见的陷阱是试图错误地将函数简化为单一线性形式； 但这会失败，因为不同的发动机在不同的点切换坡度。 另一个微妙的问题是二分搜索中的逐一处理，这里通过始终缩小到第一个有效值来处理。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, p = map(int, input().split())
    engines = [tuple(map(int, input().split())) for _ in range(n)]

    def power(x):
        total = 0
        for z, a, b in engines:
            if x <= z:
                total += a * x
            else:
                total += a * z + b * (x - z)
        return total

    lo, hi = 0, 10**18

        mid = (lo + hi) // 2
        if power(mid) >= p:
            hi = mid
        else:
            lo = mid + 1
    return str(lo)

 ## 边缘情况

 一种边缘情况是所有引擎都超过了它们的阈值，即使是在很小的情况下$x$。 例如，如果$x > \max z_i$，每个引擎始终处于第二模式。 该算法仍然可以正确处理这个问题，因为评估函数始终使用第二个公式，并且单调性仍然成立。 二分搜索将很快收敛，因为该函数变成了带有斜率的简单线性增长$\sum b_i$。 

另一种情况是没有引擎切换模式，因为最佳模式$x$永远低于一切$z_i$。 在这种情况下，每个发动机始终处于第一状态，并且系统简化为单个线性函数$\sum a_i x$。 由于求值从不使用第二个分支，二分搜索仍然可以正确运行。 

一个更微妙的情况是，当某些引擎具有非常大的$z_i$，还有一些非常小。 该函数具有多个斜率变化，但由于每次评估都会直接重新计算贡献，因此该算法不需要显式跟踪断点。 正确性来自于评估每个步骤的确切定义，而不是尝试预先计算全局斜率结构。
