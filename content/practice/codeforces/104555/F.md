 ## 解决方案
 ## 问题理解

 我们正在模拟一个非常具体的假期例程，其中两个有序的活动列表在称为处置的共享资源下竞争注意力。 威廉从处置点的初始预算开始，然后面临两个队列：消耗处置的累人活动和恢复处置的精力充沛的活动。 

该过程是贪婪且有状态的。 每时每刻都有一个指针指向下一个未进行的疲劳活动和下一个未进行的活力活动。 威廉总是尝试先进行下一个劳累的活动。 如果他有足够的倾向来支付其成本，他就会这样做并减少他的倾向。 如果他负担不起，他就会转向精力充沛的活动并进行下一项，以增强他的性格。 一旦他完成了劳累的活动，他就简单地按顺序进行所有剩余的精力充沛的活动。 

输出是进程自然停止之前执行的活动总数，该停止可能是因为两个列表都已用完，也可能是因为无法取得进一步的进展。 

约束表明两个列表都中等大小，每个列表最多 10^4，而处置最多可达 10^5。 这立即排除了任何重复向后扫描或以嵌套方式重试决策的模拟。 对两个序列进行线性传递就足够了，因为每个活动最多消耗一次并且决策是本地的。 

当幼稚的模拟错误地重新审视决策时，或者当算法假设一旦一项劳累的活动无法承担时，它就永远无法承担时，就会出现微妙的失败情况。 这是错误的，因为充满活力的步伐可以增强性格。 

例如，考虑：```
D = 10
C = 2: [15, 5]
R = 1: [20]
```天真的贪婪者可能会说“15 是不可能的，所以跳到 5”，错误地消耗了结构。 正确的做法是：不能做15个，所以必须吃20个，然后继续。 

另一个边缘情况是，当充满活力的活动不足以释放未来的疲劳活动时，因此该过程会陷入一种模式，如果不仔细正确地交替，就不可能取得进展。 

## 方法

 强力解释从字面上模拟该过程：在每一步中，我们都会检查是否可以执行下一个累人的活动。 如果是，我们就消费它； 否则我们将进行下一项令人振奋的活动。 这直接符合规则并且是正确的，因为决策仅取决于当前的处置和下一个可用的活动。 

问题是性能。 每个步骤都是 O(1)，但最多有 C + R 步骤，因此这看起来是线性的。 然而，如果我们以导致冗余扫描的方式重复检查可承受性，或者如果我们尝试在列表之间进行天真的回溯，就会出现微妙的低效率。 粗心的实现可能会在循环结构中的每个令人振奋的操作之后重复地重新评估令人疲惫的可行性，该循环结构实际上变成了二次。 

关键的观察结果是两个指针都只向前移动。 每个活动仅使用一次。 这意味着我们可以安全地单次模拟，保持当前的配置，而无需任何回滚或重复扫描。 

唯一需要的实际结构是两个索引（每个列表一个）和一个总是在 O(1) 中决定下一个操作的循环。 贪心规则本身已经定义了一条确定性路径。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力模拟（不小心反复检查）| O((C+R)^2) 最坏情况 | O(1) | O(1) | 太慢了 |
 | 两指针贪心模拟| O(C+R) | O(1) | O(1) | 已接受 |

 ## 算法演练

 ### 步骤

 1. 初始化两个指针，一个位于疲劳列表的开头，一个位于活力列表的开头，并将当前配置设置为 D。同时初始化已执行活动的计数器。 
2. 虽然任一列表中仍有未处理的活动，但尝试执行下一个繁重的活动（如果存在）。 
3. 如果存在疲劳活动并且其成本不大于当前处置，则减去其成本，前进疲劳指针，并递增计数器。 然后立即继续循环，因为我们总是优先考虑劳累的活动。 
4. 如果累人的活动存在但太昂贵，则切换到活力清单并执行下一个活动（如果有）。 将其值添加到处置中，推进该指针，并增加计数器。 
5. 如果没有剩余的令人振奋的活动，但仍然无法承担令人疲惫的活动，则该过程将停止，因为不可能采取进一步的行动。 
6. 如果疲惫的活动已耗尽，则按顺序消耗所有剩余的活力活动，添加它们的值并递增计数器。 

### 为什么它有效

 在每一步中，唯一相关的决定是在当前的处置下下一个累人的活动是否可行。 如果是，则由问题规则强制执行。 如果不存在，唯一的替代行动就是进行下一个振奋人心的活动（如果存在）。 除此之外没有任何分支选择。 

因为每个活动只消耗一次并且指针仅前进，所以系统永远不会重新访问以前的状态。 每个行动中的倾向都是单调演变的，贪婪的选择反映了问题的确定性政策。 这保证了模拟遵循规则定义的准确顺序，没有偏差。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    D, C, R = map(int, input().split())
    tiring = [int(input()) for _ in range(C)]
    invigorating = [int(input()) for _ in range(R)]
    
    i = j = 0
    d = D
    cnt = 0
    
    while i < C or j < R:
        if i < C and tiring[i] <= d:
            d -= tiring[i]
            i += 1
            cnt += 1
        else:
            if j < R:
                d += invigorating[j]
                j += 1
                cnt += 1
            else:
                break
    
    print(cnt)

if __name__ == "__main__":
    solve()
```实现直接遵循指针模拟。 当存在任何剩余活动时，循环将继续。 第一个分支强制执行优先级规则：如果可以承受下一个累人的活动，则立即进行。 

当累人的活动无法承担或耗尽时，就会触发 else 分支。 在这种情况下，我们尝试进行一些令人振奋的活动。 如果不存在，我们就会崩溃，因为不可能进一步改变状态。 

一个常见的陷阱是忘记活力活动必须按顺序消耗并且不能跳过，这是由单指针 j 强制执行的。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(C + R) | 每个活动只处理一次，因为指针仅向前移动 |
 | 空间| O(C + R) | 输入序列的存储|

 该限制允许最多 2 × 10^4 活动，因此线性扫描很容易足够快。 相对于 1024 MB 限制，内存使用量微不足道。

 ## 边缘情况

 一个重要的边缘情况是，第一个令人疲惫的活动成本太高，并且只有一个令人振奋的活动存在。 该算法正确地消耗了活力指针并在重新评估相同的疲劳指针之前更新配置。 

输入：```
D = 5
tiring = [10]
invigorating = [3]
```执行过程中，首先进行令人振奋的活动，将处置提高到 8，然后重新检查相同的疲劳活动，但仍然失败，因此它以计数 1 停止。 

另一个边缘情况是，疲劳的活动最初都是可以承受的，因此不会使用任何令人振奋的活动。 循环总是选择累人的分支，确保单调消耗而无需不必要的检查。 

最后，当充满活力的活动提前结束时，一旦下一个令人疲惫的活动变得难以承受，算法就会立即停止，因为没有任何机制可以增加处置。
