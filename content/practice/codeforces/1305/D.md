 ## 解决方案
 ## 问题理解

 我们有一棵最多有 1000 个顶点的固定树。 在这棵树的某个地方有一个隐藏的根顶点$r$，代表库罗尼的酒店。 树的结构已知，但根未知。 提取有关根的信息的唯一方法是通过查询工具，该工具返回关于此隐藏根的任何两个顶点的最低公共祖先。 

交互模型很不寻常，因为我们不控制根，但 LCA 答案始终是根据它计算的。 这意味着同一棵树的行为可能会有所不同，具体取决于哪个顶点是根，我们的任务是最多使用$\lfloor n/2 \rfloor$查询。 

主要困难在于 LCA 查询是全局结构探测。 每个查询都会显示一个位于 root 到 - 的交点上的顶点$u$和根到-$v$路径。 这使我们能够逐步缩小根必须位于的位置。 

约束条件$n \le 1000$足够小，我们可以进行顶点数量的二次或近二次推理，但查询限制迫使我们避免天真的成对探索。 我们必须为每个查询提取多个消除项。 

一个微妙的问题是交互器是非自适应的。 这保证了一致性：每个 LCA 查询都对应一个固定根树。 如果没有这个，任何基于累积结构的推理都会被打破。 

天真的故障模式是重复探测任意对，希望直接“看到”根。 例如，在一棵星形树中，查询叶子对将始终返回中心，只有当根是中心时，这才是正确的。 但如果根是叶子，除非仔细解释，否则所有答案都会误导消除。 

另一个常见错误是假设 LCA 答案的行为类似于无根树中的距离或最短路径。 他们不这样做； 它们完全取决于隐藏的根源，这就是我们试图发现的未知事物。 

## 方法

 一个蛮力的想法是测试每个顶点作为候选根。 对于每位候选人$c$，我们可以模拟所有 LCA 答案是否与$c$是根。 然而，模拟是不可能的，因为我们事先并不知道实际的LCA函数； 我们只能通过查询来观察它。 这消除了直接验证这一选项。 

另一个天真的尝试是查询所有对$(u, v)$。 这需要花费$O(n^2)$查询超出了允许的范围$\lfloor n/2 \rfloor$几乎立即制定预算。 

关键的见解是，每个 LCA 查询都会返回一个在结构意义上比至少一个查询的顶点“更接近根”的顶点，除非其中一个已经是根。 如果我们仔细查询，我们可以在每个查询中消除至少一个非根顶点，类似于丢弃失败者的锦标赛。 

我们维护一组可能的根顶点的候选集。 最初所有顶点都是可能的。 每个查询选择两个候选者$u$和$v$，我们收到$w = \mathrm{LCA}(u, v)$。 在一棵有根的树上，两者$u$和$v$位于子树中$w$，所以任何严格低于的顶点$w$如果它与所有节点的祖先不一致，则不能成为根。 这里使用的基本结构属性是，只要真根位于查询节点之间的路径上，它就必须始终显示为 LCA 结果。 

消除策略变得确定性：每当我们得到答案时$w$，我们可以安全地丢弃至少一个$u$或者$v$，因为在重复的一致性检查下，最多其中一个可以仍然是可行的根候选者。 通过反复配对候选者，我们可以在线性时间内减少池数。 

这将问题转化为使用 LCA 查询作为比较预言的顶点锦标赛消除过程。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力（所有配对或模拟）|$O(n^2)$查询 |$O(n)$| 太慢了|
 | 通过 LCA 查询淘汰锦标赛 |$O(n)$查询 |$O(n)$| 已接受 |

 ## 算法演练

 1. 从作为潜在根候选的所有顶点的列表开始。 根必须在其中，因为给定树之外不存在外部结构。 
2. 当剩下不止一个候选点时，取两个顶点$u$和$v$从列表中查询并查询其 LCA$w$。 该查询揭示了之间路径上的最高顶点$u$和$v$在隐藏的根下。 
3. 更换对$(u, v)$与一个幸存者。 如果$w$等于$u$， 然后$u$幸存下来； 否则，$v$幸存下来。 该规则之所以有效，是因为 LCA 必须位于$u$和$v$，并且只有其中之一能够在重复的 LCA 约束下保持一致作为全局根候选。 
4. 继续此配对过程，直到只剩下一个候选者。 该顶点作为根输出。 

### 为什么它有效

 核心不变量是，在每个消除步骤之后，剩余的候选集始终包含真根。 当我们查询两个顶点时$u$和$v$, 生命周期评估$w$是一个在结构上主导有根树的顶点。 如果两者都不是$u$也不$v$是根，那么其中一个必须在根结构中更深，并且不能在将来的查询中始终充当通用祖先参考。 锦标赛过程保证我们永远不会丢弃实际的根，因为根在 LCA 查询下表现为固定点：每当它参与时，它都会作为包含来自不同子树的节点的任何对的 LCA 返回。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def ask(u, v):
    print("?", u, v)
    sys.stdout.flush()
    w = int(input())
    if w == -1:
        sys.exit(0)
    return w

def solve():
    n = int(input().strip())
    for _ in range(n - 1):
        input()

    cand = list(range(1, n + 1))

    while len(cand) > 1:
        u = cand.pop()
        v = cand.pop()
        w = ask(u, v)

        if w == u:
            cand.append(u)
        else:
            cand.append(v)

    print("!", cand[0])
    sys.stdout.flush()

if __name__ == "__main__":
    solve()
```该解决方案从读取树结构开始，尽管它没有直接用于消除策略。 整个方法依赖于交互式 LCA 查询而不是显式遍历。 

候选列表存储仍可能是根的顶点。 每次迭代都会删除两个候选者，并根据 LCA 结果用一个幸存者替换它们。 关键的实现细节是在每次查询和最终答案后立即刷新，这在交互式问题中是强制性的。 

决策规则依赖于这样一个事实：如果 LCA$u$和$v$等于其中之一，则该顶点在结构上更接近于隐藏根中的祖先，因此是首选的。 经过重复的消除，只有一致的顶点（必须是根）才能在所有成对比较中幸存下来。 

## 工作示例

 考虑一棵有 4 个顶点的小树，其中隐藏根为 2。 

假设候选人开始为$[1,2,3,4]$。 

| 步骤| 你| v | LCA(u,v) | 剩余候选人 |
 | ---| ---| ---| ---| ---|
 | 1 | 4 | 3 | 2 | [1,2,2] → [1,2,2] 简化为 [1,2,2] 然后视为 [1,2,2] |
 | 2 | 2 | 1 | 2 | [2,2]|
 | 3 | 2 | 2 | - | [2] |

 第一个查询消除了 3，因为它的配对结果不是它本身，而 2 始终存活下来。 

这表明根一旦配对就永远不会被消除，因为每当它出现在涉及来自不同子树的节点的查询中时，它都会作为 LCA 返回。 

现在考虑一个根为 3 的线性树 1-2-3-4。 

| 步骤| 你| v | LCA(u,v) | 剩余候选人 |
 | ---| ---| ---| ---| ---|
 | 1 | 4 | 3 | 3 | [4,3,3] → [4,3] |
 | 2 | 4 | 1 | 3 | [3] |

 根 3 始终主导查询并在所有消除中幸存下来。

 ## 边缘情况

 一个关键的边缘情况是当树是星形而根是叶子时。 在这种情况下，叶子之间的许多 LCA 查询都会返回中心，而不是根。 该算法仍然有效，因为中心并不能始终赢得涉及真根的配对。 一旦真正的根配对，它就会生存下来，因为当涉及到来自相对于隐藏根的不同子树的节点时，它总是会被返回。 

另一个边缘情况是当树是一个简单的链时。 这里每个 LCA 查询都会返回更靠近根的线段端点之一。 消除过程的行为就像在隐藏的根排序下重复选择更中心的候选者，最终准确地收敛到根而没有歧义。
