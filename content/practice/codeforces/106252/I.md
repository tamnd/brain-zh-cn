 ## 解决方案
 ## 问题理解

 我们会按时间顺序处理编程竞赛中接受的提交内容。 每一次提交都属于一个团队和一个问题，并且所有提交都已经是成功的，因此每一行都代表了一次正确的解决方案尝试。 

对于每次提交，我们必须决定是否奖励气球。 仅当团队第一次解决问题时才会奖励气球。 然而，时机很重要。 在 240 分钟的比赛冻结时间之前，团队每首次解决一个问题都会产生一个气球。 冻结后，只有当该团队到目前为止收到的气球总数少于三个时，第一次解决才会产生气球。 

因此，任务不仅仅是跟踪每个团队和问题的第一个解决方案，还要维护每个团队已经收到的气球数量的运行计数，并根据提交时间应用条件规则。 

输入大小最多为 5000 个提交，最多 410 个团队和 13 个问题。 这足够小，我们可以轻松地在数组中维护每个团队的状态。 任何针对每个查询天真地检查先前提交的解决方案只有在实施效率低下时才会太慢，但即使二次扫描超过 5000 仍然是可以接受的； 真正关心的是干净的状态跟踪而不是渐近极限。 

一个微妙的失败案例来自于同一团队和问题的重复接受提交。 只有第一个被接受的提交才对气球逻辑重要。 

例如，如果一个团队在时间 10 解决了问题 2，并在时间 50 再次解决，则只应考虑第一个问题。 不跟踪已解决状态的简单方法会错误地奖励多个气球。 

另一个边缘情况是在冻结时间之后。 假设一个团队在时间 240 之前已经有了三个气球，然后在 240 后解决了一个新问题。即使是第一次解决，也没有给出气球。 粗心的实现可能仍然会奖励它，因为它是第一个解决方案。 

最后，排序很重要，因为提交的内容已经按时间排序。 这保证了我们可以顺序处理并保持准确的增量状态，而无需重新排序或前瞻。 

## 方法

 一种直接的方法是独立处理每个提交，并且对于每个提交，扫描所有以前的提交以确定这是否是团队第一次解决该问题。 如果是，我们就会通过扫描早期的输出来计算团队到目前为止已经收到了多少个气球。 这是有效的，因为它在每一步都明确地重建了所有必要的历史记录。 

然而，对于 n 个提交中的每一个，这都需要扫描最多 n 个先前条目，从而导致 O(n^2) 时间。 当 n 达到 5000 时，这大约是 2500 万次检查，这是临界值，但鉴于存在更简单的结构，这是不必要的。 更重要的是，这种方法很难正确实施，因为它重复地混合了已解决状态的重新计算和气球计数。 

关键的观察是我们永远不需要重新计算历史。 我们随时只需要知道两件事：一个团队是否已经解决了给定的问题，以及该团队已经收到了多少个气球。 两者都可以增量存储。 

我们为每个团队和问题对维护一个布尔状态，指示该团队是否已经解决了该问题。 我们还为每个团队保留了迄今为止奖励的气球的计数器。 然后通过检查和更新这些结构来在恒定时间内处理每个提交。 

这将整个问题简化为流模拟。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n^2) | O(n^2) | O(n) | 太慢而且没必要 |
 | 最佳| O(n) | O(团队 × 问题) | 已接受 |

 ## 算法演练

 我们按顺序一一处理提交的内容。 

1. 初始化一个二维布尔数组`solved[team][problem]`对于所有团队和问题都是错误的。 这跟踪团队之前是否已经解决了给定的问题。 
2.初始化一个数组`balloons[team] = 0`对于所有团队。 这存储了每个团队到目前为止收到的气球数量。 
3. 对于每次提交`(a, b, c)`按顺序，首先检查是否`solved[a][b]`已经是真的了。 如果为 true，则立即输出 0，因为这是重复求解并且不会生成气球。 
4. 如果错误，请标记`solved[a][b] = true`因为这是团队第一次解决这个问题。 
5.如果提交时间`c < 240`，我们总是奖励一个气球，所以我们增加`balloons[a]`并输出问题id`b`。 
6.如果提交时间`c >= 240`，我们检查`balloons[a] < 3`。 如果为真，我们增加`balloons[a]`和输出`b`。 否则我们输出 0。 

关键的设计选择是我们在第一次遇到问题时立即更新已解决的状态，确保无论何时，该问题的所有未来提交都会被忽略。 

为什么它有效：在处理流的任何时候，`solved[a][b]`准确地表示该对的第一个求解事件是否已经在序列中较早发生。 因为我们是按时间顺序处理的，所以这种状态与真实的比赛进程是一致的。 这`balloons[a]`计数器准确反映了先前接受的满足奖励规则的第一个解决方案的数量，因此可以在本地评估冻结条件，而无需历史重新计算。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    solved = [[False] * 14 for _ in range(411)]
    balloons = [0] * 411
    
    out = []
    
    for _ in range(n):
        a, b, c = map(int, input().split())
        
        if solved[a][b]:
            out.append("0")
            continue
        
        solved[a][b] = True
        
        if c < 240:
            balloons[a] += 1
            out.append(str(b))
        else:
            if balloons[a] < 3:
                balloons[a] += 1
                out.append(str(b))
            else:
                out.append("0")
    
    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```该实现直接镜像了前面描述的状态机。 这`solved`表的大小使用问题约束：最多 410 个团队和 13 个问题，因此我们分配稍微多一点以避免索引出现偏差问题。 这`balloons`数组跟踪每支球队的总计。 

一个微妙的点是我们标记`solved[a][b] = True`当我们检测到第一个解时，在应用时间逻辑之前立即进行。 这确保了即使时间条件不同，重复提交也不会意外地重新进入奖励逻辑。 

我们还将输出累积在列表中并打印一次，这避免了重复的 I/O 开销。

 ## 边缘情况

 重复一个棘手的情况来解决跨越冻结边界的问题。 假设一个团队在冻结之前解决了一个问题，并在冻结之后再次解决了问题：

 输入：```
1 1 100
1 1 250
```首次提交集`solved[1][1] = True`并奖励一个气球。 第二次提交立即使已解决的检查失败并输出 0。甚至从未考虑冻结规则，因为第一个解决条件已经被破坏，这与问题定义相匹配。 

另一个边缘情况是在冻结时恰好达到气球限制：```
1 1 10
1 2 20
1 3 30
1 4 240
```经过 3 次预冻结求解后，`balloons[1] = 3`。 第四次提交恰好发生在 240，因此处于冻结后状态。 由于该条件要求气球数量严格少于 3 个，因此不奖励气球。 实施检查`balloons[a] < 3`，所以输出正确为 0。
