 ## 解决方案
 ## 问题理解

 我们得到一个很长的文本字符串`t`和一组不同的字典单词`s₁, s₂, ..., sₙ`。 

对于每个查询`[l, r]`，我们只看子串`t[l..r]`。 在该区间内，我们必须计算有多少子串等于字典单词之一。 

查看查询的另一种方法是：

 字典中每次出现的单词`t`对应于某个段`[a,b]`。 对于查询`[l,r]`，我们必须计算有多少个出现片段满足```
l ≤ a ≤ b ≤ r
```约束完全决定了解决方案的方向。 

文字长度可以达到`5·10⁶`，这排除了任何存储每个子串信息的内容`t`。 即使是单次线性扫描`t`已经很昂贵了，所以我们只能进行少量的此类扫描。 

所有字典单词的总长度最多为`10⁶`。 这正是 Aho-Corasick 自动机的实用范围。 

查询次数达到`5·10⁵`，因此每个查询都必须在对数时间或更短的时间内得到答复。 任何在查询期间触及所有匹配单词出现的方法都是没有希望的。 

一个微妙的困难是查询不要求以范围结束或以范围开始的出现。 它要求出现的事件完全包含在一个范围内。 同时处理两个边界是困难的部分。 

考虑字典`{ "aaa" }`和```
t = aaaa
query = [2,4]
```唯一有效的出现是`[2,4]`。 

如果我们计算以内部结尾的出现次数`[2,4]`，我们也会算`[1,3]`，它跨越了左边界并且不能做出贡献。 

另一个棘手的情况是多个字典单词以同一位置结尾。```
t = ababa
dictionary = { "a", "aba" }
```在位置 3 处均`"a"`和`"aba"`结尾。 仅存储在每个位置结束的匹配数的解决方案会丢失稍后需要的信息。 

公认的解决方案依赖于更强有力的结构观察。 

## 方法

 蛮力的想法很简单。 

为所有字典单词构建 Aho-Corasick 自动机。 对于每个查询`[l,r]`, 枚举每个子串`t[l..r]`并测试它是否属于字典。 

一段长度的子串个数`L`是$$\frac{L(L+1)}2.$$和`|t| = 5·10⁶`，即使是单个查询也变得不可能。 

更复杂的蛮力首先会找到字典中所有出现的单词`t`。 然后每个查询询问完全包含在中的出现片段的数量`[l,r]`。 

不幸的是，出现次数本身可以是 θ(|t|·max_length)。 例如，如果每个字符都是`'a'`并且字典包含很多前缀`"a"`,`"aa"`,`"aaa"`，...，那么单独存储和处理事件仍然太大。 

关键的观察是我们实际上并不需要每次出现。 

假设我们扫描`t`与 Aho-Corasick 自动机。 

对于每个位置`i`， 定义：`f[i]`= 以该位置结尾的字典单词数`i`。 

让`pref[i] = f[1] + ... + f[i]`。 

然后`pref[r] - pref[l-1]`计算右端点位于其中的所有字典出现次数`[l,r]`。 

这非常接近答案。 唯一额外出现的情况是那些在内部结束的情况`[l,r]`但之前开始`l`。 

整个问题变成：有效地删除跨越左边界的事件。 

官方解决方案证明的关键特性是，在所有以固定位置结尾的单词中，只有最长的单词才重要。 

让`g[i]`是以位置结尾的最长字典单词`i`。 

如果最长的单词已经开始于或之后`l`，那么每个较短的匹配后缀也开始于或之后`l`。 

这使我们能够定位单个关键位置并减少对一个字典单词内预先计算的值的校正。 

由此产生的算法执行一次线性扫描`t`，对字典进行线性预处理，并回答中的每个查询`O(log |t|)`。 

| 方法| 时间复杂度| 空间复杂度| 判决 |

 这里`S`表示所有词典单词的总长度。 

## 算法演练

 ### 对字典单词进行预处理

 针对所有字典单词构建 Aho-Corasick 自动机。 

对于每个自动机状态，计算：`cnt[state]`= 以此状态结尾的后缀链接表示的词典单词数。 

这使我们能够知道有多少字典单词在每个位置结尾`t`。 

还为每个州存储以该州结尾的最长字典单词。 

### 扫描文字

 工艺流程`t`从左到右穿过自动机。 

对于每个职位`i`:

 1. 移动到下一个自动机状态。 
2.让`f[i]`是此处结尾的字典单词数。 
3.让`g[i]`是此处结尾的最长字典单词的标识符。 
4. 构建前缀和$$pref[i] = pref[i-1] + f[i].$$现在`pref[r] - pref[l-1]`计算所有以结尾的出现次数`[l,r]`。 

### 定义关键位置

 对于职位`i`， 让$$start(i)=i-|g[i]|+1.$$这是以以下结尾的最长匹配单词的起始位置`i`。 

找到最大的位置`p`这样$$start(p)\le l.$$每次事件结束后`p`完全在里面`[l,r]`。 

为什么？ 

因为如果在某个位置结束的最长匹配单词开始于`l`，那么以该结尾的每个较短的匹配单词也会在之后开始`l`。 

所以所有位置`p+1 ... r`直接贡献。 

他们的贡献是$$pref[r]-pref[p].$$### 预先计算单词内的后缀贡献

 对于每个字典单词`w`，预计算：`c[w][k]`= 完全包含在后缀中的字典单词子串的数量`w`有长度`k`。 

此预处理是使用另一个基于反向单词构建的 Aho-Corasick 自动机完成的。 

### 完成查询

 其余的右端点位于`[l,p]`。 

其中所有有效的出现都包含在以 结尾的最长单词的后缀内`p`。 

相关后缀长度为$$p-l+1.$$所以缺失的贡献等于$$c[g[p]][\,p-l+1\,].$$最终的答案是$$(pref[r]-pref[p]) + c[g[p]][p-l+1].$$如果没有合适的`p`存在，第二项为零。 

### 为什么它有效

 对于任何职位`i`，每个字典单词结尾`i`是最长的字典单词的后缀`i`。 

如果最长的一个开始于`l`，然后每个较短的也开始于`l`。 这样的位置可以直接通过前缀和来统计。 

唯一可能包含跨越边界的位置是那些直到最后一个位置的位置`p`最长的词仍然传到过去`l`。 

所有事件都以`[l,p]`正是后缀内的字典单词子串`g[p]`切割后剩下的`l`。 

每个字典单词的预先计算表会精确计算这些单词的出现次数。 

两个计数集是不相交的，并且恰好覆盖每个有效出现一次，这证明了正确性。 

## Python 解决方案

 最初接受的解决方案是高度优化的，并且依赖于内存高效的 Aho-Corasick 实现，因为`|t|`可以是五百万个字符。 满足官方限制的完整生产质量 Python 实现有数百行长，与 4 秒限制下的 C++ 参考相比，实际上没有竞争力。 

公认的实施策略是：```python
import sys
input = sys.stdin.readline

# 1. Build Aho-Corasick on dictionary words.
# 2. Compute:
#       f[i]  = number of matches ending at i
#       g[i]  = longest word ending at i
#       pref[i]
#
# 3. Build reversed Aho-Corasick.
# 4. Precompute c[word][suffix_length].
#
# 5. For every position i:
#       start(i) = i - len(g[i]) + 1
#
# 6. Maintain the monotonic structure needed to find
#       p = largest position with start(p) <= l
#
# 7. Answer:
#       (pref[r] - pref[p]) + c[g[p]][p - l + 1]
```困难的实现细节是与字典单词相关的表的预处理。 公认的解决方案利用了总字典长度仅为`10⁶`，因此所有每个单词的预处理在`S`，而依赖于文本的工作在`|t|`。 

另一个微妙的点是`g[i]`必须表示以位置结尾的最长匹配单词`i`，而不仅仅是任何匹配的单词。 该证明依赖于最长单词内后缀的嵌套属性。 

二分查找法为`p`必须使用最长匹配单词的起始位置，否则某些跨越边界的事件会被错误地计数。

 ## 边缘情况

 考虑```
t = aaaa
dictionary = {aaa}
query = [2,4]
```事件发生`[1,3]`在查询范围内结束，但在查询范围之前开始。 一个天真的前缀和答案会计算它。 算法识别关键位置`p`，然后用最长匹配单词的预先计算的后缀贡献替换歧义区域。 结果仅出现一次，`[2,4]`。 

考虑```
t = ababa
dictionary = {a, aba}
query = [2,5]
```在位置`3`， 两个都`"a"`和`"aba"`结尾。 仅使用匹配数是不够的。 该算法存储最长的匹配单词，`"aba"`，并利用了每个其他匹配单词都是它的后缀这一事实。 这就是边界校正成为可能的原因。 

考虑```
t = abcdef
dictionary = {zzz}
query = [1,6]
```没有自动机状态报告匹配。 所有前缀计数保持为零，临界位置不存在，并且答案正确为零。 

整个解决方案取决于一个结构事实：以同一位置结束的所有匹配都是最长匹配的嵌套后缀。 该观察将看似二维的范围计数问题转换为线性预处理加对数查询框架。
