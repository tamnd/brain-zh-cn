 ## 解决方案
 ## 问题理解

 我们设置了两个相互作用的冷却系统，其行为就像可及时重复使用的动作。 一个动作是一种产生金币的能力，可以重复使用，但每次使用后，它会在固定的时间内变得不可用。 第二个动作是一个重置工具，可以恢复所有其他冷却时间，允许立即重用黄金生成能力，但它也有自己的冷却时间。 

目标是模拟固定时间窗口内的最佳使用顺序，并计算可以执行黄金生成操作的次数。 每次执行都会产生固定数量的黄金，因此最大化黄金相当于最大化有效执行的数量。 

多个测试用例的输入大小很大，最多有 10^4 个用例，总参数总和为 10^7。 这排除了每个测试用例逐秒或逐事件迭代的任何模拟。 即使是以小增量推进时间的天真贪婪模拟，在最坏的情况下每个测试用例也会降级为 O(m)，当 m 在许多情况下达到 10^6 时，这将超出限制。 

当重置工具比主要能力的冷却时间快得多或慢得多时，就会出现关键的边缘情况。 如果速度非常快，玩家可以有效地连续重置以几乎连续地绕过冷却时间。 如果它非常慢，它就变得毫无用处，并且解决方案退化为主要能力的简单周期性使用。 另一个微妙的情况是当 m 很小时，没有重置交互变得有用，并且答案只是下限（m / a）+ 1，具体取决于是否计算零时间使用。 

幼稚的方法往往会失败，因为假设总是最佳地立即重用重置或忽略冷却时间之间的时序对齐，这会导致在边界对齐情况下（例如 a = b 或 b 稍微超过 a 时）错误计数。 

## 方法

 强力模拟将明确地对时间进行建模，跟踪两个项目中的每一个何时变得可用。 每时每刻，我们都在决定是使用主要能力还是重置工具。 这是可行的，因为系统状态是完全确定性的并且很小，但是当我们考虑所有可能的动作序列时，它在结构上基本上是指数的，并且即使是贪婪模拟每个测试用例仍然花费 O(m) ，因为在最坏的情况下单位步骤或事件跳跃的时间推进仍然发生 O(m) 次。 当 m 达到 10^6 和 10^4 测试用例时，这是不可行的。 

关键的观察是，只有两种事件很重要：使用主要能力，以及在重置工具变得有益后立即使用它。 系统结构崩溃成重复的循环。 主要技能有固定的冷却时间a，重置工具有冷却时间b。 重置后，主技能可以立即使用，如果b足够小，可以有效压缩未来的冷却间隙。 这个过程变成了一种周期性模式，我们在正常的冷却进程和偶尔的重置之间交替，这些重置比基本时间表允许的更早“插入”主要能力的额外用途。 

这将问题简化为确定每次重置可以在基线计划上解锁多少额外用途，以及在 m 秒内可以执行多少次重置。 一旦我们描述了每个周期的增益，答案就变成了简单的算术评估而不是模拟。

 ## 算法演练

 核心思想是比较两个时间线：一个不使用重置工具，另一个是每当重置增加可用主要能力施放数量时我们就最佳地插入重置。

1. 首先计算主要能力在没有任何重置交互的情况下的基线使用次数。 由于第一次使用可能发生在时间 0，然后每隔一秒发生一次，因此计数为下限 (m / a) + 1。这确定了最低保证金币。 
2. 请注意，每次我们成功使用重置工具时，我们都会立即解锁主要能力的一项额外用途，早于其他用途。 这种“额外施法”是在最佳游戏中重置使用的唯一好处。 
3.重置工具本身只能每b秒使用一次。 因此，在时间 m 内可用的最大重置次数为 Floor(m / b) + 1，再次假设在时间 0 立即使用。 
4. 每次重置并不一定总是产生值。 仅当重置时主要技能仍处于冷却状态时才有用。 如果它已经可用，则使用重置没有任何好处。 
5. 关键的减少是，交互有效地取决于冷却时间 a “落后”重置时间表 b 的次数。 有益重叠的数量对应于在主要能力自然可用之前重置到达的频率。 
6. 这导致了直接计算：通过计算b在时间窗口内“超越”a的次数来模拟对齐。 这可以表示为计数整数间隔，其中重置时间严格小于主要能力准备间隙，从而产生简单的速率算术比较。 
7. 最终答案是基线使用情况加上每次基线恢复完成之前发生的有效重置次数。 

表达最终计数的一种紧凑方式是：

 我们考虑使用间隔为 b 的重置可以“压缩”长度为 a 的等待间隔多少次。 每个长度为 a 的间隔都可以通过重置来部分填充，每当 b < a 时贡献额外的使用，否则不贡献任何内容。 

### 为什么它有效

 该系统具有单调结构：主要能力的可用时间形成一个固定的算术级数，除非通过重置进行修改，并重置自身形成另一个算术级数。 唯一有意义的交互是在主要能力的下一次预定可用性之前严格执行重置时。 每个此类事件都会将等待时间减少一个冷却单位a，并且任何重置都不会在每个此类重叠间隔内创建一次以上的额外使用。 这确保了两个级数之间的重叠计数与附加转换的数量完全匹配，从而使算术解决方案准确。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []
    
    for _ in range(T):
        a, b, m = map(int, input().split())
        
        # baseline uses of Midas (including time 0)
        base = m // a + 1
        
        # number of times we can press refresher
        resets = m // b + 1
        
        # each reset can at most create one extra use,
        # but only if reset happens before cooldown completes.
        # Effective gain is bounded by overlaps of cycles.
        
        if b >= a:
            # refresher too slow to matter
            extra = 0
        else:
            # each reset can contribute at most one extra Midas use,
            # but cannot exceed number of baseline gaps
            extra = min(resets, base - 1)
        
        out.append(str(base + extra))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```基线计算`m // a + 1`计算从零时间开始的所有自然激活。 重置计数`m // b + 1`代表我们有多少次机会尝试冷却时间刷新。 有条件的分割处理唯一在结构上有意义的政权变化：重置是否足够快以干扰冷却进程。 什么时候`b >= a`，重置永远不会提前到达以改善时序，因此答案保持在基线。 什么时候`b < a`，每次重置都有可能将一个错过的等待期转化为额外的使用，但我们不能超过可用基线间隙的数量，即`base - 1`。 

该解决方案通过将交互减少到两个算术级数之间的有界匹配来避免显式调度。 

## 工作示例

 我们追踪两个有代表性的案例。 

### 示例 1：`a = 40, b = 10, m = 50`基线使用有时为 0、40，因此 base = 50 // 40 + 1 = 2。 

重置发生在时间 0、10、20、30、40、50，因此重置 = 6。 

由于 b < a，所以 extra = min(6, 1) = 1。 

总计 = 3。

### 示例 2：`a = 1, b = 1, m = 1000000`基线是 1,000,001 次使用。 重置也会发生 1,000,001 次，但由于 b >= a，所以 extra = 0。每次重置恰好在 Midas 可用时到达，因此不可能进行加速。 

跟踪显示，尽管频繁重置，但不存在可利用的冷却瓶颈。

 ## 边缘情况

 当`b >= a`，算法立即禁用额外贡献。 例如，使用输入`a = 60, b = 200, m = 960`，基线给出`960 // 60 + 1 = 17`。 重置发生得太慢，无法在自然迈达斯恢复之前落地，因此在完整的语句上下文中，额外仍然为 0，输出按黄金因子缩放为 17。 

什么时候`a = 1`，基线已经达到最大使用密度，因此重置无法添加任何内容。 为了`a = 1, b = 1, m = 10`，基线为 11，额外为 0。 

当`m < a`，基线变为 1，意味着只能进行初始转换。 即使重置很频繁，也没有冷却时间可以压缩，因此额外值始终为 0。 

这些案例证实了该公式在简并时序机制下自然正确地崩溃。
