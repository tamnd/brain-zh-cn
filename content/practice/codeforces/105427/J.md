 ## 解决方案
 ## 问题理解

 我们得到了一系列物品，每个物品都有一个正的大小，以及固定数量的侦察兵。 每件物品必须分配给一名侦察兵。 侦察兵最多可以携带两个物品，侦察兵的负载是分配给他们的物品大小的总和。 有些侦察兵可能不会收到任何物品，这是允许的。 

目标是分配物品，使侦察兵携带的最大负载尽可能小。 换句话说，我们希望在最多 M 个侦察兵中对项目进行配对（或将它们单独保留），以使最大对和或单个项目最小化。 

约束 1 ≤ N ≤ 2M 是使问题可行的结构线索。 它保证有足够的侦察兵，这样我们就不需要在任何有效的解决方案中为每个侦察兵分配超过两个项目，事实上，它暗示问题从根本上来说是关于配对项目的。 

由于 M 至多为 100，N 至多为 200。这立即告诉我们，大约 O(N^2 log N) 甚至 O(N^3) 的解决方案可能会生存，但一般结构中的任何指数都是危险的，除非经过严格修剪。 

当一个项目与所有其他项目相比非常大时，就会出现一种幼稚但重要的边缘情况。 例如，如果我们有物品`[100, 1, 1, 1]`对于许多侦察兵来说，最好的策略是将小件物品配对在一起，而将大件物品单独放置。 总是任意配对的粗心贪婪者可能会分配`100 + 1`并不必要地增加答案。 “每个球探最多两名”的结构意味着配对决策决定了结果。 

另一个微妙的边缘情况是 N = 2M 时。 然后，每个侦察兵必须恰好拿走两件物品，或者根据配对结构，一名侦察兵必须恰好拿走一件物品。 这消除了灵活性，并使配对决策受到全局限制。 

## 方法

 强力解释是尝试将项目分配到最多两个大小的组中的所有方法，然后计算每个组中的最大总和并取最小值。 这相当于枚举所有匹配加上单例的位置，这在组合上是爆炸性的。 即使对于 N = 20，配对的数量也已经像双阶乘一样增长，而对于 N = 200，这是完全不可行的。 

关键的观察是，我们正在有效地选择如何配对项目，并且某些项目可能保持未配对状态。 由于每个侦察兵最多可以携带两个物品，并且我们至少有 N/2 个侦察兵，因此每个物品都可以被认为是成对的或单独的，除了配对结构之外没有容量冲突。 

目标仅取决于所选对或单例的总和，因此我们希望最小化最大对总和。 这是一个经典的“最小化最大配对成本”结构。 处理这个问题的标准方法是对项目和极值进行排序，但如果没有正确性论证，仅靠贪婪论证显然是不够的。 

更深层次的结构是，如果我们固定一个候选答案X，我们可以询问是否可以将项目分配到对/单例中，使得没有组超过X。这成为一个可行性问题。 如果我们可以检查可行性，那么我们就可以二分搜索答案。 

为了测试固定的 X，我们希望最大化配对，同时遵守任何对必须具有总和 ≤ X 的约束。如果我们无法配对一个项目，它一定是一个单例，因此它本身必须 ≤ X。这将问题简化为在阈值下匹配小项目和大项目，这可以在排序后贪婪地完成。 

这将问题转化为 X 上的单调可行性检查，从而能够在答案范围内进行二分搜索。

 ## 算法演练

 ### 1. 按升序对所有项目尺寸进行排序

 排序使我们能够推理极端的配对，并保证如果一个小项目无法与大项目配对，则任何中间项目都不起作用。 

### 2.定义一个函数`can(X)`检查是否所有项目都可以分配最大负载 ≤ X

 该函数编码了核心约束：每个侦察兵的负载不得超过X。 

### 3.内部`can(X)`，使用两指针策略

 在最小的未使用项目处维护一个指针，在最大的未使用项目处维护一个指针。 

### 4. 尝试将最大的剩余项目与最小的可能伙伴配对

 如果最大项和最小项之和≤X，我们将它们配对并将两个指针向内移动。 这是最优的，因为将最大的项目与最小的可行伙伴配对可以最大限度地减少对未来约束的阻碍。 

如果总和超过 X，则最大的项不能与除自身之外的任何其他项配对，因此必须单独分配它。 如果仅此一项就超过X，则该配置是不可能的。 

### 5. 继续，直到分配完所有项目

 如果我们成功分配这些规则下的所有项目，`can(X)`返回真。 

### 6. 二分查找最小的 X 使得`can(X)`是真的

 答案是单调的：如果 X 起作用，任何更大的值也起作用。 

### 为什么它有效

 正确性取决于内部的贪婪配对不变量`can(X)`。 在每一步中，我们要么将最大的剩余项目与最小的可行伙伴配对，要么在不可能配对时将其隔离。 关键属性是最大的项是最受约束的元素，因为它具有最少的有效伙伴。 如果它无法与最小的项目配对，它就无法与其他任何项目配对，因此在任何有效的解决方案中都不可避免地强制它单独存在。 这确保了贪婪决策永远不会阻止原本可能存在的可行配置。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def can(a, m, x):
    i, j = 0, len(a) - 1
    used = 0

    while i <= j:
        if i == j:
            return a[i] <= x
        if a[i] + a[j] <= x:
            i += 1
            j -= 1
        else:
            if a[j] > x:
                return False
            j -= 1
        used += 1
        if used > m:
            return False
    return True

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    a.sort()

    lo, hi = max(a), a[-1] + a[-2] if n > 1 else a[0]

    while lo < hi:
        mid = (lo + hi) // 2
        if can(a, m, mid):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```该实现首先对项目进行排序，以便可行性检查可以使用两指针策略。 二分搜索范围从最大单个项目开始，因为任何有效的分配都不能具有小于最大项目本身的最大负载。 上限是最差可能的对和。 

这`can`功能仔细跟踪配对。 条件`a[i] + a[j] <= x`尝试贪婪地形成最极端有效的配对。 如果失败，我们将被迫单独放置最大的项目，并立即确保它仍然符合阈值。 

一个微妙的细节是对已使用组的跟踪。 由于每一对或单例对应一个侦察兵，我们确保永远不会超过 m 组。 

## 工作示例

 ### 示例 1

 输入：```
3 4
10 10 10
```排序数组：`[10, 10, 10]`二分搜索检查可行性：

 | 步骤| 我| j | 行动| 团体成立 |
 | ---| ---| ---| ---| ---|
 | 1 | 0 | 2 | 10+10 = 20 ≤ X (X=10？失败，所以调整推理) | 取决于 X |

 对于 X = 10，不可能配对，因此每个 10 必须是单独的。 这需要 3 名球探，而我们有 4 名，所以这很有效。 

最小最大负载为 10。 

这表明，当所有项都相等时，配对实际上是不必要的，单例占主导地位。 

### 示例 2

 输入：```
5 4
9 12 3 9 10
```排序：`[3, 9, 9, 10, 12]`尝试 X = 12：

 | 步骤| 我| j | 配对决定| 结果 |
 | ---| ---| ---| ---| ---|
 | 1 | 0 | 4 | 3 + 12 ≤ 12？ 没有| 12 独自一人 |
 | 2 | 0 | 3 | 3 + 10 ≤ 12 是 | 对 (3,10) |
 | 3 | 1 | 2 | 9 + 9 ≤ 12 否 | 9 独自一人 |
 | 4 | 1 | 1 | 9 独自一人 | 完成 |

 所有物品都分配给 4 个侦察兵，因此 X = 12 是可行的。 

这演示了如何尽早强制使用最大的项目来防止无效配对并保持可行性检查的正确性。

 ## 边缘情况

 一种重要的边缘情况是最佳解决方案使许多项目未配对。 考虑输入`3 4`所有项目均相同。 该算法正确地认识到配对是不必要的，并且每个项目都可以独立而不超过侦察限制。 可行性检查只是分配单例并确认约束。 

另一种情况是当存在一个非常大的项目时，例如`2 2 / 1 100`。 该算法立即强制`100`被隔离，因为配对会超出任何合理的阈值。 任何小于 100 的候选 X 都会被拒绝，因为可行性检查检测到`a[j] > X`并且很早就失败了。
