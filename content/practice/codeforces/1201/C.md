 ## 解决方案
 ## 问题理解

 我们得到一个数字列表，并允许将任何单个元素重复加一。 每个这样的增量都有一个操作的成本，并且我们的总预算最多为$k$运营。 目标不是最大化总和或任何全局统计量，而是在数组排序后最大化中位数。 

由于数组大小为奇数，因此中位数是最终位于位置的元素$n/2$排序后。 关键的困难在于，当我们增加一些元素时，排序顺序可能会改变，因此中位数并不与原始数组中的固定索引绑定。 

约束足够大，任何一一模拟操作的策略都是不可能的。 和$n$最多$2 \cdot 10^5$和$k$最多$10^9$，即使是单个操作循环的长度$k$显然会超出时间限制。 任何可行的解决方案都必须将问题简化为排序加线性处理或对答案的对数搜索。 

当贪婪地考虑直接增加中间位置时，会出现微妙的失败模式。 如果我们只增加当前的中位元素，我们会忽略这样一个事实：其右侧的其他元素可能也需要增加以在排序后保留其中位状态。 例如，如果我们仅单独增加中位数，则其右侧的较小元素仍可能阻止其成为排序后的中位数。 

如果我们试图维护动态排序结构并反复调整中位数，就会出现第二个错误。 由于重复插入和删除，这变得太慢，并且还掩盖了问题的真实结构：只有位于或高于中间位置的元素对最终答案很重要。 

## 方法

 暴力方法将模拟在元素之间所有可能的分布中应用操作的过程。 每次增量后，我们都会重新排列数组并跟踪中位数。 即使我们限制自己只在有希望的元素之间分配增量，可能的分布数量也会随着$k$，使得这种方法不可行。 

关键的观察是，一旦数组被排序，中位数就位于固定位置，并且只有从该位置开始的元素才能影响数组的大小。 中位数左侧的任何元素都不会限制中位数，因为增加它们只会帮助中位数或在重新排序后保持不变。 

这导致了一个贪婪的结构：我们想要提高中位数及其右侧的所有内容，以便将中位数尽可能地向上推。 如果我们固定中位数的目标值，我们可以检查需要多少次操作才能使右半部分的所有元素至少达到该值。 这自然会导致可行性检查。 

从这里开始，二分搜索就成为自然的工具。 我们搜索最大中值，以便可以将数组的中值和后缀提高到预算内的该水平$k$。 每次检查排序后都是线性的。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | 指数为$k$|$O(n)$| 太慢了 |
 | 最优（二分查找+贪心检查）|$O(n \log (k + \max a))$|$O(n)$| 已接受 |

 ## 算法演练

 我们首先对数组进行排序，使中位数位置固定。 让$m = n/2$。 从这一点开始，我们控制的中位数位于索引处$m$，并且只有索引$m, m+1, \ldots, n-1$强制执行候选中值的问题。 

1. 我们对数组进行排序，因为任何有关中位数的推理都需要稳定的排序。 如果不进行排序，我们就无法确定哪些元素限制了中位数。 
2. 我们定义一个函数来检查给定值是否$x$可以作为中位数来实现。 这个想法是强制索引中的每个元素$m$至少以后$x$，因为如果它们至少都是$x$，中位数也至少为$x$。 
3. 为了计算实现这一目标的成本，我们从索引迭代$m$到$n-1$并累积赤字$\max(0, x - a[i])$。 这表示将这些元素提升到所需的最小增量数$x$。 原因是增加中位数左侧的元素无助于保证中位数达到$x$，因为它们可以被较大的元素推出中间区域。 
4. 如果所需总成本在$k$，那么值$x$是可行的。 否则，它太大了。 
5.我们进行二分查找$x$。 下限是当前的中值，上限可以通过添加所有值来扩展$k$在最好的情况下对中值元素进行操作。 
6.最终的答案是最大可行的$x$。 

### 为什么它有效

 关键的不变量是，在排序数组中，中位数完全由从索引开始的后缀确定$m$。 任何成功使该后缀中的所有元素至少成功的策略$x$保证中位数也至少为$x$，因为至少有一半的元素将是$\ge x$。 相反，如果后缀不能提升为$x$在预算范围内，那么任何达到中位数的尝试$x$失败，因为控制区域中的某些元素仍低于$x$，迫使中位数下降。 这使得可行性检查既必要又充分。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def can(a, m, k, x):
    cost = 0
    for i in range(m, len(a)):
        if a[i] < x:
            cost += x - a[i]
            if cost > k:
                return False
    return True

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    a.sort()

    m = n // 2

    lo = a[m]
    hi = a[m] + k

    ans = lo
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(a, m, k, mid):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    print(ans)

if __name__ == "__main__":
    solve()
```排序步骤至关重要，因为它锁定了中间位置，以便所有关于可行性的推理都变得基于位置而不是基于价值。 辅助函数`can`直接编码这样的想法：只有右半部分有助于执行候选中值。 

二分搜索在这里是安全的，因为可行性是单调的：如果一个值$x$是可以实现的，那么任何较小的值也是可以实现的，因为它不需要更多的操作。 

上限选择$a[m] + k$反映了所有操作都集中在中值元素本身的最佳可能场景。 

## 工作示例

 ### 示例 1

 输入：```
3 2
1 3 5
```排序后的数组是`[1, 3, 5]`，中位指数为`1`。 

我们测试可行性：

 | x| 后缀 [3,5] 的成本 | 可行|
 | ---| ---| ---|
 | 3 | 0 | 是的 |
 | 4 | 1（只有5个已经可以，3个需要+1）| 是的 |
 | 5 | 2 | 是的 |
 | 6 | 3 | 没有|

 二分查找在 5 处停止。 

这表明中间元素和右侧元素必须一起提升； 仅增加中位数是不够的，因为后缀限制了可行性。 

### 示例 2

 输入：```
5 3
1 2 10 10 10
```排序后的数组是`[1, 2, 10, 10, 10]`，中位指数为`2`。 

| x| [10,10,10] 的成本 | 总成本| 可行|
 | ---| ---| ---| ---|
 | 10 | 10 0 | 0 | 是的 |
 | 11 | 11 3 | 3 | 是的 |
 | 12 | 12 6 | 6 | 没有|

 答案是11。 

这表明，一旦后缀已经包含较大的值，只需要部分提升，预算直接控制中位数可以向上推多远。

 ## 边缘情况

 关键的边缘情况是中位数已经是数组中的最大元素。 In that case, the suffix is very small and increasing only the median position might seem sufficient, but the feasibility check correctly accounts for any elements to the right that still need lifting.

 另一种情况发生时$k$非常大。 二分搜索会将中位数向上推，甚至超出所有现有元素，并且成本完全取决于后缀中有多少元素，而不是它们的初始分布。
