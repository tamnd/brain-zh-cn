 ## 解决方案
 ## 问题理解

 我们会得到一份任务完成时间的排序列表，从训练开始算起，以分钟为单位。 每次对应于解决单个任务的时间。 通过将每 1440 分钟分组到一个天存储桶中，可以将这些时间戳转换为日历日。 

如果一天的 1440 分钟间隔内至少有三项任务落入其中，那么一天就“成功”了。 困难在于日期边界取决于所选时区。 将时区移动整数小时相当于为每个时间戳添加 60 分钟的固定倍数，这可以跨天边界移动任务。 

目标是选择一个每小时轮班，以最大化最长的连续成功天数。 

输入大小最多可达 200,000 个时间戳。 这立即排除了任何在每个班次超过线性或接近线性的时间内重新计算每个班次行为的解决方案。 几天内的简单二次方法或任务的成对分组会太慢，而 24 次线性扫描的量级是完全可行的。 

当任务接近一天的界限时，就会出现一个微妙的问题。 一个小小的转变可以将一组密集的任务分成不同的日期，或者将稀疏的日期合并为密集的日期。 例如，如果轮班将一项任务推到前一天或后一天，则仅执行三项任务的一天可能会变得无效。 

另一个极端情况是没有任何一个班次能够在任何一天完成至少三项任务。 在这种情况下，答案为零，因为没有成功的一天可以形成连续的段。 

## 方法

 一个直接的想法是模拟每个可能的小时班次，并将任务分配重新计算为天数。 由于班次限制为整数小时，因此只有 24 个以 1440 分钟为模的不同偏移量。 

对于每个班次，我们在应用班次后使用整数除法将每个任务时间分配给日索引。 然后我们计算每天有多少任务落地。 最后，我们扫描生成的天数，以找到每天至少有三个任务的连续日指数的最长运行。 

强力结构将是，对于每个轮班，重新计算全天分配，然后对于每个日期范围重复检查窗口。 如果效率低下，这会退化为重复扫描或重新计算范围，在最坏的情况下导致大约 O(24·n·number_of_days) 行为，这是不必要的。 

关键的观察结果是移位空间很小且固定。 我们不需要跨班次优化； 我们只需要使每个班次评估在 n 中呈线性。 这将整个问题简化为 O(24n)。 日期分组本身可以使用哈希图来处理，并且可以通过仅对实际显示为成功的日期进行排序来计算连续段。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力重新计算和扫描效率低下 | O(24·n·D) | O(24·n·D) | O(D) | 太慢了|
 | 尝试所有班次并在每个班次进行哈希处理 | O(24 · n log n) | O(24 · n log n) | O(n) | 已接受 |
 | 尝试使用 hashmap + 排序键进行所有移位 | O(24 · n + 24 · k log k) | O(24 · n + 24 · k log k) | O(n) | 已接受 |

 这里 k 是一个班次中不同天数，最多为 n。 

## 算法演练

 ### 1.限制班次的搜索空间

 我们只考虑移动 k 小时，其中 k 的范围为 0 到 23。这已经足够了，因为添加 24 小时会将每个时间戳精确移动 1440 分钟，从而保留了日期分配。 

### 2. 应用班次并计算日指数

 对于每个班次值，我们将每个时间戳 t 转换为 t + shift · 60 并将其日期索引计算为 (t + shift · 60) // 1440。这将每个任务分配给该时区下的日历日。

此步骤是核心转换，因为它模拟边界如何相对于任务时间移动。 

### 3. 计算每天的任务数

 我们维护一个字典，将日期索引映射到任务数量。 对于每个转换后的时间戳，我们都会增加其日期的计数。 

这种聚合将潜在的大时间范围压缩为可管理的不同天数。 

### 4. 确定成功的日子

 如果一天的计数至少为三，则一天是成功的。 我们将所有此类日指数收集到一个单独的结构中。 只有这几天才能得出最终答案。 

### 5. 找出最长的连续成功天数

 我们对成功的日指数进行排序并线性扫描它们。 每当连续索引相差正好 1 时，我们就会延长当前的连续性； 否则我们重置它。 

记录所有班次的最大条纹长度。 

### 为什么它有效

 每个班次将时间戳定义为日存储桶的确定性分区。 对每个存储桶的任务进行计数可以完全捕获一天是否成功，因为成功仅取决于计数阈值。 对成功的日期进行排序并检查邻接性可以正确地重建日历结构，因为日期索引空间中的连续整数与同一班次下的连续日期完全对应。 由于每个有效配置都会在 24 个班次中进行测试，因此保证评估最佳的连续块。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    t = list(map(int, input().split()))
    
    best = 0
    
    for shift in range(24):
        offset = shift * 60
        cnt = {}
        
        for x in t:
            d = (x + offset) // 1440
            cnt[d] = cnt.get(d, 0) + 1
        
        good_days = []
        for d, c in cnt.items():
            if c >= 3:
                good_days.append(d)
        
        if not good_days:
            continue
        
        good_days.sort()
        
        cur = 1
        best_local = 1
        
        for i in range(1, len(good_days)):
            if good_days[i] == good_days[i - 1] + 1:
                cur += 1
            else:
                cur = 1
            if cur > best_local:
                best_local = cur
        
        if best_local > best:
            best = best_local
    
    print(best)

if __name__ == "__main__":
    solve()
```该解决方案循环遍历所有 24 个可能的小时班次。 对于每个班次，它都会重新计算日期分配并在字典中聚合计数。 仅保留至少完成三项任务的日期以供进一步处理。 

连续天计算是在仅对有效天进行排序后完成的，这避免了扫描大范围的空天。 比较纯粹是基于整数邻接，因此不需要超出整数差异的日历算术。 

一个常见的错误是忘记轮班仅限于小时，并试图优化所有分钟轮班，这是不必要的。 另一个方法是尝试维持跨班次的全局滑动结构，这会使正确性变得复杂，而不会提高渐近性能。

 ## 边缘情况

 少于三个任务的最小输入总是产生零，因为无论转移如何，没有一天可以满足成功条件。 该算法自然地处理这个问题，因为在任何轮班中没有一天达到阈值。 

边界密集的配置（例如围绕 1440 的倍数聚集的时间戳）测试转移是否正确地在相邻日期之间重新分配任务。 在这些情况下，正确性取决于移位后的整数除法，这在实现中是一致处理的。 

完全在一天内的统一集群表明，如果所有任务都保持在单个 1440 分钟的窗口内，那么无论进行多少转移都无法将成功天数增加到超过 1 天。
