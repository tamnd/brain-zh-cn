 ## 解决方案
 ## 问题理解

 我们得到了一小组编程竞赛问题，对于每个问题，我们知道如果分配给他们三个队友，每人需要多长时间来实现它。 值为`-1`意味着某个特定的队友根本无法解决该问题。 

团队只有一台共享计算机，因此无法并行工作。 他们的比赛时间也固定为 300 分钟。 每个问题，如果选择的话，都会被分配给一个队友，并且时间贡献是该队友对该问题的相应实施时间。 目标是选择尽可能多的不同问题，以便将每个选定的问题分配给可以解决该问题的队友，并且所有选定的实施时间总和不超过 300。 

输入的结构本质上是最多 14 个项目的集合，每个项目都是三个“背包”上成本的三倍，其中每个项目可以与其中一个有效成本一起获取，也可以完全跳过。 我们没有被要求最大化总价值，而是最大化在单一全局时间预算下选择的项目数量。 

约束条件`n ≤ 14`是关键信号。 对于最多 14 个问题，任何探索问题子集的解决方案都是可行的，因为`2^14 = 16384`，它足够小，可以显式检查每个子集。 每个项目的三个选择的附加维度不会改变该可行性，因为它可以通过简单的决策规则在每个子集中解决。 

唯一微妙的边缘情况来自`-1`价值观。 天真的解释可能会认为`-1`为零或错误地忽略可行性，这将导致不可能的分配。 

例如，如果问题是：```
A -1 20 10
```那么将其分配给第一个队友是不可能的。 错误的贪心方法可能仍会尝试“选择最小时间”并错误地将其视为零，从而导致过度计算可行集。 正确的处理是完全排除该选项。 

另一个边缘情况是当所有三个值都是`-1`。 在这种情况下，即使所有其他问题都很小，问题也永远无法选择，并且必须始终被忽略。 

## 方法

 思考这个问题的一个直接方法是想象尝试所有可能的选择和分配问题的方法。 对于每个问题子集，我们将决定哪个队友解决每个选定的问题并计算总时间。 如果总数最多为 300，我们将根据该子集的大小更新最佳答案。 

这种蛮力观点是正确的，但有两层组合。 首先，有`2^n`问题的子集。 对于每个子集，每个选定的问题最多有 3 个分配选择，因此简单的扩展看起来像`O(3^n)`。 即使与`n = 14`，如果不小心实现，这已经是临界点，尽管在优化代码中技术上仍然可行。 然而，没有必要独立考虑所有分配。 

关键的简化在于，对于任何固定的问题子集，最优分配都是微不足道的：对于子集中的每个问题，我们只关心三个队友之间的最小有效时间。 就作业选择而言，问题之间不存在交互，因为无论谁解决，每个问题都消耗相同的共享时间资源。 这完全删除了第二个组合层。 

因此，问题归结为选择项目子集，其中每个项目都有一个有效成本，定义为其有效实施时间的最小值。 然后，我们希望总成本不超过 300 的最大项目数。这是一个经典的背包变体，其目标是在少量项目数的情况下实现基数最大化。 

我们现在只需要评估所有子集，计算它们的总成本和大小，并跟踪最佳可行大小。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 完整的作业枚举 | O(3^n) | O(3^n) | O(n) | 太慢了 |
 | 具有最小成本降低的子集枚举 | O(2^n·n) | O(2^n·n) | O(n) | 已接受 |

 ## 算法演练

 我们首先通过将每个问题的三个时间值转换为单个有效成本来预处理每个问题。 该成本是有效值中最小的，忽略任何`-1`条目。 如果所有三个值都是`-1`，我们将问题标记为不可用。 

接下来，我们使用位掩码枚举问题的所有子集。 每个子集代表我们试图解决的一组候选问题。 

1. 对于每个问题，计算其有效成本作为其可用队友时间的最小值。 如果全部都是`-1`，我们将其视为无限成本并确保它永远不会被选择。 
2. 迭代所有蒙版`0`到`2^n - 1`。 每个掩码都编码问题的子集。 
3. 对于给定的掩码，计算两个值：所选问题的数量和所需的总时间。 
4. 在计算总时间时，如果它超过 300，我们会提前停止该子集，因为它无法通过继续来改进。 
5. 如果总时间在 300 以内，我们将用迄今为止看到的最大问题数来更新答案。 

每个子集内的早期停止很重要，因为一旦可行性已经被破坏，它就可以避免不必要的求和，即使在 Python 中也能保持解决方案的效率。 

### 为什么它有效

 对于每个问题，将其分配给队友独立于所有其他问题，因为没有每人的能力限制，只有单一的全局时间预算。 这消除了分配决策之间的任何耦合。 因此，用最小可行分配成本替换每个问题可以保留每个子集的可行性，并且不会增加有效分配的成本。 任何最优解都必须对应于某个子集，并且在该子集中，为每个问题选择最小成本分配始终是最优的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    cost = []

    for _ in range(n):
        parts = input().split()
        name = parts[0]
        t = list(map(int, parts[1:]))

        best = 10**9
        for x in t:
            if x != -1:
                best = min(best, x)

        cost.append(best)

    ans = 0

    for mask in range(1 << n):
        total = 0
        cnt = 0

        for i in range(n):
            if mask & (1 << i):
                if cost[i] == 10**9:
                    total = 10**9
                    break
                total += cost[i]
                cnt += 1
                if total > 300:
                    break

        if total <= 300:
            ans = max(ans, cnt)

    print(ans)

if __name__ == "__main__":
    solve()
```预处理步骤将每个问题压缩为单个标量成本，这对于减少搜索空间至关重要。 然后，位掩码循环直接探索所有子集。 子集循环内的提前终止条件确保一旦确定不可行，我们就不会浪费时间来积累成本。 

一个微妙的实现细节是用非常大的数字而不是零来表示不可能的问题。 使用零会错误地允许免费选择无法解决的问题，从而人为地夸大答案。 使用像这样的哨兵`10**9`确保此类子集自动超出预算。 

## 工作示例

 考虑一个具有三个问题的简化输入：```
P1: 50 60 70
P2: -1 40 90
P3: 100 20 80
```经过预处理后，我们得到成本：

 P1 = 50，P2 = 40，P3 = 20

 我们现在枚举子集。 

| 面膜| 选择| 总成本| 计数 | 有效 |
 | --- | --- | --- | --- | --- |
 | 000 | 000 {} | 0 | 0 | 是的 |
 | 001| P1 | 50 | 50 1 | 是的 |
 | 010| P2 | 40 | 40 1 | 是的 |
 | 011| P1,P2 | 90 | 90 2 | 是的 |
 | 100 | 100 P3 | 20 | 1 | 是的 |
 | 101 | 101 P1,P3 | 70 | 70 2 | 是的 |
 | 110 | 110 P2、P3 | 60| 2 | 是的 |
 | 111 | 111 全部 | 110 | 110 3 | 是的 |

 最好的子集是总成本为 110 的所有三个问题，给出答案 3。该跟踪证实，降低到最小每个问题成本保留了所有有意义的权衡。 

现在考虑一个不可能出现的问题的情况：```
P1: -1 -1 -1
P2: 200 200 200
```成本变为：

 P1 = 不可能，P2 = 200

 | 面膜| 选择| 总成本| 有效 |
 | --- | --- | --- | --- |
 | 01 | P1 | 无效| 没有|
 | 10 | 10 P2 | 200 | 200 是的 |
 | 11 | 11 P1,P2 | 无效| 没有|

 最佳答案是 1，因为尽管 P1 存在于输入中，但它根本无法做出贡献。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(2^n·n) | O(2^n·n) | 每个子集通过扫描最多 n 个项目来评估 |
 | 空间| O(n) | 仅存储每个问题的成本和几个柜台|

 和`n ≤ 14`,`2^n`最多为 16384，乘以 14 仍然会产生远低于数十万次运算的结果，这完全符合时间限制。

 ## 边缘情况

 一种边缘情况是，每个问题对于至少一个队友来说是不可能的，但通过另一个队友仍然可行。 例如，问题可能看起来像`-1 10 200`。 该算法正确地采用 10 作为成本并忽略`-1`，确保问题仍然可用。 

另一个边缘情况是所有队友都无法解决某个问题。 在这种情况下，它的成本变得无限，并且包含它的任何子集都会被自动拒绝。 枚举仍然考虑此类子集，但一旦检测到哨兵成本，它们就会立即被过滤掉。 

最后一个微妙的情况是，存在许多小成本问题，而最佳解决方案需要解决几乎所有问题，直到预算完全饱和。 位掩码枚举保证这些组合被显式检查，并且提前停止仅影响不可行子集的修剪，而不是跳过有效组合。
