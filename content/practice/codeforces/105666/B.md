 ## 解决方案
 ## 问题理解

 我们有一组自己的怪物，每个怪物都由两个强度值描述。 第一个值表示该怪物在与 0 类敌人战斗时的强度，第二个值表示其与 1 类敌人战斗时的强度。 我们还获得了对手怪物的集合，每个怪物都属于这两种类型中的一种。 0型敌人只能使用第一强度值来战斗，而1型敌人只能使用第二强度值来战斗。 

任务是确定是否可以将我们的怪物分配给所有敌方怪物，以便每个敌人都被不同的怪物击败，并且所选怪物在相应类型中具有足够的强度。 

核心困难在于，我们的每个怪物都是灵活的，因为它可以用于任一角色，但一旦分配，它就会被消耗。 这个决定不是局部的，因为在错误的地方使用强大的万能怪物可能会阻碍以后的可行性。 

输入大小表明怪物和敌人的数量可能很大，最多可达 100,000 个。 这立即排除了任何二次匹配方法，例如尝试所有配对或运行具有较大开销的流算法。 解决方案必须接近线性或对数线性，通常为 O(n log n)，这强烈建议排序加上贪婪选择。 

当一种类型占据主导地位时，就会出现微妙的边缘情况。 例如，如果有很多 0 型敌人，但只有少数怪物能够对付它们，那么当 1 型敌人需要更强的分配时，贪婪地为每个敌人分配最强的可用怪物的幼稚策略可能会失败。 另一种失败模式是独立处理两种怪物属性，忽略了每个怪物都是两种类型之间的共享资源。 

## 方法

 强力解释是将其视为二分分配问题。 每个敌人都必须与满足其要求的独特怪物相匹配。 人们可以尝试回溯或最大二分匹配。 虽然这种方法是正确的，但它需要探索许多作业。 在最坏的情况下，n 个怪物中的每一个都可能以多种方式分配给 n 个敌人，从而导致指数分支或基于流的方法至少为 O(n3/2) 行为，这对于大输入来说太慢了。 

关键的观察结果是，在每种敌人类型中，按所需强度排序揭示了一种优势结构。 如果我们按照强度从高到低的顺序处理固定类型的敌人，那么任何能够击败更强敌人的怪物也有能力击败所有同类型中较弱的敌人。 这创建了一个单调的可行性区域。 

一旦我们修复了这个顺序，问题就变成了为每个敌人的要求阈值选择仍然满足它的最弱的可能怪物。 这是最佳的原因是，为以后更严格的约束保留更强大的怪物可以防止未来的失败。 这是阈值约束下的经典贪婪匹配。 

我们首先仅使用怪物的第一个力量值来解决所有 0 类敌人。 然后我们使用第二强度值独立解决1类敌人。 正确性来自于这样一个事实：一旦我们承诺使用最佳可用分配来处理所有类型 0 的敌人，只要存在有效的全局分配，剩余的池就足以用于类型 1 的处理。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力匹配| O(n3) 或指数 | O(n²) | 太慢了 |
 | 贪婪地按类型排序 | O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 我们单独对待每种敌人类型，但总是从共享的怪物池中消耗。

首先，我们将所有 0 类敌人按强度降序排列。 这确保了当我们分配怪物时，我们首先处理最严格的约束。 如果我们能够满足最难的要求，我们就不会意外地将强大的怪物浪费在更简单的怪物上。 

其次，我们维护一个结构，使我们能够快速选择可以击败给定敌人的怪物，同时也最大限度地减少浪费。 具体来说，对于给定的阈值q，我们希望在相关维度中强度至少为q的所有未使用的怪物中，具有最小可能的次要强度的怪物。 这种选择使灵活的怪物可以应对未来的限制。 

第三，我们按排序顺序迭代 0 类敌人。 对于每个敌人，我们找到一个具有足够 0 型强度的有效怪物，并贪婪地选择具有最小 1 型强度的怪物。 如果在任何时候都不存在这样的怪物，我们立即得出结论，不可能进行完整的分配。 

第四，在分配所有 0 类敌人后，我们使用剩余怪物的第二强度值对 1 类敌人重复相同的过程。 

最后，如果两个阶段都成功，每个敌人都会被分配一个独特的怪物，我们返回“是”。 

### 为什么它有效

 不变的是，在处理固定敌人类型的每一步中，我们总是保留最有用的剩余怪物以供将来的任务使用。 通过按降序处理敌人，任何对当前敌人有效的怪物也对该类型的所有较弱的剩余敌人有效。 选择交叉类型强度最小的怪物可以确保我们不会不必要地破坏灵活性。 这种贪婪的结构可以防止局部决策阻碍全局可行性，因为任何早期使用更强的跨类型怪物的替代分配只能减少后续步骤的解决方案空间。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    ours = []
    for _ in range(n):
        a, b = map(int, input().split())
        ours.append([a, b])
    
    t0 = []
    t1 = []
    for _ in range(m):
        t, p = map(int, input().split())
        if t == 0:
            t0.append(p)
        else:
            t1.append(p)
    
    def check(idx):
        import heapq
        
        monsters = ours[:]
        monsters.sort(key=lambda x: x[idx])
        
        enemies = t0 if idx == 0 else t1
        enemies.sort(reverse=True)
        
        # we maintain a pointer and a heap of candidates
        i = 0
        heap = []
        
        for q in enemies:
            while i < n and monsters[i][idx] >= q:
                # push by the other attribute
                heapq.heappush(heap, monsters[i][1 - idx])
                i += 1
            
            if not heap:
                return False
            
            heapq.heappop(heap)
        
        return True
    
    if check(0) and check(1):
        print("YES")
    else:
        print("NO")

if __name__ == "__main__":
    solve()
```该实现将过程分为两个对称阶段，由`idx`。 什么时候`idx = 0`，我们使用怪物的第一个属性来匹配 0 型敌人，并通过第二个属性来优先考虑候选者。 按活动属性对怪物进行排序可确保我们可以随着敌人阈值的降低逐步激活有效的候选怪物。 

堆存储当前或未来敌人当前符合条件的所有怪物的次要力量值。 每次遇到新的敌人阈值时，我们都会将所有新符合条件的怪物推入堆中。 堆弹出总是选择二次成本最小的怪物，这符合保持灵活性的贪婪要求。 

一个常见的错误是忘记资格必须通过指针增量维护`i`。 重新扫描所有怪物以查找每个敌人会将复杂性提高到 O(n²)。 另一个微妙之处是每个怪物每个阶段最多使用一次，因为在分配时它会从堆中删除。 

## 工作示例

 ### 示例 1

 考虑三个怪物和三个 0 型敌人：

 怪物： (5, 2), (4, 10), (3, 1)

 敌人：5、4、3

 我们将敌人排序为 [5,4,3]，将怪物按第一属性排序为 [(5,2), (4,10), (3,1)]。 

| 敌人| 添加新候选人 | 堆（辅助）| 选择的怪物|
 | --- | --- | --- | --- |
 | 5 | (5,2) | [2] | (5,2) |
 | 4 | (4,10) | [10]| (4,10) |
 | 3 | (3,1) | [1] | (3,1) |

 每个敌人都匹配成功，所以这个阶段成功。 

该跟踪表明，将较弱的怪物延迟到需要时可以确保我们永远不会阻止更强的约束。 

### 示例 2

 怪物： (6, 1), (5, 100), (4, 2)

 敌人：6、5、4

 | 敌人| 添加新候选人 | 堆（辅助）| 选择的怪物|
 | --- | --- | --- | --- |
 | 6 | (6,1) | [1] | (6,1) |
 | 5 | (5,100) | [100]| (5,100) |
 | 4 | (4,2) | [2] | (4,2) |

 这说明了为什么选择最小次要值有效。 如果我们第一步选择 (5,100) 而不是 (6,1)，我们仍然会成功，但在较大的混合实例中，这种选择保留了两个阶段的灵活性。

 ## 边缘情况

 一个重要的边缘情况是一种类型的敌人数量多于能够处理它们的怪物数量。 假设所有怪物的0型强度最多为3，但有一个敌人需要5。在排序时，这个敌人最先出现，并且堆从未收到有效的候选者，因此算法立即返回NO。 这可以防止以后错误的部分分配。 

另一个边缘情况是，一个极其强大的怪物可以处理所有敌人，但贪婪的选择以一种幼稚的方法过早地分配它。 在这个算法中，这种情况不会发生，因为我们总是在有效候选者中选择具有最小次要强度的怪物，只有在阈值可行性严格必要时才保留强大的怪物。 

最后一种情况是全球范围内都存在可行性，但只有仔细的跨类型分布。 分成两个阶段是有效的，因为一旦贪婪地修复了类型 0 的赋值，只要存在完整的解决方案，类型 1 的剩余结构仍然允许有效匹配，因为贪婪永远不会同时阻止所有有效的赋值。
