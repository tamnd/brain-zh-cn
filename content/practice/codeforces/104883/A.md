 ## 解决方案
 ## 问题理解

 我们获得了虚拟货币系统中玩家账户余额的按时间顺序排列的日志。 每条记录都会通过以下三种方式之一更改其余额：他们通过支付真实货币来接收货币、在游戏中花费货币或执行不影响其余额的无关操作。 

关键数量是按顺序处理所有事件后最终未使用的虚拟货币数量。 由于人民币与游戏内货币的汇率是一比一的，所以最后剩下的钱可以直接换成人民币退还。 

输入是有符号整数序列。 正值增加余额，负值减少余额，零则保持不变。 保证任何时候支出都不会超过当前余额，因此余额在处理过程中永远不会失效。 

从约束角度来看，事件数量最多为 1000 个，每个值的大小可以达到 10^9。 这立即排除了对单遍聚合之外的复杂数据结构或优化的任何需求。 即使 O(n^2) 模拟也能轻松通过，但结构表明线性扫描既足够又自然。 

一个常见的错误是过度考虑退款条件，并试图将“已用但可退款”与“已使用”货币分开。 例如，如果日志是`[+328, -328, +488]`，天真的解释可能会错误地假设第一笔存款有助于退款，因为它曾经是正数，但支出完全取消了它。 另一个微妙的情况是出现零条目时； 它们应该被完全忽略，例如`[+100, 0, -50]`应该表现得完全一样`[+100, -50]`。 任何将零视为中断段或触发单独核算的解决方案都会错误计算结果。 

## 方法

 强力解释将模拟一个具有运行余额的帐户，并且对于每个退款查询，尝试重建哪些存款仍未使用。 人们可以想象单独跟踪每笔存款，并在支出发生时将部分标记为已消耗。 这类似于维护多组可用资金并反复将提款与早期存款进行匹配。 虽然正确，但这种方法变得不必要的繁重，因为每个支出操作可能需要向后扫描以查找可用存款，从而在交替存款和取款时在最坏的情况下导致二次行为。 

关键的简化来自于认识到问题并不要求资金归属，只要求最终剩余总额。 每笔存款都会增加总可退还价值，每次支出都会减少总可退还价值，中间结构无关紧要。 由于每一步支出都保证有效，因此任何存款都不需要超出总金额的部分跟踪。 

这将整个过程压缩为计算所有值的运行前缀和。 最终答案就是所有条目的总和。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力追踪存款 | O(n^2) | O(n^2) | O(n) | 太慢了|
 | 前缀和聚合 | O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 初始化变量`balance`为零。 该变量表示任意时刻未花费的货币总量。 
2. 按顺序迭代每条记录。 对于每个值`x`， 更新`balance`通过添加`x`直接到它。 正值增加可用资金，负值减少可用资金，零则保持不变。 
3.处理完所有记录后，输出`balance`作为最终可退款金额。 

这种直接积累有效的原因是支出操作与之前的存款完全一致。 由于每笔提款都保证由现有余额支持，因此无需跟踪它来自哪笔具体存款。 该系统的行为就像一个纯粹的价值守恒，没有隐藏的约束。 

### 为什么它有效

 在序列中的任何一点，运行总和等于所有添加的资金与迄今为止花费的所有资金之间的净差。 由于支出永远不会超过可用资金，因此该金额始终与剩余的未支出货币完全对应。 任何重新分配或历史匹配都不能改变最终的净值，因为每个操作都是线性的，并且仅在总量上是可逆的，而不是在结构上。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n = int(input().strip())
balance = 0

for _ in range(n):
    x = int(input().strip())
    balance += x

print(balance)
```该实现维护一个累加器。 每个输入行都会被解析并直接添加到该累加器中。 使用快速输入是因为尽管约束很小，但这是标准的竞争性编程实践。 

一个微妙的点是不对零值应用过滤。 特别处理零只会使逻辑复杂化，而不会改变结果。 另一个重要的细节是，Python 的整数类型自然可以处理大和，因此即使所有值都接近 10^9，也不存在溢出问题。

 ## 边缘情况

 仅零序列，例如`n=3, [0, 0, 0]`产生的余额为零，因为没有操作改变状态。 该算法处理每个条目，但累加器始终保持不变。 

完全取消序列，例如`[+50, -20, -30]`逐步减少余额，直到达到零。 运行金额自然反映了这种取消，无需跟踪资金的中间所有权。 

恢复较晚的病例，例如`[+100, -150, +200]`，表明由于担保问题，暂时出现赤字是不可能的，最终结果仅取决于净额，此处为 150。
