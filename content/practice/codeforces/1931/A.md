[CF 1931A - 恢复小字符串](https://codeforces.com/problemset/problem/1931/A)

 **评分：** 800
 **标签：** 暴力破解、字符串
 **求解时间：** 1m 16s
 **已验证：** 是的

 ## 解决方案
 ## 问题理解

 我们得到一个整数，表示三个隐藏小写字母的总和。 每个字母都贡献了它在字母表中的位置，所以`a`贡献 1,`b`贡献 2，依此类推，直到`z`26. 原词总是只有三个字符，我们只观察它们的数值总和。 

任务是重建一个有效的三字母单词，其字母之和等于给定的总和。 在所有有效的三元组中，我们必须返回字典顺序最小的一个。 

这里的字典顺序的行为类似于相同长度字符串上的字典顺序，因此最小化第一个字符比第二个字符更重要，第二个字符比第三个字符更重要。 这意味着我们不仅仅是寻找总和的任何分解，而是将尽可能多的价值推入后面的字符，同时保持前面的字符最少。 

约束非常小：总和最多为 78，这恰好是最大可能值`26 + 26 + 26`。 这立即排除了对大空间搜索或超出每个测试用例的恒定时间推理的优化技术的任何需要。 即使对所有可能的三元组进行强力扫描也是可行的，因为只有$26^3 = 17576$的可能性。 

主要的边缘情况源于词典编纂的极简性。 一种幼稚的方法可能会尝试所有三元组并选择最小的有效三元组，但即使是很小的实现选择（例如错误地排序迭代）也可能导致选择一个在字典顺序上不是最小的正确和三元组。 

例如，如果总和为 24，则有效三元组包括`aav`,`ava`， 和`vaa`。 粗心的搜索会优先考虑最后一个字符或检查总和而不强制执行字典顺序，很容易返回`vaa`，这是有效的但不是最小的。 正确答案是`aav`因为它首先最小化第一个字符。 

## 方法

 蛮力的想法很简单：枚举所有三元组`(x, y, z)`其中每个变量的范围是 1 到 26，检查是否`x + y + z = n`，并跟踪字典顺序最小的对应字符串。 这是正确的，因为它耗尽了整个可行空间，并且比较时字典顺序与元组顺序匹配`(x, y, z)`直接，我们可以简单地保留最小的有效三元组。 

每个测试用例此方法的成本是恒定的：17,576 次迭代。 对于最多 100 个测试用例，这大约是 170 万次检查，这在 Python 中已经足够快了。 然而，对于如此小的结构来说，它有点矫枉过正，并且会做多余的工作，因为大多数自由度都是不必要的。 

关键的观察是字典最小化迫使贪婪的结构。 第一个字符应尽可能小，但仍允许其余两个字符形成剩余总和的有效分解。 一旦第一个字符被固定，第二个字符在可行的情况下应再次最小化，第三个字符将自动确定。 

这将问题从三个嵌套循环减少为两个具有恒定时间检查的嵌套循环，甚至更简单，直接贪婪构造。

 ## 算法演练

 我们一次构建一个字符的答案，始终确保其余位置的可行性。 

1. 通过按升序尝试从 1 到 26 的所有值来修复第一个字符。 对于每位候选人`a`,检查剩余金额是否`n - a`可以拆分为 1 到 26 之间的两个值。此可行性检查相当于验证`2 ≤ n - a ≤ 52`。 
2. 一旦找到有效的第一个字符，就永久修复它，因为首先尝试较小的值可以保证字典顺序最优性。 
3. 通过从 1 迭代到 26 来类似地修复第二个字符。对于每个候选`b`，保证剩余价值`n - a - b`位于范围内`[1, 26]`。 第一个有效`b`出于相同的词典编排原因，是最佳的。 
4.第三个字符被迫为`n - a - b`，因为所有约束都保证它位于`[1, 26]`。 
5. 通过映射将数值转换回字母`1 → a`,`2 → b`， 等等。 

该算法的结构确保每个决策在字典顺序方面都是局部最优的，并且与可行性全局一致。 

### 为什么它有效

 正确性来自单调可行性属性。 对于任何固定前缀，如果较小的选择是可行的，它总是会导致字典顺序更小的有效字符串。 超出总和限制的选择之间没有未来的相互作用，因此早期决策不会限制后来的词典优化，除非通过可行性界限。 这种解耦允许在每个位置进行贪婪选择而无需回溯。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())

        for a in range(1, 27):
            rem = n - a
            if not (2 <= rem <= 52):
                continue

            for b in range(1, 27):
                c = rem - b
                if 1 <= c <= 26:
                    ans = chr(ord('a') + a - 1) + chr(ord('a') + b - 1) + chr(ord('a') + c - 1)
                    print(ans)
                    break
            else:
                continue
            break

if __name__ == "__main__":
    solve()
```该代码完全遵循贪心构造。 外循环按升序选择第一个字符，并且仅当剩余的总和仍能形成两个有效字母时才继续。 第二个循环同样确保第三个字符在提交之前有效。 Python 的使用`else`on 循环确保一旦找到有效的第二个字符，我们就从两个循环中干净地退出。 

一个常见的陷阱是忘记第三个字符是唯一确定的。 另一个错误地允许`c`到外面去`[1, 26]`，即使总和匹配，也会默默地产生无效字符串。

 ## 边缘情况

 对于最小的总和`n = 3`，算法集`a = 1`,`b = 1`， 和`c = 1`，因为不可能有其他分割。 可行性检查立即接受第一个有效配置，产生`aaa`。 

为了最大的金额`n = 78`，算法会跳过所有小值`a`直到达到`a = 26`，那么类似地力`b = 26`，离开`c = 26`。 该结构自然收敛于`zzz`无需特殊处理。 

这些案例证实边界行为纯粹是通过可行性约束来处理的，而不需要显式的分支逻辑。
