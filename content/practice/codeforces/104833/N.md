 ## 解决方案
 ## 问题理解

 我们得到的物品非常小，总共有八种纪念品。 每种类型都有有限的库存，由八个整数组成的数组描述。 分别有$n$人，每个人都独立地要求这八种类型中的一种。 如果在考虑此人时所请求的类型仍有剩余库存，他们会收到该类型的一件物品，并且库存减少一件。 如果没有，他们就什么也得不到。 

任务是计算在这种自然的贪婪分配过程下可以满足多少人，假设我们按照给定的顺序处理人员。 

输入规模就人数而言很大，最多可达$2 \times 10^5$，但项目范围固定为大小 8。 这立即限制了解决方案空间。 任何尝试在恒定时间之外模拟每个人昂贵操作的方法只有在保持严格线性的情况下才是可接受的。$n$。 任何涉及对每人八种类型进行嵌套扫描的事情仍然没问题，但任何涉及对大于恒定大小的动态结构进行每人搜索的事情都将是不必要的开销。 

一个微妙的边缘情况来自耗尽排序。 如果天真的解释假设我们可以简单地计算每种类型的请求并独立地与供应进行比较，那么这是不正确的，因为请求是按顺序处理的，并且库存是全局消耗的。 例如，如果类型 1 有一个项目，并且有两个人请求类型 1，则只有第一个人会得到服务，即使总体推理中全球需求等于供给。 

另一种极端情况是某些类型的库存为零。 对这些类型的请求必须始终失败，即使它们出现在序列的早期。 例如，如果$a_3 = 0$如果有人请求类型 3，则无论订购或其他可用性如何，都不应将其计算在内。 

## 方法

 直接模拟按照字面上的问题陈述进行。 我们保留剩余的 8 号库存阵列。 然后我们迭代所有$n$人们。 对于每个人，我们都会检查所请求的类型是否仍有库存。 如果是，我们将其递减并增加答案。 

这是有效的，因为每个决策仅取决于该类型的当前剩余容量。 每个操作都是 O(1)，因此整个过程是 O(n)，这完全在限制范围内。 

一个常见的错误想法是聚合每种类型的计数，然后计算$\sum \min(\text{demand}_i, a_i)$。 仅当类型之间没有交互时，才会忽略排序约束，但这里的交互严格是每个类型的本地交互。 在这个特定问题中，这种聚合实际上是正确的，因为不同类型永远不会竞争同一股票。 唯一的相互作用是在每种类型内独立进行的。 这意味着该流程可以被视为八个独立的队列，每个队列都按到货顺序消耗自己的库存。 然而，与直接模拟相比，实现每种类型的频率计数是不必要的复杂性。 

真正的见解是，由于状态空间只有八个整数，因此我们可以安全地顺序模拟，而无需担心性能问题。

 ## 算法演练

 我们完全按照描述模拟分配过程。 

1.初始化一个数组`stock`尺寸为 8，包含每种商品类型的可用数量。 这代表了每种纪念品类型在任何时间点的剩余容量。 
2. 初始化计数器`ans = 0`跟踪有多少人得到了成功的服务。 
3. 按顺序迭代每个人。 对于人$i$，读取他们请求的类型$b_i$。 此顺序很重要，因为较早的消耗会降低后续请求的可用性。 
4. 检查是否`stock[b_i] > 0`。 如果是，则通过递减将该项目分配给此人`stock[b_i]`并递增`ans`。 
5.如果`stock[b_i] == 0`，不执行任何操作，因为该类型已耗尽并且无法满足进一步的请求。 
6.处理完所有人员后，输出`ans`。 

关键思想是每个库存桶独立演化，但其演化取决于请求的时间顺序。 我们永远不需要向前看或重新安排请求，因为这个过程对于到达顺序来说纯粹是贪婪的。 

### 为什么它有效

 每种类型的行为就像具有固定容量的独立资源。 每次请求类型$x$到达时，唯一重要的限制是剩余容量是否$x$是积极的。 由于任何请求都不会影响任何其他类型的库存，因此不同类型的决策是独立的。 该算法保留了以下不变量：`stock[i]`始终等于原始金额减去已接受的类型请求数$i$到目前为止所看到的。 这确保了我们永远不会过度分配任何类型，并且每个接受的分配都对应于一个真正的可用单元。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    b = list(map(int, input().split()))
    a = list(map(int, input().split()))

    stock = a[:]  # 8 types
    ans = 0

    for x in b:
        x -= 1  # convert to 0-index
        if stock[x] > 0:
            stock[x] -= 1
            ans += 1

    print(ans)

if __name__ == "__main__":
    solve()
```该解决方案读取人数，然后读取他们的请求，然后读取八种商品类型中每种商品的可用库存。 唯一微妙的实现细节是将输入中的 1 索引类型转换为 0 索引数组访问。 剩下的就是直接模拟贪婪分配规则。 

每个请求仅被处理一次，并且每次检查都是恒定时间的数组访问。 不需要额外的数据结构，因为状态完全由八元素库存数组捕获。

 ## 边缘情况

 一种极端情况是所有股票价值为零。 该算法仍然会迭代所有请求，但不会增加答案，因为每次检查都会失败。 用于输入`n = 3`, 请求`[1,2,3]`，并且库存全部为零，不变式`stock[i] >= 0`始终保持并且`ans`保持为零，产生正确的输出。 

另一种边缘情况是单一类型主导所有请求。 如果类型 1 的库存为 2 并且五个人都请求类型 1，则算法会减少库存两次，然后停止接受进一步的请求。 第二次验收后，`stock[0]`变为零，因此后续迭代正确地拒绝所有剩余的请求。 

最后一个边缘情况是库存足够大，可以满足每个请求。 在这种情况下，每个请求都会通过`stock[x] > 0`检查，算法简单地计算所有$n$人们，永远不会碰到拒绝分支。
