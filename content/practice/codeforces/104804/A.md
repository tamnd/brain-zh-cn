 ## 解决方案
 ## 问题理解

 每个测试用例都描述了在棋盘游戏会话期间收集的资源类型的集合。 对于每种类型，我们都会得到收集了该资源的多少单位以及单个单位值多少分。 任务是通过汇总所有资源类型的贡献来计算总分。 

更具体地说，每行给出一对数字。 第一个数字是特定种类物品的计数，第二个数字是一个此类物品的价值。 该类型对最终得分的贡献就是它们的乘积，答案是所有类型的这些贡献的总和。 

这些约束允许最多 100000 个资源类型，并且每个值可以大到 100000。这会立即排除任何尝试超出输入的单个线性传递的解决方案。 即使 O(n log n) 方法也是不必要的，因为除了直接聚合之外没有其他结构可供利用。 唯一可行的方法是在读取输入时累加总和。 

粗心的实现中可能出现的一个微妙问题是具有固定宽度整数的语言中的整数溢出。 例如，如果所有输入都为最大值，则单个乘积可以达到 10^10，并且将 10^5 个这样的值相加可以达到 10^15。 在 Python 中这是安全的，但在其他语言中这需要 64 位整数。 

另一个潜在的错误是尝试将累加分离到两个数组中，并在以后不必要地处理它们，这会增加开销，但不会改变正确性。 由于每条线都是独立的，因此延迟计算没有任何好处。 

## 方法

 一种强力的解释是单独扩展每个资源单元，然后一一分配值。 这意味着对于每种类型，我们概念上创建一个大小为 a_i 的列表，并将 b_i 分配给每个元素。 这是正确的，但当 a_i 很大时，立即变得不可行，因为在最坏的情况下扩展元素的总数可能达到 10^10。 

关键的观察结果是，同一类型的所有单位的价值贡献是相同的。 资源类型之间没有交互，它们之间也没有顺序或约束。 这将问题分解为计算加权和，其中每个权重只是 a_i，每个值是 b_i。 我们不是扩张，而是直接乘法和积累。 

这将整个任务减少为对输入的一次传递。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力扩张| O(Σa_i) | O(Σa_i) | 太慢了 |
 | 直接求和| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 初始化变量`total`为零。 这将存储所有贡献的运行总和。 
2.读取资源类型数量`n`。 
3.对于接下来的每一个`n`行，读取一对`(a_i, b_i)`。 
4. 计算该类型的贡献为`a_i * b_i`。 这代表该类型所有项目的总价值。 
5.将此贡献添加到`total`。 
6.处理完所有行后，输出`total`。 

关键的设计选择是在读取时执行乘法而不是存储值。 这避免了不必要的内存使用，并确保计算与输入行数严格呈线性关系。 

### 为什么它有效

 每种资源类型都独立于所有其他资源类型，并且类型中的每个单元都具有相同的值。 因此，总分是不相交组的总和，其中每个组的贡献完全相同`a_i * b_i`。 由于加法是结合性和交换性的，因此无论输入顺序如何，累积贡献都可以保持正确性。 不存在交互项，因此除了运行总和之外不需要其他状态。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    total = 0
    for _ in range(n):
        a, b = map(int, input().split())
        total += a * b
    print(total)

if __name__ == "__main__":
    solve()
```该解决方案读取每对一次并立即将其折叠到答案中。 乘法在加法之前完成，以确保我们永远不需要存储中间扩展表示。 即使总和超过 64 位限制，使用 Python 的任意精度整数也能保证正确性。

 ## 边缘情况

 一种边缘情况是所有资源计数为零。 对于输入：```
3
0 10
0 20
0 30
```每个贡献都为零，因此在整个执行过程中运行总和保持为零。 该算法执行三次乘法，但所有结果均为零，并且最终输出保持为 0，无需任何特殊分支。 

另一种情况是只有一种类型存在时：```
1
12345 67890
```该算法执行一次乘法并直接输出结果。 不会出现初始化问题，因为累加器从零开始，并且单次更新正确捕获了完整答案。 

第三种情况是当值处于最大值时。 尽管中间乘积可能很大，但 Python 可以自然地处理任意精度，因此重复累加不会溢出或丢失精度。
