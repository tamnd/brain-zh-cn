 ## 问题理解

 语句中的合并排序代码不仅对数组进行排序，还在合并两个已排序的一半时记录每次比较期间做出的决策顺序。 每次比较都会产生一个`0`或一个`1`，取决于左半部分还是右半部分贡献下一个最小元素。 

我们只得到这个记录的决策序列，并连接成一个字符串。 产生它的原始排列丢失了。 任务是构造任何排列，如果将其输入到相同的合并排序实现中，则生成完全相同的合并决策序列。 

关键的困难在于日志不直接描述值，它描述了递归合并结构之间的比较历史。 Each bit belongs to a specific merge operation deep in the recursion, and the same prefix of the log can influence multiple levels of the merge tree.

 Although the original version of the problem guarantees that a solution exists for a permutation of size 16, we are not required to output a permutation of that exact size. 合并排序轨迹与给定日志匹配的任何有效排列都是可接受的，这为重建提供了灵活性。 

天真的解释会尝试猜测数组并模拟合并排序，直到日志匹配为止。 This is immediately infeasible because the space of permutations grows factorially, and even checking a single candidate requires O(n log n) work. A second naive idea is to try to reconstruct values greedily from the log alone, but the log does not directly compare global positions, only local merge decisions, so local greedy choices break consistency across recursion levels.

 当尝试将日志解释为元素的单个全局排序时，会出现微妙的失败情况。 例如，如果日志以交替开头`0`和`1`，并不意味着元素全局交替。 这些决策可能来自不同递归深度的独立合并。 

## 方法

 归并排序的结构是固定的：它递归地分割数组，对两半进行排序，然后使用比较将它们合并。 唯一的自由在于原始值，它决定了比较如何解决。 日志消除了这种自由，并准确地告诉我们哪一方赢得了每次比较。 

强力方法将尝试所有大小为 16 的排列，模拟每个排列的合并排序，并比较日志。 原则上这是可行的，因为 16! 对于编译语言中的高度优化的暴力破解来说足够小，但在 Python 中它仍然太慢，因为每次模拟的成本为 O(n log n)，导致总工作量巨大。 

关键的观察是合并排序不需要实际值来确定结构，它只需要相对排序
