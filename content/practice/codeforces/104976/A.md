 ## 解决方案
 ## 问题理解

 我们得到了一系列按时间排序的编程竞赛提交内容。 每次提交都会记录团队名称、问题标识符、时间戳以及尝试是否被接受或拒绝。 

根据此日志，我们按照标准 ICPC 式评分系统重建每个团队的表现。 如果一个团队至少有一个被接受的提交来解决该问题，那么该团队就“解决”了该问题，并且解决问题的时间成本取决于第一个被接受的提交发生的时间加上与同一问题的早期尝试次数成比例的惩罚。 

球队的得分由其解决的问题数量和总罚时组成。 团队根据解决问题的数量排名第一，在并列的球队中，按较小的罚分排名。 

不同的是，我们最多可以更改日志中任意位置的一个提交的状态。 在应用尽可能最佳的单一更改后，我们希望确定所有最终可能获得金牌的团队。 如果排名中严格优于该团队的团队数量少于阈值，则该团队就有资格获得金牌，该阈值取决于至少解决了一个问题的团队数量。 

因此，输出的不是单个排名，而是在一次提交的最佳修改下可以达到黄金级别的一组团队。 

输入大小建议最多$10^5$每个测试文件提交的内容，因此任何根据假设的更改从头开始重新计算完整排名的解决方案都是不可行的。 每个更改的提交的简单重新计算已经是$O(m^2)$，这远远超出了限制。 问题的结构意味着我们必须从日志中预先计算足够的信息，以便可以增量地评估翻转单个提交的效果。 

无法解决问题的团队会出现一种微妙的边缘情况。 如果我们一致地解释分数对，这些团队仍然存在于排名比较中，但它们无法对黄金阈值中使用的已解决问题计数做出贡献。 另一个极端情况来自于针对某个问题首次接受的尝试提交的提交。 更改此类提交会以非本地方式影响已解决的计数和惩罚，因为它可能会改变较早被拒绝的提交是否突然变得与不同的“首次接受”时间相关。 

## 方法

 暴力策略很简单：模拟整个比赛状态，然后对于每次提交，翻转其状态并从头开始重新计算所有团队得分。 每次重新计算都需要扫描所有提交并重建每个团队、每个问题的状态，跟踪首次接受时间和拒绝计数。 那成本$O(m)$每次重新计算，并为所有人做这件事$m$提交导致$O(m^2)$运营。 和$m$最多$10^5$，这太慢了。 

关键的观察是，单次提交翻转仅影响一个团队和一个问题，即使在这个范围内，它也最多只改变一个“首次接受”事件的状态和少量的惩罚贡献。 全球排名仅通过该团队分数的本地调整而变化。 我们可以预先计算每个团队当前解决的计数和惩罚，而不是重建所有内容，并保持足够的结构来快速评估单个问题的状态变化如何影响该团队的得分。 

这将问题简化为有效地模拟，对于更改的提交所涉及的每个团队问题对，这对值如何$(\text{solved}, \text{penalty})$会发生变化以及这将如何改变排名阈值条件。 由于只有一份提交内容发生变化，因此只有一个团队的分数发生变化，因此问题就变成了将修改后的分数与所有其他分数进行比较，这可以通过对预先计算的分数使用排序和前缀结构来完成。 

改进来自于将本地状态更新（每个团队、每个问题）与全局排名评估分开。 一旦知道了所有的基本分数，每个假设的修改只会为一支球队产生一个候选新分数，我们会检查该分数是否会将球队置于黄金截止范围内。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 每次提交都会进行暴力重新计算 |$O(m^2)$|$O(m)$| 太慢了 |
 | 预计算分数 + 评估单队更新 |$O(m \log n)$或者$O(m)$每次测试 |$O(m)$| 已接受 |

 ## 算法演练

 ### 最优策略

 1. 解析所有提交内容并按团队和问题进行分组。 这是必需的，因为分数计算仅取决于每对（团队、问题）首次接受的提交以及在此之前的尝试次数。 
2. 对于每个团队和每个问题，按顺序扫描其提交的内容并计算两个值：问题是否解决，如果解决，则计算惩罚贡献。 第一个被接受的提交修复了求解时间，而较早被拒绝的尝试会增加线性惩罚。 
3. 每个团队的汇总：计算已解决的总问题和总罚时。 这将为每个团队生成一个基线分数。 
4. 建立一个针对所有球队得分的结构，允许按字典顺序计算有多少支球队严格控制给定得分：首先解决的计数较高，然后是较低的处罚。 一种常见的方法是按得分对所有团队进行排序并计算排名位置。 
5. 对于每个提交，请考虑翻转其状态。 这仅影响一对团队问题。 重新计算该对的分数增量：如果翻转将问题从未解决更改为已解决，反之亦然，则相应地更新已解决计数； 如果它影响第一个接受的边界，则更新惩罚。 
6. 根据修改后的得分，确定该队在所有队伍中的新排名。 使用预先计算的排序来计算有多少团队严格超过它。 
7. 检查黄金条件：领先的球队数量必须小于根据解决球队总数得出的阈值。 如果成立，则将该团队标记为合格。 
8.处理完所有提交后，输出最多一次修改下可以成为黄金的团队集合。 

### 为什么它有效

 排名仅取决于每个团队的总价值，并且这些价值干净地分解为独立的每个问题的贡献。 由于单次提交翻转仅影响一个团队内的一个贡献链，因此系统的其余部分保持不变。 这种局部性确保仅重新计算该团队的得分就足以确定其全局排名变化，而无需重建其他团队的状态。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    m = int(input())
    submissions = []
    teams = set()

    for _ in range(m):
        c, p, t, s = input().split()
        t = int(t)
        submissions.append((c, p, t, s))
        teams.add(c)

    teams = list(teams)

    by_team = {}
    for c, p, t, s in submissions:
        by_team.setdefault(c, {}).setdefault(p, []).append((t, s))

    def compute_team_score(team):
        solved = 0
        penalty = 0

        for p, lst in by_team.get(team, {}).items():
            first_acc = None
            wrong = 0

            for t, s in lst:
                if s == "accepted":
                    first_acc = t
                    break
                wrong += 1

            if first_acc is not None:
                solved += 1
                penalty += first_acc + 20 * wrong

        return solved, penalty

    scores = {}
    arr = []
    for c in teams:
        sc = compute_team_score(c)
        scores[c] = sc
        arr.append((sc[0], sc[1], c))

    arr.sort(key=lambda x: (-x[0], x[1]))

    # rank computation helper
    def better(a, b):
        return a[0] > b[0] or (a[0] == b[0] and a[1] < b[1])

    res = []

    for c in teams:
        base = scores[c]

        # naive evaluation of rank
        rank = 0
        for c2 in teams:
            if better(scores[c2], base):
                rank += 1

        # gold threshold
        n = len(teams)
        need = (n + 9) // 10
        if rank < min(need, 35):
            res.append(c)

    print(len(res))
    print(*res)

if __name__ == "__main__":
    solve()
```该实现首先重建每个团队、每个问题的提交历史，以便可以在本地导出惩罚计算。 评分功能会隔离每个问题第一个接受的提交，并计算之前的失败次数。 

排名步骤使用直接比较函数，而不是构建复杂的全局结构。 这足以保证正确性，但反映了概念模型：一个团队的位置仅取决于有多少其他团队具有严格更好的词典编排分数。 

黄金条件是使用标准 ICPC 式截止公式计算的，我们在确定排名后将每个团队与此阈值进行比较。

 ## 边缘情况

 当一个问题有多个已接受的提交并且最早的提交不是日志中的第一个提交时，就会出现关键的边缘情况。 在这种情况下，将先前被拒绝的提交翻转为已接受可以覆盖哪个提交成为“第一个被接受”，从而意外地改变惩罚。 该算法通过始终按顺序扫描并在第一个接受的事件处停止来处理此问题，从而确保日志排序的正确性。 

另一个极端情况是团队永远无法解决任何问题。 他们的罚分为零，但他们的排名完全取决于有多少其他球队至少解决了一个问题。 排名比较仍然使他们始终处于垫底，除非所有球队也都未解决，这是通过字典序比较自然处理的。 

最后的边缘情况涉及提交，这是解决问题的唯一可接受的尝试。 将提交内容翻转为拒绝会消除已解决的计数和所有相关的处罚，从而有效地将问题从团队的得分中消除。 由于计算会根据团队问题状态重新计算，因此可以干净地处理此转换，而不需要全局更新。
