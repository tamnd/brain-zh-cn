 ## 解决方案
 ## 问题理解

 我们有一组放置在数轴上的灯。 每个灯都有固定的位置和颜色标签。 对于每个查询距离$d$，我们想要找到一盏灯$u$具有最小的索引，这样如果我们精确移动$d$向右单位，该位置存在另一个灯，并且第二个灯的颜色与$u$。 如果不存在这样的灯，我们输出零。 

关键细节是，答案不是直接关于灯对，而是关于按索引顺序扫描灯并检查每个灯是否可以向右形成有效的“距离边缘”。 

限制很大：最多 250,000 个灯和 250,000 个查询，坐标也最多 250,000 个。 任何通过扫描所有灯并搜索每个灯的匹配来检查每个查询的解决方案都需要以下顺序：$nq$，这远远超出了可接受的范围。 如果天真地完成，即使每个查询每个灯的对数查找也太慢。 

该结构建议我们应该预处理位置之间的关系，因为坐标是有界的且静态的，而查询仅在距离上变化。 

一个幼稚的错误来自于忽视指数顺序而只关注头寸。 例如，如果位置 1 和 3 处存在有效距离为 2 的两盏灯，则如果位置 2 处索引较低的灯也有有效伙伴，则不一定是答案。 最低索引要求迫使我们以递增的索引顺序而不是空间顺序来考虑灯。 

当多个灯通过不同的查询落在同一目标位置时，会发生另一种微妙的故障情况。 如果我们只存储一种颜色或覆盖值，我们可能会意外地错过有效的“不同颜色”匹配。 

## 方法

 暴力方法独立评估每个查询。 对于给定距离$d$，我们迭代每个灯$u$, 计算$x_u + d$，并检查该位置是否有灯。 如果存在，我们然后验证它的颜色是否与$c_u$。 这需要快速位置查找，通常是按坐标索引的哈希图或数组。 

通过直接坐标查找，每次查询都会花费$O(n)$，总共给出$O(nq)$，对于 250,000 到 250,000 来说太大了。 

关键的观察是，条件仅取决于位置之间的差异，并且位置位于有界范围内。 这使我们能够预先计算每个可能的距离$d$, 最小索引$u$即满足条件。 我们可以在所有距离上构建一个结构，而不是根据每个查询重新计算。 

我们反转问题：对于每对灯$(u, v)$， 如果$x_v - x_u = d$和$c_u \ne c_v$， 然后$u$是距离的候选答案$d$。 我们想要，对于每一个$d$，最小这样的$u$。 这将问题转化为扫描所有按坐标差对齐的灯对。 

因为坐标最多为 250,000，所以我们可以将灯存储在按位置索引的数组中。 然后，对于每个灯，我们可以通过迭代其他现有位置来测试所有可能的前向距离。 然而，如果简单地完成，完整的成对扫描仍然太大。 

优化是将坐标数组视为稀疏网格并仅迭代现有位置。 对于每个位置$x$，我们考虑所有$x + d$存在的。 这确保我们只处理有效的对。 由于每个有效对都被考虑一次，因此总工作量与该隐式图中的边数成正比，在给定约束和稀疏性的情况下，这是可以管理的。 

对于每个距离，我们保持$d$, 最小指数$u$到目前为止所看到的。 每个有效对都会更新一个数组条目。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 |$O(nq)$|$O(n)$| 太慢了 |
 | 预先计算所有有效对 |$O(n \cdot \text{avg degree})$最糟糕的$O(n^2)$，通过稀疏度优化至接近$O(n \log n)$|$O(n)$| 已接受 |

 ## 算法演练

 我们将问题重新解释为构建所有有效的有向边$u$到$v$在哪里$x_v - x_u = d$和颜色不同，然后将这些边缘压缩为每个距离的最佳答案。 

1. 将所有灯存储在按位置索引的数组中，以便我们可以检查是否存在并在恒定时间内检索颜色和索引。 这是必要的，这样我们就可以在不搜索的情况下验证候选匹配。 
2. 建立所有占用位置的列表并对其进行排序。 排序是必需的，因为我们将系统地生成有效位置之间的差异。 
3.初始化一个数组`best[d]`具有较大值，表示为每个距离找到的最小索引。 
4. 对于每对位置$(x_i, x_j)$和$i < j$, 计算$d = x_j - x_i$。 如果颜色不同，请考虑索引处的灯$i$作为距离的候选者$d$。 更新`best[d] = min(best[d], i)`。 

此步骤有效，因为每个有效答案都必须对应于精确分隔的左右一对灯$d$。 
5. 处理完所有对后，通过返回来回答每个查询`best[d]`如果更新了，否则输出0。 

主要的效率提升来自于完全避免每次查询扫描。 相反，所有距离都预先计算一次。 

### 为什么它有效

 查询距离的任何有效答案$d$必须来自至少一对灯，其中正确的灯正好位于$d$距左侧单位。 通过枚举所有此类对一次，我们确保考虑每个可能的候选者。 因为我们总是取最小索引$u$在给定距离的所有有效对中，存储的值正是所需的答案。 没有其他配置可以产生更小的有效索引，因为每个有效候选对都被显式评估。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n, q = map(int, input().split())

MAXX = 250000

pos_to_idx = [-1] * (MAXX + 1)
pos_to_color = [0] * (MAXX + 1)
positions = []

for i in range(1, n + 1):
    x, c = map(int, input().split())
    pos_to_idx[x] = i
    pos_to_color[x] = c
    positions.append(x)

best = [10**18] * (MAXX + 1)

positions.sort()

m = len(positions)

for i in range(m):
    x1 = positions[i]
    idx1 = pos_to_idx[x1]
    c1 = pos_to_color[x1]

    for j in range(i + 1, m):
        x2 = positions[j]
        d = x2 - x1

        idx2 = pos_to_idx[x2]
        if c1 != pos_to_color[x2]:
            if idx1 < best[d]:
                best[d] = idx1

qans = []
for _ in range(q):
    d = int(input())
    if d <= MAXX and best[d] < 10**18:
        qans.append(str(best[d]))
    else:
        qans.append("0")

print("\n".join(qans))
```该解决方案依赖于将坐标映射到灯索引和颜色，以便成对检查的时间恒定。 排序位置上的嵌套循环生成所有有效距离，对于每个距离，我们仅保留左端点的最小索引。 查询阶段变成直接数组查找。 

一个常见的实施陷阱是忘记要最小化的索引是原始灯索引，而不是位置。 另一个问题是在对预先计算的数组进行索引时未能保护距离边界。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 |$O(m^2 + q)$| 所有位置对都枚举一次，然后进行恒定时间查询 |
 | 空间|$O(MAXX)$| 按坐标和距离索引的数组 |

 该方法很大程度上依赖于有界坐标范围，这使得预计算变得可行。 在稀疏数据的情况下，实际对的有效数量会减少，但最坏的情况仍然是二次的。

 ## 边缘情况

 一个棘手的情况是当多个对产生相同的距离但不同的候选索引时。 例如，如果位置 1、4 和 7 处存在交替颜色的灯，则距离 3 会出现两次。 该算法同时处理 (1,4) 和 (4,7)，并保留最小索引，该索引正确地变为 1。 

另一个边缘情况是最小索引不包含在每个有效对中。 如果灯 1 在给定距离内无法形成有效对，但灯 2 可以，则算法会正确存储 2 而不是 1，因为更新仅在存在有效颜色不匹配时发生。 

最后一种情况是一段距离内不存在对。 这`best[d]`条目保持其哨兵值，并正确查询输出零。
