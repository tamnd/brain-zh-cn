 ## 解决方案
 ## 问题理解

 我们在一条线上有许多点代表必须全部“访问”和清理的邮箱，另一组点代表可以沿着同一条线移动的人。 每个人从一个固定的坐标开始，每秒可以向左或向右移动一个单位。 当一个人站在邮箱位置的那一刻，那个邮箱就立刻被清理干净。 多人可以自由重叠，多个邮箱可以共享同一个坐标。 

任务是协调所有人，使每个邮箱至少被访问一次，并且我们希望在最后一个邮箱被清理之前尽可能短的时间。 

思考这个问题的一个有用方法是，每个人都可以在时间限制 T 内走完该线的连续一段，因为在 T 秒内，他们可以到达距起点距离 T 内的任何位置。 所以每个朋友定义了一个可达位置的区间，我们要选择T，使得这些区间的并集可以“覆盖”所有邮箱点。 

这些限制有力地推动了有效解决方案的发展。 每个测试用例最多有 100000 个邮箱和 100000 个朋友，人员和邮箱之间的任何二次匹配都会太慢。 如果重复扫描覆盖范围，即使排序加上简单的分配也不会通过。 这表明解决方案必须将问题简化为每个候选值的线性或近线性检查，通常使用排序和贪婪合并。 

当邮箱聚集并且远离所有朋友时，就会出现一个微妙的情况。 例如，如果所有朋友都从 0 附近开始，并且邮箱处于大的正极端和负极端，则答案将由距最近朋友的最远所需旅行距离决定，而不是由平均值或全局匹配决定。 

另一个边缘情况是重复位置。 如果许多邮箱共享一个坐标，则一次访问就足够了，但是任何在匹配逻辑中独立处理它们的简单实现都可能会浪费工作或过度计算分配。 

## 方法

 蛮力的想法是根据分配来思考。 在固定时间T内，我们检查每个邮箱是否可以分配给至少一个朋友，使得该朋友可以在T内到达它。这意味着对于每个朋友，我们计算其可达间隔，然后尝试用这些间隔覆盖所有邮箱点。 幼稚的检查可能会针对每个好友间隔尝试每个邮箱，从而导致每个测试用例的复杂度为 O(nm)。 当 n 和 m 都达到 100000 时，在最坏的情况下这会导致 10^10 次操作，这根本不可行。 

关键的观察是，在固定时间 T 内，每个朋友的可达区域是线路上的连续线段。 问题变成了覆盖问题：这些段是否覆盖了所有邮箱点？ 一旦邮箱被排序，就可以通过扫描两个排序列表来以线性时间进行检查。 

这将问题转化为决策问题：对于给定的 T，我们可以在 O(n + m) 中检查可行性。 答案本身在 T 中是单调的，因为如果所有邮箱都可以在时间 T 内被清理，那么它们也可以在任何更大的时间内被清理。 这种单调性允许对 T 进行二分搜索。 

我们使用答案范围上的二分搜索来计算最小 T，以便覆盖范围是可能的，每次可行性检查都是贪婪扫描。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力分配 | 每次测试 O(nm) | O(1) | O(1) | 太慢了 |
 | 二分查找+扫描| O((n + m) log R) | O((n + m) log R) | O(n + m) | 已接受 |

 这里R是坐标范围，最大到10^18，所以log R大约是60。 

## 算法演练

 ### 1.对所有邮箱位置和所有好友位置进行排序

 排序确保我们可以从左到右推理覆盖范围而无需回溯。 一旦订购，间隔和目标就会以结构化的方式对齐。 

### 2. 定义一个检查可行性的函数 can(T)

对于位置 p 的每个朋友，可达段为 [p − T, p + T]。 目标是检查这些段的并集是否覆盖每个邮箱位置。 

### 3. 使用指针浏览邮箱

 我们在邮箱上维护一个索引 i。 我们还按排序顺序迭代朋友。 

对于每个朋友，我们都尽力扩大覆盖范围：

 我们考虑位于其区间内的所有邮箱，即位置 ≤ p + T 的邮箱。如果当前邮箱 < p − T，则该朋友无能为力，因此我们适当地向前跳。 

关键的想法是，一旦跳过某个邮箱，后面的朋友就无法及时返回，所以我们必须确保每个邮箱都按顺序覆盖。 

### 4. 贪婪地消耗每个朋友可到达的邮箱

 对于给定的朋友，一旦我们到达有效的起始邮箱，只要邮箱在可达区间内，我们就会前进邮箱指针。 

这有效地将每个邮箱分配给最早可以覆盖它的朋友，而无需重新考虑决定。 

### 5.如果覆盖所有邮箱，则返回True

 如果指针到达邮箱列表的末尾，则时间T就足够了。 

### 6. T 上的二分查找

 我们在 T 上搜索任何邮箱和任何朋友之间从 0 到最大距离。 每个中间值都用 can(mid) 进行测试。 

### 为什么它有效

 正确性来自于覆盖区域和目标都位于一条线上的结构。 对于任何固定的T，每个朋友贡献一个连续的区间，可行性归结为一组区间是否涵盖所有点。 贪婪扫描是最优的，因为一旦我们按顺序处理朋友，尽可能扩大覆盖范围就不会阻止未来的覆盖选项。 任何延迟覆盖邮箱的替代分配只会降低灵活性，因此贪婪的从左到右的消耗在存在时准确地保留了可行性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve_case(mailboxes, friends):
    mailboxes.sort()
    friends.sort()

    n = len(mailboxes)
    m = len(friends)

    def can(t):
        i = 0
        for p in friends:
            if i >= n:
                return True

            left = p - t
            right = p + t

            if mailboxes[i] > right:
                continue

            if mailboxes[i] < left:
                continue

            while i < n and left <= mailboxes[i] <= right:
                i += 1

            if i >= n:
                return True

        return i >= n

    lo, hi = 0, 10**18

    while lo < hi:
        mid = (lo + hi) // 2
        if can(mid):
            hi = mid
        else:
            lo = mid + 1

    return lo

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        n, m = map(int, input().split())
        mailboxes = [int(input()) for _ in range(n)]
        friends = [int(input()) for _ in range(m)]
        out.append(str(solve_case(mailboxes, friends)))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```核心实现将可行性检查与二分搜索分开。 这`can(t)`功能是最微妙的部分。 指针`i`确保每个邮箱每次检查最多处理一次，因此每个可行性测试都是线性的。 周边条件`left`和`right`确保我们只在覆盖范围有效时前进，并且当无用的朋友无法到达当前邮箱段时我们会跳过他们。 

二分搜索范围保守地选择为 10^18，因为坐标可能很大，并且邮箱和朋友之间的最坏情况距离也可能达到该范围。

 ## 边缘情况

 一个关键的边缘情况是所有邮箱都位于所有朋友的一侧。 例如，邮箱位于 100、200、300 处，单个朋友位于 0 处。该算法正确返回 300，因为二分查找需要 T 足够大，以便单个区间 [0−T, 0+T] 覆盖最远的邮箱。 任何试图“首先匹配更接近的”的贪婪分配尝试都会在这里失败，因为没有分配选择，只有扩展。 

另一种情况是，朋友密密麻麻，而邮箱却稀疏。 扫描确保每个朋友仅在必要时做出贡献，并且重叠间隔不会干扰，因为指针仅向前移动，即使在许多间隔严重重叠时也能保持正确性。
