 ## 解决方案
 ## 问题理解

 我们正在模拟具有多个内核和多个存储单元的处理器。 时间被划分为多个周期。 对于每个周期，每个内核都会收到一条不执行任何操作的命令或一条写入特定存储单元的命令。 

有趣的部分是死锁是如何发生的。 

如果在同一周期内，两个或多个活动核心尝试写入同一存储单元，则会发生冲突。 涉及该冲突的每个核心都会被永久锁定，并且存储单元本身也会被永久锁定。 

核心锁定后，它会忽略所有未来的命令。 存储单元被锁定后，任何人都无法再次成功对其进行写入。 如果活动核心稍后尝试写入已锁定的单元，则该核心也会立即被锁定。 

对于每个核心，我们必须确定它被锁定的第一个周期。 如果在模拟过程中它从未被锁定，我们输出 0。 

限制非常小。 核心、周期和存储单元的数量最多均为 100。即使是同时执行与所有核心和所有周期成比例的工作的算法也很容易足够快。 整个输入最多包含 10,000 条指令，因此简单性和正确性比复杂的优化更重要。 

主要的困难不是效率，而是忠实地再现计时规则。 

一个容易犯的错误是错误地处理同时写入。 

考虑：```
2 1 1
1
1
```两个内核都在周期 1 期间写入单元 1。 

正确的输出是：```
1
1
```两个核心同时锁定，因为从该周期中发生的一组写入中检测到冲突。 一个接一个处理核心的粗心模拟可能会让第一个写入成功，但只锁定第二个核心。 

当写入之前锁定的单元格时，会发生另一种微妙的情况。```
2 2 1
1 1
1 0
```周期 1 会产生冲突，锁定两个核心和单元。 

正确输出：```
1
1
```有错误的实现可能会在周期 2 期间继续执行已锁定核心的命令，这将违反该语句。 

第三种边缘情况是仅针对当前活动的核心检查对锁定单元的写入。```
2 2 1
1 0
1 1
```周期 1 锁定核心和单元。 

正确输出：```
1
1
```在周期 2 期间，第二个核心将尝试对锁定单元进行另一次写入，但它已经被锁定，因此没有任何反应。 一旦核心被锁定，它就不会再参与。 

## 方法

 最直接的想法是完全按照描述来模拟处理器。 

对于每个周期，我们都会检查每个活动核心。 如果某个核心想要写入已锁定的单元，则该核心将立即被锁定。 否则，我们将按目标单元对所有写入请求进行分组。 任何从两个或多个活动核心接收请求的单元都会导致冲突，从而锁定所有参与核心和单元本身。 

由于约束很小，这种简单的模拟已经足够快了。 

假设我们尝试了一种更简单的方法。 对于每个周期和每个单元，我们可以扫描所有核心以查看谁想要在那里写入。 这大约需要$m \cdot k \cdot n$运营。 当所有值都等于 100 时，这只是一百万次检查，这仍然可以接受。 

然而，在处理循环时对写入进行分组更干净、更自然。 每条指令每个周期检查一次，给出运行时间与指令总数成正比的模拟。 

关键的观察结果是，每个周期都可以使用当前的一组活动核心和未锁定的单元进行独立处理。 冲突仅取决于在该特定周期内发出的写入请求，而先前锁定的核心和单元只是永远不可用。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(nmk) | O(1) | O(1) | 已接受 |
 | 最佳模拟| O(纳米) | O(n + k) | 已接受 |

 ## 算法演练

 1. 将所有指令读入一个二维数组，其中`cmd[i][j]`是核心的命令`i`循环期间`j`。 
2. 维护数组`core_locked_time`，最初全为零。 值为零表示核心仍处于活动状态。 
3. 维护一个布尔数组`cell_locked`，对于每个存储单元来说最初都是假的。 
4. 处理周期从1到`m`。 
5. 对于当前周期，创建从内存单元到尝试在此周期期间写入的活动核心列表的映射。 
6. 迭代所有核心。 

如果核心已被锁定，请忽略它。 

如果其命令为0，则忽略它。 

如果它尝试写入锁定单元，则立即将当前周期记录为其锁定时间。 

否则，将核心添加到目标小区的请求列表中。 
7. 检查完所有活动核心后，检查在此周期内收到请求的每个单元。 
8. 如果一个单元有来自至少两个核心的请求，则会发生冲突。 

将单元格标记为锁定。 

每个参与的核心在当前周期都会被锁定。 
9. 继续下一个循环。 
10. 处理完所有周期后，输出记录的每个核心的锁定时间。 

### 为什么它有效

 在每个周期开始时，算法的状态与问题中描述的处理器状态完全匹配。 每个锁定的核心都被排除在进一步执行之外，并且每个锁定的单元都会被记住。 

当活动核心写入锁定单元时，该语句表示该单元立即锁定。 第 6 步正是执行此操作。 

对于未锁定的单元，在做出任何冲突决策之前收集当前周期的所有写入请求。 这与循环的同时性质相匹配。 当且仅当至少有两个活动核心在该周期内尝试写入某个单元时，该单元才会被锁定，并且每个参与核心都接收当前周期作为其锁定时间。 

由于语句中的每个规则都以正确的时间顺序应用一次，因此模拟始终会产生与真实处理器相同的状态转换。 因此，记录的锁定时间是正确的。 

## Python 解决方案```python
import sys
from collections import defaultdict

input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())

    cmds = [list(map(int, input().split())) for _ in range(n)]

    lock_time = [0] * n
    cell_locked = [False] * (k + 1)

    for cycle in range(1, m + 1):
        requests = defaultdict(list)

        for core in range(n):
            if lock_time[core] != 0:
                continue

            cell = cmds[core][cycle - 1]

            if cell == 0:
                continue

            if cell_locked[cell]:
                lock_time[core] = cycle
            else:
                requests[cell].append(core)

        for cell, cores in requests.items():
            if len(cores) >= 2:
                cell_locked[cell] = True

                for core in cores:
                    if lock_time[core] == 0:
                        lock_time[core] = cycle

    sys.stdout.write("\n".join(map(str, lock_time)) + "\n")

if __name__ == "__main__":
    solve()
```这`lock_time`数组有两个用途。 零值表示核心仍处于活动状态，而正值则记录其被锁定的第一个周期。 

第一次通过核心处理由写入已锁定单元引起的立即锁定。 这些核心不会插入到请求列表中，因为它们从未成功参与当前周期。 

第二遍检查分组请求。 由于在检查冲突之前收集了所有请求，因此可以正确处理同时写入。 这避免了逐一处理写入的常见错误，并避免了意外地优先考虑首先访问的核心。 

条件`if lock_time[core] == 0`冲突循环内部是防御性的。 实际上，请求列表中的核心不能在同一周期内已被锁定，但检查使逻辑明确并保留“首次锁定时间”属性。

 ## 边缘情况

 考虑同时冲突的情况：```
2 1 1
1
1
```在周期 1 期间，两个活动核心都请求单元 1。单元 1 的请求列表包含两个核心，因此算法会锁定单元和两个核心。 输出是：```
1
1
```由于请求在处理冲突之前进行分组，因此两个核心都不会获得优先级。 

现在考虑写入已锁定的单元格：```
3 2 1
1 0
1 0
0 1
```周期 1 在单元 1 上产生冲突。核心 1 和 2 锁定，并且单元 1 被锁定。 

在周期 2 期间，内核 3 尝试写入单元 1。算法检测到目标单元已被锁定，并立即将锁定时间 2 分配给内核 3。 

输出：```
1
1
2
```最后，考虑已经锁定的核心接收未来的命令：```
2 2 1
1 0
1 1
```周期 1 锁定核心和单元 1。在周期 2 期间，第二个核心的命令将被忽略，因为其锁定时间已被记录。 该算法再也不会处理来自锁定核心的指令。 

输出：```
1
1
```这与处理器规格完全匹配，并防止重复计算或在锁定后更改内核的锁定时间。
