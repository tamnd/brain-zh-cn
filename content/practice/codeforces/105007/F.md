 ## 解决方案
 ## 问题理解

 每个朋友都会带来一份潜在的工作。 工作由两件事定义：在固定的 7 天一周中，爱丽丝必须遛朋友的狗的日子，以及完成整周工作的报酬。 Alice 可以接受一份工作，也可以忽略它，但她不能两次接受同一个朋友。 

日常约束是关键的结构性约束。 在这 7 天里，爱丽丝每天最多可以遛两只狗。 因此，每个选定的工作子集必须满足每天不超过两个选定的工作需要工作。 

输出是遵守每日容量限制的任何工作子集的最大总付款。 

输入的作业数量较少，最多 100 个好友。 隐藏结构位于每周计划维度中：每个作业都是一个 7 位模式，因此约束是应用于子集选择问题的七个独立容量约束的集合。 这立即表明指数子集并不是自动不可能的，但所有子集的简单枚举已经达到 2^100，这远远超出了可行的范围。 

当贪婪地思考时，就会出现一种微妙的失败模式。 例如，首先选择薪水最高的工作可能会阻碍许多中等工作，这些工作总体上会产生更高的利润，因为它们在不同日期的重叠程度不同。 另一个问题来自于独立对待每一天：优化每日任务并不考虑每项工作同时跨越多天。 

具体的贪婪失败：

 输入：```
3
1 0 0 0 0 0 0 50
1 0 0 0 0 0 0 40
0 1 0 0 0 0 0 40
```按值贪婪策略可能会首先选择第 50 个作业，使第 1 天的容量 1 未使用，并忽略第二个作业也使用第 1 天，并且在较大实例中可能会与其他日期进行不同的配对。 在小情况下，这似乎无害，但总的来说，它打破了重叠约束的最佳打包。 

## 方法

 直接暴力解决方案会尝试 N 个作业的每个子集。 对于每个子集，它通过检查所有 7 天并计算当天需要多少个选定的作业来验证可行性。 这是正确的，因为它探索整个解决方案空间，但它需要评估 2^N 个子集，并且对于每个子集在 7 天内检查最多 N 个作业，给出大约 O(N·2^N) 操作。 当 N = 100 时，这是完全不可行的。 

关键的观察结果是约束维度很小并且固定为 7 天。 每个作业都可以表示为一个 7 位掩码。 我们不是直接推理子集，而是跟踪分配给每天配置的作业数量，但这仍然不会立即降低复杂性。 

关键的重组是日复一日地审视流程。 由于每天最多允许 2 个作业，因此我们可以按顺序处理作业，并针对 7 天中每一天剩余的空位数量维护一个动态程序。 每天的容量为 2，因此状态是 {0,1,2} 中整数的 7 元组。 这最多给出 3^7 = 2187 个状态，这已经足够小了。 

每个作业在其掩码中的每个活动日消耗一个容量单位。 因此，我们对作业执行类似背包的 DP：对于每个作业，我们尝试将其分配到状态转换中，如果可行的话，从其活动天数中减去容量。 这是一个有界的小尺寸多维背包。 

因此，问题变成了代表剩余容量、最大化总价值的状态上的 DP。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力子集 | O(N·2^N) | O(N·2^N) | O(1) | O(1) | 太慢了 |
 | DP 超过 7 天容量状态 | O(N·3^7) | O(N·3^7) | O(3^7) | O(3^7) | 已接受 |

 ## 算法演练

 我们将 7 天的剩余容量编码为一个 7 长度的元组，其中每个条目为 0、1 或 2。 

1. 用一种状态初始化 DP 字典：所有日期的容量为 2，值为 0。这表示从完全可用开始。 
2. 对于每个作业，读取其 7 位掩码及其奖励。 该掩码表明该作业从哪几天开始消耗一单位容量。 
3. 对于每个现有 DP 状态，尝试两种转换：跳过该作业，或者在所有所需天数至少有 1 个剩余产能的情况下接受该作业。 
4. 接受工作时，将面具为 1 的每一天减去 1，以产生新的状态。将工作的奖励添加到累计值中。 
5. 通过仅保留每个结果状态的最大值来合并转换。 
6. 处理完所有作业后，答案是所有 DP 状态中的最大值。 

作业的顺序并不重要，因为每个作业要么贡献一次，要么根本不贡献，并且状态转换总是保留可行性约束。 

### 为什么它有效

 DP 状态准确地捕获了未来决策所依赖的内容：每天剩余多少个时段。 导致相同剩余能力向量的早期工作选择的两个不同序列对于所有未来的决策都是等效的，因为未来的工作仅通过这些能力相互作用。 这表明通过仅保留每个容量配置的最佳值来合并状态不能丢弃任何潜在的最佳解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    jobs = []
    for _ in range(n):
        *days, m = map(int, input().split())
        mask = tuple(days)
        jobs.append((mask, m))

    from collections import defaultdict

    dp = {(2, 2, 2, 2, 2, 2, 2): 0}

    for mask, val in jobs:
        new_dp = dict(dp)

        for state, cur in dp.items():
            ok = True
            nxt = list(state)

            for i in range(7):
                if mask[i]:
                    if nxt[i] == 0:
                        ok = False
                        break
                    nxt[i] -= 1

            if ok:
                nxt = tuple(nxt)
                new_val = cur + val
                if nxt not in new_dp or new_dp[nxt] < new_val:
                    new_dp[nxt] = new_val

        dp = new_dp

    print(max(dp.values()))

if __name__ == "__main__":
    solve()
```该解决方案从所有 7 天的完全可用性开始，在容量状态上构建 DP。 如果可行，每项工作要么被跳过，要么被应用。 可行性检查确保没有一天超出容量。 该字典仅存储每个容量配置的最佳可实现值，这可以防止重复状态下的指数爆炸。 

一个微妙的点是复制`dp`进入`new_dp`迭代之前。 这避免了在作业的同一迭代中链接更新，这将错误地允许多次使用单个作业。

def solve_capture(inp: str) -> str:

    from collections import defaultdict
    input = sys.stdin.readline
    data = inp.strip().split()
    it = iter(data)

    n = int(next(it))
    jobs = []
    for _ in range(n):
        days = [int(next(it)) for _ in range(7)]
        m = int(next(it))
        jobs.append((tuple(days), m))

    dp = {(2,2,2,2,2,2,2): 0}

    for mask, val in jobs:
        new_dp = dict(dp)
        for state, cur in dp.items():
            nxt = list(state)

                if mask[i]:
                    if nxt[i] == 0:
                        ok = False
                        break
                    nxt[i] -= 1
            if ok:
                nxt = tuple(nxt)
                new_dp[nxt] = max(new_dp.get(nxt, 0), cur + val)

 ## 边缘情况

 一个关键的边缘情况是多个作业需要完全相同的日期设置。 例如：

 输入：```
3
1 0 0 0 0 0 0 10
1 0 0 0 0 0 0 20
1 0 0 0 0 0 0 30
```DP 在第一天开始时容量为 2。它最多可以承担其中两项工作。 每个作业消耗一个单元后，转换会正确生成状态。 最好的结果来自选择两个最高值，达到 50，并且 DP 强制执行此操作，因为一旦容量达到零，任何第三个选择都是不可行的。 

另一个边缘情况是没有要求的工作。 这样的工作永远不会改变状态，只会增加价值。 DP总是会接受它，因为可行性永远不会失败，所以它有效地自由积累，这是正确的，因为它不消耗任何日常容量。 

第三种极端情况是一项需要 7 天时间的工作。 这会将每个容量组成部分减少一个，并且由于每日限制，所有此类作业总共只能使用两次。 DP 自然地通过每日耗尽而不是任何明确的计数逻辑来强制执行此全局约束。
