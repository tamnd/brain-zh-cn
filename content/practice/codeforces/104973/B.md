 ## 解决方案
 ## 问题理解

 我们有一堆帽子，每顶帽子都有一个独特的标签，并且任何时候都只能访问帽子堆的顶部。 人们按照从1到n的固定顺序一一到达。 当每个人到达时，我们要么给他们当前的高顶帽子（从堆栈中弹出它），要么跳过他们而不给任何东西。 

只有当一个人收到一顶标签与他们的索引完全匹配的帽子时，才会被认为是幸福的。 如果他们收到不同的帽子或什么也没收到，他们就会不高兴。 我们还得到一个二进制字符串 S 来描述哪些人必须快乐 (S[i] = 1)，哪些人必须不快乐 (S[i] = 0)。 任务是确定是否存在一系列“戴高帽”和“跳过”操作，使这些人感到高兴。 

关键结构是帽子严格按照堆栈顺序消耗，因此我们不会随意分配。 我们只是决定何时流行。 

这些约束允许跨测试用例的 n 最大为 10^5，这会立即排除任何尝试模拟所有选择或回溯操作子集的方法。 即使每个测试用例的 O(n^2) 行为也会太慢，因此解决方案必须是线性或接近线性的。 

一个微妙的边缘情况是，S 有很多帽子，但无法在正确的时间访问匹配的帽子。 例如，如果人 i 一定很高兴，但 i 在堆栈中出现得太深，并且在我们到达 i 之前就被通过了，那么就不可能恢复。 另一个失败的情况是，我们被迫跳过一个需要比赛的位置，但后来意外地过早消耗了所需的帽子。 

核心难点是管理时间：当我们被允许为索引 i 选择一顶帽子时，当我们选择服务 i 时，标记为 i 的帽子必须正好位于顶部，否则它可能会被后面的强制弹出消耗掉。 

## 方法

 蛮力策略会为每个人尝试所有可能的决策序列：要么跳过，要么戴帽子。 最坏的情况有2^n种可能性，每次模拟的成本为O(n)，这使得它完全不可行。 

然而，堆栈结构引入了一个强大的约束：帽子是按固定顺序消耗的，因此我们从不选择接下来出现哪个帽子，只选择是现在还是稍后弹出它。 这将问题转化为对排列 H 的受控遍历，同时尝试满足 S 规定的强制匹配。 

关键的见解是扭转观点。 我们不是考虑每个人的决定，而是跟踪下一个需要的“正确的帽子”是否可以与其职位保持一致。 我们模拟堆栈如何演变，同时贪婪地确保每当 S[i] = 1 时，我们必须能够将 i 与当前顶部匹配或仅以不破坏未来可行性的方式进行延迟。 

这导致使用 H 上的堆栈指针和 people 上的指针进行贪婪验证。 我们按顺序处理人员，并且仅在需要时推进帽子堆栈，同时确保我们不会错误地跳过所需的匹配。 

问题归结为检查我们是否可以以尊重堆栈顺序约束的方式安排匹配。

 ## 算法演练

 我们在帽子栈上维护一个指针，模拟按顺序处理从1到n的人。 

1. 初始化一个指针`p = 1`位于帽子堆的顶部。 我们还维护一个指向人类的指针`i = 1`到 n.
 2. 对于从 1 到 n 的每个人 i，我们尝试决定如果 S[i] 要求的话，他们是否可以幸福。 
3. 如果 S[i] = 1，我们必须确保在某个时刻我们给他们帽子 i。 由于帽子仅按堆栈顺序可用，因此我们会重复使用堆栈中的帽子，直到找到帽子 i 或耗尽堆栈。 每顶消耗掉的帽子都会立即分配给某人（不一定正确）。 
4. 如果我们在此过程中发现帽子 i 处于顶部位置，我们将其分配给个人 i 并继续。 
5. 如果S[i] = 0，我们可以自由分配或跳过，但我们仍然必须小心地消耗帽子，因为过于激进的消耗可能会破坏未来所需的匹配。 在这个公式中，我们仅在必要时进行消耗以满足强制匹配。 
6. 如果在任何时候我们需要帽子 i (S[i] = 1)，但由于堆栈已耗尽或我们错误地传递它而无法到达它，则返回 NO。 
7. 如果我们处理完所有 i 并且满足所有约束，则返回 YES。 

关键的想法是，我们永远不会将消费延迟到达到所需匹配所需的时间，因为延迟只会减少可用的未来选项。 堆栈性质保证一旦我们传递了一顶帽子，就无法恢复它，因此正确性取决于永远不会跳过所需的帽子。 

### 为什么它有效

 该算法保持堆栈的单调消耗。 在任何时候，剩余的帽子集合都是原始帽子的后缀。 当处理所需的索引 i 时，如果 i 仍在该后缀中，则按顺序只会遇到一次。 如果我们在它从后缀边界消失之前未能遇到它，则后面的跳过或拍摄序列都无法恢复它。 这就建立了一个充分必要条件：当我们按处理顺序到达 i 时，每个所需的 i 都必须出现在剩余的后缀中，并且贪婪的消耗确保我们永远不会过早地使未来的可行性失效。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        H = list(map(int, input().split()))
        S = input().strip()

        pos = {H[i]: i for i in range(n)}

        # we simulate a pointer over the stack
        i = 0
        ok = True

        # we track the furthest we have consumed
        # stack is H[0..i-1] consumed, H[i..] remaining
        for person in range(1, n + 1):
            if S[person - 1] == '0':
                continue

            # we need to find person in remaining stack
            if pos[person] < i:
                ok = False
                break

            # advance i until we reach pos[person]
            i = pos[person] + 1

        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```该代码首先将每个帽子标签映射到其在堆栈中的位置，这允许恒定时间检查所需帽子的位置。 变量`i`代表我们已经消耗了堆栈的多远。 当我们遇到一个一定要幸福的人时，我们会检查他的帽子是否还在未消耗的后缀中。 如果已经落后了`i`，这意味着我们已经不可逆地通过了它，使得配置无法进行。 

前进`i`到`pos[person] + 1`模型消耗所有中间帽子，直到我们达到所需的一顶。 这符合我们仅在需要满足需求时“强制消费”的想法。

 ## 边缘情况

 当所需的帽子位于堆栈深处但较早的所需匹配迫使我们消耗过去时，就会出现关键边缘情况。 例如，如果 S 强制首先匹配较晚的标签，我们可能会隐式跳过所需的较早的标签。 该算法检测到这一点是因为`pos[i] < i`表明我们已经消耗超过了所需的位置。 

另一个边缘情况是 S 为全 1 时。 在这种情况下，算法会有效地尝试按升序匹配每个标签，但仍然遵循堆栈顺序。 如果堆栈排列与身份排序不一致，则当所需元素位于消耗指针后面时，就会发生失败。 

第三种边缘情况是 S 全部为零时。 该算法不进行强制消费，因此`i`始终保持为零，答案始终为“是”，正确反映了不存在任何约束。
