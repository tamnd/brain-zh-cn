 ## 解决方案
 ## 问题理解

 我们会得到一份问题列表，每个问题都有所需的时间成本和分值。 不同的是，这些问题并不总是存在。 相反，有多个班级，每个班级只教授连续的问题片段。 在课堂上，学生的时间有限，可以选择所教授问题的任何子集，但每个问题在该课堂上最多可以解决一次。 

对于每个类别，我们希望通过选择区间内的问题子集来了解可能获得的最佳总价值$[l, r]$其总时间不超过$t$。 最终答案是所有类别的最优值之和。 

这些约束强烈地塑造了解决方案。 问题数量最多可达$10^4$，班级数量最多可达$10^5$。 然而，每个问题的时间限制和类容量都很小，最多 100 个。这种组合是关键信号：背包维度是有界的，这表明每个查询的伪多项式 DP 或预计算策略。 

一种简单的方法，为范围内的每个查询重新计算背包$[l, r]$会太慢了。 尽管每个背包的容量很小，但迭代最多$10^4$每个查询的项目并执行它$10^5$次导致$10^9$过渡，这是不可行的。 

一个更微妙的问题是，问题在查询中重复出现，但总是独立地重新计算。 任何不跨查询重用结构或无法利用小容量的解决方案都会超时。 

当间隔较小但容量较大，或者容量较小但间隔较大时，会出现边缘情况。 例如，如果$t = 1$，只有最有效的单个项目才重要。 简单的子集枚举可能仍会尝试考虑多个项目，从而浪费时间。 另一种边缘情况是在相同范围内重复查询，其中重新计算变得多余。 

## 方法

 蛮力的想法很简单。 对于每个查询，将所有问题放入$[l, r]$并运行一个容量为0/1的背包$t$。 这是正确的，因为它直接模拟了每个问题每个类最多可以被处理一次的约束。 代价是每个查询最多处理$O(N \cdot t)$，给出最坏的情况$10^5 \cdot 10^4 \cdot 100 = 10^{11}$转变，这远远超出了限制。 

关键的观察结果是，虽然范围很大，但容量却极小。 这表明每个查询都可以使用线性规划结构来回答$t$，不在$r-l+1$。 标准技巧是预先计算段上的背包转换，但如果在完整的项目列表上天真地完成，那么具有 DP 状态的段树就太重了。 

相反，我们翻转视角：因为价值观$v_i$与订购无关，但与重量有关$s_i$很小，我们可以为每个前缀维护一个 DP 表，该表存储最多 100 个容量的最佳可实现值。然后，我们可以通过使用线段树组合前缀状态来回答范围查询，其中每个节点存储一个大小为 的背包转换表$101 \times 101$。 每个节点代表“如果从容量 c 开始，使用该段可实现的最佳价值是多少”。 

这将每次合并减少为容量上的有界卷积，这是每个节点的恒定时间。 因此线段树支持范围查询$O(\log N \cdot 100^2)$，这是可以接受的。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 |$O(Q \cdot N \cdot T)$|$O(1)$| 太慢了|
 | 线段树DP|$O((N + Q)\log N \cdot T^2)$|$O(N \cdot T^2)$| 已接受 |

 ## 算法演练

 我们构建一棵线段树，其中每个节点都存储一个 DP 变换表。 

1. 对于每个问题$i$，我们初始化一个基础 DP 转换。 这种转变意味着要么不采取任何行动，要么采取问题$i$如果容量允许。 桌子有尺寸$(T+1)$在哪里$T = 100$。 
2. 对于叶节点，直接从其单个问题构造DP表。 对于每种容量$c$，我们决定是否采取该项目，如果$c \ge s_i$，否则我们保持价值不变。 
3. 内部节点是通过合并左右子节点来构建的。 合并表示首先应用左段，然后应用右段。 对于每个容量$c$，我们尝试将其分成$k$用于左侧部分和$c-k$用在正确的部分，取所有分割中的最大值。 

这本质上是两个 DP 表上的背包卷积。 
4. 查询$[l, r]$，我们遍历线段树并按顺序组合所有相关节点，就像范围查询一样。 结果是代表整个区间的单个 DP 表。 
5. 查询的答案是存储在容量中的值$t$在最终合并的DP表中。 

这样做的原因是每个线段树节点都编码在其间隔内从输入容量到输出最佳值的完整且正确的转换。 组合段对应于这些转换的函数组合，并且段树确保我们以正确的顺序应用它们。 

### 为什么它有效

 每个节点代表一个函数$F(c)$给出了使用该段中具有容量的项目可实现的最大价值$c$。 叶节点定义了正确的基函数，因为它们直接编码单项背包决策。 合并节点对应于组合函数：首先应用左段减少容量，然后右段对剩余容量进行操作。 由于不相交段中的背包选择是独立的，并且 DP 表中充分考虑了容量，因此组合函数保持精确。 由于每个查询都分解为不相交的段并集，因此最终组合会重现该间隔内的最佳子集选择。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

MAXT = 100

def merge(a, b):
    res = [0] * (MAXT + 1)
    for c in range(MAXT + 1):
        best = 0
        for k in range(c + 1):
            val = a[k] + b[c - k]
            if val > best:
                best = val
        res[c] = best
    return res

class SegTree:
    def __init__(self, items):
        self.n = len(items)
        self.size = 1
        while self.size < self.n:
            self.size *= 2
        self.data = [[0] * (MAXT + 1) for _ in range(2 * self.size)]

        for i, (s, v) in enumerate(items):
            dp = [0] * (MAXT + 1)
            for c in range(s, MAXT + 1):
                dp[c] = v
            self.data[self.size + i] = dp

        for i in range(self.size - 1, 0, -1):
            self.data[i] = merge(self.data[2 * i], self.data[2 * i + 1])

    def query(self, l, r):
        l += self.size
        r += self.size + 1
        left = [0] * (MAXT + 1)
        right = [0] * (MAXT + 1)

        while l < r:
            if l % 2 == 1:
                left = merge(left, self.data[l])
                l += 1
            if r % 2 == 1:
                r -= 1
                right = merge(self.data[r], right)
            l //= 2
            r //= 2

        return merge(left, right)

def solve():
    n = int(input())
    items = [tuple(map(int, input().split())) for _ in range(n)]
    seg = SegTree(items)

    q = int(input())
    ans = 0
    for _ in range(q):
        l, r, t = map(int, input().split())
        l -= 1
        r -= 1
        dp = seg.query(l, r)
        ans += dp[t]
    print(ans)

if __name__ == "__main__":
    solve()
```线段树是自下而上构建的，每个节点都存储一个满容量的DP表。 叶子初始化编码了简单的背包选择：要么跳过该项目，要么在容量允许的情况下拿走它一次。 合并操作是一个有界卷积，将两个独立的背包段组合在一起。 

查询逻辑使用标准线段树范围查询模式，但它不存储值，而是组成 DP 转换。 左累加器和右累加器确保保留顺序，因为背包组合不可交换。 

一个微妙的细节是，两者`left`和`right`必须按方向顺序合并。 反转任一侧都会破坏正确性，因为 DP 组成取决于段顺序。

 ## 边缘情况

 一个关键的边缘情况是容量小于段中所有物品的重量。 例如，单个项目$s = 10$和$t = 3$生成一个对于所有容量都保持为零的 DP 表，并且合并操作保留了这种中立性。 

另一个边缘情况是跨查询重复相同的范围。 由于每个查询都会从线段树重新计算 DP，因此正确性不受影响，但简单的解决方案会多次重新计算相同的背包，导致效率严重低下。 

最后一个微妙的情况是，最佳解决方案涉及混合来自线段树查询两端的项目。 例如，分成左右两半的项目需要正确的 DP 组合顺序。 线段树确保从左到右合并，因此像两个项目这样的情况$s = 2$和容量$t = 3$通过在每个部分产能拆分中仅允许一项来正确处理。
