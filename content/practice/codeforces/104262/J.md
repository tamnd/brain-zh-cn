 ## 解决方案
 ## 问题理解

 我们有一个系统$n$每个发动机的燃料需求都会随着时间的推移而变化。 一开始，每个引擎$i$有初始燃料需求$f_{1,i}$。 之后，还有$m$事件。 每个事件发生在特定的时间步长，并增加连续段中每个发动机的燃料需求$[l_t, r_t]$按固定金额$d_t$。 这些更新会随着时间的推移而累积，因此后来的燃油值包括影响每个发动机的所有先前贡献。 

因此，发动机的燃油值不是静态的，它是随着时间的推移应用的范围增加的前缀累积结果。 查询询问一系列发动机的总燃油量$[ql, qr]$，但只考虑燃料随时间的演变$a$截至时间$b$。 该时间间隔是包含在内的，并且可以延长至$m+1$，表示所有更新后的状态。 

关键的难点在于引擎指数和时间这两个维度都是动态的。 每次更新都会影响一系列引擎，并且每个查询都会在一定范围的引擎和一定范围的时间上进行聚合。 

这些约束促使我们寻求接近线性或每维接近线性的解决方案。 和$n, m, q \le 2 \cdot 10^5$，任何重新计算所有引擎或每个查询的所有更新的方法都会立即超出时间限制。 对全时演化的简单模拟将涉及最多$O(nm)$的转变，这远远超出了可行的范围。 

当查询包含时间时会出现微妙的边缘情况$m+1$。 这意味着我们必须将所有更新后的系统视为有效的查询端点，而不仅仅是中间状态。 另一种边缘情况是当查询跨越单个引擎或单个时间步时； 这种情况会在时间范围的前缀处理中暴露出差一错误。 

## 方法

 直接模拟将随着时间的推移维持发动机值的数组。 每次更新都会修改一个段，每个查询都会重新计算多个时间层的子数组的总和。 这将需要重新计算每个查询的前缀和或维护数组的完整历史记录。 即使引擎上有前缀和，每个时间步长仍然会变化$O(n)$值，导致$O(nm)$整体工作量太大。 

关键的观察结果是，问题在引擎索引和时间上都是线性的，并且更新是相加的。 每个更新独立地贡献于与其引擎范围和时间间隔重叠的所有查询。 这表明我们可以分开贡献。 

我们没有考虑不断演化的数组，而是将每次更新重新解释为在网格上贡献一个 2D 矩形加法，其中一个轴是引擎索引，另一个轴是时间。 查询要求计算该网格中矩形的总和。 这将问题转换为经典的离线二维范围和问题。 

我们使用将一段时间内的范围查询转变为前缀差异的想法进一步减少它。 对于查询$[a, b]$，我们计算贡献高达$b$减去贡献最多$a-1$。 因此，我们只需要一个支持前缀随时间累积的结构。 

对于每次更新$t$，它贡献$d_t$至所有发动机位置$[l_t, r_t]$对于所有时代$\ge t$。 对于固定查询，我们只关心是否$t$位于里面$[a, b]$。 这将问题转化为计算更新间隔和查询矩形之间的加权重叠。 

我们可以通过扫描时间并在引擎索引上维护芬威克树（或线段树）来离线处理所有事件。 在每个时间步骤，我们将更新作为引擎上的范围添加应用。 我们还通过维护两个 Fenwick 快照或使用随时间变化的差异技术来处理达到时间边界的查询。 

一种更结构化的方法是结合使用随时间扫描的 Fenwick 树，该树支持通过差异数组进行范围添加和范围求和。 我们以越来越长的时间处理事件，维护存储当前活跃贡献的引擎位置的 BIT。 对于每个查询，我们每次计算总和$b$减去当时的总和$a-1$，这可以通过存储查询端点并评估两次来完成。 

这导致了离线解决方案，其中更新按时间顺序应用一次，并且使用前缀累积快照来回答每个查询。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力模拟|$O(nm + nq)$|$O(n)$| 太慢了 |
 | 离线扫一扫+BIT |$O((n+m+q)\log n)$|$O(n+q)$| 已接受 |

 ## 算法演练

 我们将时间处理转换为前缀累积，将引擎处理转换为 Fenwick 树结构。 

1. Split each query$(ql, qr, a, b)$分为两个子查询：一个用于前缀$b$, 1 为前缀$a-1$，符号相反。 这是因为贡献超过$[a,b]$等于前缀至$b$减前缀最多$a-1$。 这避免了显式维护完整的时间历史记录。 
2. 按时间对所有更新和查询进行排序。 每个更新都是一个从其时间索引开始变为活动状态的事件。 
3. 维护引擎索引的 Fenwick 树。 该树存储截至当前时间已应用的所有更新的当前累积效果。 
4. 处理时间从1到$m+1$。 每一次$t$，首先应用更新$t-1$（自从更新$t$影响过渡到$t+1$）。 这使状态与前缀解释保持一致。 
5. 每当我们到达查询端点的时候$t$，使用 Fenwick 树计算其发动机范围内的总和，并将其与适当的符号相加。 
6. 通过在内部维护差异数组，在 Fenwick 树上使用范围更新 + 范围查询技巧。 每次更新$(l, r, d)$成为点更新$l$和$-d$在$r+1$，允许前缀和代表当前引擎值。 

处理完所有事件后，所有查询贡献都将累积为最终答案。 

### 为什么它有效

 该算法依赖于时间和引擎维度上贡献的线性。 每次更新都会对其范围内的每个引擎独立做出贡献，并在以后的所有时间中持续存在。 通过将时间间隔转换为前缀差异，我们确保针对时间范围包含该更新的查询准确地计算每次更新。 Fenwick 树可确保在每次快照时正确聚合引擎范围。 由于两种分解都是精确且独立的，因此不会丢失或重复计算交互项。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_add(self, l, r, v):
        self.add(l, v)
        if r + 1 <= self.n:
            self.add(r + 1, -v)

def solve():
    n, m, q = map(int, input().split())
    base = list(map(int, input().split()))

    updates = []
    for _ in range(m):
        l, r, d = map(int, input().split())
        updates.append((l, r, d))

    queries = [[] for _ in range(m + 2)]
    ans = [0] * q

    for i in range(q):
        l, r, a, b = map(int, input().split())
        queries[b].append((i, l, r, 1))
        if a > 1:
            queries[a - 1].append((i, l, r, -1))

    bit = BIT(n)

    for i, v in enumerate(base, 1):
        bit.range_add(i, i, v)

    for t in range(0, m + 1):
        for idx, l, r, sign in queries[t]:
            ans[idx] += sign * (bit.sum(r) - bit.sum(l - 1))

        if t < m:
            l, r, d = updates[t]
            bit.range_add(l, r, d)

    print("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```该解决方案使用初始燃料需求初始化芬威克树。 每次更新都会作为引擎上的范围添加应用。 查询在其端点处分为两个事件，因此每个查询都会使用 BIT 中的前缀和精确评估两次，一次为正，一次为负。 

主要的微妙之处在于排序：按时间查询$t$在应用更新之前得到答复$t$，确保时间索引与状态转换的定义匹配。 

## 工作示例

 ### 示例 1

 输入：```
4 2 3
1 2 3 4
1 3 1
2 4 3
1 4 1 3
2 2 2 2
3 4 2 3
```我们在每个时间步后跟踪 BIT。 

| 时间 | 应用更新 | BIT 状态摘要 | 查询评估 |
 | ---| ---| ---| ---|
 | 0 | 无 | [1,2,3,4] | 查询时间 1 应用 |
 | 1 | [1,3] +1 | [2,3,4,4] | 部分查询结果 |
 | 2 | [2,4] +3 | [2,6,7,7] | 评估时间 2 和 3 的查询 |
 | 3 | 无 | 最终状态| 查询已完成 |

 第一个查询在时间 1 到 3 处对整个范围进行求和，累积所有中间贡献。 第二个在单个时间快照中隔离狭窄的发动机范围。 第三个捕获稍后间隔的后缀范围，确认正确的时间切片。

 ## 边缘情况

 一个微妙的边缘情况是查询在时间 1 开始。在这种情况下，没有$a-1$贡献，因此仅使用正端点。 代码显式检查`if a > 1`在添加负贡献之前，防止无效索引到时间 0。 

另一种情况是当查询结束于$m+1$。 这些都存储在桶中以供时间$m+1$，并且由于在时间之后没有发生更新$m$，状态保持稳定并正确反映最终数组。
