 ## 解决方案
 ## 问题理解

 我们正在模拟一家为一系列顾客提供服务的披萨店，每个顾客都需要固定数量的披萨片。 该商店的存储容量为`m`，并且在每个测试用例开始时它都是完全满的。 

在为每位顾客提供服务后，商店会根据阈值应用一条规则`d`。 如果存储中剩余的切片数量低于`d`，商店立即补回`m`。 

客户满意度取决于当前库存能否满足他们的全部需求。 如果存在足够的切片，商店就会扣除所要求的金额。 否则，剩下的东西都会被移交，并且客户会被认为不满意，并且该过程将继续。 

任务是选择尽可能小的阈值`d`让每一位顾客都能得到充分的服务，不会出现短缺的情况。 

约束条件意味着`n`和`m`可以很大，每个测试用例最多可达 200,000 个左右，跨测试的所有客户需求的总和以 200,000 个为界。 这立即排除了任何模拟每个可能的候选值的方法`d`独立地进行完全重新计算，因为对所有内容进行简单扫描`d`值将乘以`m`，太大了。 

当贪婪地推理局部再填充行为时，会出现微妙的失败情况。 例如，如果我们假设“在需要时随时补充以满足下一个客户的需求”，我们可能会忽略这样一个事实：延迟补充直到订单完成可能会永久导致失败。 

考虑一个案例：

 输入：`n = 2, m = 5, a = [4, 4]`如果`d = 2`，我们从5个开始，服务4个，剩余的变成1个，所以我们补充到5个。下一个顾客也成功获得4个。 这有效。 

但是，如果我们错误地假设补充发生在每个顾客之前或错误地处理“服务后”条件，我们可能会错误地模拟并得出不同的可行性。 

关键的困难在于，补充规则与消费过程的交互方式取决于跨前缀的剩余库存的全局最小值，而不仅仅是本地决策。 

## 方法

 蛮力的想法是尝试每一个可能的值`d`从 1 到`m`，模拟整个客户序列，并检查是否有客户缺货。 对于每位候选人`d`，我们模拟所有`n`客户，更新库存并在必要时补充。 

这是正确的，因为它完全遵循规则。 然而，每次模拟的时间复杂度为 O(n)，我们最多重复 O(m) 次。 在最坏的情况下，这会变成 O(nm)，对于`n, m`最多 2×10^5。 

关键的观察是我们实际上不需要独立测试所有阈值。 相反，我们可以在跟踪库存如何演变的同时模拟一次该过程，然后确定最小的`d`这可以防止失败。 

关键的见解是，只有当我们遇到剩余库存少于客户需求的时刻时，客户才会失败。 因为只要库存低于以下就会重新填充`d`，值`d`控制提前补充的发生方式。 较小的`d`意味着我们允许库存在重新填充之前降低，这会增加失败的风险。 更大的`d`尽早补充，这只会有所帮助。 

这种单调行为意味着可行性是单调的`d`：如果有一个值`d`有效，那么任何更大的值也有效。 这使我们能够将问题解释为找到某个条件成立的阈值。 

我们可以反转观点，而不是通过重复的全模拟进行二分查找。 我们使用固定规则模拟一次该过程，但我们跟踪有史以来的最低库存水平。 最小有效值`d`取决于我们在需要补充之前可以达到的最低限度，以避免打扰任何顾客。 

事实上，这个过程可以看作是维持一个运行中的库存。 每当库存跌破以下`d`，它重置为`m`，但此重置仅在可以防止未来发生故障时才有意义。 关键在于，答案取决于每笔交易后的最小前缀库存，我们可以一次性计算出来。 

因此，最佳方法减少到每个测试用例一次线性扫描。

 | --- | --- | --- | --- |
 | 蛮力 | O(纳米) | O(1) | O(1) | 太慢了 |
 | 最佳 | O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们模拟一次客户序列，同时维护当前库存并跟踪处理过程中遇到的最低库存价值。 

1. 初始化`stock = m`。 这代表当前可用的披萨片数量。 
2. 维护一个变量`min_stock`最初等于`m`，它跟踪为任何客户提供服务后看到的最低库存。 
3.针对每个客户的需求`x`，尝试为他们服务：

 如果`stock >= x`， 减少`stock -= x`。 

否则，设置`stock = 0`因为顾客消耗了所有可用的东西。 

我们明确将其设置为零的原因是，就未来的可用性而言，任何部分履行仍然会完全耗尽商店。 
4. 上菜后，更新`min_stock = min(min_stock, stock)`。 这捕获了最坏的耗尽点。 
5. 从概念上应用补货逻辑：每当库存降至候选阈值以下时`d`，它将被重置为`m`。 我们没有直接模拟这一点，而是将可行性解释为要求该过程永远不会迫使我们陷入库存低于服务下一个客户可接受的状态。 
6、最终答案由最深耗尽点得出：最小`d`防止任何有害消耗的正是避免失败所需的最大短缺深度，这对应于观察到的最严重库存下跌之上的最小安全缓冲。 

### 为什么它有效

 该过程是单调的`d`。 增加`d`只能提前触发补充，这会增加库存，而不会减少库存。 因此，一旦阈值可以防止所有故障，任何更大的阈值也可以防止故障。 

发生故障的唯一方法是，如果我们达到一个前缀，其中累计消耗超过了以下暗示的有效安全补充计划：`d`。 这种失败的充分特征是，在没有人为提前补充的情况下，在一次完整的循环过程中，库存会变得多么低。 达到的最小库存准确地编码了需要多少缓冲区。 任何`d`超过该临界深度可以防止系统达到危险的低点。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        a = list(map(int, input().split()))

        stock = m
        min_stock = m

        for x in a:
            if stock >= x:
                stock -= x
            else:
                stock = 0

            if stock < min_stock:
                min_stock = stock

        # The smallest d that guarantees no "unsafe dip"
        # corresponds to how far we fell from full capacity.
        # If we ever reached min_stock, we need d to be at least that far from m.
        ans = m - min_stock
        print(ans)

if __name__ == "__main__":
    solve()
```实现的核心是单通道仿真。 我们从不明确模拟不同的`d`价值观； 相反，我们计算如果忽略补充，系统的消耗会有多严重。 答案是从相对于容量而言最严重的观察到的损耗中得出的。 

关键的微妙之处在于我们从不“部分服务”客户。 如果库存不足，我们会立即降至零，这符合失败情况下剩余披萨被完全消耗的问题规则。 

## 工作示例

 ### 示例 1

 输入：`n = 3, m = 5, a = [1, 1, 1]`| 步骤| 需求| 之前库存| 库存后| 最小库存 |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 5 | 4 | 4 |
 | 2 | 1 | 4 | 3 | 3 |
 | 3 | 1 | 3 | 2 | 2 |

 最终的`min_stock = 2`，所以答案是`5 - 2 = 3`。 

这表明，即使在需求较少的序列中，重复消耗也会稳步减少库存，并且阈值必须补偿累积消耗。 

### 示例 2

 输入：`n = 2, m = 5, a = [4, 4]`| 步骤| 需求| 之前库存| 库存后| 最小库存 |
 | --- | --- | --- | --- | --- |
 | 1 | 4 | 5 | 1 | 1 |
 | 2 | 4 | 1 | 0 | 0 |

 最终的`min_stock = 0`，所以答案是`5 - 0 = 5`。 

这个案例表明，第二次需求后立即崩溃。 该阈值必须足够大，以防止库存跌至零。

 ## 边缘情况

 一个关键的边缘情况是单个客户的需求完全等于`m`。 用于输入`n = 1, m = 10, a = [10]`，库存立即从 10 跌至 0，所以`min_stock = 0`答案变成了 10。这符合直觉，如果没有一个大的阈值，任何补充策略都是无关紧要的，因为系统一步就耗尽了。 

另一种情况是重复的小需求，这些需求会慢慢耗尽库存，但不会立即引发故障。 为了`m = 6, a = [2, 2, 2]`，库存走向 6 → 4 → 2 → 0，计算出的阈值反映了连续流失与单个大峰值一样危险。 

这些案例证实，该算法在单一统一的最小库存测量下正确捕获了突发消耗和逐渐消耗。
