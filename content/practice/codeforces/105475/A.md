 ## 解决方案
 ## 问题理解

 每个参加者都请求一些披萨片，并且每个请求的披萨片都有指定的配料。 一家比萨饼店出售的比萨饼中每个比萨饼只包含一种配料，并且每个比萨饼总是被精确地切成 8 个相等的片。 

任务是决定是否可以为每种配料购买一定数量的披萨，以便完全满足每个请求的切片，并且没有切片未使用。 一个关键的限制是不允许吃剩余的切片，因此每购买一块切片都必须由某人食用。 

这将问题转化为一个问题，即对每种配料的需求是否可以精确地打包成大小为 8 的组，因为每个披萨恰好提供了 8 个相同的配料切片。 

输入由多个测试用例组成。 对于每种情况，我们都会得到人数和可用配料的数量。 然后，对于每个人，我们都会得到他们想要的切片数量，然后是这些切片的配料列表。 每个案例的输出都是一个决策：是否存在完美的购买计划。 

这些限制允许每个测试用例最多 1000 人，每个用例总共 100000 个切片请求。 这意味着我们需要切片请求总数的线性或近线性解决方案。 任何与人或切片成二次方的东西都会太慢。 

一个微妙的边缘情况是，分配看起来“每人平衡”，但每个配料不能全局分割。 例如，如果一个人请求 3 片配料 0，另一个人请求 5 片配料 0，则一切在本地看起来都很好，但总数为 8，因此它可以工作。 然而，如果不同人的总数分别为 10 和 6，则根据实施情况进行简单的每人检查可能会错误地接受或拒绝，即使正确的决定仅取决于每个配料的总和。 

当输入中的配料稀疏时，会出现另一种边缘情况。 一个简单的解决方案可能会忽略零请求的配料，但这些是无关紧要的，因为它们不会影响可行性。 

## 方法

 一种直接的方法是根据任务来思考。 每个切片请求必须分配给一个披萨，每个披萨恰好贡献 8 个相同的切片。 人们可以尝试模拟将切片分成一组，每个配料 8 个，但这很快就会变得不必要的簿记。 

关键的观察结果是，披萨的配料是独立的。 一个topping t的披萨只能提供几片topping t，而且它总是恰好提供8片。 因此，对于独立的每个配料，该配料的请求切片总数必须能被 8 整除。如果这个成立，我们可以简单地购买total_sum[t] / 8 个配料 t 的披萨。 

这将整个问题简化为计算每个顶部的总和并检查整除条件。 输入的结构保证计数是足够的，因为没有交叉顶部交互，也没有排序约束。 

强力解释将尝试模拟一片一片地填充披萨，这将需要为每种配料维护多组部分填充的披萨。 在最坏的情况下，对于多达 100000 个切片，该模拟每次插入仍然是线性的，但不必要地复杂且容易出错，特别是在处理部分填充时。 

简化的基于总和的方法删除了所有状态跟踪并用单通道聚合代替。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | Brute Force（模拟填充披萨）| O(total slices) 但开销很大 | O(部分披萨的数量) | 太复杂|
 | 最佳（每个配料的总和）| O(总切片) | O(M)| 已接受 |

 ## 算法演练

 1.初始化一个数组`cnt`大小为 M，带零来存储每个配料请求的总切片数。 该数组表示我们必须为每种配料提供多少片。 
2. 对于每个人，阅读他们要求的配料列表并增加相应的条目`cnt`。 该数组中的每个条目都会累积全局需求，而不是每个人的结构。 
3. 处理完所有的人后，迭代从 0 到 M − 1 的所有配料，并检查是否`cnt[t]`能被 8 整除。此条件确保可以将需求精确地划分为用于该配料的完整披萨。 
4. 如果任何配料除以8有余数，立即得出结论：不可能在不浪费的情况下满足所有要求。 
5. 如果所有配料都满足整除条件，则得出结论，存在有效的比萨饼选择。 

关键的推理步骤是每个披萨都提供 8 个相同的切片，因此将每种配料的总需求划分为 8 个大小的组的可行性降低。 

### 为什么它有效

 对于每种配料，我们只与相同的单位、相同口味的切片进行交互。 任何有效的解决方案都必须将这些切片分配到不相交的 8 个组中，因为每个组与购买的一个披萨完全对应。 如果总计数不能被 8 整除，则至少有一片将保持未分组状态或强制披萨不完整，这是禁止的。 相反，如果整除性成立，则只需精确获取每个配料的 cnt[t] / 8 个披萨，并任意分配它们的切片来匹配请求，即可轻松构建解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve_case(n, m):
    cnt = [0] * m

    for _ in range(n):
        data = list(map(int, input().split()))
        p = data[0]
        toppings = data[1:]
        for t in toppings:
            cnt[t] += 1

    for x in cnt:
        if x % 8 != 0:
            return "NO"
    return "SI"

def main():
    out = []
    data = sys.stdin.read().strip().split()
    it = iter(data)

    while True:
        try:
            n = int(next(it))
            m = int(next(it))
        except StopIteration:
            break

        cnt = [0] * m
        for _ in range(n):
            p = int(next(it))
            for _ in range(p):
                t = int(next(it))
                cnt[t] += 1

        ok = True
        for x in cnt:
            if x % 8 != 0:
                ok = False
                break

        out.append("SI" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    main()
```该解决方案以流式传输方式读取输入，因为整数总数可能很大。 每个切片请求仅被处理一次，从而增加相应的顶部计数器。 

唯一的微妙之处是确保在多个测试用例中正确使用所有令牌。 在完整输入上使用迭代器可以避免重复的 I/O 开销并简化解析。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(总切片 + M) | 每个切片处理一次，然后每个配料检查一次 |
 | 空间| O(M)| 仅存储每个配料的计数数组 |

 这些约束允许每个测试用例最多有 100000 个总切片请求，因此对所有请求的线性传递很容易足够快。 内存使用量仍然很小，因为 M 最多为 100。

 ## 边缘情况

 A case with a single topping and a single slice request exposes the divisibility rule directly. 如果输入是`1 1`其次是`1 0`，顶部 0 的计数器变为 1，并且由于 1 % 8 不为零，因此算法立即正确地拒绝它。 

所有需求恰好是每个配料 8 的倍数的情况证实了积极的情况。 如果topping 0有16个请求，topping 1有8个请求，两者都可以被8整除，所以算法接受，匹配我们可以购买2个topping 0的披萨和1个topping 1的披萨的事实。 

一个有很多人但每个人的请求很少的案例证实了每个人的结构是无关紧要的。 即使每个人都要求混合配料，只有最终总数很重要，并且算法在检查可除性之前正确聚合所有内容。
