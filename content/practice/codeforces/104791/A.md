 ## 解决方案
 ## 问题理解

 我们正在模拟一队人使用饮水机，饮水机由相同的水桶供水，每个水桶都盛有固定量的水。 队列中的每个人都想要一定数量的升水。 分配器一开始装满了水桶，一个接一个地为人们服务。 一旦当前桶在服务期间用完，即使当前人员尚未收到其请求的金额，也会立即更换桶，并且更换算作已使用的额外桶。 该过程将持续进行，直到所有人员都被处理完毕。 

任务不是计算每个人在物理意义上实际收到了多少水，而只是计算在此规则下为每个人提供服务时消耗了多少水桶。 

这些约束允许跨测试用例的总人数最多为 100 万人，并且如果简单地完成，每个模拟步骤与人数呈线性关系。 由于每个人的用水量高达1000升，水桶容量高达1000升，因此总水流量可能很大，但关键的限制是我们无法模拟逐个单位的消耗量。 解决方案必须在恒定的时间内处理每个人。 

一种简单的方法是将剩余桶容量一次减少一升。 这会立即失败，因为单个测试用例可能需要多达 10^6 个人，每个测试用例可能需要多达 10^3 升，产生多达 10^9 次操作，这远远超出了时间限制。 

一个更微妙的错误来自于忘记替换发生在人中间。 例如，如果某人需要的水多于当前水桶中的剩余水量，则即使该人继续，水桶也会被更换并计数。 如果我们只在完成一个人后才检查，我们就会少算桶数。 

一个具体的失败场景是一个容量为 5 的桶，一个人需要 6 升。 正确答案是2个桶，因为第一个桶在5升后用完，第二个桶用于剩余的1升。 任何仅在人员完成时增加存储桶计数的实现都会错误地输出 1。 

## 方法

 蛮力模拟会跟踪当前水桶中还剩下多少水，并反复减去每个人所需的升数。 每当剩余量变为零时，我们就会增加桶计数并将剩余容量重置为 C。这准确地反映了该过程并且是正确的，但如果按升实施，则会变得太慢。 即使按人实施但仍按步骤检查减量，最坏的情况是O(总水单位)，可以达到10^9。 

关键的观察是我们永远不需要模拟单个升。 对于每个人，我们只关心他们的需求是否适合剩余的桶。 如果是这样，我们只需减少剩余容量即可。 如果没有，我们会计算在满足需求之前需要更换多少个满桶。 

这将问题转化为维护单个运行值：当前存储桶中的剩余容量。 每个请求要么直接适合，要么消耗剩余部分加上一定数量的满桶。 这使得每个人的处理时间复杂度为 O(1)。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(Σcᵢ) | O(1) | O(1) | 太慢了 |
 | 最佳 | 每个测试用例 O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们维护两个变量：到目前为止使用的桶的数量和当前桶的剩余容量。

1. 将存储桶计数初始化为 1，将剩余容量初始化为 C，因为我们从已安装的一个完整存储桶开始。 这反映了第一次使用总是消耗至少一个桶的事实。 
2. 按顺序处理每个人。 对于每个所需量 cᵢ，将其与剩余容量进行比较。 
3. 如果 cᵢ 小于或等于剩余容量，则从剩余容量中减去 cᵢ 并继续下一个人。 这是有效的，因为当前的水桶仍然有足够的水来完全满足这个请求。 
4.如果cᵢ大于剩余容量，我们首先意识到当前的桶在这个人的服务期间将被耗尽。 因此，我们将此桶计算为已使用，并计算完成当前桶后剩余的需求量。 
5. 我们从 cᵢ 中减去剩余容量，增加存储桶计数，然后重新填充新存储桶。 然后，我们使用整数除法 cᵢ // C 计算需要多少个完整的附加存储桶来满足剩余需求。每个这样的完整存储桶都被完全消耗，因此我们将该商添加到存储桶计数中。 
6. 如果使用满桶后还有余数 cᵢ % C，我们就再消耗一个桶并相应地设置剩余容量。 否则，如果它完全分开，则最后一个桶恰好以零剩余容量结束。 

关键思想是，一旦我们在人中间切换存储​​桶，他们的其余需求就可以表示为一系列完整存储桶消耗加上可能的部分存储桶。 

处理完所有人员后，每次由于耗尽而新安装一个桶时，桶计数就会反映出来。 

### 为什么它有效

 在每一步中，该算法都保持不变，即当前存储桶已部分使用，并且其剩余容量正是尚未分配给先前人员的容量。 每当我们处理请求时，我们要么减少剩余容量，要么仅在容量不足时才用新的存储桶替换它。 由于每升需求都被计算一次，并且每次跨越桶边界时，我们都会增加计数，因此桶的总数与分配器在此过程中重新填充的次数完全匹配。 排序没有歧义，因为每个人都是按顺序处理的，并且桶耗尽会在发生时立即处理。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, C = map(int, input().split())
        c = list(map(int, input().split()))
        
        buckets = 1
        rem = C
        
        for x in c:
            if x <= rem:
                rem -= x
            else:
                x -= rem
                buckets += 1
                full = x // C
                buckets += full
                rem = C if x % C != 0 else C
                if x % C == 0:
                    rem = 0
                else:
                    rem = C - (x % C)
        
        print(buckets)

if __name__ == "__main__":
    solve()
```该解决方案读取每个测试用例，初始化一个存储桶，并跟踪剩余容量。 

条件分支处理当前请求是否适合剩余的水。 如果是这样，我们只需减少剩余容量即可。 否则，我们消耗当前存储桶的剩余部分，然后将剩余需求转换为完整存储桶使用量加上可能的部分存储桶。 

微妙的部分正在更新`rem`部分食用后正确。 如果需求恰好在桶边界处结束，则剩余容量变为零，这意味着下一个人立即触发补充。 否则，我们将剩余空间存储在最后部分使用的存储桶中。

 ## 边缘情况

 一个关键的边缘情况是当一个人的需求与桶边界完全一致时。 例如，当 C = 3 和请求序列 [3, 3] 时，第一个人恰好消耗了一个存储桶，留下 rem = 0。第二个人必须立即触发一个新存储桶。 该算法会处理此问题，因为每当 x % C == 0 时，余数检查都会将 rem 设置为零，从而强制下一次迭代将系统视为空。 

当请求开始之前剩余容量已为零时，会出现另一种边缘情况。 在这种情况下，算法正确地表现得就像需要一个新的存储桶一样，因为 x > rem 会触发立即替换逻辑并在继续除法逻辑之前增加存储桶计数。
