 ## 解决方案
 ## 问题理解

 该问题模拟了一个系统，其中给定了一组时间间隔，每个间隔代表一个事件，该事件可以贡献或消耗某些资源，具体取决于其类型。 每个事件都有一个时间和一个标签，用于确定它的行为是否类似于调度过程中的“开始”操作或“结束”操作。 任务是确定在只有满足时序和排序条件时配对才有效的约束下可以形成的完整兼容事件对的最大数量。 

更具体的看待它的方式是，每个项目都可以被解释为一个定向机会：一些事件在给定时刻创造能力，而另一些事件则在以后需要该能力。 目标是最大限度地利用先前创建的容量来满足多少需求，同时尊重时间顺序。 

输入由多个独立的场景组成。 对于每个场景，我们读取一个事件列表，每个事件都由一个时间值和一个二进制标志来描述，该标志指示它是“供应类型”事件还是“需求类型”事件。 每个场景的输出都是一个整数：可以与有效供应事件匹配的需求事件的最大数量。 

关键的约束含义是事件的数量可能足够大，以至于任何二次配对策略都立即不可行。 检查所有供需事件对的解决方案在最坏的情况下需要 O(n²) 次比较，一旦 n 达到 10⁵ 左右，这种比较就会崩溃。 

当多个事件共享相同的时间戳时，会出现微妙的边缘情况。 以任意顺序处理事件的天真贪婪方法可能会错误地将需求与同时发生的供应配对，但根据排序规则实际上不允许使用。 例如，如果需求和供给都发生在时间 5，并且规则要求严格的时间优先级，则粗心的实现可能会将它们视为可互换的。 

当所有事件都属于同一类型时，会出现另一种失败情况。 如果全部都是供应事件，则不可能进行配对，并且答案必须为零。 如果全部都是需求事件，则同样不可能进行配对。 任何假设每种类型至少一种而不进行检查的解决方案都会错误地退化。 

## 方法

 蛮力的想法是明确尝试将每个需求事件与每个兼容的供应事件相匹配。 对于每一项需求，我们都会扫描较早发生的所有供应，并选择尚未使用的供应。 这是简单且正确的，因为它直接强制执行配对约束。 

这种方法的问题在于，对于最多 n 个事件中的每一个，我们可能会扫描几乎所有其他事件。 在最坏的情况下，这会导致大约 n × n 次比较，当 n 为 10⁵ 时，大约会进行 1010 次操作。 这远远超出了典型的 2 秒限制所能处理的范围。 

关键的结构观察是，只有事件在时间上的顺序才重要，而不是它们的绝对身份。 一旦我们按时间对事件进行排序，我们就可以有效地模拟一个时间表，在该时间表中我们可以维护可用的供应能力池。 每个需求要么消耗该池中的一个单位，要么在池为空时被跳过。 

这将问题转化为单遍贪婪过程。 我们没有尝试所有配对，而是维护一个计数器，表示到目前为止我们已经看到了多少未使用的供应事件。 当我们遇到需求事件时，如果可能的话，我们会立即匹配它，从计数器中消耗一个单位。 当我们遇到供应事件时，我们会增加计数器。 

这是可行的，因为任何最佳解决方案都不会从推迟供应匹配而选择较早的供应匹配中受益，而早先的供应匹配在时间顺序上更差。 最早的可用供应总是至少与后来的供应一样好，可以满足未来的需求。

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n²) | O(1) | O(1) | 太慢了 |
 | 排序+贪心计数器| O(n log n) | O(n log n) | O(1) 或 O(n) | 已接受 |

 ## 算法演练

 1. 读取测试用例中的所有事件并将每个事件表示为一对（时间、类型）。 此步骤对于将问题线性化为排序变得有意义的形式是必要的。 
2. 按时间递增对所有事件进行排序。 这确保我们按照事件发生的确切顺序处理时间线，这是必需的，因为配对取决于时间可行性。 
3. 初始化计数器`available`为零。 该变量跟踪已看到但仍未使用的供应类型事件的数量。 
4. 迭代排序的事件。 对于每个事件，根据其类型进行分支。 
5. 如果该事件是供应事件，则递增`available`一个。 这代表当时向系统添加一单位的可用容量。 
6. 如果事件是需求事件，检查是否`available`是积极的。 如果是，则递减`available`并将答案加一，因为我们可以将此需求与之前看到的一些供应相匹配。 
7. 如果`available`处理需求时为零，则跳过。 这意味着不存在可以满足它的早期供应。 

### 为什么它有效

 在每一个时间点上，`available`准确地表示已发生但尚未分配给需求的供应事件的数量。 任何有效的匹配都必须将每个需求与不同的早期供应配对，并且贪婪过程始终通过仅跟踪计数而不是身份来隐式使用最早的可用供应。 因为未来的决策从不取决于使用了哪个特定供应，而只取决于剩余的数量，因此计数器完全捕获所有相关状态。 此不变性确保每当需求匹配时，用任何其他早期未使用的供应替换该选择不会改变时间线剩余后缀的可行性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        events = []
        for _ in range(n):
            time, typ = map(int, input().split())
            events.append((time, typ))

        events.sort()

        available = 0
        ans = 0

        for time, typ in events:
            if typ == 0:
                available += 1
            else:
                if available > 0:
                    available -= 1
                    ans += 1

        print(ans)

if __name__ == "__main__":
    solve()
```实现直接遵循算法。 排序是唯一的非线性步骤，它建立了贪婪扫描所需的时间结构。 整数`available`是系统的整个状态，这避免了对显式匹配结构的需要。 

一种常见的实现错误是混淆了类型标志的解释。 如果供给和需求颠倒，算法仍然会运行，但会产生系统性错误的结果，在小型测试中通常显得合理。 另一个问题是忘记按时间排序，这打破了始终先处理较早供应的假设，并导致错误的配对顺序。

 ## 边缘情况

 一个重要的边缘情况是需求出现在供应之前。 用于输入`(1,demand) (2,supply)`，该算法首先处理需求并且正确地不执行任何操作，因为`available`为零。 当供应稍后到达时，它只能用于未来的需求，而不会追溯，从而保持了正确性。 

另一种情况是在单个需求之前有多个供应。 为了`(1,supply) (2,supply) (3,demand)`，计数器在消耗一次之前增加两次，留下一个未使用的供应。 该算法自然会保留剩余容量以满足以后的需求，而无需任何额外的簿记。 

最后一个微妙的情况是交错，贪婪的顺序在视觉上很重要，但在逻辑上却无关紧要，例如`(1,supply) (2,demand) (3,demand)`。 第一个需求消耗了唯一可用的供应，而第二个需求则被跳过。 任何试图为以后的需求“保留”供应的替代解释都不会改善结果，因为供应的贡献是无法区分的。
