 ## 解决方案
 ## 问题理解

 我们得到了几个配方，每个配方都描述了具有固定数量插槽的工艺设备在填充成分时的行为方式。 配方是 k 个位置上的模式，其中每个位置要么为空，要么包含特定的成分类型。 每次使用设备时，如果当前配置与配方匹配，则可以执行该配方并消耗模式中涉及的每个非空槽中的一个单位。 

所有成分在开始时都是无限的，但是一旦执行配方，就会减少相应槽中的计数。 只要仍然可以应用至少一种配方，该过程就会继续。 我们想要选择 k 个槽的初始填充，以便通过重复应用匹配的配方，我们最大化可以至少执行一次的不同配方的数量。 

重要的微妙之处在于，配方不会消耗全局的任意资源。 它只从它匹配的特定槽中消耗。 这使得系统完全依赖于食谱如何在位置和值之间重叠，而不是依赖于成分的任何全局计数。 

约束 n, k ≤ 2000 意味着 O(n²) 或 O(nk) 类型的解决方案是可以接受的，但是任何试图模拟配方应用程序序列或考虑所有可能的槽填充的东西都太大了。 将成分分配给槽位的强力方法是 k 的指数，这立即是不可能的。 

当多个配方共享部分结构时，就会出现幼稚的失败情况。 例如，如果两个配方仅在一个槽位上不同，则对该槽位的贪婪决策可能会错误地消除其中一个，即使不同的初始分配允许两者。 这表明每个配方的本地决策并不可靠。 

关键的隐藏结构是，一旦我们确定了每个槽中放置的成分类型，配方要么完全兼容，要么永远不会触发。 整个过程简化为选择 k 长度分配，以最大化其中“包含”的配方模式数量，这意味着所有非零条目都完全匹配。 

一种幼稚的方法会尝试模拟执行顺序或贪婪地一一选择兼容的配方，但兼容性不会以有用的方式动态变化。 一旦固定了一个槽，就无法对其进行调整以适应以后的选择，因此问题本质上是选择一个同时满足许多模式的全局分配。 

## 方法

 蛮力的想法是尝试 k 个槽的所有可能的填充，并且对于每次填充，模拟可以触发哪些配方。 即使将每个槽限制为输入配方中出现的值，仍然会留下指数数量的配置，因为每个槽可以独立地采用许多值。 对于每个配置，检查所有 n 个配方需要 O(nk)，因此总数变得完全不可行。 

关键的见解是扭转观点。 我们不选择填充和测试配方，而是将配方视为槽分配的约束。 每个配方指定，对于每个非零位置，如果我们希望该配方可执行，则槽必须包含什么内容。 如果两个配方在任何位置上不一致，则它们不能在相同的初始填充下同时满足。 

这将问题转化为选择在所需槽分配方面成对一致的配方的最大子集。 一致性是按槽定义的：每当两个配方在同一位置指定非零值时，它们必须就该值达成一致。 空条目的行为类似于通配符，并且不限制插槽。

然后可以从任何最大一致集构建最佳填充：对于每个槽，如果任何选定的配方对其进行限制，则该值是固定的； 否则它可以是任意的。 一旦选择了此分配，一致集中的所有配方都将变为可执行的，因为它们的模式与槽配置匹配，并且没有资源争用阻止它们至少出现一次。 

因此，问题简化为找到在任何位置上都不冲突的最大配方组，这是 k 维上的结构化兼容性最大化问题。

 | ---| ---| ---| ---|
 | 暴力破解所有馅料 | k 的指数 | O(k) | 太慢了 |

 ## 算法演练

 1. 读取所有配方并将每个配方视为 k 个槽上的部分分配，其中只有非零条目施加约束。 这种重新表述使每个配方成为一组（位置，值）对。 
2. 对于每个配方，尝试确定它是否与代表所选配方集的增长结构兼容。 我们不是首先显式构建最终集，而是增量地维护槽约束。 
3. 以任意顺序处理配方，并维护一个数组，为每个槽记录“未分配”或固定成分值。 该数组表示当前隐含的填充。 
4. 在考虑配方时，检查每个非零位置。 如果插槽未分配，它可以采用配方的值。 如果已经分配，​​它必须与配方的值匹配，否则该配方不能包含在当前一致集中。 
5. 如果配方兼容，接受它并更新它涉及的所有未分配的插槽。 这可确保当前分配与迄今为止所有选择的配方保持一致。 
6. 计算有多少菜谱被接受。 该计数代表最大一致集，其对应于实现许多不同的可执行配方的有效填充。 

这种贪婪构造起作用的原因是，一旦为槽分配了值，该分配就会由使用它的第一个配方强制执行。 任何与它相矛盾的未来配方都不能在同一配置中共存，因此拒绝它是不可避免的。 推迟分配决策没有任何好处，因为每个槽约束都是绝对的，并且不依赖于超出一致性的顺序。 

### 为什么它有效

 该算法保持了以下不变性：所有已接受的配方在迄今为止已分配的每个插槽上都一致。 每个新接受的配方要么引入新的约束，要么与现有的约束一致。 任何冲突都会立即意味着没有一个全局分配可以同时满足当前结构和新配方，因此跳过它不会减少最大可实现的一致集。 因此，最终的集合是成对一致配方的最大集合，它直接对应于实现所有这些配方的可行填充。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    recipes = [list(map(int, input().split())) for _ in range(n)]

    slot = [-1] * k
    used = 0

    for r in recipes:
        ok = True
        for i in range(k):
            if r[i] == 0:
                continue
            if slot[i] == -1:
                continue
            if slot[i] != r[i]:
                ok = False
                break

        if not ok:
            continue

        for i in range(k):
            if r[i] != 0:
                slot[i] = r[i]

        used += 1

    print(used)

if __name__ == "__main__":
    solve()
```该代码维护一个全局赋值数组`slot`，它代表工匠当前的隐含配置。 每次迭代中的第一个循环检查配方是否可以与此部分分配共存。 如果第二个循环被接受，则应用其约束。 

一个常见的实施陷阱是更新`slot`在完全验证兼容性之前。 这会腐蚀国家并错误地接受相互冲突的食谱。 分为验证阶段和更新阶段可以防止这种情况发生。 

另一个微妙之处是正确处理零条目。 零绝不能覆盖现有的槽值，因为它们代表“无约束”而不是空的强制分配。

 ## 边缘情况

 当多个配方尝试将不同的值分配给同一槽位但仅在部分分配已经发生之后，就会出现关键的边缘情况。 例如，如果第一个接受的配方将槽 0 固定为值 5，则必须立即拒绝任何要求槽 0 为 7 的后续配方。 该算法通过在应用更新之前检查一致性来处理此问题，确保对槽的第一次分配成为永久约束。 

当配方没有非零条目时会出现另一种情况。 这样的配方没有任何限制并且总是兼容的。 该算法正确地接受它而不修改任何槽，因为验证循环没有发现冲突的位置并且更新循环不执行分配。 

这些案例证实该解决方案正确区分约束和非约束，同时保持全局一致的分配。
