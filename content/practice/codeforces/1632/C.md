 ## 解决方案
 ## 问题理解

 我们有两个整数，最初称为$a$和$b$， 和$a < b$。 在一步操作中，我们可以将其中之一加一，或者替换$a$通过按位或$a$和$b$。 这个过程一直持续到两个数字相等，并且我们想要所需的最少移动次数。 

关键的困难在于 OR 运算不是线性的：它会急剧增加$a$一步中，取决于当前存在的位$b$。 另一方面，增量是可预测的，但可能成本高昂。 问题本质上是关于决定何时通过增加“等待”是有益的$b$，使得后面的OR运算变得更加强大。 

每个测试用例的约束足够小，涉及对每个位位置的可能状态进行对数或线性扫描的解决方案就足够了。 全部的总和$b$跨测试用例的值最多是$10^6$，这强烈表明$O(b)$或者$O(b \log b)$总体解决方案是可以接受的，但是任何尝试模拟所有操作序列的方法都会太慢，因为分支选择呈指数增长。 

当重复应用 OR 看起来很有吸引力但实际上会增加的情况下，就会出现天真的担忧$a$太多太早了。 例如，如果$a = 1$和$b = 4$，使用 OR 立即给出$a = 5$，跳过中间最优增量。 然而，在可能的情况下盲目应用 OR 可能会在更复杂的情况下超越最佳中间状态，例如$a = 3, b = 6$，其中延迟 OR 会产生更少的总操作。 

主要的微妙之处在于 OR 运算仅取决于当前的二进制表示$b$，因此增加$b$以结构化方式改变 OR 的未来用途。 

## 方法

 暴力解决方案将对待每个状态$(a, b)$作为图中的节点并运行最短路径搜索。 每个节点最多有三个转换：增量$a$, 增量$b$，或申请$a := a \,|\, b$。 这是正确的，因为每个操作都会花费一成本，并且我们正在寻找最小的操作序列。 

然而，国家空间是巨大的。 这两个变量都可以增长到超出其初始值，即使我们人为地限制它们，可达状态的数量也约为$O(b^2)$。 即使对于$b$大约$10^6$。 该搜索还浪费精力探索许多仅在对称增量上有所不同的等效配置。 

关键的观察结果是最终值必须至少为$b$，因为两个数字都只会增加或成为 OR 结果，其界限是通过增加$b$。 这表明我们可以考虑最终目标值，而不是探索任意序列$x$这两个数字最终都达到了。 一旦两者相等，就不需要进一步的“或”或增量，因此该过程以某个最终值结束$x \ge b$。 

现在确定候选最终值$x$。 我们可以计算使两个数字等于的成本$x$。 增加$b$到$x$成本$x - b$运营。 增加$a$或使用 OR 运算取决于有多少位$x$已经存在于$a$，以及必须通过首次加注“解锁”多少$b$。 结构变成：我们尝试所有可能的目标值$x$在上面的一个小社区里$b$，因为有一次$x$变得太大，线性成本占主导地位。 

这导致了一个简单的优化策略：迭代可能的最终值$x$开始于$b$，并且对于每个计算使两个数字达到的最小成本$x$， 在哪里$a$可以使用 OR 与中间值$b$。 搜索空间很小，因为一旦$x$超过一定阈值（大致$b + O(\sqrt{b})$在最坏的推理中，但实际上受到约束），增量占主导地位。 

这减少了有效评估少量候选目标的问题。

 ## 算法演练

 我们用数字修复一个测试用例$a < b$。 

1. 将答案初始化为$b - a$。 这对应于仅递增的简单策略$a$直到匹配为止$b$，同时完全忽略 OR。 这始终是有效的上限。 
2. 考虑可能的最终值$x$开始于$b$在一个小的有界范围内尝试“或”运算可能仍然是有益的。 对于每个$x$，我们计算将两个数字转换为的最小成本$x$。 
3. 计算固定成本$x$，我们模拟需要多少次 OR 运算来“对齐”位$a$和$x$。 直觉是 OR 仅在之后变得有用$b$已经增加得足够多，因此它的按位结构有助于构造$x$。 
4. 对于每位候选人$x$，计算成本为：

 筹集成本$b$到某个中间值$b'$,

 加上使用 OR 运算进行转换的成本$a$朝向$x$,

 加上剩余的增量$a$和$b$到平等。 
5. 对所有候选人保持最低限度。 

### 为什么它有效

 应用 OR 运算的过程永远不会减少信息：它只设置已经存在于$b$。 这意味着 OR 的有用性完全由应用时较大数字的位结构决定。 任何最佳策略都可以重新安排，以便所有 OR 运算在相对于当前的情况最有用时发生。$b$，并且所有增量仅用于解锁位而不是盲目地追求平等。 

由于状态空间在两个值上都是单调的，并且 OR 仅扩展位集，因此最佳路径会崩溃为少量有意义的候选端点，而不是任意长交错。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        a, b = map(int, input().split())

        ans = b - a  # only increment a up to b

        # try a few possible "final alignment points"
        # it is enough to try b + k for small k
        for add in range(0, 33):
            x = b + add

            # cost to raise b to x
            cost_b = add

            # simulate best possible growth of a using OR
            cur_a = a
            cur_b = b + add
            ops = cost_b

            # greedily apply OR when it helps
            while cur_a < x:
                if (cur_a | cur_b) > cur_a:
                    cur_a = cur_a | cur_b
                    ops += 1
                else:
                    cur_a += 1
                    ops += 1

                if ops >= ans:
                    break

            ans = min(ans, ops)

        print(ans)

if __name__ == "__main__":
    solve()
```该代码首先设置一个基线答案等于$b - a$，这相当于完​​全忽略 OR 运算。 即使所有 OR 策略结果都更糟，这也确保了正确性。 

外循环尝试略高于候选最终值$b$。 选择 33 的界限是因为增加$b$超过大约 30 步就已经超出了直接递增的成本$a$大多数情况下都在限制范围内。 

在里面，我们模拟了到达的过程$x$。 变量`cur_b`代表当前值$b$增量后，并且`cur_a`跟踪 OR 和增量运算如何演变$a$。 

在每一步中，我们都会检查应用 OR 是否会改进$a$。 如果是，我们就接受； 否则我们增加。 这个贪婪规则反映了这样一个事实：OR 仅在严格增加时才有用$a$，一旦它不再有用，增量就是唯一剩下的路径。

 我们在 1 次操作中达到了相等，从而改进了 1 的答案。 

这表明OR可以立即对齐$a$到$b$当位兼容时。 

### 示例 2：$a = 5, b = 8$基线是$8 - 5 = 3$。 

尝试$x = 8$。 

| 步骤| cur_a | cur_b | 运营| 操作|

这些痕迹表明，该算法探索了足够多的附近目标，以找到增量增长和按位加速之间的最佳平衡。

## 测试用例```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        a, b = map(int, input().split())
        ans = b - a
        for add in range(0, 33):
            x = b + add
            cur_a = a
            cur_b = b + add
            ops = add
            while cur_a < x:
                if (cur_a | cur_b) > cur_a:
                    cur_a = cur_a | cur_b
                    ops += 1
                else:
                    cur_a += 1
                    ops += 1
                if ops >= ans:
                    break
            ans = min(ans, ops)
        out.append(str(ans))
    return "\n".join(out)

 ## 边缘情况

 一个重要的边缘情况是当$a$已经接近$b$， 例如$a = b - 1$。 在这种情况下，基线答案是 1，OR 可能会也可能不会改善它。 为了$a = 4, b = 5$, 或给出$4 | 5 = 5$，所以最优答案仍然是 1。算法正确地检查$x = b$并捕捉到这一点。 

另一个微妙的情况是 OR 最初无用但在增加后变得有用$b$。 为了$a = 2, b = 5$，直接 OR 给出$7$，它会超调，但在增加之后$b$一旦，OR 就与更好的中间结构对齐。 该算法通过尝试来处理这个问题$b + add$状态并在每一步贪婪地评估 OR。 

最后一个边缘情况是$a$非常小并且$b$很大，比如$a = 1, b = 10^6$。 在这里，OR 永远不会补偿对齐位的成本，并且最佳解决方案退化为纯粹的增量。 基线$b - a$占主导地位，并且所有候选模拟都被提前修剪，因为它们超出了当前的最佳答案。
