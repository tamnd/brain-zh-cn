 ## 解决方案
 ## 问题理解

 我们有一排弓箭手，每个人都有一定的生命值。 火球只能投掷到指定位置`2 ... n-1`。 如果我们扔到位置`i`，那么：

 - 弓箭手`i`失去`a`健康，
 - 弓箭手`i-1`和`i+1`失去`b`健康。 

只有当生命值严格为负数而不是零时，弓箭手才会死亡。 我们可能会继续瞄准已经死去的弓箭手。 任务是最小化火球的数量并打印目标索引的最佳序列。 

首先重要的是限制的规模。 弓箭手数量最多为`10`, 健康值最多为`15`，并且两种伤害最多为`10`。 这些都是微小的限制。 问题不在于通常的 Codeforce 意义上的渐近优化。 相反，挑战在于发现正确的状态表示并足够积极地修剪搜索空间。 

完全不受限制的蛮力依然会爆炸。 每次射击可以瞄准其中一个`n-2 ≤ 8`职位。 即使最佳答案仅在`20`，这已经大致给出了`8^20 ≈ 10^18`可能的序列。 所以我们需要结构。 

重要的观察是局部性。 投掷位置`i`只影响`i-1`,`i`， 和`i+1`。 一旦我们向右移动得足够远，之前的立场就会变得独立，并且永远不会再改变。 这使得动态规划成为可能。 

有几种边缘情况很容易破坏不正确的实现。 

考虑这个输入：```
3 2 1
2 2 2
```唯一有效的目标是位置`2`。 每一次射击都会产生`1`末端损坏和`2`中间损坏。 两次注射后，生命值变为`[0, -2, 0]`。 端点仍然存在，因为健康状况必须严格为负数。 我们需要第三次射击。 粗心的实施检查`<= 0`而不是`< 0`产生错误的答案。 

另一个微妙的情况是，重复攻击一名已经死亡的弓箭手仍然是最佳选择。```
5 10 1
1 100 1 1 1
```中弓箭手拥有巨大的生命值。 最好的策略是始终瞄准位置`3`，即使附近的弓箭手已经死了，因为我们只关心最小化施法总数。 禁止攻击死去的敌人的算法变得不正确。 

边界处理也很危险，因为位置`1`和`n`不能直接针对。```
4 5 2
9 1 1 9
```伤害弓箭手的唯一方法`1`是通过攻击`2`，也是伤害弓箭手的唯一方法`4`是通过攻击`3`。 任何对称处理所有位置的解决方案都会在这里失败。 

## 方法

 最直接的蛮力是对健康状态的最短路径搜索。 状态是当前的健康状况数组。 从一个状态开始，我们尝试每一个可能的目标位置，并在一次施法后生成下一个状态。 由于每次施法都有相同的成本，BFS 保证了最少的施法次数。 

这是可行的，因为约束很小。 生命值很小，每次攻击只会降低生命值。 尽管如此，国家空间的增长速度仍然非常快。 每个弓箭手的生命值可能会从最初的生命值下降到一些负值，然后才能确定死亡。 即使采用积极的钳位，可达到的状态数量也会变得非常大。 分支因子可达`8`，而 BFS 大部分时间都花在重新审视结构相似的情况上。 

关键的见解是我们实际上并不关心任意的咒语顺序。 重要的是我们在每个位置投了多少次。 

假设我们定义`x[i]`作为我们攻击位置的次数`i`。 那么弓箭手受到的总伤害`j`是：

-`a * x[j]`,
 - 加`b * x[j-1]`,
 - 加`b * x[j+1]`。 

对于每个弓箭手我们只需要：```
total damage > health
```现在问题变成选择非负整数`x[i]`最小化它们的总和。 

这就是地方性变得强大的地方。 射手`i`仅取决于`x[i-1]`,`x[i]`， 和`x[i+1]`。 如果我们从左到右处理位置，那么在固定两个相邻变量后，我们可以确定下一个变量所需的最小值。 

更具体地说，有一次`x[i-1]`和`x[i]`是已知的，对弓箭手唯一剩下的未知贡献`i`来自`x[i+1]`。 我们可以贪心地选择最小的有效值`x[i+1]`。 这将问题转化为相邻计数上的 DP 问题。 

攻击位置最多为`8`，并且每个计数永远不需要变大。 最佳总拍摄次数大致由`150`，因此三次 DP 是完全可行的。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 关于健康状态的暴力 BFS | 指数| 指数| 太慢了 |
 | DP 邻近攻击计数 | O(n * M²) | O(n * M²) | 已接受 |

 这里`M`是每个位置的最大相关攻击次数，在约束条件下该值很小。 

## 算法演练

 1. 定义`x[i]`作为我们攻击位置的次数`i`，其中有效位置是`2 ... n-1`。 
2.重写每个弓箭手的伤害条件。 射手`j`收到：```
b * x[j-1] + a * x[j] + b * x[j+1]
```并且必须满足：```
damage > h[j]
```1.从左到右处理弓箭手。 在步骤`i`，假设我们已经知道`x[i-1]`和`x[i]`。 
2.弓箭手`i`仍然缺乏贡献`x[i+1]`。 计算最小值`x[i+1]`这使得弓箭手`i`死的。 

如果当前伤害已经足够，我们设置`x[i+1] = 0`。 否则我们解决：```
current + b * x[i+1] > h[i]
```这给出：```
x[i+1] = floor((h[i] - current) / b) + 1
```1. 根据最近两次攻击计数存储 DP 状态。 这种转变是确定性的，因为一旦`x[i-1]`和`x[i]`是固定的，最小有效`x[i+1]`是唯一确定的。 
2. 通过尝试所有可能的值来初始化 DP`x[2]`。 自从`n ≤ 10`健康状况很小，安全上限就像`20`或者`25`就足够了。 
3.处理完所有内部位置后，验证最后的弓箭手也死了。 最后一名弓箭手仅受到位置伤害`n-1`。 
4. 在所有有效配置中，选择最小化的一项：```
sum(x[i])
```1. 通过打印每个位置来重建答案序列`i`确切地`x[i]`次。 

### 为什么它有效

 DP 依赖于局部依赖不变量。 射手`i`仅取决于三个相邻攻击计数：```
x[i-1], x[i], x[i+1]
```从左到右处理时，一次`x[i-1]`和`x[i]`是固定的，除了`x[i+1]`与弓箭手变得无关紧要`i`。 选择大于最小可行值的值`x[i+1]`永远无法帮助减少未来的成本，因为所有攻击计数都是非负的，并且未来的弓箭手总是可以从后面的位置受到额外的伤害。 

因此，贪婪转换在局部是最优的，并且由于每个状态转换都为经过处理的弓箭手保留了可行性，因此 DP 精确地探索了所有最优的全局解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

INF = 10**9

n, a, b = map(int, input().split())
h = list(map(int, input().split()))

# x[i] means attacks on position i (1-indexed)
# valid positions are 2..n-1

LIMIT = 25

best = INF
best_x = None

def dfs(pos, x, total):
    global best, best_x

    if total >= best:
        return

    if pos == n:
        # verify last archer
        dmg = b * x[n - 1]
        if dmg > h[n - 1]:
            best = total
            best_x = x[:]
        return

    # current damage on archer pos-1
    dmg = b * x[pos - 2] + a * x[pos - 1]

    need = 0
    if dmg <= h[pos - 2]:
        need = (h[pos - 2] - dmg) // b + 1

    if need > LIMIT:
        return

    x[pos] = need
    dfs(pos + 1, x, total + need)
    x[pos] = 0

# try all possible x[2]
x = [0] * (n + 1)

for start in range(LIMIT + 1):
    x[2] = start
    dfs(3, x, start)

ans = []

for i in range(2, n):
    ans.extend([i] * best_x[i])

print(best)
print(*ans)
```该实现直接反映了数学递推。 

数组`x[i]`存储我们攻击每个内部位置的次数。 由于解释中的索引自然是从 1 开始的，因此代码保持相同的约定以避免翻译错误。 

递归函数从左到右处理位置。 当我们快要决定的时候`x[pos]`，所有早期的攻击计数都已经固定。 射手`pos-1`目前有损坏：```
b * x[pos-2] + a * x[pos-1]
```唯一剩下的可能贡献来自于攻击`pos`，其中添加`b`损害每一个。 我们贪婪地计算所需的最小值。 

在此计算之后，递归永远不会分支。 唯一的分支来自于最初的选择`x[2]`。 这是唯一不受先前约束确定的变量。 

上限`LIMIT = 25`安全是因为健康顶多`15`，并且每次攻击至少贡献`1`损害。 任何最佳解决方案都远低于该范围。 

一个微妙的细节是死亡状况。 代码检查`damage > health`， 不是`>=`。 忽略这种严格的不平等是这个问题中最常见的错误。 

另一个重要的细节是最后的弓箭手。 位置`n`只受到来自攻击的伤害`n-1`，所以在所有变量都固定之后我们必须验证：```
b * x[n-1] > h[n-1]
```在接受解决方案之前。

 ## 边缘情况

 再考虑一下：```
3 2 1
2 2 2
```该算法尝试不同的值`x[2]`。 

为了`x[2] = 2`，端点损伤为：```
b * x[2] = 2
```但端点健康状况也是`2`，因此弓箭手能够生存，因为死亡需要严格的负生命值。 DP 正确地拒绝了这种状态。 和`x[2] = 3`，伤害变为`3`，这就足够了。 

现在检查：```
5 10 1
1 100 1 1 1
```算法可能会不断增加`x[3]`即使邻近的弓箭手已经死了。 这是正确的，因为允许攻击死去的敌人，并且最小化法术数量比避免过度杀戮更重要。 

最后：```
4 5 2
9 1 1 9
```第一个弓箭手只能受到该位置攻击的溅射伤害`2`，而最后一个弓箭手仅受到该位置攻击的溅射伤害`3`。 从左到右的递归自然地保留了这些边界约束，因为第一次和最后一次检查仅涉及一个相邻攻击计数而不是两个。
