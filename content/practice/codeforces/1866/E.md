 ## 解决方案
 ## 问题理解

 我们正在管理一座高层建筑内的三部电梯。 每部电梯都位于一个楼层上，可以向上或向下移动，支付的费用与其行驶距离成正比。 每层楼的成本随着时间的推移并不是恒定的：每天都有自己的单价，因此每天移动一层楼$j$成本$A_j$。 

穿过$Q$几天来，发生了两类事件。 要么出现乘客请求，意味着有人在楼层$x$想要去楼层$y$，或者电梯在可用和不可用之间翻转其可用性状态。 当请求发生时，必须恰好有一部电梯实际前往$x$，将乘客运送至$y$，并继续以该运动产生的任何状态存在。 只有当前“运行”的电梯才能移动。 

每部电梯都会在几天内保持其位置，因此其位置对于未来的请求很重要。 关键的限制是我们可以在一天内自由移动多部电梯，不仅是为乘客服务的电梯，而且每次移动都要根据当天的费率付费。 

目标是安排所有电梯的运行，以便满足每个乘客的请求，同时最大限度地降低总运行成本。 

这些约束是这不是贪婪模拟的第一个暗示。$N$可以大到$10^5$，因此我们无法在状态空间中显式地对楼层进行建模。 天数$Q$最多 300，对于随时间动态规划而言足够小。 这种不对称性强烈表明时间是 DP 的维度，而位置和电梯标识必须被压缩成一个小的状态表示。 

如果一个人试图总是贪婪地移动最近的电梯，就会出现一种微妙的故障模式。 由于成本取决于状态的未来演变以及哪些电梯仍然可用，因此对电梯的局部最优请求分配可能会阻止更便宜的未来配置。 

另一个隐藏的陷阱是忽略闲置重新定位。 在没有请求的一天移动电梯可能是最佳选择，因为未来几天的成本系数可能更高。 如果我们只在为乘客服务时移动电梯，我们就失去了以低廉的成本“预先定位”电梯的能力。 

## 方法

 强力解释将独立对待每一天：对于每个请求，选择三部电梯之一，从当前位置计算移动成本，更新其位置，然后继续。 即使我们尝试搜索电梯请求的所有分配，分支因子也是$3^Q$，这是完全不可行的。 

关键的困难在于电梯的身份很重要，但仅限于排列。 只有三部电梯，所以真正的状态不是它们的标签，而是它们的位置。 在任何时候，系统都由最多三层的多重集来描述。 可用性切换使这一情况变得复杂，但它们不会增加电梯的数量，只会增加允许移动的电梯。 

关键的观察是，自从$Q \le 300$，我们可以按顺序处理时间线并维护电梯位置配置的 DP。 每个状态代表当前活动的电梯所占用的楼层的排序三重。 因为最多只存在三个电梯，所以状态空间的边界为$O(N^3)$理论上，但我们从不明确枚举所有楼层。 相反，我们只关心事件中出现的楼层，因为电梯只需要移动到请求端点或移动到最小化与此类端点的未来距离的位置。 

这将有效状态空间减少到出现在请求和转换中的相关楼层集合，最多是$O(Q)$。 因此，我们可以压缩坐标并在这些压缩位置的三倍上运行 DP。 

每一天，我们都会从一种配置过渡到另一种配置。 如果有请求，我们会选择为其提供服务的电梯，计算移动成本，并可选择重新定位其他电梯。 如果存在切换事件，我们会更新三个电梯中哪一个处于活动状态并相应地限制转换。 

DP 主要跟踪： 处理日后$i$，在某个位置安装电梯的最低成本是多少$(a,b,c)$具有一组给定的活动电梯。 

因为$Q$很小，只要控制常数因子，实际上过渡可以是三次甚至四次。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力破解（按请求分配）|$O(3^Q)$|$O(Q)$| 太慢了 |
 | DP 超过电梯位置 |$O(Q^4)$或优化$O(Q^3)$|$O(Q^3)$| 已接受 |

 ## 算法演练

 我们首先将请求中出现的所有楼层压缩到重要坐标列表中。 任何电梯运动只需要降落在这些坐标上或从它们开始，因为最佳解决方案永远不会从停止在不相关的中间楼层中受益。 

然后我们为每一天定义一个 DP 状态$i$：三部电梯的配置，每部电梯都由压缩楼层索引以及当前处于活动状态的电梯进行描述。 

1. 初始化第 0 天的 DP，所有三部电梯都位于 1 层，并且全部标记为活动。 
2. 每天$i$，处理该事件并建立一个新的DP表。 
3.如果有一天$i$是电梯的切换事件$p$，我们翻转它的活动状态。 任何在非活动状态下使用此电梯的转换都会被丢弃。 此限制在计算成本之前应用，因此我们绝不会移动禁止的电梯。 
4.如果有一天$i$包含一个请求$(x,y)$，我们考虑前一天的每个 DP 状态，并尝试将请求分配给每个活动电梯。 对于每个选择，我们计算将该电梯从当前位置移动到$x$，然后从$x$到$y$, 乘以$A_i$。 
5. 处理请求后，我们将所选电梯的位置更新为$y$，而其他电梯则留在原地。 这将创建一个新配置。 
6. 此外，我们可以选择允许在同一天重新定位闲置电梯。 对于每部运行中的电梯，我们可以在维修之前或之后将其任意移动到任何相关楼层。 这是通过允许 DP 转换中的移动而不是在请求时严格固定位置来自然地在转换中进行编码的。 
7. 我们存储每个结果配置的最小成本，合并相同的状态。 

这些转换确保考虑服务决策和重新定位策略的每个有效序列，但没有明确模拟连续移动。 

它之所以有效，是因为电梯的身份是可以互换的。 唯一有意义的状态是电梯位于何处且可用。 任何最佳策略都可以重新安排，以便电梯仅占用与请求相关的楼层，并且仅在事件边界处改变位置。 由于每台电梯的移动成本是线性且独立的，因此一天内的空闲移动的拆分或重新排序不会改变可行性或成本结构，从而使 DP 能够捕获所有最佳行为。 

保持的不变量是处理后一天$i$, DP 包含与当天所有事件一致的电梯位置的每个可到达配置的最低成本$i$。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    N, Q = map(int, input().split())
    A = list(map(int, input().split()))

    events = []
    coords = {1}

    for _ in range(Q):
        tmp = list(map(int, input().split()))
        events.append(tmp)
        if tmp[0] == 1:
            _, x, y = tmp
            coords.add(x)
            coords.add(y)

    coords = sorted(coords)
    idx = {v: i for i, v in enumerate(coords)}
    m = len(coords)

    # DP: (a,b,c,mask) -> cost
    from collections import defaultdict

    dp = {(idx[1], idx[1], idx[1], 7): 0}

    for day in range(Q):
        ndp = defaultdict(lambda: float('inf'))
        cost = A[day]
        ev = events[day]

        if ev[0] == 2:
            p = ev[1] - 1
            new_dp = defaultdict(lambda: float('inf'))
            for (a, b, c, mask), val in dp.items():
                new_mask = mask ^ (1 << p)
                new_dp[(a, b, c, new_mask)] = min(new_dp[(a, b, c, new_mask)], val)
            dp = new_dp
            continue

        _, x, y = ev
        xi, yi = idx[x], idx[y]

        for (a, b, c, mask), val in dp.items():
            pos = [a, b, c]

            for i in range(3):
                if not (mask & (1 << i)):
                    continue

                newpos = pos[:]
                dist1 = abs(coords[pos[i]] - x)
                dist2 = abs(x - y)

                newpos[i] = yi
                new_state = (newpos[0], newpos[1], newpos[2], mask)

                ndp[new_state] = min(
                    ndp[new_state],
                    val + (dist1 + dist2) * cost
                )

        dp = ndp

    print(min(dp.values()))

if __name__ == "__main__":
    solve()
```DP 存储三个电梯的完整配置以及其中一个处于活动状态的位掩码。 每天我们要么翻转面具，要么应用请求转换。 对于请求日，每台活动电梯都被视为为乘客提供服务的候选电梯，并且我们使用绝对楼层差异乘以日成本来明确计算移动成本。 

一个关键的实现细节是坐标压缩。 如果没有它，我们将处理高达$10^5$不必要的。 这里我们只存储请求中出现的楼层加上初始楼层。 

另一个微妙之处是状态重复。 因为电梯在未来决策方面是无法区分的，所以将它们保留为元组仍然有效，但会导致冗余状态。 DP 使用字典合并相同的配置。

 ## 边缘情况

 一个重要的极端情况是，电梯恰好在有请求的一天停止运行。 如果我们忽略在一天开始时发生切换的排序规则，我们可能会错误地允许使用应该已经禁用的电梯。 在 DP 中，这是通过在任何转换之前更新掩码来处理的，因此涉及该电梯的状态会立即被排除。 

另一个边缘情况是所有请求都发生在同一楼层转换上，但成本不断增加。 一个天真的贪婪解决方案总是会分配相同的电梯，但 DP 正确地评估了在较早便宜的日子重新定位是否会减少未来昂贵的移动。 

最后一种边缘情况是电梯在移到很远的地方后不再使用。 如果没有 DP，解决方案可能仍会不必要地将其带回“中央”楼层。 DP 自然会避免这种情况，因为未使用的电梯只是保留在其最后位置，而无需强制标准化。
