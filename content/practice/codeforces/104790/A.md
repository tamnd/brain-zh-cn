 ## 解决方案
 ## 问题理解

 我们获得了一系列软件包，每个软件包都有已知的下载大小。 在升级过程中的某个时刻，我们观察到恰好有一些数量的软件包已经完全完成下载，而​​最多可以同时下载固定数量的软件包。 下载是并行的，因此最多在任何时间`k`正在积极下载软件包，已完成的软件包不再有效。 

关键的问题是，进度指示器无法完美地区分“完全下载但尚未标记完成”和“仍在进行中”，因此在观察时刻，某些活动下载可能会有效地将其完整大小贡献给显示的进度，即使它们尚未正式完成。 

我们被要求计算在我们精确观察到的时刻可能已经完成的总下载大小的最大可能部分`m`完成的包，在最多的约束下`k`软件包同时下载，下载顺序完全未知。 

也就是说，我们可以自由选择哪些包已经下载完毕，哪些包正在下载，哪些还没有开始，只要准确`m`最多完成`k`是活跃的。 我们希望以一种最大化迄今为止下载数据总量的方式进行安排，包括已完成的包和当前正在处理的包（可以假设几乎已完成）。 

输入尺寸`n`可以达到`100000`，因此任何涉及排序的解决方案都是可行的，但任何二次或涉及排列重复模拟的解决方案都是不可行的。 尝试已完成和正在进行的包的所有子集的解决方案会太慢，因为这会组合爆炸。 

出现微妙的边缘情况时`k`相对于`n`。 在这种情况下，选择完成的包后的所有剩余包仍然可以被视为正在进行中，这意味着基本上所有内容都可以对进度总数做出贡献。 

另一个重要的情况是当`m = 0`。 那么一切都还没有完全完成，直到`k`软件包可以将其完整大小作为正在进行的下载提供。 

## 方法

 暴力方法会尝试模拟所有可能的选择方式`m`成品包最多`k`其余的活跃下载。 对于每个配置，我们将计算总贡献大小并跟踪最大值。 这在原则上是正确的，但完全不可行，因为选择完成集和活动集的方法数量是组合的`n`。 

关键的观察结果是问题的结构根本不依赖于时间顺序。 我们只关心有多少个包裹被完全清点（`m`）以及有多少额外的软件包仍然可以充分贡献，因为它们正在进行中（`k`）。 这意味着我们只是选择一组尺寸`m + k`从`n`完全有助于所观察到的进展的一揽子计划。 

为了最大化总进度，我们应该始终为已完成的集和正在进行的集选择最大的包，因为每个包在这两种情况下都贡献其完整大小。 没有惩罚或部分权衡：每个选定的包都独立且完全地贡献于百分比的分子。 

因此，最优策略简化为按降序对所有包裹大小进行排序，并对最大的包裹大小求和。`m + k`价值观。 分母是所有封装尺寸的总和。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力（选择已完成和正在进行的组）| 指数| O(n) | 太慢了 |
 | 排序并取顶部`m + k`| O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 将包裹大小存储在数组中。 

1. 计算所有包裹尺寸的总和。 这将是最终百分比的分母。 
2. 按降序对数组进行排序，以便首先考虑较大的包。 
3. 拿第一个`m + k`此排序列表中的元素。 这些代表了软件包的最佳选择，可以通过完成或正在进行但有效地算作完成来充分促进观察到的进展。 
4. 总结这些`m + k`元素以获得观察时可实现的最大下载大小。 
5. 将该总和除以总和，然后乘以 100 将其转换为百分比。 

步骤 3 有效的原因是我们可以在事后自由地将角色分配给包：最大的包`m`成为“完成”，下一个最大的`k`变为“当前正在下载但实际上已完全计数”。 

### 为什么它有效

 在观察的那一刻，恰好`m`包裹处于完成状态，并且最多`k`可以主动下载。 每个活动下载都可以贡献其完整大小以显示进度，完成的包也贡献其完整大小。 

这意味着总计数进度纯粹是通过选择最多来确定的`m + k`其完整尺寸包含在总数中的包裹。 由于对必须完成哪些特定包没有限制，只对完成多少个包有限制，因此任何角色分配都是有效的。 因此，最大化总和就等于选择最大的可用封装尺寸。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n, m, k = map(int, input().split())
sizes = list(map(int, input().split()))

total = sum(sizes)
sizes.sort(reverse=True)

take = min(n, m + k)
best = sum(sizes[:take])

print((best / total) * 100)
```该解决方案首先读取输入并计算所有包的总大小。 然后它按降序对包大小进行排序，以便我们可以首先贪婪地选择最有价值的贡献。 

变量`take`确保我们不会超过可用包裹的数量`m + k > n`。 最终结果以浮点百分比计算。 使用Python的浮点除法就足够了，因为所需的精度仅为`1e-4`。 

一个常见的实施陷阱是忘记夹紧`m + k`经过`n`，这会导致索引错误或不正确的总和。 另一个微妙的问题是整数除法，在计算百分比时必须避免它。 

## 工作示例

 ### 示例 1

 输入：```
5 1 2
10 25 30 15 20
```尺寸排序：`[30, 25, 20, 15, 10]`我们采取`m + k = 3`元素。 

| 步骤| 已选套装| 总和 |
 | ---| ---| ---|
 | 已完成 + 正在进行中的选择 | 30、25、20 | 75 | 75

 总和是`100`，所以答案是`75%`。 

这表明最好的策略是将最大的包视为已完成或接近完成，从而最大化贡献。 

### 示例 2

 输入：```
5 0 4
4 2 7 1 3
```尺寸排序：`[7, 4, 3, 2, 1]`我们采取`m + k = 4`元素。 

| 步骤| 已选套装| 总和 |
 | ---| ---| ---|
 | 精选热门元素 | 7, 4, 3, 2 | 16 | 16

 总和是`17`，所以答案是`94.1176...%`。 

这个案例表明，当没有包完成时，所有贡献都来自正在进行的下载，但同样的贪婪选择仍然适用。

## 测试用例```python
import sys, io

def solve(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m, k = map(int, input().split())
    a = list(map(int, input().split()))
    total = sum(a)
    a.sort(reverse=True)
    take = min(n, m + k)
    best = sum(a[:take])
    return str((best / total) * 100)

# provided samples (second sample)
assert abs(float(solve("5 0 4\n4 2 7 1 3\n")) - 94.117647059) < 1e-6

# custom: minimum case
assert solve("1 0 1\n5\n").startswith("100")

# all equal values
assert solve("4 2 2\n10 10 10 10\n").startswith("100")

# k = 0 case
assert solve("5 2 0\n1 2 3 4 5\n").startswith("60")

# m + k > n
assert solve("3 2 5\n1 2 3\n").startswith("100")

 | ---| ---| ---|
 |`1 0 1 / 5`|`100%`| 单元素正确性 |

 ## 边缘情况

 当`m = 0`，算法简化为选择最大的`k`包。 排序后的选择仍然直接应用，结果只是顶部的总和`k`尺寸超过总数。 

什么时候`k = 0`，不存在正在进行的贡献，因此只有顶部`m`包裹被计数。 该算法仍然有效，因为`m + k = m`。 

什么时候`m + k >= n`，所有包都包含在总和中，所以答案始终是`100%`。 钳位步骤确保我们不会尝试超出数组边界，并且逻辑自然会崩溃以对所有内容求和。
