 ## 解决方案
 ## 问题理解

 我们正在控制一艘拥有两门独立武器的船。 每种武器都有固定的威力和固定的冷却时间。 一旦武器开火，它就会在冷却时间内变得不可用，然后再次准备就绪。 

在任何时候，当至少一种武器准备就绪时，我们可以选择发射任何一种准备好的武器，或者如果两种武器都准备好了的话，可以同时发射两种武器。 如果两者同时发射，它们的力量就会在一次攻击中叠加。 

敌舰具有耐久值和恒定的护盾。 每次攻击都会降低耐久度，数值为总火力减去护盾值。 因为每次攻击都会减少护盾，所以即使是强力的组合射击也会被部分吸收。 

目标是在最短的时间内将耐用性降低到零或更低。 

关键状态不仅仅是时间，而是两个周期性过程之间的相互作用：两种武器独立充电，我们根据哪种组合最大化单位时间的伤害来选择何时开火。 

对耐久性和功率的限制很小，但对冷却时间的限制非常大，最多 10^12。 这立即排除了随着时间的推移进行的任何模拟。 如果我们密集地对待时间，我们就无法一步一步地迭代时间，甚至不能逐个事件地迭代时间。 相反，我们必须推理触发事件的结构。 

一个天真的错误是假设只要有可能就贪婪地触发是最佳的。 例如，总是在可用的情况下同时发射两种武器可能会浪费未来的对准机会，而延迟射击可以提供更强大的联合攻击计划。 

另一个微妙的失败案例来自于忽略同步。 假设一种武器的冷却时间非常短，而另一种武器的冷却时间非常慢。 幼稚的方法可能会高估等待慢速武器的价值，即使单独重复发射快速武器会更好。 

一个具体的问题场景是：

 p1 = 10，t1 = 1

 p2 = 9，t2 = 1000

 h = 5，s = 0

 如果我们总是等待两种武器，我们就会错过许多最佳的快速单发射击。 

因此，问题的根本在于在孤立的快速攻击和偶尔的同步大型攻击之间进行选择。 

## 方法

 如果我们忽略结构，我们可以根据两个激光器当前冷却计时器定义的状态来思考。 每个状态都会及时向前转换，直到至少一个激光器准备就绪，然后我们选择发射其中一个或两个。 

这导致冷却阶段网格上的连续时间最短路径问题。 如果我们将时间离散化为所有相关的充电事件，状态的数量在时间上仍然是无限的，因为冷却时间很大并且可能是很长的链。 随着时间的推移直接最短路径或 DP 是不可行的。 

关键的简化来自于观察到只有触发时刻才重要，而不是中间的等待。 在两次触发事件之间，除了两个计时器向前移动之外，没有任何变化。 所以我们只关心触发事件的序列。 

每次射击事件都会产生固定的伤害量：

 单发 1 给出 p1 - s

 单发 2 给出 p2 - s

 双射给出 p1 + p2 - s

 唯一的困难是安排这些事件的限制是双发需要两种武器同时准备好。 

我们观察到系统在结构上是周期性的，而不是跟踪绝对时间：每个激光独立循环，并且任何最佳策略都可以描述为我们等待所选子集准备好并发射的时间序列。 

此问题的标准技巧是及时对答案进行二分搜索。 如果我们固定一个时间T，我们可以问：在时间T之前我们能造成的最大伤害是多少？ 如果我们能够有效地计算这一点，我们就可以找到实现至少 h 个损害的最小 T。 

现在问题就变成了：在时间T内，每种射击模式可以使用多少次，又该如何组合呢？

我们观察到，对于任何 T，每个激光器的可能发射时间集是固定的。 激光 i 以 t_i 的倍数发射。 当两个计时器对齐时，就会发生双射击，这意味着时间是 lcm(t1, t2) 的倍数。 然而，明确使用 LCM 是不必要的； 相反，我们可以贪婪地推理配对事件。 

对于固定的 T，我们可以计算：

 每个激光器有多少个单一机会，

 其中有多少可以配对成双镜头。 

由于 h ≤ 5000，我们不需要精确的最大流量或复杂的调度。 我们只需要知道是否可以达到足够的伤害，并且我们可以贪婪地优化配对，因为如果 p1 + p2 - s 优于单个序列，则在伤害密度方面，双发严格主导在不同时间进行两次单发，但我们仍然必须尊重可用性。 

其核心思想是最优调度在时间上是单调的，并且可以在 check(T) 内进行贪婪模拟，外部结构是 T 上的二分搜索。 

这产生：

 | 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 随着时间的推移事件模拟| O(T)| O(1) | O(1) | 太慢了|
 | DP 超过冷却状态 | 无限/不切实际| O(T1·T2) | 太慢了|
 | 二分查找+贪心可行性检查| O(log T · (p1 + p2)) | O(log T · (p1 + p2)) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们定义一个函数 check(T) 来确定在时间 T 内可以造成多少伤害。 

1. 使用整数除法计算每个激光器在时间 T 内可以单独发射多少次。 激光 i 可以发射地板(T / t_i) 次。 如果我们不将它们配对，这将给出每种武器的可用单发事件总数。 
2. 通过计算两个激光器准备就绪的时间 t 来确定存在多少个同时发射时刻，该时间对应于 Floor(T / lcm(t1, t2))。 这些代表了被迫的或可能的双重机会。 
3. 首先使用双发，因为它们在每次事件中产生最高的即时伤害。 每次双发都会造成 (p1 + p2 - s) 伤害并消耗两个激光器的一次可用性。 
4. 分配双发后，从两个激光器的单独计数中减去它们的使用情况，因为这些实例不能作为单发重复使用。 
5. 独立使用剩余的单次计数，分别贡献 (p1 - s) 和 (p2 - s)。 
6. 将所有伤害相加并返回是否至少为 h。 

一旦定义了 check(T)，我们就在足够大的范围内二分搜索最小 T，以覆盖最坏情况的完全顺序触发。 

### 为什么它有效

 任何有效的射击时间表都可以重新安排，以便所有双发射击都在其自然对齐时间发生，而不会损害可行性，因为延迟或交换独立的单发射击不会减少可实现的损害。 由于伤害是累加性的，并且除了共享时间限制之外，事件是独立的，因此最佳策略完全取决于我们使用的双对齐数量和剩余的单次射击数量。 这将连续调度问题减少为对时间范围内的事件进行计数，并且贪婪分配保留了最优性，因为每次双发射严格消耗每个激光器的一个潜在发射槽。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def gcd(a, b):
    while b:
        a, b = b, a % b
    return a

def lcm(a, b):
    return a // gcd(a, b) * b

def check(T, p1, t1, p2, t2, h, s):
    l = lcm(t1, t2)

    c1 = T // t1
    c2 = T // t2
    c12 = T // l

    # double shots
    use_double = c12
    damage = use_double * (p1 + p2 - s)

    c1 -= use_double
    c2 -= use_double

    damage += c1 * (p1 - s)
    damage += c2 * (p2 - s)

    return damage >= h

def solve():
    p1, t1 = map(int, input().split())
    p2, t2 = map(int, input().split())
    h, s = map(int, input().split())

    lo, hi = 0, 10**18

    while lo < hi:
        mid = (lo + hi) // 2
        if check(mid, p1, t1, p2, t2, h, s):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```该代码首先定义了固定时间的可行性检查。 它计算每台激光器可以执行多少次发射，以及使用冷却时间的 LCM 自然对齐同时发射的次数。 这些对齐的射击首先被视为双重攻击，因为它们可以最大化每个事件的组合输出。 从每台激光器的配额中删除这些配对使用后，剩余容量将转换为单次使用。 累积总损坏并与所需的耐久度进行比较。 

外部二分搜索依赖于单调性来探索时间：如果给定时间允许破坏，则任何更大的时间也允许破坏。 

一个微妙的实现细节是安全地处理大的时间范围。 由于 t_i 可以高达 10^12，因此 LCM 可以超过 10^18，但 Python 可以安全地处理大整数，并且除法行为仍然正确。

 ## 边缘情况

 一种边缘情况是两个激光器具有相同的冷却时间。 在这种情况下，每个射击机会都是双射击，并且该算法简化为相同组合攻击的单个序列。 LCM等于冷却时间，所以每次射击时间都算一次双倍，不存在单发余数。 

当一个激光器速度慢得多时，就会出现另一种边缘情况。 例如，t1 = 1，t2 = 10^12。 这里，在任何合理的时间窗口内，两次射击最多发生一次。 该算法可以正确处理此问题，因为 c12 变为零或极小，因此几乎所有损坏都仅来自快速激光。 

最后的边缘情况是当 p1 + p2 - s 不明显大于个人贡献时。 即便如此，双发仍然可以正确计算，但它们不会人为地夸大解决方案，因为可行性检查仅累积实际损害而不是假设占主导地位。
