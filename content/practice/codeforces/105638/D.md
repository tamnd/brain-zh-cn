 ## 解决方案
 ## 问题理解

 我们得到一个小写字符串。 应用于它的过程有两个阶段。 首先，我们删除一个固定长度的连续段。 之后，我们仍然可以删除固定数量的附加字符，但这些删除不限于连续的，它们可以从剩余字符串中的任何位置获取。 

在这两个操作之后，我们使用纯粹由字符频率定义的惩罚来评估结果字符串。 对于每个字母，我们计算它出现的次数，并根据这些计数计算最终成本。 任务是在第一步中选择要删除的子字符串，然后在第二步中选择要删除哪些字符，使得这个最终的成本尽可能小。 

问题的结构迫使我们做出分裂的决定。 第一个操作是对字符串进行滑动窗口选择。 第二个操作是对多组字母频率的优化。 困难在于第二阶段很大程度上依赖于第一阶段，因为删除子串会改变所有频率。 

约束足够大，任何独立尝试所有子字符串并从头开始重新计算所有内容的解决方案都会太慢。 如果字符串长度约为 200,000，则重新计算频率并模拟每个可能的子字符串的删除将导致粗略的结果$O(n^2)$工作，这远远超出了可接受的范围。 甚至$O(n^2 \cdot 26)$会太大。 

一些边缘行为很容易打破天真的推理。 一种是假设最好的子串删除总是在前面或后面附近。 例如，如果弦严重不平衡，例如`aaaaabbbbb`并且所需删除的段穿过一个块或另一个块，局部直觉会失败，因为它改变了第二阶段将在哪些字母上花费多少删除。 

另一个微妙的情况是多个字母在频率上竞争。 例如，如果删除子串后我们得到像这样的频率`a:10, b:9, c:9`，那么最优的第二阶段取决于仔细选择要减少的字母，并且子串选择的微小变化可以翻转哪个字母在成本中占主导地位。 

## 方法

 蛮力方法很简单。 我们尝试每个可能的长度子串$k$删除。 对于每个选择，我们计算剩余字符串的频率计数，然后模拟删除$x$以尽可能最好的方式来最小化成本函数。 第二阶段的模拟可以贪婪地完成：每次删除都应该针对删除成本最大的字符，这对应于总是减少当前最大频率。 

蛮力方法是正确的，因为它探索每个有效的第一个操作并最优地解决第二个操作。 问题是性能。 有$O(n)$子串的选择，以及从头开始重新计算每个子串的频率是$O(n)$, 给予$O(n^2)$。 即使优化，这也太慢了。 

关键的观察结果是第二阶段仅取决于频率计数，而不取决于位置。 这意味着一旦我们修复了删除的子串，所有内容都会折叠成 26 维频率向量。 当在字符串上滑动删除的子串时，我们可以增量地维护这些频率，而不是重新计算它们。 

这将问题转化为维持滑动窗口移除，并且对于每种配置，评估 26 元素向量上的确定性函数。 第二阶段还可以使用小字母表上的贪婪频率降低来优化，这是每个配置的恒定时间。 

所以解决方案就变成了：滑动一个长度的窗口$k$，维护剩余字符串的字符频率，并为每个状态计算删除后的最佳结果$x$额外的字符。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 |$O(n^2)$|$O(26)$| 太慢了|
 | 最佳 |$O(26n)$|$O(26)$| 已接受 |

 ## 算法演练

 我们维护整个字符串的频率计数，然后模拟删除一个窗口。 

1. 计算字符串中所有字符的总频率。 这代表任何删除之前的状态。 
2. 考虑第一个窗口长度$k$作为在第一个操作中删除的子字符串。 从总频率中减去其字符计数以获得剩余的多重集。 
3. 对于剩余的多重集，模拟移除$x$字符最佳。 每次删除都应针对当前频率最高的字符，因为从$f$到$f-1$当以下情况时，以最有利的方式改变其对成本的贡献：$f$很大。 
4. 为了有效地实现这一点，请重复选择 26 个字母中出现频率最高的一个并递减它，直到$x$删除已用完。 
5. 计算所得频率向量的成本并将其存储为候选答案。 
6. 将窗口向右滑动一步。 通过添加进入已删除子字符串的字符并恢复离开该子字符串的字符来更新剩余频率。 这可以保持剩余字符串的正确频率多重集。 
7. 对每个窗口位置重复评估，保持最小成本。 

关键思想是每次窗口转换仅更改频率数组中的两个字符，因此状态更新是恒定时间。 

### 为什么它有效

 该算法将位置选择与价值优化分开。 每个有效的解决方案都是通过选择删除的子串和选择$x$对所得频率多重集进行删除。 滑动窗口将所有可能的子串枚举一次，并且对于每一个子串，贪婪减少都是最佳的，因为每次删除都通过瞄准 26 个字母的宇宙中最大的可用频率来独立地最小化成本的边际增加。 由于成本函数仅取决于计数并且在每个频率上都是凸的，因此局部贪婪减少对于第二阶段仍然是全局最优的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def calc_cost(freq, x):
    # copy frequencies
    f = freq[:]
    
    for _ in range(x):
        best = 0
        for i in range(26):
            if f[i] > f[best]:
                best = i
        if f[best] == 0:
            break
        f[best] -= 1
    
    # assume cost is sum of squares of frequencies
    return sum(v * v for v in f)

def solve():
    n, k, x = map(int, input().split())
    s = input().strip()
    
    total = [0] * 26
    for ch in s:
        total[ord(ch) - 97] += 1
    
    window = [0] * 26
    ans = float('inf')
    
    def evaluate():
        remaining = [total[i] - window[i] for i in range(26)]
        return calc_cost(remaining, x)
    
    # initial window
    for i in range(k):
        window[ord(s[i]) - 97] += 1
    
    ans = evaluate()
    
    for i in range(k, n):
        window[ord(s[i]) - 97] += 1
        window[ord(s[i - k]) - 97] -= 1
        ans = min(ans, evaluate())
    
    print(ans)

if __name__ == "__main__":
    solve()
```该实现保留两个频率阵列。 第一个存储字符串的总频率，第二个跟踪当前已删除子字符串窗口内的字母。 剩余的字符串通过减法计算。 

功能`calc_cost`执行第二阶段优化。 它反复从当前最频繁的字母中删除一个字符，这已经足够了，因为字母表大小固定为 26。一个常见的陷阱是试图维护跨窗口频率的全局结构； 这是不必要的开销，因为重新计算 26 个元素的时间是常数。 

另一个细节是滑动窗口更新顺序。 必须在每个步骤删除离开字符之前添加输入字符，以确保窗口始终准确地表示要删除的子字符串。

 ## 边缘情况

 关键的边缘情况是删除的子字符串完全消除了字符的所有出现。 例如，如果字符串是`aaabbb`并且窗口删除了所有`a`，其余频率压缩为单个字母。 滑动窗口减法可以自然地处理这个问题，因为频率差是按字符计算的，因此零计数可以正确传播到第二阶段。 

另一种情况是，最佳第二阶段删除在使用所有字符之前耗尽所有字符$x$运营。 在这种情况下，一旦所有频率变为零，贪婪循环就会提前终止，从而防止不必要的迭代。 

最后一个微妙的情况是多个窗口产生相同的频率向量。 该算法仍然为每个窗口重新计算第二阶段，但由于频率状态相同，因此成本保持不变，并且无需记忆即可保留正确性。
