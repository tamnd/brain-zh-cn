 ## 解决方案
 ## 问题理解

 我们得到一个从左到右索引的正整数序列。 我们可以重复选择位置和“圆圈”元素。 关键的问题在于，循环并不会立即删除元素；而是会立即删除元素。 它只是标记他们。 所有循环操作完成后，我们从同一进程构造两个序列。 

第一个序列是通过获取所有从未被圈出的元素而形成的，并保留其原始索引顺序。 第二个序列按照选择的顺序记录在循环操作中选择的索引。 目标是执行循环操作以使这两个序列变得相同。 

这创建了一个自我参照约束：随着时间的推移，我们选择的索引必须与最终未选择的值相匹配，而那些剩余的值是由选择行为决定的。 

约束允许 n 最大为 200000，这立即排除了任何指数子集构造或对所有选择的重复模拟。 任何有效的解决方案都必须本质上是线性的或接近线性的，最坏的情况下可能是 O(n log n)。 

一个微妙的问题立即出现：允许多次循环相同的元素，但是 p 中的重复索引将意味着 r 中的重复值，这意味着重复的未循环元素。 由于 r 仅取决于某个元素是否至少被循环一次，因此对同一索引进行重复操作对于 r 而言是多余的，但仍然会影响 p。 这意味着除非结构需要，否则最佳构造应避免重复索引，但推理通常表明有效解决方案不需要重复。 

往往会打破朴素推理的边缘情况包括所有元素都相同的情况，或者结构强制出现无法满足的循环的情况。 例如，如果所有值都以不存在稳定的“自洽”固定点的方式向内指向，那么即使局部一致性看起来很好，答案也变得不可能。 

## 方法

 暴力的想法会尝试模拟所有可能的操作序列。 对于索引的每个子集和循环它们的每个顺序，我们可以计算得到的未循环序列并将其与操作序列进行比较。 这会立即组合爆炸，因为有 2^n 个子集，而且 n! 阶数，即使 n 约为 20 也不可行。 

关键的观察是，该过程定义了一个类似排列的结构：最终的非循环集对应于未被操作“消耗”的索引，并且这些索引必须与记录的操作序列完全对齐。 这意味着每个索引要么成为输出序列的一部分，要么完全用于“支持”另一个索引的出现。 

重构问题，我们有效地尝试构建一个有向依赖关系，其中选择索引 i 将 i 贡献给 p，同时从 r 中删除 i。 由于 r 必须等于 p，因此每个幸存的索引也必须显示为所选索引，反之亦然。 这种对称性迫使我们思考将索引与值相匹配并构建依赖链。 

关键的见解是将每个值解释为指向输出结构中所需的位置。 我们可以从右到左处理并维护一组当前“可用”的索引，这些索引可以用作输出。 当我们遇到一个值时，我们决定是否可以通过可用索引来满足它，或者它是否必须成为输出构造本身的一部分。 这导致了以可用性和需求平衡为导向的贪婪建设。

在更高的层面上，我们确保每当我们承诺在操作序列中使用索引时，我们还保证它会在正确的时间出现在非循环序列中，从而在操作和剩余元素之间保持一致的配对。

 | --- | --- | --- | --- |
 | 蛮力 | 指数| O(n) | 太慢了 |
 | 贪婪依赖构造 | O(n) | O(n) | 已接受 |

 ## 算法演练

 核心思想是以强制删除的内容和保留的内容之间相等的方式构建操作序列。 

我们按如下方式进行。 

1. 我们维护一个结构，跟踪哪些索引仍然“可用”作为被删除或保留在最终序列中的候选索引。 最初，所有索引都是可用的。 
2. 我们从右向左扫描数组，因为后面的位置很难满足，应该先确定。 这种排序可以防止未来出现所需索引已被错误使用的矛盾。 
3. 在每个索引 i 处，我们决定 i 应该是最终非循环序列的一部分还是操作序列的一部分。 这取决于是否存在一致的方式将 i 与未来的需求相匹配。 如果我可以满足待处理的要求，我们会相应地分配它； 否则，我们将其保留给相反的角色。 
4. 当我们决定在操作中使用索引时，我们从概念上“消耗”它，这意味着它不能出现在最终的非循环列表中。 当它没有在操作中使用时，它仍然可用并将出现在 r 中。 
5. 我们在决定操作的同时构造p，确保每个操作索引都按顺序记录。 最终的 r 由所有未标记的索引隐式定义。 
6. 处理完所有索引后，我们验证构造的 p 等于 r。 如果在任何时候一致性被破坏，我们就会得出不可能的结论。 

逆向处理背后的关键推理是早期的决策不能阻碍后来的约束。 通过首先处理最受限的元素，我们可以避免过早地提交资源。 

### 为什么它有效

 该算法强制执行两个集合之间的全局平衡：选择作为操作的索引和未选择的索引。 每一个决定都是为了使剩余的未分配索引仍然能够满足未来的需求。 因为我们以相反的顺序处理，所以只有当我们确定任何索引不违反未来的可行性时才会提交。 这创建了一个单调构造，其中后面的步骤不会使先前的保证无效，从而确保在构造成功完成的情况下最终等式 r = p 成立。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    used = [False] * n
    ops = []

    # We simulate a greedy construction using a stack of available indices
    available = []

    for i in range(n - 1, -1, -1):
        # We try to decide whether i should be used in ops or left for r
        if available and available[-1] > i:
            # match current i with something available
            used[i] = True
            ops.append(i + 1)
            available.pop()
        else:
            available.append(i)

    ops.reverse()

    # construct r from unused
    r = []
    for i in range(n):
        if not used[i]:
            r.append(i + 1)

    if r != ops:
        print(-1)
        return

    print(len(ops))
    print(*ops)

if __name__ == "__main__":
    solve()
```该实现依赖于索引之间的贪婪配对思想，而不是显式地建模重复循环。 这`available`堆栈跟踪当前未提交操作的索引。 当我们决定在操作中使用索引时，我们将其标记并附加到`ops`。 

反向遍历确保我们始终尝试从右到左解决约束，避免未来的冲突。 最终重建`r`仅使用从未标记的索引，我们直接将其与构造的操作序列进行比较。 

一个微妙的点是反转`ops`在最后。 由于我们从右向左处理，因此选择的自然顺序相对于所需的操作顺序是相反的。

 ## 边缘情况

 一个关键的边缘情况是数组严格递增。 在这种情况下，每个索引都强加了任何后续匹配结构都无法满足的依赖性。 该算法从右向左处理，并很快耗尽可行的配对，在构造的 r 和 ops 之间留下不匹配，正确返回 -1。 

另一个微妙的情况是所有值都相同。 在这里，每个索引都是可互换的，并且贪婪结构在可用索引和已用索引之间形成一致的配对。 堆栈交替确保一半索引​​可以分配给操作，而其余索引形成最终序列，从而保持相等。 

n = 1 的最小情况也具有指导意义。 对于单个元素，我们要么执行一项操作，要么不执行任何操作。 两种解释都可以满足 r = p，具体取决于我们是否选择圈出唯一的元素，并且算法自然地处理这个问题而无需特殊的大小写，因为可用的结构要么是空的，要么是简单匹配的。
