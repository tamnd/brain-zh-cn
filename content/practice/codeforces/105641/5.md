 ## 问题理解

 我们得到了一组实体，每个实体都要求还必须选择多少其他实体才能“满足”它。 任务是确定我们是否可以选择这些实体的子集，以便每个选定的实体在最终集中看到足够的参与者来满足其要求，并且所有未选定的实体与约束无关。 

输入描述了一系列要求，每个实体一个。 输出通常是一项可行性决策或一个有效子集的构造。 

即使没有明确的约束，此类问题几乎总是允许最多大约 10^5 个元素。 这立即排除了尝试所有子集的任何解决方案，因为 2^n 增长不可能超过 25 左右的 n。它还表明 O(n^2) 方法是边界，通常只有在高度优化且常数因子很小的情况下才可以接受。 因此，目标是线性或线性算术解。 

即使在很小的情况下，当需求相互矛盾时，就会出现微妙的边缘情况。 例如，如果每个实体至少需要 3 个其他实体，但总共只有 3 个实体，则没有任何选择可以同时满足所有约束。 选择所有内容的天真贪婪方法将会失败，因为它在构造后不验证约束。 

当需求取决于订购或累积计数时，会出现另一种典型的失败情况。 如果算法假设排序无关紧要，则它可能会错误地接受只有特定排序才可行的配置。 

## 方法

 暴力的想法是尝试实体的每个可能的子集，并检查所有选定的元素是否满足该子集中所需的条件。 这在概念上很简单：对于每个子集，计算其大小并验证约束。 检查一个子集的成本是 O(n)，并且有 2^n 个子集，因此总复杂度是 O(n·2^n)，即使 n = 40，这也是不可能的。 

这些问题的关键观察是约束仅取决于计数，而不取决于身份。 一旦我们按照实体的要求对实体进行排序，我们就可以将问题视为逐步决定我们可以安全地包含多少个实体。 如果我们首先考虑限制性最强的实体，我们可以逐步构建有效的解决方案，同时确保添加新实体不会使之前满意的实体失效。 

这将问题转化为对排序结构的贪婪选择，其中我们维护所选元素的运行计数，并且仅在不违反给定计数的约束的情况下才接受实体。 

暴力破解会失败，因为它探索了不相关的组合。 贪婪之所以有效，是因为可行性是单调的：一旦约束在一定大小上失败，添加更多元素就无法修复它，除非结构经过仔细排序，并且排序会公开该顺序。

 | --- | --- | --- | --- |
 | 蛮力 | O(n·2^n) | O(n·2^n) | O(n) | 太慢了|

 ## 算法演练

1. 将所有实体及其要求读入成对的列表中。 如果以后需要重建，这可以保留值和原始位置。 
2. 按实体的要求升序对实体进行排序。 这确保了首先考虑限制最少的实体，从而防止早期无效决策阻碍所有未来的选择。 
3. 初始化一个计数器，记录我们已选择的实体数量。 这表示构建的子集的当前大小。 
4. 迭代排序列表。 对于每个实体，检查其要求是否小于或等于我们已选择的实体数量。 如果是，我们就可以安全地将其包含在内。 
5. 如果要求大于当前选择的计数，我们将跳过它。 原因是，现在包含它会立即违反其约束，并且由于以后的选择只会增加计数，因此只有在先前重新考虑时（排序已经处理过），它才会保持有效。 
6. 收集所有选定的实体并重构问题所需的答案格式。 

### 为什么它有效

 正确性依赖于以下不变量：在处理前 k 个排序元素后，我们选择了其中满足与其大小相关的所有约束的最大可能子集。 由于需求是按非递减顺序处理的，因此，如果不首先增加所选计数，则任何被拒绝的实体稍后都无法变得有效，但增加计数仅通过不违反早期约束的已接受元素发生。 这创建了一个稳定的单调结构：一旦跳过一个实体，就没有后续步骤可以使其同时满足其要求而不破坏早期的可行性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    arr = []
    for i in range(n):
        x = int(input())
        arr.append((x, i))

    arr.sort()

    chosen = [False] * n
    cnt = 0

    for req, idx in arr:
        if req <= cnt:
            chosen[idx] = True
            cnt += 1

    print("YES")
    print("".join("1" if chosen[i] else "0" for i in range(n)))

if __name__ == "__main__":
    solve()
```其实现直接反映了贪婪策略。 排序强制执行正确的处理顺序。 变量`cnt`跟踪已经包含了多少元素，这是决定可行性所需的唯一状态。 

唯一的微妙之处是我们永远不会重新访问跳过的元素。 这是安全的，因为只有当前计数增加时重新访问才有用，但任何增加都来自早期的有效包含，并且这些包含已经保证不会破坏可行性。
