 ## 解决方案
 ## 问题理解

 我们有三个一起旅行的人，每个人在旅行期间支付一系列账单。 每个测试用例提供三个正量列表，每人一个列表。 目标是确定如何在每对人之间转移资金，以便在所有转移之后，所有三个人最终贡献的总金额完全相同。 

输入被构造为多个测试用例。 对于每种情况，我们读取三个浮点值数组。 每个数组的总和就是该人支付的总金额。 我们真正关心的不是单项账单，而是三笔总金额。 

输出必须描述六次定向转移，每个定向转移对应三个人中的每一对有序转移。 我们必须输出 OC 发送给 KP、OC 发送给 XW、KP 发送给 OC、KP 发送给 XW、XW 发送给 OC、XW 发送给 KP 的数量。 这些传输的数量不需要是最小的或最优的。 任何达到相同最终余额的有效再分配都是可以接受的。 转账金额绝不能为负数，这意味着我们仅明确指定沿指定方向流动的资金； 如果不应该发送任何内容，我们输出零。 

每个测试用例最多 1000 个以及最多 100 个测试用例的约束 n、m、p 很小。 主要工作是读取浮点数并求和，因此每个测试用例解决方案的 O(n + m + p) 就足够了。 

主要的微妙之处是浮点精度。 由于值最多有两位小数，并且允许的绝对误差为 1e-2，因此我们必须小心避免以改变余额符号或产生应为零的轻微负转移值的方式累积舍入误差。 

当总数在浮动精度内已经相等或几乎相等、一个人不支付任何费用或一个人支付几乎所有费用时，就会出现边缘情况。 

例如，如果 OC、KP、XW 总计都相同，则每次传输必须为零。 尝试使用任意舍入“成对分割”的简单解决方案可能会引入微小的非零传输（例如 0.01），从而破坏正确性。 

另一种边缘情况是一个人支付了 0，而其他人支付了全部。 那么这个人必须从其他人那里得到钱。 如果浮动错误将计算出的赤字稍微推向负值，那么幼稚的实现可能会错误地输出负转移或不正确的方向。 

## 方法

 一种直接但误导性的方法是从成对调节的角度进行思考：对于每一对人，计算他们之间谁支付的费用更多，并尝试直接解决差异。 这很快就会变得不一致，因为它忽略了所有三个必须达到相同目标总数的全局约束。 成对平衡并不能保证传递性，并且可能在所有传输后留下残余不平衡。 

正确的观点是把问题分成两个阶段。 首先计算每个人的所有付款总额。 由此我们得出目标均等份额，即总数除以三。 然后我们计算每个人相对于该目标的净余额。 余额为正意味着该人应该收到钱； 负余额意味着他们应该付款。 

一旦我们有了这三个净值，问题就变成了三个节点之间盈余到赤字的简单重新分配。 由于我们被允许任意转账并且不需要最小化操作，因此我们可以以固定的确定性模式传送资金，例如将所有盈余从 OC 首先发送到 KP，然后发送到 XW，对于其他人也是如此。 任何尊重净余额的解释都是有效的。 

关键的见解是，该结构从许多单独的账单崩溃为只有三个数字，并且从潜在复杂的结算图崩溃为具有三个节点和固定总供给和需求的流量问题。

 ## 算法演练

 我们根据测试用例进行工作。 

1. 独立计算每个人支付的总金额。 我们将 OC 列表、KP 列表和 XW 列表中的所有值相加。 这将输入从三个数组减少到三个标量。 
2. 将三项总和相加，计算出总和。 这代表系统中花费的全部资金。 
3. 将目标份额计算为总计除以 3。这是每个人应有效支付的金额。 
4. 对于每个人，计算他们的净余额为已支付减去目标。 正值意味着他们多付了钱并且必须收到钱。 负值意味着他们支付不足并且必须汇款。 
5. 现在构建对之间的传输。 我们维护一个简单的贪婪重新分配：对于每一对（A，B），我们根据 A 和 B 的净余额比较来分配转移。 如果A有过剩而B有赤字，则A→B是金额min（过剩，-赤字）。 我们相应地减少了他们剩余的不平衡。 我们以固定的配对顺序重复此操作，以便消除所有不平衡。 
6. 按要求的顺序输出六个定向传输。 

这样做的原因是总超额等于总赤字，因此每一单位的盈余必须与一个单位的赤字相匹配。 由于只有三个节点，因此盈余和赤字对之间的任何贪婪匹配就足够了。 

### 为什么它有效

 在任何时候，不变的是所有人的剩余净余额之和为零。 每次转账都会减少相同金额的一个正余额和一个负余额，从而保持这一不变性。 因为我们总是只转移到可用的盈余或赤字，所以我们永远不会过度转移。 最终所有余额都归零，这意味着每个人都达到了目标份额。 传输的顺序并不重要，因为我们不受最小化交易数量的限制，而只受实现可行性的限制。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m, p = map(int, input().split())

        a = list(map(float, input().split())) if n else []
        b = list(map(float, input().split())) if m else []
        c = list(map(float, input().split())) if p else []

        sa = sum(a)
        sb = sum(b)
        sc = sum(c)

        total = sa + sb + sc
        target = total / 3.0

        bal = [sa - target, sb - target, sc - target]

        # balances: positive = should receive, negative = should pay
        # we will build transfer matrix trans[i][j]
        trans = [[0.0] * 3 for _ in range(3)]

        # greedy settlement among 3 people
        for i in range(3):
            for j in range(3):
                if bal[i] > 1e-12 and bal[j] < -1e-12:
                    x = min(bal[i], -bal[j])
                    trans[j][i] += x
                    bal[i] -= x
                    bal[j] += x

        print(f"{trans[0][1]:.2f} {trans[0][2]:.2f} {trans[1][0]:.2f} {trans[1][2]:.2f} {trans[2][0]:.2f} {trans[2][1]:.2f}")

if __name__ == "__main__":
    solve()
```该解决方案首先对每个人的付款求和，将整个输入压缩为三个值。 计算出全局目标后，每个人对公平的偏差被存储在`bal`。 正项代表该人应该收到的钱，负项代表他们应该发送的钱。 

传递矩阵`trans[i][j]`存储从 i 流向 j 的资金。 嵌套循环贪婪地将任何可用的盈余与任何赤字相匹配。 epsilon 阈值避免了零附近浮点噪声造成的不稳定。 

最后，输出按照指定的确切顺序打印六个所需的有向边。 

## 工作示例

 考虑一个简单的情况，OC 支付了 100，KP 支付了 50，XW 支付了 50。 

总计为 200，因此目标为 66.6667。 OC 有+33.3333，KP 和XW 各有-16.6667。 

| 步骤| 超频平衡 | KP余额| XW平衡| 转让|
 | --- | --- | --- | --- | --- |
 | 开始| +33.33 | -16.67 | -16.67 -16.67 | -16.67 无 |
 | OC → KP | +16.66 | 0 | -16.67 | -16.67 16.67 | 16.67
 | OC → XW | 0 | 0 | 0 | 16.66 | 16.66

 这表明 OC 将其盈余分配给其他双方，直到所有余额为零。 

现在考虑完全平衡的情况：OC = 30，KP = 30，XW = 30。 

| 步骤| 超频平衡 | KP余额| XW平衡| 转让|
 | --- | --- | --- | --- | --- |
 | 开始| 0 | 0 | 0 | 无 |

 不创建任何传输，并且输出全为零。 这证实了当不存在不平衡时，该算法不会引入人为运动。

 ## 边缘情况

 当三个人支付的总额完全相同时，计算出的目标等于每个人的总金额。 余额数组变为全零，因此贪婪循环永远不会触发任何转账。 输出是六个零，符合要求。 

当一个人支付所有费用时，例如OC支付100，其他人支付0，则目标变为33.33。 OC 的余额为正，其他余额为负。 贪婪匹配首先发送 OC → KP，然后发送 OC → XW，直到两个赤字都被填满。 不会出现负转移，因为我们总是通过剩余余额进行钳制。 

当浮动值引入微小的舍入误差时，例如余额变为 1e-15 而不是 0，epsilon 检查可防止意外转移。 如果没有这个保护，算法可能会尝试移动极小的值并产生不稳定的输出。
