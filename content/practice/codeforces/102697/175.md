 ## 解决方案
 ## 问题理解

 我们有一个目标卡路里数`n`和`k`可用的食品。 食品项目`i`准确贡献`c[i]`卡路里，并且每种食物都可以食用任意多次。 任务是准确地达到`n`卡路里，同时尽量减少食用的食物数量。 

输入包含`n`， 其次是`k`，然后是每种食物的卡路里值。 输出是卡路里值加起来正好等于的最小项目数`n`。 官方问题使用一秒限制和 256 MB 内存。 

关键的困难在于食物的价值是任意的。 更简单的版本具有 500、100 和 50 的固定值，其中尽可能多地获取大型项目。 在更难的版本中，贪婪的属性消失了。 例如，目标为 600，食物价值为 500、300 和 1，首先取出最大可能的食物会得到 500，然后需要用 100 份一卡路里食物来填充剩余的 100 卡路里。 最佳答案是两件 300 卡路里的食物，所以答案是 2。 

Codeforces 上的声明并未公开数值上限`n`或者`k`，所以诚实的复杂性讨论必须使用自然参数`n`和`k`。 预期的方法是标准的无界最小硬币动态规划解决方案，其运行时间为`O(nk)`。 当目标对于大小的一维数组来说足够小时，这是实用的`n + 1`，这就是该问题旨在解决的设置。 例如，第三个样品仅需要 10,000 卡路里热量，并且具有三种食物值。 

在某些情况下，实施可能会悄无声息地出错。 考虑贪婪的反例```

3

```正确的输出是```

```因为`300 + 300 = 600`。 贪婪的实现总是首先选择最大的食物，选择 500 个，然后需要 100 个一卡路里食物的副本，产生 101 个项目。 

第二个边缘情况是最佳答案使用的食物不是最大的。 为了```

```答案是`2`， 使用`6 + 4`。 仅基于最大面额的策略可能会从 6 开始，然后对其余部分做出糟糕的选择，而 DP 会考虑所有可能的最后一项。 

第三个问题是精确匹配边界。 为了```

2

```答案是`2`， 不是`3`， 因为`6 + 6`直接达到目标。 仅考虑食物值严格小于当前剩余值的实现可能会错过此转变。 

最后，允许重复使用食品。 为了```

```答案是`3`， 使用`3 + 3 + 3`。 将每种食物视为最多可用一次会错误地得出 9 无法组成的结论。 

## 方法

 直接暴力法是尝试所有可能的食物集合，并保留总数恰好为的最小数量。`n`。 实现此目的的一种方法是递归搜索：在每个状态，选择其中之一`k`食物类型并继续，直到累积的卡路里达到或超过目标。 这是正确的，因为每种可能的选择顺序都经过探索，因此不会错过最佳组合。 

问题是这个搜索重复探索相同的子问题。 如果最小的食物只有一卡路里，解决方案可能需要多达`n`选择。 有序递归搜索可以有多达`k^n`最坏情况下的选择顺序。 即使枚举的是组合而不是排序，可能性的数量也会以多项式方式增长，其程度取决于`k`，这很快就变得不可行。 

蛮力之所以有效，是因为每个解决方案都可以表示为一系列食物选择，但它会失败，因为可以通过许多不同的前缀来达到相同的剩余卡路里量。 假设两组不同的食物已经产生了 300 卡路里的热量。 从那时起，再获取 500 卡路里的最佳方式就完全与这 300 卡路里的获取方式无关了。 我们应该一次性解决剩下的问题并重复使用它的答案。 

这一观察直接导致了动态规划。 让`dp[x]`是准确制作所需的最少食品数量`x`卡路里。 对于每一个可达到的金额`x`，添加食物`c`产生卡路里`x + c`，最终的解决方案又使用了一项。 因此过渡是`dp[x] = min(dp[x], dp[x - c] + 1)`对于每一种食物的价值`c`不超过`x`。 

这是一个无界背包或最小硬币找零问题。 一种食物可以重复使用，所以经过计算`dp[x - c]`，我们可以使用相同的`c`计算时再次`dp[x]`。 由于每次转换都会从较小的卡路里总量到较大的卡路里总量，因此处理总量从 0 到`n`按依赖顺序给出所有必需的状态。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | 最坏情况下呈指数增长 | O(n) 递归深度 | 太慢了 |
 | 最佳DP | O(nk) | O(nk) | O(n) | 已接受 |

 ## 算法演练

 1. 阅读目标`n`和`k`食物热量值。 每个值代表一种可以重复使用的食物类型。 
2. 创建数组`dp`长度`n + 1`。 将每个条目设置为无穷大，除了`dp[0] = 0`。 

国家`dp[x]`意味着我们已经知道准确生产所需的最少食品数量`x`卡路里。 零卡路里需要零食品，这是基本情况。 
3. 处理卡路里总量`x`从 1 到`n`。 

每一种有效的方法`x`卡路里还有一些最后的食物。 如果最后一项有`c`卡路里，之前吃的食物必须准确贡献`x - c`卡路里。 这意味着每个最佳解决方案都由下面考虑的转换之一表示。 
4. 每种食物的价值`c`和`c <= x`， 更新```
dp[x] = min(dp[x], dp[x - c] + 1)
```我们将一项添加到最佳解决方案中`x - c`。 如果`x - c`是无法到达的，它的无穷大值可以防止该转换影响答案。 

1.所有总计处理完毕后，输出`dp[n]`。 

因为每个州只依赖于较小的卡路里总量，所以当时已经考虑了所有可能的最终食物选择`dp[n]`被计算出来。 

### 为什么它有效

 考虑一些可达到的总数的最佳解决方案`x`。 查看该解决方案中的最终食品，并使其卡路里值为`c`。 删除最后一项就剩下了`x - c`卡路里。 如果剩下的食物不是最优解`x - c`，我们可以用更好的替换它并获得解决方案`x`使用较少的项目，与最优性相矛盾。 因此每个最优解为`x`有形式`dp[x - c] + 1`对于一些可用的`c`。 该算法检查每一个这样的`c`并取最小值，所以`dp[x]`是最优的。 从正确的基本情况开始`dp[0] = 0`处理状态按递增顺序为每个建立此属性`x`， 包括`n`。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve(data=None):
    if data is None:
        data = sys.stdin.buffer.read().split()
    else:
        data = data.split()

    it = iter(data)
    n = int(next(it))
    k = int(next(it))
    calories = [int(next(it)) for _ in range(k)]

    # Food items larger than n can never appear in a valid solution.
    calories = [c for c in calories if c <= n]

    INF = n + 1
    dp = [INF] * (n + 1)
    dp[0] = 0

    for x in range(1, n + 1):
        best = INF
        for c in calories:
            if c > x:
                continue
            candidate = dp[x - c] + 1
            if candidate < best:
                best = candidate
        dp[x] = best

    return str(dp[n])

if __name__ == "__main__":
    sys.stdout.write(solve() + "\n")
```实现的第一部分读取整个输入`sys.stdin.buffer.read()`。 只有一个测试用例，因此这可以使解析器保持简单，同时避免不必要的开销。 

食物价值大于`n`被丢弃。 这样的食品不能参与精确的总和`n`因为每个卡路里值都是正值。 这种过滤对于正确性来说不是必需的，但它避免了内部循环中无用的比较。`dp[0]`初始化为零，因为什么都不吃会产生零卡路里。 所有其他状态开始于`INF`，代表无法达到的金额。 使用`n + 1`因为无穷大就足够了，因为没有解决方案可以使用超过`n`当存在一卡路里食物时的项目，以及小于或等于的任何有效解决方案`n`items 比这个哨兵小。 

外循环增加`x`从 1 到`n`。 对于每个`x`，内循环会尝试所有可以放入当前总数的食物值。 表达式`dp[x - c] + 1`完全对应于为较小的总数采取最佳解决方案并附加一种食物`c`卡路里。 

循环的顺序是经过深思熟虑的。 我们处理形成的总数，而不是处理每种食物类型，然后以可能意外施加 0/1 限制的方式迭代总数。 这里每个状态都可以使用先前计算的涉及相同食物类型的状态，因此自然支持无限重复。 

Python 整数不会溢出，因此不需要特殊的数字类型。 主要边界条件为`c <= x`; 没有它，`x - c`将变为负值并访问错误的 DP 状态。 

问题陈述没有指定无法到达的目标的输出。 因此，实现遵循预期问题的假设，即存在精确的解决方案。 如果允许无法到达的目标，则在决定如何打印它们之前，需要声明中的明确约定。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(nk) | O(nk) | 有`n`卡路里状态，每个最多检查`k`食品价值。 |
 | 空间| O(n) | DP 数组为从 0 到 的每个总计存储一个值`n`。 |

 该算法使用单个数组而不是二维表，因为总数的答案仅取决于较小的总数。 这使内存与目标卡路里计数保持线性关系，并且适用于以下情况下的一秒 256 MB 环境：`n`在预期的 DP 范围内。

## 边缘情况

 第一个不明显的情况是贪婪失败```
600
3
500
300
1
```DP 开始于`dp[0] = 0`。 当达到300时，它发现`dp[300] = 1`使用一件 300 卡路里的食物。 在 600 时，300 卡路里的转变变成`dp[300] + 1 = 2`。 500 卡路里的过渡需要`dp[100] + 1 = 101`，因为制造 100 卡路里的最佳方法是吃一百一卡路里的食物。 因此最终答案是2。 

第二种情况是完全匹配：```
12
2
6
4
```什么时候`x = 6`，过渡自`dp[0]`给出`dp[6] = 1`。 在`x = 12`，使用 6 卡路里食物可以得到`dp[6] + 1 = 2`。 4 卡路里的转变给出`dp[8] + 1 = 3`， 所以`dp[12]`变为 2. 相等条件`c <= x`这就是允许精确的 6 到 12 转换的原因。 

第三种情况展示了无限重用：```
9
2
3
5
```第一个可达的 3 的倍数是`dp[3] = 1`,`dp[6] = 2`， 和`dp[9] = 3`。 该算法被允许再次使用 3 卡路里的食物，因为`dp[9]`读取已经计算的`dp[6]`。 将食物类型视为一次性物品将失去这一解决方案。 

最终的边界情况是最小的可能目标：```
1
1
1
```这里`dp[0] = 0`，唯一的转变是`dp[1] = dp[0] + 1 = 1`。 答案正是一种食品。 这也证实了数组需要索引`n`，包含在内，并且其大小必须是`n + 1`。
