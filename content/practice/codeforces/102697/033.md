 ## 解决方案
 ## 问题理解

 该任务要求计算球队的整体罚球命中率。 有 (n) 名球员，对于每个球员，我们知道两个计数：他们罚球次数和尝试次数。 球队的百分比必须基于球队的所有罚球，因此我们首先结合球员的投篮命中率和他们的出手次数。 答案是

 [
 \frac{\text{总完成次数}}{\text{总尝试次数}}\乘以 100
 ]

 四舍五入到小数点后两位数字。 

官方问题使用 1 秒时间限制和 256 MB 内存。 输入包含 (n) 名玩家中每一位的一条记录，因此仅读取输入就需要 (\Theta(n)) 工作。 没有任何理由去做比单次遍历这些记录更昂贵的事情。 特别是，反复比较球员或枚举个人击球结果的算法会带来不必要的工作。 

正确性的关键限制是单个玩家的投掷次数不能超过其尝试的投掷次数，并且尝试的总数必须为正，因为尝试次数为零的百分比是不确定的。 Python 整数也是一个方便的选择，因为当玩家计数相加时它们不会溢出。 

有几个小案例通常会暴露不正确的实现。 假设输入是```
1
0 5
```正确的输出是`0.00`。 仅当投掷次数为正数时才计算百分比的程序可能会意外地不产生答案或除法错误。 

另一个边界情况是玩家竭尽全力：```
1
7 7
```正确的输出是`100.00`。 任何将尝试计数视为错过射击次数的实现都会出错，因为第二个值已经代表所有尝试，包括成功的尝试。 

一个更有用的聚合案例是```
2
1 2
9 10
```正确的输出是`66.67`，因为团队进行了 (1+9=10) 次尝试，共 (2+10=12) 次尝试。 平均个人百分比将得出 ((50+90)/2=70)，这不是团队的实际百分比。 尝试次数不同的球员必须根据自己的射门次数做出贡献，而不是平均。 

## 方法

 暴力解释可以将每个罚球视为一个独立的事件，并在计算百分比之前枚举所有可能的成功或错过的结果。 如果团队总共尝试 (A) 次投掷，则有 (2^A) 种可能的结果序列。 这已经是仅 20 次尝试的 (2^{20}=1,048,576) 种可能性，以及 100 次尝试的 (2^{100}) 种可能性，因此这种方法几乎立即变得不可用。 从技术上讲，它能够找到答案，但它解决的问题比输入要求我们解决的问题要困难得多。 

输入已经给出了计算百分比所需的信息。 我们不需要重建个人投篮次数，因为每个球员的投篮命中数直接影响球队的投篮命中数，而每个球员的尝试次数也直接影响球队的尝试次数。 我们可以在读取玩家的同时累加这两个量，然后在最后进行除法。 

统计计数与平均球员百分比之间的区别是中心观察结果。 例如，如果一名球员2投1中，另一名球员10投9中，那么他们个人的命中率是50%和90%，但球队的命中率是（10/12），即83.33%。 必须保留镜头总数，因此正确的聚合是总和的比率。 

这给出了具有恒定辅助存储器的单遍算法。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | (O(2^A)) | (O(A)) | 太慢了 |
 | 最佳 | (O(n)) | (O(n)) | (O(1)) | (O(1)) | 已接受 |

 ## 算法演练

 1. 读取玩家数量（n）。 我们需要这些玩家中的每一位都恰好有一对计数。 
2. 初始化`made_total`和`attempted_total`为零。 这些变量代表了迄今为止看到的完整团队总数。 
3. 对于每个玩家，请阅读`made`和`attempted`，然后将它们添加到相应的总计中。 我们对原始计数进行求和，而不是计算个人百分比，因为最终百分比必须根据每个球员尝试的投掷次数进行加权。 
4.处理完所有玩家后，计算`made_total / attempted_total * 100`。 现在分子是全队成功罚球的次数，而分母是全队尝试罚球的次数。 
5. 打印结果，精确到小数点后两位。 蟒蛇的`:.2f`格式化执行所需的小数舍入，并保留尾随零。 

### 为什么它有效

 处理完玩家的任意前缀后，`made_total`恰好等于这些球员成功罚球的次数，并且`attempted_total`正好等于他们尝试投掷的次数。 在处理任何玩家之前，这个不变量从零开始，并且保持为真，因为每个玩家的两个计数只添加一次。 在最后一名球员之后，这两个总数代表了整个球队，因此他们的比率乘以100正是球队的罚球命中率。 将该值格式化为两位小数会产生所需的输出。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    made_total = 0
    attempted_total = 0

    for _ in range(n):
        made, attempted = map(int, input().split())
        made_total += made
        attempted_total += attempted

    percentage = made_total * 100 / attempted_total
    print(f"{percentage:.2f}")

if __name__ == "__main__":
    solve()
```第一行给出了玩家记录的数量，因此循环正好运行 (n) 次。 每次迭代都会读取一名球员的已完成计数和尝试计数，并将其添加到两个运行总数中。 

除法之前将分子乘以 100 在数学上相当于将最终比率乘以 100。此处保持浮点计算是合适的，因为所需的输出是四舍五入到两位的小数。 Python 的整数类型在除法发生之前处理累积计数而不会溢出。 

最终的格式化表达式`:.2f`是重要的。 打印原始浮点值可能会产生许多小数位，而整数除法会丢失小数部分。 要求的结果必须恰好包含小数点后两位，包括以下情况`0.00`和`100.00`。 

处理后无需存储玩家。 每个记录对两个总计都有独立贡献，因此恒定的辅助内存就足够了。 

## 工作示例

 对于第一个样本，四名玩家贡献了以下计数。 

| 玩家| 制造| 尝试过| 总制作量 | 总尝试次数 |
 | --- | --- | --- | --- | --- |

 最终百分比为 (17/24\times100=70.8333\ldots)，四舍五入为`70.83`。 该迹线说明了为什么算法需要两个累积总数而不是四个单独百分比的平均值。 

第二个例子可以暴露权重问题：```
2
1 2
9 10
```| 玩家| 制造| 尝试过| 总制作量 | 总尝试次数 |

 最终计算为(10/12\times100=83.3333\ldots)，所以输出为`83.33`。 单独的百分比为 50% 和 90%，但它们的简单平均值为 70%，这表明平均百分比并不能保留正确的权重。 

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | (O(n)) | (O(n)) | 每个玩家的两个计数都会被读取并处理一次。 |
 | 空间| (O(1)) | (O(1)) | 仅存储两个累计总数和一些临时整数。 |

 该算法对输入仅执行一次传递，这是最佳的，因为每个玩家记录必须至少读取一次。 它还避免存储输入，因此无论玩家数量如何，内存使用量都保持不变。 鉴于问题的 1 秒和 256 MB 限制，这完全在预期的资源范围内。 

## 测试用例

 下面是官方样本，接下来是零成功、完美射击记录、不平等尝试次数和较大输入的案例。 该声明没有单独公布 (n) 的最大值，因此较大的案例使用 100,000 名玩家作为压力测试，而不是声称 100,000 是官方最大值。```python
import sys
import io

def solve():
    input = sys.stdin.readline

    n = int(input())
    made_total = 0
    attempted_total = 0

    for _ in range(n):
        made, attempted = map(int, input().split())
        made_total += made
        attempted_total += attempted

    print(f"{made_total * 100 / attempted_total:.2f}")

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    try:
        solve()
        return sys.stdout.getvalue()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout

# Provided sample
assert run(
    "4\n"
    "1 5\n"
    "3 4\n"
    "7 7\n"
    "6 8\n"
) == "70.83\n", "sample 1"

# Minimum-size input
assert run(
    "1\n"
    "0 1\n"
) == "0.00\n", "minimum-size input"

# Perfect percentage
assert run(
    "1\n"
    "7 7\n"
) == "100.00\n", "all attempts made"

# Unequal attempt counts, catches averaging individual percentages
assert run(
    "2\n"
    "1 2\n"
    "9 10\n"
) == "83.33\n", "weighted aggregation"

# Boundary values with many players
large_input = "100000\n" + ("1 2\n" * 100000)
assert run(large_input) == "50.00\n", "large input"
```| 测试输入| 预期产出 | 它验证了什么 |
 | --- | --- | --- |
 |`4 / 1 5 / 3 4 / 7 7 / 6 8`|`70.83`| 官方样本及正常汇总|
 |`1 / 0 1`|`0.00`| 最小尺寸输入和零投掷 |
 |`1 / 7 7`|`100.00`| 完美拍摄、尾随零格式化|
 |`2 / 1 2 / 9 10`|`83.33`| 通过尝试正确权重 |
 | 100,000 名玩家`1 2`每个 |`50.00`| 线性时间处理和大输入|

 ## 边缘情况

 零成功的情况由累积分子直接处理。 为了```
1
0 5
```该算法结束于`made_total = 0`和`attempted_total = 5`，给出 (0/5\times100=0)。 输出是`0.00`，包括所需的尾随零。 

完美百分比情况无需任何特殊分支即可工作。 为了```
1
7 7
```总数为 7 次完成和 7 次尝试，因此计算出的百分比恰好为 100。输出为`100.00`。 一个常见的错误是将尝试计数解释为未投掷的次数，这会错误地使分母为 14。 

最微妙的边缘情况是尝试次数不相等。 为了```
2
1 2
9 10
```第一个玩家在 2 次投掷中贡献了 1 次成功，而第二个则在 10 次投掷中贡献了 9 次。总数变为 10 次投出和 12 次尝试，给出`83.33`。 该算法从不计算两个单独的百分比，因此它不会意外地对它们进行平均。 

最后，当有很多玩家在场时，算法只保留两个累积值。 100,000 份`1 2`，总数为 100,000 次，200,000 次尝试，准确给出`50.00`。 运行时间随着玩家数量线性增长，而内存使用量保持不变，因此实现会随着输入的大小而不是可能的射击结果的数量而扩展。
