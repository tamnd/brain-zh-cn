 ## 解决方案
 ## 问题理解

 该队已经在小组赛中踢了一些比赛。 输入按照获胜、失败和平局的固定顺序给出三个计数，值之间用连字符分隔。 胜利贡献3分，平局贡献1分，失败则无贡献。 任务是根据这三项计数计算球队的总得分。 官方声明准确地指定了这种输入格式并给出`5-3-2`举个例子，他的答案是17。 

如果获胜、失败和平局的数量是`w`,`l`， 和`t`，分别，答案很简单`3w + t`。 

公式中没有出现损失的次数，因为每次损失都会贡献零分。 输入仅包含三个整数，并且只有一个测试用例，因此不需要数组、图、动态编程状态或重复处理。 时间限制为 1 秒，内存限制为 256 MB，但实际计算只需要恒定数量的解析和算术运算。 已发布的语句没有指定三个计数的显式上限，因此实现应该简单地使用 Python 整数，它会自动处理超出固定宽度机器整数限制的值。 

由于不寻常的连字符分隔输入格式，有一些小情况很容易处理不当。 例如，与```
0-0-0
```正确的输出是```
0
```假设每支球队都至少打过一场比赛的解决方案在这种自然边界情况下将失败。 公式给出`3 * 0 + 0 = 0`直接地。 

另一种情况是```
0-5-4
```正确的输出是```
4
```粗心的实施可能会将每个计数乘以三，错误地将输球和平局视为胜利。 只有获胜才能获得三分，而四场平局则额外贡献四分。 

第三个有用的边界情况是```
7-0-0
```产生```
21
```这里没有需要单独添加的关系，因此答案完全来自胜利。 无论其价值如何，损失计数都无关紧要。 

## 方法

 最直接的做法就是逐场模拟战绩。 我们可以读取这三个计数，每赢一场加 3 分，每平一场加 1 分，每输一场不加分。 这是正确的，因为它严格遵循评分规则。 如果球队有`w`获胜，`l`损失，以及`t`关系，该模拟执行`w + l + t`迭代，虽然`l`损失迭代不进行有用的算术。 

该方法的弱点并不在于普通输入可能会超时，因为输入本身仅包含三个数字并且没有给出明确的大界限。 其成本根本是不必要的。 如果总匹配数为`m = w + l + t`，模拟需要`O(m)`时间并准确执行`m`迭代。 对于包含十亿个匹配项的记录，这意味着十亿次循环迭代，即使可以立即从三个计数中获得答案。 

关键的观察结果是，相同结果的比赛都贡献相同数量的分数。 我们永远不需要知道胜利、失败和平局发生的顺序。 我们只需要他们的计数。 所有胜利都可以合并为`3w`点，所有损失`0l`，以及所有关系到`t`点。 这将整个计算简化为一个常数时间表达式。 

暴力方法之所以有效，是因为它单独考虑了每场比赛，但它未能利用每场比赛的贡献仅取决于其结果的事实。 通过观察可以聚合相同的结果，我们可以用三个算术运算来替换潜在的多次迭代。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(w + l + t) | O(w + l + t) | O(1) | O(1) | 实践中接受，但没有必要 |
 | 最佳| O(1) | O(1) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 将唯一的输入行作为字符串读取。 连字符是分隔符，因此该行不能被解析为三个普通的空格分隔的整数。 
2. 在每个连字符处拆分字符串，并将所得的三个部分转换为整数。 他们的顺序是固定的：胜第一，负第二，平第三。 
3. 将获胜次数乘以 3，因为每次获胜均可获得 3 分。 
4. 计算分数时忽略输球次数，因为每次输球都得零分。 
5. 添加平局数，因为每平局都会奖励一分。 
6. 打印`3 * wins + ties`。 

### 为什么它有效

 对于每场胜利，算法都会准确地贡献评分规则授予的三分。 对于每一个损失，它的贡献为零，这正是损失值。 每打一场平局，就贡献一分。 由于三个输入计数将球队的比赛结果分为这三个类别，因此将他们的贡献相加即可准确得出球队的小组赛总得分。 计算仅取决于计数，因此不需要有关匹配顺序的信息。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

record = input().strip()
wins, losses, ties = map(int, record.split('-'))

answer = 3 * wins + ties
print(answer)
```第一行将完整记录作为字符串读取，因为三个整数是用连字符而不是空格分隔的。 使用`strip()`删除尾随换行符而不更改有意义的内容。 

这`split('-')`call 恰好生成三个字符串，分别对应于胜利、失败和平局。`map(int, ...)`将它们转换为整数，元组解包按照问题使用的相同顺序分配它们。 

变量`losses`故意不在最终表达式中使用。 这并非遗漏。 损失贡献零分，因此将其乘以零不会产生任何效果。 保留变量可以使输入顺序明确，并使与问题评分规则的联系清晰。 

Python 整数不存在使用 32 位或 64 位整数类型的语言中存在的固定宽度溢出问题。 计算`3 * wins + ties`因此，即使计数大于典型的机器整数，也是安全的，仅受 Python 的可用内存的影响。 

## 工作示例

 对于提供的示例，输入是`5-3-2`。 三个解析值是五场胜利、三场失利和两场平局。 

| 胜利| 损失 | 联系 | 赢取积分 | 联系点| 答案|
 | --- | --- | --- | --- | --- | --- |
 | 5 | 3 | 2 | 15 | 15 2 | 17 | 17

 五场胜利贡献`5 * 3 = 15`点。 三亏贡献为零，两平贡献`2 * 1 = 2`。 最终得分为`15 + 2 = 17`，与官方样品相符。 

对于第二个例子，考虑```
0-5-4
```| 胜利| 损失 | 联系 | 赢取积分 | 联系点| 答案|
 | --- | --- | --- | --- | --- | --- |
 | 0 | 5 | 4 | 0 | 4 | 4 |

 没有胜利，因此胜利贡献为零。 五场失利也贡献了零分，而四场平局则贡献了四分。 结果是`4`。 该轨迹说明了为什么不能意外地将损失视为胜利或平局。

## 测试用例```python
import sys
import io

def solve():
    import sys
    input = sys.stdin.readline

    record = input().strip()
    wins, losses, ties = map(int, record.split('-'))
    print(3 * wins + ties)

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    try:
        solve()
        return sys.stdout.getvalue()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout

# Provided sample
assert run("5-3-2\n") == "17\n", "sample 1"

# Minimum-size / all-zero record
assert run("0-0-0\n") == "0\n", "all results absent"

# All losses

# All ties

 ## 边缘情况

 全零记录```
0-0-0
```通过将所有三个分量解析为零来处理。 答案计算变为`3 * 0 + 0`，所以程序打印`0`。 不需要特殊条件。 

仅包含损失的记录，```
0-5-0
```产生`0`。 算法读取`wins = 0`,`losses = 5`， 和`ties = 0`，然后计算`3 * 0 + 0`。 损失计数永远不会改变答案，与评分系统完全匹配。 

仅包含关系的记录，```
0-0-5
```产生`5`。 该算法计算`3 * 0 + 5`，因此每条平局都贡献一分。 

仅包含胜利的记录，```
7-0-0
```产生`21`。 计算公式为`3 * 7 + 0 = 21`，因此不依赖于至少一场平局或输球。 

最后，连字符分隔符本身就是一种实现边缘情况。 为了```
5-3-2
```呼叫`input().split()`会产生一个字符串，`"5-3-2"`，而不是三个值。 显式分割`'-'`需要恢复这三个计数。 在解析步骤之后，问题直接简化为评分公式`3 * wins + ties`。
