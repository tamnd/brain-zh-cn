 ## 解决方案
 ## 问题理解

 输入是一系列看似整数的标记，但这些标记是以 8 为基数而不是通常的 10 基数编写的。每个八进制数在转换为其十进制值后表示一个 Unicode 代码点。 所需的输出是将每个标记转换为其相应的 Unicode 字符并按原始顺序连接字符而形成的字符串。 例如，官方示例以`164 150 151`，它们是十进制值的八进制表示`116 104 105`，给出字符`t`,`h`， 和`i`。 

已发布的问题描述中没有说明数组大小或数字上限。 因此，相关的输入大小是八进制数字和标记的总数。 正确的解决方案应该处理每个令牌一次，因此其运行时间应该与输入量成线性关系。 任何尝试搜索可能的字符值或重复测试不相关编码的方法都会增加不必要的工作。 

输入也没有固定数量的行可供依赖。 数字由空格分隔，因此实现应该读取所​​有以空格分隔的标记，而不是假设每行一个字符。 一个令牌，例如`040`是另一个有用的边界情况：它的前导零是八进制表示的一部分，但它不会改变其数值，因此它表示十进制`32`，空格字符。 将令牌视为十进制的粗心实现会解释`40`四十而不是三十二，并产生错误的字符。 

另一个边缘情况是单个字符。 例如，输入`141`代表小数`97`，所以输出是`a`。 假设必须有多个数字的解决方案会不必要地引入索引或串联错误。 

这些值还可以表示普通小写和大写 ASCII 之外的字符，因为该语句描述 Unicode 值而不是将结果限制为英文字母。 因此，转换必须从结果代码点生成 Unicode 字符，而不是使用纯 ASCII 查找表。 

## 方法

 最直接的方法是手动转换每个八进制标记。 对于带有数字的令牌`d1 d2 ... dk`，其值是通过重复应用得到的`value = value * 8 + digit`。 这是正确的，因为每个新数字都会将先前处理的值移动一个以 8 为基数的位置。 如果输入的总位数是`L`，这完全执行`L`数字处理迭代，给出`O(L)`时间和`O(1)`除了输出之外的辅助空间。 

第二种天真的解释是尝试每一个可能的 Unicode 值，直到找到八进制表示与标记匹配的值。 这种方法原则上是正确的，但它在这里没有存在的有用理由。 为每个输入标记搜索潜在的大代码点范围可能需要比实际存在的位数更多的工作。 

关键的观察结果是编程语言已经准确地提供了问题所需的操作。 蟒蛇的`int(token, 8)`将字符串解释为以 8 为基数的整数，并且`chr(value)`将 Unicode 代码点转换为其字符。 问题不是要求我们发现隐藏的编码或推断模式。 它只是要求我们为每个标记独立地执行这两个确定性转换。 

暴力字符搜索会失败，因为它的工作取决于 Unicode 范围的大小而不是输入的大小。 直接转换将每个标记简化为单个基数 8 解析操作，然后进行字符转换。 由于 Python 的整数解析器处理标记的数字，因此总工作量与输入大小保持线性关系。

 | 直接八进制转换 | O(L) | 输出 | O(L) 已接受 |

 ## 算法演练

 1. 从标准输入中读取所有以空格分隔的标记。 输入使用空格作为分隔符，因此统一处理空格可以避免对行结构做出假设。 
2. 对于每个标记，将其解释为以 8 为基数的整数`int(token, 8)`。 第二个参数明确告诉 Python 必须使用八进制数字系统解释数字。 
3. 将结果整数转换为其 Unicode 字符：`chr(value)`。 该问题保证这些值代表有效的 Unicode 字符，因此每次转换都会生成一个字符。 
4. 将每个结果字符附加到列表中，并在末尾加入该列表一次。 以这种方式构建完整的字符串可以避免重复创建较大的中间字符串。 

### 为什么它有效

 对于每个输入标记，`int(token, 8)`精确计算该标记以基数 8 表示的整数。该问题将该整数定义为所需字符的 Unicode 代码点，并且`chr`精确返回与该代码点关联的字符。 由于令牌是按照其原始顺序处理的，因此生成的字符也按照所需的顺序。 因此，输出中的每个位置恰好对应于一个输入数字，并且具有正确的 Unicode 值。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    tokens = sys.stdin.read().split()
    result = []

    for token in tokens:
        value = int(token, 8)
        result.append(chr(value))

    sys.stdout.write("".join(result))

if __name__ == "__main__":
    solve()
```该解决方案读取完整的输入`sys.stdin.read().split()`。 尽管所需的模板定义了`input = sys.stdin.readline`，实际解决方案使用`read()`因为输入中没有有意义的行结构。 保持`input`定义仍然遵循所要求的竞争性编程模板。 

每个令牌都直接传递给`int`带底座`8`。 这比首先通过十进制文本进行转换更安全，因为它使预期的数字系统明确并自然地处理前导零。 

结果整数被传递到`chr`，它执行 Unicode 代码点转换。 Python 整数具有任意精度，因此在转换过程中不存在 C++ 风格的有符号整数溢出问题。 

字符存储在`result`并加入过一次。 这给出了最终输出大小的线性行为，而不是在循环内重复连接字符串。 

语句中的输入示例包含八进制值，例如`164`,`150`， 和`151`。 它们变成十进制`116`,`104`， 和`105`，分别是`t`,`h`， 和`i`。

 | ---| ---| ---|

## 边缘情况

 单个输入标记，例如`141`必须恰好产生一个字符。 该算法读取一个令牌，评估`int("141", 8)`作为`97`, 转换`97`到`a`，并加入单元素结果列表。 输出是`a`。 

包含前导零的输入，例如`040 141 040`，也自然处理。`040`是八进制 40，等于十进制 32，因此两次出现都变成空格。 完整的输出是`a`。 十进制解析器会错误地解释`040`作为十进制 40 并产生`(`。 

全部相等的值不需要任何特殊情况。 为了`141 141 141`，每个令牌独立地变为`a`, 给予`aaa`。 每次迭代后，不变量保持不变，因为每个处理过的标记都准确地贡献了一个正确的字符。 

输入可以包含小写字母以外的字符。 为了`101 132 141 172`，十进制值为`65`,`90`,`97`， 和`122`, 给予`Zaz`。 该算法不依赖于 ASCII 查找表，因此它可以处理问题描述的整个有效 Unicode 代码点范围。 

最后，决不能改变令牌的顺序。 为了`141 142 143`，正确的输出是`abc`，而不是这些字符的排序或其他转换版本。 循环完全按照提供的顺序处理令牌，因此最终的`join`保留所需的序列。
