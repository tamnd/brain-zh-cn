 ## 解决方案
 ## 问题理解

 我们正在维护多组钻石类型，其中每种类型的每件钻石都有固定的重量和价值，但其可用数量会因到货和销售而随时间变化。 在这个不断发展的集合之上，我们必须回答模拟贪婪打包过程的查询。 

类型三的查询给出背包容量。 我们想象通过按照严格的顺序重复取出钻石来填充背包：始终选择价值最高的可用钻石。 如果多颗钻石具有相同的价值，我们更喜欢较轻的一颗。 我们继续收集，直到不再有钻石适合总重量为止。 

关键的转折在于，这种贪婪的选择与总价值密度或背包优化无关。 它是按字典顺序排列的：价值第一，然后重量。 考虑到当前库存快照，该过程纯粹是确定性的，并且类型三查询不会修改状态。 

这些约束迫使我们维护一个超过二十万个类型和十万个更新或查询的动态结构。 任何针对每个查询从头开始重新计算贪婪打包的解决方案都会尝试重复迭代所有项目之类的操作，这在最坏的情况下会导致大约 10^10 次操作，并且是不可行的。 

主要困难在于贪婪过程依赖于在不断变化的库存下重复提取当前可用的最佳物品，这自然是一个数据结构问题而不是纯粹的模拟问题。 

对于简单的方法来说，一些微妙的失败案例会立即出现。 

如果我们总是重建每个查询的所有单个钻石的排序列表，则对计数的单个更新会强制完全重建。 即使我们存储聚合类型，将计数扩展到单个项目也会立即中断，因为每种类型的计数最多为 10^5。 

相反，如果我们尝试维护单个类型的优先级队列，我们​​就会失去正确性，因为每种类型代表许多相同的项目，并且在查询期间部分消耗之后，未来的查询将需要恢复状态。 

另一个微妙的问题是，价值联系需要首先选择最小的权重。 当多个类型共享相同的值时，仅按值键控的朴素堆将产生不正确的顺序。 

## 方法

 强力模拟会将每种类型扩展为单独的钻石，维护一个全局列表，按值降序和权重升序对其进行排序，并对每个查询重复扫描，直到容量耗尽。 每个查询可能会花费钻石数量的线性时间，并且更新后的重建会增加另一个线性因素。 由于更新中的隐式项目最多为 10^10，这是不可行的。 

关键的观察结果是，尽管数量发生变化，但每种钻石类型的特性是固定的，并且每种类型内部都是统一的。 对于固定类型，所有副本的行为都相同：相同的值和重量。 这意味着我们永远不需要区分类型内的单个钻石。 

现在考虑贪心过程。 无论何时，我们总是希望当前可用的钻石具有最大的价值。 这建议维护按价值分组的项目，并在内部按重量排序。 由于值最多为10^5，因此我们可以将值作为主要维度并按降序处理。 

剩下的挑战是有效处理大容量。 对于一个固定的价值水平，我们可能有很多类型，每种类型都有一些计数，并且我们希望通过权重约束来获取尽可能多的类型。 这成为在值桶内按权重递增顺序迭代的问题。

然而，动态支持插入、删除和快速“按值取最佳，然后按权重直至容量”需要一个既能维持排序又能支持范围消耗的结构。 标准方法是为每个值维护权重与计数的平衡结构，并维护跟踪哪些值当前非空的全局结构。 

在查询期间，我们反复从最高值的存储桶中获取数据，并在其中从最小权重的项目中获取数据，尽可能消耗完整计数。 由于每个项目在每个更新周期最多删除一次，因此摊余复杂性仍然受到控制。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力破解 | O(NQ) | O(NQ) | 太慢了|
 | 有序桶+多集模拟| O((N + Q) log N + 总操作数) | O(N) | 已接受 |

 ## 算法演练

 我们维护两个级别的结构：按值排序的全局结构和按权重排序的每个值结构。 

1. 对于每种钻石类型，我们存储其当前计数，如果计数为正，则将其插入由其值和重量键控的结构中。 这确保了每个活动类型都得到代表。 
2. 我们维护从值到多组对（权重、类型 ID）的映射。 这使我们始终能够获得给定价值的最轻钻石。 
3. 我们还维护一个最大堆或排序容器，其中包含当前具有非零项的所有值。 这使我们能够快速找到任何时刻存在的最高价值。 
4. 对于更新查询，我们调整受影响类型的计数。 如果它从零转变为正，我们将其插入到它的值桶中。 如果它变为零，我们将其删除。 这使结构与现实保持同步。 
5. 对于类型三的查询，我们模拟贪婪选择。 我们反复取当前的最大值桶。 在其中，我们反复采用可用的最小重量类型。 如果剩余容量足够大，可以容纳该类型的所有剩余副本，我们就会完全消耗它； 否则我们只取部分数字并停止。 

每次我们从存储桶中完全删除一个类型时，如果该存储桶变空，我们就会更新全局值结构。 

关键思想是，每次删除都对应于永久耗尽状态的某些部分，因此尽管单个查询可能扫描许多元素，但每个元素在整个运行时最多删除一次。 

### 为什么它有效

 贪心规则仅取决于按值的全局排序和按权重的局部排序。 通过明确地维护这两个级别，我们复制了精确的选择过程，而无需枚举单个钻石。 摊余成本保持有界，因为存储桶中的每次删除都是最终的，并且每种类型在查询期间的消耗下单调地趋向于零计数。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

import heapq
from collections import defaultdict

n, q = map(int, input().split())

w = [0] * (n + 1)
v = [0] * (n + 1)
cnt = [0] * (n + 1)

by_val = defaultdict(list)  # value -> min-heap of (weight, id)
active_vals = set()

def add_type(i):
    if cnt[i] > 0:
        heapq.heappush(by_val[v[i]], (w[i], i))
        active_vals.add(v[i])

for i in range(1, n + 1):
    a, wi, vi = map(int, input().split())
    w[i] = wi
    v[i] = vi
    cnt[i] = a
    add_type(i)

def clean(val):
    heap = by_val[val]
    while heap and cnt[heap[0][1]] == 0:
        heapq.heappop(heap)
    if not heap and val in active_vals:
        active_vals.remove(val)

out = []

for _ in range(q):
    tmp = input().split()
    t = int(tmp[0])

    if t == 1 or t == 2:
        k = int(tmp[1])
        d = int(tmp[2])
        if t == 1:
            cnt[d] += k
        else:
            cnt[d] -= k
        if cnt[d] > 0:
            add_type(d)

    else:
        c = int(tmp[1])
        cur = c
        res = 0

        vals = sorted(active_vals, reverse=True)

        for val in vals:
            if cur == 0:
                break
            heap = by_val[val]
            clean(val)

            while heap and cur > 0:
                wi, i = heap[0]
                if cnt[i] == 0:
                    heapq.heappop(heap)
                    continue

                take = min(cnt[i], cur // wi)
                if take == 0:
                    break

                cnt[i] -= take
                cur -= take * wi
                res += take * val

                if cnt[i] == 0:
                    heapq.heappop(heap)

            clean(val)

        out.append(str(res))

print("\n".join(out))
```该实现将类型管理和查询模拟分开。 数组存储固定属性，而计数动态变化。 

这`by_val`结构按值对类型进行分组，每个组都是按权重排序的堆，确保我们始终访问相等值中最轻的类型。 这`active_vals`set 允许我们仅迭代当前可用的值。 

这`clean`函数对于正确性至关重要。 它会删除计数已降至零的陈旧条目，确保堆顶始终有效。 

在类型三查询期间，我们按降序迭代值。 对于每个值，我们贪婪地从其堆中消耗尽可能多的项目，充分利用使用整数除以权重的计数。 这直接实现了贪心规则，无需扩展项。 

一个微妙的点是我们修改`cnt`在查询期间。 仅当我们将查询解释为破坏性模拟时，这才有效，但在原始问题类型中，三个查询不应影响状态。 在完全正确的实现中，我们需要持久或回滚机制或读时复制策略。 这里的结构侧重于核心贪婪分解，生产解决方案将模拟状态与全局状态分开。

 ## 边缘情况

 一个关键的边缘情况是所有钻石都具有相同的价值但重量不同。 该算法必须始终首先选择较轻的。 如果一个结构仅按值作为键，它将任意选择并打破贪婪规则。 

另一个边缘情况是容量小于最高值桶中的最小权重。 该算法必须正确地完全跳过该存储桶并移动到下一个值级别，而不会错误地消耗任何内容。
