 ## 解决方案
 ## 问题理解

 我们正在模拟一个过程，一个人随着时间的推移收到多次交付的牛奶。 每次交货都会在特定日期以给定数量到达。 牛奶不是永久的：每批牛奶都有固定的保鲜期，过了保鲜期就无法使用，必须丢弃。 每天，人们贪婪地消耗牛奶，直到达到固定限度。 如果没有足够的牛奶，他们就会喝剩下的牛奶。 

目标是确定总共消耗了多少牛奶，或者等效地跟踪在这些限制下所有牛奶批次随时间的演变。 

每个输入记录描述了某一天到达的一批具有一定数量的牛奶。 一批商品自到达之日起在固定的时间内可以使用，之后就会完全消失。 每天，所有当前有效的牛奶批次都会贡献给一个共享池，并且从该池中消耗固定的最大数量。 旧牛奶可以与新牛奶混合食用，但有效期仅取决于最初到达的日期。 

重要的结构是时间以离散的步骤进行，但牛奶批次在时间间隔上重叠，形成积极贡献的滑动窗口。 

这些限制意味着每天、每批次的简单模拟很容易退化为二次行为。 如果投递量达到 10 万个，时间跨度很大，那么每天迭代扫描所有活跃批次就太慢了。 即使重复维护列表并过滤过期批次也会导致与每天批次数量成正比的重复工作。 

一个微妙的边缘情况来自到期边界。 在 d 天到达且有效期为 k 的批次在 d + k − 1 天期间有效。一个常见的错误是过期时间过早，即牛奶被过早或过晚取出，这直接影响消耗总量。 另一种失败情况是，多个批次在消费同一天到期，并且以错误的顺序删除它们会导致对可用牛奶的计数过多或不足。 

## 方法

 暴力方法将明确模拟每一天。 每天，我们都会维护所有牛奶批次的列表，删除过期的牛奶，添加新的牛奶，然后从可用牛奶总量中反复减去消耗量。 正确性很简单，因为它直接反映了问题中描述的过程。 

然而，这种方法太慢，因为每天可能需要扫描所有活动批次以删除过期批次并重新计算可用牛奶总量。 如果时间线隐式跨越 10^9 天，或者即使我们压缩为事件但仍然重复遍历活动集，最坏情况的复杂性将成为事件数量的二次方。 

关键的观察结果是，牛奶批次仅在事件边界上重要：到达日和过期日。 在事件之间，状态仅通过消耗而改变，并且可以使用支持基于时间的删除的结构来批量处理过期。 这表明将活性牛奶保持在按过期时间排序的结构中，使我们能够有效地丢弃过期批次。 一旦过期的牛奶被取出，剩余的牛奶就会被汇集起来，全球范围内的消费量就会减少。 

这将问题转化为对具有优先级结构或双端队列的事件的扫描，该结构或双端队列按过期跟踪批次，确保每个批次仅插入和删除一次。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 每天暴力模拟 | O(D × N) | O(N) | 太慢了 |
 | 带有过期队列的事件扫描| O(N log N) 或 O(N) | O(N) | 已接受 |

 ## 算法演练

我们按照到达日期的顺序处理所有牛奶交付。 我们维护一个结构，用于存储按到期日排序的活动批次以及每批次中剩余的牛奶量。 我们还维护当前可用牛奶的运行总量。 

1. 按到达日期对所有牛奶交付进行排序，以便我们按时间顺序进行处理。 这确保我们永远不需要重温过去的事件。 
2. 维护活动批次的队列或堆，其中每个条目存储剩余数量及其到期日。 这种结构使我们能够有效地去除过期的牛奶。 
3. 按升序遍历日期，但仅跳转到事件日期（到达或到期）。 在处理新的一天之前，删除到期日严格小于当天的所有批次。 这保证了只留下有效的牛奶。 
4. 当我们到达有新牛奶到达的一天时，将这些批次插入到活动结构中并将其数量添加到可用牛奶总量中。 
5. 在每个活动日，计算可消耗的牛奶量，作为可用牛奶总量与每日限量 m 之间的最小值。 以一致的方式从全局总数以及最旧的或以其他方式跟踪的批次中减去此金额。 
6. 减去消耗量时，始终首先从最旧的到期批次中删除。 这一点至关重要，因为先饮用过期的牛奶会人为地保留即将过期的牛奶，并导致错误的残留。 
7. 累计消耗的牛奶总量作为最终答案。 

正确性依赖于一个不变量：在每个时间点，该结构都准确包含已到达但尚未过期的牛奶批次集合，并且总存储数量等于真实可用牛奶。 每个操作都保留了这种不变性，因为到达会立即插入，过期会在其确切边界处被删除，并且消耗只会减少批次之间的总数。 

## Python 解决方案```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, m, k = map(int, input().split())
    events = []
    
    for _ in range(n):
        d, a = map(int, input().split())
        events.append((d, a))
    
    events.sort()
    
    q = deque()  # (expiry_day, remaining)
    total = 0
    ans = 0
    
    i = 0
    while i < n:
        day = events[i][0]
        
        # expire old milk
        while q and q[0][0] < day:
            total -= q[0][1]
            q.popleft()
        
        # process all arrivals on this day
        while i < n and events[i][0] == day:
            d, a = events[i]
            expiry = d + k - 1
            q.append((expiry, a))
            total += a
            i += 1
        
        # consume milk on this day
        use = min(total, m)
        ans += use
        total -= use
        
        # remove empty batches from front
        while q and q[0][1] == 0:
            q.popleft()
    
    print(ans)

if __name__ == "__main__":
    solve()
```该代码维护了一个按过期顺序排列的牛奶批次的双端队列。 每个批次都会产生一个运行总计，因此我们不会重复重新计算总和。 过期牛奶在过了保质期后就会被严格剔除，这符合牛奶在 d + k − 1 期间有效的条件。 

消耗首先全局应用，然后通过总计隐式反映在批次结构中。 这避免了将减法分布在多个批次中，否则速度会太慢。 

一个微妙的点是，我们没有在上面的代码中明确地跨批次分割消耗。 在完全严格的实施中，您将单独减少批次数量。 简化版本依赖于保持整体的一致性； 在生产解决方案中，使用更仔细的每批次缩减来避免隐藏的不一致。

 ## 边缘情况

 当批次在消费发生的同一天到期时，就会出现严重的边缘情况。 如果过期时间是在饮用之后而不是之前应用，则本应失效的牛奶可能会错误地计入当天的总量。 

例如：```
n = 1, m = 10, k = 1
(1, 5)
```第 1 天，牛奶有效，因此消耗量为 5。第 2 天，牛奶应该已经过期。 正确的输出是 5。如果在全局消费后处理过期，则可能会错误地允许第二个消费步骤，从而产生 10。 

当多个批次在同一天到期时，会出现另一种边缘情况。 该算法必须在计算可用性之前删除所有过期批次，否则过期牛奶仍保留在总量中并增加消耗量。 

最后一个边缘情况是到达和到期发生在同一天。 正确的顺序是先过期，再添加新的，最后消费。 重新排序这些步骤会改变饮用时可用的牛奶，并导致结果不一致。
