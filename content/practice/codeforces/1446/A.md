 ## 解决方案
 ## 问题理解

 我们得到了几个独立的测试用例。 每个测试用例中有一个物品集合，每个物品有一个重量，以及一个固定容量的背包$W$。 任务是选择这些物品的一些子集，使得它们的总重量$C$着陆在特定区间内：必须至少为背包容量的一半（向上取整），并且不得超过$W$。 

换句话说，我们不会尝试优化任何超出可行性的事情。 我们只需要找到任何总和“足够大但仍然安全”的子集。 如果存在这样的子集，我们必须输出我们通过索引选择的项目，否则我们报告不可能。 

这些约束强烈表明我们不能尝试所有子集。 高达$2 \cdot 10^5$跨测试的项目，任何指数方法都是不可能的，甚至每个测试的二次行为也太慢。 这促使我们对每个测试用例进行线性或近线性构造，可能涉及排序或贪婪选择。 

当所有项目单独太大或太小而无法正确组合时，就会出现微妙的失败情况。 

一种极端情况是每一项都超过$W$。 例如，如果$W = 5$权重是$[6, 7]$，那么没有子集是有效的，我们必须输出`-1`。 

另一个边缘情况是，所有项目都非常小，但只有仔细组合，它们的总和才勉强达到阈值。 一个天真的贪婪者挑选了太多的小物品可能会过度$W$，即使存在有效的组合。 

第三个重要的情况是当单个项目已经位于所需的区间内时。 例如，如果$W = 10$，那么任何权重为 5 到 10 的项目都会立即成为有效答案，并且我们不应该不必要地组合项目。 

## 方法

 暴力解决方案将尝试所有项目子集，计算它们的总和，并检查是否有任何总和位于有效区间内。 这在原则上是正确的，因为它详尽地探索了所有可能性。 然而，子集的数量是$2^n$，即使对于$n = 40$，更不用说$2 \cdot 10^5$。 每个子集总和计算也会增加开销，使得这完全不可行。 

关键的观察是我们不需要精确地达到区间或最大化任何东西。 我们只需要在保持低于目标下限的情况下达到目标下限$W$。 这表明了一种贪婪的策略，我们逐渐积累权重，直到跨过阈值。 

解决此类问题的标准技巧是按任意顺序挑选项目，同时保持运行总和，但也要确保避免过度调整$W$当不必要的时候。 一种更结构化的方法是首先忽略所有比$W$，因为它们永远无法使用。 然后我们尝试积累物品，直到至少达到$\lceil W/2 \rceil$。 如果成功，我们将输出所选项目。 

然而，还有一个额外的结构见解：如果我们超过$W$，我们无法通过添加更多项目来解决这个问题，因此我们必须确保仅在总和保持在范围内的情况下添加项目。 这将问题变成了受控累积问题，而不是纯粹的子集和搜索。

 | --- | --- | --- | --- |
 | 蛮力 |$O(2^n)$|$O(1)$| 太慢了|
 | 贪婪积累|$O(n \log n)$或者$O(n)$|$O(n)$| 已接受 |

 ## 算法演练

 我们独立解决每个测试用例。 

1. 计算所需的最低金额$L = \lceil W/2 \rceil$。 这是可接受的最小总重量。 
2.过滤掉所有重量大于的物品$W$，因为它们永远不可能成为有效解决方案的一部分。 他们的指数被完全忽略。 
3. 迭代剩余的项目并维护运行总和和所选索引的列表。 对于每一项，尝试将其包括在内。 
4. 如果总和未超出则添加该项目$W$，因为超过容量会立即使子集失效。 
5. 一旦运行金额达到至少，就提前停止$L$。 此时，我们已经有了一个有效的解决方案，无需进一步添加。 
6. 如果处理完所有项目后总和仍然低于$L$， 输出`-1`。 

### 为什么它有效

 正确性取决于以下事实：所有有效解决方案仅通过其总和来表征，而不是通过结构来表征。 由于每个项目都有正权重，因此添加项目只能增加总和。 因此，一旦我们达到或超过$L$，只要我们从未超过，我们就保证可行性$W$施工期间。 

任何未能到达的情况$L$意味着即使所有可用项的总和也不够，因此没有子集可以满足下界约束。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n, W = map(int, input().split())
    w = list(map(int, input().split()))

    L = (W + 1) // 2

    chosen = []
    total = 0

    for i, x in enumerate(w, 1):
        if x > W:
            continue
        if total + x <= W:
            chosen.append(i)
            total += x
        if total >= L:
            break

    if total < L:
        print(-1)
    else:
        print(len(chosen))
        print(*chosen)
```该解决方案处理每个项目一次，维护运行总和和选定索引的列表。 关键决策点是检查`total + x <= W`，在施工过程中严格执行背包容量限制。 提前停止条件确保我们在满足下限后不会不必要地包含额外的项目。 

索引使用从 1 开始的位置，因为问题需要原始项目索引。

 输入：```

| 步骤| 项目 | 重量 | 之前总计 | 拿？ | 总计 | 之后 选择|

 ## 边缘情况

 一个关键的边缘情况是每个项目单独有效但将它们组合起来会打破约束。 考虑$W = 10$, 权重$[6, 6]$。 每件单品都可以，但两者一起带就超出了容量。 该算法处理这个问题是因为它拒绝任何超出的加法$W$，导致仅选择一项，并且仅在无法到达时才会失败$L = 5$。 在这种情况下，选择 6 中的任意一个就已经满足条件，因此算法立即成功。 

另一种情况是当所有项目都很小时，例如$W = 9$, 权重$[1,1,1,1,1,1,1,1,1]$。 该算法会累积直到至少达到 5，然后选择前 5 项。 它绝不会冒超过的风险$W$，并且运行总和保证了最终的成功，因为总和是足够的。
