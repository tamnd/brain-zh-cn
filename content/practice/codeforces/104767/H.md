 ## 问题理解

 我们正在与一系列通过无方向的“邻居”关系连接的实验室合作。 每个实验室最初都包含一定数量的桌子和显示器。 随着时间的推移，这些计数会发生变化，因为我们向各个实验室添加了桌子或显示器。 

关键的复杂性在于，当我们评估实验室时，我们不会孤立地看待它。 实验室的“可用”办公桌和显示器被定义为其自身资源加上其直接连接的相邻实验室中的所有资源的总和。 除了图中的一条边之外，没有任何东西有贡献。 

因此，每个感兴趣的查询都会问：如果我们采用一个节点并聚合其封闭邻域（其本身和所有相邻节点）的值，办公桌是否超过显示器，显示器是否更高，或者它们是否相等。 

输入约束将所有三个维度设置为最多 100000。该图可以是稀疏的或密集的。 操作数量足够大，在最坏的情况下，为每个查询从头开始重新计算邻域和会太慢。 对每个查询的邻接列表进行全面扫描将降级为密集图上的二次行为，这在 Python 的 5 秒限制下是不可行的。 

更新带来了一个微妙的问题：每个“添加”操作仅更改单个节点，但它会影响在其聚合中包含该节点的每个邻居的答案。 仅在被要求时才重新计算所有内容的简单解决方案要么会重复重新扫描邻接列表，要么不维护任何结构并根据需要重新计算，这两种情况都会面临 TLE 风险。 

值得明确的边缘情况来自图结构。 

如果图有一个节点有多个邻居，例如以 1 为中心的星形，则叶子上的每个查询都需要通过高度节点求和。 对于叶子来说，幼稚的每查询邻接遍历仍然没问题，但对中心的更新会间接影响许多叶子。 如果图很密集，就会出现对称问题：每个查询几乎涉及所有节点。 

另一个边缘情况是孤立的节点。 如果一个节点没有邻居，它的答案仅取决于它自己。 一种粗心的实现假设至少有一个邻居会错误地访问空邻接列表或错误处理初始化，但从逻辑上讲，这些节点应该是微不足道的常量时间答案。 

最后，重复更新很重要。 每个更新的量级都很小，但最多可以有 100000 个，因此任何跨所有节点的每次更新传播都是不可接受的。 

## 方法

 一种简单的方法是存储图表，并针对每个查询重新计算查询节点及其所有邻居上的桌面和监视器的总和。 这是通过迭代节点的邻接列表来累加两个值来实现的。 

这是正确的，因为可用性的定义纯粹是封闭邻域的局部性。 然而，这种方法需要为每个查询扫描所有邻居的成本。 在节点度数接近 N 的最坏情况图中，每个查询都变为线性。 对于多达 100000 个查询，这会导致最坏情况下的复杂性接近 10^10 次操作，这是不可行的。 

真正的低效率在于更新实际上并未本地化：更改一个节点会影响其所有邻居的未来查询结果。 我们不想从头开始重新计算，而是希望维护部分聚合信息。 

关键的观察是邻接表可以分为两种类型的节点：低度节点和高度节点。 如果我们特殊对待度数较大的节点，我们可以为它们维护预先计算的邻域和。 然后更新只需要传播到与更新节点相邻的那些高度节点。 由于高度节点的数量很少，这使得总工作量受到限制。

这导致了标准的“图度数的重度”优化：为低度数节点廉价地重新计算答案，并为高度数节点维护缓存的聚合。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 对每个查询进行强力重新计算 | O(Q·deg) 最差 O(NQ) | O(N + M) | 太慢了 |
 | 度分解（重-光）| O((N + Q)√M) | O(N + M) | 已接受 |

 ## 算法演练

 我们维护两个并行系统，一个用于办公桌，一个用于显示器，但两者的行为相同。 

我们选择 √M 附近的阈值 B。 度大于B的节点称为重节点，其余为轻节点。 

### 步骤

 1. 根据每个节点的度将其分类为重节点或轻节点。 

这保证了重节点的数量最多为O(M/B)，这个数量很小。 
2. 为每个节点预先计算其邻接列表，并且仅通过邻居迭代隐式地构建反向结构。 

我们并不明确需要反向边； 我们将在更新期间扫描邻接列表。 
3. 对于每个重节点，维护一个运行值，表示其整个封闭邻域内的桌面（或监视器）总数。 

最初，这可以通过对其邻接列表进行单次传递来计算。 
4. 通过以下方式处理更新“向节点 u 添加值”：

 首先更新 u 处的原始值。 

然后迭代u的所有邻居v。 

如果 v 很重，则将其缓存的邻域和更新为相同的增量。 

这是正确的，因为当 v 与 u 相邻时，u 正好对 v 的邻域做出贡献。 
5. 对于节点u的查询：

 如果u很重，则直接返回其缓存值。 

如果 u 很轻，则通过迭代所有邻居并将它们的当前值加上自身求和来计算其答案。 

这是可以接受的，因为轻节点的度数最多为 B。 
6. 对桌子和显示器独立重复相同的结构，然后比较每个查询的两个结果。 

### 为什么它有效

 正确性取决于每个重节点始终存储其闭邻域的精确总和的不变量。 这仍然是正确的，因为每当节点发生变化时，我们都会立即将该增量传播到依赖于它的所有重邻居。 轻节点永远不会被缓存，因此它们总是在需要时准确地重新计算。 由于每个查询要么使用正确的缓存，要么直接从当前基值重新计算，因此不会使用过时的信息。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class HeavyLight:
    def __init__(self, n, adj, vals, B):
        self.n = n
        self.adj = adj
        self.val = vals[:]  # base values
        self.B = B

        self.heavy = [False] * (n + 1)
        for i in range(1, n + 1):
            if len(adj[i]) > B:
                self.heavy[i] = True

        self.heavy_sum = [0] * (n + 1)

        for i in range(1, n + 1):
            if self.heavy[i]:
                s = self.val[i]
                for v in adj[i]:
                    s += self.val[v]
                self.heavy_sum[i] = s

    def add(self, u, delta):
        self.val[u] += delta
        for v in self.adj[u]:
            if self.heavy[v]:
                self.heavy_sum[v] += delta

    def query(self, u):
        if self.heavy[u]:
            return self.heavy_sum[u]
        res = self.val[u]
        for v in self.adj[u]:
            res += self.val[v]
        return res

def solve():
    n, m, q = map(int, input().split())
    d = list(map(int, input().split()))
    e = list(map(int, input().split()))

    adj = [[] for _ in range(n + 1)]
    for _ in range(m):
        a, b = map(int, input().split())
        adj[a].append(b)
        adj[b].append(a)

    B = int(m ** 0.5) + 1

    desks = HeavyLight(n, adj, [0] + d, B)
    mons = HeavyLight(n, adj, [0] + e, B)

    out = []

    for _ in range(q):
        parts = input().split()
        if parts[0] == "add":
            typ = parts[1]
            cnt = int(parts[2])
            u = int(parts[3])
            if typ == "desk":
                desks.add(u, cnt)
            else:
                mons.add(u, cnt)
        else:
            u = int(parts[1])
            ds = desks.query(u)
            ms = mons.query(u)
            if ds > ms:
                out.append("desks")
            elif ms > ds:
                out.append("monitors")
            else:
                out.append("same")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该实现将基值保留在`val`，并使用`heavy_sum`仅针对度数超过阈值的节点。 更新仅传播到那些缓存的节点。 这避免了任何完全重新计算。 

一个常见的陷阱是忘记更新会对称地影响办公桌和显示器； 两种结构必须接收相同的图和独立的值层。 另一个微妙的问题是用封闭邻域（而不仅仅是邻居）初始化大量总和，因为节点本身是查询定义的一部分。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O((N + Q)√M) | 每次更新只涉及重邻居； 每个轻节点查询最多扫描 √M 邻接大小 |
 | 空间| O(N + M) | 图形存储加上每个节点的值和大量缓存 |

 阈值选择确保所有操作的总邻接扫描保持有限。 即使在密集图中，也只有受控数量的节点被视为重节点，以防止二次爆炸。

 ## 边缘情况

 单个孤立节点是最简单的情况。 邻接列表是空的，因此查询减少为比较节点自己的桌面和监视器值。 该算法自然地处理这个问题，因为轻节点查询循环迭代一个空列表并仅返回基值。 

在星图中，如果中心节点的度数超过阈值，则中心节点会变重。 对叶子的任何更新都会传播到中心的缓存总和中，确保中心上的查询保持 O(1)。 叶子仍然很轻，并在一个邻居上重新计算，即使在频繁更新的情况下也能保持操作稳定。 

在完全密集的图中，几乎所有节点都变得很重，但这受到控制，因为阈值确保重节点的数量相对于 M 来说很小。更新仍然只沿着邻接列表传播，并且总工作仍然受到跨操作的度数总和的限制，而不是每个查询的完整扫描。
