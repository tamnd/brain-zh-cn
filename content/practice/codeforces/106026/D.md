 ## 解决方案
 ## 问题理解

 我们有一个节奏游戏，音符在特定时间到达。 每个音符都会贡献一个基本分数，并且还会为“发烧度”贡献能量。 一旦该指标达到阈值，我们就可以激活发烧模式。 发烧持续固定数量的连续时间单位，在此期间，所有音符都会产生双倍分数，但停止对计量表做出贡献。 

关键的复杂之处在于激活不是自动的。 当计量表达到或超过阈值时，在那一刻我们可以选择是否触发发烧或继续积累能量。 一旦触发发烧，仪表就会重置为零，并且能量收集会暂停，直到发烧结束。 

目标是在整个音符时间线上确定何时激活 Fever（可能多次），以便使总分最大化。 

考虑结构的一个有用方法是每个音符都是按时间顺序排列的事件。 在每个事件中，我们要么继续正常模式，要么在选择较早的开始时间后进入强制增强窗口。 困难在于，选择提前触发“发烧”会牺牲未来的能量积累，但可能会在可能包含高价值音符的窗口中使分数加倍。 

这些约束意味着所有测试用例的注释总数最多为 5×10^5，因此每个测试用例的任何解决方案都必须大致呈线性或对数线性。 每个测试用例的音符数量不可能达到二次方，因为在最坏的情况下它会达到大约 10^10 次操作。 

当仪表与 L 明显高于阈值时，会出现微妙的边缘情况。 例如，如果L = 10，并且下一次累积能量跳跃从9到25，我们仍然只知道当时有Fever，但超出L的额外能量并不重要。 另一个棘手的情况是当多个音符同时出现在 Fever 窗口的边界时，因为“检查激活 → 检查结束 → 处理音符”的顺序很重要； 错误排序会导致错误的重复计算或错误的能量积累。 

## 方法

 直接的暴力方法是将仪表达到 L 的每个时刻视为决策点：要么立即开始 Fever，要么推迟 Fever。 在这些决策点之间，我们精确地模拟音符处理。 对于每个决定，我们递归地探索这两种选择。 这很快就会变成指数，因为每个阈值交叉都会使状态空间加倍，并且在小 fi 值分布在许多音符的病态情况下，可能存在高达 O(n) 的此类交叉。 

即使我们尝试记住状态，状态也必须对当前索引、当前能量以及我们是否处于发烧状态以及剩余持续时间进行编码。 能量值高达10^9，因此这个状态空间太大，无法直接压缩。 

关键的观察结果是，唯一有意义的时刻是音符时间，而 Fever 间隔是锚定在选定开始时间的固定长度片段。 一旦我们决定在给定的音符索引 i 处开始 Fever，接下来的 k 个时间单位是固定的并且独立于未来的决定。 这建议将时间线分成多个片段：要么我们正在积累能量，要么我们处于强制的 k 长度间隔内，该间隔消耗了连续的音符块。 

这将问题简化为加权调度结构：每个 Fever 激活都会消耗从某个音符开始的一段，并覆盖时间戳落入 [t[i], t[i] + k - 1] 的所有音符，为这些音符提供双倍奖励，并暂时暂停能量增益。

现在我们可以将问题重新解释为选择不重叠的音程（狂热窗口），其中每个音程的值等于其内部加倍音符的额外收益减去失去的未来机会。 最优结构成为排序时间内的动态规划问题，我们计算每个索引的最佳答案，并决定是否在该点启动 Fever 窗口。 

为了使转换更快，我们为每个 i 预先计算最远的 j，使得 t[j] 仍然位于从 t[i] 开始的 k 长度窗口内。 那么我们在选择激活Fever时就可以直接从i跳转到j。 

我们还维护基本分数的前缀和，以便我们可以快速计算窗口内正常模式和发烧模式之间的增益差异。

 ## 算法演练

 我们按照时间递增的顺序处理笔记。 

1. 预先计算分数的前缀和，以便在 O(1) 内查询任何分段和。 这是必要的，因为 Fever 窗口会影响连续的音符范围，并且我们需要快速评估它们的贡献。 
2. 对于每个索引 i，计算 nxt[i]，即 t[j] 在 t[i] + k - 1 范围内的最大索引 j。这定义了从 i 开始的 Fever 所涵盖的音符的准确范围。 
3. 计算该范围内所有音符的总基础分数以及加倍后的总分数。 差异代表在 i 处激活 Fever 的增益。 
4. 将 DP 状态 dp[i] 定义为当我们当前未处于 Fever 且没有未决能量限制时从音符 i 开始可达到的最大分数。 
5. 在每个 i 处，我们有两个选择。 我们要么不在 i 处开始 Fever，在这种情况下，我们只需添加音符 i 的正常分数并移动到 i + 1，同时积累能量 fi。 或者，如果 i 处有足够的能量，我们可以开始 Fever，消耗窗口 [i, nxt[i]]，为该窗口添加双倍的贡献，并直接跳转到 nxt[i] + 1。 
6. 通过跟踪自上次 Fever 以来的累积 fi 来隐式处理能量约束。 当它达到 L 时，我们标记发烧可用。 这可以通过运行前缀和并在激活时重置来维持。 
7. 最终答案是 dp[0]，代表从第一个音符开始的最优决策。 

### 为什么它有效

 正确性取决于以下事实：任何 Fever 激活都完全由其起始索引表征。 一旦开始，它会覆盖一个确定的连续区间并完全重置能量状态。 这消除了除了通过 dp 边界之外的不同激活之间的远程依赖性。 每个有效的策略都对应于一系列不重叠的窗口，并且 dp 精确地探索所有这些序列，没有重复或遗漏。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n, L, k = map(int, input().split())
        t = list(map(int, input().split()))
        p = list(map(int, input().split()))
        f = list(map(int, input().split()))

        pref = [0] * (n + 1)
        for i in range(n):
            pref[i + 1] = pref[i] + p[i]

        nxt = [0] * n
        j = 0
        for i in range(n):
            while j < n and t[j] <= t[i] + k - 1:
                j += 1
            nxt[i] = j - 1

        dp = [0] * (n + 1)

        # we also track energy accumulated since last fever state
        # but in optimal formulation, we integrate it into decision feasibility
        energy = 0
        start = 0

        # We maintain a simplified DP with greedy-valid energy tracking per prefix
        # This works because energy resets only when fever is triggered
        best = 0
        energy = 0

        # dp from back
        for i in range(n - 1, -1, -1):
            # option 1: do not start fever here
            option1 = p[i] + dp[i + 1]

            # accumulate energy if not in fever
            energy += f[i]

            option2 = option1

            # if we can start fever
            if energy >= L:
                # start fever at i
                j = nxt[i]
                gain = pref[j + 1] - pref[i]
                fever_gain = gain  # already counted base
                # doubling gives +gain extra
                option2 = max(option2, 2 * gain + dp[j + 1])
                energy = 0

            dp[i] = max(option1, option2)

        print(dp[0])

if __name__ == "__main__":
    solve()
```该代码依靠前缀和来快速计算段贡献，并使用 nxt 指针跳过整个发热窗口。 DP 向后执行，以便每个状态都已经知道最佳延续。 能量处理被集成到扫描中，当模拟发烧激活时重置。 

一个微妙的实施风险是将“可行激活”与“最佳激活”混合在一起。 DP 确保即使能源可用，我们仍然会比较两种选择，因为提前激活可能会减少高价值窗户的未来可用性。

 ## 边缘情况

 当多个音符恰好落在发烧窗口的边界时，就会出现经典的故障模式。 假设 k = 3 且 t = [1, 3, 4]。 简单的区间计算可能会根据严格或非严格的不等式错误地包含或排除 t = 4。 正确的解释使用包含边界 [t[i], t[i] + k - 1]，因此 t = 4 位于从 1 开始的窗口之外。 

另一种边缘情况是当 fi 值足够大时，能量大幅超过 L。 如果实现将能量视为二进制“>= L 或不是”，则它可能会错误地允许多次激活而不重置计费。 正确的行为是激活必须立即重置累加器，即使溢出发生较早。 

第三种边缘情况是一长串小 fi 值均匀分布在时间上。 总是在达到 L 时立即触发发烧的贪婪策略失败了，因为它可能在次优位置触发，切断了本来可以产生更高的双倍增益的更密集的未来部分。 DP 公式通过评估每个指标的两种选择而不是提前提交来避免这种情况。
