 ## 解决方案
 ## 问题理解

 比赛已经结束，记分牌被冻结。 你完全知道自己球队的最终结果：你解决了多少问题以及你的总罚时。 处罚遵循 ICPC 规则，即每个问题贡献其首次接受的提交时间，加上在首次接受的提交之前每一次错误提交的 20 分钟。 

您现在正在分析另一个特定团队。 对于冻结时间之前的所有提交，您都知道一切：哪些尝试被接受，哪些尝试被拒绝。 然而，在冻结时间之后，该团队的每次提交都只能作为针对某个问题的带时间戳的尝试来查看，而不知道它最终是否会被接受或拒绝。 每一个冻结后提交的内容都可以独立地成为可接受的解决方案或错误的尝试。 

问题不是模拟所有最终排名。 相反，您需要确定该团队是否有可能在最终排名中严格高于您的团队，如果是这样，请找到他们最终必须解决的最少数量的冻结后问题。 

“严格更高的排名”遵循通常的 ICPC 规则：如果一个团队解决了更多问题，或者解决了相同数量的问题但惩罚较小，则该团队更好。 

重要的微妙之处在于，冻结后的不确定性与个人提交的问题无关，而是与冻结后每个问题是否最终得到解决有关，如果解决了，则只有您决定将最早的冻结后提交视为已接受的评分事项。 

就问题数量而言，约束非常小，最多 15 个。这立即表明任何解决方案都可以对问题子集进行指数推理，因为即使$2^{15}$只有 32768，这个数字相当小。 提交的数量最多为 1000 个，这个数量足够大，我们必须仔细进行预处理，但仍然足够小，每个问题的聚合都是微不足道的。 

导致错误解决方案的一个天真的误解是独立对待每个冻结后提交并尝试贪婪地分配接受/拒绝。 这失败了，因为多个提交属于同一问题，只有第一个被接受的提交才重要。 

另一个常见的错误是假设冻结后的提交总是会以复杂的方式增加惩罚。 事实上，如果一个问题决定在冻结后解决，最佳策略总是将其最早的冻结后提交作为已接受的问题，因为任何晚于接受的行为只会增加惩罚而无益。 

## 方法

 暴力观点首先考虑冻结后提交的所有可能的方式，以得出接受或拒绝的结果。 对于冻结后提交的每个子集，我们将重新计算最终 ICPC 分数并将其与您的团队进行比较。 这在原则上是正确的，因为它列举了与不确定性一致的所有世界。 

然而，这种做法立刻就爆炸了。 如果冻结后提交的数量最多为 1000 个，则可能接受/拒绝的分配数量为$2^{1000}$，这是完全不可行的。 

ICPC 评分的结构使这个问题变得可压缩。 关键的观察结果是，冻结后的决策仅在“冻结后哪些问题得到解决”的粒度上才重要。 一旦决定解决某个问题，其最佳接受点就是确定性的：该问题最早的冻结后提交。 其他一切要么不影响分数，要么更糟。 

这将问题从对提交的推理减少到对问题的推理。 每个未解决的问题都成为一个具有二元选择的项目：要么保持未解决状态，要么恰好贡献一个额外的已解决问题和固定的惩罚成本。 

现在的问题是选择最多 15 个项目的子集。 对于每个可能选择的项目数量，我们希望达到最小的惩罚总和。 这是一个非常小的维度上的标准背包式动态规划。 

然后，我们检查使对手严格变得更好的最小数量的选定问题，要么解决比我们更多的问题，要么通过解决的数量并列但惩罚更小。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 对所有提交结果进行暴力破解 |$O(2^{s})$|$O(s)$| 太慢了|
 | 子集DP过问题|$O(n \cdot 2^n)$|$O(n)$或者$O(n \cdot n)$| 已接受 |

 ## 算法演练

 我们首先将所有信息压缩为每个问题的状态，将已经确定的信息与不确定的信息分开。 

1. 计算每个问题在冻结之前是否已经解决。 如果是的话，它对解决计数和惩罚的贡献是固定的并且不能改变。 
2. 对于冻结前未解决的问题，提取冻结后提交的所有内容。 其中，标识最早的时间戳； 如果我们决定冻结后问题得到解决，这是唯一的候选时间。 冻结后解决该问题的惩罚贡献是该时间戳加上该问题在该时间戳之前的错误提交数量的 20 倍，这恰好是在接受第一个冻结后提交之前该问题的提交数量。 
3.将对手的最终状态分为两部分：冻结前已解决的问题数量，以及其余问题。 令已解的计数为$S_0$。 
4. 建立候选“可升级问题”列表，每个问题的成本等于如果我们决定在冻结后解决它的惩罚增加，并且价值为 1 个额外解决的问题。 
5. 运行背包动态规划，其中$dp[k]$存储通过精确选择可实现的最小总额外惩罚$k$可升级的问题。 
6.对于每一个可能的$k$，计算所得的总解决计数$S_0 + k$。 如果这超出了你的团队的解决计数，那么任何惩罚都足够了，这$k$是可行的。 如果它等于您解决的计数，那么我们还要求存储在$dp[k]$严格小于您的处罚。 
7.答案是最小的$k$满足任一条件。 如果没有$k$有效，输出-1。 

这样做的原因是每个冻结后的决策都会根据问题进行彻底分解。 ICPC 评分中的问题之间没有相互作用：每个问题对解决的计数和罚分都有独立的贡献。 这种独立性确保将每个问题优化为单个成本项可以保留所有全局最优结构。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

INF = 10**18

def solve():
    n, a, b = map(int, input().split())
    s = int(input())

    solved_before = [False] * n
    pre_wrong = [0] * n

    post_first_time = [INF] * n

    freeze_time = 240

    for _ in range(s):
        parts = input().split()
        t = int(parts[0])
        p = ord(parts[1]) - ord('A')
        v = parts[2]

        if t < freeze_time:
            if v == "ac":
                solved_before[p] = True
            else:
                pre_wrong[p] += 1
        else:
            post_first_time[p] = min(post_first_time[p], t)

    base_solved = sum(solved_before)

    items = []
    for i in range(n):
        if solved_before[i]:
            continue
        if post_first_time[i] == INF:
            continue
        cost = post_first_time[i] + 20 * pre_wrong[i]
        items.append(cost)

    m = len(items)

    dp = [INF] * (m + 1)
    dp[0] = 0

    for cost in items:
        for k in range(m, 0, -1):
            if dp[k - 1] + cost < dp[k]:
                dp[k] = dp[k - 1] + cost

    if base_solved > a:
        print(0)
        return

    ans = INF

    for k in range(m + 1):
        total_solved = base_solved + k

        if total_solved > a:
            ans = min(ans, k)
        elif total_solved == a and dp[k] < b:
            ans = min(ans, k)

    print(-1 if ans == INF else ans)

if __name__ == "__main__":
    T = int(input())
    for _ in range(T):
        solve()
```该代码首先从提交日志中重建每个问题的信息。 预冻结行为被固定为问题是否已经解决以及解决之前发生了多少次错误尝试。 冻结后提交被压缩为每个问题的单个最早时间戳，因为任何稍后的冻结后提交都不能用于减少惩罚。 

然后，每个未解决的问题都将成为一个背包物品，如果选择，则具有固定的惩罚成本。 DP 计算每个额外解决的问题可实现的最佳惩罚。 

最后，我们测试增加的解决方案的值，直到满足排名条件。 

## 工作示例

 考虑一个包含 2 个问题的简化场景，您的团队已解决 1 个问题，并受到 300 的处罚。 

假设对手在冻结之前已经解决了一个问题，并且在冻结后在时间 250 提交了一个未解决的问题。 

| 步骤| 基本解决 | k 选择 | 已解决总数 | dp[k] | dp[k] | 比较|
 | ---| ---| ---| ---| ---| ---|
 | 0 | 1 | 0 | 1 | 0 | 相等解决，比较惩罚 |
 | 1 | 1 | 1 | 2 | 成本| 更大的解决了|

 在$k=0$，他们平局，但没有额外的惩罚，所以除非他们的固定惩罚已经更小，否则他们输了。 在$k=1$，他们严格超过了已解决的计数，因此无论处罚如何，他们都会获胜。 

该轨迹显示了为什么解决的计数主导惩罚：一旦它增加，惩罚就变得无关紧要。 

现在考虑这样一种情况，两个团队最初的解决计数相等。 

| 步骤| 基本解决 | k 选择 | 已解决总数 | dp[k] | dp[k] | 状况 |
 | ---| ---| ---| ---| ---| ---|
 | 0 | 2 | 0 | 2 | 0 | 比较处罚|
 | 1 | 2 | 1 | 3 | 成本| 超过已解决|

 这里的转变点正是我们遇到一个额外已解决问题的时候。 DP 确保我们选择最便宜的此类转换。

 ## 边缘情况

 一种微妙的情况是，在任何冻结后假设之前，对手在已解决的问题上已经严格领先。 在这种情况下，冻结后的决定并不重要。 该算法立即捕获了这一点，因为$base\_solved > a$返回 0。 

另一个边缘情况是当一个问题有多个冻结后提交时。 只有最早的才重要，因为任何晚一点的接受只会增加处罚。 该算法通过在构建成本之前获取每个问题的最小时间戳来强制执行此操作。 

最后一个极端情况是根本没有冻结后提交。 那么背包集是空的，只有$k = 0$经测试。 比较简化为检查已经固定的分数是否足够，如果还没有更好，则正确地产生 -1。
