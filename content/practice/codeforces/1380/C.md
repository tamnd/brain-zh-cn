 ## 解决方案
 ## 问题理解

 我们有一群程序员，每个人都有技能值。 我们希望组建尽可能多的团队。 如果满足以下条件，则团队有效：$$(\text{team size}) \times (\text{minimum skill in the team}) \ge x$$每个程序员最多只能属于一个团队，并且某些程序员可能不会被使用。 

任务是确定可以创建的有效团队的最大数量。 

最大的测试用例包含多达$10^5$程序员，以及所有的总和$n$跨测试用例的值也至多$10^5$。 在这个输入大小下，任何重复尝试程序员不同分区的算法都是不可能的。 甚至一个$O(n^2)$解决方案需要大约$10^{10}$最坏情况下的操作，远远超出了极限。 我们周围需要一些东西$O(n \log n)$或更好。 

棘手的是，团队的质量仅取决于最弱的成员。 添加更强的程序员并不会提高最低技能，但添加更多的程序员会增加团队规模。 幼稚的分组策略很容易浪费强大的程序员并减少最终的答案。 

考虑这个例子：```
n = 4, x = 10
skills = [10, 10, 10, 10]
```正确答案是 4。每个程序员单独组成一个有效的团队，因为$1 \times 10 = 10$。 如果不小心将程序员合并成更大的团队，那么团队数量就会减少。 

另一个重要案例是：```
n = 5, x = 10
skills = [5, 5, 5, 5, 5]
```正确答案是 2。每个有效的团队至少需要两名程序员，因为$2 \times 5 = 10$。 我们可以创建两个规模为 2 的团队，并留下一名程序员不使用。 坚持使用所有人的实现将错误地返回 1。 

第三种边缘情况是无法组建团队：```
n = 4, x = 11
skills = [1, 3, 3, 7]
```即使使用所有四个程序员也会给出$4 \times 1 = 4$，仍然低于 11。答案是 0。 

这些例子表明，最大化团队数量并不等于最大化使用程序员的数量。 

## 方法

 暴力解决方案会尝试不同的方法将程序员划分为团队并检查哪些分区满足条件。 这种方法是正确的，因为它检查了所有可能性，但分区的数量呈指数增长。 即使对于几十个程序员来说，这也是不可能的。 

为了做得更好，我们需要了解有效团队的特征。 

假设团队内部的最低技能是$m$。 那么团队在以下情况下有效：$$(\text{team size}) \times m \ge x$$如果我们按降序对技能进行排序，并从最强到最弱处理程序员，那么当我们到达具有技能的程序员时$a_i$，到目前为止收集到的每个程序员至少都拥有技能$a_i$。 如果我们决定$a_i$将是团队中最弱的成员，那么$a_i$成为团队的最低技能。 

此时，我们只需要知道当前团队聚集了多少程序员即可。 如果：$$(\text{current size}) \times a_i \ge x$$那么一个有效的团队就可以立即完成。 

这一观察导致了贪婪策略。 将技能从大到小排序。 通过积累程序员来组建团队。 每当当前小组有效时，立即确定并开始组建下一个小组。 

为什么一生效就可以安全关闭团队？ 

因为这个团队消耗的每一个额外的程序员都可以帮助以后组建另一个团队。 一旦一个组已经有效，扩大它并不会增加团队的数量。 最小的有效团队始终是最佳选择。 

这将问题转化为简单的排序和扫描过程。

 | 蛮力 | 指数| 指数| 太慢了 |
 | 最优贪心 + 排序 |$O(n \log n)$|$O(1)$辅助（不包括排序） | 已接受 |

 ## 算法演练

 1.将所有技能按降序排列。 
2. 初始化计数器`current_size = 0`。 
3. 初始化`teams = 0`。 
4. 从左到右处理排序后的技能。 
5. 对于每个技能值`s`，通过增加将该程序员添加到当前未完成的团队中`current_size`。 
6. 治疗`s`作为当前群体的最低技能。 由于我们是按降序处理的，所以之前收集的每个程序员至少都有技能`s`。 
7. 检查是否：$$current\_size \times s \ge x$$如果此条件成立，则当前组已形成有效团队。 
8. 增加`teams`一个。 
9. 重置`current_size`归零并开始组建下一支队伍。 
10.所有编程器处理完毕后，输出`teams`。 

### 为什么它有效

 关键的不变量是，在扫描排序数组时，当前技能值始终是当前为未完成的团队聚集的所有程序员中的最小技能。 

每当有条件时`current_size * skill >= x`成真，我们有足够的程序员来组建一个有效的团队，其最低技能正是`skill`。 立即关闭团队会为该团队使用尽可能少的程序员。 

在团队已经有效后继续添加程序员的任何解决方案只会消耗可能有助于以后创建更多团队的资源。 由于较大的团队永远不会增加团队数量，因此贪婪地确定每个有效团队并不能减少最佳答案。 

因此，由该算法组成的每个团队都是有效的，并且每个有效的团队都使用最少数量的可用程序员，这使得团队总数最大化。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())

    answers = []

    for _ in range(t):
        n, x = map(int, input().split())
        skills = list(map(int, input().split()))

        skills.sort(reverse=True)

        teams = 0
        current_size = 0

        for s in skills:
            current_size += 1

            if current_size * s >= x:
                teams += 1
                current_size = 0

        answers.append(str(teams))

    sys.stdout.write("\n".join(answers))

if __name__ == "__main__":
    solve()
```第一步按降序对技能进行排序。 这保证了每当我们检查技能值时`s`，每个已经被放入当前未完成组的程序员至少有技能`s`。 这意味着`s`正是该潜在团队的最低技能。`current_size`存储当前团队候选者已收集了多少程序员。 添加程序员后，我们测试是否满足组队条件。 

什么时候`current_size * s >= x`，一个有效的团队已经形成。 贪心的选择是立即敲定并重置`current_size`为零。 这是关键的实施细节。 忘记重置会错误地将多个团队合并在一起。 

所有算术都适合 Python 整数。 最大可能的乘积是：$$10^5 \times 10^9 = 10^{14}$$这完全在 Python 的范围之内。

 ## 边缘情况

 考虑：```
1
5 10
5 5 5 5 5
```排序后，没有任何变化。 扫描过程如下：```
size=1 -> 1*5=5
size=2 -> 2*5=10 -> team
size=1 -> 1*5=5
size=2 -> 2*5=10 -> team
size=1 -> end
```答案是2。一名程序员仍然没有被使用。 该算法从不试图强迫所有程序员加入团队。 

现在考虑：```
1
4 10
10 10 10 10
```每一步都立即满足条件：```
1*10 = 10
```每个程序员之后组成一个团队，产生4个团队。 贪婪策略自然会发现单例团队是最优的。 

最后，考虑：```
1
4 11
1 3 3 7
```排序顺序：```
7 3 3 1
```扫描产生：```
1*7 = 7
2*3 = 6
3*3 = 9
4*1 = 4
```没有支票达到 11，因此不会组建团队。 即使在使用了所有可用的程序员之后，算法也会正确返回 0。
