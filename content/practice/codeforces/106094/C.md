 ## 解决方案
 ## 问题理解

 我们得到了一组数字，每个数字代表糖果的“风味得分”。 任务是使用固定规则将这些数字重复组合成更大的值：我们选择两个可用的数字，将它们合并成一个等于它们总和的新数字，然后重复直到只剩下一个数字。 最终剩余的数字是整个过程的总“yum值”，我们要选择合并的顺序，使这个最终值尽可能小。 

尽管操作总是将数字加在一起，但关键的问题是中间选择会影响未来的合并，从而改变流程的总成本结构。 我们并不是简单地对所有内容进行一次求和，因为重复加法的结构实际上会根据合并的时间对某些数字进行更重要的加权。 

输入代表多个测试用例。 每个测试用例都是一个整数列表，对于每个列表，我们必须使用允许的操作重复合并元素后确定最小可能的最终结果。 

这些约束（对于 Codeforces 健身房中此类问题的典型情况）表明，每次测试的元素数量可能足够大，以至于不可能对所有可能的合并顺序进行 O(n²) 模拟。 任何尝试所有对或所有合并序列的方法都会发生组合爆炸，因为合并树的数量呈超指数增长。 

当所有值都相等时，会出现微妙的边缘情况。 简单的方法可能会假设任何合并顺序都是等效的，因为加法是结合性和交换性的。 对于成本累积过程来说，情况并非如此。 例如，用数字`[1, 1, 1]`, 合并`(1,1)`第一产量`2`，然后与合并`1`产量`3`。 但是不同的合并顺序仍然会给出相同的结果，这可能会误导人们认为顺序无关紧要。 该错误在混合输入中变得明显，例如`[1, 2, 9]`，其中贪婪配对会改变中间权重，从而改变贡献。 

另一个边缘情况是单元素输入。 和`[x]`，没有执行合并，所以答案一定是`x`。 任何假设至少一个合并步骤的实现都会错误地修改该值。 

## 方法

 暴力的观点是将其视为探索数组上所有可能的二叉合并树。 每个内部节点代表合并两个子节点，其值有助于进一步合并。 如果我们模拟所有可能的配对顺序，我们就可以有效地枚举 n 个叶子上的所有完整二叉树并计算诱导成本。 

这在原则上是正确的，因为它尊重操作的确切规则。 然而，将 n 个元素配对的方式数量与加泰罗尼亚语数量成正比，大致增长为$O(4^n / n^{3/2})$。 即使对于 n = 30，这也已经是不可行的，并且典型的约束要大得多。 

关键的观察结果是，这个过程在结构上与重复组合权重相同，其中每次合并都会增加合并对的总成本。 这就是经典的“最佳合并”结构。 最终总成本可以看作是早期合并影响后来合并的贡献之和，最小化最终值相当于最小化累积中间成本。 

贪婪策略源于对局部最优性的关注：在每一步，组合两个最小的可用值会产生所有未来计算的最小立即增加。 如果较早合并较大的值，则会在后续步骤中重复添加该值，从而不必要地夸大最终结果。 

这将问题简化为始终提取两个最小的数字，合并它们，并将结果推回池中。 最小堆有效地维护当前的多重集并确保我们始终选择最佳对。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 详尽的合并树搜索 | 指数| O(n) 递归堆栈 | 太慢了 |
 | 最小堆贪婪合并| O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 我们独立处理每个测试用例。 

1. 将所有数字插入到最小堆中，以便我们可以有效地检索最小元素。 使用堆的原因是每一步都需要在动态变化的集合中选择两个最小值。 
2. 当堆中剩余多个元素时，提取两个最小值。 这些代表了成本最低的立即合并选择。 
3. 计算它们的总和并将其添加到运行总计中。 该总和代表新的合并值以及执行此合并所产生的增量成本。 
4. 将合并后的值推回到堆中，因为它参与将来的合并。 此步骤维护可用号码的正确状态。 
5. 重复直到剩下一个值，此时所有贡献都已累积。 

最终的累计总数就是测试用例的答案。 

### 为什么它有效

 在任何时候，选择两个较大的元素而不是最小的可能对都会导致更大的值向上传播到未来的合并中。 由于堆中保留的每个元素最终都会被多次合并，因此尽早引入大值会反复放大其贡献。 不变的是，在每个合并步骤之后，堆包含未解析值的正确多重集，并且贪婪选择最小化该步骤的增量成本而不损害未来的最优性。 因为每次合并都会将其总和恰好添加到总成本中一次，并且因为延迟大值只会增加它们对未来总和的重复参与，所以贪婪的选择仍然是全局最优的。 

## Python 解决方案```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        arr = list(map(int, input().split()))
        
        if n == 1:
            print(arr[0])
            continue
        
        heapq.heapify(arr)
        total = 0
        
        while len(arr) > 1:
            a = heapq.heappop(arr)
            b = heapq.heappop(arr)
            s = a + b
            total += s
            heapq.heappush(arr, s)
        
        print(total)

if __name__ == "__main__":
    solve()
```堆初始化确保我们总是可以在对数时间内访问最小的元素。 循环结构直接反映了贪婪算法：每次迭代都会将问题大小减少一个元素，同时考虑合并成本。 

n = 1 的特殊情况可防止在无法进行操作时错误地添加任何合并成本。 

一个常见的实现陷阱是忘记将合并总和累积到答案中，而只跟踪最终的堆元素。 这会错误地计算总数，因为定义目标的是中间合并成本，而不仅仅是最终的剩余价值。 

## 工作示例

 考虑输入`[1, 2, 3]`。 

我们从堆开始`[1, 2, 3]`。 

| 步骤| 堆状态 | 已选对 | 合并结果 | 总成本|
 | ---| ---| ---| ---| ---|
 | 1 | [1,2,3]| (1, 2) | 3 | 3 |
 | 2 | [3, 3] | (3, 3) | 6 | 9 |

 最终答案是9。 

这表明，首先合并最小的元素可以防止在后续步骤中重复添加大量元素。 

现在考虑`[4, 1, 1, 1]`。 

| 步骤| 堆状态 | 已选对 | 合并结果 | 总成本|
 | ---| ---| ---| ---| ---|
 | 1 | [1, 1, 1, 4] | (1, 1) | 2 | 2 |
 | 2 | [1,2,4]| (1, 2) | 3 | 5 |
 | 3 | [3, 4] | (3, 4) | 7 | 12 | 12

 该迹线显示了如何延迟大值`4`避免增加早期合并成本。 如果`4`如果提前合并，它会被添加到后续的多个总和中，从而增加最终的结果。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | 每次测试 O(n log n) | 每次 n-1 次合并都会执行两次堆弹出和一次推送 |
 | 空间| O(n) | 堆存储处理过程中的所有元素 |

 该问题类的典型约束允许测试用例中的总元素数最多为 2×10⁵ 左右，并且由于高效的堆操作，n log n 方法可以轻松地满足时间限制。

import sys, io
import heapq

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        arr = list(map(int, input().split()))
        if n == 1:
            out.append(str(arr[0]))
            continue
        heapq.heapify(arr)
        total = 0
        while len(arr) > 1:
            a = heapq.heappop(arr)
            b = heapq.heappop(arr)
            s = a + b
            total += s
            heapq.heappush(arr, s)
        out.append(str(total))
    return "\n".join(out)

 ## 边缘情况

 对于像这样的单元素输入`[7]`，堆从一开始就只包含一个值。 整个循环被跳过，算法直接输出 7，与没有执行合并的事实相匹配。 

对于像这样严重倾斜的输入`[100, 1, 1]`，堆开始于`[1, 1, 100]`。 第一次合并是`(1, 1)`生产`2`， 然后`(2, 100)`生产`102`，累计成本为`2 + 102 = 104`。 该算法自然会延迟大值，防止其参与多个早期合并，并确认大值应尽可能晚地合并的贪婪不变量。
