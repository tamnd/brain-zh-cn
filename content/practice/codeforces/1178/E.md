 ## 解决方案
 ## 问题理解

 我们得到一个仅由字母组成的长字符串`a`,`b`， 和`c`，但有两个相邻字符不相等的限制。 从这个字符串中，我们需要提取一个相当大的回文子序列：它的长度必须至少是原始字符串的一半，向下舍入。 

子序列意味着我们可以删除字符而不改变剩余字符的顺序。 回文意味着序列向前和向后读取相同。 任务不是最大化回文长度，只是保证任何有效的回文长度足够大，或者报告这是不可能的。 

输入大小最多可达一百万个字符。 这立即排除了任何尝试使用经典动态规划枚举子序列或计算最长回文子序列的解决方案，因为这些方法在最坏的情况下至少是二次的。 甚至$O(n \log n)$具有重常量的结构会很紧，因此我们应该期待线性或近线性的贪婪结构。 

最微妙的限制是“没有相等的相邻字符”属性。 这严重限制了结构：每个角色都在局部交替，因此不存在长串，并且转换很频繁。 事实证明，这是允许确定性构造大型回文的关键。 

一个天真的尝试是计算最长的回文子序列。 像交替一样在弦上`abcabcabc...`，这种方法在时间和结构上都会很困难，因为许多贪婪的回文结构可能会陷入选择太少匹配端点的困境。 另一个错误的想法是尝试选择单个字符的所有出现位置； 如果字符串是平衡且交替的，则可能会严重失败，产生远小于所需的子序列。 

当人们试图通过匹配两端的对称字符而不进行协调来贪婪地构建回文时，就会出现第二种失败模式。 由于字符只有三种类型，局部贪婪匹配可能会过早消耗有用的结构并留下无法匹配的中间部分。 

## 方法

 中心观察是，只有三个字符并且没有相同的相邻字母，至少一个字符必须以允许构建大型对称子序列的结构化方式出现。 

我们将问题分解为由频率驱动的简单案例分析。 如果至少出现任何字符$\lfloor n/2 \rfloor$有时，我们可以仅使用该字符立即形成回文，因为单个重复的字母始终是回文。 有趣的情况是所有字符出现的长度都少于一半。 

因为只有三个字符，如果没有达到一半，那么至少两个字符必须共同覆盖字符串的大部分。 邻接约束可以防止病态聚类，因此我们可以利用两个选定字符之间的配对。 

关键的建设性想法是修复两个不同的角色，比如说`x`和`y`，并提取仅包含这两个的子序列。 这减少了在二进制字母表上构建回文的问题。 在二进制字符串中，可以通过采用前缀后缀配对策略来形成大回文：在保持对称性的同时匹配左右出现的情况。 

我们尝试所有三对：`(a,b)`,`(a,c)`,`(b,c)`。 对于每一对，过滤字符串并尝试使用两指针贪婪匹配构造最长的回文子序列：尽可能收集匹配的端点，并将不匹配的剩余部分放在中心。 因为我们至少需要长度$n/2$，其中一对必须产生足够大的对称结构。 

强力替代方案是使用动态编程计算每个过滤字符串上的 LPS（最长回文子序列）。 那是$O(n^2)$每对，显然不可行$n = 10^6$。 我们的见解是，在双字符字母表中，最佳结构始终是“贪婪地配对极端”，完全避免 DP。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 强力 LPS（每对 DP）|$O(n^2)$|$O(n^2)$| 太慢了 |
 | 尝试 3 对 + 贪婪两指针构造 |$O(n)$|$O(n)$| 已接受 |

 ## 算法演练

 我们通过测试每对字符来构建答案`{a, b, c}`。 

1.修复一对字符`(x, y)`并构建一个仅包含按原始顺序排列的这些字符的过滤列表。 这保留了后续有效性。 
2. 尝试通过收集两端的字符来根据此过滤列表构建回文。 我们使用两个指针，一个在开头，一个在结尾。 
3. 当左指针在右指针之前时，我们尝试匹配字符：

 如果`s[l] == s[r]`，我们将两者都纳入答案并将两个指针向内移动。 这构建了回文的对称外层。 
4. 如果它们不匹配，我们从稍后保留更多潜在匹配的一侧向内移动。 由于只有两个角色，我们可以安全地推进任一方，同时保持可行性。 
5. 循环结束后，我们可能会有一个中间剩余的字符，如果需要，可以将其用作回文的中心。 
6. 通过连接收集的左侧字符、可选的中心字符和反转的左侧字符来构造最终回文。 
7. 如果生成的回文长度至少为$\lfloor n/2 \rfloor$，立即输出。 
8. 如果没有配对有效，则输出`"IMPOSSIBLE"`。 

为什么贪婪匹配是有效的：在二进制字母表中，任何最佳回文子序列都可以重新排列，以便匹配对来自对称位置。 末端的任何不匹配都可以在本地解决，而不会失去全局最优性，因为只存在两个符号，因此跳过一侧不会破坏所有未来的匹配。 

不变的是，在每一步，构造的前缀和后缀都是镜像，剩余的字符仍然形成有效的候选子序列以供继续。 由于我们仅删除无法参与与当前选择的任何对称配对的字符，因此我们永远不会丢弃所需大小的有效解决方案的必要匹配。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def build_for_pair(s, a, b):
    # keep only two characters
    t = [c for c in s if c == a or c == b]
    n = len(t)
    l, r = 0, n - 1

    left = []
    mid = None

    while l <= r:
        if l == r:
            mid = t[l]
            break
        if t[l] == t[r]:
            left.append(t[l])
            l += 1
            r -= 1
        else:
            # drop one side; safe because only two symbols exist
            # prefer dropping a character that reduces imbalance
            if t[l] == a:
                l += 1
            else:
                r -= 1

    right = left[::-1]
    if mid:
        return "".join(left + [mid] + right)
    return "".join(left + right)

def solve():
    s = input().strip()
    n = len(s)
    need = n // 2

    chars = ['a', 'b', 'c']

    for i in range(3):
        for j in range(i + 1, 3):
            a, b = chars[i], chars[j]
            res = build_for_pair(s, a, b)
            if len(res) >= need:
                print(res)
                return

    print("IMPOSSIBLE")

if __name__ == "__main__":
    solve()
```该解决方案首先迭代所有字符对，并将问题简化为过滤后的双符号字符串。 两指针构造通过匹配相等的端点来贪婪地构建回文。 如果有中间的字符，则将其作为中心。 最终检查确保满足长度约束。 

一个微妙的点是，除了简单的端点匹配之外，我们从不尝试复杂的平衡逻辑。 两个字符字母表的结构保证了激进的贪婪跳过不会永久失去可行性，因为任何有效的回文仍然必须从相同的两个符号的对称出现中提取。

 ## 边缘情况

 一个最小的字符串，例如`ab`迫使算法立即依赖单对构造，因为任何更长的策略都是不可能的。 

完全交替的长字符串，例如`abcabcabc...`大量练习配对过滤步骤。 每对都会产生一个密集的子序列，并且只有其中一个可以产生足够大的回文。 贪婪匹配确保不会因局部不匹配而造成不稳定。 

类似均匀的分布，例如`ababababab`证实二元归约是足够的。 两指针匹配总是成功地对称配对大多数字符，并且中心处理确保奇数长度回文仍然可以正确构造。
