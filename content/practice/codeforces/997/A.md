 ## 解决方案
 ## 问题理解

 给定一个二进制字符串，我们希望将其转换为全为 1 的字符串。 有两种类型的操作可用：我们可以反转任何连续段以获取成本，或者我们可以翻转连续段中的所有位以获取成本。 这两种操作都可以重复应用在重叠的段上。 

关键的困难在于翻转会改变值，而反转只会改变位置。 我们不要求输出操作序列，只要求输出消除所有零所需的最小成本。 

约束条件较大，字符串长度可达300000，运算成本可达10^9。 这立即排除了任何尝试模拟操作序列或显式探索段选择的解决方案。 任何对所有段分区进行推理或尝试的方法都会太慢。 

当字符串已经全部为 1 时，会出现微妙的边缘情况。 答案是零，任何算法都必须在不应用任何操作的情况下检测到这一点。 另一个边缘情况是，当零以翻转单个字符的方式隔离时，与翻转较大的段相比，翻转单个字符是最佳的，这可能会误导试图最小化段计数而不是成本的贪婪实现。 

## 方法

 天真的观点是直接编辑字符串来思考：我们尝试通过选择某种将其变成一的操作来修复每个零。 由于翻转会影响范围并且反转会重新排列结构，因此人们可能会尝试模拟操作序列或贪婪地从左到右消除零。 这很快就变得不可行，因为每个操作都可以更改字符串的大部分，并且可能的段选择数量是二次的。 

关键的观察结果是反转不会改变字符的多重集，只会改变它们的顺序。 由于最终目标是统一的字符串，因此顺序根本不重要。 任何反转只能通过重新排列零来帮助，使翻转变得更有效，但它不能减少必须翻转的零的总数。 

这意味着真正的问题归结为决定如何将零分组为我们翻转的段。 每个翻转操作都会反转一个连续的段，应用两次会抵消，因此每个段要么翻转奇数次，要么根本不翻转。 结果是我们选择并集覆盖全零的段，同时最小化成本。 在最优策略中可以忽略逆转，因为一旦我们根据连续零块操作进行推理，它们就不会改变可行性或最优成本结构。 

因此，问题变成了零段上的成本最小化：每个最大的零块都可以独立处理，并且在每个块内，我们根据分割是否会降低成本来决定是翻转整个块一次还是翻转较小的子段。 

在零块内，翻转整个块的成本为 y，而翻转每个零的每个位置的成本为 y，因此分割永远没有用，除非我们可以通过相邻操作之间的交互来降低成本。 唯一有意义的比较是单独处理块之间的转换或通过隐式反转结构合并它们是否更便宜，这有效地减少了对零段的计数并在成本模型下组合相邻的段，其中合并以反转为代价减少了操作数。 

这导致了一个经典的结构：我们对连续相等字符的段进行计数，并根据零段之间的转换计算成本，决定是为每个段支付 y 还是使用 x 来合并相邻段。

 ## 算法演练

 我们首先将字符串压缩为连续的相等字符。 这很有用，因为这两种操作都不会从在统一区域内工作中受益。 所有有意义的结构都发生在 0 和 1 块之间的边界处。 

接下来，我们计算存在多少个连续的零块。 每个这样的块代表一个必须通过翻转来固定的区域，并且最初我们可以假设如果独立处理，每个块的成本为 y。 

然后我们观察由单个一块分隔的相邻零块之间的相互作用。 如果两个零块很接近，我们也许能够使用消除分离结构的反转来合并它们的处理，有效地将翻转操作的数量减少 1，同时支付成本 x。 这就在支付额外的翻转费用或支付合并费用之间进行了权衡。 

所以我们计算零段的数量k。 基线成本为 k * y。 然后我们尝试通过合并相邻的零段来降低此成本。 每次合并都会将段数减少 1 并花费 x，因此仅当 x < y 时每次合并才有利。 如果 x >= y，合并就没有意义，我们只需独立翻转每个段。 

因此，我们最多减去 k - 1 次合并，当 x < y 时，每次合并都会节省 y - x 的费用。 

最后，我们还处理字符串没有零的情况，立即返回零。 

### 为什么它有效

 不变的是，在压缩成游程之后，除了使用反转跨单块合并的可能性之外，每个零段都是独立的。 反转不能创建新的零结构或减少零段的数量，除非将相邻段合并为一个更大的段。 翻转是唯一真正将零变为一的操作，因此每个零段必须至少支付一次。 该算法精确地探索了唯一有意义的自由度，即在支付翻转之前是否合并相邻片段，并确保没有其他操作序列可以产生更低的成本。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, x, y = map(int, input().split())
    s = input().strip()

    if '0' not in s:
        print(0)
        return

    zero_segments = 0
    i = 0

    while i < n:
        if s[i] == '0':
            zero_segments += 1
            while i < n and s[i] == '0':
                i += 1
        else:
            i += 1

    cost = zero_segments * y

    # merging adjacent zero segments via reversal costs x per merge
    # we can do at most zero_segments - 1 merges
    cost += max(0, (zero_segments - 1)) * min(0, x - y)

    print(cost)

if __name__ == "__main__":
    solve()
```该实现在一次传递中压缩字符串，计算最大零块。 这避免了对额外内存或预处理结构的需要。 计算段数后直接应用成本公式。 

微妙的部分是确保仅当 x < y 时合并才被认为是有益的，否则表达式不应降低成本。 乘法结构编码每次合并用合并成本 x 替换一次翻转成本 y。 

## 工作示例

 ### 示例 1

 输入：```
5 1 10
01000
```零段为：“0”、“000”，因此 k = 2。 

| 步骤| 零段| 到目前为止的成本| 行动|
 | --- | --- | --- | --- |
 | 扫描| 2 | 20 | 基线 k*y |
 | 合并检查| 2 | 20 | x > y 所以没有合并 |

 在分段模型下，最终答案为 20，但实际最佳答案包括通过反转结构进行交互，得出 11。 

这表明仅分段推理捕获了结构，但没有利用完全逆转交互，这凸显了单独合并是不够的。 

### 示例 2

 输入：```
5 1 10
01000
```应用相同的分段，具有两个零块。 

| 步骤| 零段| 成本| 行动|
 | --- | --- | --- | --- |
 | 扫描| 2 | 20 | 计算 k |
 | 合并| 2 | 11 | 11 最佳序列使用反向+翻转 |

 这表明反转可以重新定位零，从而使单个翻转操作变得比独立处理更有效。

 ## 边缘情况

 对于包含零的单字符字符串，该算法精确计算一个零段并返回 y，因为不可能进行合并。 对于完全统一的单字符串，它在扫描之前立即返回零，避免不必要的计算。 

对于像 010101 这样的交替模式，每个零都形成自己的段。 该算法对多个段进行计数，并根据段计数正确应用成本结构，反映最坏的碎片情况。 

对于 1 内的单个连续零块，例如 11000111，该算法准确地识别一个零段并返回 y，因为没有反转可以减少对至少一次翻转操作的需要。
