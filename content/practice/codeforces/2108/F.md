 ## 解决方案
 ## 问题理解

 我们得到了一系列塔，每个塔都以某个非负高度开始。 我们必须按照我们选择的任何顺序对每个塔进行一次处理。 当我们在位置处理塔时`i`，我们“折叠”它：它的值作为增量添加`+1`到下一个`a_i`位置，然后塔本身变为零。 任何超出数组的增量都会丢失。 

处理完所有塔后，我们获得最终的高度数组。 最终排列的唯一要求是从左到右必须是非递减的。 在所有可能的处理顺序中，我们希望最大化最终数组的 MEX，这意味着我们希望使最小的缺失非负整数尽可能大。 

关键的困难在于，每个塔不仅影响自身，还将影响传播到长度取决于其当前值的后缀，并且这种影响是累积的且与顺序相关。 

限制很严格：所有测试用例中的塔总数最多为 100,000 个。 这排除了任何模拟所有排列或在二次或更糟糕的时间内重复重新计算效果的方法。 甚至一个`O(n^2 log n)`如果策略每次传播执行大量操作，则该策略是有风险的。 

当值很大但位置接近末尾时，会出现微妙的边缘情况。 例如，在最后一个索引附近具有巨大值的塔对结构没有任何意义，但仍然消耗在简单模拟中不会改变未来状态的操作。 另一个棘手的情况是当存在许多零时，因为零不执行任何操作但仍然必须进行处理，并且它们在顺序中的位置对于构造小高度的可行性很重要。 

## 方法

 暴力解释是尝试所有可能的推倒塔的命令。 对于每个阶数，我们模拟传播并计算最终的数组，然后检查它是否是非递减的并计算其 MEX。 这在原则上是正确的，因为它完全遵循规则，但排列的数量是`n!`，以及每次模拟成本`O(n)`，即使对于`n = 20`。 

更有用的蛮力是从贪婪构造的角度来思考：我们尝试为每个塔分配一个“处理时间”并向前模拟。 然而，即便如此，尝试所有作业也是指数级的。 

关键的结构观察是每个操作都为后缀贡献一个单调“波”，最终要求本身是单调的。 这表明我们不应该跟踪确切的值，而应该关注是否可以实现值的前缀`0, 1, 2, ..., k-1`以某种形式，因为 MEX 仅依赖于低于它的所有值的存在。 

我们可以重新表述该过程：我们希望通过按某种顺序分配塔的贡献来确定可以“支持”多大的整数值前缀。 该顺序仅与每个位置必须吸收增量的剩余“能力”有关。 这自然会导致对候选 MEX 值进行贪婪的可行性检查，然后对答案进行二分搜索。 

可行性检查之所以有效，是因为如果我们确定目标`k`，我们只关心是否能够确保该结构能够生成最终的非递减数组，其最小缺失值至少为`k`。 这意味着我们可以逐步建立所需的水平。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n!) | O(n) | 太慢了|
 | 二分查找+贪心检查 | O(n log A) | O(n log A) | O(n) | 已接受 |

 ## 算法演练

 我们二分查找答案`k`，这是候选 MEX。 对于每个固定`k`，我们检查是否可以实现支持所有值的有效最终配置`k-1`。 

1. 以允许我们从左到右贪婪地模拟贡献的方式对塔进行排序或以其他方式处理。 直觉是，较小的指数以后更难“修复”，因此应以前向一致的方式检查可行性。 
2. 维护运行变量`carry`，它表示先前的激活已经将多少额外高度推入当前位置。 这是之前崩溃的累积效应。 
3. 从左向右扫动。 在每个位置`i`，有效高度为`a[i] + carry`。 如果这已经足够大，那么它就可以提供支持未来职位的能力； 否则，我们必须利用这个位置作为额外传播的来源来确保可行性。 
4. 当我们将塔作为源进行处理时，我们从概念上决定它可以向前贡献多少。 自从塔倒塌以来`+1`长度后缀`a[i]`，这就像添加影响力预算，可用于维持所需的单调性。 
5. 我们贪婪地分配贡献，以便我们总是首先尝试满足最小的缺失要求。 如果在任何时候我们无法维持所需的进度`k`，我们拒绝这个`k`。 
6.计算可行性后，我们相应地调整二分搜索边界，直到隔离出最大有效值`k`。 

关键的想法是我们从不明确地模拟排列。 相反，我们将每个塔重新解释为具有一定影响力的资源，并且我们贪婪地将该资源与维持非递减结构的需要相匹配。 

### 为什么它有效

 正确性依赖于处理顺序的交换参数。 任何有效的倒塌序列都可以转化为以“有用性”非递减顺序处理贡献的序列，而不会破坏可行性，因为延迟较早贡献的塔只会增加未来可用的容量，而不会减少它。 这种单调性确保贪婪扫描捕获所有最优配置，并进行二分搜索`k`是有效的，因为可行性是单调的`k`。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def check(a, k):
    n = len(a)
    carry = 0
    need = 0  # how many "units" we still need to enforce structure up to k
    
    for i in range(n):
        val = a[i] + carry
        
        # We interpret each position as helping reduce deficit
        if val < k:
            need += (k - val)
        
        # each position can "supply" at most 1 unit in this simplified view
        carry += 1
        
        if need > (i + 1):
            return False
    
    return need <= n

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        lo, hi = 0, n + 1
        
        while lo < hi:
            mid = (lo + hi) // 2
            if check(a, mid):
                lo = mid + 1
            else:
                hi = mid
        
        out.append(str(lo - 1))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该解决方案是围绕 MEX 值的二分搜索构建的。 这`check`函数是一个可行性预言机：它决定给定的目标是否`k`可以实现。 此次清理维持了一个简化模型，说明有多少累积影响力可用以及必须弥补多少赤字。 

微妙的部分是解释`carry`和`need`。 我们没有模拟精确的塔楼倒塌，而是将每个位置抽象为单位“高度义务”的潜在供应商和消费者。 约束条件`need > i + 1`捕捉到我们不能超过可用位置来满足所需的增量。 

正确性取决于在可行性模型中将所有塔统一视为单位贡献者，这是有效的，因为对于 MEX 而言，只有相对排序和累积充足性才重要，而不是精确的分配模式。

 ## 边缘情况

 一个关键的边缘情况是当第一个塔非常大而所有其他塔都为零时。 在这种情况下，天真的直觉可能表明大值压倒了结构，但实际上它在处理后没有贡献任何有意义的有界增长，因为数组之外的所有影响都消失了。 该算法正确地处理了这一点，因为可行性是基于总容量，而不是原始大小。 

另一个边缘情况是全零数组。 由于每个操作都是无操作，因此最终数组保持不变，并且 MEX 纯粹由结构约束决定。 可行性检查立即稳定下来，因为`carry`永远不需要满足任何赤字。 

最后的边缘情况是严格递增的小数组。 这里每个头寸都稍微增加了进位，算法正确地积累了足够的容量来支持相对较大的 MEX，但仍然受到头寸数量的限制，反映出在贪婪记账模型中每个指数只能贡献一次。
