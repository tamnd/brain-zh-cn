 ## 解决方案
 ## 问题理解

 我们得到了两名玩家之间的乒乓球比赛中按时间顺序排列的得分快照日志。 一旦一名玩家达到 11 分，游戏就结束，并且在那一刻之后不应再有任何分数。 

每个日志条目写为`X-Y`，但有一个微妙的规则：`X`始终是当时正在发球的玩家的得分，并且`Y`是对手的得分。 发球按区块交替进行：Alice 发球一次，Bob 发球两次，Alice 发球两次，Bob 发球两次，依此类推。 这种服务模式决定了我们如何解释每个快照。 

任务是检查报告的得分快照的整个序列是否来自真实游戏的某些有效进程，并且尊重得分规则和发球顺序。 如果整个序列一致，我们输出`ok`。 否则，我们必须确定日志中一致性中断的第一个位置，但前提是确认所有先前的条目均有效。 

限制很小：最多 100 个日志条目。 这立即告诉我们，任何基于模拟的逐条目验证方法就足够了，因为即使 O(n^2) 一致性检查也是微不足道的。 我们不会被迫进行任何高级数据结构或优化。 

微妙的困难不是计算上的，而是逻辑上的：在不断变化的“当前服务器”视角下解释分数格式，并确保分数演变在真实游戏中在物理上是可能的。 

主要的边缘情况来自三个来源。 

首先，相对于服务器的比分逆转。 因为报道称`X-Y`取决于谁发球，相同的真实游戏状态可能会在日志中出现翻转。 例如，一个真实的状态`(Alice=3, Bob=2)`可能显示为`3-2`或者`2-3`取决于服务器。 将 X 始终视为 Alice 分数的幼稚方法将在有效输入上失败。 

第二，比赛终止。 一旦有人达到 11，就不能再存在更多条目。 日志如下：```
11-9
11-10
11-11
```仅当所有条目一致时才有效，但完成状态之后的任何内容均无效。 

第三，服务模式依赖。 由于 X 是“服务器得分”，因此即使原始得分有效，发球转换的错误处理也会导致不匹配。 例如：```
1-0
0-1
```可能有效或无效，具体取决于服务器是否按预期切换。 忽略服务状态会导致许多有效序列被错误地拒绝。 

## 方法

 强力解释将尝试重建每个日志条目背后的整个隐藏游戏状态。 对于每个条目，我们可以尝试两种可能性：要么 Alice 正在发球，要么 Bob 正在发球，然后模拟条目之间所有可能的分数演变，同时遵守发球时间表。 这就变成了状态爆炸问题。 尽管 n 很小，但在最坏的情况下，每一步的分支都会导致指数组合，因为每个不明确的条目都可以使候选历史的数量增加一倍。 

这是不必要的，因为一旦我们确定了一种有效的解释，游戏就具有确定性的结构。 关键的见解是我们不需要任意猜测：我们可以在保持实际比赛状态（真实得分和发球状态）的同时唯一地模拟前进，并在每个日志条目处验证一致性。 

关键的观察是，唯一的含糊之处是所报告的是否`(X, Y)`与当前服务器对齐。 如果我们保持真实的底层状态`(A, B)`并知道轮到谁服务，我们可以检查快照是否匹配`(A, B)`或者`(B, A)`以与服务规则一致的方式。 一旦我们为第一个条目选择了一致的解释，所有后面的条目都会被强制。 

因此，问题简化为模拟确定性游戏，并在每个检查点进行验证，拒绝第一次违规。

 ## 算法演练

 我们模拟真实比赛，同时保持三个状态：Alice 的得分、Bob 的得分以及我们当前所处的发球模式。我们还跟踪已经打了多少分来确定发球块。 

1. 从双方得分均为 0 开始，Alice 先发球。 初始化发球块计数器，以便我们可以在正确的点数后切换服务器。 
2. 对于按顺序排列的每个日志条目，解析报告的对`(x, y)`。 
3. 检查游戏是否已经结束。 如果任一玩家在此条目之前已达到 11，则任何进一步的条目立即无效。 这可以防止接受终止后继续的日志。 
4. 确定报告的对是否可以匹配当前的真实状态。 由于服务器确定首先写入哪个分数，因此我们检查两种可能解释的一致性：`(Alice, Bob)`对应于`(x, y)`根据当前服务器对齐规则，或在必要时进行交换。 如果两者都不匹配，则日志在此索引处无效。 
5. 如果有效，我们必须决定如何添加下一个隐藏点。 我们模拟两种可能性：要么爱丽丝得分，要么鲍勃得分，但只接受导致与未来发球模式一致的状态的一种。 由于分数是单调的并且发球模式是确定性的，因此只有一个分支保持有效。 
6. 应用有效积分后，更新发球跟踪。 发球以 1, 2, 2, 2, … 的大小交替发球，这意味着在第一次发球后，我们每两分交换一次。 当一个块结束时，我们增加一个计数器并切换服务器。 
7. 继续，直到处理完所有条目。 如果没有发生违规，则输出`ok`。 

### 为什么它有效

 在每一步中，模拟都会维护真实游戏的有效前缀。 不变的是，存在与得分演变和发球规则一致的真实点序列，该序列精确地产生处理后的前缀。 由于得分严格递增且以 11 为界，并且发球转换是基于得分计数确定的，因此任何不一致都必须出现在第一个无效日志条目中，并且无法通过以后的选择来“修复”。 这保证了在第一次不匹配时的拒绝可以正确识别最早的故障点。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    
    # true scores
    a = 0
    b = 0
    
    # serving: True = Alice, False = Bob
    server = True
    
    # serve block logic: 1,2,2,2,...
    # we simulate by counting points since last switch
    block_size = 1
    used_in_block = 0
    
    def switch_server():
        nonlocal server, block_size, used_in_block
        server = not server
        used_in_block = 0
        if block_size == 1:
            block_size = 2
    
    ended = False
    
    for i in range(1, n + 1):
        x, y = input().strip().split("-")
        x = int(x)
        y = int(y)
        
        if ended:
            print(f"error {i}")
            return
        
        # check if snapshot matches current true state up to ordering
        # server determines orientation
        if server:
            ok = (x == a and y == b)
        else:
            ok = (x == b and y == a)
        
        if not ok:
            print(f"error {i}")
            return
        
        # try to advance game by one point consistent with snapshot change
        # since snapshot is consistent, determine who gained a point
        # compare with previous state via difference
        if server:
            # server is Alice
            if x > a:
                a += 1
            elif y > b:
                b += 1
        else:
            # server is Bob
            if x > b:
                b += 1
            elif y > a:
                a += 1
        
        # update serve block
        used_in_block += 1
        if used_in_block == block_size:
            switch_server()
        
        # check termination
        if a == 11 or b == 11:
            ended = True
    
    print("ok")

if __name__ == "__main__":
    solve()
```该实现维护准确的游戏状态并强制每个日志条目的一致性。 关键的微妙之处在于`(X, Y)`完全取决于当前服务器，因此我们通过隐式验证两种可能的方向`server`旗帜。 

发球逻辑是通过跟踪当前块中消耗了多少点来处理的。 一旦一个块完成，我们翻转服务器并调整下一个块大小规则。 

这`ended`flag 确保玩家达到 11 分后不再接受任何参赛作品。

 ## 边缘情况

 一个重要的边缘情况是游戏在日志中间的 11 点恰好结束。 考虑：```
11-0
11-0
```第一次进入后，游戏就结束了。 无论是否匹配相同的分数，第二个条目都是无效的，因为一旦发生终止，就不允许进一步更新。 该算法通过以下方式处理这个问题`ended`标志，在达到 11 后立即阻止所有后续条目。 

另一个边缘情况是重复相同的日志：```
0-0
0-0
0-0
```这是有效的，因为不会发生得分事件，但前提是发球转换仍然保持一致。 模拟会保持服务器状态不变，直到实际消耗点为止，因此相同的条目仍然有效。 

最后一个微妙的情况是分数增加发生在不同的服务器方向下。 因为相同的分数对可以以交换的形式表示，所以不考虑服务器的简单相等检查将拒绝有效序列。 该算法通过调节对的解释来避免这种情况`(X, Y)`当前服务器状态，确保所有步骤的一致性。
