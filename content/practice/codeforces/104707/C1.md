 ## 解决方案
 ## 问题理解

 Nadja 网站的每个访问者的行为就像时间线上的周期性事件。 游客$i$首次出现于当天$a_i$，之后继续出现$b_i$没有尽头的日子。 因此，每个访问者都会生成无限的访问天数序列：$a_i, a_i + b_i, a_i + 2b_i, \dots$。 当同一天出现多个访问者时，将按照其索引的升序处理访问。 

我们并没有被要求整天进行模拟。 相反，我们在概念上合并$n$无限算术级数并找出哪个访问者产生$k$- 合并序列中的第一个元素。 

这些限制使得随着时间的推移进行强力模拟是不可能的。 访客数量可以达到 100 万，而日值限制为 1000。周期限制也是 1000，这是关键的结构约束。 这意味着虽然时间线是无限的，但每个访问者的行为都会以小周期重复，并且许多访问者共享相似的时间表。 

一种简单的方法是每天进行模拟，维护下次访问的优先级队列。 但最早的有趣时刻已经是有问题的了。 如果所有访客出发早、时段小，前几千天的总访问量已经可以超过$10^6$，每个模拟步骤都需要堆操作最多$10^6$条目，导致运行时不可行。 

当许多访客共享相同的时间表时，就会出现微妙的边缘情况。 例如，如果所有$a_i = 1$和所有$b_i = 1$，那么每天都有$n$访问。 第一个$k$访问只是通过重复大小的块来排序$n$。 简单的模拟可能仍会每天迭代，但正确的答案仅取决于$k \bmod n$，而不是显式模拟。 

另一个重要的边缘情况来自订购关系。 如果同一天有两个访客访问，则必须先统计指数较小的访客。 任何聚合每日访问量而不保留索引顺序的解决方案都会失败。 

## 方法

 暴力破解的想法是按时间顺序模拟该过程。 我们为每个访问者维护下一次访问日期，并重复提取最小的日期，输出相应的访问者，然后推送其下一次出现。 这是使用优先级队列的经典事件模拟。 

这种方法是正确的，因为它与流程的定义完全匹配：在每一步中，我们都会选择尚未处理的最早的访问。 然而，其成本由处理的事件数量决定。 如果$k$取决于$10^6$，我们执行$k$堆弹出和$k$推动，每次成本$O(\log n)$，大致导致$10^6 \log 10^6$操作，这是边界，但仍然可以通过优化的语言。 在Python中，用$n$最多$10^6$，由于内存和初始化开销，即使构建和维护这样的堆也是不可行的。 

关键的见解来自于观察到所有访问都是确定性的、周期性的、参数很小。 我们可以反转角度：对于给定的时间阈值，而不是按递增的时间顺序进行模拟$T$，我们可以统计当天发生的访问次数$T$。 每个访问者根据其级数的项数贡献一个简单的算术计数$\le T$。 这个计数是$O(n)$，并且自从$a_i, b_i \le 1000$，我们可以有效地搜索最小的$T$这样至少$k$访问发生。 

一旦我们能够有效地计算前缀访问次数，问题就变成了按时间进行二分查找。 答案是$k$-th 事件按（天，索引）排序，我们可以找到该事件发生的确切日期$k$-th 次访问发生，然后重建当天哪个访问者贡献了特定的排名事件。 

该结构变得易于处理，因为我们需要搜索的日期范围是有限的。 最大相关日不大：约后$10^6$事件，即使最小周期为 1，我们也只需要大致上升到$10^6$天。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 使用堆进行暴力模拟 |$O(k \log n)$|$O(n)$| 对于最大约束，Python 太慢 |
 | 前缀计数+按时二分查找 |$O(n \log K)$|$O(n)$| 已接受 |

 ## 算法演练

 我们将问题转化为寻找$k$- 全局排序流对中的第一个事件（天、访客索引）。 我们不是构建流，而是利用它的结构。 

1. 首先，我们定义一个函数，给定一天$T$，计算当天或之前发生的访问次数$T$。 对于每位访客$i$，我们计算级数有多少项$a_i + t b_i \le T$。 该计数为零，如果$T < a_i$，否则就是$\lfloor (T - a_i)/b_i \rfloor + 1$。 此步骤有效，因为每个访问者对事件总数都有独立的贡献。 
2.我们二分查找最小的一天$T$使得总访问次数达到$T$至少是$k$。 单调性成立是因为增加$T$只能添加更多访问，而不能删除它们。 这保证了一个明确定义的边界日，其中$k$-th 事件必须发生。 
3.一旦我们找到这一天$T$，我们严格计算之前的访问次数$T$。 这告诉我们距离一天还有多远$T$这$k$第-事件谎言。 
4. 我们迭代所有访客并收集当天访问过的访客$T$。 对于每个这样的访问者，我们将他们的索引附加到列表中。 由于我们按顺序扫描，因此该列表自然按索引排序。 
5.我们减去前一天的访问次数$T$从$k$，为我们提供当天访问中的 1 索引位置$T$。 我们从收集的列表中返回相应的访客。 

正确性来自于将全局事件序列视为独立算术级数的排序合并。 二分搜索隔离了确切的日期边界，最终扫描解决了当天内的排序问题。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = [0] * n
    b = [0] * n

    for i in range(n):
        a[i], b[i] = map(int, input().split())

    def count_up_to(t):
        total = 0
        for i in range(n):
            if t >= a[i]:
                total += (t - a[i]) // b[i] + 1
        return total

    lo, hi = 1, 10**7

    while lo < hi:
        mid = (lo + hi) // 2
        if count_up_to(mid) >= k:
            hi = mid
        else:
            lo = mid + 1

    day = lo

    before = count_up_to(day - 1)
    remaining = k - before

    on_day = []
    for i in range(n):
        if day >= a[i] and (day - a[i]) % b[i] == 0:
            on_day.append(i + 1)

    return on_day[remaining - 1]

if __name__ == "__main__":
    print(solve())
```功能`count_up_to`实现核心算术观察：每个访客贡献一个简单的楼层划分计数。 二分搜索会隔离第 k 次访问发生的确切日期。 第二遍重建当天的排序，其中模块化算术识别哪些访客是活跃的。 减法步骤确保我们正确索引当天的访客列表。 

一个常见的实施陷阱是忘记同一天的访问者必须按索引排序，这就是为什么我们按升序附加索引的原因$i$。 另一个微妙的问题是确保二分搜索上限足够大；$10^7$安全地超过任何可行的答案，因为即使在第 1 期，$10^6$访问发生在$10^6$天。

 | 测量| 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 |$O(n \log K)$| 每个二分搜索步骤都会评估所有访问者，并且搜索会运行对数天数 |
 | 空间|$O(n)$| 我们存储大小的数组$n$对于参数 |

 这些约束允许最多 100 万访问者，但每次检查都是对它们的线性传递，并且由于天数的严格限制和高效的整数运算，检查的数量对于 Python 来说足够小。

 ## 边缘情况

 一种边缘情况是所有访问者在同一天开始，时间段为 1。在这种情况下，每天都会贡献访问者指数的完整排列。 该算法通过将贡献计算为来处理这个问题$n$每天并通过二分搜索找到正确的日期边界。 在边界日，剩余索引按顺序选择正确的访问者。 

另一种情况是，一位访客比其他访客开始得晚。 例如，如果一个$a_i$很大，二分查找仍然有效，因为`count_up_to(T)`忽略该访客，直到$T$到达开始日。 该函数保持单调性，确保边界搜索的正确性。 

最后一个微妙的情况是$k$恰好落在日期之间的边界处。 减法步骤`k - count_up_to(day - 1)`确保我们正确地将答案放在最后一天内，而不是意外地将其转移到下一天。
