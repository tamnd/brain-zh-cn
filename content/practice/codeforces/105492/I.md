 ## 解决方案
 ## 问题理解

 我们得到一个由 n 个旅行日组成的固定行程，每个旅行日都发生在特定的日历日。 对于这些日子中的每一天，如果我们决定独立购买一张票，就会产生费用。 这些天已经按时间排序，并且没有两天具有相同的时间戳。 

除此之外，还有 k 种铁路通票。 每种传递类型的行为方式都略有不同寻常。 如果我们在某一天激活通行证，它会在连续 p 个日历日的固定窗口内保持活动状态。 在该窗口内，它最多可用于覆盖我们计划的旅行天数 d。 如果窗口内的旅行日数超过 d，则通票只能涵盖其中的前 d 个旅行日，同一窗口内的任何后续旅行日必须单独支付，即使通票仍然有效。 一个关键的复杂性是通行证可以自由重叠：多个通行证可以同时处于活动状态，每个旅行日可能会同时消耗多个活动通行证的使用量，即使当天最终只做出一个付款决定。 

任务是针对每个旅行日决定是支付单独的票价还是依赖一张或多张有效通行证，以便涵盖每个旅行日并将总成本降至最低。 

这些限制在结构上非常重要。 行程天数最多为 10,000，而通行证类型的数量最多为 100。每天或每个时间间隔尝试所有通行证组合的解决方案很快就会变得不可行，因为即使是超过 10,000 天的二次或三次方法也已经太大了。 然而，少量的传递类型强烈表明每个传递类型应该独立评估并通过全局动态编程结构组合，而不是显式枚举交互。 

重叠通道和“first d use”规则产生了一个微妙但重要的边缘情况。 考虑一个有效期窗口较长但 d 较小的通行证。 如果窗口期初期旅行天数密集，则通行证的配额可能会提前到期，并且在以后的日子里变得毫无用处，即使它仍然有效。 假设“一旦购买通行证，窗口内的所有日期都可以覆盖”的天真做法就会高估其有用性。 

另一种极端情况是，在某些航段中通行证的票价明显低于单独票价，但在其他航段中则有利。 由于通行证是可重复使用的并且可以多次购买，因此决策不是每种类型的单一全局选择，而是可能在不同的开始日期进行多次激活。 

## 方法

 直接强力策略将独立对待每个旅行日，并在三种可能性中做出决定：直接支付票价，或从当天开始购买某种类型的通行证，或将该天分配给已经激活的通行证。 为了使这一点正确，我们需要跟踪所有活动通行证的完整状态，包括每个通行证剩余的使用次数以及它们未来的延伸程度。 

这导致了一个状态空间，其中每一天不仅取决于前一天，还取决于所有活动通证使用的多重集。 即使我们仔细离散化，状态数量也会随着 k 和重叠通道的数量呈指数增长。 在最坏的情况下，每天都可能启动一个通行证并与所有其他通行证交互，从而导致配置的爆炸性增长，远远超出任何可行的限制。 

结构简化的关键是视角的倒转。 我们不会考虑“现在哪些通行证处于活动状态”，而是考虑“在我们做出决定后下一个未覆盖的旅行日是什么”。 每个决定要么直接支付当前旅行日的费用，要么启动一个通行证，其贡献可以建模为覆盖订购旅行列表的某些未来部分，但对其在滑动时间窗口内可以覆盖的索引数量有上限。

这使我们能够将问题重新表述为排序旅行列表中位置的最短路径。 我们定义一个 DP，其中 dp[i] 是覆盖从第 i 天开始的所有旅行日的最低成本。 从每个位置 i，我们可以通过支付第 i 天的票价直接过渡到 i+1。 对于一种通行证类型，如果我们在第 i 天激活它，我们需要确定它在其时间窗口和配额 d 内可以覆盖多少个未来旅行天数。 这给出了从 i 到某个 j 的跳跃，并且我们添加了通过成本 c。 微妙之处在于，这个 j 取决于实际日历时间，而不仅仅是索引距离，因此我们为每个 i 和每个通道类型预先计算最远可达索引 j(i, type)。 

一旦知道了这些跳转，问题就变成了 O(nk) 次转换线上的标准 DP。

 ## 算法演练

 我们按升序处理旅行天数，并将每个位置视为决策点。 

1.首先排序或者假设出行天数已经排序，并保留两个数组：日历时间t[i]和票价f[i]。 这确保我们可以使用简单的比较来推断通过有效性窗口。 
2. 定义一个 DP 数组 dp[i]，表示从索引 i 开始的行程天数的最低成本。 我们设置 dp[n] = 0，因为最后一天之后没有剩余的旅行天数。 这给出了自然的从右到左的计算顺序。 
3. 对于每个索引 i 和每个通道类型，计算如果从 i 开始，该通道可以延伸多远。 当旅行日时间在 t[i] 的 p 天之内时，我们向前扫描，并计算有多少旅行日落入此窗口，直到达到 d 使用次数。 结果端点是 j(i, type)。 此步骤将日历约束转换为基于索引的跳转。 
4. dp[i] 的递归考虑两个选择。 我们可以直接支付第 i 天的费用，成本为 f[i] + dp[i+1]。 或者，对于每种通行证类型，我们可以在第 i 天购买该通行证，支付成本 c 加上 dp[j(i, type)]。 我们在所有这些选项中选择最小值。 这编码了这样的想法：通行证会消耗旅行天数的一些后缀并向前跳过。 
5. 计算从 n−1 到 0 的 dp，以便在需要时已知所有转换。 答案是dp[0]。 

它之所以有效，是因为每个可行的策略都必须在最早的未覆盖旅行日做出第一个决定。 任何解决方案要么支付当天的费用，要么从那里开始通行证。 一旦决定确定，问题的其余部分是相同的，但转移到稍后的索引。 DP 准确地捕获了这种分解，并且 j(i, type) 的预计算正确地编码了通道的所有效果，而无需显式跟踪重叠的活动通道。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    t = []
    f = []
    for _ in range(n):
        ti, fi = map(int, input().split())
        t.append(ti)
        f.append(fi)

    passes = []
    for _ in range(k):
        p, d, c = map(int, input().split())
        passes.append((p, d, c))

    dp = [0] * (n + 1)

    for i in range(n - 1, -1, -1):
        best = f[i] + dp[i + 1]

        for p, d, c in passes:
            limit_time = t[i] + p
            cnt = 0
            j = i
            while j < n and t[j] <= limit_time and cnt < d:
                cnt += 1
                j += 1
            best = min(best, c + dp[j])

        dp[i] = best

    print(dp[0])

if __name__ == "__main__":
    solve()
```实现直接遵循 DP 定义。 内部循环计算通行证从 i 开始可以覆盖多少个旅行天数，当超过时间窗口或达到使用限制 d 时停止。 生成的索引 j 是使用通行证后第一个未覆盖的天。 然后转换直接移至 dp[j]。 

主要的微妙之处是确保 j 仅计算实际旅行天数，而不是日历天数。 这就是为什么我们迭代索引而不是尝试计算算术界限。 另一个重要的细节是 dp 是向后计算的，因此 dp[j] 始终是已知的。

 ## 边缘情况

 一个关键的边缘情况是通行证的有效窗口很大但使用限制非常小。 例如，如果旅行日早些时候密集但后来稀疏，则该通票可能会在窗口结束前耗尽其配额。 该算法通过明确计算实际覆盖的旅行天数而不是假设整个窗口覆盖来处理此问题。 

另一个边缘情况是传球在时间上重叠但在覆盖范围上不重叠。 即使多个通道可能同时处于活动状态，DP 通过将每个通道压缩为从 i 到 j(i, type) 的单次跳转来完全避免建模重叠，从而确保我们永远不会重复计算可用性。 

当通道在行进序列末尾附近开始时，会出现最后的边缘情况。 在这种情况下，j(i, type) 很快变为 n，并且 dp[j] 正确地变为 0，这意味着通行成本仅与剩余票价进行比较，无需任何特殊处理。
