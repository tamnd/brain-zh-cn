 ## 解决方案
 ## 问题理解

 我们得到了一个冻结的比赛记分牌，其中已经按从最好到最差的顺序排列了几支球队。 每个团队都有一行描述每个问题的提交状态：已接受、已拒绝、待处理或根本没有提交。 只有待决的参赛作品才是动态的，因为在颁奖典礼上这些参赛作品会被一一解决。 

解决过程是确定性的。 在每一步中，我们都会查看当前排名，并选择排名最低但仍至少有一个待提交的团队。 在该团队内部，我们总是解决其最左边的待提交问题。 然后，根据提供的观众反应顺序，待提交的提交内容会显示为已接受或已拒绝。 如果被拒绝，其他一切都不会改变。 如果被接受，该团队解决的问题数量会增加一个，并且其在排名中的位置可能会提高，因为排名始终由接受的问题数量决定，并且固定的决胜顺序永远不会在该问题中产生歧义。 

处理所有待处理的提交后，输出会询问特定团队的最终排名。 

限制很小，最多有 100 个团队和 100 个问题。 这立即告诉我们，重复扫描所有团队并偶尔重新排序的模拟足够快。 n 中的任何二次方甚至三次方在这里都是安全的，因为操作总数仅限于几万。 

一个微妙的边缘情况来自这样一个事实：“最左边的待提交”是每个团队的，而不是全局的。 如果一个团队有多个待处理的插槽，我们必须确保始终按从左到右的顺序消耗它们。 另一个棘手的问题是选择顺序：我们总是在每一步中选择排名最低的合格团队，而不是最高的。 错误地从顶部扫描的简单实现会产生不同的更新顺序，从而产生不同的最终排名。 

## 方法

 暴力解释很简单：一步步重复模拟颁奖典礼。 在每一步中，我们都会从下到上扫描团队，以找到第一个仍有待提交的团队。 在该团队内部，我们从左到右扫描其问题，以找到第一个待解决的问题。 我们应用结果，根据需要更新接受的计数，然后通过使用接受的计数对团队进行排序来从头开始重新计算排名。 

这是可行的，因为每个操作都是明确定义的并且约束很小。 然而，原则上，每次接受后重新计算完整订单的成本可能会很高。 对于多达 100 个事件和 100 个团队，对 100 个元素进行最多 100 次排序仍然是微不足道的，但从概念上讲这是浪费。 

关键的观察结果是，影响排序的唯一动态是每个团队接受的问题数量。 待提交的结构仅决定接下来处理哪个团队，而不决定如何计算排名。 这使我们能够维护每个团队待处理索引的简单列表，并在需要时重新计算排序。 

干净的实现只需跟踪每个团队已接受的计数，并在每次接受的提交后重复对团队进行排序。 因为 n 很小，所以这已经足够最优了。

 ## 算法演练

 我们维护三个状态：每个团队当前接受的问题数量、团队的固定初始排序以及每个团队按从左到右顺序排列的待提交索引列表。 

我们还维护团队的全球排序，每当接受时我们都会更新该排序。

1. 通过计算所在行中的“A”来初始化每个团队的接受计数，并为每个团队建立待处理位置列表。 这确保了我们始终可以在每个团队的固定时间内检索下一个待处理的提交。 
2. 通过按接受数量降序对团队进行排序来构建初始排名。 这个排名代表的是仪式开始前冻结的记分牌顺序。 
3. 对于给定序列中的每个事件，我们确定接下来要解决的提交。 为此，我们从排名底部向上扫描团队，直到找到待处理列表非空的团队。 该团队是受此事件影响的团队。 
4. 从该团队中，我们删除其第一个待处理位置，因为问题指定了最左边的待处理解决方案。 
5. 如果口号表明拒绝，我们不做进一步的事情。 如果它表明接受，我们将该团队的接受计数加一。 
6. 接受后，我们会使用更新的接受计数再次对团队进行排序，从而重新计算排名。 这反映出积分榜可能出现上升趋势。 
7. 所有事件处理完成后，我们定位目标球队在排名中的最终位置并输出。 

### 为什么它有效

 不变的是，在每个事件之后，维护的排序恰好是迄今为止所有已处理提交的已接受计数的排序，并且待选择规则始终应用于具有未解决工作的排名最低的团队。 由于排名仅取决于接受的计数，并且每次接受都会在下一次选择之前立即应用，因此模拟反映了记分板的确切演变。 没有任何决定取决于未来事件，因此贪婪选择顺序始终有效。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m, r = map(int, input().split())
    r -= 1

    grid = []
    pending = [[] for _ in range(n)]
    acc = [0] * n

    for i in range(n):
        s = input().strip()
        grid.append(s)
        for j, ch in enumerate(s):
            if ch == 'A':
                acc[i] += 1
            elif ch == 'P':
                pending[i].append(j)

    order = list(range(n))

    def rebuild():
        order.sort(key=lambda i: (-acc[i], i))

    rebuild()

    for _ in range(sum(len(pending[i]) for i in range(n))):
        # pick lowest ranked team with pending
        team = None
        for i in reversed(order):
            if pending[i]:
                team = i
                break

        idx = pending[team].pop(0)

        _, result = input().split()

        if result[0] == 'A':
            acc[team] += 1
            rebuild()

    # find final rank of team r
    rebuild()
    for i, t in enumerate(order):
        if t == r:
            print(i + 1)
            return

if __name__ == "__main__":
    solve()
```该解决方案跟踪每个团队的待处理提交，以便在从列表中弹出后选择最左边的待处理元素始终是恒定的时间。 仅在接受提交后才会重新计算排名，因为拒绝不会改变任何排序。 

关键的实现选择是仅在必要时重新计算排序。 由于总共最多有 10,000 个待处理操作，因此每次对最多 100 个元素进行排序的速度非常快。 

下一个团队的选择是从当前排名的底部开始扫描，符合排名较低的团队有待提交的情况下优先处理的要求。

 ## 边缘情况

 一种极端情况是，一个团队有待提交的提交，但直到流程后期才成为排名最低的合格团队。 从底部开始扫描可确保正确性。 

另一种情况是连续多次拒绝发生。 由于拒绝不会修改接受的计数，因此排名保持稳定并且不会触发不必要的排序。 

最后一个极端情况是，一个团队的接受导致它同时跃升多个位置。 完整的重新排序会自动处理此问题，因为排名是根据更新的计数在全局范围内重新计算的，从而保持与记分板定义的一致性。
