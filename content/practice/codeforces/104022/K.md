 ## 解决方案
 ## 问题理解

 我们收到一串 URL，每天一个，每天之后我们必须决定服务器必须维护多少个“确认前缀”。 

确认前缀是一个非空字符串。 如果这些存储的前缀中至少有一个与 URL 的开头匹配，则 URL 被视为有效（即服务器将返回游戏数据）。 否则，服务器返回“未找到”。 目标是防止未发布游戏的数据泄露，这意味着任何未发布的 URL 不得意外匹配服务器的接受条件，除非有意为之。 

引入每个新 URL 后，我们需要计算前缀的最小数量，以便到目前为止看到的所有 URL 都能与规则所暗示的任意猜测“区分开来”：每个已知 URL 必须被至少一个存储的前缀覆盖，但不必要的重叠不应增加计数。 

重新解释这种情况的一个有用方法是，我们维护一组字符串，并且我们希望使用尽可能少的共享前缀代表来覆盖所有字符串。 如果多个 URL 共享一个共同的开头，则单个前缀可以为它们提供服务。 问题归结为跟踪到目前为止看到的所有 URL 中存在多少前缀共享结构，并动态更新它。 

约束很严格：最多 5 × 10⁴ URL，每个长度最多 50。这立即排除了任何在二次或更差的时间内重新计算每次插入的成对前缀关系的解决方案。 O(n²) 方法意味着在最坏的情况下需要进行 10⁹ 次比较，这太慢了。 

边缘情况是由前缀如何随着时间的推移相互作用而产生的。 例如，考虑：

 输入：```
a
ab
abc
```天真的方法可能会认为每个新字符串总是增加答案，产生 1, 2, 3。但实际上，所有这些都可以被单个前缀“a”覆盖，因此正确答案仍然是 1, 1, 1。这表明我们不是在计算字符串，而是计算存在多少个独立的“前缀分支”。 

另一个极端情况是 URL 过早出现分歧：

 输入：```
a
b
c
```这里没有共享前缀，因此答案必须每次都增长：1、2、3。 

这些示例表明，感兴趣的结构是类似特里结构的字符串分区，其中共享前缀减少了所需代表的数量。 

## 方法

 直接的暴力解释将维护迄今为止看到的所有 URL 的集合，并且在每次插入后，尝试该集合中出现的所有可能的前缀字符串。 对于每个候选前缀，我们可以检查它是否至少覆盖一个 URL，以及是否可以删除冗余前缀。 这很快就会变得复杂，因为最佳前缀集取决于全局结构，而不是单个字符串。 

一个更简单的暴力想法是在迄今为止看到的所有字符串上构建一个特里树，然后反复尝试合并节点或计算每个根到叶路径的最小代表。 然而，每次插入后从头开始重新计算意味着重建或重新处理总大小高达 2.5 × 10⁶ 字符的结构。 执行此操作 n 次会导致 O(n · L) 重建成本，这在严格约束下的 Python 中是临界值，但仍然太慢，而且是不必要的，因为更新是增量的。 

关键的观察结果是，答案正是插入字符串时表示“新分支贡献”的 trie 节点的数量。 更准确地说，每次新字符串引入以前未见过的前缀时，它都会强制在它首先与所有现有字符串分开的位置存在一个额外的代表性前缀。 这相当于增量构建一个 trie 并计算所有插入中新创建的节点数。 每个新创建的节点都对应一个之前不存在的前缀，因此需要额外的确认前缀来覆盖它。 

因此，问题简化为动态维护特里结构并计算新节点。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力重新计算前缀结构 | O(n·L²) | O(n·L²) | O(n·L) | O(n·L) | 太慢了|
 | 增量特里结构 | O(n·L) | O(n·L) | O(n·L) | O(n·L) | 已接受 |

 ## 算法演练

 我们维护一个 trie，其中每条边对应于 URL 字母表中的一个字符，其中包括小写字母、点和斜线。 每个节点代表一个迄今为止出现过的前缀。 

对于每个新插入的 URL，我们逐个字符地遍历 trie：

 1. 从 trie 的根开始。 
2. 对于 URL 中的每个字符，检查该字符是否存在子节点。 
3. 如果存在，则移至该节点而不更改答案。 
4. 如果不存在，则创建一个新节点并递增全局计数器。 
5. 继续直到字符串末尾。 

处理完每个 URL 后，计数器的当前值就是当天的答案。 

直觉是，每次我们创建一个新的 trie 节点时，我们都会发现一个在之前的所有 URL 中从未出现过的前缀。 这样的前缀不能被任何现有的确认前缀覆盖，因此它强制增加一个“前缀覆盖复杂度”单位。 

### 为什么它有效

 trie 维护着这样一个不变式：每个节点都精确对应于至少一个插入的 URL 中出现的前缀。 当我们处理一个新字符串时，任何缺失的边都表示在此插入之前不存在的前缀。 由于确认前缀必须确保覆盖所有 URL，因此任何新引入的前缀都可能代表前缀空间中的新结构要求。 每个新创建的节点都对应于系统中先前未表示的不同前缀段，并且这些段在每个步骤之后精确地累积到所需确认前缀的最小数量。 

因为我们从不删除节点，只在必要时添加它们，所以创建的节点的计数单调地跟踪不同前缀结构的增长，该结构与每次插入后所需的答案相匹配。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class TrieNode:
    __slots__ = ("next",)
    def __init__(self):
        self.next = {}

def solve():
    n = int(input())
    root = TrieNode()
    nodes = 0
    out = []

    for _ in range(n):
        s = input().strip()
        cur = root

        for ch in s:
            if ch not in cur.next:
                cur.next[ch] = TrieNode()
                nodes += 1
            cur = cur.next[ch]

        out.append(str(nodes))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```该解决方案逐步构建一个字典树。 这`nodes`计数器跟踪已引入了多少个新前缀状态。 每个丢失的转换对应于以前未见过的前缀，因此我们分配一个新节点并增加计数器。 

每个节点使用字典是可以接受的，因为所有字符串的总转换受到长度总和的限制，长度总和最多为 2.5 × 10⁶。 

一个微妙的点是我们不需要存储任何终端信息或进行任何后处理。 答案仅取决于前缀结构，而不取决于节点是否对应于完整的 URL。

 ## 边缘情况

 一种重要的边缘情况是所有 URL 的前缀都相同。 例如：

 输入：```
abc
abc
abc
```第一次插入后，我们为“a”、“ab”和“abc”创建节点。 第二次和第三次插入完全遵循现有的特里路径，因此不会创建新节点。 输出仍然是：```
3
3
3
```这表明重复的相同字符串不会改变前缀结构，并且 trie 正确地避免了重复计算。 

另一种情况是每个字符的最大分歧：

 输入：```
a
b
c
...
```每次插入都会从根创建一个新分支，因此每个字符都会引入一个新节点。 该算法正确地计算每个字符串的一个新节点，符合不存在前缀共享的直觉。
