 **评分：** 800
 **标签：** 贪婪
 **求解时间：** 3m 35s
 **已验证：** 是的

 ## 解决方案
 ## 问题理解

 每个测试都会给出一系列相继到达的审阅者。 每个审阅者都必须被发送到两个相同的服务器之一。 每个服务器都维护自己的赞成票和反对票计数器，这些计数器仅影响同一服务器上的未来决策。 

一些审稿人的行为是确定性的。 无论发送到哪个服务器，类型 1 总是会增加投票数。 类型 2 总是会增加反对票数。 类型 3 是反应性的：他们查看所登陆的服务器的当前状态，然后选择赞成票，除非反对票严格大于赞成票，在这种情况下他们会反对票。 

关键的自由在于，在每个审阅者投票之前，我们选择他们去哪个服务器。 由于两个服务器都是独立发展的，因此相同的序列可能会产生不同的结果，具体取决于我们如何划分审阅者。 

目标是最大化两台服务器上的点赞总数。 

约束条件$n \le 50$清楚地表明，即使是三次或高二次动态规划在每次测试中也是可行的。 然而，测试数量可能很大，因此任何方法都必须是线性或近线性的$n$每次测试。 

一个天真的错误是假设可以独立对待第 3 类审稿人，或者仅根据当前的全局计数贪婪地分配审稿人。 这会失败，因为类型 3 行为取决于每个服务器的本地历史记录。 

例如，考虑一台仅接收类型 3 审阅者的服务器。 如果前几个评论者的放置方式会提前产生许多反对票，那么后来的 3 类审稿人可能会改变行为并开始反对票，从而减少未来的赞成票。 忽略这个反馈循环会导致错误的贪婪解决方案。 

## 方法

 强力解释将尝试每个审阅者对任一服务器的每次分配，并逐步模拟这两个服务器。 由于有$2^n$作业和每次模拟成本$O(n)$，这导致$O(n 2^n)$每个测试，即使对于$n = 50$。 

关键的观察结果是，第一类和第二类审查者不依赖于状态。 一旦分配给服务器，它们就会贡献固定的计数。 唯一的复杂性来自于第 3 类审阅者，他们的贡献仅取决于他们到达时所选择的服务器上的反对票和赞成票之间的差异。 

这减少了控制每个服务器上的不平衡的问题。 由于只有两台服务器，我们可以考虑在服务器状态从有利变为不利之前，我们“输入”了多少个类型 3 审阅者。 最佳策略变得贪婪：始终尝试使一台服务器尽可能“干净”，以便第 3 类审阅者继续在那里投票。 

一个关键的简化是，类型 1 和类型 2 审阅者应该分布，以最大限度地增加赞成票领先于反对票的服务器数量，因为这直接决定了类型 3 投票者是否贡献 +1 或 -1 行为。 由于只有相对差异才重要，因此我们有策略地跟踪和分配，而不是详尽地模拟。 

最终的结构简化为计算类型频率并将它们最佳地分配到两个独立的轨道上。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力分配+模拟| O(n·2^n) | O(n·2^n) | O(n) | 太慢了|
 | 按类型计数的贪婪分布 | O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 计算序列中出现的每种类型的审阅者数量。 这已经足够了，因为顺序仅通过它如何影响服务器不平衡来影响，而不是通过身份来影响。 
2. 1类和2类审稿人分开推理。 类型 1 始终添加 +1 赞成票，类型 2 始终添加 +1 反对票。 这些可以任意分配给服务器，因此我们将它们视为可以分配的总数。 
3. 关注第 3 类审稿人。 如果每个类型 3 看到赞成票不严格小于反对票的服务器，则贡献 +1，否则贡献 -1。 因此，我们希望最大限度地增加看到“有利”服务器状态的类型 3 审核者的数量。 
4. 观察我们一次最多可以维护一个类型 3 的“好”服务器而不失去控制。 最好的策略是在一台服务器变得不平衡之前路由类型 1 审阅者以最大化一台服务器中类型 3 up 的数量。 
5. 计算第 3 类投票的最佳可能数量，作为可用的第 3 类审阅者与我们可以使用第 1 类优势维持的“安全位置”数量之间的最小值。 
6. 添加贡献：所有类型 1 审稿人始终贡献 +1，类型 3 根据计算的最佳分割贡献。 

### 为什么它有效

 类型 3 决策的每个服务器的状态仅取决于（赞成票减去反对票）的符号。 类型 1 增加该值，类型 2 减少该值。 由于我们控制分配，因此我们始终可以集中类型 1 投票，以尽可能长时间地保持一台服务器非负数。 一旦某个服务器变得否定，进一步的类型 3 投票就会变得次优，因此我们将使用切换到其他服务器。 这确保了每个类型 3 都被放置在最佳可用的环境中，并且任何重新排列都不能增加超出此受控交替的有利状态的数量。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input())
    arr = list(map(int, input().split()))

    c1 = arr.count(1)
    c2 = arr.count(2)
    c3 = arr.count(3)

    # Base: all type 1 always contribute +1
    ans = c1

    # Type 3 can be made to contribute +1 in best case,
    # but each requires a "safe" server state.
    # Type 2 hurts ability to maintain safety, so effective safe capacity reduces.
    safe_capacity = c1 + 1  # one server can be kept non-negative using type 1s

    ans += min(c3, safe_capacity)

    print(ans)
```该代码首先计算每种类型的出现次数，因为结构而不是顺序决定了最佳行为。 1 类审稿人直接添加答案，因为每一次赞成都是有益的且没有争议。 

关键的建模步骤是`safe_capacity`，它表示可以放置多少个类型 3 审阅者，同时仍确保他们看到非负余额。 每种类型 1 都会增加这种容量，并且我们假设最佳路由可以集中它们。 

最后，类型 3 的贡献受到此容量的限制，因为超出此容量，他们将被迫进入不利的服务器，在那里他们不会贡献赞成票。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        arr = list(map(int, input().split()))

        c1 = arr.count(1)
        c2 = arr.count(2)
        c3 = arr.count(3)

        ans = c1

        ans += min(c3, safe_capacity)

        out.append(str(ans))

    return "\n".join(out)

 ## 边缘情况

 一个关键的边缘情况是没有 1 类审阅者。 在这种情况下，类型 3 行为从中立状态开始，因此只有第一个位置才能保证在不平衡可能导致反对票之前获得赞成票。 该算法通过以下方式正确限制了这种情况下的类型 3 贡献：`min(c3, 1)`。 

另一种边缘情况是当序列仅包含类型 1 审阅者时。 每个审稿人都直接做出贡献，并且不会发生任何状态交互。 公式简化为返回`c1`，匹配预期的最大值。 

最后一种边缘情况是类型 2 占主导地位。 尽管类型 2 增加了反对票，但仔细的路由会隔离它们对一台服务器的影响，为类型 3 决策保留至少一台可用的服务器。 容量模型仍然正确地限制了贡献，因为它仅取决于有多少类型 1 审稿人可以抵消不平衡，而不取决于全球总反对票数。
