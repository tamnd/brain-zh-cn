 ## 解决方案
 ## 问题理解

 我们正在模拟一个在网格上玩的非常小的事件驱动游戏。 网格包含来自两支球队的球员、每支球队的固定球门以及最多三种类型的球：鬼飞球（用于得分）、游走球（消除接触的球员）和金色飞贼（被抓住后可以立即结束比赛）。 

输入为我们提供了所有实体的初始布局$N \times M$板，然后是一系列$T$行动。 每个动作只影响一个实体：玩家移动、捡起球或掉落鬼飞球。 移动是在网格上一步步进行的，每次动作后都会立即解决交互。 关键的困难在于，许多事情都可能作为单个动作的“副作用”而发生：得分、球重置、淘汰或比赛终止。 

输出不是最终的板状态，而是模拟期间发生的事件的日志。 我们必须按照严格的时间顺序打印淘汰赛，然后是得分项目，最后是最终得分线。 

约束足够小，可以直接模拟：$T \leq 10^4$,$N, M \leq 99$，最多20名玩家。 这立即排除了比以下更复杂的事情$O(T)$或者$O(T \log T)$。 任何尝试每一步重新计算板级结构的解决方案仍然会通过，但如果重复执行，不必要的全局扫描很容易成为性能陷阱。 

微妙之处在于，多个交互可以在同一时间步骤中发生，并且顺序很重要。 

一种常见的失败情况是忽略同时消除顺序。 例如，如果游走球和玩家最终都在同一个单元格中，则必须按玩家 ID 的字母顺序打印淘汰：

 输入场景：```
R0 and B0 collide with Bludger in same step
```正确的输出顺序：```
B0 ELIMINATED
R0 ELIMINATED
```以任意字典顺序处理玩家的简单模拟有时会逆转这种情况。 

另一个失败案例是忘记得分会立即将鬼飞球重置到中心。 如果玩家进入球门格，然后在同一步骤中投掷鬼飞球，则在重置之前，得分必须已在该步骤的较早阶段根据其位置得到解决。 

最后，抓住金色飞贼必须立即终止游戏，这意味着即使稍后出现在输入中，也不会处理进一步的操作。 

## 方法

 直接模拟是自然的起点。 我们存储网格、所有实体的位置，并维护每个玩家的状态，例如他们是否携带鬼飞球。 每个命令都按顺序执行，更新位置并检查交互。 

在暴力思维中，每次移动后，我们都会扫描所有玩家以检测与游走球的碰撞，并扫描所有单元格以检测进球和得分事件。 这是正确的，但原则上效率低下：每一步扫描所有玩家给出$O(P \cdot T)$，扫描网格会添加另一个$O(NM \cdot T)$。 虽然这仍然符合此处的限制，但这是不必要的开销并且存在实现复杂性的风险。 

关键的观察结果是所有交互都是本地的。 每个事件仅取决于在动作发生时共享同一单元格的实体。 这使我们能够维护从位置到实体的直接映射，并在每次移动后仅更新受影响的单元格。 我们永远不需要全局重新计算。 

因此，最佳解决方案仍然是模拟，但保持结构化状态：

 - 字典中的球员位置
 - 小区占用情况跟踪，以便快速查找
 - 鬼飞球位置或运营商参考
 - 预先标记的目标位置
 - 游走者和告密者的位置

 每次操作后，我们只检查受影响的一个或多个单元，而不是整个板。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力扫描棋盘/玩家每一步 |$O(T(NM + P))$|$O(NM + P)$| 概念上太慢|
 | 具有本地更新的事件驱动模拟|$O(T)$|$O(NM + P)$| 已接受 |

 ## 算法演练

 我们一步一步地模拟，保持所有实体的准确状态。 

1. 解析网格并存储：

 每位球员的位置、鬼飞球、游走球、金色飞贼以及双方球队的目标。 这可以避免稍后重新扫描网格，因为初始解析是唯一的全局操作。 
2. 维护从玩家 ID 到其位置和存活状态的地图。 死亡的玩家在未来的行动中将被忽略。 
3. 使用单独的布尔映射来跟踪玩家是否携带鬼飞球。 鬼飞球本身要么有固定位置，要么附在玩家身上。 
4. 对于每一个$T$动作，按顺序处理它们：

 如果演员已经被淘汰，则完全跳过处理。 
5. 如果动作是移动，则将实体位置更新一个单元格。 对于玩家来说，如果携带着鬼飞球，也请移动它。 每一步的运动始终是原子的，因此不存在中间状态。 
6. 每次移动后，检查游走球是否发生碰撞。 如果玩家与游走球共用一个单元格，则将其标记为已淘汰。 我们必须立即登记此举动引发的所有淘汰。 
7. 确定该步骤的所有淘汰后，按玩家 ID 排序输出。 
8. 如果幸存的球员携带鬼飞球并且现在位于对方球队的球门区内，则计算得分：

 更新得分、发出事件并立即将鬼飞球重置为中心。 
9. 如果动作是接球命令，则将指定的球附加到共享单元格的玩家身上。 
10. 如果操作是投掷命令，则分离鬼飞球并将其留在当前单元格上。 
11.如果告密者被抓住，则立即输出事件，将分数更新为10，并终止所有剩余动作的处理。 

中心不变量是处理步骤之后$i$，之后世界的状态完全符合游戏规则$i$原子动作，包括碰撞和得分的所有级联效应。 由于每个副作用都会在同一时间步内立即解决，因此后续步骤始终会观察到一致的状态。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    N, M = map(int, input().split())

    grid = []
    players = {}
    alive = {}
    carry = {}
    pos = {}

    bludger = None
    snitch = None
    quaffle = None

    red_goal = set()
    blue_goal = set()

    for i in range(N):
        row = input().split()
        for j, cell in enumerate(row):
            if cell == "..":
                continue
            if cell == ".Q":
                quaffle = (i, j)
            elif cell == ".B":
                bludger = (i, j)
            elif cell == ".S":
                snitch = (i, j)
            elif cell == "RG":
                red_goal.add((i, j))
            elif cell == "BG":
                blue_goal.add((i, j))
            else:
                team = cell[0]
                pid = cell
                players[pid] = (i, j)
                alive[pid] = True
                carry[pid] = False

    T = int(input())
    score_r = 0
    score_b = 0

    center = ((N // 2), (M // 2))

    def move(p, d):
        x, y = players[p]
        if d == "U":
            x -= 1
        elif d == "D":
            x += 1
        elif d == "L":
            y -= 1
        else:
            y += 1
        players[p] = (x, y)

    def check_elim():
        nonlocal bludger
        to_remove = []
        bx, by = bludger
        for p in players:
            if alive[p] and players[p] == (bx, by):
                to_remove.append(p)
        to_remove.sort()
        for p in to_remove:
            alive[p] = False
            carry[p] = False
            print(f"{t} {p} ELIMINATED")

    for t in range(T):
        parts = input().split()
        actor = parts[0]
        if actor not in players or not alive[actor]:
            continue

        cmd = parts[1]

        if cmd in "UDLR":
            move(actor, cmd)
            if carry[actor]:
                quaffle = players[actor]

            if bludger is not None:
                check_elim()

            # scoring after movement
            if carry[actor]:
                ppos = players[actor]
                if ppos in red_goal:
                    score_b += 1
                    print(f"{t} BLUE GOAL")
                    quaffle = center
                    carry[actor] = False
                elif ppos in blue_goal:
                    score_r += 1
                    print(f"{t} RED GOAL")
                    quaffle = center
                    carry[actor] = False

            # snitch check
            if snitch is not None and players[actor] == snitch:
                team = actor[0]
                if team == "R":
                    score_r += 10
                    print(f"{t} RED CATCH GOLDEN SNITCH")
                else:
                    score_b += 10
                    print(f"{t} BLUE CATCH GOLDEN SNITCH")
                return

        elif cmd == "C":
            ball = parts[2]
            if ball == ".Q":
                carry[actor] = True
                quaffle = None

        elif cmd == "T":
            carry[actor] = False
            quaffle = players[actor]

    print(f"FINAL SCORE: {score_r} {score_b}")

if __name__ == "__main__":
    solve()
```该实现依赖于维护显式状态而不是重建它。 玩家位置直接更新，鬼飞球要么附着在玩家身上，要么存储为坐标。 消除检查集中在一个助手中，该助手仅检查游走球的单元格，确保我们不会扫描网格的不相关部分。 

一个微妙的细节是消除的顺序：对玩家 ID 进行排序可确保输出的确定性。 另一个是在移动后但在下一个动作之前立即处理得分。 

飞贼条件在移动后立即检查，因为它会覆盖游戏的其余部分。 

## 工作示例

 考虑一个最小的交互，其中玩家携带鬼飞球进入球门：

 | 时间 | 行动| 玩家位置 | 鬼飞球 | 活动 |
 | ---| ---| ---| ---| ---|
 | 0 | R0 D | (2,2) | 携带| 无 |
 | 1 | R0 T | (2,2) | 掉落 | 无 |
 | 2 | R0 D | (3,2) | (2,2) | 蓝色目标|

 这表明得分取决于鬼飞球释放时的位置或携带状态，而不是未来的移动。 

现在考虑游走球碰撞：

 | 时间 | 行动| R0 位置 | B0 位置 | 活动 |
 | ---| ---| ---| ---| ---|
 | 0 | R0 R | (1,1) | (1,2) | 无 |
 | 1 | B0 长 | (1,1) | (1,1) | R0 淘汰，B0 淘汰 |

 这显示了同时消除顺序：两个玩家在同一步骤中被删除，并且必须进行排序。 

这些跟踪确认所有交互都是本地的，并且在每个操作后立即解决。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 |$O(T + P)$| 每个动作都会处理一次，每个实体都会进行恒定时间更新，并且消除检查仅扫描玩家 |
 | 空间|$O(P + NM)$| 玩家状态和初始网格实体的存储 |

 约束最多允许 10,000 个操作，因此具有较小恒定开销的线性模拟就足够了。 玩家数量很少，因此即使每步扫描仍然很快。

 ## 边缘情况

 一个关键的边缘情况是由游走球动作引起的同时消除。 当多个玩家在同一步骤中登陆同一个单元格时，必须先收集所有玩家，然后按排序顺序打印。 幼稚的按玩家立即打印可能会带来错误排序的风险。 

另一个边缘情况是得分，紧随其后的是同一时间步内的告密者捕获逻辑。 正确的行为是，Snitch capture 在处理移动后立即终止游戏，因此仍在同一步骤中的任何待定得分必须在终止之前已解决。 

最后一个微妙的情况是鬼飞球被带入球门，然后在同一步骤中掉落。 由于得分是根据移动之后但投掷动作之前的位置来评估的，因此命令处理的顺序确保了一致性：移动解析状态，检查得分，然后才处理投掷。
