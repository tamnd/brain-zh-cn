 ## 解决方案
 ## 问题理解

 我们得到了一个非常大的整数，但我们不应该将其视为一个数字，而应该将其视为十进制数字的多重集。 Bomboslav 删除了支票中的所有数字，并希望使用每个数字一次将它们重新组合成一个新整数。 

对最终数量的限制是严格的。 它必须是一个没有前导零的有效整数，它必须能被 7 整除，并且在所有这些有效的重新排列中，它必须在通常的数字字典意义上尽可能大。 如果不存在有效的重排，则答案为-1。 还有一个额外的约束，有效地禁止通过重建原始排列来“作弊”，除非它已经满足能被 7 整除，但实际上，这自然是通过要求所有数字恰好使用一次来强制执行的。 

输入大小最多可达 1000 位数字，这会立即排除任何尝试所有排列的方法。 阶乘爆炸是不可能的，如果天真地完成，甚至对所有数字子集进行动态编程也是不可行的。 唯一可用的结构来自于只有 10 个可能的数字值，因此输入实际上是一个小字母表上的频率表。 

一些边缘情况立即很重要。 如果数字只包含零，那么我们不能将零作为前导数字，除非它是唯一的数字。 例如，输入`0`是有效的并且产生`0`，但输入`00`仍然产生`0`重新排列后。 如果所有数字均非零，我们必须确保所选排列不从零开始，即使它在其他方面是最佳的。 

当存在具有相同数字但不同整除结果的多个排列时，会出现另一种微妙的故障模式。 例如，数字`1,2,3`可以形成很多排列，但只有一些排列满足模约束，因此仅靠贪心排序是不够的。 

## 方法

 强力解决方案将生成数字的所有排列，过滤那些不以零开头的排列，检查能否被 7 整除，然后选择最大的排列。 这是正确的，但完全不可行，因为对于最多 1000 位数字，排列数量是输入大小的阶乘。 

关键的结构观察是，我们不关心相同数字的各个位置，只关心每个数字使用了多少个。 这将问题简化为处理由 10 维频率向量定义的状态。 从任何部分构造来看，对整除性唯一重要的是当前模 7 的余数。 

这会产生一个状态图，其中每个状态由剩余数字计数和当前余数模 7 来描述。转换包括选择一位数字附加到当前数字、减少其计数并更新余数。 由于数字逐位增长，因此余数更新取决于位置权重，这在构造过程中隐式处理。 

一旦我们可以从任何状态测试可行性，我们就可以贪婪地构建答案。 在每个位置，我们尝试从 9 到 0 的数字，并选择仍然允许完成有效最终状态的第一个数字。 这保证了最大的字典顺序，因为在不破坏可行性的情况下，总是首选更高的数字。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力排列 | O(n!) | O(n) | 太慢了 |
 | DP 数字计数和余数 + 贪婪重建 | O(状态 × 10) | O（状态）| 已接受 |

 ## 算法演练

 ### 关键思想

 我们将剩余的数字视为频率表，并从左到右构建答案。 在每一步中，我们都会选择仍然允许有效完成的最大可能数字。 

### 步骤

 1. 计算输入字符串中从 0 到 9 的每个数字的出现次数。 这会将输入压缩为最多 10 个数字，而不是最多 1000 个字符。 这是我们之后使用的唯一表示形式。 
2. 定义递归函数`can(counts, remainder, position)`返回是否可以使用剩余的数字来完成有效的数字。 这`position`之所以需要，是因为数字的贡献取决于其 10 的幂，以及周期为 6 的 10 周期模 7 的幂。 
3. 记住这个函数，因为相同`(counts, remainder, position mod 6)`状态在探索过程中可以多次出现。 如果没有记忆，递归将重复地重新计算相同的子问题。 
4. 从最重要的位置开始构建最终数字。 对于每个位置，尝试从 9 到 0 的数字。 
5. 对于每个候选数字，暂时减少其数量并检查是否`can(...)`确认存在完整有效的完成。 
6. 如果候选数字得出可行的解决方案，则将其永久放置在答案中，并移动到具有更新的计数和余数的下一个位置。 
7. 如果某个位置没有数字起作用，则断定不存在有效数字并输出-1。 

### 为什么它有效

 在每一步中，算法都保持不变，即到目前为止选择的前缀在所有前缀中按字典顺序是最大的，仍然可以得出有效的完整解决方案。 可行性检查确保我们永远不会提交阻止所有有效完成的前缀。 由于数字是按降序尝试的，因此第一个可行的选择也是该位置的最大可能选择。 归纳起来，这保证了整个构造的数字是最大有效排列。 

可行性的正确性依赖于这样一个事实：模 7 仅取决于位置模 6，因此状态空间是有限的并且可以安全地缓存重新访问。 

## Python 解决方案```python
import sys
input = sys.stdin.readline
from functools import lru_cache

sys.setrecursionlimit(1000000)

MOD = 7

def solve():
    s = input().strip()
    cnt = [0] * 10
    for ch in s:
        cnt[int(ch)] += 1

    n = len(s)

    # powers of 10 mod 7, period 6
    pw = [1] * 6
    for i in range(1, 6):
        pw[i] = (pw[i - 1] * 10) % 7

    @lru_cache(None)
    def can(c0, c1, c2, c3, c4, c5, c6, c7, c8, c9, pos_mod, rem):
        counts = [c0,c1,c2,c3,c4,c5,c6,c7,c8,c9]
        if sum(counts) == 0:
            return rem == 0

        # try placing any digit next
        for d in range(10):
            if counts[d] == 0:
                continue
            counts[d] -= 1
            new_mod = (rem * 10 + d) % 7
            new_pos = (pos_mod + 1) % 6
            args = tuple(counts + [new_pos, new_mod])
            if can(*args):
                return True
            counts[d] += 1

        return False

    # initial feasibility
    init_args = tuple(cnt + [0, 0])
    if not can(*init_args):
        print(-1)
        return

    res = []
    pos_mod = 0
    rem = 0

    for _ in range(n):
        for d in range(9, -1, -1):
            if cnt[d] == 0:
                continue
            cnt[d] -= 1
            if can(*tuple(cnt + [pos_mod + 1, (rem * 10 + d) % 7])):
                res.append(str(d))
                pos_mod = (pos_mod + 1) % 6
                rem = (rem * 10 + d) % 7
                break
            cnt[d] += 1

    print("".join(res))

if __name__ == "__main__":
    solve()
```该解决方案使用递归可行性检查器，在跟踪模 7 的余数和模 6 的位置的同时探索数字位置。重建循环贪婪地从左到右修复每个数字，始终验证剩余的多重集仍然可以形成有效的完成。 

一个微妙的实现细节是，记忆键包括扩展为单独参数的数字计数。 这避免了递归内的元组散列开销，当许多状态重复时，这在深度上很重要。 另一个重要的一点是，我们从不显式构造完整的中间数，只构造它们的模状态。 

## 工作示例

 ### 示例 1

 输入：```
1234
```我们假设数字可以重新排列，并且我们希望最大的排列可以被 7 整除。 

在第一个位置，从 9 向下测试数字，但只有 4、3、2、1 可用。 假设先尝试4。 如果可行性检查失败，我们将向下移动，直到找到允许完成的数字。 

| 步骤| 剩余数字| 选择的数字 | 余数 mod 7 |

 | 4 | 1 | 1 | 1 |

 该轨迹显示了算法如何持续执行全局可行性而不是局部最优选择。

 ## 边缘情况

 一个关键的边缘情况是满足整除性的唯一方法需要提前放置零。 该算法避免了这种情况，因为每个候选前缀都经过完全可行性验证，因此在检查期间会拒绝任何会强制无效前导结构的前缀。 

另一种边缘情况是多个数字产生相同的前缀但下游可行性不同。 记忆的可行性函数确保尽早检测到这些差异，从而防止如果我们只检查局部有效性就会发生贪婪的错误。
