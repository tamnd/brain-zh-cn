 ## 解决方案
 ## 问题理解

 我们有`n`提交编号自`1`到`n`。 恰好有一个第一次提交`m`这打破了测试。 这为序列提供了一个非常有用的单调结构：每个提交的编号小于`m`很好，而每一次提交`m`往后就不好了。 

程序无法提前检查整个序列。 它通过打印一个提交编号、接收`1`如果该提交通过了测试并且`0`如果失败了。 确定后`m`，它必须打印`! m`并终止。 每个查询都必须立即刷新，因为法官只有在收到相应的查询后才提供下一个答案。 

输入开始于`n`， 在哪里`1 <= n <= 10^6`。 其余输入是交互式的：每个响应仅在程序进行查询后出现。 上界为`n`足够小，以至于对数搜索很容易足够快，但线性扫描可能需要一百万个查询，而协议只允许 25 个。因此，真正的限制是交互次数而不是 CPU 时间。 

单调性也决定了边缘情况。 如果`n = 1`，唯一可能的答案是`m = 1`，因此程序不得尝试查询无效的中点或将下限移过去`n`。 例如，使用输入`1`，最终正确的输出是`! 1`。 

第一次提交可能是破坏性的。 例如，如果`n = 5`隐藏序列是`0 0 0 0 0`，答案是`! 1`。 一种实现，假设始终至少有一次成功提交，并从搜索转换开始`1`到`0`使用下界`2`可能会完全错过答案。 

最后一次提交也可能是破坏性的。 和`n = 5`和回应`1 1 1 1 0`，答案是`! 5`。 粗心的二分搜索将`1`在中点意味着答案在于`[mid, hi]`而不是`[mid + 1, hi]`可能会卡住或返回成功的提交。 

查询响应和最终答案之间也存在重要区别。 查询`m`本身返回`0`，但这并不意味着我们需要另一个查询来验证它。 一旦搜索间隔折叠到一个位置，单调属性就已经证明该位置是第一个失败的提交。 

## 方法

 直接的解决方案是从左到右查询提交。 我们从提交开始`1`， 然后`2`，并继续直到第一个响应`0`出现。 第一次失败的提交正是`m`，因为所有较早的提交都会通过，并且来自的每个提交`m`继续失败。 如果`m = n`，该方法需要`n`查询。 

为了最大`n = 10^6`, the worst case is therefore one million queries. The protocol allows only 25, so a linear scan is not merely slower than necessary, it is invalid for most possible inputs.

 暴力方法之所以有效，是因为响应包含足够的信息来识别第一次失败。 The key observation is that one query can eliminate an entire interval, not just identify the queried position. 假设我们查询`mid`。 如果答案是`1`， 然后`mid`已知是在第一次失败提交之前，因此每个位置直到并包括`mid`可以被丢弃。 如果答案是`0`， 然后`mid`已经失败，因此第一个失败位置必须位于或之前`mid`。 

这正是二分查找所需的结构。 我们保持一个间隔`[lo, hi]`保证包含`m`。 成功的中点将其更改为`[mid + 1, hi]`，而失败的中点将其更改为`[lo, mid]`。 每个查询大约将可能答案的数量减半。 

为了`n <= 10^6`, 至多`ceil(log2(10^6)) = 20`需要查询。 这明显低于 25 的限制。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n) 次查询 | O(1) | O(1) | 太慢了 |
 | 二分查找 | O(log n) 次查询 | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 设置`lo = 1`和`hi = n`。 不变的是未知的第一个失败提交`m`总是在里面`[lo, hi]`。 
2. 虽然`lo < hi`， 选择`mid = (lo + hi) // 2`并打印`mid`。 立即刷新标准输出，然后读取法官的响应。 
3. 如果响应是`1`， 犯罪`mid`通过测试。 由于之前的每次提交`m`通过和每次提交`m`继续失败，`m`必须严格大于`mid`。 将间隔替换为`[mid + 1, hi]`。 
4. 如果响应是`0`， 犯罪`mid`失败。 第一次失败的提交不能晚于`mid`， 因为`mid`本身已经失败了。 将间隔替换为`[lo, mid]`。 
5. 什么时候`lo == hi`，该间隔恰好包含一个可能的提交。 打印`! lo`并终止。 不需要额外的查询，因为不变式证明这个位置是`m`。 

使用理由`lo < hi`间隔本身就带有正确性的证明，而不是重复查询直到出现特定响应。 一旦其端点重合，就不再存在不确定性。 

### 为什么它有效

 在每一个点上，`[lo, hi]`包含真正的第一个失败的提交。 最初这是真的，因为`m`保证在之间`1`和`n`。 如果返回中点`1`，单调性告诉我们`m > mid`，所以去掉`[lo, mid]`无法删除`m`。 如果中点返回`0`，单调性告诉我们`m <= mid`，所以去掉`[mid + 1, hi]`无法删除`m`。 因此，不变量在每次查询中都存在。 

每次迭代都会严格减小间隔的大小，同时保留`m`。 最终`lo`和`hi`变得平等。 由于唯一剩余的可能位置是真实的`m`，打印该位置是正确的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    lo = 1
    hi = n

    while lo < hi:
        mid = (lo + hi) // 2

        print(mid, flush=True)
        response = input().strip()

        if response == "1":
            lo = mid + 1
        else:
            hi = mid

    print("!", lo, flush=True)

if __name__ == "__main__":
    solve()
```程序首先读取`n`并将搜索间隔初始化为所有可能的提交。 该间隔使用基于 1 的索引，因为协议中的提交编号范围为`1`通过`n`。 

中点计算如下`(lo + hi) // 2`。 Python 整数不会溢出，尽管相同的表达式在具有足够宽整数类型的语言中也是安全的，因为`n`只是`10^6`。 

查询打印为`flush=True`。 这对于交互问题至关重要。 如果不进行刷新，Python 可能会将查询保留在其输出缓冲区中，从而在程序等待响应时让判断器处于等待状态。 

的回应`"1"`动作`lo`到`mid + 1`，因为第一个失败的提交必须严格位于右侧。 的回应`"0"`动作`hi`到`mid`， 因为`mid`它本身可能是第一个失败的提交。 使用`hi = mid - 1`这将是一个相差一的错误，并且可能会丢弃正确的答案。 

循环停止时`lo == hi`。 此时答案已经知道，因此程序会打印所需的内容`!`前缀并在终止前再次刷新。 

没有多个测试用例。 程序的每次调用都会与一个隐藏的提交序列交互。

 让`n = 8`假设第一个失败的提交是`1`。 每个查询都会返回`0`。

## 边缘情况

 当`n = 1`，初始间隔为`[1, 1]`，因此跳过循环，程序立即打印`! 1`。 对于具体输入`1`，没有有效的替代答案，因为唯一的提交必须是第一个失败的提交。 

当第一次提交被破坏时，考虑`n = 8`和`m = 1`。 第一个查询是`4`，返回`0`，将间隔更改为`[1, 4]`。 查询`2`也返回`0`, 给予`[1, 2]`，并查询`1`回报`0`, 给予`[1, 1]`。 最终的答案是`! 1`。 不需要关于早期成功提交的假设。 

当最后一次提交被破坏时，考虑`n = 8`和`m = 8`。 第一个查询是`4`，返回`1`，所以区间变为`[5, 8]`。 查询`6`回报`1`，生产`[7, 8]`，并查询`7`回报`1`，生产`[8, 8]`。 程序打印出`! 8`。 更新内容`lo = mid + 1`是什么让最终职位仍然是候选人。 

当查询提交失败时，会发生最常见的差一错误。 和`n = 5`和`m = 3`, 查询`3`回报`0`。 正确的新间隔是`[1, 3]`， 不是`[1, 2]`，因为提交`3`其本身可能就是第一个失败。 作业`hi = mid`保留该候选人。 

另一种边界情况是过渡紧接在中点之后。 和`n = 10`和`m = 6`, 查询`5`回报`1`，所以答案一定是在`[6, 10]`。 删除提交`5`之前的一切都是安全的，因为所有这些提交都已知会通过。 作业`lo = mid + 1`准确地抓住了这个推理。 

最后，查询限制本身也是正确性的一部分。 为了`n = 10^6`，二分查找最多需要 20 个查询，而允许的最大值为 25。每次提交一次查询的方法无法通过小的优化来修复，因为它的最坏情况查询计数基本上是线性的。 候选区间的对数减少是解决方案满足交互协议的核心原因。
