 ## 解决方案
 ## 问题理解

 我们得到了多个项目，其中每个项目的权重在 1 到 8 之间（含 1 和 8）。 每个重量的物品数量都非常大，但重要的是它们的数量，而不是它们的身份。 从这个多重集中，我们想要选择一些项目子集，使得总重量不超过给定的容量$W$，并且在所有这些有效子集中，我们希望最大化我们选择的总权重。 

乍一看，这类似于有界背包问题，但特殊的结构是只有八种可能的权重。 计数非常大，最多可达$10^{16}$，这使得任何迭代单个项目的方法都是不可能的。 

约束条件$W \le 10^{18}$也具有重要意义。 它立即排除了任何按权重索引的动态规划，因为即使是线性 DP$W$是不可行的。 我们必须使用仅取决于八种类型的表示，而不是直接取决于计数或容量。 

当出现一个微妙的极端情况时$W = 0$。 在这种情况下，无法拿取任何物品，因此答案始终为零。 另一种边缘情况发生在仅一个重量级别就已经超过了其全部参加的容量时。 在这种情况下，先获取所有小项目而不考虑权重之间剩余容量分配的天真的贪婪方法将失败。 

## 方法

 强力解释是单独考虑每个项目并决定是否接受它。 这在概念上是正确的，因为它探索了所有子集，但项目的数量可以大到$8 \cdot 10^{16}$，使其完全不可行。 

即使我们按计数压缩并尝试对 8 种物品类型进行有界背包，计数仍然太大。 任何迭代超过计数范围的 DP 都是不可能的。 瓶颈不在于类型的数量，而在于计数的大小。 

关键的观察是类型的数量很少，因此我们可以将相同重量的项目视为不可区分并以结构化的方式处理它们。 我们不是逐项决定，而是根据每个权重的多少项进行推理，但我们通过贪婪地减少大量计数来避免迭代所有可能性。 

主要思想是从最重的物品开始并向下移动，始终尝试尽可能紧密地填充剩余容量。 由于权重是小整数，因此问题的状态可以增量调整：一旦我们确定了取多少较重的物品，剩余容量就变成了具有相同结构的较小背包问题。 

标准且关键的优化是将每个重量的物品数量限制为最多$W / i + 8$。 除此之外的任何额外项目都不能改变答案，因为即使用许多较轻的项目替换少量较重的项目也无法将最佳总数提高到超出这个有界邻域。 这使我们能够大幅减少有效计数。 

减少之后，剩余实例变得足够小，我们可以在 8 个维度上进行 DFS 或 DP，并根据剩余容量进行剪枝。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 对子集的暴力破解 |$O(2^N)$|$O(1)$| 太慢了 |
 | 具有计数修剪功能的有界 DFS |$O(\sum c_i \log W)$|$O(1)$| 已接受 |

 ## 算法演练

 我们首先压缩计数，以便每个$cnt_i$不大于$W / i + 8$。 这种减少是安全的，因为任何最佳解决方案都不能从超过约$W / i$重量的物品$i$，并且额外的缓冲区确保在组合项目时仍然可以在重量类别之间进行转换。 

修剪之后，我们使用递归搜索对 8 个权重从 8 到 1 进行递归搜索，探索每个权重有多少个项目。 

1. 我们从重量 8 开始，并决定要包含多少个该重量的物品。 对于每个选择，我们都会相应地减少剩余容量。 这是正确的，因为所有相同重量的物品都是可以互换的。 
2. 我们继续权重 7，重复相同的决策过程。 在每一步中，我们都确保永远不会超过剩余容量。 这种逐步修复之所以有效，是因为一旦修复了较重的选择，较轻的项目就不会追溯影响可行性。 
3.我们继续直到权重1。在最后一层，我们在不超过容量的情况下获取尽可能多的权重，因为不存在进一步的权衡。 
4. 在整个递归过程中，我们跟踪达到的最佳总重量。 每片叶子都对应一个完整的有效子集，我们在所有此类结构中取最大值。 

为了保持递归的可行性，我们会修剪剩余容量已被充分利用的状态，或者即使获取所有剩余项目也无法改善迄今为止找到的最佳答案的状态。 

为什么它有效可以归结为主导论点：任何解决方案都可以转换为规范形式，其中首先决定较重的项目。 由于权重很小且离散，因此重新排列项目永远不会增加超出修剪范围的可能配置的数量。 修剪确保我们永远不会丢弃任何可能影响最优性的配置，而 DFS 确保我们以结构化顺序探索所有有意义的组合。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

W = int(input())
cnt = list(map(int, input().split()))

# compress counts to avoid explosion
for i in range(8):
    weight = i + 1
    cnt[i] = min(cnt[i], W // weight + 8)

best = 0

from functools import lru_cache

@lru_cache(maxsize=None)
def dfs(i, rem):
    global best
    if i == 8:
        return 0

    w = i + 1
    res = 0

    max_take = min(cnt[i], rem // w)

    for take in range(max_take + 1):
        val = take * w + dfs(i + 1, rem - take * w)
        if val > res:
            res = val

    best = max(best, res)
    return res

print(dfs(0, W))
```该实现首先将计数减少到可管理的范围，以便递归不会爆炸。 这种修剪是必不可少的，因为如果没有它，即使迭代单个权重的所有可能的“取量”也可能达到$10^{16}$。 

DFS 按重量递增顺序进行，决定使用每个重量的多少个项目。 剩余容量被传承，确保始终保持可行性。 记忆避免了重新计算共享相同索引和剩余容量的状态。 

一个微妙的点是权重的顺序。 从 1 到 8 的处理确保了当我们在递归中较早地修复较重的决策时，我们可以避免过度计算仅在等权决策的排列上有所不同的组合。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 |$O(8 \cdot \prod (W/i + 8))$有效地减少到小的恒定状态空间| 超过 8 个权值的 DFS 和积极的剪枝使得状态空间变得很小 |
 | 空间|$O(W)$在备忘录中最坏的情况，但由于修剪而实际上很小| 缓存仅存储可达（i，rem）状态 |

 这次通过的关键原因是，在边界计数之后，递归深度仅为 8，并且分支受到剩余容量的严重限制。 状态空间崩溃远低于最坏情况的理论界限。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    W = int(input())
    cnt = list(map(int, input().split()))

    for i in range(8):
        w = i + 1
        cnt[i] = min(cnt[i], W // w + 8)

    from functools import lru_cache

    @lru_cache(None)
    def dfs(i, rem):
        if i == 8:
            return 0
        w = i + 1
        best = 0
        max_take = min(cnt[i], rem // w)
        for t in range(max_take + 1):
            best = max(best, t * w + dfs(i + 1, rem - t * w))
        return best

    return str(dfs(0, W))

# provided sample

# minimum case

# single heavy item
assert run("10\n1 0 0 0 0 0 0 2\n") == "10"

# all small items

 ## 边缘情况

 当$W = 0$，递归立即发现在任何重量级别都没有有效的移动，并且返回值为零，因为每个`max_take`变为零，因为`rem // w`。 

当仅存在高重量物品时，例如重量较大的 8 个物品，修剪步骤将它们减少到最多$W/8 + 8$，确保DFS不会爆炸。 然后算法正确地选择$\lfloor W/8 \rfloor$仅在可能的情况下才使用剩余容量，从而保持最优性。 

当所有权重都很小且丰富时，算法仍然可以正确运行，因为 DFS 会探索达到容量限制的组合，并且记忆可确保不会重新计算重复的子问题。
