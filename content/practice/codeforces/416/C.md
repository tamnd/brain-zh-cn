 ## 解决方案
 ## 问题理解

 我们收到一组预订请求，其中每个请求代表一组客人，他们要么全部坐在一起，要么根本不来。 每个请求都有一个大小（意味着有多少人到达）和利润（意味着如果该团体被接受并入座，餐厅可以赚多少钱）。 

除此之外，我们还有一组固定的桌子，每个桌子都有一个容量。 一张桌子最多可以容纳一个团体，并且一个团体只能坐在一张容量至少等于团体人数的桌子上。 每个表最多使用一次，每个请求要么恰好分配给一个合适的表，要么完全拒绝。 目标是选择请求的子集并以最大化总利润的方式将它们分配到不同的表。 

输入的结构使键张力清晰。 我们在容量限制下匹配两个多重集中的项目，同时仅选择其中一些项目以最大化权重。 这不是一个纯粹的匹配问题，因为允许跳过两侧，并且它不是一个简单的背包，因为容量是离散的对象而不是连续的预算。 

约束很小：请求数量和表数量最多为 1000，容量和组大小以 1000 为界。这立即表明，n² 或 n² log n 数量级的解决方案是可以接受的，但任何超过 1000 个元素的立方体都将是边界和不必要的。 

一些边缘情况对于正确性很重要：

 一种情况是所有表对于所有请求都太小。 例如，请求`(5, 10)`和桌子`[1, 2]`产生零接受的预订。 天真的贪婪者可能仍会尝试分配，但一定会失败。 

另一种情况是多个表可以满足同一请求。 例如，大小为 3 的请求和表格`[3, 5, 10]`。 如果我们首先将其分配给最大的表，我们可能会阻止未来仅适合大表的更大请求，从而减少总利润。 

第三种情况是两个大的利润请求竞争一个大表，而较小的请求适合其他地方。 单纯地贪图利润可能会错误地分配大表并阻止更好的全局分配。 

## 方法

 暴力视图是考虑直接将请求分配给表。 对于每个请求，我们可以尝试将其分配给任何适合的未使用表，递归地探索所有组合。 这实际上变成了对请求和表之间所有匹配的搜索，其中每一步我们要么跳过一个请求，要么将其分配给可能的 k 个表之一。 

在最坏的情况下，这个分支生长得非常快。 即使我们只考虑分配选择，每个请求也可以分支到最多 k 个可能性，给出大约 O(k^n) 的结构，这远远超出了可行的范围。 

关键的观察是，该结构基本上是与权重进行二分匹配，但有一个非常具体的约束：表容量是小整数，并且多个表可以共享相同的容量。 这使我们能够将表侧按容量压缩为计数，而不是单独处理表。 

一旦我们按容量对表进行排序并维护每种容量剩余的数量，问题就变成了逐一选择请求并决定是否将它们放入任何可用的兼容容量中。 这表明对请求和可用表容量分布进行动态编程。 然而，更有效的解释是按固定顺序处理请求，并使用始终为小请求保留小表的结构贪婪地将它们分配给可能最好的表。 

标准技巧是按利润降序对请求进行排序，并尝试将每个请求分配到可以容纳它的最小表。 这是最佳的，因为大表对于大请求更有价值，而在小请求上浪费它们会降低未来的可行性。 

我们可以以频率数组或排序结构维护可用表，并对每个请求执行二分搜索以找到最小的可用表。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(k^n) | O(k^n) | O(n + k) | 太慢了 |
 | 最优（贪婪+搜索） | O(n log k) | O(n log k) | O(k) | 已接受 |

 ## 算法演练

 我们首先构建表，以便我们可以有效地查询哪些表可用于给定的组大小。 

1. 将所有表容量按升序排列。 这使我们始终能够找到适合请求的最小桌子。 
2. 按利润降序对请求进行排序。 原因是应首先考虑利润较高的请求，因为稍后很难以最佳方式放置它们。 
3. 对于每个请求，对已排序的表列表执行二分搜索，以查找容量至少为组大小的最小未使用表。 
4. 如果存在这样的表，则将请求分配给它，将该表标记为已使用，并将利润添加到答案中。 
5. 如果不存在合适的表，则跳过该请求。 
6. 将分配存储为请求索引和表索引对，以便我们可以重建输出。 

微妙之处在于，一旦使用表，它就会被永久删除，因此我们必须维护一个支持删除的结构。 由于 k 很小，因此带有标记的简单列表或通过二分搜索和删除实现的类似多重集的结构就足够了。 

### 为什么它有效

在该过程中的任何时刻，我们都会维护这样的属性：在所有未分配的请求中，我们总是尝试将最高利润的请求首先放入可以容纳它的最小表中。 这保留了一个不变量，即在不减少总利润的情况下，任何已接受的请求都不能与另一个请求交换，因为任何替代分配要么不必要地使用更大的表，要么阻塞稍后需要的更高容量的表。 贪婪的选择将容量稀缺性与请求大小排序结合起来，确保为大型请求保留大型表，这是唯一可以使用它们的请求。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n = int(input())
requests = []
for i in range(n):
    c, p = map(int, input().split())
    requests.append((p, c, i + 1))

k = int(input())
tables = list(map(int, input().split()))

tables.sort()
used = [False] * k

requests.sort(reverse=True)

assignments = []
total = 0

for p, c, idx in requests:
    best = -1
    for j in range(k):
        if not used[j] and tables[j] >= c:
            best = j
            break
    if best != -1:
        used[best] = True
        total += p
        assignments.append((idx, best + 1))

print(len(assignments), total)
for a, b in assignments:
    print(a, b)
```该解决方案对表进行一次排序，以便我们始终可以从最小容量到最大容量进行扫描。 这`used`array 确保每个表最多被消耗一次。 

请求按利润降序排序，这会驱动贪婪排序。 对于每个请求，我们线性扫描表以找到第一个适合的可用表。 给定 k ≤ 1000，这种 O(nk) 扫描在实践中仍然足够快。 

一个微妙的实现细节是在排序之前保留原始请求索引，因为输出需要原始编号。

    import sys
    input = sys.stdin.readline

    req = []
    for i in range(n):
        c, p = map(int, input().split())
        req.append((p, c, i + 1))

    tab = list(map(int, input().split()))

                break

        out.append(f"{a} {b}")
    return "\n".join(out)

 ## 边缘情况

 一种极端情况是没有桌子可以满足任何要求。 对于输入，其中所有`r_i < c_i`，扫描总是失败并且没有记录任何分配。 该算法正确返回零利润，因为每次请求迭代都找不到可用的表。 

另一个边缘情况是多个表共享相同的容量。 由于表是通过索引来区分的，单独标记它们可以确保我们永远不会重用物理表，即使容量相同。 

最后一种情况是存在大表但小请求按利润顺序首先到达。 因为我们总是首先选择最高利润，所以如果大的请求具有更高的价值，仍然会被优先考虑，从而防止过早消耗大容量的经典贪婪错误。
