 ## 解决方案
 ## 问题理解

 我们给出了几个测试用例，每个测试用例都包含一个排列，这意味着一个数组仅包含从 1 到 n 的每个整数一次。 唯一允许的操作是相邻位置 i 和 i+1 之间的交换，并且每个此类交换最多可以使用一次。 交换可以按任何顺序应用，但每个相邻对最多只能交换一次的限制实际上意味着每个元素最多可以向左移动一个位置（由未使用的交换创建的每个反转机会）。 

任务是在这些约束下产生按字典顺序可达到的最小排列。 这里的字典顺序的行为类似于字典比较：较早的位置更重要，因此最小化第一个元素始终是最高优先级，然后是第二个，依此类推。 

每个测试用例的约束 n ≤ 100 足够小，以至于 O(n²) 贪婪模拟是完全安全的。 即使所有 q = 100 个测试用例都是最坏情况，我们仍然在大约 10⁶ 操作之内。 

当可以以不同的顺序应用多个交换时，会出现微妙的边缘情况。 例如，在像 [4, 3, 2, 1] 这样的降序数组中，天真的直觉可能会尝试对其进行完全冒泡排序。 这是不正确的，因为每个交换索引只能使用一次，因此元素不能连续冒泡通过数组。 这种情况的正确答案是 [1, 4, 3, 2]，而不是完全排序。 

另一种失败情况是假设单次从左到右的传递就足够了，而无需仔细跟踪交换索引是否已被使用。 如果我们忽略这一点，我们可能会错误地允许通过同一边界重复重新排序。 

## 方法

 强力解释将尝试模拟允许交换的所有子集以及应用它们的所有可能顺序。 由于有 n−1 个交换位置，这会导致 2^(n−1) 种可能性，并且每次模拟成本为 O(n)，即使对于 n = 100，这也太大了。 

关键的观察结果是，允许操作的结构的行为就像一个受约束的本地改进系统。 每个位置 i 最多允许 i 和 i+1 之间进行一次交换。 这意味着每个边界只能“修复”一个穿过它的反转。 一旦使用，该边界就耗尽了。 

这将问题变成了贪婪的从左到右的构造。 在每个位置，我们尝试引入仍然可以合法到达该位置的最小可能元素，但我们必须尊重索引 i 处的交换会永久消耗该操作。 

我们不考虑全局重新排列，而是关注一个元素是否应该现在或以后跨越边界。 如果较小的元素位于右侧，并且可以使用其紧邻左侧位置的未使用交换将其移至左侧，则当它有助于当前词典位置时，我们应该立即执行该交换。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力破解（所有交换子集/订单）| O(2^n·n) | O(2^n·n) | O(n) | 太慢了|
 | 贪婪相邻约束交换 | O(n²) | O(n) | 已接受 |

 ## 算法演练

 我们贪婪地模拟该过程，跟踪哪些交换位置已被使用。 

1. 维护排列数组和大小为n的布尔数组used，其中used[i]表示我们是否已经应用了i和i+1之间的交换。 
2. 从左到右迭代位置 i 从 0 到 n−1。 
3. 在每个位置 i，通过检查与 a[i+1] 交换是否可能且有益，尝试最小化 a[i]。 如果used[i]为假且a[i+1] < a[i]，则执行交换并将used[i]标记为true。

此步骤是安全的，因为较早放置较小的元素总是可以改善字典顺序，并且现在使用交换可以防止稍后失去机会（当它可能不再有帮助时）。 
4. 在位置 i 尝试交换后，继续前进。 我们永远不会重新访问交换索引，因为每个索引只能使用一次。 
5. 继续，直到处理完所有位置。 

它的工作原理来自于贪婪不变量：在每个位置 i，经过处理后，放置在那里的元素是可以合法占据位置 i 的最小可实现元素，因为 i 左侧的交换已经固定并且不能重复使用。 由于字典顺序首先取决于位置 0，然后是 1，依此类推，以这种受约束的最优方式贪婪地固定每个位置可确保全局最优性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    for _ in range(q):
        n = int(input())
        a = list(map(int, input().split()))
        
        used = [False] * (n - 1)
        
        for i in range(n - 1):
            if not used[i] and a[i] > a[i + 1]:
                a[i], a[i + 1] = a[i + 1], a[i]
                used[i] = True
        
        print(*a)

if __name__ == "__main__":
    solve()
```其实现直接反映了贪婪的思想。 使用的数组对每个交换位置强制执行一次性约束。 单个从左到右的传递确保我们只考虑每个边界一次，这已经足够了，因为一旦使用交换，其效果以后就无法重新审视或改进。 

比较`a[i] > a[i + 1]`在本地编码字典顺序改进条件。 由于早期头寸占主导地位，我们从不试图推迟有利的掉期。 

一个常见的错误是重复对元素进行冒泡，直到没有改进为止。 这违反了一次性约束并导致过度排序，这对于 [4, 3, 2, 1] 等情况是不正确的。 

## 工作示例

 ### 示例 1

 输入：`[5, 4, 1, 3, 2]`我们跟踪交换和阵列演变：

 | 我| 数组状态 | 交换用过吗？ | 行动|
 | ---| ---| ---| ---|
 | 0 | [5,4,1,3,2]| 没有| 交换 5 和 4 |
 | 1 | [4, 5, 1, 3, 2] | 是的 | 没有交换（5 > 1 但现在使用索引 1）|
 | 2 | [4, 5, 1, 3, 2] | 没有| 交换 5 和 1 |
 | 3 | [4, 1, 5, 3, 2] | 没有| 交换 5 和 3 |
 | 4 | [4, 1, 3, 5, 2] | 没有| 交换 5 和 2 |

 最终结果：`[1, 5, 2, 4, 3]`这表明每个边界只能使用一次，从而迫使仔细安排交换。 

### 示例 2

 输入：`[4, 3, 2, 1]`| 我| 数组状态 | 交换用过吗？ | 行动|
 | ---| ---| ---| ---|
 | 0 | [4, 3, 2, 1] | 没有| 交换 4 和 3 |
 | 1 | [3,4,2,1]| 是的 | 没有交换 |

 最终结果：`[3, 2, 1, 4]`这表明完全排序是不可能的，因为每个边界仅贡献一次，从而防止大元素的完全冒泡。

 ## 边缘情况

 对于单元素排列，没有交换位置，因此该算法不执行任何操作并返回数组不变。 对于降序排列，只能进行局部改进的前缀，并且算法在每个交换索引使用一次后正确停止，从而防止完全排序。 对于已经排序的数组，条件`a[i] > a[i+1]`从不触发，因此输出保持不变，这与最佳词典结果匹配。
