 ## 解决方案
 ## 问题理解

 我们有两个长度相等的二进制字符串。 两个字符串总是以 a 开头`0`并以`1`。 我们可以重复应用一种操作，该操作采用一个字符串内的一个段，前提是该段的端点包含相同的字符，然后强制这些端点之间的每个字符变成相同的端点值。 

此操作的效果最好理解为在选定的间隔内“传播”一个值，但前提是两端都已经同意。 If you pick two`0`s，你可以把他们之间的一切变成`0`。 如果你选两个`1`s，您可以类似地用`1`s。 由于您可以在任一字符串上任意多次执行此操作，因此每个字符串都会通过合并相同值的区域来演变，直到它稳定为更粗糙的块结构。 

问题是我们是否可以使用这些操作独立地转换两个字符串，以便它们在某个时刻变得相同。 

限制总体上很小：测试用例的总长度最多为 5000。这立即排除了每个测试用例的任何立方或更差的情况，但更重要的是表明解决方案应该是每个字符串线性或接近线性的，可能使用结构表征而不是操作模拟。 

一个微妙的点是该操作不允许更改端点，只允许在相同端点之间传播现有值。 所以我们不能任意翻转位，也不能在之间创建新的转换`0`和`1`除非它们已经以受控的方式存在。 

一个天真的错误是认为我们总是可以自由地重新排列片段。 例如，在：```
a = 0101
b = 0011
```看起来我们可以将两者“平滑”成类似的东西`0001`，但实际上可达状态受到原始游程结构的限制。 

真正的挑战是理解字符串的哪些方面在操作下是不变的。 

## 方法

 关键的观察结果是，该操作只能跨间隙合并具有相同值的相邻区域，这意味着它永远不会在之间引入新的交替`0`和`1`。 相反，它仅通过展平中间段来删除一些交替。 

因此，每个字符串本质上都可以简化为一系列交替的块，但是只有当它们共享相同类型的端点时，才可以合并其中的块。 随着时间的推移，这意味着我们可以转动两个之间的任何部分`0`进入所有`0`，类似地对于`1`s，只要我们选择已经存在的端点。 重要的结果是我们可以消除相同字符之间的任何内部“噪音”，但我们不能改变第一次出现的顺序`0`和`1`发生根本性转变。 

更精确的看待它的方法是根据连续的相等字符的运行来思考。 该操作允许我们在相反字符的中间运行中合并相同字符的运行，但前提是端点匹配。 这意味着在每个字符串中，我们可以有效地将其“压缩”为规范形式，其中每个最大块都是实心的，而且，如果任何块以相同字符为界，则可以扩展以覆盖中间位置。 

对于等效性而言，重要的是两个字符串是否可以转换为通用的“块兼容性结构”。 关键的不变量是位置的序列，其中`0`和`1`必须在每个字符串可实现的任何最终配置中交替。 

突破性的简化在于我们实际上不需要模拟操作。 相反，我们观察到每个字符串都可以转换为任何遵循贪婪扫描中首次遇到转换的位置相对顺序的字符串。 这导致对每个字符串如何“支持”每个索引处的分配进行贪心比较。 

标准解决方案简化为通过跟踪强制更改的最早和最新可行位置来检查两个字符串是否可以简化为相同的规范代表。 实际上，这成为对交替运行定义的段的一致性检查。 

出现了一个更简单的等效公式：将每个字符串视为对位置的诱导约束`0`- 段和`1`-分段必须撒谎，并验证是否存在共同的细化。 这减少了比较字符串切换值的索引序列并确保它们在可行的合并下对齐。 

一个更直接、更可实现的表征是：

 如果我们扫描两个字符串，我们可以维护每个位置的前缀是否在可实现的合并中强制产生矛盾。 该条件简化为验证每当一个字符串强制另一个字符串无法通过合并模拟的转换结构时，我们就会拒绝。 这变成了仔细跟踪有效性窗口的线性扫描。

 ## 算法演练

 1. 将两个字符串压缩为连续的相等字符。 每次运行都由其字符和长度表示。 这给出了转换发生位置的结构视图。 
2. 对于每个字符串，考虑游程边界的顺序。 由于操作可以合并相同端点的运行，因此我们实际上可以删除某些边界，但永远不会对它们重新排序。 
3. 唯一有意义的不变量是之间转换的相对模式`0`和`1`。 我们跟踪每个字符串是否可以简化为与给定的翻转子序列一致的任何模式。 
4. 我们贪婪地比较两个运行序列，模拟匹配过程，其中我们尝试对齐两个字符串的运行。 
5. 如果在任何时候一个字符串需要一个转换，而另一个字符串中的兼容运行无法匹配，我们就断定这是不可能的。 
6. 如果所有的运行都可以在这些合并规则下匹配，我们得出结论可以将两个字符串转换为通用形式。 

### 为什么它有效

 该操作从不引入新的交替； 它仅通过在由相同端点界定的线段上扩展字符来删除它们。 因此，强制转换的相对顺序一直保留到删除，并且两个字符串必须承认稳定转换的公共子序列。 该算法有效地检查它们的运行结构是否允许在删除内部边界的情况下进行共同细化，这正是可变换性的条件。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def compress(s):
    runs = []
    n = len(s)
    i = 0
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        runs.append((s[i], j - i))
        i = j
    return runs

def solve_case(a, b):
    ra = compress(a)
    rb = compress(b)

    # We compare run structures in a greedy aligned way.
    i = j = 0

    while i < len(ra) and j < len(rb):
        ca, la = ra[i]
        cb, lb = rb[j]

        if ca != cb:
            return False

        # We can match min length and reduce both
        take = min(la, lb)
        la -= take
        lb -= take

        ra[i] = (ca, la)
        rb[j] = (cb, lb)

        if la == 0:
            i += 1
        if lb == 0:
            j += 1

    return i == len(ra) and j == len(rb)

t = int(input())
for _ in range(t):
    a = input().strip()
    b = input().strip()
    print("YES" if solve_case(a, b) else "NO")
```实现首先将每个字符串压缩为运行，因为只有相等块之间的转换对任何操作都很重要。 然后，贪婪匹配步骤尝试按顺序对齐相同字符的运行，像合并过程一样消耗长度。 如果在任何阶段字符不同，则意味着一个字符串需要结构转换，而另一个字符串在允许的操作下无法重现。 

一个微妙的一点是，我们从不尝试“创建”新的运行。 合并逻辑仅减少运行长度，这反映了操作仅消除边界而不引入新边界的事实。

 ## 边缘情况

 一个棘手的情况是两个字符串大量交替但共享相同的端点。 例如，`010101`相对`011111`。 一种幼稚的方法可能会比较零和一的计数，但这忽略了早期结构比总数更重要的事实。 该算法处理这个问题是因为在贪婪对齐期间立即出现运行不匹配。 

另一种情况是，一根弦已经完全压扁成大段，而另一根弦则频繁交替。 尽管两者都包含相同的多集字符，但它们的运行结构在不违反排序约束的情况下无法协调。 压缩和匹配步骤尽早暴露这种不匹配，确保正确性。
