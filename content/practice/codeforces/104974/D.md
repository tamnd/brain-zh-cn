 ## 解决方案
 ## 问题理解

 我们沿着一条笔直的道路从位置 0 移动到位置 X，以每秒一米的速度行走。 沿途有固定坐标处的红绿灯。 每个交通灯都由其位置、初始颜色和控制其在红色和绿色之间永久交替的速度的周期参数来描述。 

运动是连续的。 当我们到达交通灯时，如果当时当前颜色是红色，我们可能必须等待。 否则我们立即通过。 唯一使我们的总旅行时间超出实际距离的就是等红灯。 

输入给出 n 个交通灯，每个交通灯都有一个位置 p、一个初始颜色 c（红色或绿色）和一个周期长度参数 t。 信号每 t 秒交替一次，这意味着其完整周期为 2t 秒。 如果它开始为红色，则红色从时间 0 持续到 t，然后绿色从 t 持续到 2t，依此类推。 如果它开始呈绿色，则表示相位交换。 

我们需要从 0 开始到达 X 的总时间，其中包括步行时间和所有等待时间。 

约束最多为 100000 个灯光，距离最多为 100000 个。这立即排除了任何尝试以小增量提前时间的模拟。 唯一可行的方法是在按位置排序后，在线性或接近线性时间内处理每个交通灯一次。 任何比 O(n log n) 或 O(n) 更差的解决方案都会太慢。 

当多个灯未按位置排序时，会出现微妙的故障情况。 如果我们按输入顺序处理它们，我们可能会模拟不符合空间顺序的灯光并在错误的时间计算等待。 如果我们忘记等待取决于到达的绝对时间，而不仅仅是经过的灯的数量，就会出现另一个问题。 

例如，考虑两个灯：

 输入：```
2 10
R 5 5
G 2 3
```如果按输入顺序处理，我们可能会在位置 2 之前处理位置 5，这在物理上是不可能的，并且会导致计时不正确。 

正确的输出取决于按递增位置顺序进行处理。 

## 方法

 直接模拟就是一秒一秒地从0走到X。 每一秒我们都会检查自己是否正站在红绿灯上，以及红绿灯是否迫使我们等待。 这是正确的，因为它准确地反映了真实的过程。 然而，距离高达 100000，并且等待也会显着延长时间，因此这种方法可能会降级为每秒 O(X) 的模拟步骤，并且在最坏的情况下变得太慢。 

更好的方法是认识到除了位置和时间之外没有什么是连续变化的。 在红绿灯之间，没有任何决策。 我们可以安全地从一个红绿灯跳到下一个红绿灯，并将距离添加为行进时间。 唯一重要的计算是确定我们是否必须在红绿灯处等待，这仅取决于当前时间模 2t。 

这一观察结果将问题简化为按位置对灯光进行排序并模拟单次传递，维护当前时间并在每个灯光处更新它。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 逐步模拟| O(X + 等待事件) | O(1) | O(1) | 太慢了|
 | 排序+单遍模拟| O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 1. 按位置升序对所有交通灯进行排序。 这是必要的，因为时间沿着空间路径演化，所以我们必须按照我们物理上到达光的顺序遇到光。 
2.初始化当前时间为0，当前位置为0。时间代表我们走了多长时间，包括所有的等待。 
3. 按排序顺序遍历每个交通信号灯。 
4. 加上从之前的位置走到当前灯光位置所需的时间。 由于速度为每秒 1 米，因此这只是距离差加上当前时间。 
5. 使用 current_time modulo (2t) 计算到达时刻交通灯的状态。 这给了我们重复周期内的阶段。 
6. 根据初始颜色，判断当前相位对应的是红色还是绿色。 如果到达时灯为红灯，则将当前时间提前到下一个绿灯间隔的开始时间。 该跳跃是通过相应地从 t 或 2t 中减去当前相位来计算的。 
7. 将当前位置更新为红绿灯位置并继续。 
8. 处理完所有灯光后，将最后一个灯光的最后一段添加到 X。 

关键思想是我们从不逐秒进行模拟。 我们只在有意义的事件点（即交通信号灯）之间跳转。 

### 为什么它有效

 在连续的交通信号灯之间，系统的状态完全由单个变量（当前时间）决定。 该路段不包含依赖于时间的事件。 在每个交通灯处，等待或通过的决定仅取决于当前时间对固定周期长度的模数。 由于这种计算是精确的，并且我们按空间顺序处理光，因此模拟保留了真实的连续时间行为，而无需近似。 不变的是，current_time 始终等于解决了截至该点所需的所有等待之后到达当前位置的确切时间。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, X = map(int, input().split())
    lights = []
    
    for _ in range(n):
        parts = input().split()
        c = parts[0]
        p = int(parts[1])
        t = int(parts[2])
        lights.append((p, c, t))
    
    lights.sort()
    
    cur_time = 0
    cur_pos = 0
    
    for p, c, t in lights:
        cur_time += (p - cur_pos)
        cur_pos = p
        
        cycle = 2 * t
        phase = cur_time % cycle
        
        if c == 'R':
            if phase < t:
                cur_time += (t - phase)
        else:
            if phase >= t:
                cur_time += (cycle - phase)
    
    cur_time += (X - cur_pos)
    print(cur_time)

if __name__ == "__main__":
    solve()
```该实现完全遵循基于事件的模拟。 排序可确保正确的空间顺序。 变量`cur_time`始终表示我们到达当前点的绝对时间。 模计算隔离了我们在信号周期内的位置。 仅当我们在红色间隔期间到达时，条件调整才会向前移动时间。 

一个常见的错误是在计算下一段之前忘记更新位置，这会破坏距离计算。 另一个微妙的问题是红绿间隔的错误分类，特别是对于绿色启动灯，其中周期的后半部分是红色的。

 ## 边缘情况

 一种边缘情况是光恰好在红色和绿色之间的边界处触发。 对于周期为 t 的红启动灯，精确到达阶段 0 意味着红色，而精确到达阶段 t 意味着绿色。 该实现正确地处理了这个问题，因为它在phase < t 上使用了严格的不等式。 

另一种边缘情况是多个灯光非常靠近时。 由于每个灯在下一次移动之前都会更新当前时间，因此连续等待可以正确复合而不会产生干扰。 

最后一种情况是 X 等于交通灯位置。 在这种情况下，最后一段在处理该光后会增加零距离，因此答案只是解析最后一个光后的时间，这与精确到达交点的物理解释相匹配。
