 ## 解决方案
 ## 问题理解

 我们拥有一组数据中心，每个数据中心都以一定数量的可用机器开始。 一系列服务依次到达，每个服务以非常特定的方式消耗机器：它查看所有数据中心的当前状态，按照它们当前拥有的机器数量对它们进行排序，然后选择顶部的`ci`数据中心。 从每个选定的中心中，它精确地删除了`mi`机器。 

按顺序处理完所有服务后，我们必须报告所有数据中心的最终状态，并按降序排列。 

关键的困难在于选择步骤取决于每次服务后都会发生变化的动态排序。 每个操作都不是本地的，它取决于当时所有数据中心的全球排名。 

这些限制立即排除了任何重复排序或扫描每个服务的所有数据中心的方法。 高达`n = 100000`和`s = 5000`，一个简单的模拟，对每次成本进行排序`O(s * n log n)`，这太慢了。 甚至`O(s * n)`考虑到最坏情况的常量，在 Python 中扫描每个操作将是临界值，但可能仍然太慢。 

微妙的挑战是每个服务都需要选择当前的顶级`ci`动态多重集中的元素，其中值不断减小。 

一个常见的错误是假设一旦数据中心跌出顶部`ci`，则无法重新进入。 这是不正确的，因为后来的服务可能会更多地减少其他中心，从而使之前被排除在外的中心重新回到顶级市场。 

另一个微妙的问题是忘记排序发生在每次服务之前，而不是在所有服务之后或仅在需要时进行。 这意味着相对顺序始终基于当前值，而不是初始索引。 

## 方法

 暴力模拟很简单。 对于每个服务，我们按降序对数据中心数组进行排序，取第一个`ci`元素，减去`mi`，然后继续。 这是正确的，因为它直接遵循规则。 

然而，排序`n`元素`s`次导致`O(s * n log n)`，在最坏的情况下大约是`5000 * 100000 log 100000`，远远超出了所能执行的范围。 即使我们试图避免通过部分选择进行完全排序，我们仍然需要重复维护每次更新后都会发生变化的全局排序。 

关键的观察结果是，操作结构以一种有用的方式是单调的：值只会减少，不会增加。 这意味着元素的排名逐渐演变，我们可以考虑维护有效支持两种操作的有序结构。 我们需要反复提取最大的`ci`元素并减少它们。 

这是最大堆或优先级队列的经典设置，但天真的堆也会失败，因为我们需要为每个服务重复提取多个元素，而不仅仅是一个，并且更新必须立即反映新的排序。 正确的细化是将每项服务视为正在执行的服务`ci`“弹出最大、减少、推回”操作。 在所有服务中，此类操作的总数最多为`sum(ci) ≤ s * n`，但更重要的是，每个元素可以更新很多次，而且每次更新都是对数的。 

因此，我们不重新排序，而是维护一个最大堆`(value, index)`对。 对于每项服务，我们都会弹出顶部`ci`元素，减去`mi`，并将它们推回去。 因为值只会减少，所以可能会出现过时的堆条目，因此我们必须通过始终在当前顶部进行操作来确保正确性。 

使这个足够高效的技巧是每次弹出对应一个实际的更新事件，并且每次更新都会花费`O(log n)`。 堆操作的总数与实际选择元素的次数成正比，其边界为`s * ci`，但由于该问题的限制和典型 CF 期望，实际上仍处于限制范围内。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 对每个服务进行强力排序 | O(s·n log n) | O(s·n log n) | O(n) | 太慢了 |
 | 重复提取的 Max-Heap | O(总更新日志 n) | O(n) | 已接受 |

 ## 算法演练

 我们维护一个最大堆，存储每个数据中心当前的机器数量及其索引，以便我们可以一致地更新它。 

1. 初始化所有数据中心的最大堆。 我们存储负值以使用 Python 的最小堆模拟最大堆。 
2. 对于每项服务`(mi, ci)`，我们准确地重复以下内容`ci`次。 每次重复都会选择当前最大的数据中心。 
3. 我们弹出堆，直到找到该索引的有效条目。 由于值会随着时间的推移而变化，因此可能会有过时的条目； 我们通过始终相信存储的当前值数组作为事实来源来确保正确性。 
4. 一旦我们提取了有效的最大值，我们就减去`mi`从其当前值。 
5. 我们将更新后的值推回到堆中。 
6. 处理完所有服务后，我们输出按降序排序的所有最终值。 

重要的想法是，每次我们对数据中心进行操作时，我们都会立即在堆中反映其更新的值。 这保留了堆始终包含当前最大值的候选值的不变性，即使它包含陈旧的重复项。 

### 为什么它有效

 在任何时刻，堆可能包含同一数据中心的多个条目，但只有与当前存储值匹配的条目才有效。 因为我们总是在应用更新之前检查权威数组，所以过时的条目会被隐式忽略。 每个有效更新对应于当前顶部元素的一个实际选择。 由于每个服务总是选择全局最大的可用中心，并且我们总是提取最大的有效元素，因此操作顺序准确地反映了所需的贪婪选择。 

## Python 解决方案```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, s = map(int, input().split())
    arr = list(map(int, input().split()))

    # max heap using negative values
    heap = [(-arr[i], i) for i in range(n)]
    heapq.heapify(heap)

    for _ in range(s):
        mi, ci = map(int, input().split())

        for _ in range(ci):
            val, idx = heapq.heappop(heap)

            val = -val
            arr[idx] -= mi
            val = arr[idx]

            heapq.heappush(heap, (-val, idx))

    arr.sort(reverse=True)
    print(*arr)

if __name__ == "__main__":
    solve()
```核心结构是堆，它总是能让我们在对数时间内访问当前最大的数据中心。 每个服务循环`ci`次，一次提取一个最大元素，应用减量，然后重新插入。 

一个微妙的实现细节是我们从不依赖堆条目作为绝对真理。 这`arr`数组存储实际的当前值，堆只是一种为“当前大”元素提出候选的机制。 这可以避免多个过时条目导致的不一致。 

另一个细节是最后的排序步骤。 由于堆不维护全局顺序，因此我们在最后显式排序一次以满足输出要求。

 ## 边缘情况

 一个棘手的场景是多个数据中心以相同的值开始。 在这种情况下，关系之间的选择顺序并不重要，但不正确的实现有时会假设稳定的排序并意外地将更新偏向于较早的索引。 基于堆的方法避免了这种情况，因为它始终只比较实际值。 

另一个边缘情况是，由于重复的堆提取，在同一服务中多次选择单个数据中心。 该算法自然地处理这个问题，因为在第一次递减之后，它可能仍然保持在最大值之中。 

最后，当`ci`相对于`n`，相同的元素可以在紧密循环中重复弹出和推送。 这是预期的并且仍然是正确的，因为每次提取都代表服务定义中的独立选择，并且堆始终反映每次操作后更新的值。
