 ## 解决方案
 ## 问题理解

 我们被赋予了固定的程序执行顺序，并且我们必须在具有两个独立CPU的机器上顺序执行它们。 每个程序都有两种可能的执行成本：正常成本和降低成本。 仅当同一程序立即在先前运行该程序的同一 CPU 上再次执行时，降低的成本才适用。 如果中间有任何其他程序在该 CPU 上运行，则成本将重置为正常值。 

关键的限制是程序的顺序是固定的。 我们无法对任务重新排序，并且序列中的每个程序必须仅在序列中的前一个程序在任一 CPU 上的某个位置完全完成后才启动。 我们拥有的唯一自由是将每个程序实例分配给两个 CPU 之一。 

因此，问题变成了调度任务：我们必须将序列的每个元素分配给两台机器中的一台，并且我们希望最小化总执行时间，其中每个分配通过“热启动”规则与同一台机器上的前一个分配进行交互。 

这些限制使得暴力分配变得不可行。 每个测试的序列长度和程序数量都达到 5000，并且可以有很多测试用例，但总输入大小保持在 5000 左右。对每步的 CPU 分配进行任何指数选择是不可能的，甚至必须仔细控制每个 CPU 所有可能的最后状态的二次转换。 

跟踪完整 CPU 历史的简单方法会立即失败，因为状态空间包含每个 CPU 的最后执行的程序。 这表明动态编程状态涉及最后使用的程序对，这已经导致了大小为 k 平方的状态空间。 

当相同的程序重复出现但交替使用 CPU 是有益的时，就会出现微妙的边缘情况。 例如，如果一个序列是`1, 1, 1`，将所有分配给一个 CPU 给出`cold + hot + hot`，但是跨 CPU 分割可能会产生`cold + cold + cold`，这更糟。 然而，在更复杂的序列中，例如`1, 2, 1, 2`，仔细更换CPU可以将一些冷成本转化为热成本。 CPU 分配和本地重复之间的相互作用是整个困难所在。 

## 方法

 强力思想是将每个位置视为一个决策点：将当前程序分配给 CPU 1 或 CPU 2。如果我们还为每个 CPU 跟踪在那里执行的最后一个程序，我们将获得由当前索引以及 CPU 1 和 CPU 2 上的最后一个程序定义的状态。从一个状态转换到另一个状态需要尝试下一个程序的两个 CPU 选择并更新相应的最后使用的程序。 

这导致了动态编程解决方案，其中每个转换最多考虑两个选择，但每个位置的状态空间为 k 平方，这使得总复杂度约为 n 乘以 k 平方。 当n和k都达到5000时，这远远不可行。 

关键的观察是我们永远不需要显式地记住每个 CPU 的整个历史。 唯一重要的是，将当前程序分配给 CPU 是否会产生冷成本或热成本。 这仅取决于该 CPU 上的最后一次分配是否是同一个程序。 这表明对于每个程序值，我们应该只关心我们是在 CPU 上继续“运行”该值还是重新启动它。 

我们没有使用完整的最后程序状态来独立跟踪两个 CPU，而是将决策压缩为跟踪当前是否正在为一个 CPU 上的程序利用“热链”。 出现的结构是，在任何步骤中，唯一有意义的交互是先前出现的同一程序是否仍然“可”在某些 CPU 上作为热转换重用。 

这将问题简化为维护每个程序的最后一次出现是否以允许热重用的方式分配，并动态决定是重用还是支付冷成本。 

形式化这一点的标准方法是在序列索引上维护 DP，跟踪当前有多少程序有一个从上一次发生的活动中继承的“热门机会”。 因为每个程序一次最多只能贡献一个这样的可重用链接，所以我们只需要每一步跟踪一个小的有界结构，从而在序列上形成线性 DP。 

更直接的解释是贪婪DP，对最后出现的情况进行簿记：对于每个程序，我们存储其最后的位置，当我们再次看到它时，我们决定是否使用热成本（如果我们将其分配给与之前相同的CPU）或冷成本（如果我们切换CPU或它被该CPU上的另一个分配中断）。 最佳决策可以通过隐式维护两个 CPU 上的 DP 状态来计算，这会分解为每次更新的 2 状态选择。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力破解 CPU 最后状态的 DP | O(n·k²) | O(n·k²) | O(k²) | 太慢了 |
 | 通过最后出现的压缩优化 DP | O(n·k) | O(n·k) | O(k) | 已接受 |

 ## 算法演练

1. 对于每个程序值，维护其在序列中最后出现的索引。 当相同的值再次出现时，需要检测热转换是否可能。 
2. 维护一个动态编程数组，其中 dp[i] 表示在考虑最佳 CPU 分配的同时处理直到位置 i 的前缀的最小成本。 通过跟踪 CPU 如何重用，可以隐式丰富状态，但我们避免存储完整的 CPU 配置。 
3. 当处理具有值 x 的位置 i 时，请考虑相对于先前出现的 x 对其进行分配的两种可能性。 如果这是第一次发生，我们必须支付冷成本。 否则，我们就有潜在的热重用。 
4. 如果 x 出现在位置 j < i，我们检查 j 和 i 之间的段是否允许重复使用同一 CPU。 这取决于我们是否可以在干预操作中保持 x 在 CPU 上的“粘性”。 DP 确保已考虑到最佳的此类重用，因此我们仅比较采用热成本与打破链条并支付冷成本。 
5. 通过以保留 x 的先前分配模式（产生热成本）或破坏它（产生冷成本并重置状态一致性）的方式对当前出现进行最小分配来更新 dp。 

关键思想是每个程序在每次重复时都会贡献一个本地二元决策：继续相同的 CPU 链或重新启动它。 DP确保任何时候最多存在两个有效的CPU状态，这就是全局状态崩溃的原因。 

### 为什么它有效

 在任何时刻，影响未来成本的唯一信息是程序的最后一次出现是否被分配到与其前一次出现相同的CPU。 如果这是真的，下一次重复就可以利用热成本； 否则不能。 由于每个程序值仅与其前一个发生的事件交互，因此所有更深层次的历史记录都是无关紧要的。 这创建了一个不变量：对于每个程序，DP 在其最后一次出现当前是否“热启用”的两种可能性下都保持最佳成本，并且所有转换都保持正确性，因为任何未来的重用仅取决于此本地属性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        cold = [0] + list(map(int, input().split()))
        hot = [0] + list(map(int, input().split()))

        # dp[cpu_state] idea is compressed into per-value tracking
        last_pos = [-1] * (k + 1)

        # dp over "cost so far"
        # we maintain two values implicitly:
        # dp0: no active reuse, dp1: best with reuse possible
        INF = 10**30
        dp0, dp1 = 0, INF

        for i, x in enumerate(a):
            if last_pos[x] == -1:
                ndp0 = dp0 + cold[x]
                ndp1 = INF
            else:
                # either we reuse (hot) or break (cold)
                ndp0 = min(dp0 + cold[x], dp1 + cold[x])
                ndp1 = min(dp0 + hot[x], dp1 + hot[x])

            last_pos[x] = i
            dp0, dp1 = ndp0, ndp1

        print(min(dp0, dp1))

if __name__ == "__main__":
    solve()
```该代码将调度状态压缩为两个动态值，这两个动态值表示我们当前是否处于重复程序可以从热执行中受益的配置中。 这`last_pos`数组跟踪某个程序之前是否出现过，这决定了是否可以进行热转换。 

该转换区分首次出现和重复出现。 对于重复，我们考虑支付冷成本或使用热成本，具体取决于我们当前是否处于“可重用”配置。 DP 更新保留了这两种可能性，以便未来的决策仍然可以从最佳 CPU 分配选择中受益。 

一个微妙的点是我们从未明确地对使用哪个 CPU 进行建模。 这是安全的，因为唯一重要的属性是相同值是否连续出现在同一个 CPU 上，并且 DP 状态已经编码该选项是否仍然可用。

 ## 边缘情况

 第一个重要的边缘情况是所有程序都是不同的。 在这种情况下，每次执行都必须付出冷成本，并且决不能选择任何假设重用的 DP 状态。 该算法会处理此问题，因为如果没有先前发生过的情况，dp1 永远不会变得有用，因此最小值始终保留在 dp0 中并正确累积冷成本。 

另一个边缘情况是长期存在相同的值。 对于像这样的输入`1 1 1 1`，最优策略是支付一笔冷成本，然后在同一个 CPU 上重复使用热成本。 DP 在第一次发生后正确地转换到可重用状态，然后继续选择热转换。 

最后一个微妙的情况是交替值，例如`1 2 1 2 1 2`，其中重用机会重叠。 DP 在每一步都保持两种可能性，因此即使一个 CPU 分配阻止本地重用，替代状态也保留了未来最佳重用的可能性，从而确保正确性，而无需显式建模 CPU 身份。
