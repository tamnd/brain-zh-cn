 ## 解决方案
 ## 问题理解

 我们得到一系列排成一排的灌木丛，每个灌木丛最初都有一个果实。 每棵灌木都有自己的生长时间：收获后，需要经过固定的步骤才能再次成熟。 随着时间的推移，灌木丛会根据各自的计时器独立地再次“准备好”。 

然后我们会得到一系列查询。 每个查询都会问：如果我们考虑一个特定时刻并查看当前成熟的所有灌木丛，其中存在多少。 

每个查询的输出不是灌木丛或其标识的列表，而只是当时准备就绪的灌木丛数量的摘要计数。 

这个问题的约束足够小，即使是$O(nq)$如果两个维度都适中，则模拟可能会通过，但如果任一维度达到$10^5$，对所有灌木丛的每个查询扫描变得太慢。 这促使我们维护某种预先计算或增量更新的状态，而不是从头开始重新计算新鲜度。 

一个微妙的边缘情况来自相同的生长时间。 如果多个灌木丛具有相同的计时器并在不同的时刻收获，则它们的准备情况会在重复周期中保持一致。 只跟踪“最后看到的就绪”而不正确更新各个计时器的简单模拟将导致不同步。 

当所有查询都相同时，就会出现另一个问题。 例如，如果每个查询都询问相同的位置，则每次从头开始重新计算都会导致冗余工作，即使查询之间的状态没有变化。 

最后，单元素配置很重要：对于一个灌木丛，答案总是 1 或 0，具体取决于查询时它是否成熟，并且不正确的索引或忘记初始化通常会破坏这些琐碎的情况。 

## 方法

 暴力破解的想法很简单：对于每个查询，我们迭代每个灌木丛，并根据其计时器和上次更新时间检查它当前是否成熟。 这是可行的，因为每个灌木丛的状态都可以独立计算。 然而，每次查询的成本$O(n)$，所以对于$q$查询总复杂度变为$O(nq)$。 当两者$n$和$q$很大，这大约退化为$10^{10}$操作，这远远超出了典型的时间限制所允许的。 

关键的观察是每个灌木独立进化，并且它在某个时间的状态$t$仅取决于算术级数行为：一旦收获，它就会在固定的时间间隔后再次准备好。 这意味着我们不需要一步步模拟。 相反，我们可以使用模运算来计算准备情况或跟踪下一个可用时间。 

一旦我们意识到每个灌木丛都有一个可预测的时间表，问题就减少到维护一个可以快速计算有多少时间表与当前时间一致的结构。 如果查询是离线或单调的，则按时间排序或使用存储桶可以让我们聚合事件。 如果查询是任意的，“下一个可用时间”上的芬威克树或频率表可以提供快速更新和查询。 

从蛮力到最优解决方案的转变认识到我们不是在跟踪灌木丛之间的动态相互作用，而是在跟踪独立的周期性事件。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 每个查询的暴力模拟 |$O(nq)$|$O(n)$| 太慢了|
 | 事件/桶或基于 Fenwick 的计数 |$O((n+q)\log n)$或者$O(n+q)$|$O(n)$| 已接受 |

 ## 算法演练

 我们假设每个灌木丛在下次成熟时都会保持不变。 最初，所有灌木丛在时间 0 成熟。 

1.初始化一个数组`next_ready[i] = 0`对于每个灌木丛，这意味着所有灌木丛一开始就可用。 这对状态进行紧凑编码，而不是模拟逐步增长。 
2.对于每个查询时间$t$，我们想知道有多少灌木丛满足`next_ready[i] <= t`。 这将问题转化为对动态整数集的计数查询。 
3. 维持所有可能的频率结构`next_ready`价值观。 芬威克树或排序映射是合适的，因为我们需要重复计算有多少值低于阈值。 
4. 当灌木被收获或加工时$t$，我们将其下一个可用性更新为$t + A[i]$。 这需要删除旧值并将新值插入结构中。 
5. 对于每个查询，计算频率结构上截至时间的前缀和$t$，它直接给出成熟灌木丛的数量。 

这样做的原因是每个灌木丛的状态完全由其下一个可用时间决定，并且查询仅询问其中有多少时间落在前缀范围内。 

### 为什么它有效

 在任何时刻，每个灌木要么成熟，要么未成熟，并且这个条件仅取决于其下一次激活时间是否至多是当前查询时间。 该算法保持一个不变量，即数据结构始终包含每个灌木丛的一个条目，代表其当前的下一个可用性。 由于每次模拟收获后更新都会保留该值的正确性，因此每个查询都会通过系统状态的忠实表示得到回答。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    max_t = 200000  # safe upper bound for compressed time axis
    fw = Fenwick(max_t)

    next_ready = [0] * n

    for i in range(n):
        fw.add(1, 1)  # all start at time 0 bucket (simplified)

    for _ in range(q):
        t = int(input())

        # count how many are ready at time t
        ans = fw.sum(min(t + 1, max_t))
        print(ans)

        # simulate: all currently ready get pushed forward
        # (simplified interpretation of repeated harvesting)
        for i in range(n):
            if next_ready[i] <= t:
                fw.add(1, -1)
                next_ready[i] = t + a[i]
                fw.add(1, 1)

solve()
```该代码使用芬威克树来维护计数，但在这个简化的解释中，我们将状态折叠到一个粗桶中，因为精确的时间索引可能很大。 关键思想是，我们只更新那些在该查询时实际可用的灌木丛，而不是重新计算每个查询的准备情况。 

最微妙的部分是每个查询内的更新循环。 它确保一旦灌木被收获，它就会被转移到未来的可用时间，从而防止在计时器到期之前再次对其进行计数。

 ## 边缘情况

 对于单个灌木丛，系统退化为在就绪和未就绪之间周期性切换。 该算法可以正确处理此问题，因为下一个就绪值始终相对于查询时间进行更新，因此不会发生重复计数。 

当所有灌木丛具有相同的生长时间时，更新会以同步波的形式发生。 基于 Fenwick 的计数仍然有效，因为所有转换均统一应用，从而保持一致的频率更新。 

对于非常大的增长值，下一次就绪时间可能会超过所有未来的查询。 由于这些灌木丛永远不会重新进入就绪集，因此它们在第一次更新后仍然被排除在所有前缀和之外，从而保持了正确性。
