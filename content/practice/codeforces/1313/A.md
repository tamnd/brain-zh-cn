 ## 解决方案
 ## 问题理解

 我们得到了三种独立的供应：饺子、果汁和煎饼。 每个访问者都会收到这三个项目的子集，但有两个限制。 首先，访问者只能收到每种项目类型的一个。 其次，没有两个访问者可能会收到完全相同的子集。 每位访客必须至少收到一件物品，因此不允许空件。 

因此，餐厅实际上正在尝试分配一组三个资源的不同非空子集，同时尊重每个子集消耗每个所选资源的一个单位。 问题是在给定每个项目的有限数量的情况下可以实现多少个不同的子集。 

每个测试用例都很小：a、b、c 的计数最多为 10，并且最多有 500 个测试用例。 这立即排除了任何依赖于迭代大型输入的指数构造，但更重要的是，它表明我们可以安全地推理三个项目的所有 7 种可能的子集类型，而不必担心性能。 

一个关键的微妙之处是子集在资源使用方面重叠。 例如，如果我们给某人“饺子+果汁”，那么会消耗一个饺子和一份果汁，但也消除了以后饺子稀缺时“只给饺子”的可能性。 仅重复形成最大可用子集的幼稚贪婪策略可能会失败，因为它没有考虑子集如何交互。 

一种边缘情况是仅存在一种类型的项目。 如果a = 5，b = 0，c = 0，那么只有“饺子”有效，所以答案是1，而不是5。另一种是当资源非常不平衡时，例如a = 10，b = 0，c = 0，或a = 10，b = 10，c = 0。第二种情况我们可以形成“饺子”，“果汁”，“饺子+果汁”，给3个访客，即使 简单地计算总项目数表明可能有 20 份。 项目计数和子集组合之间的不匹配是核心困难。 

## 方法

 一个蛮力的想法是显式构建所有可能的访问者分配。 {A, B, C} 只有 7 个有效的非空子集。 人们可以尝试递归地将子集分配给访问者，每次减少资源并确保迄今为止使用的子集的唯一性。 这是可行的，因为状态空间很小，但如果推广的话，它会变得低效：对于更大的约束，子集组合的数量随着访问者分配的数量呈指数增长，在 k 个访问者的最坏情况下大约为 7^k 的数量级。 尽管这里 k 很小，但这种方法隐藏了问题的真实结构并且是不必要的。 

关键的观察是，子集的实际身份并不重要，超出了它们的计数。 由于只有三个项目，完整的解决方案仅取决于我们拥有的每个项目的数量，以及我们如何将它们分布在 7 个可能的非空子集中。 每个子集独立消耗资源，最优策略仅受供应限制的约束。 

更直接的理解方法是枚举所有可能的子集多重集，但更简单的是组合推理。 对于三个项目，不同的非空子集的最大数量为 7。因此答案不能超过 7。同时，如果我们有足够的资源，我们可以通过为每个子集分配一个访问者来实现所有 7 个子集。 因此，问题简化为确定可用计数实际上可以支持这 7 个子集中的多少个。

每个子集都有一个已知的需求向量，我们希望选择尽可能多的不同子集，这样就不会过度使用资源。 因为宇宙是如此之小，我们可以直接推断限制因素总是要么是总资源，要么是只有 7 个可能的子集这一事实。 最佳结果受到适当划分的总和和结构约束的限制，但对于这个问题，已知的简化是答案是：$$\min(a + b + c, a + b + c - \max(0, \text{overlap reduction})) \rightarrow \text{simplifies to a direct greedy evaluation of subsets}$$更具体地说，由于每个访问者至少消耗一个项目并且子集都是不同的，因此我们可以首先贪婪地形成所有单项访问者，然后是成对的，然后是三元组，确保我们永远不会超过可用计数。 由于数字非常小，我们可以隐式模拟所有子集使用模式，但最干净的已知解决方案是答案等于：$$\min(a + b + c, 7)$$当资源严重倾斜时进行修正，这是通过观察 7 个子集中的每一个最多可以存在来自动处理的，并且在给定足够资源的情况下始终可以达到该限制的可行性。 

因此，问题简化为检查我们可以实现多少个子集，这完全是通过对 7 种可能性的简单贪心计算来确定的。

 ## 算法演练

 我们明确构造三个资源的不同非空子集的最大数量，同时尊重可用性约束。 

1. 将每种访问者类型视为 {A, B, C} 的 7 个可能子集之一。 这些对应于A、B、C、AB、AC、BC、ABC。 
2. 尝试为每个子集分配一名访问者，但前提是该子集存在足够的资源。 
3. 如果所有所需资源至少有一个剩余单元，则子集是可行的。 
4. 我们贪婪地按照首先优先考虑较大子集的顺序来选择子集，因为它们消耗更多资源并且可能会阻塞未来的分配。 
5. 每次分配子集时，我们都会减少相应的资源计数并增加答案。 
6. 继续下去，直到无法形成更多子集为止。 

按大小排序之所以有效，是因为子集越大，限制越严格。 如果我们延迟分配它们，我们可能会在较小的子集中消耗它们所需的资源，从而降低未来的灵活性。 

### 为什么它有效

 每个访问者对应于三个元素的唯一子集。 该算法在资源约束下构造最大的不同可行子集集。 由于每个子集最多被考虑一次并且仅在可行的情况下才被接受，因此不会违反资源约束。 较大子集的贪婪优先级可确保尽可能长时间地保留资源密集型配置，从而防止较小子集过早消耗。 因为只有七个子集，并且每个子集都被评估一次，所以任何最佳排列都不能超过构造的解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve_case(a, b, c):
    ans = 0

    # try largest subsets first
    # ABC
    if a > 0 and b > 0 and c > 0:
        ans += 1
        a -= 1
        b -= 1
        c -= 1

    # AB, AC, BC
    if a > 0 and b > 0:
        ans += 1
        a -= 1
        b -= 1

    if a > 0 and c > 0:
        ans += 1
        a -= 1
        c -= 1

    if b > 0 and c > 0:
        ans += 1
        b -= 1
        c -= 1

    # A, B, C
    if a > 0:
        ans += 1
        a -= 1

    if b > 0:
        ans += 1
        b -= 1

    if c > 0:
        ans += 1
        c -= 1

    return ans

t = int(input())
out = []
for _ in range(t):
    a, b, c = map(int, input().split())
    out.append(str(solve_case(a, b, c)))

print("\n".join(out))
```该实现直接反映了子集构建策略。 第一个块处理三重子集，这是最严格的，因为它同时消耗所有三个资源。 然后我们处理所有成对子集，每个子​​集消耗两个资源。 最后，我们分配单项访客。 这种排序可以防止共享资源过早耗尽，从而阻塞更大的子集。 

每个条件在消耗资源之前都会检查可用性，确保每一步的可行性。 每个成功形成的子集答案都会累积一个。

 ## 边缘情况

 用于输入`0 0 0`，没有子集是可行的，因为每个子集都需要至少一个资源单元。 该算法正确地跳过所有条件并返回零。 

用于输入`10 10 10`，所有七个子集都是可行的。 该算法首先消耗 ABC，然后是 AB、AC、BC，最后是单例，达到答案 7。这表明贪婪排序不会阻塞任何必要的子集，因为资源很丰富。 

用于输入`1 0 0`，只有A是可能的。 该算法跳过所有多项目子集，只分配 A 一次，产生 1，它与唯一可行的访问者配置匹配。
