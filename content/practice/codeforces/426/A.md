 ## 解决方案
 ## 问题理解

 我们有一个容量很大的杯子`s`和几个装有水的杯子。 玩家轮流选择一个非空的杯子并将其所有水倒入杯子中。 杯子开始是空的，并且水永远不会被除去。 如果任何时候杯子内的水量超过其容量，则采取该行动的玩家就输了。 

问题是杯子是否可以按某种顺序倒，这样就不会有人丢失。 

关键细节是每个杯子最终都必须被完全倒出。 由于杯子只吸水，所以移动后的水量等于所有杯子体积的总和。 浇注顺序仅改变中间状态。 

限制很小。 最多有 100 个杯子，每个杯子的体积最多为 10 个。即使是对多种可能性进行强力搜索，在这里也能运行得足够快，但问题有一个更简单的观察，可以将所有内容简化为单一比较。 

一个常见的错误是认为浇注顺序很重要。 考虑这个输入：```
3 5
4 1 1
```正确答案是：```
NO
```粗心的做法可能会尝试倒`1`， 然后`1`， 然后`4`，希望存在更好的秩序。 但最终的水量总是`6`，超出杯子容量`5`。 由于所有杯子最终都必须被倒掉，因此某些玩家必须溢出杯子。 

当总水量与杯子容量完全匹配时，会出现另一种边缘情况：```
2 7
3 4
```正确答案是：```
YES
```仅当数量严格大于容量时才会发生溢出。 准确到达`7`是允许的。 

第三种容易忽视的情况是当有很多小杯子时：```
5 4
1 1 1 1 1
```正确答案是：```
NO
```每个单独的动作看起来都无害，但在第五个杯子之后，杯子里包含了`5`，超出了容量。 

## 方法

 最直接的蛮力想法是尝试每一种可能的浇注顺序。 对于每个排列，我们模拟该过程并检查杯子是否溢出。 

这是有效的，因为一旦我们选择了杯子的顺序，游戏就完全确定了。 如果至少一种排序可以避免溢出，则答案是`"YES"`。 

问题在于排列的数量呈阶乘增长。 和`n = 100`， 有`100!`可能的订单数量是天文数字。 即使是为了`n = 15`，在一秒钟之内穷举搜索已经是不可能的了。 

突破性的观察是顺序实际上并不重要。 

杯子里的水量只会增加。 倒完所有杯子后，杯子中的容量正好是所有杯子体积的总和。 如果这个总数超过了杯子的容量，那么在某个步骤中一定会发生溢出。 任何订购都无法避免它。 

另一方面，如果总体积最多为杯子容量，那么以任何顺序倒杯子都是安全的。 水位从未超过最终总数，并且最终总数已经合适。 

这将整个问题简化为检查：```
sum(a) <= s
```如果为真，则打印`"YES"`。 否则，打印`"NO"`。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n! × n) | O(n! × n) | O(n) | 太慢了|
 | 最佳 | O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1.读取杯子的数量`n`和杯子容量`s`。 
2. 阅读杯子容量列表。 
3. 计算所有杯子体积的总和。 
4. 将总水量与杯子容量进行比较。 

如果总数小于或等于`s`， 打印`"YES"`。 

否则，打印`"NO"`。 

### 为什么它有效

 杯子开始是空的，只添加水，而不会移除水。 经过所有移动后，杯子内的水总量等于所有杯子体积的总和。 

如果这个总数超过了杯子的容量，那么溢出是不可避免的，因为最终状态本身是无效的。 

如果总数适合杯子内，则每个中间状态也适合，因为中间数量总是小于或等于最终数量。 

由于这种单调行为，检查总和既是必要的也是充分的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n, s = map(int, input().split())
a = list(map(int, input().split()))

if sum(a) <= s:
    print("YES")
else:
    print("NO")
```该程序直接遵循算法的数学观察。 

第一行读取杯子的数量和杯子的容量。 第二行将所有杯子体积读取到列表中。 

关键的操作是`sum(a)`。 这将计算最终进入杯子的水总量。 

比较使用`<=`， 不是`<`。 达到精确的容量是允许的，因为只有当数量严格大于限制时，杯子才会溢出。 

不需要对排序进行特殊处理，因为证据表明排序不能改变结果。

## 测试用例```python
# helper: run solution on input string, return output string
import sys
import io

def solve():
    input = sys.stdin.readline

    n, s = map(int, input().split())
    a = list(map(int, input().split()))

    if sum(a) <= s:
        print("YES")
    else:
        print("NO")

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    out = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return out

# provided sample
assert run("3 4\n1 1 1\n") == "YES\n", "sample 1"

# minimum valid input
assert run("2 1\n1 1\n") == "NO\n", "minimum size with overflow"

# exact boundary
assert run("2 7\n3 4\n") == "YES\n", "sum exactly equals capacity"

# all equal values
assert run("5 10\n2 2 2 2 2\n") == "YES\n", "all equal and fits exactly"

# overflow by one
assert run("4 9\n2 2 2 4\n") == "NO\n", "sum exceeds by one"

# large input within limits
assert run(
    "100 1000\n" + "10 " * 100 + "\n"
) == "YES\n", "maximum-sized input"

 ## 边缘情况

 考虑总体积恰好等于杯子容量的情况：```
2 7
3 4
```该算法计算`3 + 4 = 7`。 自从`7 <= 7`，它打印`"YES"`。 

追踪过程：

 | 搬家后 | 杯中水|
 | ---| ---|
 | 开始| 0 |
 | 第一个杯子之后 | 3 |
 | 第二杯之后| 7 |

 杯子永远不会超过容量，因此平等必须被视为安全。 

现在考虑这样一种情况：每个杯子都很小，但总和却太大：```
5 4
1 1 1 1 1
```该算法计算`1 + 1 + 1 + 1 + 1 = 5`。 自从`5 > 4`，它打印`"NO"`。 

追踪过程：

 | 搬家后 | 杯中水|
 | ---| ---|
 | 开始| 0 |
 | 第一个杯子之后 | 1 |
 | 第二杯之后| 2 |
 | 第三杯之后| 3 |
 | 第四杯之后| 4 |
 | 第五杯之后 | 5 |

 溢出只发生在最后一步，但仍然是不可避免的。 

最后，考虑一个杯子已经接近容量的情况：```
3 5
4 1 1
```总计为`6`，所以算法打印`"NO"`立即地。 

尝试不同的订单没有帮助：

 | 订单| 最终水|
 | ---| ---|
 |`4,1,1`| 6 |
 |`1,4,1`| 6 |
 |`1,1,4`| 6 |

 最终的金额总是相同的，这就是顺序无关紧要的原因。
