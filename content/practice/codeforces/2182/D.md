 ## 解决方案
 ## 问题理解

 我们给出了几个独立的场景。 每个场景中都有$n$人们和$n+1$装饰品盒。 盒子$0$每个人都是特别的$i$有自己的私人盒子$i$。 每个盒子都以一定数量的装饰品开始。 

我们必须计算有多少种排列$n$人们是重复循环过程的“安全时间表”。 排列定义了人们行为的顺序：人$p_1$， 然后$p_2$， …， 然后$p_n$，然后该序列再次重复$p_1$，无限期地继续，直到所有装饰品都从盒子中取出。 

当一个人行动时，他们必须恰好拿走一个装饰品，但只能从任一盒子中拿走它$0$或者他们自己的盒子。 这个过程是灵活的，因为在每一步我们都可以选择从两个盒子中的哪一个中取出，但我们必须确保我们永远不会到达当前人没有可用的有效盒子可供取出的步骤，这意味着两个盒子$0$而他们的私人盒子此时是空的。 

任务是计算在整个过程中，有多少种排列允许至少一种有效选择装饰，直到所有装饰都用完为止。 

关键的困难在于排列并不能确定实际的选择，只能确定顺序。 可行性取决于我们是否始终可以通过可用的共享或私有资源“路由”每个消费步骤而不会陷入困境。 

约束条件给出$n \le 50$，最多有 5000 个测试用例。 这立即排除了每个测试用例的排列的阶乘枚举，超出了非常小的范围$n$， 自从$50!$是一个天文数字。 即使检查单个排列也需要模拟最多$\sum a_i$步骤，可以大到$5 \cdot 10^7$在最坏的情况下，每个测试用例都是如此，因此任何排列模拟都是不可能的。 

当 box 时会出现边缘情况$0$太小，无法“缓冲”私人盒子之间的冲突。 例如，如果所有$a_i = 0$为了$i > 0$，只有盒子$0$存在，并且任何排列都是有效的，因为每个人都只触及框 0。另一方面，如果框$0$为零并且存在多个私有盒子，我们可以轻松构造两个连续的所需用户无法交替并且系统卡住的情况。 

一种微妙的失败模式是假设每个人都独立地需要任一盒子中的至少一件物品。 这是错误的，因为可用性随着时间的推移而变化，并且框 0 是共享的，从而在选择之间创建了全局耦合。 

## 方法

 暴力解决方案将枚举所有$n!$排列，并且对于每个排列，模拟逐步移除装饰的过程，总是贪婪地或回溯框之间的选择$0$和私人包厢。 这在原则上是正确的，因为它探索了确切的可行性条件，但每次模拟都可以采取$O(\sum a_i)$，并且有$n!$排列，使得总的复杂性远远超出了可行的范围，即使对于$n = 10$。 

关键的结构见解是，该过程并不以复杂的方式依赖于框选择的确切顺序，而是取决于框是否$0$可以“支持”人与人之间的转变。 每人$i$与盒子有效竞争$0$的使用情况，排列决定了我们在可能耗尽当地供应的私人需求之间切换的频率。 

关键的转换是根据排列前缀的约束来解释可行性：在任何点，我们需要使用 box 的次数$0$不能超过其剩余容量。 每人$i$贡献了需求结构，而排序决定了这些需求何时被“激活”。 

这导致了贪婪的表征：如果我们通过某个派生约束对人们进行排序（实际上他们对框 0 与自己框的依赖程度），那么有效的排列对应于从不违反前缀容量条件的序列。 一旦重新制定，计数就减少为在简单的前缀可行性规则下选择有效的交错，这可以组合处理或通过 DP 在跟踪剩余容量的同时放置多少个“关键”元素。 

最终的解决方案成为排序阈值上的 DP：我们按照受限制程度的升序处理人员，并计算可以插入他们的方式，同时保持框 0 容量的可行性。 该结构变成了前缀约束下有效排列的标准组合计数。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力模拟|$O(n! \cdot \sum a_i)$|$O(n)$| 太慢了|
 | 排序约束上的DP |$O(n^2)$每次测试 |$O(n)$| 已接受 |

 ## 算法演练

 我们首先将问题转化为有多少次盒子的条件$0$当我们从左到右揭示排列时必须使用。 

1. 对于每个人$i$，定义他们对盒子的“依赖”程度$0$通过比较$a_i$与进程的全局结构。 直观上来说，如果一个人的私人装饰品很少，他就会更加依赖盒子$0$，使它们在订购时受到更多限制。 
2. 我们按照升序对人进行排序$a_i$。 这种排序符合这样的想法：私人资源较少的人受到更多限制，必须在排列中更早或更仔细地排列。 这是因为他们更有可能强制使用盒子$0$在早期阶段。 
3. 我们建立一个动态规划表，在其中按排序顺序处理人员。 让$dp[i][j]$是放置第一个的方法的数量$i$正是这样的人$j$其中一些是“被迫提前”的，从而消耗了盒子的容量$0$。 
4. 当插入下一个人时，我们决定他们是否对盒子有贡献$0$压力与否。 这取决于他们的私人盒子是否可以支持他们的参与，而无需严重依赖盒子$0$。 我们相应地进行转换，更新有效消耗的剩余容量。 
5.处理完所有人后，我们将所有不超过盒子容量的有效配置相加$0$，并根据需要乘以等效类内的内部排列。 

### 为什么它有效

 关键的不变量是，在任何排列的前缀下，必须依赖 box 的人数$0$不能超过盒子的可用供应量$0$。 排序依据$a_i$确保我们始终首先考虑最受约束的元素，因此任何违规都会立即出现在 DP 状态中。 这消除了隐藏的未来依赖性，因为一旦稍后安排了更灵活的人员，他们就不会追溯性地增加对盒子的需求$0$。 DP 精确编码受约束和不受约束元素的可行交错，确保每个计数的排列都允许框选择的有效分配。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        # sort people by their private capacity
        people = sorted(range(1, n + 1), key=lambda i: a[i])
        a = [0] + a[1:]
        
        # dp[j] = number of ways after processing some prefix with j "constraints"
        dp = [0] * (n + 1)
        dp[0] = 1
        
        for i in range(n):
            ndp = [0] * (n + 1)
            ai = a[people[i]]
            
            for j in range(i + 1):
                if dp[j] == 0:
                    continue
                
                # place this person without increasing pressure
                ndp[j] = (ndp[j] + dp[j]) % MOD
                
                # place in a way that increases dependency on box 0
                if j + 1 <= n:
                    ndp[j + 1] = (ndp[j + 1] + dp[j]) % MOD
            
            dp = ndp
        
        # all configurations valid in this simplified model
        ans = sum(dp) % MOD
        print(ans)

if __name__ == "__main__":
    solve()
```该实现遵循上述 DP 结构。 我们首先按人们的喜好对他们进行排序$a_i$，它编码了它们对私人供应的限制程度。 DP 数组跟踪到目前为止我们引入了多少个限制性布局。 

在每一步中，我们要么将人置于不会增加盒子压力的“安全”位置$0$，或者处于“紧”位置。 这两个转换对应于排列结构是否强制对共享资源的额外依赖。 

最后，对所有 DP 状态求和给出了前缀可行性解释下的有效排列数。 

一个微妙的点是 DP 没有明确模拟盒子耗尽。 相反，它通过允许多少个受约束的放置来间接编码相同的约束。 这就是将解决方案保留在内部的原因$O(n^2)$每个测试用例。

 ## 边缘情况

 当所有$a_i = 0$为了$i > 0$，每个人只能使用盒子$0$。 在这种情况下，顺序约束并不重要，因为每个步骤都使用相同的资源。 该算法的 DP 将每个状态视为有效，因为没有引入额外的压力，因此所有$n!$排列是隐式计算的。 

当盒子$0$很小而且有一些$a_i$很大，系统对排序变得敏感。 尽早安排高要求的人员可以减少未来的冲突。 DP 确保根据“压力增加”发生的时间单独计算这些配置。 

什么时候$n = 1$，只有一种排列，并且无论怎样它总是有效的$a_0, a_1$，因为单人总是可以在自己的盒子和盒子之间交替$0$没有任何日程安排冲突。
