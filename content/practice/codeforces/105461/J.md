 ## 解决方案
 ## 问题理解

 我们正在处理从 1 到 n 的位置的隐藏排列。 每当我们发送一个长度为 n 的单词时，系统就会根据这个固定的排列重新排列字母并返回结果。 

所有查询中的排列都是一致的，因此每个响应只是索引的确定性重新标记。 任务是准确重建每个原始位置的结束位置。 

关键的困难是我们最多只能交互四次，而且 n 可以大到 100000。这排除了任何试图一次恢复一个位置的排列的策略。 任何独立查询每个索引的方法都会立即超出交互的限制，甚至基于探测位置对的非交互式重建仍然需要线性或超线性交互计数。 

该结构表明每个查询必须同时携带有关许多位置的信息，并且每个响应必须允许我们间接提取位置身份。 

如果我们尝试分配相同的字符或低分辨率标签，则会出现微妙的失败情况。 例如，如果我们发送一个包含所有内容的字符串`'a'`，响应也是全部`'a'`，它没有透露任何有关排列的信息。 同样，仅使用几个可区分的符号会导致多个位置共享相同签名的冲突，从而使重建变得模糊。 

核心要求是确保每个位置都有一个唯一的标识，可以在排列后恢复，同时仅使用四个查询。 

## 方法

 一个蛮力的想法是尝试通过设计隔离位置的查询来确定每个索引的位置。 例如，可以发送仅一个位置标记不同的字符串，并观察该标记出现在输出中的位置。 这是可行的，因为我们可以跟踪每个查询的单个位置的移动。 然而，这在规模上立即失败了：识别 n 个位置将需要 Θ(n) 查询，而我们只允许 4 个。 

关键的观察是我们不需要按顺序识别位置。 相反，我们可以用一个小的固定长度签名对每个位置进行编码，并在排列后恢复该签名。 

排列不会破坏信息； 它只是重新排列它。 如果每个位置都带有唯一的“标签向量”，那么在排列之后，这些向量将简单地在位置之间进行混洗。 如果我们可以重建在每个输出索引处看到的向量，我们可以将其映射回原始位置。 

只需四个查询，每个位置就可以贡献四个信息符号。 使用 26 个字母的字母表，每个符号都可以编码一个 26 进制数字。 这为我们提供了 26^4 种可能的不同代码，这对于 n 高达 100000 来说绰绰有余。 

我们为每个位置 i 分配一个 4 位 26 进制表示形式。 在查询 k 中，位置 i 被分配为第 k 个数字作为字符。 排列后，每个输出位置都会显示其源索引的完整 4 字符代码。 这使得重建变得直接：我们将每个 4 字符元组映射回原始索引。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n^2) 或 O(n) 查询 | O(n) | 太慢了|
 | 最佳编码 | O(n) | O(n) | 已接受 |

 ## 算法演练

 1. 使用 4 位数字的 Base-26 编码为每个索引 i 分配一个唯一标识符。 这确保了每个位置都有一个可以在以后重建的独特签名。 
2. 构建四个查询字符串。 对于每个位置 i 和从 0 到 3 的每个查询 k，将字母表中 i 的第 k 个数字放置在第 k 个字符串的位置 i 处。 
3. 发送第一个查询字符串并接收排列后的结果。 对于响应中的每个位置 j，记录来自原始位置的在排列下映射到 j 的字符。 
4. 对所有四个查询重复相同的过程。 处理完所有响应后，每个位置 j 收集了 4 个字符，形成 4 个字符的签名。 
5. 使用 Base-26 解码将每个 4 字符签名转换回原始索引。 这给出了逆排列，这意味着对于每个输出位置 j，我们找到哪个原始索引 i 产生了它。 
6. 以所需的形式输出排列。 

这样做的原因是每个查询的行为就像索引的 4 维编码的投影。 排列仅对这些编码进行重新排序，但不会混合它们，因此每个位置都保留完整的、可恢复的签名。 

### 为什么它有效

 不变的是，在任何时候，排列后的字符串中的每个位置都带有与分配给唯一原始索引完全相同的 4 字符代码。 由于从索引到 4 字符向量的编码函数是单射的，并且排列保留多重集结构而不改变值，因此从任何位置重建原始索引总是明确的。 没有两个索引共享相同的 4 字符元组，因此在重建过程中不会发生冲突。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def encode(i):
    # 4-digit base-26 encoding
    res = []
    for _ in range(4):
        res.append(chr(ord('a') + (i % 26)))
        i //= 26
    return res  # least significant digit first

def main():
    n = int(input().strip())

    # build 4 query strings
    queries = [ [''] * n for _ in range(4) ]

    codes = []
    for i in range(n):
        c = encode(i)
        codes.append(c)
        for k in range(4):
            queries[k][i] = c[k]

    queries = [''.join(q) for q in queries]

    # store received characters per position
    got = [ [] for _ in range(n) ]

    for k in range(4):
        print("?", queries[k])
        sys.stdout.flush()
        resp = input().strip()

        for j, ch in enumerate(resp):
            got[j].append(ch)

    # reconstruct mapping
    pos = {}
    for i, c in enumerate(codes):
        pos[''.join(c)] = i + 1

    ans = [0] * n
    for j in range(n):
        key = ''.join(got[j])
        ans[j] = pos[key]

    print("!", *ans)
    sys.stdout.flush()

if __name__ == "__main__":
    main()
```构建阶段构建四个独立的字符层，每个层充当 26 进制标识符的一位数字。 交互循环读回这些层的四个排列版本并累积属于每个输出位置的字符。 收集完所有四个层后，每个位置都由其 4 字符密钥完全标识，然后将其解码回原始索引。 

一个常见的实现陷阱是混淆排列方向。 关键的见解是输出位置存储有关原始索引的信息，而不是相反，因此重建必须将收集的元组视为逆映射目标。 

## 工作示例

 考虑一个小排列 n = 5 和排列 p = [3, 5, 1, 4, 2]。 这意味着位置 1 移动到 3，位置 2 移动到 5，依此类推。 

我们分配 base-26 代码，但为了简单起见，想象一下字符：

 | 索引我| 代码|
 | --- | --- |
 | 1 | 啊啊|
 | 2 | 啊啊|
 | 3 | 阿巴|
 | 4 | 阿巴 |
 | 5 | 咩咩|

 排列后，位置从其源接收代码：

 | 输出位置 j | 收到代码 |
 | --- | --- |
 | 1 | 阿巴|
 | 2 | 咩咩|
 | 3 | 啊啊|
 | 4 | 阿巴 |
 | 5 | 啊啊|

 从这个表中，我们通过将代码匹配回其分配的位置来直接恢复原始索引。 

该轨迹表明，每个输出位置独立地重建其原点，无需解码之外的任何交叉位置推断。 

n = 3 和恒等排列的第二个示例证实了稳定性。 每个输出位置都准确地接收自己的代码，因此解码通常会返回 [1, 2, 3]，从而验证定点情况下的正确性。

 ## 边缘情况

 对于 n = 1，编码仍会为单个位置生成 4 个字符的签名。 所有四个查询都返回相同的单字符字符串，并且重建将该签名映射回索引 1，不会产生歧义。 

对于接近 100000 的大 n，base-26 四位编码仍然提供足够的唯一性，因为 26^4 超出了范围。 每个索引都保持唯一可识别性，并且解码图中不会出现冲突，从而确保了大规模的正确性。
