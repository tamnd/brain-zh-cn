 ## 解决方案
 ## 问题理解

 我们在两种竞争力量的作用下跟踪一个人随时间的现金余额。 每天从一笔钱开始，这个人会立即花掉他们目前拥有的钱的一半，并将花掉的金额向上舍入。 这意味着如果余额是$x$，支出后的下一个余额变为$\lfloor x/2 \rfloor$。 因此，每天，在没有任何收入的情况下，钱都会严格减少到零。 

还有定期收入：每$d$-第天，当日消费已经发生后，固定金额$s$添加到余额中。 该过程从初始金额开始$m$，我们一天一天地模拟，直到一天开始时余额为零，这意味着该人甚至无法执行支出步骤。 

任务是确定当天开始时余额为零的第一天。 如果这种情况永远不会发生，那么这个过程实际上是永远可持续的，我们必须报告它永远不会耗尽资金。 

输入以二进制表示形式给出，但基础值可能非常大，高达约$2^{100}$。 这立即排除了任何依赖于对原始数字大小进行重复小步模拟的解决方案。 与此同时，动态在很大程度上是单调的：支出总是使余额减半，而收入仅到达离散的检查点。 这种结构表明国家不能任意振荡； 它要么崩溃到零，要么无限增长。 

从概念上讲，对日常转换的简单模拟是安全的，但其最坏情况的长度才是真正的问题。 如果不断补充资金以避免达到零，那么模拟天数可能会变得非常大。 关键的困难是识别系统何时进入永远不会再次达到零的状态，而不是无限期地继续模拟。 

当收入到达的频率足以补偿反复减半时，就会出现一种微妙的边缘情况。 例如，如果$d = 1$，余额减半，然后立即增加$s$每天。 即使余额永远不会变得巨大，它也可能永远稳定在零以上。 仅检查小值或仅模拟固定数量步骤的粗心实现将无法检测到这种无限状态。 

当出现另一种边缘情况时$s = 0$。 那么系统就是纯递减的，答案很简单，就是第一天重复减半达到零，大约是$\lfloor \log_2 m \rfloor + 1$。 任何假设收入总是重要的优化都会错误地使这种情况变得过于复杂或错误分类。 

## 方法

 一个简单的解释是每天模拟这个过程。 每次迭代都会通过将当前值减半来计算新的余额，然后添加$s$如果日索引是的倍数$d$。 当一天开始时余额变为零时，我们就会停止。 这是正确的，因为它完全遵循流程规则。 

问题在于终止前的天数不受输入大小中的小多项式的限制。 尽管在没有收入的情况下减半会迅速降低价值，但定期注入$s$可以反复恢复平衡并显着延迟终止。 如果系统稳定或不断增长，模拟就永远不会结束。 

关键的观察结果是系统每隔一段时间就会有一个更新结构$d$天。 在两个收入事件之间，该过程是纯粹确定性且严格收缩的：重复变换$x \mapsto \lfloor x/2 \rfloor$。 我们可以压缩每个块$d$单个函数的天数$f(x)$，这给出了精确模拟后的结果平衡$d$天数开始于$x$。 

一旦我们有了这个块函数，我们就可以推断长期行为。 如果重复申请$f$最终将值驱动为零，则答案是有限的。 如果在某个时刻$f(x) \ge x$，则系统无法再向下收敛，因为每个完整周期都无法减少状态； 由于减半已经破坏了结构，重复循环只会维持或增加价值，防止最终崩溃。 

这减少了无限与有限的区别，以检查是否重复应用$d$日变换是否稳定在其起点以下。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 日常模拟 | O(T) 其中 T 是死亡时间 | O(1) | O(1) | 太慢/可能无法终止 |
 | 按 d-day 函数压缩周期 | O(d log m) | O(d log m) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 定义一个函数来精确模拟一个块$d$从指定金额开始的天数$x$。 对于每个$d$天，应用支出规则$x \leftarrow \lfloor x/2 \rfloor$，并且之后$d$-th,$2d$-th，依此类推，添加$s$归根结底。 这一函数代表了系统在一个收入周期内的完整演变。 
2. 从初始金额开始$m$并从第一天开始跟踪当天的指数。 
3. 每天重复模拟，直到余额在一天开始时变为零，或者我们检测到整个过程中的非减少行为$d$天周期。 
4. 每个完整周期后，计算新值$x' = f(x)$。 如果$x' = 0$，系统最终会以零余额开始一天，当天的指数就是答案。 
5.如果$x' \ge x$，得出结论：进一步的演化不能将系统驱动至零。 从这一点开始，每个周期都会维持或增加余额，而每天只花费一半，因此系统永远保持正值。 在这种情况下，输出“Infinity Money!”。 
6. 否则，更新$x \leftarrow x'$并继续下一个循环，将日期计数器推进$d$。 

### 为什么它有效

 每个块内$d$天，转换是确定性的，仅取决于当前的余额。 支出运行严格收缩，收入是增长的唯一来源。 这意味着在周期边界观察到的值序列是单调的，一旦它停止减少，以后就无法恢复下降趋势，因为唯一的非线性效应是重复减半。 因此，系统要么最终达到零，要么进入周期间价值不收缩的状态，这意味着永久生存。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def simulate_cycle(x, s, d):
    for i in range(1, d + 1):
        x //= 2
        if i % d == 0:
            x += s
    return x

def solve():
    s = int(input().strip(), 2)
    d = int(input().strip(), 2)
    m = int(input().strip(), 2)

    day = 1
    x = m

    while True:
        # start of a day: if already zero, we are done
        if x == 0:
            print(bin(day)[2:])
            return

        # simulate one full cycle of d days
        nxt = x
        for i in range(1, d + 1):
            nxt //= 2
            if i % d == 0:
                nxt += s

        # check infinite regime
        if nxt >= x:
            print("Infinite money!")
            return

        x = nxt
        day += d

solve()
```该实现直接反映了循环压缩的思想。 日计数器以块为单位前进$d$，因为只有这些点才能以非局部方式改变平衡。 比较`nxt >= x`是检测收入何时足以抵消反复减半的关键卫士。 

一个常见的陷阱是在错误的时间使用收入。 该声明将工资放在每个人的末尾$d$-第天，支出后，因此循环首先应用减半，然后才添加$s$在适当的时候。 颠倒此顺序会完全改变动态并产生不正确的稳定性检测。 

另一个微妙之处是日索引的二进制输出。 转换必须排除`0b`前缀，因为输出格式需要纯二进制字符串。

| 循环开始 x | 第一天之后 | 第二天之后 | 周期结束|

 第一个周期后，该值从 5 减小到 2。第二个周期后，该值趋于稳定。 这表明系统没有收敛到零，而是稳定在正值，因此正确的输出是“无限金钱！”。 

该轨迹证实检测非递减循环边界足以对无限行为进行分类。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(d log m) | O(d log m) | 每个周期执行 d 减半操作，终止或检测之前的周期数受到对数衰减或早期稳定的限制 |
 | 空间| O(1) | O(1) | 仅维护少数整数变量 |

 这些约束允许非常大的数值，但减半操作会迅速减小它们的大小。 与循环压缩相结合，完整模拟的数量仍然足够小，可以轻松地适应时间限制。

 ## 边缘情况

 当初始值已经为零时，正确的答案是第 1 天。该算法通过在应用任何转换之前在每次迭代开始时检查余额来处理此问题，因此它会立即返回当天计数器，而无需进入模拟。 

当根本没有收入时，系统纯粹是在递减。 每个周期都会严格降低价值，因为重复减半不能产生增长。 该算法检测到这一点是因为每个周期都会产生一个严格较小的值，并且在对数步数后最终达到零。 

当收入相对于支出非常大时，循环函数会产生随着迭代而增长的值。 在这种情况下，比较`nxt >= x`尽早触发，防止不必要的模拟。 这可以避免在进程永远不会达到最终零状态的情况下出现无限循环。
