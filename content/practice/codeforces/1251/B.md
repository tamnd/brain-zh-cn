 ## 解决方案
 ## 问题理解

 我们得到几个二进制字符串，并允许在任何字符串中的任意两个位置之间重复交换字符。 交换可以发生在一个字符串内或跨不同的字符串，因此实际上每个字符都是一个全局池的一部分，可以在所有位置之间自由地重新分配。 

目标是重新排列所有字符，以便尽可能多的原始字符串同时变成回文。 如果字符串的第一个字符与最后一个字符匹配，第二个字符与倒数第二个字符匹配，依此类推，则该字符串是回文。 

关键的观察是我们并没有试图在交换期间保留单个字符串结构。 只有每个字符串中的最终多组字符很重要，因为交换允许完全重新分配。 

每个测试用例最多有 50 个字符串，每个字符串的长度最多为 50，因此每个测试用例的字符总数最多为 2500。这足够小，我们可以全局推理字符计数和贪婪分配，而不必担心超出线性或近线性操作的性能瓶颈。 

天真的推理的一个微妙的失败案例是假设每个字符串都可以独立检查。 例如，如果一个字符串具有奇数长度并且内部有太多不匹配，人们可能会认为它不能成为回文，但与其他字符串交换可以通过导入或导出字符来修复它。 另一种失败情况是假设首先贪婪地修复一个字符串是最佳的； 这样做可能会消耗太多其他地方所需的不匹配字符。 

边缘场景示例：考虑字符串`01`,`01`,`11`。 贪婪的尝试可能会同时解决这两个问题`01`字符串首先通过位配对，但这可能会留下不足以实现最佳全局配对的结构。 正确的解决方案仅取决于全局计数`0`和`1`，不是本地安排。 

## 方法

 强力解释将尝试模拟交换并尝试跨字符串的所有可能的最终字符分布。 这相当于将所有字符分成 n 组固定大小并检查哪些组可以形成回文。 即使我们忽略重新排列并只考虑分配，分区的数量也是天文数字，像多项式系数一样增长到多达 2500 个元素，这使得它不可行。 

关键的见解是翻转视角：由于交换使所有字符都可以全局互换，因此我们只需要决定选择多少个字符串来制作回文，而不是它们最初的确切身份。 如果一个字符串的字符可以对称配对，则该字符串是回文字符串，这仅取决于有多少对`0`和`1`我们可以为奇数长度字符串分配一个可能的剩余字符。 

对于单个字符串，如果我们知道有多少个`0`和`1`它应该包含，如果我们可以在内部形成足够的对，这是可行的。 每个长度的回文`L`需要`L // 2`之间任意分布的对`0-0`和`1-1`，并且可能还有一个剩余字符，如果`L`很奇怪。 因此，每个字符串消耗一定数量的对，并且可能消耗一个单个字符。 

这将问题简化为贪婪分配：我们计算可用的总对`0`和`1`从整个输入中，然后尝试通过花费这些资源来最大化我们可以满足的字符串数量。 由于每个字符串都有固定的要求，我们首先排序或贪婪地尝试满足更便宜的字符串，但这里所有字符串在成本结构上都是对称的，因此我们可以直接以单调的方式计算可行性。 

最终的结构变成选择字符串的子集，使得它们的组合对要求不超过可用的对，并且每个字符串至多一个奇数长度中心由可用的单个字符处理。

 ## 算法演练

 我们首先计算输入字符串的全局统计数据。 我们统计一下总数`0`字符数和总数`1`人物。 从这些我们可以得出每种类型可以形成多少对，因为每个回文最终都会消耗对称对中的字符。 

接下来，我们独立检查每个字符串并计算成为回文所需的条件。 对于一个长度的字符串`L`，它需要`L // 2`字符对。 这些对可以使用以下任一方式填充`0`或者`1`只要全球资源允许，就可以成对进行。 如果字符串长度为奇数，则还需要额外的一个单个字符作为中心。 

然后，我们以任意顺序处理字符串，但从概念上讲，我们尝试将每个字符串“适合”到可用资源池中。 对于每个字符串，我们检查是否可以分配足够的对，如果需要，还可以分配一个中心字符。 如果是，我们减少全局资源并将该字符串视为已成功回文。 否则，我们跳过它。 

1. 计算所有字符串中 0 和 1 的总数。 
2. 将它们转换为可用的对数：从零到零对、从一到一对以及剩余的单对。 
3. 对于每个字符串，计算所需的对以及是否需要中心。 
4. 如果当前全局池可以满足要求，则接受该字符串并更新池。 
5. 否则，跳过它。 
6. 返回接受的字符串数量。 

这种贪婪方法起作用的原因是每个字符串仅消耗聚合资源，并且除了共享耗尽之外没有任何交互。 由于所有字符串都具有相同的结构约束（仅长度重要，而不是顺序），因此除了是否适合剩余容量之外，优先选择其中一个字符串并没有任何优势。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    Q = int(input())
    for _ in range(Q):
        n = int(input())
        strings = [input().strip() for _ in range(n)]

        total0 = sum(s.count('0') for s in strings)
        total1 = sum(len(s) - s.count('0') for s in strings)

        zero_pairs = total0
        one_pairs = total1

        ans = 0

        for s in strings:
            l = len(s)
            need_pairs = l // 2
            need_center = l % 2

            if need_pairs <= zero_pairs + one_pairs:
                # use pairs greedily
                take = need_pairs
                use0 = min(zero_pairs, take)
                take -= use0
                use1 = take

                if use1 <= one_pairs:
                    zero_pairs -= use0
                    one_pairs -= use1

                    if need_center == 0:
                        ans += 1
                    else:
                        # need a center character
                        if total0 + total1 > 0:
                            ans += 1
                            if total0 > 0:
                                total0 -= 1
                            else:
                                total1 -= 1

        print(ans)

if __name__ == "__main__":
    solve()
```该代码首先聚合所有字符串的字符计数，这是必要的，因为交换消除了每个字符串所有权的任何概念。 然后它迭代字符串，计算每个字符串消耗多少个配对字符。 

贪婪分配使用可用的`0`和`1`池以满足配对要求。 微妙的部分是确保奇数长度字符串仅在全局可用时才消耗中心字符。 该中心处理与配对分配分开，因为它不与配对结构交互。 

这里的一个常见陷阱是过早地将每串可行性与全局可行性混合在一起。 正确的解释始终是全局资源分配。

 ## 边缘情况

 一个关键的边缘情况是许多奇数长度的字符串竞争单个中心字符。 例如：```
3
1
1
1
```每根弦都需要一个中心。 每个奇数长度结构全局只存在一个中心，因此最多应该完全满足一个字符串。 贪心算法确保一旦中心被消耗，后续需要它的字符串就会被拒绝。 

另一个边缘情况是当配对供应完全平衡时。 例如：```
2
01
10
```两个字符串各需要一对，并且总资源完全匹配。 该算法按顺序接受两者，而不会超出资源计数器。 

最后的边缘情况是分布不均匀，例如：```
2
000
111
```这里每根弦需要一个中心和一对。 由于如果单数不足，两个中心不能同时满足，因此只有正确数量的字符串才应该通过。 基于资源的会计正确地实施了这一全局约束。
