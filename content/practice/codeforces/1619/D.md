 ## 解决方案
 ## 问题理解

 我们给出了几个独立的场景。 在每个场景中，弗拉德都有固定数量的朋友和固定数量的商店。 每家商店都为每位朋友提供了一个价值，代表了如果朋友在那里购买礼物会得到多少快乐。 

弗拉德必须为每个朋友分配一个商店，这意味着每个朋友都会收到一份礼物。 单个店铺可以服务多个好友，因此每个店铺的购买数量没有容量限制。 然而，弗拉德最多只允许亲自参观$n-1$不同的商店，在那里$n$是朋友的数量。 

所有任务完成后，每个朋友都有一个快乐值，解决方案的质量由所有朋友中最小快乐值决定。 目标是最大化这个最小值。 

所以我们并不是优化总的快乐，而是在我们不能自由使用所有商店的限制下，确保最弱的朋友尽可能快乐。 

约束条件$n \cdot m \le 10^5$每个测试用例意味着矩阵足够稀疏，使得解决方案更接近$O(nm \log A)$或者$O(nm)$预计。 任何平方项$m$或立方英寸$n$穿越会太慢$10^4$测试用例。 

一种简单的方法是尝试直接将商店分配给朋友或枚举商店的子集，但这很快就变得不可能，因为选择最多$n-1$商店已经意味着组合爆炸。 

当所有朋友都需要高价值但这些高价值分布在不同的商店时，就会出现微妙的失败案例。 

例如，如果一个朋友在商店 1 中具有最佳价值，另一个朋友在商店 2 中具有最佳价值，依此类推，则使用的数量少于$n$商店迫使至少一个朋友妥协，除非一家商店已经同时满足了许多朋友。 贪婪的“独立为每个朋友挑选最好的”方法失败了，因为它忽略了对商店使用的共享约束。 

## 方法

 蛮力的想法是最多选择一个子集$n-1$商店，然后将每个朋友分配到这些商店之一，以最大限度地提高他们的个人快乐。 对于固定的子集，我们将计算每个朋友可实现的最大快乐作为所选商店的最大值。 最终得分是好友中最低的。 

问题是有$\binom{m}{\le n-1}$子集，在实践中是指数级的。 即使对于中等$m$，这是完全不可行的。 

关键的观察是翻转视角。 我们问的不是选择店铺，而是：能否保证每个朋友收到的至少是超值的$x$？ 如果我们固定一个阈值$x$，每个商店都成为一组它可以“满足”的朋友（那些有$p_{ij} \ge x$）。 我们最多想选$n-1$使每个朋友都至少被一家选定的商店所覆盖。 

这是一个经典的可行性检查，可以与二分搜索结合使用$x$。 剩下的问题是如何有效地检查可行性。 

对于固定的$x$，我们根据商店满足的朋友群体对商店进行分类。 一个重要的见解是，如果一家商店在满意的朋友数量方面严格优于另一家商店，那么占主导地位的商店永远没有用处。 我们可以将每个商店减少到一个位掩码的长度$n$，但自从$n$规模较大时，我们改为对每个朋友进行推理：每个朋友需要至少被一个选定的商店覆盖。 

更清洁的转变来自双重思维。 与其选择商店来覆盖朋友，不如考虑每个朋友最喜欢使用哪家商店。 如果朋友被分配到一家满足其门槛的商店$x$，那家商店“覆盖”了他们。 一个商店可以同时覆盖多个朋友。 

现在条件变成：我们最多可以选择$n-1$商店，使每个朋友至少有一个选择的商店$p_{ij} \ge x$？ 这相当于说，在每个朋友的候选商店中，我们必须确保没有一个朋友漏掉。 

出现了一个关键的结构简化：如果朋友没有满意的商店$x$， 然后$x$是不可能的。 否则，每个朋友至少有一个可以接受的店铺，并且我们需要保证最多可以选择$n-1$与所有这些集合相交的商店。 这总是可能的，除非存在“完美匹配障碍”，这可以通过观察贪婪地解决，唯一失败的方法是当每个朋友都需要一个不同的商店时，迫使$n$独特的商店。 

这导致了标准的贪婪可行性检查：我们尝试将每个朋友分配到一个首选商店，并尽可能重用已使用的商店。 如果我们需要引入更多$n-1$店铺特色鲜明，门槛不达标。 

这将问题简化为二分搜索$x$，贪心签入$O(nm)$每次测试。

 | --- | --- | --- | --- |
 | 蛮力 | 指数| O(纳米) | 太慢了 |
 | 二分查找+贪婪可行性| O(nm log 1e9) | O(nm log 1e9) | O(纳米) | 已接受 |

 ## 算法演练

 ### 1. 二分查找答案

 我们寻找尽可能最小的快乐$x$。 对于候选人$x$，我们测试是否可以分配礼物让每个朋友至少得到$x$。 

单调性质成立：如果$x$可行，则任何较小的值也是可行的。 

### 2. 构建每个测试值的可行性信息

 对于固定的$x$，我们扫描矩阵并标记哪些（朋友，商店）对是有效的，这意味着$p_{ij} \ge x$。 每个朋友必须被分配到至少一个有效的商店。 

### 3. 贪婪构建店铺使用

 如果可能的话，我们会遍历朋友并尝试将每个朋友分配到已经选择的商店。 如果没有，我们就开一家满足他们需求的新店。 

这样做的原因是，重复使用商店不会损害可行性，因为一家商店可以不受限制地为多个朋友提供服务。 

### 4. 强制执行最多的约束$n-1$商店

 在分配时，我们会计算被迫使用多少个不同的商店。 如果这超过$n-1$，阈值$x$是不可能的。 

### 为什么它有效

 关键的不变量是，在任何时候我们都会维护一组涵盖所有已处理朋友的选定商店。 如果现有的商店无法满足朋友的需求，我们会介绍一家可以满足他们需求的新商店。 如果这个过程需要$n$不同的商店，那么这些商店中的每一个都被至少一个朋友强制，否则无法覆盖，这意味着不可能合并。 相反，如果我们留在$n-1$，我们有一个有效的作业。 这种贪婪的结构恰恰体现了可行性，因为商店的再利用是不受限制的，唯一的限制因素是不同商店的数量。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def can(x, m, n, p):
    used_shops = set()
    shop_for_friend = [-1] * n

    # try to assign each friend to some shop with p[i][j] >= x
    for j in range(n):
        assigned = -1
        for i in range(m):
            if p[i][j] >= x:
                if i in used_shops or len(used_shops) < n - 1:
                    assigned = i
                    break

        if assigned == -1:
            return False

        shop_for_friend[j] = assigned
        used_shops.add(assigned)

        if len(used_shops) > n - 1:
            return False

    return True

def solve():
    t = int(input())
    for _ in range(t):
        input()
        m, n = map(int, input().split())
        p = [list(map(int, input().split())) for _ in range(m)]

        lo, hi = 0, 10**9

        while lo < hi:
            mid = (lo + hi + 1) // 2
            if can(mid, m, n, p):
                lo = mid
            else:
                hi = mid - 1

        print(lo)

if __name__ == "__main__":
    solve()
```二分搜索位于可行性检查器之上。 在检查器内部，每个朋友都是独立处理的，但共享约束是通过一组使用过的商店进行跟踪的。 贪婪的选择确保我们尽可能地重复使用商店，从而最大限度地减少引入的不同商店的数量。 

一个常见的实施陷阱是忘记重用总是有益的，而是贪婪地将朋友锁定在他们最好的商店，即使另一个现有商店就足够了。 这打破了可行性计算。 

另一个微妙的问题是错误地初始化二分搜索下限； 由于喜悦是正数，因此从 0 开始是安全的，并且涵盖了所有值都很大但仍然有效的边缘情况。

 ## 边缘情况

 一个关键的边缘情况是每个朋友都有一个独特的最佳商店。 举例来说，如果朋友$j$仅在商店中具有最大价值$j$，然后达到高阈值迫使选择所有$n$商店，违反了$n-1$限制。 该算法检测到这一点是因为贪婪分配必然会为每个朋友引入一个新商店，并且使用的集合会增长超过$n-1$，导致拒绝。 

另一种极端情况是一家商店支配了许多朋友。 在这种情况下，贪婪分配很快就稳定在单个商店内，并且使用的商店数量永远不会超过 1，轻松满足约束。
