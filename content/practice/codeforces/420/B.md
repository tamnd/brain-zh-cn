 ## 解决方案
 ## 问题理解

 我们有一个开发团队的会议日志，其中每个日志条目都记录用户登录或注销。 日志可能在会议中间开始或结束，因此我们不知道在第一个记录的消息之前谁在线。 我们的目标是找到所有可能的团队领导者候选人。 根据定义，只要有任何参与者参与聊天，领导者就必须在场，但由于日志是部分的，因此有些人可能会在记录的片段之外出现或消失。 

形式上，每条消息都是“+ id”（带有号码的用户）`id`已登录）或“-id”（用户已注销）。 输入给出`n`用户总数和`m`消息。 我们希望识别当其他人在线时可能在线的所有用户，考虑到第一条消息可能无法捕获所有最初在线的用户。 输出是可以满足此领导者条件的用户列表。 

限制最多为 10^5 个用户和消息。 这意味着任何复杂度低于 O(n + m) 的算法都可能太慢。 在最坏的情况下，所有用户和消息的嵌套迭代将给出大约 10^10 次操作，这是不可行的。 因此，我们必须有效地处理日志，最好是在一次线性传递中。 

当日志开始时，可​​能在日志开始之前已登录的用户注销，就会出现微妙的边缘情况。 例如，如果第一个条目是`- 2`，我们必须假设用户 2 可能在日志开始之前就已经存在。 另一个边缘情况是用户从不注销或多个用户连续登录而没有任何注销。 仅检查日志中的消息的简单方法会错过这些场景，并可能错误地排除有效的领导者候选者。 

## 方法

 暴力方法会尝试将每个用户作为潜在的领导者，从头到尾模拟日志，并在其他人在线时检查该用户是否始终在线。 原则上这是可行的，因为我们可以每次维护一组“在线”用户并验证领导者条件。 然而，这需要 O(n * m) 次操作，对于最坏情况的输入最多为 10^10 - 显然太慢了。 

最佳方法的关键洞察是逐步跟踪每个用户的约束。 具体来说，如果我们注意到注销而没有相应的事先登录，则该用户在日志开始之前必须已在线。 同样，任何在日志中不活跃但从未被看到注销的用户也可能是领导者。 通过维护一组绝对不是领导者的用户，并在消息违反领导者条件时更新它，我们可以在 O(n + m) 时间内有效地缩小候选列表范围。 问题结构允许这样做，因为我们只需要一次通过消息和恒定时间集合操作来更新候选可能性。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n * m) | O(n) | 太慢了 |
 | 最佳| O(n + m) | O(n) | 已接受 |

 ## 算法演练

 1. 初始化一个空集来跟踪当前在线的用户。 另外，创建一个数组来标记不可能的领导者候选人。 一开始，我们认为所有用户都是潜在的领导者。 
2. 扫描第一条消息。 如果是注销`- id`， 认为`id`在日志开始之前就已在线并将它们添加到在线集中。 这确保我们处理日志在会议中间开始的边缘情况。 
3. 按时间顺序迭代每条消息。 用于登录`+ id`， 标记`id`和在线一样。 用于注销`- id`， 消除`id`来自在线设置。 
4. 每当用户登录时，当前未在线的所有其他用户在此之前都不能成为领导者，因为在这次登录发生时领导者必须在场。 相应地更新不可能的领导者数组。 
5. 处理完所有消息后，未标记为不可能的用户是有效的领导者候选人。 对它们进行排序并输出结果。 

为什么它有效：不变的是，当有人在线时，领导者（如果有）必须出现在在线集中。 任何不与其他用户同时在线的用户都无法满足此不变量，因此被排除在外。 通过逐步应用此逻辑并考虑在第一条消息之前在线的用户，我们捕获了所有可能的领导者候选人。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
messages = [input().strip().split() for _ in range(m)]

online = set()
cannot_be_leader = [False] * (n + 1)
first_online = set()

# Handle initial logouts
for op, uid in messages:
    uid = int(uid)
    if op == '-':
        online.add(uid)

# Now we scan and mark impossible leaders
current_online = set(online)
for op, uid in messages:
    uid = int(uid)
    if op == '+':
        for user in range(1, n + 1):
            if user != uid and user not in current_online:
                cannot_be_leader[user] = True
        current_online.add(uid)
    else:
        current_online.remove(uid)

# Collect candidates
candidates = [i for i in range(1, n + 1) if not cannot_be_leader[i]]
print(len(candidates))
print(' '.join(map(str, candidates)))
```第一个循环处理第一个事件是注销的边缘情况。 第二个循环保持不变量：只要其他人在线，领导者就必须在线。 检查当前不在线的其他用户可确保我们排除不可能的领导者。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n + m) | 每条消息都会被处理一次。 在线集合操作平均为 O(1)，并且标记不可能的领导者每次登录最多迭代 n 个用户一次。 |
 | 空间| O(n + m) | 存储消息需要 O(m)，在线用户和候选人的数组/集合需要 O(n)。 |

 当 n 和 m 达到 10^5 时，算法在 1 秒内运行良好，并且 O(n + m) 的空间使用量远低于 256 MB 的限制。

 ## 边缘情况

 如果日志以注销开始，我们假设用户已经在线。 例如，输入：```
3 2
- 3
+ 1
```最初，在线设置为{3}。 当用户1登录时，用户2处于离线状态，无法成为Leader。
