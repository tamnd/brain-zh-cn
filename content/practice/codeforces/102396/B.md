 ## 解决方案
 ## 问题理解

 我们有初始账户余额`s`和`n`必须在接下来的时间内全部发生的交易`m`天。 交易`i`改变平衡`count[i]`，但其确切日期可以是包含区间中的任何一天`[from[i], to[i]]`。 如果同一天发生多笔交易，其内部顺序不受限制。 

我们需要确定是否存在至少一种有效的交易日和日内排序选择，使余额在某一时刻为负值。 负余额是现金缺口。 如果余额正好为零，那仍然是安全的，因为公司有足够的钱来支付。 

输入的有用部分是`n`和`m`至多都是`1000`。 一个`O(nm)`解决方案最多执行大约一百万个交易日的检查，这对于时间限制来说是很合理的。 更重要的是，该界限排除了枚举可能的时间表，因为每笔交易可能有许多可能的日子。 间隔跨越所有`m`天，只需为每笔交易分配一天`m^n`的可能性。 为了`n = m = 1000`， 那是`1000^1000`在我们考虑一天的交易顺序之前就已经完成了任务。 

一些边界情况可能会使原本看似合理的解决方案变得错误。 首先，实现零并不是现金缺口。 例如，```
1 1 5
-5 1 1
```有输出`NO`，因为唯一的交易使余额为零。 支票使用`balance <= 0`而不是`balance < 0`会错误地回答`YES`。 

其次，间隔在当天之前结束的交易已经被强制发生，而间隔包括当天的交易可以故意安排在当天发生。 例如，```
2 2 5
5 1 1
-6 2 2
```有输出`YES`。 第一笔交易必须发生在第 1 天，余额为 10。第二笔交易发生在第 2 天，并将余额减少到 4，因此这个特定示例实际上是安全的。 要正确暴露边界，请将初始余额更改为 0，但约束要求`s >= 1`。 一个有效的例子是```
2 2 5
0 1 1
-6 2 2
```有输出`YES`，因为余额变为`-1`第二天。如果解决方案在检查当天之前意外地将当天结束的交易视为已完成，则可能会错误分类此类情况。 

第三，当日交易可能出现对抗性排序。 考虑```
2 1 5
-3 1 1
-3 1 1
```有输出`YES`。 第一次付款还剩 2 欧元，第二次付款则需要 3 欧元。 这里将两次付款相加就足够了，但是在正交易和负交易共享一天的情况下，假设任意固定输入顺序的实现可能会失败。 

最后，零值交易根本没有任何影响。 例如，```
2 1 5
0 1 1
0 1 1
```有输出`NO`。 在维护危险交易的活动集时，不应意外地将此类交易视为负付款。 

## 方法

 直接的暴力方法将为每笔交易选择允许的日期，然后模拟生成的时间表。 如果每个区间都是`[1, m]`， 有`m^n`可能的天数分配。 如果我们还显式地尝试每种可能的交易顺序，则可能存在另一个因素`n!`, 给予`m^n n!`候选组合，其中`O(n)`努力模拟每一个。 对于最大的限制，这远远超出了可行的范围。 

蛮力之所以有效，是因为它确实探索了交易可能发生的每一种有效方式。 它失败了，因为几乎所有信息都与问题无关。 我们不需要制定一个完整的时间表。 我们只需要知道某个时刻是否会出现负余额。 

固定特定的一天`d`，并询问当天交易前或交易期间余额可以是多少。 每笔交易都与`to < d`被迫在一天之前发生`d`，无论我们如何选择其确切日期。 它的贡献必须已经包含在余额中。 

现在考虑一个事务，其间隔包含`d`。 如果它的值为负数，我们可以安排在当天`d`并在当天所有正交易之前执行。 由于我们正在寻找尽可能小的余额，因此在检查现金缺口之前应将每笔此类负交易都包括在内。 其区间包含的正交易`d`可以推迟到危险时刻之后，因此它们无助于防止差距。 

这给出了简单的表征。 对于每一天`d`，该点可以达到的最小平衡是`initial balance + sum of all transactions with to < d + sum of all negative transactions with from <= d <= to`。 

如果该值为负数`d`，答案是`YES`。 相反，如果它永远不是负数，则任何有效的排序都不会产生现金缺口，因为该表达式已经包含了可能使该时刻之前的余额变小的每笔交易。 

我们可以在线性时间内评估这个表达式。 对于第一个总和，按结束日期对交易值进行分组。 对于第二个总和，使用差异数组维护当前活动的负交易。 负交易`[from, to]`贡献其价值始于`from`并在之后停止贡献`to`，所以我们将其值添加到`from`并减去它`to + 1`。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 |`O(m^n n! n)`|`O(n)`| 太慢了|
 | 最佳 |`O(n + m)`|`O(m)`| 已接受 |

 ## 算法演练

 1. 创建数组`ending`在哪里`ending[d]`存储所有最晚可能日期恰好是的交易更改的总和`d`。 当我们即将检查的日子`d`，每笔交易`to < d`已经被迫发生了，所以我们可以积累`ending[d - 1]`转换成一个运行值，称为`forced`。 
2. 创建差异数组`active`。 对于具有间隔的每笔负交易`[from, to]`和价值`count`， 添加`count`在`active[from]`并减去`count`在`active[to + 1]`。 其前缀总和将等于其间隔包含当天的所有负交易的总价值。 
3. 扫描日期`1`通过`m`。 白天`d`，首先添加`ending[d - 1]`到`forced`。 这使得`forced`等于必须严格在当天之前发生的每笔交易的贡献`d`。 
4.添加`active[d]`到一个运行变量`dangerous`。 前缀更新后，`dangerous`正好是当天可以执行的所有负交易的总和`d`。 
5. 计算`balance = s + forced + dangerous`。 这是处理一天时可以达到的最小余额`d`，因为每笔强制交易都已经发生，所以每笔当前可用的负交易现在都可以执行，而仍然可以延迟的正交易还没有执行。 
6. 如果`balance < 0`， 打印`YES`立即地。 否则第二天继续。 如果每天都是安全的，请打印`NO`。 

### 为什么它有效

 考虑任何一天`d`。 每笔交易都与`to < d`一定是在一天之前发生的`d`，因此它的贡献是不可避免的。 在其间隔包含的交易中`d`，每笔负数交易都可以在当天下单`d`并在正交易之前执行。 将所有这些都包括在内会产生此时可达到的最小可能平衡。 没有其他交易可以比该表达式更早地降低余额。 因此，当某些有效的交易计划可能产生现金缺口时，该算法会准确地找到负余额。 

扫描过程中的不变式是`forced + dangerous`代表当天可能的最小累计交易变化。 结束贡献说明了已经不可避免的一切，而积极的负面贡献则说明了当前可以在危险时刻之前故意放置的一切。 如果这个最小值永远不为负，则每个有效的时间表都是安全的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m, s = map(int, input().split())

    ending = [0] * (m + 2)
    active = [0] * (m + 2)

    for _ in range(n):
        count, left, right = map(int, input().split())

        ending[right] += count

        if count < 0:
            active[left] += count
            active[right + 1] -= count

    forced = 0
    dangerous = 0

    for day in range(1, m + 1):
        forced += ending[day - 1]
        dangerous += active[day]

        if s + forced + dangerous < 0:
            print("YES")
            return

    print("NO")

if __name__ == "__main__":
    solve()
```这`ending`数组存储完整的交易贡献，包括正值和负值。 交易与`to = d`没有添加到`forced`直到有一天`d + 1`，因为在这一天`d`它仍然可以在当天执行，并且可能成为危险订单的一部分。 

这`active`数组仅包含负交易。 对于有价值的交易`count < 0`和间隔`[left, right]`，添加`count`在`left`使其在第一个法定日开始有效。 减去它在`right + 1`在最后一个法定日后立即将其删除。 当天的前缀总和`d`因此恰好包含满足条件的负交易`left <= d <= right`。 

日循环中的更新顺序可以正确处理边界。`ending[day - 1]`在检查日之前添加`day`， 尽管`active[day]`是为当天本身添加的。 这种区别将已经不可避免的交易与仍然可以在当天有意安排的交易区分开来。 

Python 整数具有任意精度，因此潜在的大中间和不会溢出。 尽管最大绝对总数可以达到大约`10^9`，使用 Python 整数使得实现独立于该界限。 

## 工作示例

 对于样品 1，```
4 3 100
100 1 2
-100 1 2
1 2 3
0 3 3
```负交易`-100`在第 1 天和第 2 天是活跃的。第 2 天结束的正交易在第 2 天之前不会被强制，因此不能算作针对那里的缺口的保护。 

| 日 | 前一天被迫| 积极的负面变化| 最低余额 | 结果 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | -100 | -100 0 | 安全|
 | 2 | 0 | -100 | -100 0 | 安全|
 | 3 | 1 | 0 | 101 | 101 安全|

 第 1 天和第 2 天的最低余额正好为零。这不是负数，因此不存在现金缺口，答案是`NO`。 该示例还演示了为什么检查`<= 0`是不正确的。 

对于样品 2，```
4 3 100
100 1 2
-100 1 2
1 2 3
-1 2 2
```有两笔负数交易都可以在第 2 天执行。`-100`交易从第 1 天到第 2 天都是活跃的，而`-1`仅在第 2 天有效。 

| 日 | 前一天被迫| 积极的负面变化| 最低余额 | 结果 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | -100 | -100 0 | 安全|
 | 2 | 0 | -101 | -101 -1 | 差距|
 | 3 | 1 | 0 | 101 | 101 未达到 |

 在第 2 天，两个负付款都可以放在正付款之前`+100`和`+1`交易。 从 100 欧元开始，余额变为`100 - 100 - 1 = -1`。 该算法检测到这一点并打印`YES`。

 ## 边缘情况

 第一个边缘情况是账户恰好达到零。 为了```
1 1 1
-1 1 1
```扫描开始于`forced = 0`和`dangerous = -1`。 候选人余额为`1 - 1 = 0`，所以条件`balance < 0`为 false 并且算法打印`NO`。 这可以防止将耗尽的账户视为已经存在现金缺口的常见错误。 

第二个边缘情况涉及在当天结束的时间间隔。 考虑```
2 2 5
0 1 1
-6 2 2
```第一天，`-6`交易不活跃，因此最小余额为 5。在第 2 天，它通过以下方式变得活跃：`active[2]`，虽然它不包含在`forced`，因为它的`to`值恰好为 2 而不是小于 2。候选余额为`5 - 6 = -1`，生产`YES`。 这说明了为什么强制求和必须使用`to < day`， 不是`to <= day`。 

第三种边缘情况是同一天出现多笔负面交易。 在样本 2 中，第 2 天有积极的负贡献`-100`和`-1`， 所以`dangerous = -101`。 该算法有效地将两笔付款放在当天所有正交易之前，从而给出尽可能小的余额。 固定的输入顺序无法捕获这种可能性。 

第四种边缘情况是零找零交易。 对于诸如以下的交易`0 1 1`，代码没有添加任何内容`active`，因为零对于降低平衡既不危险也不有用。 它的存在不能改变答案，并且最大尺寸测试证实许多此类交易的处理没有特殊情况。
