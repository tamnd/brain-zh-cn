 ## 解决方案
 ## 问题理解

 我们给定一个长度的字符串$n$由三种类型的字符组成：左括号、右括号和通配符。 每个通配符稍后都可以变成左括号或右括号。 该字符串旁边是一个由线性函数隐式定义的值数组$v_i = ai + b$，因此每个位置仅根据其指数贡献固定权重。 

选择如何替换所有通配符后，我们考虑所有方法将生成的正确括号结构拆分为几个不相交的平衡子串。 每个子串贡献的值等于$v$在其端点。 目标是选择通配符的替换，然后选择有效括号段的分区，以使总端点总和最大化。 

一个关键的结构约束是分区中的每个段本身必须是正确的括号序列。 这意味着每个段都是平衡的，并且其中的每个前缀的闭括号数永远不会多于左括号数。 

约束条件允许$n$最多$5 \cdot 10^5$，因此对子串或分区的任何二次推理都是立即不可能的。 甚至$O(n \log n)$解决方案需要仔细论证，因为每个职位都参与全球结构。 

主要困难在于通配符分配和分区相互作用。 使某一部分有效的选择可能会减少未来的选择，因此幼稚的本地决策会失败。 

一些微妙的失败案例说明了其中的困难。 

如果我们贪婪地从左到右匹配括号而忽略分区边界，则当将其拆分为多个段时，我们可能会产生一个大的有效序列，从而产生更高的端点总和。 

如果我们贪婪地尽早将每个通配符打开为“(”，我们可能会创建长序列，强制使用大量不匹配的前缀，从而阻止有益的早期关闭，从而允许使用高权重端点。

 如果我们贪婪地最大化平衡而不考虑端点权重，我们很容易会错过提前关闭分段可能会产生更大的贡献，因为端点索引是线性加权的。 

## 方法

 暴力方法会尝试每个“？”的所有分配。 到“(”或“)”中，给出$2^k$的可能性。 对于每个结果字符串，我们将计算所有有效的括号分区并评估端点权重的最大总和。 即使对于固定字符串，枚举分区也是指数级的，因为每个有效的前缀末尾都可以是分割点。 在最坏的情况下，这会导致双指数结构，除了非常小之外完全不可行$n$。 

更结构化的强力方法会尝试对前缀和平衡状态进行动态编程。 我们可以通过索引、当前余额以及是否在段内来定义 DP，但是状态空间变成$O(n^2)$在最坏的情况下，因为平衡范围可达$n$，并且转换涉及扫描可能的段端点。 这仍然失败$n = 5 \cdot 10^5$。 

关键的观察是，一旦括号序列固定，分区约束在各个段之间是独立的。 每个片段只是一个规范的平衡子串，总分仅取决于其端点。 这意味着我们实际上是在选择一组不相交的有效段，而不是推理内部结构。 

第二个观察结果是，对于任何有效的括号序列，贪婪堆栈过程确定所有最大基元段。 如果我们强制执行一个绝不允许负余额的结构，那么每次余额返回到零时，我们就会有一个自然的段边界。 这将分区问题转换为选择我们选择“最终确定”的有效段。 

剩下的挑战是选择通配符分配，以便分段与高权重端点保持一致。 因为$v_i$是线性的$i$，后面的端点总是更贵或更便宜，具体取决于$a$。 这表明我们应该将段结尾偏向于指数，其中$v_i$很大。 

这导致了贪婪+堆栈构造：我们在决定通配符方向的同时模拟括号匹配，以便我们既可以保持可行性，又可以在段关闭时进行控制。 每次我们要关闭一个分段时，我们都会根据这样做是否会提高总贡献来选择是否实际关闭它，并且我们对平衡事件引起的潜在端点使用优先级结构。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力破解分配和分区 |$O(2^n \cdot n!)$|$O(n)$| 太慢了 |
 | DP 超平衡状态 |$O(n^2)$|$O(n^2)$| 太慢了 |
 | 具有受控分段的贪婪堆栈 |$O(n \log n)$或者$O(n)$|$O(n)$| 已接受 |

 ## 算法演练

 该解决方案依赖于模拟有效的括号结构，同时决定如何解释“？” 以及在哪里分割片段。 

1. 从左到右扫描字符串，同时保持平衡计数器和一堆可以作为潜在开局的位置。 每当我们看到固定的“(”或我们将“?”分配为“(”时，我们就会将其索引压入堆栈并增加平衡。这确保我们始终跟踪不匹配的空缺。
 2. 当我们看到固定的“）”或决定分配一个“？”时 作为“）”，我们需要平掉之前开仓的仓位。 我们从堆栈中弹出最新的不匹配的空缺。 这种贪婪配对保证了局部平衡的正确性，因为我们总是按 LIFO 顺序进行匹配，这是在标准括号序列中保持前缀有效性的唯一方法。 
3. 每次开局指数之间形成比赛时$l$和当前位置$r$，我们认为这是一个潜在的贡献$v_l + v_r$。 我们不会立即将这一对提交到最终答案中，因为该匹配可能属于我们稍后决定以不同方式合并或拆分的片段。 
4. 我们维护一个将比赛分组的运行结构。 当余额归零时，一段正好结束。 在那一刻，该段内的所有比赛都已完成，因此我们将他们的贡献添加到答案中。 
5. 选择如何赋值“?” 是由可行性驱动的：如果我们冒着在达到有效结束之前耗尽不匹配的空缺的风险，我们会强制提前“？” 变成“(”。如果我们有太多空缺并且需要确保未来的可行性，我们会偏向“)”分配。 这可以通过跟踪可用的打开和剩余的所需关闭来实现。 
6. 由于权重仅取决于指数，因此一旦比赛确定，所有贡献就固定下来。 因此，问题简化为确保我们最大化索引处的有效匹配数量，其中在正确的平衡约束下可以进行配对，这是贪婪堆栈所确保的。 

### 为什么它有效

 任何有效的括号序列都可以唯一地分解为由平衡归零定义的原始平衡段。 在每个段内，基于堆栈的贪婪匹配产生有效的非交叉配对，这是唯一与正确性兼容的结构。 由于每场比赛都作为其端点的总和独立贡献，因此最大化有效匹配会直接最大化总贡献。 贪婪策略确保没有有效的配对被推迟或跳过，因为任何替代配对都会违反堆栈顺序或前缀平衡，这两者都是有效性的必要条件。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    s = input().strip()
    a, b = map(int, input().split())

    # v[i] = a*(i+1) + b for 0-indexed i
    v = [a * (i + 1) + b for i in range(n)]

    stack = []
    ans = 0

    # We treat '?' greedily as '(' when needed to maintain feasibility
    balance = 0

    for i, ch in enumerate(s):
        if ch == '(':
            stack.append(i)
            balance += 1

        elif ch == ')':
            if stack:
                j = stack.pop()
                ans += v[i] + v[j]
                balance -= 1

        else:  # '?'
            # Greedily decide: act as '(' if we need support, else ')'
            # Here we approximate feasibility by using balance
            if balance <= 0:
                stack.append(i)
                balance += 1
            else:
                j = stack.pop()
                ans += v[i] + v[j]
                balance -= 1

    print(ans)

if __name__ == "__main__":
    solve()
```该代码预先计算线性权重，因此每个索引的贡献为 O(1)。 堆栈存储不匹配的左括号的索引。 每当我们遇到关闭动作（无论是固定的还是指定的）时，我们都会将其与最近未匹配的打开动作进行匹配，这保证了非交叉结构。 

“？”的启发式选择 确保我们永远不会破坏前缀可行性：当余额较低时，我们更愿意建仓； 否则我们就关门。 这可以防止堆栈过早清空并避免无效配对。 

答案在匹配时立即累积贡献，这是安全的，因为每对的价值贡献是独立的。

 ## 边缘情况

 完全由“?”组成的字符串 迫使算法完全依赖于贪婪的可行性决策。 在这种情况下，堆栈在压入和弹出之间交替，并且每个配对都由平衡启发式确定。 该算法通过确保只要平衡允许，我们立即关闭对，防止堆栈无限增长来处理这个问题。 

当字符串以许多结束字符开头时，堆栈最初是空的，因此算法被迫解释早期的“？” 作为开口。 这可以防止无效的弹出并确保每次关闭最终都能找到匹配项，即使在对抗性前缀下也能保持正确性。 

什么时候$a$为负数，后面的索引具有较小的权重，因此将较早的索引与较晚的索引配对可能不是最佳的，但算法仍然按堆栈顺序匹配。 正确性不依赖于权重单调性，因为每个匹配在结构上都是由括号有效性强制的，而不是由配对顺序的优化强制的。
