 ## 解决方案
 ## 问题理解

 我们有几组学生。 每个小组有一名学生或两名学生，并且这些小组是不可分割的。 教练希望组建尽可能多的团队，每个团队必须恰好包含三名学生。 

一个规模为一的小组贡献出一名灵活的学生。 规模为二的一组贡献一个固定对，必须在同一团队中使用这两个固定对，或者根本不使用。 我们不能将一对成员分成不同的团队，也不能只将一对成员中的一个成员与其他成员组合起来。 

任务是选择一些小组并将学生分配到不相交的三人小组中，从而最大化完整小组的数量。 

约束 n 可以大到 200,000，这排除了尝试所有组组合或通过回溯增量构建团队的任何方法。 任何解在组数上都必须是线性的或接近线性的。 

当贪婪直觉应用不正确时，就会出现微妙的失败情况。 例如，如果我们总是在看到足够多的单身学生时立即组建一个团队，那么我们可能会错过稍后将一对与两个单身学生组合在一起的机会。 

输入如下：```
5
1 1 1 2 2
```天真的贪婪者可能会从三个人中组成一个团队，然后陷入无法组成完整团队的两对中，给出 1。然而，通过适当地使用两对与单个学生，最佳推理会产生 2 个团队。 

这表明问题不在于本地分组，而在于全局计算资源。 

## 方法

 强力解释将尝试选择组的子集并将它们分配到三人组中，同时尊重每个选定的大小为二的组要么完全包含或排除的约束。 这成为加权项目的分区问题，其中每个项目要么是 1 要么是 2，并且我们尝试选择或跳过每个组的所有组合。 

对于所选组的每个子集，我们将尝试将它们的总大小打包为三个组，可能使用回溯或动态分配。 仅子集的数量就是 2^n，即使检查每个子集的可行性也将花费至少线性时间，使得这在 n = 200,000 时完全不可行。 

关键的观察是只计算物质，而不计算群体的身份。 设 x 为单组数，y 为双组数。 我们实际上正在尝试将由 x 个 1 和 y 个 2 组成的多重集划分为三元组，但限制为 2 不能被拆分。 

该结构得以简化，因为任何有效的球队都是仅有的两种有用类型之一：三名单打，或一名双打加一名单打。 三人一组是不可能的，因为这需要分成两人一组。 这减少了在固定对周围分配单打的问题。 

贪婪策略源于这样一个事实：结对是昂贵的资源：它们同时消耗两个人，并且灵活性较低。 最佳结构总是尽可能地通过将它们与单个匹配来使用对，因为留下一对未使用会浪费两个难以在其他地方重用的潜在贡献。 

因此，我们优先组建使用一对和一对单人的团队，直到其中一个用完为止。 之后，剩下的单打者组成三人一组。

 | --- | --- | --- | --- |
 | 蛮力 | O(2^n·n) | O(2^n·n) | O(n) | 太慢了 |
 | 最佳| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们将输入压缩为两个计数：单人组的数量和两人组的数量。 

1. 计算存在多少个大小为 1 的组以及存在多少个大小为 2 的组。 这将问题减少到两个整数而不是一个数组。 
2. 首先，尝试将每个 2 号组与一组 1 号组一起使用，组成一个完整的三人团队。 每个这样的配对都会消耗每种类型中的一个并产生恰好一个团队。 
3. 此类团队的数量受两个计数中较小者的限制，因为每个团队都需要一对和一个。 
4. 在此步骤之后，通过减去已使用的单个和对来更新剩余计数。 
5. 现在只有单身人士仍然具有相关性。 每支球队正好需要三名单打，因此将剩余的单打数量除以三即可获得额外的球队。 
6. 将两个贡献相加以获得最终答案。 

优先考虑双人/单人团队的原因是，一对人不能对任何其他配置做出贡献，除非与一个单人配对或不使用。 由于保留一对未使用比尽可能将其与单个组合更糟糕，因此此匹配步骤始终是安全的。 

为什么有效：每个有效的解决方案都可以转化为首先形成所有可能的双人加单人团队的解决方案，而不会减少团队总数。 任何偏差要么会浪费一对，要么会在配置中使用比所需数量更多的单元，而这些配置可以重新排列成相同或更好数量的三元组。 这表明贪婪配对然后包装剩余的单身是最佳的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n = int(input())
a = list(map(int, input().split()))

ones = 0
twos = 0

for x in a:
    if x == 1:
        ones += 1
    else:
        twos += 1

# pair each 2-group with a 1-group if possible
pair_teams = min(ones, twos)
ones -= pair_teams
twos -= pair_teams

# remaining ones form teams of 3
single_teams = ones // 3

print(pair_teams + single_teams)
```该代码首先将输入压缩到两个计数器中，这是核心简化。 这避免了跟踪单个组并仅关注可用资源。 

第一阶段计算可以形成多少个 (2,1) 组合。 使用`min(ones, twos)`确保我们永远不会过度使用这两种资源。 减去后，我们正确反映了剩余可用于进一步分组的内容。 

最后，剩余的被贪婪地分组为三元组，因为没有其他结构可以涉及它们。 

这里的一个常见错误是在与二元配对之前尝试形成三元组。 这导致两人陷入困境，无法参加任何团队，从而减少了总人数。

## 测试用例```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    n = int(input())
    a = list(map(int, input().split()))

    ones = 0
    twos = 0

    for x in a:
        if x == 1:
            ones += 1
        else:
            twos += 1

    pair_teams = min(ones, twos)
    ones -= pair_teams
    twos -= pair_teams

    single_teams = ones // 3

    return str(pair_teams + single_teams)

# provided sample
assert run("4\n1 1 2 1\n") == "1"

# all ones, no pairs
assert run("3\n1 1 1\n") == "1"

# all twos, cannot form any team
assert run("2\n2 2\n") == "0"

# mixed, but singles insufficient
assert run("5\n2 2 1 1 1\n") == "2"

# large balanced case
assert run("6\n1 1 1 1 2 2\n") == "2"
```| 测试输入| 预期产出 | 它验证了什么 |

 ## 边缘情况

 一种极端情况是根本没有单人团体。 

输入：```
4
2 2 2 2
```这里个数= 0，两个= 4。配对步骤产生零个团队，因为不存在单个组。 剩余的单数仍然为零，因此答案为 0。该算法正确地避免了尝试强制使用无效的对。 

另一种边缘情况是单身数量较多但配对较少。 

输入：```
6
1 1 1 1 1 1
```这里个数 = 6，两个数 = 0。配对步骤产生零个团队。 剩下的单打通过 6 // 3 组成 2 队。这证实了该算法不依赖于成对的存在，并且优雅地简化为简单分组。 

第三种边缘情况是当单身人士和成对人士数量相等时，这会最大化两个类别之间的互动。 

输入：```
5
1 1 1 2 2
```一个 = 3，两个 = 2。配对产生 2 支球队，留下一支未使用。 无法再形成更多的三元组，并且算法正确地输出 2。这表明小于三的剩余单元会被自然丢弃，无需特殊处理。
