 ## 解决方案
 ## 问题理解

 每个测试都会提供一组精华类型和一组按级别划分的工龙。 每种精华类型都有所需的数量，并且每个完成的龙蛋都会消耗每种精华类型的数量。 

工龙的贡献并不均等。 A级$i$工人生产$2^{i-1}$每天的精华素单位，并且每个工人必须永久分配到一种精华素类型。 多个工人可以被分配到相同的本质类型，他们的贡献会累加。 

分配工人后，每种精华类型$j$积累一些总供应量$S_j$。 那个精华只能养活有限数量的鸡蛋，即$\left\lfloor \frac{S_j}{a_j} \right\rfloor$。 由于鸡蛋同时需要所有精华类型，因此最终产生的鸡蛋数量是所有精华类型中这些值的最小值。 目标是选择最大化这个最小值的任务。 

约束的结构是解决方案的驱动力。 最多有$5 \times 10^4$整个测试用例的本质类型，但worker级别的数量最多为20个。这是关键的不平衡：worker类型种类很少，但每种类型都可以大量出现。 这立即表明我们不应该单独对待工人，而应该按级别汇总。 

一个天真的解释会尝试将所有工作人员分配给本质类型。 即使我们忽略排序，每个工人都有$n$选择，并且工人总数可能非常大，因为$b_i$上升到$10^9$。 任何针对每个工人的模拟都是不可能的。 

稍微不那么幼稚的尝试可能会尝试在没有正确性论证的情况下进行贪婪分配，例如总是将最强的工人分配给最弱的本质，反之亦然。 这失败了，因为目标取决于平衡所有香精类型的最小比率。 单一填充不良的本质类型会降低答案，因此贪婪的局部决策显然并不安全，除非我们仔细构建它们。 

一个更微妙的失败案例来自于忽略整除性。 即使全球总资源充足，但分配不善也会迫使一种精华类型达不到要求。 例如，如果一种精华需要少量但只接收低级别工人，而另一种精华则接收所有高级工人，那么即使总数看起来不错，最低限度也可能会崩溃。 

因此，真正的困难不是总资源计数，而是将加权资源划分到容器中以最大化最小比率。 

## 方法

 蛮力的观点是猜测鸡蛋的数量$x$，然后问我们是否可以分配工人，以便每个本质类型至少收到$a_j \cdot x$总产量。 这将问题转化为可行性检查：我们能否将加权的物品（工人）打包到$n$有下界的群？ 

如果我们修复作业，检查就很简单了。 问题是分配是组合的。 对于很多工作人员来说，尝试所有的发行版都是指数级的。 

关键的观察是决策版本是单调的$x$。 如果我们能生产$x$鸡蛋，那么我们也可以生产任何更少的数量。 这允许二分搜索$x$。 剩下的任务是设计可行性检查。 

工人价值观的结构使这一点变得易于管理。 所有工人的贡献都是二的幂，从$1$最多$2^{k-1}$和$k \le 20$。 这意味着我们可以将工人视为 20 个重量相同的桶。 在可行性方面，我们只关心我们分配的每个权重类别有多少。 

决定固定方案的可行性$x$，每种精华类型都成为需求$d_j = a_j \cdot x$。 我们必须分配加权项目来满足所有需求。 正确的贪婪策略源于“最大需求优先”的思想：首先使用最大的可用工人来满足最苛刻的本质类型，因为大工人是最灵活的，可以弥补小工人无法有效填补的巨大空白。 

我们按需求降序处理香精类型。 对于每一种类型，我们首先贪婪地消耗最大的可用工人类型，直到其需求得到满足或不可能。 因为权重是2的幂，所以分裂决策不需要复杂的背包DP； 贪婪提取之所以有效，是因为任何大型项目在需求较高的早期阶段总是更有用。 

这将可行性转化为超过 20 种项目类型的受控贪婪分配，$n$需求。

 | 二分查找+贪心可行性|$O((n + k^2)\log W)$| O(k) | 已接受 |

 ## 算法演练

 ### 1. 预先计算工人权重

 我们转换每个级别$i$变成一个重量$w_i = 2^{i-1}$具有多重性$b_i$。 这将整个工作集压缩为最多 20 种类型，这一点至关重要，因为所有后续操作仅依赖于每个权重的计数。 

### 2. 设置答案的二分搜索范围

 我们计算鸡蛋数量的合理上限。 可用资源总量为$\sum b_i \cdot 2^{i-1}$，所以将其除以最小的$a_j$给出一个安全上限$x$。 这确保我们永远不会超出物理上可能的生产范围进行搜索。 

### 3. 鸡蛋数量的二分查找

 我们猜测一个值$x$并测试是否可行。 如果可行，我们尝试更大的值； 否则我们减少。 

单调性来自于增加$x$只会线性增加所有需求，使可行性变得更加困难。 

### 4.将每个本质转化为需求

 对于固定的$x$, 每种精华类型$j$需要总资源$d_j = a_j \cdot x$。 我们按降序对这些需求进行排序，以便始终首先满足最严格的约束。 

这种顺序很重要，因为在处理大量未满足的需求时，大型工人是最有价值的。 

### 5. 使用可用工人的贪婪分配

 我们维护每个级别的剩余工人数量。 对于按顺序排列的每个本质，我们尝试通过重复使用最大的可用工作类型来满足其需求。 在转移到较低级别之前，我们总是从最高级别获取尽可能多的资源。 

这种贪婪的步骤确保我们避免将高价值工人浪费在可以由较低级别满足的小需求上。 

### 6. 可行性决策

 如果每种本质都可以使用可用的工人来满足其需求，那么猜测$x$是可行的。 否则就不是。 

### 为什么它有效

 核心不变量是，在可行性检查的任何时候，除非有必要，否则我们永远不会将大型工作人员分配给稍后仅使用较小工作人员即可满足的本质。 由于需求是按降序处理的，因此任何大型工作人员总是在较小的工作人员不足或效率较低的情况下使用。 两人的权力结构确保不会出现病态情况，即较小工人的组合在弥补赤字方面会严格优于较大工人。 这使得贪婪分配与固定需求排序下的最优打包策略一致。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def feasible(x, a, b, k):
    # copy available workers
    cnt = b[:]
    
    # build demands
    req = [ai * x for ai in a]
    req.sort(reverse=True)
    
    # process each essence
    for need in req:
        # try to satisfy this need using largest workers first
        for i in range(k - 1, -1, -1):
            if need <= 0:
                break
            if cnt[i] == 0:
                continue
            w = 1 << i
            use = min(cnt[i], (need + w - 1) // w)
            cnt[i] -= use
            need -= use * w
        
        if need > 0:
            return False
    
    return True

def solve():
    T = int(input())
    for _ in range(T):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        lo, hi = 0, 10**18
        
        while lo < hi:
            mid = (lo + hi + 1) // 2
            if feasible(mid, a, b, k):
                lo = mid
            else:
                hi = mid - 1
        
        print(lo)

if __name__ == "__main__":
    solve()
```实现直接遵循可行性逻辑。 工作人员计数存储在大小固定的数组中$k$，每次可行性检查从最高层向下重复消耗。 

一个微妙的点是计算需要多少给定级别的工人：`(need + w - 1) // w`计算重量的最小工人数量$w$需要满足剩余的要求。 我们通过可用的工人来限制这一点，以避免过度消耗。 

二分搜索使用足够大的上限来覆盖最坏情况的累积，因此只要使用 Python 整数，就不会出现溢出问题影响正确性。

 该跟踪显示了首先处理的大量需求，确保高价值工人不会过早浪费。 

对于第二个例子，考虑仅存在小型工人的情况。 当即使用尽所有级别也无法满足大量需求时，该算法将很快失败，这表明可行性正确地检测到不可能的配置，而没有部分错配。

 ## 边缘情况

 一个关键的边缘情况是当一种本质的需求非常大而其他本质的需求很小时。 在这种情况下，算法会首先积极地将高级工作人员分配给需求量大的要素。 这样就避免了小精消耗高级工而大精无法满足的情况。 排序需求处理保证了正确的排序。 

当全局工作人员总功率足够但无法正​​确分区时，会出现另一种边缘情况。 当某些需求即使在耗尽所有级别后仍无法满足时，可行性检查就会失败，因为贪婪消耗总是首先使用最有效的可用分配。 这确保隐藏的“不良分布”被检测到而不是被忽视。
