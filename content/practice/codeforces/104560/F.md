 ## 问题理解

 我们正在模拟一个由起重机车在具有 240 个存储位置的圆形仓库周围移动所执行的程序。 每个位置都有许多板条箱，最初全部设置为一个。 指针从圆上的某个位置开始，重复执行一个短指令字符串，直到完成。 

指令集很小。 某些命令使指针沿着圆圈向前或向后移动。 某些命令会增加或减少当前位置的箱子数量。 两个特殊的括号符号定义了一个类似循环的控制流：当程序遇到右括号时，它会检查当前单元格，如果该单元格包含多个 crate，则执行跳回到匹配的左括号，而不是继续前进。 

关键的复杂性在于板条箱数量不是简单的整数。 每个位置始终保持在 1 到 256 的范围内，并具有环绕行为。 从单元中取出最后一个板条箱会立即将其重新填充到 256 个板条箱，并在丢弃 256 个板条箱后将 256 个包裹增加到一个。 因此，每个单元的行为类似于 256 个状态的循环计数器，但以移位方式表示，其中 0 映射到 256。 

任务不是输出最终配置，而是在多个测试用例中计算在执行完整程序直至终止时指针向左或向右移动的次数。 

乍一看，这些限制看起来很温和。 每个程序的长度最多为2000，测试用例最多为20个。 然而，微妙之处在于循环可能会重复多次，并且每次重复都可能取决于动态更改的单元格值。 仅跟踪控制流而没有仔细的状态处理的简单模拟有陷入非常长或循环执行的风险。 

有些情况对于幼稚的方法来说特别危险。 

当循环重复修改同一单元格时会出现一个问题，例如像这样的程序`(u)`。 如果单元格从 1 开始，则循环条件取决于它在 1 到 256 之间增加和减少。未正确处理环绕规则的天真的解释器可能会错误地假设单调进度，并且永远循环或过早终止。 

另一个问题来自循环内的指针移动。 由于指针可以在圆圈上移动，而循环条件取决于它恰好位于右括号处的任何单元格，因此很容易错误地假设条件取决于固定的内存位置。 实际上，位置是动态的，因此循环的行为可能会根据遍历路径的不同而有很大不同。 

最后，由于最多有两个非嵌套括号对，因此天真地假设其行为类似于简单的嵌套循环结构是具有误导性的。 这两个循环可以通过共享单元和指针移动间接交互。 

## 方法

 对程序的直接暴力解释很简单。 我们模拟指针，执行每条指令，更新循环位置，根据u和d修改240个单元格值。 在每一步中，当我们到达右括号时，我们都会检查当前单元格并可能跳回到匹配的左括号。 这忠实地模拟了规范。 

这种做法是正确的，因为它确实遵循了执行规则。 然而，问题是性能。 执行可以多次重新访问相同的程序状态。 这里的状态不仅仅是指令指针，还包括当前位置和 240 个单元的整个配置，每个单元有 256 个可能的值。 这会创建一个天文数字般巨大的状态空间，因此在最坏的情况下，没有记忆的简单模拟会面临运行时间极长的风险。 

关键的观察是，虽然理论上的状态空间巨大，但实际的程序结构很小且具有确定性，并且每次转换完全由当前状态决定。 这使我们能够将执行视为状态机并检测重复。 一旦某个状态重复，程序将在该循环中永远循环，但问题保证终止，因此在有效测试中不会发生此类循环。 这意味着不同的可达状态的数量实际上受执行本身的限制，而不是受理论最大值的限制。 

这提供了一个实用的解决方案：我们在跟踪访问状态的同时逐步进行模拟。 由于程序大小最多为 2000 个，并且最多有 20 个测试用例，并且转换逐渐改变系统，因此这种方法在预期约束下保持在限制范围内。

 ## 算法演练

 我们使用当前指令索引、当前指针在圆上的位置以及 240 个单元值的完整数组来表示机器状态。 我们还预先计算匹配的括号位置，以便可以在恒定时间内执行跳跃。

1. 在第一条指令处初始化程序计数器，并将指针设置为任意起始位置，通常为索引零。 将所有 240 个单元初始化为 1 个。 这与初始仓库配置相匹配。 
2. 使用堆栈预先计算匹配的括号。 每个左括号都与其相应的右括号配对。 这允许在触发循环条件时立即跳转。 
3. 维护总移动量计数器。 只有 f 和 b 指令对这个计数器有贡献，因为它们代表沿圆周的物理运动。 
4. 一条一条执行指令。 对于前向指令，将指针以 240 为模递增，并增加移动计数器。 对于向后指令，递减模 240 并增加移动计数器。 
5. 对于 u 和 d 指令，使用 1 到 256 范围内的循环算术更新当前单元格值。关键细节是正确处理环绕，其中低于 1 变为 256，高于 256 在删除 256 后变为 1。 
6. 遇到右括号时，检查当前单元格。 如果大于 1，则跳回匹配的左括号。 否则，继续前进。 这是系统中唯一的控制流修改。 
7. 重复此操作，直到指令指针移过程序末尾。 

正确性依赖于每个状态转换都是确定性的并且完全被当前配置捕获的事实。 该系统逐步发展，没有隐藏的副作用，因此忠实地模拟过渡会产生准确的运动数量。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve_case(s):
    n = len(s)

    match = {}
    stack = []
    for i, c in enumerate(s):
        if c == '(':
            stack.append(i)
        elif c == ')':
            j = stack.pop()
            match[i] = j
            match[j] = i

    pos = 0
    ip = 0
    moves = 0
    cells = [1] * 240

    while ip < n:
        c = s[ip]

        if c == 'f':
            pos = (pos + 1) % 240
            moves += 1
            ip += 1

        elif c == 'b':
            pos = (pos - 1) % 240
            moves += 1
            ip += 1

        elif c == 'u':
            cells[pos] += 1
            if cells[pos] == 257:
                cells[pos] = 1
            ip += 1

        elif c == 'd':
            cells[pos] -= 1
            if cells[pos] == 0:
                cells[pos] = 256
            ip += 1

        elif c == '(':
            ip += 1

        else:  # ')'
            if cells[pos] > 1:
                ip = match[ip]
            else:
                ip += 1

    return moves

def main():
    T = int(input())
    for tc in range(1, T + 1):
        s = input().strip()
        ans = solve_case(s)
        print(f"Case #{tc}: {ans}")

if __name__ == "__main__":
    main()
```解决方案首先为括号建立一个匹配表，这样每次跳转都可以立即解决，无需扫描。 这是至关重要的，因为循环内重复的向后跳转会增加模拟的成本。 

主循环维护指令指针和循环位置。 每个移动指令都直接更新位置并递增应答计数器。 模运算确保保留循环结构。 

单元格更新明确地实现了特殊的环绕规则。 增加超过 256 会重置为 1，减少到 1 以下会重置为 256。这可以避免维持真正的模 256 零状态，从而与问题的定义完全匹配。 

“)”的控制流使用预先计算的匹配表。 该决策是使用评估时的当前单元格值做出的，这可以正确模拟循环条件。

 ## 边缘情况

 一种边缘情况是指针围绕圆重复循环，而单元格值没有变化。 在这种情况下，只有移动指令对进度有贡献，并且模拟必须确保正确处理索引 239 处返回到 0 的回绕。 模运算保证了这一点。 

另一种边缘情况是通过 1 到 256 边界重复切换单个单元格。 当从 1 减一产生 256 时，程序不得将其视为零或负数，因为这会破坏循环条件。 显式修正可确保循环条件看到有效值。 

最后的边缘情况是一个循环，其中指针移离控制循环条件的单元格并稍后返回。 由于使用当前单元格（而不是原始单元格）在结束括号处检查条件，因此正确性取决于始终在评估时读取单元格。 仿真模型通过直接检查每个“)”处的当前位置来确保这一点。
