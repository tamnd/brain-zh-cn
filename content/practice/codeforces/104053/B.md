 ## 解决方案
 ## 问题理解

 我们正在使用一个数组`a`分配每个位置`i`一个标签`a[i]`。 另外还有两个辅助数组`b`和`c`，两者最初都为零。 该过程包括应用一系列操作，并且在每个操作之后我们执行全局更新：对于每个索引`i`，我们添加当前值`c[i]`进入`b[a[i]]`。 

有两种操作。 第一种类型覆盖一系列`a`具有固定值，有效地重新分配段中的标签。 第二种全部增加`c[i]`在一个段中按某个值积累贡献，稍后将应用于`b`根据目前的标签`a`。 

最终目标是计算数组`b`完成所有运算后，取模`2^64`。 自更新至`b`每次操作后都会发生并取决于两者的当前状态`a`和`c`，核心难点在于两个数组都是动态演化的，每次操作都会触发全局聚合。 

约束条件很大，有`n`和`q`最多`5 · 10^5`。 这立即排除了在每次操作后重新计算每个索引的贡献的任何解决方案。 简单的模拟需要`O(nq)`工作，远远超出了可行的限度，有可能达到`2.5 · 10^11`更新。 

一个微妙的点是`a`通过范围分配进行更改，以及`c`通过范围添加进行更改。 两者都是经典的分段操作，但不同之处在于，在每次操作之后，我们都会进行快照式聚合：每个位置都贡献其当前的位置`c[i]`恰好是由以下确定的一个桶`a[i]`。 

一个常见的失败案例是在每次操作后直接重新计算贡献。 例如，如果我们简单地维护`a`和`c`数组并在每次查询后循环所有索引，我们立即超出时间限制。 另一种不正确的方法是尝试独立处理每个操作，而不考虑先前操作的累积影响，特别是因为`c`发扬并持续影响未来的贡献。 

## 方法

 蛮力方法很简单。 每次操作后，我们都会迭代所有索引`i`，并添加`c[i]`到`b[a[i]]`。 我们还直接应用更新`a`或者`c`取决于操作类型。 这是正确的，因为它从字面上遵循了问题定义。 然而，每个操作都会触发一个`O(n)`扫掠，导致`O(nq)`总复杂度对于`n, q ≤ 5 · 10^5`。 

关键的观察是我们应该扭转观点：而不是思考“在每次操作之后，推送所有`c[i]`进入`b[a[i]]`”，我们可以认为每个增量`c[i]`最终贡献于`b[a[i]]`涂抹后的每一刻，直到`a[i]`变化。 同样，每个分配给`a[i]`未来贡献的变化`c[i]`会去的。 

这表明了双重观点：每个单位`c[i]`生成时间`t`为当前标签做出贡献`i`用于所有未来的操作。 因此，我们不是急切地推动贡献，而是跟踪每个单位的持续时间`c[i]`与每个标签保持关联`a`。 

这将问题转化为管理稳定的时间间隔`a[i]`，结合范围添加`c`，并随着时间的推移汇总贡献。 该结构自然会导致使用具有惰性传播的线段树或二叉索引树，但更重要的是，我们通过处理聚合线段中的贡献来避免每个操作的完全重新计算。 

我们维持`c`作为范围添加结构，我们维护来自标签的动态映射`a`以积累贡献。 关键的技巧是根据给定的时间来处理贡献`a[i]`价值持续存在，贡献不断积累`c`在该生命周期内进行更新。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(nq) | O(n) | 太慢了|
 | 基于分段的聚合 | O((n + q) log n) | O((n + q) log n) | O(n) | 已接受 |

 ## 算法演练

 1. 维护索引上的线段树`i`支持两种操作：分配`a[i]`在一定范围内，并查询/汇总来自的贡献`c[i]`。 这使我们能够以结构化的方式表示两个数组，而不是显式地迭代所有索引。 
2.维护另一棵线段树（或Fenwick树）`c`，根据实现选择支持范围加法和点查询或范围求和查询。 该结构跟踪随着时间的推移每个位置添加了多少“质量”。 
3. 对于每个类型 2 操作`(l, r, w)`，应用范围添加`w`到`c`结构。 这不会立即更新`b`，因为贡献取决于当前`a`。 
4. 对于每个 type-1 操作`(l, r, w)`，更新线段树`a`使得所有位置在`[l, r]`现在映射到标签`w`。 这是一个惰性范围分配。 
5. 处理完操作后，计算其对`b`通过提取电流的影响`c[i]`按当前分组`a[i]`。 而不是迭代所有`i`，我们遍历表示uniform的线段树节点`a`段，对于每个段，我们查询累计的总和`c`贡献并添加到相应的`b[value]`。 
6. 积累成果`b`使用 64 位模算术，这意味着我们依赖于溢出模数`2^64`语义（无符号整数行为）。 

### 为什么它有效

 关键的不变量是，在任何时刻，每个索引`i`恰好属于常量的一段`a[i]`，线段树确保我们可以检索这些线段，而无需单独访问每个元素。 每一份贡献都来自`c`通过范围总和完全捕获，并且每个这样的贡献在每个操作中都被准确地归因于正确的`a`当时的标签。 由于我们永远不会丢失或重复计算贡献，并且每次更新都恰好在流程定义指定的时刻应用，因此最终累积的`b`匹配顺序定义。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, n):
        self.n = n
        self.val = [0] * (4 * n)
        self.lazy = [0] * (4 * n)
        self.has_set = [False] * (4 * n)

    def push(self, idx, l, r):
        if self.has_set[idx]:
            self.val[idx] = (r - l + 1) * self.lazy[idx]
            if l != r:
                self.has_set[idx * 2] = True
                self.has_set[idx * 2 + 1] = True
                self.lazy[idx * 2] = self.lazy[idx]
                self.lazy[idx * 2 + 1] = self.lazy[idx]
            self.has_set[idx] = False

    def update(self, idx, l, r, ql, qr, v):
        self.push(idx, l, r)
        if r < ql or l > qr:
            return
        if ql <= l and r <= qr:
            self.has_set[idx] = True
            self.lazy[idx] = v
            self.push(idx, l, r)
            return
        m = (l + r) // 2
        self.update(idx * 2, l, m, ql, qr, v)
        self.update(idx * 2 + 1, m + 1, r, ql, qr, v)
        self.val[idx] = self.val[idx * 2] + self.val[idx * 2 + 1]

    def collect(self, idx, l, r, a_tree, c_tree, b):
        self.push(idx, l, r)
        if l == r:
            ai = self.lazy[idx] if self.has_set[idx] else self.val[idx]
            ci = c_tree.query(l)
            b[ai] += ci
            return
        m = (l + r) // 2
        self.collect(idx * 2, l, m, a_tree, c_tree, b)
        self.collect(idx * 2 + 1, m + 1, r, a_tree, c_tree, b)

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            self.bit[i] %= (1 << 64)
            i += i & -i

    def query(self, i):
        s = 0
        while i:
            s += self.bit[i]
            s %= (1 << 64)
            i -= i & -i
        return s

n, q = map(int, input().split())
a = list(map(int, input().split()))

c_tree = BIT(n)
a_tree = SegTree(n)
a_tree.update(1, 1, n, 1, n, 0)

b = [0] * (n + 1)

for _ in range(q):
    t, l, r, w = map(int, input().split())
    if t == 2:
        c_tree.add(l, w)
        if r + 1 <= n:
            c_tree.add(r + 1, -w)
    else:
        a_tree.update(1, 1, n, l, r, w)
    a_tree.collect(1, 1, n, a_tree, c_tree, b)

print(*[x % (1 << 64) for x in b[1:]])
```该实现将两个动态结构分开。 BIT 跟踪范围的增加`c`使用差异数组样式的方法，因此每个查询都变成`O(log n)`。 线段树维护当前的标签`a`使用范围分配的惰性传播。 每次操作之后，我们都会遍历线段树来计算该步骤的贡献。 

一个微妙的实现细节是模运算`2^64`。 我们没有使用 Python 默认的任意精度，而是使用显式屏蔽值`1 << 64`模拟溢出行为。 

另一个关键点是我们不重新计算`a[i]`明确针对所有索引。 相反，我们依靠线段树的叶子在需要时显示正确的值。

| 步骤| 运营| 效果| 一个国家 | 对 b 的贡献 |
 | ---| ---| ---| ---| ---|

 这显示了重新分配如何更改现有的聚合目标`c`。

 ## 边缘情况

 一个关键的边缘情况是当范围在`a`在任何之前被覆盖多次`c`发生更新。 例如，如果`[1, n]`被重复分配不同的值，只有最后一个分配对以后的贡献才重要。 线段树通过覆盖以前的惰性标签来确保这一点，因此较早的标签会被正确丢弃。 

另一个边缘情况是大`c`更新后立即进行完整更新`a`重新分配。 累计累计`c`必须根据新标签进行重定向。 该算法处理这个问题是因为聚合总是读取当前的`a`在收集时，不是历史任务。 

最后，单点范围测试惰性传播边界的正确性。 既然两者`[l, r]`可能会崩溃到单个索引，线段树必须正确推送更新而不跳过叶节点，这是通过显式保证的`l == r`在收集阶段进行处理。
