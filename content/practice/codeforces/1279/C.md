 ## 解决方案
 ## 问题理解

 这种情况是一堆唯一编号的项目，其中只有堆栈的顶部可以直接访问。 一系列操作要求我们按照给定的顺序重复删除特定的项目。 删除一个项目不是免费的：如果在删除时它位于顶部下方的 k 个位置，我们必须临时弹出它上面的 k 个项目，获取目标，然后将这 k 个项目恢复到堆栈中。 这种操作的成本与目标项在当前堆栈状态中的深度成正比。 

一个转折让这个问题变得非同小可。 当我们恢复暂时移除的物品时，我们可以在放回之前任意重新订购它们。 然而，我们不能移动最初位于已移除目标下方的任何东西，并且我们必须永远保留该较低的结构。 通过一系列删除，这种重新排序能力使我们能够“塑造”未来目标之上的堆栈，以降低未来的访问成本。 

输入包含初始堆栈顺序和所需删除的列表。 输出是按给定顺序删除所有必需项目所需的最短总时间，假设我们在每次删除后始终使用最佳可能的重新排列策略。 

这些约束允许所有测试用例中最多包含 100,000 个元素。 任何以简单方式重复检查或模拟堆栈操作的解决方案都会面临二次行为的风险。 O(nm) 甚至 O(n²) 方法将会失败，因为每次删除都可能扫描并重新洗牌堆栈的大部分。 

当一个简单的解决方案假设一旦删除一个元素，它相对于所有剩余元素的位置就固定时，就会出现微妙的故障模式。 这是不正确的，因为重新排序“缓冲区”元素可能会使后面的目标更接近顶部。 

一个具体的误导情况是目标以深度嵌套元素交错的顺序出现。 假设堆栈是`[5, 4, 3, 2, 1]`查询是`[1, 2, 3]`。 不仔细考虑重新排序的贪婪模拟可能会在每次提取后错误地重新计算深度，错过了可以重新组织之前删除的项目以最小化未来深度的情况。 

当实现假设目标之上的元素数量是静态时，就会出现另一个问题。 事实并非如此，因为只有已经提取的目标才会影响未来的重新安排； 非目标元素可以重新洗牌，以避免阻塞未来的目标。 

## 方法

 直接模拟通过扫描堆栈来定位所请求的元素、计算其上方有多少项、然后删除并恢复它们来处理每个查询。 这在原则上是正确的，因为它准确地反映了该过程，但速度太慢。 每个查询都可能遍历堆栈，在最坏的情况下导致 O(nm) 行为。 

关键的观察结果是，只有“已处理”和“尚未处理”元素之间的相对顺序才重要。 一旦我们删除一个元素，我们就可以将其上方的所有项目视为灵活池。 我们可以自由地重新排序这个池，因此对于将来的查询，我们只关心一个元素是否已经被“激活”。 

我们按顺序处理查询，并在已使用的所有元素中保持原始堆栈中的最高位置。 每次我们选择一个新元素时，如果它位于当前“活动边界”之上，则在穿越看不见的元素方面不需要任何额外成本； 否则，我们将为边界和该元素之间的所有不可见元素付费。 

这将问题简化为跟踪原始堆栈排序中迄今为止达到的最远位置，并且仅当我们扩展到之前看到的索引之外时才对贡献求和。

 ## 算法演练

 我们首先将每个当前数字映射到其在初始堆栈中的位置。 这让我们可以在 O(1) 查找时间内将查询序列转换为索引序列。 

我们维护一个变量`max_pos`，它表示由于之前的删除而我们已经“激活”的原始堆栈中的最远深度。 我们还维护一个索引指针，可以根据需要按升序在各个位置之间移动。 

对于每份要求的礼物：

 1. 将当前内容转换到其在原始堆栈中的位置。 

此步骤将问题从值空间转换为位置空间，其中排序变得线性且可比较。 
2. 如果该位置小于或等于`max_pos`，在答案中添加 0。 

该元素已经位于先前操作在概念上已清除的区域内，因此不需要传递任何未见过的项目。 
3. 否则，添加`(position - max_pos)`到答案。 

这表示当前边界之上新遇到的元素，必须是第一次通过。 
4. 更新`max_pos`如果更大，则返回当前位置。 

这扩展了处理的区域，以便将来的查询将这些元素识别为已经考虑的元素。 

此过程背后的原因是，堆栈中的每个元素仅对成本产生一次影响，此时它成为访问前缀的一部分。 之后，可以随时重新安排，以避免重复成本。 

### 为什么它有效

 堆栈可以被视为固定的垂直顺序，但我们的自由在于在每次操作后仅重新排列当前访问元素上方的部分。 这意味着任何曾经包含在“可见前缀”中的元素都可以最佳地放置在未来目标之上，从而消除重复的遍历成本。 

不变的是`max_pos`始终表示原始堆栈中在处理过程中至少暴露过一次的最深位置。 每增加一个单位`max_pos`恰好对应于一个元素被支付一次，并且不再支付。 由于任何元素在第一次高于所需目标时都不能被跳过，因此对答案的每一个贡献都是必要的且最小的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    pos = [0] * (n + 1)
    for i, x in enumerate(a):
        pos[x] = i + 1

    max_pos = 0
    ans = 0

    for x in b:
        p = pos[x]
        if p > max_pos:
            ans += p - max_pos
            max_pos = p

    print(ans)
```关键的实现细节是将堆栈转换为位置数组。 这避免了重复扫描并允许对每个查询元素进行恒定时间查找。 变量`max_pos`对已计算的堆栈前缀的边界进行编码，确保我们不会重复计算先前包含在成本中的元素。 

一个常见的错误是重置或调整`max_pos`在每次错误查询后，将其视为滑动窗口边界。 正确的解释是单调的：一旦到达某个位置，它就永远保持到达状态。 

## 工作示例

 考虑示例堆栈`[3, 1, 2]`有疑问`[3, 2, 1]`。 

我们将值映射到位置：`3 -> 1`,`1 -> 2`,`2 -> 3`。 

| 查询 | 职位| | 之前的 max_pos 成本增加 | | 之后的 max_pos
 | ---| ---| ---| ---| ---|
 | 3 | 1 | 0 | 1 | 1 |
 | 2 | 3 | 1 | 2 | 3 |
 | 1 | 2 | 3 | 0 | 3 |

 总成本为3。 

现在考虑`[2, 1, 7, 3, 4, 5, 6]`有疑问`[3, 1]`。 

映射：`3 -> 4`,`1 -> 2`。 

| 查询 | 职位| | 之前的 max_pos 成本增加 | | 之后的 max_pos
 | ---| ---| ---| ---| ---|
 | 3 | 4 | 0 | 4 | 4 |
 | 1 | 2 | 4 | 0 | 4 |

 总成本为4。 

这些痕迹表明，只有当我们第一次扩展原始堆栈的已处理前缀时，成本才会累积。

 ## 边缘情况

 当所有请求的元素都位于堆栈顶部附近但按位置降序出现时，就会出现极端情况。 例如，如果堆栈是`[1, 2, 3, 4, 5]`和查询是`[5, 4, 3]`，算法展开`max_pos`仅在需要时，确保每个新的更深层次访问准确地贡献其未覆盖的部分。 计算正确地避免了重复计算，因为一旦`max_pos`达到 5 时，所有后续查询都位于已处理的前缀内。 

另一种情况是查询已经按堆栈顺序排列。 如果堆栈是`[4, 3, 2, 1]`和查询是`[3, 1]`，第一个查询部分扩展了前缀，第二个查询完全落在其中。 该算法自然会为第二个查询分配零额外成本，因为没有暴露新的前缀。
