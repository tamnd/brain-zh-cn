 ## 解决方案
 ## 问题理解

 大法师开始时具有大小的完整法力池`n`。 在每一秒中，他可能会花费`x`如果有足够的法力，他可以召唤一个水元素，否则他可能会等待。 做出决定后，他的气场恢复了`y`法力，但法力不能超过`n`。 

任务是在第一阶段找到尽可能多的召唤`m`秒。 每个测试用例都给出了法力限制、可用秒数、一次召唤的法力消耗以及恢复量。 

这些限制使主要困难变得清晰。 最多可以有`100000`测试用例，每个值可以大到`10^9`。 每秒处理一次的模拟最多需要`10^14`最坏情况下的操作，远远超出了2秒的限制。 该解决方案必须将每个测试用例的过程减少到恒定的时间。 

棘手的情况来自于再生和法力上限之间的相互作用。 直接模拟通常适用于小例子，但在以下情况下会失败`m`巨大或者当大法师可以永久施法或者必须依赖累积再生时。 

例如，考虑：```
1
2 5 1 1
```正确的输出是：```
5
```粗心的解决方案可能会认为法力会减少，因为每次召唤都会消耗法力。 然而，成本和再生是相等的，因此每一整秒后法力都会恢复到相同的值。 

另一个边缘情况是当再生小于法术成本时：```
1
6 10 4 2
```正确的输出是：```
6
```假设大法师应该尽可能等待的模拟可能会忽略这样一个事实：在需要再生之前，初始的全部法力可以转换为多次立即施法。 

最后的边界情况是秒数是限制因素：```
1
100 3 20 5
```正确的输出是：```
3
```尽管法力供应足以容纳更多法术，但只允许三个动作，因为游戏持续三秒。 

## 方法

 最直接的方法是模拟每一秒。 保持当前法力值，检查是否可以召唤，减去`x`如果是，则添加`y`与应用的上限。 这完全符合游戏规则，所以结果是正确的。 

问题是秒数。 自从`m`可以达到`10^9`并且可以有`10^5`测试用例，模拟总秒数可以达到`10^14`。 模拟对于理解过程很有用，但不能用于最终的解决方案。 

关键的观察结果是，唯一重要的资源是整个时期内可用的法力总量。 最初大法师拥有`n`法力。 在接下来的时间里`m - 1`最多修复一下`(m - 1) * y`可以恢复额外的法力。 最后一秒的恢复发生在最终决定之后，因此无法帮助创建另一个召唤。 

什么时候`x <= y`，每次召唤在恢复后都会有效地收回成本。 自从大法师开始满`n >= x + y >= x`，他每一秒都可以施展。 

什么时候`x > y`，每次召唤消耗的法力多于一次恢复返回的法力。 然而，可用于召唤的法力总量仍然受到初始法力加上最终行动前所有恢复的限制。 将此总数除以`x`给出最大可能的传票数量。 答案也不能超过`m`，因为只有`m`秒。 

因此，最佳解决方案是恒定时间计算。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(米) | O(1) | O(1) | 太慢了|
 | 最佳| O(1) | O(1) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1.如果再生量`y`至少是法术成本`x`， 输出`m`。 每次施法都会在第二秒结束时得到恢复补偿，因此大法师可以在每一秒内进行召唤。 
2. 否则，计算可用于召唤的总法力值：`n + (m - 1) * y`。 初始法力在第一个动作之前可用，并且仅在第一个动作之前可用`m - 1`修复可以为未来的传唤做出贡献。 
3.将此总数除以`x`以获得可用法力可以支付的最大数量的完整召唤。 
4. 将结果限制为`m`，因为即使无限的法力每秒也不能产生多于一次的召唤。 

为什么它有效：

 当`x > y`，每次召唤都会永久移除`x - y`法力恢复后会从系统中恢复。 等待和施法的确切顺序不会增加可以消耗的法力总量。 初始法力和第一`m - 1`修复是所有传票可用的完整预算。 每次召唤消耗精确`x`因此，传唤次数不能超过预算的整数除以`x`。 由于每当计数在限制范围内时，大法师总是可以安排他的行动来消耗可用的法力，因此这个限制是可以实现的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    ans = []

    for _ in range(t):
        n, m, x, y = map(int, input().split())

        if y >= x:
            ans.append(str(m))
        else:
            ans.append(str(min(m, (n + (m - 1) * y) // x)))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```该解决方案首先区分再生与法术使用同步的情况。 在这种情况下，没有理由跳过一秒钟。 

对于另一种情况，表达式`n + (m - 1) * y`代表可以贡献施法的总法力值。 乘法使用`m - 1`而不是`m`因为最后一秒后的恢复来得太晚，无法创造另一个咒语。 

Python 整数安全地处理最大的中间值。 最大的乘法约为`10^18`，它非常适合 Python 的任意精度整数类型。 这`min`操作处理计算出的法力预算允许的法术数量多于可用秒数的边界。 

## 工作示例

 对于第一个样本：```
n = 2, m = 2, x = 1, y = 1
```自从`y >= x`，每一秒都可以包含召唤。 

| 第二 | 行动前的法力 | 行动| 恢复后的法力| 传票 |
 | ---| ---| ---| ---| ---|
 | 1 | 2 | 演员 | 2 | 1 |
 | 2 | 2 | 演员 | 2 | 2 |

 该迹线显示了无限再生的情况。 每一秒后法力都会恢复到相同的值，因此时间限制是唯一的限制。 

对于第二个样本：```
n = 4, m = 4, x = 2, y = 1
```这里`x > y`，因此使用可用法力计算。 

| 变量| 价值|
 | ---| ---|
 | 初始法力 | 4 |
 | 最后一秒前的恢复| 3 |
 | 总可用法力| 4 + 3 = 7 |
 | 法术成本| 2 |
 | 基于法力的召唤| 7 // 2 = 3 | 7 // 2 = 3 |
 | 时间限制 | 4 |
 | 回答 | 3 |

 该痕迹表明最终修复体已被排除。 计算它会错误地给出一个额外的可能召唤。

 ## 边缘情况

 对于同等再生情况：```
1
2 5 1 1
```算法检查`y >= x`，这是事实。 它立即返回`5`。 这与真实过程相符，因为每一秒都会消耗 1 点法力，然后恢复 1 点法力。 

对于初始法力爆发的情况：```
1
6 10 4 2
```该算法计算：```
(6 + 9 * 2) // 4 = 24 // 4 = 6
```结果是`6`。 最初的法力值允许进行多次早期施法，而后期的恢复则为额外的召唤添加了足够的法力值。 最终修复不包括在内，因为它发生在最后一次可能的铸造之后。 

对于大时间的情况：```
1
100 3 20 5
```计算得出：```
(100 + 2 * 5) // 20 = 110 // 20 = 5
```那么答案就受到限制`m`，生产`3`。 该算法正确地尊重了这样一个事实：一秒钟最多可以创建一个水元素。
