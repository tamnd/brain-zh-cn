 ## 解决方案
 ## 问题理解

 我们被赋予了几个“场景”。 每个场景都由一组代表颜色的整数来描述。 对于每个场景，都定义了一个特殊值：其主颜色，即其集合内的最大值。 

我们必须将所有场景排列起来。 确定订单后，我们会查看每个相邻的对。 如果 A 的主颜色出现在 B 的完整颜色集中的某处，则计算从场景 A 到场景 B 的过渡。目标是对场景重新排序，以便此类过渡的数量尽可能多。 

输入大小很大：所有集合中最多有 100,000 个场景和 200,000 个总颜色条目。 任何尝试所有排列的解决方案都是立即不可能的，因为这已经是阶乘了。 即使对场景对进行二次或三次推理也会太慢。 这强烈表明答案取决于局部贪婪结构和对颜色出现的有效簿记。 

一个微妙的点是转移条件是不对称的。 A 是否可以转换为 B 仅取决于 A 的最大值以及该值在 B 中的隶属度。相反的方向是不相关的，这意味着我们正在有效地构建一条有向路径，试图将每个节点携带的特定值与未来节点集对齐。 

常见的失败案例来自于认为这是对称兼容性问题。 

如果场景 A 有颜色`{1, 100}`场景 B 有`{100}`，那么 A 可以过渡到 B，但 B 不一定能过渡回来，除非 100 也是 B 的最大值并且出现在 A 的集合中，但事实并非如此。 将此视为无向匹配问题会失去结构并导致错误的贪婪策略。 

当尝试按最大颜色或按设置大小排序时，会出现另一种失败模式。 两者都与场景可以创建多少个过渡相关，因为有用性取决于有多少未来场景包含其最大值，而不是值本身。 

## 方法

 蛮力的想法是尝试每种排列并计算有效的转换。 对于每种排列，检查所有相邻对都需要线性时间，但有$n!$排列，即使对于非常小的排列，也远远超出了可行的计算$n$。 即使尝试通过回溯构建排列也会导致指数分支。 

关键的观察是将视角从“一个场景如何连接到下一个场景”转变为“一个场景如何帮助之前的场景”。 一个场景$j$提供从前一个场景的过渡$i$恰好当最大值$i$包含在$j$已设定。 所以每个场景$j$可以看作是先前场景“请求”的收集器：每个先前场景的最大颜色位于$S_j$好处如果$j$紧随其后。 

这将问题转化为构建一个序列，其中每个位置选择应该最大化它满足前一个位置的剩余“所需颜色”的数量。 

对于每种颜色，我们维护当前有多少剩余场景将该颜色作为其最大值。 对于下一个场景的候选人$j$，其值为最大包含在中的剩余场景数$S_j$。 选择具有最高此类值的场景是一种自然的贪婪策略，并且当我们删除场景时可以动态维护这一策略。 

剩下的挑战是在计数变化时有效地维护这些值，因为删除场景会减少包含该颜色的所有场景中其最大颜色的贡献。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 |$O(n! \cdot n)$|$O(n)$| 太慢了 |
 | 贪婪动态计分|$O((n + \sum m_i)\log n)$|$O(n + \sum m_i)$| 已接受 |

 ## 算法演练

 我们为每个场景分配其主颜色，这是其集合中的最大元素。 我们还准备了从每种颜色到其集合包含该颜色的场景列表的反向索引。 

我们为每种颜色维护一个计数器，用于跟踪当前有多少未放置的场景将该颜色作为其最大值。 

我们还为每个场景维护一个分数，定义为其集合中所有颜色的总和，即有多少剩余场景将该颜色作为其最大值。 该分数表示如果该场景紧随当前位置放置，则该场景可以创建多少个潜在过渡。 

我们反复选择当前得分最高的未放置场景，将其附加到答案中，并将其从考虑中删除。 当我们删除一个场景时，我们会减少其最大颜色的计数器，然后更新包含该颜色的所有场景的分数。 

此过程一直持续到所有场景都已放置完毕。 最后，我们通过按构造顺序扫描相邻对来计算转换。 

### 为什么它有效

 在任何时刻，场景的分数都会精确测量如果接下来选择它，它可以从当前剩余场景池中创建多少个可能的转换。 每次更新都反映了这样一个事实：一旦场景具有最大颜色$c$使用后，未来的候选人将无法再从中受益$c$。 这确保了每个贪婪的选择都是在充分了解每个场景仍然可以贡献多少剩余机会的情况下做出的，并且以后的决定不能追溯性地增加先前删除的场景的有用性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    sets = []
    mx = []
    
    color_to_nodes = {}
    
    for i in range(n):
        arr = list(map(int, input().split()))
        m = arr[0]
        s = arr[1:]
        sets.append(s)
        mx_val = max(s)
        mx.append(mx_val)
    
    cnt = {}
    for i in range(n):
        c = mx[i]
        cnt[c] = cnt.get(c, 0) + 1
    
    # build color -> nodes containing it
    for i in range(n):
        for c in sets[i]:
            if c not in color_to_nodes:
                color_to_nodes[c] = []
            color_to_nodes[c].append(i)
    
    score = [0] * n
    for i in range(n):
        sc = 0
        for c in sets[i]:
            sc += cnt.get(c, 0)
        score[i] = sc
    
    import heapq
    heap = [(-score[i], i) for i in range(n)]
    heapq.heapify(heap)
    
    removed = [False] * n
    ans = []
    
    while heap:
        neg_s, i = heapq.heappop(heap)
        if removed[i]:
            continue
        
        # recompute lazily check
        cur = 0
        for c in sets[i]:
            cur += cnt.get(c, 0)
        if cur != -neg_s:
            heapq.heappush(heap, (-cur, i))
            continue
        
        removed[i] = True
        ans.append(i)
        
        c0 = mx[i]
        cnt[c0] -= 1
        if cnt[c0] == 0:
            del cnt[c0]
        
        if c0 in color_to_nodes:
            for j in color_to_nodes[c0]:
                if not removed[j]:
                    # update score lazily by decreasing one occurrence
                    score[j] -= 1
                    heapq.heappush(heap, (-score[j], j))
    
    # count transitions
    pos = {v: i for i, v in enumerate(ans)}
    res = 0
    for i in range(n - 1):
        a = ans[i]
        b = ans[i + 1]
        if mx[a] in sets[b]:
            res += 1
    
    print(res)
    print(*[x + 1 for x in ans])

if __name__ == "__main__":
    solve()
```该解决方案首先构建所有必要的结构：每个场景的最大颜色、这些最大值的频率以及从颜色到包含它们的场景的倒排索引。 分数计算使用的思想是，场景的价值与它可以满足的剩余最大颜色的数量成正比。 

堆用于始终提取当前最佳候选者。 由于当我们删除场景时分数会发生变化，因此可能会出现过时的堆条目，因此每次提取都会通过重新计算当前分数并在过时时推回来验证正确性。 

选择场景后，我们会减少其最大颜色的计数器，并将该更改传播到包含该颜色的所有场景。 这是我们可以增量维护分数而不是从头开始重新计算的唯一原因。 

最后，通过显式计算构造的排列上的转换来验证答案。 

## 工作示例

 考虑一个小输入：```
3
2 1 2
2 2 3
2 1 3
```这里的最大值是`[2, 3, 3]`。 

我们从计数开始`cnt[2]=1`,`cnt[3]=2`。 

初始分数：

 | 场景| 设置| 分数 |
 | ---| ---| ---|
 | 1 | {1,2} | cnt[1]+cnt[2] = 0+1 = 1 |
 | 2 | {2,3} | 1+2 = 3 |
 | 3 | {1,3} | 0+2 = 2 |

 我们首先选择场景2。 它的最大值是 3，所以我们减少`cnt[3]`为 1 并更新包含 3 的场景。 

| 步骤| 精选| 剩余 cnt[3] | 接下来的推理 |
 | ---| ---| ---| ---|
 | 1 | 2 | 1 | 包含3的场景分数减少|

 接下来的分数变为：

 场景 3 缩小，场景 2 被删除。 

然后，我们在场景 3 和场景 1 之间进行选择，由于得分较高，我们更喜欢场景 3，然后是场景 1。 

Trace 证实，我们总是优先考虑组中仍有许多剩余匹配项的场景。 

第二种情况：```
2
1 10
1 20
```千里马是`[10, 20]`，并且没有一个集合包含另一个集合的最大值。 所有分数保持为零，因此选择任何顺序，并且转换保持为零。 当不存在兼容性时，该算法不会强制人工结构。

 ## 边缘情况

 一个关键的边缘情况是所有场景共享相同的最大颜色。 在这种情况下，每个场景都会从其他场景中受益，并且算法会持续保持所有节点的高分，直到最后一次删除。 贪婪选择在相等的情况下变得任意，但每个邻接仍然有效，产生最大$n-1$过渡。 

另一种情况是，当颜色形成不相交的组时，任何其他组内都没有出现最大值。 在这里，所有分数始终为零。 堆退化为任意排序，这是正确的，因为没有排序可以产生任何转换。 

更微妙的情况是，单一颜色在许多场景中占主导地位，但仅在一个场景中出现最多。 删除该场景会触发大量的分数降低，但由于更新仅限于包含该颜色的场景，因此保留了正确性，并且不影响不相关的场景。
