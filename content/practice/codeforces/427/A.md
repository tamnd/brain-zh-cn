 ## 解决方案
 ## 问题理解

 我们得到了一个城市中按时间顺序发生的一系列事件。 每个事件要么是一名或多名新警察的到来，要么是犯罪事件的发生。 当新兵到来时，他们会增加可用军官的数量。 当犯罪发生时，它只会消耗一名当前可用的警官（如果有的话）； 否则，该犯罪行为不予处理。 

任务是模拟这个过程，并计算有多少犯罪行为在发生时无法分配给任何警官。 

输入大小最多可达 100,000 个事件。 这立即表明任何执行嵌套扫描或重新访问先前事件的解决方案都会太慢。 仅维护当前可用官员数量的线性扫描是充分且必要的，因为每个事件都必须按顺序处理，并且决策仅取决于当前状态。 

试图将每项犯罪与最早可能的新兵相匹配或向后搜索可用警官的暴力想法在最坏的情况下会退化为二次行为，因为许多犯罪和新兵交织在一起。 对于 10^5 个事件，O(n^2) 将远远超出可行的限制。 

一个微妙的边缘案例来自于新兵出现之前的连续犯罪。 例如，如果输入是`-1 -1 1`，前两起犯罪事件发生时警员为零，因此都没有得到治疗。 后来的招募并没有追溯帮助。 

另一个边缘情况是当新兵大量到达时超出了需要，例如`5 5 -1 -1 -1`。 只有三名军官被消耗掉，剩下的军官将继续为以后的事件做准备。 错误的贪婪方法可能会错误地“重置”每个事件的计数，而不是维护全局池。 

## 方法

 这种幼稚的方法试图将警官逐一明确地分配给犯罪分子，可能通过扫描早期事件或维护个人警官名单来为每个犯罪事件寻找可用的新兵。 虽然逻辑上是正确的，但这会导致不必要的开销，因为每个官员都是相同的并且可以互换。 唯一相关的状态是目前有多少官员是自由的。 

如果我们单独模拟每位警官，每个新兵都会增加一个列表，而每次犯罪都会从该列表中删除一个元素。 在最坏的情况下，由于转移或搜索，我们将对每个事件执行 O(n) 列表操作，当所有事件都是犯罪或新兵时，会导致 O(n^2) 行为。 

关键的观察是我们永远不需要对官员进行身份级别的跟踪。 我们只需要一个代表可用官员的柜台。 每个招募事件都会增加此计数器，并且如果可能的话，每个犯罪都会消耗它，否则会增加未处理的计数。 这将问题减少到具有恒定时间更新的单次传递。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力破解（追踪个人）| O(n^2) | O(n^2) | O(n) | 太慢了|
 | 最优（计数器模拟）| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们维护两个整数：一个用于当前可用的警官，另一个用于未处理的犯罪。 

我们按顺序处理事件。 

1. 初始化变量`available`到 0。这代表当前有多少官员是空闲的。 
2. 初始化变量`untreated`到 0。这会跟踪无法处理的犯罪。 
3. 从左到右阅读每个事件。 
4. 如果事件值为正，则增加`available`之所以如此，是因为新员工可以立即上岗。 
5. 如果事件值为`-1`，我们正在处理犯罪行为。 
6. 如果`available`大于0，减少`available`由于由一名警官处理此犯罪，因此减少 1。 
7. 否则，增加`untreated`减 1，因为此时没有官员可用。 
8.处理完所有事件后，输出`untreated`。 

每个犯罪步骤的决策都是局部最优的，因为每个警官都是相同的，并且在警官之间进行拯救或选择没有任何好处。 

### 为什么它有效

 在序列的任何前缀处，`available`准确地代表了过去的新兵仍然可以犯下多少罪行。 由于每个警官最多可以处理一项犯罪，并且不存在超出可用性的过期或排序限制，因此该系统的行为就像一个简单的资源计数器。 每次犯罪发生时，如果可能的话，消耗一个单位的该计数器总是最佳的，并且如果不这样做，每次短缺都会增加一次不可避免的损失。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n = int(input())
events = list(map(int, input().split()))

available = 0
untreated = 0

for x in events:
    if x == -1:
        if available > 0:
            available -= 1
        else:
            untreated += 1
    else:
        available += x

print(untreated)
```代码直接遵循模拟策略。 这`available`变量仅通过加法和减法更新，确保每个事件的工作时间为 O(1)。 检查的顺序很重要：我们必须在更新该事件的其他任何内容之前处理犯罪，因为该事件本身要么是犯罪，要么是招募。 

一个常见的错误是将新兵存储在列表中并从中弹出。 这是不必要的，并且存在效率低下的风险。 另一个错误是重置`available`每个事件而不是全局累积。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n = int(sys.stdin.readline())

    available = 0
    untreated = 0

        if x == -1:
            if available > 0:
                available -= 1

 ## 边缘情况

 一个重要的边缘案例是犯罪发生在新兵出现之前。 用于输入`-1 -1 -1`，算法保持`available = 0`整个过程和增量`untreated`对于每一个事件。 这符合不可能进行追溯分配的要求。 

另一个极端情况是，大批新兵在发生数起犯罪事件后抵达。 用于输入`-1 -1 5`，前两种犯罪增加`untreated`2. 当5名新兵到达时，`available`变成5，但是并没有减少已经统计的故障数。 这种行为是正确的，因为犯罪一发生就立即解决，过去的故障无法修复。 

最后一个边缘情况是新兵与序列后面的犯罪完全匹配，例如`2 -1 -1`。 第一个事件集`available = 2`。 每一起犯罪都会消耗一名警官，将计数器减少到零，没有任何犯罪会被处理。 这证实了计数器正确地模拟了一对一分配。
