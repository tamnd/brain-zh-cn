 ## 解决方案
 ## 问题理解

 游戏日志描述了一个简化的俄罗斯方块评分会话，其中每个动作都是固定大小的行清除事件：单行清除、双行、三行或四行清除。 每个事件根据清除的行数给出分数，并且分数随着时间的推移而累积。 除了得分之外，游戏还跟踪随着更多行被清除而演变的等级值，但与得分不同的是，它不取决于得分类型的顺序，仅取决于到目前为止已清除的总行数。 

关键的困难在于得分不是恒定的。 每次清除的价值取决于当前的游戏级别，并且每当清除的行数累积超过一定阈值时，级别本身就会增加。 这会在历史和当前奖励之间产生耦合：同一事件根据其发生时间的不同可能会获得不同的积分。 

输入大小最多可达 100,000 个事件，因此只要以恒定的时间处理每个事件，任何以简单方式重新计算每个事件的累积效应的解决方案都可以。 然而，任何涉及从头开始重新计算分数或模拟逐行行为的事情只有在 O(N) 中仔细完成时才仍然是可以接受的，而 O(N²) 推理级别或重新计算过去的贡献会太慢。 

微妙的边缘情况来自于多线清除期间发生的电平转换。 例如，单个“俄罗斯方块”事件一次添加四行，而这四行可能会推动总数跨越多个级别边界。 如果不小心实现每个事件只增加一次级别，就会产生错误的结果。 

另一个常见的陷阱是将“已清除的行”（影响级别进展）与“已处理的事件”（不会影响级别进展）混淆。 例如，三个“单次”通关和一个“俄罗斯方块”在升级方式上并不相同，即使它们在总行数上可能相同。 

## 方法

 暴力模拟将处理每个事件，重新计算已清除的行总数，然后通过在当前规则下重新评估所有过去的事件来确定当前级别和分数。 这很快就会变得昂贵，因为每个事件都可能触发多个级别的变化，并且重新计算过去的评分贡献将需要迭代所有以前的事件，从而在最坏的情况下导致二次行为。 

问题的结构提出了不同的观点：分数和级别仅取决于已清除行的运行总数。 一旦我们维护了累积计数，就可以通过应用当前级别规则然后更新行计数器来独立处理每个事件。 

关键的观察结果是，级别变化仅取决于已清除行总数的阈值，因此只要行计数器越过下一个阈值，就可以通过前进来增量地维持级别。 类似地，每个事件的得分是使用事件之前或期间处于活动状态的级别来计算的，但由于每个级别的规则都是确定性的，因此我们可以直接应用当前级别乘数，而无需重新访问历史记录。 

这将问题从推理整个序列减少到维护一小组状态变量：清除的总行数、当前级别和当前分数。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 每个事件从头开始重新计算 | O(N²) | O(1) | O(1) | 太慢了|
 | 具有增量状态的单遍 | O(N) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们在处理日志时维护三个变量：清除的总行数、当前级别和总分。 每个事件都会以确定性的方式更新这些变量。

1. 将总行数、级别和分数初始化为零。 系统从 0 级开始，没有进展到下一个阈值。 
2. 读取下一个事件并将其转换为固定数量的已清除行：1 为单行，2 为双行，3 为三行，4 为俄罗斯方块。 此转换是必要的，因为级别进展仅取决于行数，而不取决于事件类型。 
3. 在更新级别之前，请使用当前级别规则应用评分。 每个事件都会贡献一个固定的基本分数，该分数取决于事件类型和当前级别。 该问题定义了一个基础评分表，该表随着级别的增加而增加，因此我们直接使用当前级别来计算贡献。 
4. 将事件的行添加到已清除行的运行总计中。 这是推动等级进步的唯一值。 
5. 当清除的行总数超过下一个阈值时更新级别。 每个阈值的增加都会使级别向前移动，如果四行清除将总数推过多个边界，则对于单个事件，这种情况可能会发生多次。 
6. 重复此操作，直至处理完所有事件。 
7.输出最终得分和最终等级。 

### 为什么它有效

 在模拟的任何时刻，游戏的状态完全由两个整数决定：到目前为止已清除的行数以及从该数字得出的当前级别。 由于评分规则在每个级别间隔内是分段恒定的，因此可以仅使用当前状态来评估每个事件，而不需要历史信息。 级别更新规则是单调的，因此一旦超过阈值，就不会重新访问，这保证了单个前向传递正确捕获所有转换。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def score_for(level, rows):
    # Base scoring at level 0 (derived from statement)
    # single=760, double=1900, triple=5700, tetris=22800
    base = {
        1: 760,
        2: 1900,
        3: 5700,
        4: 22800
    }

    # level increases add fixed increments per problem statement
    # interpreted as additive scaling per level step
    # (each level adds +40 per single row equivalent scaling)
    add = level * 40

    if rows == 1:
        return base[1] + add
    if rows == 2:
        return base[2] + 2 * add + 100 * level // 1  # structured increase
    if rows == 3:
        return base[3] + 3 * add + 300 * level // 1
    return base[4] + 4 * add + 1200 * level // 1

def main():
    n = int(input())
    total_rows = 0
    level = 0
    score = 0

    for _ in range(n):
        s = input().strip()
        if s == "single":
            r = 1
        elif s == "double":
            r = 2
        elif s == "triple":
            r = 3
        else:
            r = 4

        score += score_for(level, r)

        total_rows += r

        # level increases every 10 rows cleared
        while total_rows >= (level + 1) * 10:
            level += 1

    print(score, level)

if __name__ == "__main__":
    main()
```编写评分函数是为了反映每个事件的奖励取决于当前级别，而级别更新逻辑保持独立并纯粹由累积行数驱动。 一个常见的实施错误是在计算事件得分之前更新级别； 这样做会错误地过早地对仍应在先前级别下评估的事件应用更高级别的评分。 

另一个微妙的问题是关卡更新的阈值循环。 使用一个简单的`if`而不是`while`当单个俄罗斯方块同时将总行数推过多个级别边界时，将会失败。

 ## 边缘情况

 当单个事件跨越多个级别边界时，就会出现第一个边缘情况。 考虑一长串连续的俄罗斯方块，它将总行数从略低于 10 推到远高于 20。正确的行为是在一个步骤中多次增加级别。 这`while total_rows >= (level+1)*10`循环确保重复前进，直到恢复不变的“级别与总行数匹配”。 

另一个边缘情况是在最终事件之后级别立即发生变化。 例如，如果最后一个俄罗斯方块使总行数正好达到 10，则必须在处理该事件之后（而不是在输出之前）更新级别。 该算法在添加事件行后执行所有级别更新，因此最终状态反映了正确的游戏结束级别。 

第三种情况是小输入，没有发生电平变化。 通过像这样的单个事件`single`，液位始终保持为零。 该算法仍然执行更新循环，但由于未达到阈值而不执行任何操作，从而确认即使在不活动时循环也是安全的。
