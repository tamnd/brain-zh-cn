 ## 解决方案
 ## 问题理解

 我们正在与一个隐藏号码互动$x_0$，但我们从来没有直接看到它。 相反，还有第二个不断发展的价值$x$开始等于$x_0$。 我们可以发出三种交互式命令。 有人问当前是否$x$可以被选定的数字整除$a$。 另一个从中减去选定的值$x$。 最后一个输出对原始隐藏值的猜测$x_0$，之后交互结束。 

关键的困难在于每个查询都是关于当前状态的$x$，但目标是初始状态$x_0$。 由于减法运算永久改变$x$，必须仔细控制操作顺序，以便有关的信息$x_0$还是可以恢复的。 

计算方面的限制很宽松，但交互预算方面的限制很紧张：最多 70 个查询。 这立即排除了任何试图重建的方法$x_0$使用许多探针一点一点地进行，或者依赖于扫描大范围的候选者。 该解决方案必须为每个查询提取足够的结构信息，最好使用压缩信息的算术属性。 

一个微妙的边缘情况是减法可以驱动$x$为零。 一次$x = 0$，整除性查询总是返回“是”$a$， 因为$0$可被所有非零整数整除。 如果一个策略在达到零后不小心依赖于区分值，那么它就会变得毫无用处。 

另一个问题是整除性查询是关于当前值，而不是原始值。 天真的读者可能会认为重复的查询，例如“它是否可以被$p$？” 给出有关的直接因素信息$x_0$，但减法会改变数字，因此必须通过更新仔细保留任何因素证据。 

## 方法

 一个直接的想法是将其视为黑盒数重构问题并尝试恢复$x_0$通过测试许多候选人或逐渐缩小间隔。 这立即就会遇到查询限制：即使是二分搜索$10^9$需要大约 30 个是/否决定，但每个决定都需要与固定参考值进行可靠比较，而我们没有固定参考值。 此外，减法改变了隐藏状态，因此我们无法维持稳定的比较基线。 

另一个天真的想法是使用模算术查询逐位恢复数字。 然而，我们没有模块化余数查询； 我们只对当前值进行整除性测试，其表达力要差得多。 

关键的观察结果是整除性查询“是$x$可除以$a$？” 当与受控减法相结合时，它会变得极其强大。 如果我们可以强迫$x$当它以可预测的方式变成多个已知值的状态时，我们可以有效地将结构“锁定”到数字中，并通过整除性检查将其读回。 

核心技巧是认识到可以使用减法将隐藏数减少到零，但我们实际上不需要知道中间值。 一旦数字达到零，每个整除性查询都会返回“是”，这让我们检测到我们已经完全耗尽了原始值。 

该策略是迭代地剥离来自$x_0$使用仔细选择的值，然后最终查询足够的结构来准确确定原始值。 由于交互允许自适应步骤，我们可以利用这样一个事实：在一系列减法之后，减去的总量等于$x_0$当隐藏状态为零时。 

因此，问题减少为累加总减值，同时检测何时过零，确保我们不会超调。 一旦达到零，我们就可以安全地将累加和输出为原始数字。

 ## 算法演练

 1. 维护一个变量`acc`代表到目前为止我们减去的总金额。 最初`acc = 0`。 这个想法是，如果我们将隐藏数字精确地减少到零，那么`acc`等于$x_0$。 
2. 重复选择一个固定的正整数`b`（例如 1 或任何常量策略），然后发出查询“- b”。 这减少了隐藏$x$经过`b`并增加我们的累计减法。 
3. 每次减法之后，可选择发出整除性查询，例如“？1”或其他固定值，以检测隐藏值是否已达到零。 由于零可以被所有非零整数整除，因此一旦响应变得与零行为基本一致，我们就知道我们已经达到或通过了边界。 
4. 如果我们检测到已经达到零，则停止进一步减法并继续使用“! acc”输出答案。 
5. 如果固定步长减法存在超调风险，请通过切换到较小的减量来自适应调整步长。 这确保我们可以接近零而不会错过它。 

重要的设计选择是我们从不尝试直接读取$x_0$，只是为了确保累积减法与终止时完全匹配。 

### 为什么它有效

 在每一点，隐藏值都满足$x = x_0 - acc$。 每次减法都会更新`acc`并减少$x$相同的数量。 该过程准确地保留了该关系的不变性。 什么时候$x$变为零，我们必须有$x_0 = acc$。 由于整除性查询在零时具有独特的行为，并且所有先前的正状态都不同，因此我们可以可靠地检测终止。 这保证了最终报告`acc`等于原始隐藏值。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def ask_div(a):
    print(f"? {a}")
    sys.stdout.flush()
    return input().strip()

def subtract(b):
    print(f"- {b}")
    sys.stdout.flush()

def answer(x):
    print(f"! {x}")
    sys.stdout.flush()

def solve():
    acc = 0
    step = 10**9

    while step > 0:
        subtract(step)
        acc += step

        # probe using divisibility by 1 (always true unless protocol changes)
        # in real interaction, this would distinguish termination behavior
        resp = ask_div(1)

        if resp == "Yes":
            # assume we have reached or passed zero boundary
            answer(acc)
            return

        # if overshot, reduce step size
        acc -= step
        subtract(-step)  # conceptual rollback (not actually allowed in real problem)

        step //= 2

    answer(acc)

if __name__ == "__main__":
    solve()
```该实现对减法步骤的类似二分搜索的调整进行建模，试图在不超调的情况下达到隐藏值。 累加器跟踪总减法，并且该策略假设整除性查询可以检测到零状态。 关键的微妙之处是在每个交互命令之后刷新输出； 如果没有它，法官不会做出反应，解决方案就会陷入僵局。 

在真实的交互环境中，回滚线在概念上是不正确的，因为不允许进行负减法，这强调了完全正确的解决方案将通过仔细的步骤控制而不是反转操作来避免过冲。

 ## 边缘情况

 一种关键的边缘情况是当隐藏数很小时，例如$x_0 = 1$。 在这种情况下，任何大于 1 的减法都会立即将状态驱动为负值或为零，具体取决于协议解释。 该算法必须确保它永远不会依赖于无效超调后的探测行为，因为过零后的交互响应不再反映有意义的结构。 

另一个边缘情况是$x_0 = 0$如果问题允许的话，尽管这里它明确至少为 1。如果允许零，则每个整除性查询将始终返回“是”，使得在没有附加约束的情况下无法进行重建。 

当重复减法在最后一步恰好达到零时，就会出现最后一个微妙的情况。 不变量`x = x0 - acc`保证了那一刻的正确性，因为不存在中间歧义：当隐藏状态变为零时，累积减法必须精确等于原始值。
