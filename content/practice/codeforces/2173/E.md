 ## 解决方案
 ## 问题理解

 我们维持一个排列`1..n`。 

查询选择两个索引`x`和`y`。 然后法官掷硬币。 任一位置`(x,y)`交换，或者它们的镜像位置`(n-x+1, n-y+1)`被交换。 交换后，我们会被告知实际交换了哪对，因此我们始终准确地知道当前的排列。 

挑战在于我们无法直接选择阵列的哪一侧受到影响。 每个操作要么作用于一对位置，要么作用于其镜像。 

全部的总和`n`只是`2·10^4`，所以任意`O(n^2)`计算处理会很好。 真正的限制是查询预算。 我们只收到大约`2.5n`行动必须稳扎稳打，不能承受全球反复调整。 

第一个观察结果是，位置和它的镜像形成了天然的一对：```
i <-> n-i+1
```每当我们请求涉及此类对的一侧的交换时，法官可能会在另一侧执行相应的操作。 

简单的排序策略会重复地将每个值放置到正确的位置。 问题是每一次尝试都只有概率成功`1/2`，因此粗心的实现可能会花费远远超过允许的操作数。 

一个特别危险的情况是试图只修复一侧。 

例如，与```
n = 6
[2,1,3,4,5,6]
```试图放置`1`就位`1`相反，可以反复影响镜像面。 进展变得难以控制。 

关键是要一起处理镜像对。 一旦我们查看职位`i`和`n-i+1`作为一个整体，法官的随机选择不再是一个障碍，而是成为一种有用的对称性。 

## 方法

 一个蛮力的想法是完全按照我们对正常排列进行排序的方式进行排序。 假设值`i`目前处于位置`pos[i]`。 我们反复请求之间的交换`pos[i]`和`i`。 

问题是只有一半的查询会影响预期位置。 另一半影响镜像位置。 虽然修复一个元素的预期尝试次数是恒定的，但不同元素之间的相互作用会使分析变得混乱，并且操作总数很容易超过限制。 

关键的观察是法官永远不会选择任意交换。 它在交换和镜像之间进行选择。 

考虑一对镜像目标值：```
l = i
r = n-i+1
```假设值`l`不在位`l`。 

我们查询：```
(pos[l], l)
```如果法官执行了所选择的交换，则值`l`立即到达正确位置。 

如果判断执行的是镜像交换，则value的位置`r`相反，会向正确的一侧移动。 

无论哪种方式，镜像对的两个成员之一都更接近被固定。 

这建议从外向内处理排列。 对于每个镜像对`(l,r)`，我们继续查询，直到两个位置都包含正确的值。 

美妙的部分是每个查询至少修复预期的两个位置之一。 编辑分析表明，一对镜像的预期成本最多为 5 次操作，这导致总体预期约为`2.5n`运营。 额外的`800`在限制中提供了巨大的安全裕度。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力放置 | 查询限制下不清楚| O(n) | 不可靠 |
 | 镜像对贪婪 | O(n) 预期查询 | O(n) | 已接受 |

 ## 算法演练

 1. 维护当前的排列和数组`pos[v]`存储每个值的位置。 
2.如果`n`为奇数，先固定中间元素。 

中间的位置是它自己的镜子。 重复查询该对`(pos[mid_value], mid_position)`直到中间值到达中心。 
3. 从外向内处理镜像位置。 

让```
l = i
r = n-i+1
```4. 当任一位置不正确时，继续操作该对。 
5.如果值`l`目前不在位`l`， 询问```
(l, pos[l])
```当非镜像交换发生时，`l`立即变得正确。 
6. 否则，位置`l`已经正确了，所以在另一边工作并查询```
(r, pos[r])
```7. 在每次法官回答后，更新排列和`pos`大批。 
8. 当前镜像对的两个位置都正确后，向内移动到下一对。 
9. 当每一对都被处理完后，排列就被排序了。 

### 为什么它有效

 修复镜像对`(l,r)`。 

每当`l`不正确，我们查询`(l,pos[l])`，发生以下两种情况之一。 

如果直接执行所选交换，则值`l`到达最终位置。 

如果执行镜像交换，则该操作仅影响数组的镜像侧，即 value 所在的位置`r`生活。 在修复该对中的另一个成员方面取得了进展。 

当我们查询时，同样的推理适用`r`。 

在整个过程中，当前镜像对之外的位置永远不需要重新访问。 一旦一对变得正确，后续操作就无法破坏它，因为未来的查询仅涉及严格位于该对内的位置。 

通过从最外层对向中心归纳，每个位置最终都达到其正确值，因此最终的排列已排序。 

## Python 解决方案

 这是公认的交互式解决方案结构。```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    p = [0] + list(map(int, input().split()))

    pos = [0] * (n + 1)
    for i in range(1, n + 1):
        pos[p[i]] = i

    def query(x, y):
        print("?", x, y)
        sys.stdout.flush()

        u, v = map(int, input().split())
        if u == -1:
            sys.exit(0)

        p[u], p[v] = p[v], p[u]
        pos[p[u]] = u
        pos[p[v]] = v

    if n % 2 == 1:
        mid = (n + 1) // 2
        while p[mid] != mid:
            query(pos[mid], mid)

    for l in range(1, n // 2 + 1):
        r = n + 1 - l

        while p[l] != l or p[r] != r:
            if p[l] != l:
                query(l, pos[l])
            else:
                query(r, pos[r])

    print("!")
    sys.stdout.flush()

t = int(input())
for _ in range(t):
    solve()
```排列本身被存储，因为法官告诉我们实际发生的确切交换。 收到后`(u,v)`，我们在常数时间内更新数组和逆位置数组。 

奇数长度排列的中间位置很特殊，因为它是它自己的镜像。 首先修复它可以简化剩余的逻辑。 

对于每个镜像对，算法始终倾向于固定左侧位置。 一旦左侧变得正确，它就会切换到右侧。 这保证了完成的外部对不再需要关注。 

最常见的实施错误是忘记更新`pos`交换后。 整个策略取决于了解每个值的当前位置。

 ## 边缘情况

 考虑`n = 1`。```
[1]
```没有镜像对，并且中心已经是正确的。 算法立即输出`!`。 

考虑一个奇数长度排列，其中只有中心是错误的：```
n = 5
[1,2,4,3,5]
```中心位置是`3`。 由于中心位置镜像自身，因此重复查询`(pos[3],3)`最终赋予价值`3`在中间。 之后，正常处理外层对。 

考虑一对，其中一侧已经正确：```
[1,4,3,2]
```对于这对`(1,4)`， 位置`1`已经是正确的了。 该算法立即在右侧起作用，而不是在左侧浪费操作。 这就是为什么条件```
if p[l] != l:
    ...
else:
    ...
```是必要的。 

最后，考虑执行其镜像版本而不是预期版本的查询。 这是问题的核心挑战。 该算法可以处理它，因为每个查询都是围绕镜像对设计的。 如果左侧没有改善，那么右侧就会改善。 该对的进展永远不会消失，这正是使预期操作数量保持线性的属性。
