 ## 解决方案
 ## 问题理解

 我们得到一组由已建成的道路连接的城市，形成一个无向图。 其中一些城市有啤酒厂，每个啤酒厂只生产一单位啤酒，而在一些城市还有伊戈尔想要开设的工厂。 开一家工厂正好消耗一桶啤酒，关键的限制是啤酒桶只能沿着图中同一连通分量内的道路运输。 

有些啤酒厂属于伊戈尔，有些则属于其他玩家。 伊戈尔总是可以不受限制地使用自己的酒桶，但如果他需要使用别人的酒桶，则只有在从啤酒厂城市到工厂城市有道路的情况下才有效。 

任务是确定伊戈尔将从自己的啤酒厂拿走多少啤酒桶，以及他将被迫从其他玩家那里拿走多少啤酒桶，假设他首先贪婪地使用自己的供应，然后仅在必要时使用其他供应，并尊重连接限制。 

输入规模高达 100000 个城市、工厂、啤酒厂和道路，因此任何试图模拟每对啤酒厂和工厂之间移动的解决方案都是不可能的。 对图进行简单的全对可达性检查将导致相关节点数量至少呈二次方行为，这远远超出了允许的限制。 

正确的解决方案必须将图结构压缩为连接的组件，以便所有可达性查询成为本地计数而不是路径搜索。 

当伊戈尔拥有足够多的啤酒厂但它们分散在互不相连的组件中时，就会出现一种微妙的边缘情况。 例如，假设有两个组件，一个组件有 5 个工厂和 5 个 Igor 啤酒厂，另一个组件有 5 个工厂，但没有 Igor 啤酒厂，只有对手啤酒厂。 全局上伊戈尔有足够的啤酒，但在本地他无法跨组件转移，因此他必须在第二个组件中使用对手的啤酒。 

另一个极端情况是同一城市存在多个啤酒厂或工厂。 这些应该被视为计数中的多重性，而不是单一存在标志。 

## 方法

 暴力解释是模拟每个工厂和每个啤酒厂之间的可达性。 对于每个工厂，我们将尝试找到一个可到达的啤酒厂，将其标记为已使用，然后继续，直到所有工厂都满意为止。 每个可达性检查都需要图遍历，例如 BFS 或 DFS，并且由于可能有多达 100000 个工厂和啤酒厂，因此最坏的情况会导致在大图上重复遍历，产生 O(MG + KG) 数量级的复杂性或更糟，具体取决于实现细节和访问状态的重用。 这很快就变得不可行。 

关键的观察结果是，道路将城市划分为相互连接的组件，在每个组件内，任何啤酒厂都可以为任何工厂提供服务。 一旦连接性已知，组件内部的确切路径结构就不再重要。 重要的是每个连接的组件内存在多少每种类型的工厂和啤酒厂。 

这将问题转化为组件计数问题。 如果我们知道，对于每个组件，其中有多少个工厂，其中有多少个 Igor 啤酒厂，以及有多少个对手啤酒厂，那么我们可以在本地计算出那里使用了多少个 Igor 桶：它只是该组件中的 Igor 啤酒厂与该组件中的工厂之间的最小值。 该组件中的任何剩余工厂都必须由对手啤酒厂来满足，这同样受到同一组件内可用性的限制。 

因此，使用不相交集并集结构或 BFS 标记将图简化为组件，然后每个组件聚合所有对象。

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 每个工厂的强力 BFS/DFS | O(M·(N + G)) | O(M·(N + G)) | O(N + G) | 太慢了 |
 | DSU / 连接组件聚合 | O(N + G + M + K + L) | O(N + G + M + K + L) | O(N) | 已接受 |

 ## 算法演练

 我们通过将图折叠成连接的组件并计算每个组件内的资源来解决这个问题。 

1. 在城市和每条道路的联合端点上建立一个不相交的集合联合结构。 此步骤将所有可以交换啤酒的城市分组。 
2. 处理完所有道路后，计算每个城市的代表父级，以便每个城市都映射到单个连接组件标识符。 这一步定义了图的分区。 
3. 创建三个按组件索引的数组或哈希映射：一个用于工厂数量，一个用于 Igor 的啤酒厂，一个用于对手啤酒厂。 最初所有值都为零。 
4. 迭代所有工厂并增加包含其城市的组件的工厂计数。 这将空间需求转换为每个组件的需求。 
5. 迭代所有 Igor 啤酒厂并增加相应组件中 Igor 的啤酒数量。 这将供应量转化为本地供应量。 
6. 迭代所有对手啤酒厂并增加每个组件的对手啤酒数量。 这通过可达性限制将外国供应分开。 
7. 对于每个组件，计算 Igor 的啤酒可以满足多少工厂的需求，作为该组件中工厂数量和 Igor 啤酒厂数量的最小值。 将其添加到 Igor 用法的答案中。 
8. 在 Igor 使用后计算该组件中剩余的不满意工厂。 如果可能的话，这些必须通过对手啤酒来满足，因此将剩余工厂和对手啤酒厂数量的最小值添加到对手使用量中。 

之所以如此，是因为连通性完全决定了传输的可行性。 在组件内部，任何供应都可以与需求任意匹配，因为该组件中的所有城市对之间都存在路径。 组件之间不可能进行任何传输，因此所有匹配决策都会根据组件独立分解。 这使得全局优化相当于每个连接组件中独立的局部贪婪匹配，并且组件内的贪婪是最优的，因为所有桶都是相同的并且可以互换。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class DSU:
    def __init__(self, n):
        self.p = list(range(n + 1))
        self.r = [0] * (n + 1)

    def find(self, x):
        while self.p[x] != x:
            self.p[x] = self.p[self.p[x]]
            x = self.p[x]
        return x

    def union(self, a, b):
        a = self.find(a)
        b = self.find(b)
        if a == b:
            return
        if self.r[a] < self.r[b]:
            a, b = b, a
        self.p[b] = a
        if self.r[a] == self.r[b]:
            self.r[a] += 1

def main():
    n = int(input())
    m = int(input())
    factories = list(map(int, input().split()))
    k = int(input())
    igor = list(map(int, input().split()))
    l = int(input())
    others = list(map(int, input().split()))
    g = int(input())

    dsu = DSU(n)

    for _ in range(g):
        a, b = map(int, input().split())
        dsu.union(a, b)

    comp_fact = {}
    comp_igor = {}
    comp_other = {}

    for city in factories:
        c = dsu.find(city)
        comp_fact[c] = comp_fact.get(c, 0) + 1

    for city in igor:
        c = dsu.find(city)
        comp_igor[c] = comp_igor.get(c, 0) + 1

    for city in others:
        c = dsu.find(city)
        comp_other[c] = comp_other.get(c, 0) + 1

    igor_used = 0
    other_used = 0

    for c in comp_fact:
        f = comp_fact[c]
        i = comp_igor.get(c, 0)
        o = comp_other.get(c, 0)

        use_i = min(f, i)
        igor_used += use_i

        remaining = f - use_i
        other_used += min(remaining, o)

    print(igor_used, other_used)

if __name__ == "__main__":
    main()
```该解决方案首先读取图表并在城市上构建 DSU，其中每条道路将两个城市合并为一个连接的组件。 这确保可达性查询减少到 DSU 根的相等性。 

之后，程序使用哈希映射聚合每个组件的计数。 这很重要，因为只有出现在输入列表中的城市才重要； 我们不需要所有类别的大小为 N 的数组，稀疏字典就足够了。 

最后，每个组件都被独立处理。 每个组件内部的贪婪决策（首先使用 Igor 的啤酒）是安全的，因为将一个组件中的 Igor 的啤酒保留给另一个组件没有任何优势，因为不可能跨组件进行传输。 

一个常见的实施陷阱是在计数时忘记采用 DSU 根源，或者将城市指数与成分指数混合。 另一个微妙的问题是假设全球啤酒充足； 每个组件必须始终保留正确的逻辑。

 工厂：[1,4,3,2]

 伊戈尔啤酒厂： [2, 8]

 对手啤酒厂：[8,7,6,5]

 道路连接组件：{1,2,3,4,5}、{6}、{7,8}

 我们计算组件分配：

 | 组件| 工厂| 伊戈尔啤酒| 对手啤酒| 伊戈尔使用| 对手使用|
 | ---| ---| ---| ---| ---| ---|

 伊戈尔使用总数 = 2，对手使用 = 1

 该跟踪表明，尽管 Igor 在全球拥有两家啤酒厂，但只有一家在主要需求部分有用。 

### 示例 2

 在这种情况下，图结构创建了多个相互交织的组件，其关键影响是工厂分散在 Igor 供应不均匀的地区。 逐个组件的贪婪匹配确保伊戈尔的啤酒首先被本地消耗，然后才使用对手的啤酒。 

| 组件| 工厂| 伊戈尔啤酒| 对手啤酒| 伊戈尔使用 | 对手使用 |
 | ---| ---| ---| ---| ---| ---|
 | C1 | 2 | 1 | 2 | 1 | 1 |
 | C2 | 3 | 1 | 1 | 1 | 2 |

 总计分别变为 2 和 3，与所需的输出匹配。 

该轨迹强调，某一成分中的过剩对手啤酒无法弥补另一成分中的赤字。

 ## 边缘情况

 一种重要的边缘情况是，全局计数表明足够，但组件分布阻止完全匹配。 假设存在两个组件，一个有许多工厂但没有伊戈尔啤酒，另一个有过量的伊戈尔啤酒但没有工厂。 该算法独立处理每个组件，因此剩余部分无法迁移。 DSU 分组确保这些案例保持分离，并且每个组件相应地贡献零或有限的使用。 

另一个边缘情况涉及每个城市多个条目。 由于我们增加计数而不是使用布尔标志，因此拥有多个啤酒厂或工厂的城市正确地贡献了多样性。 DSU 映射可确保将这些汇总到正确的组件总数中，从而保留正确的基于最小值的匹配所需的精确计数。
