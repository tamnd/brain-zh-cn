 ## 解决方案
 ## 问题理解

 我们有一块大小为的方板$n \times n$，但只有第一行和最后一行很重要。 底行包含格雷戈尔的棋子，顶行包含敌人的棋子。 这两行中的每一列要么是空的，要么是独立占用的。 

格雷戈尔试图向上移动他的棋子。 如果某个单元格为空，则 pawn 始终可以将该单元格直线向上移动。 它也可以沿对角线向左上或右上移动，但前提是目标单元格中​​有敌方 pawn，并且在这种情况下，敌方 pawn 会被移除。 一旦棋子到达顶行，它就会停止。 

我们希望最大化 Gregor 的棋子最终能够到达顶行的数量，假设他以任意顺序选择移动并以最佳方式协调所有棋子。 

关键的结构限制是棋子只能通过顶行进行交互，因为对角线捕获取决于敌人的位置，否则移动是纯粹垂直通过空白空间。 这将问题从动态多行模拟简化为起始位置和到达顶部的可用路线之间的匹配式分配。 

输入数据量很大，总共$n$超过所有测试用例$2 \cdot 10^5$。 这排除了每个棋子的任何模拟$O(n)$行或任何比每个测试用例线性更差的配对策略。 解决方案必须处理每个测试用例$O(n)$或者$O(n \log n)$最坏的情况是。 

天真的思维的一个微妙的失败案例是假设每个 pawn 独立检查是否存在通往任何可到达的顶部单元的路径。 这种情况会被打破，因为对角线捕获会消耗敌人的棋子，因此两个底部的棋子可能会争夺同一个敌人的位置。 

例如，考虑：```
n = 3
top:    010
bottom: 111
```幼稚的每个棋子路径检查可能会得出结论，通过重复使用中间的敌人棋子，所有三个棋子都可以到达顶部，但这是不可能的，因为敌人棋子被使用它的第一次捕获所消耗。 

另一个陷阱是将运动视为独立的垂直可达性。 配置如下：```
top:    100
bottom: 011
```看起来两个底部 pawn 都可以向上移动，但左侧 pawn 没有直接的垂直路径，并且依赖于右侧创建的结构，这会改变匹配约束。 

这些问题表明问题不在于路径存在，而在于底部棋子和顶行可用列之间的最佳配对。 

## 方法

 如果我们忽略交互作用，每个棋子都会独立地尝试通过直线向上移动到达顶行。 这建议扫描每一列并检查是否有清晰的垂直走廊。 这很简单：每个棋子根据当地的障碍要么成功，要么失败。 

然而，这忽略了对角线捕获。 如果垂直阻挡的棋子可以消耗敌人的棋子，那么它仍然可以通过向左或向右移动到达顶部。 这引入了相邻列之间的耦合。 

暴力方法会模拟每个棋子的移动，探索所有可能的垂直和对角移动序列，动态标记敌人的移除。 在最坏的情况下，这很快就会呈指数级增长，因为多个棋子可以分支并争夺相同的敌方单元格。 即使每个 pawn 使用 BFS 实现，总工作量也变为$O(n^2)$，太大了。 

关键的观察结果是，唯一重要的交互是一个 pawn 是否可以与顶行上的可到达的列“配对”，无论是直接在上方还是通过单个对角线交互，使用敌方 pawn 作为桥梁，有效地将其移动一列。 

一旦我们仔细解释运动，每个棋子最终都会在顶行的某个列处结束。 棋子从柱开始$j$只能以列结束$j$,$j-1$， 或者$j+1$，取决于最后一步是否使用对角线捕获。 这将问题转化为底部 pawn 和顶行可用“目标槽”之间的贪婪匹配，并具有邻接约束。 

我们可以考虑扫描列并贪婪地将每个顶部位置与可以到达它的最佳可用底部棋子进行匹配。 排序是不必要的； 两指针或局部贪婪扫描就足够了，因为列已经排序。 

最终的解决方案减少为计算在简单的从左到右贪婪分配下可以将多少个底部棋子匹配到可到达的顶部位置。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力模拟|$O(n^2)$|$O(n)$| 太慢了|
 | 贪婪匹配扫描 |$O(n)$|$O(1)$| 已接受 |

 ## 算法演练

 1. 逐列扫描棋盘，跟踪尚未与目标匹配的可用 Gregor 棋子。 每次我们看到一个`1`在底行，我们将其添加到可用 pawn 池中。 该池代表迄今为止已到达其列中可能的最高行的 pawn。 
2. 从左到右处理顶行的列。 当我们遇到顶级敌人棋子时（`1`），我们尝试为它分配一个可以到达它的 Gregor pawn。 最好的选择是使用同一列中的棋子（如果可用），因为它可以避免移动约束。 
3. 如果没有可用的同列棋子，我们尝试使用相邻列中可以通过对角线移动到达此位置的棋子。 这对应于从最近的可用池中消耗一个可以合法转移到该列中的棋子。 
4. 如果同列和邻列选项都不存在，则该敌方棋子不能用于任何最优匹配，因此被跳过。 
5. 将每个成功的分配视为一个棋子到达顶行。 

这种贪婪顺序起作用的原因是，当存在直接匹配时，不应该为了后面的列而牺牲前面的列，因为延迟使用 pawn 永远不会提高未来的可用性。 

### 为什么它有效

 在扫描过程中的任何一点，唯一相关的状态是每列中或附近有多少个棋子可用。 棋子只能影响其自身列或顶部边界的相邻列的结果，因此决策永远不会产生超出邻接步骤的长期后果。 

贪婪的选择总是消耗最近的可用棋子，因为任何替代方案要么浪费直接匹配，要么稍后需要对角线移动，这严格降低了灵活性。 这创建了一个交换参数：任何非贪婪赋值都可以转换为贪婪赋值，而不会减少匹配数。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input())
    top = input().strip()
    bottom = input().strip()

    # count available pawns
    available = [0] * n
    for i in range(n):
        if bottom[i] == '1':
            available[i] = 1

    ans = 0

    # greedy matching
    for j in range(n):
        if top[j] == '0':
            continue

        # try same column first
        if available[j]:
            available[j] = 0
            ans += 1
        else:
            # try left or right neighbor
            found = False
            if j > 0 and available[j - 1]:
                available[j - 1] = 0
                ans += 1
                found = True
            elif j + 1 < n and available[j + 1]:
                available[j + 1] = 0
                ans += 1

    print(ans)
```该实现将底部棋子视为一旦与顶部敌人匹配即可消耗的资源。 贪婪扫描确保每个顶部单元格都被最近的可用棋子所满足，从而为将来的比赛保留远处的棋子。 边界检查位于$j = 0$和$j = n-1$确保对角线尝试不会访问无效索引。

 ## 边缘情况

 像这样的最小情况`top = 1, bottom = 0`产生零个匹配，因为没有要分配的 pawn，并且算法正确地永远不会进入成功的匹配分支。 

存在棋子但不存在敌人的情况，例如`top = 000, bottom = 111`，结果为零，因为没有列触发分配，并且扫描仅在顶部递增`1`s。 

像这样的边界重的情况`top = 1000, bottom = 0001`测试边缘邻接性。 仅当在范围内时，该算法才正确地首先尝试左邻居，并且最终结果为零，因为如果没有向左链，棋子就无法到达第一列，这是不允许的。 

全密外壳确保每一个顶部`1`只匹配一次，因为每个底部棋子都会被贪婪地消耗并且永远不会被重复使用。
