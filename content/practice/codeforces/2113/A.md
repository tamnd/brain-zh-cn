 ## 解决方案
 ## 问题理解

 我们得到了一个在一定温度下启动的烤架和两种可以无限重复烹饪的烤肉串。 每次我们烤一份的时候，我们都要先检查当前的温度是否足够高，然后烤架的温度就会下降。 这两种类型的不同之处在于所需的最低启动温度以及从烤架消耗的热量。 

任务是决定两种类型的烹饪顺序，以便在烤架变得太冷而无法满足任一要求之前最大化烹饪的份数。 

关键是我们没有提前选择每种类型的固定数量。 每个决定都会影响未来的可用性，因为温度不断降低。 这使得该问题成为排序和贪婪优化问题，而不是简单的计数问题。 

约束最多为 10^4 个测试用例，值最多为 10^9。 这立即排除了任何以幼稚的方式在每一步重复尝试两种选择的模拟。 每步模拟可能会降低到每个测试用例的 O(k)，并且当 k 很大时，这会变得太慢。 我们需要一种解决方案来推理长序列的相同决策，而不是逐个模拟它们。 

当一种类型在要求和效率方面都严格较差时，例如需要更高的温度但也更多地降低温度，就会出现微妙的边缘情况。 在这种情况下，先煮它永远不是最佳选择，但总是选择当前可用类型的天真贪婪者可能仍然会选择它并失去未来的容量。 

另一种棘手的情况是两种类型都可用，但其中一种类型稍后变得不可用。 过早选择错误的顺序可能会永久阻止许多未来的操作，因为温度只会降低。 

## 方法

 蛮力方法将模拟所有可能的烹饪决策顺序。 在每一步中，我们都会检查哪些类型可用，并递归地尝试这两种选择，跟踪生成的温度和总计数。 这正确地探索了所有有效序列，但分支因子最多为 2，并且深度可能很大，在最坏情况温降链中可能高达 10^9。 即使应用剪枝，状态空间仍然巨大，因为可以通过不同的序列达到相同的温度。 

问题的结构使得暴力破解变得不必要。 每个动作都会永久降低温度，并且只有两种操作。 重要的观察是，我们应该始终优先考虑相对于其要求在温降方面更具“成本效益”的操作，因为这样做可以保留更多的未来灵活性。 

这导致了贪婪的排序策略。 在两种类型都可能的任何时刻，我们更喜欢温降较小的一种，因为它可以为未来的步骤保留更高的温度。 然而，我们不能简单地总是先全局选择较小的下降，因为如果我们延迟太久，更高的要求约束可能会阻止我们稍后使用该类型。 

因此，我们不是一步步完全模拟，而是压缩过程：我们重复采用尽可能多的当前最佳类型，批量更新温度，然后在其他类型变得更好或有必要时进行切换。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力模拟| 指数 / O(k) | O(1) | O(1) | 太慢了 |
 | 贪婪批量处理| 每次测试 O(1) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们独立地处理每个测试用例，并根据每个操作可以在块中应用的次数进行推理。

1. 首先，我们确定哪种类型的温降较小。 如果类型 1 的下降小于或等于类型 2，我们将类型 1 视为“贪婪首选”选项。 这很重要，因为保持温度总是有助于延长未来有效操作的数量。 
2. 只要有效，我们就尽量使用首选类型。 我们计算在保持所需的最低温度的同时可以应用多少次。 我们不是一步步模拟，而是直接通过算术计算最大计数。 
3. 每次我们应用一种类型时，我们都会将当前温度降低为其下降量乘以使用次数。 此批量更新取代了重复模拟。 
4. 一旦首选类型无法再使用，无论是因为温度太低还是因为切换变得有利，我们就切换到其他类型并重复相同的逻辑。 
5. 我们总结两个阶段的所有操作并返回结果。 

微妙的推理点是，一旦某种类型变得不适合首先使用，它对温度的影响是不可逆转的。 因此，排序完全是通过比较液滴大小来决定的，而不是通过动态交替来决定。 

### 为什么它有效

 核心不变量是，在每一步中，我们都在迄今为止使用相同操作次数的所有序列中保留最高可能的剩余温度。 由于未来操作的数量单调取决于当前温度，因此与任何其他排序相比，在每个块之后保持最高温度可确保我们永远不会丢失潜在的未来操作。 任何早期使用更高落差操作的偏差只会降低未来的可用性，而不会解锁任何新的有效动作。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve_case(k, a, b, x, y):
    ans = 0

    # Decide which type is better to use first (smaller drop is preferred)
    if x < y or (x == y and a <= b):
        first_a, first_b = a, b
        first_x, first_y = x, y
    else:
        first_a, first_b = b, a
        first_x, first_y = y, x

    # Try greedy for first type, then second type
    for req, dec in [(first_a, first_x), (first_b, first_y)]:
        if k < req:
            continue
        # how many times we can apply this type in a row
        cnt = (k - req) // dec + 1
        ans += cnt
        k -= cnt * dec

    return ans

def main():
    t = int(input())
    for _ in range(t):
        k, a, b, x, y = map(int, input().split())
        print(solve_case(k, a, b, x, y))

if __name__ == "__main__":
    main()
```实施过程首先根据温度下降决定优先考虑哪种类型。 决胜局也使用要求，因为如果两者下降相同，则要求较低的类型总是至少同样可用。 

之后，我们不再循环，而是使用简单的算术公式计算连续使用的次数。 如果我们至少可以烹饪一次，那么最后一个有效步骤是当温度仍然高于要求时，因此计数变为`(k - req) // dec + 1`。 

我们一次性减去总温降，这确保了状态转换正确，无需迭代模拟。 这避免了时间问题和浮动边界错误。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        k, a, b, x, y = map(int, input().split())
        # same logic as solution
        def solve(k, a, b, x, y):
            if x < y or (x == y and a <= b):
                req1, dec1 = a, x
                req2, dec2 = b, y
            else:
                req1, dec1 = b, y
                req2, dec2 = a, x

            ans = 0
            if k >= req1:
                c = (k - req1) // dec1 + 1
                ans += c
                k -= c * dec1
            if k >= req2:
                c = (k - req2) // dec2 + 1
                ans += c
            return ans

        out.append(str(solve(k, a, b, x, y)))
    return "\n".join(out)

 ## 边缘情况

 一种边缘情况是两种类型具有相同的落差值但要求不同。 在这种情况下，算法会优先选择要求较低的，以确保不会过早阻塞。 例如，与`k=50, a=10, b=5, x=y=2`，算法首先使用类型b，消耗`(50-5)//2 + 1 = 23`操作，然后切换到具有剩余温度的 a 型。 

另一种情况是只有一种类型最初有效，但在使用另一种类型一次后就变得无效。 批量公式自然可以处理这个问题，因为它会在更新温度后重新计算可行性，而不是假设两者仍然可用。 

最后一种情况是两种类型最初都不可用，例如`k=5, a=10, b=12`。 该算法立即返回零，因为两个条件在第一次检查时都失败，从而避免任何无效算术或负循环。
