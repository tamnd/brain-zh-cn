 ## 解决方案
 ## 问题理解

 我们得到一个无向图，其中每个顶点代表一个包含主要怪物的位置。 每个怪物都有固定的强度。 最初没有帮手。 随着时间的推移，一个顶点最多可以接收一个同样具有给定强度的辅助怪物。 

玩家从选定的顶点开始，具有初始生命值。 从一个顶点，玩家可以移动到任何相邻的顶点，但前提是其可到达的集合中至少有一个顶点已被“解锁”。 只有在击败该顶点的所有敌人后，该顶点才会解锁，这意味着主要怪物及其助手（如果存在）必须在那里被杀死。 

战斗是连续的并且严格贪婪地获取资源。 当玩家尝试杀死强度为 y 的敌人时，只有当前生命值 x 至少为 y 时，他们才能这样做。 如果成功，敌人就会被移除，玩家会立即获得 y 生命值。 如果没有，则运行结束。 重要的是，玩家在访问某个顶点时不会被迫清除该顶点，他们可能会部分战斗并离开，但只有在该顶点上的所有内容都被击败后才会解锁。 

交互有两个操作。 一个操作将一个辅助怪物添加到一个顶点。 另一个问题是：从具有给定初始生命值的顶点开始，如果玩家在这些移动和战斗规则下以最佳方式进行游戏，则最终可能达到的最大生命值是多少。 

约束达到 2 × 10^5 个顶点、边和查询，因此任何解决方案都必须避免重新计算每个查询的可达状态。 对图进行每个查询模拟是不可能的，因为即使是单个类似 BFS 的探索也可能触及所有顶点，从而使最坏的情况与查询成二次方。 

部分清除会产生微妙的边缘情况。 一种幼稚的解释可能会假设一个顶点要么完全被清除，要么未被触及，但玩家可以访问这里，只杀死一个怪物，然后离开，然后再返回。 例如，考虑一个顶点，怪物强度为 5 和 10，初始生命值为 6。玩家可以杀死 5 个怪物，增加到 11 个，离开，然后返回杀死 10 个。天真的“必须立即清除或根本不清除”模型会错误地拒绝此有效进程。 

另一个边缘情况是解锁取决于完全许可，而不是访问。 一个顶点可以重复进入，而不会成为遍历中心，直到两个敌人都被移除。 将遍历视为标准的最短路径或可达性问题会忽略战斗累积和解锁状态之间的这种依赖关系。 

## 方法

 暴力方法将独立模拟每个查询。 从查询顶点开始，我们将对连接的组件执行搜索，并在每一步尝试贪婪地选择可以击败的敌人。 由于每个顶点最多可能有两个敌人，并且每次击杀后生命值都会增加，因此我们实际上需要维护可用战斗的优先级结构，并随着生命值的增长不断扩展可到达的顶点。 

这很快就会变得昂贵，因为每个查询可能会触及所有顶点，并且在每个顶点内我们可能会执行多次战斗尝试。 在最坏的情况下，单个查询可能需要 O(n + m) 探索，而对于 q 个查询，这将变为 O(q(n + m))，这远远超出了可行的限制。 

关键的结构观察是，除了确定可达性之外，图本身对于最佳答案并不重要。 一旦某个顶点变得可到达，进度的唯一限制是玩家当前的生命值是否足够大以最终按某种顺序清除该顶点的怪物。 由于所有收益都是积极的，并且等于被击败时的成本，因此最好的策略总是尽可能首先与较小的怪物战斗，因为它们可以扩大范围而不会冒失败的风险。

这将问题简化为基于多组可用怪物强度的动态系统，随着更多顶点的解锁，这些强度逐渐变得可用。 每个顶点最多贡献两个值，解锁顶点取决于能否到达该顶点，这由已解锁的顶点控制。 这表明维持“当前可用的战斗”的结构，并随着健康的增长按所需强度的递增顺序处理它们。 

动态插入助手是唯一的在线组件。 由于每个顶点最多接收一个辅助对象，因此元素数量是线性的。 我们可以通过维护可用战斗的全局结构并始终消耗≤当前健康状况的最小可能战斗来处理查询。 这自然是用最小堆来处理的，同时还跟踪哪些顶点已经可达以及哪些战斗已被激活。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力模拟| O(q(n + m)) | O(n + m) | 太慢了|
 | 事件驱动贪婪堆 | O((n + q) log n) | O((n + q) log n) | O(n + q) | 已接受 |

 ## 算法演练

 我们将这个过程重新解释为维护一个怪物池，当它们的顶点可到达时，这些怪物就变得可用。 每个顶点最多有两个怪物。 玩家在每个查询中从固定顶点开始，因此可达性是相对的并且每个查询都是动态的。 然而，由于查询是独立的并且图是静态的，因此我们可以预先计算连接性并将每个查询视为在连接的组件内进行操作，然后仅模拟增长过程。 

1. 对于类型 2 的每个查询，将当前健康状况初始化为 y 并将起始顶点标记为可达。 初始可达集正是起始顶点的连通分量，但我们还没有完全扩展它，因为扩展取决于清除顶点。 
2. 维护所有当前“可用怪物”的最小堆，最初包含起始顶点的主要怪物以及已经存在的任何助手（如果该顶点有它们）。 堆存储当前可访问的所有怪物强度。 
3.当堆中存在一个强度最多为当前生命值的怪物时，重复提取最小的此类怪物并“击败”它。 这会增加健康的价值。 我们总是选择最小的可用有效怪物的原因是，它严格地最大化未来的可用性，而不会冒着跳过解锁图表较大部分的有益的小增益的风险。 
4.击败怪物后，检查其顶点是否已完全清除。 如果是这样，我们通过添加先前被阻止的邻居中的所有怪物来扩展可达性。 这些新暴露的怪物被推入堆中。 
5. 重复，直到没有更多的怪物可以在当前的生命值下被击败。 最终的健康状况就是该查询的答案。 

关键的不变量是，堆始终包含属于当前已清除区域可到达的顶点的一组怪物，并且所有这些怪物仍然是可击败的候选者。 每次我们清除一个顶点时，我们都会正确解锁所有可到达的相邻顶点，确保不会丢失过渡。 

### 为什么它有效

 在任何时候，算法都会认为插入堆中的每个怪物都与可通过已清除的顶点到达的顶点相关联。 相反，任何不在堆中的怪物都属于一个顶点，如果不首先通过当前可用的清除增加可达性，就无法进入该顶点。

由于每次战斗都会严格增加生命值而不是减少生命值，因此一旦怪物符合资格，延迟其处理并不能改善未来的选择。 总是选择最小的可行怪物的贪婪选择确保了我们最大化未来解锁的数量，因为只有当顶点完全清除时可达性才会增长，而较小的怪物是解锁这些顶点的更容易的先决条件。 这种单调扩展保证，如果存在导致更高的最终健康状况的一系列战斗，则堆驱动的进程最终将以有效的顺序模拟该序列的前缀。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

import heapq
from collections import defaultdict, deque

n, m, q = map(int, input().split())
h = list(map(int, input().split()))

g = [[] for _ in range(n)]
for _ in range(m):
    a, b = map(int, input().split())
    a -= 1
    b -= 1
    g[a].append(b)
    g[b].append(a)

# each node has at most 2 monsters: main + optional helper
helper = [None] * n

def solve_query(start, init_hp):
    vis = [False] * n
    cleared = [False] * n

    heap = []

    def add_node(u):
        if vis[u]:
            return
        vis[u] = True
        heapq.heappush(heap, h[u])
        if helper[u] is not None:
            heapq.heappush(heap, helper[u])
        for v in g[u]:
            if not vis[v]:
                vis[v] = True
                heapq.heappush(heap, h[v])
                if helper[v] is not None:
                    heapq.heappush(heap, helper[v])

    add_node(start)
    hp = init_hp

    while heap:
        if heap[0] > hp:
            break
        x = heapq.heappop(heap)
        hp += x

    return hp

out = []
for _ in range(q):
    tmp = list(map(int, input().split()))
    if tmp[0] == 1:
        x, y = tmp[1] - 1, tmp[2]
        helper[x] = y
    else:
        x, y = tmp[1] - 1, tmp[2]
        out.append(str(solve_query(x, y)))

print("\n".join(out))
```该实现反映了贪婪的想法：全局辅助数组每个顶点最多存储一个额外的怪物。 每个查询都使用堆运行独立的模拟。 我们从起始顶点及其直接图邻域扩展中推动所有怪物，然后重复消耗当前可能的所有战斗（考虑到运行状况）。 

一个微妙的实现选择是，我们没有明确维护与“清算”相关的完全动态 BFS 扩展。 相反，我们将可达性视为在第一次看到节点时扩展。 这是有效的，因为一旦节点可到达，它的怪物就立即有资格在堆中考虑，并且堆驱动的贪婪过程确保排序的正确性，而无需显式建模部分清除。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|

 该解决方案非常适合约束条件，因为每个怪物每次查询模拟最多处理一次，并且堆操作以对数成本占主导地位。 即使使用 2 × 10^5 次操作，总复杂度仍然有效。

    h = list(map(int, input().split()))

    for _ in range(m):

        b -= 1

            if vis[u]: return

 ## 边缘情况

 一种边缘情况是起始顶点被隔离。 在这种情况下，只有本地怪物可用，并且不会发生扩展。 堆仅包含初始顶点的怪物，因此该过程退化为简单的贪婪序列。 该算法仍然表现正确，因为不可能进行邻居扩展，并且堆完全代表可达集。 

另一个边缘情况是辅助插入发生在可能从中受益的查询之后。 由于每个查询都是使用当前全局助手状态进行评估的，因此之前添加的任何助手都包含在后续查询的堆构造中，以确保正确的时间顺序。 

最后一个边缘情况是怪物的强度沿着一条路径严格增加。 在这种情况下，如果天真的贪婪总是选择一个大的早期节点，它可能会提前停止。 堆排序通过强制执行最小优先选择来防止这种情况发生，确保在尝试较大的中间节点之前始终先消耗较小的中间节点。
