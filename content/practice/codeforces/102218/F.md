 ## 解决方案
 ## 问题理解

 我们有一系列`n`天数和每天的需求值。 更新会增加某一天的需求。 维修前，工厂生产`b`每天巧克力。 期间`k`维护日它不生产任何东西，也不能出售任何东西。 维护完成后，会产生`a`每天巧克力。 维护开始日`p`仅针对类型 2 查询选择，因此每个查询都会询问不同的可能生产计划，而当前需求数组保持固定。 原始问题正是使用这个更新和查询模型。 

关键的限制是当天的订单`i`天前无法满足`i`，但未使用的巧克力可以储存并稍后出售。 因此，工厂可以在产量超过需求的日子里积累库存，然后将这些库存用于以后的订单。 

让`D_i`是几天内的总需求`1..i`，并让`P_i`是所选维护开始时这些天的总产量。 如果`D_i > P_i`，那么至少`D_i - P_i`从第一个开始的订单`i`日子永远无法满足。 最大的前缀赤字决定了总需求中不可避免的损失有多少。 

这些限制使得直接模拟不合适。 和`n`最多`10^5`和`q`最多`2 * 10^5`，算法采用`O(n)`对于每个查询都可以执行`2 * 10^10`最坏情况下的操作。 每次更新和查询我们需要大约对数的工作。 事实上，每次需求更新都会影响从当天开始的所有前缀和，这一事实直接指向惰性线段树。 

在某些边界条件下，实现可能会悄无声息地出错。 首先是当天开始的维护`1`。 例如，```
3 1 3 1 3
1 1 2
1 3 1
2 1
```答案是`1`。 当天没有生产或销售`1`，所以当天的两笔订单都丢失了。 当天生产的巧克力`2`和`3`只能帮忙处理当天的一个订单`3`。 仅比较总需求与总产量的粗心解决方案可能会错误地声称所有三个订单均可销售。 

另一个界限是维护恰好在当天结束`n`。 考虑```
4 2 3 1 2
1 4 10
2 3
```答案是`2`。 和`p = 3`，生产仅在几天内进行`1`和`2`，赠送两块巧克力，而日子`3`和`4`都是维护日。 将维护间隔视为`[p, p+k]`而不是`[p, p+k-1]`更改生产计划并给出错误的结果。 

什么时候`k = n`，整个工厂都无法使用。 例如，```
3 3 2 1 3
1 1 1
1 3 5
2 1
```有答案`0`。 尽管名义上的修复生产率很高，但任何一天都没有生产或销售。 盲目评估后期维护范围的实施可能会意外地在日后引入生产`n`。 

最后，零需求需要特殊处理。 为了```
2 1 2 1 1
2 1
```答案是`0`。 最大前缀赤字允许为负数或零，但未满足订单数不能为负数。 忘记了`max(0, ...)`在这种情况下，最终公式可以得出否定的答案。 

## 方法

 一个简单的解决方案是为每个类型 2 查询显式模拟工厂。 对于一个选择的`p`，我们可以遍历所有`n`天，维持当前库存，在生产允许的情况下添加当天的产量，根据当天的需求销售尽可能多的巧克力，并累积销售数量。 这是正确的，因为每天尽可能多地销售永远不会损害未来的一天：今天未售出的任何巧克力稍后仍可供应，而立即满足可用订单并不会减少最终可销售的数量。 

问题是成本。 一种类型 2 查询需要`O(n)`，并且可以有`q = 2 * 10^5`查询。 在最坏的情况下这是`O(nq) = O(2 * 10^10)`白天的作业，远远超出了可用时间。 

有用的观察是我们实际上不需要模拟库存。 对于固定的生产计划，请考虑任何天数前缀`1..i`。 最多`P_i`那时巧克力已经可以生产了，所以至少`max(0, D_i-P_i)`来自该前缀的命令必定会丢失。 最严重的前缀赤字是有关整个赛程表的唯一重要信息。 

假设最大的前缀赤字是`L`。 那么至多`D_n-L`巧克力可以卖。 这个界限可以通过只要有订单就贪婪地卖出来实现，所以答案正是`D_n - max(0, max_i(D_i-P_i))`。 

剩下的任务是在需求更新的同时快速评估该最大值。 

维护开始`p`，生产具有三种简单的形式。 维护前，`P_i = bi`。 维护期间，`P_i = b(p-1)`。 维护后，生产`b(p-1) + a(i-p-k+1)`。 

根据前缀需求定义三个数组：`F_i = D_i - bi`

`H_i = D_i`

`G_i = D_i - ai`。 

那么维护前的最大赤字就是最大`F_i`为了`i < p`。 维护时为最大`H_i`为了`p <= i <= p+k-1`， 减`b(p-1)`。 维护后为最大`G_i`为了`i >= p+k`，加上一个仅取决于的常数`p`。 

当天的需求更新`d`增加每个前缀的需求`D_i`和`i >= d`。 因此，它增加了相同的值`F_i`,`H_i`， 和`G_i`在后缀上`[d,n]`。 因此我们需要一个支持后缀添加和范围最大查询的数据结构。 惰性线段树正好处理这个操作。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 |`O(nq)`|`O(n)`| 太慢了 |
 | 最佳|`O((n+q) log n)`|`O(n)`| 已接受 |

 ## 算法演练

 1. 构建三个概念数组`F`,`H`， 和`G`假设所有需求最初为零。 在位置`i`，他们的值为`-bi`,`0`， 和`-ai`。 这些正是三个生产阶段所需的表达方式。 
2. 将三个数组中每个数组的最大值存储到每个线段树节点中。 惰性值记录已应用于整个节点但尚未推送到其子节点的添加。 
3.更新时`(1, d, x)`到达，将总需求增加`x`。 前缀需求`D_i`仅更改为`i >= d`，所以添加`x`后缀上的所有三个线段树值`[d,n]`。 
4. 查询`(2, p)`， 让`m = p+k-1`。 将日期分为三个范围`[1,p-1]`,`[p,m]`， 和`[m+1,n]`。 线段树可以从以下位置找到相关最大值`F`,`H`， 和`G`对于这些范围。 
5. 维护前几天，获取`L = max(F_i)`超过`1 <= i < p`。 由于生产是`bi`当天`i`，这正是`max(D_i-P_i)`在那个范围内。 
6. 对于维护日，获取`M = max(H_i)`超过`p <= i <= m`。 任何维护日结束时的产量为`b(p-1)`，所以对应的赤字为`M-b(p-1)`。 
7. 维护后的日子里，获取`R = max(G_i)`超过`m+1 <= i <= n`。 为了这样的一天`i`，产量为`b(p-1) + a(i-p-k+1)`。 

重新排列这个表达式给出`P_i = ai + (b-a)(p-1) - ak`。 

因此`D_i-P_i = G_i + (a-b)(p-1) + ak`。 

因此，维护后赤字为`R + (a-b)(p-1) + ak`。 
8. 采取`L`,`M`， 和`R`与零一起，因为需求损失量不能为负。 如果`bad`是它们的最大值，答案是`D_n-bad`。 

### 为什么它有效

 对于每个以 day 结尾的前缀`i`，没有任何策略可以卖出超过`P_i`属于该前缀的订单的巧克力。 因此至少`D_i-P_i`只要该数量为正，订单就会丢失。 因此，最大的前缀赤字是丢失订单数量的下限。 

每当订单到达时就销售尽可能多的巧克力的贪婪策略正是实现了这一界限。 每当库存不足时，短缺恰恰是当前前缀需求减去前缀生产，遇到的最大短缺就是最大前缀赤字。 一旦后续生产到达，它可以满足后续订单，但无法修复已经错过的订单。 因此，最大前缀赤字正是不可避免的损失，从总需求中减去它就得出了最佳的巧克力销售数量。 

线段树总是代表当前值`F_i`,`H_i`， 和`G_i`。 更新将相同的数量添加到受该需求影响的每个前缀总和，因此惰性后缀更新保留所有三个定义。 查询根据每个阶段的确切生产公式对前缀赤字进行分区，因此树返回的最大值正是最大可能的前缀赤字。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

NEG = -(10 ** 30)

class SegmentTree:
    def __init__(self, n, a, b):
        self.n = n
        self.a = a
        self.b = b

        size = 4 * n + 5
        self.f = [0] * size
        self.h = [0] * size
        self.g = [0] * size
        self.lazy = [0] * size

        self._build(1, 1, n)

    def _build(self, v, l, r):
        if l == r:
            self.f[v] = -self.b * l
            self.h[v] = 0
            self.g[v] = -self.a * l
            return

        mid = (l + r) >> 1
        self._build(v << 1, l, mid)
        self._build(v << 1 | 1, mid + 1, r)
        self._pull(v)

    def _pull(self, v):
        left = v << 1
        right = left | 1

        self.f[v] = max(self.f[left], self.f[right])
        self.h[v] = max(self.h[left], self.h[right])
        self.g[v] = max(self.g[left], self.g[right])

    def _apply(self, v, x):
        self.f[v] += x
        self.h[v] += x
        self.g[v] += x
        self.lazy[v] += x

    def _push(self, v):
        x = self.lazy[v]
        if x:
            left = v << 1
            self._apply(left, x)
            self._apply(left | 1, x)
            self.lazy[v] = 0

    def add_suffix(self, start, x):
        self._add_suffix(1, 1, self.n, start, x)

    def _add_suffix(self, v, l, r, start, x):
        if r < start:
            return

        if start <= l:
            self._apply(v, x)
            return

        self._push(v)

        mid = (l + r) >> 1
        self._add_suffix(v << 1, l, mid, start, x)
        self._add_suffix(v << 1 | 1, mid + 1, r, start, x)

        self._pull(v)

    def query_phases(self, p, m):
        return self._query_phases(1, 1, self.n, p, m)

    def _query_phases(self, v, l, r, p, m):
        if r < p:
            return self.f[v], NEG, NEG

        if l > m:
            return NEG, NEG, self.g[v]

        if p <= l and r <= m:
            return NEG, self.h[v], NEG

        self._push(v)

        mid = (l + r) >> 1

        lf, lh, lg = self._query_phases(v << 1, l, mid, p, m)
        rf, rh, rg = self._query_phases(
            v << 1 | 1, mid + 1, r, p, m
        )

        return (
            max(lf, rf),
            max(lh, rh),
            max(lg, rg),
        )

def solve():
    n, k, a, b, q = map(int, input().split())

    seg = SegmentTree(n, a, b)
    total_demand = 0
    out = []

    for _ in range(q):
        query = list(map(int, input().split()))

        if query[0] == 1:
            d, x = query[1], query[2]

            total_demand += x
            seg.add_suffix(d, x)

        else:
            p = query[1]
            m = p + k - 1

            before, during, after = seg.query_phases(p, m)

            bad = before

            if during != NEG:
                bad = max(bad, during - b * (p - 1))

            if after != NEG:
                bad = max(
                    bad,
                    after + (a - b) * (p - 1) + a * k
                )

            bad = max(0, bad)
            out.append(str(total_demand - bad))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```线段树在每个节点包含三个最大值，因为相同的前缀需求与三个不同的产生公式进行比较。 所有三个值都接收完全相同的后缀添加，因此一个惰性值对于整个节点来说就足够了。 

当天的初始值`i`是`-bi`为了`F`,`0`为了`H`， 和`-ai`为了`G`。 不需要显式的需求数组。 今日更新`d`更改每个前缀和`D_d`向前，这就是更新成为后缀范围添加的原因。 

该查询例程比标准范围最大查询稍微专业一些。 两个界限`p`和`p+k-1`将整个阵列分为三个生产阶段。 如果一个段完全位于一个相中，则可以立即返回相应的存储的最大值。 只有跨越两个边界之一的节点才需要递归。 这使每个查询保持对数，同时避免三个独立的范围查询。 

这`NEG`值仅用于空相。 它故意比任何可能的实际值小得多。 由于总需求最多为`2 * 10^9`生产最多约为`10^10`，Python 整数在这里没有溢出问题。 

维护间隔为`[p, p+k-1]`，所以它的右端点计算为`m = p+k-1`。 后期维护范围开始于`m+1 = p+k`。 这两个表达式是最容易出现相差一错误的地方。

 ## 边缘情况

 ### 维护从第一天开始

 对于```
3 1 3 1 3
1 1 2
1 3 1
2 1
```我们有`D = [2,2,3]`。 自从`p=1`和`k=1`，生产量为`[0,3,3]`。 前缀赤字是`2`,`-1`， 和`-3`，所以最大赤字为`2`。 总需求为`3`, 给予`3-2=1`。 

线段树查询中，维护前范围为空，维护范围为天`1`，后期维护范围为天`2..3`。 空范围贡献`NEG`，所以它不会意外地成为答案。 

### 维护于第 n 天结束

 对于```
4 2 3 1 2
1 4 10
2 3
```查询有`p=3`和`m=4`。 产量为`1`在几天`1`和`2`，随后几天没有生产`3`和`4`。 工厂正好有两种巧克力可用，而且唯一的订单是当天的`4`，所以答案是`2`。 

树使用维护范围`[3,4]`以及空的维护后范围。 这直接检查`p+k-1`，而不是`p+k`，是最后一个维护日。 

### 维护涵盖每天

 对于```
3 3 2 1 3
1 1 1
1 3 5
2 1
```我们有`p=1`和`k=3`， 所以`m=3=n`。 每天都是维护日。 存储的维护最大值为`D_3=6`，而其他两个相位范围为空。 最大赤字为`6`，等于总需求，所以答案是`0`。 

实现永远不需要特殊情况`k=n`。 之前和之后的空范围由以下表示`NEG`，而中间范围自然覆盖整个线段树。 

### 零需求

 对于```
2 1 2 1 1
2 1
```每个需求值都为零。 维护从当天开始`1`，存储的前缀表达式都是非正数，因此原始最大赤字至多为零。 正在申请`max(0, bad)`将其精确地转换为零，答案是`D_n-bad = 0`。 

这就是为什么最终钳位为零不属于三相计算的原因。 前缀可以有剩余生产，但剩余生产不能产生负数的未满足订单。 

###同一天重复更新

 如果多个类型 1 查询针对同一天，则每次更新都会增加现有需求，而不是替换它。 假设一天收到增量`4`， 然后`7`。 其需求变为`11`，并且在该天或之后开始的每个前缀都会增加`11`总共。 线段树执行两次后缀加法，因此效果会自动累加。 

这也是为什么在处理过程中仅存储每天的最终需求是不够的。 每次更新都会立即更改稍后类型 2 查询使用的前缀表达式，并且惰性树会保留这些更改而不重建前缀和。
