 ## 解决方案
 ## 问题理解

 我们得到了一系列必须严格从左到右击败的怪物。 每个怪物都有所需的强度阈值，并且不能跳过或重新排序。 我们也有英雄池。 每个英雄都拥有战斗力和耐力，战斗力决定他们能否在怪物遭遇中生存下来，而耐力则限制他们一天可以击败的怪物数量。 

这个过程在几天内展开。 每天我们都会选择一位英雄。 该英雄从第一个不败的怪物开始战斗。 如果在任何时候，一个怪物的力量严格大于英雄，那么英雄会立即失败，并且这一天结束时不会取得超越该怪物的进展。 否则，英雄可以将怪物一一击败，直到耐力耗尽或没有怪物为止。 

任务是尽量减少击败整个序列所需的天数，或者确定这是不可能的。 

这些限制迫使我们远离简单的模拟。 每次测试最多 2×10^5 个怪物和英雄，以及最多 10^5 次测试，任何每天重新启动扫描怪物或贪婪地尝试每个位置的所有英雄选择的解决方案都将超出时间限制。 我们需要一种更接近 O((n + m) log n) 或 O((n + m) log m) 的方法。 

一个微妙的困难来自于耐力和力量之间的相互作用。 如果一个强大的怪物提前阻止了他们，那么一个可以击败一大群的英雄可能仍然毫无用处。 相反，如果分配到正确的前缀，具有高耐力的较弱英雄可能会更好。 

打破天真的贪婪想法的边缘情况包括像非常强大的怪物迟到的情况，例如怪物`[1, 1, 1, 100, 1]`。 总是使用最强可用英雄的贪婪策略可能会在早期浪费它们，但具有足够耐力的稍弱英雄可能是早期阶段的最佳选择。 

另一种失败情况是当没有英雄可以通过单个怪物时出现。 例如，如果一个怪物的力量为 10，但所有英雄的力量为 9 或更低，那么无论耐力如何，答案都是不可能的。 

最后，当耐力大但功率小时会出现误导情况。 这样的英雄在长段看起来很强，但如果过不了早期的高峰，其实没什么用。 

## 方法

 蛮力的想法很简单。 每天，尝试每个英雄并模拟他们距离当前怪物位置能走多远。 选择击败最多怪物的英雄。 这是正确的，因为它总是局部最大化进度。 然而，每次模拟最多可以扫描 n 个怪物，并且总共最多有 n 个步骤，导致在最坏的情况下每次测试的时间复杂度为 O(n²)，这太慢了。 

为了改进，我们需要避免重复模拟前缀。 关键的观察是，对于任何怪物的前缀来说，重要的不是迄今为止使用的英雄的确切顺序，而是只有能够生存到一定强度阈值的英雄中最好的耐力。 

如果我们固定一个以位置i结尾的前缀，那么覆盖以i结尾的分段的任何有效日期都必须使用一个英雄，该英雄的力量至少是该分段中的最大怪物，并且其耐力至少是分段长度。 这表明将英雄压缩到一个结构中，对于每个功率阈值，我们都知道可实现的最佳耐力。 

我们按力量对英雄进行排序，然后预处理最大耐力的前缀。 这让我们可以回答以下形式的查询：在所有力量≥x的英雄中，可用的最大耐力是多少。 

现在我们模拟贪婪地吃怪物，但不是直接尝试英雄，而是不断扩展当前片段，同时保持迄今为止看到的最大怪物值。 当我们尝试延长段时，我们会查询是否存在可以同时处理当前最大怪物和段长度的英雄。 如果是，我们延长； 否则，我们将确定当天并重新开始。 

为了提高效率，我们预先计算并使用指针在排序的英雄上移动，同时为所有符合条件的功率级别保持最佳耐力。 根据实现，每个扩展都变成摊销常数或对数。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力模拟| O(n²) | O(1) | O(1) | 太慢了|
 | 排序+贪心+预处理| O(n log n + m log m) | O(n log n + m log m) | O(米) | 已接受 |

 ## 算法演练

 我们独立处理每个测试用例。 

1. 怪物的排序已经按顺序给出，所以我们在它们上面保留一个指针。 
2.按实力从小到大对英雄进行排序。 在此过程中，我们维护一个结构，该结构可以告诉我们，对于任何所需的最低功率，满足该要求的英雄的最大耐力。 这是通过从最低功率到最高扫描英雄并保持后缀最大耐力来构建的。 
3. 我们定义一个函数，在给定所需的最小功率和所需的段长度的情况下，检查是否有任何英雄可以同时处理这两者。 这是通过二进制搜索第一个具有足够力量的英雄来回答的，然后检查从该索引开始的预先计算的最大耐力。 
4. 我们从第一个怪物开始，尝试构建一天内最长的片段。 我们跟踪当前片段中的最大怪物功率及其长度。 
5. 在每一步中，我们都尝试将片段扩展一个怪物。 扩展后，我们检查某个英雄是否可以处理它。 如果是的话，我们会继续扩张。 
6.如果没有英雄可以处理当前片段，我们将上一个片段定为一天，并从当前怪物重新开始。 我们增加日计数器。 
7. 如果在任何时候任何英雄都无法处理单个怪物，我们立即返回-1。

关键的不变量是，在任何时刻，我们都维护着从当前位置开始的最长前缀，可以由某个有效的英雄在一天内清除。 每次我们无法扩展时，都是因为不存在满足扩展段的两个约束的英雄，这意味着前一个段是最大的并且必须对应于最佳的日期边界。 

这种贪婪分段是安全的，因为任何有效的解决方案都必须将数组划分为连续的段，并且在无法扩展时延迟切割不会提高未来的可行性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    m = int(input())

    heroes = []
    for _ in range(m):
        p, s = map(int, input().split())
        heroes.append((p, s))

    heroes.sort()

    best = [0] * m
    best[-1] = heroes[-1][1]
    for i in range(m - 2, -1, -1):
        best[i] = max(best[i + 1], heroes[i][1])

    def can(power_req, len_req):
        # find first hero with power >= power_req
        l, r = 0, m
        while l < r:
            mid = (l + r) // 2
            if heroes[mid][0] >= power_req:
                r = mid
            else:
                l = mid + 1
        if l == m:
            return False
        return best[l] >= len_req

    i = 0
    days = 0

    while i < n:
        days += 1
        seg_max = 0
        seg_len = 0

        j = i
        while j < n:
            seg_max = max(seg_max, a[j])
            seg_len += 1

            if not can(seg_max, seg_len):
                break
            j += 1

        if i == j:
            print(-1)
            return

        i = j

    print(days)

t = int(input())
for _ in range(t):
    solve()
```代码首先按照力量对英雄进行排序，然后根据耐力构建后缀最大数组，以便可行性查询变得更快。 这`can`函数通过二进制搜索第一个符合条件的英雄，然后检查从该点开始可用的最佳耐力，检查是否有任何英雄可以处理具有给定最大怪物功率和长度的片段。 

主循环贪婪地构建每天的片段。 如果连一个怪物都无法启动的话，答案就是不可能。 否则，在可行性约束下，尽可能延长每个段。 

一个微妙的实现细节是我们总是增量地重新计算段最大值。 这可以避免重新扫描以前的怪物。 另一个微妙之处是后缀最大数组：如果没有它，检查耐久性将需要线性扫描，并且会破坏性能。

 ## 边缘情况

 一个关键的边缘情况是最强的怪物提前出现。 该算法通过立即使分段扩展失败并在该怪物之前强制剪切来处理它，确保不会继续进行无效的英雄分配。 

另一个边缘情况是当英雄具有高耐力但力量不足时。 预处理可确保它们永远不会被错误地视为高功率段，因为二分搜索会在检查耐久性之前强制执行功率约束。 

最后的边缘情况是具有高功率和大耐力的单一英雄。 在这种情况下，该算法将在一个段中扩展整个数组，因为每个前缀的可行性都保持不变，并且该段永远不会过早地被切割。
