 ## 解决方案
 ## 问题理解

 我们正在模拟一个监视系统，该系统监视每分钟的流量值流。 每分钟，我们都会将当前流量与固定容量阈值进行比较。 系统不会立即对单个违规或单个安全读取做出反应。 相反，它使用迟滞：只有在持续过载后才进入报警状态，只有在持续恢复后才离开报警状态。 

更准确地说，当系统处于正常状态时，它会计算流量连续严格高于阈值的分钟数。 一旦该计数达到给定限制，系统就会发出警报。 之后，当它处于警报状态时，它会计算流量连续处于或低于阈值的分钟数。 一旦恢复计数器达到另一个极限，系统就会恢复正常。 当处于警报状态时，它会持续停留在那里，直到积累足够的安全时间。 

输出是整个模拟过程中系统处于警报状态的总分钟数。 

每个测试用例的约束最多为十万分钟，最多为一百个测试用例。 这排除了任何试图在持续工作之外每分钟重新计算或模拟昂贵结构的方法。 每个测试用例的任何解决方案都必须是线性的。 

过渡会产生微妙的边缘情况。 幼稚的实现通常会忘记计数器在状态更改时重置，或者错误地对转换分钟进行两次计数。 

例如，考虑阈值为 5，连续 3 个高值后报警，连续 2 个安全值后清除：

 输入：```
6 5 3 2
6 6 6 1 1 1
```这里，警报在第 3 分钟触发。粗心的实现可能会在第 4 分钟立即开始清除，并错误地认为系统太早留下警报，或者由于不包括确切的转换结构而错误地计算了警报持续时间。 正确的行为是警报仅在第三个高分钟后开始，仅在连续两个安全分钟后结束。 

另一种极端情况是系统根本不进入警报状态。 即使存在孤立的尖峰，答案也必须为零，因为没有连续运行达到阈值。 

## 方法

 蛮力的想法是完全按照所描述的方式模拟系统，保持其当前状态并计数器连续的高值和低值。 每分钟，我们都会更新计数器并检查是否应该发生状态转换。 我们还累积警报所花费的分钟数。 

该模拟已经接近最佳状态，因为每分钟处理一次。 简单的解决方案变得缓慢的唯一方法是，如果有人尝试在每个位置从头开始重新计算连续条纹，向后扫描或重新检查片段。 在最坏的情况下，这会降低到二次时间，特别是当交替值强制重复重新扫描前缀时。 

关键的见解是该过程本质上是基于状态机的。 系统仅取决于当前状态（正常或警报）和跟踪连续运行的两个计数器。 无需重新访问之前的会议记录或维护任何复杂的数据结构。 每个转换都是由本地条件触发的，因此一次从左到右的传递就足够了。 

这减少了在扫描一次数组时保持变量数量恒定的问题。

 | ---| ---| ---| ---|
 | 蛮力（重新扫描运行）| O(N²) | O(1) | O(1) | 太慢了|
 | 状态机仿真 | O(N) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们维护当前状态和两个计数器。 

1. 在正常状态下初始化系统。 设置一个计数器`high_streak = 0`和`low_streak = 0`。 还设置了`alarm_time = 0`。 
2. 从左到右迭代每分钟的流量值。 每分钟将其与阈值进行比较。 
3. 如果当前状态正常且流量超过阈值，则递增`high_streak`。 否则重置`high_streak`为零。 什么时候`high_streak`达到所需的激活长度，切换状态至报警并复位`low_streak`。 
4. 如果当前状态为闹钟，我们将这一分钟累加到`alarm_time`在任何转换逻辑之前，因为系统被认为在整分钟内处于活动状态。 
5. 处于警报状态时，如果流量等于或低于阈值，则递增`low_streak`。 否则重置`low_streak`为零。 什么时候`low_streak`达到所需间隙长度，开关状态恢复正常并复位`high_streak`。 
6. 继续此过程，直到处理完所有会议记录。 

关键细节是警报时间是根据每分钟的状态计算的，而不是根据未来的转换。 这可以避免切换状态时出现差一错误。 

### 为什么它有效

 该系统由有限状态机完整描述，其内存仅以连续运行计数器的形式存在。 在任何时候，未来状态仅取决于当前状态和相对于阈值的当前值。 计数器确保我们正确检测连续运行，而无需这些运行之外的历史记录。 由于每一分钟只贡献一次状态转换检查和可能的一次计数器更新，因此不会丢失任何信息，也不需要重新计算。 这保证了正确性和线性处理。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []
    
    for _ in range(T):
        N, Xmax, A, C = map(int, input().split())
        arr = list(map(int, input().split()))
        
        state = 0  # 0 = normal, 1 = alarm
        high_streak = 0
        low_streak = 0
        alarm_time = 0
        
        for x in arr:
            if state == 1:
                alarm_time += 1
            
            if state == 0:
                if x > Xmax:
                    high_streak += 1
                else:
                    high_streak = 0
                
                if high_streak >= A:
                    state = 1
                    low_streak = 0
            else:
                if x <= Xmax:
                    low_streak += 1
                else:
                    low_streak = 0
                
                if low_streak >= C:
                    state = 0
                    high_streak = 0
        
        out.append(str(alarm_time))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该解决方案的结构是对流量阵列进行单次传递。 变量`state`跟踪监视器当前是否正在报警。 柜台`high_streak`和`low_streak`相互相关，具体取决于状态。 仅当系统在每分钟开始时已处于警报状态时，警报时间才会增加，从而正确捕获全分钟的覆盖范围。 

一个常见的错误是在添加之前更新状态`alarm_time`，这将失去最后的警报分钟。 另一个微妙的问题是在切换状态时无法重置相反的计数器，这可能会导致状态翻转后立即发生意外的转换。

 ## 边缘情况

 一种边缘情况是当激活阈值和清除阈值均为 1 时。系统变得极其敏感并立即翻转状态。 该算法可以处理此问题，因为条纹计数器在单个步骤中达到阈值，并且在正确处理当前分钟后仍然会发生状态转换。 

另一个边缘情况是长序列会在阵列末尾附近触发警报，而没有足够的时间来清除警报。 该算法仅计算警报分钟数，直到数组结束，并且不需要最终许可，这与问题定义相匹配，因为我们只测量观察到的警报时间。 

最后一个微妙的情况是，当流量恰好在阈值附近振荡时，计数器就会重复重置。 由于两个计数器在相反的条件下重置，因此不会发生无效的结转，并且状态机保持稳定而不会意外触发。
