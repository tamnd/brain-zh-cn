 ## 解决方案
 ## 问题理解

 每个学期有固定的周数，每周的课程数量也有限。 几个星期已经过去了，您在这几周内已经参加了一定数量的课程。 现在剩下的几周仍然摆在您面前，您必须决定在剩下的几周内参加多少课程。 

目标是确保您的最终出勤率至少占该学期所有课程的 60%。 但是，您参加的课程数量不能超过一周内实际举办的课程数量，因此剩余的每一周都有一个您可以贡献的课程数量的上限。 

任务不仅是决定是否有可能达到 60% 的出勤率，而且还要在可能的情况下为剩余几周制定有效的计划。 在所有有效计划中，您必须输出一个在剩余几周内分配出勤率的计划，同时遵守每周限制。 

关键数量很简单。 学期总课程数固定为周数乘以每周课程数。 其中一些周已经结束，您过去的出勤率也已确定。 剩下的决定是如何在每周上限下分配未来几周的额外出席人数。 

限制非常小。 周数最多为 14 周，每周最多有 5 节课。这意味着关于分布的暴力推理是完全安全的，甚至线性或贪婪的构造也绰绰有余。 问题不在于性能，而在于正确处理可行性并构建有效的分配。 

主要的失败案例有两个来源。 第一个是使用整数除法错误地计算所需的出勤阈值，这可能导致低估所需的出勤课程数量。 例如，如果总班级数为 50，则 60% 为 30，但如果计算为`50 * 60 / 100`对于某些语言中的整数截断，需要注意确保必要时正确的上限行为。 

第二个问题是假设简单地贪婪地填充剩余的几周而不考虑可行性约束总是有效的。 例如，如果剩余容量不足以达到所需的总出席人数，则必须在构建任何分配之前正确检测到不可能性。 

具体的边缘情况是已经满足了所需的出勤率。 在这种情况下，所有剩余周数应填为零，因为不需要添加不必要的出勤率，并且可能违反“每周最少”的意图。 

另一个边缘情况是，即使参加所有剩余的课程也不够。 例如，如果总课程为 20 门，所需课程为 12 门，而您已经参加了 11 门课程，并且只剩下 1 门课程可供选择，那么即使您非常接近，也是不可能的。 

## 方法

 强力方法会尝试枚举在剩余几周内分配出席人数的所有可能方式。 每周可以取 0 到 Y 之间的值，因此最多 14 周且 Y 最多 5，配置数量最多为$6^{14}$，它太大而无法直接枚举。 

然而，问题的结构使得暴力破解变得不必要。 唯一的全球要求是达到最低出席课程总数。 除了每周值不能超过 Y 之外，没有任何分配偏好。这将问题转化为简单的可行性和构建任务。 

关键的观察是，唯一有意义的数量是您仍然需要参加的额外课程的总数。 一旦我们计算出这个数字，将其分配到剩余的几周内就变成了一个有界包装问题：我们将几周填充到容量 Y 直到满足要求。 

我们首先计算该学期的课程总数和所需的阈值（60％）。 然后我们减去已经参加的课程数量，以找出还需要多少课程。 如果这个数字小于或等于零，我们就已经满足要求了。 如果超过总剩余容量，则任务无法完成。 否则，我们会贪婪地每周分配尽可能多的课程，直到满足要求。

 ## 算法演练

 1. 计算学期总课程数为$X \times Y$。 这代表了全勤宇宙。 
2. 将所需出勤率计算为总出勤率的 60%。 由于出席人数必须是整数，因此将其作为出席人数的上限$0.6 \times X \times Y$。 这确保我们永远不会接受临界值不足的情况。 
3. 将剩余所需出勤率计算为`need = required - N`。 如果该值小于或等于零，则不需要进一步出席。 
4. 计算剩余容量为`(X - Z) * Y`。 这是您仍然可以累积的最大出席人数。 
5.如果`need > remaining capacity`，输出“否”，因为即使最大的努力也无法达到阈值。 
6. 否则，将出勤率分配到剩余几周。 对于剩余的每一周，分配`min(Y, need)`并从中减去它`need`。 
7. 如果分配后还剩几周，则将出勤率填为零，因为不再需要更多。 

### 为什么它有效

 正确性依赖于这样一个事实：唯一的约束耦合周是全局出勤率总和。 除了上限之外，每周都是独立的。 因为我们总是尽力尽早满足剩余的要求，所以我们绝不会以可能阻碍以后可行性的方式浪费容量。 如果存在解决方案，则贪婪填充可确保通过在简单的线性扫描中消耗容量来构造该解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    X, Y, Z, N = map(int, input().split())

    total = X * Y
    required = (total * 60 + 99) // 100

    need = required - N

    remaining_weeks = X - Z
    remaining_capacity = remaining_weeks * Y

    if need <= 0:
        print("Yes")
        print(" ".join("0" for _ in range(remaining_weeks)))
        return

    if need > remaining_capacity:
        print("No")
        return

    ans = []
    for _ in range(remaining_weeks):
        take = min(Y, need)
        ans.append(take)
        need -= take

    print("Yes")
    print(" ".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```该解决方案首先使用上限除法计算类别总数和所需阈值，以避免低估 60% 的要求。 变量`need`捕获需要多少额外参加的课程。 

然后我们计算在剩下的几周内仍然可以参加多少课程。 这种可行性检查至关重要，因为如果没有它，即使不存在有效的完整时间表，我们也可能会构建部分时间表。 

贪心循环在每周分配尽可能多的课程，而不超过每周限制或剩余要求。 一次`need`变为零，随后的几周自动贡献为零。

 ## 边缘情况

 当要求已经满足时，算法立即输出剩余几周的零分配。 例如，如果总课程为 20 门，所需课程为 12 门，但您已经有 15 门课程，那么`need`变为负值，输出为零向量，正确保留可行性，无需不必要的分配。 

即使全部剩余容量也不足时，可行性检查也会阻止施工。 例如，如果总剩余容量为 3，但您还需要 5 个类别，则算法会检测到`need > remaining_capacity`并在尝试任何分发之前输出“否”。
