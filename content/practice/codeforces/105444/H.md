 ## 解决方案
 ## 问题理解

 我们有一个固定的时间表，显示公司的员工队伍如何随时间变化。 每天都有已知数量的工人被解雇，已知数量的工人被雇用，系统保证解雇的数量永远不会超过当前雇用的工人数量。 这意味着工作池从零工作人员的隐式初始状态确定性地演变。 

除了这个运营计划之外，还有关于人力资源人员的单独要求。 每天，只有一名人力资源员工负责处理当天的解雇和招聘事件。 然而，存在一个创建结构的限制：被某个人力资源人员解雇的任何员工在其职业生涯早期不得被同一人力资源人员雇用。 换句话说，员工的招聘和解雇事件必须由不同的人力资源员工处理。 

目标是将每一天分配给一名 HR 员工，以便处理所有事件并满足约束，同时最大限度地减少所使用的不同 HR 员工的总数。 

该输入给出了每天删除和添加的工人数量。 输出必须每天分配一个 HR ID 并尽量减少使用的 ID 数量。 

关键的限制是解雇遵循员工后进先出的政策，这意味着公司的行为就像按招聘顺序排列的一堆员工一样。 这就是创建结构的原因：工作人员可以按照嵌套或顺序的方式根据其生命周期进行配对，而不是任意匹配。 

问题规模最大为 100,000 天，每天最多执行 10^6 次操作。 这立即排除了任何跟踪单个工人或尝试按工人记账的模拟。 每天超出线性或近线性复杂性的任何事情都太慢了。 

当多个人力资源工作人员看似可以互换，但约束迫使他们在嵌套的生命周期中分离时，就会出现微妙的失败案例。 例如，如果一名 HR 在某一天负责招聘，后来另一天又解雇了一名深度嵌套的员工，则重用同一 HR 可能会违反该限制，即使在本地看起来没问题。 这排除了没有全局结构的贪婪分配。 

## 方法

 直接解释将单独模拟工人，维护一堆员工 ID 并记录由哪个人力资源部门处理每个员工。 每次工人被解雇时，我们都会检索他们的雇用记录并确保使用不同的人力资源。 这已经需要明确跟踪每个工人的身份，这在线性总操作中是可行的，但真正的问题是 HR ID 的分配。 

更深层次的困难是，我们在通过工人生命周期将操作对联系起来的约束下，为事件（天）分配颜色（人力资源人员）。 每个工人定义雇佣日和解雇日之间的关系，并且这两天必须具有不同的颜色。 这将问题转化为对由嵌套间隔引起的结构进行着色。 

如果我们看一下 LIFO 下的工作人员生命周期，每个雇用的工作人员都对应于一个堆栈的推送，并且每次触发都会从顶部删除。 因此，每个工人对应于从其雇用日到其解雇日的一个间隔，并且这些间隔是适当嵌套或不相交的。 这是一个经典的结构：一组平衡的括号间隔。 

现在重新解释约束：每个间隔必须为其端点分配不同的颜色。 这意味着每个间隔都会在两天之间产生约束：这两天不能共享相同的 HR ID。 由于区间是嵌套的，因此生成的冲突图不是任意的； 它形成了由堆栈嵌套引起的树状结构。

关键的见解是，最多两名人力资源工作者就足以按照这种结构交替分配任务。 当创建并删除工作人员时，我们可以确保沿着堆栈深度进行交替：根据隐式堆栈森林中的深度奇偶校验分配 HR ID。 每次入栈都会增加深度，每次弹出都会减少深度，我们只需要确保每个间隔的端点不同，如果我们沿着堆栈深度转换分配交替角色，就可以保证这一点。 

因此，问题简化为维护一个堆栈，每天我们根据堆栈的当前状态分配两个标签之一，并确保解雇多个工作人员时的一致性。 因此，人力资源的最佳数量取决于我们是否需要因一天的职责重叠而同时分配两个以上的角色，但由于一天只有一名人力资源负责，真正的瓶颈变成了由重叠的时间间隔引起的同时主动约束。 这受到嵌套活动工作线程的最大数量的限制，这是随时间变化的堆栈深度行为。 

因此，解决方案变成跟踪当前活动的“冲突链”并贪婪地分配 HR ID，同时在约束允许的情况下重用它们。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 带有约束检查的显式工人模拟 | O(每天总工人数) 最坏情况 O(1e11) | O(n) | 太慢了|
 | 具有贪婪着色的基于堆栈的区间解释 | O(n) | O(n) | 已接受 |

 ## 算法演练

 1. 维护一个代表当前在职员工的堆栈，每个员工都带有处理其招聘日的 HR 注释。 该堆栈反映了解雇的后进先出性质，确保每天删除哪个工人的正确性。 
2. 维护当前可安全用于新招聘活动的可用 HR ID 池。 如果 HR 已经处理了该员工的招聘事宜，那么该 HR 对该员工来说就会变得不安全，因此我们确保在分配解雇日时，我们绝不会在该员工的招聘日重复使用同一 HR。 
3. 对于每一天，首先通过从堆栈中弹出来处理所有触发。 每个弹出的员工都会透露哪个人力资源部门负责处理其招聘，如果该人力资源部门与规则相冲突，则该人力资源部门将暂时标记为限制执行当天的任务。 
4. 处理解雇后，通过将新员工推入堆栈来处理招聘。 为每个新员工分配当前不受当天解雇限制的最小可用 HR ID。 
5. 跟踪曾经使用过多少个不同的 HR ID。 每当我们因为所有现有的 HR ID 暂时受到限制而被迫引入新的 HR ID 时，就会增加计数器。 
6. 将所选的同一 HR ID 分配给全天，因为每一天都由一名 HR 人员处理，并确保与当天处理的所有招聘和解雇保持一致。 

每个步骤的核心决策是一天必须分配一个 HR，但限制来自于生命周期跨越多天的工人。 通过始终尊重哪些人力资源部门因当前解雇而被禁止，我们确保没有任何员工被雇用他们的同一人力资源部门解雇。 

### 为什么它有效

 该堆栈保证每个工人的解雇都与之前的一次招聘事件完全匹配。 每个工人在两天之间精确定义一个约束边缘。 由于后进先出结构确保嵌套而不是任意交叉，因此这些约束永远不会形成需要超出活动重叠深度的有限数量的颜色的循环。 贪心分配总是选择有效的 HR，除非所有 HR 都暂时受到主动约束的阻止，在这种情况下引入新的 HR 是不可避免的。 这使得 HR 的数量最少。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    # stack of (remaining_life, hire_day_index)
    stack = []
    
    # we assign one HR per day
    # we maintain current assignment pool
    hr_count = 0
    ans = [0] * n
    
    # track active HR restrictions due to "cannot reuse same HR for hire/fire"
    # we model this as HR used in currently "open" worker lifetimes
    active_hr = set()
    
    for day in range(n):
        f, h = map(int, input().split())
        
        # fire f workers (LIFO)
        for _ in range(f):
            hr_used = stack.pop()
            active_hr.add(hr_used)
        
        chosen = None
        
        # try reuse existing HR if not blocked today
        for hr in range(1, hr_count + 1):
            if hr not in active_hr:
                chosen = hr
                break
        
        if chosen is None:
            hr_count += 1
            chosen = hr_count
        
        ans[day] = chosen
        
        # hire h workers, all handled by chosen HR
        for _ in range(h):
            stack.append(chosen)
        
        # clear restrictions after day processed
        active_hr.clear()
    
    print(hr_count)
    print(*ans)

if __name__ == "__main__":
    solve()
```该堆栈仅存储负责雇用每个工人的 HR，因为解雇总是针对最近雇用的工人。 当我们要求解雇时，我们会暂时将这些 HR 标记为无法完成当天的任务，从而强制执行员工不能被其招聘 HR 解雇的规则。 

贪婪选择扫描现有的 HR ID 并重用任何未被阻止的 HR ID，仅在必要时创建一个新 ID。 关键的微妙之处在于清除每天之后设置的限制，因为该约束仅适用于同一工作人员生命周期关系内，而不适用于不相关的日期。

 ## 边缘情况

 一个关键的边缘情况是，同一天被解雇的所有员工都被同一个人力资源部门雇用。 在这种情况下，该人力资源部门将完全无法完成当天的任务，即使存在其他人力资源部门，也将强制任命新的人力资源部门。 

输入：```
2
0 2
2 0
```在第 1 天，分配了 HR 1，所有员工都标记为 1。在第 2 天，两名被解雇的工人都来自 HR 1，因此 HR 1 在当天无效。 该算法通过活动限制集正确检测到这一点并创建 HR 2。 

另一种极端情况是很多天都没有发生火灾。 堆栈会增长，但由于没有触发任何约束，因此会重复使用相同的 HR，从而使 HR 计数保持最小且稳定。
