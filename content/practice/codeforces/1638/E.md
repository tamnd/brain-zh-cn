 ## 解决方案
 ## 问题理解

 我们维护一个长度为 n 的数组，该数组开始时完全统一：每个位置都包含值 0 且属于颜色 1。随着时间的推移，该数组会通过两种更新进行演变。 一种类型对整个间隔重新着色，用新颜色替换现有颜色。 另一种类型为给定颜色的每个位置添加固定值。 最后，我们被要求请求单个索引的当前值的点查询。 

关键的困难在于更新通过颜色进行交互：值不是直接按简单的附加结构存储在每个索引中，而是按颜色进行累积，并且颜色本身通过范围分配随时间变化。 

这些约束将我们推向一个 n 和 q 都可以达到 100 万的状态。 任何涉及每个操作的段的解决方案都是立即不可能的。 在最坏的情况下，即使每个查询进行一次线性扫描也会导致 10^12 次操作，这远远超出了任何时间限制。 这迫使设计必须在每个操作的近恒定时间内处理重新着色和添加，并且必须在不扫描整个阵列的情况下响应查询。 

一个天真的想法是为每个索引维护其当前颜色和当前值。 然后，颜色操作更新一个范围，添加更新给定颜色的所有索引，查询简单地打印存储的值。 问题是 Add 变得昂贵，因为颜色类可能包含数组的很大一部分。 同样，颜色变得昂贵，因为它影响许多指数。 

当我们尝试“立即推送更新”时，会出现微妙的失败情况。 例如，如果我们重复对范围 [1, n] 重新着色，并且每次尝试物理更新数组，我们很快就会退化为二次行为。 更糟糕的是，当颜色重复变化时，基于颜色的结构（例如每种颜色的索引列表）就会中断，因为我们需要在每次重新着色时在集合之间移动元素，这又会在每次操作时变成线性。 

真正的障碍是索引和颜色这两个维度都是动态的：索引在颜色之间移动，并且颜色累积全局加性偏移。 

## 方法

 暴力模拟很简单。 我们存储一个颜色数组和一个值数组。 对于 Color l r c，我们循环遍历 l 到 r 并更新颜色。 对于 Add c x，我们循环遍历所有索引并将 x 添加到颜色为 c 的索引中。 查询时间复杂度为 O(1)。 

这是正确的，但立刻就太慢了。 在最坏的情况下，单个 Add 涉及 n 个元素，并且可能存在 q 个这样的操作，从而导致 O(nq) 行为。 

关键的观察是值更新仅取决于颜色，而不取决于位置。 如果我们能够以某种方式避免在颜色变化时接触单个元素，我们就可以跟踪每种颜色的累积贡献。 主要困难是索引的颜色随着时间的推移而变化，因此索引不会永久属于一组。 

突破在于反转视角：我们不再将每个索引视为属于一种颜色，而是将每种颜色视为维护一个运行的“带时间戳的值历史记录”，并且每个索引只需要知道它上次更改颜色的时间以及在更改之前“错过”了什么。 

我们在添加操作上维护一个全局时间计数器。 每种颜色 c 维护一个运行总计 add[c]，表示应用于其的所有 Add 操作的总和。 当索引改变颜色时，我们需要“冻结”它迄今为止从旧颜色累积的值，然后将其附加到新颜色而不重新计算历史记录。 

为了有效地实现这一点，我们为每个索引维护：

 - 它当前的颜色
 - 它的当前值
 - 最后看到的颜色贡献基线

我们没有存储每个索引的更新，而是为每个索引维护一个惰性“调整”，该“调整”等于最后一次更改颜色时的总颜色贡献。 查询时，我们计算当前颜色贡献和存储基线之间的差异。 

颜色更新仍然是范围分配，因此我们不能触及每个元素。 因此，我们使用对颜色进行延迟传播的线段树，其中每个线段要么是均匀的，要么是混合的。 每个节点存储其颜色是否同质； 如果是这样，我们可以直接将整个段分配给新的颜色，时间复杂度为 O(1)。 这可以防止每个元素重新着色。 

加法部分纯粹在颜色级别处理，因此它仍然是 O(1)。 

因此，最终系统结合了用于颜色分配的线段树和用于每种颜色加和的散列或数组，以及用于值增量的每叶簿记。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(nq) | O(n) | 太慢了 |
 | 线段树+颜色懒惰+每颜色总和| O((n + q) log n) | O((n + q) log n) | O(n + q) | 已接受 |

 ## 算法演练

 1. 在数组上构建一棵线段树，其中每个节点存储其线段是否具有统一颜色以及该颜色是什么。 最初，整棵树的颜色为 1。这使我们可以将颜色分配给完整的段，而无需触及每个索引。 
2. 维护一个数组add[c]，存储到目前为止添加到颜色c的总值。 每个添加查询的更新时间复杂度为 O(1)。 
3. 对于 Color l r c 操作，遍历线段树。 每当一个节点完全在范围内并且已经统一时，我们就直接覆盖它的颜色。 如果它被部分覆盖或混合，我们将其下推并递归。 这确保了以典型的惰性传播方式仅访问 O(log n) 个节点。 
4. 当一个段被新分配给颜色 c 时，我们从概念上“重置其基线”以匹配 add[c]。 这确保了未来的添加操作是相对于正确的颜色历史记录进行测量的。 
5. 对于查询 i，我们在线段树中从根走到叶子以确定位置 i 的颜色。 一旦我们知道了它的颜色 c，我们就返回 add[c] 加上该叶子的任何存储的偏移量。 

微妙之处在于每个索引并不存储其完整的值历史记录。 相反，它仅存储上次重置与当前全局颜色累积之间的差异。 这避免了重复的重新计算。 

### 为什么它有效

 不变的是，对于每个索引 i，其存储值等于自上次更改颜色以来应用于其当前颜色的所有 Add 操作的总贡献。 每次发生颜色分配时，我们都会重置该边界，以便过去的贡献不再被重复计算。 由于添加操作仅影响颜色而不直接影响索引，因此每个贡献都只计算一次，并且不会丢失任何更新或应用两次。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class SegTree:
    def __init__(self, n):
        self.n = n
        self.color = [1] * (4 * n)
        self.lazy = [0] * (4 * n)
        self.is_uniform = [True] * (4 * n)

    def push(self, v):
        if self.lazy[v]:
            c = self.lazy[v]
            self.color[v*2] = c
            self.color[v*2+1] = c
            self.lazy[v*2] = c
            self.lazy[v*2+1] = c
            self.is_uniform[v*2] = True
            self.is_uniform[v*2+1] = True
            self.lazy[v] = 0

    def update(self, v, l, r, ql, qr, c):
        if ql <= l and r <= qr:
            self.color[v] = c
            self.lazy[v] = c
            self.is_uniform[v] = True
            return
        if r < ql or qr < l:
            return
        self.push(v)
        mid = (l + r) // 2
        self.update(v*2, l, mid, ql, qr, c)
        self.update(v*2+1, mid+1, r, ql, qr, c)
        if self.color[v*2] == self.color[v*2+1] and self.is_uniform[v*2] and self.is_uniform[v*2+1]:
            self.color[v] = self.color[v*2]
            self.is_uniform[v] = True
        else:
            self.is_uniform[v] = False

    def query(self, v, l, r, idx):
        if l == r:
            return self.color[v]
        self.push(v)
        mid = (l + r) // 2
        if idx <= mid:
            return self.query(v*2, l, mid, idx)
        else:
            return self.query(v*2+1, mid+1, r, idx)

def main():
    n, q = map(int, input().split())
    st = SegTree(n)
    add = [0] * (n + 5)

    out = []

    for _ in range(q):
        parts = input().split()
        if parts[0] == "Color":
            l, r, c = map(int, parts[1:])
            st.update(1, 1, n, l, r, c)
        elif parts[0] == "Add":
            c, x = int(parts[1]), int(parts[2])
            add[c] += x
        else:
            i = int(parts[1])
            c = st.query(1, 1, n, i)
            out.append(str(add[c]))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```线段树仅负责跟踪范围分配下的当前颜色。 它从不存储值。 这种分离至关重要，因为值仅取决于颜色历史，而不取决于结构。 

add 数组存储每种颜色的累积增量，查询只需将索引映射到其颜色并读取相应的累积和。 

微妙的实现细节是延迟传播仅处理颜色覆盖。 我们从不尝试合并树内的数值，这可以保持树的干净并避免重复计算。

 ## 边缘情况

 一个关键的边缘情况是当一个段被重复重新着色时。 例如，如果我们重复应用“颜色 1 n 2”，然后应用“颜色 1 n 3”，则只有最后一个分配很重要。 线段树确保了这一点，因为惰性分配会覆盖以前的颜色状态。 

另一种情况是在任何重新着色之前对同一颜色多次调用 Add。 添加数组正确累积，并且由于查询仅解析叶子处的颜色，因此无论发生多少次添加操作，该值都保持一致。 

最后的边缘情况是查询从未显式重新着色的位置。 它们仍然是颜色 1，并且由于 add[1] 从 0 开始并且像任何其他颜色一样更新，因此它们自然会返回正确的值，无需特殊处理。
