 ## 解决方案
 ## 问题理解

 我们有一个访问序列`a[1..n]`。 对于选定的缓存容量`m`，LRU 缓存按照从最近使用到最近最少使用的顺序维护其项目。 每当访问某个项目时，它就会成为列表中的第一项。 如果缓存已满并且访问的项目不存在，则删除最后一个项目。 

每个查询给出一个容量`m`以及建议的 LRU 列表。 该列表可以包含少于`m`项，尾随零仅用作输入中的填充。 在处理具有容量的固定访问序列时，我们必须确定这个确切的列表是否在任何时刻出现`m`。 

查看 LRU 状态的关键方法是从相反的方向。 假设执行刚刚处理完`a[i]`。 从位置开始`i`并向后走。 我们第一次遇到某个值时，它是该值最近使用过的一次。 遇到的第一个不同值是 LRU 列表的前面，第二个不同值是下一项，依此类推。 因此，容量的 LRU 列表`m`是第一个`m`扫描时遇到不同的值`a[i], a[i-1], ...`向后，或所有不同的值（如果少于）`m`已经出现了。 

这一观察结果完全消除了为每个查询模拟单独链表的需要。 

边界故意设置得足够小，以便`O(n^2)`预处理步骤。 自从`n <= 5000`，二次界意味着一种情况最多约 2500 万次迭代。 官方的时间限制只有 1 秒，因此直接模拟每个查询的成本是不必要的，而立方解显然是不可能的。 查询列表元素总数最多为`2 * 10^6`，因此读取和散列查询列表本身是可以承受的。 总和为`n`和`q`跨测试用例也是有界的，这使得整个二次预处理变得易于管理。 

有几种很容易被忽略的边缘情况。 

首先，空的请求列表是有效的。 考虑：```
1
1 1
1
1 0
```缓存最初是空的，所以答案是`Yes`。 仅在第一次访问后检查状态并假设缓存必须包含某些内容的解决方案将错误地打印`No`。 预期的解决方案还将初始的空缓存视为有效的时间点。 

其次，查询可以包含比其容量更少的元素。 例如：```
1
3 1
1 2 3
3 1 2 0
```答案是`Yes`。 访问后立即`2`，缓存容量`3`仅包含`[2, 1]`。 粗心的实现可能会要求缓存恰好具有三个元素，因为容量是三个，这是错误的。 

第三，真正的 LRU 列表中不能出现重复值。 例如：```
1
2 1
1 2
2 1 1
```答案是`No`。 LRU 列表最多包含每个缓存的标识符一次。 由于哈希冲突，仅比较哈希而不检查此属性理论上可以接受重复查询，因此该实现显式拒绝包含重复项的查询。 

第四，重复访问不会创建重复条目。 例如：```
1
3 1
1 1 2
2 2 1
```答案是`Yes`。 第二次访问后`1`，状态仍然存在`[1]`，并在访问后`2`它变成`[2, 1]`。 将每次访问视为新列表元素的解决方案将失去 LRU 的定义属性。 

## 方法

 直接的方法是单独处理每个查询。 对于有容量的查询`m`，我们可以通过所有的来模拟LRU缓存`n`访问并检查请求的列表是否出现。 通过适当的哈希图加上链表，可以进行每个LRU操作`O(1)`，所以一次查询成本`O(n)`并且所有查询都会花费`O(nq)`。 在最大的单一情况下，这大约是`5000 * 2000 = 10 million`访问操作。 在多种情况下，个人的产品`n`和`q`值仍然可能变大，并且该问题是围绕更可重用的预处理步骤设计的。 基于数组的简单实现甚至更糟，因为将任意元素移动到前面可能会花费`O(n)`, 给予`O(qn^2)`操作，高达大约 500 亿个基本班次。 

暴力方法之所以有效，是因为每个查询都可以独立地重现精确的 LRU 行为。 它会失败，因为每个查询的访问顺序都是相同的，因此重复发现相同的新近度信息是浪费的。 

关键的观察是位置后的 LRU 状态`i`在我们决定采用多少个元素之前，实际上并不取决于容量。 完整的新近度排序已经由访问顺序确定。 向后扫描从`i`，在第一次遇到每个值时取它。 这会产生一个从最新到最近的不同值的通用序列。 容量`m`只是要求它的第一个`m`元素。 

这将问题变成了序列哈希问题。 对于每个端点`i`，我们向后扫描，仅保留每个值的第一次出现，并构建结果前缀的多项式哈希。 然后，查询列表可以由相同的散列表示。 如果哈希值匹配长度列表`L`，我们已经找到了所需的LRU前缀。 

对于列表短于​​其容量的查询，还有一个额外条件。 在这种情况下，缓存不能仅仅将请求的列表作为其第一个`L`元素。 它必须恰好包含那些`L`元素，因为缓存尚未填满。 因此，在端点`i`，中看到的不同值的总数`a[1..i]`也必须准确地`L`。 

我们可以改进简单的`O(n^2 + nq)`进一步散列解决方案。 不要存储每个哈希，然后扫描每个端点的所有查询，而是首先读取查询并将其目标哈希放入字典中。 在二次预处理过程中，立即解析遇到哈希的任何查询。 这给出了`O(n^2 + sum(m_i))`预计时间且仅`O(n + q)`除了输入列表之外的辅助存储器。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 使用 LRU 模拟进行暴力破解 |`O(nq)`与一个`O(1)`LRU 实现 |`O(n)`| 太重复了|
 | 基于数组的暴力破解 |`O(qn^2)`|`O(n)`| 太慢了|
 | 存储每个端点哈希，然后扫描查询 |`O(n^2 + nq + sum(m_i))`|`O(n^2)`| 在 C++ 中被接受，占用大量内存 |
 | 预处理期间的最佳哈希查找 |`O(n^2 + sum(m_i))`预计|`O(n + q)`| 已接受 |

 哈希值是无符号 64 位多项式哈希值，因此算术运算是取模`2^64`通过乘法后的掩码。 这与该问题的公认解决方案中常用的防碰撞样式相同。 

## 算法演练

 1. 在预处理访问序列之前读取每个查询。 删除尾随零填充并记录其容量、实际长度和多项式哈希。 空列表立即被标记`Yes`，因为缓存开始为空。 
2. 拒绝任何包含重复标识符的非空查询。 真正的 LRU 列表不能包含重复项，因此永远不会生成这样的查询。 
3. 计算`distinct[i]`, 前缀中出现的不同标识符的数量`a[1..i]`。 仅当所请求列表的元素少于缓存容量的查询时才需要该值。 
4. 将每个有效的查询放入一个字典中，该字典的键为`(length, hash)`。 该值是具有该精确对的查询索引的列表。 我们这样做是为了在预处理过程中发现的哈希可以立即解析所有匹配的查询，而无需再次扫描所有`q`查询。 
5.让`D`是请求的最大列表长度。 对于每个端点`i`， 扫描`a[i], a[i-1], ...`向后直到到达序列的开头或`D`已发现不同的值。 时间戳数组用于区分当前向后扫描期间看到的值，而无需每次都清除整个数组。 
6. 每当遇到新的不同值时，将其附加到当前的新近度序列并更新其多项式哈希。 如果当前不同值的数量是请求的长度，则查找`(length, hash)`在查询字典中。 
7. 对于哈希查找返回的每个查询，如果其容量等于其请求的长度，则接受它。 在这种情况下，缓存已满，并且它的第一个`length`elements 正是查询的列表。 
8. 如果容量大于请求的长度，则仅在以下情况下接受查询`distinct[i]`等于请求的长度。 这意味着只有那些请求的元素出现在已处理前缀中的任何位置，因此缓存恰好具有请求的元素数量，而不是具有额外的旧元素。 
9. 处理完所有端点后，打印`Yes`对于每个已解决的查询和`No`对于每个未解决的查询。 

### 为什么它有效

 考虑位置后立即执行`i`。 对于任何标识符`x`，发生`x`最接近`i`是其当前的最后访问。 如果我们从`i`，我们第一次看到`x`我们正好遇到了最后一次访问。 因此，通过向后扫描对第一次遇到进行排序将所有当前已知的标识符从最近使用到最近最少使用进行排序。 拿第一`m`不同的值准确给出了容量的 LRU 列表`m`。 

该算法检查每个可能的端点`i`并精确地构造那些不同的前缀。 因此，每个实际的 LRU 状态都会被考虑。 当全容量查询的序列等于这些前缀之一时，则完全匹配。 当到目前为止看到的完整值集与查询的大小相同时，较短的查询会完全匹配，否则缓存将包含其他元素。 不变量是在处理任何端点之后`i`，向后扫描的第一个`k`不同的值正是第一个`k`该端点处 LRU 新近度排序的位置。 由于检查了每个可能的端点，因此不会遗漏任何有效状态。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

MASK = (1 << 64) - 1
BASE = 911382323

def solve():
    t = int(input())
    output = []

    for _ in range(t):
        n, q = map(int, input().split())
        a = list(map(int, input().split()))

        queries = [None] * q
        answers = [False] * q

        # need[(length << 64) | hash] = query indices
        need = {}
        max_len = 0

        for qi in range(q):
            parts = list(map(int, input().split()))
            capacity = parts[0]
            values = parts[1:]

            while values and values[-1] == 0:
                values.pop()

            length = len(values)

            if length == 0:
                # The cache is empty before the first access.
                answers[qi] = True
                queries[qi] = (capacity, 0, 0, False)
                continue

            # An LRU list cannot contain duplicate identifiers.
            if len(set(values)) != length:
                queries[qi] = (capacity, length, 0, False)
                continue

            h = 0
            for x in values:
                h = (h * BASE + x) & MASK

            queries[qi] = (capacity, length, h, True)

            if length > max_len:
                max_len = length

            key = (length << 64) | h
            need.setdefault(key, []).append(qi)

        # distinct[i] = number of distinct values in a[0..i-1].
        distinct = [0] * (n + 1)
        seen_prefix = [0] * (n + 1)
        count = 0

        for i, x in enumerate(a, 1):
            if seen_prefix[x] == 0:
                seen_prefix[x] = 1
                count += 1
            distinct[i] = count

        if max_len > 0 and need:
            # Timestamp trick avoids clearing seen_backward for every endpoint.
            seen_backward = [0] * (n + 1)
            wanted_length = [False] * (max_len + 1)

            for capacity, length, h, valid in queries:
                if valid:
                    wanted_length[length] = True

            stamp = 0

            for end in range(n):
                stamp += 1
                h = 0
                cnt = 0
                j = end

                while j >= 0 and cnt < max_len:
                    x = a[j]

                    if seen_backward[x] != stamp:
                        seen_backward[x] = stamp
                        cnt += 1
                        h = (h * BASE + x) & MASK

                        if wanted_length[cnt]:
                            key = (cnt << 64) | h
                            matched = need.get(key)

                            if matched is not None:
                                total_distinct = distinct[end + 1]

                                for qi in matched:
                                    if answers[qi]:
                                        continue

                                    capacity, length, _, valid = queries[qi]

                                    if not valid:
                                        continue

                                    if capacity == length:
                                        answers[qi] = True
                                    elif total_distinct == length:
                                        answers[qi] = True

                    j -= 1

        for ok in answers:
            output.append("Yes" if ok else "No")

    sys.stdout.write("\n".join(output))

if __name__ == "__main__":
    solve()
```查询预处理发生在昂贵的访​​问序列扫描之前，因为它允许我们将每个可能的目标转换为字典查找。 查询的容量与其实际列表长度分开存储，因为当输入列表用零填充时，这两个数字具有不同的含义。 

在将查询插入之前有意执行重复检查`need`。 散列用于快速比较，但多项式散列是概率性的，因此拒绝结构上不可能的列表可以避免仅仅因为冲突而接受重复序列。 

这`distinct`前缀数组计算每个端点出现的不同标识符的数量。 对于查询`capacity > length`，条件`distinct[end + 1] == length`正是缓存尚未填充超出请求列表的条件。 

向后扫描使用时间戳数组，而不是清除每个端点的布尔数组。 什么时候`stamp`如果发生变化，每个旧标记在逻辑上都变得不活动。 这节省了额外的`O(n^2)`清除操作并使内循环专注于实际的向后扫描。 

哈希值的更新顺序与 LRU 列表相同。 如果向后扫描看到`x`， 然后`y`， 然后`z`，结果值是哈希值`[x, y, z]`，而不是相反。 掩码是必需的，因为 Python 整数不会像 C++ 无符号整数那样自然溢出。 正在申请`& MASK`显式地再现算术模`2^64`。 

屏蔽后不存在整数溢出错误，因为预期的算术恰好是模数`2^64`。 构造字典键时，长度会移动 64 位，因此不同长度的列表不能共享键，即使它们的 64 位哈希值相等。 

循环停止时`cnt == max_len`，而不是当后向索引达到特定边界时。 这已经足够了，因为没有查询要求超过`max_len`不同的值，超出该值的任何值都不会影响任何查询。

 ### 示例 1

 访问顺序为`4, 3, 4, 2, 3, 1, 4`。 每个端点处的后向不同序列是通用新近度排序，从中获得每个容量特定的 LRU 列表。 

| 端点| 访问 | 向后不同序列 | 不同前缀计数 |
 | --- | --- | --- | --- |
 | 1 | 4 |`[4]`| 1 |
 | 2 | 3 |`[3, 4]`| 2 |
 | 3 | 4 |`[4, 3]`| 2 |
 | 4 | 2 |`[2, 4, 3]`| 3 |

 | 7 | 4 |`[4, 1, 3, 2]`| 4 |

 第一个查询有容量`1`和目标`[4]`。 在端点 1 处，后向不同序列为`[4]`，所以它匹配。 

第二个查询要求`[2, 3]`有能力`2`。 没有端点将此作为其前两个不同值。 序列在端点 4 开始`[2, 4]`，而在端点 5 处开始`[3, 2]`，所以答案是`No`。 

第三个查询要求`[3, 2, 1]`有能力`3`。 没有向后的不同序列以该前缀开头，所以它也是`No`。 

第四个查询有容量`4`但仅要求`[4, 1, 3, 2]`。 在端点 7 处，看到的不同值的总数恰好为 4，并且向后的不同序列正是所请求的列表。 因此满足小于容量条件，答案为`Yes`。 

第五个查询要求`[3, 4]`有能力`4`。 在端点 2 处，后向序列为`[3, 4]`，并且只出现了两个不同的值。 由于请求的长度为2，容量为4，所以缓存正好是`[3, 4]`，所以答案是`Yes`。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 |`O(nD + sum(m_i))`预计|`D`是最大请求列表长度，并且`D <= n`; 最坏的情况是`O(n^2 + sum(m_i))`|
 | 空间|`O(n + q)`| 前缀不同计数、时间戳数组、查询和哈希字典 |

 最坏情况下的预处理最多执行`n`向后扫描，每次最多收集`n`不同的值，因此它最多执行`25 million`内迭代`n = 5000`。 总查询输入最多包含`2 * 10^6`整数。 这比为每个查询单独运行完整的 LRU 模拟要好得多，并且它避免了`O(n^2)`直接使用哈希矩阵实现了同样的思想。 官方的内存限制是512 MB，但上面的实现仅使用线性辅助内存。 

唯一的概率部分是 64 位多项式哈希。 与算术模`2^64`并且基数大于所有可能的标识符，意外相等的可能性极小。 这是预期的哈希解决方案使用的标准权衡。

case_max = (
    "1\n"
    f"{n} 2\n"
    + " ".join(map(str, sequence))
    + "\n"
    + f"{n} "
    + " ".join(map(str, reverse_list))
    + "\n"
    + "1 1\n"
)

assert run(case_max) == "Yes\nYes\n", "maximum n"
```| 测试输入| 预期产出 | 它验证了什么 |
 | --- | --- | --- |
 |`n=1`，一个空查询和一个`[1]`查询 |`Yes`,`Yes`| 初始空缓存和最小输入 |
 | 五重复`1`访问 |`Yes`,`Yes`,`No`,`No`| 重复访问、重复目标拒绝、部分缓存 |
 | 顺序`1 2 3`容量为 2 和 3 | 四`Yes`答案 | 精确的容量边界和更短的列表 |
 |`n=5000`， 顺序`1..5000`|`Yes`,`Yes`| 最大序列长度和大哈希扫描|

 ## 边缘情况

 ### 清空请求列表

 对于```
1
1 1
1
1 0
```零被删除，留下长度为零的列表。 该算法将此查询标记为`Yes`立即地。 不需要向后扫描，因为在第一次访问之前缓存是空的。 这直接处理了经常导致正确的解决方案收到错误答案的情况。 

### 列表小于其容量

 对于```
1
3 1
1 2 3
3 1 2 0
```请求的列表是`[1, 2]`，而容量为三。 在端点 2 处，后向不同序列为`[2, 1]`，所以这个特定的查询在那里不匹配。 在端点 1 处，序列为`[1]`。 在端点 3 处是`[3, 2, 1]`。 因此正确的输出实际上是`No`。 

一个更直接的正面案例是：```
1
3 1
1 2 1
3 1 2 0
```在端点 2 处，后向不同序列为`[2, 1]`， 不是`[1, 2]`，但在端点 3 处是`[1, 2]`。 仅出现了两个不同的值，因此容量为三的缓存恰好包含`[1, 2]`。 输出是`Yes`。 

平等`distinct[end] == length`这就是这种情况与完整缓存的区别。 单独匹配前缀是不够的，因为请求的列表后面可能仍然存在其他较旧的项目。 

### 查询中的重复标识符

 对于```
1
2 1
1 2
2 1 1
```查询列表是`[1, 1]`。 每个实际的 LRU 状态都包含不同的标识符，所以答案是`No`。 该实现在计算或注册查询哈希之前检测重复项。 

### 连续重复访问

 对于```
1
3 1
1 1 2
2 2 1
```各州是`[1]`,`[1]`， 和`[2, 1]`。 最终状态与查询完全匹配，所以答案是`Yes`。 向后扫描自然会处理这个问题，因为当它遇到第二个时`1`, 较早的`1`在该扫描期间将被视为重复项而被忽略。 

### 少于`m`出现了不同的价值观

 对于```
1
3 1
1 2
3 1 2 0
```到最后只出现了两个不同的标识符。 向后的不同序列是`[2, 1]`，容量为 3 的缓存恰好包含这两个元素。 一个查询要求`[2, 1]`被接受是因为它的长度是二并且`distinct[2]`也是两个。 

如果顺序是```
1
3 1
1 2 3
3 2 1 0
```所要求的`[2, 1]`在出现三个不同值的任何点上都不是完整的缓存。 一次`3`已经出现了，三容量缓存不能仅仅因为查询只有两个元素而丢弃它。 不同前缀条件可以防止这种误报。 

### 请求的列表比可用的新近度序列长

 假设访问顺序为```
1
3 1
1 1 1
3 1 2 3
```永远不会有两个或三个不同的标识符，因此向后扫描无法构造长度为三的新近度序列。 查询仍未解决，答案是`No`。 该实现自然会处理这个问题，因为内部扫描在达到请求的长度之前在访问序列的开头停止。 

### 同一目标出现在多个端点

 一个查询可能匹配多次。 例如，```
1
4 1
1 2 1 2
2 2 1
```第二次访问后匹配，第四次访问后再次匹配。 该算法不需要记住哪个端点是第一个匹配。 一旦找到哈希并且满足容量条件，答案就永久存在`Yes`。 

正确性并不取决于首先找到哪一个事件，因为问题仅询问是否至少存在一个有效端点。
