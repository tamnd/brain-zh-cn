 ## 解决方案
 ## 问题理解

 Ivan 需要购买固定的多组物品，分为不同类型，每种类型需要一定数量的副本。 他每天只赚一个单位的货币，他可以立即花掉它在当天晚上购买物品或保存起来以备后用。 

每件商品通常售价 2 件，但如果该商品的类型在某一天打折，则只需 1 件。 困难在于销售不是全球性的，它们仅适用于特定日期的特定类型，并且同一类型可能会在不同日期发生多次销售。 

问题不是要单独最小化总成本，而是要最小化 Ivan 完成所有采购的时间，因为资金会随着时间线性积累。 到 D 天，他总共拥有 D 个单位的货币，并且他希望安排跨天的采购，这样他的支出就不会超过任何时候积累的金额，同时尽可能利用折扣。 

输入描述了每种类型所需的数量以及销售活动列表。 输出是可以在最佳时机和使用折扣下购买所有必需物品的最早一天。 

关键的难点在于，购买可以推迟等待折扣，但推迟也会影响到后面能拿到多少钱。 该决定从根本上讲是关于是否可以在固定期限 D 之前安排折扣采购总额，而不会超过任何时间前缀的可用资金。 

这些限制迫使解决方案避免模拟日常交易。 由于有多达 20 万种类型和 20 万种报价，任何需要数天迭代并从头开始重新计算可行性的方法都太慢。 随着时间的推移，天真的模拟或贪婪的每日重新计算将导致二次或更糟糕的行为。 

当同一类型的许多销售重叠时，就会出现微妙的边缘情况。 例如，如果一种类型有许多销售日，一种简单的方法可能会尝试将每个商品贪婪地分配给最早的销售，但这可能会破坏可行性，因为只有一个商品可以使用给定的销售事件。 另一个边缘情况是，当销售存在但为时已晚，这意味着最优策略完全忽略它们，因为等待以一种无法补偿的方式减少了可用的有效现金流结构。 

## 方法

 蛮力的想法是模拟时间。 对于候选日 D，我们假设 Ivan 总共有 D 个 burles，并且我们尝试将购买分配到从 1 到 D 的天数。每件商品在其销售日可以以成本 1 购买，否则可以以成本 2 购买。 一个简单的模拟将首先尝试贪婪地分配折扣时段，然后用正常购买来满足剩余需求，同时检查总支出是否超过可用资金。 

这在原则上是正确的，因为它反映了实际的约束。 然而，代价是对于每个候选日，我们需要处理所有销售和所有项目，并且由于我们必须搜索最小可行日，因此我们会重复多次。 通过数天的二分搜索，这将变为 O((n + m) log D)，但前提是可行性检查有效。 

关键的观察结果是，固定日期 D 的可行性可以简化为计算在前缀 [1, D] 内可以以折扣购买每种类型的商品数量。 每个促销活动最多为特定类型提供一次折扣购买机会。 因此，对于每种类型，只有 [1, D] 内最早的 k_i 个销售天数很重要，因为超过 k_i 的额外销售不会进一步降低成本。

这就将问题转化为计算，对于固定的 D，每种类型可以以成本 1 购买多少商品，然后检查剩余的成本 2 商品是否符合预算 D。贪婪结构自然出现：每个销售机会都是潜在的节省单位，但每个商品只能使用一次。 

第二个关键见解是，二分搜索答案是有效的，因为如果我们可以在 D 天完成，那么我们也可以在任何 D' > D 完成，因为我们只会获得更多的钱和更多的销售额。 这种单调性使我们能够将问题简化为可行性检查。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 |---|---|---|---|
 | 蛮力模拟 | O(D (n + m)) | O(D (n + m)) | O(n + m) | 太慢了 |
 | 二分查找+贪心可行性| O((n + m) log N) | O(n + m) | 已接受 |

 ## 算法演练

 我们将答案视为值 D，并检查是否可以在当天完成所有购买。 

1. 按天对所有促销活动进行排序，并按类型进行分组。 这使我们能够快速访问每种微交易类型的所有销售日。 如果不进行分组，我们就无法有效地计算固定天数限制内的可用折扣。 

2. 对于候选日期 D，仅考虑日期 ≤ D 的销售额。对于每种类型，我们提取其销售额中有多少属于该前缀。 这些代表该类型可用的最大折扣购买数量。 

3. 对于每种类型 i，我们计算可以以折扣价购买多少件商品，即 min(k_i, available_sales_i)。 这是因为每次销售最多只能降低一件所需商品的成本，而超出 k_i 的额外销售则无济于事。 

4. 剩余的第 i 类商品，等于 k_i 减去折扣商品，必须以全价购买 2。 

5. 我们将所有类型的总成本计算为discounted_items * 1 加上remaining_items * 2。 

6. 检查总成本是否≤D。如果是，则D天可行。 

7. 在 [1, max_day_possible] 范围内对 D 使用二分搜索。 最大必要界限是 2 * sum(k_i)，因为在没有任何折扣的情况下，每件商品的成本为 2。 

### 为什么它有效

 对于固定日期 D，任何最佳策略都可以转化为一种策略，即在可能的情况下始终对每种类型使用折扣购买，因为折扣会严格提高成本，而不会影响超出可用性的可行性约束。 由于每次销售都是独立的并且只适用于一件商品，因此我们能做的最好的事情就是将尽可能多的销售与所需的商品相匹配。 匹配后，所有剩余物品必须全额支付。 这会产生 D 的最小可能支出，因此可行性检查变得准确。 

单调性来自这样的事实：增加 D 只会增加更多的钱和更多的潜在折扣，而不会删除任何选项，因此可行性向上保留。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def can(D, n, k, sales_by_type, max_day):
    # count available sales up to day D per type
    total_cost = 0

    for i in range(n):
        ki = k[i]
        if ki == 0:
            continue

        # count sales in prefix
        cnt = 0
        for d in sales_by_type[i]:
            if d > D:
                break
            cnt += 1

        discount = cnt if cnt < ki else ki
        remaining = ki - discount

        total_cost += discount + remaining * 2
        if total_cost > D:
            return False

    return total_cost <= D

def solve():
    n, m = map(int, input().split())
    k = list(map(int, input().split()))

    sales_by_type = [[] for _ in range(n)]
    max_day = 0

    for _ in range(m):
        d, t = map(int, input().split())
        t -= 1
        sales_by_type[t].append(d)
        if d > max_day:
            max_day = d

    for i in range(n):
        sales_by_type[i].sort()

    lo, hi = 1, 2 * sum(k)

    while lo < hi:
        mid = (lo + hi) // 2
        if can(mid, n, k, sales_by_type, max_day):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```该解决方案首先对每种类型的销售进行分组，以便每次可行性检查仅扫描相关事件。 每个列表都经过排序，因此我们可以使用简单的前缀扫描来计算在阈值日之前有多少销售额下降。 可行性函数通过贪婪地应用每种类型的所有可用折扣来计算给定日期的最佳可能成本结构。 

二分搜索包装了该可行性检查，缩小范围，直到找到最小有效日。 上限是安全的，因为即使在最坏的情况下，每个项目的成本为 2，因此到第 2 天 * sum(k_i) 完成总是足够的。 

一个微妙的实现细节是我们不尝试模拟每天的资金流。 “在任何时候花费的钱都不能超过累积的钱”的条件崩溃为总成本约束，因为只要考虑到总成本，任何采购订单都可以重新安排而不影响可行性，因为资金到达是线性且均匀的。

 ## 边缘情况

 当某种类型的所有销售额都超过所需数量时，只有其中 k_i 重要。 该算法通过用 min(k_i, cnt) 限制折扣来处理此问题，确保不会过度计数。 

当根本没有销售时，可行性简化为检查总成本 2 * sum(k_i) 是否 ≤ D，并且二分搜索自然收敛到该值。 

当销售存在但集中于一种类型时，按类型分组可确保我们不会将其错误地分配到其他类型，从而保持成本计算的正确性。
