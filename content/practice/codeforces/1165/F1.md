 **标签：** 二分查找，贪心
 **求解时间：** 3m 5s
 **已验证：** 是的

 ## 解决方案
 ## 问题理解

 Ivan 需要获取一系列物品，其中每个物品都属于多种类型之一。 对于每种类型，他必须购买所需的确切数量。 定价取决于商品是否在促销日购买：正常日每件商品售价 2 个单位货币，而促销日则售价 1 个货币单位。 

他每天只赚一个单位的钱。 只要积累了足够的钱，他可以在任何一天购买任意数量的物品。 促销是特定于类型和特定日期的，并且以成对列表的形式给出，表明特定类型在特定日期打折。 

目标是确定 Ivan 最早可以完成所有必需购买的日期，这意味着他有足够的积累资金并最佳地使用了所有有益的折扣。 

关键的困难在于 Ivan 可以选择何时购买每种商品，并且每种类型的折扣随时间而变化，因此安排不同时间的购买很重要。 

约束足够小，最多涉及大约 1000 天、1000 个类型和 1000 个总项目。 除非仔细优化，否则这排除了每次检查天数的二次方，并且强烈建议每天进行近线性处理的可行性检查是可以接受的，特别是在进行预处理的情况下。 

当贪婪的直觉被错误地应用到时间线上时，就会出现微妙的失败情况。 例如，总是在负担得起的情况下尽快购买而不考虑未来的折扣可能会失败。 另一个陷阱是假设一旦伊万有足够的总钱，他总是可以在以后回补折扣购买，这忽略了折扣与天数挂钩并且不具有追溯力。 

一个小的说明性失败场景是，某种类型在几天后才打折，但贪婪的早期购买耗尽了昂贵购买的资金，等待没有任何好处：

 输入：```
1 1
2
2 1
```如果 Ivan 在第一天立即购买，他将为两件商品支付 2。 但最佳策略是等到第 2 天，此时两个项目的成本都是 1，将所需的总资金从 4 减少到 2，这会改变可行性时间安排。 

这显示了核心结构：答案取决于在给定的一天内可以以成本 1 购买每种类型的物品数量。 

## 方法

 暴力方法是日复一日地进行模拟。 我们每天都会累积收入并检查当天是否可以完成所有购买。 为了测试可行性，我们会尝试将每个项目分配到一天，决定是使用折扣还是支付全价。 

幼稚的可行性检查可能会尝试首先贪婪地分配所有折扣机会，然后以全价填充剩余的项目。 然而，每天独立执行此操作而没有结构会导致重复扫描所有报价，并可能每天重新评估作业，产生 O(nm) 或更糟的结果。 

关键的观察是，对于固定日期 D，唯一的相关信息是，对于每种类型，其有多少商品在 D 日或之前至少有一次折扣。每个此类商品都可以以成本 1 购买； 其余成本为 2。因此，可行性降低为每种类型的确定性计算。 

我们可以为每种类型预先计算折扣日的排序列表。 然后，对于候选日 D，我们可以使用二分搜索快速计算出该类型有多少折扣单位可用。 这将可行性检查变成了 O(m log m + n log m) 总预处理加上每次检查 O(n log m)。 

由于 D 在可行性上是单调的，因此我们可以在 1 到 1000 天内对答案进行二分搜索。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力模拟| O(D·(n + m)) | O(D·(n + m)) | O(米) | 太慢了 |
 | 二分查找+预处理| O((n + m) log m + n log D) | O(米) | 已接受 |

 ## 算法演练

 我们想要测试给定的 D 天是否足以完成所有购买。 

1. 按类型对所有折扣日进行分组。 对于每种类型，存储折扣天数的排序列表。 排序是必要的，这样我们才能高效地查询到D为止有多少折扣。 
2. 定义固定日期 D 的可行性检查函数。该函数确定如果允许 Ivan 在 D 天之前购买，他是否可以完成所有购买。 
3. 对于每种类型 i，计算有多少个折扣天数 ≤ D。该值表示以成本 1 可以购买多少该类型的商品。 
4. 将其与所需数量 k_i 进行比较。 如果需要 k_i 件商品，并且有 x 个折扣机会，则可以便宜地购买 x 件商品，而剩余的 max(0, k_i - x) 必须以成本 2 购买。 
5. 将所有类型的总成本相加。 这给出了在 D 天之前完成所有购买所需的最低金额。 
6. 将所需成本与 Ivan 在 D 天之前积累的钱进行比较，即为 D（因为他每天赚 1）。 如果总成本≤D，则D天是可行的。 
7. 二分查找 [1, 1000] 范围内最小的 D，使得可行性成立。 

### 为什么它有效

 对于任何固定日期 D，每个折扣要么存在，要么不存在。 类型之间没有交互，因为每种类型的价格都是独立的。 一种类型中的最佳策略始终是首先使用所有可用的折扣时段，因为它们严格降低成本，且不限制可用性。 这使得每种类型的成本计算具有确定性。 单调性随之而来，因为增加 D 只会增加更多折扣机会并增加可用资金，因此可行性不会随着 D 的增长而降低。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
k = list(map(int, input().split()))

discounts = [[] for _ in range(n)]
for _ in range(m):
    d, t = map(int, input().split())
    discounts[t - 1].append(d)

for i in range(n):
    discounts[i].sort()

def can(day):
    total_cost = 0

    for i in range(n):
        need = k[i]
        if need == 0:
            continue

        dlist = discounts[i]

        # count how many discounts are available up to 'day'
        l, r = 0, len(dlist)
        while l < r:
            mid = (l + r) // 2
            if dlist[mid] <= day:
                l = mid + 1
            else:
                r = mid
        cheap = l

        cheap = min(cheap, need)
        total_cost += cheap + 2 * (need - cheap)

    return total_cost <= day

lo, hi = 1, 1000
ans = 1000

while lo <= hi:
    mid = (lo + hi) // 2
    if can(mid):
        ans = mid
        hi = mid - 1
    else:
        lo = mid + 1

print(ans)
```该解决方案首先构建每种类型的折扣日列表。 这种结构至关重要，因为它以一种可以有效查询的方式隔离所有与时间相关的信息。 然后，可行性函数将调度问题转换为纯算术成本计算。 

二分搜索依赖于这样一个事实：如果 Ivan 可以在 D 天之前完成，他也可以在以后的任何一天完成，因为金钱和折扣可用性只会增加。 

里面`can`，对每个折扣列表的二分搜索是唯一重要的步骤。 它计算截至候选人当天有多少晋升机会。 这个数量直接决定了可以便宜地购买多少物品。

 ## 边缘情况

 一个重要的边缘情况是某种类型的折扣天数多于所需商品的折扣天数。 该算法正确地限制了可用折扣`min(cheap, need)`，防止过度计数。 

另一种情况是折扣存在但发生在最佳完成日之后。 例如：```
1 1
2
5 1
```即使有折扣，但早期也没用。 可行性检查确保仅考虑天 ≤ D 的折扣。 

最后一个微妙的情况是，伊万有足够的钱，但折扣不足，这意味着成本仍然很高。 该算法处理这个问题是因为可行性取决于积累的资金和可实现的降低成本，而不仅仅是预算。
