 ## 问题理解

 我们得到了一个重复多次的非常小的模拟。 每个测试用例都描述了一个人试图通过钻木头生火的场景。 尝试的成功仅取决于三个整数：所需的阈值，以及表示操作的强度和执行速度的两个参数。 

对于每个测试用例，我们都会给出一个阈值$N$, 一种力量$S$，和速度$V$。 如果将钻探的综合“有效性”建模为产品，则该过程会成功$S \times V$, 达到或超过$N$。 如果产品足够大，木材就会点燃，否则不会点燃。 

因此每个查询都是独立的，输出是一系列二元决策： print 1 if$S \cdot V \ge N$，否则打印 0。 

限制非常小：$T \le 100$并且所有值最多为 100。这立即意味着即使是最简单的计算在性能方面也是微不足道的。 每个测试用例将两个整数相乘是一项持续的工作，因此即使是一个简单的循环也足够了。 

唯一微妙的陷阱来自于正确解释条件。 一个常见的错误是比较$S + V$反对$N$，或者要求严格的不平等而不是允许平等。 另一个可能的错误是在具有固定宽度整数的语言中溢出，但在 Python 中这是无关紧要的。 第三个微妙的问题是忘记每个测试用例都是独立的并且意外地在用例之间携带状态，尽管这个问题不会自然地引入状态。 

## 方法

 暴力解释是直接的：对于每个测试用例，计算乘积$S \times V$并将其与$N$。 这已经是最优的，因为没有链接测试用例的结构，也没有有助于进一步减少计算的预处理。 每个决策仅取决于三个数字，因此任何算法都必须至少读取它们并执行一次乘法。 

蛮力方法运行在$O(T)$，因为每个测试用例都需要恒定的时间工作。 即使我们想象更复杂的逻辑，输入大小也严格限制了一切，以至于除了直接评估之外的任何优化都是有意义的。 

关键的观察结果是，问题不在于跨多个输入的搜索或优化。 它纯粹是对单个导出值的阈值比较。 一旦认识到这一点，解决方案就会分解为单个算术检查。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(T)| O(1) | O(1) | 已接受 |
 | 最佳| O(T)| O(1) | O(1) | 已接受 |

 ## 算法演练

 1.读取测试用例数量$T$。 这决定了我们将执行多少次独立检查。 
2. 对于每个测试用例，读取三个整数$N$,$S$， 和$V$。 这些充分定义了场景。 
3. 计算乘积$P = S \times V$。 这代表了有效钻井功率。 
4. 比较$P$和$N$。 如果$P \ge N$，输出 1，因为达到或超过点火阈值。 
5. 否则输出0，因为钻孔不足以点燃木材。 

### 为什么它有效

 每个测试用例简化为一个不等式，仅涉及$S$,$V$， 和$N$。 案例之间不存在隐藏的相互作用或顺序效应。 该算法直接评估成功的定义条件，因此它完全符合问题的成功标准。 由于乘法和比较是精确且确定性的运算，因此决策始终是正确的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def main():
    t = int(input())
    out = []
    for _ in range(t):
        n, s, v = map(int, input().split())
        out.append("1" if s * v >= n else "0")
    print("\n".join(out))

if __name__ == "__main__":
    main()
```该解决方案使用有效地读取输入`sys.stdin.readline`干净地处理多个测试用例。 每个测试用例在循环内独立处理。 

关键计算发生在一行中：`s * v >= n`。 这对乘法和阈值比较进行编码。 结果存储为字符串，因为输出格式要求每行一个值。 

使用列表来收集输出可以避免循环内重复的 I/O 调用，这是一种标准的竞争性编程实践，尽管这里的约束并不严格要求它。

 ## 边缘情况

 一个关键的边缘情况是当乘积完全等于阈值时。 例如，输入：```
1
6 2 3
```这里$S \times V = 6$，等于$N$。 该算法将乘积计算为 6，将其与 6 进行比较，并输出 1。这证实了条件是包容性的，而不是严格的。 

另一种情况是产品仅比需要的少一个：```
1
7 2 3
```乘积为 6，小于 7，因此输出为 0。该算法不会尝试任何舍入或近似，而是直接计算整数乘积。 

由于所有计算都是小整数，因此不存在溢出或精度问题，并且每种情况都干净地简化为确定性比较。
