 ## 解决方案
 ## 问题理解

 我们给出了三个正整数，每个都代表线程的长度。 在一次操作中，我们选择一个线程并将其分成两个具有整数长度的较小线程，两者都严格为正数，并且它们的总和等于原始长度。 所有线程中总共最多允许三个这样的拆分。 在执行一些分割序列之后，我们希望所有生成的线程具有完全相同的长度。 

关键输出是可行性检查：对于每个测试用例，我们必须决定是否有可能使用不超过三个分割来获得等长片段的集合。 

测试数量方面的约束很大，最多 10^4 个案例，而每个测试案例的大小都是恒定的。 这立即排除了任何模拟任意分裂配置或状态搜索的方法，因为即使是分区上的适度分支 BFS 也会爆炸。 每项测试都必须在恒定或接近恒定的时间内完成。 

微妙的一点是，件数不固定。 每次操作都会使 threadlet 总数增加 1，因此最多经过 3 次操作后，我们总共最多可以有 6 个线程。 最终状态大小的硬上限使得直接组合推理成为可能。 

往往会打破天真的思维的边缘情况包括一个值远大于其他值的情况，例如 (1, 1, 1000000000)，或者两个值已经相等但第三个值稍有偏差的情况，例如 (5, 5, 6)。 这些通常会诱惑贪婪的“通过分割最大来均衡”策略，但这些策略忽略了严格的操作限制和对段大小的整数约束。 

## 方法

 一个蛮力的想法是模拟执行最多三次切割的所有可能方法。 每次切割都会选择一个当前段并将其分成两个正整数。 分支因子随着段的长度而增长，因为长度为 L 的段有 L−1 个可能的分裂。 即使只有三个操作，这也会创建一个巨大的可能性树，并且许多状态以不同的切割顺序重复。 配置总数远远超出了 10^4 个测试用例所能枚举的数量。 

关键的观察是我们实际上并不关心中间配置，只关心是否存在统一的最终长度。 如果最终长度为x，则每个原始段必须分解为长度为x的片段。 这将问题转化为检查每个数字是否可以表示为等份之和，并附加一个限制，即我们总共只能引入最多三个切割。 

这个限制非常严格：每次切割都会将片段数量增加一倍，因此从三段开始，我们最多可以得到六段。 因此，最终配置的大小可以为 3、4、5 或 6。由于所有片段必须具有相等的长度，因此总和 S 必须满足 S mod k = 0（对于 {3,4,5,6} 中的 k），其中 k 是最终的片段数。 对于每个有效的k，我们检查每个原始片段是否可以被分割成大小为S/k的整数，以及所需的分割总数是否不超过3。 

对于固定的目标长度 x，如果 a 可被 x 整除，则长度为 a 的线段贡献的切割等于 (a/x − 1)，否则不可能。 将所有三个部分相加即可得到所需操作的总数。 如果 [3,6] 中存在一些可行的 k 产生有效的 x 并且最多需要 3 次切割，那么答案是“是”。

 ## 算法演练

 我们继续测试所有可能的最终数量。

1. 计算三个螺纹长度的总和S。 这是必须平均分配给所有最终相等部分的总长度。 
2.对于从3到6的每个候选最终块数k，检查S是否能被k整除。 如果不是，则该 k 无法产生相等的段并被丢弃。 
3. 对于每个有效 k，计算目标片段长度 x = S / k。 这是每个最终线程的唯一可能的长度。 
4. 对于每个原始线段a，检查a是否能被x整除。 如果不是，这种配置是不可能的，因为我们无法分割成碎片。 
5. 如果可整除，则计算该段内需要多少次切割，即 a / x − 1。这是因为将 a 分成 m 个相等的块需要恰好 m − 1 次切割。 
6. 将所有三个段的切割计数相加。 如果总数最多为3，那么这个配置是可以实现的，所以我们可以立即返回YES。 
7. 如果[3,6]中没有k起作用，则返回NO。 

### 为什么它有效

 每个操作都会将段数恰好增加 1，因此从三个段开始，我们最多只能达到具有六个段的配置。 这将相等块的最终数量限制在一个小的恒定范围内。 对于固定的最终分割大小，每个原始片段内的切割结构是强制的：相等的片段意味着唯一的目标长度，并且每个片段独立地确定它贡献多少个切割。 由于除了通过共享的最终长度约束之外，片段不会相互作用，因此检查可行性减少为求和独立成本并验证全局削减预算。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def possible(a, b, c):
    total = a + b + c

    for k in range(3, 7):
        if total % k != 0:
            continue
        x = total // k

        cuts = 0
        ok = True

        for v in (a, b, c):
            if v % x != 0:
                ok = False
                break
            cuts += v // x - 1

        if ok and cuts <= 3:
            return True

    return False

t = int(input())
for _ in range(t):
    a, b, c = map(int, input().split())
    print("YES" if possible(a, b, c) else "NO")
```该实现直接遵循以下观察结果：只有从 3 到 6 的最终分区大小是相关的。 k 上的循环枚举了所有可能的最终状态，对于每一种状态，我们验证是否可以用最多 3 次切割来构造它。 

切割的计算使用这样的恒等式：将一个段分成 m 个相等的部分正好需要 m−1 次操作。 这避免了显式模拟分裂过程。 布尔标志确保我们在整除失败时尽早丢弃无效的分解。

 ## 边缘情况

 像 (1, 1, 100) 这样的情况强调了割集是全局有界的限制。 该算法会尝试 [3,6] 中的所有 k，但对于从这些 k 值导出的任何有效 x，大段会强制进行太多分割或破坏整除性，因此所有候选者都会失败，并且输出为“否”。 

对于 (6, 3, 3)，正确的解决方案需要认识到只有一个段需要拆分，并且拆分产生的段数恰好正确，且不超过操作限制。 该算法通过计算精确的每段切割计数而不是模拟任何序列来捕获这一点。 

对于已经相等的输入（如 (5, 5, 5)），k = 3 且 x = 5 的情况会产生零割，这会立即满足约束，产生 YES 而不执行任何操作。
