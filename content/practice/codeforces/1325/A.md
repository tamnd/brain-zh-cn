 ## 解决方案

 ## 问题理解

 我们给定一个数字 x，对于每个查询，我们必须构造两个正整数 a 和 b，这样当我们计算它们的最大公约数和最小公倍数时，这两个值的总和正是 x。 

与其将其视为算术恒等问题，不如将其视为构造任务：我们试图将 x 分成来自一对数字结构的两个相互作用的部分。 gcd 捕获它们共享的因子结构，而 lcm 捕获它们组合的乘法跨度延伸的距离。 

就测试用例数量而言，约束很小，但 x 本身可以大到 10^9。 这立即排除了任何尝试搜索所有 a 和 b 对甚至每个测试用例的所有 gcd 候选者的方法。 在最坏的情况下，每个测试用例的二次甚至线性扫描都会太慢。 

一个微妙的点是 gcd 和 lcm 紧密耦合。 许多天真的尝试尝试随机对或固定一个值并导出另一个值，但这些方法经常会失败，因为更改 a 和 b 以非线性方式同时更改 gcd 和 lcm。 一种常见的故障模式是假设自动选择较小的 gcd 会使 lcm 的行为可预测，但除非仔细构建数字，否则这是不正确的。 

## 方法

 暴力破解的想法很简单：迭代所有对 (a, b) 直到 x，计算 gcd(a, b) 和 lcm(a, b)，并检查它们的总和是否等于 x。 这是正确的，因为它耗尽了整个搜索空间。 然而，对的数量约为x^2，在最坏的情况下最多可达10^18次操作。 即使使用对称性或边界进行优化也无法使这一点接近可行。 

关键的见解是停止尝试直接独立控制 gcd 和 lcm。 相反，我们利用一个标准恒等式：如果我们写 a = g·u 和 b = g·v，其中 gcd(u, v) = 1，则 gcd(a, b) = g 且 lcm(a, b) = g·u·v。 表达式变为g + g·u·v = g(1 + u·v)。 这表明整个结构取决于因子 g 和互质对 u 和 v。 

现在我们想要 g(1 + u·v) = x。 满足这一点的最简单方法是选择 g = 1。这消除了所有 gcd 复杂性，并将条件简化为 1 + u·v = x，或 u·v = x − 1。我们总是可以通过选择 u = 1 和 v = x − 1 来满足这一点，它们是平凡互质的。 这给出 a = 1 和 b = x − 1，这总是有效的。 

问题陈述还接受任何有效对，并且示例包含 x = 14 的另一个有效构造，因此存在多个解决方案。 然而，最简单的构造已经满足所有限制。

 ## 算法演练

 我们为每个测试用例独立构建答案。 

1. 读x。 
2. 设置a = 1。 
3. 设 b = x − 1。 
4. 输出a和b。 

选择 a = 1 有效的原因是它强制对于任何 b 来说 gcd(1, b) = 1。 这完全简化了 gcd 和 lcm 之间的交互。 

1 和 b 的 lcm 始终为 b，因为 1 不与任何数字共享质因数并能整除所有数字。 因此表达式 gcd(a, b) + lcm(a, b) 变为 1 + b。 设置 b = x − 1 使总和恰好为 x。 

### 为什么它有效

 正确性取决于两个不变的属性：gcd(1, b) 始终为 1，lcm(1, b) 始终为 b。 这些对于所有正整数都成立 b． 一旦这些被固定，表达式就会折叠成 b 的线性方程，我们直接求解它，两个函数之间没有任何相互作用。 不存在隐藏约束，因为 gcd 和 lcm 在 1 存在的情况下都表现出确定性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    x = int(input())
    print(1, x - 1)
```代码准确地反映了结构。 对于每个测试用例，它读取 x 并输出 (1, x−1) 对。 循环内部没有边缘条件，因为 x 保证至少为 2，因此 x−1 始终为正。 

一个微妙的实现细节是我们从不显式计算 gcd 或 lcm。 任何这样做的尝试都是不必要的，只会带来开销。

 ## 边缘情况

 唯一有意义的边缘情况是可能的最小 x，即 x = 2。在这种情况下，算法产生 a = 1 和 b = 1。直接计算得到 gcd(1, 1) = 1 和 lcm(1, 1) = 1，因此要求总和为 2。 该结构不会被破坏，因为 x − 1 仍然为正。 

对于任何更大的 x，结构上没有任何变化。 无论 b 如何，gcd 都保持为 1，并且 lcm 恰好保持 b，因此输出始终满足所需的方程，而不需要特殊处理或分支逻辑。
