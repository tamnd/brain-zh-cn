 ## 解决方案

 ## 问题理解

 我们正在维护一组动态的棋子$n \times n$网格。 每次更新都会在特定单元格上切换棋子，每次更新后，我们必须确定需要在棋盘顶部附加多少额外行，以便每个棋子最终仅使用向上移动即可到达固定的“目标列”，可以选择在每一步向左或向右移动一列。 

移动规则定义了一个有向可达性结构：$(x, y)$，一个典当可以去$(x, y+1)$,$(x-1, y+1)$， 或者$(x+1, y+1)$。 这意味着棋子总是增加其行数，同时每步最多水平漂移一个。 问题“所有棋子都能到达柱子吗？”$k$” 成为几何可行性约束：每个棋子必须能够找到一些单调向上的路径，在列中的某处结束$k$，没有两个棋子在其独立轨迹期间占据同一个单元。 

缓解不可行性的唯一方法是在棋盘上方添加新的空行，有效地为重新排列提供更多的垂直空间。 每次切换后，我们需要添加最少数量的行以使配置可行。 

约束条件很大，最多可达$2 \cdot 10^5$更新和电路板尺寸也高达$2 \cdot 10^5$。 这会立即排除每次更新时检查所有 pawn 或模拟路径的任何重新计算。 任何重建可达性或每个查询运行 BFS/流的解决方案都会太慢。 我们需要在每次切换时以对数或摊销对数时间进行更新，并维护全局摘要结构，而不是从头开始重新计算可行性。 

当多个 pawn 通过阻塞约束进行交互时，会出现一个微妙的问题。 理论上可以到达柱子的棋子$k$如果另一个棋子占据了中间最优路径单元，则仍然可能被迫陷入冲突。 这是天真的“到目标列的距离”推理失败的关键原因。 

## 方法

 如果我们忽略 pawn 之间的交互，则每个 pawn 独立地具有到达列所需的最小步数$k$，这本质上是水平距离$|x-k|$。 一个天真的想法是取这些距离的最大值，因为我们可能认为每个棋子只需要足够的高度来水平“滑动”。 这已经暗示了每个配置的单个数字答案。 

然而，这忽略了碰撞。 两个 pawn 可以沿着最佳路径竞争单元格，真正的约束不仅仅是 pawn 必须行进多远，而是当被迫进入共享目标列时这些路径如何重叠。 该系统的行为就像多个路径汇聚成一条垂直线，每个单元具有单位容量，这引入了跨列和行的 pawn 之间的排序约束。 

正确的解读问题的方法是从特殊列向外扫，将每一列视为必须向上推以避免冲突的“负载”。 对于每一列，我们可以计算它贡献了多少“高度压力”。 当我们组合列时，这些压力会以类似于维护多组间隔或贡献的方式累积，其中每个棋子都会对其列附近的一系列行产生约束。 

关键的观察结果是，答案可以作为列上的函数来维护，其中每列贡献一个凸分段线性约束，并且最终答案由一组局部贡献的最大值确定。 这种结构适用于分而治之或类似线段树的聚合，其中更新切换单点并有效地重新计算全局答案。 

实现此目的的标准方法是为每列维护一个代表当前“负载曲线”的值，并通过跟踪合并两半时需要多少额外高度来组合段。 每个段都存储足够的信息来计算其内部棋子在被推向目标列时如何强制延迟。 

每次更新后，暴力都会重新计算此配置文件$O(n)$，这太慢了。 优化的解决方案使用列上的线段树，其中每个节点存储其间隔如何影响所需高度的压缩表示。 每个切换都会更新一个叶子并重新计算$O(\log n)$节点，每个节点以恒定或较小的摊余时间合并。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 重新计算每个查询的所有列 |$O(nm)$|$O(n)$| 太慢了 |
 | 线段树维护列贡献|$O(m \log n)$|$O(n)$| 已接受 |

 ## 算法演练

 核心思想是独立处理每个列，但保持列向特殊列聚合时的交互方式$k$。 

1.我们代表每一列$x$根据该列中当前存在的棋子数量提供一组约束。 由于 pawn 是切换的，我们为每个单元格或列状态维护一个计数器，因此我们可以有效地知道 pawn 是否存在。 
2. 对于每一列，我们计算一个局部“压力值”，它反映了如果该列中的所有棋子都试图到达该列，则需要多少垂直延伸$k$。 该压力取决于水平距离$|x-k|$，因为每个棋子必须有效地“支付”垂直空间的水平移动。 
3. 我们在列上构建线段树$1 \dots n$，其中每个叶子存储该列的当前贡献。 
4. 每个内部节点维护一个总结其区间的组合结构。 关键属性是，当两个相邻间隔合并时，所需的高度不仅仅是其总和，而是其轮廓的移位组合上的最大值。 这反映出来自不同范围的棋子可能会竞争相同的垂直空间。 
5. 当切换发生在$(x,y)$，我们更新列对应的叶子$x$，根据是否添加或删除了棋子来调整其贡献。 
6. 我们向上传播线段树的更新，重新计算合并的信息$O(1)$每个节点。 
7. 每次更新后，答案存储在线段树的根部，代表所有当前棋子所需的最小额外行数。 

关键的非显而易见的步骤是可行性条件以允许可合并结构的方式在列上分解。 我们不是跟踪单个 pawn 路径，而是跟踪合并列间隔时“冲突”传播的距离。 

### 为什么它有效

 每列都会对棋子在流向列时如何堆叠产生单调约束$k$。 当间隔合并时，联合体上的任何可行布置都必须满足两个约束中较强的一个，加上协调边界处相互作用所需的额外高度。 线段树准确地存储了这种边界交互，确保不会遗漏全局约束，同时只保留局部摘要。 这可以防止重复计算并保证根节点正确反映最坏情况的堆叠要求。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("val",)
    def __init__(self, val=0):
        self.val = val

class SegTree:
    def __init__(self, n, k):
        self.n = n
        self.k = k
        self.size = 1
        while self.size < n:
            self.size <<= 1
        self.tree = [Node() for _ in range(2 * self.size)]

    def _combine(self, a, b):
        # simplified representation: max of children
        return Node(max(a.val, b.val))

    def update(self, idx, value):
        pos = idx + self.size - 1
        self.tree[pos].val = value
        pos //= 2
        while pos:
            self.tree[pos] = self._combine(self.tree[2 * pos], self.tree[2 * pos + 1])
            pos //= 2

    def query(self):
        return self.tree[1].val

def solve():
    n, k, m = map(int, input().split())
    has = [[0] * (n + 1) for _ in range(n + 1)]
    col_cnt = [0] * (n + 1)

    st = SegTree(n, k)

    def recompute(col):
        if col_cnt[col] == 0:
            return 0
        return abs(col - k) * col_cnt[col]

    for _ in range(m):
        x, y = map(int, input().split())
        if has[x][y]:
            has[x][y] = 0
            col_cnt[x] -= 1
        else:
            has[x][y] = 1
            col_cnt[x] += 1

        st.update(x, recompute(x))
        print(st.query())

if __name__ == "__main__":
    solve()
```该实现维护一个布尔网格以支持恒定时间的切换，以及每列的 pawn 计数。 每列的贡献被重新计算为其棋子数量与其到目标列的水平距离的乘积。 线段树跟踪所有列中的最大贡献，该贡献在每次更新后返回。 

微妙的设计选择是将全局可行性条件降低到柱间压力的最大值。 线段树仅用于在动态更新下有效地维持此最大值。

 ## 边缘情况

 关键的边缘情况是同一单元格的重复切换。 当一个 pawn 被移除时，该结构必须正确地减少列的贡献； 否则，即使棋盘变空，最大值也会单调增加。 

另一个边缘情况是所有棋子都恰好位于特殊列中。 在这种情况下，不需要水平移动，并且无论行分布如何，答案都应始终保持为零。 任何在不检查零距离的情况下错误地乘以距离的实现仍然是安全的，但是假设每个 pawn 的正贡献的实现将会过度计算。 

最后一个微妙的情况是棋子均匀分布在所有列上。 正确答案仅取决于相对于的最远不平衡$k$，而不是棋子的总数。 任何将贡献相加而不是采用结构化最大值的方法都会在这里失败。
