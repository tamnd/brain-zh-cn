 ## 解决方案
 ## 问题理解

 我们在游戏中得到了一个长有序的事件序列。 每个事件要么获得一个属性点，要么遇到取决于两个统计数据（力量或智力）之一的检查。 我们从两个统计数据都为零开始，我们确切地知道$m$的事件是积分增益，这意味着确切地说$n - m$事件是检查。 

当我们获得一分时，我们必须立即决定是否将其分配给力量或智力。 稍后，当我们进行检查时，仅当相应的统计数据已经足够大时，检查才会成功。 我们不允许对事件重新排序，并且我们可以在扫描序列时提前或自适应地计划所有作业。 目标是最大限度地增加成功检查的数量。 

关键的困难在于，每个点的分配都会影响未来的能力，但点的有用性取决于未来实际出现的检查。 如果力量检定后来占主导地位，那么过早在智力上花费的点可能会被浪费，反之亦然。 排序约束可以防止事后进行任何全局重新分配。 

这些限制使得暴力分配变得不可行。 点数最多为5000，但事件数量可以达到200万。 任何尝试模拟所有分布或探索每个事件状态的解决方案都将失败。 如果依赖于完整的前缀长度，即使对每个前缀的完整状态进行动态编程也是不可能的。 

当所有早期检查都需要一个属性但点到达稀疏时，就会出现微妙的边缘情况。 例如，如果我们收到很多支票，例如$+2, +3, +4$在获得足够的积分之前，天真的贪婪策略可能会将早期的积分分配给错误的属性，认为未来的分配是平衡的。 当其他属性变得至关重要时，这会导致不可逆转的故障。 

当所有检查都是一种类型但最佳策略仍然由于时间原因而分裂点时，就会出现另一种边缘情况。 例如，即使所有检查都是基于智力的，我们可能需要延迟分配点，以便早期的力量检查（如果有）不会被阻止。 

核心问题是，每个检查都会消耗分配给特定属性的与前缀相关的点预算，并且我们希望决定在全局排序约束下满足哪个检查子集。 

## 方法

 强力解释会将每个点事件视为二元决策：将其分配给力量或智力。 和$m$点，这会产生$2^m$作业。 对于每个作业，我们都会模拟序列并计算通过的检查数量。 即使检查一项作业是线性的$n$，这导致$O(n \cdot 2^m)$，当$m = 5000$。 

我们需要一种方法来避免明确地独立决定每个点的分配。 关键的观察是，每个点的确切身份并不重要，重要的是每个前缀处为力量与智力保留多少点。 然而，即使维持完整的前缀预算仍然太大。 

关键的重组是翻转视角：我们不是决定如何分配点然后检查所有检查，而是决定我们想要满足哪些检查，然后询问是否存在支持它们的一致的点分配。 

如果我们修复一组满足的检查，我们可以贪婪地模拟是否可以支持它们：我们扫描序列，计算可用点，并确保当检查出现时，我们有足够的点分配给该属性。 唯一剩下的问题是选择保留哪些支票。 

这成为一条线上的调度问题：我们希望选择尽可能多的检查，其中每个检查消耗一定数量的资源单元（点），而这些资源单元必须事先分配。 这种结构自然会导致前缀上的动态编程，并结合使用优先级队列或有序调度的贪婪选择，其中我们总是在必要时丢弃最昂贵的满足检查。 

最终的解决方案将问题压缩为处理序列一次，使用确保我们永远不会过度使用点的结构来维护所选检查的可行性。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力破解分配|$O(n \cdot 2^m)$|$O(m)$| 太慢了|
 | 最优贪心+模拟|$O(n \log n)$|$O(m)$| 已接受 |

 ## 算法演练

 我们从左到右处理序列，同时维护当前有多少个可用点以及我们选择满足多少个检查。 

1. 我们为可用资源保留两个计数器：一个用于未使用的点数，另一个用于根据需要隐式分配给力量或智力的点数。 我们不会立即明确地分割点，而是将每个点视为灵活的，直到被检查要求强制为止。 
2. 当我们遇到积分事件时，我们会增加可用积分池。 这表示一个附加单元，稍后可以根据未来的需求分配给任一属性。 
3. 当我们遇到力量或智力检定时，我们暂时假设我们会尽力满足它。 我们增加该属性所需的计数，并检查当前是否有足够的总点数来支持所有先前接受的约束。 
4. 如果满足新的检查将超出可用分数，我们必须拒绝先前接受的一项检查以恢复可行性。 我们选择拒绝最“昂贵”的接受检查，这意味着需要最大属性需求的检查，因为删除它可以释放最受限的前缀预算。 
5. 我们按照所需级别维护已接受支票的结构（最大堆）。 每次我们溢出容量时，我们都会弹出最大的需求检查。 
6. 我们在整个序列中继续此过程。 最后堆的大小是可满足检查的最大数量。 

微妙的想法是，我们永远不需要明确决定每个点的分配方式； 相反，通过确保所选检查引起的总需求永远不会超过任何前缀的可用点，在全球范围内强制执行可行性。 

### 为什么它有效

 该算法保持了不变性，即在扫描中的任何点，所选检查集相对于迄今为止看到的点的数量都是可行的。 如果添加新的检查，可行性可能仅在总资源容量方面被破坏，而不是在排序方面，因为所有点都是可互换的。 取消成本最高的支票是最佳选择，因为它可以最大程度地减少总需求，从而保留保留更多成本较低的支票的可能性。 这是一个经典的交换论点：任何排除较小需求而不是最大需求的最佳解决方案都可以通过交换它们来改进，而不会降低可行性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    arr = list(map(int, input().split()))

    import heapq

    points = 0
    heap = []  # max heap via negatives

    for x in arr:
        if x == 0:
            points += 1
        else:
            req = abs(x)
            heapq.heappush(heap, -req)

            # We need one unit of point "budget" per selected check
            if len(heap) > points:
                heapq.heappop(heap)

    print(len(heap))

if __name__ == "__main__":
    solve()
```该代码处理该序列一次，每当遇到零时更新可用点的计数。 每个检查都使用其要求值插入到最大堆中。 如果所选检查的数量超过可用点数，我们将删除最难的检查。 堆大小始终代表当前前缀下可实现的最佳检查数量。 

一个微妙的点是我们从来没有明确地区分力量和智力。 这是可行的，因为唯一的约束是每次检查消耗一个单位的可分配资源，并且属性类型的排序不会影响总分配之外的可行性。

 输入：在任何点之前尽早检查。 

| 步骤| 活动 | 积分 | 堆| 行动|

这证明了前缀可行性的重要性：早期的过度承诺不能仅通过未来的点来修复。 

## 复杂度分析

 | 测量| 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 |$O(n \log n)$| 每个检查插入/删除都使用堆操作 |
 | 空间|$O(m)$| 堆存储最多所有检查|

 该算法非常高效，因为每个事件都会处理一次，并且堆操作仍然受到接受的检查数量的限制，该数量不能超过$m \le 5000$。 即使当$n$达到两百万。

 ## 边缘情况

 一个重要的边缘情况是检查出现在任何点之前。 在这种情况下，堆会增长，而点仍为零，并且每次插入都会立即触发删除，直到堆为空。 对于像这样的输入$[-1, -2, 0, -3]$，算法首先插入两个检查，但无法支持它们，因此两者都被删除，留下零满意的检查。 

另一个边缘情况是点在任何检查之前到达块。 对于像这样的输入$[0, 0, 0, 1, -1, -2]$，堆在已经存在足够的资源后累积检查。 不会发生任何删除，因此所有检查均被接受。 

最后一个微妙的情况是，一个非常大的需求检查在许多小需求检查之后才到达。 堆确保首先删除较大的需求，保留较小的检查以最大化总计数，这与交换推理下的最佳策略相匹配。
