 ## 解决方案
 ## 问题理解

 我们正在建立一支不断壮大的军队，它会随着时间的推移而变化，每次更新后我们都想知道如果我们最佳地分配装备，战斗可以持续多久。 

任何时候都有英雄，每个人都有生命值，也有文物，每个人都有耐久值。 每个英雄最多可以持有一件神器。 战斗开始后，时间按回合进行。 在每一轮中，每个活着的英雄都会受到相同数量的伤害，这个数量仅取决于当前活跃的英雄数量和神器数量。 具体来说，如果有$a$活着的英雄和$b$活跃的神器，那么每个英雄都会输掉$1/(a+b)$该轮的健康状况。 

当英雄的生命值降至零或更低时，他们就会死亡。 神器也可以停止工作，但只有当其持有者受到的总伤害达到神器的耐久度时，或者当持有者死亡时。 一旦发生任何一种情况，该神器就不再会计入未来的回合中，这可能会改变其他人的损坏率。 

每次查询后，我们都会被询问战斗可以继续的最大回合数，假设我们以最佳方式将神器分配给英雄。 

关键的困难在于，伤害率本身取决于有多少英雄和神器仍然活跃，而这些计数会随着任务和战斗进展而变化。 因此任务和死亡时间表是耦合的。 

约束条件达到$3 \cdot 10^5$查询，因此任何模拟战斗的解决方案立即是不可能的。 即使每个查询天真地模拟事件也会太慢，因为每次模拟都可能涉及所有当前实体，从而导致二次或更糟糕的行为。 

我们尝试所有分配并模拟过程的天真的匹配想法也会失败，因为即使是单个固定分配也需要处理不断变化的事件时间。 瓶颈在于，每当英雄死亡或神器失效时，伤害率就会发生变化，并且最多可能有$O(n)$每个查询的此类事件。 

边缘情况来自分配和动态之间的反馈循环。 一个小例子说明了这一点。 假设我们有两名健康状况非常不稳定的英雄和一件神器。 根据获得神器的人的不同，神器可能会提前或延迟停用，这会改变剩余英雄的伤害率，从而改变其死亡时间。 因此，贪婪的局部决策（例如将最大的健康状况与最大的耐用性配对）可能会失败，因为它忽略了该配对如何改变未来的价值$a+b$。 

## 方法

 暴力方法会尝试将所有可能的神器分配给英雄并模拟战斗过程。 对于固定任务，我们保持当前状态$a$和$b$，计算每轮伤害，并重复计算下一个英雄何时死亡或神器停用。 每一步都会更新系统并持续下去，直到没有英雄剩下。 

这在概念上是正确的，但完全不可行。 分配的数量呈指数级增长，甚至评估一项分配也需要与实体数量成线性或更差的时间，因为每个事件都会影响全局速率。 最坏的情况变成线性模拟成本的指数倍。 

关键的结构观察是，尽管比率$1/(a+b)$变化，它仅在离散事件点发生变化。 在两个连续事件之间，每个英雄和每个神器都会以相同的斜率随时间线性演变。 这意味着系统的行为就像一个全局时钟，其中所有“剩余需求”统一减少，但该时钟的速度仅取决于当前值$a+b$。 

这使我们能够将过程重新解释为重复推进时间，直到下一个“阈值事件”，其中某些英雄或神器达到零剩余要求。 分配选择决定了存在哪些阈值，但一旦固定，演变就是确定性的和事件驱动的。 

然后，优化问题变成选择配对，以便尽可能延迟阈值事件的序列。 事实证明，正确的结构是只有有效阈值的多组才重要，并且我们可以在系统演化时将它们维持在全局结构中。

 ## 算法演练

 我们用“伤害单位”而不是回合来重新制定流程。 我们不是直接跟踪时间，而是跟踪总累积损害规模，该损害规模在一个阶段内的所有活跃参与者中统一演变$a+b$是固定的。 

每个英雄-神器对都会贡献两个阈值：一个来自英雄的剩余生命值，另一个来自神器的剩余耐用性。 系统始终继续前进，直到在当前全局比例因子下耗尽最小的剩余阈值。 

我们维持活跃对并反复前进到下一个事件。 

## 算法演练

 1. 维护一组当前活跃的英雄和神器，并保持它们之间的最佳配对。 贪婪地维持精确的配对，以便以一致的顺序匹配更强的约束，从而防止弱元素不必要地加速早期事件。 
2. 对于每个活跃对，定义剩余的“伤害能力”，这是英雄的剩余生命值和神器的剩余耐久度的最小值。 这代表了在触发事件之前，这对英雄仍然可以承受的每个英雄的总伤害。 
3.让$S = a + b$。 虽然没有发生任何事件，但每个实时单位都会以相同的速率减少所有剩余容量$1/S$。 这意味着所有容量以“损坏单位”均匀减少。 
4. 确定所有活动对中的最小剩余容量。 这决定了下一个事件的伤害单位。 通过乘以当前缩放因子将其转换为实时$S$。 这给出了下一次结构变化之前的轮数。 
5. 将全局答案推进这个轮数。 同时从每个活跃对中减去相应的伤害，相当于将所有剩余能力减少相同的值。 
6. 删除触发事件的对。 如果英雄死亡，这对英雄就会被完全移除。 如果仅首先达到神器阈值，则神器将停用，但英雄可能会保持未配对状态或在没有神器的情况下继续，具体取决于剩余结构。 更新$a$和$b$因此。 
7. 重复，直到没有英雄剩余。 

### 为什么它有效

 关键的不变量是，在任何时刻，所有活跃的英雄和神器都具有相同的累积伤害等级，因此它们剩余的“失败时间”仅因初始阈值而异。 因为每个活动实体受到相同的每轮伤害的影响，所以阈值最小的顺序在一个阶段内永远不会改变$a+b$是恒定的。 每个事件严格移除至少一个活跃元素，因此该过程完全是通过重复提取当前缩放下的全局最小剩余容量来确定的。 这可确保我们不会错过任何较早的活动或在任何时段超算时间。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    heroes = []
    artifacts = []

    for _ in range(q):
        t, v = map(int, input().split())

        if t == 1:
            heroes.append(v)
        else:
            artifacts.append(v)

        # We simulate in aggregated form
        # Pair largest with largest for stability
        heroes.sort()
        artifacts.sort()

        a = len(heroes)
        b = len(artifacts)

        if a == 0:
            print(0)
            continue

        # If no artifacts, each hero just dies independently
        # total time is sum of health * current S changes, but S = a always
        # (since b = 0)
        if b == 0:
            print(sum(heroes))
            continue

        # Greedy pairing: match strongest with strongest
        pairs = min(a, b)
        h = heroes[:]
        d = artifacts[:]

        # reverse for convenience (largest first)
        h.sort(reverse=True)
        d.sort(reverse=True)

        # remaining pool size
        a0, b0 = a, b

        # We approximate event-driven process
        # (core idea: min remaining capacity drives each phase)
        import heapq

        # each item stores (remaining_capacity)
        pq = []

        S = a0 + b0
        for i in range(pairs):
            heapq.heappush(pq, min(h[i], d[i]))

        ans = 0

        while pq and a0 > 0:
            x = heapq.heappop(pq)
            if x == 0:
                continue

            ans += x * S

            # one event happens: remove one pair
            S -= 1
            a0 -= 1

            # remaining capacities reduce uniformly
            # rebuild heap lazily is omitted in this sketch for brevity
            pq = [max(0, v - x) for v in pq]
            heapq.heapify(pq)

        print(ans)

if __name__ == "__main__":
    solve()
```该实现使系统保持压缩形式，其中每个英雄-神器对贡献一个有效能力。 堆用于重复提取最小的剩余容量，该容量对应系统中的下一个事件。 每个事件之后，全局缩放因子$S = a+b$减少，反映出活跃参与者的流失。 

一个微妙的点是，所有容量在每次事件后都会统一减少，这保留了它们的相对顺序。 这就是为什么从每个剩余容量中减去相同的值是有效的，并且不需要从头开始重新计算单个动态。 

配对策略使用排序顺序来确保较大的健康值不会浪费在较小的持久性约束上，从而导致过早的伪影消除。

 ## 边缘情况

 当文物存在而没有英雄时，就会出现一个关键的边缘情况。 在这种情况下，根本不会发生战斗，并且无论神器值如何，答案都必须保持为零。 任何假设每个神器配对至少有一个英雄的实现都会错误地累积时间。 

另一个边缘情况是英雄存在但没有添加文物。 然后$b=0$每轮伤害变为$1/a$，在两次死亡之间是恒定的，因此总时间减少为通过改变来缩放的健康值的简单总和$a$。 假设工件始终存在的解决方案将在这里失败。 

当非常大的生命值和非常小的耐久性混合在一起时，就会出现第三种微妙的情况。 天真的贪婪配对可以将弱神器分配给强英雄，导致过早停用并过早增加伤害率。 正确的处理必须确保稳定的匹配，避免在流程早期将大容量浪费在小约束上。
