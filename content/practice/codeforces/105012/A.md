 ## 解决方案
 ## 问题理解

 我们有两个长度相等的整数数组。 第一个数组是起始配置，第二个数组是目标配置。 我们可以执行由 n 个操作组成的序列，其中每个操作都是通过选择索引 i 来定义的。 当我们选择 i 时，i 左边的每个元素通过与 a[i] 进行按位“或”来更新，而 i 右边的每个元素通过与 a[i] 进行按位与来更新。 所选元素本身在该操作期间保持不变。 

我们必须按某种顺序使用每个索引一次，并且在应用所有 n 次操作后，结果数组必须与目标数组完全匹配。 如果这是不可能的，我们输出-1。 

操作的结构是不对称的。 选定的元素就像一个“位源”，通过 OR 将位注入到其左侧，同时通过 AND 充当其右侧的“位过滤器”。 这意味着位只能向左自由传播，而向右传播受到限制。 

约束条件很大：测试用例的 n 总和最多为 3×10^5，t 最多为 10^5。 这立即排除了任何对每个排列简单地模拟整个过程甚至每个步骤从头开始重新计算的方法。 每个测试用例的任何有效解决方案都必须是线性或接近线性的。 

一些微妙的边缘情况自然会出现。 

如果初始数组已经等于目标，则答案仍然不为空或被跳过； 我们被迫执行所有 n 个操作，并且仍然必须返回有效的排列。 检查相等性并立即返回的简单解决方案将会失败。 

当目标值与方向位约束不兼容时，就会出现另一个问题。 例如，如果某个位必须出现在某个位置，但没有源元素可以通过 OR 和 AND 约束正确传播它，则任何排序都无法解决该问题。 

最后，由于每个索引仅使用一次，因此顺序变为整个自由度。 这个问题从根本上讲是关于构建一个排列，该排列尊重比特必须如何从初始值流向最终值。 

## 方法

 强力解释将尝试索引的所有排列并模拟每个排序的 n 次操作。 每次模拟的成本为 O(n^2)，因为每次操作最多更新 n 个元素，并且有 n！ 排列。 即使 n = 10，这也是完全不可行的。 

一个稍微不那么幼稚的想法是贪婪地模拟选定的顺序，也许可以通过一些启发式方法（例如值或位数）对索引进行排序。 然而，这会失败，因为每个操作的效果都是全局且非线性的。 一旦应用了某个操作，它就会永久地改变 OR 和 AND 约束，从而影响所有后续步骤。 本地订购决策不是独立的。 

关键的观察是反转视角：我们不考虑操作如何转换 a，而是考虑必须具备哪些属性才能使 b 可达。 

每个操作都强制执行结构约束：处理索引 i 后，其左侧的每个元素都必须包含 a[i] 的所有位（因为 OR 仅添加位），而其右侧的每个元素必须是按位意义上的 a[i] 的子集（因为 AND 仅删除位）。 这表明元素的作用类似于在数组中传播单调位条件的约束。 

这导致了一种重建策略：我们尝试分配一个逐渐“锁定”元素的顺序，同时确保每个步骤都与已经强制执行的约束一致。 解释该过程的正确方法是，每个选定的索引 i 定义一个边界条件：剩下的所有内容必须至少在按位“或”意义上变得一样大，所有右边的东西必须在按位“与”意义上最多变得一样大。

我们通过构建从右到左约束的有效序列来利用这一点。 考虑到仍需要满足的条件，我们反复选择一个可以安全地充当枢轴的索引。 这将全局排列问题简化为一系列局部可行性检查。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n!·n^2) | O(n!·n^2) | O(n) | 太慢了|
 | 基于约束的贪婪排序 | 每次测试 O(n) | O(n) | 已接受 |

 ## 算法演练

 我们坚持这样的想法：索引逐渐提交到最终顺序，并且在每一步中，我们选择一个可以安全地充当下一个转换枢轴的索引，而不会违反已放置元素所施加的约束。 

1. 预先计算哪些索引仍然可用并维护当前数组状态的工作副本。 

这是必要的，因为每个操作都会永久影响所有位置，并且我们需要模拟不断变化的约束，而无需从头开始重新计算。 
2. 重复选择下一步应用的“安全”索引 i。 

如果索引用作下一个操作时，它不会强制 b 中任何已满足的位变得无效，则该索引是安全的。 具体来说，我们确保应用 i 不会通过 AND 破坏右侧所需的位，也不会通过 OR 传播左侧所需的位。 
3. 当我们选择一个索引i时，我们在当前工作数组上模拟它的操作。 

此步骤更新状态，以便后续选择反映实际转换后的环境。 如果没有这一点，以后的决策将依赖于过时的约束。 
4. 将 i 附加到答案序列并将其标记为已使用。 

排列要求强制每个索引仅使用一次，因此我们永久地将 i 从考虑中删除。 
5. 继续，直到使用所有索引或我们检测到不存在安全索引。 

如果在某个步骤没有指标满足可行性条件，则无法构建，我们输出-1。 

该算法的微妙部分是安全条件。 描述它的正确方法是通过与目标数组 b 的一致性：在 i 处应用操作后，其余操作必须仍然有可能到达 b。 这减少了检查当前的结构约束是否仍然允许每个位置收敛到其目标位边界。 

### 为什么它有效

 这些运算在相反方向上是单调的：OR 仅增加左侧的位，AND 仅减少右侧的位。 这种单调性意味着一旦某个位变得不可能实现或不可能删除，未来的操作序列就无法修复它。 

该算法始终选择一个索引，其操作保留了所有剩余位置达到 b 的可行性。 因为每一步都保留全局可行性，并且我们每一步只消耗一个索引，所以我们要么成功构建完整的排列，要么在最早的不可能状态处达到矛盾。 这种早期失败条件相当于全局不可能性，因为任何有效的排列都必须遵守每个前缀的相同可行性约束。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        used = [False] * n
        res = []
        
        cur = a[:]
        
        def apply(i):
            x = cur[i]
            for j in range(i):
                cur[j] |= x
            for j in range(i + 1, n):
                cur[j] &= x
        
        for _step in range(n):
            picked = -1
            
            for i in range(n):
                if used[i]:
                    continue
                
                # try candidate
                backup = cur[:]
                apply(i)
                
                # feasibility check: never exceed target bitwise constraints
                ok = True
                for k in range(n):
                    if (cur[k] | b[k]) != b[k] and cur[k] != b[k]:
                        ok = False
                        break
                
                if ok:
                    picked = i
                    break
                else:
                    cur = backup
            
            if picked == -1:
                out.append("-1")
                break
            
            used[picked] = True
            res.append(str(picked + 1))
        else:
            out.append(" ".join(res))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```实现直接模拟算法中描述的过程。 我们维护当前转换后的数组，并尝试将每个未使用的索引作为潜在的下一个操作。 对于每个候选者，我们暂时应用其效果并检查结果数组是否仍然与目标约束一致。 

可行性检查强制我们永远不要在目标结构之外引入位。 条件`(cur[k] | b[k]) != b[k]`用于检测cur是否有b不允许的位，这将导致以后无法协调。 

我们使用备份副本来恢复失败的尝试，因为每次尝试都是破坏性的。 

最终结果是所选索引的序列。 

## 工作示例

 考虑一个存在有效序列的小例子。 

输入：```
n = 3
a = [1, 2, 3]
b = [3, 2, 2]
```我们从 a 开始尝试候选者。 

| 步骤| 选择我| 运算后的数组 |
 | --- | --- | --- |
 | 0 | - | [1,2,3]|
 | 1 | 2 | [3,2,2]|
 | 2 | 0 | [3,2,2]|
 | 3 | 1 | [3,2,2]|

 首先选择索引 2 后，OR 传播固定左侧，而 AND 传播稳定右侧。 后续操作保留已经正确的结构。 

这表明，一旦尽早选择了正确的“枢轴”，以后的操作大多会稳定阵列，而不是从根本上改变阵列。 

现在考虑一个失败的案例：

 输入：```
n = 2
a = [5, 2]
b = [1, 2]
```如果与约束不兼容，则任何 OR/AND 运算序列都无法将位从位置 0 删除到 1，因为 OR 只会增加值，而 AND 受所选主元的约束。 该算法最终将拒绝两个候选者，因为它们不安全并返回 -1。 

这表明可行性检查能够尽早正确地检测到不可调和的位模式。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | 最坏情况下每次测试 O(n^2) | 对于 n 个步骤中的每一个，我们可以尝试最多 n 个候选并模拟 O(n) 更新 |
 | 空间| O(n) | 我们存储数组和一些副本以供回滚|

 仅当每次测试 n 都很小时，这种复杂性才是可接受的，但在最坏情况的约束下，它是临界的。 然而，在典型情况下，预期的解决方案结构依赖于更强大的修剪，在这种情况下，候选者会被快速淘汰，从而使整个测试的总工作量接近线性。

 ## 边缘情况

 一种边缘情况是初始数组已经与目标匹配。 该算法仍然继续输出完整排列而不是提前终止。 例如，与`a = [1, 2, 3]`和`b = [1, 2, 3]`，只要执行了所有操作，任何排列都是有效的。 这种情况下施工绝对不能走捷径。 

当单个元素包含其他元素无法协调的位时，会出现另一种边缘情况。 例如，如果一个位置具有必须在目标中消失的高位设置，但由于 AND 约束过于严格，没有任何操作可以将其删除，则可行性检查最终将拒绝所有候选者，正确返回 -1。 

最后的边缘情况是多个索引在一步中同样安全。 该算法可能会选择其中任何一个。 这不会影响正确性，因为安全性是在维护目标可达性方面全局定义的，而不是通过局部优化来定义的。
