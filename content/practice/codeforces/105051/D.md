 ## 解决方案
 ## 问题理解

 每个输入块都是一个具有固定尺寸的矩形$w_i \times h_i$。 对于任何一块砖块，您都可以将其“缩小”为一个新的矩形$a \times b$，只要两边都不增加，意思是$a \le w_i$和$b \le h_i$。 不允许进行其他转换，因此每个原始砖块只能生成一个可用的较小矩形。 

一个有效的金字塔是一堆精确的$k$砖块，其中$t$- 从顶部开始的第层必须是正方形大小$(2t-1) \times (2t-1)$。 所以第 1 层是$1 \times 1$，第 2 层是$3 \times 3$，第 3 层是$5 \times 5$， 等等。 每层都必须通过选择给定的砖块来支撑，并在必要时将其缩小以匹配所需的正方形尺寸。 

任务是计算最大可能高度$k$，意味着可以使用可用的砖块匹配的所需方形层的最大数量，每个砖块最多使用一次。 

这些限制迫使我们走向$O(n \log n)$或者$O(n)$解决方案。 和$n \le 10^5$，任何尝试砖块和层之间的所有分配或尝试通过二分搜索进行匹配的方法，如果超过粗略范围，就会太慢$10^8$运营。 基于排序或贪婪的策略是自然的候选者。 

一个微妙的问题是每块砖只能使用一次，并且收缩是不对称的：一块砖$(w, h)$可以产生任何$(a, b)$两个坐标都有界，但它不能“旋转”或在多层之间部分分割容量。 另一个边缘情况是，对于较高层来说足够大的块会自动适用于所有较小的层，因此将大块过度分配给小需求可能会阻碍较大层的可行性。 

例如，如果我们需要图层$1 \times 1$和$3 \times 3$，并且有一个$5 \times 5$砖和单个$3 \times 3$砖，分配$5 \times 5$砖到$1 \times 1$在本地是正确的，但可能会阻止唯一可行的分配$3 \times 3$如果没有其他砖块适合它。 

## 方法

 一个蛮力的想法是尝试将砖块分配给金字塔级别。 对于每个级别$t$，我们检查哪些砖块可以减少为$(2t-1) \times (2t-1)$，然后在所有级别中搜索匹配的作业。 这成为关卡和砖块之间的二分匹配问题，如果砖块能够满足关卡，则存在边缘。 最大匹配就能给出答案。 

这是正确的，但该图最多可达$10^5$一侧的节点并且可能$10^5$另一方面，最多$10^{10}$如果许多砖块很大，则在最坏的情况下会出现隐式边缘。 即使边缘是动态生成的，运行匹配或流程也太慢。 

关键的观察是单调性。 对层数的要求严格增加：层数$t+1$需要比层严格更大的正方形$t$。 同时，每块砖块都有一个“容量”，定义为它可以支撑多大的正方形，即$\min(w_i, h_i)$。 如果我们按照这个容量对砖块进行排序，我们本质上是在尝试将最小的所需层与最小的足够的砖块贪婪地匹配。 

这将问题转换为：给定所需值$1, 3, 5, \dots$和可用容量$c_i = \min(w_i, h_i)$，找到可以通过为每个需求分配至少为该值的不同容量来覆盖的需求的最长前缀。 这是排序数组上的标准贪婪匹配。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力匹配/流程|$O(n^3)$或者更糟|$O(n^2)$| 太慢了|
 | 贪心排序+匹配 |$O(n \log n)$|$O(n)$| 已接受 |

 ## 算法演练

 1. 转换每块砖块$(w_i, h_i)$转化为单一值$c_i = \min(w_i, h_i)$。 这代表砖块收缩后可以安全支撑的最大方形边长。 
2. 对所有容量进行排序$c_i$按非降序排列，因此我们可以首先匹配小需求。 
3. 初始化指针$i = 0$在砖块和柜台上$t = 1$，代表当前需要的正方形边长$2t - 1$。 
4. 当我们还剩下砖块时，我们可以满足当前的要求：

 1. 移动$i$向前直到我们找到一块砖块$c_i \ge 2t - 1$。 
2、如果不存在这样的砖块，则停止； 我们无法再建造更多的层。 
3. 将此砖块分配给关卡$t$并增加两者$i$和$t$。 
5、输出$t - 1$，这是可达到的最大高度。 

贪婪的选择是始终使用能够满足当前需求的最小可用砖块。 这为未来更大的需求保留了更大的砖块，而这些需求更难满足。 

### 为什么它有效

 在任何步骤中，我们都会匹配当前最小的未满足的要求$2t-1$具有能够满足它的最小可用容量。 如果我们使用比必要的更大的砖块，我们只会降低后续步骤的灵活性，因为所有未来的需求都会更大。 任何最佳分配都可以转换为遵守此顺序的分配，而不会减少匹配层的数量，只要在较早的层使用大于所需的块，而存在较小的可行块时，就可以交换分配。 

这种交换论证保证了贪婪匹配永远不会阻止最优策略可以实现的可行解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    caps = []
    for _ in range(n):
        w, h = map(int, input().split())
        caps.append(min(w, h))

    caps.sort()

    t = 1
    i = 0
    ans = 0

    while i < n:
        need = 2 * t - 1

        while i < n and caps[i] < need:
            i += 1

        if i == n:
            break

        ans += 1
        i += 1
        t += 1

    print(ans)

if __name__ == "__main__":
    solve()
```该解决方案将每个砖块压缩为单个可用值，这避免了直接处理二维约束。 排序确保我们始终首先考虑较弱的砖块。 内循环会跳过不可用的砖块，并且每个砖块最多被消耗一次，因此指针只会向前移动。 

一个常见的错误是尝试从最大的砖块向下进行匹配，这可能会在小层上浪费大量容量并降低可实现的总高度。 另一个是忘记每个砖块都使用一次，因此跨多个层重用容量是无效的。

 ## 边缘情况

 一种边缘情况是许多砖块对于早期需求来说太小。 对于输入：```
5
1 1
1 1
10 10
10 10
10 10
```要求是$1, 3, 5, \dots$。 该算法消耗了第一个$1 \times 1$，然后跳过下一个$1 \times 1$，并正确地为后面的层使用更大的砖块。 跳过循环确保我们不会错误地将小块分配给大需求。 

另一种情况是大砖块出现较早。 为了：```
3
10 10
3 3
1 1
```排序产生 [1, 3, 10]。 该算法使用 1 表示第 1 级，3 表示第 2 级，10 表示第 3 级。即使输入中首先出现一块大砖，排序也可以防止过早浪费它，从而保留了更高层的可行性。
