 ## 解决方案

 ## 问题理解

 每个朋友都与两种食物类型相关，并且每种食物类型的盘子数量有限。 当朋友被叫到时，他们会尝试从自己喜欢的两种类型中各吃一盘。 如果这两种类型中至少一种仍有库存，则该朋友安全离开并减少相应的食物数量。 如果此时两种类型都已为空，则朋友会变得危险并立即结束该过程。 

任务不是按照固定顺序进行贪婪模拟，而是判断是否存在朋友的某种排序，使得每个朋友都可以从他们的一对中至少得到一个盘子，如果存在，则输出这样的顺序。 

约束足够大，任何尝试所有朋友排列的解决方案都是不可能的。 甚至拥有多达 20 万好友$m!$或者任何类似阶乘的推理都是无关紧要的。 即使是关于朋友的二次策略也会太慢，因为$m^2$达到$4 \cdot 10^{10}$。 这推动我们走向线性或近线性图处理。 

当某种食品类型的初始库存为零时，就会出现微妙的边缘情况。 任何两种食物都从零开始的朋友在每次点菜时都必须立即失败，所以答案自然是不可能的。 另一个棘手的情况是，当多个朋友依赖一种容量很小的食物类型时。 如果我们过早地以错误的依赖方向消耗该资源，即使存在有效的全局排序，后来的朋友也可能会被阻止。 这正是天真的贪婪逐步或任意排序失败的情况。 

## 方法

 如果我们尝试天真地推理，我们可以想象模拟这个过程：重复选择当前可以提供服务的任何朋友，从他们可用的食物之一中吃掉一盘，并将其附加到答案中。 这类似于贪心调度问题。 正确的直觉是“只要有人现在能满意，我们就会处理他们”。 然而，这会失败，因为过早食用某种食物可能会减少未来的可用性，从而使一些剩下的朋友变得不可能。 

另一个蛮力的想法是尝试朋友的所有排列并检查可行性。 由于阶乘增长，这是立即不可行的。 

关键的观察结果是，每个朋友只需要在处理两个资源时至少有一个可用。 这可以重新构建为一个图形过程，其中只要至少一种事件食物类型仍然具有容量，每个节点（朋友）就“活着”。 当其边缘的两个端点都耗尽时，该节点就会死亡。 

我们可以反过来看。 我们可以模拟从最后删除“安全”朋友，而不是构建避免失败的订单。 如果在考虑所有其他食物类型后，他的两种食物类型中至少有一种仍有剩余容量，则该朋友可以安全地排在最后。 这表明我们应该反复删除在当前剩余容量的情况下保证生存的朋友，并在我们将其提交给订单时逐渐减少容量。 

这会导致图上的贪婪过程，其中边消耗顶点的容量。 正确的策略是始终选择仍然有效的朋友，当我们放置它们时，我们会以受控的方式降低其端点之一的可用性。 为了避免错误的选择，我们总是选择仍有剩余容量的端点。 

更结构化的观点是将食物类型视为具有能力的节点，将朋友视为边缘。 我们保持剩余容量的程度，并始终删除仍然可以满足的边缘。 当获取一条边时，如果可能的话，我们会减少其端点之一的容量。 如果两个端点都没有容量，则该过程是不可能的。 

这简化为具有可用边缘的堆栈或队列的贪婪构造。

 | ---| ---| ---| ---|
 | 蛮力排列 | O(米！) | O(米) | 太慢了 |
 | 贪婪+容量驱动移除| O(n + m) | O(n + m) | 已接受 |

 ## 算法演练

 我们将每个朋友建模为两种食物类型之间的边缘，并跟踪每种食物类型的剩余容量。 

1. 为每种食物类型建立邻接表，存储哪些朋友依赖它，并维护当前剩余容量$w_i$对于每种类型。 这使我们能够快速知道哪些边缘仍然是可以满足的。 
2. 计算一组初始“安全”朋友，即至少一种端点食物类型当前具有正容量的朋友。 这些是我们在任何步骤中都可以安全处理的唯一候选者。 
3. 维护候选好友的堆栈（或队列）。 最初推送所有未完全死亡的朋友（即，不是两个端点的容量都为零）。 
4. 反复从堆栈中弹出好友。 如果它的两种食物类型已经处于零容量，我们就无法处理它，所以我们跳过它。 
5. 否则，我们将该朋友分配到应答顺序。 我们尝试从一个盘子的端点之一消耗它。 如果两个端点仍然有正容量，我们可以任意选择，但稳定的选择是从任何有剩余容量的端点进行消费。 
6. 食用某种食物类型后，更新其剩余容量。 如果这导致连接到它的新朋友变得新“安全”或新相关，请将他们推入堆栈。 
7. 继续，直到处理完所有朋友或直到不存在有效的移动。 如果我们处理了所有朋友，则输出构建的订单； 否则输出失败。 

### 为什么它有效

 核心不变量是，只有当朋友的至少一个端点仍然具有可用容量时，我们才会将其放入排序中。 这确保了我们永远不会在两种资源都耗尽的时候分配一个朋友。 由于每次消耗都会将容量减少一倍，并且我们仅在提交朋友时减少容量，因此我们保留了所有剩余未处理边的可行性。 

该过程在动态收缩的资源图上有效地构建了有效的反向拓扑排序。 任何失败状态都完全对应于一种配置，其中每个剩余的朋友仅与耗尽的食物类型有关，这意味着不存在有效的订购。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    w = list(map(int, input().split()))

    g = [[] for _ in range(n)]
    edges = []

    for i in range(m):
        x, y = map(int, input().split())
        x -= 1
        y -= 1
        edges.append((x, y))
        g[x].append(i)
        g[y].append(i)

    used = [False] * m
    order = []

    # current availability
    import collections
    q = collections.deque()

    # initially push all edges
    for i in range(m):
        q.append(i)

    while q:
        i = q.pop()
        if used[i]:
            continue

        x, y = edges[i]

        if w[x] == 0 and w[y] == 0:
            continue

        used[i] = True
        order.append(i + 1)

        # consume from a valid endpoint
        if w[x] > 0:
            w[x] -= 1
        else:
            w[y] -= 1

        # push neighbors again since state changed
        for j in g[x]:
            if not used[j]:
                q.append(j)
        for j in g[y]:
            if not used[j]:
                q.append(j)

    if len(order) != m:
        print("NO")
    else:
        print("YES")
        print(*order[::-1])

if __name__ == "__main__":
    solve()
```该实现保留了一堆候选好友并反复尝试分配它们。 关键的微妙之处在于颠倒最终顺序，因为我们正在有效地构建有效的移除序列，而不是直接的向前调度。 

邻接列表确保每当食物类型的容量发生变化时，所有受影响的朋友都会被重新考虑。 访问过的数组可以防止重复处理已经固定的朋友。 

一个常见的错误是任意选择端点而不检查可用性。 条件`if w[x] > 0`确保我们永远不会从疲惫的类型中消费。

 ## 边缘情况

 当朋友的两种食物类型都从零开始时，就会发生直接失败的情况。 该算法立即丢弃这样的朋友，因为`w[x] == 0 and w[y] == 0`，如果处理结束时存在任何这样的朋友，则总计数将不匹配`m`，产生NO。 

当许多朋友共享单一低容量食物类型时，就会出现瓶颈情况。 该算法仅在可用时消耗某种食物类型，一旦其达到零，则仅当其他端点仍有容量时才会处理剩余的边缘。 如果两个端点都已耗尽，则这些边将被正确拒绝，从而防止无效排序。 

每个朋友重复共享两个端点的密集图情况仍然有效，因为每条边最多处理一次，并且邻接推送仅通过现有连接发生，从而保留了线性复杂性。
