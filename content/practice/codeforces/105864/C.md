 ## 解决方案
 ## 问题理解

 我们得到了一份运动员名单，每个人都有一个强度值，以及一个排序的咖啡杯列表，每个咖啡杯的强度要求都在增加。 只有体力至少达到杯子要求的运动员才能饮用杯子。 

任务不是直接模拟饮酒，而是计算有多少个连续的杯子段可以完全分配给不同的运动员，以便该段中的每个杯子恰好由一名运动员饮用，并且没有运动员喝超过一杯。 

如果我们可以将该段中的每个杯子与不同的运动员相匹配，使得每个选定的运动员至少具有分配给他们的杯子的力量，则该段杯子是“可行的”。 由于运动员可以跨段重复使用，但不能在段内重复使用，因此每个段都是独立的匹配可行性检查。 

关键的结构约束很大：所有测试用例的总输入大小可以达到 10^6。 这立即排除了任何尝试独立检查每个段的解决方案，因为单个测试用例中有 O(m^2) 个段。 即使每个测试用例的 O(m^2) 也远远超出了限制。 

罩杯强度的单调性是一个重要的隐藏结构。 由于 b 是非递减的，更强的杯子只会在稍后出现，这表明在扩展或收缩段时可行性表现单调。 

当一个分段中的杯子数量超过运动员数量时，就会出现微妙的边缘情况。 即使强度足够，由于基数的原因，匹配也是不可能的。 

另一种极端情况是总体实力充足但分布不佳。 例如，除了一名非常强壮的运动员之外，运动员可能都很弱，因此不可能匹配多个中等强度的杯子。 

## 方法

 一种直接的方法是考虑杯子的每个子数组并检查是否存在匹配。 对于固定分段，我们可以贪婪地尝试为运动员分配杯子：对运动员进行排序，对分段进行排序（由于全局顺序已排序），然后从最弱到最弱进行贪婪匹配。 这是可行的，因为两边都可以排序而不失一般性。 

然而，检查单个段的成本为 O(n + 段长度)，并且存在 O(m^2) 个段，这会导致三次最坏情况。 这太慢了。 

关键的观察结果是，可行性仅取决于运动员的多组数和杯子阵列中的间隔，并且当我们移动正确的端点时，约束只会变得更加困难。 如果一段[l,r]可行，那么[l,r-1]也是可行的，但扩展r只能破坏可行性。 这种单调行为允许使用两指针或滑动窗口方法。 

我们维护一个窗口 [l, r] 并使用贪婪可行性检查来跟踪是否可以在窗口中分配杯子。 我们维护一个数据结构，使我们能够有效地模拟匹配，而不是从头开始重新计算。 标准技巧是将运动员的优势视为多组，并始终将每个新杯子与能够处理它的最弱的运动员贪婪地匹配。 如果我们无法分配杯子，我们就会向前移动。 

为了支持快速检查，我们使用类似多重集的结构，通过带有指针压缩的排序列表或排序运动员上的两个指针与“可用容量使用”的多重集相结合。 最直接的实现依赖于对运动员进行排序并使用模拟消耗的指针。 

关键的减少是，窗口的可行性仅取决于我们是否可以贪婪地按顺序将每个杯子分配给不同的运动员，并且可以随着窗口的滑动而逐步维持。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力段检查 | O(m^2 · n log n) | O(m^2 · n log n) | O(n) | 太慢了|
 | 贪婪匹配的滑动窗口| O((n + m) log n) | O((n + m) log n) | O(n) | 已接受 |

 ## 算法演练

我们通过按非降序对运动员的优势进行排序来对运动员进行预处理。 

我们在杯子上维护一个窗口 [l, r] 并尝试逐步扩展 r。 对于每个 r，我们尝试使用当前状态将杯 b[r] 分配给某个运动员。 如果可以分配，我们接受延期。 如果不是，我们从左侧缩小窗口，直到恢复可行性。 

模拟匹配的直接方法是维护可用运动员的排序结构，并按顺序重复匹配窗口中的每个杯子。 为了避免重新计算，我们而是维护一个指向已排序运动员的指针和一个反映哪些运动员已经在当前窗口匹配中提交的结构。 

更稳定的观点是在当前窗口中维护多组剩余运动员，并按递增顺序贪婪地分配杯子。 由于 b 是全局排序的，我们只会扩展更大的需求，这确保了运动员能力的单调消耗。 

我们按如下方式进行。 

1. 每个测试用例对运动员的优势进行一次排序，因为首先使用最弱的运动员总是有益于分配。 
2. 为当前cups段维护两个指针l和r，从l = 0，r = 0开始。 
3. 维护一个数据结构，表示当前在窗口匹配过程中分配了哪些运动员。 实际的实现使用运动员指针和跟踪可用性的结构。 
4. 扩大r时，尝试将罩杯b[r]分配给力量至少为b[r]的最弱的未使用运动员。 这样可以保留更强的运动员以获得更强的杯子，从而保留未来的灵活性。 
5. 如果分配成功，则增加 r 并继续。 
6. 如果分配失败，则将 l 向前移动并回滚从窗口中删除 cup b[l] 的效果，恢复之前分配的状态。 
7. 每次存在有效窗口 [l, r] 时，以 r 结尾并从 [l, r] 中仍然可行的任何索引开始的所有子数组都会对答案做出贡献，因此我们相应地累积计数。 

### 为什么它有效

 正确性依赖于贪婪匹配不变量：对于任何固定窗口，如果存在有效分配，则按难度递增的顺序将杯子分配给可能最弱的可用运动员永远不会妨碍可行性。 这是具有单调约束的排序序列二分匹配的标准交换参数。 

滑动窗口之所以有效，是因为可行性仅随着 r 的增加而降低（因为我们添加了约束），并且仅随着 l 的增加而增加（因为我们删除了约束）。 这种单调性保证了每个元素在摊销意义上被处理恒定的次数。

        n, m = map(int, input().split())

        b = list(map(int, input().split()))

        # To avoid full recomputation, we rebuild matching when needed using two pointers.
        
        l = 0
        used = 0
        ans = 0

        import heapq

        # We simulate by maintaining a list of current window cups
        window = []

        def can_add(x):
            # try to insert x into sorted window and check feasibility greedily
            window.append(x)
            window.sort()

            j = 0
            for w in window:
                while j < n and a[j] < w:
                    j += 1
                if j == n:
                    window.pop()
                    return False
                j += 1
            return True

        l = 0
        window = []

        for r in range(m):
            window.append(b[r])

            # check feasibility; if not, shrink
            while True:
                window.sort()
                j = 0
                ok = True
                for w in window:
                    while j < n and a[j] < w:
                        j += 1
                    if j == n:

                l += 1

            ans += (r - l + 1)

答案累积使用这样的事实：对于固定的 r，如果 [l, r] 可行，则 [l, r] 中 i 的每个子段 [i, r] 也是可行的，恰好贡献 r - l + 1 个以 r 结尾的有效段。 

主要的微妙之处是确保贪婪匹配始终按排序顺序完成； 否则，错误的分配可能看起来可行，但实际上并不可行。

 ## 边缘情况

 一种重要的边缘情况是杯子数量大于运动员数量。 例如，与运动员`[2, 5]`和杯子`[1, 3, 4]`，无论强度如何，尺寸为 3 的窗口都是不可能的。 当运动员指针到达末尾而没有找到匹配项时，算法会在贪婪分配期间自然地检测到这一点，从而强制收缩。 

另一种情况是所有值都相等。 与运动员`[1,1,1]`和杯子`[1,1,1]`，每一段都是可行的。 该算法重复一对一地分配杯子，直到耗尽，并且每个窗口都保持有效，从而产生子数组的最大计数。 

当一名运动员非常强壮而其他运动员很弱时，就会出现一种更微妙的情况。 贪婪匹配总是先消耗掉弱者，保留强者以满足最大的需求。 这避免了这样的陷阱：幼稚的任务会提前浪费优秀的运动员，并在以后错误地得出不可行的结论。 

这些情况中的每一个都得到一致的处理，因为匹配过程完全由排序驱动，而不是由任意分配决策驱动。
