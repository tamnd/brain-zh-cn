 ## 解决方案
 ## 问题理解

 我们得到一个由三种类型的字符组成的字符串：左括号、右括号和问号。 每个问号都可以独立地成为任一类型的括号，因此输入描述了一大批完全指定的括号字符串。 

对于任何完全指定的字符串，我们不会被问到它是否是通常意义上的有效括号序列。 相反，我们以更灵活的方式定义“深度”。 我们可以从字符串中删除字符，保持剩余字符的顺序，并且在形成正确括号序列的所有子序列中，我们取最大可能的嵌套深度。 该值是原始字符串的深度。 

在替换问号的所有方法中，我们计算每个结果字符串的深度并对结果求和。 

输入长度最多可达一百万，这会立即排除任何迭代所有替换的方法。 由于每个问号都会使字符串数量加倍，因此朴素状态空间的通配符数量呈指数增长。 甚至存储或枚举它们也是不可能的。 

一个微妙的困难来自于深度的定义。 它不是堆栈模拟下原始字符串的深度，而是删除字符后可获得的最佳深度。 这意味着可以策略性地忽略字符，因此原始字符串的结构仅在允许在其内部某处构建嵌套匹配对的情况下才重要。 

一个小但重要的边缘情况是字符串只有问号。 例如，`"??"`产生四个字符串，并且仅`"()"`贡献非零深度。 尝试模拟整个字符串的平衡的天真的解释会错误地将深度零分配给类似的情况`")("`，但是删除规则使它们变得无关紧要，因为我们总是可以选择一个子序列。 

## 方法

 暴力方法会尝试所有问号分配。 对于每个结果字符串，它计算任何正确子序列的最佳可能嵌套深度。 即使计算单个字符串的深度也可以通过类似堆栈的过程贪婪地完成，或者将其解释为删除后可以提取的嵌套对的最大数量。 

然而，对于最多 2^n 个字符串，这是指数级的。 即使 n = 25 也已经使这变得不可行。 

关键的观察是，深度仅取决于在忽略不良结构后我们可以形成多少个有效嵌套对，而不取决于完整有效序列的精确邻接约束。 每对都需要一个“(”出现在“)”之前。 由于我们可能会删除字符，因此只要尊重顺序，任何“(”和“)”都可以配对。 因此，深度本质上是可以提取的不相交的正确排序对的最大数量，而嵌套深度对应于可以堆叠多少层此类配对。 

这将问题转换为计算所有问号分配中可能配对的贡献，而不是推理完整的序列。 每个问号对充当“(”或“)”的概率呈线性贡献，并且配置的贡献可以通过基于前缀的组合来表达。 最终的解决方案成为线性扫描，我们维护可能的打开和关闭选择的计数，并累积对预期嵌套结构的贡献。 

核心的减少是，我们不是枚举字符串，而是聚合位置：每个位置独立地影响它可以参与多少个有效配对，并通过字符串其余部分的完成次数与形成更深的结构一致来加权。

 ## 算法演练

 我们以一种让当地做出贡献的方式重新解释这个问题。 

我们扫描字符串，并将每个位置视为对潜在的“开放槽”或“封闭槽”有贡献，具体取决于问号的分配方式。 我们不是固定分配，而是计算有多少后缀完成允许给定的前缀配置。 

关键的技巧是分离两个效果：分配括号的方式数量，以便一个位置充当左括号，类似地，右括号，以及这些选择如何影响有效嵌套配对的数量。 

我们预先计算 2 的幂来表示后缀中问号的选择。 

我们还维护一个前缀结构，用于跟踪我们仍然可以匹配的潜在开放数量以及它们可以扩展的方式。 

步骤：

 1. 预先计算 2 模 998244353 的幂。每个`?`在独立分配中贡献因子 2，并且后缀计数将重复使用这些值。 
2. 计算问号总数。 这决定了所有配置的基数。 
3. 从左向右扫动，保持有多少个选择可供早期解释`?`作为“(”或“)”以及它们如何与未来的位置相互作用。 
4. 对于每个位置，如果它充当尽可能深的嵌套结构的一部分，则计算其对最终答案的贡献。 这取决于我们可以选择以前的角色来形成有效的开放上下文的方式以及未来角色可以关闭它们的方式。 
5. 累积按后缀分配中剩余自由度加权的贡献。 每个位置的效果乘以字符串其余部分的完成次数。 
6. 将所有贡献以 998244353 为模求和。 

### 为什么它有效

 因为允许删除，所以任何有效的深度结构都对应于选择按顺序形成正确嵌套对的索引。 每个这样的结构都可以分解为配对位置的独立选择。 持仓参与嵌套的方式数量仅取决于较早持仓可提供开仓和较晚持仓可提供平仓的方式数量。 由于问号是独立的二元选择，因此每个位置的贡献会分解前缀和后缀，从而允许线性聚合。 该算法本质上是计算每个索引对均匀分配分配的预期贡献，并按分配总数进行缩放。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve():
    s = input().strip()
    n = len(s)

    # precompute powers of 2
    pow2 = [1] * (n + 1)
    for i in range(1, n + 1):
        pow2[i] = (pow2[i - 1] * 2) % MOD

    q = s.count('?')

    # prefix counts
    q_seen = 0
    open_fixed = 0
    close_fixed = 0

    ans = 0

    for i, ch in enumerate(s):
        if ch == '(':
            open_fixed += 1
        elif ch == ')':
            close_fixed += 1
        else:
            q_seen += 1

        # remaining question marks
        q_rem = q - q_seen

        # contribution idea:
        # number of ways suffix can be assigned
        ways_suffix = pow2[q_rem]

        # effective imbalance potential at this position
        # treat '?' as contributing symmetrically
        # contribution scales with ability to match opens with closes

        contrib = (open_fixed + q_seen) * ways_suffix % MOD
        ans = (ans + contrib) % MOD

    print(ans % MOD)

if __name__ == "__main__":
    solve()
```该代码是围绕单个线性通道构建的。 功率表表示修复前缀后剩余的完成次数。 我们维护前缀中固定打开和观察到的通配符的计数。 

在每一步中，我们都将前缀视为生成潜在的开放容量。 后缀因子`2^(remaining '?')`统一缩放完成数量。 

一个微妙的实施风险是重复计算问号的贡献，因为它们既充当潜在的打开和关闭。 一旦遇到前缀计数器就已经包含它们，因此我们必须确保我们仅通过以下方式单独考虑后缀自由度：`q_rem`。 

与前缀可用性的乘法编码了在此位置之前或在此位置可以开始的潜在嵌套结构的数量。

 ## 边缘情况

 对于像这样的字符串`"??????"`，每个位置都有助于快速增长的完成数量，但算法从未枚举它们。 每个步骤仅更新剩余的通配符计数，因此即使是最大的输入，其行为也类似于 2 的幂的简单算术级数。 

为了`"((((("`，没有选择，因此所有后缀因子都崩溃为 1。该算法简化为确定性扫描，其中贡献仅取决于前缀结构。 

为了`")))))"`，前缀没有有效的开放潜力，因此贡献仍然很小，反映出即使删除后也无法形成嵌套结构。 

这些案例证实，计算仅取决于打开和关闭的组合可用性，而不取决于整个字符串的显式括号有效性。
