 ## 解决方案

 ## 问题理解

 我们有一排糖果，每个糖果的大小都是正数，还有两个玩家从两端吃掉它们。 Alice 总是从左侧消费，Bob 从右侧消费。 他们交替轮流，每一轮都包括从各自的一侧吃一个或多个连续的糖果。 

关键规则是，玩家在自己的回合中必须吃掉足够的糖果，以便他们消耗的总大小严格超过对手在上一回合中吃掉的糖果。 爱丽丝首先开始，并被迫在她的第一步中只吃一颗糖果。 此后，双方玩家总是尝试最小限度地超过对手之前的步数总和。 

游戏继续进行，直到所有糖果都被消耗掉，我们必须报告发生了多少轮以及每个玩家吃掉的糖果总量。 

这些约束允许最多 5000 个测试用例，总共总共 200000 颗糖果。 这意味着任何处理每种糖果恒定次数的解决方案就足够了。 如果每个测试用例的二次模拟重复地重新扫描已处理的段，那么在最坏的情况下会太慢。 该过程的结构建议采用两指针模拟，其中每个糖果都会被消耗一次。 

当一名玩家所需的目标超过剩余目标时，就会出现微妙的边缘情况。 在这种情况下，玩家只需吃掉所有剩余的糖果，该过程就会立即结束。 另一个棘手的情况是，当许多小糖果累积起来刚刚超过之前的总和时，这可能会迫使每回合多次指针前进。 任何错误地重置指针或从头开始重新计算总和的解决方案都可能在交替长序列上失败。 

## 方法

 直接模拟遵循字面上的规则：在每一回合中，我们从当前的左指针或右指针开始扫描并累积糖果值，直到总和超过前一个对手的总和。 每回合结束后，我们都会交换玩家并继续。 这是正确的，因为它准确地反映了游戏定义。 

然而，重新计算总和或重新扫描段的简单实现会导致每个测试用例重复出现 O(n²) 行为的风险。 在最坏的情况下，就像所有的情况一样，每一回合只会前进一步，重复扫描会不必要地重新访问许多元素。 

关键的观察结果是，每个糖果都被消耗一次，并且指针仅向内移动。 因此，我们维护两个指针并增量累加总和，而无需重新访问元素。 每一步都会延长当前玩家的总和，直到满足条件。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 每回合重新扫描蛮力 | 每次测试 O(n²) | O(1) | O(1) | 太慢了|
 | 两指针增量模拟| 每次测试 O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们使用两个指针（一个在左端，一个在右端）以及每个玩家的运行总数来模拟游戏。 

1. 初始化指针`l = 0`,`r = n - 1`。 放`alice_sum = 0`,`bob_sum = 0`， 和`prev = 0`跟踪前一步的消耗总和。 Alice 首先开始，所以我们也将回合数初始化为 0。 
2. 在爱丽丝的第一步中，她必须从左边恰好吃掉一颗糖果。 我们添加`a[l]`到她的总数，增量`l`， 放`prev`到该值，并增加移动计数。 这是一个强制规则，并且从一开始就打破了对称性。 
3. 切换到鲍勃。 轮到鲍勃时，我们从右侧累积，反复取`a[r]`并减少`r`直到鲍勃当前的回合总和严格大于`prev`。 
4.一旦鲍勃超过`prev`，我们更新`prev`到鲍勃的回合总和，增加移动计数，然后切换回爱丽丝。 
5. 在爱丽丝的一般回合中，我们再次从左边开始累加，添加糖果，直到总和超过`prev`，然后更新 Alice 的总数和`prev`。 
6. 重复步骤3-5，直到吃完所有糖果。 如果在任何时候由于没有剩余糖果而无法满足所需条件，则当前玩家拿走所有剩余糖果，并且该过程立即结束。 

### 为什么它有效

 关键的不变量是，每个糖果索引都被访问一次，并按照指针移动指定的顺序永久分配给 Alice 或 Bob。 每回合严格增加一侧的总消耗段，并且停止条件确保每次移动在单调累积下是最小的。 由于两个指针仅向内移动而从不反向，因此不会重新考虑任何元素，并且模拟忠实地重建了游戏状态，无需多余的工作。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        l, r = 0, n - 1
        moves = 0
        alice = 0
        bob = 0
        prev = 0

        turn_alice = True

        while l <= r:
            s = 0

            if turn_alice:
                if l == 0:
                    s = a[l]
                    l += 1
                else:
                    while l <= r and s <= prev:
                        s += a[l]
                        l += 1
                alice += s
            else:
                while l <= r and s <= prev:
                    s += a[r]
                    r -= 1
                bob += s

            if s == 0:
                break

            prev = s
            moves += 1
            turn_alice = not turn_alice

        out.append(f"{moves} {alice} {bob}")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该解决方案维护两个指针并且仅向内扩展它们。 交替标志跟踪轮到谁了，而`prev`存储最后一步的总数，以便下一个玩家知道所需的阈值。 每个循环至少消耗一颗糖果，保证终止。 

一个常见的实施陷阱是单独错误地处理 Alice 的第一个强制移动，然后意外地跳过或重复计算第一段。 另一个是忘记重置运行总和`s`在每一轮上，这会错误地跨轮累积并打破严格的比较条件。

 ## 边缘情况

 单个糖果输入会立即被爱丽丝强制的第一步处理，因为她完全消耗了它，并且循环随着两个指针交叉而终止。 所有相等值的序列迫使算法以最小的增长交替几乎每一步，测试“严格大于先前”条件是否正确实现。 增加的序列给鲍勃后来的移动带来压力，其中右侧累积可能需要多次选择才能超过爱丽丝不断增长的总数，从而确认指针移动和总和重置不会跨回合泄漏。
