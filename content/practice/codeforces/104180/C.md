 ## 解决方案
 ## 问题理解

 我们有两个整数集合。 一个代表朋友要求的布朗尼蛋糕尺寸，另一个代表可用的烘焙罐，每个罐子恰好生产一个固定尺寸的布朗尼蛋糕。 如果分配给朋友的布朗尼蛋糕的尺寸严格大于他们要求的尺寸，朋友就会感到满意。 每个罐子最多可以使用一次，每个朋友最多可以收到一个罐子。 

任务是以最大化满意朋友数量的方式将罐子与朋友匹配。 

这里的关键结构是两个数组之间的一对一匹配问题，对可行性有严格的不等式约束，并以最大化成功匹配的数量为全局目标。 

每个数组中的元素最多为 200,000 个。 尝试所有配对或贪婪地检查每个朋友与所有罐子的二次解决方案在最坏的情况下将执行大约 400 亿次比较，这远远超出了 2 秒的限制。 这立即表明任何可行的解决方案都必须至多为 O(n log n) 或 O(n)。 

一些边缘情况很重要：

 如果所有罐子都太小，例如朋友要求`[10, 20, 30]`罐头是`[1, 2, 3]`，答案为零。 任何在不检查严格不等式的情况下将最小到最小配对的贪婪算法仍然会在此处正确失败，但反向不等式错误通常会导致错误的计数。 

如果罐头明显大于请求，例如请求`[1, 1, 1]`和罐头`[100, 101, 102]`，每个朋友都应该满意。 如果不仔细协调匹配，有缺陷的解决方案可能会以非最佳顺序在已经可以满足的小请求上浪费大罐子。 

当存在重复项时，例如请求，就会出现微妙的失败情况`[5, 5, 5]`和罐头`[6, 6]`。 正确答案是 2。始终将其看到的第一个兼容罐配对的简单方法可能会意外地重用未正确将罐标记为已消耗的逻辑，从而导致计数过多。 

## 方法

 一个蛮力的想法是尝试递归地或通过二分匹配将罐子分配给朋友。 我们可以尝试朋友和未使用的罐子之间的每一次配对，选择是分配还是跳过。 这形成了一个二分匹配搜索空间，每个选择都有分支。 即使我们修剪无效匹配，在大多数罐足够大的最坏情况下，有效部分匹配的数量也会组合增长。 对于 200,000 个元素，这是完全不可行的。 

更结构化的观点是对两个数组进行排序。 分类后，我们可以尝试总是首先使用能够满足要求最低的朋友的最小罐头来满足他们。 这是一个关键的观察：如果我们将一个大的锡分配给一个小的需求，而一个较小的锡可以工作，我们可能会降低未来的灵活性，而没有任何好处。 正确的策略是始终使用仍然可用的尽可能最小的锡，以最大程度地减少浪费的容量。 

这会导致排序数组上的贪婪匹配过程。 我们按升序扫描请求，并在罐上维护一个指针，不断前进，直到找到严格超出当前请求的罐。 找到后，我们匹配两个指针并将其向前移动。 否则，我们将停止该请求并继续。 

这将问题简化为对排序数组的两指针扫描。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 |---|---|---|---|
 | 蛮力 | O(N·M) 或指数 | O(N + M) | 太慢了|
 | 最优贪心 + 排序 | O(N log N + M log M) | O(N log N + M log M) | O(1) 额外（忽略排序） | 已接受 |

 ## 算法演练

 1. 对request数组和tin数组进行非降序排序。 这确保我们始终先处理较简单的需求，然后再处理较难的需求，从而防止在小请求上浪费大罐头。 

2. 初始化两个指针：一个用于请求，一个用于罐，都从索引零开始。 还要维护一个成功匹配的计数器。 

3. 对于当前请求，向前移动tin指针，直到找到第一个大小严格大于请求的tin。 每个跳过的罐都太小，无法满足此请求或任何较早的请求，因为请求已排序。 

4. 如果找到这样的罐，则将其分配给当前请求，递增匹配计数器，并使两个指针前进。 这确保每个罐子最多使用一次。 

5. 如果不存在合适的tin，则仅向前移动请求指针。 任何剩余的锡都无法满足这一要求。 

6. 继续，直到用尽任一列表。 

重要的细节是锡指针永远不会向后移动。 一旦罐子对于给定的请求来说太小，那么对于任何以后的请求来说它也会太小，因为请求只会增加。 

### 为什么它有效

 正确性依赖于排序后的单调可行性结构。 当两个数组都已排序时，将最小的可行锡与最小的未满足请求进行匹配始终是安全的，因为对此请求使用更大锡的任何替代分配都无法提高以后的匹配数量。 大罐子更灵活，因此保留它们以满足更大的要求不会降低最佳性。 这种交换论证确保任何最优解决方案都可以转化为遵循这种贪婪配对的解决方案，而不会减少满意朋友的数量。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    req = list(map(int, input().split()))
    tins = list(map(int, input().split()))
    
    req.sort()
    tins.sort()
    
    i = j = 0
    ans = 0
    
    while i < n and j < m:
        while j < m and tins[j] <= req[i]:
            j += 1
        if j < m:
            ans += 1
            i += 1
            j += 1
        else:
            break
    
    print(ans)

if __name__ == "__main__":
    solve()
```解决方案首先对两个数组进行排序，以便我们可以安全地从小到大进行处理。 两个指针`i`和`j`分别跟踪我们在请求和罐中的位置。 

内循环前进`j`直到我们找到一个严格大于`req[i]`或耗尽所有罐头。 严格的不平等很重要； 使用`<=`确保我们不会错误地匹配相同尺寸的罐子。 

一旦找到有效的tin，我们就将其视为成功的分配，并推进两个指针，消耗请求和tin。 

如果没有锡可以满足当前请求，则循环结束并打印答案。 

一个常见的实现错误是在匹配发生时忘记前进请求指针，这会错误地多次重复使用同一请求。 另一种方法是使用单遍而不排序，这打破了贪婪结构。

```排序：

 | 我（要求）| j（锡）| 请求[i] | 罐头[j] | 行动| 比赛|

 ## 边缘情况

 一个关键的边缘情况是，许多罐头对于早期请求来说太小，但如果我们正确跳过，仍然可以满足后来的请求。 例如，请求`[5, 6]`和罐头`[4, 7]`。 该算法首先丢弃`4`对于请求`5`，然后正确使用`7`对于请求`6`，实现一场比赛。 尝试独立匹配每个请求而不正确推进锡指针的贪婪策略将重用`4`或错误地得出失败的结论。 

另一种情况是罐头充足，但只有少数罐头足够大。 对于请求`[1, 2, 3, 4]`和罐头`[2, 2, 2, 10]`，该算法确保为可以使用它的最大请求保留单个大罐，而较小的罐则由较小的请求消耗，从而产生最佳利用率。
