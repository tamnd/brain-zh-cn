 ## 解决方案
 ## 问题理解

 这是一个交互问题。 存在未知的非负余额`n`， 和`n <= 10^18`。 我们无法阅读`n`直接地。 相反，我们可能会要求终端提取一些正金额`x`。 如果当前余额至少为`x`，终端回答`accepted`并减去`x`来自余额。 否则它会回答`rejected`并且余额保持不变。 

目标是使余额恰好为零，然后打印`finish`。 困难在于查询限制。 如果`q`是满足的最小整数`n <= 2^q`，那么终端最多允许`q + 10`撤回尝试。 自从`10^18 < 2^60`，一个盲目测试两个的所有幂的解决方案`2^59`下降到`1`使用 60 次尝试，这对于较小的值来说太多了`n`。 

没有包含普通输入`n`。 输入流由我们的程序打印命令后交互器的回复组成。 同样，输出是一系列交互式命令，例如`withdraw x`最后`finish`。 每个命令都必须立即刷新，以便交互器可以回答它。 

界限`10^18`很有用，因为它只给出 60 个相关的二进制位置。 因此，直接的二进制分解最多需要 60 次成功或拒绝的提款尝试。 挑战不是通常意义上的计算复杂性，而是将交互数量减少到最多`q + 10`， 在哪里`q`取决于未知数`n`。 

粗心的实施可能会因小额余额而失败。 例如，如果余额是`0`，正确的交互很简单`finish`， 因为`withdraw 1`将被拒绝并浪费可用的尝试之一。 为了平衡`1`,`withdraw 1`必须被接受，然后`finish`是正确的。 始终执行所有 60 个二次方查询的策略所浪费的资源远远超过允许的范围`q + 10 = 10`尝试。 

另一个微妙的情况是接受的查询会更改隐藏的余额。 假设余额为`10`我们要求`8`。 答案是`accepted`，但现在余额是`2`。 任何后来的推理都必须使用新的平衡，而不是原始的平衡。 最佳方法是经过精心设计的，可以容忍这种变化的值。 

## 方法

 基本的解决方案是直接处理二进制表示。 开始于`2^59`，询问该金额是否可以提取。 如果可以的话，从余额中减去它。 然后继续`2^58`,`2^57`，依此类推至`1`。 在每一步中，如果设置了相应的二进制位，则将其删除。 考虑完所有 60 种权力后，余额为零。 

这是有效的，因为每个数字最多`10^18`小于`2^60`，所以它的二进制表示仅包含来自`2^59`通过`2^0`。 问题在于交互的数量。 对于小额余额，例如`n = 1`，这种方法仍然会进行 60 次尝试，而终端只允许 10 次。官方竞赛教程正是将此描述为基线，然后通过二分搜索减少查询次数。 

关键的观察是，我们实际上不需要知道当前可以提取的确切的最大幂。 我们只需要一个足够大的幂来限制剩余余额，因为一旦我们有了这样的限制，处理所有较小的幂就足以完成。 

我们可以通过对 60 种可能的幂进行二分搜索来找到有用的起始指数。 对于查询`2^m`， 一个`accepted`答案证明当前余额至少为`2^m`， 所以`m`是一个有效的指数，我们将左边界移动到`m`。 一个`rejected`答案证明当前余额低于`2^m`， 所以`m`无法使用，我们将右边界移动到`m`。 

复杂的是接受的查询会减去金钱，因此在二分搜索期间余额会发生变化。 幸运的是，这并没有破坏该方法。 每个被记录为可接受的指数都对应于当时天平中实际存在的功率。 由于余额只会减少，所以那股力量也不会比原来的余额大。 于是最终的`l`永远不能超过原值的二进制对数`n`。 

当二分查找结束时`r = l + 1`，最后拒绝的边界告诉我们当前余额小于`2^r = 2^(l+1)`。 我们现在可以简单地尝试`2^l`,`2^(l-1)`, ...,`1`。 这些是小于以下数字的二进制表示形式中可能出现的所有幂`2^(l+1)`，因此它们足以完全耗尽帐户。 

由于只有 60 个可能的指数，因此最多有 6 个二分搜索查询`2^6 = 64 > 60`。 清理最多使用`l + 1`查询，以及`l <= q`， 在哪里`q`是原始余额的对数。 因此总数最多为`q + 7`，舒适地低于允许的`q + 10`。

 | 最佳| O(log n) 交互 | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 设置`l = 0`和`r = 60`。 该区间表示所有可能的二进制指数，从`0`通过`59`， 和`2^60`已知超出了所有可能的初始余额。 
2. 虽然`r - l > 1`， 选择`m = (l + r) // 2`并要求撤回`2^m`。 这是二分搜索步骤。 一个被接受的响应证明了指数`m`是可以实现的，所以设置`l = m`。 被拒绝的回复证明`2^m`对于当前余额来说太大，所以设置`r = m`。 
3. 如果交互者回答过`fail`，立即终止。 之后继续`fail`无法作出有效的判决。 
4. 二分查找后，处理指数`l`下降到`0`。 对于每个指数`i`, 要求撤回`2^i`。 如果答案是`accepted`，该功率将从剩余余额中删除。 如果是的话`rejected`，与该功率相对应的位不存在，因此无需更改任何内容。 
5. 打印`finish`经过所有权力`2^0`已被考虑。 此时余额必须为零。 

### 为什么它有效

 在二分查找结束时，`r = l + 1`，右边界对应于在某个时刻被拒绝的幂。 余额只有在被拒绝后才会减少，所以当前余额肯定小于`2^r = 2^(l+1)`。 每个小于的非负整数`2^(l+1)`可以仅使用幂来表示`2^l, 2^(l-1), ..., 1`。 清理阶段精确测试这些权力并撤回所有存在的权力，因此剩余余额变为零。 

查询限制由第二个不变量得出。 每当二分查找设置`l = m`，撤回`2^m`被接受，这意味着原始余额至少为`2^m`。 因此`m <= q`。 最后`l <= q`。 二分查找最多需要6次查询，清理最多需要`l + 1 <= q + 1`查询，总共最多`q + 7`，即下面的`q + 10`。 

## Python 解决方案

 该问题是交互式的，因此该程序旨在与官方交互器进行通信，而不是读取传统的测试用例。```python
import sys
input = sys.stdin.readline

def ask(x):
    print(f"withdraw {x}", flush=True)
    response = input().strip()

    if response == "accepted":
        return True
    if response == "rejected":
        return False

    # The only other possible response is "fail".
    sys.exit(0)

def main():
    l = 0
    r = 60

    # Find an exponent l such that the remaining balance is below 2^(l+1).
    while r - l > 1:
        m = (l + r) // 2

        if ask(1 << m):
            l = m
        else:
            r = m

    # The remaining balance is smaller than 2^(l+1).
    # Its binary representation therefore uses only these powers.
    for i in range(l, -1, -1):
        ask(1 << i)

    print("finish", flush=True)

if __name__ == "__main__":
    main()
```这`ask`函数只执行一次交互式提款。 使用`flush=True`至关重要，因为交互器在收到命令之前无法响应。 该函数为两个正常响应返回一个布尔值，并立即终止`fail`。 

二分搜索间隔使用指数而不是金额。`r = 60`是安全的，因为每个可能的初始余额都严格小于`2^60`。 循环条件`r - l > 1`留下连续的边界，所以在循环之后`r = l + 1`。 

表达式`1 << m`计算`2^m`直接地。 Python 整数具有任意精度，因此不存在溢出问题。 产生的最大价值是`2^59`，这也安全地在允许的提款金额之内`10^18`。 

清理循环故意向下进行。 如果我们先处理较小的幂，后来接受的较大幂仍可能留下包含较小位的余额，从而使推理变得不那么直接。 递减幂反映了普通的二进制分解，并保证每个剩余位都被处理一次。 

不会尝试跳过被拒绝的清理查询。 被拒绝的查询仍然算作一次交互，但这是必要的，因为我们需要确定该二进制位是否存在。 此类查询的数量已包含在`q + 7`边界。

## 测试用例

 因为这是一个交互问题，普通`run(input_string)`测试无法通过标准输入提供隐藏的平衡。 相反，有用的离线测试工具会模拟交互器。 以下代码对假终端使用相同的算法，检查最终余额是否为零，并验证查询限制。```python
import io
import sys

def run_simulation(initial_balance):
    balance = initial_balance
    attempts = 0
    commands = []

    def ask(x):
        nonlocal balance, attempts
        attempts += 1
        commands.append(f"withdraw {x}")

        if balance >= x:
            balance -= x
            return True
        return False

    l = 0
    r = 60

    while r - l > 1:
        m = (l + r) // 2

        if ask(1 << m):
            l = m
        else:
            r = m

    for i in range(l, -1, -1):
        ask(1 << i)

    commands.append("finish")

    q = 0
    while (1 << q) < initial_balance:
        q += 1

    assert balance == 0
    assert attempts <= q + 10

    return "\n".join(commands)

# Provided sample 1 corresponds to an initial balance of 1.
sample1 = run_simulation(1)
assert sample1.endswith("finish"), "sample 1"

# Provided sample 2 corresponds to an initial balance of 0.
sample2 = run_simulation(0)
assert sample2.endswith("finish"), "sample 2"

# Minimum-size balance.
assert run_simulation(0).endswith("finish"), "zero balance"

# Small boundary values around powers of two.
for n in [1, 2, 3, 4, 7, 8, 9, 15, 16, 17]:
    run_simulation(n)

# A large value close to 2^60.
assert run_simulation(10**18).endswith("finish"), "maximum allowed balance"

# Exact powers of two exercise the boundary between q values.
for n in [2**10, 2**20, 2**30, 2**40, 2**50, 2**59]:
    run_simulation(n)

# Values immediately below and above powers of two catch off-by-one errors.
for n in [2**10 - 1, 2**10, 2**10 + 1]:
    run_simulation(n)

## 边缘情况

 ### 零余额

 对于`n = 0`，确切的输入情况由拒绝每个积极撤回的交互器表示。 二分查找最终留下`l = 0`，并且清理要求`1`，被拒绝。 余额仍为零，因此`finish`是正确的。 该算法从不假设必须发生接受的查询。 

### 余额等于一

 对于`n = 1`，在二分查找过程中，每一个大于 1 的幂都会被拒绝。 由此产生的`l`为零，所以清理要求`1`。 该查询被接受并保留零。 这个案例特别有用，因为`q = 0`，仅允许最大允许的提款尝试次数`10`。 

### 2 的精确幂

 假设`n = 16`。 在二分查找过程中，查询`16`可能被接受，立即将余额减少到零。 指数`l = 4`记录了`2^4`可用。 稍后清理查询`16`,`8`,`4`,`2`， 和`1`是无害的，因为余额已经为零，并且全部被拒绝。 决赛`finish`是有效的。 这说明了为什么改变平衡的接受的二分搜索查询不会使算法失效。 

### 略低于 2 的幂

 假设`n = 15`。 查询`16`被拒绝，因此右边界变为对应于的指数`16`。 最终二分查找建立一个较低的指数，其下一次幂大于当前余额。 清理检查`8`,`4`,`2`， 和`1`，并且所有四位均被接受。 他们的总和是`15`，因此余额为零。 

### 略高于 2 的幂

 假设`n = 17`。 查询`16`可以接受，留下余额`1`。 二分查找记录指数`4`，并且清理随后检查电源是否从`16`。 由于余额仅`1`，较大的权力被拒绝并且`1`被接受。 最终余额为零。 这个案例说明了为什么清理工作必须一直持续到`2^0`，即使在大量力量已经被撤回之后。 

### 最大余额

 对于`n = 10^18`，我们有`q = 59`因为`2^59 <= 10^18 < 2^60`。 二分查找最多使用 6 个查询，并且`l`最多 59 个，因此清理最多使用 60 个以上查询。 在终端允许的情况下，总数最多为 66`q + 10 = 69`尝试。 因此，即使在最大可能的平衡下，该算法仍保持在限制内。
