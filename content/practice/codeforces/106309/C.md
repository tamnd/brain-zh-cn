 ## 解决方案
 ## 问题理解

 我们得到了有限数量的面团和几种可以烘烤的面包。 每种面包类型消耗固定数量的面团，对于调味面包，它也消耗有限数量的特定馅料。 每个面包都会产生固定的利润。 此外，还有一种额外的“原味”面包类型，仅使用面团且无限供应，而每种风味类型还受到可用馅料数量的限制。 

任务是决定每种类型要烤多少个面包，以便我们在不超过面团和每种馅料的可用量的情况下最大化总利润。 

困难在于，所有选择都通过单一共享资源（面团）进行交互，而每种口味类型也有自己独立的上限。 

限制很小：面团最多约为 1000 个，口味数量最多为 10 种。这立即排除了对每种口味的确切数量的任何指数搜索，因为即使是中等的分支因子也会爆炸。 纯粹贪婪的方法也是不安全的，因为每克馅料利润较高的面包可能会消耗过多的面团，并阻碍其他产生更高总利润的面包的组合。 

当按每个面包的利润进行贪婪排名具有误导性时，就会出现微妙的失败案例。 

例如，假设一种面包的利润很高，但消耗了太多的面团，而另一种面包的利润稍低，但面团的使用效率更高。 总是选择最高即时利润的贪婪策略可能会过早耗尽面团并错过更好的整体组合。 

另一个常见的陷阱是单独处理每个面包并尽可能多地处理每种类型。 这忽略了多吃一个任何类型的面包都会减少所有其他面包的全球容量。 

## 方法

 关键的观察结果是，风味类型的数量非常少，因此我们可以将它们视为我们采用每种类型的面包数量的决策层，而其他所有内容都将分解为剩余面团的一维优化。 

一个蛮力的想法是尝试我们采取的每种口味的面包数量的所有组合。 对于每种口味 i，我们可以选择 0 到 min(ai, n / ci) 个面包。 如果我们直接尝试这样做，状态的数量大约会变成每种口味最多 100 个选择的乘积，这是一个天文数字。 

拯救我们的结构是，一旦我们确定了每种类型的风味包子的数量，剩下的问题就微不足道了：所有剩余的面团都应该花在原味包子上。 这将整个问题简化为选择最多 10 个物品的有限背包选择，其中每个物品都有有限的多重性和线性成本。 

我们没有枚举所有组合，而是使用标准有界背包分解技巧独立优化每种口味。 每个风味包贡献固定的利润并消耗固定数量的面团，但我们不能超过ai / bi项目。 这将每种口味转换成一个有界的项目集，整个问题就变成了一个容量超过 n 的背包。 

原味包子只不过是又一个无限量供应的物品，自然就填补了DP的剩余容量。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 所有口味计数的完整枚举 | m 和 ai 的指数 | O(1) 额外 | 太慢了|
 | 分解物品上的有界背包| O(n·分解项之和) | O(n) | 已接受 |

 ## 算法演练

1. 我们将每个风味包解释为最多可以使用 ai / bi 次的物品。 这将“填充的资源约束”转换为我们可以获取每个项目的次数的简单上限。 
2. 我们使用最大计数的二进制分割将每种口味转换为多个 0-1 项。 这确保我们能够有效地处理大的限制，而无需迭代所有计数。 
3. 我们创建一个动态编程数组 dp，其中 dp[x] 表示使用 x 克面团可实现的最大利润。 我们将除 dp[0] = 0 之外的所有状态初始化为不可到达。 
4. 我们迭代所有转换的项目并按面团使用的降序更新 DP。 这可以防止在一次转换中多次重复使用同一项目，从而保留 0-1 行为的正确性。 
5、所有风味包子加工完成后，我们将原味包子作为最终的无界物品。 我们通过允许重复添加普通面包成本和利润的过渡来放松 dp，或者等效地，我们通过尝试所有剩余的面团使用并用普通面包填充它来预先计算最佳可能的组合。 
6. 考虑到任何剩余的面团总是可以转化为普通面包，最终的答案是所有 dp 状态的最大值。 

整个 DP 的不变量是 dp[x] 始终表示在处理前缀的物品后使用恰好 x 单位的面团可实现的最佳利润。 每次转变都保留了可行性，因为我们永远不会超过可用的风味面包的多样性，而且我们永远不会超过面团的总量。 

正确性取决于以下事实：每个有效的烘焙计划都对应于选择一组有界风味食品加上一些普通面包，并且这种表示完全由背包状态捕获。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m, c0, d0 = map(int, input().split())

    items = []

    for _ in range(m):
        a, b, c, d = map(int, input().split())
        max_cnt = min(a // b, n // c)
        k = 1
        while max_cnt > 0:
            take = min(k, max_cnt)
            items.append((take * c, take * d))
            max_cnt -= take
            k <<= 1

    dp = [-10**18] * (n + 1)
    dp[0] = 0

    for cost, val in items:
        for j in range(n, cost - 1, -1):
            if dp[j - cost] != -10**18:
                dp[j] = max(dp[j], dp[j - cost] + val)

    best = 0
    for used in range(n + 1):
        if dp[used] < 0:
            continue
        remaining = n - used
        best = max(best, dp[used] + (remaining // c0) * d0)

    print(best)

if __name__ == "__main__":
    solve()
```DP 数组按面团用量而不是面包数量进行索引，这使得不同面包类型之间的交互变得清晰。 每种风味类型都使用二进制分割进行扩展，这就是为什么即使一种风味可以多次使用，内部循环也能保持高效。 

最后一个循环至关重要：DP 仅考虑风味面包，因此我们明确地将剩余面团转换为普通面包。 忘记这一步是错误答案的常见原因，因为单独的 dp[n] 不一定是最佳的。 

## 工作示例

 ### 示例 1

 输入：```
10 2 2 1
7 3 2 100
12 3 1 10
```我们加工第一种口味，最多允许 2 个面包（因为 7/3 = 2）。 我们创建对应于 1 和 2 个小圆面包的物品。 对于第二种口味，我们同样分解它的极限。 

DP 之后，我们跟踪最佳状态：

 | 用过的面团| 最佳利润|
 | --- | --- |
 | 0 | 0 |
 | 2 | 100 | 100
 | 4 | 200 | 200
 | 5 | 210 | 210
 | 6 | 220 | 220
 | 8 | 230 | 230

 现在我们添加成本为 2、利润为 1 的普通面包：

 对于每个状态，剩余的面团都会被转换。 

例如，在已用 = 8、剩余 = 2 时，我们再增加 1 利润，得到 231。所有状态中最好的变为 241，匹配风味面包和原味面包的最佳组合。 

该跟踪表明，仅凭风味决策是不够的，剩余的转换才是最终实现最优性的因素。

| 用过的面团| 利润|

 已用 = 60，剩余 = 40 时可得到 1 个普通面包。 

总计变为 40 + 30 = 70 等效增益添加到基础结构中，但最佳解决方案更喜欢完全跳过调味面包并仅使用普通面包，产生 200 个。 

这表明，即使有风味面包，也不会自动带来好处。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(n × 总项目数) | 每个 DP 转换针对每个分解的物品扫描背包数组一次 |
 | 空间| O(n) | DP 阵列超过面团容量 |

 约束 n ≤ 1000 和 m ≤ 10 确保即使在二进制分割之后，项目数量仍然足够小，以使 DP 在限制内舒适地运行。

 ## 边缘情况

 一种极端情况是风味面包比普通面包差得多。 输入```
5 1 1 10
5 1 1 1
```导致 DP 考虑风味选项，但最终的转换步骤确保完全跳过它是最佳的，产生 50 而不是更小的混合值。 

另一种情况是最好的解决方案根本不使用调味面包。 DP 仍必须正确返回 0 以用于风味用途，并允许完全转换为普通面包。 如果不考虑最终循环中的“used = 0”状态，该解决方案将错误地错过 all-plain 最佳配置。 

第三种情况是风味包子完全填满面团，不留任何剩余物。 该算法仍然有效，因为最终转换项变为零，因此DP单独决定结果而不受干扰。
