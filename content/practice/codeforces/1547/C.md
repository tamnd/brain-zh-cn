 ## 解决方案
 ## 问题理解

 两个程序员正在对同一个文件进行编辑，但他们的工作历史在时间上是交错的。 我们有两个有序的动作序列，每个人一个。 每个操作要么是在文件末尾插入，要么是对现有行进行编辑。 该文件以一些初始行数开始，并且两个人都在相同的不断变化的文件状态下操作。 

任务是重建所有动作的有效全局时间线，以便当我们按顺序将该时间线投影到每个人的动作上时，我们可以恢复他们的原始序列。 同时，每个编辑操作必须仅在目标行此时已存在于文件中之后发生。 

因此，该结构是两个序列与动态状态变量的受约束合并：文件中的当前行数仅通过插入增加，而编辑取决于该行数是否足够大。 

约束足够小，O(nm) 动态构造已经可以轻松通过，因为每个序列的长度最多为 100，并且最多有 1000 个测试用例。 这使得最坏情况下的操作总数最多约为几千万，这在 Python 中对于简单转换来说仍然是安全的。 然而，问题的结构允许更清晰的贪婪构造。 

一种幼稚的错误方法是简单地贪婪地合并，始终从任一序列中采取下一个可用操作，而不跟踪编辑当前是否有效。 例如，如果文件大小为 3，并且下一个选择的操作是“编辑第 10 行”，则即使稍后插入可以实现，这也将是无效的。 这会失败，因为可行性取决于未来的插入，而不仅仅是本地排序。 

当一个序列强制进行早期编辑，需要比另一个序列当前提供的插入更多的插入时，就会发生另一种微妙的失败。 如果我们不明确跟踪当前文件大小，我们可能会接受不可能的交错，或者在提交错误的前缀后错误地返回 -1。 

## 方法

 暴力的观点是考虑逐步构建合并序列，在每个点选择 Monocarp 的下一个动作或 Polycarp 的下一个动作，同时保持当前文件大小并确保所有编辑都有效。 这本质上是对所有交错的搜索，在最坏的情况下探索所有二项式（n + m，n）的可能性。 即使进行剪枝，分支因子仍为 2，深度为 n + m，使其呈指数增长。 

关键的观察是我们永远不需要任意猜测。 在每个步骤中，如果插入在任一序列中可用，则延迟插入总是安全的，除非编辑迫使我们增加文件大小。 唯一可能阻碍进度的约束是目标行号大于当前大小的编辑。 这意味着插入的行为就像可以自由推迟的资源，而编辑则对当前状态施加严格的最低要求。 

这导致了贪婪的构造，我们在序列中维护两个指针并模拟文件。 每当接下来的两个操作都是编辑，或者当前无法进行编辑时，我们必须首先选择插入，直到文件变得足够大。 如果两个操作都是插入，我们可以安全地选择其中一个。 

这消除了所有回溯，因为一旦采取行动，只要我们遵守文件大小限制，它就永远不会使未来的可行性失效。

 | --- | --- | --- | --- |
 | 蛮力 | O(2^(n+m)) | O(2^(n+m)) | O(n+m) | 太慢了 |
 | 贪心模拟 | O(n+m) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们模拟该过程，同时跟踪文件中当前存在的行数。

1. 将文件大小初始化为 k，并在两个序列的开头设置两个指针 i 和 j。 还维护一个空的结果列表。 
2. 在每一步中，检查我们是否可以采取 Monocarp 的下一个动作或 Polycarp 的下一个动作。 
3. 如果两个序列都已穷尽，则过程结束并输出结果。 
4. 如果 Monocarp 还有剩余动作，请检查他的下一个动作。 如果是插入，则始终有效，因为插入不依赖于文件大小。 如果是对第 x 行的编辑，则仅当 x 小于或等于当前文件大小时才有效。 
5. 对 Polycarp 的下一个动作进行同样的有效性检查。 
6. 如果接下来的两个操作都有效，则优先选择任一插入（如果存在），因为它不会限制未来的灵活性。 如果两者都是编辑，我们必须选择任何一个有效的。 
7. 如果接下来的两项行动中只有一项有效，我们必须采取那一项。 
8. 如果两个操作均无效，则意味着这两个操作都需要尚不存在的行进行编辑。 在这种情况下，唯一可能的前进方式将需要将来的插入，但是两个序列都不允许在模拟中的此时插入，因此答案是不可能的。 
9. 当我们进行插入时，增加文件大小。 当我们进行编辑时，文件大小不会改变。 

### 为什么它有效

 关键的不变量是，在每一步中，当前文件大小等于已放置在合并序列中的插入数量。 仅当任何编辑引用最多为该大小的索引时，才会接受任何编辑，因此我们永远不会构造无效状态。 由于插入永远不会受到未来编辑的限制，因此推迟插入不会降低可行性，只会增加灵活性。 因此，只要存在选择，首选插入永远不会阻止有效的解决方案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    input()
    k, n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    i = j = 0
    cur = k
    res = []

    ok = True

    while i < n or j < m:
        moved = False

        if i < n and a[i] == 0:
            res.append(0)
            cur += 1
            i += 1
            moved = True
        elif j < m and b[j] == 0:
            res.append(0)
            cur += 1
            j += 1
            moved = True
        elif i < n and a[i] <= cur:
            res.append(a[i])
            i += 1
            moved = True
        elif j < m and b[j] <= cur:
            res.append(b[j])
            j += 1
            moved = True

        if not moved:
            ok = False
            break

    if ok:
        print(*res)
    else:
        print(-1)
```该解决方案保持对不断演变的文件的直接模拟。 指针对跟踪每个序列已消耗了多少，而变量`cur`表示当前存在的行数。 插入会立即增加该计数器，这很重要，因为后续编辑的有效性取决于它。 排序逻辑尽可能优先考虑插入，因为它们严格增加了未来编辑的可行性，而不消耗约束。 

一个微妙的点是，编辑仅根据编辑时的当前大小进行检查，而不是根据未来的潜在大小进行检查。 这就是贪婪策略安全的原因：如果编辑当前无效，我们还无法安排它，并且只有在至少一个序列中稍后出现某些插入时才可能延迟它。 

## 工作示例

 考虑 k = 3 的样本，Monocarp 具有 [2, 0]，Polycarp 具有 [0, 5]。 

一开始，cur = 3，i = 0，j = 0。两个第一个动作都可用，但 Polycarp 首先有一个插入，所以我们从 Polycarp 中取 0。 现在 cur = 4。接下来，Monocarp 可以编辑 2，所以我们接受它。 然后 Monocarp 插入，然后 Polycarp 编辑 5。 

| 步骤| 我| j | 当前| 采取的行动| 状态|
 | --- | --- | --- | ---| --- | --- |
 | 1 | 0 | 0 | 3 | 0 (波利卡普) | 当前=4 |
 | 2 | 0 | 1 | 4 | 2（单果树）| 当前=4 |
 | 3 | 1 | 1 | 4 | 0（单果树）| 当前=5 |
 | 4 | 2 | 1 | 5 | 5（波利卡普）| 完成 |

 这显示了如何尽早使用插入来解锁以后的编辑。 

现在考虑一个失败情况：k = 0，a = [1]，b = [2]。 最初 cur = 0，接下来的两个操作都是无效编辑。 由于两个序列都没有首先提供插入，因此算法立即停止并返回 -1。 这反映了这样一个事实：如果没有事先插入，这两个编辑都不会变得有效，但两个序列都没有在前面提供一个，从而使排序变得不可能。

 ## 边缘情况

 关键的边缘情况是两个序列都以需要大于 k 的行索引的编辑开始。 例如，k = 1，a = [5]，b = [6]。 该算法正确返回 -1，因为两个序列都无法在需要第一个操作之前尽早贡献插入以增加文件大小。 

另一种情况是插入在一个序列中延迟但在另一个序列中可用。 贪婪的选择确保我们总是在可用时立即使用插入，从而防止人为阻止依赖于文件大小增加的后续编辑。
