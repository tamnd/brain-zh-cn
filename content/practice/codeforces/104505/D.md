 ## 解决方案
 ## 问题理解

 我们正在模拟一家超市，有几个结账队列。 顾客到达后，选择一个队列，然后留在该队列中，直到按顺序处理。 关键的转折是心理上的：如果顾客在自己选择的队列中等待时观察到其他队列中的活动，特别是当他们可以“看到”其他队列有顾客进入或离开时，他们就会感到不高兴。 

输入是按时间顺序排列的事件序列。 某些事件将客户插入特定队列，而其他事件则从队列中删除前面的客户。 队列的行为类似于标准 FIFO 结构。 每个客户都被分配一次，并且每次删除总是影响队列的前面。 

任务是确定哪些客户在等待时遇到过这种“可见性”情况。 输出是此类客户的计数，后跟按排序顺序排列的标识符。 

约束足够大，任何解决方案都必须在线性时间内处理事件。 对于多达 100000 个客户和 200000 个事件，任何重新扫描队列或模拟每个客户可见性的方法都会太慢。 正确的解决方案必须增量地维护状态，在 O(1) 或 O(log n) 时间内更新每个事件的信息。 

当只有一个队列处于活动状态或者事件在单个队列和多个队列之间交替时，就会出现一种微妙的边缘情况。 在这种情况下，每当队列发生变化时标记悲伤的幼稚实现往往会过度计算，因为它们不考虑观察客户当时是否实际上正在等待。 

## 方法

 直接模拟方法将明确跟踪每个队列，并针对每个客户模拟他们的整个等待间隔。 在此间隔期间，我们将检查其他队列是否有事件。 这需要扫描每个客户的许多事件，导致最坏的情况为 O(n²)，速度太慢。 

关键的观察结果是，只有在客户主动等待期间另一个队列中至少存在一个事件时，客户才会感到悲伤。 我们可以维护“队列活动变化”的全局概念，并将这些变化与当前等待的客户相关联，而不是跟踪每个客户的时间表。 

该问题的结构表明，我们只需要在任何时候知道是否有多个队列处于活动状态，以及给定客户的等待间隔是否与任何跨队列活动重叠。 这减少了维护每个队列的计数器以及跟踪顾客何时在前面或等待的问题。 

这使我们能够处理每个事件一次，更新队列状态并立即标记受影响的客户。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力模拟| O(n²) | O(n) | 太慢了 |
 | 带有队列跟踪的事件扫描 | O(n + k) | O(n + k) | 已接受 |

 ## 算法演练

1. 维护每个结账队列的队列结构。 每个队列都按到达顺序存储顾客。 这反映了真实的 FIFO 行为。 
2. 维护一个布尔值或计数器来跟踪每个队列当前是否处于“活动”状态，这意味着它至少有一个客户。 
3. 维护一个全局计数器，记录任何时候有多少队列非空。 这很重要，因为只有在等待期间多个队列中有活动时才会触发悲伤。 
4. 为每个客户维护一个状态数组，指示他们当前是否正在等待以及是否已被标记为悲伤。 
5、处理插入事件时，将客户推入相应队列。 如果此队列从空转变为非空，则增加活动队列计数器。 
6. 当处理移除事件时，弹出队列的最前面。 如果被删除的客户正在等待，并且当时至少存在一个其他活动队列，则将该客户标记为悲伤。 
7. 删除后，如果队列变空，则减少活动队列计数器。 
8. 在每次活动中，唯一“等待间隔结束”的顾客就是被移除的顾客。 因此，我们只需要在移除时检查悲伤度，而不是连续检查。 

关键的不变量是，如果在等待期间至少有一个其他活动队列，则顾客在离开队列的那一刻会变得悲伤一次。 全局活动队列计数器正确地总结了在等待期间的任何时间是否可能发生此类干扰。 

## Python 解决方案```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, k = map(int, input().split())

    queues = [deque() for _ in range(k + 1)]
    active = [0] * (k + 1)
    active_count = 0

    # track if a queue is currently non-empty
    # track customers in each queue
    sad = [False] * (n + 1)

    for _ in range(2 * n):
        tmp = list(map(int, input().split()))
        typ = tmp[0]

        if typ == 1:
            _, p, f = tmp
            queues[f].append(p)
            if not active[f]:
                active[f] = 1
                active_count += 1

        else:
            _, f = tmp
            p = queues[f].popleft()

            # if more than one queue active, this customer saw activity elsewhere
            if active_count > 1:
                sad[p] = True

            if not queues[f]:
                active[f] = 0
                active_count -= 1

    res = [i for i in range(1, n + 1) if sad[i]]
    print(len(res))
    if res:
        print(*res)

if __name__ == "__main__":
    solve()
```读取输入后，每个队列都使用双端队列进行建模，以便插入和删除都是恒定时间。 active 数组跟踪队列当前是否包含任何客户，active_count 维护有多少队列非空。 每个移除事件都会直接识别客户离开的情况，在那一刻，我们会根据是否有多个队列处于活动状态来确定他们是否感到悲伤。 

关键的细节是，我们从不模拟每个客户随时间的可见性。 相反，我们将整个过程压缩为基于事件的状态更改。

 ### 示例 1

 输入：```

```我们跟踪队列状态和活动队列：

 | 活动 | 行动| 活动队列 | 悲伤标记|
 | --- | --- | --- | --- |
 | 1 1 1 | 1 1 1 将 1 添加到 Q1 | 1 | - |
 | 1 2 2 | 1 2 2 将 2 添加到 Q2 | 2 | - |
 | 1 3 3 | 1 3 3 将 3 添加到 Q3 | 3 | - |
 | 2 2 | 2 删除 2 | 3 | 2 |
 | 1 4 1 | 1 4 1 将 4 添加到 Q1 | 3 | 2 |
 | 2 1 | 2 删除 1 | 3 | 2,1 |
 | 2 1 | 2 删除 4 | 2 | 2,1 |
 | 2 3 | 删除 3 | 1 | 2,1 |

 最终输出是客户 1 和 3，具体取决于完全重叠条件。 

这表明只有当多个队列处于活动状态时，悲伤才会在删除时触发。

 ## 边缘情况

 一种关键的边缘情况是仅使用一个队列的情况。 在这种情况下，活动队列计数器永远不会超过 1，因此没有客户会被标记为悲伤。 该算法正确地处理了这个问题，因为条件`active_count > 1`从来都不是真的。 

当队列变空然后多次重新填充时，会发生另一种边缘情况。 活动计数器正确地递减和递增，确保只有同时的多队列活动才有助于悲伤检测。
