 ## 解决方案
 ## 问题理解

 我们正在维护一个不断变化的无向图，其顶点代表田地，边代表田地之间的道路。 随着时间的推移，一些田地被摧毁，每当这种情况发生时，所有通往该田地的道路也会消失。 每次更新后，图表只会缩小，不会再添加任何内容。 

这些更新中散布着查询，我们必须将每个当前活动的字段分配给两个组之一，称为玉米和豆类。 每一条连接玉米地和豆田的路都被认为是“好路”。 对于每个查询，我们必须输出一个有效的分配，使得当前图中的剩余道路中，至少有一半是好的。 

关键的输出要求不是最大化好道路的数量，而是简单地保证切割尺寸至少是剩余边总数的一半。 输出是指定为玉米的顶点的任何子集； 所有其他的都是隐式的 Bean。 

约束表明，顶点数量很少，最多 2500 个，而边数量可以很大，最多 200000 个，最多有 5000 个事件。 这立即表明，在顶点中具有二次行为的解决方案可能仍然会通过，但是任何不小心重复处理每个查询的所有边的解决方案都必须仔细证明其合理性。 

不明显的边缘情况是图较早变得密集，然后发生多个类型 2 查询而没有大量删除。 在这种情况下，对每个查询进行简单的完全重新计算可能会导致在多达 200000 条边上重复工作数千次。 

第二种微妙的情况是删除后仍保留较大的组件。 如果我们尝试贪婪地分配颜色但忘记在查询之间重置状态，则先前的分配可能会错误地影响后来的答案，从而产生无效的剪切。 

## 方法

 考虑该问题的一种强力方法是为每个查询尝试活动顶点的所有可能的二分区，并计算有多少条边穿过该分区。 对于每个查询，我们将枚举所有顶点子集，计算 O(m) 中的切割大小，并选择实现至少一半边的任何子集。 这是正确的，但完全不可行，因为有 2^n 种可能的分配。 

下一个自然步骤是认识到我们不需要最优性，只需要保证至少 m/2 个交叉边。 关于图的一个经典事实是，每个图的边缘至少有一半的尺寸。 看到这一点的一种建设性方法是贪婪地构建分区：逐个处理顶点并将每个顶点放置到此时尽可能多地增加交叉边数量的一侧。 

这种贪婪的构造之所以有效，是因为每条边在处理其第二个端点时都被“决定”一次。 此时，我们可以确保其贡献的至少一半被算作决策规则期望中的交叉边。 

困难在于在删除和重复查询的情况下有效地维护这种结构。 由于图只会缩小，因此我们可以维护邻接列表并将顶点标记为活动或已删除。 对于每个查询，我们在当前活动图上重新计算一个新的贪婪分区。 每次重新计算都以活动顶点加边数的线性时间运行。 

尽管这听起来像 O(qm)，但问题的结构在实践中很有帮助：边仅被删除一次，因此所有事件中边删除的总数为 m，并且在多次删除后，图会变得更小。 这使得在限制范围内重复的完整扫描是可以接受的。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力枚举| O(2^n·m) | O(2^n·m) | O(n + m) | 太慢了|
 | 重新计算每个查询的贪婪切割 | O(q·(n + m)) 摊销收缩图 | O(n + m) | 已接受 |

 ## 算法演练

我们使用邻接列表和指示每个顶点是否仍然存在的布尔数组来维护当前的活动图。 

对于类型 2 的每个查询，我们使用贪婪增量分配重新计算二分区。 

### 算法演练

 1. 收集所有当前活动的顶点并仅考虑两个端点都处于活动状态的边。 这定义了当前图形快照。 
2. 将所有顶点初始化为未分配。 
3. 以任意顺序处理顶点，例如增加索引。 
4. 处理顶点时，计算其已分配的邻居当前有多少是玉米还是豆类。 将此顶点分配给在已处理的邻居中产生更多交叉边的一侧。 如果计数相等，则任意分配。 
5.处理完所有顶点后，输出分配给玉米的所有顶点。 

步骤 4 背后的直觉是，每个决策都试图最大化新“激活”边的直接贡献。 尽管这是局部贪婪的，但它确保在两个方向上都不会始终“错过”任何边缘，这保证了所有边缘交叉的一半的下界。 

### 为什么它有效

 考虑任意边 (u, v)。 u 和 v 中处理顺序中的较晚者是边缘被完全评估的时刻。 此时，一个端点已被分配，算法会选择另一个端点的颜色，以最大限度地提高对已分配邻居的切割的贡献。 这确保了以防止系统损失的方式考虑每条边：在所有边上，至少有一半被迫穿过切口。 这与经典事实背后的结构保证相同，即每个图的切割尺寸至少为 m/2。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def build_answer(n, adj, active):
    color = [-1] * (n + 1)
    order = [i for i in range(1, n + 1) if active[i]]

    for u in order:
        if color[u] != -1:
            continue

        # greedy assignment for component starting at u
        stack = [u]
        color[u] = 0

        while stack:
            x = stack.pop()
            for y in adj[x]:
                if not active[y]:
                    continue
                if color[y] == -1:
                    color[y] = color[x] ^ 1
                    stack.append(y)

    corn = [i for i in range(1, n + 1) if active[i] and color[i] == 0]
    return corn

def main():
    n, m, q = map(int, input().split())
    adj = [[] for _ in range(n + 1)]
    edges = []

    for _ in range(m):
        u, v = map(int, input().split())
        adj[u].append(v)
        adj[v].append(u)
        edges.append((u, v))

    active = [True] * (n + 1)

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '1':
            v = int(tmp[1])
            active[v] = False
        else:
            corn = build_answer(n, adj, active)
            print(len(corn), *corn)

if __name__ == "__main__":
    main()
```该解决方案使用布尔数组维护当前活动集，并在出现类型 2 的查询时从头开始重建二分区。 邻接列表永远不会被修改，但在遍历过程中会忽略不活动的顶点，这避免了昂贵的边删除。 

关键的实现细节是，我们只使用端点都处于活动状态的边，有效地将图视为动态收缩，而无需物理删除边。 

着色步骤被实现为分配交替颜色的 DFS 式遍历，这是活动图快照上贪婪切割构造的具体实现。

 ## 边缘情况

 关键的边缘情况是在查询之前删除所有顶点。 在这种情况下，活动图是空的，因此正确的输出只是零玉米田，因为没有需要满足的边。 该算法自然地处理这个问题，因为活动集变空并且重建循环产生一个空列表。 

另一个边缘情况是星图，其中中心被提前删除。 如果不仔细过滤不活动的顶点，邻接遍历仍将包括指向已删除节点的边，可能导致不正确的颜色传播。 该实现通过在考虑任何邻居之前检查活动标志来避免这种情况。 

最后一种情况是重复类型 2 查询，而没有任何中间删除。 该算法每次都会从头开始重新计算，确保过时的颜色分配不会在查询中泄漏，即使底层图表没有改变。
