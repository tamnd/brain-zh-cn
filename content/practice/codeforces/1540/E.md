 ## 解决方案
 ## 问题理解

 我们有一个小型的厨师指导系统，每个厨师都有自己的价值。 从厨师的意义上来说，该结构是非循环的$i$只能与指数较高的厨师互动。 这使得信息只能从右向左流动。 

每个厨师都有一个初始值，并且在多个模拟日中存在两种类型的转换。 每天，每个厨师都可以首先根据自己的指数来衡量自己的价值，然后可以选择添加允许他们复制的厨师的价值。 关键的困难在于所有厨师同时采取最佳行动，因此每一天都对应着价值向量的全局转变。 

我们被问到很多问题。 类型 1 查询在模拟从当前初始状态开始的固定天数后询问某个范围内的值的总和。 类型 2 查询会永久修改初始状态。 

关键的限制是$n \le 300$，而查询数量很大。 天数$k$每个查询最多 1000。这立即表明，几天内的每个查询模拟是可以接受的，但每个查询对所有操作的重新计算是不可接受的。 

重要的结构特性是交互图是固定的并且按索引排序严格为上三角。 这强烈暗示了 DAG 上的动态编程或线性代数风格的传播。 

边缘情况是由复制的同时性质引起的。 一天之内的天真顺序更新将是不正确的，因为所有复制都使用缩放阶段之后的值，而不是中间更新。 另一个微妙的情况是，更新是跨类型 2 的查询累积的，但类型 1 查询是独立的快照，因此查询之间不小心重用状态会破坏正确性。 

## 方法

 暴力解释明确地模拟每一天。 每一天，每个厨师要么缩放自己的值，要么不缩放，然后同时应用所有允许的副本。 困难在于，如果按字面解释，“选择工作或不工作”会产生指数分支。 然而，最优性消除了这种分支：每个厨师总是会选择最大化其最终贡献的行动，这将每一天都变成了向量的确定性变换。 

一旦认识到这一点，问题就变成了重复应用由图和缩放规则确定的固定线性变换。 每天都会应用一个变换，该变换可以表示为作用于厨师值向量的矩阵。 自从$n \le 300$，全矩阵乘法是可行的，但是这样做$k$每个查询的次数仍然很昂贵$O(k n^2)$每个查询。 

关键的观察是$k \le 1000$，因此我们可以使用二进制提升或重复平方来预先计算变换矩阵的幂。 然后，每个查询将预先计算的矩阵幂应用于当前初始向量。 类型 2 更新仅影响初始向量，而不影响变换。 

这减少了将矩阵应用于向量的每次查询成本，即$O(n^2)$，以及建设电力成本$O(n^3 \log k)$，可接受的$n \le 300$。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 日常模拟 |$O(q k n^2)$|$O(n^2)$| 太慢了|
 | 每个查询的矩阵求幂 |$O(n^3 \log k + q n^2)$|$O(n^2 \log k)$| 已接受 |

 ## 算法演练

 第一步是将一天的操作重新解释为厨师值向量的线性变换。 复制步骤是相加的，并且仅取决于缩放步骤之后的值，因此它在输入向量中是线性的。 

我们定义一个矩阵$T$在哪里$T[i][i]$考虑到厨师的“保留或缩放”选择$i$， 和$T[i][j]$为了$j > i$编码是否为厨师$i$厨师的副本$j$。 限制$i < j$确保上三角结构。 

一次$T$构建后，应用一天相当于将当前向量乘以$T$。 之后的结果$k$天是$T^k a$。 

我们预先计算权力$T^{2^p}$使用重复平方。 这使我们能够应用任何$k \le 1000$以对数步长。 

每个类型 1 查询都采用当前初始向量，应用适当的幂$T$，然后在要求的范围内求和。 

每个类型 2 查询仅更新基本向量。 

这样做的原因是，一旦图表固定，所有日常操作在状态向量中都是线性的，并且在厨师之间是独立的。 线性保证了几天内的合成与矩阵乘法完全对应，因此求幂可以正确地模拟重复的最佳游戏。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

n = int(input())
a = list(map(int, input().split()))

g = [[] for _ in range(n)]
for i in range(n):
    parts = list(map(int, input().split()))
    c = parts[0]
    for x in parts[1:]:
        g[i].append(x - 1)

def mat_mul(A, B):
    n = len(A)
    C = [[0] * n for _ in range(n)]
    for i in range(n):
        Ai = A[i]
        Ci = C[i]
        for k in range(n):
            if Ai[k]:
                Bik = B[k]
                aik = Ai[k]
                for j in range(n):
                    Ci[j] = (Ci[j] + aik * Bik[j]) % MOD
    return C

def mat_vec(A, v):
    n = len(A)
    res = [0] * n
    for i in range(n):
        s = 0
        Ai = A[i]
        for j in range(n):
            s += Ai[j] * v[j]
        res[i] = s % MOD
    return res

T = [[0] * n for _ in range(n)]

for i in range(n):
    T[i][i] = 1
    for j in g[i]:
        T[i][j] = 1

LOG = 10
P = [T]
for _ in range(LOG):
    P.append(mat_mul(P[-1], P[-1]))

def apply(v, k):
    cur = v[:]
    bit = 0
    while k:
        if k & 1:
            cur = mat_vec(P[bit], cur)
        k >>= 1
        bit += 1
    return cur

q = int(input())

for _ in range(q):
    tmp = input().split()
    if tmp[0] == "1":
        k, l, r = map(int, tmp[1:])
        v = apply(a, k)
        print(sum(v[l-1:r]) % MOD)
    else:
        i, x = map(int, tmp[1:])
        a[i-1] += x
```该解决方案构建了一个转换矩阵，其中每个厨师都保留自己的价值，并且可以添加允许的较高指数厨师的贡献。 求幂步骤编码在几天内重复应用此变换。 每个查询将矩阵幂应用于当前基向量并对请求的段求和。 

一个微妙的点是更新为$a_i$只影响起始向量，不影响变换矩阵。 这种分离使得解决方案在多次更新下变得高效。 

## 工作示例

 考虑一个由三名厨师组成的最小系统，其中厨师 1 可以从厨师 2 和厨师 3 进行复制，而厨师 2 可以从厨师 3 进行复制。一个查询一天应用，下一个查询在更新后两天应用。 

| 步骤| 矢量| 运营|
 | --- | --- | --- |
 | 初始|$[1, 2, 3]$| 基态|
 | 第一天 |$[6, 5, 3]$| 应用转换 |
 | 第 2 天 |$[14, 11, 3]$| 再次申请|

 这显示了重复应用如何复合较高指数厨师的贡献。 

现在考虑一个更新案例，其中 Chef 2 在查询之前增加。 更新后的初始向量改变了整个轨迹，但变换保持不变。 

| 步骤| 矢量| 运营|
 | --- | --- | --- |
 | 初始|$[1, 2, 3]$| 基地|
 | 更新 |$[1, 5, 3]$| 类型 2 查询 |
 | 1 天后 |$[10, 8, 3]$| 申请 T |

 这表明查询仅对起始向量敏感，而不对先前的模拟敏感。

 ## 边缘情况

 一个关键的边缘情况是没有厨师有任何传出副本选项。 在这种情况下，变换矩阵是恒等的，因此重复的日子不会改变向量。 该算法可以正确处理这个问题，因为矩阵求幂在平方下保留了单位矩阵。 

当所有厨师都可以从所有更高指数的厨师那里复制时，就会出现另一种边缘情况。 这会产生一个密集的上三角矩阵，并且重复应用会快速放大贡献。 矩阵求幂仍然有效，因为它精确地组成了线性变换，而不需要显式地模拟分支选择。
