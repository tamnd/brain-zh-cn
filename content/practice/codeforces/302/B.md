 ## 解决方案
 ## 问题理解

 播放列表是由重复歌曲块构建的。 歌曲`i`有持续时间`t[i]`，尤金妮听着`c[i]`连续几次，然后转到下一首歌曲。 

如果一首歌曲持续 4 分钟并重复 3 次，则该块将为播放列表时间线贡献 12 分钟。 查询会提出以下问题：

 “从播放列表开始的第 57 分钟，播放的是哪首歌？”

 重要的细节是，我们不会被询问正在播放哪一首歌曲的重复内容，只会询问歌曲索引本身。 

播放列表最多可包含`10^5`歌曲块和`10^5`查询。 直接逐分钟模拟是不可能的，因为每个`c[i] * t[i]`可以非常大。 播放列表总时长可达`10^9`，这意味着构建所有分钟的显式数组将需要数十亿个元素。 

和`10^5`查询低于 2 秒限制，我们应该期待一些事情`O(n log n)`或者`O(n + m)`舒适地通过。 任何扫描整个播放列表以查找每个查询的解决方案都会变得太慢。 

一个微妙的问题是查询在时间上是 1 索引的。 如果一首歌占据几分钟`[1, 16]`，然后查询`16`仍然属于那首歌，而查询`17`属于下一个。 相差一的错误在这里很常见。 

考虑这个例子：```
2 3
1 3
1 2
1 3 4
```播放列表时间线是：```
minutes 1..3 -> song 1
minutes 4..5 -> song 2
```正确输出：```
1
1
2
```使用严格的粗心实现`<`而不是`<=`在二分搜索期间会错误地映射分钟`3`唱歌`2`。 

当一个歌曲块非常大时，会发生另一种棘手的情况：```
1 3
1000000000 1
1 500000000 1000000000
```所有查询仍必须返回歌曲`1`。 这排除了任何逐分钟扩展播放列表的方法。 

最后一个细节是查询已经越来越排序。 一些解决方案使用两个指针来利用这一点，但是对前缀和的二分搜索也足够快并且更易于推理。 

## 方法

 蛮力的想法很简单。 我们可以每分钟生成完整的播放列表时间线，并存储每分钟播放的歌曲。 

例如：```
song 1: duration 2, repeats 3 times
```将贡献：```
[1, 1, 1, 1, 1, 1]
```因为这首歌一共占了6分钟。 

然后每个查询都变成直接查找。 

这是合乎逻辑的，因为每一分钟都被明确表示。 问题是尺寸。 总时长可达`10^9`，所以这个数组可以包含十亿个条目。 内存和运行时间都变得不可能。 

下一个改进是观察每首歌曲在全局时间线上占据一个连续的间隔。 

假设我们计算累积持续时间：```
song 1 ends at minute 10
song 2 ends at minute 25
song 3 ends at minute 40
```现在查询`x`只是问：

 “第一首结束时间至少为`x`？”

 这正是一个二分搜索问题。 

累计结束时间自然排序，因为每首歌曲都会增加一个正的持续时间。 对于每个查询，我们二分搜索第一个前缀和`>= x`。 

这大大减少了工作量：

 我们不是单独扫描分钟，而是为每个歌曲块只存储一个数字。 

我们不是对每个查询进行线性搜索，而是使用二分搜索`O(log n)`时间。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(总持续时间 + m) | O(总持续时间) | 太慢了 |
 | 最佳 | O(n + m log n) | O(n + m log n) | O(n) | 已接受 |

 ## 算法演练

 1.读取歌曲块数`n`和查询数量`m`。 
2. 构建前缀和数组。 

对于每个歌曲块，计算：```
block_duration = c[i] * t[i]
```然后附加到目前为止的累计总持续时间。 

如果前缀和变为：```
[10, 25, 40]
```这意味着：

 歌曲1占用分钟`1..10`歌曲2占用分钟`11..25`歌曲3占用分钟`26..40`3. 阅读每个查询分钟`x`。 
4. 对前缀和数组进行二分查找，查找第一个大于或等于的值`x`。 

这给出了包含分钟的歌曲块`x`。 
5. 将歌曲索引输出为从 1 开始的索引。 

### 为什么它有效

 前缀和数组存储每个歌曲块的结束分钟。 由于每个区块持续时间都是正数，因此这些结束时间严格增加。 

对于任何查询分钟`x`，正确的歌曲恰好是结束时间至少为的第一个块`x`。 

如果前一个前缀和小于`x`，然后所有较早的歌曲在分钟前结束`x`。 如果当前前缀和至少为`x`，则当前歌曲已经开始，尚未结束。 

因为二分搜索精确地找到了这个边界，所以算法总是返回正确的歌曲。 

## Python 解决方案```python
import sys
from bisect import bisect_left

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())

    prefix = []
    total = 0

    for _ in range(n):
        c, t = map(int, input().split())
        total += c * t
        prefix.append(total)

    queries = list(map(int, input().split()))

    ans = []

    for x in queries:
        idx = bisect_left(prefix, x)
        ans.append(str(idx + 1))

    sys.stdout.write("\n".join(ans))

solve()
```解决方案的核心是`prefix`大批。 每个条目都存储该歌曲块占用的最后一分钟。 

例如，如果：```
prefix = [6, 15, 21]
```然后：```
song 1 -> minutes 1..6
song 2 -> minutes 7..15
song 3 -> minutes 16..21
```

`bisect_left(prefix, x)`返回值至少为的第一个索引`x`。 这正是包含分钟的歌曲`x`。 

这`+1`是必要的，因为 Python 列表使用从 0 开始的索引，而歌曲编号是从 1 开始的。 

一个常见的错误是使用`bisect_right`。 在歌曲恰好结束的边界分钟内，这将失败`x`。 

另一个容易犯的错误是忘记时间线是从分钟开始的`1`，不是分钟`0`。 使用累积结束时间自然可以避免这个问题。 

Python 整数在这里安全地处理最大可能的总数，因此不需要特殊的溢出处理。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(n + m log n) | O(n + m log n) | 构建前缀和是线性的，每个查询都使用二分搜索 |
 | 空间| O(n) | 前缀和数组为每个歌曲块存储一个值 |

 和`n, m ≤ 10^5`，这很容易符合限制。 大约`10^5`对大小的数组进行二分搜索`10^5`完全在 Python 允许的运行时间之内。

# helper: run solution on input string, return output string
import sys
import io
from bisect import bisect_left

def solve():
    input = sys.stdin.readline

    n, m = map(int, input().split())

    prefix = []
    total = 0

    for _ in range(n):
        c, t = map(int, input().split())
        total += c * t
        prefix.append(total)

    queries = list(map(int, input().split()))

    ans = []

    for x in queries:
        ans.append(str(bisect_left(prefix, x) + 1))

    sys.stdout.write("\n".join(ans))

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    output = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return output

# provided sample
assert run(
    "1 2\n"
    "2 8\n"
    "1 16\n"
) == "1\n1"

# minimum-size input
assert run(
    "1 1\n"
    "1 1\n"
    "1\n"
) == "1"

# boundary transition between songs
assert run(
    "2 4\n"
    "1 3\n"
    "1 2\n"
    "1 3 4 5\n"
) == "1\n1\n2\n2"

    "1000000000 1\n"

 | ---| ---| ---|

 ## 边缘情况

 考虑边界情况，其中查询恰好落在歌曲块的最后一分钟。

```前缀和变为：```

该算法从不构建十亿分钟的数组，因此它保持快速和内存效率。
