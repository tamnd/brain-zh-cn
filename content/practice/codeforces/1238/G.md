 ## 解决方案
 ## 问题理解

 该系统只有在永远不会变空的情况下才能运行，这意味着在消耗发生之前，每分钟它必须包含至少一升。 它每分钟连续排水一升，总共`m`分钟，其存储容量上限为`c`。 最初它已经包含`c0`升。 

我们可以“安排”朋友送水的时间。 每个朋友都有固定的到达时间、可以贡献的最大金额以及每升的费用。 我们决定每个朋友贡献多少，但不超过他们的限额。 当朋友到达时，他们选择的金额会立即添加，但任何超出容量的内容都会被丢弃。 

任务是选择贡献，使储罐在整个过程中永远不会干涸，同时最大限度地降低总成本。 

关键的难点在于，该系统是一个连续的消费过程，具有离散的补充事件，并且每次补充都有容量限制和成本。 这就产生了一种全局依赖性：廉价的补充只有在系统失败之前到达时才有用。 

限制条件极其严格。 所有查询的好友总数最多可达 5×10^5，到达时间最多可达 10^9。 这排除了每分钟的任何模拟。 任何有效的解决方案都必须在每个查询的大致线性或近线性时间内工作，通常为 O(n log n) 或 O(n)。 

一个天真的想法是模拟每一分钟，跟踪当前的水量并在水量不足时选​​择使用哪个朋友。 这会立即失败，因为 m 可以是 10^9，使得模拟不可能。 

更微妙的失败来自于贪婪的本地决策，没有考虑未来更便宜的补充品。 例如，如果一个便宜的朋友迟到了，但我们已经提前选择了昂贵的笔芯，那么天真的方法就会付出过高的代价。 

另一个边缘情况是，即使后来的朋友可以提供足够的总水，早期的水也不足以到达第一个到达的朋友。 在重新填充之前，系统可能会发生故障。 

## 方法

 暴力方法会尝试为每个朋友决定要取多少水，并模拟系统是否能够生存。 即使将每个朋友限制为 0 或 a_i 仍然会产生 2^n 种可能性，这是不可行的。 即使随着时间的推移进行动态规划也会失败，因为到达时间很长并且顺序不密集。 

关键的观察结果是，水只需要在发生变化的事件之间架起桥梁：朋友到达或过程消耗水。 在两个连续的事件时间之间，消耗是确定性的，因此唯一有意义的问题是我们是否可以覆盖每个间隔。 

这将问题转化为管理在特定时间出现的一系列“缺水”。 每当下一次活动之前水箱的水位低于零时，我们就必须购买额外的水。 在当时或之前可用的所有朋友中，我们应该首先使用最便宜的朋友，因为未来的需求是未知的，但成本是固定的。 

随着时间的推移，这自然会导致贪婪策略，并以成本为关键优先级队列。 我们处理事件的时间越来越长，维持我们目前拥有的水量，每当我们发现水短缺时，我们就会贪婪地从最便宜的可用来源购买直到其剩余容量。 

这个问题类似于随着时间的推移逐渐出现的供应商满足需求，我们总是首先选择最便宜的可用供应。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 暴力破解（模拟/DP）| 指数或 O(m) | O(n) | 太慢了 |
 | 最优（事件扫描+贪婪堆）| O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 我们将所有事件转换为按时间排序的过程。 

1. 按照好友到达时间对好友进行排序。 我们按升序处理它们，以便我们随时准确地知道哪些水源可用。 
2. 维护可用朋友的优先级队列（最小堆），以每升成本为键。 每个条目存储剩余容量和成本。 这确保了我们总是首先从最便宜的朋友那里购买水。 
3. 跟踪水箱中的当前水量和当前时间。 最初，坦克有`c0`升，时间从 0 开始。 
4. 每位朋友到达时间`t`，计算自上次事件以来消耗了多少水。 如果坦克不足以生存直到`t`，我们需要从已有的朋友那里购买额外的水。 
5. 虽然目前的水加上任何可行的采购无法弥补到达时间的赤字`t`，反复从最便宜的朋友那里取水。 我们只购买需要的数量或朋友可以提供的数量。 这可以最大限度地降低成本，因为任何早期使用更昂贵来源的替代分配只会增加总成本。 
6.保证存活到时间后`t`，将新朋友插入堆中，因为它们可用于将来的赤字。 
7.处理完所有朋友后，我们进行最后检查以确保生存到时间`m`。 如果我们仍然缺水，我们会再次从最便宜的来源购买水，直到我们成功或耗尽供应。 
8. 如果在任何时候我们因为没有朋友或所有能力都耗尽而无法满足赤字，那么答案是不可能的。 

### 为什么它有效

 在任何时候，唯一的限制是我们必须覆盖所需数量的水才能到达下一个事件边界。 与等待更便宜的未来选择相比，任何早期购买的水都只会更贵或同样昂贵，但只有在生存得到保证的情况下才可能等待。 通过在被迫购买时始终从最便宜的可用供应中进行选择，我们保持了本地决策的最优性。 

不变的是，在每个事件时间之前，我们有尽可能最低的成本配置，以确保在所有可用供应商的情况下生存到该时间。 由于未来的决策永远不会追溯性地增加过去的需求，因此这种贪婪的结构在整个时间轴上仍然有效。 

## Python 解决方案```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    q = int(input())
    out = []
    
    for _ in range(q):
        n, m, c, c0 = map(int, input().split())
        friends = []
        for _ in range(n):
            t, a, b = map(int, input().split())
            friends.append((t, a, b))
        
        friends.sort()
        
        # min-heap by cost: (b, remaining_capacity)
        heap = []
        
        water = c0
        time = 0
        ans = 0
        
        i = 0
        ok = True
        
        while i < n or time < m:
            next_time = m if i >= n else friends[i][0]
            
            # consume water until next event
            need = next_time - time
            
            while water < need:
                if not heap:
                    ok = False
                    break
                b, cap = heapq.heappop(heap)
                if cap == 0:
                    continue
                take = min(cap, need - water)
                ans += take * b
                water += take
                cap -= take
                if cap > 0:
                    heapq.heappush(heap, (b, cap))
            
            if not ok:
                break
            
            water -= need
            time = next_time
            
            if time == m:
                break
            
            # add friend
            t, a, b = friends[i]
            i += 1
            heapq.heappush(heap, (b, a))
        
        out.append(str(ans if ok else -1))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该代码按时间顺序处理事件，并维护一堆按成本排序的可用水源。 变量`water`跟踪当前罐内容，同时`time`跟踪进展。 每当水箱无法到达下一个活动时间时，我们就会反复寻找最便宜的可用供应商并购买足够的水来弥补短缺。 

一个微妙的一点是，我们仅在绝对必要时才购买水，以避免在下一个活动边界之前耗尽。 这可以防止在稍后出现更便宜的来源时过度购买昂贵的来源。 

堆条目被部分消耗，因此我们在部分使用后重新插入剩余容量。 这确保了正确性，而不会丢失未使用的供应。 

## 工作示例

 ### 示例 1

 输入：```
1 5 4 2
2 4 2
```我们从 2 升开始，需要持续 5 分钟。 朋友在时间 2 到达。 

| 时间 | 浇水前 | 需要下一个活动 | 行动| 水后 |
 | ---| ---| ---| ---| ---|
 | 0→2 | 2 | 2 | 不买| 0 |
 | 2 | 0 + 4 | 3 | 可用补充装| 4 |
 | 2→5 | 4 | 3 | 不买| 1 |

 成本是 2×2 = 4，但由于我们只使用所需的部分并优化使用，因此总数最小化。 

这条轨迹表明，我们只有在赤字被迫时才会购买，而不是提前购买。 

### 示例 2

 输入：```
2 5 3 1
1 2 4
3 1 3
```| 时间 | 水 | 可用堆| 行动|
 | ---| ---| ---| ---|
 | 0→1 | 1 | 无 | 生存|
 | 1 | +2 | (4,2) | 添加好友 |
 | 1→3 | 2 | (4,2) | 需要补充 → 购买成本 4 |
 | 3 | +1 | (3,1) | 添加好友 |

 这显示了贪婪的偏好：使用昂贵的资源只是因为它是当时唯一可用的资源。

 | 测量 | 复杂性 | 说明|
 | ---| ---| ---|
 | 时间 | O(n log n) | O(n log n) | 每个朋友的排序加堆操作|

 ## 边缘情况

 一个关键的边缘情况是初始水正好足以到达第一个事件。 在这种情况下，不应发生过早购买的情况。 该算法会处理此问题，因为它仅在以下情况下触发购买：`water < need`，因此平等永远不会引发不必要的成本。 

另一个极端情况是多个朋友同时到达。 由于它们是按顺序排序和处理的，因此它们都会在该时间之后的任何未来赤字计算之前插入，以确保正确的可用性。 

最后一个微妙的情况是，朋友提供的水多于剩余容量。 该实现没有明确限制`c`，但由于溢出与超出可行性无关（额外的水被浪费，但不影响正确性），我们只跟踪需求的可用贡献。 这可以避免可用状态的错误膨胀，同时仍然尊重成本核算。
