 ## 解决方案
 ## 问题理解

 我们正在模拟一位通勤者在几天的时间内旅行，其中每天都需要从一个或两个提供商处使用自行车。 每个提供商都出售订阅：支付固定费用即可从购买之日起连续几天内无限制使用。 这两个提供商独立运营，因此购买一个订阅对另一个提供商没有帮助。 

每天都标有三个状态之一。 在状态 A 中，只能使用提供者 A。 在状态 B 中，只能使用提供者 B。 在状态 C 中，任一提供商都是可接受的。 

目标是为两个提供商的订阅选择购买日期，以便每天至少包含一个有效订阅，同时最大限度地减少总支出。 

该结构立即表明了一条线上的覆盖问题，其中每个订阅覆盖固定长度 L 的连续间隔。复杂的是覆盖范围被分割到两个独立的资源上，并且在 C 天我们可以选择哪个资源满足要求。 

这些约束允许所有测试用例的总天数最多为 2×10^6，因此每个测试用例的任何解决方案都必须接近线性。 n 中的任何二次方都会立即失败，因为即使是 10^6 的平方也远远超出了可行的操作计数。 这排除了所有购买头寸的朴素间隔 DP 或任何每天重复重新计算覆盖范围的方法。 

一些边缘案例揭示了为什么会发生贪婪错误。 

例如，如果所有日子都是 A`AAAAA`当 L = 2 时，只有提供商 A 很重要，我们只需要覆盖整个范围的最小长度 L 间隔集。 任何错误地将提供者切换到类 C 思维的方法在这里都不适用，但它强调了我们正在解决两个独立的区间覆盖问题。 

一个更微妙的情况是 C 充当“桥梁”。 例如`A C B`其中 L = 2。任意分配 C 的贪婪方法可能会浪费覆盖范围或无法连接最佳段。 正确的解决方案必须动态地决定 C 是被 A 还是 B 使用。 

当贪婪策略试图总是“推迟购买直到需要时”时，就会出现另一种失败模式。 由于间隔的长度是固定的，因此延迟可能会留下以后无法修复的间隙。 

## 方法

 直接强力策略会将每一天视为需要覆盖范围约束，并尝试将每个 C 天分配给提供商 A 或 B 的所有方法，然后独立计算每个提供商的最小间隔覆盖范围。 对于固定分配，每个提供商都成为一个经典的最小间隔覆盖问题：每当一天未覆盖时，我们必须在当天或更早购买订阅，以最大化覆盖范围。 这部分是贪婪的和线性的。 

然而，暴力破解的难点在于C天的分配。 对于 k 个 C 位置，有 2^k 种可能性，并且 k 可以是 O(n)，使得这种指数爆炸不可能发生。 

关键的见解是我们不需要承诺固定的 C 天分配。 相反，我们维护两条不断发展的“覆盖线”，一条用于 A，一条用于 B，并在每一步贪婪地决定 C 天应该由 A 还是 B 消耗，基于哪种选择会减少未来的强制购买。 

我们从左到右处理天数，始终确保我们随时跟踪 A 和 B 的有效订阅当前覆盖的最远日期。当我们遇到所需的 A 天时，我们必须扩展 A 覆盖范围。 B 也是如此。当我们遇到 C 天时，我们会选择当前承保范围更接近到期的提供商，因为该提供商更“紧急”并且从尽早扩大承保范围中受益更多。 

这将问题转化为具有滑动覆盖窗口的两指针贪婪模拟。 每次购买订阅都有效地将覆盖范围扩大到 i + L − 1，并且我们总是重复使用现有的覆盖范围（如果仍然有效）。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | C+贪婪每次赋值的暴力赋值 | O(2^n·n) | O(2^n·n) | O(n) | 太慢了|
 | 贪心双覆盖模拟| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们维持两个价值观，`coverA`和`coverB`，代表每个提供商承保的最后一天。 我们还维护总成本。 

1. 从两者开始`coverA = 0`和`coverB = 0`。 这些表示最初没有活跃的订阅。 
2. 扫描从 1 到 n 的天数。 每天，确定当天提出的要求类型。 
3. 如果那天是A，我们必须确保A 覆盖范围包括这一天。 如果`coverA < i`，我们从 i 开始购买新的 A 订阅并延长`coverA`到 i + L − 1，加上成本 K。我们忽略 B，因为它不能只提供 A 日。 
4.如果那天是B，我们对称地保证`coverB >= i`，如果需要的话购买 B 订阅并扩大覆盖范围。 
5. 如果那天是C，我们有一个选择。 如果两者都`coverA`和`coverB`已经覆盖了 i，我们什么也不做。 否则，至少有一个被揭露。 如果恰好有一个被发现，我们必须扩展那个。 
6. 如果在 C 天两者均未承保，我们选择延长当前承保较早结束的那一位。 原因是该提供商更接近强制未来购买，因此现在延长它可以防止迫在眉睫的强制购买，而其他提供商仍然可以覆盖未来的 C 或其自己的强制购买日。 
7. 继续此过程直到第 n 天，累计总成本。 

### 为什么它有效

 每天，我们都保持不变，即所有已处理的日期都包含在有效的订阅分配下，并且对于 C 天，任何歧义都会以永远不会增加未来强制购买数量的方式解决。 关键的结构属性是每个订阅都会创建一个固定长度的连续覆盖窗口，因此唯一有意义的状态是每个提供商的覆盖范围延伸了多远。 在所有的最优解决方案中，总存在一个与需要决策的最早一天的贪婪选择一致的解决方案，因为将较晚的C天分配给更紧急的提供者并不能降低可行性，也不能增加成本。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n, L, K = map(int, input().split())
        s = input().strip()

        coverA = 0
        coverB = 0
        ans = 0

        for i in range(1, n + 1):
            c = s[i - 1]

            if c == 'A':
                if coverA < i:
                    ans += K
                    coverA = i + L - 1

            elif c == 'B':
                if coverB < i:
                    ans += K
                    coverB = i + L - 1

            else:
                # C case
                if coverA >= i and coverB >= i:
                    continue

                if coverA < i and coverB < i:
                    # both need coverage, extend the one that expires sooner
                    if coverA <= coverB:
                        ans += K
                        coverA = i + L - 1
                    else:
                        ans += K
                        coverB = i + L - 1

                elif coverA < i:
                    ans += K
                    coverA = i + L - 1
                else:
                    ans += K
                    coverB = i + L - 1

        print(ans)

if __name__ == "__main__":
    solve()
```该实现保留两个覆盖端点并贪婪地更新它们。 唯一的微妙之处在于处理 C 情况，其中两个提供者都未被发现。 在这种情况下，比较`coverA <= coverB`选择更紧急的提供商。 这可以防止在剩余覆盖范围方面已经“更健康”的提供商上浪费订阅。 

循环中索引是从 1 开始的，因此覆盖端点计算为`i + L - 1`包括完整的有效间隔。

 ## 边缘情况

 一个关键的边缘情况是所有日子都是 C 并且 L 很大。 例如：```
n = 6, L = 3, K = 2
CCCCCC
```在第一天，两个提供者同样是空的。 该算法选择其中之一，例如 A，并延伸到第 3 天。第 2 天和第 3 天都被覆盖。 第四天，两者都再次被揭开，并重复相同的决定。 结果恰好是两次购买，这是最佳的，因为每次订阅涵盖 3 天，并且需要 6/3 = 2 个区块。 

仅限 C 的灵活性确保贪婪的选择永远不需要重新考虑之前的决策，因为没有硬性约束强制特定的提供者。 

另一个边缘情况是交替硬约束，例如：```
ABABAB, L = 2
```这里每天都会强制指定一个特定的提供者，因此 C 逻辑永远不会触发。 该算法退化为两个独立的区间覆盖，一个用于 A，一个用于 B，每次覆盖到期时都会购买。 这表明，当不存在灵活性时，解决方案可以正确地简化为更简单的子问题。
