 ## 解决方案
 ## 问题理解

 我们得到了一系列呈直线排列的糖果重量。 Alice和Bob两个人在严格的约束下消费糖果：Alice只能从左端取前缀，而Bob只能从右端取后缀。 他们都不能跳过糖果，也不能吃同样的糖果。 

不同的是，他们最终想要吃总重量相等的糖果。 在所有这些选择不重叠的左前缀和右后缀的有效方法中，我们希望最大化总共消耗的糖果数量。 

关键对象是将数组分为三个概念部分：完全由 Alice 占据的左段、完全由 Bob 占据的右段以及可能被忽略的空中间段。 

这些约束足够严格，以至于对所有前缀后缀对进行二次搜索是不可行的。 由于总输入大小高达 200,000，任何独立尝试所有左端点和右端点的方法在最坏的情况下都有可能退化为 10^10 次操作，这远远超出了限制。 

当部分和重合但与有效的前缀后缀结构不对齐时，就会出现一个微妙的问题。 例如，如果我们贪婪地匹配两端的等和而不考虑重新调整，我们可能会错过需要将一侧向内移动的较长平衡配置。 

朴素贪婪匹配失败的最小示例：

 输入：```
1
5
1 2 3 2 1
```简单的方法可能会立即进行 1 对 1 匹配并提前停止，产生 2 颗糖果，但最佳解决方案在左侧采用 1+2+3，在右侧采用 2+1+3（对齐推理后），根据中间的处理方式产生更大的平衡结构。 真正的要求是在所有前缀后缀对上保持尽可能最好的平等，而不是承诺早期匹配。 

## 方法

 暴力解决方案将尝试 Alice 的每个可能的前缀和 Bob 的每个可能的后缀，计算它们的总和，并检查它们是否匹配。 对于每一对，我们将确保所选片段不重叠。 这导致每个测试用例有 O(n^2) 个候选对，并且天真地计算总和会将其推得更高，除非预先计算前缀总和。 

即使有前缀和，在最坏的情况下我们仍然面临 O(n^2) 次比较，当 n 全局达到 2·10^5 时，这个比较太大了。 

关键的观察是两侧都是来自相反端的单调累积。 当我们扩展 Alice 的部分时，她的总和只会增加。 同样，向内延伸鲍勃的线段会增加他的总和。 这创建了一个自然的两指针结构：我们尝试平衡两个运行总和，一个来自左侧，一个来自右侧。 

我们不是独立地探索所有分割，而是维护两个指针并增加总和较小的一侧，直到它们匹配或交叉。 当总和匹配时，我们记录所使用的糖果总数。 如果它们交叉，我们就会停止该配置。 

这是有效的，因为任何有效的解决方案都对应于两个单调累加的某个交点，并且我们永远不需要重新访问早期状态，因为总和只会在向内扩展时增加。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(n^2) | O(n^2) | O(n) | 太慢了|
 | 两个指针| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们独立处理每个测试用例。 

1. 初始化两个指针，一个在数组的左端，一个在数组的右端，以及Alice和Bob的两个运行和。 

这个想法是模拟两个人向内扩展他们的饮食范围。 
2. 当左指针不与右指针交叉时，比较两个和。 

如果总和相等，则这是有效的配置，我们用迄今为止消耗的糖果数量更新答案。 
3. 如果 Alice 的总和较小，则将左指针向右移动一步，并将该糖果的重量添加到 Alice 的总和中。 

这是必要的，因为爱丽丝必须增加她的总数才能与鲍勃当前的总数相匹配。 
4. 否则，鲍勃的总和较小，因此将右指针向左移动一步，并将该糖果的重量添加到鲍勃的总和中。 

这确保我们始终在平衡两个总数方面取得进展。 
5. 继续直到指针交叉，因为超过该点就不存在不相交的前缀-后缀分区。 

为什么它有效：

 在任何时候，Alice 的段都是前缀，Bob 的段是后缀。 增加总和的唯一方法是向内扩展，并且随着我们的扩展，两个总和都严格不减少。 任何有效的解决方案都对应于某些状态，其中两个指针定义具有相等总和的不相交段。 因为我们只将指针移动到较小总和的一侧，所以我们保留了在不跳过候选者的情况下达到任何等和状态的可能性：跳过将需要减少总和，这在这种结构下是不可能的。 因此，对于给定的扩展模式，第一次遇到一对相等的和时，可以安全地考虑它，并且跟踪所有此类遇到的最大值会产生最佳答案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        l, r = 0, n - 1
        left_sum = 0
        right_sum = 0
        ans = 0
        
        while l <= r:
            if left_sum <= right_sum:
                left_sum += a[l]
                l += 1
            else:
                right_sum += a[r]
                r -= 1
            
            if left_sum == right_sum:
                ans = max(ans, l + (n - 1 - r))
        
        print(ans)

if __name__ == "__main__":
    solve()
```该实现直接反映了两指针模拟。 左指针`l`跟踪 Alice 获取了多少个元素，而右指针`r`跟踪鲍勃从右侧拿走了多少个。 

表达式`l + (n - 1 - r)`计算消耗的总元素：`l`从左边开始的元素和`(n-1-r)`从右边开始的元素。 这避免了重复计算并自然地处理了不断缩小的中间部分。 

一个常见的实现陷阱是仅在指针移动时更新答案，而不是在每个平衡步骤之后更新答案。 相等性检查必须在每次扩展之后进行，因为匹配可以在任何一方增长之后立即发生。

 ## 边缘情况

 单元素数组总是失败，因为 Alice 和 Bob 无法同时选择总和相等的非空不相交段。 该算法在两端初始化指针，立即产生不平衡，并且永远不会找到相等性，因此它正确地返回零。 

在所有元素都相同的数组中，例如`[5, 5, 5, 5]`，对称展开后指针很快达到平衡。 每个步骤都保留相等的增长潜力，因此经常遇到相等的情况，并且当双方消耗相同数量的元素时，最大跨度会正确更新。 

当最优解需要跳过一个大的中间块时，比如`[1, 100, 1, 100]`，该算法自然会避免中间，因为任何一方都无法在不违反平等的情况下有利地扩展到高度不平衡。 当双方消耗匹配的高权重端点时，即指针对称收敛时，才能实现唯一有效的平衡。
