 ## 解决方案
 ## 问题理解

 我们有一个整数矩阵和重复应用于它的三种运算。 

一项操作交换两行。 另一个交换两列。 第三个请求当前在特定行和列中可见的值。 

棘手的部分是矩阵本身可以大到一百万个单元，而查询数量可以达到五十万。 每次都以物理方式重新排列整个行或列的解决方案将花费太多时间移动数据。 

输入首先给出表的尺寸和操作的数量。 然后是初始矩阵。 之后，每个查询都是以下之一：`r x y`交换行`x`带行`y`。`c x y`掉期栏`x`带柱`y`。`g x y`询问当前位于行的值`x`， 柱子`y`。 

对于每一个`g`查询，我们打印请求的数字。 

这些约束极大地影响了解决方案。 矩阵大小最多为`1000 × 1000`，在内存中是可以管理的。 真正的压力来自于`500000`运营。 甚至一个`O(n)`或者`O(m)`每次交换的成本在这里变得危险。 

假设我们物理交换行。 单行交换触及`m`元素。 和`m = 1000`和`500000`操作，大致变成`5 × 10^8`最坏情况下的任务。 Python 将无法在时限内生存。 

我们需要每个操作以恒定的时间运行。 

不明显的部分是，交换开始后，行索引和列索引不再与原始矩阵匹配。 粗心的实现经常会将“当前行位置”与“存储在内存中的原始行”混淆。 

考虑这个例子：```
2 2 3
1 2
3 4
r 1 2
g 1 1
g 2 1
```交换第 1 行和第 2 行后，可见矩阵变为：```
3 4
1 2
```正确的输出是：```
3
1
```忘记重新映射行的有缺陷的实现仍然会从原始矩阵中读取并打印`1`然后`3`。 

列交换从另一个方向产生了相同的问题。```
2 3 2
1 2 3
4 5 6
c 1 3
g 1 1
```可见的第一行变为：```
3 2 1
```答案是`3`， 不是`1`。 

另一个微妙的情况是相同行或列的重复交换。```
2 2 3
1 2
3 4
r 1 2
r 1 2
g 1 1
```两次交换相互抵消。 答案必须回到`1`。 随着时间的推移，错误地改变数据的解决方案可能会偏离真实状态。 

## 方法

 蛮力的想法很简单。 完全按照矩阵的显示方式存储矩阵。 对于行交换，交换两个整个行数组。 对于列交换，迭代每一行并交换两列值。 对于查询，直接读取请求的单元格。 

这是可行的，因为每个操作都直接模拟表状态。 

问题是成本。 行交换需要`O(m)`，因为我们移动了这些行中的所有条目。 列交换需要`O(n)`。 在最坏的情况下，与`500000`交换和尺寸接近`1000`，总工作量达到数亿次操作。 

关键的观察是交换实际上并没有改变值本身。 它们仅更改当前出现在给定可见位置的原始行或列。 

我们可以保留两个映射数组，而不是移动数据：`row_pos[i]`告诉我们哪个原始行当前占用可见行`i`。`col_pos[j]`告诉我们哪个原始列当前占用可见列`j`。 

最初：```
row_pos[i] = i
col_pos[j] = j
```当我们交换行时，我们只交换内部的条目`row_pos`。 

当我们交换列时，我们只交换内部的条目`col_pos`。 

对于查询`(x, y)`，实际值来自：```
matrix[row_pos[x]][col_pos[y]]
```现在每个操作都变成常数时间。 

暴力解决方案之所以有效，是因为它直接维护了精确的可见矩阵。 优化的解决方案之所以有效，是因为矩阵内容永远不会按逻辑移动，只有索引的解释发生变化。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(k × max(n, m)) | O(k × max(n, m)) | O(纳米) | 太慢了 |
 | 最佳 | O(k + nm) | O(nm + n + m) | 已接受 |

 ## 算法演练

 1. 将矩阵读入内存。 

在整个程序中我们保持原始矩阵不变。 
2. 创建行映射数组。`rows[i]`存储当前出现在可见行的原始行`i`。 

最初，每一行都映射到其自身。 
3. 创建列映射数组。`cols[j]`存储当前出现在可见列中的原始列`j`。 

最初，每一列都映射到其自身。 
4. 逐一处理每个查询。 

每个查询都会修改映射或请求一个值。 
5. 对于行交换查询`r x y`， 交换`rows[x]`和`rows[y]`。 

这会立即更新可见顺序，而无需触及矩阵本身。 
6. 对于列交换查询`c x y`， 交换`cols[x]`和`cols[y]`。 

同样，只有列位置的解释发生了变化。 
7. 对于 get 查询`g x y`，计算：```
original_row = rows[x]
original_col = cols[y]
```然后输出：```
matrix[original_row][original_col]
```8. 继续，直到处理完所有查询。 

### 为什么它有效

 不变量是：`rows[i]`始终等于当前显示在可见行的原始行`i`， 和`cols[j]`始终等于可见列中当前显示的原始列`j`。 

最初这是正确的，因为没有任何内容被交换。 

行交换交换两个可见位置，因此交换相应的条目`rows`准确地保留了不变量。 同样的论点也适用于列交换。 

查询要求当前可见的值`(x, y)`。 根据不变量，实际存储的值来自原始行`rows[x]`和原始专栏`cols[y]`。 从未更改的矩阵中读取该单元格始终会返回正确的答案。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())

    table = [list(map(int, input().split())) for _ in range(n)]

    rows = list(range(n))
    cols = list(range(m))

    ans = []

    for _ in range(k):
        t, x, y = input().split()
        x = int(x) - 1
        y = int(y) - 1

        if t == 'r':
            rows[x], rows[y] = rows[y], rows[x]

        elif t == 'c':
            cols[x], cols[y] = cols[y], cols[x]

        else:
            ans.append(str(table[rows[x]][cols[y]]))

    sys.stdout.write("\n".join(ans))

solve()
```矩阵被存储一次，之后不再修改。 这是中心的实现思想。 所有的改变都是通过`rows`和`cols`映射数组。 

这些映射使用从零开始的索引，因为 Python 列表是从零开始的。 每个查询都会立即从输入索引中减一。 忘记这种转换是这个问题中最常见的差一错误。 

对于行交换，代码仅交换内部的两个整数`rows`。 这同样适用于列。 矩阵元素没有物理移动。 

查询操作乍一看有点不对称：```
table[rows[x]][cols[y]]
```这有效是因为`rows[x]`已经告诉我们哪个原始行当前占用可见行`x`。 矩阵本身仍然使用原始坐标。 

输出累积在列表中并在最后打印一次。 在 Python 中，逐行打印最多 50 万次可能会变慢。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | O(nm + k) | 读取矩阵的成本为 O(nm)，每次查询的成本为 O(1) |
 | 空间| O(nm + n + m) | 矩阵存储加上行列映射|

 该矩阵最多包含一百万个整数，完全符合内存限制。 每个查询仅执行几次数组访问或交换，因此即使是五十万个操作也能在时间限制内高效运行。

 ## 边缘情况

 考虑重复交换相同的行。 

输入：```
2 2 3
1 2
3 4
r 1 2
r 1 2
g 1 1
```执行：

 第一次交换后：```
rows = [1, 0]
```第二次交换后：```
rows = [0, 1]
```映射返回到其原始状态。 询问`(1,1)`访问：```
table[0][0] = 1
```该算法自然地处理这个问题，因为交换仅交换映射条目。 

现在考虑独立的行和列重新映射。 

输入：```
2 3 3
1 2 3
4 5 6
r 1 2
c 1 3
g 1 1
```行交换后：```
rows = [1, 0]
```列交换后：```
cols = [2, 1, 0]
```查询`(1,1)`映射到：```
table[1][2] = 6
```可见的左上角单元格真正变成了`6`，因为可见行 1 是原始行 2，可见列 1 是原始列 3。 

最后，考虑最小的可能矩阵。 

输入：```
1 1 1
99
g 1 1
```不存在交换，因为只有一行和一列。 映射数组仍然是：```
rows = [0]
cols = [0]
```查询内容如下：```
table[0][0] = 99
```这证实了该实现可以正确处理边界尺寸，没有特殊情况。
