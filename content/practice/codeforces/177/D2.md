 ## 问题理解

 我们得到一个代表消息的整数序列和另一个代表密钥的较短序列。 两个序列都在从 0 到 c 减 1 的固定模数范围内，并且每次加法都以 c 为模。 

加密被定义为重复的滑动过程。 在从左到右的每个位置 i，我们从 i 开始获取一个长度为 m 的窗口，并将键按元素添加到该窗口中。 这不是单遍更新：每个操作都会立即影响以后的窗口，因为后面的窗口会看到已经修改的值。 

输出是应用所有这些重叠窗口更新后数组的最终状态。 

关键的难点在于每个位置都参与多个窗口。 如果我们从贡献的角度考虑，每个键值 b[j] 都会被添加到许多位置，具体取决于有多少个窗口覆盖该索引。 

这些限制使我们远离简单的模拟。 当 n 达到 100,000 时，直接模拟其中 n 减 m 加 1 的每一步都会更新 m 个元素，在最坏的情况下会导致大约 10^10 次操作，这远远超出了 Python 中 2 秒的限制。 即使在优化的 C++ 中，这也是临界点。 

重叠行为会产生微妙的边缘情况。 由于更新是按顺序应用的，因此天真的解释可能会假设我们可以在原始数组上独立计算每个窗口。 这是不正确的。 

例如，考虑：```
n = 4, m = 2, c = 5
a = [0, 0, 0, 0]
b = [1, 2]
```如果我们错误地将所有窗口应用于原始数组，位置 2 将仅收到来自第二个窗口的贡献。 实际上，由于重叠传播，它也会间接受到先前更新的影响。 这种差异正是为什么必须谨慎处理朴素的类似卷积的思维的原因。 

## 方法

 蛮力解释很简单。 我们模拟从 0 到 n 减 m 的每个步骤 i，并且对于每个步骤，我们将 b[j] 添加到 a[i + j]。 这是正确的，因为它直接反映了定义。 然而，每一步都会涉及 m 个元素，因此在最坏的情况下，总工作量为 n 乘 m，当两者都是 100,000 时，达到 10^10 次操作。 

关键的结构观察是，尽管更新重叠，但每次更新都是相加且独立的。 顺序不会改变每个位置的最终总和，因为每个操作只是加上模 c 的固定值。 这意味着我们可以计算每个 b[j] 对每个位置的贡献次数，而不是模拟该过程。 

修复数组中的位置 i。 它包含在起始索引 s 满足 s ≤ i ≤ s + m − 1 的所有窗口中。该不等式在 [i − m + 1, i] 中变为 s。 因此，将 b[j] 贡献给位置 i 的有效窗口的数量仅取决于 i − s = j 时存在多少这样的 s。 

重写 i − s = j 得到 s = i − j。 因此，当且仅当窗口起始 i − j 有效时，位置 i 才会收到贡献 b[j]，即 0 ≤ i − j ≤ n − m。 这将整个过程转化为直接累积问题，可以使用线性时间来计算
