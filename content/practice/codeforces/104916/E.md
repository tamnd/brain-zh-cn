 ## 解决方案
 ## 问题理解

 该系统模拟了一个有多个灯笼的公园，每个灯笼都装有一盏最终会烧坏的灯。 每盏灯都有已知的使用寿命，因此每盏灯都可以被认为在特定时间产生“到期事件”。 当灯烧坏时，该灯会暂时无法使用，直到从共享库存中收到替换灯。 

模拟并不是简单地孤立地一盏一盏地更换灯。 相反，故障会被批量处理。 当烧毁的灯笼数量达到阈值时，所有受影响的灯笼都会被收集在一起。 然后按照索引升序处理这些灯，并从有限的库存中安装替换灯。 每次更换都会立即为该灯笼安排一个新的燃尽时间，以便该灯笼重新进入未来故障系统。 

该过程按照灯故障的时间顺序日复一日地继续。 当库存中没有足够的灯来执行所需的更换时，模拟会在第一时刻停止，答案是发生这种情况的那一天。 

因此，输入描述了一个独立的周期性计时器系统（每个灯笼一个）、触发故障批量处理的全局阈值 m 以及在处理过程中可能耗尽的有限资源池。 输出是单个时刻：系统无法再完成所需维护的最早一天。 

从复杂性的角度来看，自然约束意味着在每个时间步扫描所有灯笼的简单模拟是立即不可行的。 该过程由事件（灯到期）驱动，并且此类事件的数量可能很大，可能高达执行的更换数量。 这迫使使用对数时间数据结构的事件驱动方法。 

一些边缘情况破坏了简单的实现。 

问题之一是同时发生故障。 如果多个灯同时失效，则必须一起处理。 例如，如果三个灯笼都在时间 10 过期且 m 等于 2，则必须在同一批次中收集所有三个灯笼，而不是分成多天收集。 一种逐一处理过期的简单方法会错误地触发多个部分替换。 

另一个问题是补货时按灯笼索引排序。 如果该批次包含任意顺序的灯笼，但必须从最小索引开始分配替换，则无法对该批次进行排序会导致错误的库存消耗顺序，从而导致未来故障的时间不正确。 

最后，在尝试批量重新填充任何灯笼之前，必须检查库存耗尽情况。 如果批次中途库存不足，则必须立即停止模拟。 

## 方法

 直接模拟保持每个灯笼的当前状态，并重复扫描下一个故障时间。 每个时间步骤都会处理所有过期的灯，重建状态，然后继续。 虽然概念上很简单，但这种方法会退化为重复扫描或分类所有灯笼。 如果有 n 个灯笼，每个灯笼可能有 O(n) 个事件，这会导致 O(n²) 行为或更糟。 

关键的观察结果是该系统完全是事件驱动的。 每个灯笼都会提供一系列未来的到期时间，而我们只关心下一个最小的到期时间。 这建议将所有活动灯维护在按到期时间排序的结构中。 最小堆自然支持有效地提取最早的故障。 

第二个结构要求是按时间对故障进行分组。 当我们提取最小过期时间时，我们还必须收集所有具有相同过期时间的灯笼。 这可以防止错误地分割同时发生的事件。

一旦形成一批失败的灯笼，我们就必须按照灯笼索引递增的顺序对其进行处理。 这需要第二个有序结构或排序步骤。 分配替换后，每个受影响的灯笼都会产生一个新的到期时间，并且必须重新插入到全局时间排序结构中。 

该过程变成了一个双结构系统：一个按过期时间排序的堆用于事件调度，另一个按灯笼索引排序的临时排序结构用于批处理。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力模拟| O(n²) 或更糟 | O(n) | 太慢了|
 | 基于堆的事件模拟| O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 我们维护一个最小堆（expiration_time，lantern_id），代表每个灯笼的下一次失败时间。 我们还备有可用灯具的库存柜台。 

我们按照时间递增的顺序重复处理事件。 

1. 使用每个灯笼的初始过期时间来初始化堆。 每个灯笼只贡献一个条目。 这代表每个灯笼第一次失败。 
2. 反复从堆中提取最小过期时间。 这给出了至少一盏灯烧坏的最早时刻。 
3. 收集过期时间等于该最小时间的所有堆条目。 这些代表所有同时失效的灯笼。 我们将它们分组在一起，因为它们必须作为一个批次进行处理。 
4. 检查这批灯笼有多少个。 如果库存少于此数字，则该过程无法继续，当前时间就是答案。 
5. 按索引对受影响的灯笼进行排序。 这确保了以正确的确定性顺序分配替换。 
6. 对于按递增索引顺序排列的每个灯笼，从库存中消耗一盏灯，通过添加其固定生命周期来计算其新的到期时间，并将更新的事件推回到堆中。 
7. 继续该过程直至库存耗尽。 

关键的不变量是堆始终存储每个当前活动灯的下一个有效过期时间。 每次处理批次时，我们都会准确删除当前最短时间发生的那些事件，并用新的未来事件替换它们。 没有灯笼被跳过或重复，并且按时间排序保证了模拟时间线的正确性。 

## Python 解决方案```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m, stock = map(int, input().split())
    
    # lifetime of each lantern's lamp
    life = list(map(int, input().split()))
    
    # current heap: (expire_time, lantern_id)
    heap = []
    
    for i in range(n):
        heapq.heappush(heap, (life[i], i))
    
    current_time = 0
    
    while heap:
        t, _ = heap[0]
        
        # collect all events at time t
        batch = []
        while heap and heap[0][0] == t:
            _, i = heapq.heappop(heap)
            batch.append(i)
        
        # check stock
        if stock < len(batch):
            print(t)
            return
        
        # process in index order
        batch.sort()
        
        for i in batch:
            stock -= 1
            new_t = t + life[i]
            heapq.heappush(heap, (new_t, i))
    
    # if never exhausted
    print(-1)

if __name__ == "__main__":
    solve()
```堆存储每个灯笼的下一次故障时间。 每次迭代都会拉出最早的时间并收集当时失败的所有灯笼。 按索引对批次进行排序会强制执行所需的重新填充顺序。 每次更换都会立即安排该灯笼的下一次故障时间，从而保留事件驱动的结构。 

一个微妙的点是我们只在完全形成批次后检查库存。 这是必要的，因为批次的部分处理是无效的：要么组中的所有灯笼都被重新填充，要么没有。 

## 工作示例

 考虑一个具有三个灯笼、生命周期的小型系统`[2, 3, 2]`，和库存`5`。 

我们从堆条目开始`(2,0)`,`(3,1)`,`(2,2)`。 

| 步骤| 堆最小 | 批量| 库存| 行动|
 | --- | --- | --- | --- | --- |
 | 1 | 2 | [0,2]| 5 | 处理两者 |
 | 2 | 3 | [1] | 3 | 流程一|

 在时间 2，灯笼 0 和 2 同时失效。 由于库存充足，因此两者均被更换并按时间 4 和 4 推迟。在时间 3 时，灯笼 1 发生故障并被更换。 

这证明了同时发生的事件的正确分组。 幼稚的逐灯笼处理会错误地分别处理灯笼 0 和 2，从而破坏预期的批处理逻辑。 

现在考虑库存耗尽。 生命周期`[1,1,1]`， 库存`2`。 

| 步骤| 堆最小 | 批量| 库存| 行动|
 | --- | --- | --- | --- | --- |
 | 1 | 1 | [0,1,2]| 2 | 停止|

 在时间 1，所有三个灯笼同时失效。 批量大小超过库存，因此答案为 1。任何一一处理故障的方法都会错误地认为库存足以进行两次单独的更新。 

## 复杂度分析

 | 测量 | 复杂性 | 说明|

 ## 边缘情况

 一个关键的边缘情况是所有灯笼同时失效。 在尝试任何替换之前，该算法必须形成包含所有这些的单个批次。 基于堆的分组保证了这一点，因为我们在处理之前不断弹出具有相同时间戳的所有条目。 

另一个微妙的情况是批次期间的部分库存可用性。 正确的行为是在发生任何替换之前停止。 该实现在消耗库存之前根据完整批次大小检查库存，确保原子处理。 

最后的边缘情况是重复重新插入具有相同寿命的灯笼。 即使多个灯笼生成相同的未来到期时间，它们仍然是独立处理的，因为每个堆条目都带有唯一的灯笼标识符。 这可以防止错误地合并不同状态的冲突。
