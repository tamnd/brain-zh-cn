 ## 问题理解

 我们得到固定的衣物集合，每件衣物都有物理宽度和干燥曲线。 在数周内，哈利有两条长度相等的平行晾衣绳，并且每周可用长度都会发生变化。 每件物品都必须在一周开始时立即悬挂，如果正常悬挂，它恰好占据一行的空间，或者可以将其分成两行，在这种情况下，它同时使用两行上的空间，但干燥得更快。 

因此，每个项目都有两种“模式”。 在正常模式下它占据一个连续的长度段$d_i$一行并完成后$t^{slow}_i$。 在加速模式下，它占据相同的宽度，但会在两条线上拉伸，同时占用两条线的空间并在完成后完成$t^{fast}_i$， 在哪里$t^{fast}_i \le t^{slow}_i$。 给定一周的目标是将每个物品分配给两种模式之一，并将所有物品放置在两条线上而不重叠，以便最大限度地缩短所有物品的最大干燥时间。 如果不存在符合线长度约束的放置，我们必须输出不可能。 

输入给出$N$项目一次。 每个查询给出一个行长度$L_j$。 对于每个查询，我们必须计算可实现的最佳完成时间。 

约束足够大，以至于不可能对所有项目进行任何每次查询的贪婪放置或模拟。 和$N \le 3 \cdot 10^4$和$Q \le 3 \cdot 10^5$， 甚至$O(N)$每个查询已经推入$10^9$运营。 这会立即排除每个查询从头开始重新计算任何分配的情况。 

一个关键的困难在于，使用快速模式的可行性取决于线路容量，并且不同的项目子集可能需要根据线路容量切换模式。$L$，这使得该结构本质上是全局的。 

天真的推理的一个微妙的失败案例是假设按宽度对项目进行排序并贪婪地放置它们可以提供最优性。 例如，选择最大的物品来始终快速移动可能会浪费生产线容量，从而阻碍较小但数量众多的物品。 另一种失败模式是将可行性视为每条线的一个背包； 它忽略了快速模式项目同时消耗两条线。 

## 方法

 直接的暴力方法将尝试将每个项目的每个分配设置为慢速或快速模式，并且对于每个分配检查项目是否可以打包成两行长度$L$。 即使使用贪婪装箱策略以最佳方式完成装箱，仅模式分配的数量就是$2^N$，这是不可行的。 

即使我们固定一个阈值时间$T$并且只允许带有以下内容的项目$t^{fast}_i \le T$为了可能更快，我们仍然需要决定将这些项目的哪些子集实际分配给快速模式，因为快速模式消耗两倍的空间资源。 核心观察是，问题不在于订购物品，而在于选择将多少物品分配给昂贵的“双线”资源与单线资源。 

我们可以通过选择“广泛消耗”的项目子集（快速模式）来重新解释该问题。 如果一个项目是快速模式，它会消耗$d_i$同时从两条线路中获取单位，否则会消耗$d_i$仅在一根线上。 总可用资源是两行长度$L$，但分配给慢速模式的项目被分成两条线，因此真正的约束是平衡总宽度分布。 

关键的简化来自于查看固定时间阈值的可行性$T$。 我们只考虑具有$t^{fast}_i > T$作为强制慢速模式候选者和项目$t^{fast}_i \le T$一样灵活。 在灵活的项目中，选择快速模式会减少单行的负载，但会增加双行的负载，因此可以通过按宽度对项目进行排序并贪婪地决定有多少项目运行得快来进行权衡。 

这将每个可行性检查转换为结构化计算，可以有效地进行预处理和回答，从而在回答时间内实现二分搜索。

 ## 算法演练

 ### 关键思想：对答案进行二分搜索

 我们将每个查询的最终答案视为一个值$T$。 对于固定的$T$，我们检查所有项目是否都能按时间完成$T$在最佳布局下。 

### 第 1 步：快速预处理项目

 我们按项目对项目进行分组$t^{fast}_i$。 对于候选人$T$, 项目与$t^{fast}_i > T$被强制进入慢速模式。 其余的可以选择慢速和快速模式。 

这将“强制慢速”和“可选快速”项目分开。 

### 第 2 步：计算宽度要求

 对于固定的$T$，每个项目都有一个宽度要求：

 如果一个项目很慢，它会消耗$d_i$恰好在一条线上。 如果速度快的话就会消耗$d_i$在两条线上。 

因此，就共享容量而言，快的项目更昂贵，而慢的项目则更灵活。 

问题变成了决定哪些可选项目应该很快，以便我们可以将所有内容打包成两行长度$L$。 

### 步骤 3：降低平衡负载的可行性

 我们将这两行解释为两个容量数组$L$。 慢速项目可以在线路之间任意分割，因此它们的行为就像单个单元负载。 快速项目同等地消耗两条线，因此它们的作用类似于同步加载。 

一个关键的观察结果是，可行性仅取决于总宽度和我们引入的“双人入住”数量。 

如果我们让所有可选项目都很慢，可行性是最容易的。 将项目转为快速模式会降低灵活性，因此我们仅在必要时才执行以满足时间限制。 

### 第四步：排序后的贪心结构

 我们按宽度降序对可选项目进行排序。 快速分配的最佳候选者是最大的项目，因为根据结构约束，快速分配大型项目可以最有效地减少单线拥塞。 这种排序使我们能够测试需要多少快速分配。 

我们迭代有多少最大的物品被强制进入快速模式，并检查包装是否可行。 

### 步骤 5：固定配置的可行性检查

 考虑到分为慢速和快速项目：

 我们必须确保两条线路都能容纳所有慢速物品，并且快物品不超过共享容量。 这减少了检查分配给每条线路的总负载是否不超过$L$，考虑到快速项目同时占据两者。 

如果满足这两个约束，则该配置是可行的。 

### 步骤 6：每个查询进行二分搜索

 对于每个查询长度$L_j$，我们二分查找最小值$T$使得可行性成立。 

### 为什么它有效

 正确性取决于时间上可行性的单调性$T$。 如果所有项目都能按时完成$T$，那么他们也可以在任何更长的时间内完成，因为约束只会放松：更多项目有资格进入快速模式。 这种单调结构允许二分搜索。 

在固定的时间内$T$，贪心选择哪些可选项目变得更快是最优的，因为宽度主导决策影响，并且快速模式统一增加共享消耗，同时降低每行灵活性。 按宽度排序可确保我们始终优先转换最“放置成本最高”的项目，这可以防止碎片化，否则会破坏可行性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def feasible(items, L, T):
    slow = []
    fast = []

    for d, tf, ts in items:
        if ts <= T:
            # already finished even in slow mode
            continue
        if tf <= T:
            fast.append(d)
        else:
            slow.append(d)

    slow.sort(reverse=True)
    fast.sort(reverse=True)

    # try assign greedily to two lines
    left1 = L
    left2 = L

    # place fast items first (they occupy both)
    for d in fast:
        if left1 >= d and left2 >= d:
            left1 -= d
            left2 -= d
        else:
            return False

    # place slow items greedily on better-fitting line
    for d in slow:
        if left1 >= d:
            left1 -= d
        elif left2 >= d:
            left2 -= d
        else:
            return False

    return True

def solve():
    N, Q = map(int, input().split())
    items = [tuple(map(int, input().split())) for _ in range(N)]
    queries = [int(input()) for _ in range(Q)]

    # candidate times are all tf and ts values
    cand = sorted({x[1] for x in items} | {x[2] for x in items})

    def check(L):
        lo, hi = 0, len(cand) - 1
        ans = -1
        while lo <= hi:
            mid = (lo + hi) // 2
            if feasible(items, L, cand[mid]):
                ans = cand[mid]
                hi = mid - 1
            else:
                lo = mid + 1
        return ans

    out = []
    for L in queries:
        if not feasible(items, L, float('inf')):
            out.append("-1")
        else:
            out.append(str(check(L)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该实现首先隔离可行性检查，它模拟项目在给定时间阈值下如何占据两行。 快速模式项被强制同时消耗两行，而慢速模式项则被贪婪地打包到有空间的行中。 这种贪心分配之所以有效，是因为在固定的$T$，重要的是放置是否存在，而不是确切的安排。 

然后，求解器将所有相关时间候选压缩到排序列表中，因为最佳答案必须来自现有的$t^{fast}_i$或者$t^{slow}_i$。 对于每个查询，我们首先检查是否存在任何排列； 如果不是，我们立即返回-1。 否则我们对候选时间进行二分搜索。 

一个微妙的实现细节是确保快速项目放置在慢速项目之前，因为快速项目同时约束两条线。 颠倒此顺序将错误地填充一行并错误地拒绝可行的配置。

| T | 快速物品| 慢速物品| 左线1 | 左线2 | 可行|
 | --- | --- | --- | --- | --- | --- |
 | 1 | {2} | {1,3} | 3 | 3 | 没有 |

 在$T=1$，项目 2 变得很快，但项目 3 仍然很慢并且无法容纳。 在$T=2$，第 1 项和第 2 项都可以很快，这可以减少各个线路上的压力，足以允许放置。 

该轨迹表明，可行性是由快速转换和封装灵活性之间的相互作用驱动的，而不仅仅是总宽度。

 ## 边缘情况

 一个关键的边缘情况是所有项目都必须处于慢速模式，因为没有项目满足$t^{fast}_i \le T$。 在这种情况下，算法简化为纯粹的两行装箱问题。 可行性函数仍然有效，因为它尝试将每个项目贪婪地放置在有空间的行上。 这确保了当总宽度超过时正确拒绝$2L$。 

当除了一个大的慢速项目之外几乎所有项目都很快时，会出现另一种边缘情况。 该单个慢速项目可能会强制剩余项目的特定分配，并且首先订购快速项目可确保它不会被较早的放置所阻止。 

最后，当$L$非常大，所有物品都很合适。 该算法可以处理这个问题，因为快速放置总是成功，而慢速项目可以在没有冲突的情况下进行分配，从而立即实现可行性，并且二分搜索返回尽可能短的时间。
