 ## 解决方案
 ## 问题理解

 我们得到两个仅由两个符号组成的字符串，一个“减号”和一个“加号”。 唯一允许的移动采用两个相邻的减号，并将它们替换为一个加号，这会将字符串缩短一个字符。 该操作可以按任意顺序重复任意次数。 

任务是确定是否可以使用这些替换将起始字符串转换为目标字符串。 

这些限制迫使我们处理多达 100,000 个测试用例，总输入大小高达 200,000 个字符。 这立即排除了任何重复重写字符串的二次或模拟。 任何正确的方法都必须对每个字符处理恒定的次数。 

一个微妙的点是，操作会改变长度和局部结构，因此，如果假设操作顺序无关紧要，那么天真的“模拟所有归约”方法不仅在性能上失败，而且在正确性上也会失败。 

打破天真的思维的一个边缘情况是当多个归约在一长串减号内相互作用时。 例如，像“----”这样的字符串有多个有效的缩减路径，不同的选择会改变加号出现的位置。 另一种情况是，目标的加号位置与源中的原始加号并不明显对应，因为可以通过合并减号对来创建加号。 

## 方法

 一个蛮力的想法是重复扫描字符串并用“+”替换任何出现的“--”，然后继续，直到没有剩余的移动。 从某种意义上说，这是正确的，因为它探索了有效的缩减过程，但它太慢了，因为每次替换都会移动字符串，并且单个测试用例可能会退化到二次时间。 

关键的观察结果是，该操作仅影响相邻的减号字符，并且不会与加号交互，除非插入它们。 这将结构隔离成最大连续的减号块。 在这样的块内，操作永远不会跨越其边界，因为加号充当分隔符。 

因此，问题归结为理解在执行任意归约后，单个连续减号块会变成什么。 每个操作都会删除两个减号并引入一个加号，因此在长度为 L 的块内，我们实际上是在选择要转换的不相交对的数量。 如果我们在块内执行 p 个操作，那么我们会消耗 2p 个负号并产生 p 个正号，留下 L − 2p 个负号。 

这意味着从块导出的任何最终配置必须满足两个约束：从该块产生的符号总数由选择的对数决定，剩余负号的奇偶校验由使用的对数决定。 

关键的简化是，在一个块内，我们只关心计数：剩余多少个减号以及创建了多少个加号。 它们的确切交错与可达性无关，因为不同的配对选择可以实现与这些计数一致的任何排序。 

因此，如果我们可以将源中长度为 L 的每个块划分为一定数量的减号和加号字符（对应于 L = m + 2p），则源中每个长度为 L 的块都可以匹配目标的一个段，其中 m 是我们保留的减号数量，p 是产生的加号数量。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力模拟 | 每个测试用例的 O(n²) | O(n) | 太慢了 |
 | 块计数和匹配 | 总共 O(n) | O(n) | 已接受 |

 ## 算法演练

 我们通过将两个字符串分成连续的相同字符的交替块来处理它们。 对于每个字符串，这会生成一系列段，例如“++++”、“----”、“++”、“---”等。

然后，该算法按顺序将目标字符串中的段与源字符串中的段进行匹配，但仅将负块视为可消耗资源。 

1. 将两个字符串拆分为连续的相同字符。 
2. 从左向右遍历目标路线。 每当我们在目标中遇到一串加号时，它必须通过现有的加号或通过转换某些源减号块内的减号对来生成。 因此，我们不需要在结构上匹配正运行，只需确保它们可以由可用的负对来解释。 
3. 将指针保持在源运行上，并将负运行作为资源重点关注。 对于源中长度为 L 的每个减号游程，我们可以通过配对相邻的减号字符来生成一定数量的加号。 每对消耗两个减号并产生一个加号。 
4. 当在长度为 m 的目标中处理负运行时，我们确保它可以由可用源减去容量形成。 我们聚合源减号运行，直到我们有足够的总容量来满足剩余减号加上必须在该部分中创建的加号数量的两倍的目标要求。 
5. 如果在任何时候我们需要的负容量多于相应源区域中可用的容量，则转换是不可能的。 
6. 继续，直到处理完所有运行，确保没有剩余的不匹配结构。 

### 为什么它有效

 源中的每个减号运行都充当令牌的存储库。 目标中保留的每个减号消耗一个令牌，而目标中的每个加号消耗两个令牌，因为它必须来自合并对。 由于操作永远不会跨源中现有的加号运行创建的结构边界移动信息，因此唯一有意义的约束是每个所需的段是否可以通过来自相应可用区域的足够数量的减号代币来资助。 贪婪的消耗确保我们永远不会过度使用源块并尊重配对的不可逆性质。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def compress(s):
    runs = []
    i = 0
    n = len(s)
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        runs.append((s[i], j - i))
        i = j
    return runs

def solve():
    k = int(input())
    out = []
    
    for _ in range(k):
        s = input().strip()
        t = input().strip()

        rs = compress(s)
        rt = compress(t)

        i = j = 0
        ok = True

        while i < len(rs) or j < len(rt):
            if i == len(rs):
                ok = False
                break
            if j == len(rt):
                ok = False
                break

            cs, ls = rs[i]
            ct, lt = rt[j]

            if cs == '+':
                if ct != '+':
                    ok = False
                    break
                if ls != lt:
                    ok = False
                    break
                i += 1
                j += 1
                continue

            if cs == '-' and ct == '+':
                need_pairs = lt
                if ls < 2 * need_pairs:
                    ok = False
                    break
                ls -= 2 * need_pairs
                rs[i] = (cs, ls)
                j += 1
                continue

            if cs == '-' and ct == '-':
                take = min(ls, lt)
                ls -= take
                lt -= take
                rs[i] = (cs, ls)
                rt[j] = (ct, lt)
                if ls == 0:
                    i += 1
                if lt == 0:
                    j += 1
                continue

            ok = False
            break

        out.append("YES" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```该代码首先将两个字符串压缩为运行，因此我们永远不会逐个字符地进行操作。 然后它使用两个指针遍历两个运行列表。 加号运行必须完全匹配，因为源中的加号不能消失或重新定位。 减号运行可以灵活处理：它们可以保留减号字符，也可以成对使用以在目标中生成加号。 仔细递减游程长度可确保我们仅使用可用容量一次，并且不会在不同的匹配中重复使用字符。 

一个常见的陷阱是未能减少部分消耗后的就地运行。 这在这里很重要，因为单个源运行可能会分为多个目标运行。

 ## 边缘情况

 一个关键的边缘情况是减号游程太短而无法支持目标所需的加号数量。 例如，如果源包含“--”但目标需要“+++”，算法会立即检测到配对容量不足，因为每个加号需要两个减号。 

另一个边缘情况是不匹配的加结构。 如果源包含长度为 3 的加号游程，而目标在同一结构位置需要长度 2，则算法会拒绝它，因为无法删除或合并现有的加号。 

第三种情况是处理所有目标运行后剩余的负号。 这是允许的，因为操作是可选的，并且算法从不强制完全消耗源运行，仅根据目标需求检查可行性。
