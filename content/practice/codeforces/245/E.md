 ## 解决方案
 ## 问题理解

 我们得到了一份按时间顺序排列的俱乐部单个夜晚的日志。 输入字符串中的每个字符代表一个事件：“+”表示有人进入俱乐部，“-”表示有人离开。 我们不知道在日志开始之前最初有多少人在里面，我们也不知道在日志结束时里面有多少人。 

关键的微妙之处在于我们并不是试图重建个体的确切历史。 每个人可以多次进入和离开。 相反，我们只关心可能产生观察到的进入和退出序列的不同人员的最小数量。 

这意味着我们可以在不同的事件中自由地“重用”身份，只要我们不违反一致性：每个“-”必须对应于当前在里面的人，并且我们希望最大限度地减少总体上需要的不同个人的数量。 

字符串长度最多为 300 的约束足够小，即使是二次或简单的贪婪线性扫描也足够了。 任何尝试显式模拟所有分配的解决方案仍然没问题，但结构表明答案仅取决于在有足够的条目出现支持它们之前发生了多少次退出。 

一个天真的错误是假设人数等于内部同时容纳的最大人数。 这接近正确的想法，但是当在看到任何条目之前退出时就失败了。 

例如，考虑序列“-”。 如果我们假设一开始没有人在里面，我们就会陷入困境，因为有人在有人进入之前就离开了。 正确的解释是，一开始就至少有一个人在里面。 所以答案是1。 

另一个边缘情况是交替模式，如“-+-+-”。 天真的运行余额可能会多次变为负值，每次人们都可能错误地认为必须介绍一个新人。 但实际上，只要我们正确地考虑了初始占用情况，一个人就可以反复循环进出。 

## 方法

 强力解释会尝试将每个事件显式分配给一个身份。 我们将模拟所有可能的方式，将“+”事件与现有人员或创建新人员相匹配，并将“-”事件与当前在场人员相匹配。 每项任务都会跟踪使用了多少不同的人员。 在最坏的情况下，长度为 n 时，分配的数量会组合增长，因为每个“+”都可以重用现有人员或引入新人员，而每个“-”可以与任何当前活跃的人员匹配。 这很快就会变成指数级的，大约为 O(2^n) 或更糟，即使 n = 300 这也是不可行的。 

关键的观察是我们实际上从来不需要跟踪身份。 我们只需要确保在每个“-”事件中，都有人可以离开。 如果当前模拟的内部人数变为负值，则意味着我们一开始假设的人数太少，并且我们必须至少再多安排一个人。 

因此，我们假设初始人员为零来模拟该流程，并跟踪“内部计数”的运行余额。 每个“+”增加它，每个“-”减少它。 每当它降至零以下时，我们就会从概念上从一开始就“添加”一个人来解决这个赤字。 每一个这样的缺陷都对应于在初始集合中需要一个额外的不同的人。 

最后，我们还考虑最终的平衡：如果我们最终得到的人数为正数，那么这些人也必须对应于在某个时刻存在的不同个体，因此他们对总数的最小值做出了贡献。 

这将问题简化为跟踪运行余额低于零多远，并将其与最终的正盈余相结合。

 ## 算法演练

 我们模拟该序列，同时维护一个整数变量，表示当前假设有多少人在里面，从零开始。 

1. 初始化变量`cur = 0`代表内部现有人员，以及`need = 0`代表由于提前退出而我们被迫引入的额外人员数量。 
2. 从左到右扫描输入字符串中的每个字符。 
3. 如果字符是“+”，则递增`cur`因为有人进入俱乐部。 
4. 如果字符为“-”，则减1`cur`因为有人离开了俱乐部。 
5. 如果在任何时候`cur`变成负数，我们不能允许负数的人进去。 这意味着在任何可用的进入者存在之前要求一个人离开的顺序。 
6. 每当`cur < 0`, 增量`need`加 1 并递增`cur`按 1 来模拟在开始时介绍一个在日志开始之前就已经在里面的新人。 
7. 处理完所有事件后，答案是`need + cur`。 

最终总和之所以有效，是因为`need`考虑到需要证明提前退出合理性的人，同时`cur`代表由于条目不匹配而必须仍然存在的人。 

### 为什么它有效

 在序列的每个前缀处，我们认为调整后的`cur`永远不会是负数。 每次我们修复一个否定前缀时，我们都有效地断言在序列开始之前必须有另一个人在场。 没有其他结构可以解决这一缺陷，因为退出不能在不违反时间顺序的情况下重新分配给未来的条目。 最后剩余的正余额代表进入但从未离开的人，并且每个人也必须对应一个独特的个体。 由于每次纠正都是由不同的违规事件强制进行的，并且每个剩余的盈余对应于不同的不匹配的进入链，因此总和给出了与日志一致的最小人数。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    
    cur = 0
    need = 0
    
    for ch in s:
        if ch == '+':
            cur += 1
        else:
            cur -= 1
        
        if cur < 0:
            need += 1
            cur += 1
    
    print(need + cur)

if __name__ == "__main__":
    solve()
```该代码准确地反映了模拟。 变量`cur`假设我们从零开始，跟踪里面假设的人数。 循环内的修正步骤增强了可行性：每当发生无人可用的离开时，我们立即考虑隐藏的初始参与者。 

最后总和`need + cur`结合了两个逻辑上不同的贡献：由于提前退出而强制初始占用者，以及剩余的不匹配的条目。 

## 工作示例

 ### 示例 1：“+-+-+”

 我们一步步跟踪这个过程。 

| 步骤| 查尔 | cur（修复前）| cur（修复后）| 需要|
 | --- | --- | --- | --- | --- |
 | 1 | + | 1 | 1 | 0 |
 | 2 | - | 0 | 0 | 0 |
 | 3 | + | 1 | 1 | 0 |
 | 4 | - | 0 | 0 | 0 |
 | 5 | + | 1 | 1 | 0 |

 最终答案是`need + cur = 0 + 1 = 1`。 

这显示了一个完美平衡的序列，除了最后一个额外的条目，这意味着一个人可以重复执行所有操作。 

### 示例 2：“--+”

 | 步骤| 查尔 | cur（修复前）| cur（修复后）| 需要|
 | --- | --- | --- | --- | --- |
 | 1 | - | -1 | 0 | 1 |
 | 2 | - | -1 | 0 | 2 |
 | 3 | + | 1 | 1 | 2 |

 最终答案是`2 + 1 = 3`。 

这表明，多次提前退出迫使我们在日志开始之前假设多个初始占用者。

 ## 边缘情况

 对于单个字符输入“-”，运行余额立即变为负数。 算法增量`need`为 1 并恢复`cur`为 0。这正确地模拟了在日志开始之前必须有人在场的情况。 

对于像“---”这样重复提前退出的序列，每一步都会导致赤字，所以`need`增加三倍。 最终结果变为3，反映出一开始必须存在三个不同的人来支持所有出口。 

对于以多余条目结尾的序列，例如“++”，算法永远不会触发更正，最终答案只是 2，反映了两个不同的个体进入并且从未与退出匹配。
