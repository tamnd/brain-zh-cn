 ## 解决方案
 ## 问题理解

 我们给出了两个长度为 n 的序列，它们描述了相同的问题主题多重集。 第一个序列描述了解决方案一个一个地变得可用的顺序，并且每个新解决方案都被放入堆栈中。 第二个序列描述了从堆栈中取出并处理这些解决方案的确切顺序。 

每时每刻，我们要么将第一个序列中的下一个可用元素压入堆栈，要么弹出堆栈顶部并将其输出作为第二个序列的下一个所需元素。 目标是确定是否可以执行恰好 n 个压入和 n 个弹出的序列，以便弹出的序列与第二个数组完全匹配，如果可以，则构造这样的操作序列。 

约束 n ≤ 100 意味着任何二次解甚至使用线性堆栈操作的简单模拟都足够快。 除了简单的贪婪模拟之外，不需要高级数据结构或优化。 唯一的微妙之处是重复项下的正确性，因为值并不不同，并且必须仔细调整通常的“1 到 n 的堆栈排列”直觉。 

天真的尝试可能会尝试回溯所有可能的推送和弹出交错。 这种方法每一步都有分支，导致状态呈指数级增长。 即使 n = 100，这也是完全不可行的。 

一个更微妙的错误方法是始终先推送所有内容，然后尝试按顺序弹出。 当所需的输出需要在稍后的元素被推送之前提前弹出时，这显然会失败。 

关键的边缘情况模式是当下一个所需的输出在未来的输入序列中更深时，但不同的元素当前在堆栈上阻塞它。 如果我们提前弹出错误的元素，我们可能会永久阻止所需的订单。 

## 方法

 蛮力方法考虑 S 和 C 操作的每个序列，维护当前堆栈并检查生成的输出是否与目标匹配。 由于 2n 个位置中的每一个都可以是带有约束的 S 或 C，因此有效序列的数量会组合增长。 在最坏的情况下，它会按照类似加泰罗尼亚数字的结构进行探索，该结构随着 n 呈指数增长。 即使 n = 30，这也很快变得不可能。 

关键的观察是该过程具有很强的贪婪结构。 一旦一个元素位于堆栈顶部并且它与下一个所需的输出匹配，延迟其删除永远不会有帮助。 任何其他选择只会将其埋得更深，并有可能阻碍未来所需的元素。 这意味着每当栈顶匹配下一个需要的元素时，我们必须立即弹出。 

有了这个想法，整个过程就变成了对输入序列的一次从左到右的扫描，模拟推送，同时尽可能连续弹出。 这减少了维护堆栈和指向目标序列的指针的问题。

 | ---| ---| ---| ---|
 | 蛮力 | O(2^{2n}) | O(2^{2n}) | O(n) | 太慢了|
 | 最佳| O(n) | O(n) | 已接受 |

 ## 算法演练

 我们使用堆栈、两个指针和结果字符串来模拟该过程。

1. 初始化一个空堆栈，并为目标序列设置指针 j = 0。 
2. 在源序列上从 0 到 n − 1 迭代 i。 对于每个元素，将其压入堆栈并记录“S”操作。 推送是必要的，因为我们只能通过堆栈结构访问元素，并且必须使当前源元素可用于未来潜在的匹配。 
3. 每次压入后，反复检查栈顶。 当堆栈不为空且顶部等于当前目标元素 b[j] 时，将其从堆栈中弹出，记录“C”，并递增 j。 这种贪婪的删除确保我们永远不会延迟可用的正确匹配，因为延迟只会在其上方添加阻塞元素。 
4. 继续此过程，直到所有源元素均已推送。 
5. 完成所有推送后，如果我们成功匹配了目标序列中的所有元素（j == n），则记录的操作形成有效的解决方案。 否则的话，那是不可能的。 

### 为什么它有效

 不变的是，在模拟中的任何一点，堆栈准确地表示已被压入但尚未输出的元素集，并且它们的相对顺序由插入时间固定。 每当堆栈顶部与下一个所需输出匹配时，立即删除它总是安全且最佳的，因为离开它只会推迟有效匹配，同时可能会在其上方引入新的阻塞元素。 如果进程以目标序列中不匹配的元素结束，则意味着某些所需元素从未在正确的时间暴露在堆栈顶部，这无法通过重新排序操作来修复。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    
    stack = []
    res = []
    j = 0
    
    for x in a:
        stack.append(x)
        res.append('S')
        
        while stack and j < n and stack[-1] == b[j]:
            stack.pop()
            res.append('C')
            j += 1
    
    if j == n:
        print("YES")
        print("".join(res))
    else:
        print("NO")

if __name__ == "__main__":
    solve()
```实现直接遵循算法。 该堆栈存储所有当前持有的解决方案。 每次推送后，内部循环都会贪婪地删除立即满足下一个所需输出的任何元素。 指针 j 确保我们永远不会跳过或重新排序目标序列。 最终检查确保产生了所有所需的输出； 否则，某些元素会被堆栈排序永久阻止。 

一个微妙的点是重复项是自然处理的。 由于匹配是按值而不是按身份完成的，因此多个相同的值可以互换处理，并且贪婪规则仍然成立，因为正确性仅取决于堆栈顺序，而不取决于唯一性。 

## 工作示例

 ### 示例 1

 输入：

 n = 4

 a = [4, 1, 2, 2]

 b = [1, 2, 4, 2]

 | 步骤| 行动| 堆栈| j | 输出|
 | ---| ---| ---| ---| ---|
 | 1 | 推 4 | [4] | 0 | S |
 | 2 | 推 1 | [4,1]| 0 | SS |
 | 3 | 流行 1 | [4] | 1 | SSC |
 | 4 | 推2 | [4,2]| 1 | SSCS |
 | 5 | 流行 2 | [4] | 2 | 南南服务中心 |
 | 6 | 推2 | [4,2]| 2 | SSCSCS |
 | 7 | 流行 2 | [4] | 3 | SSCSSC |
 | 8 | 流行 4 | []| 4 | SSCSCCSC |

 此跟踪显示每当顶部与目标匹配时立即弹出如何确保不会发生不必要的阻塞。 每次出现匹配时，都会立即解决。 

### 示例 2

 输入：

 n = 3

 a = [2, 3, 1]

 b = [1, 2, 3]

 我们压入2（stack [2]），压入3（stack [2,3]），然后最终必须输出1。然而，1永远不会在正确的时间出现在堆栈顶部； 当 2 和 3 已经阻挡它时，它就来得太晚了。 该过程以堆栈 [2,3,1] 结束，但我们无法在 3 和 2 之前弹出 1，从而无法实现所需的顺序。 

这表明，即使两个序列包含相同的多重集，堆栈约束也会使排序变得不可行。

 ## 边缘情况

 当出现许多相同的值时，就会出现微妙的边缘情况。 该算法仍然表现正确，因为相等比较不依赖于位置，并且每次出现在可行性方面都是无法区分的。 堆栈结构本身就决定了正确性。 

另一种情况是目标序列在推送之前需要一个元素。 在这种情况下，贪婪模拟将推动一切，直到它可以在顶部访问或保持阻塞。 如果它永远不会到达顶部的正确位置，则最终指针 j 将不会到达 n，从而正确地表示不可能。
