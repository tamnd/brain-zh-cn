 ## 解决方案
 ## 问题理解

 我们有同一组朋友的两种排列。 第一个排列`a`是当前顺序，第二个排列`b`是所需的订单。 

单个操作可以选择任何非空的朋友集。 所选择的朋友将从当前位置移除，其相对顺序被颠倒，并且结果序列被放置在最前面。 未被选中的朋友保持其相对顺序。 

例如，如果当前序列是`1 2 3 4 5`我们选择`{2, 4}`，选定的朋友出现为`2, 4`，所以在反转它们并将它们移到前面后，我们得到`4 2 1 3 5`。 

我们不需要最少的操作次数。 我们只需要一些最多 15 个改变的操作序列`a`进入`b`。 输出包含操作数，后跟每个操作中选择的好友号码集。 

价值`n`至多 10000。这足够大，以至于显式尝试排列是不可能的，因为有`n!`可能的订单。 即使考虑一个操作的每个子集也已经给出`2^n - 1`可能性，这是无望的`n = 10000`。 约束的有用部分是 15 次操作的限制。 自从`2^14 = 16384 > 10000`，基于 14 个二元决策的构造就足够了。 

有两种微妙的情况很容易处理不当。 首先，当`n = 1`，只有一种可能的排列。 例如，```text
1
1
1
```已经满足目标，所以正确的输出很简单`0`。 盲目计算的构造`ceil(log2(n))`然后假设至少存在一个操作可能会意外创建无效的空操作。 

其次，保证输入排列包含不同的值。 因此，诸如此类的测试```text
3
1 1 2
1 2 1
```根本不是一个有效的测试用例。 不需要处理重复的值，并且任何依赖于每个朋友都具有唯一目标位置的构造都可以通过输入来证明是合理的。 

另一个边界情况是二的幂。 为了```text
4
4 3 2 1
1 2 3 4
```我们只需要两位来区分所有四个目标位置。 该结构使用四个不同的两位代码，因此不需要额外的操作，因为`n`达到代码空间的容量。 

对于非 2 的幂，例如`n = 5`，我们使用所有八个三位代码的适当顺序中的前五个代码。 未使用的代码根本不属于任何朋友，因此它们对结果排列没有影响。 

## 方法

 直接方法会尝试搜索可能的操作。 有`2^n - 1`可以在一次操作中选择的非空子集。 将一个候选者应用于序列成本`O(n)`如果显式重建序列，那么即使检查所有可能的首次操作成本`O(n 2^n)`。 深度搜索几个级别的情况要糟糕得多，分支因子大致为`2^n`。 对排列进行最短路径搜索也是不可能的，因为状态空间有`n!`州。 

蛮力在概念上是有效的，因为每个合法的举动都在这些子集中明确表示。 它的失败完全是由大量可能的子集和由此产生的排列引起的。 

关键的观察是，可以使用每个朋友的单个二元决策来描述操作。 给每个朋友一点信息，说明该朋友是否参与该行动。 选定的好友将移动到所有未选定的好友之前，选定的部分则相反。 

假设我们执行多个操作并为每个朋友分配一个由其参与位组成的二进制代码。 最终顺序由这些代码决定。 有趣的是，代码的顺序不是普通的二进制顺序。 因为每个选定的组都是相反的，所以自然码排序是反映的格雷码排序。 

为了`k`操作，有`2^k`可能的二进制代码。 如果所有朋友都收到不同的代码，他们原来的订单就变得无关紧要。 我们只需要分配代码，以便操作序列产生所需的目标顺序。 

让`G_k`是通常的二进制反射格雷码序列。 对于三位来说是`000, 001, 011, 010, 110, 111, 101, 100`。 

我们的操作产生的顺序与此顺序相反：`100, 101, 111, 110, 010, 011, 001, 000`。 

目标位置的代码有直接公式`r`:`code[r] = gray(2^k - 1 - r)`，

在哪里`gray(x) = x XOR (x >> 1)`。 

我们按照朋友出现的顺序将这些代码分配给他们`b`。 然后操作`i`准确选择那些分配代码为 bit 的朋友`i`放。 

施工只需`ceil(log2 n)`运营。 自从`n <= 10000`，最多为 14，远低于要求的限制 15。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 |---|---|---|---|
 | 蛮力 |`O(n 2^n)`仅针对一个搜索级别 |`O(n)`每个州| 太慢了 |
 | 最佳|`O(n log n)`|`O(n log n)`直接表示| 已接受 |

 实际实现时只能使用`O(n)`额外的内存，因为每个代码都是在需要时生成的，所以实际的空间使用量甚至比表的一般界限还要小。 

## 算法演练

 1.如果`a`已经等于`b`，输出零运算。 这对于一般结构的正确性来说不是必需的，但它给出了最简单的可能答案和处理`n = 1`自然。 

2. 选择最小的`k`这样`2^k >= n`。 有足够多的不同`k`位代码为每个目标位置提供唯一的代码。 因为`n <= 10000`，我们总是有`k <= 14`。 

3. 对所需排列的位置进行编号`0`通过`n - 1`。 对于职位`r`, 计算`x = 2^k - 1 - r`然后分配代码`x XOR (x >> 1)`。 

这些正是第一个`n`反映格雷码排序的反向二进制码。 

4. 对于每一点`i`从`0`通过`k - 1`，构造一个操作。 扫描目标排列`b`。 如果分配的代码为`b[r]`有位`i`设置，放置朋友`b[r]`投入运行`i`。 

所选朋友号码的打印顺序并不重要。 该操作本身会在反转它们之前恢复它们当前的相对顺序。 

5.输出全部`k`从位开始按递增位顺序进行操作`0`咬`k - 1`。 

这些操作的顺序至关重要。 最后一个操作对最终分组的影响最大，而操作引起的递归反转正是给出逆格雷码顺序的原因。 

### 为什么它有效

 考虑所有`2^k`可能的代码。 第一次操作后，用位编码`0`等于`1`以相反的顺序移到前面，而带有位的代码`0`等于`0`之后留下来。 下一次操作后，按位进行相同的过程`1`，与所选部分相反。 继续这种方式给出递归序列`C_k = 1 + reverse(C_{k-1}), 0 + C_{k-1}`当高位先写入时。 碱基序列为`C_1 = [1, 0]`。 

标准反映格雷码满足`G_k = 0 + G_{k-1}, 1 + reverse(G_{k-1})`。 

反转这个身份给出`reverse(G_k) = 1 + G_{k-1}, 0 + reverse(G_{k-1})`,

 这正是我们的操作生成的序列。 因此不同代码的最终顺序是`reverse(G_k)`。 

我们分配第一个`n`该序列的代码到元素`b`按目标顺序。 因此，经过所有操作后，好友完全按照顺序出现`b`。 由于每个分配的代码都是不同的，因此没有一对朋友需要其原始的相对顺序来打破平局。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def build_operations(a, b):
    n = len(a)

    if a == b:
        return []

    k = 0
    while (1 << k) < n:
        k += 1

    operations = []

    # code[r] is the r-th code in reverse Gray-code order.
    # We only need the codes for the n target positions.
    codes = [0] * n
    full = (1 << k) - 1

    for r in range(n):
        x = full - r
        codes[r] = x ^ (x >> 1)

    for bit in range(k):
        mask = 1 << bit
        selected = []

        for r in range(n):
            if codes[r] & mask:
                selected.append(b[r])

        if selected:
            operations.append(selected)

    return operations

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    operations = build_operations(a, b)

    print(len(operations))
    for op in operations:
        print(len(op), *op)

if __name__ == "__main__":
    solve()
```这`build_operations`函数首先处理已经排序的情况。 这避免了产生不必要的操作，也意味着`n = 1`立即产生零操作。 

循环计算`k`找到能够表示至少的最小位数`n`不同的价值观。 为了`n = 10000`，它停在`k = 14`因为`2^13 = 8192`太小而`2^14 = 16384`就足够了。 

表达式```python
x ^ (x >> 1)
```是标准的二进制到格雷码的转换。 我们使用`full - r`而不是`r`因为所需的排序是相反的格雷码顺序。 

这`codes`数组为每个目标位置存储一个整数。 自从`b[r]`是必须占据目标位置的朋友`r`，代码存储在`r`属于`b[r]`。 

最后的嵌套循环构造实际操作。 操作中选择好友`bit`正是当它的代码设置了该位时。 该操作不需要我们知道好友当前的位置，这是该构建的主要实现优势。 

Python 中不存在整数溢出问题。 即使在具有固定宽度整数的语言中，这里的最大值也如下`2^14`，所以普通的 32 位整数就足够了。 

打印的朋友号码可以以任何顺序出现，因为该语句仅要求子集。 法官使用当前排列重建选定的子序列，然后将其反转。

## 复杂度分析

 | 测量| 复杂性 | 说明|
 |---|---|---|
 | 时间 |`O(n log n)`| 有`k = O(log n)`操作，并且每个操作都会扫描`n`目标位置|
 | 空间|`O(n)`| 代码数组和输出操作最多包含`O(n log n)`最差表示形式的整数，而实现可以直接存储选定的集合 |

 为了`n <= 10000`,`k <= 14`，因此构造最多执行约140000次基本位置检查。 这很容易在给定的 2 秒限制内，并且操作次数严格低于所需的最大值 15。 

## 测试用例

 建设性问题的输出不是唯一的，因此根据一个固定字符串检查输出将是不正确的。 以下测试工具解析生成的操作，模拟它们，并验证最终的排列是否等于`b`。 它还检查每个操作是否为非空，每个朋友每次操作最多选择一次，并且打印的操作不超过 15 个。```python
import sys
import io

def build_operations(a, b):
    n = len(a)

    if a == b:
        return []

    k = 0
    while (1 << k) < n:
        k += 1

    full = (1 << k) - 1
    codes = [0] * n

    for r in range(n):
        x = full - r
        codes[r] = x ^ (x >> 1)

    operations = []

    for bit in range(k):
        mask = 1 << bit
        selected = []

        for r in range(n):
            if codes[r] & mask:
                selected.append(b[r])

        if selected:
            operations.append(selected)

    return operations

def solve_string(inp):
    data = io.StringIO(inp)

    n = int(data.readline())
    a = list(map(int, data.readline().split()))
    b = list(map(int, data.readline().split()))

    operations = build_operations(a, b)

    out = [str(len(operations))]
    for op in operations:
        out.append("{} {}".format(len(op), " ".join(map(str, op))))

    return "\n".join(out) + "\n"

def run(inp: str) -> str:
    return solve_string(inp)

def validate(inp: str):
    lines = inp.strip().splitlines()
    n = int(lines[0])
    a = list(map(int, lines[1].split()))
    b = list(map(int, lines[2].split()))

    output = run(inp)
    tokens = output.split()
    ptr = 0

    k = int(tokens[ptr])
    ptr += 1

    assert 0 <= k <= 15

    current = a[:]

    for _ in range(k):
        c = int(tokens[ptr])
        ptr += 1

        assert 1 <= c <= n

        chosen = list(map(int, tokens[ptr:ptr + c]))
        ptr += c

        assert len(chosen) == c
        assert len(set(chosen)) == c
        assert all(1 <= x <= n for x in chosen)

        chosen_set = set(chosen)

        selected = []
        remaining = []

        for x in current:
            if x in chosen_set:
                selected.append(x)
            else:
                remaining.append(x)

        current = selected[::-1] + remaining

    assert ptr == len(tokens)
    assert current == b

5 4 3 2 1
3 4 5 1 2
"""

sample2 = """\

3 4 7 6 2 5 1
2 6 3 4 5 7 1
"""

validate(sample2)

custom1 = """\

"""

1 2
"""

## 边缘情况

 对于`n = 1`，唯一可能的排列是`[1]`。 自从`a`和`b`必须都包含唯一的值，它们相等并且`build_operations`立即返回一个空列表。 输出是`0`，这是有效的，因为不需要任何操作。 

为了`n = 2`，一点就够了。 逆格雷码序列是`[1, 0]`。 如果目标是`[1, 2]`，朋友`1`接收代码`1`和朋友`2`接收代码`0`。 唯一操作选择好友`1`，无论初始排列如何，都会生成目标顺序。 

为了`n = 4`，两位逆格雷码序列为`[2, 3, 1, 0]`，对应二进制字符串`10, 11, 01, 00`。 所有四个代码都是不同的，因此施工完全在容量边界进行。 无需担心未使用的代码。 

为了`n = 5`，需要三位。 分配的代码是`111, 110, 101, 100, 000`应用公式后按适当的逆格雷排序。 其余三个代码未使用。 它们不会影响任何操作，因为没有朋友拥有它们。 

为了`n = 10000`,`k = 14`因为`2^13 = 8192`是不够的，而`2^14 = 16384`就足够了。 每个朋友都会收到一个唯一的14位代码，因此构建只需要14次操作，将保证金的一次操作限制在15次以内。 

最常见的差一错误是使用`gray(r)`而不是`gray(2^k - 1 - r)`。 前者产生普通的格雷码顺序，而运算则产生相反的顺序。 减去一`2^k`也是必不可少的。 使用`2^k - r`将产生超出预期的值`k`- 第一个位置的位范围。 

另一个常见的错误是从最高位到最低位进行操作。 该构造依赖于以递增的位顺序执行的操作。 最后一个操作反转所有先前操作创建的选定组，而递归反转正是生成反射格雷码结构的原因。 

最后，原来的排列`a`选择操作后，不会出现在代码构造中。 这是故意的。 分配的代码都是不同的，操作顺序迫使每对朋友按照其代码确定的相对顺序进行操作。 初始相对顺序可以影响中间排列，但毕竟不能影响最终顺序`k`运营。
