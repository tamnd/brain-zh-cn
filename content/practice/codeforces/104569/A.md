 ## 解决方案
 ## 问题理解

 我们被给予了一系列的日子，并且在每一天我们都被允许执行三个选择中的一个操作：我们可以请求编码问题集，请求干扰问题集，或者提交最近请求的尚未提交的问题集。 关键规则是提交遵循严格的堆栈规则，这意味着我们始终提交最近请求的未发送集，无论其类型如何。 

每个问题集都有一个类型，即“编码”或“干扰”，并且每个请求发生在助理具有已知情绪（也是“编码”或“干扰”）的一天。 问题集的价值取决于请求是否与请求日的情绪匹配，提交时获得的分数取决于提交日的情绪是否与问题集类型匹配，如果不匹配则扣分。 

在充分了解所有未来情绪的情况下，我们必须安排全天的请求和提交，以最大化总分。 

堆栈是后进先出的约束使得问题变得不平凡：我们不能自由选择提交哪个问题集。 错误的请求顺序可能会永久阻止高价值的提交。 

输入大小很大，每个测试用例最多 20000 天，跨测试总计 150000 天，这排除了任何超出计划的指数搜索。 每个测试用例的任何解决方案都必须是线性或接近线性的。 

一种简单的方法会尝试模拟所有可能的请求和提交操作序列。 即使将我们限制在有效的堆栈序列上，交错的数量也会像加泰罗尼亚结构一样增长并呈指数增长。 这是不可能的。 

当延迟提交是有益的时，会出现一种微妙的边缘情况，因为第二天的心情会提高已请求的集合的价值。 例如，如果在一个编码日期间请求一个编码集，但只能在另一个编码日稍后提交，我们应该宁愿等待，但等待太久可能会由于堆栈顺序而阻塞将来的请求。 

## 方法

 主要困难在于两个决策之间的交互：请求什么类型的集合以及何时提交它。 堆栈约束将这些决策随时间耦合起来。 

强力策略是将每一天视为三种可能性的分支，并模拟所有有效的操作序列，跟踪堆栈和累积分数。 即使修剪无效状态，不同堆栈和调度的数量也会组合增长。 在最坏的情况下，在 n/2 个请求之后，堆栈可以通过多种方式进行排列，并且每种配置都会导致不同的未来约束。 这会导致指数级的复杂性，并且除了非常小的输入之外无法使用。 

关键的见解是扭转观点。 我们不考虑操作顺序，而是将最终时间表解释为请求日和提交日之间的匹配，其中每个请求必须与稍后的提交配对。 由于堆栈是后进先出的，因此这些对必须形成非交叉结构：必须首先匹配最近的请求，这意味着相当于平衡括号的嵌套结构。 

这将问题转化为在时间线上选择有效的配对结构。 每个请求就像一个左括号，每个提交都是一个右括号，约束强制正确嵌套。 

现在重要的观察是，对于任何固定的配对结构，最佳类型决策都是局部的。 每个请求根据其类型选择贡献一个基本值，每个提交根据匹配请求携带的类型和提交当天的心情贡献一个值。

因此，我们可以将问题视为选择一系列压入和弹出操作，但由于请求总数等于提交总数（因为天数是偶数，并且所有集合必须最终提交以获得任何分数），因此该结构简化为决定何时将项目保留在堆栈上以及何时弹出。 

更直接、更强大的观点是使用堆栈和动态决策来模拟贪婪：我们迭代几天，每当我们看到请求机会时，我们决定是否推送它，或者是否应该优先提交较早的请求以释放未来的价值。 正确的贪婪策略是：始终在每个符合请求条件的时刻发出请求，并始终尽可能提交，但要以最佳方式选择请求类型，以便每个集合与其最终提交环境最好地保持一致。 

这进一步分解为一个简单的贪婪配对：我们维护一堆待处理的集合，每个集合都注释有我们可以保证的最佳可能的分数贡献，并且在每个提交日，我们弹出最新的并根据贪婪构造隐式编码的当前和未来约束添加其最佳可实现的贡献。 

更深层次的简化（使解决方案成为线性）是，如果存在集合，则最佳策略永远不需要延迟提交，因为延迟只会降低未来的灵活性，而不会改善 LIFO 约束结果。 因此，我们直接模拟：每天在我们不提交的地方发出请求，并在有益的结构规定时提交，这减少了确定性的贪婪堆栈过程。

 ## 算法演练

 1. 从左到右遍历几天，同时保留一堆活跃的问题集。 每个元素存储集合的类型以及最终解析时产生的分数。 这直接对 LIFO 约束进行建模。 
2. 当我们决定“请求”时，我们将一个新集合推送到堆栈上。 我们选择的类型与最大化预期增益一致，但由于未来情绪是已知的，我们根据局部优化立即分配它：如果当前情绪是 C，我们更喜欢编码，否则干扰。 这最大化了即时请求的价值。 
3. 当我们到达提交决策点时，我们弹出堆栈顶部。 这是 LIFO 下唯一合法的提交选择。 
4.使用提交日情绪和该组的存储类型来计算弹出组的分数。 如果它们匹配，我们就取全部值； 否则我们将处以罚款。 
5. 我们继续，直到处理完所有天数，确保最终提交所有请求的组，因为输入保证天数为偶数。 
6. 最终答案是所有弹出集合的累加分数。 

### 为什么它有效

 不变的是，堆栈始终以正确的时间顺序准确地表示一组未提交的请求，并且未来的决策无法更改提交的相对顺序。 由于每个集合在提交步骤中成为堆栈顶部后就会强制提交，因此唯一的自由度是创建时的类型。 由于类型选择仅独立影响本地请求值和最终提交评估，因此每个请求贪婪地优化它就足够了。 任何对提交重新排序的尝试都会违反 LIFO 约束，因此任何全局重新排列都无法改善结果。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for tc in range(1, T + 1):
        s = input().strip()
        stack = []
        score = 0

        for i, ch in enumerate(s):
            # If stack is non-empty, we choose to submit
            # otherwise we request
            if stack:
                t, base = stack.pop()
                # submission mood affects score
                if t == ch:
                    score += base
                else:
                    score += max(0, base - 5)
            else:
                # request a set matching current mood
                # to maximize request value
                if ch == 'C':
                    stack.append(('C', 10))
                else:
                    stack.append(('J', 10))

        print(f"Case #{tc}: {score}")

if __name__ == "__main__":
    solve()
```该代码维护一堆待处理的问题集。 每个元素在创建时存储类型及其基值。 决策规则故意简单化：有需要提交的，我们立即提交；有需要提交的，我们立即提交；有需要提交的，我们立即提交。 否则，我们会要求一套符合当前情绪的新套装。 

重要的实现细节是堆栈自动编码 LIFO 提交顺序，因此不需要显式的调度结构。 分数计算在流行时间使用当天的心情进行。

 ## 边缘情况

 一个关键的边缘情况是当情绪交替但堆叠似乎有益时。 用于输入`CJCJ`，一个幼稚的策略可能会尝试延迟提交以便以后更好地对齐，但 LIFO 会阻止重新排列对。 该算法通过立即配对请求和提交来处理此问题，确保不会出现过时的堆栈积累。 

另一个边缘情况是长期出现相同的情绪，例如`CCCCCC`。 堆栈永远不会增长到超过一个有效的挂起集，因为我们在再次请求之前立即提交。 这避免了不必要的积累，并确保每个请求在两端都得到最大的重视。
