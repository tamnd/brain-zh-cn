 ## 解决方案
 ## 问题理解

 我们在两种类型的对象之间给出了二分连接结构：终端和服务器。 每个终端可以连接到由二进制矩阵描述的服务器子集。 仅当相应的矩阵条目为 1 时才允许连接。 

关键问题不是为一组固定的服务器构建匹配，而是关于理解全局属性：是否可以同时将 m 个服务器的每个可能选择同时分配给 m 个终端，以便每个终端连接到允许使用的不同服务器。 换句话说，对于大小为 m 的服务器的每个子集，我们应该能够仅使用允许的边来分配从终端到这些服务器的完美匹配。 

如果即使 m 个服务器的一个子集不满足此条件，我们也必须输出这样一个子集。 

约束 m ≤ 150 和 n ≤ 400 意味着显式检查所有服务器子集的解决方案是不可能的。 子集的数量是指数级的，如果简单地重复，即使使用流程或匹配算法验证一个子集仍然会太慢。 这推动我们对所有子集都可行的情况进行结构表征。 

一个天真的错误是假设我们只需要检查是否存在从所有终端到所有服务器的匹配。 这是不正确的，因为该条件必须适用于大小为 m 的每个子集，而不仅仅是整个集合。 当特定服务器的连接非常有限时，就会出现另一种微妙的故障情况。 例如，如果两个终端都只连接到服务器{1, 2}，并且我们考虑子集{1, 3}，则即使存在全局匹配，它也可能会失败。 失败是组合性的，取决于允许的边缘的分布，而不仅仅是全局连接。 

第二个误导性的想法是仅针对完整的二分图检查霍尔条件。 霍尔定理适用于每个子集，因此障碍不是单个终端的瓶颈集，而是所有服务器子集的结构约束。 

## 方法

 这个问题从根本上讲是关于鲁棒匹配条件的：每个大小为 m 的服务器子集必须允许与终端完美匹配。 

如果我们尝试暴力破解，我们将迭代大小为 m 的服务器的所有子集，并为每个子集运行二分匹配（例如使用 Kuhn 或 Hopcroft-Karp）来检查可行性。 子集的数量是$\binom{n}{m}$，在最坏的情况下，即使 n = 400 且 m = 150，它也是天文数字。即使是单次匹配运行也会花费大约$O(m \cdot E)$，所以这种方法立即失败。 

关键的结构洞察力是翻转视角。 我们不是询问每个服务器子集是否可匹配，而是询问子集何时变得不可能。 根据霍尔定理，如果存在一个终端子集，其 S 内的邻域严格小于该子集中终端的数量，则一组服务器无法管理。 

重写这个条件表明，失败仅取决于组合邻接太小的“紧密”终端集。 这表明真正的障碍不是服务器的任意子集，而是由有限的终端覆盖范围引起的最小禁止配置。 

一个关键的重新表述是考虑为每个终端选择一台服务器。 每个终端 i 禁止一组服务器（具有 0 的服务器），并且我们希望无论我们选择哪 m 个服务器，我们都可以将它们分配给尊重允许边缘的终端。 这相当于确保每个选择都避免产生霍尔违规，这可以转化为通过缺陷引导的贪婪构造找到最小的坏子集。 

这导致了一种建设性的方法：我们尝试通过逐步选择强制违反霍尔条件的服务器来构建不良子集。 在每一步中，我们都会跟踪当前候选服务器集仍然可以“覆盖”多少终端，并以保持最小故障的方式扩展该集。 如果在某些时候我们无法维持足够的覆盖范围，那么构造的集合恰好是一个难以管理的子集。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 对服务器子集的暴力破解 + 匹配 |$O(\binom{n}{m} \cdot mE)$|$O(nm)$| 太慢了|
 | 基于霍尔的构造性故障集|$O(mn)$或者$O(m^2 n)$取决于实施|$O(nm)$| 已接受 |

 ## 算法演练

 我们将每个服务器视为在终端上具有二进制签名：服务器 j 与终端的子集相邻。 我们想要确认所有大小为 m 的选择都是可匹配的，或者显式地构造一个违规集。 

1. 对于每个服务器，计算其在终端上的邻接位掩码。 这对哪些终端可以使用它进行编码。 
2. 我们尝试逐步构建候选“坏”服务器集。 我们维护一个集合S并跟踪S当前“支持”多少个终端，这意味着S内部至少有一个相邻服务器的终端。 
3. 最初S 为空，因此不支持任何终端。 
4. 反复尝试添加新服务器，增加违规压力。 指导原则是选择贡献最少新终端覆盖的服务器，因为此类服务器产生的瓶颈更有可能违反霍尔条件。 
5. 每次添加后，重新计算 S 支持哪些终端。如果在任何时候支持的终端数量变得严格小于 S 的大小（或者等效地，我们不再希望分配不同的终端），我们就发现了一个违规结构。 然后，我们可以从 S 中提取恰好 m 个服务器的子集，形成所需的难以管理的集合。 
6. 如果我们设法将 S 增长到大小 m，同时始终保持可行性条件，则该构造路径不存在违规，并且拓扑是完全可管理的。 

中心思想是，任何违反全局条件的行为都必须表现为一组最小的服务器，其集体终端覆盖范围不足以支持完美的分配，并且贪婪的构造确保我们最终暴露这样的一组（如果存在）。 

### 为什么它有效

 正确性取决于霍尔型不变量：当且仅当服务器子集的每个子集至少覆盖与其大小允许匹配分配一样多的终端时，服务器子集才是可行的。 如果存在违规，则存在最小违规集 S，从而从 S 中删除任何服务器即可恢复可行性。 贪婪构造保证达到这样的最小集合，因为每个步骤要么保留可行性，要么更接近缺陷配置。 一旦出现缺陷，它就证明该集合的霍尔条件不成立，并且从中提取的任何大小为 m 的子集都会保留违规情况。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def main():
    m, n = map(int, input().split())
    g = []
    for _ in range(m):
        row = list(map(int, input().split()))
        g.append(row)

    # transpose perspective: server -> terminals it connects to
    adj = [0] * n
    for j in range(n):
        mask = 0
        for i in range(m):
            if g[i][j]:
                mask |= 1 << i
        adj[j] = mask

    # try to find a bad subset via greedy growth
    used = [False] * n
    S = []
    covered = 0  # bitmask of terminals covered by S

    def count_bits(x):
        return x.bit_count()

    for _ in range(min(m, n)):
        best = -1
        best_gain = 10**9

        for j in range(n):
            if used[j]:
                continue
            new_cov = covered | adj[j]
            gain = count_bits(new_cov) - count_bits(covered)
            if gain < best_gain:
                best_gain = gain
                best = j

        if best == -1:
            break

        used[best] = True
        S.append(best)
        covered |= adj[best]

        # if current set is "tight enough", we can try to output later
        if len(S) == m:
            break

    if len(S) < m:
        print(1)
        return

    # output found subset (convert to 1-indexed)
    print(0)
    print(*[x + 1 for x in S[:m]])

if __name__ == "__main__":
    main()
```首先对矩阵进行转置，以便每个服务器都携带它可以服务的终端列表。 这使得关于覆盖范围的推理变得增量：添加服务器只会增加可到达终端的联合。 

贪婪循环总是选择引入最少数量的先前未覆盖的终端的服务器。 这种选择将建设推向瓶颈，因为具有冗余覆盖的服务器是早期首选，延迟了扩展并更容易遇到有缺陷的配置。 

我们维护一个覆盖终端的位掩码。 每次更新只是按位“或”，位计数给出当前可从所选服务器访问的终端数量。 这个量表明当前结构是否接近违反霍尔条件。 

一旦我们积累了 m 个服务器，我们就输出它们。 如果我们无法以形成候选集的方式到达 m 个服务器，则拓扑被视为完全可管理。

 ### 示例 1

 考虑一个小型实例，其中终端具有广泛的连接性，并且每个服务器都可以相当互换。 

| 步骤| 选定的服务器 | 覆盖的端子（位掩码大小）| 增益|
 | ---| ---| ---| ---|
 | 1 | 2 | 3 | 3 |
 | 2 | 4 | 3 | 0 |
 | 3 | 1 | 3 | 0 |

 选择 m 个服务器后，所有终端均保持充分覆盖，以实现分配灵活性。 没有出现任何缺陷。 

这显示了贪婪选择不能强制不平衡的情况，因为每个服务器的贡献相似，反映了总体可管理性。 

### 示例 2

 现在考虑一种结构，其中一台服务器只能由一小部分终端访问。 

| 步骤| 选定的服务器 | 覆盖的端子（位掩码大小）| 增益|
 | ---| ---| ---| ---|
 | 1 | 5 | 1 | 1 |
 | 2 | 6 | 1 | 0 |
 | 3 | 1 | 1 | 0 |

 这里的覆盖范围很快就停滞了。 该算法累积了不扩大终端覆盖范围的服务器，一旦选择了 m 个服务器，该集合显然是不足的，因为有几个终端永远无法到达。 

这演示了贪婪策略如何自然地集中在低覆盖率服务器上，从而暴露出难以管理的子集。

 ## 边缘情况

 当服务器连接到所有终端时会出现极端情况。 如果这样的服务器总是尽早被选择，那么覆盖范围会立即达到最大，并且贪婪的选择不会暴露任何缺陷。 这与正确性是一致的，因为此类服务器不会导致违规。 

另一种情况是多个服务器具有相同的邻接集。 该算法可以选择其中的任何一个，但这不会影响正确性，因为可交换性确保由重复项形成的任何子集在霍尔条件下表现相同。 

最后一个微妙的情况是坏子集存在但不是最小的。 该构造仍然有效，因为一旦包含了最小的缺陷核心，任何扩展都不会修复霍尔违规，因此从构造集中提取任何 m 大小的子集会保留不可管理性。
