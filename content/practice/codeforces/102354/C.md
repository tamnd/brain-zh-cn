 ## 解决方案
 ## 问题理解

 我们按时间顺序处理一系列资金共享事件。 正值意味着向公众账户添加了很多钱。 负值表示借款人要求相应的正金额。 我们必须决定批准哪些请求，以便帐户余额永远不会变成负值。 

在所有有效决策中，首要目标是批准尽可能多的请求。 同样，我们希望最大限度地减少拒绝请求的数量。 当存在多个最佳决策时，任何一个都会被接受。 

每个事件的输出都有一行。 积极的事件总会产生`resupplied`。 对于负面事件，输出表明该请求最终是否被批准或从所选请求集中删除。 

最多可以有 (10^5) 个请求和 (10^5) 个重新供应，因此整个序列最多包含 (2\cdot10^5) 个事件。 尝试许多请求子集的算法是立即不可能的，因为 (2^{100000}) 远远超出了任何实际界限。 即使是 (O(n^2)) 算法，在最坏的情况下也会执行大约 (10^{10}) 次操作，这对于一秒的时间限制来说太多了。 我们基本上需要线性或 (O(n\log n)) 处理。 

这些值本身的大小可以达到 (10^9)，并且可以有 (2\cdot10^5) 个事件，因此总金额可以达到大约 (2\cdot10^{14})。 Python 整数可以安全地处理这个问题，而具有固定宽度整数的语言应该使用 64 位算术。 

当只有当我们稍后删除已接受的较大请求时才可能接受当前请求时，会发生一种微妙的情况。 例如：```
3 1
+5
-3
-4
-2
```最优输出为：```
resupplied
declined
approved
approved
```接受后`-3`，只剩下 2 个单位，所以`-4`不能与其一起接受。 粗心的贪婪算法可能会直接拒绝`-4`，然后也拒绝`-2`因为它只关注当前余额。 更好的决定是用规模 4 的请求替换之前规模 3 的请求。此时批准的请求总数仍为 1，其余 2 个单位可以批准最​​终请求。 

另一个边缘情况是导致余额变为负数的请求本身就是最大的已接受请求。 例如：```
1 1
+3
-5
```唯一正确的输出是：```
resupplied
declined
```暂时接受请求后，算法不得将余额保留为负数。 它应该立即删除最大的已接受请求，这是当前请求。 

第三种情况是请求金额恰好等于可用余额：```
2 1
+5
-5
-1
```正确的输出是：```
resupplied
approved
declined
```一个条件使用`balance <= 0`而不是`balance < 0`会错误地拒绝使用全部余额的请求。 剩余零钱是完全有效的。 

最后，请求之间可以出现多个补给：```
3 2
+2
+3
-4
-1
-1
```前两个请求可以被批准，剩下的钱为零，而最后一个请求必须被拒绝。 独立处理每次补给而不是维持累积平衡的解决方案将做出错误的决定。 

## 方法

 最直接的方法是考虑请求的每个子集。 对于每个子集，我们按时间顺序模拟事件，并检查每个选定的请求是否可以在其位置支付。 在所有可行的子集中，我们保留一个包含最多请求数的子集。 这是正确的，因为每组可能的批准请求都被明确考虑。 

问题是子集的数量。 对于 (n) 个请求，有 (2^n) 个可能的选择，检查一个选择需要 (O(n+m)) 时间。 因此，最坏情况的操作计数是 (O((n+m)2^n))，即使是几十个请求，这也已经是无望的了，更不用说 (10^5) 了。 

关键的观察结果是，每个请求对于我们的目标都具有完全相同的价值：批准任何请求都会为答案做出贡献。 请求之间唯一不同的是它们消耗了多少钱。 

假设在某个时刻，所选择的请求需要的资金多于目前已提供的资金。 我们必须删除至少一项已接受的请求。 由于删除任何一个请求都会使已批准的请求数量减少 1 个，因此最好的修复方法是删除释放最多资金的请求。 删除较大的请求至少为我们提供与删除任何较小的请求一样多的剩余余额，同时花费完全相同的批准成本。 

这自然会导致贪婪策略。 暂时接受每个请求。 如果这样做导致余额为负，请删除当前接受的所有请求中最大的请求。 最大堆可以让我们有效地找到该请求。 

重要的是，较早删除的请求可以由较晚的请求替换。 这就是为什么仅仅拒绝第一个不合适的请求是不够的。 堆使我们能够修改先前的决定，同时保留最大可能数量的已接受请求。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | (O((n+m)2^n)) | (O(n+m)) | 太慢了 |
 | 贪婪最大堆 | (O((n+m)\log n)) | (O(n)) | (O(n)) | 已接受 |

 ## 算法演练

 1. 读取完整的事件序列并创建一个最初不包含每个事件决策的输出数组。 保留一个变量`balance`，最初为零，代表迄今为止处理所有批准的请求后当前可用的资金。 
2. 对于每一个积极的事件，增加其价值`balance`并写`resupplied`为了那个活动。 补给永远不会与其他决策竞争，因此它总是可以立即合并。 
3. 对于每一个负面事件，让`cost`为其绝对值。 通过减去暂时批准请求`cost`从`balance`。 将这个已接受的请求及其位置存储在最大堆中。 
4. 如果结果余额为非负值，则继续批准请求。 当前接受的请求集此时是可行的，因此没有理由删除任何内容。 
5. 如果余额为负，则从堆中移除已接受的成本最大的请求。 将该请求标记为`declined`并将其成本加回到`balance`。 因为所有请求都为目标贡献了一个单位，所以删除最大的请求是最好的修复：每一次可能的删除都会失去一个批准，而最大的请求会返还最多的钱。 
6. 继续完成整个事件序列。 最后，堆中剩余的每个请求都会被批准，而从堆中删除的每个请求都会被拒绝。 输出数组已经记录了每个请求的最终状态，包括暂时接受并随后删除的请求。 

### 为什么它有效

 在处理事件序列的任何前缀之后，堆包含一组可行的已批准请求，其中包含该前缀的所有可行选择中的最大可能数量的请求。 

当新的请求适合时，添加它会使已批准的请求数量增加 1，因此新的请求集对于该前缀来说是最佳的。 当它不适合时，必须删除一些已接受的请求。 每一次可能的删除都会使批准数量减少一，但删除最大的请求会留下最大可能的平衡。 因此，堆包含所有具有最大批准数量的选择中可能最好的可行集。 由于未来的事件仅取决于剩余的资金量和已选择的请求，因此在同等规模的解决方案中保持最大可能的剩余余额永远不会损害未来的可行性。 这保持了整个序列的不变性，并给出了批准请求的全局最佳数量。 

## Python 解决方案```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    total = n + m

    events = [int(input()) for _ in range(total)]

    balance = 0
    heap = []
    answer = [""] * total

    for i, x in enumerate(events):
        if x > 0:
            balance += x
            answer[i] = "resupplied"
        else:
            cost = -x

            balance -= cost
            heapq.heappush(heap, (-cost, i))
            answer[i] = "approved"

            if balance < 0:
                neg_cost, idx = heapq.heappop(heap)
                removed_cost = -neg_cost

                balance += removed_cost
                answer[idx] = "declined"

    sys.stdout.write("\n".join(answer))

if __name__ == "__main__":
    solve()
```这`balance`变量表示所有当前批准的请求后剩下的实际资金。 在做出任何请求决定之前，积极的事件会增加它。 

对于请求，代码首先插入`(-cost, index)`进入Python的最小堆。 否定成本会将最小的堆键变成最大的原始成本，从而有效地给我们一个最大堆。 

请求最初被标记`approved`因为贪心算法需要将其视为候选者。 如果这会产生负余额，则会删除一个请求。 弹出的堆条目告诉我们要拒绝哪个请求以及该决定恢复了多少钱。 

每个堆条目中存储的索引是必要的，因为从堆中删除的请求可能不是当前请求。 如果没有索引，我们可以知道要删除的数量，但无法更新相应的输出行。 

测试是`balance < 0`， 不是`balance <= 0`。 余额为零是有效的，因为最后批准的请求可能会消耗帐户的全部剩余余额。 

Python 中不存在整数溢出问题。 最大可能的累积值约为 (10^{14})，Python 的任意精度整数可以轻松处理。 

输入被读取`sys.stdin.readline`，并且所有输出都组装成一个字符串。 这避免了为最多 (2\cdot10^5) 行执行许多单独的输出操作的开销。

## 复杂度分析

 | 测量 | 复杂性 | 说明|
 | --- | --- | --- |
 | 时间 | (O((n+m)\log n)) | 每个请求都会插入堆中，也可能从堆中删除一次。 |
 | 空间| (O(n+m)) | 事件数组和输出包含整个序列，而堆最多包含 (n) 个请求。 |

 最多有 (2\cdot10^5) 个事件和最多 (10^5) 个堆条目。 每个堆操作的成本为 (O(\log n))，在最坏的情况下大约给出 (2\cdot10^5\log(10^5)) 堆级操作。 这很容易在给定约束的预期复杂性范围内，而强力指数方法是完全不可行的。

 ## 边缘情况

 第一个不明显的情况是替换先前的请求。 为了```
3 1
+5
-3
-4
-2
```补给后余额变为5。 3的请求被接受，剩下2。4的请求被暂时接受，余额为-2。 堆包含大小为 3 和 4 的请求，因此大小 4 的请求实际上被删除，留下大小 3 的请求已批准，余额为 2。然后接受大小 2 的最终请求。 输出是：```
resupplied
approved
declined
approved
```在这种情况下，简单的“拒绝当前请求”规则恰好起作用，但堆公式还可以处理更困难的反向情况，即当前请求小于先前的请求。 

请考虑：```
3 1
+5
-3
-2
-4
```在前两个请求之后，余额为零，堆中包含 3 和 2。暂时接受 4 的请求，产生余额 -4。 最大接受的请求是 4 本身，因此将其删除。 前两项请求仍然获得批准。 输出是：```

declined

+5
-5
-1
```批准后余额为零`-5`，因此不会发生删除。 只有最后的请求被拒绝。 输出是：```
resupplied
approved
declined
```使用`<= 0`在堆修复条件下会错误地删除 size-5 请求。

3 2
+2
+3
-4
-1
-1
```在第一次请求之前余额已达到 5。 批准4的请求后，为1，因此1的请求也被批准，余额变为零。 最终请求无法获得批准。 输出是：```

```该算法只是将每个积极事件累积起来`balance`，因此连续补给不需要特殊处理。

+1000000000

```余额达到(2\cdot10^9)，两个请求都被批准，剩下零。 Python 的整数运算直接处理这些值，堆存储请求成本，无需任何转换或截断。 

最后的微妙之处在于，被拒绝的请求可能已经发生了许多更早的事件。 当堆稍后删除它时，它的输出行必须更改。 这就是每个堆条目存储原始事件索引的原因。 如果没有该索引，算法可以找到正确的请求大小，但无法生成所需的每个事件输出。
