 ## 解决方案
 ## 问题理解

 我们按照写入的确切顺序获得了一系列日志条目。 最初，每个条目都有日期和时间，但日期丢失了，因此仅保留 12 小时时钟时间戳。 

任务是重建可以产生给定序列的尽可能少的不同天数，同时保持条目按时间顺序排列。 

棘手的部分是时间顺序是全局的，而不是每个时间戳字符串。 如果一个日志行接连出现，那么它的真实时刻必须大于或等于前一个日志行。 允许使用相同的时间戳，因为同一分钟内可能会发生多条消息，并且该语句保证每分钟最多 10 个条目。 

时间戳使用 12 小时格式：

 -`12:00 a.m.`是午夜。 
-`12:00 p.m.`是中午了。 
-`01:00 p.m.`24 小时制的时间是 13:00。 

限制很小。 我们最多有 100 个对数行，因此即使是二次解也很容易足够快。 困难不在于性能，而在于正确处理时间转换和日期转换。 

一个常见的错误是错误地处理了时间的特殊作用`12`。 

例如：```
[12:00 a.m.]
[01:00 a.m.]
```午夜必须成为`00:00`， 不是`12:00`。 

另一个简单的错误是假设需要严格增加时间。 相同的时间是有效的，因为同一分钟内可能会发生多个条目。 

例子：```
[05:00 a.m.]
[05:00 a.m.]
```答案依然是`1`。 

当时钟倒退但未跨过 24 小时制的午夜时，会出现更微妙的边缘情况。 

例子：```
[01:13 p.m.]
[01:10 p.m.]
```按 24 小时计算，这是：```
13:13
13:10
```由于时间减少，第二次输入不能在同一天进行。 我们必须在这里开始新的一天。 

另一个危险的情况是中午的过渡。 

例子：```
[11:59 a.m.]
[12:00 p.m.]
```这个数字正在增加，因为`11:59 -> 12:00`。 

但：```
[12:00 p.m.]
[11:59 a.m.]
```必须开始新的一天，因为`12:00 -> 11:59`减少。 

整个问题归结为一个问题：在按顺序扫描日志时，我们有多少次被迫移至第二天？ 

## 方法

 最直接的暴力想法是为每个日志条目分配一个日期编号，并检查完整的序列是否按时间顺序排列。 由于每个条目理论上可能属于许多不同的日子，因此这会变成对许多作业的搜索。 

如果我们尝试每一种可能性，状态空间就会爆炸。 即使每个条目只有两个选择，我们也已经得到了`2^100`，这是无望的。 

蛮力之所以感觉自然，是因为该问题涉及重建丢失的日期。 听起来我们必须明确猜测日期。 但时间条件的结构要简单得多。 

假设我们将每个时间戳转换为从午夜开始的分钟数。 然后每个条目就变成一个整数`0`和`1439`。 

现在考虑两个连续的条目：

 - 如果当前时间大于或等于前一个时间，则它们可能属于同一天。 
- 如果当前时间较小，则此处的日期必须增加。 

该决定没有自由。 时间的减少会迫使新的一天开始，而不减少永远不会从新的一天的开始中受益，因为我们想要最少的天数。 

这一观察结果将问题分解为单个线性扫描。 

我们将所有时间戳转换为 24 小时分钟，然后计算序列减少了多少次。 答案是：```
1 + number_of_decreases
```因为第一个日志条目总是从第一天开始。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(2^n) 或更糟 | O(n) | 太慢了 |
 | 最佳 | O(n) | O(n) | 已接受 |

 ## 算法演练

 1. 阅读所有日志行。 
2. 从每行中提取时间戳。 

时间戳总是出现在方括号内，所以我们只需要前面的子字符串`]`。 
3. 将 12 小时格式转换为 24 小时分钟。 

为了`a.m.`:

 -`12:x a.m.`变成小时`0`。 
- 其他时间保持不变。 

为了`p.m.`:

 -`12:x p.m.`停留`12`。 
- 任何其他时间添加`12`。 

然后计算：```
total_minutes = hour * 60 + minute
```4. 将答案初始化为`1`。 

即使单个日志条目也需要一天的时间。 
5. 扫描连续的时间戳。 

如果当前时间戳小于前一个时间戳，则同一天的时间顺序就变得不可能，因此我们必须开始新的一天。 

将答案增加`1`。 
6. 打印答案。 

### 为什么它有效

 该算法为日志的每个前缀维护尽可能最小的日期分配。 

每当时间减少时，保持同一天就会立即违反时间顺序。 开始新的一天是强制性的。 

只要时间不减少，保持同一天总是有效的，永远不会比创建新的一天更糟糕。 由于我们想要最少的天数，因此添加不必要的一天是没有帮助的。 

由于每个转换都得到最佳且独立的处理，因此最终计数很少。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def to_minutes(s):
    parts = s.split()

    hm = parts[0]
    period = parts[1]

    h, m = map(int, hm.split(':'))

    if period == 'a.m.':
        if h == 12:
            h = 0
    else:
        if h != 12:
            h += 12

    return h * 60 + m

def solve():
    n = int(input())

    times = []

    for _ in range(n):
        line = input().strip()

        end = line.index(']')
        time_str = line[1:end]

        times.append(to_minutes(time_str))

    days = 1

    for i in range(1, n):
        if times[i] < times[i - 1]:
            days += 1

    print(days)

solve()
```第一个重要部分是将 12 小时时间转换为 24 小时分钟。 小时的特殊处理`12`这就是这里的全部困难。 

午夜：```
12:xx a.m. -> 00:xx
```中午：```
12:xx p.m. -> 12:xx
```每隔一个`p.m.`小时收益`12`。 

解析器仅提取括号内的子字符串。 我们完全忽略该消息，因为它对时间顺序没有影响。 

扫描本身很简单。 我们将每个时间戳与前一个时间戳进行比较。 如果时间向后移动，当前条目不能属于同一天，因此我们增加日期计数器。 

比较必须严格`<`， 不是`<=`。 相同的时间戳在同一天有效。 

## 工作示例

 ### 示例 1

 输入：```
5
[05:00 a.m.]: Server is started
[05:00 a.m.]: Rescan initialized
[01:13 p.m.]: Request processed
[01:10 p.m.]: Request processed
[11:40 p.m.]: Rescan completed
```换算时间：

 | 进入| 时间 | 分钟 | 比较| 天|
 | --- | --- | --- | --- | --- |
 | 1 | 上午 05:00 | 300 | 300 开始 | 1 |
 | 2 | 上午 05:00 | 300 | 300 300 >= 300 | 300 >= 300 | 1 |
 | 3 | 下午 01:13 | 793 | 793 793 >= 300 | 1 |
 | 4 | 下午 01:10 | 790 | 790 790 < 793 | 790 < 793 2 |
 | 5 | 晚上 11:40 | 1420 | 1420 1420 >= 790 | 2 |

 最终答案：```
2
```此示例演示了为什么相等的时间戳不能创建新的一天，以及为什么单个后退步骤会强制创建新的一天。

 ## 边缘情况

 考虑重复的时间戳：```
3
[05:00 a.m.]: A
[05:00 a.m.]: B
[05:00 a.m.]: C
```转换后的序列为：```
300, 300, 300
```该算法仅在当前值严格小于前一天时开始新的一天。 既然允许平等，答案仍然是`1`。 

现在考虑午夜处理：```
2
[11:59 p.m.]: A
[12:00 a.m.]: B
```转换变成：```
1439, 0
```自从`0 < 1439`，算法开始新的一天并输出`2`。 

如果午夜被错误地视为小时，则这种情况会失败`12`。 

另一个微妙的情况是中午：```
2
[11:59 a.m.]: A
[12:00 p.m.]: B
```转换变成：```
719, 720
```序列是递增的，所以答案是`1`。 

如果`12:00 p.m.`被错误地转换为`24:00`，逻辑就会被打破。 

最后，考虑多次强制重置：```
4
[03:00 p.m.]: A
[02:00 p.m.]: B
[01:00 p.m.]: C
[12:00 p.m.]: D
```转换后的序列：```
900, 840, 780, 720
```每一步都会减少，因此每一步都需要新的一天。 算法输出`4`，这是最小的，因为没有两个连续的条目可以共享一天。
