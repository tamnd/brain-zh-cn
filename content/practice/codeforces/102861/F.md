 ## 解决方案
 ## 问题理解

 输入是 Fastminton 比赛的时间记录。 每个字符描述了比赛期间发生的一个事件：发球者得分、接收者得分或请求打印当前得分。 程序必须准确地按顺序重播比赛，并以当时比赛的状态回答每个得分请求。 

一场比赛最多包含三场比赛，最先赢得两场比赛的玩家获胜。 在每场比赛中，积分都会累积，直到一名玩家达到获胜条件。 玩家要么获得至少 5 分并领先至少 2 分，要么在达到 10 分时立即获胜。 每得分后，得分的球员将成为下一分的发球员。 第一局从左边发球的选手开始，后面的比赛则从上一局赢得发球的选手开始。 

没有大的数字限制，因为输入只是事件序列。 相关界限是该序列中的字符数。 直接模拟对每个事件处理一次，因此运行时间随着输入大小线性增长。 任何从一开始就为每个查询重复重建匹配状态的方法都会执行不必​​要的重复工作，并且如果存在许多分数公告，则可能会变得二次。 

有几个细节可能会破坏一个简单的实现。 一个常见的错误是忘记了达到 10 分的玩家会立即获胜，即使没有两分优势。 例如，输入`SSSSSSSSSSQ`最终左侧玩家以 10 分赢得比赛，因此输出为`0 (winner) - 0`如果这是第一场比赛并且比赛结束后要求最终比赛得分。 仅检查 5 分和 2 分差异条件的解决方案将错误地保持游戏运行。 

另一个棘手的情况是比分公布后发球的球员。 对于输入`SQ`，左边的玩家获得唯一的分数，并且必须被标记为下一个发球者。 输出是`0 (1*) - 0 (0)`。 将原始服务器保留到下一次集会的解决方案会标记错误的玩家。 

游戏之间的转换也很容易处理不当。 例如，右方选手赢得第一局比赛后，右方选手在第二局比赛中发第一分。 服务器不会重置为左侧玩家。 忘记这条规则会改变所有后来的分数公布。 

## 方法

 最直接的解决办法就是模拟每次集会。 对于每个角色，暴力实现可以维护当前分数、检查游戏是否结束、更新游戏分数并打印请求的状态。 这已经是规则的自然表示，并且它是正确的，因为比赛规则仅取决于当前位置之前发生的事件。 

一个不太仔细的暴力版本可能会处理所有`Q`通过从头开始重播整个输入前缀来重建乐谱。 如果输入包含很多分数请求，并且序列长度为`n`，这可能需要大约`n`每个的操作`n`请求，导致`O(n²)`工作。 

消除这种重复的观察结果是每个事件仅改变匹配状态一次。 未来事件所需的完整信息很少：每个玩家获胜的游戏数量、游戏中当前的分数、当前服务器以及比赛是否已经结束。 由于不需要重新访问旧事件，因此在从左到右扫描时存储此状态就足够了。 

暴力破解之所以有效，是因为规则是确定性的，但当它重新计算已经处理过的信息时，它会失败。 通过观察匹配状态具有恒定大小，我们可以将整个问题简化为单遍模拟。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 蛮力 | O(n²) | O(1) | O(1) | 对于大型事件序列来说太慢 |
 | 最佳| O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 1. 记录左右选手获胜的局数、当前局分以及下一局发球的选手。 最初由左边选手发球，比赛得分和得分均为零。 这些变量描述了可能影响未来事件的一切。 
2. 从左到右读取事件序列中的每个字符。 对于得分事件，确定获得分数的玩家。 如果服务器得分，则服务器获得一分。 如果接球员得分，则另一名球员获得一分。 得分后，让该球员担任下一个发球手，因为记分员总是在下一个回合发球。 
3. 每分完后，检查当前游戏是否结束。 如果玩家至少拥有 5 分并领先至少 2 分，或者达到 10 分，则该玩家获胜。 检查必须在更新总得分后进行，因为最近的拉力赛可能已经完成了比赛。 
4. 当游戏结束时，增加获胜者的游戏次数并将分数重置为零。 如果该游戏让玩家获得两局总胜利，则比赛结束。 否则，已完成游戏的获胜者将成为下一场游戏的服务器。 
5. 当出现分数通知时，打印存储的状态。 如果比赛仍在进行中，则打印两个游戏得分和两个得分，并将服务器标记添加到正确的玩家。 如果比赛结束，则仅打印最终比赛得分并标记获胜者。 

为什么有效：维护的状态正是规则确定下一个事件结果所需的信息。 在处理每个字符之后，变量代表迄今为止看到的所有事件之后的真实匹配情况。 由于每次集会都会应用一次，并且每次游戏转换都直接遵循规则，因此未来的每个分数公告都是从正确的状态生成的。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()

    games = [0, 0]
    points = [0, 0]
    server = 0
    finished = False
    winner = -1

    ans = []

    def game_winner():
        if points[0] >= 10:
            return 0
        if points[1] >= 10:
            return 1
        if points[0] >= 5 and points[0] - points[1] >= 2:
            return 0
        if points[1] >= 5 and points[1] - points[0] >= 2:
            return 1
        return -1

    def current_score():
        if finished:
            if winner == 0:
                return f"{games[0]} (winner) - {games[1]}"
            return f"{games[0]} - {games[1]} (winner)"

        left = str(points[0]) + ("*" if server == 0 else "")
        right = str(points[1]) + ("*" if server == 1 else "")
        return f"{games[0]} ({left}) - {games[1]} ({right})"

    for c in s:
        if c == 'S' or c == 'R':
            if not finished:
                scorer = server if c == 'S' else 1 - server
                points[scorer] += 1
                server = scorer

                w = game_winner()
                if w != -1:
                    games[w] += 1
                    points = [0, 0]
                    if games[w] == 2:
                        finished = True
                        winner = w
                    else:
                        server = w
        else:
            ans.append(current_score())

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```这`games`数组存储比赛得分，而`points`仅存储当前游戏得分。 将这些分开可以避免混合两种不同的获胜条件。 

这`server`变量总是指下一次发球的球员。 在得分事件后立即更新它是必要的，因为得分球员会再次发球，无论他们最初是发球还是接发球。 

这`game_winner`函数在两点规则之前检查 10 点规则。 并非每个状态都需要这种排序，但它使立即结束条件变得明确。 函数返回`-1`当比赛继续进行时。 

当游戏结束时，点数组将被重置。 该代码仅在非决赛后更改服务器，因为在决定比赛获胜者后没有下一场比赛。 

乐谱格式与模拟是分开的。 这可以防止输出细节影响匹配逻辑，并使活动匹配和已完成匹配之间的区别变得清晰。

 ## 边缘情况

 10 分规则是通过在依赖两分优势条件之前检查它来处理的。 对于输入`SSSSSSSSSSQ`，左边玩家达到10分，第一局立即结束，得分请求打印`1 (winner) - 0`。 该算法从不等待更大的领先优势。 

每次对局后的发球转换都是通过将记分员指定为新的发球手来处理的。 对于输入`SQ`，第一个事件给左边的玩家一分，第二个事件打印`0 (1*) - 0 (0)`。 星星出现在左侧，因为记分员负责下一场比赛。 

新游戏开始时使用前一局游戏的获胜者作为服务器。 如果左边玩家赢得第一场比赛并且第二场比赛开始，模拟将保留左边玩家作为服务器，而不是重置为原来的起始玩家。 这遵循匹配状态不变性并防止未来的点分配不正确。 

完成的比赛状态也会被保留。 一旦玩家赢得两场比赛，稍后`Q`events 继续打印最终结果，而不是尝试继续评分。 在知道获胜者后，比赛状态就变得不可变。
