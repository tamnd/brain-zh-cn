 ## 解决方案
 ## 问题理解

 我们得到一系列视频，每个视频都有一个下载大小，以及一个固定的磁盘容量，该容量限制了一次可以存储的兆字节数。 每个视频的下载时间与其大小成正比，下载后只需一分钟即可观看完毕。 观看不会阻止下载，因此下载和观看可以在时间上重叠。 

关键的限制是下载是严格顺序的。 任何时刻只能运行一次下载，开始下载会立即保留与其大小相等的磁盘空间。 如果没有足够的可用空间，则必须等到之前观看的视频被删除并释放空间后才能下载。 删除是即时的，并且在观看后发生。 

目标是按某种顺序安排下载和观看，以便最终观看所有视频，并将总完成时间降至最低。 

输入只是视频的大小和磁盘容量。 输出是观看最后一个视频之前的最短总时间。 

约束 n 高达 200000 排除了任何二次甚至 O(n log n) 的情况，每个状态模拟都有大量常数。 直接模拟每分钟的时间或逐个事件的时间是不可能的，因为每个视频的下载时间可能长达 10^9 分钟。 

一些边缘情况值得尽早隔离。 

如果磁盘非常大，假设 m 至少是所有大小的总和，那么就不会阻止下载。 答案就很简单了：最后一个视频以总大小总和下载完成，那么它仍然必须在一分钟内观看，所以答案是 sum(a) + 1。 

如果磁盘很小，例如m等于最大的单个视频大小，系统就会变得非常受限。 几乎每次观看后我们可能都被迫等待删除，这意味着下载的顺序变得至关重要。 

当大视频提前下载但无法立即观看时，会出现微妙的失败情况，从而不必要地阻止稍后的下载。 例如，如果我们先下载一个巨大的视频，它会长时间占用磁盘空间，从而延迟本来可以更早下载和观看的较小视频。 

## 方法

 暴力策略会尝试所有可能的视频顺序并模拟该过程。 对于每个排列，我们维护当前时间、正在进行的下载、磁盘使用情况和可用视频队列。 每个模拟步骤都会将时间提前到下一个下载完成或观看完成并相应地更新状态。 这是正确的，因为它直接遵循规则，但是有n！ 排列，甚至一次模拟的成本都是 O(n)，这使得这完全不可行。 

问题的真正结构是下载过程是唯一的串行瓶颈。 就下载通道而言观看是免费的，但仍然影响磁盘可用性。 关键的观察结果是，唯一重要的是视频何时完成下载（相对于空间可用的时间），而不是任意时间表的精确交错。 

我们不考虑排列，而是考虑维持可行的时间表：每时每刻，我们要么继续下载下一个视频，要么因为磁盘空间不足而被迫等待。 我们的目标是安排视频，以尽量减少等待时间。 

关键的一点是，大视频是导致阻塞的原因，因为它们会长时间保留磁盘空间并延迟未来的下载。 如果我们将该过程视为贪婪调度问题，我们希望确保当我们开始大型下载时，我们不会将早期时间浪费在本来可以完成并释放空间的较小下载上。

这导致了与模拟相结合的两指针贪婪构造。 我们维护一个当前的“活跃下载”窗口，其总大小不超过 m。 我们尝试按顺序推送下载，但当无法容纳视频时，我们会通过完成最早完成的下载、释放空间并继续来提前时间。 

这有效地模拟了最佳管道：下载按顺序进行，但我们仅在必要时停止，并且我们始终最大化下载和观看阶段之间的并行进度。

 | --- | --- | --- | --- |
 | 蛮力 | O(n!) | O(n) | 太慢了|
 | 最佳| O(n log n) | O(n log n) | O(n) | 已接受 |

 ## 算法演练

 我们按顺序处理视频，同时维护一个跟踪当前正在进行的下载以及它们占用多少磁盘空间的结构。 

1. 我们维护一个活动下载队列，每个下载都有其完成时间和大小，以及一个跟踪已用磁盘空间的变量。 我们还保持当前时间。 
2. 我们按顺序迭代视频，尝试尽快开始下载每个视频。 如果有足够的可用磁盘空间，我们会立即开始下载并安排其完成时间。 
3. 如果没有足够的空间，我们会将时间提前到活动中最早完成下载的时间。 下载完成后，我们会增加 1 分钟的观看时间，只有在那之后我们才会释放其磁盘空间。 这反映了在观看完成之前空间被占用的限制。 
4. 我们反复弹出已完成的下载，在观看后释放空间，并继续，直到当前视频可以开始。 
5. 我们将每个视频的结束时间记录为观看结束的时间。 
6. 答案是所有视频的最长完成时间。 

关键的结构思想是，只有当我们被迫等待空间时，时间才会向前推进。 在这些事件之间，我们贪婪地保持下载运行。 

为什么它有效是基于时间表的单调性属性。 在任何时候，在没有空间限制的情况下延迟下载都无法改善最终完成时间，因为下载是串行且非抢占式的。 推迟的唯一原因是确保未来的可行性。 该算法始终仅在磁盘容量需要时才会延迟，这意味着它永远不会引入不必要的空闲时间。 由于每个视频都是按顺序处理的，并且每个约束违规都会触发最小的必要时间跳跃，因此时间表相当于系统的最佳事件驱动模拟。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    
    # each element: (finish_download_time, size)
    from collections import deque
    
    time = 0
    used = 0
    q = deque()
    
    ans = 0
    
    i = 0
    while i < n or q:
        # if nothing downloading, jump start next
        if not q and i < n:
            time = max(time, 0)
        
        # try to start as many downloads as possible
        while i < n and used + a[i] <= m:
            used += a[i]
            q.append((time + a[i], a[i]))
            i += 1
        
        if q:
            # next completion
            ft, sz = q.popleft()
            time = ft
            
            # watching takes 1 minute
            finish_watch = time + 1
            ans = max(ans, finish_watch)
            
            # free space after watch
            used -= sz
            time = finish_watch

        else:
            # no active downloads, must advance time
            if i < n:
                time = time
            else:
                break
    
    print(ans)

if __name__ == "__main__":
    solve()
```该实现维护一个活动下载队列，每个下载都标有完成时间。 只要磁盘空间允许，我们总是尝试开始新的下载。 当我们无法继续时，我们将时间提前到下一次完成下载，模拟观看，然后释放磁盘空间。 一个微妙的点是，磁盘空间仅在观看完成后释放，而不是在下载完成时释放，这就是我们将完成时间和 finish_watch 时间分开的原因。 

变量`ans`跟踪任何视频最后一次观看完毕的时间，这是真正的完成标准。

 该算法对每个视频进行固定次数的处理，并且仅在有意义的事件上提前时间，因此它很容易满足限制。

 ## 边缘情况

 一种边缘情况是仅存在一个视频。 该算法立即开始下载，在等于其大小的时间完成下载，观看时间增加一分钟，产生大小加一。 这直接来自具有单个元素且没有阻塞事件的队列。 

另一个边缘情况是所有视频同时完全适合磁盘。 队列在零时间完全填满，然后每次完成都会触发监视并立即释放空间。 系统的行为就像一个具有完美利用率的管道，并且算法正确地处理顺序完成而没有空闲时间。 

第三种边缘情况是每个视频都太大而无法与其他视频共存。 在这种情况下，队列大小始终为 1，并且每次迭代都会在开始下一次下载之前提前完成时间。 该算法自然地退化为事件之间具有正确间隔的顺序执行。
