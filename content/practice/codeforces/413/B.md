 ## 解决方案
 ## 问题理解

 我们有一家公司，员工参加几个独立的聊天组。 每个聊天都有预先定义的固定成员资格。 随着时间的推移，日志会记录消息：每个事件都表明特定员工在特定聊天中发帖。 

关键规则很简单但不对称：当某人在聊天中发送消息时，同一聊天的所有其他参与者都会收到一条通知。 发件人在该聊天中不会收到有关自己消息的通知。 

任务是计算每个员工在所有聊天和日志中的所有消息中收到的通知数量。 

输入结构使用 n × m 二进制矩阵描述员工和聊天之间的二分关系，其中 m 非常小（最多 10）。 接下来是多达 200,000 个消息事件的序列。 每个事件都是独立的，并向相关聊天的所有其他成员提供通知。 

这些限制立即表明了重要的不平衡。 员工数量可达20,000人，但聊天数量却很少。 这种不对称性使我们能够避免在所有参与者上天真地模拟每条消息。 仅当每次聊天都很小或事件很少时，每个事件的直接模拟仍然有效，但这里两者都可以很大。 

一个简单的实现是，对于每个事件，扫描所有 n 个员工并检查他们是否属于聊天，从而增加计数器。 这会导致 200,000 个事件乘以 20,000 名员工，在最坏的情况下相当于 40 亿次检查，显然太慢了。 

如果尝试预先计算邻接列表但仍然在完整聊天成员资格上迭代每个事件而不优化重复工作，则会出现一种更微妙的故障模式。 这仍然退化为 O(k · n) 行为。 

打破简单解决方案的边缘情况包括：

 1. 包含几乎所有员工的单个聊天，其中包含许多消息。 每一次活动都需要接触几乎所有员工。 
2.同一聊天中多次重复消息。 任何针对每个事件的完整扫描都会不必要地重复相同的工作。 
3. 属于多个聊天的员工（最多 m = 10）。 如果操作不当，每个事件的每个员工的聊天聚合仍然会变得很重。 

## 方法

 蛮力的想法很简单。 对于每个消息事件 (x, y)，我们查看从 1 到 n 的所有员工 i。 如果员工 i 在聊天 y 中并且 i 不是 x，我们会增加他们的通知计数器。 这是正确的，因为它直接模拟了通知传递的定义。 

然而，在这种方法中，每个事件花费 O(n) 时间。 当 k 达到 2·10^5 且 n 达到 2·10^4 时，这会产生大约 4·10^9 次操作，这远远超出了限制。 

关键的观察是，我们在传播过程中实际上并不关心发送者的身份，除了将他们排除在接收通知之外。 我们可以汇总每个聊天的贡献，而不是迭代每个事件的所有参与者。 

对于每个聊天 y，我们维护其中发送的消息总数。 然后，对于属于聊天 y 的任何员工 i，他们会收到 y 中每条消息的通知，但由我作为发件人的消息除外。 这意味着我们可以将聊天中的消息总数与每个员工在该聊天中作为发件人的次数分开。 

因此，我们维护两条信息：每次聊天的消息总数，以及每个员工每次聊天发送的消息数量。 由于 m 最多为 10，因此存储 n × m 表足够便宜。 

那么每个员工的答案就是他们所属的所有聊天的总和（total_messages_in_chat - messages_sent_by_employee_in_that_chat）。 

这避免了迭代每个事件的所有成员，并将其替换为每个事件的 O(1) 更新。

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 每个事件的暴力扫描所有员工 | O(k·n) | O(k·n) | O(1) | O(1) | 太慢了 |
 | 带计数器的每聊天聚合 | O(k + n·m) | O(k + n·m) | O(n·m) | 已接受 |

 ## 算法演练

 我们利用这样一个事实：聊天是独立的消息容器，并且通知仅取决于成员资格和消息计数。 

1. 读取隶属度矩阵。 对于每个员工 i 和聊天 y，我们存储 i 是否属于 y。 由于 m ≤ 10，这是一个紧凑的布尔表。 
2. 初始化一个大小为m的数组total_chat，用于存储每次聊天发送的消息数量。 
3. 初始化一个数组sent[i][y]来存储我个人在聊天y中发送的消息数量。 
4. 处理每个事件（x，y）。 我们增加total_chat[y]。 我们还增加已发送[x][y]。 这捕获了聊天中的全局活动和发送者的贡献。 
5. 处理完所有事件后，通过迭代所有聊天 y 来计算每个员工 i 的答案。 如果员工 i 属于聊天 y，则将total_chat[y] - sent[i][y] 添加到他们的答案中。 

减法至关重要，因为total_chat[y] 会计算所有消息，但不应将自己的消息通知员工。 

### 为什么它有效

 修复任何员工 i 和任何聊天 y。 聊天 y 中的每条消息都会向 i 贡献一条通知，除非 i 是该消息的发送者。 因此，对于 y 中的所有消息，i 收到的通知总数等于 y 中的消息总数减去 i 在 y 中发送的消息数。 跨聊天独立地求和是有效的，因为来自不同聊天的通知是不相交的事件并且不交互。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())

    # membership[i][j] = 1 if employee i is in chat j
    membership = []
    for _ in range(n):
        membership.append(list(map(int, input().split())))

    total = [0] * m
    sent = [[0] * m for _ in range(n)]

    for _ in range(k):
        x, y = map(int, input().split())
        x -= 1
        y -= 1
        total[y] += 1
        sent[x][y] += 1

    ans = [0] * n

    for i in range(n):
        res = 0
        for j in range(m):
            if membership[i][j]:
                res += total[j] - sent[i][j]
        ans[i] = res

    print(*ans)

if __name__ == "__main__":
    solve()
```会员矩阵被直接读入列表列表中，因此我们可以在 O(1) 中查询聊天参与情况。 这`total`数组跟踪每个聊天的消息量，而`sent`隔离其中有多少消息属于每个员工。 

最后的累积步骤是正确性出现的地方：对于员工所属的每个聊天，我们从全局计数中减去他们自己的贡献。 

一个微妙的点是索引。 输入是从 1 开始的，因此员工索引和聊天索引都会立即递减，以避免以后重复出现相差一的错误。

 ### 示例 1

 输入：```
3 4 5
1 1 1 1
1 0 1 1
1 1 0 0
1 1

```我们跟踪每次聊天的消息总数和每个员工的贡献。 

| 活动 | (x, y) | 总计[聊天] | 已发送[x][聊天] |
 | ---| ---| ---| ---|
 | 1 | (1,1) | [1,0,0,0]| 发送[1][1]=1 |
 | 2 | (3,1) | [2,0,0,0] | 发送[3][1]=1 |
 | 3 | (1,3) | [2,0,1,0] | 发送[1][3]=1 |
 | 4 | (2,4) | [2,0,1,1] | 发送[2][4]=1 |
 | 5 | (3,2) | [2,1,1,1] | 发送[3][2]=1 |

 现在计算每个员工：

 员工 1：聊天 1,2,3,4

 贡献 = (2−1) + (1−0) + (1−1) + (1−0) = 1 + 1 + 0 + 1 = 3

 员工 2：聊天 1,3,4

 贡献= (2−0) + (1−0) + (1−1) = 2 + 1 + 0 = 3

 员工 3：聊天 1,2

 贡献 = (2−1) + (1−1) = 1 + 0 = 1

 输出匹配：```
3 3 1
```此跟踪确认每个聊天的分离正确地避免了每个事件的扩展。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdout
    import sys

    n, m, k = map(int, inp.splitlines()[0].split())
    membership = []
    idx = 1
    for _ in range(n):
        membership.append(list(map(int, inp.splitlines()[idx].split())))
        idx += 1

    total = [0] * m
    sent = [[0] * m for _ in range(n)]

    for line in inp.splitlines()[1+n:]:
        if not line.strip():
            continue
        x, y = map(int, line.split())
        total[y-1] += 1
        sent[x-1][y-1] += 1

    ans = [0] * n
    for i in range(n):
        res = 0
        for j in range(m):
            if membership[i][j]:
                res += total[j] - sent[i][j]
        ans[i] = res

    return " ".join(map(str, ans))

 ## 边缘情况

 几乎每个员工都参与的密集聊天强调需要避免针对每个事件进行扫描。 假设 20,000 名员工都属于一个聊天室，并且有 200,000 条消息。 简单的模拟需要 40 亿次更新。 相反，优化方法对每个事件执行两次增量，并为每个员工执行一次最终减法。 

重复的自我发帖是另一个微妙的案例。 如果一名员工在聊天中发送所有消息，其他所有参与者仍会收到所有通知，但该发件人收到的通知应为零。 公式total_chat-sent自动确保这一点：他们的发送计数与总数匹配，从该聊天中产生零贡献。 

稀疏成员资格的处理很自然，因为最终循环仅考虑成员资格为 1 的聊天，因此避免了不必要的减法。
