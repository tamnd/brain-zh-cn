 ## 解决方案
 ## 问题理解

 两名玩家各自维护一个固定的他们喜欢的游戏排序列表。 他们并不立即知道该选择哪种常见游戏，因此他们会经历一个确定性的交替过程，一次推荐一个他们个人喜欢的游戏，而不重复任何建议。 

这个过程从爱丽丝开始。 轮到她时，她必须从她的列表中推荐一款以前从未推荐过的游戏。 如果鲍勃也喜欢该游戏，则该过程立即结束。 否则，鲍勃会通过从他自己的列表中建议一个新的未使用的游戏来做出回应，而爱丽丝会检查它。 他们像这样不断交替，直到推荐的游戏之一同时属于两个列表。 

我们想要的数量是在最终进入共同游戏之前可以强制提出的最大建议数量，假设两个玩家的行为方式都尽可能延迟这种交叉。 

输入约束很小：每个列表最多有 100 个元素，值也以 100 为界，同时给出最多 1000 个测试用例。 这立即排除了每个测试用例需要的任何超二次方； 即使对每个值进行简单的线性扫描或一些设置操作就足够了。 

一种简单的方法可能会尝试模拟所有可能的建议订单。 这会失败，因为每个玩家都可以选择任何未使用的元素，因此分支会组合爆炸。 即使限制排列，序列的数量也会以 n 和 m 的阶乘方式增长，即使对于 n = m = 100，这也是完全不可行的。 

一个更微妙的错误来自于假设答案仅取决于一个最佳公共元素，例如选择最早或最晚的交叉点。 这还不够，因为最佳策略取决于有多少元素位于两侧交集之外，而不仅仅是交集发生的位置。 

一个小的说明性陷阱是：

 输入：```
1
3 3
1 2 3
3 4 5
```这里唯一的公共元素是 3，并且该过程必须在 3 处结束。任何试图通过选择与交叉点相关的位置来“延迟”的天真的推理都会忽略这样一个事实：所有非公共元素在达到 3 之前都只是浪费的建议。 

## 方法

 关键的观察是，该过程实际上并不是关于每个列表内的排序或策略，因为列表已经是固定的。 唯一的自由是每回合选择哪个未使用的元素，但由于我们正在最大化建议的数量，因此两个玩家总是会通过首先耗尽非共享元素来尽可能地延迟共享元素。 

这意味着我们可以将每个列表分为两部分：Alice 独有的元素、Bob 独有的元素以及两者共享的元素。 令共享集大小为 c，仅限 Alice 的大小为 a，仅限 Bob 的大小为 b。 

每次玩家推荐一款游戏时，如果它不在另一个列表中，它就会消耗一个独特的元素。 最终，一旦双方都用尽了所有独特元素，下一个建议必须是一个公共元素，当它被提出时，该过程立即结束。 

在成功提出任何共同元素之前，最优策略有效地迫使双方所有非共同元素出现在序列中。 因此，过程长度取决于有多少个元素在交集之外加上一个最终成功的建议。 

更准确地说，双方的每个独特元素都会在终止前被建议一次，然后最后一个建议会触发比赛。 

所以答案就变成了：

 总建议 =（仅在 Alice 中的元素数量）+（仅在 Bob 中的元素数量）+ 1。 

由于我们只需要集合运算，因此我们计算交集大小并导出其他所有内容。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 所有选择的暴力模拟| 指数| 指数| 太慢了|
 | 基于集合的独特和常见元素计数 | 每个测试用例 O(n + m) | O(n + m) | 已接受 |

 ## 算法演练

 我们使用集合运算独立地解决每个测试用例。 

1. 读取 Alice 的列表和 Bob 的列表，并将两者转换为集合，这样重复和顺序就不再重要。 这简化了推理，因为只有成员资格才是相关的。 
2. 计算两个集合的交集，它代表两个玩家都喜欢的游戏。 
3. 通过从 Alice 的集合大小中减去交集大小，计算有多少个元素是 Alice 独有的。 这给出了爱丽丝可以建议的所有元素，而无需立即结束游戏。 
4. 对鲍勃执行同样的操作。 
5. 答案是仅限 Alice 的元素、仅限 Bob 的元素以及建议并接受共享游戏的最后一步。 

这种排序有效的原因是，在选择任何共享元素之前，每个非共享元素必须出现在交替过程中的某个时刻，因为两个玩家都被迫避免重复，并且只有在出现共同建议时才终止。 

### 为什么它有效

 在终止之前的任何时刻，该进程只是消耗任一集合中之前未使用的元素。 共享元素是唯一可以结束游戏的元素，因此最大化建议数量相当于尽可能长时间地延迟第一个共享元素。 由于必须在强制任何共享元素之前建议所有非共享元素，因此过程长度是固定的，等于非共享元素总数加上一个终端共享建议。 该不变量不依赖于排序选择。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n, m = map(int, input().split())
    a = set(map(int, input().split()))
    b = set(map(int, input().split()))
    
    common = len(a & b)
    only_a = len(a) - common
    only_b = len(b) - common
    
    print(only_a + only_b + 1)
```该代码使用Python集合来直接计算隶属关系。 十字路口`a & b`提供共享游戏。 从每盘中减去它的大小就可以得出双方独占游戏的数量。 为最终共享游戏添加一个帐户以结束该过程。 

重要的微妙之处在于重复并不重要。 尽管在这个问题中输入列表是严格增加的，但将它们视为集合直接符合“最多建议一次不同游戏”的逻辑。

## 测试用例```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n, m = map(int, input().split())
        a = set(map(int, input().split()))
        b = set(map(int, input().split()))
        common = len(a & b)
        out.append(str(len(a) - common + len(b) - common + 1))
    return "\n".join(out)

 ## 边缘情况

 一种极端情况是所有游戏都是通用的。 在这种情况下，无论先建议什么，游戏都会立即结束。 该公式在两侧给出零个唯一元素加一，产生 1，这与第一个建议已经结束该过程的事实相匹配。 

另一种情况是，只有一侧有许多独特的元素，而另一侧几乎没有。 例如，如果 Alice 有 100 个独特的游戏，而 Bob 只共享一个游戏，则该过程必然会在到达共享游戏之前消耗所有 100 个 Alice-only 元素以及任何 Bob-only 元素。 该解决方案的结构正确地解释了这种不对称性，因为它在添加最终共享动作之前独立对待双方。 

最后一个微妙的情况是共享元素是多个时。 即使这样，也只需要其中一个就可以终止进程，因此单独计算所有共享元素就会过多。 该算法通过将所有共享元素折叠成单个终止事件而不是单独处理它们来避免这种情况。
