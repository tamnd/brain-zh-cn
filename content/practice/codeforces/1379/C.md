 ## 解决方案
 ## 问题理解

 我们正在准确地选择$n$鲜花来自$m$可用类型，其中每种类型可以无限次使用。 每朵花的采摘价值并不是线性的，相反，每种类型的行为都表现为递减的奖励流。 第一种花型$i$贡献$a_i$，并且每多一朵相同类型的花都会贡献$b_i$比上一个多。 所以如果我们采取$x_i$花的类型$i$，贡献是$a_i + (x_i - 1)b_i$什么时候$x_i > 0$，否则为零。 

任务是分发$n$这些相同的选择$m$算术奖励序列使总和最大化。 

约束立即排除任何直接组合分布的计数$x_i$。 自从$n$可以大到$10^9$，我们甚至无法考虑迭代可能的分配。 即使迭代从单一类型中获取的花朵总数也是不可能的。 

所有测试用例的类型数量最多为$10^5$，这表明每个测试用例基于排序或线性扫描是可以接受的，但是任何二次的$m$不是。 

当人们假设在没有结构的情况下贪婪地选择每朵花的边际收益时，就会出现天真的错误。 例如，将每种类型视为独立并在所有类型中重复选择最佳的下一个边际收益将需要一个优先级队列$10^9$的操作，这是不可行的。 

另一个微妙的失败案例出现在$b_i = 0$。 在这种情况下，只有第一朵花很重要，任何假设每种类型收益增加或稳定的贪婪方法，如果不将“第一朵花”贡献与“后续线性尾部”贡献分开，都可能错误地过度分配。 

## 方法

 关键的困难在于每种类型都会贡献凸或线性序列的边际收益：第一个选择给出$a_i$，第二个给出$b_i$，第三个给出$b_i$， 等等。 这表明在第一次选择之后，同一类型的所有剩余贡献都是相同的。 

蛮力公式会尝试所有分布$n$进入$m$桶，本质上是指数级的。 甚至动态规划也结束了$n$是不可能的，因为$n$取决于$10^9$。 

关键的见解是扭转观点：我们不是决定每种类型要采多少朵花，而是考虑整体上选择最佳边际贡献。 

每种类型都会贡献一个排序的增益列表：$$a_i, b_i, b_i, b_i, \dots$$我们想要顶级$n$来自这些序列的并集的值。 

然而，由于它们的大小，我们仍然无法明确地构建这些序列。 该结构拯救了我们：每种类型都变成了前缀决策加上统一的尾部。 

对于固定阈值$x$，我们可以计算至少有多少贡献$x$，并计算它们的总和。 这使得可以对值进行二分搜索$n$-第一个最佳选择。 

一旦我们确定了阈值，我们就可以贪婪地获取高于该阈值的所有贡献，然后用等值的项目填充剩余的插槽。 

中心归约是将一个巨大的选择问题转化为超过阈值的单调计数函数，这正是二分搜索的实现。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | 指数| O(米) | 太慢了 |
 | 最优（二分查找+计数） |$O(m \log V)$| O(1) | O(1) | 已接受 |

 这里$V$是可能的贡献值的范围。 

## 算法演练

 我们将每种花类型视为产生两种贡献：单个特殊值$a_i$以及价值的无限重复$b_i$（在第一次选择之后）。 

1. 对于固定的候选值$x$，计算所有类型的总贡献至少有多少$x$。 这是通过独立检查每种类型来完成的。 

如果$a_i \ge x$，它贡献了1个保证大值。 然后我们还考虑它有多少$b_i$- 值至少为$x$，理论上是无限的，但实际上受到我们需要的选择数量的限制； 我们仔细计算贡献计数，因为我们只需要计数到$n$。 
2. 对于每种类型，计算它至少可以贡献多少个有价值的选择$x$。 如果$b_i \ge x$，然后在取出第一朵花后（如果$a_i \ge x$），该类型的所有后续选择也有效。 否则，它只能贡献很小的有限数量。 

此步骤是作为直接公式而不是模拟来实现的。 
3. 使用二分查找$x$, 顶部中的最小值$n$选定的贡献。 我们在范围内搜索$[0, \max(a_i)]$。 
4.找到阈值后$x$，计算严格大于的贡献总数$x$，并直接将它们的值相加。 
5. 捐款额等于$x$，我们只需要足够的时间来准确地达到$n$项，因为多种类型可能贡献相同的边际价值。 

### 为什么它有效

 所有花类型的边际贡献形成一个多重集，其中在第一次采摘稳定在$b_i$。 函数“至少有多少贡献$x$” 是单调递减的$x$，这保证了二分查找的正确性。 一旦确定了截止值，则始终采用高于该值的所有贡献，并用等值元素以最佳方式填充剩余部分，因此任何重新排列都无法改善结果。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve_case(n, m, arr):
    lo, hi = 0, 10**18

    def count_ge(x):
        cnt = 0
        for a, b in arr:
            if a >= x:
                cnt += 1
            if b >= x:
                cnt += max(0, n - (1 if a >= x else 0))
        return cnt

    def sum_ge(x):
        total = 0
        for a, b in arr:
            if a >= x:
                total += a
                cnt = 1
                if b >= x:
                    cnt += n - 1
                    total += (n - 1) * b
        return total

    for _ in range(60):
        mid = (lo + hi) // 2
        if count_ge(mid) >= n:
            lo = mid
        else:
            hi = mid - 1

    x = lo

    total = 0
    used = 0

    for a, b in arr:
        if a >= x:
            total += a
            used += 1
            if b >= x:
                take = min(n - used, n - 1)
                total += take * b
                used += take

    if used < n:
        total += (n - used) * x

    return total

def main():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        arr = [tuple(map(int, input().split())) for _ in range(m)]
        print(solve_case(n, m, arr))

if __name__ == "__main__":
    main()
```代码首先对阈值进行二分查找$x$，它代表所选中的最小贡献$n$花朵。 帮手`count_ge`估计至少有多少捐款$x$，将每种类型视为贡献类型$a_i$如果它符合条件，然后是有限数量的$b_i$型贡献。 

找到阈值后，第二遍贪婪地构造答案。 首先，所有贡献严格高于或等于$x$以受控的方式跟踪已使用的物品数量。 任何剩余的槽位都填充有值$x$，因为根据构造，未使用的贡献不能超过此阈值。 

一个微妙的点是帽子`n - used`，这可以防止过度计算超出所需总选择大小的类型的贡献。

 ## 边缘情况

 当所有的情况发生时，就会出现关键的边缘情况$b_i = 0$。 在这种情况下，每种类型实际上只提供一朵有用的花。 算法的阈值搜索自然会选择$x$等于$n$第三大$a_i$，第二阶段恰好需要$n$明显的第一朵花，没有尾花。 实现处理这个问题是因为条件`b >= x`所有类型都会失败，除非$x = 0$，防止任何过度计数。 

另一个微妙的情况是当$a_i < b_i$。 这不会破坏结构，因为模型不假设每种类型的序列递减； 它仅使用个人贡献的阈值。 如果$b_i$很大，二分查找会放置$x$因此，计数函数正确地优先考虑了那些重复的收益，因为它们占主导地位$a_i$在第一个比较步骤之后。
