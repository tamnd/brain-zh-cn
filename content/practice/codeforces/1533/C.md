 ## 解决方案
 ## 问题理解

 我们得到了一个圆形排列的糖果，标记为 1 到 n。 每个糖果要么“喜欢”，要么“不喜欢”。 安雅执行确定性过程，将糖果从圆圈中一颗一颗移除。 

每个测试用例的过程都有两个阶段。 首先，如果任何地方至少有一种喜欢的甜食，那么无论她是否喜欢，她都会立即吃1号甜食。 之后，她重复执行相同的运动规则：从顺时针方向剩下的下一个糖果开始，按顺序数出剩余的 k 个糖果，并吃掉她落在的第 k 个糖果。 每次移除后，圆圈都会闭合，下一步总是从刚刚吃过的糖果顺时针方向开始。 

这个过程一直持续到圆圈中不再有喜欢的糖果为止，此时它立即停止。 输出就是总共吃了多少糖果，包括一路上移除的喜欢的和不喜欢的糖果。 

所有测试用例的总 n 最多为 5000 的约束改变了一切。 每次吃甜食花费 O(n) 的模拟是可以接受的，因为所有测试用例的总工作量仍约为几千万次操作。 任何依赖于重型数据结构（如平衡树）的解决方案在这里都是不必要的，但在没有仔细索引的情况下，每一步对数组进行重复的完整重新扫描仍然会变得太慢或容易出现错误。 

一些微妙的边缘情况自然会出现。 

如果根本没有喜欢的糖果，则该过程永远不会真正“正确启动”，并且答案为零，即使规则提到了初步检查。 

如果第一个糖果是唯一喜欢的，那么它会立即被吃掉，并且该过程会立即停止，即使在圈子中仍然可能有更多的步骤。 

另一个棘手的情况是当 k 相对于剩余糖果的数量很大时。 因为计数是绕圈的，所以忘记模运算或忘记排除移除的糖果的实现要么超出范围，要么选择不正确的目标。 

第三个常见的失败是假设我们只关心喜欢的糖果并过滤数组。 这打破了这个过程，因为不喜欢的糖果仍然参与计数并影响所有未来的位置。 

## 方法

 思考这个过程最直接的方法就是从字面上模拟圆。 我们维护当前的活着的糖果列表，并根据规则重复删除元素。 每次移除都需要遍历剩余的圆来找到下一个第 k 个元素。 由于圆圈会随着时间的推移而缩小，因此每次删除最多需要 O(n) 工作量。 

在最坏的情况下，几乎所有糖果都会被吃掉，因此我们执行 O(n) 次移除，每次移除成本为 O(n)，导致每个测试用例的总工作量为 O(n²)。 由于测试的总 n 限制为 5000，这仍然可以接受。 

关键的观察结果是，该过程中没有任何事情需要比线性选择更快的速度。 我们永远不需要查询范围、总和或计数； 我们只需要在不断缩小的循环列表中一步步移动即可。 这意味着一个简单的活动元素数组就足够了，我们可以将其视为循环索引结构。 删除一个元素后，我们从其后继继续，通过从当前活动列表中的该位置前进 k-1 步来找到下一个目标。 

这将问题简化为动态列表上的受控模拟，其中正确性仅取决于维持活动序列中的当前位置。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 无需仔细索引的暴力模拟 | 每次测试 O(n²) | O(n) | 有风险/可能出现 TLE 或 bug |
 | 优化的基于列表的循环模拟 | 总共 O(n²) | O(n) | 已接受 |

 ## 算法演练

我们使用活动索引数组显式模拟圆。 

1. 建立一个清单`alive = [1, 2, ..., n]`代表当前圆。 我们还维护一个指针`idx`显示此列表中的当前位置。 最初`idx = 0`，对应甜蜜1。 
2. 计算最初存在多少个喜欢的糖果。 这让我们可以决定这个过程的开始是否有意义。 
3. 如果至少有一个喜欢的糖果，我们立即删除糖果 1。`idx = 0`，这对应于`alive[0]`。 如果 sweet 1 被喜欢，我们就会减少喜欢的计数器。 
4.删除一个元素后，我们不向后移动或重新开始； 我们保留`idx`在同一位置，现在引用缩减列表中的下一个元素。 
5. 当还剩下喜欢的糖果时，我们重复执行以下操作：

 - 移动`k-1`使用模运算在循环列表中前进：`idx = (idx + k - 1) % len(alive)`。 
- 删除位于`alive[idx]`并根据需要更新喜欢的计数器。 
- 移除后，自然是下一个起始位置`idx`，因为列表已左移并且下一个元素占用该索引。 
6. 一旦没有喜欢的糖果剩余，立即停止。 

### 为什么它有效

 关键的不变量是`alive`始终代表剩余糖果的准确当前顺时针顺序，并且`idx`始终指向该顺序的下一个起始位置。 每个操作要么删除当前元素，要么在循环列表中前进固定的步数，这与问题的顺时针计数剩余糖果的定义完全匹配。 由于除了当前配置之外，没有任何步骤依赖于过去的历史记录，因此该状态完全决定了所有未来的动作，确保了正确性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        s = input().strip()

        alive = list(range(1, n + 1))
        idx = 0

        liked = [c == '1' for c in s]
        liked_cnt = sum(liked)

        eaten = 0

        if liked_cnt == 0:
            print(0)
            continue

        # initial forced eat of 1
        eaten += 1
        if liked[0]:
            liked_cnt -= 1

        # remove index 0
        alive.pop(0)
        liked.pop(0)
        if not alive:
            print(eaten)
            continue

        idx = 0

        while liked_cnt > 0 and alive:
            idx = (idx + k - 1) % len(alive)

            if liked[idx]:
                liked_cnt -= 1

            alive.pop(idx)
            liked.pop(idx)
            eaten += 1

            if idx == len(alive):
                idx = 0

        print(eaten)

if __name__ == "__main__":
    solve()
```该解决方案使用收缩列表直接对循环过程进行编码。 唯一的微妙之处是删除后指针的处理：当删除一个元素时，下一个候选元素自然会转移到相同的索引，除非我们删除了最后一个元素，在这种情况下我们会回绕到零。 

我们还显式地维护一个布尔列表，其中包含哪些糖果被喜欢，这样我们就可以在每次删除时以 O(1) 的时间减少剩余的喜欢计数器。

 ## 边缘情况

 一个关键的边缘情况是第一个糖果是唯一喜欢的糖果。 在这种情况下，算法会立即吃掉位置 1，将喜欢的计数器递减至零，并在任何循环跳跃开始之前停止。 由于每次移除后都会检查停止条件，因此状态会正确崩溃。 

当 k 大于剩余糖果的数量时，会出现另一种边缘情况。 由于索引更新使用模运算，`idx = (idx + k - 1) % len(alive)`，选择正确地环绕多次，而不需要显式重复列表。 这可以防止越界访问并确保与多次物理循环表相同的行为。 

当所有糖果都不受欢迎时，算法会在计算喜欢的元素后立即返回零，从而避免不必要的模拟。
