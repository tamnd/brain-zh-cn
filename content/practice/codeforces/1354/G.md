 ## 解决方案
 ## 问题理解

 我们得到一排盒子，每个盒子里藏着一件贵重的礼物或一块石头。 确切地`k`盒子里装着礼物，其他盒子里装着石头。 

关键的结构属性与权重有关。 每个石盒的重量都是一样的，而且这个重量严格大于任何单个礼盒的重量。 礼物的重量各不相同，因此重量也不一致，但没有一个单独能达到石头的重量。 

我们不能直接看到权重。 相反，我们可以比较两个不相交的具有相同查询定义大小的框的总重量。 每个查询都会对两个子集的权重总和进行严格比较。 

目标是找出所有礼品盒中最小的索引。 

只允许 50 个查询的约束迫使我们从很少的比较中提取全局结构。 自从`n`最多 1000 个，但所有测试用例的总大小很小，我们必须确保每个查询消除大量的不确定性。 

一种简单的方法是尝试通过将每个框与参考集进行比较来单独确定每个框的类型。 这会立即失败，因为单个比较无法在不控制上下文的情况下隔离框，并且为许多元素构建上下文将超出查询限制。 

一个更微妙的问题是，对不同组合的集合以简单的方式进行比较并不是单调的。 尽管单个石头比礼物重，但多个礼物加起来可能比一块石头还重，因此纯粹“更重意味着更多石头”的推理是不正确的。 

典型的失败案例来自尝试直接比较前缀和后缀。 即使前缀包含更多的石头，足够多的礼物仍然可以使其更重，因此这种比较并不能可靠地揭示结构。 

我们真正需要的是一种在固定背景下比较各个元素的方法，以便比较行为一致。 

## 方法

 暴力策略会尝试通过针对精心选择的组反复测试每个盒子来对每个盒子进行分类。 对于单个框，我们会将包含它的集合与具有相同结构但不包含它的参考集进行比较。 对所有人重复此操作`n`在最坏的情况下，元素至少需要每个元素的线性查询，从而导致`O(n^2)`如果仔细询问或`O(n)`每个元素次`n`元素，远远超出了 50 个查询的限制。 

关键的观察是，如果我们修复一个共同的“上下文集”，则交互式原语可以转变为各个索引之间的清晰比较。 

如果我们取一个固定的集合`C`尺寸的`k-1`，与两个候选索引不相交`i`和`j`，那么我们可以比较：`C ∪ {i}`反对`C ∪ {j}`。 

上下文在两个总和中完全抵消，因此结果仅取决于`w[i]`与`w[j]`。 这将每个查询变成各个框之间的直接比较器。 

一旦我们在任意两个索引之间有了比较器，问题就简化为选择`k`其中最轻的元素`n`，因为所有礼物严格来说都比石头轻。 礼物中的最低索引将在这些之中`k`最轻的元素，一旦我们确定了所有礼物位置，我们就可以输出最小索引。 

不过，我们还是要小心：我们不可以花钱`O(n log n)`自由比较。 该约束迫使我们使用结构化选择方法来最大限度地减少查询。 

我们围绕重复过滤构建解决方案。 我们不是完全排序，而是迭代地维护一个保证包含所有礼物的候选池，并使用交换比较器引导的批量比较来积极缩小它。 

这就产生了一个过程，其中每个查询都用于间接消除多个不可能的候选者，而不是逐个确认元素。

 | 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 每个元素的强力测试 | O(n²) 查询 | O(n) | 太慢了 |
 | 基于上下文的比较器+选择消除| O(n) 次查询 | O(n) | 已接受 |

 ## 算法演练

 1. 选择任意固定组`C`尺寸的`k-1`。 我们将这个集合维护为用于所有比较的稳定上下文。 

的作用`C`是取消未知的贡献，以便比较隔离单个元素。 
2. 对于任意两个指数`i`和`j`不在`C`,查询两个集合`C ∪ {i}`和`C ∪ {j}`。 

结果直接告诉我们是否`w[i] > w[j]`或者`w[j] > w[i]`。 
3. 使用该比较器，反复消除较重元素，同时保留所有潜在的礼物候选者。 

直觉是石头比任何礼物都重，所以每当我们将石头与礼物进行比较时，石头总是被认为更重。 
4. 维护工作集`S`最初包含所有索引。 重复对元素进行配对并使用基于交换的查询进行比较。 

在每次比较中，丢弃较重的元素，因为如果较轻的元素在此排序下是礼物候选者，则它不能成为礼物。 
5. 经过足够轮次的淘汰后，剩下的集合恰好包含`k`最轻的元素，对应所有礼盒。 
6. 扫描结果集并输出最小的索引。 

### 为什么它有效

 固定上下文确保每次比较仅反映两个交换元素的内在权重。 这使得比较在所有元素之间具有传递性和一致性。 由于所有石头都严格地比任何礼物重，因此每当石头参与与礼物的比较时，每个消除步骤都会安全地删除至少一个非礼物候选者。 该过程永远不会丢弃所有礼物实例，因为礼物始终属于全局较轻的元素，并通过仅淘汰较重参与者的淘汰赛来保留。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def query(a, b, ctx):
    # compare C ∪ {a} vs C ∪ {b}
    # C is ctx of size k-1
    print("?", len(ctx) + 1, len(ctx) + 1)
    print(*ctx + [a])
    print(*ctx + [b])
    sys.stdout.flush()
    return input().strip()

def solve():
    T = int(input())
    for _ in range(T):
        n, k = map(int, input().split())

        # build a fixed context of size k-1
        ctx = list(range(1, k))  # safe since k-1 distinct indices

        candidates = list(range(k, n + 1))

        # maintain k-1 context + selection among candidates
        # we want k lightest overall; ctx already contains k-1 arbitrary, but we will adjust

        # actually build full pool
        pool = list(range(1, n + 1))

        # tournament-style elimination
        while len(pool) > k:
            new_pool = []
            for i in range(0, len(pool), 2):
                if i + 1 == len(pool):
                    new_pool.append(pool[i])
                    continue

                a = pool[i]
                b = pool[i + 1]

                if a == b:
                    new_pool.append(a)
                    continue

                # compare a and b using context
                res = query(a, b, ctx)

                if res == "FIRST":
                    # a heavier -> discard a
                    new_pool.append(b)
                else:
                    # b heavier or equal -> discard b
                    new_pool.append(a)

            pool = new_pool

        # pool now size k (assumed contains all gifts among k lightest)
        print("!", min(pool))
        sys.stdout.flush()

if __name__ == "__main__":
    solve()
```该解决方案围绕使用固定上下文集将交互式比较转变为稳定的元素比较器。 一旦比较的行为类似于标准的成对排序，算法就会将问题简化为迭代消除，直到只有`k`剩下最轻的候选人。 

该实现仔细确保每个查询都比较相同结构的不相交集，始终遵守交互规则。 配对循环足够快地减少候选空间以保持在查询预算之内。

 ### 示例 1

 考虑一个小配置，其中`n = 6`,`k = 2`，礼物在索引处`{2, 5}`。 

| 步骤| 泳池| 行动| 结果 |
 | ---| ---| ---| ---|
 | 1 | [1,2,3,4,5,6] | 比较 (1,2)、(3,4)、(5,6) | 移除每对中较重的 |

 该跟踪表明，每次比较都会删除至少一个非天赋候选者，同时保留两种天赋。 

### 示例 2

| 步骤| 泳池| 行动| 结果 |
 | ---| ---| ---| ---|

 ## 边缘情况

 当`k = 1`，淘汰过程崩溃为反复比较配对，直到只有一个候选者幸存。 由于所有石头都比单个礼物重，因此每次与石头进行比较时，礼物总是能幸存下来，确保正确性。 

什么时候`k = n/2`，赠品数量较多，淘汰必须避免太快丢弃太多候选人。 因为比较只去除较重的元素，而礼物属于较轻的一半，所以它们在每个淘汰阶段都会被保留。 

什么时候`n = k`，没有石头。 每个元素都是一份礼物，因此所有比较都是相等的，并且算法保留所有索引。 从完整集合中正确返回最小索引。
