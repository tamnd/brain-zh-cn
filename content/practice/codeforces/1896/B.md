 ## 解决方案
 ## 问题理解

 我们得到一个仅由两个字符 A 和 B 组成的字符串，可以将其视为一行相邻的图块。 唯一允许的移动是选择一个 A 紧跟着 B 的位置，然后交换它们，使 A 向右移动一步。 两个字符之间的每个位置最多可以用作交换位置一次，但交换可以按任何顺序应用，并且字符串会随着交换的执行而演变。 

任务是确定在整个过程中可以执行的此类交换的最大数量。 

所有测试用例的长度总和至多为 2⋅10^5 的约束立即表明每个测试用例的 O(n²) 模拟太慢。 每个测试用例的任何解决方案都必须基本上是线性的或接近线性的。 

一个关键的微妙之处是交换会改变字符串，因此局部贪婪决策可能会影响在同一索引处是否可以进行另一次交换。 另一个陷阱是假设计算“AB”的初始出现次数就足够了。 例如，在ABAB中，在位置1交换后，我们得到BAAB，它在最初不存在的不同位置创建一个新的“AB”。 

第二种微妙的情况是当将 A“移动”到 B 的长块上时。 例如，在ABBBBA中，一个A可能与多个边界交互，但每个索引只能使用一次，这防止了无限冒泡。 

核心困难在于交换不是独立的：它们消耗位置，但字符串配置的演变方式可以在其他地方启用新的交换。 

## 方法

 暴力模拟将重复扫描字符串，找到 AB 存在且尚未使用的任何索引 i，应用交换，然后重复，直到没有剩余移动为止。 每次交换都需要 O(n) 来找到下一个有效操作，并且在病态情况下可能会发生最多 O(n²) 交换，从而在幼稚的实现中给出 O(n³) 总行为。 即使进行了仔细的记账，维持一组动态的有效头寸仍然是昂贵的，因为掉期在本地创造和破坏机会。 

关键的观察是我们实际上不需要模拟弦的演化。 每次交换对应于一​​个A在一个边界处跨越一个B，并且每个边界索引最多可以使用一次。 我们不考虑改变琴弦，而是跟踪可以实现哪些潜在的“交叉”。 

如果我们将每个 A 解释为可以在 B 上向右移动的东西，那么每次交换本质上都是解决局部反转 AB → BA。 然而，一旦在索引 i 处发生交换，该边界就会永久耗尽，因此该结构更接近于在不断演化的邻接图中选择不相交的有效 AB 转换。 

关键的简化是认识到该过程相当于重复消耗可用的 AB 边界，但只有当 A 向右移动穿过 B 时才会出现新的 AB 边界。这会产生类似流的效果，其中每个 A 可以与多个 B 块配对，但每个索引只能使用一次。 捕获此问题的正确方法是从左到右处理，同时保持有多少 A “可用于左侧”以消耗 B 转换。 

我们维护仍然可以向右移动的活跃 A 的计数。 每次我们看到 B 时，它都可能与其左侧的 A 之一进行交换，但前提是存在未使用的边界。 每个 B 有效地代表了一个可用 A 贡献的潜在消耗，并且每个成功的配对对应于一个有效操作。 

这导致了贪婪扫描，我们积累 A，并在遇到 B 时消耗它们，确保每次交互对应于唯一的索引使用。

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | --- | --- | --- | --- |
 | 暴力模拟| O(n2) 到 O(n3) | O(n) | 太慢了 |
 | 贪婪扫描计数交互 | O(n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们从左到右处理字符串，并维护当前有多少个 A 可参与未来的交换。 

1.初始化一个计数器`available_A = 0`和一个答案`ops = 0`。 
2. 从左到右扫描字符。 
3.当我们看到一个`A`，我们增加`available_A`1。这代表 A 可能会直接越过未来的 B。 
4.当我们看到一个`B`，我们检查其左侧是否有可用的 A。 如果`available_A > 0`，我们执行一项操作：我们将这个 B 与一个可用的 A 进行匹配，增量`ops`加 1，然后递减`available_A`。 

直觉是，每次成功的匹配都对应于 A 跨越 B 边界的一次交换。 

1. 继续直到字符串末尾。 
2. 输出`ops`。 

总是将 B 与最早可用的 A 进行匹配的贪婪选择是安全的，因为左侧的任何 A 在对未来交换的贡献方面都是可互换的。 延迟比赛不会增加未来比赛的数量，因为每个 B 在有利的配对中最多可以使用一次。 

### 为什么它有效

 在扫描过程中的任意一点，`available_A`表示仍然有未使用潜力参与与其右侧 B 互换的 A 数量。 每次我们通过 B 消耗一个时，我们都致力于一次不同的索引级交互。 由于每次成功的操作都会永久消耗左侧 A 容量的一个单位和一个 B 位置，因此除了以受控方式降低可用性之外，任何操作都不会干扰其他操作。 这维护了可能交换的单调计算，确保每个计数操作对应于某个可实现序列中的有效且不同的 AB 交换位置。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = input().strip()

        available_A = 0
        ops = 0

        for ch in s:
            if ch == 'A':
                available_A += 1
            else:
                if available_A > 0:
                    available_A -= 1
                    ops += 1

        print(ops)

if __name__ == "__main__":
    solve()
```该解决方案的结构围绕每个测试用例一次通过。 我们维护的唯一状态是当前有多少 A 可用于未来的交换以及我们已经计算了多少交换。 

关键的实现细节是我们从不显式模拟交换或修改字符串。 这避免了任何不正确的连锁反应或丢失新创建的 AB 对的风险。 扫描顺序保证每个 B 只考虑严格位于其左侧的 A，这与允许操作的方向性质相匹配。

 ## 边缘情况

 一个微妙的边缘情况是所有 A 都在左侧而所有 B 都在右侧，例如`AAABBB`。 该算法首先处理所有 A，累加`available_A = 3`，然后在 B 出现时消耗它们，产生 3 个操作。 这与每个 B 可以与较早的 A 配对这一事实相符。 

另一个极端情况是 A 和 B 频繁交替。 例子`ABABAB`表明贪婪匹配仍然会成功，因为如果可能的话，每个 B 都会立即消耗一个可用的 A，并且稍后会正确考虑新出现的 A。 

最后的边缘情况是 B 的前缀后跟 A，例如`BBBAAA`。 由于遇到 B 时没有可用的 A，因此根本无法进行任何操作，并且由于方向限制，后来的 A 无法追溯影响先前的 B。
