 ## 解决方案
 ## 问题理解

 我们得到了四个非负整数，描述了我们拥有四种类型 A、B、C 和 D 的项目数量。我们希望从这些项目中组装相同的“集合”，并且每个集合必须是三种固定模式之一：

 一种模式消耗两项 A 项目、一项 B 项目和一项 C 项目。 另一个消耗两个 A 项目和两个 C 项目。 第三个消耗一件 A 物品、一件 B 物品、两件 C 物品和一件 D 物品。 

任务不是明确地构建集合，而是确定可以从 A、B、C 和 D 的可用供应中形成的集合的最大数量。 

该问题有趣的部分是这三种集类型在资源使用方面严重重叠。 特别是，A 和 C 在所有结构中共享，B 在其中两个结构中使用，而 D 仅出现在一个结构中。 这会产生耦合约束，而不是独立的资源消耗。 

这些约束意味着我们需要一个在每个测试用例中以大致线性或对数时间运行的算法。 对集合类型的所有可能分布进行强力搜索将导致组合爆炸，因为每个集合都可以分配三种模式之一，从而导致集合数量呈指数分支。 对于除非常小的总数之外的任何事情来说，这是完全不可行的。 

天真的贪婪方法也会失败，因为关于是否将资源花费在一种模式与另一种模式上的早期决策可能会阻碍未来更有利可图的配置。 

当 A 相对于 B 和 C 极其丰富时，就会出现微妙的边缘情况。例如，如果 B 和 C 都是 5，而 A 是 100，则限制因素显然是 B 和 C，我们可以形成 10 个集合。 然而，如果 A 只有 8，则不同结构之间共享 A 之间的交互可能会以不明显的方式减少可实现的集合数量。 当 D 稀缺时，会出现另一种边缘情况，这仅限制一种构造类型，但仍间接影响最佳混合。 

## 方法

 直接的暴力策略将尝试确定每个集合的类型是一、二还是三，然后模拟资源消耗。 如果我们尝试构建 k 个集合，这就会变成将 k 的所有组合分为三个类别的搜索，其数量级为 O(3^k)。 即使进行了修剪，状态空间仍然太大，因为 k 本身可能很大（在典型的 Codeforces 设置中约为 10^5）。 

关键的见解是将视角从单个集合转移到对中间资源转换的推理。 本教程引入了一个有用的抽象：资源配对可以被视为组合成集合的中间“单元”。 如果我们定义概念对类型，例如 AB、AC 和 BCD，那么每个最终集合都会成为这些中间单元的组合。 这减少了从集合的组合构造到线性约束下中间构建块的分配的问题。 

一旦这种转换被接受，形成 k 集的可行性就减少为检查我们是否可以从 A、B、C 和 D 生成足够的中间结构。然后，问题变成分段线性，具体取决于 A 是否足够丰富以支持 B 和 C 之间的所有必要配对。 

这导致对固定 k 进行简单的可行性检查，然后我们可以二分查找最大 k。 

| 方法| 时间复杂度| 空间复杂度| 判决 |
 | ---| ---| ---| ---|
 | 蛮力 | O(3^k) | O(3^k) | O(k) | 太慢了|
 | 最优（二分查找+贪心可行性） | O(log n) | O(1) | O(1) | 已接受 |

 ## 算法演练

 我们检查给定数量的集合 k 是否可以实现。 

设 a、b、c、d 为 A、B、C、D 的可用计数。 

1. 首先，考虑 A 相对于 B 和 C 足够大的情况，特别是当 b + c ≤ a 时。

在这种情况下，A 不是瓶颈。 每个 B 和 C 都可以在需要时与 A 配对，因此限制因素只是有多少 B 和 C 项目参与构建。 最大集合数为 b + c，因此当 k ≤ b + c 时 k 是可行的。 
2. 如果b + c > a，则A 成为瓶颈资源。 我们不能自由地将 A 分配给每个可能的配对，因此在形成 AB 型和 AC 型组件之间需要进行一些协调。 

我们从概念上尝试形成尽可能多的有用的 AB 和 AC 配对，但超出 A 支持范围的每个单元都迫使我们做出妥协。 这会造成不可避免的灵活性损失，由 (b + c − a) / 2 量化，它衡量有多少“额外”的 B 和 C 项目无法与 A 独立配对。 

在这种情况下，D 也限制了系统，因为它只能用于需要 BCD 结构的构造。 因此，D 直接限制了可以存在的此类复合结构的数量。 

最终可行的集合数由 b、c、d 和有效剩余调整界限 (b + c − a) / 2 中最紧的一个决定，并且我们要求它至少为 k − a，因为部分解决方案空间已经被 A 驱动的灵活性所消耗。 
3. 我们使用上述两种情况来评估条件，以确定 k 是否可以实现。 
4. 为了找到最大 k，我们对答案空间从 0 到安全上限（例如 a + b + c + d）进行二分搜索。 

### 为什么它有效

 核心不变量是，每个有效的构造都可以通过将共享的 A 和 C 资源分配到中间配对来表示，并且一旦 A 饱和，通过平衡多余的 B 和 C 消耗来完全捕获剩余的灵活性。 分段条件将 A 不具有约束力的机制与 A 强制 B 和 C 分配之间的耦合机制区分开来。 由于所有约束在每个机制中都简化为线性不等式，因此可行性测试在 k 中是单调的，这证明了二分搜索的合理性。 

## Python 解决方案```python
import sys
input = sys.stdin.readline

def can(a, b, c, d, k):
    # case 1: A is not limiting
    if b + c <= a:
        return k <= b + c

    # case 2: A is limiting
    # remaining flexibility after using A
    extra = b + c - a

    # after saturation, effective constraints
    limit = min(b, c, d, extra // 2)

    # a units are "easy" part in transformation view
    return k <= a + limit

def solve():
    a, b, c, d = map(int, input().split())

    lo, hi = 0, a + b + c + d
    ans = 0

    while lo <= hi:
        mid = (lo + hi) // 2
        if can(a, b, c, d, mid):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    print(ans)

if __name__ == "__main__":
    solve()
```该解决方案将可行性检查分离为单个函数，然后使用二分搜索来查找可实现的最大 k。 可行性函数编码了两种结构机制：A 是否足够丰富以解耦 B 和 C，或者 A 是否成为强制耦合校正的限制资源。 

一个常见的实现陷阱是忘记了与 a 相比，转换点恰好是 b + c。 另一个微妙的问题是剩余项中的整数除法； 必须是楼层划分，因为剩余的 B 和 C 对只能用于完整组合。

 ### 示例 1

```我们测试 k = 6 的可行性。 

| 步骤| 状况 | 结果 |
 | ---| ---| ---|
 | b + c ≤ a | 7 ≤ 5 | 没有 |

 这显示了一种混合机制，其中 A 不足，但剩余配对仍然允许有限的额外结构。

| 步骤| 状况 | 结果 |

def run(inp: str) -> str:

    import sys as _sys
    input = _sys.stdin.readline

    def can(a, b, c, d, k):
        if b + c <= a:
            return k <= b + c
        extra = b + c - a
        return k <= a + min(b, c, d, extra // 2)

            if can(a, b, c, d, mid):
                ans = mid
                lo = mid + 1
            else:
                hi = mid - 1
        return str(ans)

    return solve()

 ## 边缘情况

 当所有计数都为零时，算法立即落入第一种状态，因为 b + c ≤ a 保持为 0 ≤ 0。可行性检查正确返回无法形成任何集合。 

当仅存在 A 时，例如 a = 10 且 b = c = d = 0，我们再次满足 b + c ≤ a，但界限 b + c 为零，因此答案正确为零。 任何假设 A 单独可以对集合做出贡献的贪心方法都会错误地多算。 

当 A 与其他情况相比非常大时，例如 a = 100 和 b = c = d = 1，则适用第一种情况，答案变为 b + c = 2。这表明，除非 B 和 C 也可扩展，否则 D 没有帮助，如果尝试优先考虑基于 D 的构造，则幼稚的实现可能会错过这一点。
